# 抽象协议设计插件（protocol）

两条领域事实、两个工具、一张视图、一条只读路由：模型可以提出一个协议（名字、标题、
目的、消息序列），让参与者加入；不同参与者达到两个，协议才算**成立**。名册 #43
「抽象协议设计（L4）」的能力包。

## 它交什么

| 面 | 交出物 | 谁用 |
|---|---|---|
| 工具 | `protocol_propose(name, title, purpose, messages)` / `protocol_join(name, participant)` | 模型（经工具面调用） |
| 行为 | 一次成功提案 / 加入 ⇒ 一条领域事实草稿 | 宿主唯一的写口（I-1，D-213） |
| 事实 | `protocol.proposed` / `protocol.joined`，格位 `domain × asserted` | 写闸按声明校验名字与格位；`seal` 按归宿行判它有没有人看护 |
| 视图 | `protocol.catalog` → `{ count, observations, by_status, protocols }` | 本包私有的折叠；外部第二方走 `catalog` 路由（不按视图名读） |
| 路由 | `protocol/catalog`（**只读**） | 第二方：网关 `/invoke` 或另一个实例 |

**没有配置、没有 VDFS 挂载点、没有新端口。**

## 「协议需要第二方」怎么落

提案只来自一方，**不算成立**。视图按**不同参与者**计数：

- 1 个参与者 ⇒ `draft`；
- 2 个及以上 ⇒ `established`。

`participants` 按不同值去重，顺序按首次加入；`by_status` 只统计当前状态。
加入一个没有被提出的名字不产生条目——协议必须先被提出。

## 为什么需要一条路由

前三条同类能力（#35 / #40 / #41）的读方都住在宿主里；协议的第二个读方是**另一个
实例或另一个代理**，不该被迫链接本 crate 才能问「现在有哪些协议、成立没有」。一条
只读路由是最小的跨实例读入口，且不需要给对方任何类型。

路由与视图调用**同一个**折叠函数：两边看到的成立状态不会分叉。

## 路由为什么只读

写口只有一个（I-1，D-213）：路由拿事实源读现状，不拿它写。加入仍走工具与行为端口，
于是「谁写的」在转写里有 `produced_by`，不需要再给路由开一条旁路。

网关的 `/invoke` 只带 metadata，不含装配层下发的 `FACT_SOURCE`；路由因此先取该句柄，
取不到再按 `session_id` 走已登记的事实源开面——两条路都只读，读到的是同一份事实。

## 名字、幂等与幂等键

- 协议名：小写字母开头、只含 `[a-z0-9_]`、3–40 字符；
- 参与者：非空、最长 64 字符；
- 幂等键 = 轮锚 + 调用 id + 协议名（加入再带参与者）：同一次调用重放不会记两次，
  再提案 / 再加入各自成键；
- **不设执行前拒绝**：同名再提案按后写覆盖（标题或消息序列可以不同），重复加入由视图
  按参与者去重——都不是错误；
- 空标题 / 空目的 / 空消息序列 / 非法名字在工具与行为两层都拒。
