# 会话上下文压缩设计

> 目标：**保持与大模型的会话持续不中断**——上下文永不因膨胀而失败，且压缩后模型仍能无缝继续工作。
>
> 本文是**设计层总览**：分层机制、优先取舍、不变量。具体实现（文件位置、函数、常量定义、代码细节）见 `../README.md` 五大策略——那是唯一实现事实源。

## 四个核心问题

1. 多轮会话轮次太多后，如何有效压缩或淡化？
2. 单轮响应内工具调用次数太多后，如何有效压缩？
3. 单轮工具调用与多轮会话之间的优先关系及取舍？
4. 主动压缩机制（启用工具，由模型自己决定时机）？

---

## 0. 总原则

1. **确定性优先**：能用纯本地规则解决的（截断、存档、整轮切窗）绝不花 LLM 调用；语义压缩（LLM 摘要）只做兜底。
2. **不改写投影正文**：发给模型的对话体是**事实网格的纯投影**
 （[D-048a](../README.md "symbio/src/plugins/session/README")）——模型看到的每条历史都必须能在网格里
 找到**逐字相同**的出处。因此治理只允许三种动作：**写入时就裁**（L0，网格里存的就是裁后的那一份）、
 **换基**（L5/L6 写一格快照事实，旧事件移入归档段）、**丢整轮**（轮次窗口切的是事件切片，不是正文）。
 **在请求组装期改写历史正文**这一整类动作被 [D-078](../README.md "symbio/src/plugins/session/README") 否决。
3. **配对永不离散**：`ToolCall`（assistant 请求）与其 `Tool` 结果子节点必须同生共死，任何切分点不得拆开它们，否则请求包非法。
4. **失败必回滚**：语义压缩失败时回滚到原始上下文，绝不让 `[压缩指令]` 残留，绝不让压缩失败阻断对话。
5. **单一计量**：所有层统一使用 `CalibratedTokenizer`（启发式 × provider 用量反馈校准），禁止裸 `len/4`（对中文严重失准）。
6. **失败不裁剪历史**：压缩失败（含"待压缩历史超出模型输入上限"）时**一条消息都不丢**，只如实报错；
 失败节点带原因、可重试、可持久化。历史是用户的资产，"这次压缩放不下"不构成"可以静默丢历史"的
 授权（见 [D-018](../README.md "symbio/src/plugins/session/README")）。

## 1. 分层机制总览

| 层 | 名称 | 作用域 | 手段 | 成本 |
|---|---|---|---|---|
| L0 | 单条工具结果守卫 | 单条 Tool 结果（**写入时**） | 超预算 → 全文存档 + 头尾摘要（单行超长时按字符截断兜底）；网格里存的就是裁后那一份 | 0 |
| L4 | 存储清理 | 持久层 | append 时物理删除老 ToolCall 及其子节点（**不动归档文件**，归档由 L0 守卫滚动淘汰） | 0 |
| L5 | 全局快照（被动） | 跨轮历史 | ≥ 70% 上限 → LLM 摘要替换（**换基**：写一格 `session.consolidated`） | 1 次调用 |
| L6 | 压缩重试（人在环） | 跨轮历史 | 用户点失败压缩节点 → `force` 走同一条流水线 | 1 次调用 |
| — | 轮次窗口 | 请求组装期 | `window_by_turn` 按 turn 丢整轮，**不碰任何一条的正文** | 0 |

L0 / L4 / 轮次窗口是确定性机制，常开；L5 是被动兜底；L6 是人在环的重试——**L5 与 L6 是同一个入口的
两种触发**，不是两套实现。

> 编号沿用既有标识（L0 / L4 / L5 / L6），**空出的 L1–L3 不是待实现的层，是不该存在的层**——见 §1.1。

> 各层的**阈值与实现位置**（文件 / 函数 / 常量）只在 `../README.md` 五大策略维护，
> 本文不复述数字——同一数字写两处必然漂移。

### 1.1 为什么请求组装期不改写正文

压缩这一族最自然的想法是「发出去之前把太长的压短」：单条超长正文换头尾摘要、老工具结果换摘要、
窗口外的工具明细换占位符。这一族（编号 L1/L2/L3）**整族不存在**
（[D-078](../README.md "symbio/src/plugins/session/README")），理由三条，每一条单独都够：

1. **与投影判据互斥**。运行器每发一次请求都跑 `verify_prompt_fidelity`，它的配对判据是正文
 **精确相等**。改写正文 ⇒ 同一节点同时报「网格有、prompt 无」与「prompt 有、网格无」两条缺口。
 守卫一旦能按正文逐个豁免，就不再是守卫，而是一份需要人维护的白名单。
2. **服务的能力缺口在 v2 不存在**。那三层里最重的一层（窗口骨架化）只为一个「工具上下文窗口」
 上限服务，而 v2 的口径是**工具轮不设上限、整批结果全留**。一条为不存在的上限服务的裁剪。
3. **接线要再造一条渲染路径**。运行器环体 mid-turn 复用同一份基线追加本轮交换，而这三层是
 「每请求重算」的；接进去就得在 `turn_runner::prepare::render_messages` 之外另立一条组装路径——正是
 [D-048](../../model/README.md "symbio/src/plugins/model/README") 立项要消灭的那件事。

**代价如实登记**：v2 现在没有「请求视图级」的体积上界。唯一的界是 L0 的每条约 8K token、单条响应
32 次工具调用、轮次窗口、L5 的 70% 水位。长轮里几十条 `role=tool` 是**设计**而不是缺陷——丢掉它们
会让模型反复重读同一份材料。将来若实测超窗，正确的位置是 **L0 上限与 L5 水位**，不是在请求视图里
改写历史。

## 2. 目标一：多轮会话膨胀 → 全局快照（L5）

**触发**：上下文估算 ≥ 70% × 有效上限，且通过迟滞检查（快照后再增长不足 15% 则跳过，防止循环压缩）。

**切分与执行**（实现见 session 策略③）：
- 只在 **User 边界**切分，保留最近 30% 原文明细，待压缩部分 < 5% 不压缩；
- 禁止全量压缩；尾部存在未配对 ToolCall 时本轮放弃；
- 压缩前完整历史转存（可回溯）；快照缺失时附纠正指令重试一次，仍失败则**保留原历史、
 以 `Failed` 节点如实报错**（原因 + 重试入口），不把未验证的散文升级为唯一记忆；
- 失败回滚原始上下文（一条消息都不丢），对话不中断；历史超出模型输入上限时**不本地
 截断**，只报 `input_over_limit` 并给重试入口（见 §0 原则 6）。

**为什么它是「换基」而不是「改写」**：快照写成**一格新事实**，被取代的旧事件移入归档段；
投影与复核都按这一格重新起基线（`prompt_fidelity` 有专门的取代格分支认领它）。网格本身没有被篡改，
只是多了一格「从这里往后以我为准」。

---

## 3. 目标二：单轮工具洪峰 → 两道防线

单轮内工具轮次不受硬上限（用户诉求），膨胀由以下机制消化：

1. **L0 守卫**：单条结果超预算 → 存档 + 头尾摘要（尾部多为结论/错误更关键；单行超长时再按字符截断兜底，防止单行大 JSON 绕过）；
2. **轮次窗口**：请求只带最近 `context_messages` 个 turn 的**整轮**事件。它不裁正文，
 所以「模型看到的这一条」与「网格里的这一条」逐字一致；
3. **轮内不压语义快照**：模型不持有压缩工具，"巨型单轮"由 L0 与轮次窗口消化；L5 的 User 边界
 切分在单轮里找不到切分点时，结果是**本轮不压**而不是裁掉历史（裁决与恢复该能力的前提见
 [D-072](../README.md "symbio/src/plugins/session/README")）。

**没有「请求组装期的最后一道防线」**：请求体不因历史大而失败，因为**历史本来就只带一个窗口**；
窗口内单条过大由 L0 在写入时已经按住。这两条加起来就是全部——不设第三道。

## 4. 目标三：优先关系与取舍决策顺序（从便宜到昂贵、从精准到模糊）：

| 情形 | 首选机制 | 理由 |
|---|---|---|
| 单条工具结果超大 | L0 | 确定性、零成本、精准定位；**在写入时裁**，投影无需二次加工 |
| 单轮里工具交换堆得很长 | 轮次窗口 | 丢整轮不碰正文；且长轮自身的交换**跨轮累加**是设计（模型要看得见自己做过什么） |
| 存储里老工具链越积越多 | L4 | 物理删节点、不删归档，存储态治理不牵连视图 |
| 压缩失败后用户要求再试 | L6 重试（`force`） | 明确意愿，越过迟滞与熔断，但不越过配对不变量 |
| 跨轮历史膨胀逼近上限 | L5 快照 | 被动兜底，保证不中断 |

**不变量**（任何机制都不得破坏）：
- ToolCall/Tool 配对完整；
- 当前轮的用户指令原文保留（在保留区或快照中）；
- assistant 思维链尽量保留；
- 压缩失败必回滚；
- **投影逐字可回溯**：模型看到的每一条正文都能在网格里找到同一条（§0 原则 2）。

**阈值关系**：L0 / L4 / 轮次窗口常开；L5 由水位阈值触发、L6 由用户点失败节点触发（具体百分比见
`../README.md`）。

## 5. 目标四：压缩只有一个入口（`auto_compress_process`）

「何时压」一个入口两种触发，「怎么压」一个实现（`compress_with_snapshot_core`）：

- **阈值触发**：§2 的 70% 判定 + 迟滞检查；
- **用户重试**（`RetryCompaction`）：`force = true`，越过迟滞**并**绕过熔断——熔断约束的是
 "每轮自动白等一次注定失败的请求"，用户点重试是他的明确意愿，不该被冷却挡住；
- **收益护栏**：待压缩历史 < 4000 token ⇒ 不值得一次 LLM 摘要调用（`has_compaction_payoff`）；
- **护栏**：每轮最多一次压缩；失败回滚并保留"压缩已跳过"的如实记录；全程支持 abort。

模型**不持有**压缩工具，请求视图里也没有"提醒模型自己去压"那一段——这条链的退役裁决与
将来恢复它的前提（注册成能力行走 v2 分发）都在 [D-072](../README.md "symbio/src/plugins/session/README")。

**请求组装期不做水位治理**：那里只排三段**注入段**（长期记忆召回 / 就绪任务集 / 委派判定），
只追加不改写。水位归本节的唯一入口，两者不共用时机。

## 6. 维护原则

1. **单一职责**：每层只处理自己作用域内的问题；跨层行为差异必须在常量表（`../README.md`）有注释。
2. **不变量优先**：ToolCall/Tool 配对、User 边界切分、失败回滚、投影逐字可回溯——任何新压缩机制
 必须先证明不破坏这四条。
3. **可观测性**：每次压缩记录 `[DIAG]` 日志（触发原因、前后估算、消息数），便于线上排查。
4. **测试锚点**：切分点函数、快照提取、token 估算（含中文用例）、迟滞判断必须有单元测试。
