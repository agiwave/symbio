# 节点状态流（Node-State Streaming）—— 实时面即节点状态

> 前置阅读：[vdfs.md](../../../../../docs/design/vdfs.md)（机制规范）、
> [vdfs-session-messages.md](./vdfs-session-messages.md)（转写即列表）、
> [core-loop.md](./core-loop.md)（会话主循环）。
>
> 本文回答一个问题：**会话的"正在发生什么"如何只由节点状态表达**，
> 使前端不再消费任何事件序列，从而**不存在事件顺序问题**。
>
> - **读面**（历史）走 VDFS：`read(<根>/session/<sid>)` 一次拿整份历史，地址与 §2.1 一致。
> - **实时面只有一条通道**：`event_bus` 的 `kind = "vdfs"` 频道。消息**是**
>   `<根>/session/<sid>/message/<mid>` 这个文件，流式输出是该文件内容的**增长**；
>   会话运行态是会话节点（`<根>/session/<sid>`）的 `status`。两者的**落点都是被变更
>   节点自身的地址**，都在这一条频道上，没有第二种通道。
>
> 信封是 **`{ path, data? }`**，**没有操作枚举**（没有 `created` / `updated` /
> `deleted` / `appended` / `truncated` / `renamed`）。`path` **恒为被变更节点自身的
> 地址**；语义全在 `data` 的形状上：
>
> | `data` | 落点 | 消费端动作 |
> |---|---|---|
> | `ChatMessage`，`delta` 有 | 消息节点 | **尾部追加**，零回读 |
> | `ChatMessage`，`content` 有 | 消息节点 | **整条替换**，零回读 |
> | `ChatMessage`，`status = removed` | 消息节点 | **就地移除** |
> | `VdfsNode` | 会话节点 | 全量节点视图（状态 / 结局 / 标题 / 计数），零回读 |
> | 缺失 | 任意节点 | 无载荷资源信号（创建 / 删除 / 改名 / metadata）⇒ 回读收敛（`NotFound` 即删除） |
>
> **顺序是节点属性**（`ChatMessage.seq`），与到达顺序无关：两个并行工具的变更
> **混着到**、后生成的**先到**，显示都正确——因为每条变更都指向一个明确的 `path`，
> 而节点自带位置。

---

## 0. 一句话

**把「运行中」从事件里拿出来，变成节点的属性。**

前端持有的是一张**按地址索引的节点表**；它唯一消费的是「某个地址的节点变成了什么样」，
按**地址的作用域**订阅，不按事件类型分派，也不推断"上一条事件是什么"。于是：
**事件可以丢、可以重放、可以乱序，节点状态不会因此错**——因为状态是幂等的全量视图，
而事件是增量的、有顺序的。

---

## 1. 为什么状态不放在事件里

事件是**增量**：它只说"刚刚发生了什么"，丢了就没有第二次机会，而"谁先到"决定 UI 对错。
把会话的运行事实做成事件流，会反复出现这几类缺陷：

| 事实 | 事件化后的缺陷 |
|---|---|
| 会话忙 / 闲 | 事件是增量：丢一次就没有第二次机会；两条事件的**顺序**决定 UI 对错 |
| 上一轮以错误结束 | 同一件事被表达为「失败节点」与「事件」两处，消费端需要启发式去重 |
| 用户中止 | 中止不是错误也不是正常结束，只能靠"谁先到"区分音色 |
| 连接态 | 前端连接态与业务态混在一条通道上 |
| 切会话漏事件 | 需要一层「挂起重放」缓冲补顺序缺口——缓冲本身就是"顺序会被打乱"的补丁 |

**修法不是把缓冲做得更精细，而是取消"顺序"这个前提**：
让每次变更都携带**该节点的状态**（或足以收敛的载荷），那么"谁先到"只影响最终收敛的
**速度**，不影响**正确性**。

## 2. 节点分类与状态机

### 2.1 地址 = 节点

一个节点 = 一个地址 = 一份状态。会话域的全部节点：

```text
<根>/session                                  会话清单（目录）
<根>/session/<sid>                            会话节点        ← 运行态的承载者
<根>/session/<sid>/message                    转写列表（集合）
<根>/session/<sid>/message/<mid>              消息节点（列表项）
<根>/session/<sid>/AGENTS.md                  会话记忆（文件）
<根>/session/<sid>/subsession[/<sub>]         子会话清单 / 子会话节点
<根>/session/<sid>/workdir[/<rel>]            工作目录树
```

消息节点内部再由 `attributes.parent_id` 组织成树——**树是节点的一个属性，
不是另一套地址**。这样列表（有序、可分页、可增量追加）与树（表达归属）两个需求
用同一份数据同时满足。

**变更的落点是节点自身的地址**：消息节点的变更落在
`<根>/session/<sid>/message/<mid>`（**不是**目录 `<根>/session/<sid>/message`），
会话运行态的变更落在 `<根>/session/<sid>`。地址形状统一为
`<sid>/<集合段>/<项 id>`：会话是**容器**，其下是若干并列的**集合**（消息 / 子会话 /
记忆 / 工作目录……），因此"哪一类集合"由**地址段**回答，机制不认识任何一类集合。

### 2.2 节点类型（taxonomy）

| 节点 | `ext` | `type`（`attributes.type`） | 组合？ | 状态取值 |
|---|---|---|---|---|
| 会话 | `session` | — | 否（叶子 + 内部区段之父） | `working` / `active` / `failed` |
| 轮次 Turn | `message` | `turn` | **是**（仅分组，无正文） | `pending` → `streaming` → `completed` / `failed` |
| 思考 Reason | `message` | `reasoning` | 否 | `pending` → `streaming` → `completed` / `failed` |
| 正文 Text | `message` | `text` | 否 | 同上 |
| 工具调用 ToolCall | `message` | `tool_call` | **是** | `pending` → `streaming` → `waiting_user_action` → `completed` / `failed` |
| └ 请求 Request | — | （即 ToolCall 的**内容**） | — | 随 ToolCall：参数流式期 `streaming` |
| └ 响应 Response | `message` | `text` / `turn` | 视内容 | `pending` → `streaming` → `completed` / `failed` |
| 用户应答 UserPrompt | `message` | `user_prompt` | 否 | `waiting_user_action` → `completed` |

**工具调用的「请求 + 响应」不需要两个地址**：`read(.../message/<tc-id>)` 取到的正文
**就是请求体**（参数 JSON），它的**子节点就是响应**。这与 LLM 协议同构
（`tool_calls[].function.arguments` + `tool` 角色消息），也与既有存储同构。
把请求另立一个地址会立刻产生"同一份参数存两处"，那才是真的坏设计。
前端渲染里的请求节点（`meta.__toolRequest`）是**渲染标记**——它表示"这是一个由内容
提升出来的请求视图"——**不是第二个状态来源**：它的状态（`streaming` / `completed`）
取自 ToolCall 节点（§5.3）。

### 2.3 状态机

```text
                    ┌──────────────────────────────┐
                    │  pending  未开始              │
                    └──────────────┬───────────────┘
                                   │ 开始产生内容 / 开始执行
                    ┌──────────────▼───────────────┐
              ┌─────│  streaming  运行中（会话：    │
              │     │              working）      │
              │     └──────────────┬───────────────┘
              │                    │
   需要用户响应│     ┌──────────────▼───────────────┐
              └────▶│ waiting_user_action  等待     │
                    └──────────────┬───────────────┘
                                   │ 用户响应 / 直接结束
              ┌────────────────────┴────────────────────┐
              │                                         │
    ┌─────────▼──────────┐                   ┌──────────▼─────────┐
    │ completed  已结束   │                   │ failed  错误        │
    └────────────────────┘                   └────────────────────┘
```

**会话节点是一个例外（有意为之）**：会话是**长期存在**的，它没有"未开始 / 已结束"。
它的三个状态是 `working`（处理中）、`active`（空闲）、`failed`（上一轮以错误结束）。

| 状态 | 语义 | 用在哪 |
|---|---|---|
| `pending` | 已声明、尚未产生任何内容 | 消息 |
| `streaming` | 正在产生内容 | 消息 |
| `working` | 正在执行（会话的同一件事） | 会话 |
| `waiting_user_action` | 阻塞在用户输入上（审批 / 提问） | 消息 |
| `completed` | 正常结束 | 消息 |
| `active` | 空闲（会话的"无特殊状态"） | 会话 |
| `failed` | 以错误结束 | 消息 + 会话 |

### 2.3.1 为什么不把 `streaming` / `working` 合成一个词

它们是同一个概念在两类节点上的两种拼法。合并看起来更"统一"，但代价是：
`status-*` 的 CSS 类名、`isWorkingStatus()` 的判据、以及两处测试断言会一起改，
而**漏改 CSS 类名不会报错、不会失败，只会让流式动画静默消失**。收益（少记一个词）
远小于风险。故：**词汇保持不变**，`isWorkingStatus()` 仍是"会话忙不忙"的唯一判据。

`failed` 是会话的终态之一，与 `active`（空闲）并列，而不是写成
`active + last_failed=true` 这种"状态 + 平行布尔"——后者要求读状态的人同时读两个
字段，任何一处漏读就静默错；`failed` 单独成态后，"会话是否可重试" =
`status == 'failed'`，一处判定。

### 2.4 状态不做有损映射

若 `message_status()` 把 `Completed` 与「未标注」**都**映射成 VDFS 的 `active`，
消费端就必须把 `active` **读回** `completed`——一次信息丢失 + 一次猜测还原。

因此：**节点状态就是消息状态**——`pending|streaming|waiting_user_action|completed|failed`
原样透传，消费端不做任何还原（`active` 只作为旧数据的兜底别名保留）。
前端映射在 `registry/messageTypes::messageStatusOf`；未知状态词一律留痕（§8 #21）。

> 会话节点的 `active`（空闲）与消息的 `completed`（已结束）不是同一个概念，
> 也不构成"两套词表"：一套词表里 `active` 是"无特殊状态"，`completed` 是"终态"。
> 二者若被合并成同一个字符串，就是一处有损映射。

## 3. 传输契约：信封 + 载荷

### 3.1 唯一通道

会话域的一切实时变化都经 `kind = "vdfs"` 一条频道，**不存在第二条**。
消息与会话节点的运行态都在这一条上，落点都是**被变更节点自身的地址**（§2.1）。

### 3.2 信封与载荷

信封形状是 `{ path, data? }`（`VdfsChange`）：

```text
path  ：被变更节点自身的地址    —— 身份就是地址末段，与 list / read 的节点地址逐字同源
data? ：业务载荷                —— 缺失 = 无载荷资源信号
```

`path` 的取值：

- 消息节点 → `<sid>/message/<mid>`（**不是**目录 `<sid>/message`）；
- 会话节点 → `<sid>`（会话既是清单里的文件、又是容器目录，变更落点就是它自身）。

**没有操作枚举**——`data` 的形状决定语义，消费端按字段落地、零翻译：

| `data` 形状 | 触发 | 消费端动作 |
|---|---|---|
| `ChatMessage`，`delta` 有、`content` / `status` 无 | 节点正文尾部追加（流式 token） | **尾部拼接**（零回读） |
| `ChatMessage`，`content` 有 | 首帧全量副本 / 整条替换（含落库换号） | **整条替换**（零回读） |
| `ChatMessage`，`status = removed` | **这一个**节点消失 | **就地移除**这一项 |
| `ChatMessage`，其余 `status` | 状态迁移（`pending → streaming → …`） | **就地迁移**状态（零回读） |
| `VdfsNode` | 会话运行态 / 结局 / 标题 / 计数 | 全量节点视图，**零回读**就地收敛 |
| 缺失 | 创建 / 删除 / 改名 / metadata | 回读 `stat` 收敛：`NotFound` 即删除 |

**同帧 `delta` + `content` 是协议违例**（写入点 `Transcript::apply` 与前端落地
`sessionTranscriptSync` 用同一条判据报错丢弃）。`delta` 与 `content` 互斥，正是
"帧的语义只由字段给出"的全部内容：消费端不必从帧的形状推断"该拼接还是该替换"。

**载荷宽度按频率分配**：纯增量每帧都发 → 只带 `delta`；状态迁移每轮数次 → 带全量
（视图或整条消息）。若状态不带全量，消费端就得回读 `stat` / `read`——一次状态迁移
一次 IPC，而状态迁移恰恰是**最需要即时**的路径。

### 3.3 会话节点：视图载荷与场景属性

会话运行态变更的 `data` 是**全量节点视图**（`VdfsNode`），由编排层在**调用那一刻**
从权威源构造（`session_node`，与 `stat` 同一构造点）——不是缓存的旧副本，
因此消费端**零回读**就地收敛。视图缺席（会话已删、取不到）⇒ 退化为**无载荷变更**，
消费端回读 `stat` 得 `NotFound` 即删除。

```text
attributes.outcome = "completed" | "aborted" | "failed"   // 上一轮怎么结束的
attributes.error   = "<面向用户的错误短消息>"              // 仅 failed 时存在
```

- `outcome` 是**状态**（"上一轮的结局"），不是事件：提示音据此选音色，
  不需要"谁先到"来区分中止与失败。
- `error` 挂在会话节点上，是为了覆盖「错误发生在任何消息节点创建之前」这一类
  （能力收集失败、provider 解析失败、transport 级失败）——此时没有任何失败节点
  可承载错误。它是节点的属性，不是一条平行事件，也不是前端平行状态。

会话节点的 `data` **不带正文**：`read(<根>/session/<sid>)` 才是历史读入口（整份会话
JSON）；视图足以表达状态，正文由消息集合承载（§9）。

## 4. 顺序无关性

### 4.1 为什么成立

顺序无关性有两半：**状态**（全量视图 ⇒ 幂等）与**位置**（`seq` ⇒ 节点属性）。

| 变更形态 | 幂等？ | 可交换？ | 依据 |
|---|---|---|---|
| 状态 / 全量替换（`data` 为全量 `ChatMessage` 或 `VdfsNode`） | **是** | **是** | 携带全量视图；同一节点的两次状态按任意顺序应用，收敛到较新者 |
| 无载荷资源信号 | 是 | 是 | 消费端回读（`stat` / 重拉清单）收敛，与到达顺序无关 |
| 纯增量（`delta`） | 否 | 否 | 增量语义天然有序——正文是"前缀的延长" |

因此规则是：**状态类变更按地址应用即可；纯增量必须在一条单写入者、单 FIFO 的
通道上按序到达**。顺序由 `event_bus` 那条频道与"同一节点的正文只有一个写入者"
（`Transcript`）共同给出，而不是靠消费端记历史。

### 4.2 残留假设（明确写出，不假装没有）

1. **总线是单条有序通道**。同一连接上，后端发出的顺序 = 前端收到的顺序。
   跨重连丢帧不产生乱序，只产生"少一次状态"——由 resync + 整份重读修复（§8 #20）。
2. **快照不得降级运行态**。`list` 的快照可能比在途变更旧，因此「快照只能把
   `active` 升级为 `working`，不得把 `working` 降级」这条规则保留
   （`stores/sessions.ts::refreshList` 只做 `false → true` 的升级，降级交给节点状态变更）。
3. **纯增量依赖路径级串行**：同一节点的正文只由单一写入者（`Transcript`）追加；
   `Transcript::deliver` 的合帧只合并**相邻**的增量，不改变先后（§10.2）。

### 4.3 顺序无关性依赖什么

顺序无关性不是免费的，它依赖两条**现行约束**：

- **状态变更必须携带全量视图**（`data` = 完整 `ChatMessage` / `VdfsNode`）。一旦改成
  只发"相对变化"（"正文多了 3 个字符"、"状态从 A 变成 B"），迟到的那条就会把较新的
  状态**打回旧值**，而丢帧后**没有任何机制会纠正**——状态变更的可交换性当场消失。
- **纯增量必须单写入者、单 FIFO**（§4.2）。`delta` 是"前缀的延长"，天然不可交换；
  它能与状态变更同处一条通道，是因为消费端对增量只做**尾部拼接**，而顺序由通道
  与单写入者给出。

换句话说：**"事件可以丢、可以重放、可以乱序"这三句在状态上成立，在增量上不成立**。
因此"同一节点的增量在一条有序流上"这条要求成立——它是增量语义的固有属性，
不是顺序假设的残留。

## 5. 前端消费模型

### 5.1 一条通道，两个作用域

```text
kind = "vdfs" 变更（唯一实时通道，消费端按作用域订阅）
      │
      ├─ <根>/session/<sid>              ← stores/sessionNodeSync（directChildren）
      │    ├─ data = VdfsNode            → applySessionState(sid, node)   （零回读）
      │    └─ data 缺失                  → 回读 stat：NotFound 即移除；
      │                                    其余防抖重拉清单（800ms）
      │
      └─ <根>/session/<sid>/message/**   ← stores/sessionTranscriptSync
           ├─ delta 有                   → 尾部拼接（零回读；id 未知才回读补身份）
           ├─ content 有                 → 整条替换（零回读）
           └─ status = removed           → 就地移除
```

**为什么不需要「按地址分派」**：`path` 恒为被变更节点自身的地址，**身份就是地址
末段**——消费端按作用域订阅即可，不必把地址翻译成"消息 / 会话 / 运行态"三种目标
再分派。两种载荷都携带全量视图（或增量前缀），状态本身幂等，消费端同样不必记历史。

"状态可以乱序"只对**状态**成立：纯增量依赖单写入者与单 FIFO（§4.2），
因此消息的实时面在变更里带 `delta`，而不是靠消费端去推断"上一条是什么"。

此外通道上还有**资源**变更（创建 / 删除 / 改名 / 标题 / metadata）。它们发生在
**没有在途轮次**时，并且是粗粒度的：收敛方式统一为**回读 / 重拉清单**
（幂等 ⇒ 无序无害）。因此资源信号**不带载荷**——消费端只要"变了"这个事实，
不必逐字段合并（§11，另见 `stores/sessionNodeSync.ts` 模块文档）。

两个消费者**互不重叠**：会话叶子的**运行态**归会话节点订阅，**资源**归清单订阅，
**转写**归转写订阅。重叠会让同一份状态被写两次。

### 5.2 状态 → 视图，不做推断

| 视图 | 唯一依据 |
|---|---|
| 会话卡片状态点 | 会话节点 `status` |
| 会话卡片"上次失败" | 会话节点 `status == 'failed'` |
| 会话卡片"等待审批" | **派生**：转写中存在 `status == 'waiting_user_action'` 的节点（纯函数，不是事件） |
| 活动文字（"正在思考…"） | **派生**：最近变化的节点的 `status` + `type` + `tool_name`（工具名的 attributes 键**不能**叫 `name`——那与 `VdfsNode.name`（节点 id）在 flatten 序列化下同名冲突，见 `message_node` 注释） |
| 消息块外观（流式动画 / ⚠ / 骨架） | 消息节点 `status` |
| 提示音 | 会话节点 `working → 非 working` 的**迁移** + `attributes.outcome` |
| 错误条 | 失败节点（有则用节点）；无失败节点时用会话节点 `attributes.error` |

「派生」是**纯函数**：同样的节点表必然得到同样的视图。
事件流做不到这一点——它必须知道"之前发生过什么"。

### 5.3 工具调用的三段式

渲染仍是「请求 / 过程 / 结果」三段，但每一段的**状态来源**写死：

| 段 | 数据来源 | 状态 |
|---|---|---|
| 请求 | ToolCall 节点的 `content` | `streaming`（参数仍在流式）/ `completed` |
| 过程 | ToolCall 的子 `turn` 节点（子会话过程） | 子节点自身状态 |
| 结果 | ToolCall 的其余子节点 | 子节点自身状态 |

`meta.__toolRequest` 保留为**渲染标记**（表示"这是一个由内容提升出来的请求视图"），
但它**不再是状态来源**——状态一律读 ToolCall 节点。

**请求那段的内容是窄增量下发的**：ToolCall 的参数与正文 / 思考**同构**——首帧
（身份字段出现）是完整快照，其后每片参数只发 `append`。若每片参数都全量重发，
线材开销会随参数长度 **O(n²)** 增长；更糟的是，它诱导消费端按"`tool_call` 的帧
都是全量"去猜语义——那条猜测一旦蔓延到 `role = tool`，就会把工具响应**真正的增量**
也当成全量替换（§8 #27）。

### 5.3.1 ToolCall 的 `streaming` 覆盖「参数流式 + 执行」两段

§2.2 的状态机写的是 `pending → streaming → waiting_user_action → completed / failed`，
其中 `streaming` **同时覆盖两个阶段**：

```text
  pending ──▶ streaming ────────────────────────────────▶ completed / failed
              │                    │
              │ ① 参数流式          │ ② 执行窗口
              │   （模型逐 token     │   （一次编译 / 一次网络请求 /
              │     吐出 arguments） │     一个子智能体跑完 —— 往往最长）
              └────────────────────┴──────────────────────
```

**这两段之间没有中间态**，也不该有：对用户而言"这次调用还没结束"是同一件事。

#### 为什么必须有 ② 的状态

`finalize_assistant_turn` 在 LLM 流结束时天然是"参数齐了"这一刻。若它**在此把所有
ToolCall 标 `Completed`**，前端在执行窗口内就没有任何「运行中」迹象：参数流完画面
静止，直到结果突然出现。窗口越长的工具（语义索引、长命令、子智能体），这段静默越长，
用户无法判断"还在跑"还是"卡死了"。因此终态必须留给执行方（见下）。

#### 不变量：ToolCall 的终态只由执行方给出

| 执行路径 | 终态来源 |
|---|---|
| 正常分发 | `tool_executor::process_tool_calls_async` |
| 恢复执行（approve / retry / supply） | `resume::process_tool_resume_action` |
| 被 PreToolUse 拦下 / 用户中止 / 交互中断 | `process_tool_calls_async` 末尾统一收口：父节点 `Completed` + `meta.failure_kind = "not_executed"`，并由 `not_executed_result` 补一条结果子节点（**成对**，缺一就是「有请求无响应」） |

**"本批每一个 ToolCall 都必须以终态收场"** 由 `process_tool_calls_async` 负责保证：
调用前广播 `Streaming`，调用后广播终态，未执行的批尾在函数末尾一次性收口。
漏掉任何一条，前端就会有一个**永远转下去的「运行中」**（比"没有迹象"更糟：
它把"卡住"伪装成"在跑"）。

#### 不变量：有调用必有结果（终态之外的第二半）

终态只说"这次调用结束了"，而"这次调用的结果"在树里是一条**子节点**——
前端 `ToolCallNode` 的响应段就按子节点渲染。因此收口同样必须**成对**：

> 每一个 ToolCall 都必须有结果子节点（`role = tool`，`process_tool_calls_async`
> 的 `tool_messages` 里一条），无论它是执行了、失败了、还是根本没轮到。

只补父节点是一个**静默**的缺口（实测事故）：卡片有请求、没有响应，
而会话照常往下走；下一轮请求又因为 `flatten_chat_messages` 会为无结果的
ToolCall 合成占位 tool 结果而**始终合法**——于是「模型看得见、用户看不见」，
没有任何机制会纠正它。因此结果子节点必须在**存储**里成立
（`not_executed_result`），而不是只在请求视图里成立。

#### `meta.started_at`：把"运行中"从断言变成判据

`Streaming` 状态只回答"在不在跑"，不回答"跑了多久"。因此执行开始时同时写入
`meta.started_at`（毫秒），前端据此显示 `运行中 · 47s`：

- **为什么是节点属性而不是前端计时**：切会话 / 重连后前端计时从零重来，会把
  "已经跑了 3 分钟"显示成"刚刚开始"——恰好丢掉用户最需要的那条信息；
- **为什么前端在锚点缺失时不显示时长**：宁可不说，也不给一个看起来合理但
  没有依据的数（旧数据没有该字段）；
- 只写 `started_at`（一个不可变的事实），**不写** `running: true` 这类布尔——
  布尔在结束时需要有人负责清除，漏清就是永久误报。

> 前端另有一条独立收益：`syncActivity` 若在 `finalize_assistant_turn` 的
> `Completed` 到达时把活动文字清空，执行窗口内就会是空的。运行态跨越执行窗口后，
> 活动文字（`正在调用 <name>…`）与节点标签自然同步，无需额外接线。

### 5.3.2 组合节点的终态**跟随子树**（Turn 与 ToolCall 同一条规则）

`turn` 与 `tool_call` 都是**组合节点**（自身无正文，只负责分组），因此共用一条规则：

> **组合节点的终态不得早于它的子树。**

对 ToolCall，这条规则落在 §5.3.1——终态只由执行方给出（"参数齐了" ≠ "调用结束了"）。
对**根 Turn**，它落在**收尾点**：

| 层 | 位置 |
|---|---|
| `chat_loop.rs` | `close_turn` 返回之后调用 `finalize_turn_root` —— 全流程**唯一**一处 |
| `chat_loop/io.rs` | `finalize_turn_root`：从权威转写取那条节点 → 改状态 → 广播 |

若它在 `finalize_assistant_turn`（LLM 流结束那一刻）发出，就会比子树早整整一个
**执行窗口**：树上出现"容器已经完成、其中的工具调用仍在运行"这种自相矛盾的形状
（实测抓包里「Turn 已完成」出现在「工具开始执行」之前）。

**发出的就是即将落库的那条节点**（`build_assistant_messages` 的产物，与
`persist_messages` 同源），因此**实时帧与存储按同一取值收敛**，不需要第二套
"终态"构造逻辑。（副作用：实时流里那条快照不带流式占位期的 `meta.turn`——
存储本来也没有它，两边一致。）

## 7. 实时面覆盖的行为

实时面覆盖的每一项行为，及其依据的机制：

| # | 行为 | 依据 |
|---|---|---|
| 1 | 发送后立即显示"处理中…" | 本地乐观置位保留，随后被权威节点状态覆盖（`useChatConnection.send`） |
| 2 | 流式逐字输出 | `delta` 就地拼接，零回读（§3.2） |
| 3 | 思考 / 工具调用单行折叠 + 状态标签 | 标签覆盖 `运行中 / 待确认 / 失败`，运行中另带三点脉动 + 已运行时长（§5.3.1） |
| 4 | 工具审批：卡片角标 + 表单 | `waiting_user_action` 节点状态（§5.2） |
| 5 | 失败：根级 Turn ⚠ + 重试 | 失败节点状态（§5.2） |
| 6 | 失败但无节点（transport 级） | 会话节点 `failed` + `attributes.error` → 同一条错误条（§3.3） |
| 7 | 中止：状态回落 + "已中止" | 会话节点回落 `active`，`outcome = aborted`（§3.3） |
| 8 | 结束提示音（三音色） | 会话节点 `working → 非 working` 的迁移 + `outcome`（§5.2） |
| 9 | 切会话来回不丢状态 | 状态是节点属性，不依赖回放缓冲（§4） |
| 10 | 会话列表状态点 | 会话节点 `status`（§5.2） |
| 11 | 重连后状态收敛 | resync 整份重读 + `list` 快照（只升不降，§4.2 / §8 #20） |
| 12 | 中止后不再有节点转圈 | ToolCall / reason / Turn 全部落终态；Turn 落 `Failed` 以给出重试入口（§5.3.1 / §5.3.2） |
| 13 | 切回「正在跑」的会话 | 正在跑的那一轮**仍在**：叶子读含在途（`overlay_live`）+ 前端水合不丢弃在途（§8 #14） |
| 14 | 长会话触发压缩时 | 消息流里出现「上下文压缩」节点：运行中脉动 + 已用秒数，完成后显示"已压缩上下文（X → Y 条）"（§8 #15） |
| 15 | 压缩请求的内容 | 历史以**对话形态**下发（不是 JSON 转储），末尾一条压缩指令（§8 #16） |
| 16 | 压缩失败 | 节点落到 `Failed` / `Completed(aborted)`，且 `error` + `meta.failure_kind` 写明**原因**（Llm / InvalidSnapshot / InputOverLimit）（§8 #17） |
| 17 | 压缩连续失败 | 达阈值后熔断 5 分钟冷却，期间**跳过 LLM 压缩**但仍正常回复；冷却结束半开重试一次（§8 #19） |
| 18 | 压缩失败后的历史 | **一条不动**（四种失败出口全部还原为调用前列表）；节点上是错误条 + 原因（§8 #22） |
| 19 | 压缩失败后重试 | 失败节点上给「重试」入口（resume `retry_compaction`）：删失败节点 → 重新压缩；绕过熔断（§8 #24） |

## 8. 不变量

1. **一个节点一个地址一份状态**：状态变更只发生在节点上，不在通道上。
2. **状态变更携带全量视图**：会话运行态变更的 `data` 是 `VdfsNode`（与 `stat` 同一
   构造点），全量消息帧的 `data` 是完整 `ChatMessage`；消费者**不得**为状态回读。
3. **热路径窄**：纯增量帧只带 `delta`。
4. **消费端不按事件类型分派**：按**作用域**订阅、按 `data` 形状落地；没有
   `switch (event.type)`。
5. **派生是纯函数**：等待审批、活动文字、可重试性都由节点表算出，不记录"历史事件"。
6. **补丁与变更同生共死**：任何送达前端的会话状态变化都必须经同一个出口
   （后端 `emit_session_state`），漏发即 UI 永久停在旧状态且无人纠正。
7. **`completed` 不再坍缩为 `active`**：消息状态原样透传，消费端不做还原。
8. **会话状态词只有三个**：`working` / `active` / `failed`——不为会话造 `pending` /
   `completed`（它没有"未开始"与"已结束"）。
9. **失败是状态不是标志**：不再有 `last_failed` 布尔。
10. **实时面只有一条通道**（`kind = "vdfs"`，ADR-025），两条事实各是一个节点：
    消息**是** `<根>/session/<sid>/message/<mid>` 这个**文件**（流式 = 它的内容增长，
    `data` 带 `delta`），会话运行态是会话节点（`<根>/session/<sid>`）的 `status`
    （`data` = `VdfsNode`，与 `stat` 同源）。**顺序是节点属性**（`ChatMessage.seq`），
    与到达顺序无关——两个并行工具的变更**混着到**、后生成的**先到**，显示都正确，
    因为每条变更都指向一个明确的 `path`。因此**不需要第二种通道**。判断「本轮 /
    子会话结束」看会话节点的 `status`（不再有 `Status idle` 帧可等），**不是**根 Turn
    的终态（一轮里它会多次定格）。旧事件频道（`kind = "session"`）已整体废除——前端
    （`stores/sessionNodeSync.ts` / `composables/useVdfs.ts`）、CLI（`cli/src/client.rs`）
    与子智能体转播（`agent/host/subagent.rs`）三处消费者都订同一条 `KIND_VDFS` 变更。
11. **ToolCall 的 `streaming` 覆盖执行窗口**：`finalize_assistant_turn` 不得提前定格；
    每个 ToolCall 都必须以终态收场（未执行者收口为 `Completed` +
    `meta.failure_kind = "not_executed"`），不得有节点停在 `Streaming`（§5.3.1）。
12. **运行时长是节点属性**：`meta.started_at` 由执行方写入；前端不自造锚点，
    锚点缺失即不显示时长。
13. **中止自行收口，不等 chat_loop**：`handle_abort` 一旦复位 `is_working`，消费循环
    就可能因 `!is_working` 提前 `break` 而跳过 `persist_failure`。因此中止路径自己调
    `converge_inflight`，且必须**幂等**（`handle_abort` 与消费循环的中止出口都会跑）。
14. **同一份数据的两个地址给出同一份内容**：会话叶子 `read` 与转写列表都叠加在途缓冲
    （`overlay_live`）；在途副本**继承**存储分配的 `seq`——顺序锚点只由存储分配，
    否则同一条消息会以「有 seq / 无 seq」两种形态排到列表的两个位置。
15. **系统动作也是节点**：压缩不挂会话级横幅，而是 `msg_type = compression` 的**消息
    节点**——它有位置（当前时刻）与状态（进行中 / 已完成），可回溯；横幅没有位置概念，
    滚动即消失。但它**不是对话内容**，`flatten_chat_messages` 必须把它剔除出请求包。
16. **给模型的输入按模型的视角投影**：压缩请求把历史**原样**交给 provider 的
    `flatten_chat_messages`，而不是 `serde_json` 序列化存储结构——后者会为 `id` /
    `parent_id` / `seq` / `meta` 等模型完全不关心的字段原样付费。
17. **失败要留证**：节点的 `Failed` / `Completed(aborted)` 必须带 `error`（人读原因）与
    `meta.failure_kind`（机读码），不得无差别地落"未完成"却留空 `meta` / `error`——
    否则事后无法区分"LLM 挂了"与"摘要结构非法"。
18. **优化项失败不得阻断主路径**：自动压缩是上下文优化、失败时历史已回滚，因此它失败
    最坏的代价是"本轮用更长上下文跑"，绝不能 `TurnExit::Failed` 让用户消息也拿不到回复。
19. **连续失败要熔断**：只看当前水位不看历史，会让"注定失败的压缩"每轮重试、每次都白等
    一次完整 LLM 往返。达阈值即开闸冷却，冷却期内跳过而非硬扛。
20. **丢了怎么自愈**：`event_bus` 满通道时**不摘除订阅**——保留订阅并补送一条
    **resync 指令**（`data.data.type == "resync"`）；**前端重连成功**也补一次。
    消费端收到即按自己登记的作用域**整份重读**（重读源是 VDFS 读面，权威且幂等，
    无需补帧）。这是**唯一**一层恢复机制，消息与运行态**共用**。因此消费端不得把
    "没收到终态"就地把节点猜成 `completed`——服务端可能定稿成 `aborted` / `failed`，
    猜错就是"把半截谎报成正常结束"。
21. **状态词表前后端逐字同源**：后端 `MessageStatus::as_str()` 产出的每一个词，
    前端 `schemas/vdfs.ts` / `registry/messageTypes` 都必须登记。漏一个的代价不是
    "少显示一个标签"，而是**整条状态被静默丢弃**（消费端的未知分支），节点以"无状态"
    落进 store，被缺省兜底成 `completed`——终态被谎报。故未知状态词一律 `logger.warn`
    留痕，且新增状态词时两侧一起改。
22. **压缩失败不改动历史**：四种失败出口（LLM 失败 / 快照校验失败 / 输入超限 / 用户
    中止）全部把消息列表还原为调用前状态，**一条不丢**。历史是用户的资产，"这次压缩
    放不下"不构成"可以静默丢历史"的授权（ADR-018）。
23. **失败不得伪装成成功**：压缩的输入超限预判只允许"跳过注定失败的请求"，**不得**
    顺势本地截断并回报 `Ok`——那会让节点显示"已压缩上下文（N → M 条）"，用户既不知道
    出了事，也没有任何入口可点。
24. **失败态必须给出路**：压缩失败节点必须同时满足三件事——原因可见（节点正文 +
    `meta.failure_kind`）、**可重试**（resume `retry_compaction`）、**可持久化**
    （节点落库，重开仍在）。少了"可重试"，用户唯一的出路（换更大上下文的模型后重试）
    就断了；重试入口**不按 `failure_kind` 分档**，判断权归用户。
25. **有调用必有结果**：ToolCall 的终态补丁与它的**结果子节点**成对出现——
    执行、失败、被拦下、未轮到、中止，五种收场都要有结果（`not_executed_result`）。
    只补父节点（#11 满足）是一个**静默**缺口：卡片有请求、没有响应，而请求视图
    被 `flatten_chat_messages` 的占位兜住 ⇒ 模型看得见、用户看不见。
    显示层另有一条兜底文案（`registry/messageTypes::missingResultNoteOf`，
    按父节点自述的 `meta.failure_kind` 给出），服务于缺结果的历史数据，
    不是本不变量的替代（§5.3.1）。
26. **组合节点的终态跟随子树**：`turn` / `tool_call` 的终态不得早于它的子树。
    ToolCall 由执行方定格（#11）；根 Turn 由 `finalize_turn_root` 在 `close_turn`
    返回之后定格，**全流程唯一一处**（§5.3.2）。它**不得**在
    `finalize_assistant_turn`（LLM 流结束那一刻）发出——那会比子树早一整个执行窗口。
    发出的节点与 `persist_messages` 落库的是**同一份**，因此实时帧与存储按同一
    取值收敛，不需要第二套"终态"构造逻辑。
27. **帧语义只由字段给出，不由节点类型反推**：`delta` = 尾部追加，`content` = 整条替换；
    同帧携带两者是**协议违例**（写入点报错丢弃——不发布、不落地）。追加对正文 /
    思考 / **工具参数** / **工具响应**一律成立（后端构造帧只有三处：
    `turn.rs::message_frame`（完整消息）/ `state_frame`（剥正文的状态帧）/ `emit_delta`
    （增量）；工具参数与 Text / Reasoning 同构，工具响应透传子会话的增量帧）。
    消费端按 `type` / `role` 猜"该追加还是该替换"是错误来源：实测曾把
    `role = tool` 的流式响应当成全量重发，正文被**最后一片**覆盖——工具卡片
    有请求、响应是空的。落地动作与字段**一一对应**（`sessionTranscriptSync` 的落地口
    按字段分派），中间不得再插一层"合并"。
28. **投递可以合帧，但正文不得少一个字符；分级与折行只作用于日志**：
    `Transcript::deliver` 只把**相邻的同节点纯增量**在 `DELIVER_WINDOW_MS` 内合成
    一帧再投——语义逐字等价（正文一个字符不多不少），一次流式回复的出帧数降到约 1/6；
    首帧全量副本 / 状态迁移 / 删除 / 整条替换**必然立刻发**，且排在待投递的增量
    **之后**（§10.2）。日志侧（`FrameLogLevel` 分级 + `DeltaLogCoalescer` 折行）是
    **另一个**机制，只决定"要不要打这一行、打成什么样"——`seq`、载荷、投递一个字节
    都不变（§10.4）。顺序不靠到达顺序：`ChatMessage.seq` 是节点属性。

## 9. 取舍与风险

| 项 | 说明 |
|---|---|
| 会话节点状态无独立版本号 | 依赖 §4.2 的三条假设。加 `rev` 需要跨进程单调时钟，收益不足以抵消脆弱性——宁可把假设写清楚 |
| 会话节点载荷是**视图**、不是正文 | 会话节点的 `data` 是 `VdfsNode`（状态 / 结局 / 标题 / 计数），`read(<根>/session/<sid>)` 才是历史读入口（整份会话 JSON）。视图足以表达状态，正文由消息集合承载 |
| 资源信号**不带载荷** | 创建 / 删除 / 改名 / metadata 是粗粒度的，消费端本来就要重拉清单；捎带快照只会让每个消费端都背一次"逐字段合并"的成本。运行态的视图则必须带——它是最需要即时的路径（§11） |
| `attributes.outcome` 是场景字段 | VDFS 只透传（与 `message_count` / `meta_tags` 同一手法），不构成机制新增 |
| 订阅是**全局广播**，订阅表没有会话过滤位 | `fan_out` 把每帧 `clone()` 后交给**全部**订阅者，归属由帧里的 `session_id` 给出。这是**有意**的：CLI 靠它「订阅一次覆盖所有会话、切会话不必重连」，前端靠它显示后台会话进度。代价是单会话消费端收全量帧——目前唯一真正吃亏的是 `agent/host/subagent.rs` 的转播桥（每个子会话一条订阅，N 个子智能体并行时是 N 个订阅者 × (N+1) 个会话的帧投递，投递还含克隆）。**已知的收窄方向（记录备将来，不是待办）**：给订阅加一个**可选**的会话作用域；**不能改成必填**——那会让 CLI 的「切会话不必重连」与前端的多会话收敛一起退化。等真的观察到帧投递成为热点再做 |
| 投递合帧的延迟 | `DELIVER_WINDOW_MS` 的窗口过期由**每一帧到达时**检查（无后台定时器），因此最坏情形是"一段增长的最后一帧晚于窗口到达"；而一段增长的两个端点（首帧与终态帧）都不进窗口 ⇒ 没有内容会被无限期扣住（§10.2） |
| 核心日志的分级 + 增量折行 | 默认输出只剩**骨架**（出现 / 终态 / 等待用户 / 删除），过程细节（`Update` 帧与折行统计）要 `--verbose` 才见。代价是"某一帧长什么样"不再直接可见；换来的是时间线重新可读（§10）。需要逐帧细节时按节点 `id` 去同一节点的变更里取，不靠日志 |

## 10. 核心日志：分级与折行

### 10.1 问题：时间线被同一件事填满

`Transcript::emit` 的注释原本写着「每帧一行，即时间线本身」。这句话对**状态帧**
（开始 / 增长态 / 终态 / 删除）成立，对**纯流式增量**不成立——增量帧数由模型决定，
不由人决定。

一段约 200 字回复的转写帧日志（真实模型）：

| | stderr 总行数 | 帧日志行数 | 其中增量帧 |
|---|---|---|---|
| 逐帧一行 | **622** | 587 | **580** |
| 折行后 | **44** | 9 | 2（区间统计） |

即 93% 的日志是 `[T#N] <id> - Update +1c` 这类行。要在这几百行里找"工具什么时候
开始跑的"需要 `grep`，而时间线本该一眼看完。

### 10.2 机制：只折日志，不碰载荷

`DeltaLogCoalescer`（`transcript.rs`）：相邻的、**同 `message.id`** 且**纯流式增量**
（带 `delta`、无 `status`）的帧并入同一个 run，不产出日志行；换 id、或该帧带了
状态迁移 / 全量正文、或显式冲刷（`persisted` / `clear`）时，把 run 渲染成**一行**。

```text
单帧（与不折行逐字相同）      [T#7] a - Update +3c
多帧（带区间 / 帧数 / 累计字符）[T#4..473] a - Update 470 帧 / +470c
```

状态帧（`Start` / `End` / `Removed` 等）**一律不折**——它们才是时间线上的骨架。

`seq` 分配与投递**一行代码都没动**——折行器只被 `emit` 用于决定日志。
（§10.4 之后，折行统计行落在 `DEBUG`：默认输出里它也不再出现。）

**与投递合帧的关系**：投递侧的合帧是**另一个**机制（`Transcript::deliver`，
按 `DELIVER_WINDOW_MS` 的时间窗口合并**载荷**）。两者要保住的东西不同——日志要保住
"一次增长有多少帧、多少字符"这个**过程量**（所以按帧序折叠、并记录首末帧号），
投递要保住"正文一个字符不少"这个**正确性**（所以按时间窗口合并、与帧序无关）。
触发条件不同，因此不共用一个结构（§8 #28）。

### 10.3 折行后的时间线（同一场景）

```text
[T#1] u… - Start
[T#2] 8d8c16bb streaming Start
[T#3] ed59707c streaming Start        ← 推理节点
[T#4..328] ed59707c - Update 325 帧 / +1536c
[T#329] e8f0b51b streaming Start      ← 正文节点
[T#330..611] e8f0b51b - Update 282 帧 / +479c
[T#612] ed59707c completed End
[T#613] e8f0b51b completed End
[T#614] 8d8c16bb completed End
```

结构一眼可见：两个内容节点各自增长了多少、谁先谁后、`seq` 如何分配。
（下面这段是**折行但未分级**时的形态。§10.4 分级之后，`Update` 统计行移入 `DEBUG`，
默认输出只剩 `Start` / `End` 这些骨架行。）

### 10.4 日志分级（骨架 / 细节）

折行把"一次回复几百行"降到几行，但**剩下的行并非同等重要**。一轮工具对话里真正
要读的是**骨架**：什么节点出现了、什么时候结束、什么时候停下来等人；而 `Update`
帧（`pending → streaming` 的迁移、正文替换、仅 `meta` 变更）与折行统计都只是过程量。

于是核心日志分两级（`FrameLogLevel`），判据是**相位**（`frame_log_of`，机械判别）：

| 相位 | 条件 | 级别 | 例 |
|---|---|---|---|
| `Start` | 节点在帧前不在内存图中 | `INFO` | `[T#3] 6004d9e9 streaming Start =12c` |
| `Wait` | 迁到 `waiting_user_action` | `INFO` | `[T#12] bca66001 waiting_user_action Wait` |
| `End` | 迁到任一终态词（`completed` / `failed` / `aborted` / `removed`） | `INFO` | `[T#14] 05a937cd completed End` |
| `Update` | 其余 | `DEBUG` | `[T#15] bca66001 streaming Update` |

折行统计行（`[T#4..583] … N 帧 / +Nc`）同为 `DEBUG`。**折行只对 `Detail` 开放**——
骨架帧一律各自留行，`DeltaLogCoalescer::feed` 的 `foldable` 参数就是这个开关。
首帧尤其不能折（§8 #28）：`apply` 明确允许"未知 id 的增量帧自给自足"，故首帧可能
恰好是纯增量；它一旦被吞掉，时间线就缺掉一个节点的起点与 `seq`。测试侧的锚：
`a_skeleton_frame_is_never_folded`、`frame_log_splits_skeleton_from_detail`。

`waiting_user_action` 是**独立的骨架相位**：它既不是结束（用户回完节点还会继续长），
也绝不该沉到 `DEBUG`——**要人做事**的时刻必须默认可见。

一次「推理 + 正文 + 工具调用 + 收尾」的两轮对话（CLI）实测：

| | stderr 总行数 | 转写帧行数 |
|---|---|---|
| 只要等级（默认 `INFO`） | 47 | **14**（全是骨架） |
| `SYMBIO_LOG=debug` | 69 | 19（+ 5 行细节：`Update` 与折行统计） |

默认输出（`INFO` 的全部转写帧行，逐字）：

```text
[T#1] u1a0c89257fa0 completed Start =18c      ← 用户消息
[T#2] a299b4ea streaming Start                ← Turn
[T#3] 6004d9e9 streaming Start =12c           ← 推理节点
[T#5] bf2f3488 streaming Start =0c            ← 工具调用（参数从空开始，逐帧长到 22c）
[T#8] ce528d47 streaming Start =6c            ← 正文节点
[T#13] 6004d9e9 completed End
[T#14] ce528d47 completed End
[T#16] ee4031f0-… completed Start =28c        ← 工具响应
[T#17] bf2f3488 completed End                 ← 工具调用终态（在结果之后）
[T#18] a299b4ea completed End
[T#19] 47562921 streaming Start               ← 下一轮
[T#20] 10b9741d streaming Start =6c
[T#27] 10b9741d completed End
[T#28] 47562921 completed End
```

骨架一眼看完：**谁出现、谁结束、`seq` 怎么排**。`INFO` 与 `DEBUG` 的差别**只在
stderr 的行数**——`seq` 分配、载荷、投递一个字节都没变（§8 #28）。

## 11. 为什么资源变更留在 VDFS

会话叶子上变的东西分两类，都走 `kind = "vdfs"` 这一条通道，但**载荷形状不同**：

| 会话叶子上变的东西 | 载荷 | 消费端收敛 |
|---|---|---|
| 运行态（`working` / 终态 / 结局 / 警告 / 错误） | `data` = `VdfsNode`（全量节点视图，与 `stat` 同源） | **零回读**就地落定 |
| 资源（创建 / 删除 / 改名 / 标题 / metadata） | **无载荷** | 回读 `stat` 分辨删除；其余防抖重拉清单 |

**运行态为什么带视图**：状态迁移是最需要即时的路径，而视图在**调用那一刻**从权威源
构造（`session_node`，与 `stat` 同一构造点），不是缓存副本 ⇒ 一次状态迁移零回读。
丢一次不要紧——状态幂等，下一次 `list` / 回读收敛。

**资源为什么无载荷**：改名 / metadata 写入是**粗粒度**的，消费方本来就按"重拉清单"
处理；捎带快照只会让每个消费端都背一次"逐字段合并"的成本。只关心运行态的消费端
（CLI / 心跳守护）收到无载荷信号即等于"与本轮无关"，直接丢弃即可——判据是**用途**，
不是"无载荷"本身。

**资源为什么留在 VDFS、不跟着消息一起走**：创建 / 删除 / 改名 / 标题 / metadata 覆盖
**发生在没有在途轮次的时候**——此刻没有活跃转写可供依附。而它们都是**幂等**的
（消费端回读即得权威值），因此不需要一条有序流来承载：走 VDFS 变更 + 回读收敛即可。

**为什么两者可以在同一条通道上**：顺序是**节点属性**（`ChatMessage.seq`），到达顺序
不参与排序，因此不需要"用一条带序号的流来承载状态"这种机制（决策见 ADR-025）。
资源信号与运行态都是幂等的（视图 / 回读），可以丢、可以重放、可以与其他变更交错到达；
唯一的顺序要求留给纯增量（§4.2）。
