# 会话消息的 VDFS 化 —— 转写即列表，流式即追加

> 前置阅读：[vdfs.md](../../../../../docs/design/vdfs.md)（机制规范）、[vdfs-frontend.md](../../../../../docs/design/vdfs-frontend.md)（前端页面规范）。
>
> 本文回答一个问题：**会话消息如何整体并入 VDFS 体系**，以及为什么
> 「会话列表本身也是列表，流模式其实就是列表项的变更」不是一句类比，
> 而是可以直接落地的机制判断。取舍的裁决见
> [ADR-025](../../../../../docs/DECISIONS.md)。

---

## 1. 命题

会话清单与会话消息共用**同一套读入口与实时入口**：

| 数据 | 读入口 | 实时入口 |
|---|---|---|
| 会话清单 | `vdfs/list(<根>/session)` | `kind = "vdfs"` 变更 |
| 会话消息（转写） | `vdfs/read(<根>/session/<sid>)`，一次拿整份历史 | `kind = "vdfs"` 变更 |
| 会话运行态 | `<根>/session/<sid>` 的节点视图 | `kind = "vdfs"` 变更 |

命题是：**消息不需要自己的读协议，它就是一张列表**。流式输出也不是另一种模式，
它是「列表最后一项的内容在增长」——同一地址上的正文追加。

会话域因此只剩**两条**路由：`chat/send`（发言 / 编排）与 `chat/abort`（控制）——
且 `chat/send` 本身也只是「往收件箱写一条」的薄包装（§5.3），用户消息只有这一个入口。
「会话在不在」这类问题走**进程内纯接口探测**：`Plugin::get_vfs_provider()` 取
provider，`stat("<挂载名>/<sid>")` 判 `attributes.message_count`——既不占一条路由，
也不必为回答「在不在」读回整份历史。实时面只有 `kind = "vdfs"` 一条频道。

## 2. 为什么成立

### 2.1 转写天然满足列表的全部条件

| 列表的性质 | 转写的实际情况 |
|---|---|
| 有序 | `seq` 是**唯一权威顺序锚点**（见 `chat_message.rs` 的 `seq` 文档） |
| 每项有稳定标识 | `ChatMessage.id` |
| 每项有独立内容 | `content`（正文） |
| 项可增、可删、可改 | 追加、删除某条及其后、状态迁移 |
| 顺序与内容分离 | 顺序 = `seq`；内容 = `content` |

所以「会话内部」和「`<根>/session` 根目录」在机制上是**同一种东西**，
只是层级不同。既然根目录已经是 VDFS 列表，没有理由内层反而不是。

### 2.2 流式不是模式，是变更

消息的实时形态就是**一个节点在改变**。信封是 `{path, data?}`：`path` 恒为被变更
节点**自身**的地址，语义全在 `data` 的字段上。

| `data` 里的字段 | 语义 | 消费端动作 |
|---|---|---|
| `delta` | 该节点正文**尾部追加**了这些字符 | 拼接，**不重读** |
| `content` | 该节点正文**整条替换** | 就地替换 |
| `status = removed` | 该节点没了 | 就地移除 |
| （`data` 缺失） | 无载荷资源信号 | 回读收敛（`NotFound` 即删除） |

**没有操作枚举**：`path` 已经指明是哪个节点，字段已经说明它怎么了。一次流式响应
会产生几十到上百帧；若每帧都靠「重读该节点」来表达，流量是 O(n²)。尾部追加必须能
**零回读**地表达——这是 `delta` 存在的唯一理由。

集合级的两种删除语义由**节点动作**承担：`action(<sid>/message/<mid>, "truncate")`
（该条**及其之后**全部没了）与 `action(<sid>/message, "clear")`（列表清空）。
两者下发的是**逐条移除帧**，每条落在被删消息自己的地址上，载荷是
`ChatMessage.status = removed`——「那个节点没了」的元数据，不需要集合级的新取值。

## 3. 地址与节点形状

### 3.1 地址空间

```text
<根>/session/                          会话清单
<根>/session/<sid>                     单个会话（ext = session，点开即聊天工作区）
<根>/session/<sid>/message             转写列表（l 位）
<根>/session/<sid>/message/<mid>       单条消息（ext = message，r 位）
<根>/session/<sid>/inbox              收件箱：待消费的用户消息（l 位，写即入队）
<根>/session/<sid>/inbox/<iid>        单条待消费消息（ext = message，kind = inbox）
<根>/session/<sid>/subsession[/<sub>]  子会话清单 / 单个子会话
<根>/session/<sid>/workdir[/<rel>]     工作目录树
```

`消息` 是会话**本体**（转写），因此排在内置子目录的第一位。

集合项的地址形状统一为 `<sid>/<集合段>/<项 id>`——身份就是末段。会话是**容器**，
其下是若干**并列的集合**（消息 / 收件箱 / 子会话 / 记忆 / 工作目录），
因此机制不认识任何一类集合：新增一类集合只需在 `internal_dirs` 里
声明一个段，信封与消费端都不动（`收件箱` 就是照这条加进来的那一个）。

### 3.2 列表项的分工：正文进内容，结构进 attributes

```text
read(<根>/session/<sid>/message/<mid>)
  → VdfsContent::text  = 这条消息的正文（流式追加的正是它）
  → VdfsNode.attributes = { role, type, tool_name, parent_id, tool_call_id, seq, error, meta }
  → VdfsNode.ext        = "message"
  → VdfsNode.status     = pending | streaming | waiting_user_action
                          | completed | aborted | failed | removed
  → VdfsNode.title      = 角色（工具调用补工具名：「助手 · vdfs_list」）
  → VdfsNode.description = 正文首行预览（限 60 字符）
```

`status` **原样透传** `MessageStatus` 的状态词，不为场景再造一套：把 `completed`
与「未标注」都归成 VDFS 的 `active`，只会让消费端必须把 `active` **猜回**
`completed`（一次信息丢失加一次还原）。会话节点的 `active`（空闲）与消息的
`completed`（已结束）本来就是两件事，不共用词。

为什么这样切分：

- **正文必须在内容里**——否则「追加」无法表达（JSON 文档的尾部追加没有语义）；
- **结构必须在 `attributes` 里**——`role` / `type` / `parent_id` 是场景数据，
  VDFS 只透传，渲染器按 `ext` 自行取用（与 `session_node` 挂 `message_count` 同一手法）；
- **组合节点（`turn` / `tool_call`）没有正文**：`read` 退化为它们的 JSON 视图，
  使前端与 LLM 在同一地址上都能取到完整结构。

### 3.3 顺序

列表顺序**只认 `seq`**（稳定排序，缺 `seq` 的排最后并保持原有相对顺序）。
这与 `ChatMessage.seq` 的既有契约完全一致：`timestamp` 会并列、会回拨、会缺失，
`seq` 由存储在写入时分配、单调且永不并列。

**`seq` 不随整表重写而改变。** 这是硬约束，不是优化：`seq` 是**消费者（前端）手里的
顺序锚点**——前端在流式阶段就按它排好了序，整表重写若把既有消息改成新号，
两边就各持一套互不相容的序号，同一条消息会以两种形态排到列表的两个位置。

因此 `replace_messages` 的契约是**只补缺号**（`assign_seq`）：无号项从**相邻的既有序号
向外让位**——开头段整体落在首号之前（往下）、末尾段接在末号之后（往上）、夹缝用间隙；
**既有序号一个都不改**。压缩（前缀重写）的列表是 `[快照, 保留区…]`，快照的槽位序号由
调用方显式给出（`compression::snapshot_slot_seq` = `保留区首条 seq − 1`），使新列表
**本来就单调**，`assign_seq` 于是退化为"只填缺号"。

### 3.4 落库回包 = 交回权威序号（因此「每条落库消息都必须有出口」）

位置序号是**创建时**就有的节点属性，来源有两段：

| 段 | 分配者 | 量级 |
|---|---|---|
| **在途号** | 转写（`Transcript::apply`）在**首次见到该节点时**分配，起点 `INFLIGHT_SEQ_BASE` | 远离存储号段（`1 << 50`），必然排在全部历史之后——两个并行工具的消息即便在同一毫秒创建也能定序 |
| **权威号** | 存储在**写入时**分配，单调且永不并列 | 「第几条消息」量级 |

在途号**永不落库**：存储边界（`append_messages` / `replace_messages`）按号段拒收它
（`is_inflight_seq`）并重新分配。落库后由一条**带存储分配 `seq` 的完整消息帧**把它
交回权威号——这是**唯一**的换号时机：`Transcript::apply` 只在帧带 `seq` 时采用外来值。
于是有一条不变量：

> **每一条被落库的消息都必须发一次变更（带存储分配的 `seq`）。**

漏一条，那条消息就**永远只有在途号**。一旦本地游标与存储水位错开（截断 / 重试 /
压缩重写之后很常见），同一棵树上就并存两套号——排序随之错位，而只有整份回读
（刷新 / 重开会话）才会恢复。实测形态：用户消息持小存储号（1、4）、助手侧节点持
在途号（`1 << 50 + n`），于是第二轮的用户消息排到了第一轮的助手消息**之前**，
界面显示成 `user-user-assistant-assistant`（端到端回归：`e2e/cases/t16-live-order.mjs`）。

**这条不变量的落地点是「谁落库、谁发帧」**：`append_messages` 把落库后的权威副本
交回调用方（它返回消息而非条数的唯一原因——号是临界区内补在私有副本上的，调用方
手里那条没有号），每个落库调用点随即下发：

| 落库调用点 | 出口 |
|---|---|
| 助手侧增量落库（`chat_loop/io.rs::persist_messages`） | `EventSink::emit`（逐条权威副本） |
| 用户发言（`orchestrator/entry.rs`） | `SessionPlugin::emit_persisted_messages` |
| 压缩节点（`chat_loop/compress.rs`） | `CompressionEmitter::emit_persisted` |

`content` 整条替换（而不是 `delta`）：持有乐观副本 / 在途副本的消费端要**替换**成
权威正文，而不是往自己那份后面再拼一遍。这也是 `delta` / `content` 两个字段必须
分开的原因——同一个消费端既可能需要追加（流式），也可能需要替换（权威副本对齐），
而帧必须自证是哪一种。

前端收到带权威号的帧即**就地覆盖**本地号，不回读。流式期间与回读的竞争由**代际守卫**
处理：读取期间若本端正文又变过，本地比这次响应新，该响应作废（`useVdfs` 的详情视图与
`sessionTranscriptSync` 各持一个实例——两者的作废时机不同，不共用）。

## 4. 变更语义（实时链路）

订阅地址：`<根>/session/<sid>/message`（或更上层的 `<根>/session`）。**落点**恒为被
变更节点**自身**的地址——消息是 `<根>/session/<sid>/message/<mid>` 这个文件，会话
运行态是 `<根>/session/<sid>` 这个节点。

| 场景 | `path`（落点） | `data` | 消费端 |
|---|---|---|---|
| 新增一条消息 | 该消息节点自身 | 该节点的**全量副本**（首帧） | 插入列表项（**零回读**） |
| 正文流式追加 | 该消息节点自身 | `ChatMessage{ id, delta }` | 尾部拼接，**不重读** |
| 状态迁移 / 整条替换 | 该消息节点自身 | `ChatMessage`（带 `status` 或 `content`） | 就地收敛（**零回读**） |
| 落库回包（含用户发言） | 该消息节点自身 | 存储权威副本（带存储 `seq` / `timestamp`） | 就地替换成权威版本；权威 `seq` 由此换入（§3.4） |
| 截断（`action "truncate"`） | **每条被删消息各自的地址** | `ChatMessage{ status: removed }` | 逐条就地移除；回执 `data` = 权威被删 id 列表 |
| 清空（`action "clear"`） | **每条被删消息各自的地址** | `ChatMessage{ status: removed }` | 同上 |
| 会话运行态 | `<sid>` | `VdfsNode`（全量节点视图） | 就地收敛（**零回读**）；`data` 缺失 ⇒ 回读收敛（`NotFound` 即删除） |
| 入队一条用户消息 | `<sid>/inbox/<iid>` | 该条目的节点视图（`kind = inbox`） | 列表里多一条「待消费」（**零回读**） |
| 取消排队中的条目 / 清空队列 | 每条被取消条目各自的地址 | 无载荷 | 就地移除（回读为 `NotFound` 即收敛） |

**为什么截断 / 清空是逐条下发，而不是「目录整份重读」**：移除帧是**元数据**
（路径 + 状态，每条几十字节），而「清空 + 从存储整份重读」会把所有**保留的**消息
重传一遍——对「删几条」这个动作，逐条通知恰恰是更便宜的形态。回执里的权威 id 列表
让调用方不依赖推送也能幂等对齐。这两种集合语义都不借用 `delete`（`delete` 是
「**这一个**节点没了」），也不在信封上挂「级联」标志位——「是哪种删除」不该需要
同时读两个字段才判得对。

**整表重写（L2 语义压缩）也必须发变更。** 压缩把旧历史蒸馏成快照、新列表变成
`[快照, 保留区…]`——这是**列表构成**的改变，不是某一条消息的状态迁移。它由
`emit_transcript_rewritten` 下发：被压掉的逐条移除帧 + 新首条一条完整消息帧
（`content` 整条替换）。只写存储而不发变更，前端就会永久停在压缩前的历史，
而没有任何机制会纠正它。

**唯一订阅通道**是 `kind = "vdfs"`：会话**任何**面向外部的变化都走它——消息走消息
节点，`title` / `status` / 结局走会话节点。

### 4.0 变更**不重放**——因此消费端必须能自愈

本频道**没有帧序号**，丢帧本身不可检测；`VdfsChangeSubscriptions::notify` 在订阅表为空时
**直接返回**（订阅登记是 fire-and-forget 的异步动作）。**丢一次不会重来**，消费端
不能假设「变更一定到齐」。已知的丢帧有两处，都由消费端兜底：

- **通道满**：后端丢帧但**保留订阅**，并补送一条 resync 指令（`VDFS_BUS_RESYNC`）
  ——这是消费端唯一能得知「我刚才漏了东西」的信道指令；
- **连接断开期间**：后端见连接已关会摘除订阅，帧被静默丢弃且**不补 resync**
  （订阅已经不在表里，没人知道该通知谁）。因此**前端重连成功**那一刻必须由本端
  补一次重读。

resync 的动作是「按自己登记的作用域整份重读」——粗粒度，但重读幂等，**足够**；
**不做精确缺口检测**。清单、转写、工作目录各有自己的消费端与重读口。

### 4.1 载荷为什么随变更一起下发

只发「哪里变了」而不发「变成了什么」，消费端就只能自己回读——每次变更 1–2 次往返
（`stat` + `read`）。现行的取舍是**热路径窄、冷路径全**：

| 形状 | `data` 宽度 | 频率 |
|---|---|---|
| 纯增量（同节点正文增长） | 只有 `delta`，O(delta) | 逐帧（流式主干道） |
| 首帧全量副本 / 状态迁移 / 删除 / 整条替换 / 落库回包 | 完整字段 | 每节点几次 |
| 会话运行态 | 全量节点视图 `VdfsNode` | 每轮几次 |

一次会话轮次会产生十几次这类帧，回读方案是净增几十次 IPC；带载荷的帧则**零回读**。
反过来，流式增量必须保持窄：把整节点挂在每帧上，流量立刻退化成 O(n²)，正好抵消
增量存在的意义。于是规则就是上面那句：**热路径窄（只有增量），冷路径全（节点视图
+ 正文快照）**。

**投递可以合帧。** 相邻的**同节点纯增量**在 `DELIVER_WINDOW_MS`（50ms）窗口内由
`Transcript::deliver` 合成一帧再投——语义**逐字等价**（正文一个字符不多不少），一次
流式回复的后端出帧数因此降到约 1/6。非纯增量帧（首帧全量副本 / 状态迁移 / 删除 /
整条替换）必然**立刻发**；窗口过期由每一帧到达时检查，不需要后台定时器。前端在落地
侧另有一层 48ms 的合帧窗口（`sessionTranscriptSync`）——它按会话攒批，省的是每帧一次
store 提交与消息树重建。合帧是**投递层**的优化：线上形状与单帧逐字一致，消费端
无从也无需知道它被合过。

> `data` 是**可选**的：provider 不填时消费端回退到回读（`stat` + `read`）。
> 因此这是纯增益扩展，不构成对任何 provider 的强制。

## 5. 写入：**发言**不走 VDFS，**改写与删除**走

### 5.1 发言不是一次文件写入，而是一次动作

`chat/send` 会触发一整轮编排：模型调用 → 工具执行 → 多轮循环 → 流式落库。
把它建模成 `vdfs/write` 会造成两处语义错位：

1. `vdfs/write` 是**同步返回**的存储操作，而发言是长事务；
2. `vdfs/write` 的语义是「把这段内容存到那个地址」，而发言的语义是
   「以这段内容为输入，跑一轮编排」。

因此 `write` 在 `<根>/session/<sid>/message`（**列表本身**）上**明确拒绝**（`Forbidden`），
`create` 意图在**消息节点**上也一律驳回——新增消息即发言。不是静默降级。

### 5.2 改写与删除是普通的节点操作

判据是**「触发不触发编排」**，不是「碰不碰消息」。

| 操作 | 是不是「发言」 | 入口 |
|---|---|---|
| **新增**一条消息 | 是（触发一整轮编排） | 聊天协议（唯一） |
| **改写**既有消息的字段 | **不是**（纯存储改写，不触发任何编排） | `write(<sid>/message/<mid>)` |
| **删**该条及其后 | 不是 | `action(<sid>/message/<mid>, "truncate")` |
| **清空**历史 | 不是 | `action(<sid>/message, "clear")` |

改写一条消息与改会话标题在机制上是同一类事——都是「把内容存到那个地址」，地址语义
完全成立。前端自发起的那两条操作已在本地收敛，因此后端各有一个「只发变更、不发前端
帧」的入口；漏发任何一条，VDFS 视图都会残留一个已不存在的节点且永不纠正。

新增消息仍然只有一个入口（聊天协议）；「一条消息只有一个地址」也仍然成立——改写与
删除用的正是那个地址。

### 5.3 收件箱：**写即入队**，由空间自己消费

`<sid>/inbox` 是「还没被消费的用户消息」那张列表。它不是第二份转写，而是同一条消息的
**前一态**：

| 阶段 | 住在 | 谁写 |
|---|---|---|
| 已入队、未消费 | `<sid>/inbox/<iid>`（条目） | `vdfs/write(…/inbox[/<iid>])`——`chat/send` 走的就是它 |
| 已消费 | 转写（`<sid>/message/<mid>`） | 统一发送链路（落库 + 发变更） |

写入正文两种形状，判据只有首字符：**以 `{` 起头**即 JSON（`ChatMessage` 字段子集，
`id` 缺失由地址补）；**其余**整段就是消息文本。条目 id 的优先级是「地址末段 > 写体里的
`id` > provider 生成」—— `chat/send` 带的是客户端生成的 id，保留它是必须的：前端先按
自己的 id 放了乐观副本，落库回包若换了 id，那条副本就永远等不到替身。

**运行由空间自己起**：入队后唤醒该实例的收件箱消费者，它在会话**空闲**时取出队首、
调与 `chat/send` 完全相同的执行路径跑一轮，跑完再取下一条（FIFO、忙则排队、不抢占）。
这就是「子智能体空间没有调用方也能跑完整会话」的全部机制（[ADR-026](../../../../../docs/DECISIONS.md)）。

条目**出队即消失**：消费后它已经是转写里的一条消息，不再回队列。因此两种「取消」作用在
不同对象上，各走各的入口：

| 取消什么 | 入口 |
|---|---|
| 排队中（还没被取走） | `vdfs/delete(…/inbox/<iid>)`——找不到即 `NotFound`（已出队的那条不在此列） |
| 正在跑（已出队） | `chat/abort` |

`action(…/inbox, "clear")` 清空待消费队列（= 逐条移除，与转写的 `clear` 同款语义）。

## 6. 不变量

1. **顺序锚点仍是 `seq`**——VDFS 列表序、前端消息表、LLM 上下文三者同源；
2. **一条消息只有一个地址**：`<根>/session/<sid>/message/<mid>`；
3. **正文只有一个位置**：节点内容。`attributes` 只放结构，不放正文；
4. **前端与 LLM 恒等**：同一地址、同一份数据、同一组访问位；
5. **变更只有一个通道**：`kind = "vdfs"`；落点恒为被变更节点**自身**的地址
   （消息 → `<sid>/message/<mid>`，会话运行态 → `<sid>`）；
6. **语义全在字段上**：信封是 `{path, data?}`，没有操作枚举——`delta` 有 ⇒ 尾部追加、
   `content` 有 ⇒ 整条替换、`status = removed` ⇒ 就地移除；`data` 缺失 ⇒ 消费端回读收敛。
   不从节点类型或信封取值反推语义；
7. **首帧必带全量**：未知节点上的窄增量无法建立基线，因此每条消息的第一帧是图里
   合并后的**全量副本**（正文一个字符不少）；
8. **投递可合帧，正文不得少字**：相邻的同节点纯增量在 `DELIVER_WINDOW_MS` 内合成
   一帧，语义逐字等价；非纯增量帧必然立刻发。合帧是投递层的优化，不是协议的一部分；
9. **顺序不靠到达顺序**：`seq` 是**节点属性**，消费端按它排序，与变更的到达先后无关
   （后生成的先到、并行工具的变更混着到，显示都正确）；
10. **发言只有一条链路**：`chat/send` = 往 `<sid>/inbox` 写一条，由空间自己的消费者
    取出后跑一轮——转写列表仍然拒绝直接写入（`write` 在列表目录上被拒、`create` 意图在
    消息节点上被驳回）；改写与删除是普通 VDFS 节点操作（`write` / `action`），不触发
    编排——见 §5.2 / §5.3；
11. **在途消息可读**：`list` / `stat` / `read` 看到的转写 = 落库 ∪ 在途。在途缓冲与
    转写是**同一个 `Arc`**——不是两份需要同步的拷贝；
12. **在途号永不落库**：存储边界拒收在途号并重新分配；落库回包是交回权威号的唯一
    时机（§3.4）；
13. **删除也发变更**：消息级删除（`action("truncate")` / `action("clear")` / 压缩重写）
    一律发逐条移除帧，否则列表会残留已不存在的节点；截断的回执带**权威**被删 id 列表；
14. **变更出自唯一写入点**：`Transcript::apply`——内存图、位置序号、变更投递在同一个
    函数里完成，没有旁路。新增发射路径若绕开它，实时面会**永久**落后，而两条链路
    互不校验，不会有人发现。

## 7. 取舍与风险

| 取舍 | 说明 |
|---|---|
| 组合节点退化为 JSON 视图 | `turn` / `tool_call` 无正文；强行扁平化会丢失层级。JSON 视图是诚实的降级，`attributes.type` 让渲染器知道该按什么渲染 |
| 图片消息只暴露文本部分 | `MessageContent::Parts` 里的 `image_url` 不在正文中。需要时再走 `binary` 内容通道（本期不做） |
| 投递合帧会推迟增量到达 | 窗口 ≤ 50ms，且只在「同节点纯增量」这一种形状上生效；首帧 / 终态 / 删除 / 整条替换必然立刻发，因此没有内容会被无限期扣住。20 次/秒以上的更新率肉眼已看不出分块 |
| `data` 是**可选**载荷 | 带载荷的帧（增量 / 首帧 / 状态迁移 / 落库回包）**零回读**；不带载荷的资源信号回退到回读（`stat` + `read`）。若一律不带，热路径就是净增几十次 IPC/轮次；字段可选，不填时消费者回退回读 |
| 状态词原样透传 | 消息节点用 `MessageStatus` 的七个词，不做有损映射。消费端遇到词表外的状态即丢弃该帧并留 warn——宁可丢一条，也不造出状态错误的消息 |
| 在途号与存储号是两个独立递增的计数器 | 共存的前提只有一条：**在途号永不落库**。一旦某个在途号被当成权威号存下，存储水位就被抬进在途号段，此后两个计数器在同一数值区间各自递增、**必然撞号**。因此这条守卫落在存储边界（而非各调用点） |
| 会话叶子同时是「文档」与「内部区段之父」 | `<根>/session/<sid>` 是叶子（`rw`，内容是整份会话 JSON），其下又挂 `消息` / `子会话` / `工作目录`。这不是矛盾：**叶子是会话本体，区段是它的视图**。好处是整份历史一次 `read` 拿到，省掉专用协议 |
| 在途缓冲与落库转写有重叠窗口 | 每轮结束时落库，随后清空在途缓冲。重叠期内同 id 以在途版本为准且继承 `seq`，因此列表不会出现两份或错序；真正需要警惕的是「清空早于落库」——清空点因此都放在落库之后 |
| 读与流的竞争是**静默**失败 | 旧快照覆盖已应用的增量，不会报错、不会崩溃，只会让 UI 少一段字或多一段字。对策是**代际守卫**：每次正文落地 +1 代，回读发起时取快照，响应回来若代际已变则该响应作废（`useVdfs` 的详情视图与 `sessionTranscriptSync` 各持一个实例） |
| 窄增量帧不自带身份字段 | 帧上只有 `id` 与 `delta`，拿不到 `role` / `type` / `parent_id`；因此**身份未知**的增量先落地（占位）再回读补身份——一次 IPC，换来「帧自给自足、不依赖任何先行帧」 |
| 地址规则只有一份实现 | `..` 判定与前缀比较收敛在 `symbio_core::vdfs_provider`（`vdfs_has_parent_segment` / `vdfs_path_within`），规则与测试各只有一份 |
