## 内容

### 为什么这是**一步**而不是两步

`D-222` 诚实划界 5 原写三步（删端口 → 并守卫 → 统一签名与表）。第 2、3 步在类型层上不可分，
理由是可核的：

- "守卫同处"的落点是**那个唯一的循环体**。三张表 + 三个 `Ctx` 类型 → 一旦把循环体抽成一个函数，
  得到的是"三处调用同一个函数"，而 `TC-1a` 判的是**循环体的份数与选债口的份数**，
  三张表意味着三个 `next(..)` 调用点 ⇒ 选债口仍是三个（`TC-1b` 红）。
- 反过来，只要把表与签名合成一个，守卫就已经在那个唯一的循环里了——不需要单独一步去"并"它。

所以 `D-222` 的兑现顺序已按此订正为两步（**先删后裁**：旧的"三步"表述在裁决里被替换，不留两份）。
把两步合成一次提交也不行：删端口是**可独立回退**的形状改动，它与合表失败时的排查面完全不同。

### 三件事，一件比一件深

| # | 要收的东西 | 今天 | 收法 |
|---|---|---|---|
| 1 | **绑定表**（4 → 1） | 轮内 19 条执行体 / 轮首 4 条 / 汇报 1 条／幕那张表（已删） | 合成一张 `ROWS` 的绑定表；表数由 `run` 签名个数唯一决定——签名一种，表就只可能有一张（第二张表是编译错误，`D-222` 可判断言 C） |
| 2 | **签名**（4 种 → 1 种） | `TurnStep` / `HeadStep` / `ReportStep` 三种借用面，动作是 `for<'a> fn(&'a mut X) -> StepFuture<'a>` | 一个 `Ctx`：那一次动作借走的那片状态的**超集**，动作按步取字段；`run(&mut Ctx)` 之后"另一张表"没有对象 |
| 3 | **环**（4 段 → 1 段） | `chat_loop` 的幕间 `loop`（读 `next_stage_round`）/ `drive_steps`（轮内）/ `drive_head`（轮首，从 `prepare_turn_inputs` 里被调用）/ `drive_report`（批次边界，从 `RoundInjector` 里被调用） | 一个循环体。"再开一幕"是 `continue-turn` 一笔债（`D-222` 裁决 2/3：上界 `MAX_STAGE_ROUNDS` 折进那一行的前件）；轮首与批次边界是**行**，由同一个环按 `prio` 与 `owes` 选中（`drive_report` 今天是一次性选债、不是循环体——它属 `TC-1b` 的"第二选债口"那一类，不是 `TC-1a` 的循环体那一类） |

### 第 3 件是真正的难点：一个外层循环 + 两个嵌套点

这三处不是"顺手"，是 `TC-1c` 第五道守卫的三个反例：

- **幕间**：`chat_loop` 的外层 `loop` 读完 `next_stage_round` 决定"再开不开一幕"。它必须变成表上的一笔债
  （`continue-turn`）：轮已经存在，「再跑一段」就有完整的前件（`closure = exhausted` ∧ 轮次未到上限）与出口
  （新的 `round` 格）。留在代码里就是"按步骤号决定下一步"——判据 2 的最后一格（`D-222` 裁决 2/3）。

- **轮首**：`prepare_turn_inputs` 末尾调 `drive_head`。它之所以能成立，是因为那时的 `TurnState`
  还没有被轮内借走。合表之后，`policy.classify` / `policy.compress` / `policy.recall` / `policy.reflex`
  四行就是环的**开头几步**——幕一开，环先按 `prio` 选中它们，`execute-turn`（60）自然排在后面。
- **批次边界**：`RoundInjector` 每批工具跑完就自己调 `drive_report`。它之所以是嵌套，是因为
  "跑完一批工具"发生在 `dispatch-tools` 这个**动作内部**；而环本来就停在两次动作之间——
  把派发撤掉，`policy.report` 的 `report_due` 前件在下一问问表时天然为真，环自己会选中它。
  这一条同时解释了"为什么它有一个专用视图"：**视图是给选债用的，不是给回调用的**。

**判据形态**：合成之后，"再起一个环"应当**写不出来**——动作只拿到 `&mut Ctx`，
拿不到第二个 `&mut Session`/`&dyn Store` 的组合。类型守不住的地方（比如把 `store` 也放进 `Ctx`）
就是设计没做完，不许用运行期 `if` 补。

### 不做什么

- **不动求解器**：`ring::drive`（选债半边）字节冻结；本任务动的是调用它的那一侧。
- **不动 `TurnState` 的字段**：只把它从"三个借用面各自持有"变成"一个 `Ctx` 里的一项"。
  字段收敛归 [T-013](013-冗余残留收敛.md "T-013-冗余残留收敛")。
- **不删行**：19+4+1 行合成一张表之后**行数不变**。行的增删属各自的行化裁决，不属本任务。
- **不改 `MAX_STEPS_PER_DRIVE` 的取值**：上界是策略（`D-222` 裁决 3 把 `MAX_STAGE_ROUNDS` 折进前件，
  那一条在 T-005 随幕一起消失；轮内上界仍在派发器里，取值不变）。

### 开工记（2026-10-28）：五个选债口，不是四个

「在途可观测」闭环之后（`573d6415`）先数了一遍现场，两件事与上面的计划不同：

1. **`drive_steps` 有两个调用点**，不是一个：`turn_exec/call.rs:264` 与 `turn_exec/persist.rs:282`。
   加上幕间 `loop`（`chat_loop`）、`drive_head`（`chat_loop/inputs.rs:192`）、`drive_report`
   （`turn_exec/call.rs:162`，嵌在工具派发的动作里）——今天一共有**五个**选债口/循环体。
   合并的判据因此不止「三个 `drive_*` 收成一个」，还要把 `drive_steps` 的两个入口并成一个。
2. **`TurnStep` 现在只剩两处借用**（端口已 owned 化）：`session: &'a mut TurnSession` 与
   `dispatch: Option<&'a dyn ToolDispatch>`。`HeadStep` 那边仍有四处借用（编排器 / 请求 /
   会话上下文 / 本轮状态），`ReportStep` 是七项纯引用/值。

由此定下第一刀：**先把 `dispatch` 也 `Arc` 化**，用的是 `T-015` 已经走过一遍的手法
（`store` / `llm` / `sink` / `tools` 都这么改的），行为零变化、单独可回退。它要换来的是
`TurnStep` 只剩 `session` 一处借用——那时 `Ctx` 是否带生命周期参数就成了**唯一**待定的事，
而这件事决定四种动作能不能共用同一个 `Action` 类型（「签名一种」的可判断言就在这上面）。

第二刀才是 `Ctx` 的字段面：轮首那五项（编排器 / 请求 / 会话上下文 / 本轮状态）在轮内能否
从 `TurnSession` 派生，决定 `Ctx` 是同名超集还是需要分阶段构造。这一问要读 `chat_loop`
的幕内时序，不能凭形状猜——所以它排在 `dispatch` 那一刀之后，而不是之前。

### 第一刀已落地：`dispatch` 也 `Arc` 化

`TurnStep` 现在**只剩 `session` 一处借用**（`store` / `llm` / `sink` / `tools` 早已 owned，
`dispatch` 这一步跟上）。改法与前四个端口逐字同手法：

- `TurnStep.dispatch` 与 `drive_steps` 的入参从 `Option<&dyn ToolDispatch>` 变成
  `Option<Arc<dyn ToolDispatch>>`；动作体按步取 `step.dispatch.as_deref()` 交给草稿。
  于是 `turn_runner` 的三个方法（`open` / `authorize` / `dispatch`）**签名一字未动**——
  `as_deref()` 把 Arc 退回 `&dyn`，借用只活在那个动作里。
- 生产侧构造点（`turn_exec/call.rs`）把 `SessionDispatchPort` 包进 `Arc`，传 `clone()`；
  执行完之后 `take_produced` / `take_derived` 照旧（Arc 的 Deref）。
- 夹具侧 13 处实参改成 `Some(arc.clone())`，9 处 `let dispatch = …` 改成 `Arc::new(…)`——
  后续 `dispatch.take_*()` 之类的读法经 Deref 不动。

**行为零变化**：`cargo test -p symbio-plugin-loop --lib` 510 绿、`node scripts/gate.mjs`
161/162（唯一未判定是 MSRV 环境跳过）、e2e 86/86、clippy 零告警。

至此 `Ctx` 的形状问题收窄成一句话：**它带不带来第二个生命周期**。三种 `Step` 的借用面并起来
是 `&mut TurnSession` / `&mut SessionContext` / `&mut TurnState` 三处**互不重叠**的可变借用加
若干 `&T`，所以「一个 `Ctx<'a>`、一个生命周期」在类型上成立——前提是这三样在同一个幕里同时
存在。这正是要核的那件事：轮首四行跑的时候 `TurnSession` 还没建（它由 `TurnRunner::begin`
产出），要并成一个 `Ctx`，得让草稿在**幕一开**就存在，而轮首那四行改成它的开头几步。

### 第三刀（2026-10-28）：幕的推进折成一格；`Ctx` 的时序问题定形

1. **幕间两条判据搬进声明**（`D-222` 裁决 2）：新增视图 `turn_next_round`——把
   `turn_head` 的 `closure` 与 `round` 再折一格，吐 `{round: N+1}` 或空。
   `next_stage_round` 只剩「取那一格」，`MAX_STAGE_ROUNDS` / `has_next_round` 跟着搬到
   `control_decl`（策略跟着行走，不跟着投影走；`loop_rows` 只留一条 `pub(crate) use` 的路径）。
   这一步是 `continue-turn` 行的**前置**：行立起来时 `owes` 直接指这一格，判据侧零改动。
   行为零变化（`cargo test -p symbio-plugin-loop --lib` 512 绿）。

2. **`Ctx` 的第二问已裁**（`D-222` 订正 3）：不需要第二个生命周期；**草稿在幕首就建**，
   `Ctx.session` 是 `&mut TurnSession` 而不是 `Option`，轮首四行改当那个唯一环的开头几步。
   裁的依据是终态判据（`TC-1a` 判循环体份数 / 裁决 8 要求中止守卫在环里且不许用运行期断言
   补类型洞），不是实现难易——「被中止的幕不再跑判决 / 压缩 / 召回」是「守卫在环首」的
   直接后果，不是副作用。下面是当时的现场（留作施工时的对照）：
   `stage::run_stage` 的三段是「备输入（末尾起轮首那台 host）→ 跑一轮（`TurnRunner::begin`
   在这里才产出 `TurnSession`）→ 收好产出」。轮首四行跑的时候草稿还不存在，而 `Ctx` 是
   「那一次动作借走的那片状态的**超集**」⇒ 三条出路各自有代价，得先裁一条再动字段面：

   | 出路 | 形状 | 代价 |
   |---|---|---|
   | 草稿提前到幕首 | `begin` 搬到 `prepare` 之前，`Ctx` 的字段面一次填满 | **行为改变**：中止的检查点提前到轮首四行之前——被中止的幕不再跑判决 / 压缩 / 召回。要一次裁决 |
   | `session: Option<&mut TurnSession>` | 零行为变化 | 动作里出现 `expect("轮内动作必有草稿")`——用运行期断言补类型洞，`D-222` 裁决 8 明确不许 |
   | 轮首四行搬进环 | 就是本任务第 3 件的终态 | `policy.compress` 的产出在 `prepare` 结束时被取走（`consolidation`），搬进环会改「压缩影响哪一幕」的语义 |

   结论：`Ctx` 的形状不是类型问题，是**幕首时序**问题。三条里第一条看起来最省（一次裁决换
   一个填满的字段面），但它改的是中止语义，不该在实现里顺手定。

### 第四刀（2026-10-28）：备输入的产物从 `TurnInput` 退场——「建草稿」与「填」分开

`D-222` 订正 3 裁的是「草稿在幕首就建」。它有一个**类型前件**：`TurnRunner::begin` 的
入参不能含「备输入之后才有」的东西，否则草稿永远只能在备输入之后建，裁决就落不了地。

清点 `TurnInput` 的 17 个字段，真正「开幕就有」的是 15 个；两个不满足：

| 字段 | 谁产 | 为什么开幕时没有 |
|---|---|---|
| `prefix` | `prepare_turn_inputs` 的 ⑥（请求视图） | ⑥ 依赖召回寄存的 `context_sections`，而召回是环里的一行 |
| `reflex` | 轮首 `policy.reflex` 那一行的寄存物 | 同上：它也是环里的一行 |

于是它们退场，入口改成 `TurnSession::set_prefix` / `set_reflex`，填的时机在 begin 之后、
**任何选债之前**——这是硬前件不是便利：`set_prefix` 必须早于第一次请求（它改的是基线
prompt 的第一条），`set_reflex` 必须早于第一次选债（它决定环先选中 `close-turn` 还是
`announce-model`）。两样打成一个包 `TurnFeed` 而不是两个位置参数：它们是同一时刻到的
一批东西，而派发器的形参已经够宽。

**这份清点漏了三个**（第六刀施工时补上，同一判据「备输入之后才有」）：

| 字段 | 谁产 | 为什么开幕时没有 |
|---|---|---|
| `tier` | 接缝上由 `turn_head.reflex_answered` 折出（`D-223` 订正 1） | 快路作答是 `policy.reflex` 那一行的出口，幕首还没有那一格 |
| `opening_text` | 轮首判决行的 `Escalate` 首响（`Spoke`） | 同上：判决是环里的一行 |
| `opening_dialog` | 同上（节点身份与标记） | 同上 |

三者与 `prefix` / `reflex` 不同之处只在**落点**：`prefix` / `reflex` 进草稿（环内要用），
而 `opening` / `tier` 只是**入格 + 上线**，草稿一格都不读 ⇒ 它们的入口不是 `set_*`，是接缝上
两个自由函数（`chat_loop::land_opening` / `land_dispatch`），与 `begin_drive` 同一族。

**`D-048` 的双向完整性复核跟着前缀走**：`declared` 只有在前缀真被插进去的那一刻才有值，
留在 `prepare_turn` 里就成了「声明了却没插」的假一致。复核用的快照按建草稿时那一份
（`Prepared::full_snapshot`）与同一个窗口重裁——与原实现逐字同输入，只是时机从「构造期」
挪到了「填前缀期」；`Prepared` 为此多存一格 `window_turns`（不存裁好的切片：`full_snapshot`
已经是全量）。

行为零变化：`cargo test -p symbio-plugin-loop --lib` 512 绿、clippy 零告警。
「前缀排在基线之前」与「快路零往返」两条用例改走带 `feed` 的接缝（`drive_with_actors`
的第二个接缝，第一个是换绑定表），断言一条不动——它们钉的是**位置**与**往返数**，
不钉「前缀从哪个字段进来」。

**下一刀的位置因此确定**：`begin` 从 `drive_steps` 里提到 `run_stage` 的 ①② 之后、
③（轮首派发点）之前。那时 `TurnFeed` 的两样由 ③ 之后的代码填，`drive_steps` 只剩
`&mut TurnSession` 一个可变借用——`Ctx` 的 `session` 字段因此可以不是 `Option`。

### 第五刀（2026-10-28）：`begin` 从派发器里出来——`drive_steps` 只驱动一个已存在的草稿

上一刀把「填」分出来了，这一刀把「建」也分出来：`drive_steps` 的第一参从
`input: TurnInput` 变成 `session: &mut TurnSession`，「开一轮」归调用方。

形状上的三件事，都不是搬运：

1. **`drive_steps` 再也拿不到第二份 `TurnSession`**。`D-222` 裁决 8 的第五道守卫
   （不重入）是「由类型守」——它要求「动作里再起一个环」**写不出来**。草稿从入参进来
   之后，本函数手里只有一个 `&mut`，它没法再构造一个；而在此之前，`begin` 在里面，
   「再开一轮」至少是语法上写得出的一行。
2. **`TurnSessionBegin::Done` 的早退挪到调用方**。它本来就是「本幕没有环可跑」的
   两种情形（首请求前中止 / 空答兜底），不是环的出口——放在驱动函数里，等于让驱动
   函数也负责「开」。
3. **`TurnFeed` 退场**。「建」与「填」都归调用方之后，两样备输入的产物直接是两次
   `set_*`，再包一层只是给夹具用；夹具需要时自己收两个 `Option`。

调用方因此是三步（`begin` → 填 → `drive_steps`），两处生产（工具轮 / 定稿答话轮）
与夹具门面逐字同序。**下一刀**把这三步整体上提到 `run_stage`，`begin` 才真正落在
「任何选债之前」——本轮只是把它从派发器里请出来。

行为零变化：`cargo test -p symbio-plugin-loop --lib` 512 绿、clippy 零告警。

### 第六刀的前件已裁（2026-10-28）：档位读视图，`begin` 才能排在环首

第五刀之后 `begin` 已经在调用方手里，但调用点还在 `call_model` 里（环尾）。要把它提到
幕首，还差一块：档位字段（`tier`）的取值链是「`reflex.is_some()` ⇒ Reflex 档」，而
`reflex` 是 `policy.reflex`（`prio` 50）那一行的寄存物——档位要等环跑到最后。

`D-223`（裁在 [DE-022](../003-design/022-行表与派发面.md "DE-022-行表与派发面")：档位是 `Decl::tier` 的
读法，归属行表那一卷）先裁成「读 `turn_head` 的 `skill_hit` ∧ `!resumed`，幕首可判」——**这一条
在施工前就被自己推翻了**（`D-223` 订正 1）：`skill_hit` 由召回行的出口格折出，幕首那一刻恒
`false`。订正后的规则是：**档位在接缝（轮首四行跑完、内环未起）读 `turn_head.reflex_answered`**，
`turn.dispatch` 由那一次定档落，档位字段退场。

于是第六刀的施工图完整了：

| # | 做什么 | 为什么躲不开 |
|---|---|---|
| 0 | `opening_text` / `opening_dialog` / `tier` 从 `TurnInput` 退场，改由接缝上两个落格函数（`land_opening` / `land_dispatch`）落 | 三者都是「备输入之后才有」；`opening` 是判决行的首响，`tier` 是快路行的出口。它们只入格、草稿不读 ⇒ 不是 `set_*`，是接缝的自由函数 |
| 1 | `assemble_turn` 拆两段：幕首（`store` / `bridge` / `emitter` / `actor` / `to`）与备输入之后（压缩入格，读 `consolidation`） | 压缩的寄存位在 ③ 之后才取走（S2.7-b2），那一段只能留在原处 |
| 2 | `turn_root_id` 的分配点从 `prepare_turn_inputs` 的 ④ 提到 `run_stage`（`turn.resume_root.take()` 或 `llm_short_id()`） | 它现在是 `TurnInput` 的字段，而 `begin` 要用它；④ 只是「把它发给流式桥」，两件事本来就该分开 |
| 3 | `run_stage` 调 `begin` → ③（`drive_head`）→ ③′③″④⑤⑥ + 接缝落格（`land_dispatch` / `land_opening` / `set_prefix` / `set_reflex`）→ `drive_steps` → 收好产出 | 这一步之后 `session` 与 `turn` / `context` 同时存在，`Ctx` 的字段面才填得满 |
| 4 | 立 `Ctx`：`session` / `turn` / `context` / 编排器 / 请求 / 端口 / 汇报面 | 一张表一个签名的前件 |

`prepare_turn_inputs` 届时只剩 ①②（提示词 + 工具 + 开销）——那一段是环前的纯读，不含
任何选债口，与 `TC-1b` 无关。

**接缝上那四个动作都是「填」**，填的都是「轮首四行跑完才知道」的东西：`land_dispatch`（档位）、
`land_opening`（首响）、`set_prefix`（请求视图）、`set_reflex`（快路正文）。合表之后它们不再是
接缝——`Ctx` 里有 `&mut TurnState`，需要它们的那几个动作自己读，四个入口一起退场。

**第 3 步会改一处行为，必须写进提交**：中止守卫随环前移，被中止的幕不再跑判决 / 压缩 /
召回。这是 `D-222` 订正 3 明文认下的后果（「守卫在环首」的直接推论），不是顺手改的。

### 第六刀第 0 步已落地（2026-10-28）：`TurnInput` 只剩幕首可给的东西

清出的三个字段与它们的落点：

| 字段 | 谁产 | 落点 |
|---|---|---|
| `tier` | `turn_head.reflex_answered`（`D-223` 订正 1） | `chat_loop::land_dispatch` |
| `opening_text` | 轮首判决行的 `Escalate` 首响 | `chat_loop::land_opening`（经流式桥上实时面） |
| `opening_dialog` | 同上 | 同上 |

落点在**接缝**：压缩之后、`begin` 之前。三条次序各有一条判据钉着——压缩早于派发
（`consolidation_is_forwarded_before_the_turn_runs`）、两格早于 `begin`（基线 prompt 从
事实源投影）、开场白要经桥上实时面（桥在 `assemble_turn` 里建，所以那一步只能在那里）。

`TurnRunner::begin` 因此**不再要流式出口**（四参变三参）：那个参数只为开场白节点存在。
至此 `TurnInput` 的十二个字段**全部**是「开幕就有」的，`begin` 搬到幕首的类型前件已满足。

剩下三步都是形状活，但都改时序：`assemble_turn` 拆两段（桥与发射任务提到幕首）、
`turn_root_id` 的分配点提到 `run_stage`、`begin` 进 `run_stage`。第 3 步的行为改变见下。

### 第六刀第 1 步已落地（2026-10-28）：幕首段与接缝段分开

`assemble_turn` 原来一段做完两件事：幕首该做的（取事实源 / 建桥 / 定主体）与**要等轮首
那几行**才做得了的（压缩入格 / 定档 / 首响上线）。现在它只做前者，后者搬进
`turn_exec::assemble::land_seam`，由阶段② 在 `begin` 之后调。

| 段 | 做什么 | 为什么只能在这一段 |
|---|---|---|
| 幕首（`assemble_turn`） | 取事实源、补落寄存变更、建收集器与流式桥、定主体与来源主体 | 都是「不需要等那几行」的；草稿要排在这些之后、任何动作之前（`D-222` 订正 3） |
| 接缝（`land_seam`） | 压缩入格 → 定档（`turn.dispatch`）→ 首响上线（`chat.assistant.opening`） | 三格的内容要等 `policy.compress` / `policy.reflex` / 判决那几行跑完 |
| 接缝（调用方紧接着） | 渲染基线 prompt → 插前缀 → 寄存快路正文 | 前两件要往草稿里写，而草稿是 `begin` 建的；且渲染必须晚于压缩 |

**这一刀顺手破了一个环**（裁在 `D-223` 订正 2）：`TurnInput::actor` 原来是
`request_actor_spec(ctx, tier, scope)` 用**档位**造的，而档位只能在接缝上读
（订正 1）——「主体在幕首建」与「档位在接缝读」互相派生，`begin` 因此永远排不到幕首。
破法是认出这里本来就是两个量：主体带**声明档**（由 `pattern` 派生），本幕的预算归
`turn.dispatch.budget_ms`（由 `tier.budget_ms()` 直接折）。

**基线 prompt 的渲染也跟着搬了**：它原来在 `prepare_turn`（建草稿时）渲染，而压缩改的
就是消息列表——建草稿那一刻压缩还没落，照那一份渲染，模型读到的就是**没压过**的历史。
入口改成 `TurnSession::render_base`，读点在接缝上、压缩之后；`Prepared::full_snapshot`
在那里重取一次并覆盖（幕首那一份只够给产物编号，后一次是前一次的超集）。

行为零变化（`cargo test -p symbio-plugin-loop --lib` 512 绿、clippy 零告警）：
`begin` 之后、渲染之前，事实面一格没动，所以「渲染看到什么」与拆分前逐字相同。

**第 2 / 3 步因此只剩搬运**：`turn_root_id` 的分配点提到 `run_stage`（④ 只管「把它发给
流式桥」，与「定这个 id」本来就是两件事）、`begin` 进 `run_stage` 的幕首。第 3 步那一处
行为改变（中止守卫随环前移）仍照前文记着。

### 第六刀第 2/3 步已落地（2026-10-28）：`run_stage` 就是那一幕的直线

两件事是同一次搬运的两半，分开做会留下「`begin` 在幕首、根 id 却还在备输入里」的
中间态——那个态编译得过，但 `begin` 拿不到根，`TurnInput` 还得再开一个洞。

1. **根 id 在幕首分配**：`turn.resume_root.take()` 有值就复用（续写幕：骨架已经发过，
   再发会把已完成的卡打回运行态），否则 `llm_short_id()`。`fresh_root` 这个布尔只控制
   ④「把骨架发给流式桥」发不发——**定 id** 与**发骨架**本来就是两件事，此前挤在
   `prepare_turn_inputs` 的 ④ 里只是因为草稿那时在它后面建。④ 仍在压缩之后：压不动
   时不该留半截 Turn 根。
2. **`begin` 进 `run_stage` 的幕首**：`assemble_turn` 之后立刻 `open_turn`，轮首那几行
   在**已经存在的草稿**上跑（`D-222` 订正 3）。于是 `run_stage` 的读法就是那一幕的形状：

   ```
   幕首 collect_reads → 定根 → assemble_turn → open_turn
        ├─ Opened::Done  → into_running → 归类落格
        └─ Opened::Run   → land_head → inputs / branch 两格 → AfterHead → drive_opened → 归类落格
   收好产出 settle
   ```

`drive_opened` 之后 `Running` 手里还借着一批幕级局部量（请求视图段 / 压缩快照 / 首响两格），
而 `settle` 要可变借用 `turn`——所以**归类与落格在各自的分支臂内收掉**（
`classify_and_persist` 一个小助手），出臂时借用结束。原先把 `Running` 抬到 match 外面
再统一归类，借用检查器（正确地）拒绝；这不是要加一格生命周期参数就能绕过的形状问题，
而是「产出必须在借出它的那段里被消费」。

**夹具跟着换形**：`stage.test.rs` 按「跑一整幕」重写（`prepare` 这个入口随搬运退场：
备输入与建草稿不再分两次调用），三条用例分别钉「ready 一格 + 定稿格」「一次重试只落
一格 branch 且登记被消费」「答话轮在轮首就地收束——`closed` 一格、零次模型往返」。
`turn_exec.test.rs` 保留原有五个 `ExecTurn` 字面量不动：测试内定义一个同名字段的结构体
遮蔽 `super::*` 的导入，再由 `split()` 把它拆成幕首 18 项与接缝那 7 项两份入参——
断言一条不动，钉的还是同一批事实。

**行为变化（照前文，写进提交）**：中止守卫随环前移，被中止的幕不再跑判决 / 压缩 / 召回。
这是 `D-222` 订正 3 明文认下的后果（「守卫在环首」的直接推论），不是顺手改的。另有
两处时序在搬运中定型、方向与订正 1/2 一致：`DRAIN_PARKED` 落在幕首（早于轮首那几行）、
压缩入格早于定档（S2.7-b2）。

行为零变化的部分：`cargo test -p symbio-plugin-loop --lib` 512 绿、clippy 零告警。

**下一刀**：`drive_head` / `drive_report` / `drive_steps` 三合一（一个循环体，轮首四行与
`policy.report` 都是行），绑定表三张合一，`continue-turn` 行立起来——然后才是第 4 步
立 `Ctx`。

### 第七刀已落地（2026-10-28）：幕内三段收成一个环

`drive_head` / `drive_report` / `drive_steps` 并进 `turn_exec::drive`，`head_exec.rs`
整个删除，`report_exec.rs` 只剩 `ReportPort` / `ReportLanding` 两半（措辞能力口与那句话

| 收掉的形状 | 收法 |

**汇报那一行合表之后多了一道判据**（`report_due` v5 → v6，`D-163` 裁决 4 的兑现）：
旧触发点只在批次边界被调用，「一次边界只派发一次」是免费的；合表之后环**每一步**都会问
它，`progress_interval_ms = 0` 的配置会对着同一批连报（配额成了唯一刹车）。v6 的 `due`

到期，环在两格之间空转。「试过」由 `report_due` 在**开账侧**读那一格判，不把它算进

**五道守卫各一份**（`drive` 的文档表就是判据面）：中止只在第一圈、选债之前；判成答话

`DriveEnd::Answered`）；步数上界在选债之后、动作之前，有一笔在飞时先收回；写封闭在动作
之后读账本尾段；空账本同上，**处置只有一种**（`exhausted{no_progress}`，「在等」不判死）。

拿得到第二个「`&mut Session` + `&Store`」的组合。第二道（判成答话）落在环里而不是建草稿

### 本刀**没有**收的那一半：幕间那个 `loop`

exit 判据里「生产代码只剩一个 `loop {`」今天**还不成立**：`chat_loop.rs` 的幕间 `loop`
（读 `next_stage_round`）原样留着，`continue-turn` 那一行也还没立。它不是「顺手漏了」，
是那一行今天写不出来：

- 它的 `owes` 读 `turn_next_round`，而那一格要等**本幕**收束之后才有值——也就是说，
  这一行只能在 `drive` 已经跑到「没有可还的债」之后才开账，而那个时刻今天正是 `drive`
  的**出口**（落停机格、返回 `DriveEnd::Finished`）。
- 折进同一个环还牵着 `now`：本次 `drive` 的 `now` 是幕锚那条事实的 `ts`（判据 12），
  一幕一个锚。同一 `drive` 里再开一幕，那一幕的时间条件（静默 / 租约）就会读着上一幕的
  时钟。要么让环中途重读锚，要么让每幕各起一次 `drive`——两条都要一次裁决，
  不该在合表这一刀里顺手定。

所以本刀收的是**幕内**那三段（轮首 / 接缝 / 内环），幕间那段与 `continue-turn` 行
留给下一刀：先裁「第二幕的锚与 `now` 怎么算」，`loop {` 的份数才真正降到一。
