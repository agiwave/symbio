# 会话内实现体收口

## 内容

首响、中途汇报、后台会话启动判据这三类实现体至今住在 session 内，没有独立能力包。
按终态要么把实现体与配置一起迁进各自能力包，要么在残留账本里逐条写明
「为什么它是会话基底而不是能力」——不允许含糊留在中间态。

同时清掉收集期残留的按名判断（插件在场检查、前缀去重），改由声明面回答在场。

## 处理过程

- **本批已完成**：`plugin/turn.rs` 不再硬编码任何能力键，也不再按 `PLUGIN_ID_COMPOSE`
  去债表查在场——`compose_enabled` 改由 compose 插件在收集期贡献（D-427 裁决 4）。
  会话侧只写 `system_prompt` / `tools` / `tools_empty_reason` / `capability_errors`
  这类本轮装配面，其余格子按 owner 合并。
- **本批已完成（补）**：会话基底格不走广播。`opening_enabled` / `progress_*` 由
  `plugin/turn.rs` 在**写格那一处**直接投影——真源与实现体都在本插件，绕一次收集期
  声明只会让这一格的可⻅性依赖 `traverse` 与写格的先后。副作用是 `session` 的 SDK
  依赖面只多一个读口、不多上报口（`E-009` 豁免条目与 D-427 裁决 4 同步记明）。
- **残留账（未完成）**：首响（`opening.rs`）与中途汇报（`progress.rs`）的实现体仍在
  本插件内，没有独立能力包；键名因此仍出现在控制面源码里（写格处的那七行）。
  暂判「会话基底」而非能力的理由：两者只描述**会话自身的呈现节奏**（派活前说不说
  一句、长任务中途要不要打断），没有独立事实族、没有可替换的产线、卸载它们不会让
  任何能力消失——与 `classify` / `compose` 那类「有独立产线、可整体缺席」不同。
  这条判断必须随下一次拆分复核：一旦首响或汇报长出独立事实族 / 路由 / 可卸载边界，
  它们就该迁出，`SessionConfig` 与 RE-001 的 session 行同步删键。
- **另一处未完成**：`plugin/turn.rs` 的 `dedup_subtree_twins` 仍按 `agent_` 前缀判重，
  属「收集期按名判断」的残留，等 agent 子树的声明面能回答在场后再收。
- 出口：每一处残留都能指到一条写明的裁决；控制面源码里没有按能力名分流的分支。
- 这一批允许分批推进，但每批都要留下逐行账，不许宣布「拆到一半即完成」。
