## 内容

`DE-090 §1.1` 是六步施工路径，但今天它读起来像「全部未做」——而代码里步 2 / 3 / 5 的
形状已经在了。这不是小事：路径表的读者（含未来的自己）会照着它重做已经做完的事，
或者误以为架构目标还很远。

第二份核心评估（`tmp/core-review-2026-10-24/01`）补了两个**读法层面**的缺口，
归口在本任务：

- **P1-1「一个环」表述超前于实现**：`DE-015 §0` 的目标句没有就地限定——实现交付的是
  「一轮内部的模型/工具环」，外层仍是 `chat_loop` 的固定七步。不改架构，只改口径，
  否则后续评估会把「内环闭环」误读为「目标达成」；
- **P1-4 `by=None` 一字段三义**：11 行 `by=None` 里，4 行是等待/看护语义（D-130）、
  2 行是适配器派发的粗端口过渡、5 行是真正未接线。四分类写进现状节之后，
  「接线率」才可判，T-282 的统计也有类可依。

### 对账方法（每步同一套）

1. 从 §1.1 抄下该步的**收口判据**原文；
2. 找到判据在代码/测试里的**现实验证点**：用例名（`loop_rows.test.rs` 的网格对拍）、
   `grep` 可复核的形状清单；
3. 找到把形状落进去的**提交号**（`git log --oneline -S`）；
4. 三者都齐 ⇒ 记「已收口」；缺验证点 ⇒ 补用例（这算 T-297 / T-298 的范围）或判「该步未完成」。

### 判据「事实网格 + Step 序列逐格比对」的现状

`loop_rows.test.rs` 有 2136 行，覆盖五条策略行的 owes / until / unless 与端口级联。
待核的问题是它**是否构成 §1.1 要求的「逐格比对」**——即是否有一张表（事实网格）
断言「同一输入下，新路径与旧路径的每一格一致」。若有，给出用例名；若没有，
这就是步 2 / 3 真正缺的东西（比「行在不在表里」深一层）。

### 不许做的事

- 不许把「行存在」当成步已收口——判据写的是比对，不是存在性；
- 不许在 `DE-090` 正文指任务编号（D-014）——在途工作写成缺口条目，让 `registry-board` 反向指过来；
- 不许顺手改代码——对账只动文档；发现缺用例，登记后再做。
