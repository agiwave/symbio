# 驱动安全阀出口在非 CLI 宿主可见

## 内容

`Exhausted` / `Stalled` 的文案由驱动入口（`crates/symbio/src/drive.rs::drive_notice`）
写 stderr。CLI 宿主的 stderr 就是调用面的读数；但 Tauri / gateway 这类**没有控制台**的
宿主里 `eprintln!` 没有读者——GUI 进程的 stderr 无人捕获，两条安全阀出口在界面上
与「正常结束」同形。**在非 CLI 宿主里，这两条目前没有可见路径。**

这与「声明在、写方在、读方没有」是同一类：写方在、文案在，读方（宿主 / UI）没有。
安全阀出口静默的后果比停摆本身更糟——停摆至少还有读数，静默只剩「轮结束但没有终答」。

出路：把出口提升为**事实或运行态错误**（例如落一条 `driver.stalled`，或把
`Exhausted` 的 `outstanding` 写进会话节点的 error 字段），由 VDFS 订阅面直接可见。
在此之前，非 CLI 宿主看到「轮结束但无终答」先按本条核对，不要当成正常完成。

**D-376 只走了一格**：两条出口已经是 `DriveOutcome` 的中性面、随 `DriveReport` 从
`Host::drive` 返回，所以「宿主拿得到」成立；但仓库里唯一调用方是 CLI 的
`drive_notice` → `eprintln!`，既没落事实、也没写会话节点 error——非 CLI 宿主仍无读者。
本条要补的是**落格与读方**，不是再造一个返回值。

## 处理过程

1. 先选载体：事实（可回放、可订阅）与会话节点 error（与轮状态同页）二选一，写清
   谁写、写什么名、谁读；两条安全阀共用一种载体，不各开形状。
2. 写方只在驱动入口，按现有判定点写一次；CLI 的 stderr 文案保留不动，避免改调用面行为。
3. e2e 断言非 CLI 路径能读到该出口；反向用例：安全阀不触发时不得落这条事实 / 字段。
4. 落地后把 `RE-014` §7 的对应条改为已结并指到落地提交。
