## 内容

### 为什么先取证

合并版报告是**读源码**得出的，它自己在 §6 里列了五条诚实边界。sprint 若直接从"读出来的缺口"开工，
会有两种失败形态：改完仍然红（把基线红当成自己改坏）、或改完以为绿（把没跑到当成通过）。
这一条的任务就是**先把"现在的数"钉死**，让后面每一条收敛动作都有一把可比的尺。

三组读数各自回答一个问题：

| 读数 | 回答什么 | 为什么不能省 |
|---|---|---|
| `cargo test` 两个 crate | 形状改动之前，已有用例是绿的吗 | 645 条里有大量断言的是"当前形状"（`port=turn`、行数、四种循环），它们会随收敛变红；不先记下绿的基数，就分不清"变红是用例该改"还是"我改坏了" |
| `gate.mjs`（含 e2e） | 端到端是真跑通了吗 | 报告 §6 第 1 条："所有'用例存在'都是读源码，不是'用例通过'" |
| `obligation-bypass-audit` | 派发面的两个计数今天各是几 | `OB-001` / `OB-002` 已按 `SP-033` §4 降为读数，但**读数仍要准**：它是"收敛到哪一步"的唯一粗尺 |

### 台账的形态（本任务的核心产出）

不是再写一份清单——清单已经有两份（报告 §2 / §3.2）。台账要回答的是另一个问题：
**每一条缺口，谁在收它**。三档处置：

| 处置 | 判据 | 落点 |
|---|---|---|
| **有承载** | 指得到一个 `T-nnn` 的 `exit` | 覆盖矩阵的"承载"列 |
| **已裁** | 指得到一条 `D-nnn`，且裁决已排除该形状 | 覆盖矩阵的"已裁"列 + 一句"为什么它不再需要动作" |
| **降为读数** | 按 `SP-033` §2 的 `J0`，它断言的是过渡构件 | 覆盖矩阵的"读数"列 + 它归哪条 `TC-n` 裁决 |

**三档之外不许有第四档。**"以后再说""优先级低"不是处置——那正是报告 §3.1 里 F 组 0/5 的成因：
缺口被承认了，但没有任何一条裁决或任务对它负责。
