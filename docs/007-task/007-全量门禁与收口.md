### 已修的真问题：e2e 读 WAL 的边界拼接

`t8` / `t11` / `t18` / `t63` / `t106` 各自抄了一份 `walEvents`：把 live 段与归档段的
**原文直接 `join('')` 再切行**。而写方（`store/wal.rs::append`）分两次落盘——先写行、
再写换行——读方落在两步之间时，末行是一条**完整但无换行**的 JSON，接上下一份文件
就把两条事件粘成一行，`JSON.parse` 报「Unexpected non-whitespace character after
JSON」。五个副本收成 `e2e/helpers.mjs::sessionWalEvents`：逐文件切行、末行解析不了
就丢（未提交的尾行按定义不是事件）、其余行解析不了照抛。

### 残留账（未兑现，如实留着）

- **e2e 用例集在并发 7 下有既有抖动，不是本批引入**。实测（同一台机器、同一并发）：
  基线 `HEAD` 9 轮里 2 轮各有 1 例失败（`t77` / `t25`）；本批 12 轮里 4 轮各有 1 例
  （`t63` / `t11` / `t4` / `t23` / `t25` / `t57`）。逐个单跑均 100% 通过（`t4` 单跑 12/12），
  失败例每次都不同——形态是**资源竞争**而不是某条判据错。已修的一类是真实缺陷
  （上面的 WAL 拼接）；其余（轮边界汇报被抑制、末轮答复缺失、`workerRequests` 把
  同一轮的插件请求算进 worker、两条发言在负载下并成一轮）需要单独的诊断批次，
  **本批不动**，也不靠调低并发刷绿。
- 其中最值得单独查的一条：`t4` / `t57` 的「两轮各一次请求」在负载下会变成一次。
  `t4` 走 REPL 管道模式，第二行只在前一轮 `ask` 返回后才写进收件箱，因此**并轮
  不该发生**——它要么说明 `ask` 在负载下提前返回（末轮答复随之丢失，`t4` 的
  stdout 证据正是「第二个提示符打出来了、没有正文」），要么说明收件箱消费与
  驱动之间存在窗口。这是产品侧的健壮性问题，不是测试口径问题。

### 复现这类抖动的方法（下一次照这个做，别再跑全量）

先花两分钟把「要不要负载」问清楚，再决定用多重的炮：

1. **先单跑 N 次**（N ≥ 20，每次 1~2s）。单跑就有失败 ⇒ 它是可单例复现的竞态，
   直接单例调试，**不要跑全量**。
2. 单跑 0 失败才加负载，而负载**必须与 e2e 隔离**：纯 CPU 忙循环进程即可。
   **不要拿别的 e2e 用例当负载源**——实测 `t47` / `t106` / `t32` / `t36` 在互相
   挤压下会自己卡死并残留（20 分钟后仍在跑、占着端口与 CPU），被测用例的失败
   原因就变成「环境脏」：本批踩过一次，表现为「基线 15/15 全失败、mock 请求数
   5/6/7」——那不是基线更差，是连到了残留 mock。清理后同一条命令 10/10 通过。
3. 每次负载实验前后各查一次残留（`Get-Process symbio-cli,node`），有残留先杀再测。
4. 只跑全量是**最后**一步（收口时确认），不是复现手段：一轮 57s、命中率 20~30%、
   每轮挂的用例还不同。

`t23` 已按此复现：单跑 20 次 0 失败；加负载后 12 次里 1 次失败，形态是**整轮卡住**
（等「末轮正文落库」60s 超时，正常 1.3s），与门禁里那次「少一条汇报」不是同一种。
尚未判定是否本批引入（A/B 因负载源污染作废，需用干净的负载源重做）。

补测（本批代码，纯 CPU 负载 6 线程打满 6 核）：`t23` 单跑 **14 次 0 失败**。故那次
「整轮卡住」**不是 CPU 竞争**，只在多个 e2e 用例互相挤压（端口 / 子进程 / 磁盘）时
才出现；而基线在并发 7 下同样会挂（`t77` / `t25`），所以它属于 e2e 并发环境问题，
不归因于本批。真要复现，负载源必须**同时占端口与起子进程**——那就不是「隔离负载」了，
所以这条留给独立的诊断批次，用 e2e 自带的并发跑法在受控条件下做，而不是在本批里追。
