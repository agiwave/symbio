## 内容

`lease_keeper` 能落 `retry{attempt}` 与下一次 `request`，但行层债键是 `(port, id)`：
上一 attempt 的出口格已经关行，重试出来的 `request` **不欠任何一行**，没有执行体会派它。
因此真表上 `max_attempts` 全为 1，只有「到顶即判死」一条路在跑（DE-090 原「重试通道未启用」一节）。

裁决必须说清四件事，缺一条就只是「跟着代码补个编号」：

1. **为什么键必须含 `attempt`**：行层按 `(port,id)` 开账时，上一 attempt 的出口格
   （`sent` / `failed`）已经把 `dispatch-*` / `await-*` / `authorize-tool` 关掉。
   键含 attempt 之后，重试**重新开账**，上限才敢从 1 抬到 2。
2. **为什么 `failed` 也收窄**：`failed` 关逻辑 id 与「重试」在同一笔上打架——第一次失败
   就把所有尝试关掉，第二次尝试的债无处可开。收窄后「不再重试」由「没有后继 `request`」
   表达（可回放、可断言）。
3. **重试的两个前提**：`sent.awaited`（这次尝试有没有活着的等待方）∧ `attempt < attempt_cap`，
   缺一即判死。`awaited` 是**逐次尝试**的属性不是端口属性：普通工具批次的结果等在当前
   草稿里，进程一死等待方就没了；唤醒调用能由 `wake_batch` 从事实重建。
4. **回放边界**：旧日志的 `failed` 没有 `attempt`，按三元组绑定取不到实例——旧事实不参与
   尝试级收口。本仓不承诺跨版本回放（回放服务的是同版本崩溃恢复），这条写进决策，不靠读者猜。

**被否的候选**：单开 `retry-<port>` 行（重试不是新的欠，是同一笔债的下一次尝试）；
`failed` 保留逻辑键另立事实名（词汇表为一个粒度问题加词，且逻辑键继续把重试后的尝试提前关掉）；
只抬 `max_attempts` 不改键（抬了也没人派发，等于一条永不执行的债）。

**为什么断言行层而不是事件条数**：只数事件的话，`dispatch-tools` 忘了加 `attempt` 也能过——
事件照写，行还是不欠。断言 `owes()` 的待办集合里出现 `(port, id, attempt=1)` 的三笔债。
`awaited:false` 是绝大多数调用（普通工具批次），它若多写一条 `retry`，日志里就会出现
没人派发的 `request`——正是本裁决要防的形状，所以反向用例与正向用例同批在册。
