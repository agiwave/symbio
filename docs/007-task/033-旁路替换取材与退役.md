## 四、三个已知风险在新路径上的落点

1. **端口嵌套**（session 执行体内派 model）
   - 谁派谁：`request(port=session, id=decided-<user.message event_id>)` → session 执行体 → `request(port=model, id=<触发调用 event_id>)`。
   - 环路怎么断：外层 `until` 只认外层 `(port=session, id=decided-…)`，内层只认 `(port=model, id=…)`；`scope` 相同但 `port`+`id` 不同，配对天然不交叉。
   - 约束：`attempt` 必须按 `(port,id)` 各自起租约，不能共用外层 id；否则内层的 `response` 会被外层读成「还了」。

2. **收束判定**（谁定一个 `scope` 完事）
   - 唯一写方：`finalize` 债（`port=session`）。`owes` 由**一个视图**判：本 scope 有终局（`chat.decided.result=answered` / 模型输出耗尽 / `authz.denied`）且无 `chat.assistant.final|fallback`。
   - `until`：`response(port=session, id=f-<scope 锚事实 id>)`（或 `fb-…`）。
   - 禁止：任何「第几步 / round / stage」字段进入这个视图；判定必须能只读世界事实复算。

3. **旧 WAL 兼容**
   - 现状：旧日志的幕锚是 `loop.step{id:"resume"}`、进度是 `loop.step`。新读面不再读它。
   - 落点一：`drive_of` / `is_drive_anchor` / `turn_head` 三处视图——旧 WAL 续写会把 `user.message` 当新幕，导致重跑。
   - 落点二：replay 入口——需要一层只读影子：把旧 `loop.step` 事实映射成等价的 `session.prepared` / `chat.decided`（只读、不写、不影响新 WAL）。
   - 判定：若不做影子，旧 WAL 的「恢复幕」会丢锚；若做，必须保证影子只作用于 `seq < 切换点` 的事实。

## 五、给新会话的三条硬提醒

1. 机制 crate 里**不许**出现 `"session"` / `"model"` / `"tool"` 字面量；端口名只从声明数据流入。
2. 债 `id` 由事实派生、禁计数；`attempt` 才是租约的递增位。
3. 先建「旁路」，再按 P1…P6 拆旧壳；迁移线不要再走「保绿即保旧壳」的原地改造。
