## 内容

执行 T-294 时撞到的一个**判定器静默降级**现场：

`symbio/src/plugins/compose/plugin.rs` 的工作树副本是 CRLF，`routeArmDocs`
（`scripts/route-facts.mjs`）按 `^\s*\/\/[/!]?\s?(.*)$` 抽「路由臂上方的 `///`」——
JS 的 `.` 不吃 `\r`、`$`（无 `m` 标志）又要求行尾对齐，于是**整段注释一条都抽不到**。
后果不是报错，而是能力矩阵里 `compose/wording` 的职责变成 `—`，
再由 `facts.test.mjs`「每条静态路由都有一句职责」变红——
**守卫红了，但报的是「表里没写」，真实原因是「读取器读不到」。**

### 为什么这不是偶发

`git ls-files --eol` 的现状（2026-10-24）：

| attr | 文件数 | 说明 |
|---|--:|---|
| `text eol=lf` 且工作树 `w/crlf` | 98 | `.md` 42 / `.ts` 14 / `.mjs` 11 / `.vue` 5 / 其余若干 |

而 `git diff` 对此**一个字符都不显示**：index 里是 LF、attr 声明 `eol=lf`，
git 在 diff 时把工作树 CRLF 归一化掉了。于是整仓「看起来干净」，
只有像 `routeArmDocs` 这种用 `$` 锚定行尾的读取器知道真相——它不会说，它只是抽不到。

入库方向没有受损（index 是 LF，提交不会带 CRLF），**受害的只有读取侧**：
任何按行切分 + 行尾锚定的解析器都在这 98 个文件上失效。这不是一份文件的毛病，
是一条**没人观测的输入前提**。

### 为什么不在每个正则里补 `\r?`

补 `\r?` 是逐个调用点兜底，代价是每个解析器各自持有一份「行尾无关」的口径，
而这份口径没人复核——今天补了三个正则，明天新写的第四个照样踩。
行尾属于**输入的前提**，前提应当由一处判据守住（仓里 LF），
而不是由 N 个解析器各自容忍。这与 `SP-013`「锚必须是版本化的地址」同型：
把环境的默认值变成被检查的事实。
