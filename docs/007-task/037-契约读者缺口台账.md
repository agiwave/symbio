# 契约读者缺口台账

## 内容

## 1. 这是哪一类缺陷

**声明在、写方在、读方（或调用方）从未接上。** 契约三件套里缺的是**最后一跳**，
而这一跳在代码静态可读的面上常常「看起来有」：事件名出现在常量表、视图的 `reads`
列着它、trait 方法有完整实现——只是没有一条运行路径真的去读它 / 调它。

与 T-036（`rev().find` 只取最后一条 ask）同一族——**事实落了、读的人没有**——但更隐蔽：
T-036 的错是「读得不完整」，这里根本没有读的人。写方自己不会报错，载荷也照样进库，
所以所有「事实存在」型断言都是绿的。

严重性在于**失效被另一张脸遮住**：

- 对 `session.consolidated`：压缩确实发生、快照确实落库、对话面确实变短——每一格都真；
  但**模型输入从未受影响**，水位只涨不落，压缩在同一会话里反复触发。
- 对 `retire_prefix`：归档实现是真的（`archive_before` 真写盘），只是从来没人宣布
  「这段前缀已固化、可回收」，于是归档永不发生。

这两例都不是「机制坏了」，而是**机制与消费面之间断了一根线**：改动在写侧完全正确，
症状却出现在一个没人看的读数上。

## 2. 已修：`session.consolidated`

- 声明与写方：`symbio-plugin-compact`（D-053 / D-336 的换基事实），载荷 `messages`
  是整份消息列表，取代它之前的一切。
- 缺口：模型请求组装（`symbio-plugin-model` 的 `turn_input`）只按 `message.added`
  增量回灌，从未消费快照。于是压缩只改对话面，模型仍读全量历史。
- 实测（t47，修前）：整场压缩 **11 次**，主请求仍带 **21** 条 `user` 消息——压缩做了，
  输入没变。
- 修法：`turn_input` 从最近一条快照的载荷整份起折（与 `message.added` 共用同一译法
  `append_payload_nodes`）；修后压缩回落到 **2 次**，大结果被换基真正吃掉。
- 判据：t47 证据 ③（`session.consolidated` 落格 ≥ 2）＋证据 ⑤（主请求里不再出现
  大结果、轮次回落）。修前两条都绿、而事实无效——正是本类缺陷的典型：**要判「谁读了」，
  不能只判「谁写了」**。

## 3. 仍存：`retire_prefix`（属 T-045）

`FactSource::retire_prefix(before_seq)`（`crates/symbio-plugin-api/src/fact_source.rs`）
有完整实现（`symbio-plugin-session` 的 `store::fact_source` 调 `archive_before`），
也有契约文字（「该前缀已固化，可回收」），但**全仓没有调用点**。归档因此不会发生。

它与第 2 节是同一类：缺的是「换基之后由谁宣布可回收」这一跳（T-045）。

## 3a. 本轮一并补上：信封 `cost_ms`

t28 走绿时暴露的第三例，比第 2 节更早断：`cost_ms` 的**读方**齐全（`slo` 分位数、
成本台账、`I3` 预算判据都读事件的信封字段），**信封却从未被填**——模型端口把实测
耗时写在载荷的 `cost_ms` 里，`draft_into_event` 只搬载荷、不搬信封，于是所有读方
读到恒 0（`I3` 的预算判据也因此永不触发）。

修法在契约自己写明的位置：模块头说「信封的 `event_id` / `seq` / `ts` / `cost_ms`
一律由事实源在入库时生成」——`draft_into_event` 现在把载荷同名值提进信封。
这不是新增字段，是把已有契约的最后一句落地。

## 3b. 读数口径：中止轮不进时延样本（不是样本缺失）

`slo.latency` 只数 `chat.assistant.final` 的信封 `cost_ms`；t7 恢复中止后，中止轮也会
落一条 `final{status:"aborted"}`。**它按 `status` 排除，而非留空**——理由写死在这里：

中止样本的耗时是「被打断的那一截」，它度量的是用户按下停止的时点，不是模型 / 工具
的服务能力。把它计入会把 p95 往「用户手速」拉，属于**样本语义污染**；留空则会让读方
以为「这一档没跑过」，又是另一种误读。所以排除是口径决定，不是数据缺口——以后看到
`final` 条数多于时延样本数，先按本条核对，不要当成丢样本。

## 3c. 仍存：`deadline_ms` 声明在、生产侧零读者

`PortExecContext.deadline_ms`（`crates/symbio-plugin-api/src/port.rs`）由环在派发时写入
（`sent.at_ms + lease_ms`），但**没有任何执行体读它**：模型端的 180s 流空闲 / 1800s
总超时、工具端的 600s 空闲看护，都是各执行体自己的常数，不是从这一格来的。它现在
只表达「环建议的截止」，没有真读者。

两条出路，二选一（本轮只登记，不改代码）：
1. 给它真读者——由在飞对账 / 租约看护消费它；
2. 从 `PortExecContext` 删除，别把建议数据挂在公共形状上当注释。

在此之前看到这一格，不要当成「超时已经生效」。

## 3d. 仍存：驱动安全阀出口在非 CLI 宿主没有读者

`Exhausted` / `Stalled` 的文案由驱动入口（`crates/symbio/src/drive.rs::drive_notice`）
写 stderr。CLI 宿主的 stderr 就是调用面的读数；但 Tauri / gateway 这类**没有控制台**的
宿主里 `eprintln!` 没有读者——GUI 进程的 stderr 无人捕获，两条安全阀出口在界面上
与「正常结束」同形。**在非 CLI 宿主里，这两条目前没有可见路径。**

这与第 2 节的 `session.consolidated` 同一类：写方在、文案在，读方（宿主 / UI）没有。
安全阀出口静默的后果比停摆本身更糟——停摆至少还有本台账，静默只剩「轮结束但没有终答」。

出路（本轮只登记，不改代码）：把出口提升为**事实或运行态错误**（例如落一条
`driver.stalled`，或把 `Exhausted` 的 `outstanding` 写进会话节点的 error 字段），
由 VDFS 订阅面直接可见。在此之前，非 CLI 宿主看到「轮结束但无终答」先按本条核对，
不要当成正常完成。

## 4. 以后怎么提前发现


1. **读方清单**：每一条 `shared_events` / 每一个公开 trait 方法，登记时同时填
   「读法」——owner 视图名、reader 函数、IPC 出口、调用点四者之一；填不出 = 红灯。
   清单按**格**而不是按**插件**组织（同一格可以有几个读法，但至少一个）。
2. **消费面检查**：每落一格先问「它能改变哪个用户可见的输出？」。答不出，它就只是
   日志，不该出现在契约表里；答得出就把那个输出写进对应 e2e 判据（t47 的
   「压缩后主请求变小」就是这么来的）。
3. **观测症状**：单调量（水位、压缩次数、被遗忘条数）只涨不落；同一载荷在对话面
   变了而请求面没变；「事实计数在涨、下游读数不随它变」——三者任一出现，先查读方。
4. **门禁化**：`shared-event-vocab-audit` 已要求共享格至少有一个**其他插件**引用；
   同类检查可以再加一条「引用方必须是读法而不是同名常量」——本台账不要求本轮加，
   先按第 1、2 条人工过。

## 5. 抖动登记与处置纪律

抖动本身不是缺陷，**「红了就重跑」的习惯**才是：真回归会被当成抖动放过。因此：

- 每次抖动都记下**用例名 + 失败点**（断言的那一格，不是用例名泛称）；
- 同一失败点累计到**两次**，即按缺陷查，不得再以「单跑绿」结案；
- 一次 rustc 进程级异常（Windows 访问冲突，退出码 0xC0000005）也按一条失败点登记；
- 凡「加了等待 / 同步然后串行绿了」，必须能指出**哪一份实例在等、谁在通知**。
  说不出这两头就不算修好，串行绿不构成证据（t29 的 D-359 就是这样漏过去的：
  等待挂在一份永远空闲的实例上，串行绿靠的是另一条路径上的第二次等待）。

已登记：

| 日期 | 用例 | 失败点 | 复跑结果 |
| --- | --- | --- | --- |
| 2026-11-07 | t18 | 第 6 轮用户消息在事实源中应恰好出现一次，实际 0 | 单跑绿（1 次） |
| 2026-11-07 | t29 | 跨会话召回 3 行、实际 4 行；四条经验都在，缺合并产物（巩固未在 B 首轮前可见） | 单跑 0/10 绿；12 路并发 2 批复现（5/12、6/12 红）⇒ **按缺陷查** |

t29 的失败点已累计两次，按上表纪律转入缺陷。**根因（2026-11-07 定案）不是又一条
时序，而是等待等错了实例**：`install_root` 绑 home、插件 `drive_entry` 绑父 composite，
`HostDriveBinding::bind` 每次 `new` 一份 ⇒ 两份 `KickState` 表。CLI 的 `settled` 读的
那份永远空闲，等待立即返回；`session/project` 于是在「终答已落、编码未落」的窗口
投影并 `Finished`，CLI 退出带走收轮任务，四条经验在、合并产物无。

**D-359 那次修的等待在 CLI 路径上从未生效过**（串行能绿靠的是收轮侧另一份实例的
显式等待）——这是**修复未生效**，不是修复后又回归。修法与判据见 D-365；验收为
t29 并发 20 批 × 12 路全绿，且探针显示 CLI `settled` 与 `project_final_turn` 的
`waited_ms` 非 0、两者指向同一个驱动实例。

**同形状的已知边界与触发条件**：`store::fact_source::STORAGE_DIR` 取进程级首个会话
插件的目录，子智能体树的会话目录不同。开面今天只服务主根 CLI，故本批不收；**触发信号**
是「子智能体树的会话调用 `FactSourceOpener::open`」——出现这样的调用点、需求或用例，
就必须先让开面契约带上根，再改实现（详见 D-365 的已知边界）。

环境注意事项（不是抖动，是门禁继承的宿主状态）：门禁继承环境变量，**RAM 盘上的
`TEMP`** 会让 `content_search` 一族报 `os error 1` / `EISDIR`；跑门禁要带真实临时目录，
例如 PowerShell：

```powershell
$env:TEMP='<真实临时目录>'; $env:TMP=$env:TEMP; node scripts/gate.mjs
```
