# e2e 并发抖动诊断

## 内容

e2e 用例集在并发 7 下有**既有抖动**：同一台机器、同一并发，基线 HEAD 9 轮里 2 轮
各有 1 例失败，能力自配置迁移批的 12 轮里 4 轮各有 1 例；逐个单跑均 100% 通过
（其中一条单跑 12/12），每次失败例还不同——形态是**资源竞争 / 环境竞争**，不是某条
判据错。不靠调低并发刷绿，也不把它算进迁移批的收口。

要查的是三件事，逐条分开，别混成一个「偶发失败」：

1. **产品侧健壮性**：`t4` / `t57` 的「两轮各一次请求」在负载下会并成一次。`t4` 走
   REPL 管道模式，第二行只在前一轮 `ask` 返回后才写进收件箱，因此并轮不该发生——
   要么说明 `ask` 在负载下提前返回（末轮答复随之丢失，stdout 证据是「第二个提示符
   打出来了、没有正文」），要么说明收件箱消费与驱动之间存在窗口。
2. **e2e 并发环境**：轮边界汇报被抑制、末轮答复缺失、`workerRequests` 把同一轮的
   插件请求算进 worker、两条发言在负载下并成一轮；以及 `t23` 那种「整轮卡住」
   （等末轮正文落库 60s 超时，正常 1.3s）。
3. **归因边界**：CPU 忙循环打满 6 核时 `t23` 单跑 14 次 0 失败，故「整轮卡住」不是
   CPU 竞争，只在多个 e2e 用例互相挤压（端口 / 子进程 / 磁盘）时出现；基线在并发 7
   下同样会挂，不能归因于某一批代码。真要复现，负载源必须同时占端口与起子进程。

出口：每一类失败都能给出**可复现条件与归属**（产品缺陷 / 测试环境 / 判据口径），
产品缺陷修在产品侧、环境问题修在测试跑法里；不靠调并发、改判据口径或重跑刷绿。

## 处理过程

- 从能力自配置迁移批收口时转出：那一批只收它承诺的终态，抖动按原文「留给独立的
  诊断批次」，不标记完成。
- **已修的一类真缺陷**（不在本任务范围内，留作背景）：`t8` / `t11` / `t18` / `t63` /
  `t106` 曾各自抄一份 `walEvents`，把 live 段与归档段的原文直接 `join('')` 再切行；
  写方分两次落盘（先写行、再写换行），读方落在两步之间时末行是完整但无换行的
  JSON，接下一份文件就把两条事件粘成一行。五个副本已收成
  `e2e/helpers.mjs::sessionWalEvents`：逐文件切行、末行解析不了就丢（未提交的尾行
  按定义不是事件）、其余行解析不了照抛。

### 复现方法（先问「要不要负载」，再决定用多重的炮）

1. **先单跑 N 次**（N ≥ 20，每次 1~2s）。单跑就有失败 ⇒ 它是可单例复现的竞态，
   直接单例调试，**不要跑全量**。
2. 单跑 0 失败才加负载，而负载**必须与 e2e 隔离**：纯 CPU 忙循环进程即可。
   **不要拿别的 e2e 用例当负载源**——实测 `t47` / `t106` / `t32` / `t36` 在互相
   挤压下会自己卡死并残留（20 分钟后仍在跑、占着端口与 CPU），被测用例的失败原因
   就变成「环境脏」：曾经表现为「基线 15/15 全失败、mock 请求数 5/6/7」，那不是
   基线更差，是连到了残留 mock；清理后同一条命令 10/10 通过。
3. 每次负载实验前后各查一次残留（`Get-Process symbio-cli,node`），有残留先杀再测。
4. 只跑全量是**最后**一步（收口时确认），不是复现手段：一轮 57s、命中率 20~30%、
   每轮挂的用例还不同。

- `t23` 已按此复现过：单跑 20 次 0 失败；加负载后 12 次里 1 次失败，形态是整轮卡住，
  与门禁里那次「少一条汇报」不是同一种。A/B 因负载源污染作废，需用干净负载源重做。
- 补测（纯 CPU 负载 6 线程打满 6 核）：`t23` 单跑 14 次 0 失败。
