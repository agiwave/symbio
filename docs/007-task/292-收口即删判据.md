## 内容

`docs/007-task/README.md` 与 `docs/README.md` 都写死一条规矩：

> `done` / `wont` 是过渡档，不是归档档——结论落进设计文档后**删掉这个文件**。

2026-10-23 刚执行过一次（提交 `0f47b1f3`，清 244 篇），**24 小时后**又躺着 18 篇 done。
`grep "收口即删" scripts/*.mjs` 只命中审计脚本的提示文案——它是一条**没有判据的纪律**，
回归是必然的（`SP-011`）。

### 判据为什么是「文件数 > 0 即红」而不是「超过 N 天」

- 按天宽限需要新增字段与解析，而宽限期内的文件恰恰是「结论还没落」的那几篇——宽限没有意义；
- 「收口即删」的字面就是同一提交内闭环：`done` 必有 `evidence`（RG-007 已强制），
  结论落的地址已经写好了，删文件是零成本动作；
- 若真实工作流里确有「结论要等下一提交」的情形，那该由 `deps` 表达（闭下一批时一起删），
  而不是由判据放行。

### 与 `deps` 的耦合（RG-006 不许破坏）

依赖闭环的同一提交里，引用方必须删掉这条 `deps` 边——边的语义是「必须先有」，先有了就不必再指着它。
本任务的实现里要给 RG-031 的错误信息补一句：「若有条目的 `deps` 指向你，同一提交里把这条边摘掉」，
否则删除动作会被 RG-006 卡死，规矩在第一次真实使用时就停摆。

### 删除前的门槛

18 篇逐篇核对：`evidence` 指向的设计条目**确实承载了结论**（`impl` 档位、`### D-NNN` 或验收清单）。
指向 `tmp/` / `logs/` 的四篇（T-262 / 264 / 269 / 271）按「证据已不可核对」处理：
结论若在设计文档里有第二落点，正常删；没有的，先补落点再删——不许凭「任务写过」就删。
