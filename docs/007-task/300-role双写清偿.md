## 内容

`GO-003 E5` 的判据是「过渡入口 `with_role` / `set_legacy_role` 的直写格数只降不升」——
它兑现了一半：棘轮在跑（146 处，只降），但**没有任何任务在降它**，
退役计划（「d-iii 末档」）只出现在 `scripts/grep-audit.mjs` 的注释与一条已归档的 ADR 里。
`docs/` 全仓搜「存量 role / d-iii / 字段退役」零命中：
**146 处双写债务没有设计文档 owner**。

### 为什么先有裁决再有第一批

146 处不是一批能清的（清偿会碰测试与 wire 形状，熔断线 §1.3 的 300 行约束在这里同样适用）。
没有末档形态就开清，清到一半必然出现「这段到底还留不留 role」的现场猜测——
那正是双写能存活到今天的机制。裁决至少要回答：

1. **末档是什么**：`role` 完全退出 `ChatNode`（读写都无），还是保留为纯派生读
   （`node_role()` 从 `principal.kind` 折叠，写侧无入口）？两者判据不同。
2. **分档按什么切**：按模块（`chat` / `session` / `gateway`…）还是按入口
   （先收 `set_legacy_role` 的写侧、再收 `with_role` 的构造侧）？每档要给出
   「这一档完成时 `grep` 什么命令、期望什么数」。
3. **谁依赖它**：读侧如果不止 `node_role()` 一个读者（前端投影、事件载荷），
   先列清单再动——不允许清着清着发现 wire 上还有人读。

### 第一批的形状

裁决落纸后，第一批只做**最便宜的一档**（例如全部测试代码里的直写，或某一个模块），
把「S-014 基线下降」变成事实而非计划。后续各档各立任务，本任务不背 146 的全部。
