# 折叠呈现轴——三种叶子共用一个呈现轴

## 内容

### 现场

[DE-019-前端机制化](../003-design/019-前端机制化.md) 的记录是：`Text` / `Reasoning` / `Compression` **已是叶子**（节点
类型收敛完成），但「缺一个统一的呈现轴（默认折叠 / 流式 / 类型图标）」。

后果不是「少一个组件」，而是**同一件事三处各写一遍**：

- 默认折叠：三种叶子各自判「该不该默认收起」，判定条件与实现位置都不同；
- 流式态：`Text` 有流式，`Reasoning` 有流式，`Compression` 没有——但「谁在流」的判据散落；
- 类型图标：三种叶子各自的图标映射，新增一种叶子要再写一遍。

这是典型的「行表即闭集」缺口：**叶子类型已经收敛成闭集，呈现却是开集**。

### 判定

呈现轴是一条**纯派生**：输入是 `{kind, streaming, collapsedByDefault, meta}`，输出是
`{icon, defaultOpen, live}`。它不持有状态，也不读后端事实——折叠是用户态，存在前端 store。

判据有两条，缺一条就是「看起来统一了」：

1. **新增一种叶子时只改一处**：类型联合加一个成员 + 派生表加一行，其余组件零改动；
2. **三处不出现第二份判定**：`grep` 不出「`kind === 'text' || kind === 'reasoning'`」
   这类分支。

### exit

- 一条派生函数（或一张表）供三种叶子共用，`Text` / `Reasoning` / `Compression` 都从它取
  `icon` / `defaultOpen` / `live`；
- 新增第四种叶子的成本 = 一处（有单测证明：加一行即可，组件不改）；
- 前端单测覆盖「三种叶子的默认折叠与流式组合」的矩阵；`frontend-build` 绿；
- `DE-019` 该行改为落地锚。

### 不做什么

- 不把折叠状态搬到后端——那是用户态，不是事实。
- 不为「统一」把三种叶子合成一个组件（它们的节点语义不同，合了要长出一堆 `if`）。
- 不顺手改节点类型（叶子已收敛，本条只统一呈现）。
