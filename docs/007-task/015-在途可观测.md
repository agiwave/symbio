## 内容

### 缺口：失败与成功在返回值上同形（第二处）

`sent` 与 `response` 落在**同一个动作窗口**（`port::dispatch_full` 把 `run().await` 包在中间），
所以在两次选债之间「已派出、未收清」在环里读不出来：

| 事实 | 后果 |
|---|---|
| `stale_sent` 在正常跑里恒空 | 租约看护扫不到任何过期尝试，「接回派发器」只是形式 |
| `waiting` 恒假 | 这个停机理由只在下一次生命读上一次崩溃的日志时才有意义 |
| `TC-1c` 的空账本守卫判「环不前进」 | 在途恰恰是「环合法地不前进」——今天这两种处境在事实面上同形 |

### 终态已裁，照着做（`D-222` 订正 2）

裁决写在 [DE-015-义务环](../../docs/003-design/015-义务环.md "DE-015-义务环") 的 `D-222` 订正 2，
这里只留施工要点：

1. **in-flight 槽**：`dispatch-*` 把「发出 → 等应答 → 落 `response`」整段 `async move` 包成
   future 寄存进 `TurnSession`，`await-*` 的动作 poll 它一次。
2. **借用面已经验过**：`call_model` 的闭包只捕获 `llm` / `tok` / `messages` / `tools` / `sink`
   五个参数，**不捕获 `&mut Prepared`** ⇒ future 不借草稿 ⇒ 槽是
   `Option<Pin<Box<dyn Future<Output = …> + 'a>>>`，代价是 `TurnSession` 带一个生命周期参数。
3. **三处必须同批改**（少一处就是死锁，见裁决正文的表）：`dispatch-*` 的出口、`await-*` 的
   `by`、`no_progress` 守卫。**`by = None` 从此不再表示「在等」**——那件事的唯一表达回到
   `waiting` 视图与 `exhausted{waiting}`。

### 不做什么

- **不把 `now` 加第二个来源**：`D-115` 的输入闭包不动。于是「等了多久」在轮内不流动——
  被判死的仍是上一个幕遗留的在途。要让轮内也判死是另一条裁决（裁决正文的"被否的候选"末条）。
- **不做成「超时即失败」**：判死仍归 `reap` 与 `D-138` 的两条前提（`awaited` ∧ 未到上限）。
- **不动求解器**：`ring::owed` / `ring::drive` 字节冻结（`PTS-003`）。
- **不为 `tool` 端口留旧形状**：模型与工具两条路必须同形。留一套旧的，等于承认有两个派发器。

  2. 本任务的第 1–3 步，in-flight 槽成为 `Ctx` 的一个字段；
  3. `T-011` 的第二段：合表、合环、守卫归一。

  `deps` 拆成「`Ctx` 先于本任务、合表后于本任务」两半，要么证明 `Ctx` 可以在不动 `Ctx` 的

### 实做记录（`model` 端口已落地，`tool` 端口待做）

上面「第 1 步的坑」与「依赖互逆」那两段**已被实测否证**，按 `SP-033` §1 收回：

- **草稿不必带生命周期参数**。出路不是给 `TurnSession` 加 `'a`，而是把 `TurnStep` 的端口
  全部改成可克隆句柄（`Arc<dyn Store>` / `Arc<dyn LlmAdapter>` / `Arc<[CapabilityMeta]>` /
  `Arc<dyn DeltaSink>`，`FullModel` 加 `Copy`）。消灭借用之后 future 是 `'static`，
  `Action` 的 `for<'a>` 只需对一个生命周期成立。**这一步零行为变化、单独可回退**。
- 因此**本任务独立于 `T-011` 先做**，`T-011` 的 `deps` 不必拆成两半——它等的是一个已经
  做完的本任务，而不是「先给 `Ctx` 再回来」。

已落地（`cargo test -p symbio-plugin-loop --lib` 510 绿、闸门 161/162 其中 1 项为
MSRV 环境跳过、e2e 86/86、`port-surface-audit` 绿）：

1. `dispatch-model` 出口 → `sent`；`await-model` 的 `by` → `waiter`（`run_await`）。
2. in-flight 槽（`TurnSession::inflight`，`'static` 框）+ `begin_model` / `poll_flight` /
   `settle_flight` 三段；`await` 那一侧 **poll 一次**、`Pending` 就 `yield` 并原样放回槽里。
3. 四处连带：`turn_head.model_open` 的关账格挪到终局三格（视图 v14）、`waiting` 改按形状问、
   步数上界不在一笔未落地时生效、`await-*` 与 `dispatch-*` 不许共名。
4. 两条反向用例：`an_in_flight_round_is_observable_between_selection_rounds`（装饰事实源，
   每写一格问一次 `waiting`）与 `a_round_still_in_flight_parks_the_ring_instead_of_killing_it`
   （去掉空账本守卫里那半句 ⇒ 红在 `no_progress`，已实测）。

未做的两件，按顺序：

1. **`tool` 端口跟上——它卡在一条裁决上，不是卡在力气上。**

   接口那一刀很清楚：`sent` 现在由 `ToolDispatch::dispatch` 在批次内部写（先落 N 条
   `sent`、再跑、再关账），而 `courier` 一个动作兼着 `dispatch-tools`（68）与
   `deny-tools`（69）两条债；要让 `dispatch-tools` 的出口成为 `sent`，得把
   `ToolDispatch` 拆成 `begin`（落 `sent` + 关被拒的 `failed` + 定格正文 / 广播工具节点）
   与 `finish`（跑执行层 + 关账 + 映射结果）两半。切点干净（`dispatch` 方法里
   `begin_calls` 到 ③ 之间正好是前半）。

   真正挡住的是**装载期第 6 条后半**（`Gap::ActorCannotClose`）：
   > 出口全是引擎独占格时（派发行的形状：引擎落 `before` / `failed` 替它关门），
   > 判它的**名单是不是空的**。

   `courier` 今天的 `writes` 是四格——`artifact.added`（2c）、`chat.assistant.progress`
   （2d）、`turn.supplemented`（2f 注入）、`chat.assistant.reported`（2f 的批次边界派发点）。
   **这四格全在 `finish` 那一半**。拆完之后 `courier` 只写 `sent` / `failed`（都是引擎格），
   名单必然为空 ⇒ 装载期直接红。

   `relay`（`dispatch-model`）能过这一关，是因为它的**控制面失败**路径真的落一条
   `chat.assistant.fallback`（`ACTOR_RELAY` 名单上就是它）。`courier` 的前半没有对应的
   领域落格：`begin` 的唯一失败面（`NotOwed`）落的是 `failed`，也是引擎格。

   所以三条路，每条都要一条裁决，**不许在实现里顺手挑一条**：

   | 路 | 代价 |
   |---|---|
   | 把 `chat.assistant.reported` 的批次边界派发点从 2f 挪进前半 | 汇报的时机变成「工具还没跑完」，`D-163` 的「往返进行中落地」在这一侧反而失真 |
   | 给前半找一条真实的领域落格 | 今天没有这样的事实；造一格等于为一个装载期判据造事实 |
   | 改第 6 条后半：出口全是引擎格时，改判「执行体调用了 `port::begin`」而不是「名单非空」 | 判据从声明面挪到实现面，`writes` 对纯派发行的意义要重新说清楚——这是 `D-222` §三 第 6 条那一档的改动 |

   结论：**`tool` 端口这一半拆成了独立任务**
   [`T-016-工具端口的在途可观测`](016-工具端口的在途可观测.md)，它先裁上表里的一条再动手。
   本任务因此以「`model` 端口落地 + `tool` 端口待裁」收口，而不是硬凑成两端口同形。
2. `DE-090` 的相关段落回写（`DE-015` 一侧已回写：`D-222` 订正 2 的「借用面」段与新增的
   「四处连带」表）。
