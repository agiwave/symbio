## 内容

2026-10-23 的两条实测（单轮 9 格 / 工具轮 27 格）**J1…J8 全绿**，但覆盖是有边界的：
它们证明的是「`drive` 驱动的那 6 行工作正常」，不是「整个环都在派发」。

| 未覆盖 | 为什么 | 怎么造 |
|---|---|---|
| `policy.compress` 真压缩 | 会话短，判为不需压缩（`model_calls: 0`） | 长会话，超阈值触发压缩 |
| `policy.recall` 命中 | 结果 `miss` | 先编码记忆，再问相关内容 |
| `deny-tools` | `vdfs_read` 被放行 | 请求越权路径 / 未授予的能力 |
| 租约到期判死 | `max_attempts = 1`，正常路径不触发 | 造「只有 `sent`」的 WAL，重启 |
| 轮外压缩重试 | 需先制造压缩失败再点重试 | 见 T-254 |

**注意第 4 项的判据口径**：DE-015 判据 16 说「能重试**或**判死」。`retry` 分支按 §2.3
明确「未启用」（行层债键 `(port, id)` 会让重试出来的 `request` 不欠任何行），
所以本项验的是**判死**路径，不是重试路径。别把「retry 不可达」当缺陷重开——
§2.3 已经裁决过。

**为什么这五项要一起做**：它们共用同一套「造 WAL / 跑 CLI / 判 J1…J8」的流程，
分开做要重复搭五次环境。但每项的证据必须**独立**（各自的会话号 + 各自的验收输出），
不许合成一份。
