# S9：A 类十条能力插件化——不用改架构的正向验证

## 内容

迁移账证明「存量能拆出去」；这一段证明「新增能长出来」。名册 §5.2 里判为 A 的十条——
因果结构、未来预测、世界模型、幂等与重试、因果表征工具、可逆性设计、制造工具（L2）、
抽象协议设计（L4）、人格语气一致、可解释——的共同点是：它们只需要今天已有的扩展面
（事实 / 视图 / 工具 / 效果 / 上下文 / 路由）。

正向验证的判据与 EX-001 同形：**落地 diff 里五棵树（`sdk` / `kernel` / `plugin-api` / `loop` / `session`）的非生成物为零**（唯一口径见 D-372），且 `plugin-api` 不出现新增能力名（行为名由能力包自报、宿主收集，D-363）、逐条登记（口径由 front-matter 的 `exit` 持有）。
如果某一条实测需要改这些目录、或往 `plugin-api` 加机制，说明它其实不是 A，改判为 B 并先出决策——这正是验证的
价值，而不是失败。

## 处理过程

1. 每条一个能力包（可同包但账里写明），从最小可观察形态开始：先落事实或视图，再补工具 / 段。
2. 每条配一条端到端用例：能力出现 → 读数可见 → 卸任后消失（T3 形状）。
3. 逐条记录 diff：按 `exit` 判——`kernel` / `loop` / `session` 为零、`plugin-api` 无新增能力名并逐条登记；出现其余非零即停下改判。行为名的登记面见 D-363（下表早期条目的读数保留当时形态，不再作为新增能力的样板）。
4. 受限条目（制造工具 L2、抽象协议设计 L4）写清限制：只能造自己插件的工具 / 协议需要第二方。
5. 十条走完后更新名册账与 DE-026 §5 的读数，绿灯后提交。

四条实现约束值得留给后面各条：

1. **能力表键是全表唯一的名字空间（族不参与键）**。`persona` 那条同时有一个挂载行
   `persona`，段若也叫 `persona` 会把挂载行顶掉，而顶掉之后**没有任何报错**——设置页
   少一项、VDFS 少一个挂载点、配置再也改不了。段名因此是 `persona-tone`（`memory` 的
   `agent-memory`、`model` 的 `model-persona` 是同一条纪律），单元测试里有一条结构性
   断言钉着它。
2. **平凡值必须让「装不装本插件」在没配置时逐字无差**。人格出厂为空 ⇒ 一条段都不交
   ⇒ 系统提示词与今天相同。这一条让 `t46` / `t57` 那类提示词形状判据不需要为新插件改
   基线——否则每落一条 A 类能力都要动一遍全局基线，「架构稳定」就成了纸面话。
3. **能力包自己的事实一定要有归宿行**（`ROWS`）。少了它 `seal` 报 `OrphanFact`，整张
   装配表失败；而在**单元测试**里也会失败，因为测试二进制不链接 `loop` —— 协议五格的
   自读行要由测试夹具补（`decl.test.rs` 里的 `protocol_rows`，与 `notes` 同形）。
4. **行为名不再进 `plugin-api`（D-363）**。名字与造格声明由能力包在自己的 crate 里自报
   （`submit_behavior!` + `ToolBehavior::kind`），宿主只收集；上面 #33 / #39 / #49 / #37
   读数里的「`behaviors.rs` 加常量 + 收进 `KNOWN`」记录的是当时形态，**不再是新能力的样板**。
   判据由单测 `behaviors::tests::this_module_holds_no_capability_names` 钉住：
   `behaviors.rs` 出现字符串常量即红。新增能力只改自己的 crate（装配与生成的清单见下）。

## 新增一个能力的装配清单（D-363 之后）

「只改自己 crate」指**机制面**：`kernel` / `loop` / `session` / `plugin-api` 零改动。装配面
仍有必须碰的文件，按性质分两类，不美化：

**装配 / 配置（每次都要写，但都是声明，不是代码耦合）**

- 新 crate 的 `crates/symbio-plugin-*/Cargo.toml`（根 workspace 用 `crates/*` 通配，**不动**）
- 新 crate 的 `PLUGIN.yml`：`plugin_id` / `plugin_order` / `plugin_assembly` /
  `plugin_provider`，以及工具命名空间、触发种类、主体行等声明
- 工具元数据的 `behaviors` 与实现里的 `ToolBehavior::behavior`：同一个名字常量在
  **本 crate 内**写两处（工具声明 + 实现），这是「两侧各自声明」的设计，不是中心表
- 一份 e2e 用例（`e2e/cases/`，能力若新增 LLM 可见工具）

**门禁基线（手改，但只是把新事实登记进棘轮）**

- `scripts/tool-decls-audit.mjs` 的 `DEFAULT_BASELINE`：新增 LLM 可见工具时
- `scripts/gate.d/_shared.mjs` 的 `e2eCases`：新增 e2e 用例时（只许升；降要 `baseline-allow`）

**生成物（跑门禁自动写，不手改；`--check` 防漂移）**

- `crates/symbio/Cargo.toml` 的插件链接块、`crates/symbio/src/lib.rs` 的链接行
- `crates/symbio-deploy/src/lib.rs`（装配清单，各 `PLUGIN.yml` 的投影）
- `docs/004-ref/006-当前事实表.md`（插件 / 挂载点 / 路由 / 工具名等结构事实）

**还欠的代码耦合（不属于新增能力的必经面，但改名要同时改两处）**

- `task_table`：声明方在 `symbio-plugin-local` 的 `todo_write`，实现与登记在
  `symbio-plugin-task`；`E-009` 禁插件间依赖，所以名字串两边各写一次。要收掉它，
  只能把工具并入实现方，或给「声明方」一个不依赖兄弟插件的共享词汇位——两者都要
  单独决策，不在本条里顺手做。
