# S6：loop 存量能力逐批迁出

## 内容

前置的账（`DE-026` §2.3）与三样通用件（S3–S5）补齐后，`loop` 里的能力就能一段一段搬走。批次以 §2.3 的账为准
（名册在 loop 的 10 行：工作记忆、情景记忆、语义记忆、程序记忆、长期记忆检索、
副作用分级、规划与重规划、技能编译、反自动化回退、独立验证与返工）；另有三步
名册不单列（折在「多轮对话」里）但同样按名字存在于 `loop`，`SC-006` 的零工具名口径一并要求
逐条归类：语义压缩、判决 / 措辞、汇报产线（后两条 = L6，判不成批，见 `D-291`）。按「先无耦合、后带模型」排序，每批一个提交，
每批都带 T1 / T2 / T3 与一条反向用例（D-245）：

每批的验收不是「代码搬了多少行」，而是**删掉了什么**：`loop_rows.rs` 里的那一条行 /
那一个 `ActorDecl` / 那一段按名字的分支不再存在，而端到端输出不变。

**迁移提交不含机制增量**（`EX-007` / D-247）。某一批若发现「还缺一条端口 / 一条分支才迁得动」，
说明前置设计不足：停下这一批，把补件单列为带 `### D-NNN` 的独立提交（通用、不含能力名），
再恢复迁移。不许在迁移提交里顺手在 `loop` 加行、加分支、加常量；也不许把能力实现搬进
`core` / `kernel` 或别的控制面模块来「满足」封闭集——那是反向拆分。

**L2b 起手前勘察出的六条约束**（省下一次重复勘察，都是这次实际踩到的；第 4 / 5 / 6 条
已由 `D-268` 裁决消失，原文与「为什么消失」都留着——那三条正是「前提错了会造出三个
假阻塞」的样本）：

1. **不新建 crate，落 `symbio-plugin-memory` 的子模块**（`D-267`）。记忆是一个所有者：
   文件形态（`AGENTS.md` / `WORKSPACE.md`）与事件形态（`memory.encoded`）是同一个
   所有者的三种载体，拆成四个插件之后没有任何一处说得出「记忆归谁」。`episodic`
   子模块已经并回去了，`recall` / `semantic` 照同一个形状落。
2. **扫描配额要在包内重算**。`Retrieval` 自带 `degraded`，意味着
   `RECALL_SCAN_QUOTA` 的截断语义（`Projection::apply` 的三行：配额取 `max(1)`、
   只截尾、`degraded = 窗口 < 全长`）必须由 `Retriever::retrieve` 自己实现一遍。
   省掉就是「空且不标降级」——DE-036 §6 验收 2 要消灭的那个形态。
3. **测试面比代码面大**。`memory_events.test.rs` 里有 15 条用例直接钉
   `recall_view` / `prompt_section` 的口径（新近序、查询语义维、跨会话只扫一层、
   降级措辞、同文去重、排除式遗忘）。它们随能力一起搬，不能删——那 15 条就是
   D-264 四条口径的验收，删掉等于把验收一起搬没了。
4. **`memory.live` 的两块事实形状 —— 已裁决（`D-268` 第 3 条），落地时订正（`D-270`）**：
   `memory.consolidated` / `memory.forgotten` 今天没有 `FactDecl`，而 `ViewDecl.reads` 只认
   已登记字段。`D-268` 原判「形状随写方走，补在 `control_decl` 的 `FACTS` 里」——**实测
   不成立**：`OrphanFact` 要求形状至少被一行**直接或经视图**读到，而 `ROWS` 在能力包，
   loop 的私有小世界（`loop_rows::tests`）里没有任何行读它，58 项当场红；反过来把形状留
   宿主，包内 `memory.live` 的 `reads` 报 `UnknownFact`（`E-009`）。`D-270` 因此改判：
   **形状随事实词汇的 owner 走，不随写方走**——两张形状与归宿行同住能力包。它是**同一批
   的声明面**，不是前置补件。
5. **`memory.forgotten` 的排除边读信封字段 —— 已裁决（D-268）**：`produced_by` 在信封上，
   `reads` 只收 `(事实名, 载荷字段)` ⇒ 依赖图少一条边。读数不受影响（折叠拿的是完整
   `&[Event]`），缺口登记在 D-268「一处登记在案的缺口」里。不开 `reads` 的口子。
6. **巩固的失败方向 —— 已裁决（D-268）**：不再有「视图不可用」这一支要裁。`memory.live`
   由记忆包声明，包被停用 ⇒ **编码也不发生**（写方是同一个包）⇒ 没有增长要治；巩固按
   `ViewRead` 的既有缺席态跳过并记一条 debug。原担心（跳过 ⇒ 无界增长）的前提不成立。

第 4 / 5 / 6 条同源：它们都由「折叠做成声明视图」这一个前提推出来，前提是对的，只是
三条都不是**补件**——两张形状是同一批的声明面、信封边是一条登记在案的缺口、失败方向
由「包停用则编码也不发生」直接答掉。L2b 因此是**一次纯迁移**：落点、配额重算、测试面
三条约束 + 声明面（`memory.live` + 两张 `FactDecl`）。**巩固不迁**——它落在 `D-269`
的「聚合触发」空格里，名册 #2 记 `拆（受限）`；L2b′ 取消。


**L1 起手前勘察**（名册 #1 与 #16 都不成批，理由不是「难拆」，是**没有判定生产者**）：

1. **工作记忆 = 四块，没有一块还在 `loop` 里等着搬**。DE-001 §9.1 把它列成**投影参数**
   （`since(now-5min)` + 容量 4 = 窗口），不是一套存储，也不是一条判定——那四块是：
   - **段**已迁完：召回段随 L2b 进 `recall::provider`、调度段随 L3a 进 `symbio-plugin-task`。
     委派段留 `loop` 是既有裁决（D-208 / D-215 / D-220：它判「本会话有哪些工具、worker
     怎么起」），不是本批的漏项。
   - **压缩**是 `context.rs` 的主体（阈值 / 切分点 / 收益护栏 / 摘要提示词 / 流水线），
     由 L5 承接——它不在名册里单列，却是 #1 唯一还带着判定的一块。
   - **窗口**是会话基底：容量来自 `session.context_window()`，投影由会话侧给出，`loop`
     不持有它的判据。
   - **装配**是环的一步：`build_request_sections` 不知道自己有几段，只按 owner 序拼、
     空段过滤（D-215），接缝动作挂在 `seam` 行上——那是 L7 要判的东西。
2. **跨步状态不再另写一遍事实**：`Prepared.exchange` 是工具往返消息的**第二次物化**，
   源头已在 I-1（工具结果本身就是事实）。把它「走 I-1」再写一遍，等于给同一件事加第二个
   写者（D-020）；「每步从事实重放」是性能选择，不是能力迁移。
3. **规划与重规划没有判定生产者**：全仓没有持久化的计划——每一步的「计划」就是一次模型
   往返（I-4），重规划是环的 decide → act → observe 本身（D-222 裁决 1）。要迁它，先得有
   一条按名字存在的判定；今天没有。
4. **所以 L1 取消**：名册 #1 记 `拆（受限）`（段已落、压缩归 L5）、#16 记 `留 环`。
   将来真要做「≈4 槽」的工作记忆策略（DE-031 已记今天没有这个语义），那是**新增能力**
   ——读已记录的事实、交 I-2 段——走准入（DE-026 §2.2），不是一次迁移。

**L5 起手前勘察**（下一步的入口，省一次重复勘察）：压缩整条**建在 `core` 的 ops 上**
——`run_ops` 的 `CompressionBegin` / `CompressionFinish` / `Consolidate` /
`ReplaceAll` / `RemoveNodes`，外加流式帧（`CompressionEmitter`）与前端广播。能力包只链接
`plugin-api`（DE-025 D-258）⇒ **L5 的前置是一次补件**，不是搬代码：省略面（I-5 的
`elision` 事实已有，D-249）、摘要往返（I-4 的 `RowStep::Ask` 已有）、压缩帧（前端可见的
那一段）三样得先落进 `plugin-api`，压缩才可能只交「一条省略事实 + 一次往返」。这与批次表
给 L5 写的目标形状（「模型往返端口 + 通用省略事实」）是同一件事——顺序是补件在前。

**L7 起手前勘察**（续幕 / 装配两条都不成批，理由与 L1 同族：**没有可搬的判定**）：

1. **`continue` 是环的续幕动作**，不是能力。`chat_loop::drive::continue_drive` 的全部内容
   是「用新幕的锚把环再开一次」：复用轮号与用户格、落一格
   `turn.stage{stage:"round", round:N+1}` 作新幕锚、重落当轮生效配置。动作体里没有一条
   分支读别人的名字，`ACTOR_CONTINUE` 的名单也只有那两格。它是 `D-222` 裁决 2 的宿主侧
   ——I-6 交的是**一条让前件成立的事实**，不是实现；把实现搬进能力包等于让能力决定
   「环什么时候再转一圈」，那正是环自己的判据。

2. **`seam` 是装配，不是能力**。`land_seam` 落的五格（`turn.stage{stage:"inputs"}` /
   `session.consolidated` / `turn.dispatch` / `chat.assistant.opening` / `turn.branch`）
   是**一件事的五个落点**：「轮首那几行跑完之后、请求之前的这一次装配」。五格归一个
   执行体的理由 `ACTOR_SEAM` 的注释已经写明——拆成五行会让「谁先落」重新变成代码里的
   行序。它的输入全部来自别的行（压缩的合并结果、判决、召回），本段只把它们按序落到
   事实面，不产出任何一条属于某个能力的判定。

3. **`session.consolidated` 那一格看起来像能力，但它已经归 L5**：这一格的**内容**是压缩
   的产物，这里只是它的落点。L5 落地后这一格仍由接缝落——压缩能力交的是省略事实（I-5）
   与摘要正文，落点不随能力走，这是「写口唯一」的直接后果（`D-241` 的同一条理由）。

4. **所以 L7 的产出是这条判定本身，不是代码**：名册里没有「续幕」与「装配」两行
   （它们折在 #11 多轮对话里，而 #11 已裁 `留 环`），两条执行体都落在五类残留的**环**
   这一格。`loop_rows.rs` 里 `CONTINUE` / `SEAM` 两条声明保留，理由住这里而不是代码注释里
   ——注释是「这一段为什么这样写」，账是「这一条为什么不搬」，两件事。

**L6 起手前勘察**（判形状用；结论是 `D-291` 的「不成批」，留下的两条硬事实是它的依据）：判决**已经不是 loop 的策略**。
`chat_loop::decide.rs` 只做三件事——投出对话线、经容器 `route` 调 `classify/decide`、
照它给的计划打一次**入账的**模型往返再经 `classify/parse` 收回判决；「什么样的输入该走
工具循环」这条判据在 `crates/symbio-plugin-classify` 里（`rules.rs` / `decide.rs`）。措辞
同理：`ReportPort` 交下来的只是一个 `ReportTextFn`，产文本的是
`crates/symbio-plugin-compose`。于是 L6 剩的不是「把策略搬走」（策略已经搬完了），而是
**把这段 glue 从「本插件私有的一次往返」换成 I-4 的一行**：`ACTOR_CLASSIFY` 的名单里
`turn.stage` 那一格、`port/classify.rs` 的三格记账、`decide_turn` 的 provider 解析，三样
合起来正是一条 `RowStep::Ask`（宿主执行、预算与租约归宿主、请求与应答落格）。它归哪一类
**取决于形状够不够**，而这一格实测出的第一条硬事实是：**`RowHandler::parse` 的产物是
`Vec<FactDraft>`，`RowStep` 只从 `run` 出**（`crates/symbio-plugin-api/src/rows.rs` 的两个
方法签名）。于是「打一次模型往返，然后这一轮到此为止」这个组合今天写不出来——`Ask` 之后
只能落事实、只能继续欠下一步。判决要的正是那个组合：`run_classify` 拿到 `Decision` 之后经
`apply_verdict` 改写对话面并可能直接收尾（`VerdictEffect::Finish`）。

第二条硬事实给出一条**看起来**绕得开的路：判决与措辞本来就是两个能力（前者在
`symbio-plugin-classify`，后者在 `symbio-plugin-compose`），而能力之间不许互相调用
（`E-009`）⇒ 它们只能靠事实接力。于是可以拆成两行：判决那一行 `run` 交 `Ask`、`parse` 只落
一条判决事实（这是 `parse` **做得到**的）；措辞那一行读那条事实，在自己的 `run` 里交
`Answer`（`run` 交 `Answer` 也是**做得到**的）。两行各自落在自己的包里，中间那条事实就是
接力的全部。

**裁决已出（`D-291`）：不成批。** 按「先判形状，再判类别」走完，两条路都不通，而卡住的地方
不在 `parse` 的产物类型上：接力只解决「一次往返 + 作答」这一半，把判决变成**被另一行消费的
中间事实**正触发 `D-235` §四 自己写下的翻案条件（⇒ 按 `announce` / `dispatch` / `await`
三行走，而那三行是 `D-235` 被否表里「拆成 `plan` / `parse` 两行」那一条）；另一半卡在两处
写口——两行的出口是阶段格（`D-228`：「这一步做过没有」只有一种写法，`stage_events::land`，
而 `turn.stage` 不在 `plugin-api` 生成的跨插件事件词汇里，能力包连名字都拿不到），判决与
汇报的产物一半是对话面节点与实时上线（`D-020` 转写唯一写口；上线属 I-7 过程体，不开放）。
`apply_verdict` 对 `Escalate` / `Report` / `Silent` 三种结局的对话面改写**落不成事实**这一
待判点因此有了答案：它不是判决能力自己的事，是「谁改转写」的事，答案是没有别人。

于是 L6 与 L1 / L4 / L7 / L8 同一处置：**没有可搬的判定**，本批的产出是这条判定本身。
`policy.classify` / `policy.report` 两条声明留在表上，归**环**那一类——前件折自
`turn_head` / `report_due`，说的是「轮到这一步」，不是「某个能力的 owner 在场」；四条归属、
三条被否与两条翻案条件写在 `D-291`，这里不复述理由。

**为什么不半途提交**：`D-245` 要求「插件落好 → 绑定切换 + 旧实现删除」同一提交，
`D-247` 禁止迁移提交夹带机制增量。两批各是一个原子批次，起手就必须走完；
把 crate 建好但 loop 未切绑定的中间态**不能进主干**（两份实现同时生效，`EX-003`
正是判它的反向用例）。

1. 每批先在新 crate 落实现（未绑定，不生效），核对 `deactivate` 下系统完整运行。
2. 同一提交切换绑定并删除 `loop` 旧实现；不允许两份同时生效。
3. 跑该能力的端到端用例与 `EX-003` 反向用例（两份实现同时生效必须红）。
