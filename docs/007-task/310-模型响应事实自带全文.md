## 内容

2026-10-25 的一次外部分析对着代码问「一次世界端口调用该落一条事实还是多条」，查出现状**既不是
一条也不是多条，而是同一条内容有三个 owner**：

| 事实 | 载荷里现在有什么 | 出处 |
|---|---|---|
| `response{port=model}` | 只有 `calls`（字段白名单 `port` / `id` / `attempt` / `calls` / `via`） | `symbio_core/decl/mod.rs` 的 `RESPONSE_FIELDS`；写方 `turn_runner/stream.rs` |
| `chat.assistant.final`（收束格） | `text` / `reasoning` / `rounds[]` / `tool_calls[]` —— **整轮**聚合，跨多次调用 | `turn_runner/facts.rs` 的 `produced_payload` |
| `artifact.added`（工具产物格） | 第一批那一格额外带 `round`＝**这一轮中途的正文与思考** | `turn_runner/batch.rs` 的 `land_artifacts` |

目标形状只有一句话：**事实 = 一次发生的原子事件**，而一次模型调用是一次原子事件——
`Reasoning` / `Text` / 多个 `ToolCall` 来自同一个请求的同一次响应，不是三次独立的世界事件。
把它们拆成三条事实会让 `await-model` 没人关账、`Store::append` 的逐事件原子性造出
「有思考没正文」这种世界不会产生的半状态，而分组键照样得留着。所以正确的拆分只有一处：
**`calls` 是集合字段**，由 `open-tools` 的 `expand` 逐元素开成 `request{port=tool}`，
每次工具调用各成一对端口事实（批次是集合不是单项）。

三处并存的代价是可数的，也正是本次要避免的过渡形状：

1. **`response` 不是它自己的完整响应。** `stream.rs` 的注释写着「模型调用是可恢复的最小单位」，
   而这个单位的事实不自洽——按 `seq` 重放这一次调用，取不到它说了什么。
2. **中途内容挂在工具产物上是投影补丁。** `batch.rs` 的理由写得很直白：只记在收束格，
   重开会话会把中途产出整体挪到全部工具卡片之后。它绕过的恰恰是第 1 条的缺口。
3. **同一件东西两种形状。** `response.calls` 带 `name` / `arguments`，收束格的 `tool_calls`
   带 `id` / `name` / `args` / `wire_id` / `result_id`；改一次要动两处，且必然漂移。

## 判据

| # | 判据 | 承担者 |
|---|---|---|
| 1 | 一次模型调用一条 `response`，载荷含这次调用的全部产出 | 字段声明 + 写方用例 |
| 2 | 正文 / 思考 / 工具调用各只有一个 owner | 重建用例按 `seq` 读，不再读收束格的 `rounds` |
