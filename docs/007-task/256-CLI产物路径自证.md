## 内容

**已发生的事故**（2026-10-23 实测）：照 `cli/README.md` 与 `build-cli.mjs` 的提示找产物，
用的是仓库根 `target/debug/symbio-cli.exe`（10-09 22:41，陈旧），而真实产物在
`symbio/target/debug/symbio-cli.exe`（10-23 23:36）。陈旧二进制跑出来的 WAL 只有 2 格
（`user.message` + `chat.assistant.final`），`produced_by` / `ts` / `reason` 全缺，
`obligation-ring-accept` 报 J4 红 + J8 差额 2 —— **一整批结论跑在假红上**。

**为什么会这样**：`cli/.cargo/config.toml`（机器本地、不入库）把 `target-dir`
重定向到 `<仓库根>\symbio\target`（理由见该文件：复用 `symbio` 的 C 依赖缓存，
避免 aws-lc-sys 全量重编）。于是「规范位置」与「本机落点」不一致。

**为什么不能靠改文档解决**：`doc-symbol-audit` 的 D-012 **明令禁止**文档里出现
`symbio/target/…`（具名目录段即红），因为那条路径在标准布局下指向的是几个月前的旧产物。
所以文档必须继续写规范路径，**该修的是脚本**：它现在无条件打印 `cliArtifactRelPath(PROFILE)`，
从不检查那个文件在不在。

**修法**（以「工具自证」为准，不以「补一句注释」为准）：

1. `scripts/cli-binary.mjs` 增加按 profile 解析的出口（现成的 `cliBinaryCandidates`
   已经会探测三个位置，但只对 `release` 暴露）——取**实际存在且最新**的一份。
2. `cli/scripts/build-cli.mjs` 在 `status === 0` 之后：
   - 解析实际产物；不存在 ⇒ `fail()` 并列出全部候选（构建成功却没有产物 = 构建配置有问题，必须喊）；
   - 打印绝对路径 + 规范相对路径两行，读者照哪一行都不会走错。
3. `cli/README.md` 补一句「以脚本打印的绝对路径为准；若本机改过
   `cli/.cargo/config.toml` 的 `target-dir`，规范位置不适用」——**不写具体机器路径**。

**判据**：这条任务自己就是判据的补丁——D-012 管「文档别写错位置」，
本任务管「脚本别报错位置」。两者合起来，「产物在哪」才只有一份真相。
