## 内容

2026-10-25 的一次外部分析对着代码问了一句「Turn 为什么还在」，得到的答案分两半：
**Turn 作为一次运行的根身份不是遗留**（`Event.turn` 分桶 N3、零债答话轮的落点、工具轮 /
续写轮 / 恢复幕的同一次运行、上下文窗口按轮、UI 根骨架、单写者与看门狗），
**Turn 作为整轮编排容器加固定七步才是过渡态**。后半句正是本任务。

目标形状早就写在 [`docs/003-design/001-核心架构.md`](../003-design/001-核心架构.md "DE-001-核心架构") §4.3：
`agent = fixpoint(decide) over (事实日志 × 世界端口)`，单环 / 一表 / 一源。
今天到得了的地方是**一轮之内**：两台 host 各有一个派发点（`drive_head`、`drive_steps`），
它们把「这一轮此刻欠什么」整个交给 `ring::drive`。一轮之外仍是 `chat_loop` 按步骤编号
走的直线代码（准备 → 执行 → 汇报 → 收束 → 落库 → 唤醒），[`docs/003-design/090-过渡方案.md`](../003-design/090-过渡方案.md "DE-090-过渡方案") §1.1.2
把这条限定写在了现状文档里，理由正是「内环闭环」与「目标达成」在读数上长得一样。

这条限定**不该继续被支持**：推迟它的那条裁决（[`docs/003-design/015-义务环.md`](../003-design/015-义务环.md "DE-015-义务环") 的 D-107）
是施工期的判断，而 A1 / A2 已随外环收编前三批落地，剩下的只有七步本身。
D-159 裁的是「五行怎么接回」，它自己写着「不裁七步本身」——所以缺的是**一条新裁决**，
不是一次搬运。

顺带收掉一处命名遗留：`execute-turn` 这一行执行的是**一次模型往返**（`prio` 60，出口是
`turn_closed`），名字还停在 v1「一轮 = 一次调用」的粒度上；行名随本任务的新形状一起定，
不在形状未定之前改名（改了下一批还要再改）。

  核对到的现状（对着代码，不是对着文档）：

  | 七步 | 今天谁做 | 有没有行 |

  | 落库 | `finish_turn` → `persist_messages` | 无 |
  | 唤醒 | `wake::process_wake`（在循环之前） | 无 |

  顺带修了一处**文档与代码漂移**：DE-015 §2.5 把 `execute` 行的输入写成
  「`turn.inputs.ready` 视图（所有前置阶段已完成）」，而这个视图在代码里不存在——
  `execute-turn` 的 `owes` 读的是 `turn_head` 的三格让位前件（`tools_open` /
  `reflex_answered` / `model_open`）。已按代码改口径。

  新裁决要回答的三件事（三段今天没有行，各自的「欠」与「还」是什么）：

  1. **准备**：欠不欠一次「为这一幕装载输入」？前件是幕已开 ∧ 输入未就绪；出口只能是
     「输入就绪」这件事落成事实（今天它是函数返回值，`prepare_turn_inputs` 的 `Ok`）。
     它同时是 `dispatch-turn` 接线的**前件**——`turn` 的派发点要有东西可派，就得先有
     「请求已构造」这个事实（D-166 给 `model` 端口裁过的同一件事）。
  2. **落库**：欠不欠一次「把这一幕写进会话存储」？今天它是 `finish_turn` 里的一步，
     失败只报错不给环——而它恰恰是「收束之后才能做」的一笔（键取 `turn`）。
  3. **唤醒**：它是**幕间**的事（下一次要开会话跑起来吗），还是幕内的一行？这决定外环的
     单位是「幕」还是「会话」——若是后者，`drive` 的 host 集合要多一台，`TurnState`
     也不再是唯一的借用面。**这一条要先裁，另外两条的形状跟着它定。**

- 2026-10-25（批 1 · 判据 1 收口）：**DE-015 新增 D-168**，把三问一起裁掉。结论与三问的
  预设不同——只有「准备」该有行，另外两段**不该**：

  | 段 | 归属 | 一句话理由 |
  |---|---|---|
  | 准备 | 一行 `prepare-turn`，出口 `turn.stage{stage:"inputs"}` | 有完整的「欠 → 还」，且它是 `dispatch-turn` 的前件 |
  | 收束 | 已归 `close-turn`（轮内 host）；「流向判定」折进 `turn_head` 一格 | 流向是**幕推进的条件**，读它的是迭代器，不是执行体的返回值 |
  | 收尾两段 | 不进表，是 `dispatch-turn` 的产出处理 | 输入是 `TurnOutput` / 内存镜像，没有独立前件 |
  | 落库 | 不进表，是**写投影** | 两头都不是事实 ⇒ 没有 `until` 可写，重复执行是 no-op |
  | 唤醒 | 不进表，是**交换点** | 与「工具完成 / 插话 / 定时 / 审批」同类（DE-001 §4.3）：只有入口，没有前件 |

  最要紧的一条是**「开一幕」不能是一行**：债的前件按幕收窄，而开一幕产出的正是幕号本身
  ⇒ 自指。所以它是**迭代器**，在环外一层；外环因此长成「幕的迭代器 + 幕内的不动点」两段，
  而不是一个把七步圈起来的 `loop`（那正是 DE-021 提前否掉的「假的不动点」）。

  顺带改口：`dispatch-turn` 的 `by = None` 不是「还没接」，是**它的派发点在外环里**——
  外环不成环就没有能选中它的地方。这条改口让 T-311 剩下的半批与本任务合流成同一件事。

  三项诚实划界已写进 D-168 的「这一条没有解决什么」：续写次数仍在内存里（「再开一幕」的
  第二个入口在事实面上还不完备）、`TurnState` 仍不是纯借用面、表外的点问不在射程。

  判据 1 由此收口；判据 2-5 待后续批（接回顺序见 D-168 的「接回读数」段）。

  **判据 2 还没有收口**：主循环体仍留着准备段与步骤 5-7（收尾 / 结算 / 封根）的直线代码，

  成立；`obligation-bypass-audit` 的调度旁路基线仍是 0/0（幂等点问 3/3），改动后未破。

  踩到的三个装载红（都是行表自己报的，不是事后补的注释）：

  1. `ActorCannotClose { row: "announce-turn" }`：出口写成 `turn_closed` 时，宣布行的 `writes`
     只有 `request`，与「收束 / 兜底两格」无交集 ⇒ 宣布这一笔永远关不掉自己。
  2. 改成把 `turn` 端口进度并进 `turn_head`（原打算加 v12 两格）⇒
     `DependencyCycle { cycle: ["announce-turn", "open-tools", "announce-turn"] }`：
     `turn_head` 的证据集是读面全集、含 `request`，宣布行挂它出口就把 `request` 拉进出口线，
     与同样写 `request`、同样以 `request` 关门的 `open-tools` 连成**假环**。裁决 5 的
     「单开 `turn_round`」由此是被装载器逼出来的，不是设计偏好。
  3. `prio` 是全局裁决序：宣布行（57）必须先于执行行（60），整块表序因此重排。

  一项改口：`dispatch-turn` 的 `by = None` 不再是「还没接线」——它的派发点在外环里，
  外环不成环就没有能选中它的地方（D-168 的「接回读数」段）。

- 2026-10-25（批 3 · 准备段接回）：**步骤 3 退场**——`prepare-turn` 成了外环的第一条行
  （prio 56，`by = prepare`，前件 `turn_head.prepared == false`，出口
  `turn.stage{stage:"inputs"}`）。`chat_loop` 里那段 `prepare_turn_inputs(...)` 的调用
  与它的 `match Err(exit)` 一起删净，主循环体因此少一个「按步骤编号的调用点」。

  形状上的三处新东西：

  | 落点 | 形状 | 为什么必须这样 |
  |---|---|---|
  | `turn_head` v12 | 新格 `prepared`（本幕落过 `inputs` 没有） | 读面不变（`turn.stage` 本来就在证据集里），只是把「这一幕准备过没有」折成一格 |
  | `StageName::Inputs` | 新阶段名，`result` 两档 `ready` / `closed` | 定稿答话轮在准备段就收束，那一幕**没有**输入；只落 `ready` 会让收束幕与「还没准备」同形，环重来一遍再答一次 |
  | `stage_closed` | 外环的**幕间**停机判据（读 `turn_closed` 视图） | 收束格落下之后 `announce-turn` 与「还没派出」在事实面上同形（两者都没有 `response(port=turn)`）。这一条**不能**写成某一行的前件：那样那一行要以收束格为出口，与 `close-turn` 成环 |

  另两处收窄：`StageDrive` / `StageStep` 不再接收 `&TurnInputs`，改成
  `&mut Option<TurnInputs>` 的**交接槽**（准备放进、派出取走、收尾读一次 `root_id`），
  `drive_stage` 交回 `StageOutcome { inputs, result }`；压缩寄存位（`context.consolidated`）
  的取用点从环之前搬进派发那一环步（见下面第一条红）。

  本批踩到的四个红（都是既有判据/用例抓到的，没有一处靠放宽判据过关）：

  1. **压缩事实静默消失**（e2e t8 / t11 / t45）：`context.consolidated.take()` 原本在
     环**之前**——那时压缩还没跑（它在准备段里由 `policy.compress` 跑），取到的是空值。
     取用点搬进 `run_dispatch_turn`，与「压缩只在派发前一刻有效」这件事对齐。
  2. **续写幕的准备落不进日志**（e2e t27 / t78 / t47）：`inputs` 阶段格的同一性原本是
     `(turn, round, stage)`——续写幕复用轮号与请求轮次，与首幕**撞成同一格**，
     `land` 把 `Duplicate` 当成功吞掉 ⇒ 派发点读到「没准备」，环在那一幕停住。
     同一性补上幕锚（与 `recall` / `reflex` 同形）。
  3. **`prepare-turn` 与 `execute-turn` 成环**：准备段的定稿答话那一档在窗口里落了
     `chat.assistant.final`，而那是 `execute-turn` 的出口格 ⇒
     `DependencyCycle ["prepare-turn","execute-turn","prepare-turn"]` 与
     `["close-turn","prepare-turn","execute-turn","close-turn"]`。收窄名单到
     `turn.stage` 一格：名单按「谁拥有这一格」配，不按「谁在窗口里碰到它」配。
  4. **`actor.writes_that_cell` 的保守分支**：`execute-turn` 的出口是收束格、
     不含 `turn.stage`，于是「它写这一族落在哪一格」不可判 ⇒ 保守成边
     （`execute → prepare`）。这与 3 的两条边合起来才成环——只拆一条不够。

  判据 2 的读数：主循环体只剩准备**之前**的装载段（步骤 1 / 2 / 2a）与**派出之后**的
  收尾段（步骤 5-7 / 落库）。三步账（准备 / 宣布 / 派出）都在表上，选债仍只有
  `ring::drive`；`obligation-bypass-audit` 的调度旁路基线仍 0/0。
