## 内容

### 缺口是什么

`Decl.expand` 今天只做一件事：把一条 `owes` 展开成 N 个键，于是 N 笔债各自开账。
派发侧仍是**一批一次**：`dispatch-tools` 的动作内部按顺序跑完所有元素。
于是 [DE-015-义务环](../003-design/015-义务环.md "DE-015-义务环") §2.8 的
"`concurrent: true` 时同批子债可并发派发"这句话，在实现里**没有任何执行方**——
它不是"没做完"，是"没有判据能发现它没做"。批次耗时因此是元素耗时之和。

### 为什么它排在 T-011 之后

并发派发是**派发器的能力**，不是工具层的优化。派发器在 T-011 之前有三份（轮内 / 轮首 / 批次边界），
在这一层做并发就得做三遍；而且"同批子债"这个概念在那三份里只有一份认得出（轮内那张表才有 `expand`）。
一个环之后，这里是唯一的地方。

### 三个必须一起回答的问题（缺一条就是"并发了个寂寞"）

1. **上界**：并发度是几？无上界等于把 `MAX_STEPS_PER_DRIVE` 的语义偷换成"步数 × 并发度"。
   上界必须是一个声明位（行上或 `PortDecl` 上），不是一个常量。
2. **部分失败**：三个元素两成一败，那一笔败的债落 `failed`，另外两笔照常收——
   "整批失败"会让已经成功的世界副作用被事实面否认。
3. **写冲突**：同一批元素的 `response` 落在同一行、同一视图里，键是 `(port, id, attempt)`，
   元素身份在键里 ⇒ 不冲突。这一条要**证明**（反向用例），不能假定。

### 不做什么

- **不改求解器的选债**：`ring::drive` 仍一次给一笔。并发发生在**派发器拿到这一笔之后**：
  它问一次"这笔属于哪个 `expand` 实例、同批还有哪几笔"，再一起派出。
  （把选债改成一次给 N 笔就是改求解器字节，`PTS-003` 会红。）
- **不动 `concurrent: false` 的行**：副作用型的工具必须串行，这条不在本任务改。
