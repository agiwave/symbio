## 内容

审计 §1.3-① 最重的一条：`DE-090 §1` 的六步路径**只有步 1 有任务载体**（DE-103），
`DE-002 §4` 把「一个能力一个插件、可卸载」列进不可妥协的架构面，而它的验证判据正是步 6。
这批 13 条缺口任务做完，得到的是账更诚实、几个能力补上——但**「一环一表一源」仍停在 1/6 的读数**。

复核代码后（2026-10-24），六步的实际状态比审计初读要靠前，**差距主要是账没记**：

| 步 | §1.1 的收口判据 | 代码现状（初步） |
|:-:|---|---|
| 1 | Step 循环 + 事件批序 + 投影 | 已收口（DE-103） |
| 2 | 建行表，挂 `policy.classify` / `policy.report` | `loop_rows.rs` 已有这两行（含全套端口/授权级联行）——**判据「事实网格 + Step 序列逐格比对」是否真跑过，待核** |
| 3 | 压缩 / 记忆 / 技能 / 反射移入行表 | `policy.compress` / `recall` / `reflex` 三行在表；「每行有独立开关可逐个验证」待核 |
| 4 | 工具 / 模型 / 提示词 / 挂载四族迁入 | 工具、模型两族有行；**`prompt` / `mount` 两族无行** |
| 5 | 删 v1 外壳与 `TurnState` 簿记字段 | `run_with_tools` 只在测试里存在；`TurnState` 已不在生产代码——**待正式记入** |

所以本批的形状是：**一条对账（T-296）+ 两条真缺口（T-297 / T-298）+ 一条契约显形（T-303）**。
对账本身就有产出——如果步 2 / 3 / 5 的判据确实满足，§1.1 记上提交号后，
「架构目标 1/6」的旧读数就被纠正成 5/6，剩余工作的边界也随之清楚。

第二份核心评估（`tmp/core-review-2026-10-24/01`）的 P1-1 / P1-4（口径类）归 T-296，
P2-1 / P2-2（契约边界类）归 T-303；P1-3 / P2-5（执行方缺失类）是裁决，归 T-289；
P1-2 / P2-3（旁路与策略行）归 T-282 的重写。**本批不收能力缺口的裁决**——
「不为字面目标硬塞行表」是评估给的明确告诫，外层七步是 DE-090 的合法中间态。

**熔断线照抄 §1.3**：一处结构性改动超过 300 行即判定抽象错误，退回。
