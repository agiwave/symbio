# 扩展局部性受保护树裁决——host 纳入与否先裁后做

## 内容

### 现场

`EX-002` 的受保护树是**五棵并集**（`sdk` / `kernel` / `plugin-api` / `loop` / `session`，
`D-372`），由 `capability-migration-audit.PROTECTED_TREES` 单点定义、
`extension-locality-audit` 直接引用。`symbio-host` **不在其中**。
按 `DE-002` 的分层，host 是宿主运行时：发现族行、按会话起驱动、把债表当数据读，
「插件不依赖它」，且 `host/src/lib.rs:209-219` 对 `DRIVE_FAMILY` 强制唯一 runner。

### 判定（这一项最容易被「实现简单」带偏）

不纳入的理由会是「纳入后历史提交回溯判红、`BEFORE_GUARD` / `GRANDFATHERED` 要补一批、
现在门禁正绿」——那是**实现成本**，不是架构判据。按终态标尺：

- `DE-002 §4`：架构面（切分 / 封闭集合）不得妥协，额度只够用在「怎么写」。
- 扩展局部性的命题是「加能力不碰架构面」；host 是架构面里最硬的一层（唯一 runner 的持有者）。
  它不在受保护树里，等于**命题留了一个可机读的缺口**。
- 因此**方向是加严**：把 host 纳入并集。收窄覆盖面按 `CS-002` 精神不需要以「实现困难」为由否决，
  但**树名单是判据面**，改它属架构调整，按「架构改动只认方案为源」必须**先落一条 `D-NNN`
  判定决策**（`docs/008-judgement/`），裁决落定后再动脚本与回归用例。

裁决要回答三问：① host 是否属于「能力不该碰」的面；② 历史提交如何处置
（新口径回溯判红时，用带理由的 `BEFORE_GUARD` 逐条列明，而不是给某批能力开新豁免）；
③ 纳入后 `EX-002` 的夹具与回归用例怎样证明「新增能力时给 host 加一行按能力名分支 ⇒ 红」。

### 动作

1. 落 `draft` 判定决策单文档，列待裁问题与可选走法，**不写裁决、不动代码**。
2. 裁决转 `active` 后，改 `PROTECTED_TREES`、`extension-locality-audit` 的回归用例与
   `gate.d/30-docs.mjs` 注释，同步 `D-372` 相关正文。
3. 门禁绿；`EX-002` 回归用例证明新覆盖面真的会红。

exit: 受保护树名单有单一 owner 且覆盖终态所需的架构层；新增能力批次碰 host 会被判红；
`EX-002` / `EX-003` 回归绿；裁决编号可打开。

不做什么：不为让门禁绿而放宽树名单；不给具体能力开白名单；不在裁决落定前改脚本。
