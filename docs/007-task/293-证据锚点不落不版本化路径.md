## 内容

审计 §1.3-④ 与 §1.4-4 的同一类病：**判据指向一个清一次临时目录就消失的地址**。

- T-272 的 exit 第 1 条要求 `tmp/design-verify/2026-10-24/02-实现缺口清单.md` 的 G-01…G-28
  逐条有处置——`tmp/` 在 `.gitignore` 第 14 行，不进 git；
- 4 篇 done 任务的 `evidence` 指 `tmp/...` 或 `logs/gate-3.log`，其中 T-262 指向的
  `tmp/verify-2026-10-23/` **已经不存在**——这条证据今天已不可核对。

`SP-013` 要求「判据要么是守卫，要么是脚本可核对的锚」——被 ignore 的路径两条都不满足。

### 为什么挂在 `registry-lib` 而不是 `doc-link`

`evidence` / `where` 是 front-matter 字段，不是正文链接；`doc-link` 的 D-001 只判正文 markdown 链接。
但实现上**不重复造解析**：`.gitignore` 的读取与匹配如果 `doc-link` 或其它脚本已有现成实现，
RG-032 直接复用同一份（找不到就实现一份极简匹配：目录前缀 + `*.ext` 两种形状够用，
`.gitignore` 的完整语义——取反、`**`——不在本任务范围，遇到即报「形状不支持」而不是静默放行）。

### `tmp/` 不许当判据 ≠ `tmp/` 不许存在

过程材料放 `tmp/` 是合法的（本任务登记时引用的审计报告就在那里）。纪律只有一条：
**引用它的判据必须同时有一个版本化的落点**——结论进设计条目、原始材料随提交入库或明说「不留」。
RG-032 判的是字段与 exit，不判目录本身。
