## 内容

[`docs/003-design/090-过渡方案.md`](../003-design/090-过渡方案.md "DE-090-过渡方案") §1.1.3 把 17 行里 `by = None` 的八行分成三类，
其中「② 粗端口过渡」两行今天还挂着：

| 行 | 现状 | 为什么是过渡形状 |
|---|---|---|
| `dispatch-model` | `by = None`；引擎面在 `port::round_trip`，而调用点在**执行体内部** | 派发动作被写成了模型调用的一步，派发不是由表触发的 |
| `dispatch-turn` | `by = None`；`turn` 端口的往返就在整轮执行体里跑 | 同上，粒度还是「一整轮」 |

同一族的 `dispatch-tools` 已经接了 `courier`（`prio` 68），所以这不是要不要做的问题，
是**同一张模板还剩两行没照自己已落的形状补齐**。§2 的那句话把目标写死了：
粗端口期间崩溃恢复只能按整轮重放，细端口落地后在途从「一轮」细到「一次调用」。

`await-turn` / `await-model` / `await-tools` / `lease` 四行不在本任务射程内——
它们的 `by = None` 就是 `Wait` 的折叠，是目标态不是过渡态（§1.1.3 的 ① 类）。

## 判据

| # | 判据 | 承担者 |
|---|---|---|
| 1 | 两行 `by: Some`，绑定表按 host 分片（不新增 host） | 行表用例 + 装载七道检查 |
| 2 | 协议四格的写方仍是引擎 | 协议面用例 + PTS-001 |
| 3 | 在途 = 一次调用：杀掉再重放只补那一笔 | 恢复用例（断点在第二次往返前） |
| 4 | 求解器字节不动 | PTS-003 |
| 5 | DE-090 §1.1.3 的 ② 类清空、§6「粗端口在途」一行按删除条件收口 | `node scripts/registry-audit.mjs` |

## 处理过程

- 2026-10-25：登记，来自一次对着代码的过渡态盘点。前件是派发面只剩求解器
  （外环收编把策略行接净），否则派发点还在长形状，两行接进哪张绑定表都没定。

- 2026-10-25（批 1 · 模型那半）：`dispatch-model` 接回派发面——`by` 上是新执行体 `relay`，
  宣布归 `execute-turn`（落 `request`）、派出归 `relay`，两步之间靠草稿的 `pending_round`
  交接；`turn_head` 升 v11 加 `model_open`，执行行的让位从「`prio` 60 < 66 碰巧排对」
  变成事实前件。三条判据的落点：① 协议四格仍只由引擎写（`relay` 的动作调
  `port::dispatch_full`，`sent` / `response` / `failed` 全在 `port` 里落）；
  ② 派发由选债触发——宣布之后那一笔在日志上开着，派发行因此被 `next()` 选中，执行体
  不再在内部顺手调一次往返；③ 在途粒度是一次调用（一笔 `request` / 一次 `sent`，
  id 带幕锚与步号）。顺带清掉一条过渡豁免：兜底两格随写方搬到 `relay` 之后**声明得了**
  （它的出口是引擎独占的 `sent` / `failed`，与 `close` 不同族）⇒ `transitional` 全表清零。
  **未承接**：`dispatch-turn`。它的派发点在一轮之外（`chat_loop` 的固定七步里），
  没有外环就没有能选中它的派发点——前件是外环收成环那一批；判据 3 的「重放只补那一笔」
  同样要那个形状（今天重启开的是新的一幕，整轮会重走一遍）。
