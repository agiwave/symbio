# 债行同族写法台账

## 内容

## 1. 写法本身

`DebtSource::rows` 里用 `facts_of(ASK_KIND).rev().find(...)` 只取「最后一条」在等的 ask，
再据它申报一笔端口债。这个写法隐含一个前提：**同一时刻同一行最多只有一条待回执的 ask**。
前提不成立时，先发出的 ask 没人申报债、等不到自己的回执，回合计不静止——t98 就是
一回合两条便签、只发一次往返、第一条 ask 永远悬空。

## 2. 已修：notes（t98）

`crates/symbio-plugin-notes/src/debt.rs` 的 `NotesDebts::rows` 改为按 `row` 筛出本行
全部 ask，**每条 ask 各成一笔债**，债 id 取 ask 事实自己的 id（逐 ask 天然可区分）；
排除条件按每条 ask 自己的 `tool_call_id` 钉同一键的洞察，避免一条便签反思过就跳过其余。

验收：t98 单跑绿；t59 / t89 / t91 相邻 notes 用例不回归。

## 3. 仍存：classify（本轮只登记，不改）

位置：`crates/symbio-plugin-classify/src/debt.rs` 的 `ask_for`（`facts_of(ASK_KIND)` +
`rev().find`）；调用点在 `ClassifyDebts::rows`。

**当前为何安全**：`ask_for` 不是在全部 ask 里取最后一条，而是先按
`row == classify.decide` 且 ask 载荷 `key.id == user_id` 过滤，`user_id` 又取自
**最新一条 `user.message`** 的事实 id（`latest_fact_id`）。一回合只落一条 user.message，
且行在已有 ask 时改挂 `EVENT_RESPONSE`（同一 key 不会同时发出第二条 ask），
所以过滤后的候选**在同一时刻至多一条**，`rev().find` 与「取那一条」等价。

**什么条件下会变危险**（任一成立就必须按 t98 的修法改，不要等它红）：

1. 一回合落多条 `user.message`（插话 / 补充 / 重放也走同一种事实），最新那条的 ask
   与更早那条的 ask 会同时存在；
2. 同一 `user_id` 出现两条**同时等待**的 ask（行的「先答再问」约束被放宽）；
3. 过滤键变宽或换键：去掉 `key.id` 过滤、把 `user_id` 换成会话级 / 轮次级非唯一键。

## 4. 同族已定格：`latest_fact_id` 的单实例口径（D-369）

`DebtFacts::latest_fact_id(kind)` 与 `rev().find` 是同一族写法：**只取一份**，多份时
静默丢其余。契约现已写明口径——它指认「当前计划所对的那**一份**实例」，调用方只有在
**同一时刻至多一份有效实例**时才可用；否则必须用 `facts_of` 逐条。

生产调用点清点（全部按「当前那一份」读，前提由写方保证）：

| 种类 | 调用点 | 当前那一份是什么 | 前提 |
| --- | --- | --- | --- |
| `user.message` | classify / compact / compose / model / session（answer、progress、opening）/ tool | 本轮用户原话 | 一回合一条（t18 钉住） |
| `tool.requested` | tool 首派 | 还没派发过的那一轮往返 | 工具往返串行 |
| `artifact.added` | model（接工具结果） | 刚结束的那一轮产物 | 往返串行，且 `when_no_open(tool)` 挡住并行 |
| `user.answer` | tool 恢复 | **已改为按 `call_id` 反查所属请求** | — |

工具恢复原先是「最近一条答复 × 最近一条请求」——两条请求同时在场时最近的那条不是配对。
现在每条答复读自己的 `call_id`，在 `tool.requested.calls[].id` 里找到所属请求再回原键；
找不到所属请求就不恢复，不拿别的请求顶替。

**已知边界（留给「批债 / 逐笔债」的单独裁决）**：同一个 `tool.requested` 里有多条待用户
动作的调用时，恢复只消费一条答复（取最后一条），其余答复不会各自恢复——一次恢复对应
一笔请求债。触发信号：出现「同一批内两张以上待答复卡片，且用户逐张答复」的需求或用例。
届时按逐调用债务处理（每个 `call_id` 一笔恢复债），并按 t98 补「同批两卡各自恢复」的
负向用例；在裁决前不要把这一段悄悄改成逐笔。

本批试做「同一轮两次提问」的真链路用例时，还暴露了第二个边界：第二次提问的
`artifact.added` 与 `user_prompt` 事实都已落格，但消息面**没有它的 tool_call 卡**
（`call_ask_2-result` 直接挂在 turn 节点下）。这属于读方缺口而不是配对缺口，已登记
契约读者缺口台账的「同一轮第二次提问的 tool_call 卡在消息面缺失」一节；它与批内多卡
同一片区域，一起等裁决。
