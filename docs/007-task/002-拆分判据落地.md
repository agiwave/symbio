# S0：拆分判据先于迁移变红

## 内容

[DE-026-能力拆分与影响类](../003-design/026-能力拆分与影响类.md "DE-026-能力拆分与影响类") §5 的七条判据，
在迁移开始前就要能判红。否则迁移会以「全绿」停在半路：`seal` 通过、`ActorDecl` 在、
测试也绿，而派发时整条被 `bound_rows` 静默过滤掉。

- **`EX-005` 声明即绑定**：`bound_rows` 今天静默丢弃 `by` 不在 `ACTORS` 里的行；
  改成 `seal` 期报错，并补一条反向用例（声明一条无人执行的行必须红）。
- **`EX-002` T1**：新增能力只改自己目录，`core` / `kernel` / `loop` / `session` diff = 0。
  判定读的是夹具新增前后的目录指纹，不是「有没有新 crate」。
- **`EX-003` T2**：一条能力迁出后旧实现已删且同提交；反向输入是两份实现同时生效。
- **`EX-004` T3**：卸任插件后能力消失、系统完整运行；反向输入是卸载后仍有一处按名字生效。
- **`CP-009`**：`loop` / `session` 非测试代码零能力名 / 工具名，存量记进基线（文件 + 名字 + 处数），
  超一处即红，代码少了基线没跟上同样红；基线条目挂能打开的 `### D-NNN`（D-218 口径）。
- **`EX-006` 名册全覆盖**：`DE-008 §6.1` 的 54 行每一行恰好一条处置。判定读的是账本文件与
  `DE-008` 名册的对账：漏行、重复行、或留守项没写残留类与理由，都判红。
- **`EX-007` 补件与搬运分离**：对一段迁移提交的 diff 判定——`core` / `kernel` 零改动，
  `loop` / `session` 的新增只出现在生成物与装配链接；加入机制的提交必须带一条存在的
  `### D-NNN`，且新增标识符不含能力名 / 工具名。反向输入：迁移提交里加一行 `Decl`、
  或补件引用不存在的决策号，都必须红。

## 处理过程

1. 先写脚本与反向用例，跑一遍确认对现状判红的位置就是账本要记的位置。
2. 生成基线并人工核对每一条「为什么它不是能力」。
3. 接入 `scripts/gate.d/`，与既有 CP-001…CP-008 同一个入口；`EX-007` 读暂存区 / 提交区间，
   只在迁移批次上生效，补件提交凭决策号豁免。
4. 门禁全绿后提交；后续每段迁移只允许把基线往下改。
