# 抢占闭环接线

## 内容

`DE-037` §3 的抢占状态机今天只有**两端各自存在、中间没有闭合**：

- 判定端：`PreemptionDecider` / `spec` / `decide` 与三个落格函数
  （`held_event` / `resume_event` / `control_event`）都在
  `transcript/inbox.rs`，但只有测试调用；
- 存储端：`ActiveSessionState::preempt` 没有生产写方，`task.held` 没有生产写方，
  空闲分支的 `preempt.is_some()` 恒假。

`scripts/exemptions/session-dead-code.json` 把这一组登记为死代码（`batch: preemption`），
所以它们今天既不触发死代码审计，也不产生行为——**「插话会挂起任务」这句话在代码里
没有执行路径**。

本条只做一件事：把「忙窗判定 → 空闲落格」接成一条真实路径。`D-380` 已裁：**不开
跨窗端口**——两端都在 `session` 内，是同一个 owner 的两个写窗口，不是两个 owner；
接线之后若判定仍要拆出，再按那时的证据另裁。

## 处理过程

1. 忙窗：插话入队时按 `spec` / `decide` 判一次，判定结果写
   `ActiveSessionState::preempt`（三态只在这里写一次，不散落）。
2. 空闲分支：消费三态并落 `task.held` / `task.controlled`，落格后清三态；
   落格失败按既有写闸的失败方向处理，不吞。
3. 删除 `session-dead-code.json` 里 `batch: preemption` 的五条豁免（死代码审计会红，
   这是接线完成的机械判据）。
4. `t34` 补正向与反向：注入打断 → 80ms 内 `task.controlled`；预算放宽到 60000ms
   → 判定翻转；挂起期间任务离开 `readyset`；恢复后投影与挂起前一致（`DE-037` §6）。
5. 接线完成后按 `D-380` ② 复核 #14 的拆分归属：判定器若仍只有 `session` 一个 owner，
   就留在控制面并写清它属于哪一类残留；要拆再另裁，不预设端口。

## 与 T-008 的关系

`T-008` 的 #14 行以本条为**触发条件**：本条不完成，#14 不迁，也不重复论证「不是补件」
（`D-380` 已裁一次）。本条完成后再回 `T-008` 判 #14 的去留。
