## 内容

审计 §1.3-③：T-273 / T-278 的正文都写「等决策落纸后再动代码（`SP-003` 纪律 0）」，
但**没有任何任务、也没有任何 exit 是「写这条决策」**。看板上它们是 `now` / `next`，
实际启动条件不在任何人手里。这是任务粒度与纪律的冲突：任务模型缺一个能承载「裁决」的单元。

本任务只写裁决，不改代码（代码归 T-273 / T-278）。

### 裁决一：D-064 的放宽条件

`DE-034` 的行表今天只有「借来的 `held` + 单写者 FIFO + 候选集投影」；调度器、租约 TTL、
`readyset:cap` 被 D-064 收窄掉了，代价是 SC-004 的「并行推进 + 抢同一份活有仲裁」在用户面不存在。
要裁的是**事件词汇表为何必须变宽**：

- 不加 `task.ready` / `task.assigned` 能不能表达「谁可以领、谁领到了」？（否决路径要说清代价：
  例如靠视图推算 ⇒ 每次选债多读多少、崩溃后能不能重建）
- 加了之后单写者是谁、`ActorSpec` 在哪个构造点、80ms 的节拍属于哪一层；
- 收窄当初的正确性不能被这次放宽否定——决策要写「当时的约束哪一条不再成立」。

### 裁决二：权限「部分执行」的边界

`DE-090 §4.1` 记的是「声明性质」，`T-278` 要求四字段同批。要裁的是**部分执行为什么更坏**：

- 「四字段同批」是排期偏好还是不可妥协？若是后者，给出一条判据（例如「任一字段已执行而另一字段
  仍为声明 ⇒ 拒绝装载」，把半执行状态变成装载期错误）；
- 允许分档时的最小可接受形态：未接线的字段必须在声明面**显式可见**（字段名、注解或装载期告警），
  不许「同名不同义」；
- `declared_permissions` 这个「说清它没有执行方」的临时命名，在哪种裁决下改回 `permissions`。

### 裁决三：引擎失败面与「装载期拒绝开幕」的执行方（第二份核心评估 P1-3 / P2-5）

`DE-015` 引擎硬约束第 3 条写「执行体 `Err` ⇒ 引擎写 `failed{id,why}`」，但驱动器层
**没有执行方**：`ActorError` 今天只有 `Append` 一个变体，驱动器的 `Err` 分支只上抛，
`failed` 实际由端口适配器写。今天不触发（没有业务失败变体），一旦新增第一种业务失败，
这条硬约束就变成「文档有、代码无」。同类：验收判据 7 的「装载期拒绝开幕」只有运行期半条
（空表可装载、永不推进），装载期检查里没有对应的一条。

要裁的是二选一，不许 silent 悬着：

- **收窄条文**：把硬约束 3 改写为「端口失败由端口层写 `failed`；驱动器级业务失败变体
  引入时本条同步生效」；判据 7 的「拒绝开幕」改指生产装载路径恒非空（`Builder::builtin`）；
- **补执行方**：驱动器加失败变体与用例、`Builder::seal` 加空表拒绝——代价是立即多两条
  机制，收益是判据不用改。

判据是「条文与代码各指对方」：改完之后，这两条要么各有可指认的执行方，要么条文承认
执行方在别处。
