# e2e 覆盖矩阵 · 能力域 × 场景形态

> **这张表回答什么**：「从能力域倒推，正常 / 异常 / 过程缝隙各自测到了什么、还缺什么」。
> 它是**缺口清单的登记处**，不是第二份用例索引——用例事实的 owner 是 `e2e/cases/`
> 目录发现式加载 + 各用例文件头（每条钉什么在那里，本表不复述）；格子里只写编号与
> 缺口归属。任务出处与推进记录见 [T-068-e2e用例体系化升级](../009-task/068-e2e用例体系化升级.md)；注入机制归
> [T-067-mockLLM体系化机制化](../009-task/067-mockLLM体系化机制化.md)（mock-llm / mock-mcp 的能力清单见
> [e2e/README](../../e2e/README.md)，不在此复述）。
>
> **列语义**：`正常` = happy path 契约；`异常` = 注入 / 输错 / 硬件级故障后的用户可见行为；
> `缝隙` = 用户使用过程中的缝隙（多轮中途恢复、切换回来、等待与排队）。

| MCP 断连 / 挂死（stdio 无响应） | **暂不补（待接线批次）** | mock-mcp 已有断连编排能力（`e2e/README` 组件表），但「外部执行与熔断」的上游能力接线在 T-129 阶段；届时按接线判据纪律（开关翻红）配用例，先补判据会测到自己 mock 的想象行为 |
| 断流重发后的槽位形态（幽灵调用 / 重复卡片） | **已清偿：t54** | 「单响应工具超限卡死」修复三件套中，超限丢弃+反馈（t48）与断流可见失败（t49）有锚；第三件——**重发批次只产出更少调用**时的用户可见形态（不留同批两套卡片、不产出空壳调用）原先只有 `tool_accumulator.test.rs` / `stream.test.rs` 白盒判据。t54 用 mock-llm 编排「首批吐 3 个调用增量后中途 destroy → 原样重发的第二批只产出 1 个并正常收尾」，判据只走用户可见出口：实时面（与前端同构）钉「重发复用 id、不新建」，生产读出口钉「转写恰好 1 个调用、id 前缀复用、无空壳幽灵」 |

### 面缺失六项的逐行判定

> 为什么逐行而不是整批：六行看上去都是「缺用例」，但**能不能写用例**取决于各自
> 有没有可驱动的面。核实结果分成三类——有的能直接打本地靶子，有的缺一个配置位
> （属能力新增，不是本表能顺带解决的），还有一行的**前提本身不成立**。
