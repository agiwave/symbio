## ADR-011: 资源存储 = `VdfsProvider` 的集中实现

**状态**：已接受

**决策**：在宿主实现层提供**三个基于 `VdfsProvider` 接口的集中实现**——`SingleFileVdfs`（一个条目 = 一份主文件，内部不外露）、`DirVdfs`（一个条目 = 一个目录，可下钻，主文件承载内容）、`MemoryVdfs`（只在进程内）。三者共用 `entry.rs` 的条目寻址与落盘原语、`pack.rs` 的 zip / base64 与导出载荷 `VdfsPack`。磁盘布局为 `<homedir>/<category>/<id>/<manifest>`。

**理由**：
- **不再有两套并行的资源访问抽象**：存储实现本身就是 `VdfsProvider`，「一类资源 = 一份存储抽象 + 一份翻译」收缩为「一类资源 = 一次挂载点选型」。
- **换拓扑不动数据、换类别不碰协议**：三型差别只在访问拓扑。
- **不是重蹈 `EntityProvider` 覆辙**（ADR-010）：这里**没有**通用钩子 trait、没有注册表、没有适配器去猜资源形状。三个各自**完整**的具体实现，差异（标题、状态、`ext`、`schema`、写前校验、写后内存同步）由调用点以普通 Rust 参数显式传入。也**不走** `creator_create_object` 工厂——不存在第二种实现，套 `dyn` 只是把一次构造换成一次字符串查表。

**后果与不变量**：
- **三种拓扑必须显式选**：挂载点声明用哪一型、主文件叫什么（类别段名 = 插件名 = `PLUGIN_*`，主文件名 = 插件内部 `const MANIFEST`）；机制不去目录里猜。选错表现为「条目内部不该外露却外露」这类可见问题，而不是静默错乱。
- **「manifest 补齐 id」不再有唯一实现**：`model` / `mcp` 各持一份 `with_id`（有意为之：它是该资源的写入语义，不是跨插件共享原语）。
- 内存镜像与磁盘清单**同一条广播频道、同一套操作语义**，消费者无需区分条目住在哪儿。
- 变更通知的形状见 ADR-025（信封 = `{path, data?}`，**含载荷**）。

## ADR-012: 读侧成本是设计约束（「现在是什么」必须有一张可核对的表）

**状态**：已接受

**背景**：一个真实消费者（审查本仓库的 agent 会话）复盘自己的低效，五类摩擦里三类直接指向**读侧**：无法一次建模；没有可核对的读侧事实表（手抄清单会漂移）；核对不划算时读者会自动切换成「停止验证、退回文档口径」，并用自信语气包装未验证结论。

**决策**：把读侧成本当作与写侧成本对等的设计约束：
- **事实从代码提取，不从人手抄**：`docs/CURRENT.md` 由 `scripts/gen-current-facts.mjs` 只做提取（插件注册名 / VDFS 挂载点 / 自有路由臂 / LLM 工具 / 存储布局），提取不到就如实标注「运行期动态」，绝不臆造；CI `--check` 门禁保证不漂移。ADR 的「状态」行同理——它回答「这条决策现在是死是活」。
- **骨架化摘要必须支撑一次建模**：列表类 JSON 给 `count=N` + 前若干条目名（`names=[…]`），文本输出给首个有内容的行；摘要预算按能容纳完整条目名推导，不截在半个名字上。
- **占位符必须自描述取回路径**：骨架化结果附带定位锚点与 `Re-run <tool> to get the full output.`——把「要不要赌一把摘要」变成一次可预期的工具调用。

**理由**：写侧收益省的是**改代码**；读侧成本随读者数**相乘**，而反推贵到一定程度，读者会开始输出未验证的结论——这不是能力问题，是成本结构问题。修复方式不需要推翻任何既有设计。

**后果**：`CURRENT.md` 与手抄速览并存，但手抄件必须注明以生成表为准；新增插件 / 工具 / 路由后忘记重跑生成器，CI `--check` 会失败——维护者由此承担「同步事实表」的显式义务。

## ADR-028: `VdfsRequest::Move` **不收**——移动是外层组合，不是核心原语

**状态**：已接受

**背景**：`VdfsRequest` 是 `VdfsProvider::dispatch` 的**操作载荷**，而 `path` 是第一个分发键（**一个 provider = 一棵子树**）。`Move { to }` 是唯一的例外——它带**两个地址**。代价在跨子树时才显形：同一棵树内移动 = 重命名（物理盘直接 `rename`），**跨虚拟挂载树**时两端分属两棵子树，「移动」就不再是原语，而是 `copy + delete`；trait 表达不出这件事，只能由某个 provider 假装自己同时拥有两端——`composite` 就不得不先解析 `to` 属于哪个子目录、再拒绝跨目录的情形，即**用错误表达能力的缺失**。于是 `Move` 只有**恰好一个**实现者能真做，其余一律 `NotImplemented`，而「用不了」的形态在 trait 上占着一个位置、还逼着每个实现方写一条拒绝臂。

**决策**：
1. **`VdfsRequest::Move` 删除**，且**不应加回来**。删除后 `VdfsRequest` 只收拢操作载荷——**地址一律走 `path` 参数，载荷里没有任何地址字段**。
2. **`VdfsRequest::map_paths` 随之删除**（它存在的唯一理由是翻译 `Move.to`）；`VdfsChange::map_paths` **保留**——它是变更事件路径翻译的唯一入口。
3. **外层那条链一并下线**：协议操作 `vdfs/move`、LLM 工具 `vdfs_move`、前端「重命名」入口与提示态。要用移动由**外层组合**（`copy + delete`），当前外层**也不提供**——需要时再加，加在外层而不是核心 trait 上。

**理由**：删掉之后，**一类错误在结构上不可能发生**——载荷里没有第二个地址，于是「跨半移动」（物理 ↔ 虚拟）与「跨子目录移动」都没有可表达的形式，原先那两条守卫与它们的用例一起消失（**消失是因为要守的形态没了**）。这比「运行时判前缀再拒绝」是更强的保证。拒绝面收窄不等于能力收窄：`vdfs/move` 的唯一真实用途是物理盘 `rename`，而重命名在**配置型资源**上语义本就可疑——那些资源的**地址就是它的身份**（`model` / `mcp` / `skill` 皆如此），改名等于换一个对象。

**后果**：`VdfsRequest` 与 `VdfsChange` 从此各自只有一条翻译入口、各自只翻译一种东西；能力将来加在外层，核心层不受影响。

## ADR-029: 导入是**详情页动作**，不是类型入口——`VdfsNewType` 收成纯呈现定义

**状态**：已接受。取代 ADR-027 的第 2、3 条。

**背景**：ADR-027 把「可新建类型」收敛为至多一个，同时把「整包导入」表达成**类型内的第二种入口**（`VdfsNewType.import`），前端据此先问「选哪种方式」。这一版留下三处不对称：**一对逆操作分在两个层级**（导出早已是 `vdfs/action` 上的 provider 自持动词，导入却占着 `VdfsNewType` 的一个字段）；**一个呈现结构承担了操作语义**（`VdfsNewType` 的其余字段全在回答「落成后长什么样」，`source` / `import` 回答的却是「怎么把它造出来」）；**`VdfsProvider` 上多出一个系统级接口**（`root_new_type()`——而该 trait 的模块文档写着「只暴露纯接口：`VdfsProvider` 只有一个方法 `dispatch`」，且**只有根**有这条通道）。

**决策**：
1. **导入改走 `vdfs/action`**：新增 `VDFS_ACTION_IMPORT`（与 `VDFS_ACTION_EXPORT` 互为逆向），载荷是入向的 `VdfsUnpack{filename, b64}`——与出向的 `VdfsPack` 同形，只差出向独有的 `id`。
2. **`VdfsNewType` 收成纯呈现定义**：只剩 `ext` / `title` / `description` / `icon` / `node_ext` / `schema`；`source` / `import` / `VdfsNewImport` 全部撤除。
3. **新增 `DetailAction.pack`**：声明「本动作的载荷是一个本地文件」（值 = 包后缀）。前端因此**不认识「导入」这个动作**——它只认「这个动作的载荷是文件」这个形状，与导出侧认「`filename` + `b64`」的形状恰好对称。
4. **动作的适用态由 `when` 表达**：导入声明 `when: {is_existing: false}`，只在草稿（新建）态出现——同一份详情定义服务两种态，不靠第二份定义。
5. **前端撤除「选入口」这一档**：新建 = 直接进详情页；导入 = 详情页上的一条动作，取文件由渲染器的原生文件选择器完成。

**理由**：「导入」与「删除」同级——都是「对某个地址做一件事」，占的是详情页的一条动作。删除没有 `VdfsProvider::root_delete()`，导入也不该有 `root_new_type()`。**形状判定优于动作判定**：`pack`（取文件）与「导出侧认文件名 + 内容」是同一类声明（「这一步需要原生能力」），前端只翻译形状、不解释动词 ⇒ 新增同类动作零前端改动，且前端不再持有任何后端不认识的动词。撤除 `root_new_type()` 之后，`VdfsProvider` 回到「只有一个方法」——模块文档那句从假话变回真话。

## ADR-030: 地址属于**条目**，不属于节点——`VdfsItem` 拆出，写回执只给**名字**

**状态**：已接受

**背景**：`VdfsNode` 里有一个不属于它自己的字段：`path`。
1. **地址是关系，不是属性**。它回答的是「这个节点在**某一份列表**里的位置」，而同一个节点可以在不同列表里以不同地址出现（实证：设置页的一项指向插件自己那份配置文档 `<目录名>/PLUGIN.yml`，落在**另一个挂载点**里；同一份文档在自己的目录里就叫 `PLUGIN.yml`）。
2. **于是每个 provider 都得知道自己在树里的位置**：容器、虚拟层、三个存储实现各自在拼 `<父地址>/<name>`——同一条推导写了五遍；拼不出来的地方就留空，再靠访问层补一次。**两处都在补**，口径各自维护，必然漂移。
3. **`VdfsWriteResponse.path` 更含混**：具名写时它回传的是调用方刚给的地址（把已知的东西还回去）；匿名写时它是 provider 生成的名字**混在地址里**——前端因此要取末段，还得额外挡「空路径 == 虚拟根」这个哨兵。

**决策**：
1. **`VdfsNode` 去掉 `path`**——它是纯自述（`name` 已是父内的路径段）。
2. **新增 `VdfsItem { path, #[serde(flatten)] node }`**：`vdfs/list` / `vdfs/tree` 的每一项都是它。**线格式与「带 `path` 的节点」逐字节相同**，故不改变任何既有消费者读到的 JSON。
3. **`path` 的回填只有一处**：provider 不填时，分发层按 `<父地址>/<name>` 推导；只有「地址不是那个形状」时由拥有者自己填（设置页条目是唯一实例）。
4. **`VdfsContent` 去掉 `path`**——内容总是「请求的那个节点」的内容，地址在请求里已经有了。
5. **`VdfsWriteResponse.path` → `name: Option<String>`**：**仅匿名写有**，值是 `VdfsNode::name` 口径的路径段、不是地址——地址由调用方拿它和自己请求的那个目录拼（它本来就知道请求的是哪个目录）。

**理由**：**一条推导只写一处**（provider 不需要知道自己在树里的位置）；**回执只给调用方不知道的那一个**（具名写回传地址是冗余；匿名写唯一的新信息是 provider 生成的名字）；**线格式不变** ⇒ 这次拆分对任何既有消费者（含 CLI 与 e2e）都是**透明的**。
