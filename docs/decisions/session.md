## ADR-015: 前端显示由**节点状态**驱动，不由事件顺序驱动

**状态**：已接受

**背景**：会话实时显示原基于**事件流**（`Status{busy|idle}` / `Abort` / `Error` / `Connected`，前端 `switch (event.type)` 逐类处理，另靠 `last_failed`、`sessionErrors` 等平行状态拼补）。代价是**正确性依赖到达顺序**，而顺序不是免费保证的——`eventBus.ts` 里那段 `replayBuffer`（切会话防乱序缓冲）就是为修顺序而存在的机制。**一段只为修顺序而存在的机制，说明模型本身选错了**：把「现在是什么」表达成「刚刚发生了什么」的增量序列。

**决策**：**把运行态从事件里拿出来，变成节点的属性**，前端按地址消费节点状态。
- 会话节点 `<根>/session/<sid>` 承载 `status`（`working` / `active` / `failed`）+ `attributes.outcome`（`completed` / `aborted` / `failed`）+ `attributes.error`；
- 消息节点承载 `status`（`pending` / `streaming` / `waiting_user_action` / `completed` / `failed`）；
- 状态类变更**必带全量节点视图**，消费端**零回读**；
- 前端只有按地址分派，**没有 `switch (event.type)`**；等待审批、活动文字、可重试性等都由节点表**派生**（纯函数）。

**理由**：状态**幂等、可交换、丢一次不影响正确性**，事件是增量、有顺序、丢了没有第二次机会——一次变更携带全量视图后，「谁先到」只影响收敛**速度**；顺序敏感类补丁随之消失；判据只剩一处（「上一轮失败了吗」= `status == 'failed'`）；修掉 `completed` 与「未标注」都映射成 `active` 的有损映射。

**后果与不变量**：
- **任何送达前端的会话状态变化都必须经 `emit_session_state`**（运行态的唯一出口），且 `updated` 必带节点视图。漏发即 UI 永久停在旧状态且无人纠正。消费者侧**不做静默回读兜底**（那会把它掩盖成「看起来能用」），只记 warn，靠下一次 `list` 快照收敛。
- **词汇不合并**：`streaming`（消息）与 `working`（会话）保持两个词——合并会连带改 `status-*` CSS 类名与 `isWorkingStatus()`，而**漏改 CSS 类名不报错、不失败，只会让流式动画静默消失**。
- `kind = "session"` 频道已整体废除，会话实时面收敛到 VDFS 变更频道（ADR-025）；机制细节见 [session/docs/node-state-streaming.md](../../symbio/src/plugins/session/docs/node-state-streaming.md)。

## ADR-018: 压缩失败**不得裁剪历史**——失败必须是可见、可重试、可持久化的状态

**状态**：已接受

**背景**：上下文压缩（L2 语义压缩）失败时，历史上有一条「本地机械兜底」：若预判 LLM 摘要请求必然超限，就按 token 预算机械砍掉早期消息、插入截断说明头，然后**回报成功**。而这条路径的触发时机恰恰是「压缩反复失败的终点」⇒ **压缩失败的最终代价由历史买单**，用户看到的却是「已压缩上下文」的成功态节点——没有原因、没有重试入口、历史凭空变短、后续内容与截断前失联。

**决策**：
1. **压缩失败一律不改动历史**。四个出口（LLM 失败 / 快照校验失败 / 输入超限 / 用户中止）全部还原为调用前的消息列表，一条不丢。
2. **失败是可见的**：压缩节点落 `Failed` + `meta.failure_kind` + 可读原因（`llm_error` / `invalid_snapshot` / `input_over_limit`），落库持久化。
3. **失败是可重试的**：`ResumeAction::RetryCompaction` 给失败节点一个「重试」入口。
4. **删除机械裁剪**（`emergency_tail_compression`）。预判仍保留——但只保留「跳过注定失败的巨型请求」这一收益，不再顺势裁历史。

**理由**：历史是用户的资产，不是压缩机制的资源；「这次压缩放不下」不构成「可以静默丢历史」的授权（截断破坏性且不可逆，失败可逆）；静默降级把故障伪装成成功，与 ADR-015 的精神一致——状态必须如实。重试**不按 `failure_kind` 分档**：`input_over_limit` 当场重试必然再失败，但那会掐掉唯一的出路——用户换一个上下文更大的模型后同一次压缩就能成功。

**后果**：会话可能停在错误上（带原因 + 重试入口，而不是带着残缺历史继续跑）——这是**刻意的取舍**，可见的失败优于静默的数据损失；用户出路三条（换更大上下文模型后重试、手动精简、另起会话），都是显式动作；压缩节点的失败形态必须与成功形态**视觉可分**。

## ADR-024: 会话选项并入**详情方言**——「选项行」是配置表单的字段，不是独立协议

**状态**：已接受

**背景**：「新增一类资源、前端零改动」靠一条统一链路维持：后端在列表 / 详情节点上挂 `schema`（`DetailDefinition`），前端用唯一渲染器 `DetailForm` 解释它。**会话是唯一例外**：它自带一套 `OptionNode` 协议（专用端点 `session/options/list`、贡献方在节点上算好 `value` / `value_label`、写回走专用端点 `session/update`、跨插件汇聚另走 `OptionVisitor`，前端另有一套 `useSessionOptions` + `ChatOptionBar` + `OptionFormDialog` + `services/options.ts` + `schemas/options.ts`）。两套机制描述的是**同一件事**：一组「有当前值、可改、改完要落库」的字段。

**决策**：
1. **选项 = 会话配置表单的字段**；选项栏 = `DetailDefinition` 的**第二种渲染形态**（与 `DetailForm` / `DetailShell` 并列），不是新协议。
2. **定义随节点下发**：已落盘会话挂 `node.schema`，草稿态挂 `new_type.schema`。不再有「取定义」的专用端点。
3. **当前值随节点**：`node.attributes.metadata`。
4. **写回走 `vdfs/write(<根>/session/<id>, {"metadata": …})`**——`VdfsProvider::write` 的覆盖分支本就是 metadata 浅合并，不需要第二条写入路径。
5. 给共享方言补四件事，**都通用、非选项专用**：`DetailField.icon` / `disabled_when` / `pick`（原生取值闭集）/ `form` + `widget="form"`（结构化子表单）。
6. **旧机制整体下线**（`OPTIONS_LIST` / `SESSION_STATE_ENDPOINT` / `OPTION_TYPES` / `OPTION_PICKS` / `options/list` 与 `session/update` 路由）。`OptionVisitor` + `traverse` **保留**（汇聚机制不变），只把产物从 `OptionNode` 换成 `(order, DetailField)`。

**理由**：会话选项与其它资源的「新建表单」语义上**没有区别**（字段 + 默认值 + 候选 + 条件可用性），合成一条链路后前端**零业务字段名、零业务枚举**——独立协议让每个字段名都要在前后端各写一遍，而没有任何守卫能发现这种漂移（ADR-019 记的正是这类手工镜像的代价）。四件方言补充都是**通用能力**，不是为选项开的口子。**`session/update` 的退役不需要扩协议**：`VdfsProvider::write` 的文档**早已**写明「**具名节点** + 不存在 ⇒ 就地创建，id 来自地址；只有**目录自身**才由 provider 生成名字」，会话 provider 是**唯一**违反者——**给通用机制加字段之前，先看特例是不是在违反通用机制已有的成文规则**。

**后果与代价（不粉饰）**：级联选项从「任意深度」收窄为**一层**；`invoke` 型命令选项改由 `DetailAction` 承担；懒加载取消（定义随节点全量下发，量级无虞，将来字段数上量时这条要重新评估）；`order` 号段留在后端收集层、不下发。

**踩坑**：`VdfsNode.attributes` 是 `#[serde(flatten)]` 的，**线上**（`vdfs/list` / `vdfs/stat` JSON、前端 `services/session.ts`）看到的是**摊平**后的节点——`metadata` 是**顶层键**，没有 `attributes` 这一层；Rust 侧才读 `attributes`。

现行规范见 [session/docs/session-options.md](../../symbio/src/plugins/session/docs/session-options.md)。

## ADR-025: 顺序是**节点属性**；`delta` 是 `updated` 的**传输形态**

**状态**：已接受

**背景**：VDFS 是**虚拟动态文件系统**——会话转写在这个语境里本来就有唯一自然形态：`<根>/session/<id>/message` 是一个文件夹、`<id>/message/<mid>` 是一个文件（一条消息）、流式输出即该文件的内容在增长。这套形态**数据面早已落地**（`transcript_of` 返回「落库转写 ∪ 本轮在途缓冲」；`read` 拿到的是已含增量的正文；`list` 按 `ChatMessage.seq` 排序）。**但通知面走偏了两次**：先把消息挂到 VDFS 变更频道上（带 `appended` / `delta` / `truncated` / `renamed` / `to` / `node` / `content` 一堆可选载荷），后拆掉改走独立的 `session/stream` 转写流，再往后把运行态也并进转写流。两次拆解的理由（**频道没有流内序号**、**载荷全量 / 增量混合**）是当时的正确判断，但被记成了**能力性结论**：「`appended` 需要的是**一条有序流**，而不是在资源变更频道上挂一个 `delta` 字段」。**这句话是错的**——错的不是观察，是**归因**：它把**数据的属性**（顺序）误当成了**传输的属性**。

**决策**：
1. **顺序是节点属性，不是投递属性**。`ChatMessage.seq` = 消息在该文件夹里的位置，由写入者分配、随节点下发；消费端按它排序。于是**到达顺序与显示顺序无关**：后生成的先到、两个并行工具的变更混着到，都正确显示——每个变更都指向一个明确的 `path`，节点自带位置。
2. **「追加」不是新取值，是载荷上的 `delta` 字段**：`delta` 有 ⇒ **尾部追加、零回读**；载荷无 ⇒ 节点变了、**回读**（`stat` / `read`）收敛。**取值集合上没有任何「操作枚举」**——消费端不需要猜「这次是追加还是替换」，字段的有无就是答案。任何「内容会增长」的 provider 都能用它（转写、日志、流水），**机制里没有任何会话特化**。
3. **不加快照载荷**（`node` / `content`）。理由是**独立于顺序**的：快照携带的是它**生成那一刻**的状态，迟应用会把运行态回退——这是**陈旧写入**问题，不是乱序问题；而回读（`stat` / `read`）永远最新且**幂等**，是正解。
4. **丢失靠幂等重读兜底，不靠序号**：`event_bus::try_publish` 满通道 → 保留订阅 + 补送 resync 标记；会话终态 → 宽限定时器 → 复查本地非终态节点 → 整份回读；订阅即登记（登记先于加载，避免启动窗口漏变更）。
5. **`session/stream` 与 `transcript_stream` 退役**：它存在的三条理由（顺序、背压、免回读）现在都不成立；`event_bus` 的 `kind = "vdfs"` 成为**唯一实时通道**，`symbio_core` 里不再有第二个投递设施——新域（MCP 工具流、模型流）**不需要再造一个**。
6. **信封收敛为 `{path, data?}`**：`data` 是该路径的业务载荷（消息节点上是 `ChatMessage`，会话节点上是 `VdfsNode`），**缺失 = 无载荷**（回读收敛）。**操作枚举（`created` / `updated` / `deleted`）整个退役**——它们描述的「资源层面发生了什么」与载荷描述的「业务数据变成了什么」是同一件事的两种说法，而消费端真正消费的只有后者。
7. **`path` 恒为被变更节点自身的地址**：集合项的地址形状统一为 `<sid>/<集合段>/<项 id>`，身份就是末段。会话是**容器**，其下是若干**并列的集合**（消息 / 子会话 / 记忆 / 工作目录……），所以**机制不认识任何一类集合**——新增一类集合只需在 `internal_dirs` 里声明一个段，信封与消费端都不动。
8. **删除的表达**：资源域 = 「载荷缺失 + 回读 `NotFound`」（删掉的节点本就没有视图可带）；消息域 = `ChatMessage.status = removed`（消息词汇本就有它）。

**理由**：
- **热路径用载荷、冷路径回读**——高频帧（逐 token）全部带增量，只有低频帧（创建 / 终态 / 压缩）才回读。**载荷该不该有，取决于它落在热路径还是冷路径上。**
- **`event_bus` 的背压纠正已上移**，所以「一条机制」的成本已从两处降到一处。
- **顺序从来不是投递层的职责**：两个并行工具的变更混着到、后生成的先到，显示都正确。

**后果与不变量**：
- **一个变更取值（或载荷字段）必须有生产性生产者**（这是批次 G 删除载荷时立的判据）。词汇表旁**必须同时留下生产者清单与本节链接**——否则下一个改动者会按「零生产者」再删一次。
- `delta` 回到它本来的位置——**`ChatMessage.delta` 字段本身**，不再是信封上的副本；门面不再换信封（与 `VdfsChange` 形状逐字相同的影子类型已合并删除）。
- 运行态随载荷带全量节点视图（与 `stat` 同一构造点），消费端零回读就地收敛；资源信号保持无载荷，消费端防抖重拉。

现行规范见 [design/vdfs.md](../design/vdfs.md) §9「变更通知」。

## ADR-026: 子智能体的完整会话**在 VDFS 空间内自驱动**——用户消息入 `inbox` 集合，进程内唤醒消费，不走 `route`

**状态**：已接受

**背景**：`agent_run` 是「在父会话下派生一次性子会话」的**工具**，产出归档在父会话的 `subsession` 集合——钉死这一点是为了不把它和「子智能体」混为一谈。「子智能体」是一等**空间**：`agent/<id>/` 已装配为**含自身 `session` 插件实例的完整子树**，其存储目录就是自己的插件目录——**缺的不是空间，而是在没有调用方连接时驱动它跑一轮的入口**。而 `chat/send` 是请求-响应式的，它把「接收消息」与「跑一轮」绑在一起，并依赖 `route` 的调用方连接来观测输出。

**决策**：
1. 用户消息**只是 VDFS 写入**：向 `<sid>/inbox/` 写一条新条目即入队，条目本身就是一条待消费的 `user` 消息。
2. **运行由空间自身消费队列**：写入后在同一进程内唤醒该会话的收件箱消费者，消费者逐条取出并调用既有的一轮执行路径。
3. **机制统一到所有会话**，不特设子智能体分支——顶层与子智能体共用同一套 `inbox` 语义，子智能体只是「恰好没有人替它调 `chat/send`」的那种会话。
4. **FIFO、忙则排队**：会话正在跑时新消息只入队；消费者严格「跑完一轮再取下一条」，不并发、不抢占、不合并。

**理由**：VDFS 已有空间与挂载遍历（`agent/<id>/session/<sid>` 本就可达），把「发消息」表达为对空间的一次写入，就不必为子智能体复制一套 route 入口；会话内部集合**按设计可扩展**（`inbox` 正是「再加一类集合」，与 ADR-025 的集合模型同构）；「写即入队、忙则排队」用**一条队列**同时表达投递与背压，投递方无需等待，天然适配无连接的脱机空间；不把 `chat/send` 的请求-响应语义套到子智能体上，避免「需要一个此刻并不存在的调用方」的自相矛盾。

**后果与不变量**：
- 消费者是**每插件实例一个**、在构造点起，**不是在写入点按会话起**——否则「第一次写入由谁消费」会取决于装配顺序，不可测。
- 忙碌不再由单次调用隐式携带：**一批**待办与「正在跑」各由队列和运行态表达。
- 取消一条**已排队**消息 = 删除对应 `inbox` 条目；**正在处理**（已出队）的那条已是转写里的消息，取消走 `chat/abort`——两种取消作用在不同对象上，因此是两个动作。
- 取向与从前相反：新消息**排队**而不是抢占当前轮次。换来的是「没有调用方的空间也能被可靠驱动」这一条最硬的保证。

## ADR-031: 会话的**输入**是地址上的写入 / 动作——路由不承担输入，`chat/send` 与 `chat/abort` 退役

**状态**：已接受（**含未完成项**）

**背景**：子智能体空间里发起会话后「发消息跑在**父智能体**的空间里」、同一会话的「停止」点了没反应。三条根因：**`chat/send` / `chat/abort` 是全局路由**，由根 composite 分发 ⇒ 落点恒为**根** `SessionPlugin` 实例，而子智能体空间有**自己的**实例却没有路由入口（于是消息由根实例消费、人格 / 工具 / 存储全是父智能体的；`chat/abort` 更安静：根实例 `get_or_create` 造出一个**空状态**，`handle_abort` 读到空信号 ⇒ 什么都不做，还留下一个永生幽灵状态）；**前端会话层按 id 寻址，且只认一个全局挂载目录**（前缀匹配收不到子空间的变更地址；新建会话同样恒写到根空间）；**输入面没有「哪个空间」这一维**（信封里只有一个裸 `session_id`）。

**决策**：
1. **会话的输入统一表达为「对这个会话地址的一次写入 / 动作」**，路由不再承担输入：

   | 意图 | 地址操作 |
   |---|---|
   | 发一条用户消息 | `write(<A>/inbox/<iid>)` |
   | 取消一条排队消息 | `delete(<A>/inbox/<iid>)` |
   | 清空排队 | `action(<A>/inbox, "clear")` |
   | 停止正在跑的那一轮 | `action(<A>, "abort")` |
   | 重试 / 审批 / 补充 / 回答 | `action(<A>/message/<mid>, "<ResumeAction 线上词形>")` |

   三条落点的分界沿用 ADR-026：**会话节点** = 正在跑的这一轮；**inbox 条目** = 还没成为消息的消息；**message 条目** = 已经是转写里的一条消息。「停止」在 UI 上是**两个动作**（`abort` + `clear`），不给 `abort` 加 `clear_inbox` 开关——机制动词保持单一职责，组合发生在调用方。
2. **前端会话的身份从「id」升级为「地址」**（挂载目录 + id）。挂载目录**不止一份**，因此地址方案、订阅前缀、清单读取全部按挂载目录分别登记。
3. **用户消息的显示恒由后端通知驱动**：任何发送方（前端 / CLI / telegram / 心跳 / 子智能体）的消息都走同一条路进前端。

**理由**：**地址是子空间唯一的可达方式**——「用路由送进子空间」在机制上不可能成立，不是实现没写对；**同一个事实只有一个来源**（把它拆成「id（协议里）+ 空间（前端某处的全局变量）」，就是两个来源必然漂移）；**控制动作必须是可查询的，而不是会被创建出来的**（`abort` 走 `ActiveSessionManager::get` 而非 `get_or_create`，否则一次「停一个没在跑的会话」会在表里留下永不释放的空状态）；**路由版与动作版共用同一份实现**（`abort_turn`），否则两个入口必然分叉——而这次 bug 正是「路由能到、地址到不了」的分叉。

**后果与明确接受的代价**：
- **store 的键仍是会话 id**（不是地址）：id 由后端生成为短 guid、跨空间全局唯一，因此「同一个会话」只有一份状态，「它在哪个空间」作为寻址信息单独记。
- 「停止」变成两次 IPC（低频操作，换机制动词的单一职责）。
- `<A>/inbox` 的写入正文是一条 `ChatMessage`，**带不了本次运行的选项**（`mode` / `risk_level` / `include_history` / `provider_id`），由会话 metadata 回退。
- 前端会话键从 id 变地址是最大的一块改动（两个 sync + 一个 store + 三个组件 + 一个 composable）。

**未完成（有意留下，需要自己的 ADR）**：`chat/send` / `chat/abort` 两条路由**保留**。前端已无调用方；后端剩 CLI / telegram / `agent_run` / 心跳四处，其中 `agent_run` 必须携带 `provider_id`（子会话 metadata 里没有它），而写入面表达不了运行选项。**「地址写入要不要承载运行选项」是一次协议决定**，不顺手发明。完整分析见 [design/session-input-addressing.md](../design/session-input-addressing.md) §5.6。

## ADR-039: `session` 按域重组——一域一目录，编排层与领域层分离

**状态**：已接受（**取代 ADR-017**——其三条触发条件全部命中）

**背景**：ADR-017 把 `session` 的规模债判为「带触发条件的延后」，并写明命中触发条件时应由新 ADR 取代、而非直接删除。现三条同时成立：①「改 A 必须同时改 B」的跨文件连锁确已出现，根因是 `session` 内部职责混杂；②单次改动的 diff 大到无法被人完整审阅——若干文件同时装着几类互不相干的职责；③各部分职责的归属与作用域能明确说清，下放不再需要「先切再看」。

**决策**：`session` 按**域**重组，判据五条：①**一域一目录（或一文件）**——一个职责域 = 一个 `X/` 目录（`mod.rs` + 子模块）或一个 `X.rs`，不允许多类互不相干的职责同居一文件；②**编排层与领域层分离**——编排层只做装配、调度与收口，领域层内聚自己的机制，依赖单向（编排 → 领域）；③**副作用出口唯一**——领域的落库 / 广播 / 事件经该域单一出口；④**域内分层，测试恒外置**——一个实现文件对应一个测试文件，两种合法形态由 `scripts/test-layout-audit.mjs` 判定；⑤**跨域共享面走门面**——`pub` + 域根 `pub use` 导出，`pub(super)` 只表达域内部分工。判据逐条表述与「它挡住什么」见 `symbio/src/plugins/session/docs/module-layout.md` §0；域清单与逐文件落点同见，文件数与行数以 [CURRENT.md](../CURRENT.md) 为准，本条不复述。

**理由**：ADR-017 反对的是**按现状切几刀**，不是拆分本身；五条判据按职责边界而非行数给切法——每个域都要能一句话回答「它是什么、它不做什么」，答不出就不成域。拆分必须**可证伪**：全程纯搬移、每步零行为变更，用代码行多重集逐条归因、用例数不减、门禁全绿自证「没有丢东西」；测试外置与门面导出是这套自证的**前提**而非结果——`#[path]` / 同级 `tests.rs` 让测试随实现文件走而模块路径不变，门面让跨域调用点在改名时只改一处。编排与领域分开后，「机制变了」与「接线变了」成为两类 diff：前者落在领域内审阅，后者落在编排层——这正是触发条件 ② 所要求的可审阅性。

**被否决的方案**：**按行数阈值机械切分**（行数不表达职责，切出来仍是按现状切几刀，维持 ADR-017 对这条的否决）；**只外置测试、不动生产划分**（能解决混放，解决不了跨文件连锁——连锁恰恰都长在生产代码的职责缝上）；**一次性整体重组**（diff 无法审阅，且把搬移风险与行为风险混在一次变更里；改为分阶段纯搬移，每阶段独立验收提交）。

**后果与不变量**：新增职责先归域，无域可归的进编排层或最贴近的既有域，不新建「杂物」文件。与 [ADR-023](./core.md#adr-023-symbio_core-的准入规则--依赖方数量不是够不够底层)（core 准入 = 依赖方数量）互补：本条管 **session 域内**的落位，ADR-023 管 **core 与插件之间**的落位——同源的判据（职责与依赖方），不同的作用面。既有单一实现约束不因重组放松（压缩内核、回合收口、消费循环等的唯一落点），清单见 `symbio/src/plugins/session/docs/core-loop.md`。判据约束**新代码与被触碰代码的落位**，不冻结现状、不触发顺手搬迁；域边界将来若不合适，改的是归属，不是机制。

## ADR-041: 会话的响应性由编排层调度 + 无副作用对话服务承担

**决策**：
1. 新增 `chat` 插件，**无工具、无副作用、无状态**：`chat/reply` 输入
   「用户输入 + 已投影上下文 + 运行现状快照 + intent」，输出 `Answered` / `Escalate` / `Report`。
2. `session` 保留唯一编排者与唯一转写写入者；它在三个调用点（轮首 triage / 轮边界 triage /
   进度 tick）调 chat，并写回返回文本。
3. **收件箱是输入缓冲**：抽干整队、合并成一条用户消息、在轮边界折进当前轮。
4. **异常一律 `Escalate`**（fail-safe 方向是多干一次活）。
5. **会话只有一份存储、两条线**：对话线（用户 ↔ 助手）与工作线（worker ↔ 任务）是同一份
   存储的两个**读法**，各有自己的窗口；不新增存储，也不为 chat 另建上下文收集通道——
   "我知道什么"走 `register_system_prompt`（与 worker 同一通道），
   "现在在发生什么 / 我们聊过什么"由 session 在调用那一刻投影进 `ctx`。
6. **分界规则是单点纯函数**（`conversation_view`）：三处共用（chat 上下文 / 前端对话面板 /
   工作线请求视图）；chat 的请求视图里**不得出现** `tool_call` / `role = tool` / Turn / 推理节点，
   由投影保证而非提示词保证。
7. **两条线在呈现上严格分开**：工具 / 推理节点不进对话面板。今天把工具卡片插进对话列表
   是既有混乱的来源，本次一并改。

**理由**：三条目标（直接回答 / 补充整体整合 / 中途汇报）都指向"何时说人话"没有被显式调度，
而不是缺少决策者；把 chat 设计成无副作用服务，则只需**一条单向边**，
写入者、`seq` 分配、终态收敛的单点保证全部不动。
两条线若各存一份，**一条助手消息会被劈成两半**（正文进对话流、工具调用进工作流），
请求视图必须再拼回一条——混乱没有消失，只是从呈现层搬到数据层，并新增 join 的正确性负担。

**后果与不变量**：见 §8.1 十五条。关闭 chat 后行为与改造前逐字一致。

## ADR-047: 委派者三项真源——判定回 `reason`、能力走注入、进展读磁盘事实

**状态**：已接受

**背景**：目标形态是**主会话不持有工具**，于是主会话缺三样外部事实——worker 何时启动、自己有哪些能力、进展如何。[ADR-046](./core.md#adr-046-事实能力进-symbio_core不以可选插件承载必须有值的机制) 已定 `feat/v2-bridge-b1-fact-envelope` 的处置边界：其**插件式结构**不在移植清单上，其中的**体验价值**（含委派者三项真源）另按 `docs/plan/` 路径评估，且**改行为面的先写 ADR**。本条即那个「先写 ADR」的产物。

**决策**：三问的答案**都必须是数据而不是机制**，各自唯一真源：

1. **Q1 · worker 启动条件 = 三层判据的合取纯函数**——显式前缀 `/work `（带尾空格）、关键词（子串，出厂空集）、主题长度阈值（出厂 0），**必须回 `reason`**。形态照搬 `classify_by_rule`：纯函数、无 I/O、无状态、无 async、命中回理由码、未命中回 `None`，全部行为可被测试穷举。
2. **Q2 · 能力可见性 = `list_capability()` 折出的按分类分组的名字目录（digest），不走工具**。注入点是 `session::chat_loop::inputs::prepare_turn_inputs`，且**必须在能力收集之后**才动笔。
3. **Q3 · 进展 = 从 worker 会话的磁盘事实推**——子会话按 `metadata.parent_session_id` 归档在父会话的 `sessions/` 子目录下，**必须按 `parent` 过滤**。

**理由**：三问若答以**机制**而非数据，主会话就得重新持有工具——而「不持有工具」正是这个目标形态的前提。
- Q1 若「总是先开一个 worker 再决定」，**每条寒暄都会产生一个后台会话**；若把判定交给模型，则**判定权落在不可审计的一侧**——同一句话两次判定可能不同，也没有可回放的理由。
- Q2 若走工具，模型得先**知道**有这么个工具才会去调它：**能力可见性不能以调用能力为前提**。注入点之所以不是插件侧，是收集本身决定的：收集是**广播**——容器 `composite::traverse` 逐子插件转发，而它取的实例表快照（`PluginRegistry::snapshot`）直接遍历 `HashMap` 且**不排序**。于是在遍历**尚未结束**的任一子插件里取能力集合，必然漏掉还没被访问到的兄弟；顺序又每次不同，**漏了哪几项次次不同**——既静默（不报错、不缺项告警）又难复现。
- Q3 若用进程内注册表，服务重启后注册表为空而磁盘事实仍在 ⇒ 两处对不上，**注册表就成了第二份真相**；这与 ADR-026 定的形态一致——子会话本来就在 VDFS 空间内自驱动，读侧应当读那一处。

**被否决的方案**：
- **总开一个 worker 再决定**（寒暄也开后台会话）；**模型自判**（不可审计、不可回放）。—— Q1 的两个反面。
- **能力经工具暴露 / 在插件 traverse 期算目录**。—— 见 Q2 理由。
- **进程内 worker 注册表**。—— 重启后与磁盘不一致 = 第二份真相。
- **照搬成新插件**。—— 那正是 ADR-046 否掉的形态；移植落点与本仓现状见 [04 §3.2](../plan/04-工程落地.md)。

**后果与不变量**：
- **注入点在能力收集之后**：owner 是 `prepare_turn_inputs`，新段必须并进它既有的请求视图次序——现状为**记忆段 `index 0` / 就绪段 `index 1`**，该次序由 `build_request_view` 单点保证（`prepare_turn_inputs` 的第 6 步），且有测试钉住「记忆仍在 0、就绪段在其后」。
- **Q1 不回 `reason` 就等于没判**：没有理由码的判定不可审计，也不可被测试穷举。
- **Q3 不按 `parent` 过滤比没有进展更糟**：串台会把别人的进展报成本会话的进展。
- 三者都是**数据**：不新增存储、不新增注册表、不新增跨插件调用。落地分两步（B1 输入面 / B2 前端过程段收起），见 [04 §3.2](../plan/04-工程落地.md)。

## ADR-048: 出厂档位改 `full`——v2 链路是出厂路径，`bridge` 退役

**状态**：**部分接受 · 已落地 1/3 步**（2026-10-09 补记）

**决策**：`V2Mode` 的 `#[default]` 由 `Bridge` 改为 `Full`，并**退役 `bridge` 档**——
转写路径（`record` / `record_to_wal` / `authorize_close` / `first_user_utterance` /
`last_assistant_text` / `V2Closure`）与只服务于「跳过它」的 `TurnState::v2_executed`
一并删除；`v2_bridge.rs` 收缩为只剩派生事实写入两个函数，改名 `v2_facts.rs`。
`full` 档的覆盖面 = **全部轮次**（无工具轮 / 工具轮 / 审批与问答恢复，恢复续写同一
`turn`、用户格不重开）——`docs/plan/10` 批 1 / 2a / 2b 全部落地。

**⚠️ 补记（2026-10-09）：本条的第一版论证有三条不成立，已作废**

第一版把「`full` 的覆盖面 = 全部轮次」当作既成事实写进理由 1，而**它当时只有约 10% 的
e2e 覆盖支撑**（42 个用例里只有 4 个跑 `full`，其余全在 `bridge` 上）。把默认档位
翻过去之后，e2e 立刻照出**三个真实缺口**——它们在 HEAD 就存在，门禁却是绿的，因为
**门禁从来没在那条路上跑过**。三条见下文「被证伪的覆盖面声明」。

这不是「测试没写好」，是**验证设计的缺失**：本仓对代码层纪律的守卫很强
（`panic-audit` / `dead-code` / 棘轮 / `doc-link`），而对「两条执行路径的产品行为
是否等价」几乎没有守卫。三条缺口全是**静默**的——不报错、不告警、断言全绿（事实照样
入格、`session/stats` 照样有数），**用户唯一的察觉方式只能是发现 agent 变差了**。

**理由**：

1. **`full` 是唯一能兑现 v2 承诺的档位。** v2 的立身之本是「prompt 从事实网格投影
   出来，而不是另存一份对话副本」——这永久消灭了「转写与对话漂移」那一整类 bug。
   留在 `bridge` 上等于把 v2 钉在旁路位置：**它永远不会被真实负载压到**，缺口也就
   永远不会被照出来（上面那三条正是这么活下来的）。`bridge` 档自 [ADR-045](./core.md#adr-045-v2-事实桥生产流量经转写进事实源不等整体切换)
   起就自述「整体切换完成后退役」，现在退役它。
2. **`bridge` 是 [ADR-045](./core.md#adr-045-v2-事实桥生产流量经转写进事实源不等整体切换) 的过渡设施。** 该条自述「未来整体切换完成后，本桥退役为兼容层再移除」。把它留作出厂默认 = **过渡态永久化**，而它要退役的前提已经成立。
3. **事实源是同一份，读侧零改动。** v2 原生入格写的 `<会话目录>/v2-events.wal` 与桥写的是同一个文件、同一常量（`paths.rs` 的 `V2_WAL_FILE` 单源），`session/stats` 一行不改。桥在 `chat_loop.rs` 的 `!turn.v2_executed` 处已被正确跳过 ⇒ **同一轮不存在两份记账**（那是假象，不是冗余）。
4. **`full` 档的难处已经补齐。** 流式 UI 帧通道原先无界（`on_delta` 是同步回调、传不回背压），已换成有界队列：满时**合并增量**而非丢帧——`Finalize` 丢一次正文节点永远转在「流式中」，`Snapshot` 丢一次那轮正文整段消失，所以丢帧不是可选项。

**被证伪的覆盖面声明（2026-10-09 补记）——三条，同一个根因**

根因：**事实网格不是「模型看到的」的完整记录**。v2 只把**轮次级**事实搬进了网格，
而 v1 请求路径上还有一批东西只住在「消息列表 / 请求视图」那条路上。凡走那条路的，
`full` 下模型看不见——而这三条**全部静默**：

| # | 缺口 | 内容住在哪 | `full` 下模型看见吗 | 状态 |
|---|---|---|---|---|
| 1 | 记忆召回 / 就绪任务集 / 委派者真源三段 | `build_request_view`（请求级，不落库） | **否** | **已修**（见下「补上缺口 1」） |
| 2 | `context_messages = 0` 的语义 | `window_by_turn`（读侧窗口） | **历史被清空** | **已修**（`keep == 0` = 不截断） |
| 3 | 轮边界折进的补充 | `context.messages`（消息列表） | **否** | **待修**（下一步） |

- **缺口 1 机制**：`full` 的 prompt 来自 `Reasoner::render_prompt` 对事件快照的渲染，
  经 `ProviderLlmAdapter::generate_turn` 作为**一条** user 消息发出；而三段在 v1 里是
  `build_request_view` 插进 `request_view` 的**独立消息**。`V2Turn` 没有承接它们的
  字段 ⇒ 不显式带进来就消失。**补法**：`TurnInput::prefix`（请求级前缀，排基线
  **之前**、不进「就地累积」、每轮重算不跨轮累积）+ `chat_loop::request_view_prefix`
  按 `meta.kind` 取三段、按语义优先级（记忆 → 就绪 → 委派者）拼。判据
  `request_prefix_precedes_the_baseline_and_is_not_accumulated` 带反向自检。
- **缺口 2 机制**：`window_by_turn` 的 `keep == 0` 分支返回**空切片**，而
  `SessionConfig::context_messages` 的 `0` 一贯是「不按轮次截断」——同一份配置在两条
  路径上**含义相反**。**补法**：`keep == 0` = 全量；判据
  `zero_window_means_no_truncation_not_empty_history` 带反向自检与 `Some(1)` 对照
  （证明窗口本身仍在裁）。
- **缺口 3 机制**：`chat_loop.rs` 把抽干的补充 `push` 进 `context.messages`，v1 靠
  `request_view` 把它发给模型；而 `TurnInput.text` 在**轮首**就定死，补充在轮中途
  到达时网格里那条 `user.message` 记的还是原话 ⇒ 补充**从未成为事件** ⇒ 投影里没有。

**下一步（缺口 3 的修法，已定方向）**

新增事件 kind `turn.supplemented`（`Entity::Turn`，载荷 `{ text, count }`），由
transcript 投影渲染成一行用户发言。**不改写原 `user.message`**——append-only，且 N3
的判据是「每轮一条 `user.message`」，改写它就是让已落的事实可变，那条线一破，整套
「靠构造成立」的不变量都要重审。新增 kind 不碰任何既有判据：同一轮本来就有
`artifact.added` / `commitment.*` / `task.*` 多个事件。

⚠️ **不做**：把补充塞进运行器的 `exchange`（就地累积）。那样模型看得见，但它**永久
丢失**——`session/stats` 与 transcript 都没有，与 ADR-044「实测与判据同源」相反。
用户补充是**用户确实说了这句话**，它是事实，不是请求级的临时物。

**被否决的方案**：

- **给快路另找一个不依赖 `full` 档的落点**（13 号 P3 登记给出的另一半）：否决。快路要跳过的**正是「v2 运行器里那一次模型调用」**；把它挂到 v1 链路上等于**新写第二条执行链**，而 `v2_exec` 的模块文档明确划界「它不是『又一条执行链』」。为一个开关的可达性去造第二条链，代价与收益不成比例。
- **同时把 `skill_fast_path` / `skill_compile_enabled` 也改默认为 `true`**：否决——**这是第二个、独立的**行为改变（命中时以技能正文收束、**一次模型调用都不发生**），且它的 `false` 默认带着成文理由（「不加速」是安全退路口，「只编译不加速」本身是有意义的观察形态）。两处行为改变捆进一批就**没法只回退其中一处**，违反本仓「一批一提交、独立可回退」。若确实要出厂即产反射样本，另立一批。
- **删掉 `bridge` 档**：**接受**（2026-10-09 补记，推翻第一版的否决）。第一版以「回退旋钮有价值」为由保留它——但回退旋钮的前提是「`full` 已经跑过真实负载、缺口已被照出并修完」。事实相反：在 `full` 还没被真实负载压过的情况下，`bridge` 恰恰是**缺口能一直活着的条件**（它们在 HEAD 就存在、门禁全绿，因为门禁跑的是 `bridge`）。过渡态的代价不是「配置项多两个」，是「v2 永远得不到验证」。
- **保留 `bridge` 档、等缺口修完再退役**：否决。这与「删掉 `bridge`」是同一个动作的两种时机，代价相同（v2 继续留在旁路、继续不被压到）。既然要退役就一次退役干净，把缺口在 `full` 上修完。
- **把补充塞进运行器的 `exchange`**：否决。见上「下一步」的 ⚠️。
- **改写原 `user.message` 事件**：否决。append-only + N3 的组合不允许「已落的事实可变」。

**后果与不变量**：

- **影响面**：`v2_mode` 是**实例配置**。显式写过 `v2_mode` 的实例**完全不受影响**（`serde` 读的是已落盘的值）；没写过的取新默认 ⇒ 影响面 = 「未显式配置的实例，从下一次轮次起走 v2 执行链路」。**既有会话不需要任何迁移**——它读的是同一个 key。
- **反射档样本仍为零，且本 ADR 解决不了。** 反射档要**三个开关同时开**：`skill_compile_enabled`（产出已编译技能）→ `skill_fast_path`（`fast_armed`）→ `v2_mode = Full`（`inputs.rs` 的 `matches!`）。出厂三个默认值 `false / false / bridge` **全部关着**，本 ADR 只开第三个。档位由**令牌类型**给出（`RuleOnly ⇒ reflex`，`run_reflex` 只收 `RuleOnly`），所以没有反射令牌就没有 `reflex` 事件，`session/stats` 的 reflex 桶恒零。
- **13 号 P3 原登记的出口判据建立在一个错误前提上**——它假定「翻 `v2_mode` 一处就能解锁反射档」，实际不能。判据随之改为：**出厂档位下 `session/stats` 的兜底率与时延按 tier 分桶有样本**（`deep` 桶有样本、`unspecified` 不静默吞），反射档产样本另立一批。
- **ADR-045 的桥降为兼容层**：只在 `off` / `bridge` 档运行。桥的退役与移除不在本 ADR 范围。
- **不变量**：`V2_WAL_FILE` 仍单源；同轮不两份记账；`declared_tier` 归属判据不变（`full` 档未命中快路时仍是 `deep`）；流式通道有界（合并而非丢帧）。
- **本仓缺的那类守卫（2026-10-09 补记）**：**「同一负载跑两条执行路径、比对模型实际看到的内容」**。三条缺口全绿的直接原因就是没有它。有的话它们在 HEAD 就红。补上它的时机与形态另议，但**它比再补一个缺口更要紧**——逐个在读取侧打补丁会一直漏（每补一个都得重跑 42 个 e2e 才知道有没有牵出下一个）。
- **「更有效」这件事目前没有证据（2026-10-09 补记）**：`full` 把整个窗口转写渲染成**一条** user 消息，工具结果从 `role=tool` **降级**成 user 消息里的纯文本（`render_tool_exchange`）。本仓**没有任何度量能回答「这样对模型是变好还是变坏」**——没有 prompt 格式的 A/B、没有工具调用成功率的统计。所以「v2 让 agent 更强」目前是**未验证的假设**，不是已兑现的事实。这不构成回退理由（v2 的架构收益是实在的），但意味着**在补上等价性判据与一份 prompt 格式基线之前，不该基于「更有效」去翻任何默认值**。

### 系统性失败的防线：为什么分步顺序要重排（2026-10-09 补记）

**问题的形状**：翻默认档位的过程中，每一步都改 prompt 的**呈现层**，每一步都要全量重跑
42 个 e2e，每一步又照出下一个此前看不见的缺口。三条缺口是这样连着掉出来的。这个循环
本身就是**系统性失败**——不是「再有一个 bug」，是「按这个顺序做下去，永远收敛不了」。

**根因**：本仓有很强的**代码层纪律**守卫（`panic-audit` / `dead-code` / 棘轮 /
`doc-link`），但对「**模型实际看到的东西**」几乎没有守卫。三条缺口全绿的直接原因就是
这个空白：它们都是**静默**的（不报错、不告警、断言全绿），只有 e2e 在换档位的那一瞬间
偶然照到。

**原先的顺序是错的**：把守卫排在最后一步，等于「先改三轮呈现层、每轮靠全量 e2e 肉眼
扫，最后再补自动检测」。那三轮里的每次改动都在**没有护栏**的情况下合入——守卫建成的
那一刻，它本该照出的缺口已经不止现在这三条。

**重排后的原则**：**先建防线，再动呈现层；此后每一步都要让防线保持可预期的颜色。**

**防线的形态不是「两条路径对照」**。`bridge` 已退役，对照法失去对象。正确的形态是
**双向完整性判据**——直接断言「事实网格里该给模型的东西都给了、且 `role` 完好；给了
模型的东西里没有网格之外的（除声明过的请求级三段）」：

| 方向 | 断言 | 能照出 |
|---|---|---|
| 网格 → 模型 | 每条 `user.message` → 一条 `role: user`；每条 `chat.assistant.final` → `role: assistant`；每条 `artifact.added` → `role: tool` 且带 `tool_call_id` | 缺口 3（补充没落格就永远到不了模型） |
| 模型 → 网格 | prompt 里除**声明过的**请求级三段（`meta.kind` 齐全）外，每条消息都能在网格里找到出处 | 「模型看到了事实源没有的东西」= 两条真源 |
| `role` 完好 | `tool` 消息必须带 `tool_call_id`，不得降级进 user 消息 | ADR-048a 的拍平退步 |

**为什么这个形态比「两条路径对照」好**：它**不依赖被退役的路径**、它是**单向可判的**
（网格是唯一真源，判据有唯一一侧）、而且它**在单测层就能跑**（不需要起 CLI、不需要 mock
LLM）——所以它便宜到可以每轮都跑，不会因为「太重」而被跳过。

**实现落点（2026-10-09，已建成）**

`symbio_core/projection/prompt_fidelity.rs`（判据 + `PromptGap` / `PromptReport` +
`verify`）与同名 `.test.rs`（四条反向自检 + 平凡值 + 工具轮重开复核，共 3 条）。
**接在生产路径上**：`TurnRunner::run_with_tools` 组装 prompt 的那一步跑一次 `verify`，
缺口只 `plugin_warn` **不抛错**——prompt 已经发出去了，此时抛错只会把「模型看得不全」
变成「这一轮直接失败」，而看得不全恰恰是静默的。

**判据自身也被本仓的守卫照了三次**（记在这里，因为它正是本条存在的证明）：

1. 写完 clippy 判**死代码**——`pub mod` 也救不了。第一反应是「加根导出绕过」；
2. 根导出招来 **C-003**「占 core 根出口却零消费」——而唯一调用方在 core 内部，
   按 C-002「core 外无深引」的正确做法是**不占根**、走模块路径；
3. 改名对齐 **N-001**（`projection` 域前缀登记表）⇒ `Gap` → `PromptGap`、
   `Report` → `PromptReport`，并在 [symbio_core/README.md 的域表](../../symbio/src/symbio_core/README.md)
   的域表里登记，同时写清它**不是投影而是投影的复核**（不改「纯函数视图」的形态约定）。

三步之后判据既在生产里被调、又不占根出口、命名也在登记表内。**这是被守卫逮住的，
不是自己想清楚的**——所以这条防线对「守卫本身」的适用范围，与对产品代码一样。

**它与三条缺口的关系**：缺口 1、2 已在第 1 步修掉，判据对它们是**回归保护**；缺口 3
**未修**，所以判据建成后会先红一次——那正是它该有的样子（守卫先立、看见红、再修绿）。
**先看见红再修**，与「修完再补一个恒绿的守卫」是两种完全不同的次序。

### 分步推进（2026-10-09 补记）

| 步 | 内容 | 状态 | 防线 |
|---|---|---|---|
| 1 | 退役 `bridge` + 出厂改 `full` + 前缀注入（缺口 1）+ `keep == 0`（缺口 2） | ✅ 代码完成，Rust 绿 | 尚不存在 |
| 2 | **建双向完整性防线**（见上节）：网格 → 模型 / 模型 → 网格 / `role` 完好 | ✅ 已建成并接入生产路径 | 建成时**对缺口 1/2 绿**；缺口 3 在**会话输入侧**不在本判据的范围内（见下注） |
| 3 | **prompt 结构化**（ADR-048a）：投影出消息数组 + adapter 边界不拍平 + `exchange` 退役 | ☐ 未开工 | 须保持第 2 步的红，且红点**只剩缺口 3** |
| 4 | 缺口 3：`turn.supplemented` 事件 + 投影成 `role=user` 消息 + 不变量核对 | ☐ 未开工 | **转绿**（第 1 步以来第一次） |
| 5 | 用防线的数据决定反射档开关是否翻默认；补一份 prompt 形状的基线度量 | ☐ 未开工 | 保持绿 |

⚠️ **防线覆盖不到的一半（据实记录，别当成「它能照出所有缺口」）**：缺口 3 是
「**会话接受了一句用户话，但它从未成为事实**」——那发生在**事实网格的写入侧**，
而本判据的两向都以**已落盘的网格**为基准，所以它**照不出**缺口 3。要照出它需要第三条
判据：「会话接受的每句用户发言都能在网格里找到出处」，落点得在抽干点与 `TurnInput.text`
的取值处（第 4 步一并落）。第 2 步只把**投影层与 prompt 层**纳入了自动检测。

⚠️ **第 2 步与第 3 步的次序不可颠倒**：先立防线再改呈现层。反过来做就是「在没有护栏的
三轮改动之后才建护栏」，而守卫建成时它本该照出的缺口已经不止三条。

⚠️ **第 3 步做完防线仍是红的，这是预期**：那时红点应当**只剩缺口 3**。把它变绿是第 4
步的事。若第 3 步之后红点变多，说明结构化引入了新的丢失路径——那正是要在有护栏时才发现
的东西。
**回退**：`git revert` 本条对应的提交。**`v2_mode` 只剩 `off` / `full` 两档**，
没有「运行时切回 v1」的旋钮——这是刻意的：回退旋钮的价值只在「`full` 已跑过真实负载」
之后才成立，而现在它恰恰是缺口能存活的条件（见被否决的方案第二条）。`off` 档仍在，
它保留的是「v1 执行 + 不落事实网格」，**不是**「v1 执行 + 事实照落」。

### ADR-048a（2026-10-09）：v2 的 prompt 形状必须回到结构化消息

**状态**：已接受 · 未实现（先于 ADR-048 的第 2/3 步落地）

**背景**：ADR-048 把「`full` 让工具结果从 `role=tool` **降级**成 user 消息里的纯文本」
记为「未验证的假设」。**复核后判定：这不是假设，是明确的退步**——本条把它钉成决策。

**决策**：v2 的 prompt **必须是结构化消息数组**，保留 `role`（`user` / `assistant` /
`tool`）与 `tool_call_id`，**不得**把整段对话渲染成一条 user 消息的纯文本。

**理由**：

1. **工具结果的承载方式是协议，不是排版。** `ModelProvider::execute_turn` 的签名就是
   `(system_prompt, messages: &[ChatMessage], tools, root_id, env)`——`role: tool` +
   `tool_call_id` 是**跨栈契约**（模型插件把它序列化成各家协议的 tool 段）。
   v2 在 `ProviderLlmAdapter::generate_turn` 里把渲染结果包成**一条** user 消息
   （`&[message]`，单元素），等于**在适配器边界把结构化输入拍平成纯文本**：
   - 工具结果失去「这是哪个调用的结果」的机器可读关联（只剩散文里的 `工具结果(名)`）；
   - 整段会话以「用户说的内容」的身份进模型，而不是以**对话**的身份；
   - 模型是在 `role: tool` 结构上训练工具使用的，把它降级进 user 消息是格式上的退步。
2. **「prompt 从事实网格投影」的正确形态是「投影成消息数组」，不是「投影成一段文本」。**
   ADR-048 的立身之本（事实网格 = 对话的唯一真源）**不要求**把消息拍平——transcript
   投影本来就有 `role`（`user` / `assistant` / `tool`）这个字段，是 `to_prompt()`
   这一步把它 `render_line` 成了散文。改成投影出 `Vec<ChatMessage>`，「唯一真源」与
   「结构化协议」两个目标可以同时成立。
3. **飞轮的方向相反。** 行业在往「显式结构 + 更长的工具链 + 更强的工具调用」走，把
   结构拍平成散文是往回走。

**被否决的方案**：

- **保持拍平，理由是「渲染点唯一、模型看到的就是事实源投影」**：否决。可观测性归
  `session/stats` 与 transcript 投影，**不归 prompt 形状**；拍平换来的「一处渲染」
  收益，远小于丢掉协议结构的代价。
- **「先跑一段，看效果再定」**：否决。本仓没有任何度量能回答「拍平对模型是变好还是变坏」
  （ADR-048 后果节已记），所以「看效果」在没有度量时等于凭感觉拍板——而现状是**已知的
  协议退步**，不需要实验来证明它更差。
- **在 `full` 档保留拍平、另加一个「结构化 prompt」档**：否决。两个 prompt 形状意味着
  两条要各自验证的行为面，而它们的差别恰好是**静默**的（形状不同、都能跑通），无法靠
  门禁发现。形状只该有一个。

**后果与不变量**：

- **落点**：新增 transcript 投影的「投影成消息数组」出口（与 `to_prompt` 同源、不同
  呈现）；`TurnRunner` 把基线 prompt 从 `String` 改为 `Vec<ChatMessage>`；
  `LlmAdapter` 的 `generate*` 系列相应改为收消息数组（**adapter 边界不再拍平**）；
  `ProviderLlmAdapter` 把数组原样交给 `ModelProvider::execute_turn`。
- **`TurnInput::prefix` 的位置随之改**：前缀现在是「排在基线之前的若干行」，结构化之后
  它应是**插在消息数组最前的一条 user 消息**（记忆段 / 就绪段 / 委派者段各自一条，
  `meta.kind` 随消息走，不再靠空行分隔）。语义优先级（记忆 → 就绪 → 委派者）不变。
- **就地累积的 `exchange` 随之退役**：它是为「往一段文本里追加本轮工具交换」而存在的，
  结构化之后本轮的工具调用与结果**直接进消息数组**（`tool` 角色 + `tool_call_id`），
  不再需要拼接格式。
- **不变量**：事实网格仍是唯一真源（投影换呈现不换来源）；不变量集合不变（新增投影出口
  不新增事件、不改既有判据）。
- **⚠️ 这会连带改动 e2e**：t2 / t19 / t38 / t39 的「工具结果以什么形状出现」判据**要按
  结构化形态重写**（本轮为迁就拍平形态写的那些适配要撤掉），t29 / t35 的「按空行切段」
  改为按消息边界切。**这不是「又一轮改测试」，而是上一轮的适配本身要被撤销** —— 记在这里
  是为了下一次读到 e2e 改动时知道它该往哪去。

**分步位置**：本条是**第 3 步**，排在「建双向完整性防线」之后、「缺口 3」之前。
