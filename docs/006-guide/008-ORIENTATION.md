# Symbio 心智模型入门（30 分钟）

> 文档类型：概念入门 —— 先建立"这套系统由什么撑起来"的心智模型，再去看操作步骤。
> 按 [GU-006 · 快速上手](006-QUICK_START.md "GU-006-QUICK_START") 跑通一次之后读本文最省力；反过来也行，读完之后再去跑。

这篇指南只回答一个问题：**代码为什么长成现在这个样子**。它不复述结构事实（插件数、路由、配置项——那些各有 owner），只把理解系统所必需的几个概念串起来，每个概念都指向它的权威出处。想知道"有多少 / 叫什么"看 [当前事实表](../004-ref/006-当前事实表.md "RE-006-当前事实表")，想知道"为什么这样设计"看文末指出的设计文档。

## 读法

30 分钟按七步走，每步一个概念：**先看一句话定义，再顺着链接读权威文档**。不要试图一次记住所有细节——目标是知道"遇到某类问题时该去哪篇文档"。

## 一、一个递归的形状：分形插件

整个系统的能力都由同一种东西构成：插件。容器插件可以包含子插件，叶子插件提供具体能力，两者实现同一个 `Plugin` trait。于是"某功能是谁提供的"这个问题，答案永远是一棵树上的某个节点，而不是散落的注册表。

这是全系统最重要的一条自相似性假设，目标形态见 [核心架构](../003-design/001-核心架构.md "DE-001-核心架构")，设计哲学与长期约束见 [架构总览](../003-design/002-架构总览.md "DE-002-架构总览")。

## 二、一条统一的地址：路径协议

树上的任意节点和任意能力，都用一条 `/` 分隔的路径定位；`traverse`（走子树）与 `route`（派发到能力）共享这套路径语义。模型输出一个路径就能调用一个能力，不需要代码生成。文件、会话等资源则走 `vdfs/*` 分支，仍落在同一个地址空间里。

线上路径形状见 [协议规范](../003-design/005-协议规范.md "DE-005-协议规范")，绝对/相对路径的两种形态见 [插件路由与地址](../003-design/006-插件路由与地址.md "DE-006-插件路由与地址")。

## 三、三个各司其职的角色：会话 / 执行 / 模型

这是最容易混淆的一处，务必分清：

- **session（会话）** 持有转写与事实源，只在"轮"的边界上派发工作；它是状态与真相的所在。
- **loop（执行）** 是单轮的执行引擎，负责上下文装配、轮首判决、工具循环与收束；它是无状态的一轮机器。
- **model（模型）** 是无状态的 LLM 网关，只做请求与流式返回，不持有会话。

Agent 在这套结构里不是一个独立进程，只是一个可以绑定到会话上的资产。目标形态见 [核心架构](../003-design/001-核心架构.md "DE-001-核心架构")，会话与地址的细节见 [会话输入与地址](../003-design/012-会话输入与地址.md "DE-012-会话输入与地址")，Agent 为何是一个目录见 [Agent 目录规范](../003-design/011-Agent目录规范.md "DE-011-Agent目录规范")。

## 四、一种统一的资源观：VDFS

文件、模型、Agent、技能、MCP、设置……全都是有地址的资源，共用 `<根>/…` 这一套心智模型；一个插件就是一个目录。这解释了为什么许多配置不是"设置页里的一个选项"，而是资源树里的一条目——因为配置就是它自己那棵子树。

规范见 [VDFS 规范](../003-design/009-VDFS规范.md "DE-009-VDFS规范")，前端地址模型见 [VDFS 前端页面规范](../003-design/010-VDFS前端页面规范.md "DE-010-VDFS前端页面规范") §3。

## 五、执行的心脏：债表驱动与义务环

执行不是"按调用栈顺序跑"，而是"看账上还有哪笔债没还"。端口插件申报自己欠哪几笔债（债表），义务环只根据事实判断哪些债可以还、派发执行、等待收束；没有可还的债就停下。判据全部机械可判，写入口只有一个。

这是理解日志和排障的钥匙——当系统"不动了"，通常不是卡住，而是账上没有可还的债。设计思想见 [义务环事实词表与债务表](../003-design/050-义务环事实词表与债务表.md "DE-050-义务环事实词表与债务表")，机制形状见 [机制形状规格](../003-design/051-机制形状规格.md "DE-051-机制形状规格")，判据如何推导见 [义务环判据与归属推导](../003-design/047-义务环判据与归属推导.md "DE-047-义务环判据与归属推导")，行表与派发面见 [行表与派发面](../003-design/022-行表与派发面.md "DE-022-行表与派发面")。

## 六、五条事实撑起一个协议格

端口与执行之间不靠函数调用约定，靠一组固定形状的事实：`request` / `sent` / `response` / `failed` / `retry`。端口数增加时协议格不膨胀——端口与尝试号是事实的载荷，不是新的事实种类。理解这五条，就理解了为什么日志里翻来覆去只有这几种事件。

出处同 [义务环事实词表与债务表](../003-design/050-义务环事实词表与债务表.md "DE-050-义务环事实词表与债务表") 与 [行表与派发面](../003-design/022-行表与派发面.md "DE-022-行表与派发面")。

## 七、文档即登记：找事实的正确姿势

这个仓库里，**每一篇活跃 `.md` 自己就是一条登记**：开头五行 front-matter 声明它的编号、状态与类别，汇总页由脚本从这些 front-matter 投影生成，不手改。因此：

- 想知道"为什么这样设计"→ 去对应设计文档的长期约束与取舍正文。
- 想知道"现在有哪些 / 叫什么"→ 去自动生成的 [当前事实表](../004-ref/006-当前事实表.md "RE-006-当前事实表")，它从代码提取，不会漂移。
- 想知道"有什么路由 / 错误码 / 配置"→ 去各自的 [路由参考](../004-ref/003-ROUTES.md "RE-003-ROUTES")、`002-ERROR_CODES`、`001-CONFIGURATION`。

登记机制见 [登记与汇总机制](../003-design/017-登记与汇总机制.md "DE-017-登记与汇总机制")，字段规范见 [SP-001](../005-spec/001.md)，提交纪律见 [提交纪律总册](../005-spec/003.md "SP-003")。

## 三条判据：随时用来衡量一个设计

读架构文档时会反复遇到三条尺子，先记住它们，后面会越来越有感觉：

1. **可表达性**：这个能力能不能被路径与协议表达出来？
2. **平凡值**：删掉它之后，系统是不是照样能跑（那它就不该存在）？
3. **静默失效**：它出问题时，是会明确报错，还是悄悄给出错误结果？——后者是本项目最不能忍的一类。

展开见 [架构总览](../003-design/002-架构总览.md "DE-002-架构总览")。
