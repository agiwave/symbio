# ADR-121：唤醒不进 `await` 行的 `until`，它开新账或收旧账

## 背景

[PL-017-端口细粒度化](../004-plan/017-端口细粒度化.md) §3.2 有一条只有两行的规定：

> **审批 / 用户补充 / 中止**：都是**外部事件**，由唤醒源落事实（`approval.*` /
> `user.message` / 收束格），`await-tools` 的 `until` 增加对应的事实名。

[T-244-唤醒事实接入与resume旁路退役](../009-task/244-唤醒事实接入与resume旁路退役.md) 要照它施工时撞上一条更硬的规定。[PL-016-义务环](../004-plan/016-义务环.md) §2.3 把 `await-<port>` 行的债键
钉死成**逻辑 id**：

> **键取逻辑 id `(port, id)`，不是尝试号。** `failed` 关的是逻辑 id（所有尝试）
> ——带 `attempt` 的键永远匹配不上它。

而三个唤醒源里：`authz.granted` / `authz.denied` 带 `(port, id)`，`user.message` 与两条
收束格（`chat.assistant.final` / `chat.assistant.fallback`）**只带 `turn`**。把它们写进
`await-tools` 的 `until`，`owed` 的匹配要求出口键与债键同构（`(port, id)` vs `(turn)`），
结果是**一条永远匹配不上的出口**——装载期第 6 条（执行体收口）与第 2 条（每行收口）都会
把它判成缺口，或者更糟：它形状上合法而永不命中，那笔工具债只能等租约判死。

同一处还有第二个空洞：§3.1 的 `close-turn` 行 `owes: turn.has_final ∧ ¬closed`，而
`turn.has_final` 至今没有任何实现（仓内 grep 无此字段）。视图只读日志，「执行体手里有
一份草稿」这类内存状态原理上折不进视图——不先定它的日志口径，这一行无法进表。

## 决策

**两条，都是把方案读通，不是改方案。**

1. **唤醒事实不改 `await` 行的 `until`；它按来源分两种作用。**
   - **审批通过 / 用户补充**：唤醒源落 `authz.granted(port=tool, id)`（审批）或
     `user.message`（补充）。前者**重新开账**——`dispatch-tools` 的 `owes` 本来就是
     `authz.granted(port=tool)`，审批一落就成为可还的一笔，`courier` 接着落 `sent` 并执行；
     旧那笔悬着的 `sent` 由**租约行**收：`stale_sent.exhausted` 未到顶 ⇒ `lease_keeper` 落
     `retry{attempt+1}` + `request{attempt+1}`，`await-tools` 在旧尝试号上由 `retry` 收清
     （[PL-016-义务环](../004-plan/016-义务环.md) §2.3 行 C 的原话）。到顶 ⇒ `failed{why:"lease_expired"}` 判死。
   - **中止**：中止方落一条**协议格** `failed(port=tool, id, why:"aborted")`，
     再落收束格。`await-tools` 由既有的 `failed` 出口收清，**不需要**为它加 `until`；
     收束格归 `close-turn` / `execute-turn` 的出口，不归端口行。
     `failed` 的写方是引擎或引擎授权的收束方（§2.4 表：`failed` = 搬运者；引擎在
     `run = Err` 时兜底），中止是「这次没成功」的一种，不是第六个协议名。
2. **`turn.has_final` 是视图字段，口径钉在日志上**：本幕**最近一条** `response(port=model)`
   的 `calls` 为空（§2.4 的 `expand: ["calls"]` 就是「这条响应要不要转出工具债」的唯一
   数据面），且本幕未收束。于是 `close-turn` 的 `owes` 与 §3.1 的
   `response.has_tool_calls` 是同一个判断的两个用法，不需要新事实名，也不需要把执行体的
   内存草稿折进视图。

## 理由

- 协议五名是**闭集**（[PL-016-义务环](../004-plan/016-义务环.md) §2.4），端口是载荷。让一条 `(turn)` 键的事实去收一笔
  `(port, id)` 键的债，等于给求解器加第二个匹配维度——那是判据 1「加端口 ⇒ `drive`/`owed`
  diff = 0」的反例。
- 「审批之后要重跑工具」今天由 `resume.rs:186-545` 的旁路做，它做的正是**执行 + 落结果**。
  而行表里已经有一行专管这件事（`dispatch-tools` owes `authz.granted`）。旁路的真实身份是
  「没有事实面时手工重放这一行」，所以退役它不需要新机制，只需要审批格真的落到日志里。
- 中止用 `failed` 而不是新事实名：判据 2（每次调用都有 `sent` + **应答**）要求中止的轮
  也数得清「那笔工具调用有没有回来」。`failed{why:"aborted"}` 是这句话唯一有键的形状。

## 被否决的方案

- **照 §3.2 字面把三个事实名加进 `await-tools.until`**：否决。`user.message` / 收束格没有
  `(port, id)`，加进去要么装载判红、要么永不命中；且「审批通过 = 这笔 await 收清」会把
  「工具到底跑没跑成」这个信息抹掉——判据 2 反过来被入账动作破坏（与 [T-247-插件内部模型往返进环](../009-task/247-插件内部模型往返进环.md) 里
  `sent` 的语义冲突是同一种错）。
- **给 `await` 行加第二个债键（turn 侧键）**：否决。一行一个债键是 `owed` 的折叠前提，
  加维度要改求解器字节，撞 PTS-003。
- **`turn.has_final` 用执行体返回的内存布尔**：否决。视图只读日志（§2.2），内存布尔
  正是 PL-014 一路在消灭的「执行侧自觉」；崩溃恢复后它就是假的。

## 后果

- [T-244-唤醒事实接入与resume旁路退役](../009-task/244-唤醒事实接入与resume旁路退役.md) 的验收口径按本裁决订正三处：① 「插话唤醒 `await-turn`」不是方案要求
  （§3.2 只写 `await-tools`），改为「补充格进 `turn.supplemented` / `user.message` 的既有
  出口，不新增 `await` 出口」；② 中止的收口格从「收束格进 `until`」改为
  `failed{why:"aborted"}` + 收束格两条；③ `close-turn` 的 `owes` 口径由本 ADR 给定，
  进 facts 与视图版本号。
- **`tool` 端口的 `max_attempts` 解锁条件由本裁决满足**：[PL-016-义务环](../004-plan/016-义务环.md) §2.3 要求重试
  「由活着的等待方决定」，`loop_rows.rs` 的注释一直把上限 > 1 押在「等步 4 的唤醒事实接上」。
  唤醒接好 ⇒ 等待方在表里 ⇒ `tool` 的 `max_attempts` 才可以 > 1，且 `retry` 路径的用例
  必须用真实 `PortDecl`（销「只有合成覆盖」）。
- 本 ADR 只定**行语义**，不定 `resume.rs` 三条路径的代码迁序（那是 T-244 的施工步）；
  压缩/判决路径的入账归 [T-247-插件内部模型往返进环](../009-task/247-插件内部模型往返进环.md)，两者互不依赖。
