# ADR-116：授权级联的家是收束行

## 背景

[ADR-115](115.md "ADR-115") 决策 6 把授权改成**正事实级联**：`authorize` 行
`prio: 0` 交回 `authz.granted` / `authz.denied`，`dispatch` 行以 `granted` 为前件，
没有 `granted` 就永不派发。方向成立（"允许"不能再靠"没有 `denied`"推断），但
**它在哪个端口上才有前件可判**当时没有答案：粗端口 `turn` 的 `request` 不带能力
维度，[T-226](../009-task/226-授权行.md "T-226-授权行") 因此把两行级联移交
[T-227](../009-task/227-端口细粒度化.md "T-227-端口细粒度化") 步 3，理由是
「工具调用自带审批与权限面」。

T-227 步 3 施工前逐点核对工具批的权限面，发现**那个理由不成立**。

## 事实（三条，都在代码里可查）

1. **工具批的派发时刻没有单一可判的能力。** 批首读四道闸
   （`tools/dispatch/gates.rs`），判据分别是风险档、工具自声明的
   `provides_assign_work` / `owns_task_table` 位、以及钩子——它们**不是同一个
   能力名**，也没有"这次调用需要能力 X"这条数据。
2. **拒止的产物是结果，不是"没发生"。** 拒因经结果正文（`Refused: …` /
   `Blocked: …`）回灌模型，`failure_kind` 落在父节点上。若「`denied` ⇒ 无
   `sent`」把整批拦在派发之前，下一条请求就带一条**没有结果的 `tool_call`**
   ——provider 直接拒收（`record_protocol_failure` 的注释就是为此写的）。
3. **拒止按设计不产事件。** `RefusalTraceKind::ZeroEvent` 是外部执行 `Refuse`
   的既定语义：拒止**不产任何领域事件**（`gates.rs` 的四个出口
   `ZeroEvent` / `Recorded` / `Audited` / `AuditedNoDelegation` 是四份**事实
   出口**，不是一个布尔的四种写法）。把拒止一律落成 `denied` 事实，等于把
   四份出口压成一份——那不是补齐，是抹掉一个已经裁决过的区分。

## 决策

1. **级联不在工具端口上落地。** `dispatch-tool` 行仍是
   `owes: request(port=tool)`、`until: sent | failed`——工具批的**派出**不需要
   许可，需要许可的是**它的结果成为哪一格事实**（产物闸，ADR-067 已在那儿判）。
2. **级联的家是收束行**（`close-turn`）。它的全部动作就是落一格发言收束格，
   闸门谓词是 `reply`（`can_land_speech`），而拒绝的语义**恰好**是"不落这一格"
   ——`authz.denied` 已在 T-219 落事实，`granted` 补上另一半即可：

   ```
   行  authorize-close  owes:   turn.closing(turn)
                        until:  authz.granted(turn) | authz.denied(turn)
                        by:     authorizer
                        prio:   0

   行  close-turn       owes:   authz.granted(turn)
                        until:  chat.assistant.final | chat.assistant.fallback
                        by:     closer
                        prio:   5
   ```

   `denied` ⇒ `close-turn` 的 `owes` 永不成立 ⇒ 不落格（今天的行为），而"被拒"
   是写了的事实（T-219）。`owes` 里没有否定原子。
3. **前置是"收束先成为行"。** 今天收束写在 `turn_runner::stream::halt` 里（程序
   而不是表），所以本决策**随 T-227 步 4 落地**，不随步 3。

## 施工修正（2026-10-22，步 4 落地时）

本 ADR 初稿写的两个细节在施工时被改掉了，理由都是"按初稿写会得到一个不成立的
结构"，不是口味问题。

**修正一：前件从 `turn.has_final` 改成 `turn.closing`（决策本身）。** 初稿的理由是
"收束这件事的前件就是'模型回来了'"，并为此要求 `response{port:model}` 的载荷补
「有没有请求工具」「正文是否非空」两个字段。逐点核对**六条**收束路径之后，这个
前件站不住：

| 收束路径 | 落格处 | 有模型往返吗 |
|---|---|:-:|
| 深度档正常收束 | `stream::halt` | 有 |
| 兜底 | `settle::land_failure` | 有 |
| 上界耗尽 | `settle::append_exhausted` → `land_failure` | 有 |
| 首请求前中止 | `stream::aborted` | **无** |
| 定稿答话 | `prepare`（1b） | **无** |
| 反射档 | `reflex::run_reflex` | **无** |

三条零模型往返的路径**永不**满足 `turn.has_final`——以它为前件，它们就永不收束，
于是收束行在三条路径上把一轮话卡死。而"这一轮要收束了"这个**决策**对六条路径
都成立，是唯一的前件。改完之后 `response{port:model}` 的载荷**不必**补字段：
本 ADR 决策 3 列的第二个前置条件被结构性消掉，不是被绕过。

**修正二：`prio` 从 0 / 10 改成 0 / 5。** 行表要求 `prio` 全局严格递增，而 10 已被
`policy.classify` 占着。把十二条行整体重编号只为凑一个整数，会制造一次纯噪声的
diff（且下次再加行还要再来一次）。取 0 / 5 落在 `execute-turn`（60）之前，语义
（"收束类判据先于执行类判据"）不变。

**落地形状**（`symbio/src/plugins/loop/close.rs`）：一个 `allow()` 依次做三件事
——落 `turn.closing`（幂等键 `closing-{turn}-{kind}`）→ 若欠 `authorize-close` 则
过 `closure_gate` 并落 `authz.granted` 或 `authz.denied` → **问表**：`close-turn`
还欠不欠。第三问刻意**问行**而不是"查日志里有没有 `granted`"：判据只该有一处
（表里），否则代码里会多出一个不跟表变的第二判据，下次改表它就撒谎。


## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 在 `dispatch-tool` 上加 `authorize` 行，`dispatch` 以 `granted` 为前件 | 拒止会失去结果（事实 2）或失去"零事件"语义（事实 3）；二者都是行为变更，且都不是本任务要买的 |
| 给 `CapabilityMeta` 加一个 `required_capability` 字段，把四道闸折成一个能力名 | 四道闸判的不是同一件事（风险档 / 派活资格 / 任务表资格 / 钩子），折成一个名字就是造一个假概念；且这是 core 面变宽，须单独裁决 |
| 先落 `granted` 事实、级联"以后再说" | T-226 已否决过同一条：一条**无读方**的事实入库，看起来像已经实现了级联 |

## 后果

- [T-226](../009-task/226-授权行.md "T-226-授权行") 等的不是工具端口，而是
  T-227 步 4；它停在 `doing` 的理由从"前件无内容可判"改为"家还没成为行"。
- [T-227](../009-task/227-端口细粒度化.md "T-227-端口细粒度化") 的判据 8b 改写为
  「收束行的授权级联」，随步 4 验收；步 3 交付的是**工具批端口**本身。
- [T-216](../009-task/216-义务环收敛批.md "T-216-义务环收敛批") 的第 16 条判据
  因此也落在步 4 之后——批次不因本决策提前变绿。
- 工具批的拒止维持四份出口不变（`ZeroEvent` 仍是零事件）。
- **记账失败 fail-closed 且不上抛**：`turn.closing` / `authz.granted` /
  `authz.denied` 三格任一落不进去，一律不放行（只 warn）。收尾时刻的任务是
  "这一轮怎么结束"，把记账失败变成 `Err` 会让它吃掉那个问题。
