# ADR-116：义务环的集合展开

## 背景

[PL-017](../004-plan/017-端口细粒度化.md "PL-017-端口细粒度化") §3.3 要求工具批次是
**N 笔子债**，不是一笔整批债：

```
dispatch-tools   owes: response(port=model) ∧ response.has_tool_calls
                 expand: (calls, id)          ← 一个批次展开成 N 个元素
await-tools      owes: sent(port=tool)
                 until: response(port=tool) | failed(port=tool) | retry(port=tool)
```

`Decl.owes` 是一个 `Pattern`——「一个源实例开一笔债」。批次场景里一个 `response`
实例的 `calls` 数组才是需要逐笔开债的集合，求解器没有这个能力。

[T-227](../009-task/227-端口细粒度化.md "T-227-端口细粒度化") 的处理过程记了当时的
偏差：不改求解器字节，改在派发时对每笔调用各落一条 `request` / `sent`。这与「批次
展开成元素」在**可达债集合**上等价，但并发许可只能靠执行体自觉，且不是 PL-017 §3.3
的目标形状。[T-228](../009-task/228-批次并发声明.md "T-228-批次并发声明") 先把
「同批能否并发」挪到 `PortDecl.concurrent`，本裁决补上另一半：**债从哪来**。

## 决策

1. **`Decl` 增加 `expand: Option<(&'static str, &'static str)>`**，语义是
   `Some((list_field, element_key_field))`：`owes` 实例的 `list_field`（数组）
   逐元素开一笔债。
2. **只有 `owes` 展开。** `until` / `unless` 按键命中，一个键已经唯一；再展开会把
   同一笔出口读成多笔，把「还清」误判成「还有」。求解器把展开只接进
   `keys_of_expanded(&decl.owes, decl.expand, …)` 一条路。
3. **`eq` 拦外层，键取自元素。** 等值约束（`port=model`）仍对 `owes` 的实例求值；
   键绑定（`owes.key`）对**数组元素**求值。`element_key_field` 必须出现在
   `owes.key` 里——它是元素的身份字段；缺了它只能开一堆同键债，`until` 无从分辨
   还了哪一笔（装载期判 [`Gap::ExpandKeyMissing`]）。
4. **事实源的列表字段要由 `FactDecl.expand` 承认**（`Gap::UndeclaredExpand`）。
   事实已经在声明层列了「哪些字段可展开」；求解器读一个事实不承认的字段是拼错名字
   的静默形态。视图源没有这张声明（视图的求值函数就是它的形状），本裁决不补。
5. **基线更新是决策的一部分。** `owed` 的字节随本裁决变化；PTS-003 的
   `scripts/baselines/port-surface.json` 同批更新为当前指纹，`adr` 指向本裁决。
   这不是端口渗进引擎（判据 1 防的是那件事），是引擎按机制演进——演进必须挂在
   一条决策上，本裁决就是那条。

## 理由

| # | 依据 | 本裁决做了什么 |
|---|---|---|
| 1 | PL-017 §3.3 把批次定义为「集合，不是单项」 | 给求解器一个通用的集合展开，而不是在批次执行体里手写 |
| 2 | 债的键是「一笔账的身份」 | 展开后键必须落在元素上，`until` 才能逐元素还 |
| 3 | 声明层已有 `FactDecl.expand` | 事实侧的可展开字段是既有声明，求解器引用它而不是另立一份 |
| 4 | PTS-003 的判据口径（PL-016 §6 判据 1） | 改 `owed` 字节必须挂 ADR；本裁决与基线同批落地 |

**这不是对 ADR-115 的改判。** `owed` 的输入闭包（事实 / 视图 / `now`）不变，执行
契约不变，端口分级不变。变的是 `owes` 从「实例 → 债」到「实例的集合 → 债集合」的
一条投影。

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 把 `expand` 放进 `Pattern` | `until` / `unless` 也用 `Pattern`；一次声明会让同为出口的集合再展开一次，把一笔还清读成多笔 |
| 在批次执行体里手写逐元素循环 | 正是 T-227 的过渡态：并发与重试藏在代码里，不在事实面 |
| 为工具批次新增一个事实名 | 判据 1 要求「加一个端口 = 0 个新事实名」；批次是 `response` 的集合字段，不是新事实种类 |
| 让 `until` 按元素自动匹配外层键 | 键的语义会变成「看情况」，装载期的 `KeyMismatch` 判据失效 |

## 后果

- **求解器能力先落地，生产行后接。** `dispatch-tools` 的 `owes` 今天仍写
  `authz.granted`（T-227 的蕴含写法），因为把它改成 `response(port=model)` 需要先让
  审批 / 恢复成为 `await-tools` 的唤醒事实——恢复路径今天创建 `tool-resume-*`
  调用，没有对应的模型响应前件。生产接入见 PL-017 步 4→5。
- 在接入之前，`expand` 由 `decl::ring` 的用例覆盖（逐元素开债 / 逐元素还 /
  缺列表不开债 / 两类装载期 gap / 正例无 gap），不靠一条尚未存在的生产行背书。
- 事实量不变：展开是**读侧投影**，不落新事实；元素债与逐调用 `sent` 是同一批
  事实的两种读法。
