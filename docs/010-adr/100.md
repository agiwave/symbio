# ADR-100：绑定即登记——能力随会话装配点的绑定来，可见域不登记

## 决策

**会话装配点把本轮主体登记进运行期绑定面**（`authz::bind_inheriting`），能力面按
**部署表 ∪ 绑定登记**合流判定（`authz::EffectiveMatrix`，取表口 `production_matrix`
的返回类型）。三条口径：

1. **能力随绑定来**：根会话（`Scope::Root`）继承**会话面缺省行**（主智能体行），
   委派子会话（`Scope::Child(parent)`）继承**父行**——委派不放大权威；
2. **可见域不登记**：`sees_of` / `can_see` 只认部署表——绑定不使任何主体成为矩阵成员；
3. **静态行不被改写**：主体已在 `ROWS` 里 ⇒ 绑定是空操作，窄行不被放大成会话面。

`governance::PermissionMatrix` 保持「常量表 + fail-closed 谓词」原样不动；合流住在
`authz`（「部署事实怎么看待运行期身份」是这张表的裁决，不是判定机制的裁决）。

## 背景

[ADR-099](099.md "ADR-099") 把「未登记 = 拒」立成全表唯一口径，删掉了派生分支——
对一切未登记的 `agent:<id>` 不再**静默**派生主智能体整套能力。删得对：「忘配窄行」
从此是一条会被看见的拒绝，不是一次静默超权。

但删干净之后暴露出**可用性**的真空：e2e 的根会话以 `--agent <id>` 选定身份
（t30 / t39 / t57 / t76 的形态），这些身份**不在部署表里**（`ROWS` 是部署事实，
只登记 `session/main` / `worker` / `planner` / `verifier` 等固定角色），于是——

- 收束闸（`turn_runner::closure_granted`，读 `ActorSpec` 自带能力集）拒 ⇒ 收束落不了格；
- 记忆不编码 ⇒ 下一轮召回段为空（t76 的「C 的请求应有召回段」、t57 的召回段断言落空）；
- 工具闸拒（t39 的 `vdfs_read`：`Refused: 未持外部执行能力（produce.artifact）`）。

这四个失败**同一个根因**：身份会话缺一行，而缺的这行**本应由「会话选定了这个 agent」
这件事**给出来。

## 为什么不是「派生回滚」

回到 `matrix_for` 派生是一种**隐式**给权：没有任何一处登记动作，任何 `agent:<id>`
都自动拿到会话面整套能力。ADR-099 否决的正是这个——「少一行」不再是一条判据，
因为永远会有一行凭空长出来。

本条形态相反：给权仍然需要一次**可见的登记动作**，只是这次动作发生在**会话装配点**
（`request_actor_spec`——全 crate 唯一的 `ActorSpec` 生产构造点，带 `Scope`）。
装配点知道两件派生面不知道的事：**这一轮的主体是谁**、**它的作用域（根 / 挂在哪个
父下）**。判据链因此闭合：**判的对象（规格）与给它赋能的来源（这次绑定）有单一出处**。

## 五条边界（逐条有判据，见 `authz.test.rs`）

| 边界 | 判据用例 |
|---|---|
| 能力随绑定来 | `a_bound_subject_takes_the_source_row`：绑定前谓词全假，绑定后收束闸放行 |
| 静态行不被改写 | `binding_never_widens_a_deployed_row`：绑 `worker` 后其行仍是单能力 |
| 可见域不登记 | `binding_grants_no_visibility_scope`：绑定主体 `sees_of` 仍为 `None`、读不到他人 `shared` |
| 淘汰面只认部署表 | `the_elimination_face_ignores_bindings`：`deployed_can_write_name` 看不见绑定 |
| 委派两侧都在册 | `delegated_binding_registers_both_sides`：`from` 无行时先给它登记缺省，子继承父行 |

### 第三条为什么必须单列（可见域与能力分家）

`governance::PermissionMatrix::can_see(Shared)` 的判据是 `sees_of(viewer).is_some()`
——即「是矩阵成员」。若把可见域也随绑定登记，任何绑定 agent 都会变成矩阵成员、
**读到他人 `shared`**（t76「ghost 读不到他人 shared」的反判据当场破）。所以：
**能力可以随绑定来，「看见别人的 shared」只能来自部署登记**。

### 第五条为什么必须单列（委派上限两侧都在册）

`turn_runner::within_delegation_ceiling` 判**父主体也持有**对应能力。委派链上若父主体
自己不在册，子会话会因「父也不持」而收束不了——所以 `from` 无行时先给 `from` 登记
会话面缺省，两侧都在册，上限判得出来。

## 与 ADR-099 的关系（同一条纪律的两段，不是矛盾）

- 合流面仍 fail-closed：既未部署、又未绑定 ⇒ 每个谓词为假；
- 给权仍需一次**可见动作**，只是从「部署配表」扩到「会话装配点绑定」；
- **少一次登记动作 = 一条拒绝**（不再是「一条静默超权」）。

## 代价（诚实划界）

- **绑定面是进程级、单调增**：`BOUND` 是进程内全局 `RwLock<HashMap>`，只增不减——
  长驻进程里每个出现过的 agent 身份都会留下一行。这是**已知代价**：绑定随会话而来、
  边界是「≤ 会话面缺省行 / ≤ 父行」（委派不放大权威），故不构成超权；收窄它
  （登记与会话生命周期同寿）归 [T-182](../009-task/182-创建即登记迁移步.md "T-182")。
- **绑定不带可见域**：绑定主体读不到他人 `shared`——这是与能力面**有意**的不对称
  （见上第三条）。
- **登记失败 = 不登记**：锁中毒只告警跳过，未登记的主体照旧每个谓词为假（fail-closed
  的方向不因登记通道故障而松开）。

## 不在本条范围

`ROWS` 之外的**声明行**（创建会话即声明能力，不经装配点绑定）归
[T-182](../009-task/182-创建即登记迁移步.md "T-182")；本条只落「装配点绑定」这一形态。
