# ADR-109：检索内核不合一，排序口径合一到「全序」这一半

## 决策

1. **记忆召回与代码检索不合成一套内核**，本批以「裁决 + 一条口径补实」结案
   （[T-210-资产与清单单源化批](../009-task/210-资产与清单单源化批.md) 项三给的两种合法结案方式之一）。判据是下面那张清单：两条链路只在
   **骨架**上重合，在**候选来源、打分函数、降级形状、输出契约**四格上各自不同——
   合一套内核要引入的是「跨事实层与文件系统两界的检索抽象」，那是新的架构元素，
   而它换来的收益（少写一次 `sort_by`）今天已经有了更便宜的实现方式（第 3 条）。
2. **打分口径各归各，不设共享打分器**：
   - 「查询 → 相关性」这条口径的**记忆侧**唯一 owner 是 `projection/recall_score`
     里的 `terms` / `overlap` / `rank`——它同时是**生产与召回评测集**共用的那一份
     （`verify/recall_eval.rs` 用 `#[path]` 包含同一文件，T-085 批③ 的立身之本）；
   - **代码侧**唯一 owner 是 `plugins/local/codebase_search.rs` 的 `semantic_search`
     （嵌入向量余弦）。词面重叠分与余弦相似度的**量纲不同**（计数 vs [−1,1]），
     强行合一只有两种下场：要么输出契约里 `score` 变成「看模式才知道是什么意思」的
     悬浮数，要么把其中一面的分辨率削到另一面能接受的程度。
3. **合一的那一半是「全序」判据**：分数降序之后**必须**还有稳定次级键，top-k
   **必须**截断在全序之后。这条是本 ADR 的唯一 owner 声明，两侧各自的实例：
   - 记忆侧：平手看 `ts`（编码时刻）降序、再平手看 `seq` 降序；
   - 代码侧：平手看相对路径升序、再平手看起始行升序（本批补实的那一半，
     此前只有 `partial_cmp(...).unwrap_or(Equal)`，平手块先后由**增量重建的历史**决定）。
4. **代码检索的关键词降级路径不在本口径内**：它按「遍历序（名字钉死）+ limit 截断」
   返回，`score` 恒 `0.0`——那是**没有相关性排序**这件事的如实表达，不是排序算错。
   `mode` 字段（`semantic` / `keyword_fallback`）负责把两种形状分开，读数方要看 `mode`
   才知道 `score` 有没有意义。

## 清单：共同点与差异点（本批的第一产出）

| 维度 | 记忆召回 | 代码检索 | 是否同一条口径 |
|---|---|---|---|
| 候选来源 | 事件 Log 的 `memory.*` 投影（as-of、排除式遗忘） | 工作区文件分块索引（增量重建、二进制落盘） | **否**——一侧是事实层纯函数，一侧是派生缓存 |
| 打分函数 | 词面重叠计数（拉丁词 + CJK 二元组） | 嵌入余弦（归一化点积） | **否**——量纲不同 |
| 排序方向 | 分数降序 | 分数降序 | **是** |
| 平手判据 | `ts` 降序 → `seq` 降序（全序） | 相对路径升序 → 起始行升序（全序，本批补实） | **是**（决策 3） |
| top-k 截断点 | 全序之后（预算由框架 `Projection::apply` 执行，ADR-105） | 全序之后（`take(limit)`） | **是** |
| 过滤参数 | `tag`（认知内容标签） | `path`（路径子串） | **否**——各自的坐标系 |
| 降级形状 | `degraded` 标志 + 部分结果（不删事实） | `mode` 换成 `keyword_fallback` + `notice` 说原因 | **否**——一侧「少给点」，一侧「换个做法」 |
| 输出契约 | `RecallView`（住 core 的中性视图层，跨包共享） | 工具返回体 JSON | **否** |
| 时间维 | 承重（新近度是平手判据，跨会话比得了） | 无（文件没有「编码时刻」，`mtime` 只做增量指纹） | **否** |

## 为什么不合一（把否决的理由写实）

- **合了要放在哪一层？** 代码检索的输入是文件系统 + 嵌入服务，记忆召回的输入是事件
  切片。要写一份同时接受两者的内核，就得在 `symbio_core` 立一个「检索请求」抽象——
  而 core 的形状是冻结的（CS-001 三格只许降），这一格**变宽**需要的是一条独立论证，
  不是顺手加的。更硬的理由：**两侧今天没有一个共同调用方**，没有共同调用点的抽象
  只有作者。
- **两条链路的「相关」定义不同**，而这不是实现细节：记忆的相关是「这条编码跟本轮
  意图词面重合多少 + 它多新」；代码的相关是「这段文本在向量空间里离查询多远」。
  把它们压进一个函数签名，参数得写成 `score: impl Fn(...) -> f32` 之类的注入点——
  那正是 ADR-083 废除的形态（按实现触点凑出的端口契约）。
- **真正会漂移的地方已经收住了**：生产与评测共用同一份源码这件事只发生在记忆侧
  （`recall_score` 不许 import crate 内类型，否则两边编译不了）。代码侧没有对应的
  评测集，也就没有第二份临摹件需要消灭。

## 判据与落地锚

| 半边 | 锚 |
|---|---|
| 记忆侧全序（分数 → `ts` → `seq`） | `projection/recall_score.rs::rank`；无查询时的平凡值是纯 `ts`/`seq` 降序 |
| 代码侧全序（分数 → 路径 → 起始行） | `plugins/local/codebase_search.rs::semantic_search` |
| 反例用例（存放顺序相反的两份索引给同一份 top-k） | `codebase_search.test.rs::tied_chunks_are_ordered_by_a_stable_secondary_key` |
| 降级路径不参与相关性排序 | `keyword_search` 的 `score: 0.0` + `mode` 字段（T-199 的 `notice` 同一处） |

## 代价与边界

- 排序口径的「合一」只到**判据形状**这一层，代码上仍是两处 `sort_by`。这是自觉的选择：
  两处各自不到十行，抽出来要跨 core/插件边界，而跨边界的抽象比重复更贵。
- **代码侧的平手判据用路径而不是新近度**，因此两个块分数相等时，先返回的是路径字典序
  小的那个——它与「哪个文件更新」无关。今天没有更合适的次级键（索引里没有可靠的时间语义，
  `mtime` 只用于增量判定且已知对 `rsync -t` 这类保留写入失灵）。
- **关键词降级面的 top-k 是遍历序前 N 条**，不是「最相关的 N 条」。要修它得给 grep
  命中做词频/位置打分，那是另一件事，本 ADR 不顺带立项，只把「它不是相关性排序」写进
  决策 4，免得后来者把 `score: 0.0` 当成一个待修的 bug。
