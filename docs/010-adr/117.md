# ADR-117：工具批次的两段债

## 背景

[PL-017](../004-plan/017-端口细粒度化.md "PL-017-端口细粒度化") §3.3 把工具批次定义为
**N 笔子债**，并给出示意行：

```
dispatch-tools   owes: response(port=model) ∧ response.has_tool_calls
                 expand: (calls, id)
```

[ADR-116](116.md "ADR-116") 只裁决了求解器能力（`Decl.expand`），把生产接入留到
审批 / 恢复的唤醒事实接上之后；它的「后续」也照抄了上面这句：把 `dispatch-tools`
的 `owes` 迁到 `response(port=model)`。本裁决核对实现后发现，**这句话本身把两段
债合成了一段**，照做会同时坏掉两件事：

1. **派发行必须被授权闸住。** `authorize-tool` 对拒绝的那一笔落 `authz.denied`，
   而派发行的 `until` 只有 `sent` / `failed`、`unless` 为空。若它欠的是
   `response(port=model)`，**被拒绝的调用同样有模型响应** ⇒ 派发行照样欠、引擎
   照样派——授权行的拒绝在派发侧没有作用点。求解器没有否定原子（ADR-116 的
   「被否决的方案」已拒绝「按元素自动匹配外层键」这类隐式语义），补一个
   `unless: denied` 也不行：事实只追加，用户批准后旧 `denied` 仍在，那笔账
   永远开不回来。
2. **恢复调用没有、也不该有模型响应。** 审批 / 重试 / 补充是**外部动作**，它写的
   是一笔新的 `request(port=tool, id=tool-resume-…)`。要求它先有一条
   `response(port=model)` 是把「用户批准」伪装成「模型又答了一次」——既不合事实
   语义，也让模型端口多出一种不由模型产生的实例。

## 决策

1. **工具调用有两段债，两行分别承担：**

   | 行 | `owes` | `expand` | 出口 | 谁写入口事实 |
   |---|---|---|---|---|
   | `open-tools`（新增，prio 66） | `response(port=model)` | `Some((calls, id))` | `request(port=tool)` | 模型端口应答之后的创建者 |
   | `authorize-tool`（不改） | `request(port=tool)` | `None` | `authz.granted` / `authz.denied` | 授权者 |
   | `dispatch-tools`（不改） | `authz.granted(port=tool)` | `None` | `sent` / `failed` | 派发者 |

   **`dispatch-tools` 的 `owes` 不迁。** 它欠的仍然是「已放行、尚未派出」，与调用
   从哪来无关：批次调用和恢复调用都在这里汇合，各得一笔 `sent`。
2. **`expand` 只落在 `open-tools`。** `response` 的 `calls` 数组是这个集合的
   **唯一来源**；元素键是协议调用 id（`(port, id)` 的 `id`），与后续 `request` /
   `authz.*` / `sent` 同键。ADR-116 的求解器语义不变（只展开 `owes`，键绑定在
   元素上）。
3. **`response(port=model)` 的载荷要能承载集合。** 它在 `calls` 里带元素
   `{id, name, arguments}`（id 是**协议调用 id**，不是模型原样 id 的裸值——批次
   跨轮不能撞键，具体编码在实现里定，见后果）；`FactDecl` 把 `calls` 写进
   `expand` 与 `fields`，否则装载期判 `Gap::UndeclaredExpand`（ADR-116 决策 4）。
4. **恢复调用是**创建者**，不是派发者。** 审批动作写下的 `request` 就是它的债
   前件；它不经 `open-tools`，直接进 `authorize-tool` → `dispatch-tools`。因此
   `resume.rs` 的旁路不需要为「没有模型响应」补一条事实。
5. **不新增事实名、不新增端口。** `open-tools` 是 `tool` 端口上的一条新行；
   `calls` 是 `response` 的载荷字段。PL-016 §6 判据 1 的「加一个端口 = 0 个新
   事实名」不受影响。

**与 PL-017 §3.3 的关系**：目标形状（批次 = N 笔子债、并发由集合表达）不变；
变的是**示意行把创建与派发写在了一行**。本裁决把这段债拆开，是本批的架构裁决，
不是「实现困难」的让步——反过来，照示意行写会在授权拒绝上直接失败。

## 理由

| # | 依据 | 本裁决做了什么 |
|---|---|---|
| 1 | 授权行的拒绝必须对派发有作用点（T-226 判据 8b） | 派发行继续欠 `authz.granted`，拒绝即无债 |
| 2 | 恢复是外部动作（PL-017 §3.2） | 恢复的 `request` 就是债前件，不伪造模型响应 |
| 3 | 批次是集合（PL-017 §3.3） | `expand` 落在唯一能看见 `calls` 的创建行 |
| 4 | 一行只写「什么时候欠、什么算还」（T-222） | 创建与派发各一行，各读各的前件 |

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 把 `dispatch-tools.owes` 迁到 `response(port=model)`（PL-017 示意行） | 被拒绝的调用仍有模型响应 ⇒ 派发绕过授权；恢复调用则失去债 |
| 给派发行加 `unless: authz.denied` | 事实只追加：用户批准后旧 `denied` 仍命中，那笔账永远开不回来 |
| 让恢复写一条合成的 `response(port=model)` | 把用户动作伪装成模型应答，污染模型端口的语义与统计 |
| 恢复写一条新事实 `tool.resume` 作前件 | 判据 1 要「0 个新事实名」；恢复的 `request` 已经是它的事实前件 |
| 先在派发前落 `sent`、审批通过再执行（把审批变成 `await` 唤醒） | 需要把风险闸与用户批准拆成两个出口，改动面大于本批；若将来要让审批成为 `await-tools` 的唤醒事实，另立 ADR，不拿它当本裁决的前提 |

## 后果

- **T-232 的实现面**：新增 `open-tools` 行；`response` 载荷加 `calls`、`FactDecl`
  加 `expand: ["calls"]`；`open_batch` 在写 `request` 前问 `owes("open-tools")`。
  逐调用 `request` 的 id 必须在**本轮内**唯一（跨轮同 id 会被 `until` 误关），
  由创建者在元素里带协议 id 解决。
- **T-233 的调度面**：引擎按 `prio` 会先看到 `open-tools`，再 `authorize-tool`，
  再 `dispatch-tools`；三段各自是一次执行体调用，不存在双调度器。
- **恢复路径零改动**：`open_resume` 继续写 `request` → `authz.granted` → `sent`；
  本裁决只把它「不依赖模型响应」这件事钉成判据（T-231 的用例）。
- **基线**：`owed` 的字节不变（ADR-116 已改）；行表与事实声明变化，`scripts/baselines/port-surface.json`
  的哈希由 T-232 按实际指纹重算，`adr` 指向本裁决。
