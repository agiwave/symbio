## 决策

**背景**：[ADR-053](053.md) 把「编辑 / 删除 / 压缩」
逐个补进事实网格。补到 S2.7-b3 前置时出现一个信号：**每遇到一个新场景，就发现「这里也没有事实」**
——恢复路的删子树、abort 的改父节点、压缩记录节点、`partial` 节点、写侧裁剪……一处处补，
像在给一个漏水的桶贴补丁。用户的判断是对的：**这样一直打补丁，很可能彻底破坏方案的正确性**。

但「WAL 只追加不修改」**不是**元凶。追加本身没有逼出任何补丁：`archive_before` 归档的是
**被取代的前缀**，段与段不重叠，拼起来仍是原 WAL——b2 因此做到零回退损失。真正让补丁涌现的是三件事：

1. **顺序反了。** 写侧现在的形状是 `读列表 → 改 Vec → replace_messages 落库 → （补一条事实）`。
   事实是**事后补的**，所以它天然是「可选项」——忘了补，代码照样编译、测试照样绿。b3 前置那四处
   （`resume.rs` ×3、`pipeline.rs` ×1）就是照这个形状补的，**那批补丁本身正是这个病的实例**。
2. **粒度按场景命名，不按原语。** 网格里已经有三个变更格子，但它们是**按场景**被发现和命名的
   （「编辑」「删除」「压缩」）。于是每来一个新场景（「恢复路删子树」「压缩记录节点」），
   看起来都像需要一个新格子——而其实它们都是既有原语的组合。
3. **强制靠人工审计，不靠类型。** 10 个列表写入口里有 6 个没有对应事实。这个比例不是疏忽，
   是**机制问题**：没有任何东西在编译期或 CI 期要求「改了列表就必须落事实」。

**决策**：

1. **列表的变更收成闭集：三个节点级 + 一个列表级。** 任何对消息列表的改动都且只能是这四种：

   | 原语 | 语义 | 事实 | 网格格 |
   |---|---|---|---|
   | **诞生** | 一个此前不存在的节点出现 | `message.added` | `message × opened` |
   | **断言** | 一个已存在的节点现在读作 Y | `message.edited` | `message × asserted` |
   | **关闭** | 一个节点没了 | `message.removed` | `message × closed` |
   | **取代** | 整段历史现在读作 L | `session.consolidated` | `message × progressed` |

   前三个是**节点级**（改一条），第四个是**列表级**（改全部）。**判据是可证伪的**：
   新场景若需要第五种原语 ⇒ 模型错了，应当改模型而不是加补丁。

   > **为什么是四个而不是三个**（我最初的口述漏了「诞生」）：当时把「诞生」算进了既有事实的
   > **副产物**——`turn × opened` / `assistant × progressed` / `artifact × added` 这些事实
   > **顺带**产出节点（`nodes_of`）。但压缩记录节点、`partial` 节点没有既有事实可搭车，
   > 它们的诞生必须自己是一条事实。**「诞生」也不是「断言」的特例**：`message.edited` 对
   > 不存在的 id 是**跳过**（位置无从谈起，见 `rebuild.rs` 的 `edited_node` 注释），
   > 把两者合成一个「upsert」会让窗口外的旧消息被塞到列表末尾——比不显示更糟。

2. **顺序反转：先落事实，列表是折叠出来的。** 写侧的形状从
   `读列表 → 改 Vec → 落库 → 补事实` 改成 `落事实 → 折叠 → 列表`。
   内存里的 `Vec<ChatNode>` 因此**降级**：从「正在被编辑的真相」变成「本轮草稿」——
   它是事实的一个**渲染**，不是可以写回去的东西。`replace_messages` / `append_messages`
   这类「把一份列表写进存储」的入口，要么**由事实驱动**（内部先落事实再落缓存），要么**不存在**。

3. **类型强制：让「改了列表却没落事实」变成编译错误。** 目标态是把写入口收成一个变更枚举：

   ```rust
   pub enum MessageChange {
       Added(cm::ChatNode),             // 诞生
       Edited(cm::ChatNode),            // 断言
       Removed(Vec<String>),               // 关闭
       Consolidated(Vec<cm::ChatNode>), // 取代
   }
   ```

   `PersistentChatSession` 上只暴露 `apply(MessageChange)`：它**在同一个函数里**落事实 + 更新缓存，
   两者不再可能分开。此时「改列表不落事实」不是纪律问题，是**类型系统里表达不出来**。
   过渡期（b3 完成前）由**守卫**顶上：`scripts/list-write-fact-audit.mjs` 枚举所有列表写入口，
   每处必须**要么**伴随一条事实落格调用，**要么**在白名单里带非空理由。
   **守卫是永久结构守卫，不是过渡品**：`pending` 棘轮的职责是钉住存量缺口，缺口归零后
   它的职责换成「结构还对吗」（`append_messages` / `v2_messages::*` 出 `write.rs` ⇒ LWF-001；
   `replace_all` 出 `write.rs` 而无寄存锚 ⇒ LWF-002）。这条职责是永久的：它守的是本条
   不变量「存储里的列表 == `fold(WAL)`」的**唯一入口**，而类型强制只管得住 `apply` 那一侧，
   管不住「有没有人绕开它」——「靠纪律守的东西迟早会漏」仍是本条的起点。

4. **S2.7-b3 的出口判据随之改变**：不再是「主读路径切到重建」，而是
   **「没有任何地方能改列表而不落事实」**。前者是手段，后者才是目标——只切读路径而不收写侧，
   等于把「两个 owner」从一个地方搬到另一个地方。

**理由**：

1. **模型对了，缺口就是可枚举的。** 拿四原语模型去套那 6 处缺口，**全部落在模型内**：
   恢复路删子树 = `Removed`（一棵子树）；abort 改父节点 = `Edited`；删旧子 = `Removed`；
   压缩记录节点 = `Added`；`partial` 节点 = `Added`；写侧裁剪 = `Removed`。
   **没有一个需要新原语**——这既是模型的验证，也说明「6 处没事实」不是 6 个独立疏漏，
   是**同一个机制缺失的 6 个表现**。
2. **顺序反转把「补」这个动作消灭掉。** 事实先落之后，「忘了补事实」不再是可能的失败——
   因为**没有「补」这一步**。这比「记得补」可靠得多，也是本条最值钱的一步。
3. **类型强制取代人工审计。** 6/10 的漏检率说明人工审计不适合当强制机制。它适合当**发现**
   机制（正是它找出了那 6 处），不适合当**保证**机制。
4. **与 [ADR-049](049.md) 同一条。**
   「一个事实只能有一个 owner」——顺序反转是它在**写侧**的落地：列表不再拥有真相，
   只拥有真相的一个视图。

**被否决的方案**：

- **维持「三原语」，靠 `message.edited` upsert 兜住诞生**：否决。见决策 1 的注——
  upsert 会把窗口外的旧消息塞到末尾（位置是错的），且掩盖了「诞生」与「断言」是两件不同的
  发生过的事。
- **维持现状 + 把纪律写进文档**：否决。那正是本条要治的病：10 处漏 6 处，文档拦不住。
- **只切读路径（b3 原定义），写侧不动**：否决。见决策 4——两个 owner 只是换了地方，
  切过去照样丢历史（写侧还在改缓存，重建看不到）。
- **先做类型强制、守卫不做**：否决。类型改造要动 `replace_messages` 的全部 10 个调用点，
  一次性做完会把 b3 前置与 b3 主体揉成一批、丢掉「独立可回退」；守卫能在**今天**就把存量钉住。
- **给 `message.added` 另起一个实体**：否决。它落在 `message × opened` 这格**空位**上，
  是 §6 网格里已预留的位置；另起实体等于把「同一件事」拆成两个名字。

**后果与不变量**：

- **存储层的变换也是列表变更，也必须落事实。** `prune_historical_tool_calls`
  （`SessionConfig::prune_tool_history`，默认 `true`）与 `max_messages`（FIFO 上限，默认 100）
  今天直接改列表、不落事实——切源后**被裁掉的节点会复活**。它们要么转成 `Removed` 事实，
  要么变成**纯读侧**的投影（不进存储）。**没有第三种**。
- 网格加一格（`message × opened` = `message.added`）——按 [PL-001 §6](../004-plan/001-核心架构.md "PL-001-核心架构")
  「新增事件 = 在网格里加一格」，是**数据变化不是机制变化**（J1 通过）。
- **不变量**：b3 完成后，存储里的列表 == `fold(WAL)`；b3 完成前，两者的差**必须**能被守卫枚举干净。
- WAL 仍 append-only；本条不引入任何改写历史的机制（「取代」仍是**多一条快照事件**）。
- 与 ADR-053 的边界：ADR-053 定**格子**（哪三个格子表达变更）；本条定**纪律与强制**
  （顺序、闭集、类型）。ADR-053 是「有哪些原语」，本条是「怎么保证只有这些、且真的被用」。

**落地形态与草图的三处差别**（有理由，不是漂移）：

1. **「诞生」是 `Born { nodes, carrier }` 而不是 `Added(msg)`。** 诞生多一个问题要答：
   「这条节点的承载事实由谁落？」——用户发言归 `turn × opened`、助手正文归收束格、工具结果归
   `artifact × added`，这些**不能**再落一条 `message.added`（一个事实只能有一个 owner）；
   只有「没有别的格可搭车」的节点（压缩记录等界面文本）才由 `apply` 落 `message.added`。
   答案收进 [`Carrier`] 枚举（`Runner` / `Here`），代价不对称写在其文档里：
   该 `Runner` 写成 `Here` 无害（「同 id 只认首次」去重），该 `Here` 写成 `Runner` 是
   **数据丢失**——所以拿不准时选 `Here`。
2. **「取代」不是 `MessageChange` 的变体。** 草图里的 `Consolidated(...)` 没有进枚举：
   取代是**列表级**原语，它的事实 owner 是执行口的令牌窗口（`v2_exec::consolidate_into_wal`），
   而压缩现场**不持令牌**——`apply` 若就地落 `session.consolidated` 会拿到 `NotTheWriter`，
   且那是静默的。所以取代保持独立入口（`replace_all` + `SessionContext::consolidated` 寄存 +
   `V2Request::consolidation` 落格），`apply` 只收节点级三原语。
3. **守卫同步升级为结构判定（v2）**。`list-write-fact-audit.mjs` 不再要登记行、不再有
   `pending` 棘轮，改为判**结构**：`append_messages` 与 `v2_messages::{added,edited,removed}`
   出了 `write.rs` ⇒ LWF-001；`replace_all` 出了 `write.rs` 而窗口内没有
   `consolidated = Some(...)` 的真实赋值 ⇒ LWF-002。待补缺口 4 处**全部经 `apply` 收口，
   pending 归零**——14 处写入口全部在类型强制之下，不再是守卫钉住的存量。
4. **守卫是永久结构守卫**。`scripts/gate.d/30-docs.mjs` 接线 `list-write-fact-audit`，
   口径是 v2（只发 LWF-001–002，不再要登记行）。理由：决策 4 的出口判据「没有任何地方能改列表
   而不落事实」**不是一次性验收项，而是持续成立的不变量**——类型强制把 `apply` 定成
   唯一入口，但「有没有第二条路」是结构性质，只有机械判定能**持续**保证（正是理由 3
   「人工审计适合发现、不适合保证」的同一逻辑，只是把保证方换成守卫）。
   配套：`30-docs.mjs` 的接线注释与守卫头注释同为 v2（登记形态、判据码段 LWF-001–002、
   寄存锚口径）。号段只有 001–002（见 `docs/006-ref/GATE_CODES.md`）——v1 的「登记表漂移」
   「同义反复」两码对应的形态不存在。
