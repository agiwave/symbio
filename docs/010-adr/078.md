## 决策

**背景**：[T-166](../009-task/166-上下文淡化层级未接入v2请求.md "T-166-上下文淡化层级未接入v2请求") 立项时
那句判断很轻——「v2 请求里的历史部分不经过 `build_request_view` 的三层裁剪」。核完前提
发现这句话**只说对了一半**，而错的那一半决定了处方：

- 三层**确实**在算。`chat_loop/inputs.rs::prepare_turn_inputs` 每轮照常调
  `build_request_view`（内容淡化 → 工具结果淡化 → 分层滑窗骨架化），产物也照常存进
  `TurnInputs`。
- 但只有其中一段被用上：`chat_loop.rs:713` 取的是 `request_view_prefix(...)` —— 三段**注入段**
  （记忆召回 / 就绪任务 / 委派者真源）拼成的那一条前缀。**历史部分的裁剪结果一个字也没进请求体。**
- 请求体的历史部分是运行器自己从事实源重建的：`turn_runner.rs:941` 的
  `store.range(Seq::new(0))` → 944–947 的轮次窗口 → 964 的 `render_messages(&snapshot)`。
  它压根不知道 `TurnInputs` 里还躺着一份裁剪过的视图。

所以成本照付、收益为零。按「先证前提、再定做不做」的口径，这是
「处方不成立、要求成立」：**要接线**这件事站不住，**让它们退场**站得住。理由不是「没人用」这么
弱——是**接不了**：

**一、接线与 [ADR-048a](048a.md) 结构上互斥。** 运行器每发一次请求都跑一遍双向完整性复核
（`turn_runner.rs:990` 的 `verify_prompt_fidelity(&snapshot, &base_messages, declared)`）。它的配对
判据是**正文精确相等**（`projection/prompt_fidelity.rs:295` 的 `m.text == text`）。三层淡化改的
恰恰是正文：

| 层 | 改写动作 | 接线后 `prompt_fidelity` 会报的缺口 |
|---|---|---|
| L1 内容节点淡化 | 超长正文/思考换头尾摘要 | `DroppedFromPrompt`（网格有全文、prompt 只有摘要）＋ `NoSourceInGrid`（prompt 的摘要在网格里找不到出处），**同一节点两条** |
| L2 工具结果淡化 | 老工具结果换头尾摘要 | 同上 |
| L3 分层滑窗骨架化 | ToolCall 参数与结果换成占位符 | 同上，且一条 ToolCall 连带它的结果节点 |

`declared` 那条豁免救不了：它是**一个** `Option<&str>` 槽位、按正文整串比对，只够放过「按设计
不进网格的那一条」（三段前缀）。N 条改写就是 N 条豁免，而这个模块开头自己写着「一个永远红的
守卫等于没有守卫」——**一个什么都放过的守卫同样等于没有守卫**，且更危险：它看上去还在工作。

**二、接线还要付一笔时序账。** 运行器环体 mid-turn 复用 `base_messages.clone()`
（`turn_runner.rs:1110`）追加本轮的 `exchange`。三层是「每请求重算」的（淡化阈值读 `request_round`），
接进去就得改成「每轮一次」，等于在 `render_messages` 之外**再造一条渲染路径**——正是
[ADR-048](048.md) 立项要消灭的那件事。

**三、三层本来就没有生产消费方。** 退役面逐个查过，没有一个是「删了会掉能力」：

- **L3 骨架化**的唯一作用是把窗口外的工具明细压成占位符，而它服务的旋钮
  `tool_context_window` 在 v2 **不存在**——`tools/mod.rs` 的模块文档自己写着「v2 口径：工具轮不设
  上限，整批工具结果全留」。一条为不存在的上限服务的裁剪。
- **`CapabilityToolContextRetention`（`All` / `LastN` / `LastOnly`）** 的唯一消费方就是 L3 的
  「声明保留策略的工具最新 N 次豁免窗口」。L3 走，它就没有第二个读方。
- **L1/L2 的阈值**（`compress_line_threshold` / `compress_keep_recent` / `fade_activate_rounds` /
  `fade_keep_recent_turns`）四个键，删掉之后 `SessionConfig` 里没有任何字段变孤儿。
- `build_request_view` 的 `viewer` 过滤是**死代码**：`context.messages` 进函数前已被
  `render_messages(&snapshot)` 按同一个 `viewer` 滤过一次。

**裁决一：三层淡化整族退役。** L1 内容节点淡化、L2 工具结果淡化、L3 分层滑窗骨架化，连同它们
的四个配置键、`context/window.rs` 整模块、`tool_result_guard` 里只被 L1 消费的
`summarize_tool_result` / `summarize_head_tail`、`tokenizer` 里只被它们调用的两个截断函数，一并删除。

**裁决二：`CapabilityToolContextRetention` 从 `symbio_core` 退场。** 删枚举、删
`CapabilityMeta::context_retention` 字段、删 `with_context_retention()` 与
`effective_context_retention()`。vdfs 的 `tool()` 工厂随之少一个形参。**这是 core 的公开面收缩**，
判据由 `capability/tests.rs` 的 `declared_enum_field_serde_roundtrip` 接手——它不测这个被删的
字段，它测「`CapabilityMeta` 上声明式枚举字段的 serde 往返 + 缺键不产默认值」这条**机制**，
载体换成仍然在册的 `risk: CapabilityRiskLevel`。载体换掉、机制不许跟着死。

**裁决三：`build_request_view` 改名 `build_request_sections`，签名从 11 个参数收到 3 个。**
名字里带 `view` 在暗示「它产出的是一份可替换的请求体」——这正是病灶的语言版本。它现在只做一件
事：把三段**本轮才成立**的读视图（长期记忆召回 / 就绪任务集 / 委派判定）排成 `Vec<ChatNode>`，
插入次序 委派 → 调度 → 记忆（各 `insert(0, …)`，读作 记忆 0 / 调度 1 / 委派 2），每段带
`meta.kind`。**只追加，不改写历史。**

**裁决四：v2 现存的上下文治理收为四条，共同点是「不改写投影正文」。**

| 机制 | 时机 | 为什么不算改写 |
|---|---|---|
| L0 工具结果守卫（`guard_tool_result`，8192 token/条） | **写入时** | 网格里存的就是裁剪后的那一份，投影与网格一致 |
| 轮次窗口（`context_messages` / `window_by_turn`） | 请求前 | 切的是**事件切片**（丢整轮），不是正文；`prompt_fidelity` 拿到的 `snapshot` 就是本切片，判据仍在同一基准上成立 |
| 压缩（`auto_compress` → `session.consolidated`） | 70% 水位 | **换基**：写一格事实，旧事件移入归档段。`prompt_fidelity` 有专门的取代格分支认领它 |
| 存储期工具链裁剪（`prune_tool_history`） | 保存时 | 物理删节点 + 归档，改的是存储态，不是视图 |

**否决的替代：**

- **把三层结果当 `base_messages` 接进去**：见背景一、二。要与 ADR-048a 并存，就得给
  `prompt_fidelity` 开一条「已知改写」豁免通道，而那条通道的粒度是正文精确匹配。**守卫一旦能
  被逐个正文地豁免，它就不再是守卫，是一份需要人维护的白名单。**
- **只接 L1，不接 L3**：「最小改动」听起来合理，但 L1 同样改写正文，同样撞判据；而它的收益
  （超长内容压短）已被 L0 的 8192 token 写入上限、轮次窗口与压缩水位三重覆盖，边际价值接近 0。
- **保留配置项、标 deprecated、行为上忽略**：配置项是**承诺**。留一个不生效的键，就是
  [ADR-074](074.md) 亲手记下的那种病——「配错与没配看起来一模一样，没有一条信号能区分」。
- **给 `SessionConfig` 加 `deny_unknown_fields` 以暴露旧键**：否决，与
  [ADR-072](072.md) / [ADR-074](074.md) 同一条先例——旧存档与用户手写配置里的残留键由 serde
  静默忽略，不做数据迁移；把一个能自动通过的启动变成「必须手改配置才能起」，代价远大于收益。

## 后果

- **配置面少五项**：`session/PLUGIN.yml` 的 `compress_line_threshold` / `compress_keep_recent` /
  `tool_context_window` / `fade_activate_rounds` / `fade_keep_recent_turns`，前端设置页据此渲染的
  五个控件，以及 session README §2 样例与策略表那两行随之删除。结构未开 `deny_unknown_fields`，
  旧配置里的残留键被静默忽略，无需迁移。
- **代码面净删**：`context/window.rs`（487 行）与其用例整文件删除；`context/view.rs` 由 297 行
  重写为「三段注入」约 60 行；`tool_result_guard` 的两个 `summarize_*`、`tokenizer` 的
  `truncate_head_chars_if_over` / `truncate_tokens` 删除；`chat_session` 的四个访问器、
  `plugin.rs` 的五个控件、`model_chat::Request` 与 `TurnRequest` 的 `tool_context_window` 字段删除。
- **能力矩阵少一列**：`scripts/facts/_capability.mjs` 不再抽取 `retention`，
  [RE-006 当前事实表](../006-ref/006-当前事实表.md "RE-006-当前事实表") 由 `node scripts/gen-facts.mjs` 重生成
  （26 插入 / 26 删除，只有表头与那一列变了）。
- **测试净 −31（1778 → 1747）**：`context/view.test.rs` 8 → 5（旧的三层判据换成五条注入段判据：
  `memory_section_is_prepended` / `readyset_section_sits_after_memory` /
  `delegate_section_lands_at_index_two` / `empty_sections_produce_nothing` /
  `every_section_carries_its_kind`）、`context/window.test.rs` 整文件、`capability/tests.rs` 2 → 1、
  其余 `model_chat` / `chat_loop/state` / `heartbeat` / `tokenizer` 各删随字段或函数退场的用例。
  棘轮基线 `rustTests` 落 1747，逐条归属见 `35-baseline` 的 `baseline-allow` 注。
- **v2 现在没有任何「请求视图级」的体积上界**（如实登记）。唯一的界是：L0 的
  `DEFAULT_TOOL_RESULT_TOKEN_CAP = 8192`（每条工具结果，写入时）、单条响应内
  `MAX_TOOL_CALLS_PER_RESPONSE = 32`、轮次窗口 `context_messages`、压缩水位 70%。长轮里出现 45 条
  `role=tool` 是**设计**而不是缺陷——[t55](../../e2e/cases/t55-multi-tool-round-memory.mjs) 记着
  丢掉它们的代价（模型反复重读同一份材料）。将来若实测超窗，正确的位置是 L0 上限与压缩水位，
  **不是**在请求视图里改写历史。
- **判据落在两处**：`prompt_fidelity` 每轮复核（既有，现在不再需要「请求体可能被改写」这条假设）；
  `build_request_sections` 的五条注入段判据钉住次序与 `meta.kind`（次序反了三段位置全部错位，
  而段位置就是模型读到的优先级）。
