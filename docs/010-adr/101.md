# ADR-101：内置插件的执行策略保留放开默认——安全边界在审批闸，不在用户偏好

## 决策

`local/policy` 的四个默认值**保持放开**（`autonomy = Full` · `workspace_only = false` ·
`max_actions_per_hour = 0` · `block_high_risk_commands = false` /
`require_approval_for_medium_risk = false`）。审计把这一处与授权表
[fail-closed](099.md "ADR-099") 并列为「方向相反」，核验后**不成立**：两者回答的不是同一个问题。

| 面 | 回答的问题 | 默认方向 | 依据 |
|---|---|---|---|
| 授权表 `authz::ROWS` | 这个**主体**能不能做这一类事 | **拒**（未登记 = 每个谓词为假） | 身份是部署事实；少一行必须是拒绝 |
| 审批闸 `approval_gate` | 这一次**调用**要不要用户批准 | **拦**（阈值缺省 `Medium`，High 风险工具需批准） | 风险由工具按参数自答（shell 按命令分级） |
| `local/policy` | 同一个主体内部，**用户自己的**执行偏好 | 放开 | 用户偏好不是安全边界；默认替他做主会有可见代价 |

## 为什么这条不是「默认不安全」

三类危险动作各有自己的闸，`local/policy` 不是唯一那道：

1. **高风险命令进不了执行**：`ShellCapability::risk_for` 按命令分级（`rm` / `sudo` /
   `chmod` / `curl` / 包装器等为 High），审批闸的缺省阈值是 `Medium` ⇒
   `High > Medium` ⇒ 需要用户批准；`mode = auto` 时走 `PERMISSION_DENIED`
   （`approval.test.rs::auto_mode_returns_permission_denied_not_confirm_card`）。
   `block_high_risk_commands` 是**用户批准之后**的额外硬拒，不是第一道闸。
2. **工具级风险照样过闸**：`vdfs_delete` 等 High 风险工具在注册收口点统一加壳
   （[ADR-068](068.md "ADR-068")），与 `local/policy` 无关。
3. **结构性拒绝不可关**：命令替换 / 引号未闭合等结构检查在 `split_subcommands` 里，
   不受白名单与默认值影响（fail-closed）。

## 为什么限流也保持 0

`max_actions_per_hour` 曾在 `100` 上留下实测事故：会话 `09d74431` 的 cmd 通道被锁死近一小时，
325 次调用被拒，全部是**自伤**——被拒的不是危险动作，而是正常工作。在拿到「正常长任务的
小时动作分布」之前，把默认值从 0 改成任何非零数都是**猜**；猜错的代价落在可用性上，
且只在长任务里出现（短会话测不出来）。

## 后果

- `local/policy` 的注释与配置项说明指向本条，不再复述「默认全放开」的理由
  （一个事实一个 owner）。
- 后续要收紧任何一项默认值，必须满足两条：**有实测分布**（不是感觉）、**单独成提交**
  （[PL-006 §0.3 纪律 1b](../004-plan/006-分步实施计划.md "PL-006-分步实施计划") 第 4 条）。
- 这条裁决不改变审计点名的另一半：熔断闸的时间基准是真缺陷，已按
  [T-186](../009-task/186-虚闸清偿批.md "T-186-虚闸清偿批") 修在调用点与判据签名上。
