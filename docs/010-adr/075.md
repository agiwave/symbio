## 决策

**背景**：[PL-014](../004-plan/014-单环一表收敛.md "PL-014-单环一表收敛") §5 步骤 6 的判据是
「每个插件可独立卸载且系统仍完整」，[T-167](../009-task/167-会话插件切分.md "T-167-会话插件切分")
把它接成任务并要求先审再切。审计读数（2026-10-18，全部 `file:line` 实测）里有一条判据一直没被
任何人检查过它**今天能不能成立**：

- **注册表侧不是障碍**：`session` 的所有能力行只从一个地方 `put`——
  `SessionPlugin::traverse`（`plugins/session/plugin.rs` 579–632：option / tool / mount / prompt /
  `capability_announce_configurable` 全在这一处）；而那张表**每次收集都是新建的**
  （`capabilities.rs:70` `DefaultToolVisitor::new()` 后遍历容器子插件）。一个插件从容器里摘掉，
  下一轮收集自然不再有它的行。**卸载不需要「这行是谁给的」这一列**。
- **真正的障碍是两条常驻循环**：`heartbeat/mod.rs:149`（`run_heartbeat_loop`，`loop { ticker.tick() }`）
  与 `transcript/inbox.rs:171`（`spawn_inbox_consumer`，`loop { drain_inbox_once() }`），加上
  `workdir/fs_watcher.rs:60`——三处都在构造点 `spawn`（`plugin.rs` 367–375），**不留 `JoinHandle`、
  没有取消位**，而 `SessionPlugin` **没有实现 `Plugin::stop`**（默认体是 no-op，
  `symbio_core/plugin/mod.rs:409`）。把它们从容器里 `shift_remove` 之后，任务仍在跑、
  仍持着 `Arc<SessionPlugin>`——**「卸载」今天只是从名册里划掉一个名字**。
- **第三个障碍是手柄形状**：五处 `Arc`/`Weak<SessionPlugin>` 捕获——`orchestrator/sink.rs:35`
  （`TranscriptSink` 的生产实现反过来调 `plugin.emit_session_state`）、`chat_loop/state.rs:454`
  （`CompressionEmitter`）、`:602`（`SupplementDrain`，它的 `target()` 把 `&SessionPlugin` 交给
  上下文面 `context/pipeline.rs:630`）、`tools/heartbeat_tool.rs:31`（`Weak` 再 `upgrade`）、
  以及 `plugin/vdfs_provider.rs:523` 的 `me()`（provider 侧任何一次「开跑一轮」都要把整个插件的
  `Arc` 交给驱动器）。全仓**没有** `dyn Plugin → SessionPlugin` 的 downcast，所以这一类耦合
  只有这一种形态，可以逐条消掉。

**裁决一：步骤 6 的施工顺序反过来——先让「卸载」这件事真的发生，再谈目录归谁。**
三条前置，按影响面从小到大，各自成批、各自有机器判据：

- **P1 常驻任务可取消**：两条 loop 与 fs watcher 改为持有取消位（`stop` 里置位并 `abort`/等待退出），
  `SessionPlugin` 实现 `Plugin::stop`。判据：一条 e2e 或守卫用例钉「停用 session ⇒ 心跳不再触发新一轮、
  收件箱消费者退出」。这是判据本身，不是重构口味。
- **P2 `Arc<SessionPlugin>` → 窄手柄**：sink / emitter / drain 三处只拿它们实际用到的那件事
  （落一帧、发一条压缩事件、抽一份补充），不再拿整个插件；`me()` 那一处把「开跑一轮」升成一个
  显式端口。判据：`session/` 里 `Arc<SessionPlugin>` 的捕获点从 5 处降到 0（构造点除外）。
- **P3 跨片调用走表或端口**：`heartbeat` 需要的是「列出会话 + 排一条收件」，`inbox` 需要的是
  「启动一轮」——这些在切分后必须经能力行或路由臂拿到，而不是同结构体的方法调用。
  判据：被切的那片不再 `use super::` 宿主的私有项。

**裁决二：不给 `CapabilityRow` 加「贡献者」列。** 这是一次典型的「拿 core 的变宽去付实现方的账」：
表逐次重建已经提供了卸载语义（背景第一条），加了列反而要再防它与实际 `put` 方不一致。
`CapabilityRow` 仍是两格（`name` + `payload`，`symbio_core/capability/row.rs:130`），
core 三格不动（CS-001 只降不升）。

**裁决三：留守名单——六段里只有一段现在被列为可切，两段永远不切。**

| 切片（实测含测试行数见 [T-167](../009-task/167-会话插件切分.md "T-167-会话插件切分") signal） | 裁决 | 理由（读代码得，不是口味） |
|---|---|---|
| 存储与生命周期（13,956） | **留守，永久** | 它是宿主的数据层：`store/` `transcript/` `chat_session/` 被驱动器、宿主外壳、上下文、心跳四方反向依赖，且各自只接 `Arc<SessionStore>` + 一份配置句柄（`plugin.rs` 453–463 一次性发出）。切成插件等于把一份持久化交给两个插件写——违反 ADR-044 的「同一事实一份持久化」。 |
| 记忆两腿 `memory.rs` + `v2_memory.rs`（非测试 716） | **留守，永久** | 会话记忆就是会话数据：`MEMORY.md` 落在**会话目录里**随会话一起删（`memory.rs` 模块头），事件记忆是 `v2-events.wal` 里的普通事件（`v2_memory.rs` 模块头）。`plugins/memory`（1,986 行，早已独立）持的是**工作区与智能体**两腿，与本层各写各的文件、互不干涉。 |
| 宿主外壳（7,894） | 留守 | `traverse` / `route` / provider / 配置面是「一个插件」这件事的全部声明位；声明不可再分。 |
| 分发与工具（5,766） | 随驱动器同片 | `v2_tools.rs` 是 `DispatchPort` 的插件侧落地、`tools/` 是执行基础设施（`tool_executor` 族 / `tool_result_guard`），它服务的就是那一圈环；session 在这段里只贡献一条能力行（`heartbeat`），而它属于心跳。 |
| 上下文与请求视图（6,250） | **暂不切**，排在 [T-166](../009-task/166-上下文淡化层级未接入v2请求.md "T-166-上下文淡化层级未接入v2请求") 与 P2 之后 | 它自己零 `SessionPlugin` 引用（是六段里最干净的），但边界正被两件事拉扯：`context/pipeline.rs:630` 经 `SupplementDrain::target()` 拿宿主去落库（P2 没做就切不开），而三层淡化的接入方式一旦改变这段的边界就跟着变（T-166）。 |
| **心跳（`heartbeat/` 501 + `tools/heartbeat_tool.rs` 198 + `heartbeat_state` 一格）** | **第一个切出去的就是它** | 最小的一片，且它把三条前置全都碰一遍：一条常驻循环（P1）、一条 `Weak<SessionPlugin>`（P2）、两个跨片调用——`list_sessions` 与 `enqueue_inbox`（P3）。第一次做「卸载守卫」在这片上练手，不要第一刀切驱动器。 |

驱动器（17,800）单独立片是**最后一步**：P1–P3 落地、且它对存储的触点核到只剩 sink 与句柄之后才动。
卸载它之后 session 只剩存储与生命周期——那才是「系统仍完整」的最强形态。

## 否决的替代方案

- **先搬目录，再补卸载能力**：被否。搬目录把「一个 `impl Plugin`」变成「五个」，但五处 `Arc` 捕获
  跟着变成**跨 crate 的循环引用**，P2 的成本上升而非下降；而且搬完之后门禁全绿也证明不了判据成立——
  PL-014 对这一步的原判据（独立卸载）恰恰是没有测试的那一条。
- **给 `CapabilityRow` 加贡献者列，卸载时按列逐行清除**：被否，见裁决二。表逐次重建已经提供了
  这个语义，加列是把一次性成本换成永久的一致性负担。
- **把 `memory` / `compact` 照 PL-014 §5 的字面清单切成插件**：被否（memory）与推迟（compact），
  理由见裁决三表。这不是把方案原清单当成别人的设计——PL-014 §0 立的尺是「形状是裁决（走 ADR），
  路径是数据」，本条就是按这把尺改路径，改动同时回写在该任务的出口里。

## 后果

- **步骤 6 从「搬目录」变成「补一条一直缺的能力」**：`Plugin::stop` 这条钩子在 P1 之前全仓只有
  `composite` 一个实现（`plugins/composite/composite.rs:227`），其余插件的常驻资源同批接受同一判据
  检查——可照的样板是 `gateway` 的 `stop_server()`（`plugins/gateway/plugin.rs:176`：持有句柄、
  `take()` 出来再停，配置热更时先停后启），只是它今天挂在配置变更路径上、没接到 `Plugin::stop`。
  **心跳与收件箱这两条不修，任何插件都谈不上可卸载**。
- **判据机械化**：一条守卫钉「卸载该片 ⇒ 该片的能力行在下一轮收集里消失、其余仍在，且宿主仍完整」。
  现有的 `composite/registry.test.rs`（uninstall 两条）与 `t17-plugin-assembly.mjs`（只测停用、
  且明写「停用不删目录」）都不覆盖「行消失 + 任务退出」，这条守卫是新增判据而不是复述。
- **core 不动**：三格 18/56/18 不变、机制键新增 0（v2 守恒律判据未放宽）；P1–P3 全部落在插件层。
- **T-167 的出口条件随之改**：原文三条（ADR 定边界 / 独立卸载判据 / 黑盒纪律 + 全绿）不变，
  但批次顺序按本 ADR 重排为 **P1 → 心跳片（练守卫）→ P2 → P3 → 上下文片（待 T-166）→ 驱动器**。
- **`impl: partial` 的档位说明**（残余逐条指得出归属）：**P1 已落地**——`SessionPlugin::stop`
  持停机位 + 唤醒 + 句柄册，两条 loop 在可取消点自己收尾、监听一次性交还，判据用例是
  `plugins/session/plugin.test.rs` 的 `stop_terminates_resident_loops`（停用后两条句柄都
  `is_finished()`）；**P2、P3 未动**，由
  [T-167](../009-task/167-会话插件切分.md "T-167-会话插件切分") 的后续批次承载，
  心跳片切出前两者必须落地——否则「独立卸载」在句柄之外的那两半仍然没有判据。
