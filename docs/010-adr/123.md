# ADR-123：账本是日志的一段，不是执行体交回的一份报告

## 背景

[T-249-执行体值返回账本](../009-task/249-执行体值返回账本.md) 要把 PL-016 §2.3 的
动作面形状落地：`run` 返回账本，装载期第 5 / 6 条之外的**运行期那一半**（「实际写入
逐条 ⊆ `ActorDecl.writes`」）按账本对账。方案的字面签名是 `Result<Vec<Fact>, ActorError>`。

回表时发现字面签名与现码的写拓扑有两处冲突，两处都不是「实现困难」，而是**形状本身
问错了对象**：

1. **执行体交回的 `Vec<Fact>` 是一份自报。** [ADR-118](118.md) 订正 2 已经把这条
   说清了：`append_all` **不是**领域事实落格的通道，执行体在执行中直接写同一个 store，
   账本只是**判定输入**。既然写不经过账本，账本就是执行体对「我写了什么」的陈述——
   漏报一条就对账不上一条，而漏报正是这条判据要拦的那件事。
2. **一个动作的写不止走 `TurnStep.store` 这一个句柄。** 本轮实测：`plugins/loop` 下
   30 处 `append` 散在 15 个文件（运行器 / 批次 / 阶段事件 / 工具派发 / 派生事实），
   而 `ACTOR_EXECUTE.writes` 名单里的 `session.consolidated`（`loop_rows.rs:99`）
   根本不是经派发器传入的 `store` 落的——它由
   `plugins/session/orchestrator/consolidate.rs:74` 在**会话侧**持令牌落格
   （「压缩入格是会话动作，事实源归档不在 core `Store` 面内」，见 `turn_exec.rs` 头注）。
   把**其中一个**句柄包成记账句柄，这一格就系统性少报；把 30 处收进一个记账句柄，
   改的是写拓扑而不是判据。

同一件事在派发器里已经有一个不撒谎的版本：`drive_steps` 的无进展守卫
（`turn_exec.rs:910` 取 `head`、`:928` 动作后比较日志长度）读的就是日志尾。

## 决策

1. **账本 = 引擎在动作前后各读一次日志，取尾部那段。** 执行体**不自报**写了什么：
   `run` 的签名取 `Result<(), ActorError>`（`Option<TurnOutcome>` 那一半的退役见
   决策 5，两半同批换的理由见决策 3 的改判注），派发器以
   `ledger = store.range(head)`（`head` = 动作前的 `store.head()`）得到这一次动作的实际写入集。
   PL-016 §2.3 的 `Vec<Fact>` 返回位由此改读为**引擎侧的账本读取**——两者服务的
   判据（⑤⑥ 与运行期对账、判据 14 的空账本 ⇒ `no_progress`）一条不减，
   只是判定输入从陈述换成事实。§2.1 草图里 `Ok(facts) => log.append_all(facts)`
   那一支随之作废：写已经在 store 里，引擎不再二次落格。
2. **运行期对账取「协议格豁免，领域格必须声明」的口径。** `ledger` 里每条领域事实名
   必须 ∈ 该执行体 `ActorDecl::writes`；协议五格（`request` / `sent` / `response` /
   `failed` / `retry`）豁免——它们本来就**不该**出现在 `writes` 里
   （`decl/mod.rs:400` 的 `ENGINE_ONLY_CELLS` 装载期已拦），粗端口期由 `port::dispatch` 在动作内部落，
   细端口接线后回到引擎在动作前后落，豁免名单不随端口粒度变。
   越界的形状 ⇒ 派发器不静默：**落一条停机收束格 `exhausted{why: "undeclared-write"}`
   并出声**（`plugin_warn` 带执行体名、越界的格名与行名），随后按现有停机路径退出
   ——**红**落在事实面，不靠 panic。
   > 本条原文写的是「落一条 `failed{port, id, why}`」，施工时改判：内环那笔债的键是
   > `turn=N`，**没有 `port` / `id` 可填**（`execute-turn` / `close-turn` 两行不带端口，
   > 端口的 `request`/`failed` 是外环 `chat_loop` 那一次 `port::dispatch` 的事），
   > 而收束判据只承认停机格——补一条没有 `(port, id)` 的协议 `failed` 既不收任何账，
   > 又会让这一轮**没有收束格**（`check_all` 报「未收束」，比越界本身更难定位）。
   > 今天兑现的形状就是 `TurnSession::exhausted`（引擎是写方，`produced_by` 是派发器）。
3. **`ActorError` 不是 `String`，住在动作面所在的部署层。** 现码动作面只可能因
   `AppendError` 失败，所以它今天是一元枚举（`ActorError::Append(AppendError)`）；
   这条不是凑形状：动作面的失败种类从此**只能靠加变体**扩展，每加一个变体都要回答
   「引擎为它落哪条事实」，而 `String` 版失败会把这件事藏进文本。停机判据仍在派发器
   （ADR-118 决策 7 不变）。
   > 本条原文写的是「`ActorError` **进机制层**」，施工时改判，理由是这条 ADR 自己的
   > 前置裁决 [ADR-119](119.md) 决策 1：**声明面进机制层、动作面留部署层**。
   > `ActorError` 是 `run` 的返回类型的一半，跟着 `run` 住在 `plugins/loop`；
   > 机制层既不产它也不读它（`ring::drive` 只裁决欠不欠），抬进 core 就是一个
   > **单消费方导出**——正是 `core-export-audit` C-003 要往下沉的那种东西，
   > 也是 `AGENTS.md`「不要拿机制面去付实现面的账」的那条形。判据的实质（不是 `String`、
   > 只能加变体）与类型住在哪一层无关。
   >
   > 同批把「`run` 的返回逐字取 `Result<(), ActorError>`」推到决策 5 那一批：
   > 一条动作既不交回 outcome 又不报错时，收束判断**必须已经有地方可读**（账本），
   > 两个通道分两批改会造出一个中间态的空档。动作面因此**一次**换掉两个通道，
   > 逐字形状就是 `Result<(), ActorError>`。
4. **执行体绑定表是派发器的输入。** `drive_steps` 收 `&'static [ActorEntry]`
   （生产传 `loop_rows::ACTORS`），派发器不再硬编码查表。这是判据 14 夹具的接缝：
   「动作写了零格 ⇒ `exhausted{no_progress}`」这条用例需要一个**注册在同名 `by` 上的
   空动作**才能造出来——没有接缝就只能永远说它「按构造不可达」，而 ADR-118 订正 3
   已经撤销那句免责。接缝是依赖注入，不是为测试留的后门：表本来就是部署事实
   （ADR-119 决策 1 的「动作面留部署层」）。
   > 这条接缝今天有两个使用者（`turn_runner.test.rs` 的 `actor_ledger_tests`）：
   > 空动作钉 `exhausted{no_progress}`，名单外的动作钉 `exhausted{undeclared-write}`。
   > 夹具的 `ActorEntry` 照抄生产声明（`loop_rows::ACTOR_EXECUTE`）、只换手法，
   > 名单一改两边一起改；两条都用反向自检确认过「把派发器那一步删掉就红」
   > （分别红在 `step_limit` 与越界那格的 `Duplicate`）。
5. **`run` 不再交回 `Option<TurnOutcome>`。** 收束的判据是账本里出现了停机格
   （`invariants::is_stop_fact` 同一口径），由派发器读；执行体把产出寄存在**本轮草稿**
   （`TurnSession`），派发器收工时从草稿取 `TurnOutcome` 交回调用方。这不动
   PL-016 §2.1 的 ②→③→④ 循环，只把 ADR-118 决策 4「执行体拿不到『下一个动作是什么』
   的选择权」补全成「也拿不到『本轮结束了没有』的判断权」。
   > 施工的两处补充，都是「判据在日志上」这一条推到底的结果：
   >
   > - **收束口径不止停机格。** 等待用户那一格是 `chat.assistant.progress` +
   >   `status:"pending"`——它**不是**停机格（本轮尚未了结，收束格留给恢复幕），
   >   但它是本轮的**最后一步**。派发器若只认 `is_stop_fact`，「等你回答」之后还会
   >   再选一次债、再跑一次模型往返，把等待跑成「又答了一轮」。判定因此是
   >   `turn_exec::ends_the_drive`：停机格 **或** 本轮的 pending 进展格。
   > - **账本收了工而草稿里没有产出**，是一种新的错账形状（有一条收束路径写了停机格
   >   却没寄存它）。派发器不猜一个产出——那等于把「没记账」读成「记了个空账」——
   >   出声（`plugin_warn` 带执行体名、那一格的格名与行名）并落
   >   `exhausted{unrecorded-outcome}`，与 `no_progress` / `undeclared-write` 同一处置形态。
   >   今天三条收束路径（`model` / `close` / `tools`）都寄存，所以这条分支按构造不落；
   >   它留在派发器里是因为**判据在日志上**之后，「日志说收了工」与「草稿说有产出」
   >   就是两件事，两件事一旦分家必须有人叫。
6. **对账第一次落地就抓到两处越界，两处的处置不同**（本裁决的施工期补充）：
   - `turn.supplemented`（轮内抽干的用户补充，`turn_exec/call.rs` 的
     `supplement_into_request`）——**它本来就该在 `ACTOR_EXECUTE.writes` 里**，
     名单缺这一条是登记遗漏。直接补声明，没有豁免。
   - `chat.assistant.final`——`execute` 确实写得出它（中止轮在 `stream::aborted`
     就地落收束格；续写幕旁路在 `run_execute` 里直接调收束），但**声明不了**：
     写进 `ActorDecl.writes` 就等于让 `close-turn` 的出口格同时是两个执行体的出口格，
     装载期的依赖图检查立刻以 `DependencyCycle ["close-turn","execute-turn","close-turn"]`
     拒绝整张表（[T-244-唤醒事实接入与resume旁路退役](../009-task/244-唤醒事实接入与resume旁路退役.md) 步 5 注①已经记过这一格）。
     处置是**把它写成表项上的过渡豁免**：`ActorEntry::transitional`，只在那一条 `by` 上
     生效，由用例 `the_transitional_exemptions_are_pinned` 钉死内容（名单变长即红），
     删除条件 = T-244 步 5b/5d 把这两条收束路径改走 `close-turn` 行。
     **不采用**的另一写法：在 `Next::writes_closed` 里加一条「`execute` 允许写 final」的分支——
     那会把豁免藏进谓词，名单不再可 diff，也不会有人因为删掉它而看到一条红。

## 被否决的方案

- **按字面实现 `Result<Vec<Fact>, ActorError>`，账本由执行体自报**：对账变成两份陈述
  互相印证（写了什么 vs 说写了什么），少报永远绿。PL-016 §2.3 的
  「实际写入逐条 ⊆ writes」问的是**实际写入**，日志尾是唯一能回答它的东西。
- **把 `TurnStep.store` 包成记账句柄**：只覆盖 30 个写点里走这一个句柄的那些，
  少报的形状与自报相同，只是把谎说得技术性。
- **判据 3「`Err` ⇒ 引擎写 `failed`」按字面补一条环形 `failed`**：现码已经落到位——
  整轮动作由 `chat_loop.rs` 经 `port::dispatch` 派发，动作失败时 `failed(port=turn)`
  由端口层落（`port.rs` 的 `DispatchError::Actor` 分支），模型 / 工具端口同一条路。
  而 `execute-turn` / `close-turn` 两行的 `until` 是 `turn_closed` 视图与
  `chat.assistant.final`（领域格），再落一条协议 `failed` 不收任何账，只是重复记账。
  本裁决因此把 T-249 判据 3 的适用范围记为**已兑现**，判据 5（四格写方收口）同理
  ——`grep` 全插件，协议格的写点只在 `port.rs`。这条从本批起不再是人工核对：
  `scripts/port-surface-audit.mjs` 的 **PTS-005** 判「协议四格的写点文件名单长度 == 1」
  （钉「唯一」而不是钉「是哪一个文件」，名单为 0 也判红——协议格没人写是环不转）。

## 后果

- T-249 的 `exit` 按本裁决重写：判据 3 / 5 记已兑现（附实测位置），判据 1 / 2 换成
  本裁决的形状（引擎读尾 + 运行期对账 + `ActorError`），判据 4 的空账本夹具随决策 4 的
  接缝一起做。T-245 口径 ④（判据 14 会红的夹具）与本批同一条用例，随 T-249 收口。
- PL-016 的正文按本裁决同批改文，不留两套形状：§2.3「`run` 返回的 `Vec<Fact>` 是写入
  账本」那段改读为**账本是日志的一段**；§2.1 草图的 `Ok(facts) => append_all(facts)`
  那一支作废，换成「读尾段 + 对账」；§2.6 契约 2 的返回类型与契约 6 的「比较日志头」
  随之改；§3.4 第 5 条补上判定输入（装载期查声明、实际写入那一半在运行期对账）。
- 粗端口期遗留的嵌套（`port::dispatch` 在执行体内部）不因本裁决改变：它是
  PL-017 §7.2 承认的过渡形状，端口行接回派发器（T-244 步 5b）后，`sent` 回到
  动作前、`response` / `failed` 回到动作后，账本读法不变。
- 施工分两批，各自 ≤300 行：**批一** = 决策 1–2 + 3 + 6（派发器读尾段对账、
  `ActorError` 换掉动作面的错误通道、PTS-005 把「四格写方唯一」钉成门禁、
  两处越界的处置）；**批二** = 决策 4–5（执行体表作 `drive_steps` 入参、
  空账本夹具、收束判断换到账本、`Option<TurnOutcome>` 通道退役）。
  决策 1 里 `run` 的逐字签名要等批二，理由见决策 3 的改判注。
