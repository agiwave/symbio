# ADR-123：账本是日志的一段，不是执行体交回的一份报告

## 背景

[T-249-执行体值返回账本](../009-task/249-执行体值返回账本.md) 要把 PL-016 §2.3 的
动作面形状落地：`run` 返回账本，装载期第 5 / 6 条之外的**运行期那一半**（「实际写入
逐条 ⊆ `ActorDecl.writes`」）按账本对账。方案的字面签名是 `Result<Vec<Fact>, ActorError>`。

回表时发现字面签名与现码的写拓扑有两处冲突，两处都不是「实现困难」，而是**形状本身
问错了对象**：

1. **执行体交回的 `Vec<Fact>` 是一份自报。** [ADR-118](118.md) 订正 2 已经把这条
   说清了：`append_all` **不是**领域事实落格的通道，执行体在执行中直接写同一个 store，
   账本只是**判定输入**。既然写不经过账本，账本就是执行体对「我写了什么」的陈述——
   漏报一条就对账不上一条，而漏报正是这条判据要拦的那件事。
2. **一个动作的写不止走 `TurnStep.store` 这一个句柄。** 本轮实测：`plugins/loop` 下
   30 处 `append` 散在 15 个文件（运行器 / 批次 / 阶段事件 / 工具派发 / 派生事实），
   而 `ACTOR_EXECUTE.writes` 名单里的 `session.consolidated`（`loop_rows.rs:99`）
   根本不是经派发器传入的 `store` 落的——它由
   `plugins/session/orchestrator/consolidate.rs:74` 在**会话侧**持令牌落格
   （「压缩入格是会话动作，事实源归档不在 core `Store` 面内」，见 `turn_exec.rs` 头注）。
   把**其中一个**句柄包成记账句柄，这一格就系统性少报；把 30 处收进一个记账句柄，
   改的是写拓扑而不是判据。

同一件事在派发器里已经有一个不撒谎的版本：`drive_steps` 的无进展守卫
（`turn_exec.rs:910` 取 `head`、`:928` 动作后比较日志长度）读的就是日志尾。

## 决策

1. **账本 = 引擎在动作前后各读一次日志，取尾部那段。** 执行体**不自报**写了什么：
   `run` 的签名取 `Result<(), ActorError>`，派发器以
   `ledger = store.range(Seq::new(head))` 得到这一次动作的实际写入集。
   PL-016 §2.3 的 `Vec<Fact>` 返回位由此改读为**引擎侧的账本读取**——两者服务的
   判据（⑤⑥ 与运行期对账、判据 14 的空账本 ⇒ `no_progress`）一条不减，
   只是判定输入从陈述换成事实。§2.1 草图里 `Ok(facts) => log.append_all(facts)`
   那一支随之作废：写已经在 store 里，引擎不再二次落格。
2. **运行期对账取「协议格豁免，领域格必须声明」的口径。** `ledger` 里每条领域事实名
   必须 ∈ 该执行体 `ActorDecl::writes`；协议五格（`request` / `sent` / `response` /
   `failed` / `retry`）豁免——它们本来就**不该**出现在 `writes` 里
   （`decl/mod.rs:400` 的 `ENGINE_ONLY_CELLS` 装载期已拦），粗端口期由 `port::dispatch` 在动作内部落，
   细端口接线后回到引擎在动作前后落，豁免名单不随端口粒度变。
   越界的形状 ⇒ 派发器不静默：落一条 `failed{port, id, why: "undeclared-write"}` 并
   带 `produced_by` = 派发器，随后按现有失败路径退出——**红**落在事实面，不靠 panic。
3. **`ActorError` 进机制层且不是 `String`。** 现码动作面只可能因 `AppendError` 失败，
   所以它今天是一元枚举（`ActorError::Append(AppendError)`）；这条不是凑形状：
   动作面的失败种类从此**只能靠加变体**扩展，每加一个变体都要回答「引擎为它落哪条事实」，
   而 `String` 版失败会把这件事藏进文本。停机判据仍在派发器（ADR-118 决策 7 不变）。
4. **执行体绑定表是派发器的输入。** `drive_steps` 收 `&'static [ActorEntry]`
   （生产传 `loop_rows::ACTORS`），派发器不再硬编码查表。这是判据 14 夹具的接缝：
   「动作写了零格 ⇒ `exhausted{no_progress}`」这条用例需要一个**注册在同名 `by` 上的
   空动作**才能造出来——没有接缝就只能永远说它「按构造不可达」，而 ADR-118 订正 3
   已经撤销那句免责。接缝是依赖注入，不是为测试留的后门：表本来就是部署事实
   （ADR-119 决策 1 的「动作面留部署层」）。
5. **`run` 不再交回 `Option<TurnOutcome>`。** 收束的判据是账本里出现了停机格
   （`invariants::is_stop_fact` 同一口径），由派发器读；执行体把产出寄存在**本轮草稿**
   （`TurnSession`），派发器收工时从草稿取 `TurnOutcome` 交回调用方。这不动
   PL-016 §2.1 的 ②→③→④ 循环，只把 ADR-118 决策 4「执行体拿不到『下一个动作是什么』
   的选择权」补全成「也拿不到『本轮结束了没有』的判断权」。

## 被否决的方案

- **按字面实现 `Result<Vec<Fact>, ActorError>`，账本由执行体自报**：对账变成两份陈述
  互相印证（写了什么 vs 说写了什么），少报永远绿。PL-016 §2.3 的
  「实际写入逐条 ⊆ writes」问的是**实际写入**，日志尾是唯一能回答它的东西。
- **把 `TurnStep.store` 包成记账句柄**：只覆盖 28 个写点里走这一个句柄的那些，
  少报的形状与自报相同，只是把谎说得技术性。
- **判据 3「`Err` ⇒ 引擎写 `failed`」按字面补一条环形 `failed`**：现码已经落到位——
  整轮动作由 `chat_loop.rs` 经 `port::dispatch` 派发，动作失败时 `failed(port=turn)`
  由端口层落（`port.rs` 的 `DispatchError::Actor` 分支），模型 / 工具端口同一条路。
  而 `execute-turn` / `close-turn` 两行的 `until` 是 `turn_closed` 视图与
  `chat.assistant.final`（领域格），再落一条协议 `failed` 不收任何账，只是重复记账。
  本裁决因此把 T-249 判据 3 的适用范围记为**已兑现**，判据 5（四格写方收口）同理
  ——`grep` 全插件，协议格的写点只在 `port.rs`。

## 后果

- T-249 的 `exit` 按本裁决重写：判据 3 / 5 记已兑现（附实测位置），判据 1 / 2 换成
  本裁决的形状（引擎读尾 + 运行期对账 + `ActorError`），判据 4 的空账本夹具随决策 4 的
  接缝一起做。T-245 口径 ④（判据 14 会红的夹具）与本批同一条用例，随 T-249 收口。
- PL-016 §2.3 的 `ActorEntry.run` 签名与「`run` 返回的 `Vec<Fact>` 是写入账本」那段
  补文按本裁决订正（同批改方案正文，不留两套形状）；§2.1 草图的 `append_all` 那一支
  随之作废。§3.4 第 5 / 6 条的判定输入从「交回的账本」改读为「日志尾那段」。
- 粗端口期遗留的嵌套（`port::dispatch` 在执行体内部）不因本裁决改变：它是
  PL-017 §7.2 承认的过渡形状，端口行接回派发器（T-244 步 5b）后，`sent` 回到
  动作前、`response` / `failed` 回到动作后，账本读法不变。
- 施工分两批，各自 ≤300 行：批一 = 决策 1–3（读尾 + 对账 + `ActorError`）；
  批二 = 决策 4–5（表注入 + 空账本夹具 + 收束判断换到账本）。
