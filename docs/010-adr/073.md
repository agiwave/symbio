## 决策

**背景**：[PL-014 §5](../004-plan/014-单环一表收敛.md "PL-014-单环一表收敛") 步骤 5b 要清零
`TurnState` 的簿记字段。逐字段做读写矩阵（谁读它、谁能改它）后，结论是这些字段
在 v2 里**已经不是数据**：

- **工具轮次不经这里**：[ADR-072](072.md "ADR-072") 立的那条事实——工具在 `execute_turn` 内部
  经 `DispatchPort` 一批批跑完，`chat_loop` 一轮只经过一次请求。于是没有任何时刻会往
  `TurnState` 上递增轮次：`tool_rounds` 恒 0、`in_flight_tools` **连写方都没有**（恒空集合）。
- **只写不读的两格**：`progress_reports`（汇报次数）、`model_elapsed_ms`（模型耗时）各有一处
  自累加，全仓没有读方——它们记录的是没人看的历史。
- **恒不命中的分支**：闸门的 `WaitForTools` 判的就是那个恒空集合；中途汇报的旧入口
  `report_if_due` 头一句是「`tool_rounds == 0` 就不说」，于是**恒不汇报**——真实的汇报判定
  早已由 `RoundProgress`（挂在运行器轮边界回调上）承担，那三格只是它留下的一份影子。

**裁决**：四条一起删除，闸门坍缩成两态（`Proceed` / `Exit`）。删除的名册（符号级）：
`TurnState::in_flight_tools`、`TurnState::progress_reports`、`TurnState::model_elapsed_ms`、
`Gate::WaitForTools`、`chat_loop::progress::report_if_due`，以及 `chat_loop.rs` 装配处为
`model_elapsed_ms` 计时的 `v2_started` 与它的累加语句。

「**不完整不唤醒**」这条不变量没有被放弃，它换了承担者：**运行器的环体只在把本批工具结果
接进 `exchange` 之后才发下一次请求**（`turn_runner.rs` 2e）。结构上带半个批次出门不可能发生，
所以它不需要一个运行时集合来守。

**否决的替代**：

- **把 `TurnState` 搬进 `Arc<Mutex<_>>`，让轮内计数真的活起来**：为三个没人读的字段翻整个主循环
  的借，换来一份「轮内 / 轮间」两处都要同步的数。轮内的真源已经有 `RoundProgress`，加锁只会
  造出第二个。
- **留着 `WaitForTools` 当作将来异步工具的「形状预留」**：形状不是预留出来的。真做异步分发时
  需要的是**分发口的完成协议**（谁在等、等多久、超时怎么报），那不是一个只有 `chat_loop`
  一侧能观察到的枚举值——现在留着它，读代码的人得到一个「工具在途有判据」的假承诺。
- **把汇报判定挪回 `chat_loop` 的轮顶**：那是引入运行器之前的位置，那里一次请求只经过一次，
  「又走完了一轮」这件事在轮顶根本不成立（成立的地方在批次边界，即回调处）。

## 后果

- **闸门只剩退出条件**：`gate_turn` 从此只回答「这轮要不要停」，不再回答「这轮能不能 start」。
  [AR-015-core-loop](../../symbio/src/plugins/session/docs/015-core-loop.md "AR-015-core-loop")
  §2.1 / §4.1 的形状描述随之改；「启动条件是显式判据」那句在 [PL-014 §1.3](../004-plan/014-单环一表收敛.md "PL-014-单环一表收敛")
  的诊断里是**改造前**的病灶描述，不随本裁决作废。
- **两条用例随之删除**（它们的被测对象整体退场，不是覆盖丢失）：`in_flight_tools_block_wakeup`、
  `wait_for_tools_takes_priority_over_exit_conditions`。`gate_turn` 的两条真实退出条件
  （软上限优先于中止）与放行仍由同文件的其余用例钉住；棘轮基线 `rustTests` 1758 → **1756**。
- **`RoundProgress` 成为轮次与静默时钟的唯一持有者**：`progress.rs` 里「同一轮内两份数」的
  登记作废——死字段没了，剩下的那份就是唯一那份。
- **`TurnState::tool_rounds` 留下，但它仍然恒 0**：它的读方是软上限判定、fade 判定与
  抽干分支三处，都是**语义上还在等真实轮数**的地方。清零它要一并裁决 `fade_activate_rounds`
  / `max_tool_rounds` 两个旋钮归属（哪一个该拿到真实轮数、该由谁喂），那是下一步的裁决，
  不在这一批。
- **抽干分支与静默时钟的一处漏**（同批发现，不在本裁决范围内处置）：「抽干会把静默时钟归零」
  现在只写在 `chat_loop.rs` 的抽干分支里，而该分支前提恒假 ⇒ 用户补充到达后可能立刻抢报进度。
  登记在 [T-165](../009-task/165-控制面收敛.md "T-165-控制面收敛") 的 5b 条；与之同族的
  「三层淡化未接入 v2 请求」曾登记在 [T-166](../009-task/166-上下文淡化层级未接入v2请求.md "T-166-上下文淡化层级未接入v2请求")，
  已由 [ADR-078](078.md) 裁决退役（接线与投影判据互斥，见该文）。
