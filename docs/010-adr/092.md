## 决策

**本阶不实现 A2A（Agent2Agent）对外互操作，也不发布 Agent Card。** 内部的多主体与对等协商
（[PL-001 §12](../004-plan/001-核心架构.md "PL-001-核心架构")）继续按自己的事件模型走，
**不**为将来可能的 A2A 预留抽象。等出现第二个**真实对端**（不是演示、不是自家另一个实例）
时再开这一批。

## 背景

[RE-008 §1](../006-ref/008-行业能力前沿参照.md "RE-008-行业能力前沿参照") 记录的现实是：
A2A v1.0 已生产就绪、150+ 组织接入。而本仓现状：**无 Rust 实现、无 Agent Card、无对外协商端点**。
若把「高阶智能体平台」理解成「能与外部智能体互通」，这确实是入场券。

## 为什么现在不做（三条，按强度排）

1. **没有对端，协议实现就只是自测。** A2A 的价值全在**跨厂商语义**：card 里声明什么、
   任务状态机怎么对齐、错误怎么传播。这些只有在与一个**实现不同、利益不同**的对端
   联调时才会暴露。对着自己写的 mock server 跑通 100 条断言，证明的是「我按我理解的
   A2A 实现了」，不是「我能与别人的智能体协商」——这恰恰是本仓反复警惕的
   「验证器自 mock 的扩散」形态。
2. **它会往核心灌进一批不由本仓演进的概念。** 协商需要引入对方的状态机词汇、鉴权模型、
   能力发现格式。按 [PL-001 §8](../004-plan/001-核心架构.md "PL-001-核心架构") 的取值准入，
   每一个都得回答「谁在生产侧消费它」；在只有一个实现方时，答案全是「将来会有人」——
   那正是「只写不读的值」的典型来源。
3. **真正的缺口不在这里。** [RE-008 §4](../006-ref/008-行业能力前沿参照.md "RE-008-行业能力前沿参照")
   的差距对照里，本仓最硬的两块是**沙箱执行**（最大安全缺口）与**长时程可靠性度量**。
   把同一份力气先放到 A2A，是用「看起来更平台」换掉「实际上更安全 / 更可测」。

## 代价（明写）

- **对外叙事受限**：不能说「支持 A2A」。只能说「内部多主体已按事件模型落地，
  跨平台互操作未接」——[RE-008 §4](../006-ref/008-行业能力前沿参照.md "RE-008-行业能力前沿参照")
  的「工具协议」行已经这么写。
- **将来接入会更贵**：等有真对端时，能力发现 / 任务状态机 / 鉴权这三处要一次补齐，
  而不是渐进长出来。这是**推迟**的代价，不是**取消**的代价。
- **生态位可能被占**：若目标用户群体在两年内普遍以 A2A 作为接入前提，本仓会被挡在门外。

## 失效边界：命中任一条就回来重开这一批

1. 出现**第一个真实外部对端**（客户 / 合作方 / 生态伙伴），且对方要求走 A2A；
2. 产品定位从「本地平台」改为「平台间协作节点」（那时 A2A 不是加分项，是定义）；
3. 内部多主体已经稳到可以对外暴露，且**有第二个实现**能对着联调。

## 最小切口（真要做时，从这里开始，不要一次做全）

先做**只读一半**：发布 Agent Card（声明能力与端点）+ 接收任务 + 回事件流；
**协商**（双向状态机对齐、任务移交、子任务分派）留到第二个对端提出真实需求时。
理由：card + 单向任务流能在不引入对方状态机词汇的前提下验证「我的能力描述是准的」，
而这一条本身就是有价值的判据——**声明与实现不一致**是最容易出、也最该早发现的错。

## 后续

- 本裁决不阻塞任何内部多主体工作：[PL-001 §12](../004-plan/001-核心架构.md "PL-001-核心架构")
  的对等承诺、递归子智能体、声誉投影都按原计划走，它们与 A2A 无关（**协议是外壳，不是模型**）。
- 若命中失效边界，新 ADR 必须同时给出「对端是谁、联调判据是什么」——没有对端的 A2A
  实现一律按上面第 1 条否决。
