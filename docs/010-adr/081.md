## 决策

**背景**：[ADR-075](075.md "ADR-075") 给驱动器切片（[T-167](../009-task/167-会话插件切分.md "T-167-会话插件切分")
批次 6）留了一句前置——「它对存储的触点核到只剩 sink 与句柄」。逐条核对证明这句话
**字面上不成立**：`PersistentChatSession` 本身就是存储域对象（会话引擎），
拿到句柄与调用存储域构造器在代码里是同一件事；按字面执行只会得出一条永远满足不了的判据。
同一次核对还数出十处「绕开句柄自己上手」的形状，并把两件事留成未答问题：这十处该收敛成一条
P4、还是某些形状本来就该留在驱动器；若立 P4，它的判据取哪种形式。本裁决一起答掉。

**裁决一：P4 成立，判据是「四个不」，十处触点逐条定归属。**

驱动器（批次 6 那片：`chat_loop*` + `turn_runner` + `turn_exec` + `orchestrator*` 中除手柄
实现的部分）在生产代码里满足：

1. **不解存储**——`store::resolve_store` 的调用点只许在收敛手柄 `Convergence` 上；
2. **不绕开口柄构造会话**——`PersistentChatSession::new` / `::detached` 在驱动器侧只许
   经 `Convergence` 的工厂调用（含 ephemeral 臂），外加**一处具名豁免**：
   `chat_loop/io.rs` 的降级回退；
3. **不把存储内部对象拿回家**——`Arc<Mutex<Transcript>>` 只许作为转写域自己的字段存在；
   驱动器经借来的 `ActiveSessionState` 做收敛操作（sink 落一帧、broadcast 发状态、consume
   清在途）**不在禁形之列**——读数当日它们已记为合规的半边，禁的是把内部对象的 `Arc`
   抄成驱动器侧自己的字段（那等于把它钉在状态生命周期之外）；
4. **不把存储侧「两步」自己拼**——「取批 + 合并 + 成形」与「枚举子会话 + 寻址 + WAL 投影 +
   回落」这类多步编排，在存储侧落成**一个入口**，驱动器只调那一下。

十处归属（处数与落点只裁走向，不重排表）：

| 触点 | 裁决 | 归属理由 |
|---|---|---|
| `orchestrator/entry.rs` `TurnLauncher::open_session_handle`（三臂构造） | **收敛** | `TurnLauncher` 已持 `convergence`，却又自带一整条构造路径——这是 P2 判据没抓到的**第二条构造口**（P2 数的是 `Arc<SessionPlugin>` 捕获，不是构造点）。三臂整体并入 `Convergence` 工厂：持久臂 `Convergence::open_chat_session` 已经写着（构造同款、依赖同款），两个 ephemeral 臂只要的一份配置快照 `Convergence` 也持有（`config` 是同一只 `Arc<RwLock<SessionConfig>>`）。launcher 侧不留同名转发（3c-1 的「插件上不保留同名转发」同一条纪律）。 |
| `chat_loop/io.rs:108` 缺句柄回退构造 | **保留，登记为豁免** | 它是「句柄交付失败 ⇒ 降级内存会话、不阻断对话」契约的另一半天（交付点在 `orchestrator/entry.rs` 的 `start_turn`，失败只记日志继续）。它只依赖存储域的**声明构造**与默认配置，不碰 store。把它改成 fail-fast 等于重写一条已成立的契约。 |
| `orchestrator/broadcast.rs:114` `Convergence::get_store` | **保留，并登记归属：`Convergence` 属留守层** | 手柄的四个字段（存储格子 / 目录 / 配置 / 活跃名册）**全是**「存储与生命周期」那一段的所属物；它今天物理住在 `orchestrator/`，只因 3c 那批把 owner 从插件搬下来，不代表它是驱动器的一部分。搬目录随批次 6b 切片与留守层合流——提前换目录不等于卸载能力（[ADR-075](075.md "ADR-075") 裁决四同一条理由）。 |
| `chat_loop/state.rs:111` `SessionContext.session` | **保留** | 这就是句柄通道本身（`SESSION_HANDLE` 交付与读回），判据里「句柄」指的就是它。 |
| `chat_loop/state.rs` `TranscriptWriterBridge` | **收敛** | 桥把 `Arc<Mutex<Transcript>>` 抄成自己的字段——裁决一第 3 条禁的正是这个形状。桥的全部工作是「锁转写 → apply」，而 `Transcript` 是转写域类型 ⇒ 桥整体迁进 `transcript/`，对 core trait 的实现一行不削，只是换住址。 |
| `chat_loop/state.rs` `SupplementDrain::take_inbox_batch_sync` 桥 | **收敛** | 见裁决三。 |
| `chat_loop/delegate.rs` `list_sub_sessions` / `load_sub_session` | **保留** | 句柄自身的方法，合规——「经句柄读别的会话」与「自己开存储」是两件事，前者是转写 API 的既定面。 |
| `chat_loop/delegate.rs` 的 `paths::session_dir` 寻址 + `worker_progress::progress_from_wal` + 归属复核 + 旧读法回落 | **收敛** | 这是**存储的读侧投影在驱动器里跑**，且方向已经拧了：`worker_progress.rs`（存储侧模块，直接开 WAL）返回 `chat_loop::delegate::WorkerProgress`（驱动器类型）——存储层反向依赖驱动器。整组（类型 + `progress_of` + 编排）反向搬进 `worker_progress.rs`，对外的入口是 `worker_progress::for_session(&session)`，`chat_loop` 侧只调那一下；`delegate.rs` 只留委派判定本身。 |

**裁决二（问题②的答案）：P4 的判据形式是 grep 式（依赖方向），不是卸载；卸载判据留在
批次 6b 的切片面上。** P4 不是一片可卸载的代码——它不贡献能力行、无常驻任务，照
[ADR-075](075.md "ADR-075") 裁决三订正 ② 的口径，对它套卸载形式就是一个永远为真的空判据。
机器判据两条，都在 6a 落地批当场可验：

- **禁形清零**：驱动器文件（生产代码，测试随迁）grep
  `store::resolve_store` / `PersistentChatSession::new(` / `PersistentChatSession::detached(` /
  `transcript::supplements::merge_supplements` / `transcript::inbox::take_inbox_batch_sync` /
  `worker_progress::progress_from_wal` / 把 `Mutex<…Transcript>` 持成字段，命中 = 0；
- **豁免名册只许一条**：`chat_loop/io.rs` 的 `PersistentChatSession::detached`（缺句柄回退），
  豁免的期限就是 6b——切片那一刻这条回退要么随驱动器找到新的合法形态，要么被显式废除。

批次 6b 的真判据不受影响：驱动器贡献 turn 的 spawn 与消费循环，用**卸载形**——
停用 ⇒ 不再开新一轮、在飞的轮在有限时间内收敛（`Convergence` 的存储格子比插件活得久
正是为这半设计的，3c-1），且存储侧读写照常。

**裁决三（问题①里 supplements 那一半的答案）：补充消息的「到达」归存储，驱动器只
「要一批」。** 队列与变更通知都在存储侧（`ActiveSessionState::inbox` 与
`VdfsChangeSubscriptions`），驱动器掌握的只有**要的时机**——工具循环批次边界（`turn_runner`
的 2f 挂点）。所以今天由 `SupplementDrain` 在驱动器侧拼的两步（`transcript::inbox::
take_inbox_batch_sync` 取批 + `transcript::supplements::merge_supplements` 合并）连同那个
手写的「按 `meta.supplement*` 拆回字段」的成形段，一并落成存储侧的**一个**同步入口，
返回类型 `DrainedSupplement` 随入口迁进转写域；drain 手柄退化成「持着那三样、调一下」。
读件语义不变（S-011 钉的 2e < 2f 行序与静默时钟归零条款都不动）。

**否决的替代方案**：

- **不立 P4，切片时把这十处连同驱动器一起搬**：被否。这与批次 5 被撤销是同一条理由——
  把环上的触点搬进新插件是换位置不是收敛；而 `worker_progress` 那条反向依赖不先掰正，
  6b 切完存储层与驱动器仍是环。
- **判据按字面「只剩 sink 与句柄」执行**（回退删掉、构造一律不许出现在驱动器）：被否，
  见背景段——句柄就是存储对象，字面判据不可能满足，硬执行只会逼出更扭曲的绕法。
- **把 `Convergence` 提前搬进存储目录**：被否。归属先登记、搬家等 6b（裁决四先例：
  判据在切片那一刻才咬人，提前搬是把一次改动拆成两次，代价由全部消费方付）。
- **`io.rs` 的回退也一并收敛成「经手柄注入降级会话」**：被否。注入需要 `ctx` 里多带一个
  工厂闭包，而那个闭包的依赖（配置 + 默认值）正是回退本来就有的；为消灭一个豁免位把
  契约面加宽，是给判据凑数。

## 后果

- 批次 6 从此分两批：**6a = P4 收敛**（裁决一/三的逐处搬家与入口合并，行为不变），
  **6b = 真切片**（驱动器成片 + `Convergence` 归位留守层 + 原批次 5 背的两块 + 共享词汇
  四类归属一起定）。6a 判据的当场核验记录进
  [T-167](../009-task/167-会话插件切分.md "T-167-会话插件切分") 处理过程，不另建守卫脚本
  （P2/P3 同口径：grep 核对 + 台账，形态稳定后再考虑进门禁）。
- **两处活指针同步修**：`tools/tool_executor/task_decl.rs` 与
  `transcript/supplements.rs` 的注释指向不存在的 `context/window.rs::apply_layered_sliding_window`
  ——doc-symbol-audit 只核符号名不核文件路径，这正是批次 4a 登记过「假地址」那一段。
- **core 三格 18/56/18 不动**；机制键新增 0。6a 不改任何目录归属（那是 6b 的事），
  改的是文件的住址与入口的形状。

## 落地形态

裁决二的豁免名册**不存在**：`chat_loop/io.rs` 整文件在 `plugins/loop`，
「缺句柄回退」的驱动器侧形态没有位置——会话句柄由 `TurnDispatch.facts` / `TurnSession`
承载，缺事实源即 `Internal`（`session/plugin/run_actions.rs` 的模块头写明「驱动器侧
没有豁免」，ADR-082 裁决五）。驱动器文件侧的 grep 判据对象是：
`plugins/loop/**` 的 import 根由 `plugin-entry-audit` 的 **E-013** 钉在 ADR-083 §4 闭族内
（取代本裁决落地当日对 `store::resolve_store` 等六个符号的逐条 grep），`crate::plugins::session`
同时由 E-009 与 E-013 两条覆盖。
