# ADR-112：跨栈清单与载荷不另立自述面

## 背景

[T-215](../009-task/215-路由与载荷契约单源化批.md "T-215-路由与载荷契约单源化批") 的两项问的是
同一件事：**地址与载荷这两类跨端事实，能不能从「人工清单」变成「生成物」**。原报告（02 建议 3 / 4）
给的路线是给 `Plugin` trait 加一个 `manifest()` 成员，让插件在运行期自述自己的路由，
守卫随之从「守人工清单」升级为「守清单与代码一致」。

本仓纪律：给 core 的 trait 加成员是**变宽**，「收窄不需要批准，变宽需要论证」
（[ADR-055](055.md)），CS-001 把三格形状冻成只许降。所以这条路线必须先答一个问题：
**自述面买到的一致性，是不是现有的代码投影给不了的？**

## 判据（两项共用的一问）

> **一个跨栈事实要不要「生成化」，只问它有没有第二个 owner。**
>
> - 有第二个 owner（多处必须相等）⇒ 收成**一处代码事实** + 生成物 + 一致性判据；
> - 只有一个 owner（一方下发、一方消费）⇒ 消费方的镜像由**字段级镜像判据**看守，
>   不建第二处自述。

「再补一份自述」不是纪律的加强，而是**把复述制度化**：多一处声明就多一个 owner，
而守卫的任务从此变成「比对两份真相」，不是「代码即真相」。

## 决策

### 1. 不给 `Plugin` trait 加 `manifest()`（不做，登记理由与撤销条件）

1. **地址清单的唯一 owner 已经是代码**：`route()` 的 `match` 臂 + 臂上一句职责注释，
   由 `scripts/route-facts.mjs` 单点提取（`extractRouteArms` / `controlPlaneRoutes` /
   `dispatchableRoutes`），三个下游共用同一份抽取：RE-006 §2.3、`routes.gen.ts`、
   `plugin-entry-audit` 的 E-002 / E-005 / E-012。
   ⇒ 一致性判据**已经在位**，且它比对的是「代码 vs 代码的投影」，不是「代码 vs 人工清单」。
2. **加成员造出的是第二处声明**：`manifest()` 返回的路径列表与 `match` 臂没有任何编译期或
   运行期关系——两边不一致时既编译得过、也跑得起来，于是必须再写一条守卫去比对两者。
   **用一条新判据去守一个新造的事实，净收益为负**（[ADR-070](070.md) §决策 2 反对的正是这种
   「值已有产者、又抄一份」的形态）。
3. **代价摊在所有人身上**：`Plugin` 的生产实现 21 个，`fn` 成员总数是 CS-001 的第二格，
   加一个成员需要一条 `core-shape-allow` 与全部实现方各写一份清单；而它换来的信息静态提取已全部有。
4. **运行期自述在 CI 里反而更贵**：本批的判据全部是**源码级**的，门禁因此不需要装配插件树；
   改用 `manifest()` 意味着 CI 必须先跑起一次装配（21 个插件、含 gateway / telegram 的 IO 副作用），
   才能拿到那份清单——把静态可判的东西换成运行期才能判的，是退化。
5. **动态分发覆盖不到，而那正是它最难的地方**：`local/<工具短名>`、`web/<工具短名>`、
   `vdfs/<操作>`、容器挂载名没有可静态枚举的臂。这份边界**按裁决不进生成物**
   （[T-183](../009-task/183-质量与机制清偿总批.md "T-183-质量与机制清偿总批") §5-1），
   `manifest()` 同样只能要么漏、要么在运行期枚举——后者等于承认「清单要跑起来才知道」。
   `E-012` 用**逐行豁免 + 写明运行期来源**处理这类常量，而不是给脚本加白名单表，理由相同。
6. **`E-006` 只判前缀不是钝化，是分工**：人工权威清单里必须能出现**已退役**的地址
   （`session/append`…），否则迁移记录无从写起；「整条路径必须存在」第一轮报出的 22 条
   **全部**是这类正当历史提及。现役地址的完整性由 §2.3 生成物与契约键判据守，
   退役地址由 §退役路由索引守——**两份职责都已有人，不需要第三处自述**。

**撤销条件**（满足其一才重开这条决策，且必须先立 ADR 再改 trait）：

- 出现一个**运行期**必须持有全量静态路由表的消费者（不是 CI，而是产品行为——
  例如入站网关按路由表分档鉴权、或外部插件宿主需要向宿主声明可达地址）；
- 仓内出现**第二种装配方**，使「臂 = 该插件的可寻址面」这条等式不再是全仓唯一规则。

### 2. 载荷契约同源 = 后端命名类型 + 前端镜像 + 字段级登记

1. **载荷形状要「可判」，前提是它在后端是一个类型**。`json!({...})` 内联字面量拼出的响应
   **没有任何守卫能读**（脚本找不到结构体，于是「前端抄错了」无处变红）。
   ⇒ 控制面路由的响应一律落为 `schemas.rs` 里的命名结构体，字段名就是线上契约。
2. **登记按 D 组既有判据，不放宽**：只有**前端逐字段镜像了它**的对才进 `STRUCT_SETS`；
   按需取几个字段的响应（`session/stats` 只取 `panel` 与 `has_wal`）**不登记**——
   没有镜像关系就没有漂移可判，硬塞进来制造的是噪音。
3. **不引入运行时 schema 注册表、不生成 TS**：前者是在 21 个实现方之外再造一处自述（同 §决策 1），
   后者把「前端手写契约」变成「前端构建产物」，而 [ADR-070](070.md) 的分工是前端**自己持有**
   呈现侧类型、由守卫比对。**逐路由渐进**：每加一对就多一处被看守的契约，不动机制。
4. **跨栈导航头两个方向都判**：后端 `Corresponding Frontend` 早已在 E 组判据里，前端
   `Corresponding Backend` 却无人看守。只守一个方向等于让另一份指针**免检**——它悬空了没有任何
   信号，而读前端代码的人恰恰是靠它找后端的。假指针比没有指针更糟，故 E 组扩成双向，
   **写了就必须指向真实文件**。
5. **同名结构体按模块限定登记**：`home/schemas.rs` 里四条路由各有一个 `Response`
   （`home_reload::Response` 与 `home_get_workspace::Response` 同名不同契约），
   D 组的抽取器原本按名字在整份文件里取**第一个**匹配 ⇒ 会悄悄配错对。
   登记项因此支持可选的 `module` 限定，且**限定后仍按同一条判据比字段**；不限制则维持原行为。

## 理由

- 三项判据（E-012 的常量值真实性、契约表的键多一即红、G 组的顶层字段必须有直接消费者）
  都已经是「代码 vs 代码的投影」型判据，`manifest()` 属于另一种形状：**代码 vs 代码的复述**。
  本仓对后者的态度一贯（[ADR-070](070.md) / [ADR-111](111.md) 都在删复述，不在加复述）。
- 「难实现/不够优雅」都不构成理由；真正的理由是**它不解决任何现有判据没解决的问题**，
  而它会解决掉「两份声明谁说了算」这个原本不存在的问题。

## 代价

- **契约表可以缺行**（RE-003 的键「可以缺、不能多」）：新路由还没有人写契约时不判红。
  代价是**未成文的现役路由**可能存在；接受它的理由是反向判据会把施工逼出来——地址与职责
  已经自动进 §2.3，缺的那一列只有「调用方 / 返回类型 / 备注」，是**只有人知道的事**。
- **命名类型 + 手写镜像仍要人改两处**：后端改名当天前端不会自动跟上，但 D 组会在**同一次门禁**
  里报「前端持有后端不存在的字段」。这是本 ADR 认定的**足够**——它要的是「漂了会红」，
  不是「漂了自动修」。
- 载荷命名只对**控制面静态路由**逐个补（本批做 home 四条），资源面（VDFS）早已由
  `schemas/vdfs.ts` 的 A/C/D 三组覆盖，其余控制面路由按出现消费方时再补。

  E-002 / E-005 / E-006 / E-012）。任务侧结案见
  [T-215](../009-task/215-路由与载荷契约单源化批.md "T-215-路由与载荷契约单源化批") 段一。

  模块名、类型名 = 后端结构体名，带 `Corresponding Backend` 头）、
