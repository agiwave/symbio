## 决策

PL-014 §4 机制 2 的「一张表装策略行与能力行（同表异 kind）」，落地形状是：
**一个行形状 + 两个目录**。能力行在 core 的 `capability::Registry`（`CapabilityRow`），
策略行在 loop 插件的 `loop_registry::Registry`（`Row`），两张表两个类型。

「一」指的是**形状与裁决规则**只有一份（`{name, prio, 纯判据}`、`(prio, name)` 全序、
先命中者胜），不是「一个 Rust 类型」。合表留下的死变体 `CapabilityRowKind::Policy`
随之删除。

### §1 判据不是美学，是消费方

| 行类型 | 消费方数量 | 谁需要看见它 |
|---|---|---|
| 能力行（Tool / Model / Prompt / Mount / Option / Configurable） | ≥2（模型工具列表、VDFS 挂载、设置页、统计） | 跨插件 ⇒ **必须**在共享地址 |
| 策略行（Policy） | **1**（`plugins/loop`） | 只有环 ⇒ 留在 loop |

合表的两个后果都是本项目明确反对的形态：

1. **core 变宽**：`LoopState` 是 loop 的私有类型（十个字段全是环的运行时视图），
   合表要么把它拉进 core，要么把 `Registry` 变成泛型——前者是「控制面细节写进
   机制层」，后者是「泛型传染」，两个都得付 CS-001 的形状账。
2. **单消费方占公共面**：违反 C-003 的判据（`ActorSpec` 之所以能占根出口，是因为
   它是 F3 冻结锚点，走的是登记豁免；策略行没有这个身份）。

两张表的行形状高度相似（`name` / `prio` / 一个纯函数），这正是「形状是一份」的证据；
而它们的**载荷与判据**不同（能力行带 `Arc<dyn Capability>` 等，策略行带
`fn(&LoopState) -> Option<Capsule>`），这是它们不共类型的理由。

### §2 删除 `CapabilityRowKind::Policy`

这个变体不是「还没接上」，是「接不上」：策略行的判据依赖 `LoopState`（loop 私有）。
留着它有两个实际害处：

- `CapabilityRowKind` 是 `list(kind)` 的过滤键，多一个永不产出的值，等于给读者
  一条「这里有东西可查」的假线索；
- 唯一引用它的是 `tool_visitor.test.rs` 里 `assert!(list(Policy).is_empty())`——
  一条**因为变体存在才存在**的恒真断言，删变体时必须一并删掉（否则测试变成
  「证明一个不存在的族是空的」）。

删除后 `CapabilityRowKind` 六个值：`Tool` / `Model` / `Prompt` / `Mount` / `Option` /
`Configurable`，每一个都有生产点。

### §3 判据

| # | 判据 | 命令 | 现状 |
|---|---|---|---|
| 1 | `CapabilityRowKind` 无 `Policy` | `rg 'CapabilityRowKind::Policy'` 无命中 | ✓ |
| 2 | 每个 kind 都有生产点 | `rg 'CapabilityRowPayload::'` 六个变体各有构造点 | ✓ |
| 3 | 两张表各自的行形状一致（`name` / `prio` / 纯函数判据） | 人工核对两处 `struct Row` | ✓ |
| 4 | 恒真断言随变体一起消失 | `rg 'list\(CapabilityRowKind::Policy\)'` 无命中 | ✓ |

### §4 不做

| 不做 | 理由 |
|---|---|
| 合表（泛型 `Registry<T>` 或 enum 载荷） | `LoopState` 进 core / 泛型传染；单消费方占公共面（C-003） |
| 把策略行搬进 core 的 `capability` 域 | 判据依赖 loop 私有状态，搬进去就是「架构层挂业务钩子」 |
| 给 `CapabilityRowKind` 加「开放 tag」 | 当前六族没有造成实际阻塞；等第一个「复用 `Invoke` 形状的新族」出现再做（那时才有第二个样本） |
