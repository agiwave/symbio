# GO-000 · 价值主张

> **这个 kind 回答什么**：要达成什么——价值主张与可度量的验收判据。
> 四层分工（goal / stage / plan / task 各回答什么、依赖怎么表达）的唯一解释在
> [docs/README · 目标分层与依赖链](../README.md "docs/README")，本文不复述。

## 0. 一句话

本层只有一类内容：**要达成什么**，以及「达成了没有」的**可度量判据**。
设计本身（要变成什么样、一句话架构是什么）在 [plan/README](../004-plan/012-高阶智能体平台v2.md "PL-012-高阶智能体平台v2")，
分步走法在 [stage/T-120 路线图总览](../009-task/120-路线图总览.md "T-120-路线图总览")——
本层不放设计，只放判据（§1）与判据当前的诚实缺口（§2）。

## 1. 要达成什么

| 目标 | 具体含义 | 兑现方式 | 服务对象 | 可度量判据 |
|---|---|---|---|---|
| **能力规划得足够远** | 覆盖到当前能设想的最高阶形态 | 五维 × 五轴的**坐标系**（轴带四级刻度、天梯由名册算出、每条判断写明反证现象），而不是一张会过时的能力清单（[PL-002](../004-plan/002-能力坐标系.md "PL-002-能力坐标系")） | 往平台里加能力的人 | 新场景只加数据不加机制：事件格子 + 投影参数 + ActorSpec + grants 各一行（机制表顶层键数由 [T-027 生成物](../004-plan/verify/facts/mod.rs) 出，`doc-count-audit` DC-002 判） |

| **关键声称有证据** | 可复现，而不是修辞 | 16 个可编译运行的验证程序，全部带反向用例（[verify/](../004-plan/verify/)） | 质疑这些声称的评审者 | verify 程序数与各程序 `assert!` 总数只增不减（门禁基线 `BASELINE` 的 `verifyPrograms` / `verifyAsserts` 两格） |

每条判据的执行方都是门禁里的机械判定（码表见 [ref/GATE_CODES.md](../006-ref/GATE_CODES.md)），
不靠人工核对——**判据之所以是判据，是因为它会在违反时变红**。

## 2. 尚未成为判据的（诚实缺口）

§1 四条判据全部回答「**架构有没有失控**」（机制键数、出口存量、冻结锚点、证据程序），
没有一条回答「**用户得到了什么**」。后者的读数**已经存在**，但不在本层：
[T-011](../009-task/011.md "T-011") 已给五轴中的四条挂上效标：三条出读数
（时域跨度 = `span`、自主程度 = `autonomy`、主动性 = `conation`），
自我模型精度有口径（`calibration`，见 [RE-004](../006-ref/004-slo-calibration.md "RE-004-slo-calibration")）尚未出数；
口径与三条纪律的唯一 owner 是 [PL-002 §3.1.1](../004-plan/002-能力坐标系.md "PL-002-能力坐标系")，本文不抄数；
**抽象层级仍只能人工判**，这一条缺口原样留着。

本层判据表**仍只放架构项**——不是因为没有读数，而是因为「用户得到了什么」的 owner
是 PL-002 §3.1 那张表：同一事实写两处，改一次要动两处，且必然漂移。本层只引用，不抄数。
等 §3.1 的读数稳定到可直接当验收阈值时，再决定是否上提。
