# 多主体与对等承诺

## 内容

前置：S07 ｜ **新增机制键 2**（`principal`、`vis_scope`）｜ 参数变化 5 ｜ 阶段二→三

## 1. 场景：要什么能力

多个主体（子智能体 / 对等智能体 / 人）同时存在，各自有身份、权限、可见域；
彼此之间能**立约**（承诺交付什么、何时交付），违约可被观测，声誉可被计算。

相对 S07 高了什么：**从"一个大脑分身"到"多个独立主体"**。
T4 的定义是"能分工"，T5 是"分工之间有可追责的契约"。

## 2. 为什么它能落在 v2 上（J1）

多主体最容易被做成"第二套架构"（很多系统为 Agent 通信单开一层协议）。在 v2 里：

| 看起来新的东西 | 实际是 |
|---|---|
| 主体 | `principal` —— **字符串 ID，数据，可无限增长** |
| 隔离 | `vis_scope`（`thread_private` / `shared` / `public`）+ grants 表 |
| 通信 | **没有直连**——一切经事实源（I1 的直接推论） |
| 立约 | `commitment` 实体的一格事件 |
| 声誉 | 一个投影（`projection = reputation`） |

**关键**：本阶是**递归是树、协作是图**的分界。子智能体递归（`scope = child`）只能表达树，
覆盖不了对等协作的图——所以才需要 `commitment` 实体加格子。**加格子，不加机制。**

## 3. 增量清单（只加数据）

| 类型 | 内容 |
|---|---|
| 事件格子 | `commitment/opened`（`commitment.offered`）、`commitment/closed`（`commitment.released`、`commitment.broken`）、`commitment/asserted`（`commitment.asserted`） |
| 新参数键 | **`principal`**、**`vis_scope`** —— 本阶两个新增机制键 |
| ActorSpec 行 | 对等体 `{ principal: "agent:peer-b", pattern: translator, capabilities: [ProduceArtifact], budget_ms: 30000, scope: root }` |
| grants 行 | 每个主体一行；**读写成对**（`grants_of` + `sees_of`，缺一不可） |
| 投影参数 | `projection = reputation` |

**本阶点亮的机制键**（阶梯总表的「新增机制键」由这张块算出；`scripts/gen-verify-facts.mjs` 从这里取输入）：

```capability-assign
event.entity = commitment
principal = agent:peer-b
vis_scope = thread_private
projection = reputation
actor.pattern = translator
```

### 3.1 落地状态：这一节里哪些增量今天存在

上表逐条对代码（本阶核实：**机制侧成立，对等侧数据行部分落地**（grants 行已落第一行；`commitment.asserted` 的**对等 offer/assert** 写方与「对等角色跑一轮」的路径仍未落——两者的依赖关系与裁决见本节末与 [D-065](../003-design/011-Agent目录规范.md "DE-011-Agent目录规范")）——树形委派侧已在生产，
对等图形侧只有测试实例）：

**规格粒度 = 主体（该批 裁决，2026-10-15）**：本仓 `ActorSpec`
是**主体的**规格，不是「步骤」的规格——一个主体一份规格，`pattern` / `capabilities` 从该主体在
`authz::ROWS` 的登记行派生（`Pattern::for_principal` + `grant_names_of`，单一真源）。「角色」在
生产里的落地形态因此只有一个：**登记窄行的主体 + 该主体驱动的会话 / 轮次**（[D-065](../003-design/011-Agent目录规范.md "DE-011-Agent目录规范")
/ 该批 先例，`agent:peer-b` 是第一个实例）。
该批 随后同批落了三个**登记角色行**——
`agent:worker`（S02 委派收束）/ `agent:planner`（`define.work` 独持）/ `agent:verifier`（`assert.verification` 独持），
均 ThreadPrivate、严格窄于派生集，各阶段落地状态见 [GO-122 §3.1](122-工具调用与产物.md "GO-122-工具调用与产物") /
[GO-123 §3.1](123-多步任务与返工.md "GO-123-多步任务与返工")；planner/verifier 的会话驱动路径因收束闸两臂不覆盖而挂起，登记 该批。
推论有两条，是后续各阶角色行的判据：

1. **同主体、跨步**的 `pattern` / `capabilities` 差异**不是** ActorSpec 行，而是**步内函数**
 （检索步 / 编译步是会话主体轮内的动作，不是另一个主体）；
2. 主体一旦出现，**必须自带窄行同批落地**，不许靠派生（未登记 `agent:<id>` 走
 [`matrix_for`](../../symbio/src/symbio_core/authz/mod.rs "authz/mod.rs") 派生分支拿主智能体整套含 `reply.*`）——
 故「角色行」任务与「该角色的执行路径」任务**同批**，不单独建行。

### 3.2 `scope` 的语义：**权威的上限**（该批 裁决，2026-10-15）

§2 的分界「**递归是树、协作是图**」在 `ActorSpec.scope` 这一格上落地。本节把语义划到
**可当读方用**的精度（这是 `Scope::Child` 从「只有类型」到「有生产构造点与真读方」的前置）：

| `scope` | 是谁 | 语义 |
|---|---|---|
| `Root` | **独立主体**：本会话自己的主体、对等体（§3 的 ActorSpec 行明写 `scope: root`） | 无上限——按自己那一行判 |
| `Child(parent)` | **`agent_run` 派生的子会话**（树侧；`metadata.parent_session_id` 非空） | **权威的上限**：子主体能落的格，其父主体 `parent` 也必须能落 |

**读方**（唯一）= 写侧收束闸 `turn_runner::closure_gate`：主体自己那一行之外，
再问一次 `scope` 指出的父主体（`authz::matrix_for(parent)`）持不持**同一项**能力
——谓词与许可同源（`can_reply` / `can_produce_artifact`），两处各写一套会让上限与许可分叉。

**为什么是「上限」而不是「许可」**：委派**不得放大权威**。未登记的 `agent:<id>` 走
`matrix_for` 的平凡值分支拿到**主智能体整套**（本阶 §4 给子智能体的口径）——于是
「窄父主体派生出宽子主体」是一条真实可走的路（对等体只持 `produce.artifact`，它派生的
子会话未选智能体 ⇒ 主体是 `agent:main` ⇒ 子比父宽，且没有任何东西会变红）。上限那道闸
把它收回来：子主体不得`reply.*`（父主体不持），产物照常（父主体也持）。

**取值点**（生产构造点）= `chat_loop::state::request_scope`：子会话 `metadata.parent_session_id`
→ 父会话 `metadata.agent_id` → `principal_of`；**顶层会话恒 `Root`**（与接线前逐字一致）。
取值链读不到（父会话已删 / 读失败）⇒ 也退 `Root`——这不是 fail-open：上限是**第二道**，
主体自己那一行（fail-closed 的结构）照常判，缺的只是「父主体可否」。

**与 §3.1 纪律的关系**：子会话是 `agent_run` 的**派生物**，它的主体由派生分支给（§4 平凡值），
故它**不**自带窄行；对它施加约束的正确位置是**上游**（父主体那道上限），而不是给每个
可能的子身份硬编码一行。判据：`turn_runner.test.rs::scope_ceiling_tests`（反向用例
——父主体不持该能力 ⇒ 收束被拒；`scope` 改回 `Root` ⇒ 同一份能力集放行）。

## 4. 平凡值与回退（J2）

| 参数 | 完整值 | **平凡值** | 平凡值下 |
|---|---|---|---|
| `principal` | `agent:peer-b` | **`agent:main`** | 仍完整运行——所有 ActorSpec 同一身份，退化成单主体 |
| `vis_scope` | `thread_private` | `public` | 仍完整运行——无隔离，退化成一个共享大脑 |

**两个平凡值合起来 = S07 的状态**。所以本阶是可整阶跳过的，且跳过不破坏任何低阶能力。

## 5. 静默失效与强制（J3）

| 约束 | 违反时信号 | 强制方式 |
|---|---|---|
| 权限与可见域 | **无**——违反时没有任何测试会失败 | **必须第零天就位**（[DE-001 §7](../003-design/001-核心架构.md "DE-001-核心架构")）：事后补要重写所有历史事件 |
| 任意两主体无直连 | **无** | 静态扫描 + CI 断言 |
| 读写授权必须成对 | **无**——只有读侧 = 能给自己授权看一切 | 编译期成对检查 |

> 权限是**静默失效**的典型：它违反时系统照常跑，只是"越权了"。
> 这是三条不变量之外最该做成 CI 断言的一条。

## 6. 验收断言

1. 两个不同 `principal` 的事件在对方 `vis_scope` 之外互不可。
2. 静态扫描：代码中不存在主体到主体的直接调用（只有 Store）。
3. 只有写侧授权的主体 → 授权检查必须拒绝（成对性）。
4. **反向用例**：把 `vis_scope` 改成 `public` → 断言 1 必须失败（证明可见域参数在生效）。
