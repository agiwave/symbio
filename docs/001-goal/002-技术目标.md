# GO-002 · 技术目标

> 产品目标问「用户得到什么」，本文问「架构必须长成什么样才装得下」，工程目标问
> 「怎么保证做对了」。设计本身（怎么实现、为什么这样选）在 [design/](../003-design/README.md "DE-000-设计总览")，
> 本文只写**必须成立什么**与**违反了会不会变红**。

## 0. 一句话

**一个原语 + 一组参数，装下一条没有终点的能力清单**：能力增长只新增数据与配置，
不新增机制键，不推翻已成立的架构。

## 1. 子目标

### T1 架构足够简洁

到达可论证的下界，没有冗余机制：一个原语、三条判据，其余全部是参数
（机制见 [DE-001-核心架构](../003-design/001-核心架构.md)）。简洁不是「文件少」，是**同一件事只有一个表达方式**——
两条路径能同时成立，就是两条都要维护。

| 判据 | 执行方 |
|---|---|
| 机制表的顶层键数等于生成物里的数——键增减必须先从生成物改起 | `doc-count-audit` 的 DC-002 |
| `symbio_core` 根出口的单消费方存量只减不增（第二消费方出现即该挪走） | `core-export-audit` 的 C-003 |

### T2 扩展永不推翻重构

冻结的锚点不许被新能力触碰，触碰即视为「这一阶其实要改架构」，走决策前置闸门
（[DE-016-工程落地与验证](../003-design/016-工程落地与验证.md) 的守恒律审计与决策前置闸门）。这条不是纪律口号：
它把「会不会重构」变成一次可执行的判定，而不是事后才知道。

| 判据 | 执行方 |
|---|---|
| 触碰任一冻结锚点 ⇒ 守恒律审计红 | `DE-016` 的守恒律审计（门禁） |
| 13 个能力阶覆盖到「能设想的最高阶形态」，且**新增机制键总数为 0**；越界键、假回退、值域扩张均为红 | [DE-030-能力阶梯总览](../003-design/030-能力阶梯总览.md) 的阶梯总表 + `docs/003-design/verify/scenario_ladder.rs`（可复算） |

### T3 能力规划得足够远

能力清单是开放的，坐标系是封闭的：五维 × 五轴，每轴带四级刻度，天梯由名册算出而不是手工排
（[DE-008-能力注册表与能力坐标系](../003-design/008-能力注册表与能力坐标系.md)）。指标本身是坐标，不是一张会过期的清单——
新能力进来只改「在哪一格」，不改「有哪些格」。

| 判据 | 执行方 |
|---|---|
| 新增一个场景只加数据：事件格子 + 投影参数 + ActorSpec 行 + grants 行各一行，机制表顶层键数不变 | DC-002（锁键数）+ `DE-030` 阶梯审计（逐阶新增键数可复算） |
| 每条能力在坐标系里有落点与权重，落点指向点亮它的那一阶；名册与阶梯不许各说一套 | `gen-verify-facts`（从名册与阶梯抽事实，两处不一致即红） |

### T4 前端去业务化

宿主（对话面 / 三栏 / 表单）不承载任何业务分支：**同一套机制跑全部资源类型**，
业务差异收敛为数据（一份注册配置）而不是代码分支。四个面：

| 面 | 要达成什么 | 设计 |
|---|---|---|
| 三栏机制 | 左导航 / 中列表 / 右详情成为资源管理的唯一框架：会话、模型、智能体与 Agent 内部资源全部走同一套三栏、同一套条目化登记 | [DE-019-前端机制化](../003-design/019-前端机制化.md) |
| 表单机制 | 设置 / 新建 / 编辑由 schema 驱动：渲染与校验从一份声明推出，业务只描述字段与约束 | [DE-019-前端机制化](../003-design/019-前端机制化.md) |
| 统一资源管理 | 三栏抽象为统一资源管理：任意资源从任意入口经全局跳转进入独立全页，资源之间不再各有「列表 + 详情 + 编辑」的私有实现 | [DE-019-前端机制化](../003-design/019-前端机制化.md) |
| 显示由状态驱动 | 界面显示由节点状态决定，不由事件到达顺序决定——重放与实时是同一份视图 | [DE-019-前端机制化](../003-design/019-前端机制化.md) |

| 判据 | 执行方 |
|---|---|
| 同一套机制覆盖系统级与模块级资源（就近放置、单一来源） | `registry-audit` 的 RG-020（仓内每个活跃 `.md` 都在登记机制内） |
| 表单校验失败有机读出口（错误码表驱动，不是散落的提示文案） | [RE-002-ERROR_CODES](../004-ref/002-ERROR_CODES.md)（现行） |
| 新增一类资源 = 一份配置 + 一个渲染器 + 一条导航注册；框架零类型分支 | `kind-branch-audit` 的 KB-001（框架格恒为 0，机制格只降不升）+ KB-002（每条命中都归属两格之一）。「分支」= 与 `NODE_KIND_*` / `VDFS_EXT_*` / `VDFS_KIND_*` 的比较、对 `nodeKindOf` / `vdfsExtOf` / `resolveVdfsRenderer` 结果的比较、渲染器字面量比较，以及 `Record<NodeKind, …>` / `Record<…, VdfsRenderer>` 映射表；表单控件轴（`.widget` / `.tag`）不计 |

### T5 就近放置、单一来源

文档与代码同住：模块文档放模块目录，系统级文档只留跨模块的契约，涉及单模块内部实现时引用
而不复制（机制见 [DE-017-登记与汇总机制](../003-design/017-登记与汇总机制.md)）。这一条约束的不只是文档，是**知识的位置**——
一条约定只有一个 owner，其余位置是引用。

| 判据 | 执行方 |
|---|---|
| 全仓每个活跃 `.md` 都是登记条目，`id` 与文件名对账、`title` 与首个 H1 对账 | `registry-audit` 的 RG-020 / RG-021 / RG-003 |
| 一份清单只有一个 owner；正文里的清单标记与 front-matter 声明两面对账 | RG-026 / RG-027 / RG-029 |
| 文档间引用只写编号，地址由机制算——手工地址指向已登记文档即红 | `gen-doc-refs` 的 RF-003 |

## 2. 判据的共性

上表每一条都满足同一个形状：**违反时会变红，且由脚本判**。做不到这一点的，写在 §3，不写进表——
把「希望」写成「判据」是本层最容易犯的错。

## 3. 尚未成为判据的（诚实缺口）

1. **「架构足够简洁」只锁了键数与出口存量。** 两个数不涨，冗余仍可能藏在**值的语义**里：
 同一机制被两处以不同参数各表达一遍，键数不变、出口不变，判据看不见。这类问题只有
 「先找同构的既有模式」这道人工闸门能拦（[DE-016-工程落地与验证](../003-design/016-工程落地与验证.md) 的决策前置闸门）。
2. **坐标系覆盖度没有反证。** 名册能证明「每条被登记的能力都有落点」，证明不了
 「还没想到的能力将来放得进去」——后者只能靠新场景进来时重跑阶梯审计来逐步证伪。
