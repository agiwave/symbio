# GO-003 · 工程目标

> 产品目标问「用户得到什么」，技术目标问「架构长成什么样」，本文问**怎么保证做对了**。
> 工程纪律本身的设计（门禁怎么分阶段、棘轮怎么记账）在 [DE-016-工程落地与验证](../003-design/016-工程落地与验证.md)，
> 条文与判据在 [spec/](../005-spec/README.md "SP-000-规范汇总")，本文只写**必须成立什么**。

## 0. 一句话

**每个声称都要有一条能复现的命令，每条纪律都要有一个会在违反时变红的判据。**
说得出的东西必须跑得出来；跑不出来的，不许说成已经成立。

## 1. 子目标

### E1 关键声称有证据

「架构装得下」「这条不变量成立」「这个边界守得住」——这类声称全部以**可编译可运行的验证程序**
为证据，每项带反向用例（证明检查本身不是摆设）。证据随设计走，住在 `docs/003-design/verify/`。

| 判据 | 执行方 |
|---|---|
| verify 程序数与各程序的断言总数只增不减（删证据必须是一次显式的基线调整） | 门禁基线的 `verifyPrograms` / `verifyAsserts` 两格 |
| 每个验证程序都有反向用例：注入违例必须失败 | `gate` 的 verify 阶段逐个跑，反向用例失败即红 |

### E2 全面完整的 e2e 体系

任何能力阶的正常场景与异常场景都有可复现的判据，而不是只被「出厂 happy path」压过的功能。
两个支撑面：

1. **mock 模拟真实模型与真实网络**——流式分片、思考、工具参数流式聚合之外，
 响应流中断、限流、内容不规范、网络延迟与停顿也按**场景字段**分级注入，
 不是每个用例手写一次特判。
2. **用例模拟真实使用过程**——长驻会话、多轮、「历史 + 实时」两个出口、恢复与审批、
 压缩、记忆，正常路径与异常路径各有一个可数、可盘点的覆盖面。

| 判据 | 执行方 |
|---|---|
| 全量 e2e 绿，且用例数棘轮不为降 | `gate.d/58-e2e.mjs` 与基线用例数格 |
| 模型侧的正确性有断言面：信封参数、system 装配、历史保真、工具反馈、工具面、user 消息纯度、辅助请求形状，均有模型视角的契约用例 | e2e 契约库 LC-001…007 |
| 异常注入按场景字段组织，每种注入有独立用例钉「注入会红 / 被测系统按纪律收敛」 | `injection-matrix-audit` 的 INJ-001…003 + [RE-012-注入矩阵](../004-ref/012-注入矩阵.md)（12 种注入 × 4 个能力面 = 48 格的逐格归属；用例、不适用理由、缺口 owner 三者可验，缺口 3 格挂 DE-039） |

### E3 条文与判据一一对应

规范文档里**每一条**必须成立的条文（`## 规范`）都带它的判据（`## 判据`），判据落到具体脚本与判据码。
一条只有措辞没有判据的规范，等于一条建议——它会漂移，而且没人知道什么时候漂的。

| 判据 | 执行方 |
|---|---|
| 判据码不撞号、不重复定义、不在脚本外自造 | `gate-codes-audit` 的 GC-001…006 |
| 每条规范都写明了执行方（脚本名或判据码），或明确标注「无机器判据」及其理由 | `spec-coverage-audit` 的 SPC-001…003（活跃规范逐条判「机器执行方 / 人工理由 / 缺失」，人工理由须非空且成句；口径自洽与编号唯一另判） |
| 判据码总表由脚本声明生成，不手写 | `docs/004-ref/GATE_CODES.md`（生成物） |

### E4 门禁是唯一的合入闸

任何「已经成立」的判断以门禁通过为准，不以口头或文档措辞为准。门禁分阶段（格式化 / 文档 /
事实 / 后端 / e2e / 验证 / MSRV），阶段可以分开跑，但合入前必须全绿——**跳过某一阶段不是加速，
是把那一阶段的判据换成人的记忆**。

| 判据 | 执行方 |
|---|---|
| 全量门禁全绿才允许提交 | `scripts/gate.mjs` + 提交钩子 |
| 生成物与源码不许漂移：事实表、登记汇总、判据码表、基线文件都由脚本重算，手改即红 | `gate` 的 facts 阶段（重算后比对） |

### E5 过渡结构与死码只减不增

迁移留下的过渡入口、兼容分支、无人调用的代码，都是**未来某次事故的入口**。
它们不靠一次性大扫除解决，靠棘轮：存量记在基线上，只许降，涨一个即红。

| 判据 | 执行方 |
|---|---|
| `ChatNode.role` 的直写零处（构造点只写 `principal`；读边界与存量读法用例带豁免） | `grep-audit` 的 S-014 棘轮（基线 0） |
| 每处 `#[allow(dead_code)]` 都带理由且挂到设计条目，不留裸豁免 | `dead-code-audit` 的 R-002 |
| 没有可移除的死码（可达性分析报 0） | `dead-code-audit` |
| 旁路与直连调用（`S-016` / `S-017` / `NDC-001…002`）在真实仓库零处 | `grep-audit` 与 `no-direct-call-audit` |

## 2. 判据的共性

上表每条都能独立跑、独立变红，且不依赖「记得去看」。**不能自动化的纪律不写进表**，
写在 §3——把希望写成判据，比没有判据更糟：它会让绿色的门禁显得像保证。

## 3. 尚未成为判据的（诚实缺口）

1. **性能与成本不在判据面。** 延迟、预算超支、上下文费用都只有读数，没有阈值。
 阈值一旦定死就会误报，所以它们停在「可观测量」而不是「判据」——这是一处刻意的空白，
 不是遗漏。
