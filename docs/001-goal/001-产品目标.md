# GO-001 · 产品目标

> 这一层只回答两件事：**要达成什么**，以及**达成了没有**。
> 三个大目标的分工固定：产品（本文）回答「用户得到什么」，[技术目标](002-技术目标.md "GO-002-技术目标")回答
> 「架构必须长成什么样才装得下」，[工程目标](003-工程目标.md "GO-003-工程目标")回答「怎么保证做对了」。
> 设计与机制在 [design/](../003-design/README.md "DE-000-设计总览")，用户判据的账本在 [scene/](../002-scene/README.md "SC-000-场景汇总")。

## 0. 一句话

一个**能长期陪着一个人干活**的智能体：能对话、能动手、能记住、能被纠正、能自己发起，
并且每长一项能力都不需要推翻已经成立的那部分。

### 1.1 未承诺能力：五项草案已移出承诺清单

`SC-014`（深度研究）/ `SC-015`（浏览器自动化）/ `SC-016`（数据与文件分析）/
`SC-017`（定时巡检）/ `SC-018`（对抗评审）曾是五项有场景、无机制、无判据的草案。
裁决：**全部移出承诺清单，不立项**（[D-157](../003-design/002-架构总览.md "DE-002-架构总览")）——
判据必须先于能力，先写判据再补能力只会把愿望清单写成路线图。五个场景文档保留为草案，
作为讨论材料；重开条件（出现真实消费方且判据能指向已有读数，或机制先独立落成）住在 D-157。
本层不再维护「尚未承诺的能力」索引。

## 2. 可度量判据

| 判据 | 执行方 |
|---|---|
| **能力面的每一项都能解析到真实条目**：本表索引的编号不存在即红 | `gen-doc-refs` 的 RF-001（编号不存在）、RF-002（地址漂移自动重算） |
| **用户判据只在一个地方有账本**：本表不持判据，场景文档的「用户判据（诚实账）」是唯一 owner；引用只写编号 | `doc-link` 的 D-007（锚点必须指向真实标题）与 `RF-003`（手工地址判红） |
| **目标与场景不脱钩**：场景条目改名或搬迁，本表跟着断——断链即红，不靠记性 | `doc-link` 的 D-001（站内链接有效） |

判据之所以是判据，是因为它会在违反时变红。上表三条都挂在已有守卫上，没有一条需要人工核对。

## 3. 尚未成为判据的（诚实缺口）

**「用户得到了什么」整体上仍无自动读数。** §2 三条判的是**账本结构**（链接有效、编号存在、
owner 唯一），不是**结果**——一次结构全绿而用户什么都没得到，在这套体系里是可能的。
逐项的用户判据现状在各篇场景文档的表里（有用例的写用例，没有的写「缺口：无判据」），
本层不抄那一列数字，因为抄一遍就多一处维护点。

两个具体的缺口：

1. **产品完成度没有总读数**。今天能答的是「某项能力的账本里有多少格有读数」，能答这个的
 是逐篇场景文档；没有一张按域汇总的表。是否需要它，取决于「按域看进度」这件事有没有真实
 消费方——没有消费方之前不建，避免又一份需要同步的投影。
2. **未承诺能力不产生完成度口径**。五项草案已移出承诺清单（D-157），本层不再为它们维护
 「做完了没有」——没有承诺，就没有完成度读数。
