# GO-005 · 全面完整的 e2e 测试体系

> **这个 kind 回答什么**：要达成什么——价值主张与可度量的验收判据。
> 「为什么这样设计 / 怎么实现」不写在本条目：设计归 plan 层（[PL-003-演进与验证](../004-plan/003-演进与验证.md)），推进归 [T-067-mockLLM体系化机制化](../009-task/067-mockLLM体系化机制化.md) / [T-068-e2e用例体系化升级](../009-task/068-e2e用例体系化升级.md)。

## 1. 要达成什么

e2e 测试升级为**全面完整的质量保障体系**：任何能力阶（[ST-000-路线图总览](../003-stage/000-路线图总览.md)）的
正常场景与异常场景都有可复现的判据，而不是只被「出厂 happy path」压过的功能。
两个支撑面：

1. **mockLLM 体系化 / 机制化**——mock 尽量模拟真实 LLM 服务与真实网络环境：
   正常形态（流式分片 / 思考 / 工具参数流式聚合）之外，异常形态也成分级注入机制
   （响应流中断、429 限流、响应内容不规范、网络延迟与停顿……）——注入是**配置驱动
   的场景字段**，不是每个用例手写一次特判。
2. **e2e 用例体系化建设与升级**——用例尽量完整模拟实际用户使用过程
   （长驻会话、多轮、「历史 + 实时」两个出口、恢复与审批、压缩、记忆……），
   正常路径与异常路径各有一个可数、可盘点的覆盖面。

## 2. 可度量判据

| 判据 | 执行方 / 现状 |
|---|---|
| 异常注入按场景字段组织，每种注入有独立 e2e 用例钉「注入会红 / 被测系统按纪律收敛」 | 待建（本条目的出口，走 [T-067-mockLLM体系化机制化](../009-task/067-mockLLM体系化机制化.md)） |
| 正常 / 异常场景覆盖矩阵成文，每格标「有用例 / 缺口 / 明确不做」 | 待建（本条目的出口，走 [T-068-e2e用例体系化升级](../009-task/068-e2e用例体系化升级.md)） |

## 3. 本层不放什么

mock 的场景字段命名、注入协议、覆盖矩阵的具体格子与用例拆分归 [T-067-mockLLM体系化机制化](../009-task/067-mockLLM体系化机制化.md) / [T-068-e2e用例体系化升级](../009-task/068-e2e用例体系化升级.md)

写清「钉的是什么」）。
