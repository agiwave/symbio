## 决策

**背景**：能力扩充阶梯（[ST-000](../stage/ST-000-路线图总览.md "ST-000-路线图总览")）的 S04 承诺「能并行、能仲裁」，阶梯总表里记
**新增机制键 0 / 参数变化 4**——即「只加数据」。[ST-004](../stage/ST-004-并发调度与租约.md "ST-004-并发调度与租约") §3 因此列了四行增量
（事件格子 / 调度者 ActorSpec 行 / grants 行 / 投影参数），§4 把 `readyset:cap=1` 称作
「本阶最漂亮的一个平凡值」，§6 给了四条验收断言。

2026-10-13 的逐阶落地审计把 §3 的四行逐条对到代码（§3.1），结论是**四行里三行不存在**：

- `task.held` 在生产，但写方是 **S07 抢占路借来的**（`transcript/inbox.rs` 的
  `commit_preemption` → `symbio_core::actors::control::held_event`，principal 写死 `agent:reflex`）
  ——**无 TTL、无发放方**，不是租约；正文的 `task.ready` / `task.assigned` 两个事件名**不存在**
  （`event/mod.rs` 的任务格只有 `opened / progress / held / asserted / rework_created`）。
- 调度者 ActorSpec 行不存在（80ms 档位真、行假；档位 = `LatencyTier::Reflex`，用在抢占判定）。
- 「调度者独占 `task.assigned`」的 grants 行不存在（`assign.work` 挂在 `agent:main` 上，
  但**无任何写侧消费方**）。
- `readyset` 在生产，但**无容量参数、无租约占用判定**——模块头把容量推给「调用方的调度器」，
  而那个调度器不存在。

**决策**：

1. **收窄本阶的能力承诺到已落地的形态**。ST-004 的真实增量 = ① 单写者 FIFO 仲裁
   （`store/mod.rs` 的「查重 → 赋 seq → 落库」原子 + `wal.rs` 跨进程写者令牌 `NotTheWriter`
   + `scripts/no-direct-call-audit.mjs`）；② `task.held`（借 S07 抢占路的挂起格）；
   ③ `readyset` 就绪集投影（**只取「终态 + 依赖闭合」**，不含租约占用判定）。§3 的表格按此改写。
2. **不立 `task.ready` / `task.assigned` 两个事件名，也不给 `readyset` 加 `cap` 参数**——
   理由见下「理由」2 / 3（它们是**没有写方、或没有消费方**的格子）。
3. **§6 的断言 1（100 并发持有 ≤1）与 3 / 4（`cap` 正反）随本次修订删除**：它们今天**无执行方**
   （断言 3 / 4 的参数根本不存在）。保留断言 2（有执行方：`store/mod.test.rs` + e2e **t32** +
   `helpers.mjs` 的 seq 断言 + `verify/invariants.rs` 的 `I1SeqNotMonotonic`）。本仓对
   「无执行方的验收断言」态度明确：它读起来像有守卫，实际判不了——正是各阶 §3.1 建制要消灭的形态。
4. **「调度器 / 租约 TTL / cap」登记为未来能力**（写进 ST-004 §7），**不在本阶梯的已落地承诺内**。
   将来要做，须先按 [ADR-055](ADR-055.md) 立一条**放宽决策**（动 `symbio_core` 事件词汇表 = 核心公共面变宽），
   且**写方与消费方同批落地**（「闸不能晚于发起者」的反面：格子也不能先于它的写方进词汇表）。
5. **§3 的 ` ```capability-assign ` 块形状不动**（`scripts/gen-verify-facts.mjs` 从它取输入）；
   §4 的退路口行保留（生成器要求每阶**恰有一行**加粗平凡值），但标注「`cap` 参数未落地」。

**理由**：

1. **阶梯的自证条件被 S04 自己否证了**。[ST-000](../stage/ST-000-路线图总览.md "ST-000-路线图总览") 写「答案若不是『只加数据』，
   这个阶梯就失败」；S04 §3.1 的结论恰是「不是补数据行就能落地的增量」。把「未实现」写成
   「0 新增键 / 4 参数变化」，会让下一轮把叙事当事实——这正是各阶 §3.1 建制要消灭的形态。
2. **没有写方的格子不能先进词汇表**。`task.ready` / `task.assigned` 今天既无写方也无消费方；
   立了它，`symbio_core` 多两个**0 消费方导出**——撞 `core-export-audit` 的单消费方棘轮（C-003），
   而且它给读者的信号是「能力存在」。这与 [ST-012](../stage/ST-012-自主层与长期目标.md "ST-012-自主层与长期目标") §3.1 为自主主体
   修掉的同形静默面是同一类。
3. **没有调用方的参数是死参数**。`readyset` 的容量参数被模块头明确推给「调用方的调度器」，
   而那个调度器不存在。先加 `cap`，等于先建闸再找发起者。
4. **诚实划界优于虚设判据**。§6 断言 1 / 3 / 4 无执行方，保留它们等于给「并发调度」这个能力
   盖一个没人验过的章。

**被否决的方案**：

- **落地（补事件名 + TTL 租约 + cap，实现另拆任务）**：**暂缓，不是否决**。它是**放宽
  `symbio_core` 公共面**（[ADR-055](ADR-055.md) 的适用面），而本阶梯的头条承诺是「全梯 13 阶架构改动 = 0」。
  单方放宽会让头条失真；要做就按 [ADR-055](ADR-055.md) 另立决策，并把写方与消费方同批排期。
- **保留 §6 断言 1 / 3 / 4 并标「待实现」**：否决。无执行方的断言与「没有守卫」等价，
  但读起来像有——比删掉更坏。
- **把 `task.held` 改名回正文的 `task.blocked`**：否决。`symbio_core::event` 已**单点定义**
  该格为 `task.held`（`event/mod.rs` 明确注释「ST-007 里这一格的事件名叫 `task.blocked`，
  本仓库以 `task.held` 单点定义」）。改名 = 造第二份真相。本次修订把 §3 的旧名标注为「正文旧称」。

**后果与不变量**：

- **本批不动任何生产代码**：不新增 / 改名事件、不改 `readyset`、不改 `held` 的写方。
- **阶梯总表（ST-000 §1）的 S04 行不因本次修订改动**——`新增机制键 0 / 参数变化 4` 是**目标值**；
  改动的是 ST-004 正文的「今天」形态与 §6。
- **`gen-verify-facts.mjs` 全程绿**：`capability-assign` 块与 §4 的加粗平凡值行原样保留。
- **能力名册 S04 的锚不动**：`projection/cost.rs::cost_ledger` 与 `readyset.rs::readyset`
  都生产在用（§3.1 已核）。
