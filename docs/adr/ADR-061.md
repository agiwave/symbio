## 决策

**背景**：[01 §8](../plan/PL-001-核心架构.md "PL-001-核心架构") 的 `store` 值域里写着 `distributed`，而
`Store` 的不变量里写着 **`seq` 单调**（I1）。这两条在多副本下**直接冲突**：副本 A 与副本 B
各自追加，谁先谁后没有全局顺序；而事件网格的溯源边依赖 `seq` 严格递增
（[01 §13.3](../plan/PL-001-核心架构.md "PL-001-核心架构")「溯源边只能从高 seq 指向低 seq」）——`seq` 一旦不是
全局单调，派生图的**无环保证**就没了，而那是「无溯源不声明」（I2）能成立的前提。

本仓此前的诚实状态是「没有分布式实现，也没有任何东西在宣称它可用」。但**没有实现 ≠ 没有
风险**：值域里留着这一格，等于配置面上可以写一个**当前语义下必然违反 I1** 的取值，而
`in_domain("store", "distributed")` 会判它合法——值域本身在撒谎。

**决策：`distributed` 从 `store` 的值域退役**（[01 §8](../plan/PL-001-核心架构.md "PL-001-核心架构") 表中标注
退役并指认本 ADR）。理由：

1. **多副本部署不在计划内**，触发信号（[PL-003 §7.3 G4](../plan/PL-003-演进与验证.md "PL-003-演进与验证")、
   [PL-004 §5 R5](../plan/PL-004-工程落地.md "PL-004-工程落地") 都写「出现多副本部署需求」）从未发生。
   一个没有需求、没有实现、且语义上**与既有不变量冲突**的取值格，留着只是负债。
2. **留一格比删一格更容易骗人**。「将来也许能用」的形态会让读者以为这条路径已想清楚，
   而它恰恰是**最没想清楚**的一格（见下：四问一个都没答）。删掉它，缺口就回到缺口表里，
   那里有 owner、有触发信号。
3. **退役不是放弃**：下面四问是**重新引入时必须同时回答**的清单——它随本 ADR 一起留下，
   比留一个空取值格更有信息量。

## 重新引入时必须同时回答的四问

1. **全局序从哪来**（共识日志 / 单写者代理 / 分区 + 分区序号）——没有它，`seq` 单调不成立。
2. **同一 `event_id` 在两副本各命中一次时谁是权威**（幂等去重按什么键）——本仓的去重键是
   `event_id`，跨副本时这个键的权威方必须唯一。
3. **溯源边在跨副本时指向什么**（局部 `seq` 还是逻辑时钟）——若改用逻辑时钟，§13.3 的
   「高 seq 指向低 seq」要整体改写成「时钟序」，那是一次跨多处的语义变更，不是加个字段。
4. **脑裂时哪边能发言**（一致性级别与 I3「到点必答」的关系）——I3 要求到点必答，强一致
   要求在点让渡；两者在多副本下必须选一个，不能都要。

四问答不全 ⇒ `distributed` **不得回到值域**。答全了 ⇒ 写一条新 ADR 取代本条，并**同时**
改 [01 §8](../plan/PL-001-核心架构.md "PL-001-核心架构") 的值域表与本 ADR 的状态。

## 判据落点（这条决策有能红的落点）

`store` 值域住在 [01 §8](../plan/PL-001-核心架构.md "PL-001-核心架构") 的表里，由 `gen-verify-facts` 生成进
`facts::DOMAINS`；`docs/plan/verify/scenario_ladder.rs` 据此判每阶赋值是否越界。故：

- **`scenario_ladder` 断言 `store` 的值域不含 `distributed`**——谁把它加回值域表，facts 里
  就会有它，这条断言立刻红。**这就是本 ADR 的落点**：决策不是「写完了」，是有一个能红的
  地方看着。
- 反之，值域里没有它 ⇒ 任何 `store = distributed` 的赋值都会被 `in_domain` 判**越界**，
  配置面再也写不出一个 I1 必然不成立的组合。

## 后果

- [01 §8](../plan/PL-001-核心架构.md "PL-001-核心架构")：`store` 的取值域由
  `memory / wal / sharded / distributed` 变为 `memory / wal / sharded`，`distributed` 一格
  标注「ADR-061 退役」并指认本条。
- `facts::DOMAINS` 随生成器重生成（`distributed` 消失）；`scenario_ladder` 新增上述断言。
- [PL-003 §7.3 G4](../plan/PL-003-演进与验证.md "PL-003-演进与验证") 与 [PL-004 §5 R5](../plan/PL-004-工程落地.md "PL-004-工程落地")
  的措辞随本条收敛：缺口不再是「分布式 seq 单调怎么共存」，而是「多副本需求出现时，按
  ADR-061 四问定口径并把取值加回值域」。
- [T-014](../task/T-014.md) 关闭（判断 = 不在计划内 ⇒ 退役，而非定口径）。
- **在此之前 `store = distributed` 不得被任何文档或配置当作可用取值宣称**——现在这一点由
  值域本身（而非自觉）保证。
