## 决策

**背景**：目标形态是**主会话不持有工具**，于是主会话缺三样外部事实——worker 何时启动、自己有哪些能力、进展如何。[ADR-046](./ADR-046.md) 已定 `feat/v2-bridge-b1-fact-envelope` 的处置边界：其**插件式结构**不在移植清单上，其中的**体验价值**（含委派者三项真源）另按 `docs/plan/` 路径评估，且**改行为面的先写 ADR**。本条即那个「先写 ADR」的产物。

**决策**：三问的答案**都必须是数据而不是机制**，各自唯一真源：

1. **Q1 · worker 启动条件 = 三层判据的合取纯函数**——显式前缀 `/work `（带尾空格）、关键词（子串，出厂空集）、主题长度阈值（出厂 0），**必须回 `reason`**。形态照搬 `classify_by_rule`：纯函数、无 I/O、无状态、无 async、命中回理由码、未命中回 `None`，全部行为可被测试穷举。
2. **Q2 · 能力可见性 = `list_capability()` 折出的按分类分组的名字目录（digest），不走工具**。注入点是 `session::chat_loop::inputs::prepare_turn_inputs`，且**必须在能力收集之后**才动笔。
3. **Q3 · 进展 = 从 worker 会话的磁盘事实推**——子会话按 `metadata.parent_session_id` 归档在父会话的 `sessions/` 子目录下，**必须按 `parent` 过滤**。

**理由**：三问若答以**机制**而非数据，主会话就得重新持有工具——而「不持有工具」正是这个目标形态的前提。
- Q1 若「总是先开一个 worker 再决定」，**每条寒暄都会产生一个后台会话**；若把判定交给模型，则**判定权落在不可审计的一侧**——同一句话两次判定可能不同，也没有可回放的理由。
- Q2 若走工具，模型得先**知道**有这么个工具才会去调它：**能力可见性不能以调用能力为前提**。注入点之所以不是插件侧，是收集本身决定的：收集是**广播**——容器 `composite::traverse` 逐子插件转发，而它取的实例表快照（`PluginRegistry::snapshot`）直接遍历 `HashMap` 且**不排序**。于是在遍历**尚未结束**的任一子插件里取能力集合，必然漏掉还没被访问到的兄弟；顺序又每次不同，**漏了哪几项次次不同**——既静默（不报错、不缺项告警）又难复现。
- Q3 若用进程内注册表，服务重启后注册表为空而磁盘事实仍在 ⇒ 两处对不上，**注册表就成了第二份真相**；这与 ADR-026 定的形态一致——子会话本来就在 VDFS 空间内自驱动，读侧应当读那一处。

**被否决的方案**：
- **总开一个 worker 再决定**（寒暄也开后台会话）；**模型自判**（不可审计、不可回放）。—— Q1 的两个反面。
- **能力经工具暴露 / 在插件 traverse 期算目录**。—— 见 Q2 理由。
- **进程内 worker 注册表**。—— 重启后与磁盘不一致 = 第二份真相。
- **照搬成新插件**。—— 那正是 ADR-046 否掉的形态；移植落点与本仓现状见 [04 §3.2](../plan/04-工程落地.md "docs/plan/04-工程落地")。

**后果与不变量**：
- **注入点在能力收集之后**：owner 是 `prepare_turn_inputs`，新段必须并进它既有的请求视图次序——现状为**记忆段 `index 0` / 就绪段 `index 1`**，该次序由 `build_request_view` 单点保证（`prepare_turn_inputs` 的第 6 步），且有测试钉住「记忆仍在 0、就绪段在其后」。
- **Q1 不回 `reason` 就等于没判**：没有理由码的判定不可审计，也不可被测试穷举。
- **Q3 不按 `parent` 过滤比没有进展更糟**：串台会把别人的进展报成本会话的进展。
- 三者都是**数据**：不新增存储、不新增注册表、不新增跨插件调用。落地分两步（B1 输入面 / B2 前端过程段收起），见 [04 §3.2](../plan/04-工程落地.md "docs/plan/04-工程落地")。
