## 决策

**背景**：[ADR-048a](ADR-048a.md) 判定「把工具结果拍平成纯文本是退步」，依据是协议契约与
训练形态的**论证**；它同时留下一句没被兑现的话——本仓**没有任何度量**能回答
「这样对模型是变好还是变坏」。[plan/13 终点第 2 条](../archive/13-质量改进总纲.md)
因此一直没闭环（登记条目 [S-end①](../task/S-end①.md)）：连「现在实际送出去的是什么形状」
都没有一份可核对的记录，任何「更有效」的判断都只能拍板。而拍板在批次执行时一定有词：
「这次改动让 prompt 更结构化，所以更好」。

**决策**：

1. **基线从运行时抓，不从装配代码静态读**。执行方是
   [`e2e/cases/t46-prompt-shape-baseline.mjs`](../../e2e/cases/t46-prompt-shape-baseline.mjs)：
   跑一次真实链路（CLI × mock LLM × mock MCP，出厂 `full` 档），把 mock-llm 收到的
   **原样请求体**交给 `scripts/prompt-shape-audit.mjs` 提取形状并比对。
2. **进判据的只有「由装配代码决定的结构」**：
   信封取值（`model` / `stream` / `temperature` / `tool_choice` / `max_tokens`）、
   消息序列（`role` + `tool_calls` 条数 + 工具结果是否带 `tool_call_id` + 正文形态）、
   system 前缀的**小节标签序列**（`【…】` 只在**行首**才算标签——正文里引用别的标签不算）、
   工具面的**数量与名字顺序**（原序直比——顺序是注册序的产物，换序就是换形状）。
   **字节规模不进判据**，只作为重生成当时的一次观测写进同一份文件并标明日期。
3. **基线文件既是判据本体也是人类可读投影**：
   [`docs/ref/PROMPT_SHAPE.md`](../ref/PROMPT_SHAPE.md) 里
   ` ```json:prompt-shape ` 块是判据，两张表是同一份 JSON 的渲染，唯一写者是该用例带
   `PROMPT_SHAPE_UPDATE=1`。
4. **场景名进判据**，本基线钉的是「主线装配 + 一次真实工具轮 + **对话面显式关闭**」；
   对话面的形状归 t21–t23 那三条用例。
5. **链路没跑出请求 ⇒ 退出 2（PS-003）**，不允许「空形状与空基线一致」报通过。

**理由**：

1. **「送进模型的是消息数组还是拼平的文本」是一条运行时事实**。静态读 `render_messages` /
   `request_view_prefix` 只能读出**打算**发什么；中间隔着投影、截断、记忆召回与协议适配器
   （四种 wire 形态各有一套 flatten，见 [ADR-004](ADR-004.md)）。ADR-048a 争的正是这一层，
   所以记录必须来自真实请求体。
2. **规模与结构在文本上不可分，在判据上必须分**。正文字节同时由**用例文本**与**召回内容**
   决定——把它钉进判据，「改一句用例措辞」就红，而那只与装配无关。一个会因无关改动而红的
   守卫，最后的下场是被喂到失效（本仓为此写过一整节，见 `core-export-audit.mjs` 的 W1 注）。
   判据管「结构在不在」，观测管「结构花多少」：两次重生成之间的观测差 = 那次结构变动的代价。
3. **一份文件两个身份，是为了不给「形状」造第二个真相源**。判据 JSON 与读它的表同源同生成，
   改代码 → 重生成 → 两处一起动；分两份文件就要动两处，而它们必然漂移。

**被否决的方案**：

- **静态解析装配代码生成基线**：否决。理由见决策 1——它记的是意图，不是模型收到的东西，
  而 ADR-048a 判的恰是「适配器边界上有没有被拍平」。
- **把字节数（含每小节规模）钉进判据**：否决。会把无关改动判红，且红得没有诊断价值；
  本仓对这类守卫的结局有记录。
- **判据存 `e2e/*.json`、散文说明另写一份 md**：否决。两份文件同一事实，正是「复述即重复」；
  生成物里嵌 JSON 块已有先例形态（脚本渲染 + 不手改）。
- **让基线跑出厂默认（对话面开着）**：否决。对话面每轮插静默请求，请求下标就依赖分类器的
  路由结果，一次对话面调优会让「主线形状」整块变红；而对话面自己的形状本就是 t21–t23 的主题。
  基线的场景名把这件事**写进判据**，换场景不能顶替旧基线。
- **给四种 wire 协议各建一份基线**：暂不。本轮要闭环的是「有没有一份可核对的形状记录」，
  多协议各一份要先解决同一场景在不同协议下的可比性——那是另一条决策，不在本批顺手扩面。
  `extractShape` 的输入就是 mock-llm 收到的请求体，接入第二种协议时改的是**用例**不是口径。

**后果与不变量**：

- **落点**：判据执行方在 58-e2e 阶段（用例文件按名自动纳入，无需登记）；
  提取与比对实现 `scripts/prompt-shape-audit.mjs` 登记在 `30-docs` 的 `TEST_ONLY`
  （回归测试双向钉：结构载体没进形状 ⇒ 拍平红不了；规模成了判据 ⇒ 改用例措辞就红）。
- **它不回答「变好还是变坏」，只让这个问题第一次变得可问**。基线给出的是代价与形态的读数；
  「对模型更好」还需要**真实模型上的对照**，那是 [S-end②](../task/S-end②.md) 的面，
  不在本条的承诺里。
- **不变量**：本批**不动任何装配代码**——不改 `symbio_core` 的公共形状（CS-001 三格不变），
  不改 prompt 的一个字节。基线是记录面，记录面不通过改被记录的东西来变好。
- **基线第一次跑就抓到的两个同族缺陷（口径当时把它们遮住了）**：口径写成
  「名字排序后比」的那一刻，它就顺带遮住了一个真缺陷——`tools` 数组的顺序**每起一个进程
  重洗一次**（`PluginRegistry::instances` 与 `DefaultToolVisitor::tools` 都是哈希表，
  而注册序 = 能力收集的广播序）。系统提示词的小节序因此同样不稳定：同一份装配跑 t46
  **20 次里 13 次**是另一种小节顺序。两处已改为保插入序的表（摘除走 `shift_remove`，
  停用 / 卸载不重排其余项），修后 **20/20 一致**；判据同步收紧成上面第 2 条的「原序直比」。
  顺序不是外观：工具面实测 18KB 对正文 1.1KB，每轮换一次序等于每轮把这段前缀作废。
- **形状确实该变时的姿势**：`PROMPT_SHAPE_UPDATE=1` 重生成 + 在同一条提交/ADR 里说清
  「结构上多了什么、观测到的代价是多少」。基线漂移不是失败，**无人解释的漂移**才是。
