# 能力横向扩充的通路

> 先给结论：**加一个自足的能力今天已经近乎零成本；成本全在「这个能力要被别人用」
> 这一件事上。** 而被别人用**不是**靠插件互相依赖解决的——那是 E-009 的反面，也是
> 本次拆 crate 的全部意义所在。这条路上真正缺的只有两样东西：
> **地址不能声明化**（每加一条跨插件调用都要改一个不属于任何插件的共享文件），
> **共享类型没有上移口径**（每次上移都要现场论证一遍"这算不算扩大内核面"）。
>
> 本文只做这三件事：把零依赖写成可执行的判据、把地址变成生成物、把上移写成一条
> 有登记口的常态动作。

## §0 结论先行

1. **编译期零依赖、运行期寻址，是两条不能混的通路。** 插件之间**编译期**没有任何
   依赖边（不 import、清单不声明、不经宿主门面）；它们**运行期**只通过容器路由互调
   （`ctx.parent()` → `parent.route(ctx)`，地址来自常量），载荷是 `PluginFrame` /
   `PluginPayload` 的 **JSON 形状**，不是某个插件的 Rust 类型。零依赖不等于零互操作。
2. **插件间依赖边 = 0 条，且由 E-009 逐条通路判。** 22 个插件 crate 的 `[dependencies]` 里
   没有一条兄弟插件；源码里 `symbio_plugin_*` 只出现在宿主门面的私有链接行与注释里（`D-417`）。
3. **守卫必须读依赖清单。** 拆 crate 之后兄弟插件是独立 crate，`crate::plugins::<兄弟插件>`
   这个路径不可能存在——约束的物理位置搬到了 `Cargo.toml`：能让插件互可见的唯一动作就是
   加一行依赖。E-009 因此判五条通路：清单（含 `alias = { package }` 改名与
   `workspace = true` 继承两种绕法）、源码裸 `symbio_plugin_<x>`、`crate::plugins` 回退、
   `symbio` 宿主门面（只许 dev）、`include!` / `#[path]` 跨 crate 搬源码。
4. **共享类型只有一条路：上移。** 而 C-003（根出口符号须有 ≥2 个消费方）**恰好在上移
   那一刻满足**——第二个消费者出现，正是上移的时机。所以棘轮不是障碍，它是上移的
   **时机判据**。
5. **跨插件地址由各插件自己声明、生成到宿主。** 8 个 `ROUTE_*` 常量住在
   `crates/symbio-plugin-api/src/routes.rs`，但它是**生成物**：事实源是各插件
   `PLUGIN.yml` 的 `plugin_routes` 行（`scripts/facts/routes-rs.mjs` 读取，并与
   `route()` 臂 / `VDFS_OPS` 逐条核对）。加一条跨插件调用 = 改**自己目录**里的清单。
6. **判据已经先行落地**：`core-change-audit` 的 CC-001 / CC-002 让"改插件却顺手动
   core/kernel"无法不留理由地通过；E-009 现在按清单 / 源码 / 门面三层判定。没有这两条，
   前五条修好半年后必然长回去。
7. **事件词汇已归零（D-203 裁决三）。** 内核 `event/mod.rs` 的业务事件常量与
   `CELLS` 业务行都为 0，`event/grid.rs` 整文件退役：名字 → 格位只有 owner 的
   `EventDecl` 一张表。新插件写一个新事件名只改自己的声明（§3 动作 C，D-204…D-206），
   不动任何共享文件。

## §1 实测：加一样东西到底要动几处

读数取自事实表与判据脚本（`docs/004-ref/006-当前事实表.md`、`core-shape-audit`、
`core-export-audit`）。

| 扩充对象 | 必须人改的落点 | 其中**不属本插件**的 | 漏改时谁红 |
|---|---|---|---|
| 一个自足的工具（只有本插件实现、不被别人调） | 插件内 `Capability` 实现 + `PLUGIN.yml` | 0（链接清单由目录投影） | 不装配 ⇒ 模型看不见它 |
| **一个要被别的插件调的能力** | 同上 + 自己 `PLUGIN.yml` 的 `plugin_routes:` 一行（生成 `routes.rs`） | **0** | E-012（名字↔值同构 / 值可分发）；`gen-facts --check`（幽灵地址 / 生成物漂移） |
| **一个要被别的插件看见的类型** | 同上 + 共享语法层（`symbio-kernel`）的**领域模块**一条 | 1（同一提交，须挂 `Core-Change:`） | C-003（<2 消费方）/ C-004（条数） |
| 一条策略 / 时机 / 执行体 | 插件内 `loop_rows.rs` | 0 | 装载期判据 |
| 一个新能力族 | 插件内 `CapabilityFamily` 常量 + 载荷 | 0 | 读侧 `payload::<T>()` 给 `None` |
| **一个新事件名 / 一条新事实** | 插件内 `EventDecl`（进环再交 `FactDecl`） | **0**（D-197 / D-198 之后） | `seal` 的 `FactWithoutEvent`；写闸 `OffGrid` |
| **一个新视图** | 插件内 `ViewDecl` + `submit_declarations!` | **0**（D-198 之后） | `seal` 的字段 / 证据集检查 |

第三行是唯一需要动 core 的一行，而它同时是**唯一一条本来就该动 core** 的行：一个类型
被两个插件看见，它就不再属于任何一个插件，它属于领域。把它留在插件里，等于让第二个
插件依赖第一个——那正是要禁的事。

配套读数：

- 34 个 crate（22 插件 · 5 provider）；core 非内核根账本 **343** 条，内核公共面 29 条。
- `core-shape-audit` CS-004：内核文件集里插件 id 字面量 **8 处 / 2 个文件**，域文件 **25 处**
  （后者是 C 阶段迁出账，不设门禁）。
- 每个 crate 的 `[dependencies]` 按**真正用到**声明（用不用、带哪些 feature），版本只在根
  `[workspace.dependencies]` 出现一次；`ort`（ONNX）与 `tokenizers` 只在
  `symbio-provider-embedding` 一处。新增一个插件的起点是插件内几条依赖，不是一份含
  ONNX 运行时的清单。
- **这条口径有一个系统性盲区，值得单独记**：日志宏（`plugin_info!` / `plugin_warn!` /
  `plugin_error!` / `plugin_debug!`）在**调用站点**展开，宏体里的 `tracing::warn!` 按调用方
  作用域解析 ⇒ 12 个 crate 对 `tracing` 是真实依赖，而它们在源码里一个 `tracing::` 字面都
  没有。对照 `submit_object_creator!`：它写 `$crate::inventory`，卫生，调用方不需要声明
  inventory。**判据是「宏是否卫生」，不是「有没有 `use`」**——这 12 条已带注释写回清单，
  否则下一次体检会再删一次。

## §2 三个根因

### 2.1 跨插件地址（**已收口**）

`routes.rs` 是宿主侧的地址常量表，存在理由成立（地址是装配方的词汇，不是 core 的
语法，D-184 已裁决）。它的**事实源**现在是各插件 `PLUGIN.yml` 的 `plugin_routes` 行：
`scripts/facts/routes-rs.mjs` 按目录名补前缀，与插件 `route()` 的臂（或 `VDFS_OPS`）
逐条核对后生成常量。声明一条没人能到达的地址直接抛错；生成物漂移由
`gen-facts --check` 判红。

加一条跨插件地址因此只改**自己目录里的清单**，所有插件都依赖的共享文件零 diff。

### 2.2 能力不成包（**放大登记次数**）

一个能力的五个面（实现 / 提示词 / 地址 / 授权行 / 装配位）各自有各自的登记口。前两个住
插件内；后三个都是**清单投影**——地址来自 `PLUGIN.yml` 的 `plugin_routes:`（生成
`routes.rs`）、授权行来自 `principal_*`（生成 `rows.gen.rs`）、装配位来自目录与
`PLUGIN.yml`（生成链接清单与 `symbio-deploy`）。五个面没有一处以「能力包」为单位：
它们分散在同一插件的多个文件与几条生成链里。

### 2.3 词汇写进语法 + 物理门槛（**成本，不阻断**）

`Principal::tool_principal` 认的命名空间是一张**生成表**（`TOOL_NAMESPACES`，来自各插件
`PLUGIN.yml` 的 `tool_namespace:` 行），而不是内核里手写的白名单。`mcp` / `agent` /
`legacy` 三个是拼接规则的产物，住 `principal.rs`。一个**没声明** `tool_namespace` 的
插件（如夹具 `glossary`）的后果：

```text
tool_principal("glossary_define") -> Tool  legacy/glossary_define   ← 没进自己的命名空间
from_legacy("glossary/define")    -> Agent glossary/define          ← 族判错（未知 namespace 按 Agent 兜底）
tool_principal("vdfs_write")-> Tool  vdfs/write         ← 声明过命名空间，正常
```

**如实说：这不阻断功能。** 两者都是 `Tool` 族里的一次地址退化（前者）或一次 fail-closed
的族兜底（后者），授权表按 id 精确判，不会因此放权。它影响的是**身份地址与统计口径**——
未声明的插件工具落在 `legacy/` 下，地址里看得见。所以本项降级为报告项（§4 的 D-195），
不占施工排期。

物理门槛只剩链接图事实：插件要进 `inventory` 必须以依赖形式被链接，而那一行由目录投影
生成（`GEN-002`），加插件时不改共享文件；插件自己只声明「用哪些依赖、带哪些 feature」。

## §3 方案：三条动作

### 动作 A（原则）：编译期零依赖，共享一律上移

**不开任何形态的插件间依赖口。** 没有 `contract` 模块，没有"只许类型"的例外，没有
"经宿主门面再导出"的后门——三者都是同一条边的三种写法。

跨插件要用的东西，只有三条合法出路，按代价排序：

| 需要共享的东西 | 出路 | 代价 |
|---|---|---|
| **数据**（调用的入参与结果） | `PluginPayload` / `PluginFrame` 的 JSON 形状。双方各自 `payload::<T>()` 反序列化到**自己的**类型 | 0 |
| **词汇**（地址 / 能力名 / 事件名） | `PLUGIN.yml` 声明 → `scripts/facts/` 生成（动作 B） | 0（改自己目录） |
| **类型**（同一领域对象的结构） | 上移共享语法层的**领域模块**（不是门面出口），按 C-002 的深引规则消费 | C-004 +1~3，须挂 `Core-Change:` |

第三行不是妥协，是**归属判定的正确结果**：一个类型同时被两个插件看见，它就不属于任何
一个插件。D-180 说的「归生产者 owner」指的是**谁登记**（哪个域的账本），不是**放在谁的
crate 里**——把后者当成"允许依赖"的依据，等于用「谁先写」取代「谁在用」。

**上移的时机由 C-003 给出**：第二个消费者出现时，≥2 消费方条件自动满足，棘轮不挡路。
所以"上移"从来不是"突破棘轮"，而是"棘轮一直在等的那个时刻"。

**样本：`agent → vdfs` 的根地址**（`crates/symbio-plugin-agent/src/host/subagent.rs` 的
`session_vdfs_addr`）

它要拼子会话的 VDFS 地址，需要三样东西，各自落在一条出路上：

| 需要什么 | 落在哪 | 形态 |
|---|---|---|
| 地址 | `symbio_plugin_api::routes::ROUTE_VDFS_ROOT` | 宿主词汇常量（动作 B 之后是生成物） |
| 调用 | `ctx.fork()` → `set(PATH, …)` → `parent.route(c)` | 容器路由，运行期寻址 |
| 响应 | `symbio_kernel::vdfs::VdfsListResponse` | 领域类型 |

零 `use symbio_plugin_vdfs`。第三行是关键：若这里只拿 `Value` 再手写 `v.get("path")`，
`vdfs` 改字段名不会让 `agent` 编译失败，只在子会话订阅时抛 `InternalError`。而
`VdfsListResponse` 的两个字段类型（`VdfsNode` / `VdfsItem`）本就在 kernel，上移只是把
"已经在共享层的零件"拼成一个共享层的类型——这是 C-004 该涨的那一次，不是新开出口。

**判据覆盖五条通路**，任何一条被破都能红：清单声明（含改名与 workspace 继承）、源码
`use`、旧形态 `crate::plugins::<兄弟>` 回退、宿主门面 `symbio` 进生产依赖、
`include!` / `#[path]` 跨 crate 搬源码。**已知边界**：这是文本判据，拦的是
"写出来的依赖"；运行期动态加载（`libloading` / dlopen）不在模型内——本仓插件是编译期
链接的（`inventory`），若将来引入动态插件，那是另一套隔离模型，不是本条能覆盖的。

### 动作 B：地址与能力都走向声明 + 生成

- `PLUGIN.yml` 的 `plugin_routes:` 段声明地址，`scripts/facts/routes-rs.mjs` 生成
  `symbio-plugin-api/src/routes.rs`（常量名保持 `ROUTE_*`，消费方只引常量）。
- 同一条路继续走：`principal_*` 投影授权行、`shared_events` 投影事件名、`tool_namespace` /
  `trigger_kinds` 投影内核表。视图名的公开动作不走清单投影，而是 owner 自己在
  `decl.rs` 里 `submit_reports!` 一条报表描述符（`D-387`）。能力本身由
  `submit_object_creator!` 在链接期发现（`inventory`），不另立能力清单——只有「跨插件
  可见」这件事需要声明，而它按面各写一行。
- 生成物的守卫：手改判红（与 `gen-facts --check` 同一条路）。

效果：加一条跨插件调用 = 改**自己目录里**的 `PLUGIN.yml`，共享文件零 diff。

### 动作 C：把新增插件的物理门槛压下来

各 crate 只声明**真正用到**的依赖（用不用、带哪些 feature），版本只在根
`[workspace.dependencies]` 出现一次；内部 crate 之间仍写 path——相对路径是目录结构的
投影，上提到根反而多一处要同步的地址。

口径是「源码零引用」，可判（多删一条 cargo 立刻报错，少删一条没有收益），唯一盲区是宏的
隐形依赖（§1 末条）。`ort` 的 341 MB 预编译产物只挂在一个 crate 上。

派生判据：新增插件要改的共享文件为零——链接清单由目录投影（`GEN-002`），版本在根上
一次性登记；插件自己只写「用哪些依赖、带哪些 feature」。

## §4 判据

| 编号 | 判据 | 状态 |
|---|---|---|
| E-009 | 插件不得依赖兄弟插件：清单不声明 · 源码不引用 · `crate::plugins` 回退 · 宿主门面只许 dev · `include!`/`#[path]` 不跨 crate | **已落**（五条通路，测试代码同样判） |
| CC-001 | 触及 core/kernel 的提交必须带 `Core-Change:` 段 | **已落**（`scripts/arch-change-audit.mjs`；core crate 退场后该判据改判 `symbio-kernel` / `symbio-sdk`） |
| CC-002 | 同一提交既动插件又动 core/kernel 时，理由里必须有决策号 | **已落** |
| GEN-001 | `routes.rs` 是生成物，手改判红 | **已落**（`scripts/facts/routes-rs.mjs` 生成；`gen-facts --check` 判漂移，生成器逐条核对注册处） |
| EC-001 | 新增插件必须人改的落点 ⊆ {插件目录, `PLUGIN.yml`} | **口径成立**：链接清单 / 地址 / 授权行 / 装配表全是目录与清单的投影；`gen-facts --check` 判生成物与目录一致 |

早期一条审查意见（「`contract` 模块只放类型」）已作废：依赖口本身被否，闸门随之取消。

判据的取舍理由：**CC 是唯一能拦"原因"的一条**。C-003 / C-004 判的是 core 出口宽度（结果），
而"为了让新插件跑起来在内核里加个分支"是一次提交的意图，静态扫描看不见。

## §5 不做清单

- **不开任何形态的插件间依赖**：`contract` 模块、`pub use` 转发、dev-dependency 通融、
  "只依赖类型不依赖实现"——一律不行。零依赖是拆 crate 的全部意义，破一次就不再有边界。
- 不把 `symbio-plugin-api` 扩成"第二个 core"。它是**宿主词汇**（地址、钩子），不是任意共享类型的
  垃圾场——把共享都倒进去只是给同一份账本换名字（D-188 已经拒过一次同形态的候选）。
- 不为了"统一"把 core 的机制类型搬去插件：机制必须只有一份实现。
- 不给"声明数 / 变体数"再加计数器——扩展夹具才是可执行的判据（DE-023 §2 末尾）。
- 不为 §2.3 的工具命名空间另开一轮重构：名字由插件的 `tool_namespace` 声明投影，
  未声明的插件看得见地落 `legacy`；它不阻断功能。

## 关键决策

### D-192（修订）插件间编译期零依赖，互操作只经容器寻址

**原方案已否决**：曾计划"按 DAG 开放插件间依赖，只许经对方的 `src/contract.rs`"。否决理由是
它把架构公理当成了可以打折的约定——一旦允许一条边，就没有理由拒绝第二条；而"只许类型"的
闸门需要一个**每周都在现场判断"这算行为还是类型"**的人，那不是一个可执行的判据。

现在的定位是：**编译期零依赖（E-009 三层判定，物理保证）+ 运行期寻址（容器路由 +
`PluginFrame` JSON 形状）**。前者保证插件可独立卸载、独立编译、独立演进；后者保证它们
仍然能互相调用。这两件事从来不是同一个问题。

代价与边界：跨插件调用的载荷**没有编译期类型检查**，错在运行期（`payload::<T>()` 返回
`None` 或反序列化失败）。这是明确的取舍——用"形状约定"换"零依赖"，并用装载期判据 +
`PluginPayload` 的显式形状覆盖错误面。

### D-193 地址与能力一律声明 + 生成，手写共享表退出

`ROUTE_*` 从手写常量改为 `PLUGIN.yml` 的投影（`scripts/facts/` 生成）。理由：地址是**装配方的词汇**
（这一点 D-184 已经裁决），而装配清单早已是生成物；唯一手写的共享表就此消失。
常量名保持不变，13 个消费方文件零改动——这是"先换来源、再谈形态"的顺序。

**落地形态**：`PLUGIN.yml` 的 `plugin_routes`（相对臂，逗号分隔）是唯一声明处；
`scripts/facts/routes-rs.mjs` 生成 `crates/symbio-plugin-api/src/routes.rs`，并逐条
核对声明地址是否真在插件的 `route()` 臂 / `VDFS_OPS` 里——声明幽灵地址直接抛错。
E-014（手写常量数只许降）的判据对象（手写表）不再存在，该编号随之退场；
生成物漂移由 `gen-facts --check` 判红（GEN-001）。

### D-194 依赖版本上提到 workspace，插件只声明用到的

22 个 crate 抄同一份 45 行清单（含 `ort` / `reqwest`）。新增一个插件的第一个动作不该是复制
一份包含 ONNX 运行时的清单。

### D-195 principal 的插件命名空间按部署事实派生，且降级为报告项

kernel 里的命名空间白名单是词汇写进语法的残留，但**不阻断扩能力**（实测只造成 `legacy/`
地址与族兜底，不影响授权）。等动作 B 落地、插件 id 集合成为可查询的部署事实之后，
由 `symbio-deploy` 的 id 表派生，kernel 只留纯函数接收集合。

### D-196 共享类型一律上移，归属按领域判而不是按插件判

一个类型被第二个插件需要时，它已经不属于任何插件，属于领域；上移到共享语法层（`symbio-kernel`）的对应
**领域模块**（不是门面出口），按 C-002 的深引规则消费。

这条给 D-180 补上了落点：D-180 说「归生产者 owner」，此前无处可执行，因为它被读成"消费方
依赖生产者的 crate"。正确读法是「登记在生产者的**域账本**里」——物理位置在 core，
owner 是那个域。C-003 的 ≥2 消费方条件在上移那一刻自动满足，因此棘轮不构成阻力。
样本是 §3 的 `agent → vdfs`（`VdfsListResponse`，core 账本 396）。

被否候选：允许插件开 `src/contract.rs` 供他人依赖。见 D-192 的否决理由。

### D-197 事件格位随 owner 声明走，`EventDecl` 与 `FactDecl` 分表

`Entity` × `Verb` 仍是封闭语法（F5），**名字与格位不是**：每个事件名由 owner 插件交
一行 `EventDecl { name, cell }`，`Frozen` 建 name→cell 表，写闸按它判定。
`seal` 额外要求「插件声明的事实都能在事件表上找到同名行」（`FactWithoutEvent`）。

**为什么不把 `cell` 塞进 `FactDecl`。** 一张表回答两个问题会逼其中一个说谎：

- `FactDecl` 是**义务环的输入**，只有进环的事实才需要 `port` / `key` / `expand` /
  `fields`，且必须满足判据 7（声明事实有归宿）。业务事件里只被投影读的那些没有行、
  没有视图，进这张表就会被判成孤儿。
- `EventDecl` 是**网格的输入**，每个名字恰有一格，与字段、端口、环无关。

**被否候选**：

- 给 `FactDecl` 加 `cell` + `ring: bool`：`ring` 标记会变成第二份真相——「到底谁在
  环里」由行与视图已经回答过一次，再加一个布尔位就有两个答案。
- `EventKind` 枚举：加名字 = 改 core 的枚举，正是 F5 / [DE-001 §6](001-核心架构.md "DE-001-核心架构") 要避免的 L-schema 变化。
- 保留 `CELLS` 再生成一份副本：两份表必然漂移，而漂移的表现是**静默少一条事实**。

**闭族的随之调整。** 名字与格位搬回 owner 后，loop 的驱动器写事件只能从自己的声明
表取名；E-013 的闭族因此承认 `crate::control_decl`——它装的是 loop 自己的事件词汇与
控制面声明，**没有**兄弟插件的实现面，E-013 要拦的正是后者（D-083 §4 的答案：它代表
loop 自己的事实词汇）。

迁移期 `CELLS` 与 `EventDecl` 并存，parity 用例逐条钉住两边相等；业务事件归零后
`CELLS` 只剩协议五格，随后整表随 `event/grid.rs` 退役（D-203）。

**迁移存量与停止条件。** 内核 `event/mod.rs` 里的业务事件常量与 `CELLS` 的业务行是
**读侧词汇**：core 的投影与判据（`event_node_of` / `rebuild` /
`transcript` …）按名字读它们。CS-005 把这两格冻结成只许降，而**当前条数只由那道守卫
报出**——写在这里的数字记不住自己。它们**不再是扩展口**——
新插件的新事件经 `EventDecl` 落格，不需要进这两张表；一份新能力只有在 **core 自己
要对它做判定**时才需要 core 侧词汇，那时加的是 core 的行为，不是插件的能力。
删除存量要等对应读方随 owner 迁出（读写同源），在那之前逐条删除会让 core 的判据
只能猜名字；每迁走一条就同步下调基线。**这条停止条件在三批迁出后由 D-202 判定执行
完毕**：留在内核的每一条名字都有了逐名的据，而据现在是一道门禁，不是一张人工核对的表。

### D-198 声明表是装配期产物，经链接期收集

`crates/symbio-plugin-loop` 的私有 `Builder::declare` 不再是唯一生产入口：任何插件都可以在模块
作用域调用 `symbio_plugin_api::submit_declarations!(owner, make)`，声明表随二进制在
链接期收集；装配方按 owner 排序后逐个 `declare`，一次 `seal`。插件仍只依赖
`symbio-plugin-api`（它已依赖 `symbio-sdk` 的声明容器），**不认识任何兄弟插件**，
E-009 的零依赖判据不受影响。

**为什么收集点住 `symbio-plugin-api` 而不是 core / `symbio-deploy`。**

- 住 core：会新增 root 出口（C-004 是只许降的棘轮），而声明表是**装配**的账，不是
  封闭语法；
- 住 `symbio-deploy`：它今天是零依赖的名词表，加 `symbio-sdk` + `inventory` 会把
  装配清单 crate 变成机制实现，且生成文件要额外维护一个手写模块；
- 住 `plugin-api`：所有 21 个插件已经依赖它，`inventory` 与宏卫生同
  `submit_object_creator!` 一条路，零新依赖边。

**被否候选**：生成一份「插件 → 声明构造函数」的手写清单。声明是 Rust 数据
（`FactDecl` / `ViewDecl` / `Decl` 的字段都是 `&'static` 切片），不是 YAML 能表达的
形状；先生成再编译等于给同一件事加第二个生成器和第二个会漂的模块列表。

### D-199 写闸按「实例 → 进程 → 共享表」取格位（**已收口**）

`WalStore` 在打开时挂上装配期 `Frozen`（`with_declarations`），写闸按「本实例冻结表
→ 进程装配表 → 清单生成的共享表」的顺序取格位；三份都不认识 ⇒ `OffGrid`（fail-closed）。
迁移期的第三条回退（内核名字表）已随 D-203 归零删除——内核不再替任何人记名字。

删除顺序不能反：内核表曾是 45 个名字 × 多插件的读面，一次性删除无法独立回退；而
「先让新名字能经声明表落格、再逐个迁旧名字」每一步都可回退，且新插件从第一天起就
不需要改内核。

**被否候选**：等全部迁移完成再切写闸。那段时间新插件仍然写不出新事件——正是要修的
那处泄漏；且切换当天的失败面最大。

### D-200 扩展夹具必须端到端，词汇棘轮只许降

现有的「事实扩展」夹具只声明一条事实并断言 `Frozen::fact` 存在，**从不构造事件、
从不 append**——写闸坏了它仍然绿。判据改为一条端到端路径：

```text
declare(EventDecl + FactDecl) → seal → append 一条该事件 → range 读回
```

两个方向都要有反向用例：不在表上的名字被 `OffGrid` 拒；在表上但自述挪了一格也被拒。
端到端夹具住在**拥有写门的 crate**（`symbio-plugin-session` 的
`injected_declarations_are_the_grid_the_gate_reads`）；`symbio-testkit` 的五类夹具只到
声明面，两处各判一半、不复制第二份写闸。

词汇棘轮按「只许降」冻结：内核业务事件常量数、`CELLS` 业务行数、单消费方 core 投影数。**不新增「声明数 / 变体数」计数器**——计数可以在通道完全不可用
时保持绿色，端到端夹具不能。这四个数各自的 owner 就是现在解析它的那道守卫
（`core-shape-audit` / `plugin-entry-audit` / `core-export-audit`），不另立第二份扫描。

### D-201 域投影搬到唯一消费方，词汇随投影退役

D-197 的停止条件（读方随 owner 迁出后才删存量）在首批之后撞上形状：剩余 32 条业务

拿它判「这条事实的载荷折成哪个节点」，`actors/*` 拿它做配对。删名字必须先迁读者。

**裁决：按消费方分布搬投影——只有唯一插件消费方的域投影，随该插件走；名字与 core 根
出口一起退役。**

### D-202 留在内核从默认状态改成需要证据的状态（CS-006）

三批迁出把 CS-005 从 40/38 推到 30/29，但**那个数字说不出这 30 条凭什么还在这里**。
D-201 的归属判据当时是一张人工核对的表，而人工核对的表会在下一次搬家时失效；最容
易重新长回来的形状恰好是「只有一个插件读、core 已经不读」——它不再减少，于是静静地
躲在只许降的数字里。

**裁决（本条的定性部分被 D-203 作废，落地机制 CS-006 由 D-203 翻转方向后保留）：把 D-201
的判据落成逐条门禁 CS-006（owner：`core-shape-audit`）——一条内核
业务事件名要留在内核，必须给出下面两种据之一：**

| 据 | 怎么判 | 为什么它属于内核 |
|---|---|---|
| ① ≥2 个 crate 生产消费 | 插件 / provider 各自的生产代码里出现该常量**或**该线上名字 | 独占它就得让另一个插件跨墙引用兄弟插件（E-009），所以它只能是共享词汇 |
| ② 共享层生产代码读它 | `symbio-sdk` / `symbio-kernel` 除那两张登记表以外的文件读它 | 读写同源（D-197）：名字的归属跟着那条读者（投影 / 判据）走，读者还在共享层，名字就还在共享层 |

第三种形态（恰好一个消费方且 core 不读）**判红并点名**该随哪个 owner 的 `EventDecl`
走；谁都不读的同样判红。口径的四个细节都是为了「不误报也不空转」：`pub use` 转手不
算读者（出口是账本，不是归属证据）；被 CS-005 数的那两张表自己不算读者（它们是名字
的登记处）；注释与 `#[cfg(test)]` 剥掉；`symbio-plugin-api` 是宿主↔插件的协议 crate，
它的引用不构成「某个插件在读」。夹具仓库没有插件 crate ⇒ 不适用并明说。

**实测（30 条全绿，`--verbose` 可逐条复算）**：① 12 条——`user.message` /
`turn.branch` / `chat.assistant.final` / `fallback` / `progress` / `session.consolidated`
/ `memory.encoded` / `task.controlled` / `task.opened` / `progress` / `held` / `asserted`；
② 18 条，读者住在 `invariants`（收束与停机）、`rebuild` / `transcript` / `prompt_fidelity`
（节点折回与保真度）、`mutations` / `branch` / `readyset` / `autonomy` / `calibration` /
`reputation` / `turns` / `turnstate` / `changes` / `fallback` / `slo`、`actors/commitment` /
`actors/control`（写侧成格与读侧翻译）。

**曾挂着的两个待裁决名字就此定案**：`task.controlled` 的写方在两个插件各一个（熔断
与拒因在 loop 的工具闸、打断处置在 session 的 inbox），`verdict.asserted` 写侧在 loop
轮末、读侧翻译在 session——两者都**不是待迁存量**，留在内核的理由是 E-009；
`memory.encoded` 同（第三批已记）。`commitment.*` 四条则是另一种形态：插件从不命名
它们，两侧都经 core 的成格函数与翻译函数（`commitment_events` / `commitment_records`）
进出，名字因此跟着那条配对规则住 core。

本条当时的结论是「D-197 的停止条件执行完毕，CS-005 记的是有据的内核词汇」——**那句不成立**，
由 D-203 作废：据② 是硬编码的自证，而往内核两张表加一条**新**共享名字（两个插件都要写、
core 不判定）按本条的据会判绿。CS-005 / CS-006 拦住的只是存量再长大，拦不住增量走正道，
因为当时**没有**正道。

**被否候选**：

- **只把结论写进 D-201 那张表，不落地成判据**：下一次搬家就没人重新核，而「单消费方
  的名字赖在内核」正是这张表要防的形状。
- **把 CS-005 直接归零**：当时判定剩余 30 条里 18 条的读者是 core 的语义脊柱，把它们塞进任一
  插件要么 E-009 判红，要么让脊柱去认插件实现坐标（CS-003 判红）。归零不是目标，
  「新能力不再往里加」才是。**本条被 D-203 推翻**：那 18 条的读者之所以存在，是因为
  判据把名字硬编码在 core 里；脊柱读的是格子与角色，不是名字，归零就是目标。

### D-203 判据读格子与角色，不读名字——内核业务事件名归零

D-202 把「留在内核」变成需要证据的状态，方向是对的，但它给的两条据把因果写反了：据①
（≥2 个 crate 同字符串）会把「两个插件共享一条 core 根本不判定的新事件名」判成合格——
那正是「扩展功能就得改内核」这件事本身；据②（core 读它）守住的是一份手抄副本，因为
core 读一条名字**恰恰是因为**这个名字抄在内核里。两个插件共享一个新名字的通路仍然只有
「改内核两张表 + 一条 `core-shape-allow`」，所以本条推翻 D-202 的定性，并把判据本身改掉。

**复核九条「守卫输入」得到两个事实：**

1. **执法点从来不在内核。** I1 / I2 / I3 / N3 全部由 `crates/symbio-plugin-session` 的写闸执行，它查的
   是 `Frozen`（唯一写入口 `AppendError::OffGrid`）。内核那张表不是执法者，是登记处的副本。
2. **副本已经在漂移。** `chat.assistant.final` / `.fallback` / `.progress` 同时是 loop 自己
   `EVENTS` 表上的 `EventDecl` 与内核常量——**登记早就在 owner 手里了**，内核那一行只剩下
   「core 的判据要拿这个字符串比一下」这一个作用。删掉它不会让守卫失能，只会逼判据去查表。

而不可撤销性本来就不来自「住在内核源文件」：`Frozen` 自带 owner 归属表、装载期一次成型、
之后只读——插件改不动冻结表，与改不动内核源码是同一种强度，且前者是整个装配过程的性质，
不依赖某个文件归谁。所以「守卫的输入不能被被守卫者撤销」这条真需求，正确的落点是**冻结表**，
D-202 却把它落在了内核名字表上。

**裁决（三条）：**

**一、五处判据改成只看格子——名字那一维本来就是冗余的。** 逐条对照 `CELLS` 的同行成员：

| 判据 | 现形 | 改后 | 等价的理由 |
|---|---|---|---|
| `is_turn_open` | `turn×opened` ∧ `user.message` | `turn×opened` | 该格只有这一个名字；「落在开轮格」就是开轮的定义，不是某个名字的属性 |
| `closes_turn` | (`turn×closed` ∧ final∣fallback) ∨ (`artifact×asserted` ∧ `artifact.added`) | `turn×closed` ∨ `artifact×asserted` | 同上；且新名字落这两格**应当**算结算——原来它会被静默漏掉 |
| `needs_provenance` 的 turn 两臂 | 按四个名字点收 | `turn×closed` ∨ `turn×progressed` | 整格都在宣称「已答复」或「用户看得见的动静」，都要溯源。协议族当初刻意不落 `progressed`（`CELLS` 的注释）正是为了绕开点名单——格子判定之后不需要这层绕行 |
| `is_stop_fact` 的 closed 臂 | `turn×closed` ∧ final∣fallback | `turn×closed` | 收束格上的每个名字都回答「这一轮为什么停」 |
| `verdict_grants_changes` | `verdict×asserted` ∧ `verdict.asserted` | `verdict×asserted` | 该格只有这一个名字 |

**二、同格确实要区分两个名字的，区别落成声明里的一维角色，而不是内核里的一个名字。**
`EventDecl` 增加 `roles: &'static [FactRole]`；`FactRole` 是内核持有的**闭集小枚举**，本批
四档：`finalizes_scope`（本 scope 的定稿发言，`final` 独占——`fallback` 不算，读侧收束闸比写侧宽）、
`stops_scope`（回答「为什么停」的否定事实，`model.speech.denied`——语音键拒因；工具侧的授权拒因不带角色，D-390）、`declares_budget`（本 scope 预算档，
`turn.dispatch`）、`counts_rework`（重做计数，`task.rework_created`——终止前提的计数对象）。
判据经 `Frozen::has_role` 读它。这四档答的是「这条事实在判据里扮演什么」，是**语义**；语义
集合小、稳定，加一档罕见且必须论证——那才是精简架构该有的边界。「任何新名字都算架构变更」
不是边界，是把边界画错了地方。

**三、判据的词汇随数据传，不留全局副本。** 迁移期三级回退（实例 `Frozen` → 进程声明 → 内核
`CELLS`）在内核表归零后删除；回退命中不再静默，与 I3 同一条纪律（`plugin_warn!` 点名）。

**数字：** 内核业务事件名 30 → **0**；`CELLS` 业务行 29 → **0**（协议五格留在网格表）；
core 生产代码引用业务事件名 → **0**。通路分三类：角色名随 `roles` 放出（9）；单消费方的
折叠名随投影迁出（D-201 那条路，11）；多消费方的折叠名改读「格子 + `FactDecl` 载荷形状」，
需要点名单的最后一类（节点折回形状）把形状本身交进声明（8 + `commitment.*` 4）。

**被否候选：**

- **进程级全局角色登记表**（`OnceLock` 供纯函数读）：判据从「读入参」变成「读全局」，而
  `docs/003-design/verify/` 的可执行论证与 core 单测都在**没有装配**的进程里跑——它们会读到
  空表，守卫全绿而实际不判。这正是 J3 点名的静默失效形状。
- **按载荷字段 duck-type 区分 `final` / `fallback`**：把「这条事实的语义」推给载荷猜测，改载荷
  等于改判据；声明里的一维角色是同一信息的显式形态。
- **保留内核名字表当「读侧词汇」，只加棘轮**（D-202 原方案）：见本条开头。

**D-201 / D-202 中被本条作废的部分：** D-201 被否候选第二条「投影改成按格位读、不认名字……
等于把载荷形状推给调用方」——载荷形状那一维 `FactDecl{port, key, expand, fields}` 早已声明化，
缺的只是角色，不是不可能；D-202 的据②与「剩余的不是待办存量，而是**有据的内核词汇**」的定性。
CS-006 随之翻转方向：从「给留下的名字找一条据」改成「core 生产代码里出现业务事件名即判红」，
与 CS-005 一起构成只许降的两格。

**本批落地（裁决一 / 二 / 三的当批部分）：** `FactRole` 四档与 `EventDecl::with_roles` 就位，
core 的九条判据改成「格子优先、角色兜底、名字不出现」——判据的词汇面是**形参**
（`check_all(vocab, …)`），由调用方交出冻结表；「每一档都有人住」当时打算由装载口（loop 的
`load` 拒空转）钉住，**实际落在整仓判据 `CS-011` 上**（`scripts/shared-event-vocab-audit.mjs`
逐档查插件生产声明里的 `FactRole::*`）：装载口判不了这件事——`assemble_declarations` 也会被
只链接了部分插件的用例调到，那种子集装配缺档是假红。内核表那条「回退臂必须住满每一档
角色」的用例随本批作废——它把迁移存量当成了词汇源，而词汇源是装配表：名字迁出，这张表上的
角色就该跟着变少；现在的对应用例只判「表上仍有的每一行，角色读得回来且不多认」（`decl/mod.test.rs`）。
写闸的三级回退命中改点名（`plugin_warn!` 一次）。

**第一条走新通路迁出的名字**：`task.rework_created` — core 的 `rework_bounded` 读
`CountsRework` 角色之后，它的唯一生产消费方只剩 loop，CS-006 逐名点出 ⇒ 内核常量与 `CELLS`
行同批退役，名字随 loop 的 `EventDecl` 走 ⇒ CS-005 **30/29 → 29/28**。core 单测里那条判据
因此交出**自己造的一行**当词汇面（`actors/mod.test.rs` 的 `REWORK_VOCAB`）——这正是「词汇是
数据」的可执行证据：判据不为任何插件改名，装配表由 owner 交来。CS-006 的方向翻转（core
生产代码出现业务事件名即判红）要等剩余 28 条的读者迁完，那一跳才是归零的封口——落地形态见下
（不是把 CS-006 翻转：它的输入是内核那张表，表归零之后它**没有输入**了，翻转要另立一格）。

**归零批落地（那一跳）：** CS-005 **21/21 → 0/0**，CS-006 **≥2 crate 消费 0 · core 读者 0**。

- **`event/grid.rs` 整文件退役**：`CELLS`（名字 → 格位）与 `event_cell` 一起删。名字 → 格位
  从此只有一张表——owner 的 `EventDecl`，`declare` 一次交齐、`seal` 装载期核。`PROTOCOL_EVENTS`
  留下，它是内核唯一还需要「名字 → 格位」的地方：协议五格由内核预置，不属于任何 owner。
- **内核里最后一处按名字点收搬出**：`event_node_of` 的三目键（21 条业务名字 → 节点 id）拆成两半。
  载荷规则留在内核（`event_payload_node_id` / `event_produced_text_node_id` /
  `event_output_text_node_id` / `event_tool_result_node_id` / `event_answer_node_id`——它们只读
  `payload`，不问名字）；「这条名字落在哪个节点」的判据按词汇面搬进 `projection/vocab.rs` 的
  `slot_node_of`，判据读 `ChatSlot` 枚举 ⇒ 加一档是编译期不穷尽，不是静默漏一档。
- **一张表拆成三张按面切分的表**：`ChatVocab`(11) / `MessageVocab`(5) / `CommitmentVocab`(4)。
  合并成一张 20 字段的表更省事，但那会把耦合面说宽：`reputation` 只认承诺四条，`changes` 只认
  产物一条——让它们各收一张全表，等于让每个读侧都得知道全族名字。**判据是「这张表多大」，
  不是「名字在不在里面」**：表的大小必须等于那个折叠算法真正的依赖。
- **共享表必须投影角色**（本批发现的生成器缺口）：`CELLS` 的第三臂曾在迁移期替所有名字答
  「扮演什么角色」。那一臂删掉之后，`symbio-plugin-api/src/events.rs` 若只投影「名字 + 格位」，
  `is_turn_final` / `is_stop_fact` 会**静默失效**（守卫永远看见「没有名字扮演这档角色」）。
  修在生成器上（`facts/events-rs.mjs` 对带角色的行输出 `EventDecl::with_roles`），不是在运行时
  补一条回退——回退一旦存在，「角色没交」这件事就再也不会红。
- **`verdict.asserted` 退出共享清单**：唯一写方是 loop，session 读的是**格子**不是拼写。
  CS-007 的「owner 外要有真消费方」它不满足，于是拼写改由 owner 自己持有——共享清单收的是
  **多消费方的拼写**，不是「有人提到过这个名字」。
- **`symbio_plugin_api::vocab()` 成为「没有内核表」的词汇面口径**：冻结表在 ⇒ 读冻结表；
  不在 ⇒ 读共享表；都没有 ⇒ `None`（fail-closed，`OffGrid` 照报）。删掉的是**内核表那一级**，
  不是判据。
- **判据翻转落成 `CS-008`，不是翻转 CS-006**：CS-005 与 CS-006 的输入都是内核那张表，
  表归零之后两者都**没有输入**——一个没有输入却常绿的判据挡不住名字从第二条路回来：
  `match e.kind.as_str() { "chat.assistant.final" => … }`。`CS-008` 直接判 core / kernel 的
  生产代码里不出现事件名字面量，判据形状是「首段是 `Entity` 的某个变体（小写）」——
  `Entity` 是 F5 冻结的闭集，所以这一族可判别；`"text.plain"` / `"application/json"` 这类
  同形串首段不在闭集里，自动落在闸外（与 D-009 的「同族」闸同一思路：闭集收窄，不用豁免兜底）。
  `#[cfg(test)] mod x;` 声明的夹具文件被剔出判据面——夹具交自己的字面量是合法的，而且正是
  D-205 / D-206 要的证据形态。

**验收口径的兑现方式**：加一条新事件名，动的是 owner 的 `EVENT_*` 常量 + `EVENT_DECLS` 一行 +
（若跨插件）`PLUGIN.yml` 的 `shared_events` 一行。`CS-005` 没有可增的行，`CS-006` 不会为它
生成条目——「新名字需要内核动作」这条边已经不存在，剩下的唯一动作在 owner 自己家里。

### D-204 跨插件事件名的登记口是清单：共享词汇表由生成物承担

**这一条补的是最后一条「只能住内核」的据。** D-203 把 core 读侧的账清掉之后，剩下的名字里
有一类的理由不是守卫、也不是 core：`memory.encoded` 的读侧在 loop 与 session 两个插件里，
`task.controlled` 的写侧在两个插件里各一个，core 一行都不读。D-202 据此写下「两个插件同时
消费的名字不能被任一插件独占（E-009），故留在内核」——**这条推论不成立**：E-009 禁的是插件
之间的那条依赖边，不禁「名字由 owner 的清单登记、投影成一份谁都能依赖的共享常量表」。同一
形状在地址侧已经走过：`PLUGIN.yml` 的 `plugin_routes` → `routes.rs`（D-193）。留在内核的
真正代价是：**下一条要跨插件的能力仍得改架构文件**，正是本设计要修掉的形状。

**裁决（三条）：**

**一、跨插件事件名由 owner 在自己目录的 `PLUGIN.yml` 里登记（`shared_events:`），投影成
`crates/symbio-plugin-api/src/events.rs`。** 加一条跨插件事件 = 改 owner 自己的清单 +
在 owner 的 `EventDecl` 里给它格位；内核与 core 的文件零 diff。共享表住 `symbio-plugin-api`
（插件唯一可依赖的宿主面），不是住内核——内核的两张表只留封闭语法。

**二、共享表投影「名字 + 格位」两维，角色不在这里。** 写闸问的是「这个名字落在哪一格」，
所以生成物连 `EventDecl` 一起投一份 `SHARED_EVENTS`：链接了 `symbio-plugin-api` 的每个进程
都认得它，不必把 owner 插件链进同一个二进制。`FactRole` 是 owner 交给守卫的陈述，只经装配表
读，不进生成物——两处都能读到角色，角色就有了两个主人。

**三、格位的唯一来源仍是 owner 的声明。** 生成器逐条核对 owner 确实为这个名字提交了带
`(Entity::…, Verb::…)` 的 `EventDecl`，读不到格位就抛错而不是猜——幽灵常量比不生成更坏
（`routes-rs` 同一条纪律）。名字形状（`<域>.<事实>`）与「一条名字两个 owner」也在生成器这一层
拦住：清单读不懂就连生成物都产不出，判据不必再判一遍。**判据 CS-007 判两条红**：除 owner 外
至少一个插件真在引用（单消费方不进共享表）、内核两张表上不许再有这个名字；另有一类**只报数
不判红**——内核表上仍被 ≥2 插件消费、还没走正道的名字，那是待迁存量，拦住它就是把它写成禁令。

**数字：** CS-005 的 27 条里 **12 条**是这一形状（≥2 个插件消费）；本批先走两条 core 完全不读的
（`memory.encoded`、`task.controlled`）⇒ CS-005 **29/28 → 27/26**。剩下 10 条要等 core 的读侧
投影按 D-201 迁出后，逐条登记进清单——那时它们不再需要任何内核动作。

**被否候选：**

- **让第二个消费方复述字面量**：同一个事实两个 owner，改一次要动两处（`CONTRIBUTING.md §4`
  「复述即重复」），而且没人能拦住两处漂移。
- **名字与格位都写进清单**（`shared_events: memory.encoded=memory.opened`）：格位有两个来源，
  Rust 的 `EventDecl` 与清单必然分叉，而写闸认的是装配表。
- **运行期经 `declared_vocab()` 取名字、不生成常量**：读侧要匹配 `e.kind` 字符串，把「名字登记
  没登记」的失败从编译期推到运行期；且 core 的读侧根本链接不到 `symbio-plugin-api`。
- **把共享表放回内核 `CELLS`、只删常量**：常量只是表的一行，留着行就是留着「加能力改架构」的
  那条路。

**本批落地：** `scripts/facts/events-rs.mjs`（生成器 + 幽灵名 / 无格位抛错）·
`scripts/shared-event-vocab-audit.mjs`（CS-007 两条红判据 + 存量提示）· `crates/symbio-plugin-api/src/events.rs`
（生成物）· loop 的 `PLUGIN.yml` 加 `shared_events:` 并在 `control_decl::EVENTS` 交出这两条的格位 ·
`store/wal.rs` 的词汇面加**共享臂**（实例 `Frozen` → 进程声明 → 共享表 → 内核 `CELLS`，最后一臂
随内核表归零一起删）· 内核删两条常量与 `CELLS` 两行 · core 的根出口删掉这两条名字，core 单测改交
**自己的字面量**（与 D-203 的 `REWORK_VOCAB` 同一形状：词汇是数据）。

### D-205 投影的词汇面是形参：core 的折叠不再抄业务事件名

**这一条把 D-203 的纪律从守卫推广到投影。** 守卫侧已经改完（九条判据从 `vocab` 形参取角色）；
剩下的 16 条「core 读者」全住在投影里——`calibration` / `fallback_rate` / `slo_report` /
`transcript` / `rebuild` 这些纯函数按名字比对自己的输入。名字比对一次，core 就得认识这个名字，
而认识一个名字就意味着内核必须替它登记格位（`CELLS` 那一行）——于是「给技能加一路观测」又要动架构。

**裁决（三条）：**

**一、`Projection` 的闭包形状不动，词汇进在构造函数上。** 折叠读哪条名字由**交出名字的调用方**
在构造期决定：`calibration_for(observed: &str)`。`apply(events, now, budget)` 三形参是内核语法
（F2 纯净判据按形参集合判），往那儿加词汇等于改语法，且把一次性的构造决定变成每次调用的义务。

**二、名字的来源按调用方分两条，core 一条都不占。** owner 插件用自家 `EventDecl` 旁边那个常量，
第二个消费方用清单生成物 `symbio_plugin_api::events::*`（D-204）。core 既不链接
`symbio-plugin-api` 也不链接任何插件，所以「core 里那条名字」在结构上**无法**由 core 自己提供——
只能由调用方交进来，这不是风格选择。

**三、`memory.calibrated` 走这条通路当第一个例子。** 写方只有技能能力（`row::SkillRecall` 的观测格），
读侧投影 `calibration` 被技能能力（`skill.recall` 的置信度闸与 `skill.retreat`）与 session（`stats` 的校准列）
同时消费，投影因此留在机制层（两个插件共用、纯函数），而**名字登记进 owner 清单**：内核常量与
`CELLS` 行同批退役 ⇒ CS-005 **27/26 → 26/25**（D-262 起 owner 从 loop 换成 `symbio-plugin-skill`；
D-286 起折叠本身也随词汇 owner 进那个包，session 那一半读者改按名字读 `skill.calibration`）。

**被否候选：**

- **把投影搬进 loop 或 session**：两个插件同时消费，搬给哪一边都要让另一边跨墙引用兄弟插件
  （E-009 禁那条边）——搬家解决不了「共用」，只有「词汇进形参」能。**（被 D-286 部分改判**：搬家
  解决不了「共用」的前提是读者只能引用代码；按名字读视图的机制件立起来之后，折叠可以住 owner、
  另一方读名字，`memory.calibrated` 的折叠就此随词汇 owner 进技能包。）
- **给 `Projection` 加词汇形参**（`apply(events, now, budget, vocab)`）：动内核闭包形状，且每次
  读数都要交表；构造期一次决定的东西不该在热路径上重复问。
- **core 继续比对字符串、只删内核常量**：内核常量删了而 core 还写死同一个串，词汇源只是从
  内核换成 core——加能力仍然要改架构模块，本设计要修掉的正是这个形状。
- **按格子认输入**（`Memory × Asserted` 整格都算校准观测）：这一格现在只有校准观测，但格子是
  **共享**的，将来任何落这格的新断言都会被算进技能置信度。本文件注释里那条「不按载荷字段猜输入」

**本批落地：** core 的 `calibration` 折叠构造器改名 `calibration_for`、词汇进在构造期（形参 `observed`）· 技能包的
`decl::EVENTS` 交出它的格位与事实形状、`PLUGIN.yml` 的 `shared_events` 加这一条 · 技能包 `row.rs`
与 session `stats.rs` 各交自己那条名字 · core 根出口删掉 `EVENT_MEMORY_CALIBRATED` · 内核删常量与
`CELLS` 一行 · core 的 `calibration.test.rs` 改交**自己的字面量**（第三个「词汇是数据」的形状：
夹具不需要任何人认识这个名字）。

### D-206 一族词汇是一张结构体：多名字折叠按算法角色分支

D-205 那条通路只解决**一个名字**的折叠。core 剩下的 16 条读者多数不是这个形状——一个折叠
按**一族**名字分支：`readyset` 认五格（建节点 / 推进 / 挂起 / 恢复 / 终态 / 租约），
`autonomy` 认两格。往那儿推词汇，形参的形状要先定下来，否则每条名字加一次、每次都要重裁一遍。

**裁决（四条）：**

**一、词汇进一张按族的结构体，仍是构造期形参。** `readyset_for(vocab: TaskVocab<'_>, cap)` ——
`TaskVocab { opened, progressed, held, terminal, lease }`。字段名是**这一族在算法里的角色**，
不是事件名的拼写：折叠认的是「这一格在我的算法里算什么」，`task.opened` 只是那个角色的当前拼写，
由 owner 交出。

**二、字段按角色命名不是修辞，是这一族的形状逼出来的。** `task.asserted`（终态）与
`task.assigned`（租约）落在**同一格** `Task × Asserted`——用格子名命字段会得到两个同名字段，
用事件名命字段则把「词汇表」降级成「名字表的别名」。按角色命名字段，才是这一族真正的闭集。

**三、名字 → 角色的映射在折叠里做一次，分支换成枚举。** `vocab.role(kind) -> Option<TaskRole>`
把 `match e.kind.as_str()` 的五个字符串臂换成 `match role` 的五个枚举臂，不认识的那一格显式
`None ⇒ continue`。字符串比对留在热循环里，判据就还是名字；换成枚举之后，「这一族有哪几格」
在折叠内部第一次变成编译期的闭集。

**四、同族折叠共用同一张表**（core 的 `readyset_for` 用五格，`symbio_plugin_session::autonomy`
只用 `held` 与 `terminal` 两格）。理由不是省参数：一张表 = owner 交出这一族的**完整**拼写，
同族的几个折叠读同一族就不可能各读各的拼写而漂移。它的代价也随之落地——读一个折叠就要交出整族，
所以 `task.assigned` 尽管只有 loop 写，也随这一族进共享表；session 交出这张表时它就是消费方，
CS-007 的「owner 外要有真消费方」由此**自然成立**，不需要为多名字折叠开一条口径。

**被否候选：**

- **切片形态**（`readyset(cap, &[("task.opened", TaskRole::Opened), …])`）：字段名变成运行期数据，
  少交一格、拼错一个角色都不报错，只剩「投影算出来是空的」这种最难定位的症状；结构体让
  「五格都在」成为类型事实。
- **位置形参**（`readyset_for(opened, progressed, held, terminal, lease, cap)`）：五个 `&str` 相邻
  同型，交换两处编译照样通过而语义反了——`autonomy` 的 `held` 与 `terminal` 一交换，
  「无人干预完成率」立刻变成另一个数，且没有任何东西会红。
- **把 `readyset` 搬进 loop 或 session**：session 的 `stats` 与 loop 的调度段两处都在读它，
  搬给谁都让另一边引用兄弟插件（E-009）——与 D-205 被否第一条同一理由。**同一条判据对
  `autonomy` 给出相反的处置**：它唯一的生产消费方是 session 的 `stats` / `stats_reading`，
  留在 core 就是「占根出口而 core 自己不读」，于是随消费方搬进会话插件（D-200 / D-201）。
  这不是两份口径，是「消费方分布」这一条判据作用于两个不同分布的两个答案。
- **整格当词汇**（`Entity::Task` 全算任务事件）：`Task` 格上除了这五格还躺着 `task.ready` /
  `task.rework_created` / `task.controlled`，而 `readyset` 的挂起—恢复算法**必须**区分 `held` 与
  `progressed`；按格子读会把返工与就绪声明一并算进调度候选，那是把两种语义并成一格——
  D-205 里「校准观测不许复用 `memory.recalled`」同一件事的另一个方向。
- **`TaskVocab` 用 `&'static str` 字段**：夹具与测试就得交出 `'static` 的名字，把「词汇是数据」
  变成「词汇必须是编译期常量」；带生命周期才是形参该有的形状。

**本批落地：** core 新增 `projection/task_vocab.rs`（`TaskVocab` + `TaskRole`，随族出根）·
`readyset()` → `readyset_for(vocab, cap)` · `projection/autonomy.rs` 连同它的用例搬进
`symbio-plugin-session/src/autonomy.rs`（`autonomy_for(vocab)` 仍是构造期收表，收的是
`crate::declarations::TASK_VOCAB`——与 core 的 `readyset_for` 那一份同源）· loop 的
`control_decl::EVENTS` 交出这一族五格的格位、`task_vocab()` 交出本族拼写、`PLUGIN.yml` 的
`shared_events` 加五条 · session 的 `stats` / `stats_reading` / `inbox` / `conation` 改经
`symbio_plugin_api::events::*` 取名字并交出同一张表 · 内核删五条常量与四行 `CELLS` ·
core 的 `actors/mod.test.rs` 与 `readyset` 的用例改交**自己的字面量**
⇒ CS-005 **26/25 → 21/21** · C-004 根账本 **377 → 371**（五条名字不再出根、`TaskVocab` 出一条、
`autonomy` 一族两条出口随投影退役），其中「单消费方」一格因这条搬迁回到 **11**。

### D-282 视图可以读「有格位、无事实声明」的断言格——报告，不判红

判据 3「字段都在声明里」的输入是 `FactDecl.fields`。
一条事实若只有 `EventDecl`（名字与格位）而没有 `FactDecl`（载荷形状），这条判据**没有
输入**：它既不能说「字段错了」，也不能说「字段对了」。原来一律判
`Gap::UnknownFact`，把两种完全不同的情况混成一个红：

- 名字连事件格位都没有 ⇒ 真拼错，**必须红**；
- 名字在事件表上、只是没有声明表 ⇒ 读法合法，**只是无从校验字段**。

改法：第二种进 `Frozen::assertion_reads()` 这份**报告名单**（与 `overlaps` 同一条通道：
冻结成功才存在，装载入口打日志，用例可查），不产生缺口。

**为什么不静默跳过。** 「无从校验」是一个可诊断的空白，不是可以忘掉的事实。静默跳过等于
让「字段声明缺席」不可观测——下次真拼错一个字段，没有任何东西会变红。名单随表冻结一次，
`loop_rows::assemble` 把它打成一行 `plugin_info!`。

**为什么需要它：审计 / 读数视图的断言格没有格子可站。** 现例是 `turn.dispatch` 的 `tier`
——「本幕以哪一档跑」的唯一来源（`user.message` 的 `tier` 是历史形态，新写入不再带它）。
它**不能进 `FactDecl`**：没有任何行以它为前件或出口，进去就会被判 `OrphanFact`；它
**也不能被视图合法声明**：`reads` 一写就是 `UnknownFact`。于是 SLO 三列（时延 / 兜底 /
跨度）只能留在控制面当内部投影，读数能力一条都搬不出去。

**被否候选**：

- **放宽 `OrphanFact` 的第二跳**（`read_by_used_view` → 任一视图）：试过，**错**。
  `OrphanFact` 是**按装配**判的，而 `turn.dispatch` 的消费者是一个**可卸载**的能力包：
  loop 自己的单测装配里没有那个包 ⇒ 判孤儿 ⇒ 行表装载失败、义务环拒绝启动。这不是测试
  装配的偶然——T3 判据要求「卸载能力包后系统完整运行」，若这条事实的归宿依赖那个包在场，
  **卸载它 loop 就起不来**，那正是 T3 要拦的静默边。所以「给事实找一个消费者」这条路对
  可卸载的消费者天然不成立。
- **`turn.dispatch` 进 `FactDecl`**：同一条理由，且它本来就没有义务环归宿，也不该有。
- **`seal` 对视图 `reads` 的 `UnknownFact` 全部降级为警告**：那会把「名字真拼错」也放过
  ——本条只放过「有格位、无声明」这一种，拼错仍然红。

**代价（写明）。** 这类读法不享受逐字段校验；名单里出现一条就等于承认「这一格的字段今天
没有 owner 声明」。它不新增面：没有新字段、没有新方法参数，只多一份随表冻结的报告名单。

### D-284 读侧没有扫描上界：`cost` 是环内窗口的预算，不是读口的许可

**裁决**：`ViewDecl::cost` 只回答一件事——**义务环每轮求值**允许扫多少条事实（`Frozen::eval`
超界回 `None`，切片长度由 `Frozen::scan_bound` 回答）。跨插件读口（`symbio-plugin-api::views`）
不查它：调用方给多大的切片就折多大的，既不截断也不报缺席。`ViewUnavailable::OverBudget`
随本条退场，缺席态是四种（`not_sealed` / `not_shared` / `unknown` / `not_aggregable`）。
机制面因此**收窄**：删一个变体、删一处判定，没有新字段、没有新方法、没有新参数。

**为什么非改不可（触发实况：名册 #18 成本台账搬家）。** 把 `sdk` 里的 `cost_ledger()` 折叠
搬进能力包，读方要从类型读改成名字读（[DE-025-能力包与扩展面](025-能力包与扩展面.md) 的 `D-221` 那条路）。改完读数就变了：
会话事实超过 4096 条时，`session_cost_ms`（外部执行熔断的「本轮已花毫秒」）从一个真实累计
变成一次缺席，读方按「没花过钱」继续 ⇒ 熔断 **fail-open**；`session/stats` 的成本列同刻
从数字变成缺席。折叠本身照样折得动——`cost` 拦住的不是算力，是读口的许可。而 `S8` 段的退出判据
写死了「迁移前后读数逐字不变」：这条上界让「搬家」与「读数不变」不能同时成立。

**为什么是删，不是放宽。** 三个形状都不如删：

- **调大 `cost`**：全仓只能有一个数（`seal` 的 `ViewCostMismatch`——环只支持一个切点），
  调大等于把环内每一轮的窗口一起放大，用读侧的问题付环的账。
- **读侧另开一条「不检查的读法」**：同一份切片、同一个 `eval`，一条路报错一条路放行——
  这恰好说明那个数在「读」这件事上不是判据。留一个只在无人走的路径上生效的守卫就是空转
  （`D-280`）。
- **给读口加一份「读侧预算」形参**：新增面，还把 owner 的声明变成读方的参数，正是 `D-221`
  「读方不抄口径」否掉的形状。

**保留的强度。** `cost` 的判定面没有变宽，反而更清楚：环侧「超界不许静默变成『没有欠账』」
原样生效，装载期一致性
（`ViewCostMismatch`）原样生效。读侧没有上界也不等于没有代价——`Projection::read_all` 本来就是
`Budget::generous()`，全量读与它同一口径；长会话的读数代价本来就要付，付在宿主那一侧，
而不是伪装成「这一格没算出来」。

**落地。** `crates/symbio-plugin-api/src/views.rs` 删 `OverBudget` 变体与 `read_in` 的长度检查 ·
`crates/symbio-kernel/src/decl/mod.rs` 的 `ViewDecl::cost` 文档写明它只约束环内窗口 ·
判据用例 `the_read_side_has_no_scan_bound_while_the_ring_keeps_it` 一条钉两半（读侧把超界
切片折完，环侧对同一片仍回 `None`）· 四个能力包的 `COST` 注释同口径 ·
读侧那一半的现行描述在 [DE-025-能力包与扩展面](025-能力包与扩展面.md) §2.6 就地改写，
`D-221` 第 2 条挂出订正。

### D-363 行为名由实现自报，宿主只收集

**裁决**：`symbio-plugin-api` 不再持有任何能力名。能力包在自己的 crate 里定义名字常量，
随 `ToolBehavior` 的实现（名字 + 新增的 `kind()`：造格 / 不造格）经 `submit_behavior!`
链接期登记；`behaviors::known()` / `kind_of()` / `lands_facts()` 从已登记的实现收集。
手写名单（`KNOWN`）与「名 → 种类」对照表（`KINDS`）退出。判据：`behaviors.rs` 出现
字符串常量即红（单测 `this_module_holds_no_capability_names`）。

**理由**：

1. **这是最后一个「装能力改架构模块」的常态破口**。`D-211` 把部署事实搬进清单后，
   新增一条能力的剩余中心改动就是「往 `plugin-api` 加常量、再收进 `KNOWN`」；而名字的
   owner 本就是实现（工具与 handler 同包），中心表只是复写。
2. **收集结果不可能漂移**。`KNOWN` 是手写清单时，「加了名字忘了收」「收了名字没有实现」
   两种漂移只能靠 review；改为从实现收集后它们不再是可表达的状态。
3. **形状与 `submit_row!` / `debt_row` 同族**。能力包只动自己：定义常量、提交实现、
   在工具元数据里声明同一个常量。宿主不认识任何一个名字。
4. **未知行为仍 fail-closed**。未登记（或同名实现声明不一致）⇒ `lands_facts` 为 `None`，
   违约判据按「应当造格」处理——不会让一个没声明种类的行为静默空转。

**残余（不美化）**：声明方与实现方分属两个插件时，名字串在两侧各写一次（`E-009` 禁插件
间依赖）；今天只有 `task_table`（声明在 `symbio-plugin-local`，实现与登记在
`symbio-plugin-task`）。这不是架构模块的清单，是一处待收的代码耦合。

**被否候选**：

- **保留中心常量、用脚本做「清单 ↔ 实现」对照**：两份真相，脚本只能证明「此刻一致」，
  下一次加能力仍要改 `plugin-api`。
- **只在 `PLUGIN.yml` 声明行为名**：工具声明在代码里（`CapabilityMeta.behaviors`），
  装配清单再写一份就是第二处；而且清单是部署事实，不是编译期词汇。
- **让宿主静态扫描源码收集名字**：判据可以扫，运行时仍要一份链接期收集结果；两份。
- **让 `known()` 继续返回手写清单、只加一个「收集」旁路**：读侧立刻要判断以哪份为准，
  正是 `D-210` 否掉「两份真相」的同形错误。

### D-364 共享名住词汇层，实现住各自插件

**裁决**：同一个名字若被两个插件 crate 消费，名字住 `symbio-plugin-api` 的**词汇面**，
实现住各自插件。词汇面按已有出口分派：事件名 → `events.rs`（`shared_events` 投影）、
跨插件路由名 → `routes.rs`（`plugin_routes` 投影）、其余无法从清单投影的名字（端口名 /
跨插件的行行为名 / VDFS 路径段 / 详情表单条件键 / 治理能力名）→ `vocab.rs`；视图名不走
清单，公开动作是 owner 的报表登记（`submit_reports!`，`D-387`）。两侧 import 同一常量，
插件之间仍不互相依赖（E-009 / W-001）。

判据 `SV-001`（`scripts/shared-name-audit.mjs`，进 `30-docs` 门禁）：非 `plugin-api`
的插件生产代码里，① 同一个含 `.` 或 `/` 的名字出现在两个以上 crate 即红；② 同名
`const` 在两个以上 crate 各声明一次即红。测试文件与标准 MIME 类型 / 文件名按语法形状
排除，不设按名字的手写豁免表。

**理由**：

1. **「两份字面量」就是两个 owner**。改名只改一处，另一处静默漂移；编译器看不见，
   测试也未必覆盖到。
2. **词汇层是插件之间唯一合法的共同住处**。不让 `task` 依赖 `local`、也不反过来；
   共享名走 `plugin-api` 是 E-009 边界内的唯一形状。
3. **让清单投影成为默认，`vocab.rs` 成为有意的例外**。能从 `PLUGIN.yml` 投影的名字
   不手写常量；只有投影不了的（端口 / 行行为 / 路径段 / 详情条件键）才进 `vocab.rs`，
   每加一条都是一次明确决定。
4. **判据不靠豁免表**。唯一不判的两类是标准 MIME（owner 是 IANA）与文件名（路径不是
   名字），按语法形状识别；名字多义（`"tool"` 既是端口又是消息角色、`"inbox"` 既是
   路径段又是消息种类）由「同名 const 两个家」那一半守，而不是靠一张逐条开的口子。

**落地**：`plugin-api/src/vocab.rs`（`PORT_MODEL_ASSIST` / `PORT_TOOL` /
`BEHAVIOR_TASK_TABLE` / `SEG_INBOX` / `CAP_ASSIGN_WORK` / `COND_CAP_TEST_CONNECTION`）·
`views-rs.mjs` 为每条公开视图生成 `VIEW_*` 常量 · `vdfs/PLUGIN.yml` 的 `plugin_routes`
扩到九条跨插件消费的操作（`list` / `tree` / `stat` / `read` / `write` / `search` 与既有
`root` / `watch` / `unwatch`），`protocol.rs` / `gateway` / `telegram` / `cli` 引同一常量 ·
`local` 的 `todo_write` 与 `task` 的 `task.rs` 引 `BEHAVIOR_TASK_TABLE` · 六个插件引
`PORT_MODEL_ASSIST` · `agent` / `heartbeat` / `telegram` / `session` 引 `SEG_INBOX` ·
`reputation` 引 `CAP_ASSIGN_WORK` · `mcp` / `model` 引 `COND_CAP_TEST_CONNECTION`。

**未收（不硬收）**：

- **消息 metadata / 载荷键**（`exclude_from_context`、`success`、`id` 一类）：它们是
  一条消息在流水线各段的 wire 字段，owner 是 SDK 的节点构造与各插件的载荷形状，不是
  插件间约定的「名字」。收进 `vocab.rs` 会让词汇层持有 wire 形状，层不对；判据只对
  「同名 const 两个家」生效，不扫普通单词。
- **`provider.json`**：VDFS 入口文件名，写侧只有 `model` 一个插件；`cli` 是读取方且
  不是插件，不构成插件间共享词汇。
- **`application/json` / `image/jpeg`**：标准 MIME 类型，owner 是 IANA 注册表。

**被否候选**：

- **让消费方直接依赖 owner 插件**：破 E-009 / W-001，且让插件卸载 / 替换产生编译期
  耦合。
- **给 `task_table` 建一个共享新 crate**：为一个名字加一个 crate，比 `plugin-api`
  多一层装配点；下一个共享名会要求同样的新 crate。
- **判据用一张按名字的豁免表**：豁免项一多就变成「问题清单」，且新增名字默认落进
  表里就再也没人看；按语法形状排除 MIME / 文件名，不需要逐条维护。

### D-387 视图的注册面交给 owner：`shared_views` 与生成的名字常量退役

**裁决**：跨插件视图的注册面从「`PLUGIN.yml` 写 `shared_views` → 生成
`plugin-api/src/view_names.rs`」改为「owner 在自己的 `decl.rs` 里 `submit_reports!` 一条
**报表描述符**」；读方只遍历描述符，不再持有任何视图名。八列（九条视图）连同
`conation.intents` 的汇报半边在本条迁完。

```rust
// symbio-plugin-api/src/reports.rs —— 只有类型、宏与遍历，零业务名
pub struct ReportCtx<'a> { pub principal: &'a str, pub cap: usize, pub readable: bool }
pub struct ReportDecl {
    pub owner: &'static str,
    pub slot: &'static str,             // session/stats 的顶层键；全局唯一
    pub order: u8,                      // 面板段顺序
    pub views: &'static [&'static str], // owner 自己的名字，按 owner 的次序
    pub fleet: Option<&'static str>,    // 实例级落点（叶路径，如 axes.conation / by_tier）
    pub render: fn(&[Value], &ReportCtx<'_>) -> Value,
    pub fleet_render: Option<fn(&[Value], &ReportCtx<'_>) -> Value>,
    pub panel: Option<fn(&Value, &ReportCtx<'_>) -> ReadingSection>,
}
inventory::collect!(ReportDecl);
```

`ReportCtx.readable` 区分「读侧闸不给看」与「读失败」；空形状、`own` 行、`cap` 截断与按档并表全在 `render` 里。

**`order` 平手规则**：两个报表 `order` 相同时按 `slot` 字典序（`slot` 已被判据保证全局
唯一，平手不会退化成链接顺序）。实现必须带一条「同一装配连跑两次，`session/stats`
序列化逐字节相同」的用例。

  仍是本插件字段（`usage` / `spend` 随写方归 `model`，`D-461`）。
- 八个具名列从具名 `Value` 字段改为 `reports: Map<slot, Value>` + `#[serde(flatten)]`——
  **JSON 顶层路径不变**（`stats.cost.total_ms` / `stats.calibration.by_skill` /
  `stats.tiers[0]` 等 e2e 断言不动）；`empty_*` 五条删除，空形状随 `render` 回 owner。
- `capability_views` 保留为诊断列：遍历 `reports()` 的视图；没有第二份清单读口，
  `shared_views()` 随名单退役一并消失。

判据 `SV-003`（进 `shared-name-audit` 同一门禁）：`reports()` 的 `(slot, fleet)` 集合与这张表不一致
——新增 / 删除 / 改名都算——⇒ 红；改表必须由一条能打开的 `### D-NNN` 追加 `baseline-allow`，不由 owner 随手改。

**`conation.intents` 只留汇报半边**：`declared` 删除——`D-386` 之后升格去重由 `conation/src/debt.rs` 直接读事实判，视图不再是判据源；`intents` / `expressed` / `escalated` / `adoption_rate` 保留，登记 `slot = conation`、`fleet = axes.conation`；`conation.autonomy` 同批登记 `slot = autonomy`、`fleet = axes.autonomy`。

**`memory.live`**：Q3 把巩固从会话搬进 memory 后它不再有跨插件读方，已随报表描述符转成
`slot = memory`、`fleet = None`——公开动作是报表登记（`D-387`），`shared_views` / `view_names.rs` 随之退役。

**判据**：

- `SV-001` 原义保留：**一个视图名在插件 crate 里只许出现一次**（owner 的 `const`）；
  `session` 的读数代码出现任一视图名即第二份 ⇒ 红——守的是「不许在两个 crate 各写一份」。
- `SV-002` 随 `view_names.rs` 退役（清单不存在，判据无处可判）；「名字只在 owner 一处」由 `SV-001` 承担。
- 登记判据返回 `Result`，不 panic：`slot` 重复、同一视图进两条报表、`views` / `slot` /
  `fleet` 为空 ⇒ `reports()` 交回 `ReportError` 清单，由装载面或读数方报出（与
  `sealed_declarations()` 同形）。`Gap` 是内核声明 / 环的词汇，报表是出品装配面，
  不把错误类型塞回内核；也没有「只能 panic」的硬理由——每个调用方都能接 `Result`。
- `HS-002`：`reports` 面（1 struct + 1 ctx + 1 宏 + 1 遍历 + 1 collect）按本条调基线，
  补件记 `EX-007`。

**理由**：

1. 现形状把注册面放在架构层：`shared_views` → 生成器 → `plugin-api/view_names.rs`。生成物
   不算手改，但**名字作为业务身份住进了机制层**，读方仍要「知道有哪几条」才能出列。
2. 报表描述符把「哪一格、怎么排版、读哪几条」交给 owner，读方只留一条遍历；空形状不再由读方猜。
3. 与 `settle` / `context` / `retrieval` / `rows` 的链接期登记同形：owner 在自己 crate 里
   `submit_reports!`，宿主链接即生效，没有中心表要维护。

**被否候选**：

- 保留生成常量、只删 session 的具名列：架构层仍留业务名，加一条报表仍要跑生成；session
  一写名字面量就撞 `SV-001`，把红线留给下一个改的人。
- 用 `ViewDecl` 加 `report: bool`：改内核声明形状，所有字面量都要跟改；报表是读侧排版，不是事实语法。
- 用运行期 `CapabilityRow` 家族登记：`session/stats` 是纯路由，拿不到收集期的 `Registry`。
- 让 session 继续具名列、名字换成 owner 导出的常量：跨插件编译期依赖（`E-009` 红）。
- 把八列整条删掉、只留 `capability_views`：读数形状与 e2e 出口路径一起丢。
- 让 `render` 落回 session：把 owner 的形状知识再抄一次，与本条要消的东西同形。

**与 `D-221` / `D-281` / `D-386` 的关系**：`D-221` 的读口、缺席态与「读方零知识」全部有效，
本条只换知识源（生成清单 → owner 登记），缺席态收敛为 `not_sealed` / `unknown` 两态；
`D-281` 的 `eval` / `agg` 不改，`fleet_render` 是
`agg` 之后的排版，不是第三份口径；`D-386` 已移走 `conation.policy`，本条收掉 `intents` 汇报半边。

**实施顺序**（每步一笔、`--full` 绿报号）：

1. `reports.rs` + 登记判据（`Result`，不 panic）+ 单测（`slot` / 视图去重、`readable = false`
   的空形状、`order` 平手的确定性）；完成后先报一次，不直接进入逐列迁移。

   有读者就在提交说明里逐条写「读者 → 改调用点 or 保留访问器」，不得先改再靠编译报错发现。
