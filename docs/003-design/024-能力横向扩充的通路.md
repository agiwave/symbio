# 能力横向扩充的通路

> 先给结论：**加一个自足的能力今天已经近乎零成本；成本全在「这个能力要被别人用」
> 这一件事上。** 而被别人用**不是**靠插件互相依赖解决的——那是 E-009 的反面，也是
> 本次拆 crate 的全部意义所在。这条路上真正缺的只有两样东西：
> **地址不能声明化**（每加一条跨插件调用都要改一个不属于任何插件的共享文件），
> **共享类型没有上移口径**（每次上移都要现场论证一遍"这算不算扩大内核面"）。
>
> 本文只做这三件事：把零依赖写成可执行的判据、把地址变成生成物、把上移写成一条
> 有登记口的常态动作。

## §0 结论先行

1. **编译期零依赖、运行期寻址，是两条不能混的通路。** 插件之间**编译期**没有任何
   依赖边（不 import、清单不声明、不经宿主门面）；它们**运行期**只通过容器路由互调
   （`ctx.parent()` → `parent.route(ctx)`，地址来自常量），载荷是 `PluginFrame` /
   `PluginPayload` 的 **JSON 形状**，不是某个插件的 Rust 类型。零依赖不等于零互操作。
2. **实测：插件间依赖边 = 0 条。** 22 个插件 crate 的 `[dependencies]` 里没有一条兄弟
   插件；源码里 23 处 `symbio_plugin_*` 有 22 处是宿主门面的 `pub use`，其余全是注释。
   （上一版本文把 composite 的 `dev-dependencies` 上方一句注释读成了依赖边，已改正。）
3. **但守卫是假的。** `E-009` 判的是 `crate::plugins::<兄弟插件>`——那是拆 crate **之前**
   的形态。拆完之后这个路径不可能存在（兄弟插件是独立 crate，`crate::plugins` 已不存在），
   全仓 4 处 `crate::plugins` 全是注释 ⇒ 本条**静默空转**，绿灯不代表任何东西。真正的
   依赖边现在住在 `Cargo.toml` 的依赖表里，而旧实现从不读清单：加一行
   `symbio-plugin-web = { path = … }` 就能让插件互可见，且不留红。**已修**（§4 E-009）。
4. **共享类型只有一条路：上移。** 而 C-003（根出口符号须有 ≥2 个消费方）**恰好在上移
   那一刻满足**——第二个消费者出现，正是上移的时机。所以棘轮不是障碍，它是上移的
   **时机判据**。上一版把这件事读成"每长一个跨插件能力都要突破棘轮"，是错的。
5. **跨插件地址住在一个共享手写文件里。** 8 个 `ROUTE_*` 常量手写在
   `crates/symbio-plugin-api/src/routes.rs`，13 个文件消费。加一条跨插件调用 = 改一个
   **不属于任何插件**的文件——这是"改外部模块"的日常来源。
6. **判据已经先行落地**：`core-change-audit` 的 CC-001 / CC-002 让"改插件却顺手动
   core/kernel"无法不留理由地通过；E-009 现在按清单 / 源码 / 门面三层判定。没有这两条，
   前五条修好半年后必然长回去。

## §1 实测：加一样东西到底要动几处

读数取自本次会话（提交 `3659952f` 之后）。

| 扩充对象 | 必须人改的落点 | 其中**不属本插件**的 | 漏改时谁红 |
|---|---|---|---|
| 一个自足的工具（只有本插件实现、不被别人调） | 插件内 `Capability` 实现 + `PLUGIN.yml` + 链接清单一行 | 1（`crates/symbio/Cargo.toml`） | 不装配 ⇒ 模型看不见它 |
| **一个要被别的插件调的能力** | 同上 + `PLUGIN.yml` 的 `routes:` 段（**今天是**改 `plugin-api/src/routes.rs` 手写常量） | **1**（今天 2） | E-012（名字↔值同构 / 值可分发） |
| **一个要被别的插件看见的类型** | 同上 + `symbio-core` 的**领域模块**一条 | 1（同一提交，须挂 `Core-Change:`） | C-003（<2 消费方）/ C-004（条数） |
| 一条策略 / 时机 / 执行体 | 插件内 `loop_rows.rs` | 0 | 装载期判据 |
| 一个新能力族 | 插件内 `CapabilityFamily` 常量 + 载荷 | 0 | 读侧 `payload::<T>()` 给 `None` |

第三行是唯一需要动 core 的一行，而它同时是**唯一一条本来就该动 core** 的行：一个类型
被两个插件看见，它就不再属于任何一个插件，它属于领域。把它留在插件里，等于让第二个
插件依赖第一个——那正是要禁的事。

配套读数：

- 33 个 crate（22 插件 · 5 provider）；core 非内核根账本 **395** 条，内核公共面 27 条。
- `core-shape-audit` CS-004：内核文件集里插件 id 字面量 **14 处 / 2 个文件**，域文件 **22 处**
  （后者是 C 阶段迁出账，不设门禁）——这批就是"词汇回流进语法"的现存账。
- 每个 crate 的 `[dependencies]` 是**同一份 45 行清单的复制**（22 个 crate 都是 45 行，最多 65 行），
  含 `ort`（ONNX）与 `reqwest`。新增一个插件的第一步是抄这 45 行。
- **实测这份清单不是「用到的依赖」，是「照抄的依赖」**：`symbio-deploy` 是一个 99 行纯常量文件
  （零 `use`、零函数、零 `impl`），却挂着 40 条依赖。把它的 `[dependencies]` 清空后
  `cargo check --workspace --all-targets` **全绿**——40 条一条都没被用到。本次已裁掉。
- 拆 crate 之后共 3 个提交，其中 **2 个同时改动插件与 core/kernel**。

## §2 三个根因

### 2.1 跨插件地址住共享文件（**阻断"被别人调"**）

`routes.rs` 是宿主侧的地址常量表。它的存在理由成立（地址是装配方的词汇，不是 core 的
语法，D-184 已裁决），但形态是错的：**手写常量 + 单一文件**。加一条跨插件地址要改一个
所有插件都依赖、却不属于任何插件的文件。

`gen-facts` 已经能从 `PLUGIN.yml` 生成装配清单（`symbio-deploy`），地址表没有理由不照
同一条路走。**这是唯一一处"加能力必须改共享文件"**，也正是动作 B 的全部内容。

### 2.2 能力不成包（**放大登记次数**）

一个能力的五个面（实现 / 提示词 / 地址 / 授权行 / 装配位）各自有各自的登记口。前两个住
插件内（好），后三个各有一处中心（地址 → 共享文件、授权 → core 的表、装配位 → 生成的清单）。
**装配位已经是生成的**（`PLUGIN.yml` → `symbio-deploy`），这是唯一已经走通的一条，也是
另外两条该照抄的形态。

### 2.3 词汇写进语法 + 物理门槛（**成本，不阻断**）

`Principal::tool_principal` 里有一份**硬编码的插件命名空间白名单**（`"vdfs" | "web" | "local" | "agent"`），
住在 `symbio-kernel/src/chat/principal.rs`。实测一个新插件 `notes` 的后果：

```text
tool_principal("notes_add") -> Tool  legacy/notes_add   ← 没进自己的命名空间
from_legacy("notes/add")    -> Agent notes/add          ← 族判错（未知 namespace 按 Agent 兜底）
tool_principal("vdfs_write")-> Tool  vdfs/write         ← 白名单内正常
```

**如实说：这不阻断功能。** 两者都是 `Tool` 族里的一次地址退化（前者）或一次 fail-closed
的族兜底（后者），授权表按 id 精确判，不会因此放权。它影响的是**身份地址与统计口径**——
新插件的工具统一堆在 `legacy/` 下。所以本项降级为报告项（§4 的 D-195），不占施工排期。

物理门槛是真的：新增插件要抄 45 行依赖（含 `ort` / `reqwest`），并在 `crates/symbio/Cargo.toml`
加一行链接。后者是 Rust 的物理事实（`inventory` 依赖链接图），不是设计缺陷；前者是。

## §3 方案：三条动作

### 动作 A（原则）：编译期零依赖，共享一律上移

**不开任何形态的插件间依赖口。** 没有 `contract` 模块，没有"只许类型"的例外，没有
"经宿主门面再导出"的后门——三者都是同一条边的三种写法。

跨插件要用的东西，只有三条合法出路，按代价排序：

| 需要共享的东西 | 出路 | 代价 |
|---|---|---|
| **数据**（调用的入参与结果） | `PluginPayload` / `PluginFrame` 的 JSON 形状。双方各自 `payload::<T>()` 反序列化到**自己的**类型 | 0 |
| **词汇**（地址 / 能力名 / 事件名） | `PLUGIN.yml` 声明 → `scripts/facts/` 生成（动作 B） | 0（改自己目录） |
| **类型**（同一领域对象的结构） | 上移 `symbio-core` 的**领域模块**（不是根出口），按 C-002 的深引规则消费 | C-004 +1~3，须挂 `Core-Change:` |

第三行不是妥协，是**归属判定的正确结果**：一个类型同时被两个插件看见，它就不属于任何
一个插件。D-180 说的「归生产者 owner」指的是**谁登记**（哪个域的账本），不是**放在谁的
crate 里**——这一点上一版读反了，导致它被当成"允许依赖"的依据。

**上移的时机由 C-003 给出**：第二个消费者出现时，≥2 消费方条件自动满足，棘轮不挡路。
所以"上移"从来不是"突破棘轮"，而是"棘轮一直在等的那个时刻"。

**判据覆盖六条通路**，任何一条被破都能红：清单声明（含改名与 workspace 继承）、源码
`use`、宿主门面 `symbio` 进生产依赖、`include!` / `#[path]` 跨 crate 搬源码、非插件 crate
`pub use` 转发（`mcp → testkit → web` 这种间接链）。**已知边界**：这是文本判据，拦的是
"写出来的依赖"；运行期动态加载（`libloading` / dlopen）不在模型内——本仓插件是编译期
链接的（`inventory`），若将来引入动态插件，那是另一套隔离模型，不是本条能覆盖的。

### 动作 B：地址与能力都走向声明 + 生成

- `PLUGIN.yml` 增 `routes:` 段，`scripts/facts/` 生成 `symbio-plugin-api/src/routes.rs`
  （常量名保持 `ROUTE_*`，13 个消费方文件一行都不用改）。
- 同一条路继续走：`capabilities:` 段声明能力名与是否导出，宿主经**链接期发现**
  （`submit_object_creator!` 已经在用 `inventory`，同一个机制）。
- 生成物的守卫：手改判红（与 `gen-facts --check` 同一条路）。

效果：加一条跨插件调用 = 改**自己目录里**的 `PLUGIN.yml`，共享文件零 diff。

### 动作 C：把新增插件的物理门槛压下来

`[workspace.dependencies]` 统一版本，各 crate 只声明**真正用到**的依赖。
现状是 22 个 crate 抄同一份 45 行（含 341 MB 预编译产物的 `ort`）。

**第一个样本已经落地**：`symbio-deploy`（纯常量文件）的 40 条依赖清空后全仓编译仍绿——
这条口径本身就是可判的：「清空后仍绿」说明它们从来没被用过。其余 crate 按同一条口径逐个体检，
风险为零（多删一条 cargo 立刻报错，少删一条没有收益）。

## §4 判据

| 编号 | 判据 | 状态 |
|---|---|---|
| E-009 | 插件不得依赖兄弟插件：清单不声明 · 源码不引用 · 宿主门面只许 dev · `include!`/`#[path]` 不跨 crate · 非插件 crate 不转发 | **已落**（六条通路 + 19 条回归用例） |
| CC-001 | 触及 core/kernel 的提交必须带 `Core-Change:` 段 | **已落**（`scripts/core-change-audit.mjs`） |
| CC-002 | 同一提交既动插件又动 core/kernel 时，理由里必须有决策号 | **已落** |
| GEN-001 | `routes.rs` 是生成物，手改判红 | 待落（动作 B 的配套） |
| EC-001 | 新增插件必须人改的落点 ⊆ {链接清单, PLUGIN.yml, 生成物} | 待落（动作 B 完成后即为 0 条中心件） |

**AR-001 已作废**：它原本是"`contract` 模块只放类型"，用来给一个不该开的依赖口配闸。
依赖口本身被否，闸门随之取消。

判据的取舍理由：**CC 是唯一能拦"原因"的一条**。C-003 / C-004 判的是 core 出口宽度（结果），
而"为了让新插件跑起来在内核里加个分支"是一次提交的意图，静态扫描看不见。

## §5 施工顺序

1. **判据先行**（E-009 覆盖六条通路，见 §4）。顺序不能反：先开依赖口再补判据，中间那段时间
   没有守卫，而那段窗口恰是"顺手 import 一下"最容易发生的时刻。
2. **动作 B 的生成器**（`routes` → 生成），因为它是**唯一一处"加能力必须改共享文件"**，
   且不改变任何运行时语义，风险最低、收益最直接。
3. 动作 A 的真实效用检验：拿一个真实的跨插件调用走一遍三条出路，确认"数据走 JSON 形状"
   够用、不需要 contract 模块。样本取 `composite` 调 `vdfs_list`。
4. 动作 C 的清单上提（纯机械，最后做）。

## §6 不做清单

- **不开任何形态的插件间依赖**：`contract` 模块、`pub use` 转发、dev-dependency 通融、
  "只依赖类型不依赖实现"——一律不行。零依赖是拆 crate 的全部意义，破一次就不再有边界。
- 不把 `symbio-plugin-api` 扩成"第二个 core"。它是**宿主词汇**（地址、钩子），不是任意共享类型的
  垃圾场——把共享都倒进去只是给同一份账本换名字（D-188 已经拒过一次同形态的候选）。
- 不为了"统一"把 core 的机制类型搬去插件：机制必须只有一份实现。
- 不给"声明数 / 变体数"再加计数器——扩展夹具才是可执行的判据（DE-023 §2 末尾）。
- 不为 §2.3 的 principal 白名单单独开一轮重构：它不阻断功能，等动作 B 完成后
  「插件 id 集合」自然由装配事实派生（`symbio-deploy` 已是零插件实现的名词表）。

## 关键决策

### D-192（修订）插件间编译期零依赖，互操作只经容器寻址

**原方案已否决**：曾计划"按 DAG 开放插件间依赖，只许经对方的 `src/contract.rs`"。否决理由是
它把架构公理当成了可以打折的约定——一旦允许一条边，就没有理由拒绝第二条；而"只许类型"的
闸门需要一个**每周都在现场判断"这算行为还是类型"**的人，那不是一个可执行的判据。

现在的定位是：**编译期零依赖（E-009 三层判定，物理保证）+ 运行期寻址（容器路由 +
`PluginFrame` JSON 形状）**。前者保证插件可独立卸载、独立编译、独立演进；后者保证它们
仍然能互相调用。这两件事从来不是同一个问题。

代价与边界：跨插件调用的载荷**没有编译期类型检查**，错在运行期（`payload::<T>()` 返回
`None` 或反序列化失败）。这是明确的取舍——用"形状约定"换"零依赖"，并用装载期判据 +
`PluginPayload` 的显式形状覆盖错误面。

### D-193 地址与能力一律声明 + 生成，手写共享表退出

`ROUTE_*` 从手写常量改为 `PLUGIN.yml` 的投影（`scripts/facts/` 生成）。理由：地址是**装配方的词汇**
（这一点 D-184 已经裁决），而装配清单早已是生成物；唯一手写的共享表就此消失。
常量名保持不变，13 个消费方文件零改动——这是"先换来源、再谈形态"的顺序。

### D-194 依赖版本上提到 workspace，插件只声明用到的

22 个 crate 抄同一份 45 行清单（含 `ort` / `reqwest`）。新增一个插件的第一个动作不该是复制
一份包含 ONNX 运行时的清单。

### D-195 principal 的插件命名空间按部署事实派生，且降级为报告项

kernel 里的命名空间白名单是词汇写进语法的残留，但**不阻断扩能力**（实测只造成 `legacy/`
地址与族兜底，不影响授权）。等动作 B 落地、插件 id 集合成为可查询的部署事实之后，
由 `symbio-deploy` 的 id 表派生，kernel 只留纯函数接收集合。

### D-196 共享类型一律上移，归属按领域判而不是按插件判

一个类型被第二个插件需要时，它已经不属于任何插件，属于领域；上移到 `symbio-core` 的对应
**领域模块**（不是根出口），按 C-002 的深引规则消费。

这条给 D-180 补上了落点：D-180 说「归生产者 owner」，此前无处可执行，因为它被读成"消费方
依赖生产者的 crate"。正确读法是「登记在生产者的**域账本**里」——物理位置在 core，
owner 是那个域。C-003 的 ≥2 消费方条件在上移那一刻自动满足，因此棘轮不构成阻力。

被否候选：允许插件开 `src/contract.rs` 供他人依赖。见 D-192 的否决理由。
