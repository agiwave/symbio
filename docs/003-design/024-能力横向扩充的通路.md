# 能力横向扩充的通路

> 先给结论：**「加一个自足的能力」今天已经几乎零架构成本；成本全部出在「这个能力要被别人用」
> 这一件事上。** 而「被别人用」正是能力网络化的必然方向。所以本文只做三件事：给跨插件
> 共享开一条不进机制层的通路、把跨插件地址从共享文件里搬出去、把一个能力收成一个可宣告的包。

## §0 结论先行

1. **主矛盾是共享，不是注册。** 插件之间没有任何依赖边（21 个插件 crate 里唯一的跨插件边是
   `composite → agent`），而 `plugin-entry-audit` 的 E-009 明令禁止互相 import。于是「两个插件都要
   看见的同一个东西」在物理上只有一处可放：`symbio-core`。而 core 的入口是一道**只许缩**的棘轮
   （C-001 根出口唯一 · C-003 双消费方 · C-004 条数冻结）。两条规则叠起来的后果是：
   **每长一个跨插件能力，都要先付一次「扩大内核面」的代价**——这就是"改架构"。
2. **D-180 与 E-009 今天不能同时成立。** D-180 说「共享类型归**生产者** owner」，那必然要求
   插件 A 依赖插件 B；E-009 说不许。两条都登记在册，实际执行的是 E-009（拆 crate 之后它由
   cargo 的依赖图物理保证），所以 D-180 至今**没有一条可执行的落点**。这不是新增需求，
   是本次拆 crate 暴露出来的规则冲突。
3. **跨插件地址住在一个共享文件里。** 8 个 `ROUTE_*` 常量全部手写在
   `crates/symbio-plugin-api/src/routes.rs`，13 个文件消费它。加一条跨插件调用 = 改一个
   **不属于任何插件**的文件，而这正是"改外部模块"的日常来源。
4. **一个能力散在五处**：`Capability` 实现、提示词、路由、授权行、装配位。没有一处能整包宣告
   「我提供这些」，所以每加一个能力都要在五处各登记一次。
5. **判据已经先行落地**：`core-change-audit` 的 CC-001 / CC-002 让「改插件却顺手动 core/kernel」
   无法不留理由地通过。没有这条，前四条修好半年后必然长回去。

## §1 实测：加一样东西到底要动几处

读数取自本次会话（提交 `235e7347` 之后）。

| 扩充对象 | 必须人改的落点 | 其中**不属本插件**的 | 漏改时谁红 |
|---|---|---|---|
| 一个自足的工具（只有本插件实现、不被别人调） | 插件内 `Capability` 实现 + `PLUGIN.yml` + 链接清单一行 | 1（`crates/symbio/Cargo.toml`） | 不装配 ⇒ 模型看不见它 |
| **一个要被别的插件调的能力** | 同上 + `symbio-plugin-api/src/routes.rs` 一条常量 | **2** | E-012（名字↔值同构 / 值可分发） |
| **一个要被别的插件看见的类型** | 同上 + `symbio-core` 根出口一条 + C-004 豁免 | **3**（且要动收缩棘轮） | C-003（<2 消费方）/ C-004（条数） |
| 一条策略 / 时机 / 执行体 | 插件内 `loop_rows.rs` | 0 | 装载期判据 |
| 一个新能力族 | 插件内 `CapabilityFamily` 常量 + 载荷 | 0 | 读侧 `payload::<T>()` 给 `None` |

配套读数：

- 33 个 crate（22 插件 · 5 provider）；core 非内核根账本 **395** 条，内核公共面 27 条。
- `core-shape-audit` CS-004：内核文件集里插件 id 字面量 **14 处 / 2 个文件**，域文件 **22 处**
  （后者是 C 阶段迁出账，不设门禁）——这批就是"词汇回流进语法"的现存账。
- 每个 crate 的 `[dependencies]` 是**同一份 45 行清单的复制**（22 个 crate 都是 45 行，最多 65 行），
  含 `ort`（ONNX）与 `reqwest`。新增一个插件的第一步是抄这 45 行。
- **实测这份清单不是「用到的依赖」，是「照抄的依赖」**：`symbio-deploy` 是一个 99 行纯常量文件
  （零 `use`、零函数、零 `impl`），却挂着 40 条依赖。把它的 `[dependencies]` 清空后
  `cargo check --workspace --all-targets` **全绿**——40 条一条都没被用到。本次已裁掉
  （动作 C 的第一个样本）。
- 拆 crate 之后（`crates/` 布局下）共 3 个提交，其中 **2 个同时改动插件与 core/kernel**。

## §2 四个根因（按是否阻断扩能力排序）

### 2.1 共享无路（**阻断**）

`E-009` 的原文是「插件不得直接 `use crate::plugins::<兄弟插件>`」，理由是"插件之间互不可见"。
拆 crate 之前这条是**约定**（Rust 的私有可见性并不阻止同 crate 内互相路径）；拆 crate 之后它变成
**物理约束**——没有 `Cargo.toml` 依赖就 import 不到。约定变成了硬墙，而墙的另一侧没有门。

于是「两个插件共享一个类型」的唯一出路是 core。core 又被三重棘轮锁成单向门：

- C-001 根出口唯一（`pub mod <域>` 不许回来）；
- C-003 根出口符号必须有 ≥2 个消费方；
- C-004 非内核账本条数冻结，**只许降**。

**这三条都是对的**——它们是防止 core 变垃圾场的唯一手段。问题不在棘轮，在于**除 core 之外
没有第二个合法的共同可见处**。

### 2.2 跨插件地址住共享文件（**阻断"被别人调"**）

`routes.rs` 是宿主侧的地址常量表。它的存在理由成立（地址是装配方的词汇，不是 core 的语法），
但形态是错的：**手写常量 + 单一文件**。每加一条跨插件地址，都要改一个所有插件都依赖、
却不属于任何插件的文件。`gen-facts` 已经能从 `PLUGIN.yml` 生成装配清单（`symbio-deploy`），
地址表没有任何理由不照同一条路走。

### 2.3 能力不成包（**放大登记次数**）

一个能力的五个面（实现 / 提示词 / 地址 / 授权行 / 装配位）各自有各自的登记口。前两个住插件内
（好），后三个各有一处中心（地址 → 共享文件、授权 → core 的表、装配位 → 生成的清单）。
**装配位已经是生成的**（`PLUGIN.yml` → `symbio-deploy`），这是唯一已经走通的一条，
也是另外两条该照抄的形态。

### 2.4 词汇写进语法 + 物理门槛（**成本，不阻断**）

`Principal::tool_principal` 里有一份**硬编码的插件命名空间白名单**（`"vdfs" | "web" | "local" | "agent"`），
住在 `symbio-kernel/src/chat/principal.rs`。实测一个新插件 `notes` 的后果：

```text
tool_principal("notes_add") -> Tool  legacy/notes_add   ← 没进自己的命名空间
from_legacy("notes/add")    -> Agent notes/add          ← 族判错（未知 namespace 按 Agent 兜底）
tool_principal("vdfs_write")-> Tool  vdfs/write         ← 白名单内正常
```

**如实说：这不阻断功能。** 两者都是 `Tool` 族里的一次地址退化（前者）或一次 fail-closed 的族兜底
（后者），授权表按 id 精确判，不会因此放权。它影响的是**身份地址与统计口径**——新插件的工具
统一堆在 `legacy/` 下。所以本项降级为报告项（§4 的 D-195），不占施工排期。

物理门槛是真的：新增插件要抄 45 行依赖（含 `ort` / `reqwest`），并在 `crates/symbio/Cargo.toml`
加一行链接。后者是 Rust 的物理事实（`inventory` 依赖链接图），不是设计缺陷；前者是。

## §3 方案：三条动作

### 动作 A（主）：给共享开一条不进机制层的通路

**允许插件间依赖，但只许单向、只许经对方的 `contract` 面。**

- 每个插件可以在自己 crate 里开 `src/contract.rs`，放**它愿意让别的插件看见的东西**：
  类型、常量、trait。**不放实现**（无 `fn` 体、无行为 `impl`）。
- 其他插件 `use symbio_plugin_<owner>::contract::…`；依赖方向由 cargo 保证无环。
- `E-009` 从「一律禁止」改判为「只许命中对方 `contract` 模块」——它拦的从来不是"依赖"，
  而是"依赖到别人的实现面"。

效果：D-180 终于有落点；core 不再是唯一的共同可见处；C-004 不再被结构性推高。
代价：插件间出现真实的依赖边，编译图变宽。**这也是为什么它必须配一条"contract 只放类型"
的判据**，否则三个月后每个插件都会有一个什么都往里塞的 `contract`。

### 动作 B：地址与能力都走向声明 + 生成

- `PLUGIN.yml` 增 `routes:` 段，`scripts/facts/` 生成 `symbio-plugin-api/src/routes.rs`
  （常量名保持 `ROUTE_*`，13 个消费方文件一行都不用改）。
- 同一条路继续走：`capabilities:` 段声明能力名与是否导出，宿主经**链接期发现**
  （`submit_object_creator!` 已经在用 `inventory`，同一个机制）。
- 生成物的守卫：手改判红（与 `gen-facts --check` 同一条路）。

效果：加一条跨插件调用 = 改**自己目录里**的 `PLUGIN.yml`，共享文件零 diff。

### 动作 C：把新增插件的物理门槛压下来

`[workspace.dependencies]` 统一版本，各 crate 只声明**真正用到**的依赖。
现状是 22 个 crate 抄同一份 45 行（含 341 MB 预编译产物的 `ort`），这不仅拖慢新增插件，
也让每次全量编译为"谁都依赖谁"付账。

**第一个样本已经落地**：`symbio-deploy`（纯常量文件）的 40 条依赖清空后全仓编译仍绿——
这条口径本身就是可判的：「清空后仍绿」说明它们从来没被用过。其余 crate 按同一条口径逐个体检，
风险为零（多删一条 cargo 立刻报错，少删一条没有收益）。

## §4 判据

| 编号 | 判据 | 状态 |
|---|---|---|
| CC-001 | 触及 core/kernel 的提交必须带 `Core-Change:` 段 | **已落**（`scripts/core-change-audit.mjs`） |
| CC-002 | 同一提交既动插件又动 core/kernel 时，理由里必须有决策号 | **已落** |
| AR-001 | `contract` 模块只放类型 / 常量 / trait，不放实现 | 待落（动作 A 的配套） |
| GEN-001 | `routes.rs` 是生成物，手改判红 | 待落（动作 B 的配套） |
| EC-001 | 新增插件必须人改的落点 ⊆ {链接清单, PLUGIN.yml, 生成物} | 待落（动作 B 完成后即为 0 条中心件） |

判据的取舍理由：**CC 是唯一能拦"原因"的一条**。C-003 / C-004 判的是 core 出口宽度（结果），
而"为了让新插件跑起来在内核里加个分支"是一次提交的意图，静态扫描看不见。

## §5 施工顺序

1. **动作 A 的判据先落地**（AR-001）+ 一个 `contract` 样例。顺序不能反：先开依赖口再补判据，
   中间那段时间没有守卫。
2. **动作 B 的生成器**（`routes` → 生成），因为它是**唯一一处"加能力必须改共享文件"**，
   且不改变任何运行时语义，风险最低、收益最直接。
3. 动作 A 的真实迁移：把 `[L1]` 那 11 条单消费方出口里**属于某个插件**的逐条搬到生产方
   `contract`（今天只能搬进 core 的消费者，因为无处可去）。
4. 动作 C 的清单上提（纯机械，最后做）。

## §6 不做清单

- 不把 `symbio-plugin-api` 扩成"第二个 core"。它是**宿主词汇**（地址、钩子），不是任意共享类型的
  垃圾场——把共享都倒进去只是给同一份账本换名字（D-188 已经拒过一次同形态的候选）。
- 不为了"统一"把 core 的机制类型搬去插件：机制必须只有一份实现。
- 不给"声明数 / 变体数"再加计数器——扩展夹具才是可执行的判据（DE-023 §2 末尾）。
- 不为 §2.4 的 principal 白名单单独开一轮重构：它不阻断功能，等动作 A 完成后
  「插件 id 集合」自然由装配事实派生（`symbio-deploy` 已是零插件实现的名词表）。

## 关键决策

### D-192 插件间依赖按 DAG 开放，只许经 `contract`

`E-009` 改判为「跨插件 `use` 必须命中对方 `src/contract.rs` 的导出」。理由：拆 crate 把
"插件互不可见"的**约定**变成了**物理约束**，而共享却没有第二条路，于是所有共享回流 core、
再被 C-004 的单向棘轮顶回来——D-180（共享类型归生产者 owner）因此从登记那天起就无法执行。
本决策让 D-180 可执行，而不是新开一层抽象。

被否候选：把共享类型都堆进 `symbio-plugin-api`。那只是把 core 的账本换个名字，且 plugin-api
没有棘轮、没有 owner 登记，会比 core 更快变成垃圾场。

### D-193 地址与能力一律声明 + 生成，手写共享表退出

`ROUTE_*` 从手写常量改为 `PLUGIN.yml` 的投影（`scripts/facts/` 生成）。理由：地址是**装配方的词汇**
（这一点 D-184 已经裁决），而装配清单早已是生成物；唯一手写的共享表就此消失。
常量名保持不变，13 个消费方文件零改动——这是"先换来源、再谈形态"的顺序。

### D-194 依赖版本上提到 workspace，插件只声明用到的

22 个 crate 抄同一份 45 行清单（含 `ort` / `reqwest`）。新增一个插件的第一个动作不该是复制
一份包含 ONNX 运行时的清单。

### D-195 principal 的插件命名空间按部署事实派生，且降级为报告项

kernel 里的命名空间白名单是词汇写进语法的残留，但**不阻断扩能力**（实测只造成 `legacy/`
地址与族兜底，不影响授权）。等 D-192 落地、插件 id 集合成为可查询的部署事实之后，
由 `symbio-deploy` 的 id 表派生，kernel 只留纯函数接收集合。
