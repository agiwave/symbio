# Symbio 协议规范

> 帧 / 载荷 / 通道的准确规格。

## 帧协议 (PluginFrame)

沿 `PluginChannel` 发送的最小消息单位，是 **2 态穷尽枚举**（定义在 `symbio_core`）：
`Data(serde_json::Value)` 或 `Error(message, details)`，其中 `details` 约定含
`{ "code": "ERR_CODE" }`（错误码见 [错误码参考](../004-ref/002-ERROR_CODES.md "RE-002-ERROR_CODES")）。

### 帧类型

| 类型 | 用途 | 示例 |
|------|------|------|
| `Data` | 正常业务数据 | `{"type": "text_delta", "content": "Hello"}` |
| `Error` | 执行异常 | `("API key missing", Some({"code": "CONFIG_ERROR"}))` |

---

## 载荷协议 (PluginPayload)

`route` 和 `traverse` 的返回类型，是 **3 态穷尽枚举**（定义在 `symbio_core`，
变体名即下表左列）：

### 载荷类型

| 类型 | 用途 | 序列化行为 |
|------|------|-----------|
| `Empty` | 操作成功但无返回值 | `null` |
| `Data` | 一次性返回的数据 | 跨进程 → JSON；进程内 → 零拷贝 |
| `Session` | 长连接流式会话 | 返回 channel，后续用帧通信 |

> **构造与访问的签名以代码为准**：`PluginPayload::new` 自动推断载荷类型、
> `payload.get::<T>` 进程内零拷贝 downcast、`payload.serialize` 强制 JSON。
>
> **为什么没有「原生对象」变体**：历史上有一个 `Native(Arc<dyn Any>)`（自述
> 「进程内原生接口」），但它**从未有过构造点**——`Arc<dyn Any>` 恰恰是协议层
> 表达不了的东西，唯二的匹配点只能写「拒绝跨传输」。进程内对象的透传走 `ctx`
> 的扩展桶（`PluginInvokeRequest::set_raw`），与载荷枚举无关：载荷描述「这次调用
> **返回**什么」，扩展桶描述「这次调用**带着**什么」。
>
> **交付分类只有一处**：`gateway::server::classify_payload` 把 3 态分成
> 「一次性」（`Data` / `Empty`）与「长连接」（`Session`），两个传输入口
> （HTTP / WS）共用它，各自只保留**真差异**——HTTP 把 `Session` 折叠为最后一帧、
> WS 做双向转发；`Empty` 在 HTTP 写 `null`、在 WS 直接关连接。

## 通道协议 (PluginChannel)

全双工流式会话的底层通道（收发两端各持一个 `mpsc` 端，定义在 `symbio_core`）。

> **职责边界：`PluginChannel` 只管跨进程传输，不承担执行期协议。**
> 执行层（LLM 单轮 / 工具调用）与宿主层之间的出口 / 入口是 `EventSink` / `AbortSignal`
> （[D-020](001-核心架构.md "DE-001-核心架构")；机制见 [`symbio/src/plugins/session/docs/102-core-loop.md`](../../symbio/src/plugins/session/docs/102-core-loop.md "DE-102-core-loop") §6）——
> 因此**帧里不存在中止帧**。本文件不复述该分离。

### 通道生命周期

```
1. 创建: PluginChannel::pair(buffer_size)
2. 返回: PluginPayload::Session(peer_channel) ← 给调用方
3. 使用: 后端通过 my_channel.tx 发送帧
4. 结束: channel drop → rx 收到 None (EOF)
```

### 缓冲区大小

```rust
// 典型用法
let (my_channel, peer_channel) = PluginChannel::pair(64);
// 64 = 缓冲区帧数，防止慢消费者阻塞生产者
```

## 路由上下文 (PluginInvokeRequest)

请求的上下文注入接口（trait 定义在 core，签名以代码为准）。标准键：

### 标准上下文键

<!-- list:protocol-messages owner -->

| 键 | 类型 | 用途 |
|----|------|------|
| `PATH` | String | 目标路径 (如 `session/stats`；资源类走 `vdfs/*` + `<根>/…` 地址) |
| `payload` | 任意（调用方定） | 交互载荷数据（桶名见 `symbio_core::PLUGIN_PAYLOAD_KEY`） |
| `WORKDIR` | String | 当前工作区根路径 |
| `SESSION_ID` | String | 会话唯一标识 |
| `TRACE_ID` | String | 调用链追踪 ID |
| `AGENT_ID` | String | 当前 Agent 标识 |
| `SOURCE_PRINCIPAL` | String | 入站请求的**来源主体**（完整主体名，如 `agent:main`；[D-067](011-Agent目录规范.md "DE-011-Agent目录规范")）——「这条消息是谁发的」，轮末 `commitment.*` 的 `to` 据它取值；缺省 = 本机用户。线上形态 = 请求 `metadata.source_principal` |
| `CONTENT` | String | 通用内容字段 |
| `KIND` | String | 通用类型字段 |
| `ID` | String | 通用 ID 字段 |
| `NAME` | String | 通用名称字段 |
| `SCOPE` | String | 作用域 |
| `DESCRIPTION` | String | 描述 |

> **哪些键能跨进程**：`SymbioKey::WIRE`（缺省 `true`）声明「本键能否在进程外表达」。
> 标 `false` 的是 6 个**进程内专用**键——`parent`（`Weak<dyn Plugin>`）、
> `tool_visitor` / `option_visitor` / `configurable_visitor`（trait object）、
> `event_sink`（闭包）、`abort_signal`（`CancellationToken`）——它们的值无字符串 /
> JSON 形态，`parse` 恒返 `None`。这是「一次调用能否送到进程外插件」的准入判据。

## 工具发现协议 (traverse)

### 触发常量

```rust
pub const TRAVERSE_AVAILABLE_TOOLS: &str = "available_tools";
```

### 发现流程

```
1. 调用 root.traverse("available_tools", ctx)
2. 容器插件将自身 path 前缀下发给子插件
3. 叶子插件返回 ToolDefinition 列表
4. 工具对模型的全名 = `<挂载点>/<短名>` (如 "local/content_search")
```

### 工具定义

```rust
pub struct CapabilityMeta {
 pub name: String, // 工具名称 (带路径前缀)
 pub description: String, // 工具描述
 pub input_schema: Value, // JSON Schema 参数定义
 pub keywords: Vec<String>, // 意图识别关键词
 pub category: Option<CapabilityCategory>, // 能力分类
 pub examples: Option<Vec<String>>, // 使用示例
}
```

## 跨进程通信 (Tauri IPC)

### 线格式 (Wire Format)

```rust
// 请求
pub struct PluginMessageWire {
 pub metadata: serde_json::Value, // { path, trace_id, origin?, ... }
 pub payload: serde_json::Value, // 业务数据
}

// 响应载荷
pub enum PluginPayloadWire {
 Data(serde_json::Value),
 Connection(String), // 返回连接 ID
}
```

宿主命令面（3 个：`route_v2` / `route_v2_send` / `route_v2_close`）**以
[当前事实表](../004-ref/006-当前事实表.md "RE-006-当前事实表") §5 为准**（自动生成）——本文不抄一份会漂移的副本。

### 流式会话建立

```
1. 前端调用 route_v2 (带 client_id)
2. 后端返回 Connection(conn_id)
3. 后端通过 Tauri emit 推送帧到 `route/{conn_id}` 事件
4. 前端通过 route_v2_send 发送后续帧
5. 前端调用 route_v2_close 关闭连接
```

## AI 会话流式规范

**没有会话专用流协议**：发言 = `vdfs/write(<根>/session/<id>/inbox)`，
输出 = `kind = "vdfs"` 的变更（消息落在 `<id>/message/<mid>`、运行态落在
`<id>`），两端都只需既有的 VDFS 能力：

1. **发一条消息**：`vdfs/write(<根>/session/<id>/inbox, text)` —— 写即入队，响应立刻返回；
2. **看输出**：`event_bus/subscribe` + `vdfs/watch(<根>/session/<id>)`（两步缺一不可，见
 `e2e/cases/t9-ws-stream.mjs`）——首帧带全量、后续带窄 `delta`，顺序由节点属性 `seq` 决定；
3. **终止判据**：会话节点 `status` 离开 `working`（结局在 `attributes.outcome` / `error`），
 它必然排在**本轮全部消息帧之后**（同一 FIFO）。

> 机制与不变量见 [`symbio/src/plugins/session/docs/109-vdfs-session-messages.md`](../../symbio/src/plugins/session/docs/109-vdfs-session-messages.md "DE-109-vdfs-session-messages")；
> 旧形态（`PluginPayload::Session(channel)` + `PluginFrame::Data(done)`）已随 D-025 退役。

## 事件总线频道 (`kind`)

AI 增量与资源变更**不随请求返回**，而是经全局事件总线广播：客户端建立连接后另发一帧
`event_bus/subscribe`（HTTP/WS 入口见 [HTTP(S) 开放接口插件设计](013-HTTP开放接口.md "DE-013-HTTP开放接口") §5.3），
之后持续收到 `{ type: "bus_event", data: { kind, session_id, data } }` 帧，**按 `kind` 分派**。

`kind` 的闭集是 `system` / `vdfs` <!-- vocab:EVENT_BUS_KIND_ -->，常量定义在
`symbio_core::event_bus`（`EVENT_BUS_KIND_SYSTEM` / `EVENT_BUS_KIND_VDFS`）。**发布方一律引
常量**——`kind` 是跨进程字符串，改名不会编译失败，只会让消费方静默失效（`grep-audit`
的 S-009 拦裸字面量）：

| `kind` | 发布方 | 消费方 |
|--------|--------|--------|
| `system` | 总线插件自身（`event_bus/subscribe` 的 `connected` 握手） | 前端订阅连接 |
| `vdfs` | vdfs 宿主的变更投递（`plugins/vdfs/host.rs`） | **一切资源与转写的实时消费方**：前端（`composables/useVdfs.ts` 通用浏览器、`stores/sessionNodeSync.ts` 会话清单、会话转写）、`cli`（`cli/src/client.rs`）、telegram 回合（`plugins/telegram/turn.rs`）、子智能体转播桥（`plugins/agent/host/subagent.rs`）——都按**地址**分派，不依赖事件到达顺序 |

> **帧只有两种，解包入口也只有一个对**：变更由 `event_bus_vdfs_change_of` 解出，
> **背压重同步指令**（`{ "data": { "type": "resync" } }`，刻意不带 `path`）由
> `event_bus_resync_of` 认出——两者互斥，且都由 `symbio_core::event_bus` 提供。
> 消费方**不许手写判别**：一条指令的含义是「你可能漏了帧，按自己的作用域重读」，
> 而漏认它的那一方表现为「子会话早已收尾、父会话仍在等」——它没有第二条通道可等。
> 通道满时的处置（丢帧 + **保留订阅** + 补送指令）见 `symbio_core::event_bus` 的
> `EventBus::try_publish`；这里**没有投递序号**，靠幂等重读兜底
> （[D-025](#d-025-顺序是节点属性不是投递属性)）。

> **会话域不另设频道**：消息与运行态都是 VDFS 变更——消息是 `<根>/session/<id>/message/<mid>`
> 这个**文件**，运行态是会话节点（`<根>/session/<id>`）的 `status`，因此都走 `kind = "vdfs"`。
> 顺序是**节点属性**（`ChatNode.seq`，消费端按它排序），**不是投递属性**——所以「到达顺序」
> 与「显示顺序」无关，无需任何投递层的顺序保证
> （[D-025](#d-025-顺序是节点属性不是投递属性)）。
>
> **资源变更不另设频道**：一切资源的生命周期与状态变化都是 VDFS 变更，统一走 `vdfs`。
>
> **它是广播通道，不是多频道总线**：
> `kind` 是闭集两条、服务端不按 `kind` 分流（订阅请求 `EventBusSubscribeRequest` 里没有
> 过滤器字段），分派一律发生在**消费方自己那一侧、按地址**。`event_bus` 与 `bus_event`
> 分别是插件身份与跨栈线上名，保留它们不是待清的债；要把这里做成真多频道总线
> （服务端分流 + 新增频道），先立一条决策再说形状。

## 数据契约 (Schemas)

跨端数据结构**不再集中在一个目录**：每个结构住在「它描述什么」的那个域里
（[D-087](001-核心架构.md "DE-001-核心架构")）。原来的 `symbio_core/schemas/` 把三件不相关的
事装进了同一个名字——会话线格式、对话面控制契约、宿主呈现方言——而它的存在又让
这些类型绕过了 §1.2 的域前缀纪律（该目录曾是前缀规则的唯一豁免）。

| 契约 | 住哪（`symbio_core::`） |
|---|---|
| 会话线格式（`ChatNode` 家族 / `Principal` / 两个入口请求） | [`chat/`](../../symbio/src/symbio_core/chat/)——叶子模块 `chat_node` / `principal` / `chat_request` / `session_chat` |
| 对话面控制契约（`Verdict` / `DecideRequest` / `ComposeRequest` / `WordingReply` / `RunSnapshot`） | [`dialog/`](../../symbio/src/symbio_core/dialog/) |
| 宿主呈现方言（`Detail*` / `Reading*`） | [`present/`](../../symbio/src/symbio_core/present/)——`detail` / `reading` |
| 轮次面（`Turn*` / 动作载荷 / 压缩包） | [`turn/`](../../symbio/src/symbio_core/turn/)——`dispatch` / `node_build` / `facts` |
| 插件扩展点（`HookEvent` / `HookOutput`）与路由回体（`SimpleResponse` / `SuccessResponse`） | [`plugin/`](../../symbio/src/symbio_core/plugin/)——`hook.rs` / `response.rs` |
| 模型状态帧（`llm_emit_message` 等） | [`llm/`](../../symbio/src/symbio_core/llm/)——`frames.rs` |
| 事件 → 状态的读侧重放（`rebuild`） | [`projection/`](../../symbio/src/symbio_core/projection/)——`rebuild.rs` |

**文件清单以目录为准**，本文不抄一份会漂移的副本。命名与归属的机械判据是
[`core-naming-audit`](../../scripts/core-naming-audit.mjs)，规则源是
[内核 README §1.2 的域前缀对照表](../../symbio/src/symbio_core/README.md "symbio/src/symbio_core/README")。

两条命名约定：

- 所有结构派生 `Serialize` / `Deserialize`，命名**全程 `snake_case`**——线上键名与 Rust 字段名
 逐字相同，**没有任何 host 侧的 `camelCase` 转换**；
- 唯一例外是 [`plugins/mcp/types.rs`](../../symbio/src/plugins/mcp/types.rs)：它镜像 MCP 的**外部
 规范报文**（`readOnlyHint` 等），camelCase 由规范规定，故用 `#[serde(rename_all = "camelCase")]`
 显式声明。

## 注册与扩展

### `submit_object_creator!` 宏

每个插件模块在其 `plugin.rs` 末尾调用：

```rust
submit_object_creator!(PLUGIN_X, XPlugin::build, dyn Plugin);
```

宏利用 [`inventory`](https://docs.rs/inventory) 在编译期把构造函数注册到全局 `ObjectCreatorRegistry`。宿主首次调用 `creator_create_object::<dyn Plugin>(id, ctx)` 时惰性收集完毕，**无需手动注册**。

### 工厂只给「有第二种实现」的服务

`creator_create_object::<dyn T>(名字, ctx)` 的价值是**换实现不改调用方**，因此只有可替换的
宿主服务登记工厂项（`dyn Plugin`、`dyn EmbeddingService`）。

**资源存储不走工厂**：`providers/vdfs_service` 的三个实现（`SingleFileVdfs` /
`DirVdfs` / `MemoryVdfs`）本身就是 `VdfsProvider`（接口在 core 已定，不会换），
插件**直接组合具体类型**——`use crate::providers::{DirVdfs, SingleFileVdfs,
MemoryVdfs}`（`providers` 是唯一出口，子目录私有、不深引）。套一层 `dyn` 工厂只会把一次构造换成一次字符串查表。
（历史上这里有一个工厂项 `"storage_service"`，随 `StorageService` / `EntityStore`
一并废除；定位与依赖边界见 [VDFS 前端页面规范](010-VDFS前端页面规范.md "DE-010-VDFS前端页面规范") §2 分层与落点 与 §8 一致性要求。）

### 容器动态挂载

`home` 构造 `worker`（Composite）时经 ctx 键 `REQUIRED_PLUGINS` 传入**必需插件清单**
（`home::SYSTEM_PLUGINS`）；容器据此**扫描自己的目录**（其下一层目录即一个插件）——逐目录读
`PLUGIN.yml`，`plugin_provider` 指向已注册工厂（`creator_has`）即 `creator_create_object`
实例化，并把该目录经 ctx 键 `PLUGIN_DIR` 告知插件（插件据此读写**自己的**配置）。
容器**不内置任何清单**（它是通用容器，可以嵌套另一个容器）。

### `PLUGIN.yml` 的保留键

保留键属于**装配方**（容器 / 插件管理插件），插件自己的配置不得占用同名键。
单一清单见 `symbio_core::plugin::dir::PLUGIN_RESERVED_KEYS`——读写时的「剥离 / 保留」都遍历它。

| 键 | 谁写 | 说明 |
|---|---|---|
| `plugin_provider` | 装配方 | 工厂 id（装配方据此构造） |
| `plugin_name` | 装配方 | 实例名；缺省 = 目录名 |
| `plugin_enabled` | 装配方 | 装配位；键不存在 = 启用 |
| `plugin_title` / `plugin_description` / `plugin_version` / `plugin_author` | 装配期**一次性**投影 | 插件**身份**（运行期唯一来源，见 D-032） |
| `plugin_api` | 插件作者手写 | 要求的宿主插件 API 版本（第三期起强制校验） |
| `plugin_grants` | 宿主手写 | 宿主**授予**的能力闭集（第三方插件规范 §7） |

**身份的投影方向是单向的**：出厂声明（`Plugin::meta`）→ 装配期落进 manifest →
此后 manifest 权威（用户可改），运行期一切消费（`PluginEntry`、挂载点目录节点）
都读 manifest。因此**停用的插件也有身份**——它只是不被构造，而不是不存在
（D-032）。

新增插件只需：
1. 把目录放到 `symbio/src/plugins/` 并实现 `Plugin`
2. 调用 `submit_object_creator!` 注册工厂
3. 若要随系统启动，把插件名加进 `home::SYSTEM_PLUGINS`
4. 在配置里挂载

## 关键决策

> 本节是**仍然约束现行代码的取舍**：每条一句决策、一句理由。已退场或主题已消失的决策不在其中（`git log` 是历史）。

### D-019 跨栈契约手工镜像 + 审计守卫；G3 前端面板去语义否决

前端 `tauri/src/schemas/` 与后端 `symbio_core` 之间是手工镜像。复核给出两条路：引入 `ts-rs` / `schemars` 从 Rust 导出 TS，或扩展 `scripts/protocol-mirror-audit.mjs` 把已存在的镜像纳入守卫。

### D-022 SSE 增量解析：契约拆两个方法，字段名留协议层

为了首字延迟，`parse_sse_stream` 在换行到达前会先尝试从半截 JSON 里挤出正文。这件事原先由 core 内置的启发式解析器代劳（在整行里搜五个硬编码字段名），三个后果：加协议要改 core；两条路径两套转义（core 的 `unescape_partial` 与协议解析器的 `serde_json` 对 `\uXXXX` 处理不同 ⇒ 按前缀截断会吃字，最隐蔽——不报错，只是偶尔少一个字）；

### D-069 Principal 三字段——kind 与 id 分家，id 是可路由地址

`ChatNode.principal: Option<String>` 今天承载两件事——「主体是谁」与「主体是哪一族」。 值域 `agent:main` / `user` 把 kind 编进了字符串本身；`AGENT_PREFIX = "agent:"` 是判定用的形状， `matrix_for` 与 `visible_to` 都靠它分岔。三处形状问题： kind 混在 id 里 ⇒ id 不再可路由。

### D-079 同名两物：core 的 ActorSpec.pattern 是主体分类，S11 §4 的 actor.pattern 是开关参数——前者不该做分派点

立项时的 判断是「`ActorSpec.pattern` 生产零读取，三处 Decider 特判各自为政——让它成为分派点」。核完前提 发现这句话里藏着一个系统里有两个都叫 `pattern` 的东西，而且它们不是同一个。

### D-091 事件不做 schema 版本化：用「只增不改」换掉一个没有读方的版本号

事件信封不加 `schema_version`，`payload` 保持无类型 JSON。 作为交换，把「只增不改」 写成三条可核对的纪律，并明写这套做法判不了的三类情形与它的失效边界—— 不写就是拿一句纪律盖住一个不可判定的事实。

### D-095 keys 域环拆解：键与值同住，Aborted 载荷不跨域，vdfs_change_of 归 event_bus

keys域环拆解 把 `core-vocab-audit`（V-002）基线里最大的一族八域连环（`capability⇄chat⇄event_bus⇄exec⇄keys⇄llm⇄plugin⇄present⇄vdfs`） 拆到消失。三条决策，各自独立生效： 键定义搬到值所在的域（根因一）。

### D-112 跨栈清单与载荷不另立自述面：路由的真相是 route 的臂，载荷的真相是命名类型

三项判据（E-012 的常量值真实性、契约表的键多一即红、G 组的顶层字段必须有直接消费者） 都已经是「代码 vs 代码的投影」型判据，`manifest` 属于另一种形状：代码 vs 代码的复述。 本仓对后者的态度一贯（D-070 / D-111 都在删复述，不在加复述）。 「难实现/不够优雅」都不构成理由；

### D-025 顺序是节点属性，不是投递属性

**决策**：`ChatNode.seq` = 消息在该文件夹里的位置，由写入者分配、随节点下发，消费端按它排序。
「追加」不是新取值，而是载荷上的 `delta` 字段（有 ⇒ 尾部追加、零回读；无 ⇒ 回读 `stat` / `read`
收敛）；不加快照载荷（`node` / `content`）——快照携带的是生成那一刻的状态，迟应用会把运行态
回退，那是**陈旧写入**问题，与乱序无关。信封收敛为 `{path, data?}`，操作枚举（`created` /
`updated` / `deleted`）整个退役，`kind = "vdfs"` 是唯一实时通道。

**理由**：到达顺序与显示顺序因此无关——后生成的先到、两个并行工具的变更混着到，都正确显示。
把「顺序」当成「传输的属性」曾导致两次拆解（先在资源变更频道挂 `delta`，后另开转写流），
两次都是在为数据属性造传输机制。**丢失靠幂等重读兜底，不靠序号**：通道满 ⇒ 保留订阅 + 补送
resync，会话终态 ⇒ 宽限定时器复查非终态节点后整份回读。
