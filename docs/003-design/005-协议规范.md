# 协议规范

> 帧 / 载荷 / 通道的准确规格。

## 帧协议 (PluginFrame)

沿 `PluginChannel` 发送的最小消息单位，是 **2 态穷尽枚举**（定义在 `symbio-kernel` 的 `plugin` 域）：
`Data(serde_json::Value)` 或 `Error(message, details)`，其中 `details` 约定含
`{ "code": "ERR_CODE" }`（错误码见 [错误码参考](../004-ref/002-ERROR_CODES.md "RE-002-ERROR_CODES")）。

### 帧类型

| 类型 | 用途 | 示例 |
|------|------|------|
| `Data` | 正常业务数据 | `{"type": "text_delta", "content": "Hello"}` |
| `Error` | 执行异常 | `("API key missing", Some({"code": "CONFIG_ERROR"}))` |

---

## 载荷协议 (PluginPayload)

`route` 和 `traverse` 的返回类型，是 **3 态穷尽枚举**（定义在 `symbio-kernel`，
变体名即下表左列）：

### 载荷类型

| 类型 | 用途 | 序列化行为 |
|------|------|-----------|
| `Empty` | 操作成功但无返回值 | `null` |
| `Data` | 一次性返回的数据 | 跨进程 → JSON；进程内 → 零拷贝 |
| `Session` | 长连接流式会话 | 返回 channel，后续用帧通信 |

> **构造与访问的签名以代码为准**：`PluginPayload::new` 自动推断载荷类型、
> `payload.get::<T>` 进程内零拷贝 downcast、`payload.serialize` 强制 JSON。
>
> **为什么没有「原生对象」变体**：历史上有一个 `Native(Arc<dyn Any>)`（自述
> 「进程内原生接口」），但它**从未有过构造点**——`Arc<dyn Any>` 恰恰是协议层
> 表达不了的东西，唯二的匹配点只能写「拒绝跨传输」。进程内对象的透传走 `ctx`
> 的扩展桶（`PluginInvokeRequest::set_raw`），与载荷枚举无关：载荷描述「这次调用
> **返回**什么」，扩展桶描述「这次调用**带着**什么」。
>
> **交付分类只有一处**：`gateway::server::classify_payload` 把 3 态分成
> 「一次性」（`Data` / `Empty`）与「长连接」（`Session`），两个传输入口
> （HTTP / WS）共用它，各自只保留**真差异**——HTTP 把 `Session` 折叠为最后一帧、
> WS 做双向转发；`Empty` 在 HTTP 写 `null`、在 WS 直接关连接。

## 通道协议 (PluginChannel)

全双工流式会话的底层通道（收发两端各持一个 `mpsc` 端，定义在 `symbio-kernel`）。

> **职责边界：`PluginChannel` 只管跨进程传输，不承担执行期协议。**
> 执行层（LLM 单轮 / 工具调用）与宿主层之间的出口 / 入口是 `EventSink` / `AbortSignal`
> （[D-020](001-核心架构.md "DE-001-核心架构")；机制见 [`crates/symbio-plugin-session/src/docs/102-core-loop.md`](../../crates/symbio-plugin-session/src/docs/102-core-loop.md "DE-102-core-loop") §6）——
> 因此**帧里不存在中止帧**。本文件不复述该分离。

### 通道生命周期

```
1. 创建: PluginChannel::pair(buffer_size)
2. 返回: PluginPayload::Session(peer_channel) ← 给调用方
3. 使用: 后端通过 my_channel.tx 发送帧
4. 结束: channel drop → rx 收到 None (EOF)
```

### 缓冲区大小

```rust
// 典型用法
let (my_channel, peer_channel) = PluginChannel::pair(64);
// 64 = 缓冲区帧数，防止慢消费者阻塞生产者
```

## 路由上下文 (PluginInvokeRequest)

请求的上下文注入接口（trait 定义在 core，签名以代码为准）。标准键：

### 标准上下文键

<!-- list:protocol-messages owner -->

| 键 | 类型 | 用途 |
|----|------|------|
| `PATH` | String | 目标路径 (如 `session/stats`；资源类走 `vdfs/*` + `<根>/…` 地址) |
| `payload` | 任意（调用方定） | 交互载荷数据（桶名见 `symbio_kernel::plugin::PLUGIN_PAYLOAD_KEY`） |
| `WORKDIR` | String | 当前工作区根路径 |
| `SESSION_ID` | String | 会话唯一标识 |
| `TRACE_ID` | String | 调用链追踪 ID |
| `AGENT_ID` | String | 当前 Agent 标识 |
| `SOURCE_PRINCIPAL` | String | 入站请求的**来源主体**（完整主体名，如 `session/main`；[D-067](011-Agent目录规范.md "DE-011-Agent目录规范")）——「这条消息是谁发的」，轮末 `commitment.*` 的 `to` 据它取值；缺省 = 本机用户。线上形态 = 请求 `metadata.source_principal` |
| `CONTENT` | String | 通用内容字段 |
| `KIND` | String | 通用类型字段 |
| `ID` | String | 通用 ID 字段 |
| `NAME` | String | 通用名称字段 |
| `SCOPE` | String | 作用域 |
| `DESCRIPTION` | String | 描述 |

> **哪些键能跨进程**：`SymbioKey::WIRE`（缺省 `true`）声明「本键能否在进程外表达」。
> 标 `false` 的是 6 个**进程内专用**键——`parent`（`Weak<dyn Plugin>`）、
> `tool_visitor` / `option_visitor` / `configurable_visitor`（trait object）、
> `event_sink`（闭包）、`abort_signal`（`CancellationToken`）——它们的值无字符串 /
> JSON 形态，`parse` 恒返 `None`。这是「一次调用能否送到进程外插件」的准入判据。

## 工具发现协议 (traverse)

### 触发常量

```rust
pub const TRAVERSE_AVAILABLE_TOOLS: &str = "available_tools";
```

### 发现流程

```
1. 调用 root.traverse("available_tools", ctx)
2. 容器插件将自身 path 前缀下发给子插件
3. 叶子插件返回 ToolDefinition 列表
4. 工具对模型的全名 = `<挂载点>/<短名>` (如 "local/content_search")
```

### 工具定义

```rust
pub struct CapabilityMeta {
 pub name: String, // 工具名称 (带路径前缀)
 pub description: String, // 工具描述
 pub input_schema: Value, // JSON Schema 参数定义
 pub keywords: Vec<String>, // 意图识别关键词
 pub category: Option<CapabilityCategory>, // 能力分类
 pub examples: Option<Vec<String>>, // 使用示例
}
```

## 跨进程通信 (Tauri IPC)

### 线格式 (Wire Format)

```rust
// 请求
pub struct PluginMessageWire {
 pub metadata: serde_json::Value, // { path, trace_id, origin?, ... }
 pub payload: serde_json::Value, // 业务数据
}

// 响应载荷
pub enum PluginPayloadWire {
 Data(serde_json::Value),
 Connection(String), // 返回连接 ID
}
```

### Tauri Commands

宿主命令面（3 个：`route_v2` / `route_v2_send` / `route_v2_close`）**以
[当前事实表](../004-ref/006-当前事实表.md "RE-006-当前事实表") §5 为准**（自动生成）——本文不抄一份会漂移的副本。

### 流式会话建立

```
1. 前端调用 route_v2 (带 client_id)
2. 后端返回 Connection(conn_id)
3. 后端通过 Tauri emit 推送帧到 `route/{conn_id}` 事件
4. 前端通过 route_v2_send 发送后续帧
5. 前端调用 route_v2_close 关闭连接
```

## AI 会话流式规范

**没有会话专用流协议**：发言 = `vdfs/write(<根>/session/<id>/inbox)`，
输出 = `kind = "vdfs"` 的变更（消息落在 `<id>/message/<mid>`、运行态落在
`<id>`），两端都只需既有的 VDFS 能力：

1. **发一条消息**：`vdfs/write(<根>/session/<id>/inbox, text)` —— 写即入队，响应立刻返回；
2. **看输出**：`event_bus/subscribe` + `vdfs/watch(<根>/session/<id>)`（两步缺一不可，见
 `e2e/cases/t9-ws-stream.mjs`）——首帧带全量、后续带窄 `delta`，顺序由节点属性 `seq` 决定；
3. **终止判据**：会话节点 `status` 离开 `working`（结局在 `attributes.outcome` / `error`），
 它必然排在**本轮全部消息帧之后**（同一 FIFO）。

> 机制与不变量见 [`crates/symbio-plugin-session/src/docs/109-vdfs-session-messages.md`](../../crates/symbio-plugin-session/src/docs/109-vdfs-session-messages.md "DE-109-vdfs-session-messages")；
> 旧形态（`PluginPayload::Session(channel)` + `PluginFrame::Data(done)`）已随 D-025 退役。

## 事件总线频道 (`kind`)

AI 增量与资源变更**不随请求返回**，而是经全局事件总线广播：客户端建立连接后另发一帧
`event_bus/subscribe`（HTTP/WS 入口见 [HTTP 开放接口](013-HTTP开放接口.md "DE-013-HTTP开放接口") §5.3），
之后持续收到 `{ type: "bus_event", data: { kind, session_id, data } }` 帧，**按 `kind` 分派**。

`kind` 的闭集是 `system` / `vdfs` <!-- vocab:EVENT_BUS_KIND_ -->，常量定义在
`symbio_sdk::event_bus`（`EVENT_BUS_KIND_SYSTEM` / `EVENT_BUS_KIND_VDFS`）。**发布方一律引
常量**——`kind` 是跨进程字符串，改名不会编译失败，只会让消费方静默失效（`grep-audit`
的 S-009 拦裸字面量）：

| `kind` | 发布方 | 消费方 |
|--------|--------|--------|
| `system` | 总线插件自身（`event_bus/subscribe` 的 `connected` 握手） | 前端订阅连接 |
| `vdfs` | vdfs 宿主的变更投递（`crates/symbio-plugin-vdfs/src/host.rs`） | **一切资源与转写的实时消费方**：前端（`composables/useVdfs.ts` 通用浏览器、`stores/sessionNodeSync.ts` 会话清单、会话转写）、`cli`（`crates/symbio-cli/src/client.rs`）、telegram 回合（`crates/symbio-plugin-telegram/src/turn.rs`）、子智能体转播桥（`crates/symbio-plugin-agent/src/host/subagent.rs`）——都按**地址**分派，不依赖事件到达顺序 |

> **帧只有两种，解包入口也只有一个对**：变更由 `event_bus_vdfs_change_of` 解出，
> **背压重同步指令**（`{ "data": { "type": "resync" } }`，刻意不带 `path`）由
> `event_bus_resync_of` 认出——两者互斥，且都由 `symbio_sdk::event_bus` 提供。
> 消费方**不许手写判别**：一条指令的含义是「你可能漏了帧，按自己的作用域重读」，
> 而漏认它的那一方表现为「子会话早已收尾、父会话仍在等」——它没有第二条通道可等。
> 通道满时的处置（丢帧 + **保留订阅** + 补送指令）见 `symbio_sdk::event_bus` 的
> `EventBus::try_publish`；这里**没有投递序号**，靠幂等重读兜底
> （[D-025](#d-025-顺序是节点属性不是投递属性)）。

> **会话域不另设频道**：消息与运行态都是 VDFS 变更——消息是 `<根>/session/<id>/message/<mid>`
> 这个**文件**，运行态是会话节点（`<根>/session/<id>`）的 `status`，因此都走 `kind = "vdfs"`。
> 顺序是**节点属性**（`ChatNode.seq`，消费端按它排序），**不是投递属性**——所以「到达顺序」
> 与「显示顺序」无关，无需任何投递层的顺序保证
> （[D-025](#d-025-顺序是节点属性不是投递属性)）。
>
> **资源变更不另设频道**：一切资源的生命周期与状态变化都是 VDFS 变更，统一走 `vdfs`。
>
> **它是广播通道，不是多频道总线**：
> `kind` 是闭集两条、服务端不按 `kind` 分流（订阅请求 `EventBusSubscribeRequest` 里没有
> 过滤器字段），分派一律发生在**消费方自己那一侧、按地址**。`event_bus` 与 `bus_event`
> 分别是插件身份与跨栈线上名，保留它们不是待清的债；要把这里做成真多频道总线
> （服务端分流 + 新增频道），先立一条决策再说形状。

## 数据契约 (Schemas)

跨端数据结构**不集中在一个目录**：每个结构住在「它描述什么」的那个域里
（[D-087](001-核心架构.md "DE-001-核心架构")）。把会话线格式、对话面控制契约、宿主呈现方言
这三件不相关的事装进同一个 `schemas` 名字，会让这些类型绕开 §1.2 的域前缀纪律。

| 契约 | 住哪 |
|---|---|
| 会话线格式（`ChatNode` 家族 / `Principal` / 两个入口请求） | [`chat/`](../../crates/symbio-sdk/src/chat/)——叶子模块 `chat_node` / `principal` / `chat_request` / `session_chat` |
| 对话面控制契约（`Verdict` / `DecideRequest` / `ComposeRequest` / `WordingReply` / `RunSnapshot`） | [`dialog.rs`](../../crates/symbio-contract/src/dialog.rs)——契约层（`symbio_contract::`，门面转出） |
| 宿主呈现方言（`Detail*` / `Reading*`） | [`present/`](../../crates/symbio-kernel/src/present/)——`detail` / `reading` |
| 轮次面（`Turn*` / 动作载荷 / 压缩包） | [`turn/`](../../crates/symbio-sdk/src/turn/)——`dispatch` / `node_build` / `facts` |
| 插件扩展点（`HookEvent` / `HookOutput`）与路由回体（`SimpleResponse` / `SuccessResponse`） | [`plugin/`](../../crates/symbio-sdk/src/plugin/)——`hook.rs` / `response.rs` |
| 模型输入词汇（`PromptMessage`） | [`llm.rs`](../../crates/symbio-contract/src/llm.rs)——契约层；模型状态帧发射（`llm_emit_message` 等）仍住 [`llm/round.rs`](../../crates/symbio-sdk/src/llm/round.rs)（服务臂，有 IO） |
| 事件 → 状态的读侧重放（`rebuild`） | [`projection/`](../../crates/symbio-sdk/src/projection/)——`rebuild.rs` |

**文件清单以目录为准**，本文不抄一份会漂移的副本。跨端结构的住址随
[D-486](023-内核边界与扩展局部性.md "DE-023-内核边界与扩展局部性") 五层规划变为三处：
内核（封闭语法）、`symbio-contract`（插件 ABI 纯形状）、`symbio-sdk`（宿主机制与策略）——
纯形状归契约层，带 IO / 机制的归 sdk。命名与归属的机械判据是
[`domain-vocab-audit`](../../scripts/domain-vocab-audit.mjs)（域清单与依赖方向）与
[`arch-shape-audit`](../../scripts/arch-shape-audit.mjs)（数据面棘轮）。

两条命名约定：

- 所有结构派生 `Serialize` / `Deserialize`，命名**全程 `snake_case`**——线上键名与 Rust 字段名
 逐字相同，**没有任何 host 侧的 `camelCase` 转换**；
- 唯一例外是 [`crates/symbio-plugin-mcp/src/types.rs`](../../crates/symbio-plugin-mcp/src/types.rs)：它镜像 MCP 的**外部
 规范报文**（`readOnlyHint` 等），camelCase 由规范规定，故用 `#[serde(rename_all = "camelCase")]`
 显式声明。

## 注册与扩展

### `submit_object_creator!` 宏

每个插件模块在其 `plugin.rs` 末尾调用：

```rust
submit_object_creator!(PLUGIN_X, XPlugin::build, dyn Plugin);
```

宏利用 [`inventory`](https://docs.rs/inventory) 在编译期把构造函数注册到全局 `ObjectCreatorRegistry`。宿主首次调用 `creator_create_object::<dyn Plugin>(id, ctx)` 时惰性收集完毕，**无需手动注册**。

### 工厂只给「有第二种实现」的服务

`creator_create_object::<dyn T>(名字, ctx)` 的价值是**换实现不改调用方**，因此只有可替换的
宿主服务登记工厂项（`dyn Plugin`、`dyn EmbeddingService`）。

**资源存储不走工厂**：`providers/vdfs_service` 的三个实现（`SingleFileVdfs` /
`DirVdfs` / `MemoryVdfs`）本身就是 `VdfsProvider`（接口在 core 已定，不会换），
插件**直接组合具体类型**——`use crate::providers::{DirVdfs, SingleFileVdfs,
MemoryVdfs}`（`providers` 是唯一出口，子目录私有、不深引）。套一层 `dyn` 工厂只会把一次构造换成一次字符串查表。
（历史上这里有一个工厂项 `"storage_service"`，随 `StorageService` / `EntityStore`
一并废除；定位与依赖边界见 [VDFS 前端页面规范](010-VDFS前端页面规范.md "DE-010-VDFS前端页面规范") §2 分层与落点与 §8 一致性要求。）

### 容器动态挂载

`home` 构造 `worker`（Composite）时经 ctx 键 `REQUIRED_PLUGINS` 传入**必需插件清单**
（`home::SYSTEM_PLUGINS`）；容器据此**扫描自己的目录**（其下一层目录即一个插件）——逐目录读
`PLUGIN.yml`，`plugin_provider` 指向已注册工厂（`creator_has`）即 `creator_create_object`
实例化，并把该目录经 ctx 键 `PLUGIN_DIR` 告知插件（插件据此读写**自己的**配置）。
容器**不内置任何清单**（它是通用容器，可以嵌套另一个容器）。

### `PLUGIN.yml` 的保留键

保留键属于**装配方**（容器 / 插件管理插件），插件自己的配置不得占用同名键。
单一清单见 `symbio_sdk::plugin::dir::PLUGIN_RESERVED_KEYS`——读写时的「剥离 / 保留」都遍历它。

| 键 | 谁写 | 说明 |
|---|---|---|
| `plugin_provider` | 装配方 | 工厂 id（装配方据此构造） |
| `plugin_name` | 装配方 | 实例名；缺省 = 目录名 |
| `plugin_enabled` | 装配方 | 装配位；键不存在 = 启用 |
| `plugin_title` / `plugin_description` / `plugin_version` / `plugin_author` | 装配期**一次性**投影 | 插件**身份**（运行期唯一来源，见 D-032） |
| `plugin_api` | 插件作者手写 | 要求的宿主插件 API 版本（第三期起强制校验） |
| `plugin_grants` | 宿主手写 | 宿主**授予**的能力闭集（第三方插件规范 §7） |

**身份的投影方向是单向的**：出厂声明（`Plugin::meta`）→ 装配期落进 manifest →
此后 manifest 权威（用户可改），运行期一切消费（`PluginEntry`、挂载点目录节点）
都读 manifest。因此**停用的插件也有身份**——它只是不被构造，而不是不存在
（D-032）。

新增插件只需：
1. 建一个 crate `crates/symbio-plugin-<id>/`，实现 `Plugin` 并调用
 `submit_object_creator!` 注册工厂
2. 在 crate 根写 `PLUGIN.yml`（`plugin_provider` 指向该工厂；`plugin_assembly`
 决定它进哪棵标准树），链接行与装配清单由 `scripts/facts/` 的生成器投影
3. 若要随系统启动，确认生成出的 `ASSEMBLY_SUB_AGENT_PLUGINS` 含它
 （`plugin_assembly` 的取值决定，不在插件里另写清单）
4. 在运行期配置（`<homedir>/<id>/PLUGIN.yml`）里挂载

> **维护原则**：协议变更必须向后兼容，错误码字符串是 ABI 的一部分。

## 关键决策

> 本节收录口径见 [DE-017 §6](017-登记与汇总机制.md "DE-017-登记与汇总机制")。

### D-019 跨栈契约手工镜像 + 审计守卫；G3 前端面板去语义否决

前端 `tauri/src/schemas/` 与后端 `symbio-kernel` 之间是手工镜像。复核给出两条路：引入 `ts-rs` / `schemars` 从 Rust 导出 TS，或扩展 `scripts/protocol-mirror-audit.mjs` 把已存在的镜像纳入守卫。

### D-022 SSE 增量解析：契约拆两个方法，字段名留协议层

为了首字延迟，`parse_sse_stream` 在换行到达前会先尝试从半截 JSON 里挤出正文。这件事原先由 core 内置的启发式解析器代劳（在整行里搜五个硬编码字段名），三个后果：加协议要改 core；两条路径两套转义（core 的 `unescape_partial` 与协议解析器的 `serde_json` 对 `\uXXXX` 处理不同 ⇒ 按前缀截断会吃字，最隐蔽——不报错，只是偶尔少一个字）；

### D-069 Principal 三字段——kind 与 id 分家，id 是可路由地址

`ChatNode.principal` **只承载 id**（可路由地址），kind 由独立的 `PrincipalKind` 给——值域是按归属插件分段的地址（`session/main` / `person/local` / `vdfs/write` …），不再是「把 kind 编进字符串」的形状。分派判据是独立的 `PrincipalKind`（`is_agent()` 给族），id 层只做归属段解析（`crates/symbio-sdk/src/authz/mod.rs::principal_namespace`），id 因此始终可路由。

### D-079 同名两物：core 的 ActorSpec.pattern 是主体分类，DE-041 §4 的 actor.pattern 是开关参数——前者不该做分派点

立项时的判断是「`ActorSpec.pattern` 生产零读取，三处 Decider 特判各自为政——让它成为分派点」。核完前提后发现这句话里藏着一个系统里有两个都叫 `pattern` 的东西，而且它们不是同一个。

### D-091 事件不做 schema 版本化：用「只增不改」换掉一个没有读方的版本号

事件信封不加 `schema_version`，`payload` 保持无类型 JSON。作为交换，把「只增不改」写成三条可核对的纪律，并明写这套做法判不了的三类情形与它的失效边界——不写就是拿一句纪律盖住一个不可判定的事实。

### D-095 keys 域环拆解：键与值同住，Aborted 载荷不跨域，vdfs_change_of 归 event_bus

`keys` 域环拆解把 `core-vocab-audit`（V-002）基线里最大的一族八域连环（`capability⇄chat⇄event_bus⇄exec⇄keys⇄llm⇄plugin⇄present⇄vdfs`）拆到消失。三条决策，各自独立生效：键定义搬到值所在的域（根因一）。

### D-112 跨栈清单与载荷不另立自述面：路由的真相是 route 的臂，载荷的真相是命名类型

三项判据（E-012 的常量值真实性、契约表的键多一即红、G 组的顶层字段必须有直接消费者） 都已经是「代码 vs 代码的投影」型判据，`manifest` 属于另一种形状：代码 vs 代码的复述。本仓对后者的态度一贯（D-070 / D-111 都在删复述，不在加复述）。「难实现/不够优雅」都不构成理由；

### D-025 顺序是节点属性，不是投递属性

**决策**：`ChatNode.seq` = 消息在该文件夹里的位置，由写入者分配、随节点下发，消费端按它排序。
「追加」不是新取值，而是载荷上的 `delta` 字段（有 ⇒ 尾部追加、零回读；无 ⇒ 回读 `stat` / `read`
收敛）；不加快照载荷（`node` / `content`）——快照携带的是生成那一刻的状态，迟应用会把运行态
回退，那是**陈旧写入**问题，与乱序无关。信封收敛为 `{path, data?}`，操作枚举（`created` /
`updated` / `deleted`）整个退役，`kind = "vdfs"` 是唯一实时通道。

**理由**：到达顺序与显示顺序因此无关——后生成的先到、两个并行工具的变更混着到，都正确显示。
把「顺序」当成「传输的属性」曾导致两次拆解（先在资源变更频道挂 `delta`，后另开转写流），
两次都是在为数据属性造传输机制。**丢失靠幂等重读兜底，不靠序号**：通道满 ⇒ 保留订阅 + 补送
resync，会话终态 ⇒ 宽限定时器复查非终态节点后整份回读。

### D-266 多模态不进载荷形状：产物走 `Domain` + 引用，上限写在这里

**裁决**：不开放 `Event.payload` / `ChatNode` 的形状。多模态内容作为**领域产物**存在
（`Entity::Domain` 的事实 + VDFS 可寻址路径），转写里只留「引用 + 替代文本」
（markdown 链接形态）。供应商侧的收发转换住在 provider 插件——**形状转换在组装请求
那一刻发生，不落到事实上**。名册 #46 因此从「待裁决」收口为「留 基底」，上限见本节末。

**理由**：

1. **`CS-009` 是单向棘轮**（core + kernel 的 `pub struct` 字段数、`pub enum` 变体数只许降）。
   开放载荷 = 给 `ChatNode` 加一格 `parts`、再加一个 `ContentPart` 枚举——那正是这条棘轮
   要挡的事：数据面靠加字段变宽，而所有形状判据照旧全绿。要过就得改基线，而基线存在的
   全部意义就是不让这件事靠改基线发生。
2. **回放承诺要每个读侧都加一条分支**。`v2-events.wal` 与 `messages.json` 重放必须得到
   同一个转写；新的内容种类意味着转写、统计、压缩、召回、校准、前端折叠**每一处**都要
   认它。漏一处的后果是静默丢内容（`content` 读成空串），没有任何判据看得见。
   `D-091` 那条「payload 无类型 JSON + 只增不改」能成立，前提正是内容始终是**一段文本**；
   换成多种内容种类，它就从纪律退化成一句没有判据的口号。
3. **`Domain` 已是声明的扩展位**（`D-244`：能力包只声明事实名与格位、不得新增实体，
   `Domain` 是唯一的领域扩展位；`notes` 是已落地的样本）。图像 / 音频的身份是**一个可
   寻址的产物**——有 id、有生命周期、有可见域——不是一段带类型的文本。产物形态今天
   已经全有（VDFS 的存取 / 引用 / 可见域），缺的从来不是「装不装得下」。
4. **引用形态今天就能跑通**：`![alt](vdfs://…)` 在 `ChatNode.content` 里是一段普通文本，
   模型读得到替代文本与路径，provider 插件在组请求时把引用换成供应商的 image / audio
   part。这与 `D-252`（端口只交词干，扩展面不说容器词）同向：能力包不该替宿主决定
   容器形状。

**上限——不开放时多模态最多能做到哪一层**：

| 能做到 | 做不到 |
|---|---|
| 多模态产物的存取、引用、可见域与生命周期（VDFS 已有） | 转写的**原生读侧**：统计 / 压缩 / 召回 / 校准看到的仍是一段文本（引用 + alt），不是像素或音频本身 |
| provider 侧的发送与接收转换（provider 本来就是插件） | 前端按 `ChatNode` 的类型判据渲染专用控件——只能解析 markdown 链接 |
| 转写里出现「这里有一张图」的**可寻址引用**与替代文本 | 模型**返回**的多模态内容进 `ChatNode`——只能作为产物落 VDFS 再由引用指向 |
| 跨会话召回的「记得那次发过什么」 | 召回的语义维（内容重叠分）对多模态内容退化到 alt 文本 |

**被否**：

- 给 `ChatNode` 加 `parts` / 加 `ContentPart` 枚举——见理由 1、2。
- 在 `Event.payload` 里塞 base64：事实形状承载二进制 ⇒ WAL 体积与回放成本失控，且
  「写了就是有了」的假承诺进事实形状（与 `D-110` 同一条反面）。
- 新增 `Entity::Media`：`D-244` 明确 `Domain` 是唯一扩展位，新增实体是**语义决定**；
  多模态不是核心语义。
- 只在 provider 侧做、转写里什么都不留：回放出来的对话缺一条，用户看不到自己发过
  什么——省下那一格形状，换来的是一份不完整的转写。

### D-335 Turn 不作为可见节点：用户消息节点即轮，骨架只补字段、不参与发布身份

**裁决**：实时面里**没有独立的 turn 组合节点**。`rebuild` 折出的 Turn 骨架
（`msg_type = skeleton`、id 取事实载荷的 `turn_id`）只承担 `meta.context` 等字段补全，
**不参与发布身份**：它的 id 就是发起这一轮的用户消息事实 id，`Transcript::apply` 按 id
合并帧时并入用户节点——不新建节点，也不为它派生 `turn:<id>` 这类新身份。

**理由**：

1. 「轮」不是一条消息，而是用户消息节点上的一个生命周期读数：运行态（`working` / 终态）
   已由**会话节点**承担（`emit_session_state` 投 `<sid>` 的变更帧，`data` = 全量会话视图），
   前端据此显示停止按钮与结局角标。再造一个 turn 可见节点 = 同一事实的第二份呈现身份。
2. 同 id 合并是既有纪律：`rebuild` 内部「同 id 只认首次」、`Transcript::apply` 以 id 为键
   合并帧。为骨架派生新 id 会让「这一轮」与「这条用户消息」在实时面上分家，分支切换 /
   截断 / 压缩按轮定位时就要多认一套身份（与 `D-025` 同一条：顺序是节点属性，身份也只该
   有一套）。
3. 判据落在**真实存在的对象**上：`t10` ⑩ 断言「各子节点终态到达序早于会话终态帧」，
   不再断言「必须有 turn 节点」——后者与「展示上不需要轮次」的既定口径冲突，且它守的
   正是本条否决的形态。

**被否**：

- 给 Turn 骨架派生 `turn:<turn_id>` 独立身份——实时面无可见消费者，只多一套身份。
- 让用户消息节点自己承担运行态状态机——运行态归会话节点；用户消息落点即终态，
  不参与节点状态机（既有协议空洞，不在此钉成不变量）。

### D-426 首响挂轮根：开场白是轮内容，不另立根级兄弟

**背景**：`D-335` 之后轮根 = 用户消息节点，工具卡 / 思考 / 正文都是它的子孙；前端渲染走
`D-423` 的结构轴递归（有子就画子树）。首响（`chat.assistant.opening`）此前折成**根级**节点
（`parent_id = None`，来自「对话面节点与 Turn 兄弟」的旧形状）——时序上它在用户发言与首条
工具结果之间，渲染上却被排到整轮子树之后，看起来像轮末补的一句话；按根切窗口
（`useTranscriptWindow`）也会把它多算一轮。

**裁决**：首响挂**轮根**。事实载荷带 `root_id`（用户消息节点 id，与 `turn.dispatch` /
`response` 同名字段同取值），`rebuild::opening_node` 据此设 `parent_id`；实时投影与重建
走同一个 `rebuild`，两面逐字同形。轮内位置由 `seq` 给出：首响事实先于读者 `request` /
工具事实落格，因此排在轮内第一。它与 `D-425` 的轮占位同父——首响落格即让位（占位换成
真实的第一句话），随后读者请求再起新的占位。

**旧事件容错**：存量首响事实没有 `root_id`，节点 id 形如 `opening:<用户消息 id>`，重建按
前缀回填父 id（与载荷缺 `id` 时合成 id 的同一条容错纪律）。

**判据**：① 首响 `parent_id` = 本轮用户消息节点 id（e2e `t20` C 线 / `t22` B2）；② 轮内
`seq` 顺序为用户 → 首响 → 工具卡 → 终答，实时面与落库面同形；③ 首响不作为根节点进入渲染
窗口计数；④ 存量会话重读后同样挂在用户消息下。

**被否**：为首响新造节点形态 / 事实 / 帧；重引入 Turn 节点（`D-335` 不变）；改
`meta.surface`（数据概念，前端不按它分面板）；动 `exclude_from_context` 的剔除语义。

### D-381 失败轮节点由自己的诞生事实承载

- **现状（按代码）**。会话收束的失败分支（`crates/symbio-plugin-session/src/convergence.rs`
  的 `project_final_turn`）按三个 owner 落：① 落一条 `chat.assistant.fallback` 兜底格，
  `text` 刻意留空（正文不写进兜底格）；② `rebuild` 折出的用户 / 助手 / 工具节点走
  `Carrier::Runner`（它们各自由运行器的事实承载）；③ 失败节点
  `id = "failed:<failed.event_id>"`（`msg_type = body`、`status = failed`、`error = detail`）
  **单独一批**走 `Carrier::Here`，落 `message.added`——它没有别的格可搭车（兜底格 `text`
  为空），必须靠自己的诞生事实进读面。`Carrier::Runner` 在
  `crates/symbio-plugin-session/src/chat_session/write.rs` 的 `Born { carrier: Runner, .. }`
  分支里**不落任何事实**；`Carrier` 自己的文档写明了后果：「该 `Here` 写成 `Runner` ⇒
  节点在事实源里没有出生记录，切主读后整条消失，是数据丢失」。
- **为什么必须是自己的诞生事实**。读面（`vdfs/read(<根>/session/<sid>` 与 `<sid>/message`，前端
  加载历史走同一条地址）是 `load_session`（**WAL 重建优先**）+ `overlay_live`：
  `rebuild` 从 WAL 折不出走 `Runner` 的节点；`overlay_live`
  （`crates/symbio-plugin-session/src/plugin/nodes.rs`）又刻意丢掉「带权威 `seq`、却不在
  落库列表里」的副本（换基防复活）。若失败节点走 `Runner`：实时帧里在
  （`transcript_apply` 当轮下发），**任何读都看不见**（含换进程重开）。
  两端分叉是静默的——CI 里只有把它当判据的用例会红。
  同一处还有第二个后果，按本条一并收口：`rebuild` 给兜底格折出的骨架节点 id 取
  `root_id`，而 [D-335] 之后 `root_id` **就是**用户消息事实 id；骨架与用户节点同 id，
  被「同 id 只认首次」并掉。若只并 id 不移交状态，骨架上的 `error`（失败原因）随之丢失。
  本条要求并 id 时**一并移交** `status` / `error` 到用户节点；
  `crates/symbio-sdk/src/projection/rebuild.test.rs` 的
  `fallback_carries_the_failure_reason_onto_the_turn_node` 用生产形状
  （`root_id` = 用户消息事实 id）断言这一点。
  会话节点仍是失败读数的第二道出口：`status = failed`、`outcome = failed`、
  `error = detail`（场景属性在线上 flatten 到节点顶层；前端错误条与它同源），即
  `crates/symbio-plugin-session/src/docs/105-node-state-streaming.md` §7「错误条」一行的兜底；
  模型级失败现在有自己的节点，不再只靠这条兜底。
- **裁决**。
  ① 失败节点必须由**它自己的诞生事实**承载：这一条走 `Carrier::Here`（`message.added`，
  载荷自带完整节点，`message_events::added` 的幂等键取首条节点 id）。它正是该格文档说的
  「没有别的格可搭车的界面文本」，与压缩记录同类。
  ② **拆成两次追加**，不能把整批翻成 `Here`：同一批里还有 `rebuild` 折出的用户 / 助手 /
  工具节点，它们的承载事实已经由运行器落，再补 `message.added` 就是第二个 owner。做法是
  `Carrier::Runner` 追加重建节点，失败节点单独一批用 `Carrier::Here`。
  ③ 兜底格载荷**不动**：`text` 仍为空，不把正文写进兜底格——`rebuild` 的「空正文不长出
  正文节点」判据（`fallback_carries_the_failure_reason_onto_the_turn_node`）与它同一口径。
  ④ **不改 `Carrier` 的两态语义**：重建节点仍归 `Runner`，失败节点归 `Here`；
  两条追加分属两个 owner，不把整批翻成 `Here`。
- **谁写谁读**。写：`convergence::project_final_turn` 的失败分支（唯一写点）。读：
  `rebuild::added_nodes`（`message.added` → 节点，逐条收下）与 `overlay_live`（按 id 命中
  落库列表，不再走「带权威号就丢」的分支）；`prompt_fidelity` 不认领它（它不是模型产出，
  不在 `responses` 里）。
- **代价**。每失败轮多一条 `message.added` 事实（已有事件名，不新增机制键）；失败轮多一次
  追加（两次 `append_and_publish`）；重入时多一次 `Duplicate` 判断（键 = 节点 id）。
  换来的是两个地址同一份内容，以及失败原因不再依赖「实时帧恰好没丢」。
- **判据**。失败轮结束后，`vdfs/read(<根>/session/<sid>/message)` 与 `<sid>` 叶子都出现
  一条 `status = failed`、`error = detail` 的 `body` 节点，id 与实时面同一条；
  **换进程重读仍在**。`fallback_carries_the_failure_reason_onto_the_turn_node` 的夹具是
  生产形状（`root_id` = 用户消息事实 id），断言失败节点在新 id 上带 `error`；
  `turn-root-audit` 的 F1 测试面随夹具收窄到 182（实测相等）。`t47` 的失败轮判据另读
  会话节点（`vdfs/stat` 的 `status = failed` 与 `error`），与失败节点同源。
- **不做什么**。不改 `Carrier` 的两态语义；不把正文写进兜底格；不给失败节点派生第二套身份；
  不动环——这条属会话收束的落格面，不是环的派发面。

### D-382 同一轮多次提问：工具卡按 `tool.requested.calls[]` 逐一出生，不再按助手往返出生

- **现状（按代码）**。消息面的工具卡今天只有两个出生点：
  - 实时面：模型流式帧（`crates/symbio-plugin-model/src/stream.rs` 的 `ToolCall` 分支）
    为每个 `tool_calls[]` 发一张 `Skeleton + tag tool` 节点，`id = tc_id`（节点身份）、
    `tool_call_id = wire_id`；
  - 重建面：`crates/symbio-sdk/src/projection/rebuild.rs::artifact_nodes` 按产物格出卡，
    卡的身份经 `node_of_call` 从助手 `tool_calls[]` 反查；`output_nodes` 只出正文 / 思考。

  两次提问都在 `tool.requested` 里留了真事实（`calls[] = {id, node_id, name, arguments}`，
  `artifact.added{tool_call_id, needs_user_action}` 与 `user_prompt` 也都在），但**第二次提问
  没有对应的助手往返**：它是同一次工具执行在恢复后再次发问，模型侧没有第二段 `tool_calls[]`。
  于是第二张卡从未出生；`artifact_nodes` 按 `node_of_call` 反查不到 `call_ask_2 → node_id`，
  退回用 wire id 当父节点，结果挂在轮节点下——读面成了「一张卡 + 一个没有来处的提问」。

- **为什么现有形状不够**。「卡的存在」被绑在助手往返上，而「调用存在」的唯一事实是
  `tool.requested`。这与 D-381 是同一类：**中途 / 收尾事实不能只活在某次合成里**。
  只要还存在「没有助手往返的调用」（恢复后再次提问、无模型往返的唤醒路径），按往返出卡
  就必然漏卡；而结果侧已经按 wire id 找父卡，两边不是同一个来源。

- **裁决**。
  ① **卡的存在只由 `tool.requested.calls[]` 决定**：同一 `request_id`（今天载荷里叫
     `root_id`）下，每个 `call.id` 恰好一张卡；卡节点 id 取该条 `calls[]` 的 `node_id`
     （缺则同 wire id）。助手往返的 `tool_calls[]` 只供这张卡的**增量内容**
     （名称 / 参数 / 流式片段），不再决定卡是否存在——两套来源就此合一。
  ② **只有一份投影**：实时与重建都按①出卡；`node_id` 重复时只认首次（沿用「同 id 只认首次」）。
     同一 `request_id` 下按 `call_id` 排序，不按到达时刻排——到达时刻会把恢复路径的卡甩到末尾。
     不新开第二套读法，也不靠 `overlay_live` 的「复活旧副本」补卡（那是双读法的代价）。
  ③ **配对照旧按 wire id**：`artifact_nodes` 的 `node_of_call` 改为合并两个来源
     （`calls[].id → node_id` 与助手 `tool_calls[].wire_id → node_id`），结果 / `user.answer` /
     授权事实仍按 wire id 配对。**债行的批债 / 逐笔债配对一律不碰**——刚立住的形状不在这条里回卷。
  ④ **恢复锚点落到多卡形状上**：卡上继续带 `tool_call_id`（wire id）；恢复入口按 wire id
     找到**那一张**卡，而不是「这一轮唯一那张」。第二次提问与第一次同形。

- **谁写谁读**。写：`tool.requested` 的唯一写方（环 / 工具端口的派发点，事实今天已有），
  不新增事实种类、不新增字段（`calls[].node_id` 已在载荷里）。读：`rebuild` 的两处索引——
  `group_of_call` 只认 `tool.requested`（存在性）、`node_of_call` 以 `calls[].node_id` 为主来源
  并按 `call_id` 排序（身份）；`plugin/nodes.rs` 的实时面卡身份改由同一份调用清单给。
  **物化点仍在产物格**（`artifact_nodes`）：卡与结果同格出生，才能保住「中途思考排在它那一轮
  卡之前」的既有形状；产物格只推进同一张卡的状态（`carries_state`），不再提供存在性。
  因此**不新增 `nodes_of` 臂**——那是第二套读法（②）。前端不改合并键（仍按节点 id 合并）。

- **代价**。重建面卡的存在性从助手往返改由派发清单裁定，身份多一条 `calls[].node_id` 来源；
  实时面的卡身份从流帧改读调用清单，骨架帧要能与清单对齐（同 `node_id` 时只补内容）。换来的是：
  一张卡一个出生事实、恢复锚点唯一、读面不再出现无父结果。
  本条**不改**：`ToolBehavior`、`Carrier`、债行配对、`session.config` 的工具面。

- **实施那一笔的判据**。同轮两次 `user_prompt` 跑完后：消息面恰好两张 `tool_call` 卡，
  `tool_call_id` 分别为 `call_ask_1` / `call_ask_2`；两张结果分别挂在对应卡下；换进程重读
  同形；两卡顺序与 `call_id` 排序一致。反向：同一 `request_id` 下不得出现第三张卡，也不得
  出现父节点为轮节点的 `user_prompt` 结果；恢复入口按 `call_ask_2` 能取到卡与答案。

- **不做什么**。不改债行配对；不做第二套读法（不靠 `overlay_live` 补卡）；不给卡派生第二套
  身份；不把「同一请求内多卡」推广成「跨请求共享卡」。

### D-401 压缩摘要只装「装得下的最旧前缀」：预算切片 + `keep_from` 换基

- **现状（按代码）**。`crates/symbio-plugin-model/src/assist.rs::transcript_nodes` 给摘要
  请求拼的是**整份**用户发言 / 助手终答；`compact` 只在 `model` 收束载荷越过
  `0.7 × limit` 时才欠这一笔（`crates/symbio-plugin-compact/src/debt.rs`）。于是转写
  越接近窗口上限，摘要请求越先撞同一个上限——在唯一需要它的时刻必失败。这不是缺重试，
  是请求本身装不下。

- **裁决**。
  ① **摘要输入按预算切片**：`compact` 在申报债行时从最旧的事实取一段对话线，累计到
     `k × limit`（`k = 0.5`：另一半留给 system 指令、协议信封与摘要输出；多数 provider
     把输出也算进同一窗口）。system 指令与每条消息的协议开销在预算里先扣，执行体据此
     装请求——摘要请求的输入因此不超过 `k × limit`。
  ② **只压这一段，产物写回该段位置**：`session.consolidated` 载荷增加
     `keep_from`（首条未压事实 id）。三个读面（`rebuild` / `transcript` /
     `prompt_fidelity`）从该事实的下标起接着折，后缀原样保留；`keep_from` 缺席
     （整份压掉 / 旧快照）⇒ 回落「快照下标 + 1」，与旧行为逐字一致。
  ③ **超长单条必须能再切**：按消息边界停（下一条装不下就留给后缀）；只有「最旧一条自己
     就超过预算」才头尾截断（头 3/5、尾 2/5，按字符截——估算器里 1 字符 ≤ 1 token，
     是硬上限），并在快照载荷记 `split: true`、节点 `meta.split` 留一份给展示面。
  ④ **端点不可读 ⇒ 响亮失败**：执行体找不到 `from` / `to` 在事实读面的位置时，这一笔
     `NonRetryable` 失败，**不得**退回整份转写（那正是原始故障）。

- **为什么不是「再试一次」**。重试解决的是瞬时失败；这里的失败是确定性的：同一份转写、
  同一个窗口，第二次仍然装不下。把输入钉在窗口的一半，才让压缩从「请求装不下」变成
  「产物装得下」。

- **代价**。摘要不再看见最近几轮；完整上下文只留在请求包的后缀里（那是模型真正需要的），
  摘要节点本身是界面折叠叶（`style_tag = compression`，不进请求包）。截断段的信息有损，
  由 `split` 显式留痕。**不改**：阈值 `0.7`、两行债的形状、端口分工（D-336）。

- **判据**。small-window 端到端：一份远大于 `k × limit` 的转写，每个摘要请求的输入 token
  ≤ `k × limit`；连续两轮压缩后主请求水位真实下降。反向：切片端点缺失时不得出现摘要
  请求；`keep_from` 缺席的旧快照读法与改造前逐字相同。

- **不做什么**。不改 `model.assist` 的角色投影；不把摘要正文塞进端口载荷（正文仍从事实读）；
  不在读侧做「缺卡补卡」式的兜底。

### D-402 压缩失败留痕与跨轮抑制：失败是产物，抑制按前缀指纹

- **现状（按代码）**。`crates/symbio-plugin-compact/src/port.rs::CompactExecutor` 拿不到可信
  摘要时返回成功、不落事实 ⇒ 压缩节点恒 `Completed`；`RetryCompaction` 只在
  `is_compression() && failed` 时派生（`symbio-sdk/src/chat/chat_node.rs`），因此永不出现，
  会话侧的 `retry_compaction` 也只是 `NotImplemented`。两行债的 id 按 `user_id` 派生、每轮
  都变：同一份前缀每轮重新欠一次注定失败的往返。`PortErrorClass` 只有三档，没有
  「这一类以后别再欠」的表达位。

- **裁决**。
  ① **失败必须落事实**：`compact-write` 拿不到摘要 ⇒ `PortOutcome::failed`（本行只读事实，
     重跑不会改变结论，故类为 `NonRetryable`；上游的类记进 `failure_class`），载荷带
     `failure_class`（原因分类：`non_retryable_context_length` / `non_retryable_provider` /
     `retryable_provider` / `needs_human` / `non_retryable_empty_summary`）、`detail`、
     `compression_id` 与切片边界（`from` / `to` / `truncate` / `keep_from` / `split`）。
     该债行加 `failure_card(FailureProjection::Compression)`，读面把它折成 `status = Failed`
     的压缩节点（`style_tag = compression`，`meta.failure_kind` = 原因分类）；
     `RetryCompaction` 由该节点形状派生。
  ② **跨轮失败记忆 = 环的收束事实，按前缀指纹寻址**：两行债的 id 从 `user_id` 改为
     **前缀指纹**（最旧未压事实 id + provider 上限 + **代** = **上一轮及更早**的成功压缩
     事实 id），失败与成功都落在同一把键上；成功换代、失败不换代。**本轮的压缩不算代**：
     否则成功一落成，同一轮立即换一把新键、把同一段重压一遍（`unless_id` 也钉不住）。
     债源读 `closing("compact-write:<指纹>")`，已收束（Ok / Failed）就不再欠。能力包不持有
     运行期状态。
  ③ **重试 = 删掉失败产物 + 换一把指纹**：`retry_compaction` 落一条 `message.removed`
     （目标 = 失败压缩节点 id）。读面因此丢弃失败节点；债源看到「该节点的最新一次移除」就把
     指纹换成带重试纪元的键（`<指纹>|retry:<移除事实 id>`），不欠水位也重跑同一段切片。
     再次失败 ⇒ 新收束键照样抑制；再点一次 ⇒ 新纪元。失败节点的**身份也按指纹派生**
     （`compression:<指纹>`）：读面把 `message.removed` 当作永久隐藏，若重试沿用旧身份，
     重建出的节点永远不可见——换纪元即换身份，新一代产物才可读、可再重试。
  ④ **永久失败格不进 `PortErrorClass`**：三档是「这一笔能不能重试」的通用结论；「这一类
     以后别再欠」是能力包的策略，落在失败事实的 `failure_class` 上，由 `compact` 的债源读它。
     机制面不涨。

- **为什么这样裁**。失败记忆必须同时被读面与债源看到；环的收束事实天然两处都读，另存一份
  状态会造出第二个事实源。指纹取「最旧未压事实 + 上限」而不是整段正文：整段每轮都变，抑制
  当场失效；前缀不变才意味着同一段在本窗口下已被判过。

- **代价**。同一前缀的持续失败在下一次重试或换模型（上限变化）前不再尝试；水位继续上涨时
  主请求可能先撞窗——这是显式取舍，失败节点与重试入口都在界面上，不是静默。

- **判据**。持久失败 6 轮 ⇒ 摘要请求只发生一次（环内按类重试除外）、无新
  `session.consolidated`；读面恰有一个 `Failed` 压缩节点且 `actions` 含 `retry_compaction`；
  点一次重试 ⇒ 多一次摘要请求且出现**新一代**失败节点（新身份，旧身份被移除事实隐藏）；
  换一个更大上限的 provider ⇒ 指纹变化、自动重跑。移除失败节点后读面不再出现它。

- **不做什么**。不加 `PortErrorClass` 格；不给 `compact` 增加运行期状态；不改阈值与切片
  预算（D-401）；不在 provider 错误文本上假设未登记的特征——超窗按已知特征归类，其余如实
  落到 `*_provider`。

### D-482 终答的节点构造已唯一：两个产出点只写载荷，树由一处折

**问题**（`D-345` 的出口，裁在 [DE-053-环驱动与写口裁决](053-环驱动与写口裁决.md)）。`chat.assistant.final` 有两个产出点，`D-345` 的复查把病根从
「字段不同」定到「两棵不同的树」；`D-435` 裁了形状（答话挂在轮根下的正文子）并让
`dialog` 子对象、`produced_nodes` 专用分支、`mutations::produced_text` 一起退场。本条回答
剩下的两件：**「一个构造器」落在哪**，以及**四个面凭什么同树**。

**裁决一：节点构造只有一处。** 终答的节点树由 `rebuild::produced_nodes` 从事实折出
（身份经 `event_output_text_node_id`、形状经 `llm_build_text_node`）；两个产出点
（`model::port::outcome_payload` / `session::answer::answer_step`）只写载荷，**不建节点**。
所以「两个产出点调同一个构造器」的落地形态是**没有第二个构造器**——不是抽一个共用函数
让两边各调一次（那仍然允许两边各折一棵树）。

**裁决二：载荷拼装仍两处，不合并。** 两份键集不同是**信息差**，不是重复：模型端口知道
`text_id` / `truncated` / `calls[]` / `usage`，答话行知道对话面标记 `meta`。合并要造一个
「谁都不全知道」的构造器（参数表就是两份键的并集），而树形一致由判据钉住，不靠构造器
强制。键集另有两道既有守卫：`FactDecl.fields`（字段声明）与读方（`root_id` 被
`session.close-turn` 的行键要，`text` / `answer` 被对话线回灌要），缺键即红。

**四个面凭什么同树**：

| 面 | 与重建面的关系 | 判据 |
|---|---|---|
| 重建面 | 本体（从事实折节点） | `rebuild.test.rs::the_two_final_writers_fold_into_one_tree` |
| 实时面 | 同一次 `rebuild` 的输出 + 在途缓冲按 id 合并 | `overlay_live` 的既有用例 |
| 按根切窗口 | 重建输出按根闭合截取（父不悬空、轮不被劈开） | `transcript_window_keeps_turns_whole` / `_is_parent_closed` |
| 前端渲染 | 读同一棵树，按 `ChatNode` schema 映射 | `frontend-static` 的类型检查（节点形状不在渲染侧定义） |

后三面都是重建面的**下游**：它们不重新从事实折节点，所以「同一条事实一棵树」只需在源头
钉一次。

**判据**：`the_two_final_writers_fold_into_one_tree`——模型端口形状与答话行形状各折一遍，
`shapes`（id / 父 / 型 / 身份 / 正文 / 状态）逐字段相等；并断言条数与两个父节点，防
「两边都空」的假绿。它钉的是 `D-345` 的病根（拓扑），不是字段。

**重开条件**：①出现第三个写方且它必须**建节点**（而不只是写载荷）；②前端需要一种「只
存在于渲染层」的节点形状——那说明树里少了东西，该补在投影侧而不是渲染侧。
