# 能力注册表与能力坐标系

状态：**已落地**——步骤 4 的施工图整体实施完毕，各处形态见 §5。
回答开工前必须先答的三个问题，并把 DE-014 §4 里两处与现网契约不符的签名修正掉。

范围：`symbio_core` 的收集口（`CapabilityVisitor` / `OptionVisitor` / `ConfigurableVisitor`）+
三个默认收集器（`providers/collectors/`）+ 第二实现方（`SubAgentVisitor`）。**不含** 19 个工具的
`Capability::execute` 实现体。

## §1 判据：每一步 core 三格净下降，session 行数不增

| 判据 | 表达 | 现有棘轮 |
|---|---|---|
| core 形状只降不升 | `pub trait` 18 · `fn` 成员 56 · 默认体 18 | `core-shape-audit.mjs`（CS-001） |
| 收集口收敛 | `CapabilityVisitor` 16 方法 + `OptionVisitor` 2 + `ConfigurableVisitor` 2 ⇒ **1 个 trait，3 个方法** | 本文档 §2 的账 |
| session 不增 | `session` 非测试行数 ≤ 搬入前 | `find` + `wc -l` |
| 行为不变 | 工具清单逐条比对 + schema 导出比对 + e2e 77 条 | 现有 e2e |
| 零新增机制键 | --- | `verify/mechanism_growth` |

**「不新增 trait、就地变形」是关键选择**：如果新写一个 `trait Registry` 再慢慢删旧 trait，
中途 `pub trait` 会从 20 涨到 21，CS-001 当场判红。因此正确形态是**把 `CapabilityVisitor`
这个 trait 就地改成 3 个方法**——trait 数不变（变换过程中恒为 20），方法数每一步严格下降。
trait 改名（`CapabilityVisitor` → `Registry`）是最后一步的纯重命名。

## §2 六个族，一张表

`Registry` 三方法的表达力来自**族是载荷变体**：加一个族 = 加一个变体，不是加三个方法。
十六方法要解决的问题不是「一个方法参数太多」，而是**六个族各写了一整套三方法**——同一件事
（把登记项交给引擎）被说了六遍。

| 族（`CapabilityRowKind`） | 载荷 | 行名 | 谁读 |
|---|---|---|---|
| `Tool` | `Arc<dyn Capability>` | `meta.name` | 工具循环；子 Agent 作用域投影 |
| `Model` | `{ provider, active }` | `provider_id` | 会话引擎取生效者；插件选自己的模型 |
| `Prompt` | `{ text }` | 段名 | 会话装配系统提示词；`compose` 拼提示词 |
| `Mount` | `{ provider, active }` | 目录名（根行固定 `<root>`） | 访问层取 `<根>` 的服务者 |
| `Option` | `{ field, order }` | `field.key` | 前端设置表单；装配期选项快照 |
| `Configurable` | `Box<VdfsItem>` | 目录名 | 可配置目录清单 |

`Policy` **不在表里**（[D-089](014-单环一表.md "DE-014-单环一表")）：策略的判据依赖 `loop` 私有的
`LoopState`，它接不上这张「在共享地址上被 ≥2 个消费方看见」的表，本就不该有变体。

收集器有**两个实现方**，这是迁移的真正成本所在：

- `providers/collectors/tool_visitor.rs:69` `DefaultToolVisitor`——生产主路；
- `plugins/agent/host/scope.rs:116` `SubAgentVisitor`——子智能体作用域投影，
 它必须与被投影者**同时**改，否则子智能体的工具集会静默退回空表。

`ConfigurableVisitor`（`capability/configurable.rs:63`）与另外两个 visitor 同源（插件配置树的
收集口），并入同一 trait 的动作一并记账，不另立批次。实测它是 **2 个方法**
（`register_configurable` · `list_configurables`）， 原记的「3」多数了一个自由函数。

## §3 表的目标形状

```rust
enum RowKind { Policy, Tool, Model, Prompt, Mount, Option }

struct Row {
 name: String,
 prio: u32,
 kind: RowKind,
 schema: RowSchema, // Tool ⇒ CapabilityMeta；Option ⇒ DetailField；其余按需
 run: Run,
 effects: RowEffects, // risk / approval / retention（Tool 已有）+ 预算档（Policy）
}

enum Run {
 /// 纯决策：策略行。签名收 `&State`——它结构上碰不到 ctx（见 §4 Q1）。
 Policy(fn(&State) -> Option<Step>),
 /// 有副作用执行：能力行。见 §4 Q2。
 Cap(Arc<dyn Capability>),
}
```

trait 只剩三个方法：

```rust
trait Registry {
 fn put(&self, row: Row) -> Result<, RowConflict>;
 fn get(&self, name: &str) -> Option<Row>;
 fn list(&self, kind: RowKind) -> Vec<Row>; // 按 (prio, name) 升序
}
```

`session/loop_registry.rs` 是这张表的**第一任实现**——它现在就长这样，
只是 `RowKind` 与 `Run` 的 `Cap` 变体还没落地。**策略目录的行多一个 `site` 字段**
（决策点闭集，[D-093](014-单环一表.md "DE-014-单环一表")）：能力行不按决策点分，
所以那个字段不属于共享形状，是策略目录特有的第六列。**这张表从 session 出发，最终搬进 core**：
策略行是 `session` 的私有知识，能力行是全插件共用的协议，两者必须同表才能说
「一个能力一个入口」。搬的动作属步骤 6（切插件），不在步骤 4 内。

## §4 三问的裁决（含对 DE-014 §4 的修正）

### Q1 `ctx` 信封与 §3 硬规则 a「只携带引用」

**裁决：`ctx` 不进表。** 它是**执行期环境**，不是**注册数据**。

```rust
// 执行侧持有 ctx，注册行只持能力与判据
let row = registry.get(name)?;
row.run.invoke(args, &env, ctx).await // ctx 由调用方给，不由行携带
```

`Policy` 与 `Cap` 是 `Run` 的两个变体，**策略行在类型上就拿不到 ctx**——不是靠纪律，
是签名。这也让 `Arc<dyn PluginInvokeRequest>` 保持"在每个需要它的调用点显式传入"，
与现网逐字一致。

### Q2 工具结果 → `Vec<Fact>`：**修正 DE-014 §4 的 `Exec` 签名**

DE-014 §4 写的是 `Fn(Capsule, &Store) -> BoxFuture<Result<Vec<Fact>, ExecError>>`。
**不按这个签名实现**，三条理由：

1. **现网 `Capability::execute(args, &ExecEnv, ctx) -> Result<Value, PluginError>` 已经是
 `Run` 的 `Cap` 变体的完整形态**。19 个工具无一需要 `&Store`；让它们都拿到一个 store 句柄，
 是在为一个假设给所有人加参数。
2. **「谁落格」现在有唯一答案**：调用方（`turn_exec` 收束时写）。改成执行体自己产 Fact，
 等于同时改 19 个实现的职责与网格的写方纪律——那是另一个批次，不是搬迁。
3. **`Vec<Fact>` 需要 `ExecError` 与事实网格的类型打通**，那是 core 的形状变更，
 必须走 CS-002 并有决策。迁移批次里夹带它，会把 300 行熔断线直接顶穿。

因此：**`Run` 只有 `Policy` 与 `Cap(Arc<dyn Capability>)` 两个变体**。`Exec` 签名在
**第一个真正需要 Store 的能力族**出现时再引入，届时它的 `&Store` 是 per-session 的
`EventWalStore`（与 `turn_exec` 持有的同一个），不会是全局 store。

> DE-014 §4 的 `Exec` 段与 §5 步骤 4 与此处口径一致。

### Q3 `&Store` 是哪个 Store：**推迟，且推迟本身就是答案**

所有签名零 `Store`。若将来某族需要，判据是：**只可能是 per-session WAL**，因为
跨会话的写入口子一旦打开，double-write 就会从"两处记账"变成"两个真源"。
把它做成显式参数（而不是全局单例）也是同一条理由：参数拦得住调用方，全局拦不住。

## §5 落地形态

- **行词汇** `capability/row.rs`：`CapabilityRowKind`（六值）+ `CapabilityRowPayload` +
 `CapabilityRow`（**两个字段**：名字 + 载荷；族别从载荷派生，结构上不存在两种答案）。
 改一个族 = 加一个变体，`list(kind)` 的签名不再变形——十六方法糜烂的来路正在于「每加一族都要动签名」。
- **meta 不另存一份**：`row.meta` 每次从能力自述现取。两份表示只会在改名装饰器
 （`PrefixedCapability`）上分叉，而那种装饰器改的正是 `meta.name` 本身。
- **`invoke` 不在表上**：按名执行 = `get(name)` + `capability_invoke`，NotFound 文案
 逐字保持。`put` 内裹审批闸（纪律原样）。
- **顺序 = 注册序**：`list(kind)` 按族过滤后即表序（IndexMap），族内不按名重排
 （[D-057](../../symbio/src/plugins/session/README.md "symbio/src/plugins/session/README")）。策略行的 `(prio, name)` 先命中者胜在 session 的
 `loop_registry`，两件事。
- **生效位长在行上**：`Model` / `Mount` 带 `active` 位——「生效者必然是目录里的一员」这条
 不变量由**结构**承载，不再是批量注册的签名。`put` 收到带生效位的行时，先把同族旧生效行
 降位：降位是**换一个 `Arc` 副本入表**（`CapabilityRow::demote`），不是就地改位，否则读者会
 读到「两个生效者」的中间态。旧行**留在表里**（降为普通目录行）：`active` 只答「谁在槽里」，
 「目录里有谁」是同一批行的另一问。
- **根行的行名由构造函数填**：根不是某个插件的目录，不可能由调用方命名，故填保留值
 `"<root>"`，读侧按 `active` 找。一族两形由此各被一处守住——「根不可按名查」与
 「根不在挂载点清单里」是同一个过滤的正反两面。
- **提示词行 = 一段文字**：段名的两条语义写在 `capability/prompt.rs` 模块文档——**注册在这里的
 一定会送达模型**（没有「取一个」的竞争）、**段名是覆盖键不是分类**；空段由拼接方跳过。
- **选项行带 `order` 但不下发**：读侧 `capability_option_fields` 稳定排序后即丢——排序答案与字段
 是同一行的两个事实。
- **作用域规则只在 `put` 一处**：`SubAgentVisitor::put` 按族判——工具 / 提示词 / 选项加
 `agent/<id>/` 前缀，模型族丢弃子 Agent 的注册，子树根行丢弃（否则劫持整个 `<根>`，
 判据 = `scope.test.rs` 单测 + e2e t39）。写入口只有一个，作用域规则也就只有一处。
- **读侧是自由函数，不回头往 trait 挂方法**：`capability_model_active` / `capability_model_resolve`
 （严格查 id，取不到落回生效者——降级方向只有一处定义）、`capability_prompts`、
 `capability_vdfs_root` / `capability_mounts` / `capability_mount`、`capability_option_fields`。
 `capability_mounts` 是**预留的 LLM 可见资源裁剪入口**，当前读侧只有单测——不是死代码，
 判据写在 `mount.rs` 模块文档。
- **同族重注册 = 表语义（同名覆盖）**，不再整体替换目录；跨族同名（表键是全表唯一的名字空间）
 **留一条告警再覆盖**——静默被顶掉的那一族不会以任何别的方式表现出来。告警上岗即顶掉三处
 真碰撞（提示词段名与插件名撞键 memory / setting / model），改的是段名：`agent-memory` /
 `agent-setting` / `model-persona`。
- **收集口名 vs 通道名**：`CAPABILITY_VISITOR` / `OPTION_VISITOR` / `CONFIGURABLE_VISITOR`
 三个键与键类型 `…VisitorKey` 保留——它们命名的是**广播通道**（与 `TRAVERSE_AVAILABLE_*`
 端点成对），不是收集口 trait；实现名 `DefaultToolVisitor` 同此理由保留（住 collectors 层）。
- **core 三格 18/56/18**，`SHAPE_BASELINE` 与之相等。
- **守门人**：同一份清单以两种口径导出逐条相等（走表的 `list(Tool)` 与 `CapabilityMeta` 全量
 转储，含顺序），加顺序 / 覆盖 / 缺失 / 单槽移交 / 族内排序五格；e2e 全绿。

## §6 session 不增的纪律

步骤 4 会让 `session` 变**小**的可能性来自 （`v2_` 前缀退役）与 （工具名
元数据化）先落地。两条硬规矩：

1. **新机制进 `loop_registry`**（它是 `loop` 插件的种子），不进 `chat_loop`。
2. **`chat_loop` 问表**：把 `if let Some(x) = ...` 换成 `registry.get(name)`，净行数为负或零；
 出现净增长时，说明混进了别的东西。

## §8 风险与不动清单

- **`SubAgentVisitor` 是第二个实现方**，漏改它 = 子智能体工具集静默退空。判据：
 e2e（含子智能体场景）全绿，不能只靠单测。
- **`invoke` 是热路径**：`registry.get(name)` 比 `DashMap` 直读多一次匹配。
 判据是 `verify/latency_gate` 不红；若红，`get` 用 `DashMap<name, Row>` 加只读快照，
 `list(kind)` 走排序后的 `Vec`，两者同一份事实的两个视图。
- **不动**：`Capability::execute` 的签名、`PluginError`、`ExecEnv`、审批闸门的
 `risk_for` 取值口径（动的是它的**来源**，不是它的值）。
- **不动**：`traverse` 的广播协议本身。改的是广播的**接收端**（visitor → registry），
 广播方（插件）的调用形态一行不改。

## §9 出口条件

1. `symbio_core` 只剩 1 个收集口 trait，3 个方法；`pub trait` ≤ 18，`fn` 成员 ≤ 56。**已达成**（实测 18/56/18）。
2. `providers/collectors/` 三个 visitor 收敛为一个 registry 实现；
 `SubAgentVisitor` 是同一张表的作用域投影。**已达成**。
3. 工具清单两种口径逐条相等，e2e 全过，core 三格棘轮不升。**已达成**。
4. `session/loop_registry.rs` 长成策略 + 能力同表，行数不含工具实现体。
 ——本条属 DE-014 步骤 5/6 的账面，不是步骤 4 的收口前置。

> **回答一个问题：能力能长到哪去，以及怎么判断"这算不算高阶"。**
> 清单是开放集，永远列不完；坐标系是封闭的，可以吸收清单的开放性。
> 这正是"架构必须收敛"的理由：**用坐标系的封闭性，去吸收能力清单的开放性。**

## 2. 横向：五维（分类的完备性）

任何能力都落入且只落入这五维之一。**判据是四个追问，无遗漏也不重叠**：

> 我**知道**什么？我**能做**什么？我如何**说**？我做得**对不对**？我**想要**什么？

| 维度 | 回答 | 内涵 | 条数 |
|---|---|---|:-:|
| **知** Episteme | 我知道什么 | 事实、记忆、时间、因果、世界模型、检索 | 10 |
| **行** Action | 我能做什么 | 工具、执行、副作用、具身、承诺 | 13 |
| **言** Utterance | 我如何表达 | 对话、人格、时延、节奏、主动性、多模态 | 8 |
| **省** Reflection | 我做得如何 | 规划、自我模型、校准、评估、审计、信任 | 16 |
| **欲** Conation | 我**想要**什么 | 动机、目标生成、好奇、价值偏好 | 7 |

**「条数」这一列由 §6.1 的名册算出**——程序逐维核对，名册加一行而这里没同步就红。

### 2.1 为什么必须有「欲」

前四维都是**功能性**的（"能做什么"）。缺了「欲」，系统永远只是**高级工具**——有能力，没有能动性。

- 「省」回答"我做得**对不对**"
- 「欲」回答"我**想不想**做、**为什么**要做"

心理学对应：认知 + 情感 + **意志**。缺意志就是缺「欲」。
**缺了这一维，系统再强也不会自己想做事**——它永远在等指令。

### 2.2 组合不是第六维，但组合要记账

**判据**：一个能力若同时属于两维，登记为 `维A × 维B` 的**组合**（§4 第 1 问），不是新维度——
新维度要有自己的判据（四追问之一答不出就落回原五维）与自己的生长位。

**但"组合"是一个逃逸口，必须给它记账**：**同一组合登记到 3 条即触发维评审**。
判据是这个逃逸口被用了几次——五维完备性的主张之所以可被检验，靠的就是
"连续三个新能力都只能落在同一个组合上"这种**可数的事实**，而不是"我觉得够了"。

### 2.3 时延属于「言」的横切属性

分层（反射/快速/深度/自主）回答的是"**我多快能回应**"，这是**表达问题**，不是结构问题。
所以它不是第五维，也不占用架构位置——它是 `actor.budget_ms` 的取值（[DE-001 §10](001-核心架构.md "DE-001-核心架构")）。

> 这也是"双脑"说法的正确归属：快/慢是参数，不是两个脑。

### 2.4 「欲」的最小可执行形态（不是分类，是设计）

> 「欲」最容易停在**分类学**上：把"动机/目标生成/好奇/价值偏好"归成一维，然后说"缺了它不高阶"。
> 但这是**命名**，不是**设计**。真正的问题是架构问题：**"想要"在系统里以什么形式存在？**
>
> 若答"用一个 Motivation 模块 / Drive 原语 / Goal 基类"——立即违反 J1（本架构承诺只有 1 个原语）。
> 所以「欲」**必须落成数据**。

三个可执行子问题（**E1 欲是什么 / E2 欲如何不直接变成行 / E3 欲如何被关停**）、
那张表、不可伪造的 `ApprovedTask` 与三条反向用例的实测输出，**owner 是
[DE-001 §4.2](001-核心架构.md "DE-001-核心架构")** —— 本文不复制（同一张表写两处，改一次要动两处）。
本节在本坐标系里的结论只有一条：**「欲」占 L-grid，不占新机制键**。

**准入判定复核**：4 项「欲」能力（目标自生成 / 内在动机 / 好奇与探索 / 价值偏好）
全部落在**已有机制键的新取值**上（`event.entity=conation`、`projection=conation` 等），
**新增机制键 = 0**。这正是 §4 准入判定第 3 问（J1）的通过条件。

> **「欲」这一维解决的是"欲如何被治理"，不是"欲从哪来"。**
> 后者是价值对齐问题，架构不回答。架构只保证三件事：
> **想要的都留痕（E1）、都必须过闸（E2）、都可关停（E3）。**

## 3. 纵向：五轴（高阶的刻度）

每条轴是一个**连续的量**，不是标签。§3.1 给它四级刻度；§3.2 把天梯定义成
这五条轴的组合，**天梯不再另立一套语义**。

| 轴 | 低阶 | 高阶 | 要求的性质 | 禁止的性质 |
|---|---|---|---|---|
| **主动性** | 只在被要求时行动 | 主动发现问题、发起目标 | `unprompted` | `prompt_only` |
| **时域跨度** | 单轮、当下 | 可规划数周、跨会话坚守目标 | `cross_session` | `turn_local` |
| **抽象层级** | 具体指令 | 理解意图、处理模糊、归纳规则 | `generalize` | `literal_only` |
| **自我模型精度** | 不知道自己不知道 | 精确校准、知道边界 | `calibrate_self` | `silent_confidence` |
| **自主程度** | 每步请示 | 可长时间独立工作，只在关键点请示 | `unsupervised` | `ask_each_step` |

**后两列是判据，不是描述**：两条轴若「要求的性质」与「禁止的性质」**完全相同**，
它们就是同一条轴（必须合并）；若 A 轴要求的性质正是 B 轴禁止的，它们**互相抵消**，
不能各自独立度量。这条判据由 `verify/axis_orthogonality.rs` 按冲突矩阵算出，
不是口头保证（做法与 [DE-001 §1.1](001-核心架构.md "DE-001-核心架构") 的职责冲突矩阵同源）。

**"高阶"不能用能力清单衡量，必须用这五轴度量。** 一个能力若不能说明它把哪条轴
抬到了第几级，它就没有让系统变高。

### 3.1 五轴的刻度（四级）

| 轴 | L1 | L2 | L3 | L4 |
|---|---|---|---|---|
| **主动性** | 只在被要求时行动 | 在既定规则内例行触发 | 主动发现问题并提出，未经指派 | 自主选题，并权衡要不要打扰 |
| **时域跨度** | 单轮内 | 单会话 / 单任务内 | 跨会话可恢复 | 跨周跨月的长期目标与承诺坚守 |
| **抽象层级** | 逐字执行具体指令 | 按意图归纳，识别同义请求 | 抽象出规则并跨任务复用 | 从经验中形成可迁移的原则 |
| **自我模型精度** | 无置信度，不知自己不知 | 有置信度但不据此行动 | 置信度经校准、可度量 | 知道能力边界，据此求助或降级 |
| **自主程度** | 每步请示 | 关键点请示，路径自选 | 长任务独立完成，失败才求助 | 长时间无人值守，行为可审计可回退 |

**L1 是平凡基线**（关闭后系统仍完整运行，J2），不必由名册行代表；
**L4 必须有人**——顶格无人占据的刻度是装饰，`capability_frame.rs` 逐轴判它非空。
L1–L4 的格数由本表的列数算出，程序不写死"四级"。

#### 3.1.1 外部效标：每条轴挂一个可复现的读数

上表的刻度是**观察口径**（"跨会话可恢复""置信度经校准"这类说法在任何系统上都成立，
正因如此它们不构成证据）。要判"某能力把某轴抬到第几级"，得有一个与系统内部实现
无关的量——**外部效标**。每条轴挂一个，读数口是生产读数口
（[`plugins/session/stats.rs`](../../symbio/src/plugins/session/stats.rs) 的某列），
不是为评测临时搭的脚本：

| 轴 | 效标读数 | 出口 | 状态 |
|---|---|---|:-:|
| 时域跨度 | 会话事实源首末事件跨度（可完成任务时长的系统侧下界） | `span` 列 · `fleet.axes.span.median_ms` | 有读数 |
| 主动性 | 自发发起且被采纳率 = 已升格欲 / 已表达欲（被否决、被忽略的算分母） | `conation` 列 · `fleet.axes.conation.adoption_rate` | 有读数 |
| 自主程度 | 无人干预完成率 = 闭环且全程未被 `task.held` 挂起 / 已闭环 | `autonomy` 列 · `fleet.axes.autonomy.unattended_rate` | 有读数 |
| 自我模型精度 | 校准误差（ECE / Brier）+ 说到做到率 | `calibration` 列（口径见 [RE-004](../004-ref/004-slo-calibration.md "RE-004-slo-calibration")） | 有口径 |
| 抽象层级 | 措辞依赖度（同一请求换个说法是否仍找得回）= 原述 recall@k − 换述 recall@k，由 [`verify/recall_eval.rs`](verify/recall_eval.rs) 打印（33 案 × 2 条**冻结**换述，[`verify/fixtures/paraphrases.tsv`](verify/fixtures/paraphrases.tsv "verify/fixtures")）。**它不覆盖三件事**：① 测的是**排序器对措辞的敏感度**，不是「系统会归纳」——读数低只说这套排序不靠字面；② 换述是人写的 ⇒ 只是效标的下界（故带指纹锁，改一个字节即红）；③ 有 6 案属时间兜底类（期望的就是最新那条），任何查询都命中、换述读数在上面恒为 1，所以程序另报「措辞能左右结果」的 27 案子集 | 离线读数（`gate` 的 `verify` 阶段） | **离线读数 + 残余人工判** |

**纪律**（与 [RE-004](../004-ref/004-slo-calibration.md "RE-004-slo-calibration") 同一条规矩）：

1. **读数没出来之前，本表不得改写成"可测量"的口吻**——有读数 ≠ 已达标。上表只说
 "这个数由哪个口产出"，不说"这个数现在是多少"。
2. **设定的数字必须标"设定值"**。跨会话基线（如"时长中位数 ≤ X"）一旦写进任何口径
 文档，必须是实测出来的，不能是拍的；拍的数字只能以"设定值 · 待实测"形态出现。
3. **一条轴一个读数都给不出，就在表里写明"本轴目前只能人工判"**——比编一个数诚实。
 抽象层级此前就处在这个状态（跨域迁移要离线评测，而离线评测不在生产读数口内）。
 2026-10-20 起它有了**离线**读数，
 状态改成"离线读数 + 残余人工判"——**不是"有读数"**：它不在生产读数口内，而且它测的是
 排序器的性质，不是系统的归纳能力。这一格改成什么样，由 [D-097](016-工程落地与验证.md "DE-016-工程落地与验证") 记。

**边界（不假装测到了）**：三条"有读数"的轴测的都是**系统侧下界**，不是人的对照值。
"人需要多久"要 METR 式的人类基线，本仓没有那条数据——所以"时域跨度 = 可完成任务时长"
这句话在本表里只以"系统侧下界"的形态成立，缺的那半边是人工判的部分。
抽象层级同理，且缺口更大一圈：措辞依赖度是**排序器**的读数，而"抽象"是**系统**的性质——
两者之间那一步（排序器不靠字面 ⇒ 系统会归纳）没有任何数据支撑，不能替它说话。

### 3.2 天梯 T1–T8 = 五轴的递进

**T 级不另立语义**：T1–T8 是"截至该级的全部能力集合"，它在五条轴上的等级向量
由名册算出（`capability_frame.rs` 打印）。表里的「核心能力」列必须逐条对应名册里
**该级的行**——写一个不在该级名册里的能力名即红。

| 级 | 名称 | 核心能力 | 工具层级 |
|---|---|---|:-:|
| T1 | 能对话 | 多轮对话、工作记忆（≈4 槽）、流式输出 | L1 |
| T2 | 能干活 | 工具接入（L1）、时延分层（反射→自主）、打断与插话、人格语气一致 | L1–L2 |
| T3 | 能记住 | 情景记忆、语义记忆、时序历史、长期记忆检索 | L2 |
| T4 | 能自省 | 因果结构、权限与配额、自我校验、自我模型、校准（说到做到率） | L2 |
| T5 | 能递归 | 制造工具（L2）、造工具的工具（L3）、抽象协议设计（L4）、对等协商、共同目标与分工 | L3 |
| T6 | 能感知时间 | 未来预测、世界模型、主动开口、节奏与时机、独立验证与返工、价值偏好 | L3 |
| T7 | 能具身 | 具身实时闭环 | L4 |
| T8 | 能学习 | 技能编译、反自动化回退、目标自生成、内在动机、好奇与探索、主动求知 | L4 |

**每级的验收三问**：① 低级场景全部仍工作；② 无新增机制（只有新参数取值）；③ 关闭本级配置可退回上一级。

### 3.2.1 与外部「L0–L5」等级表的关系：不换算

**裁决：不采用任何外部等级表，也不自造换算表。**依据是一次出处核查（2026-10-20），
它找到一个比「没找到出处」更硬的事实——**「L0–L5」在 AI agent 领域不是一张表，是四张
互不兼容的表共用一个记号**：

| 出处 | L3 的定义 | 分级依据 |
|---|---|---|
| SAE J3016（2014/2021，唯一权威原生出处） | —— | 它分的是**驾驶自动化**，不是 AI agent；各家 AI 版 L0–L5 都是**借用其形式** |
| CSA Agentic Trust（2026-01） | 边界内自主决定、边界条件上报 | **谁控制动作执行**（监督/治理） |
| alphaXiv 2405.06643（Yu Huang） | 用 LLM 取代 IL/RL、加记忆与反思 | **底层技术栈**（规则 → IL/RL → LLM → 自主学习 → 个性） |
| 多家综合口径（COMPEL 等） | 多步执行、审结果不审每步 | **人类审批节奏**（模仿 J3016 的 ODD 词汇） |
| DeepMind《Levels of AGI》（2311.02462） | —— | 明确**拒绝**单一维度：能力与自主是**正交两轴**（同表 5×5=25 格） |

两边都写着「L3」、含义却不同——这正是本任务原文预警的「借错了」形态，且实查表明
**借对是不可能的**：没有一个「行业共识的 L0–L5」可供借。DeepMind 的正交性洞察反而
与本仓同构：五轴（时域跨度 / 自主程度 / 主动性 / 自我模型精度 / 抽象层级）就是
「拒绝把系统压成一个数字」的做法，任何一个 L 数字都会丢掉其余四条轴的信息。

**自造换算表的代价**（留在原任务里的话，挪到这里）：它给叙事加装饰——
「本仓在 L3」这句话看起来有出处，而那份出处就是本仓自己；纪律二
（设定的数字必须标"设定值"）对等级表同样成立，而一张每一格都标着
「设定值 · 待实测」的等级表不构成对外沟通件。

**对外沟通的缺口是真的，但解在别处**：天梯 T1–T8 本身就是对外件——它的每一级
逐条对应名册行（§3.2 的硬判据），比「L3」多带一份可复核性。缺的不是另一张表，
是 T 级叙述附带五轴读数（§3.1.1 的口），让读者自己对着任何一张外部表定位。

### 3.3 轴与轴之间：共线的上限与登记

**共线**指两轴被同一批能力抬起，导致它们度量同一件事。五轴不做正交性证明
（做不到），改为**测量 + 登记**：程序统计「一对轴在 8 阶里有几阶同时被抬起」，
超限的轴对必须在本节逐条登记理由；理由说不清 ⇒ 合并或删轴。

**超限上限 = 4**（8 阶的一半）。

| 轴对 | 共同抬起的阶数（算出） | 为什么接受这条共线 |
|---|:-:|---|
| 时域跨度 × 抽象层级 | 5 | 记忆类能力把"跨会话可复用"与"跨会话可用"同时带上来：语义化本身就是抽象，此处共线是同一件事的两面 |
| 抽象层级 × 自我模型精度 | 5 | 归纳与校准共享同一环（用旧结论验新结论），T2–T5 几乎成对出现；二者分离要到能独立校准时才有意义 |

> 这张表是**声明**，数据是名册算出的阶数；两者对不上即红。
> 数字变大意味着这条共线在加深——要么在表里写清理由，要么合并。

## 4. 新增能力的准入判定

```
admit(capability):
 1. 它属于五维中的哪一维？ 答不出 → 登记为 `维A × 维B` 组合（§2.1；同组合满 3 条 ⇒ 维评审）
 2. 它把哪一轴抬到第几级？ 答不出 → 走第 5 问，**不得直接判为"宽度"**
 3. 它能否表达为 §8 参数表的新取值？ 不能 → 走决策流程（[DE-016 §3](016-工程落地与验证.md)）
 4. 它的平凡值是什么？ 没有 → 驳回（J2）
 5. 它高在哪、怎么观察？（第 2 问答不出时的唯一出路） 写不出 → 驳回（伪高阶，§5）
```

第 3 问是 J1 的直接应用，第 4 问是 J2 的直接应用。**两问都过 = 加一行数据，不是改架构。**

**第 5 问是这份判据里唯一带方向的一条**：早先的写法是"答不出提升哪一轴 ⇒ 它是宽度/工程"，
那是**判定的兜底而不是判据**——它让"五轴足以度量高阶"这句话**永远不会错**。
现在轴外的能力必须自己说清"高在哪、怎么观察"，说不清才判伪高阶。
**§3.1 的刻度就是第 5 问的观察口径**：说不出"从 L1 到 L2"的具体变化，就是没有高度。

## 5. 伪高阶识别

> 以下都是**宽度或工程，不是高度**。它们让系统变大，不让它变高。

| 说法 | 为什么是伪高阶 |
|---|---|
| 工具数量多 | 是「行」的宽度 |
| 上下文更长 | 是容量，且 Cowan 2001 证明核心工作记忆只有 4±1 组块，堆长度不如建结构化组块 |
| 反应更快 | 是工程（除非进入了反射层预算，那才是架构） |
| 支持更多模型 | 是配置 |
| 能跑很久 | 是耐力；**跑很久但每步请示 = 低阶** |
| 会写代码 | 是技能 |
| 加了护栏 / 加了仪表盘 | 是工程；护栏只有在改变某条轴的可观察判据（§3.1）时才算抬高 |

上面这张表的「说法」列**就是** `verify/capability_frame.rs` 的伪高阶词表——程序直接吃它，
不另抄一份；判据函数配反向用例（真实能力不得被误判）。

## 6. 覆盖矩阵（实测）

### 6.1 能力名册（全仓唯一一份，`verify/capability_frame.rs` 的输入）

新增能力在这里登记一行，并回答 §4 的追问。**条数、覆盖矩阵、天梯分布全部由这张表算出**
——任何一处对不上就红，不要改那些数字，改名册。

「类型」列区分**这个能力是什么性质的东西**，避免把工程可靠性与认知能力混在同一张表里计数：

| 类型 | 它管什么 |
|---|---|
| **认知** | 模型、记忆、推理、表达本身的能力 |
| **工程** | 可靠性、时延、隔离、容量、管线这类**不抬高智能**但决定系统能不能用的东西 |
| **治理** | 权限、预算、闸门、审计、可解释这类**决定能力可不可被约束**的东西 |

「落点」列把名册接到实施阶梯上：它写这条能力由 [能力扩充阶梯](030-能力阶梯总览.md "DE-030-能力阶梯总览") 的哪一阶点亮
（`SNN`，多阶写 `SNN+SNN`）。**每一阶至少要有一行名册落在它上面**——
否则坐标系与实施阶梯就是两张互不相干的表。

「锚点」列把名册接到**代码**上：取值 `文件` 或 `文件::符号`（反引号形态），
`—` 表示"尚未落地"。已标的锚点必须指得到——`doc-symbol-audit` 的 **D-011** 判
（文件在仓内存在、`::符号` 查 D-005 同一份 Rust 语料，**不另起一份符号解析**），
改一处锚点指向不存在的符号即红。

> **为什么要有这一列**：`capability_frame.rs` 验的是**文档之间**的一致
> （名册 ↔ 矩阵 ↔ 声明），不验文档 == 系统。没有锚点，"坐标系已归位"与
> "这条能力真的存在"在日志里长得一模一样——那是复盘 E6 在坐标系上的残留面。
>
> **锚定率进日志**（`已锚定 / 总行数`）：`—` 本身合法，但"名册在长、锚定率不动"
> 必须看得。填 `—` 只该发生在真的没落地的行上。

### 6.1.1 一能力多居：记忆 / 技能 / 任务的对账口径

名册的一行是**一个能力**，不是一个文件——`verify/capability_frame.rs` 按行计数，
**D-011** 只验「锚点指得到一个实现」。记忆、技能、任务三条能力的腿散在多个模块，
读名册的人会问「这条能力住哪、谁判它」，所以这里给一份逐腿归属口径：
**判据只挂名册那一行的主腿**，其余居处各回答一个不同的问题，不另计一条能力
（计数、覆盖矩阵、天梯分布仍只按 §6.1 的行算）。

| 能力（名册行） | 各居处与它管的那件事 | 主腿 = 名册锚点 |
|---|---|---|
| 记忆（**情景记忆** · **语义记忆** · **长期记忆检索** · **工作记忆**） | `symbio/src/plugins/memory/`（工作区与智能体两腿，各写各的文件 + VDFS 出口）· `symbio/src/plugins/session/memory.rs`（会话 `MEMORY.md`，随会话目录一起删）· `symbio/src/plugins/loop/memory_events.rs`（事件腿：`encode` 与 `memory.recalled` 落格）· `symbio/src/symbio_core/actors/recall.rs`（语义召回的判定）· `symbio/src/symbio_core/projection/recall.rs`（检索读数） | `plugins/loop/memory_events.rs::encode`（情景行）与 `actors/recall.rs::recalled_event`（语义行） |
| 技能（**程序记忆（技能）** · **技能编译**） | `symbio/src/plugins/loop/skill_events.rs`（路由观测落格 `{skill_id, fallback}`）· `symbio/src/symbio_core/actors/skill.rs::SkillCompiler`（把观测编成技能）· `symbio/src/symbio_core/projection/calibration.rs`（回退率读数，出口在 `session/stats` 的校准列） | `plugins/loop/skill_events.rs`（程序记忆行）与 `actors/skill.rs::SkillCompiler`（技能编译行） |
| 任务（**独立验证与返工** · **凸显仲裁** · **成本控制**） | `symbio/src/plugins/loop/task_events.rs`（任务表写方，`task.*` 入格）· `symbio/src/symbio_core/projection/readyset.rs`（就绪视图）· `symbio/src/symbio_core/invariants/mod.rs`（`acyclic_deps` / `rework_bounded` 的判定）· `symbio/src/plugins/session/stats.rs`（就绪列与不变量列的读数口）· `symbio/src/plugins/loop/context/view.rs`（就绪视图进请求装配） | `plugins/loop/task_events.rs`（返工行）与 `projection/readyset.rs::readyset`（凸显仲裁行） |

**为什么不做成名册的第八列**：一列只填一个取值，而这三条能力各有三到五个居处；
把多腿塞进「锚点」列，D-011 就从「这个符号在不在」退化成「这一串里有一个在就行」，
丢掉它要防的那个信号。本表只声明**归属**，不是第二份名册——新增能力仍然只在 §6.1
登记一行，多腿的在这里补一句。

### 6.2 覆盖矩阵与生长位

程序把 §6.1 按（维 × 轴）计数并打印 5×5 矩阵（每格的行数一并打印——密度不均是事实，
只有"有没有"才是格子语义）。矩阵里空格子的**集合**必须与下表逐格对应——
多一格、少一格、名册里填了某个空格却没同步这张表，都让 `verify/capability_frame.rs` 变红。

空格子是**坐标系预留的生长位**，不是缺口——它们告诉你下一步可以往哪长：

| 空格 | 可能的生长方向 |
|---|---|
| 知 × 自我模型精度 | "我知道我哪些记忆不可靠"（记忆的元认知） |
| 知 × 自主程度 | 自主决定是否值得记住 |
| 言 × 自我模型精度 | "我说的话有多可能被误解" |
| 言 × 自主程度 | 自主决定什么时候闭嘴 |
| 欲 × 时域跨度 | 跨会话的长期动机 |
| 欲 × 抽象层级 | 从价值到原则的抽象 |
| 省 × 主动性 | 主动发起自省而不只是被动评估 |

> **这是坐标系相对清单的最大价值**：清单只告诉你"有什么"，坐标系还告诉你"缺什么、缺在哪"。

## 7. 第 6 个坐标：主体数（不是第六维）

前五个坐标描述"**一个**主体能到哪"。多主体不是第六维，而是**同一批能力发生在几个主体之间**
的结构参数——取值 `1`（单体）与 `N`（多主体）。

**为什么不能把它塞进某一维**：格子的含义会随主体数变化（"对等协商"在 N=1 时无意义，
在 N>1 时才有），同一维在两种取值下装的不是同一类东西。坐标系的维度是**分类**，
主体数是**规模**——两者混在一起，矩阵就不再是矩阵。

递归是**树**（主从），对等协作是**图**。以下能力树结构表达不了，必须显式支持
（[DE-001 §12.2](001-核心架构.md "DE-001-核心架构")）：

| 能力 | 提升的轴 |
|---|---|
| 对等协商 | 抽象层级 |
| 跨体承诺 | 时域跨度 |
| 声誉与互信 | 时域跨度 |
| 传递性信任 | 抽象层级 |
| 共同目标与分工 | 自主程度 |
| 冲突与仲裁 | 自主程度 |
| 可撤销的承诺 | 时域跨度 |

> **没有承诺机制，就没有真正的协作——只有并发。**

## 8. 边界：什么是判断，什么现象说明它错了

「已验证」= 有可执行断言，改输入会变红。「判断」= 有依据但未被证明——
**每条判断必须写出它的反证现象**，否则它只是一句修辞。

| 主张 | 性质 | 什么现象出现说明它错了 |
|---|---|---|
| 五维正交且完备 | **判断**（依据是四个追问无遗漏，但无法证明不存在第六维） | 同一个 `维A × 维B` 组合连着登记到 3 条（§2.1）——那时它是一条被组合掩盖的维度 |
| 五轴足以度量"高阶" | **判断** | 出现一个公认高阶、却在五轴上答不出归属的能力，且第 5 问也写不出观察口径 |
| 五轴互相独立 | **判断**（不做证明，改做测量 + 登记） | 某一对轴的共同抬起阶数越过 §3.3 上限而表里没有理由，或理由已不成立 |
| 五轴的刻度可用 | **判断** | 某条轴的 L4 无人占据（顶格是装饰），或 L1–L4 区分不出可观察的差别 |
| 天梯 T1–T8 是"当前能想到的最远" | **判断**，不是"存在的最远" | 出现一个能力，其每条轴的等级都不低于某个 T 级，却无法归入任何一级 |
| §6.1 名册的每一行都归得了位 | **已验证**（程序，含反向用例） | — |
| §6.2 空格子 = 生长位而非缺口 | **判断**（它也可能是我没想到的能力） | 某个生长位被"填满"，却说不出它对应哪条能力 |

**正因能力清单是开放集，架构才必须收敛。** 这是本方案把能力放进坐标系、把扩展放进参数表的全部理由。

### D-059 能力坐标系的科学化：轴要有刻度、天梯不再另立语义、每条判断写明反证现象

`docs/003-design/008-能力注册表与能力坐标系.md` 是一份内部自洽的文档——`verify/capability_frame.rs` 能把名册逐行归位，能把七格生长位对回去。但一次针对它的系统评估暴露出四件它自己没做的事： 天梯 `T` 已经是两套语义，且没有任何程序对账。

### D-068 审批闸门住在能力注册的收口点（`DefaultToolVisitor::register`），判据一份、入口两处

实测现场：`vdfs_delete` 在 `CapabilityMeta.risk` 里声明 `High`，`--mode interactive` 的会话里直接被执行——连一张审批卡都没出。

### D-100 绑定即登记——能力随会话创建而来、与会话同寿，可见域不登记

`local/policy` 的四个默认值保持放开（`autonomy = Full` · `workspace_only = false` · `max_actions_per_hour = 0` · `block_high_risk_commands = false` / `require_approval_for_medium_risk = false`）。
