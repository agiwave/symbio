# 前端机制化

> 把前端从「知道一轮、知道工具、知道压缩」的业务呈现，改成「只认树、只认 kind、只认主体」的机制呈现。
> 上下游：本文是「会话呈现与协议」这一步的具体化，属 [DE-090](090-过渡方案.md "DE-090-过渡方案")
> 所管的过渡范围；协议决策见 [D-069](005-协议规范.md "DE-005-协议规范")
> 与本篇 [D-070](#d-070-nodekind-是唯一前端分派轴style_tag-降级为后端注记)。

## 0. 目标一句话

**协议层**：`ChatMessage` → `ChatNode`；`Turn` 语义退役；顶层字段瘦身到「前端不依赖业务即可消费」的四类
（`kind` / `status` / `principal` / `stats`）+ 内容三件套。
**主体层**：PRINCIPAL 从「agent 一族 + user」扩到 **person / agent / tool / system** 四前缀，工具与用户升为**平级主体**。
**呈现层**：前端只按 `(kind, style_tag, principal)` 分派渲染器；建树策略由后端配置，前端零结构假设。

## 1. 为什么现在做

CLI 会话可用性实测拿真实长任务压了一次前后端协议，暴露的缺陷里有三类**根都在协议把业务写死**：

- 审批卡 / ask_user 在 CLI 无呈现出口——因为 `UserPrompt` 是协议里的**专名**，不是通用交互协议；
- 中断轮永不收束——因为「一轮 = 一个 Turn 根、Opened/Closed 配对」被写进了协议；
- 大结果检索聚合口径缺位——因为工具结果节点里没有「总量」这一格统计。

三条都不是补丁能修的形状问题——协议把「轮 / 工具 / 压缩」当成了**概念**，而不是**渲染分派**。
把协议收敛到「树 + 类型标签 + 主体」，这些缺陷自然消失或换成有出口的形状。

## 2. 现有形状盘点对比

Explore 阶段核过，目标形状**已在实码里约 80% 落地**，改名与解绑占多数工作量：

| 目标 | 今天 | 差什么 |
|---|---|---|
| 节点树 | `ChatMessage.parent_id` 已在；`useChatConnection.ts` 按 `parent_id` 组树 | 只差改名 |
| 组合骨架 | `MessageType::Turn` / `ToolCall` 文档原话就是"组合节点，仅分组子节点" | Turn 语义被"轮"绑死 |
| 折叠叶子 | `Text` / `Reasoning` / `Compression` 已是叶子 | 缺一个统一的呈现轴（默认折叠 / 流式 / 类型图标） |
| Typing 占位 | 无 | 新增 `kind: typing` + 兄弟到达即替换 |
| 主体平级 | `principal: Option<String>` 已在；值域已是可分派地址（`session/*` / `person/*` / `tool/*` / `system/*`），kind 由 `PrincipalKind` 独立给 | 已落地（D-069） |
| 后端定显示策略 | 前后端各自假设「一轮 = 一个 Turn 根」 | 加 `presentation_tree` 开关 |
| 骨架惰性重取 | 无（`transcript_window` 是上下文侧不是 UI 侧） | 新增 VDFS 动作 `expand_skeleton` |

## 3. 协议收敛后的 `ChatNode`

```rust
pub enum NodeKind {
 Body, // 正文叶子；默认展开；可流式
 Notice, // 折叠叶子；默认折叠；覆盖 reasoning / compression / 未来 step_summary
 Skeleton, // 容器骨架；默认折叠；携带 stats
 Interaction, // 需用户应答（ask_user / 审批 / 补参）
 Typing, // 占位；同父下一非-typing 兄弟到达即 removed
}

pub struct ChatNode {
 pub id: String,
 pub parent_id: Option<String>,
 pub kind: Option<NodeKind>,
 pub style_tag: Option<String>, // 'tool' / 'reasoning' / 'compaction' / 'sub_agent' / ...
 pub title: Option<String>, // 呈现文本；工具节点=工具名，用户节点=显示名
 pub principal: Option<Principal>, // 4 前缀，见 §4
 pub status: Option<NodeStatus>, // 保留原七值
 pub content: Option<MessageContent>,
 pub delta: Option<String>,
 pub error: Option<String>,
 pub stats: Option<NodeStats>, // 只 Skeleton 携带
 pub seq: Option<i64>,
 pub timestamp: Option<i64>,
 pub meta: Option<Value>, // 业务兜底：tool_call_id / args / responds_to / interaction_kind ...
}

pub struct NodeStats {
 pub total: u32,
 pub by_kind: BTreeMap<NodeKind, u32>,
 pub unfinished: u32,
}
```

**协议里没有**：`tool_call_id`（沉 `meta`）、`role`（与 principal 前缀重复）、`tool_name`（用 `title`）、
`skeleton_kind` 硬枚举（用 `style_tag`）、`Compression` / `UserPrompt` / `Reasoning` / `Turn` 四个专名
（分别合并进 `Notice` / `Interaction` / `Notice` / `Skeleton`）。

## 4. PRINCIPAL——kind 与可路由地址分家（[D-069]）

**id 是主体地址**：拿着这个地址可以找到主体、调用它、查看它的各种信息——与 VDFS 地址
`<sid>/message/<mid>`、route `/session/:sid`、`plugin/name` 同族形状。

- 形状：`<namespace>/<name>` 或更长路径段；`namespace` = 归属插件（无插件时用概念名 `person` / `system`）
- kind 独立：`PrincipalKind` 枚举 `Person` / `Agent` / `Tool` / `System`，**不进 id**
- 例子：`session/main`、`session/worker`、`person/local`、`vdfs/write`、`web/fetch`、
 `local/content_search`、`system/compactor`；若 reflex 拆到独立 decider 插件——`decider/reflex`
- 分派判据：`AGENT_NAMESPACES: &[&str] = &["session"]` + `is_agent_id(&str) -> bool`
 （agent 的判据是**命名空间闭集**，不按前缀猜）

写侧唯一入口在 `plugins/session/transcript/publish.rs::attributed`。工具调用**请求**节点：
`{kind: Agent, id: session/<调用者>}`；工具**响应**叶子：`{kind: Tool, id: <plugin>/<name>, title: <显示名>}`。
骨架节点：`{kind: Agent, id: session/<拥有该骨架的主体>}`。

授权表按 id 索引，扩行至 tool / system 族——`vdfs/write` / `web/fetch` / `local/content_search` 三条工具主体
各自一行（其余按名册补，见 [CURRENT.md §2]）；`system/compactor` 一行。kind 不参与主键。

## 5. 建树策略（后端配置，前端零假设）

会话配置加一格 `presentation_tree: flat | grouped | deep`：

| 模式 | 组树规则 |
|---|---|
| `flat` | 所有节点挂会话根；只有工具调用内部有自己的骨架 |
| `grouped` | 每条用户消息开一个 `Skeleton{style_tag:"run"}` 根，本轮所有节点挂它下（今天默认） |
| `deep` | 递归——`session/worker` 派生子会话时，子会话每一步也是父骨架下的 `Skeleton{style_tag:"sub_agent"}` |

前端**不知道这个开关存在**：收到帧就按 `parent_id` 插树。今天已有的"子会话转播桥"（agent 插件）是 `deep` 模式的雏形。

## 6. 骨架折叠 + 惰性重取

新 VDFS 动作 `<sid>/message/<skeleton-id>?action=expand_skeleton`：

- **入参**：`{ depth?: "1" | "all", since_seq?: i64 }`。`depth` 是**字符串**（数字 `1` 与布尔
  都不认），`since_seq` 是 `seq` 水位（只回更高的后代）；**给了但不合法 ⇒ 报 `invalid` 错误码**，
  不静默按缺省处理——静默的后果是「以为只要直接子」的调用方实际拿到整棵树，而他从回执里
  看不出来。显式 `null` 与缺省同义（「不过滤」的线上写法）。
- **出参**：`{ session_id, root, nodes }`——`nodes` 是该骨架子树的**窄帧序列**（按 `seq` 升序，
  每条带 `id` / `parent_id` / `seq`，够前端按 `parent_id` 装回原处；**不含骨架自身**）。
  骨架不存在 ⇒ 空数组（只读动作，「没有」就是空，不是错误）。
- **只读**：不落变更、不投变更帧、不触发新一轮——这是它与「恢复」的分界（恢复落在同一个
  地址上，但会起新一轮）。

前端「释放折叠骨架的子节点」只是本地 store 的事，不改协议：折叠时把子树从本地转写里摘掉，
并把「多少条 / 什么类型 / 还在跑几个」记进**本地账本**（`unloaded` 是纯前端状态，不进
`ChatNode` 线格式——进 wire 会被前后端字段比对判红），折叠态据此渲染一行摘要；跨刷新由
历史水合处回放（骨架已不在快照的账目就地清偿，随会话丢弃一并清掉）。**在途骨架不释放**
（streaming / 待审批的增量会经落地口把节点带回来，当场与账本分叉）。

## 7. Typing 占位

**由前端本地合成**，后端不发。规则：父节点在 `streaming` 且尚无子节点 ⇒ 显示一个 typing 兄弟；
同父下一非-typing 兄弟到达即把 typing 就地标 `status=removed`。协议侧不需要 `Removed` 之外的新状态。

## 8. 顶层字段消费纪律（[D-070]）

**一条判据**：`ChatNode` 顶层每字段，前端 / CLI 至少有一处**不查看 `meta` 语义**就能消费它。
不满足 ⇒ 沉 `meta` 或只留后端。

**落守卫**：`scripts/protocol-mirror-audit.mjs` 加一组 G 项——扫 `chat_node.ts` 接口的每一字段，
grep 前端 / CLI 消费者，命中但**判据里读了 `meta.xxx`** 的算违规。

## 9. 与主流形态的对照结论

调研过 AG-UI 1.0、Vercel AI SDK v6、Claude Code UI / CloudCLI、assistant-ui Chain of Thought、
LangGraph Studio、ChatGPT Deep Research 六处。三条结论：

- **后端下发树结构**（LangGraph Studio / Claude Code UI 的做法）与**前端合成折叠**（assistant-ui 的做法）是两条可行路；
 本方案选前者，理由：更贴 v2「后端决定显示策略」的一贯方向、也保住 `parent_id` 是**协议原语**而不是启发式产物。
- **一个后端两种视图**（graph ↔ chat）是工业先例——`presentation_tree` 开关不是自造概念。
- **AG-UI 生态兼容** 值得外挂，作为**外挂面**（`plugins/session/agui_bridge/`）而不是**内核**——
 内核保 `ChatNode` 树，外挂把帧流翻译成 AG-UI 事件；这条不在第一轮（排期待定，可选）。

## 10. 关键决策

### D-070 NodeKind 是唯一前端分派轴——`style_tag` 降级为后端注记

**决策**：前端渲染器按 `kind` 分派；`style_tag`（`run` / `tool` / `sub_agent` / …）只是后端写下的
**注记**，呈现细节（标题 / 图标 / 动作）走节点数据，前端没有专名分支。配套纪律：`ChatNode` 顶层
每个字段，前端 / CLI 至少有一处**不查看 `meta` 语义**就能消费它（§8）。

**理由**：「轮 / 工具 / 压缩」当协议概念 ⇒ 每加一种形态都要改两侧代码（`Turn` / `Compression` /
`UserPrompt` / `Reasoning` 四个专名就是这么长出来的）；`kind` 闭集 + 注记让新增形态只加数据。
`Turn` 语义因此从协议退役，容器改由 `Skeleton` 承担。

**执行方**：`scripts/protocol-mirror-audit.mjs` 的 G 项（§8）；`NodeKind` 五值闭集登记在
[机制强制等级清单](../004-ref/010-机制强制等级清单.md "RE-010-机制强制等级清单")。

### D-015 前端显示由节点状态驱动，不由事件顺序驱动

**决策**：运行态是**节点的属性**，不是事件流里的增量——会话节点 `<根>/session/<sid>` 承载
`status`（`working` / `active` / `failed`）+ `attributes.outcome`（`completed` / `aborted` /
`failed`）+ `attributes.error`，消息节点承载自己的 `status`；状态类变更**必带全量节点视图**，
消费端**零回读**、不做静默回读兜底。前端只有按地址分派；等待审批 / 活动文字 / 可重试性都由
节点表**派生**（纯函数）。

**理由**：状态幂等、可交换、丢一次不影响正确性；事件是增量、有顺序、丢了没有第二次机会。
「按事件流显示」的正确性依赖到达顺序，而顺序不是免费保证——`eventBus` 里那段 `replayBuffer`
（切会话防乱序缓冲）就是为修顺序而存在的机制；**一段只为修顺序而存在的机制，说明模型选错了**。

**词汇不合并**：`streaming`（消息）与 `working`（会话）保持两个词——合并会连带改 `status-*`
CSS 类名与 `isWorkingStatus()`，而漏改 CSS 类名不报错、不失败，只会让流式动画静默消失。

### D-146 生成的路由常量是**全量契约面**——未用常量不删，R-003 按文件头承认

`tauri/src/constants/routes.gen.ts` 由后端 `route()` 的 `match` 臂生成，21 条常量里前端
当前只调用一部分。审计把它报成「15 个未用导出」，而文件又自称「没有第二份真相」——
读代码的人分不清「契约面」与「生成器偷懒」。

两条路：**契约面**（全量导出 + 文件头声明口径 + 承认账本）或**消费面**（生成器只导出
被引用的）。**选契约面**，因为消费面有一条死结：**引用了才生成，可没生成就引用不了**——
前端第一次要用 `telegram/send` 时，常量还不存在，只能先手写字符串再重新生成，而那正是
这份生成物要消灭的东西。契约面的代价是一份「当前没人用」的清单，但那不是债务，是
**契约的另一半**：后端注册了这条地址，前端迟早要么调用它、要么在文档里指它。

机械形态两件：

- **口径写在生成器里**（`scripts/facts/routes-ts.mjs` 的 `HEADER` + `WAIVER`）——重新生成
  不会把声明冲掉，而「口径」与「生成行为」因此不可能分叉；
- **`dead-code-audit` 的 R-003**：前端未用导出必须二态——删掉，或整份文件在文件头写
  `// dead-code-allow R-003: <理由>`。理由为空 = 未承认（与 R-001 / R-002 同一条约定）。
  作用域放大到整个文件是有意的：只有「这份文件的完整就是契约」才配用它，而那种文件
  通常是生成物——生成器负责不让它漂，所以新加一条未用导出不会成为漏网。

同一批清掉的第三态：`messageFacts.ts` 的三个「备用」谓词（`isSkeletonFacet` /
`isUserNode` / `isSkeletonNode`）与 `MESSAGE_FAILURE_KIND_ERROR` **删除**——组件谓词没有
「契约另一半」的辩护（组件的消费方就是自己），静默留着只会让下一个读代码的人以为
「某处一定在用」。

| 被否的候选 | 否掉的理由 |
|---|---|
| 生成器只导出被消费的路由 | 死结：没生成就引用不了，第一次用某条地址必须先手写字符串——正是要消灭的东西 |
| 15 条逐个写声明级豁免 | 69 行的文件长出一倍注释；而它们共享**同一个**理由，重复 15 遍只会让理由贬值 |
| 让 R-003 只警告不判红 | 「说不清该不该用」正是要消灭的第三态；警告读起来像「可以不管」，实测就是没人管 |
| 把四个谓词也塞进承认账本 | 它们没有 owner 也没有契约地位——承认一个没人要的东西，等于把冗余写成制度 |

### D-149 兼容层只有两种去处：删掉，或者并进唯一的那一份定义

「未发布、不留兼容」（`SP-008`）是本仓的长期口径，但兼容层一旦落地就会自己长出理由——
没有人会在它「暂时有用」的时候删它。四处前端兼容层因此长期停在**默认保留**态，它们的
共同点不是「还有用」，而是**没有一个裁决记录谁什么时候该动它**。逐条按「删掉 / 并进共享
定义」裁决，不留第三种：

| # | 位置 | 原来的说法 | 裁决 |
|:-:|---|---|---|
| 1 | `messagePresentation.ts` 的 `NODE_STATUS_LABELS` | `active` 是旧数据别名，仅为已落库历史节点保留 | **删**——`ChatNode.status` 的闭集就是 `NodeStatus` 那七个，`active` 没有生产写方；缺文案时 `messageStatusLabel` 原样返回，不崩也不误标 |
| 2 | `chat_node.ts` 的 `principal?: Principal \| string` | 读侧兼容历史 `messages.json` 的裸字符串，迁移后可收窄 | **收窄成 `Principal`**；`normalizePrincipal` 只解析地址形态（`<ns>/<name>`），旧形态（`agent:main` / 裸 `user`）不再归一 |
| 3 | `router/index.ts` 的六条旧地址 redirect | 书签 / 深链的兼容 | **删**——未发布，那类地址只存在于开发机；删后落到既有的兜底（回首页由守卫接手），不改变任何代码可达的行为 |
| 4 | `controls.css` 与两个组件的同名 scoped 副本 | 副本特异性更高，视觉不受共享文件影响 | **并进共享定义**——取值按副本的实际渲染搬进 `controls.css`，副本删掉，一处定义 |

**第 2 条的边界要写清楚，否则下一次读代码的人会以为两栈漂了。** 后端 `Principal::from_legacy`
仍认旧形态，但它服务的是**另一件事**：`ActorSpec.principal` 里的 actor 名（`agent:researcher-01`
这类，`verify/mechanism_growth.rs` 在用），不是 `ChatNode.principal` 的兼容层。前端只归一
`ChatNode.principal`，所以「两栈同一张表」这句话收敛成「两栈的**命名空间表**逐段对齐」。
`principal` 收窄之后，旧数据里的裸字符串会落到「尚未标身份」——可见域判据把它当可见、
角色按 `role` 格折，与「没接线的写方」走同一条路径，不会因为少一次迁移而消失或报错。

**第 4 条为什么不是「排期清副本」**：副本的差异只有三格（`flex-shrink`、`.text-input` 的
内边距与背景、focus 样式）。排期意味着「先把差异记下来，以后再统一」——而差异记在注释里
就等于没有。把差异**并进共享定义**再删副本是同一件事的完成态，成本就是改两处 CSS。唯一的
可观察变化在 `DetailForm` 的禁用按钮上：共享定义带 `:disabled { opacity:.5 }`，副本没有——
那是补上该有的反馈，不是新引入的视觉。

| 被否的候选 | 否掉的理由 |
|---|---|
| 保留 `active` 别名但加一条「到期删」的注释 | 注释不会红；两年后它还在，而读的人会以为这是活约定 |
| 让 `ChatNode.principal` 继续收字符串、只在注释里说「已废弃」 | 类型是唯一会被人真读的声明；留着联合就等于允许新写方传字符串 |
