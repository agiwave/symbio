# 第三方插件体系

> **本期范围外**：本文是设计预留；`ExternalPlugin`、stdio/HTTP 传输、样例外部插件、§9 第二/三期
> 均不在本期实施范围，代码现状只到内置插件（源码内编译期插件）；本文只作未来裁决输入。

> 让「插件」不再限于编译期内置的 Rust 实现。
>
> **边界**：本文只回答「怎么设计」。一次性的现状评审已随归档层退役（历史在 `git log`），
> 本文不再引用它的条目号；单条决策定案后写进该主题设计文档的「关键决策」节。
>
> **参照系**：MCP（Model Context Protocol）。本文与 MCP 的**关键差异**是范围——
> MCP 的接入点是「工具清单」，本方案的接入点是**完整的 `Plugin` trait**：
> 路由 / 资源树挂载 / 配置表单 / 生命周期。§8 逐项对照。

## 1. 目标与不变量

### 目标

让一个**不在本进程、不必是 Rust** 的实现，成为一个与内置插件**同构**的插件：

- 有挂载点（出现在资源树里，有标题、图标、排序）；
- 有路由（`<挂载名>/<子路径>` 可寻址）；
- 有工具（出现在 LLM 的能力清单里）；
- 有配置表单（在自己的目录里读写 `PLUGIN.yml`）；
- 可启用 / 停用 / 卸载（与内置插件同一套动作）；
- 被约束（声明需要什么，宿主决定授不授）。

### 四条不变量（不得违反）

| # | 不变量 | 出处 |
|---|---|---|
| **I1** | 一个插件 = 一个目录；搬走目录 = 搬走插件（含配置与状态） | `crates/symbio-sdk/src/plugin/dir.rs` |
| **I2** | 挂载名 = 目录名 = 实例名 = 路由前缀 | `routes.rs` 模块文档 |
| **I3** | 插件之间互相不可见，只经 core 契约交互 | `plugin-entry-audit.mjs` E-009（物理约束由 cargo 依赖图给出） |
| **I4** | 容器是通用容器：它不认识任何具体插件，只认 `Arc<dyn Plugin>` | `composite` 设计 |

**I4 是本方案能成立的关键**：容器对子插件的要求只有「实现 `Plugin`」。
因此**只要外部插件能提供一个 `Arc<dyn Plugin>` 的实现，容器就不需要任何改动**。
方案的全部工作，就是造出这个实现。

## 2. 现状：八类障碍

以下是「外部实现为什么现在接不进来」的完整清单（详见评审文档，此处只列与设计相关的约束）。

**处置列的性质**：这八行是**方案**，不是施工项——`D-407` 裁「本期只做源码内编译期插件」，
八条一律**不实施**，各自的方案留在这里作未来裁决的输入。不逐格重复写「不实施」：
同一句事实写八遍，改一次要动八处，也必然漂移。

| # | 障碍 | 位置 | 若开放的处置（本期不实施，`D-407`） |
|---|---|---|---|
| 1 | `inventory` 编译期注册 + `TypeId` 严格相等 + 裸函数指针 | `crates/symbio-sdk/src/creator/mod.rs` | §3 两级 provider 解析 |
| 2 | `ctx` 扩展桶有不可序列化键（`SymbioKey::WIRE = false`） | 已按「键与值同住」分散到各值域（`keys/mod.rs` 模块文档） | §5.2 线上可表达子集（P3） |
| 3 | ~~`PluginPayload::Native` 死变体~~ ——**已删除**（评审 P1 已落地） | `transport.rs` | 已完成 |
| 4 | 闭包 sink / 事件总线 channel / `ExecEnv` | `exec.rs` | §5.4 出口的线上形态 |
| 5 | 共享内存状态（`&self` dispatch / visitor 槽 / `HookRegistry`） | 各插件内部 | §5.3 声明式替代 |
| 6 | 无插件级权限模型 | 仅 `crates/symbio-plugin-local/src/policy/mod.rs` 的 `SecurityPolicy` | §7 manifest 授予 |
| 7 | 无生命周期钩子 | `Plugin` trait（`crates/symbio-kernel/src/plugin/mod.rs`） | §6 `init` / `shutdown` 帧 |
| 8 | `gateway` 是**纯入站**（外部调用本应用，反向不成立） | `gateway/server.rs` | §3.3 复用其线上类型，方向相反 |

**障碍 8 值得单独说明**：`gateway` 已经解决了「外部进程怎么调用本应用」——
它有完整的线上类型（`PluginMessageWire` / `PluginPayloadWire` / `PluginFrame`）
与三种传输（Tauri IPC / HTTP / WS）。本方案要的是**同一个问题的反向**：
「本应用怎么调用外部进程」。因此**线上类型可以原样复用**，只是发起方向相反、
且外部侧需要多一组生命周期帧。

## 3. 核心决策：把 provider 从「一个 id」扩展为「一个描述」

### 3.1 两级 provider 解析

**现状**：`plugin_provider` 的值必须命中 `inventory` 表（`crates/symbio-sdk/src/plugin/dir.rs` 的装配判据）。

**改动**：把「查表」升级为「解析」，解析结果有两种来源：

```
plugin_provider: web → Builtin("web") ← 现状完全不变
plugin_provider: "ext:stdio:./weather" → External(Stdio) ← 新增
plugin_provider: "ext:http:http://127.0.0.1:8080" → External(Http) ← 新增
```

**关键性质**：

1. **零新增保留键**——只扩展 `plugin_provider` 的**值语法**，键本身不变。
 这直接服务于「减少新加机制」：`PLUGIN.yml` 的骨架、`creator_has` 判据、
 `PluginEntry` 结构都不动，只多一条解析分支。
2. **内置路径行为完全不变**——无 `ext:` 前缀即走现有 `creator_create_object`，
 一个字节都不改。
3. **解析发生在装配方**（`composite`），与「谁构造插件」同处——不引入新角色。

### 3.2 装配期数据流

```
composite.mount_all
 └─ 逐目录读 PLUGIN.yml
 ├─ plugin_provider = "web" → creator_create_object("web") → Arc<dyn Plugin>
 └─ plugin_provider = "ext:stdio:./weather" → ExternalPlugin::spawn(..) → Arc<dyn Plugin>
 ↑
 容器从这里往后完全一致
```

**这就是全部**：`ExternalPlugin` 是一个**普通的 `Plugin` 实现**，它的
`route` / `traverse` / `vdfs_dispatch` 三个方法体内不发本地逻辑，而是**把调用翻译成帧、
发给子进程、等响应、翻译回来**。

从容器视角，它与 `web` 插件没有任何区别——因为容器只认 trait。

### 3.3 形态选型

| 形态 | 隔离 | 跨语言 | 复用现有资产 | 结论 |
|---|---|---|---|---|
| **stdio 子进程** | 进程级 | ✅ | `PluginFrame` 帧编解码 | **推荐（首选）** |
| **HTTP/WS 端点** | 网络边界 | ✅ | `PluginMessageWire` / `PluginPayloadWire` | **推荐（次选）** |
| WASM（wasmtime） | 沙箱 | ✅（编译目标） | 无 | 后续评估 |
| 动态库（`abi_stable`） | **无**（同进程） | ❌（Rust ABI） | 无 | **不推荐** |

**为什么动态库不推荐**：它只解决「编译期」不解决「隔离」——而隔离恰是第三方插件的
核心诉求。且 Rust 无稳定 ABI，`abi_stable` 需双方锁定同一版本，生态代价高。
本方案的建议是**连提都不提它**：把它与 `wasmtime` 并列会让人以为两者是可比的隔离方案。

**为什么 stdio 首选**：它是 MCP 已验证的形态；隔离是进程级的（不共享内存、
崩溃不传染）；且**宿主已有的 `PluginFrame` 就是 JSON 帧**——子进程只需实现
「读一行 JSON、写一行 JSON」。

## 4. 外部插件的清单（manifest）

`PLUGIN.yml` 在外部插件上的形态（**复用 §3.1 的值语法，不新增连接类保留键**）：

```yaml
plugin_provider: "ext:stdio:./weather" # 连接方式（值语法，见 §3.1）
plugin_name: weather # 实例名（缺省 = 目录名）
plugin_enabled: true # 装配位
plugin_title: 天气 # 身份：展示标题（D-032）
plugin_description: 查天气的外部插件 # 身份：语义描述
plugin_version: 1.2.0 # 身份：版本
plugin_author: someone@example.com # 身份：作者
plugin_api: "1" # 新增：要求的宿主插件 API 版本
plugin_grants: [fs.read, net.http] # 新增：宿主授予的能力（§7）

# 以下仍是插件自己的配置字段（现状不变，宿主不解释）
weather_units: metric
```

**身份键（`plugin_title` / `plugin_description` / `plugin_version` /
`plugin_author`）已在第一期落地**（D-032）：运行期唯一来源是 manifest，
出厂声明（`Plugin::meta`）只在装配期投影一次。对外部插件而言这尤其自然——
它**没有** Rust 侧的实现可承载身份，manifest 是唯一可能的位置。

**新增两个保留键，各有不可省的理由**：

| 键 | 为什么必须在 manifest 里（而不是别处） |
|---|---|
| `plugin_api` | 宿主必须在**启动子进程之前**就知道「这个插件我认不认识」——否则要么盲目启动（可能挂），要么启动后才发现不兼容（已产生副作用） |
| `plugin_grants` | 权限是**宿主**的决定，必须在宿主侧可审计（I1：跟着目录走，搬走目录 = 带走授予） |

**注意**：插件「**需要**什么」**不**在 manifest 里——那是插件自己在 `init` 响应里
声明的（§7）。manifest 只记「宿主**授予**了什么」。两者分开，才能有「授予 < 需要」
这个可检测的状态。

## 5. 线上化协议

### 5.1 帧形态

**复用现有类型**：宿主侧的线上格式已是 `PluginMessageWire { metadata, payload }`
（`crates/symbio-kernel/src/plugin/transport.rs` 的 `PluginMessageWire`）。外部插件协议在此之上加一个**操作头**与**请求 id**：

```jsonc
// 宿主 → 插件
{
 "op": "route" | "traverse" | "vdfs" | "init" | "shutdown",
 "id": 1, // 请求 id，用于配对（流式会话时同一 id 多帧）
 "path": "forecast", // route / traverse / vdfs 的路径（相对本插件）
 "metadata": { "trace_id": "…", "session_id": "…" }, // 线上可表达子集（§5.2）
 "payload": { … }
}

// 插件 → 宿主（一次性）
{ "id": 1, "ok": true, "payload": { … } }
{ "id": 1, "ok": false, "error": { "code": "NOT_FOUND", "message": "…" } }

// 插件 → 宿主（流式，多帧同 id）
{ "id": 1, "frame": "data", "value": { … } }
{ "id": 1, "frame": "error", "message": "…", "details": { … } }
{ "id": 1, "frame": "end" }
```

**`op` 的闭集是 5 个**——正好对应 `Plugin` trait 的五个方法（`init`/`shutdown`
对应 §6 新增的生命周期钩子，`meta` 不需要，因为身份来自 manifest）：

| `op` | 对应 trait 方法 | 响应形态 |
|---|---|---|
| `route` | `Plugin::route` | 一次性或流式 |
| `traverse` | `Plugin::traverse` | 一次性 |
| `vdfs` | `Plugin::vdfs_dispatch` | 一次性（`VdfsRequest`/`VdfsResponse` 本就可序列化） |
| `init` | （新增，§6） | 一次性，带声明（§5.3） |
| `shutdown` | （新增，§6） | 一次性 |

**`frame` 与 `error.code` 都复用现有资产**：帧的三态（`data`/`error`/`end`）与
`PluginFrame` 的两态（`Data`/`Error`）同构；`error.code` 直接用
`PluginErrorCode`（`crates/symbio-kernel/src/plugin/error.rs`）——**这是评审 P4 记录的「可直接复用」**。

### 5.2 线上可表达的上下文子集

`ctx` 的键按值类型分三类（评审 P3）：

| 类 | 值长什么样 | 外部插件可见 |
|---|---|---|
| **字符串键** | `String` | ✅ 原样进 `metadata` |
| **可序列化对象键** | `Value` / 路径串 / 名字清单 | ✅ 序列化后进 `metadata` |
| **进程内对象键** | `trait object` / `Arc<Mutex<..>>` / 闭包 / 中止信号 | ❌ 见 §5.4 |

**这一分类已是类型事实**（评审 P3，**已落地**）：`SymbioKey::WIRE`（缺省 `true`）
声明「本键能否在进程外表达」，第三类标 `false`——「哪些键能进 `metadata`」现在
可静态读取、可机检，不必靠人记住。**名单的 owner 是键本身**：值类型属哪个域，
键就住那个域（D-095），`WIRE` 与值类型写在同一处；本文不复制这份名单——它每加
一个键就旧一截，而类型定义始终是最新的。

### 5.3 能力声明：用「声明」替代「宿主拉」（评审 P8）

**问题**：内置插件的能力清单是**宿主 `traverse` 时现场算出来的**（`traverse` 是同步
调用栈里的回调）。外部插件做不到——它不能在宿主的遍历中「被调用一下然后返回」。

**解法**：外部插件在 `init` 时**一次性声明**自己提供什么：

```jsonc
// 宿主 → 插件
{ "op": "init", "id": 1, "metadata": { "api": "1" } }

// 插件 → 宿主
{
 "id": 1, "ok": true,
 "declare": {
 "api": "1", // 确认版本（不匹配则宿主拒绝）
 "capabilities": [ // = CapabilityMeta 清单
 { "name": "forecast", "description": "…", "input_schema": { … } }
 ],
 "options": [ … ], // = 选项（可展示的数据节点）
 "configurable": { "label": "天气设置", "definition": { … } }, // = 配置文档声明
 "vdfs_root": true, // = 是否暴露资源树挂载点
 "needs": ["fs.read", "net.http"] // = 需要的能力（§7）
 }
}
```

**宿主侧的接线**（这是本设计的**关键**）：

外部插件对应的 `ExternalPlugin` 实现里，`traverse` 方法**不转发给子进程**，
而是**返回 init 时缓存下来的声明**：

```rust
async fn traverse(self: Arc<Self>, path: String, ctx: Arc<dyn PluginInvokeRequest>) -> … {
 match path.as_str {
 // 宿主遍历到本插件时，把「声明」原样交出去——与内置插件的回填同形
 "available_tools" => Ok(PluginPayload::new(&self.declared.capabilities)),
 "available_options" => Ok(PluginPayload::new(&self.declared.options)),
 _ => /* 其他路径转发给子进程 */,
 }
}
```

**于是容器完全不需要知道「这个子插件是内置的还是外部的」**——它遍历时收到的都是
一份清单。内置插件是「现场算的」，外部插件是「init 时缓存下来的」，
**对汇聚点完全同构**。

这正是评审 P8 那句「声明是外部插件的入口，visitor 仍是宿主的唯一汇聚点」的落地。

### 5.4 四条进程内通道的处置

| 通道 | 用途 | 外部插件的对应物 |
|---|---|---|
| `CAPABILITY_VISITOR` / `OPTION_VISITOR` / `CONFIGURABLE_VISITOR` | 宿主拉清单 | §5.3 声明（**推**模型） |
| `EVENT_SINK`（执行期出口） | 工具执行时推事件 | 流式帧（§5.1 的 `frame: data`，同 id 多帧） |
| `ABORT_SIGNAL`（执行期中止） | 编排层中止工具 | 带外帧 `{ "op": "abort", "id": 1 }`（宿主 → 插件） |
| `PARENT`（父插件引用） | 子插件回看父 | ❌ 不提供——**违反 I3**（插件互相不可见）。若某插件真需要，那是它该经 core 契约表达的需求 |

表外还有一类进程内键（能力收集期的错误桶、子 Agent 权限作用域、本轮交付句柄等）：
它们是**宿主自己的**收集与派发状态，不出现在外部插件的调用路径上，故不需要对应物——
这一条按「调用路径是否经过插件」判，不按「键是不是 `WIRE = false`」判。

**`EVENT_SINK` 的对应物已经存在**：现有 `PluginPayload::Session(PluginChannel)` 正是
「长连接 + 多帧」的机制，而 `gateway` 的两个传输入口已经在处理它——分类统一在
`classify_payload`（`crates/symbio-plugin-gateway/src/server.rs`），HTTP / WS 各自只决定怎么消费。
外部插件的流式响应**直接复用这条路径**——不需要新机制。

## 6. 生命周期（评审 A2，**已落地 = D-033**）

### 钩子

`Plugin` trait 上两个**可选**钩子（默认空实现，既有 impl 一行不改、行为不变）：

```rust
/// 装配后、开始服务前调用一次。默认无操作。
fn start(&self, _ctx: Arc<dyn PluginInvokeRequest>) -> Result<(), PluginError> { Ok() }

/// 停用 / 卸载 / 进程退出前调用。默认无操作。
///
/// `reason` 区分三种情形（可恢复停用 / 卸载 / 全局收尾），
/// 因为插件的处置可能不同（如卸载时是否保留数据）。
async fn stop(self: Arc<Self>, _reason: PluginStopReason) -> Result<(), PluginError> { Ok() }
```

**`start` 同步、`stop` 异步**，这是两条路径的约束，不是随手选的：装配路径
（`HomePlugin::build` → `Composite::build` → `PluginRegistry::mount_all`）本身同步，
工厂签名非 async，那里 await 不可用；而 `stop` 的调用点全在 async 上下文，清理又必须
await（发 shutdown 帧、等子进程退出、flush 落盘）——同步的 `Drop` 做不了这些。

### 调用点（已接线）

| 动作 | 实现 | 接线 |
|---|---|---|
| 装配 | `PluginRegistry::mount_all` 构造 | 构造后调 `start` |
| 停用 | `PluginRegistry::set_enabled(name, false)` 移除实例 | 移除前调 `stop(Disabled)` |
| 卸载 | `PluginRegistry::uninstall(name)` 移除实例 + 删目录 | 删目录前调 `stop(Uninstalled)` |
| 退出 | 容器递归下发 | 逐插件调 `stop(Shutdown)` |

### 事件钩子（`HookEvent`）的触发面

`HookEvent` 是**写给用户配置**的扩展点：用户在 `hook` 插件里按**事件名**注册命令，
宿主在关键点经 `hook/fire` 发一帧。14 个变体里**只有三个有产者**——`PreToolUse` /
`PostToolUse`（工具端口执行体，调用前后）、`PreCompact`（压缩端口执行体，压缩前）；
其余十一个**没有产者，也不再补**，因为它们要通知的事情都已经是一条**事实**
（逐个对应见 `D-478` 的表）。

判据的落点：`grep -rn "fire_hook(" crates/` 的非测试调用点是三处；每个无产者变体在
`crates/symbio-plugin-api/src/hooks.rs` 的文档注释里写着「无产者（`D-478`）」并指向
它对应的事实名。**加产者要新裁决**——对照组是 `PreCompact`：它成立的理由是
「压缩发生前」这个**时刻**没有任何格可订阅，不是「这个变体看起来该响」。

### 外部插件的实现

`ExternalPlugin::stop` 发 `shutdown` 帧 → 等 `ok` → 关闭 stdin → 等进程退出
→ **超时则 kill**（宽限期如 5 秒）。`start` 在 spawn 后发 `init` 帧并校验版本。

**对内置插件**：`start`/`stop` 默认空实现，**行为不变**——这是「加钩子
不改变现状」的保证。

## 7. 权限与信任（评审 A4）

### 两侧声明，取交集

```
manifest（宿主写） plugin_grants: [fs.read, net.http] ← 宿主决定「我允许你用什么」
init 响应（插件给） "needs": ["fs.read", "net.http", "proc.spawn"] ← 插件声明「我需要什么」

 授予 ⊇ 需要 → 通过
 授予 ⊉ 需要 → 拒绝 init（记录缺失的能力）
```

**为什么是两侧而非一侧**：只有「授予」没有「需要」，宿主不知道插件要干什么，
只能全授（等于没约束）；只有「需要」没有「授予」，插件自己说了算（等于没权限）。
两侧都有，才有「**授予 < 需要**」这个可检测、可审计的状态。

### 能力清单（已定案，闭集）

| 能力 | 含义 | 风险 |
|---|---|---|
| `fs.read` / `fs.write` | 读写**本插件目录之外**的文件 | 高 |
| `net.http` | 出站 HTTP | 中 |
| `proc.spawn` | 启动子进程 | 高 |
| `env.read` | 读环境变量 | 中 |
| `host.ctx` | 读 `metadata` 里的会话 / 追踪信息 | 低 |
| `vdfs.read` / `vdfs.write` | 经宿主读写**共享资源空间**（会话 / 技能 / 记忆 / 其它插件的数据） | 高 |
| `event.publish` | 向事件总线投递事件（可被其它插件与前端订阅） | 中 |

**为什么是这九个而不是最小集**：前三项（`fs` / `net` / `proc`）是「进程能对外做什么」，
后三项（`host.ctx` / `vdfs` / `event`）是「**插件能对宿主做什么**」——后者才是本体系
真正的权限面：一个第三方插件若能任意写 VDFS，它就能改会话转写、改别人的配置、
伪造记忆，**而它根本不需要碰文件系统**。只列前三项会让权限模型看起来完整、
实际上漏掉最大的那一片。`event.publish` 单列（而非并入 `vdfs.write`）：投递事件是
**广播**语义，影响面跨插件，与写一个文件不是同一类风险。

闭集的意义：新增能力必须改本表 + 一条决策，**不允许插件自定义能力名**——
否则「授予 ⊇ 需要」退化成字符串游戏。

**与 `SecurityPolicy` 的关系**（评审 A4）：**分层共存，不替换**。
`SecurityPolicy`（`crates/symbio-plugin-local/src/policy/mod.rs`）管「local 插件**自己的工具**怎么安全执行」；
本表管「**宿主**允不允许一个插件碰文件系统 / 共享空间」。前者是插件内部的实现细节，
后者是装配契约。

**强制点**：本期**只做声明与校验**（拒绝不匹配的 `init`），不做运行时沙箱
（如 seccomp / 网络隔离）。理由：stdio 子进程已是**进程级隔离**，宿主能做的事
（拒绝启动）已经足够表达「不信任就不装」。运行时沙箱留给后续按需引入。

## 8. 与 MCP 的对照

| 维度 | MCP | 本方案 |
|---|---|---|
| 传输 | stdio / HTTP+SSE / streamable HTTP | stdio / HTTP（**复用 gateway 线上类型**） |
| 报文 | JSON-RPC 2.0 | JSON 帧（`op` + `id`，§5.1） |
| 能力协商 | `initialize` → `capabilities` | `init` → `declare`（§5.3） |
| **覆盖范围** | **只有工具**（+ 资源 + 提示词） | **完整插件**：路由 / 工具 / 资源树挂载 / 配置表单 / 生命周期 |
| 宿主角色 | LLM 客户端 | **插件容器**（插件可嵌套，分形） |
| 挂载语义 | 工具加前缀（`server__tool`） | **挂载名 = 目录名 = 路由前缀**（I2），且出现在资源树里 |
| 配置 | 无（由客户端自行处理） | 插件在自己的目录里读写 `PLUGIN.yml`（I1） |
| 权限 | 无（靠用户逐次确认） | manifest 授予 + init 需要，取交集（§7） |
| 隔离 | 进程（stdio）/ 网络 | 同 |

**「MCP 只管工具」的具体含义**：MCP 的插件是一个**工具提供者**，接入点是「工具清单」；
本方案的插件是**智能体的组成单元**，接入点是完整的 `Plugin` trait。因此本方案多出
四件 MCP 没有的事：**资源树挂载点**（§5.3 `vdfs_root`）、**配置文档声明**
（§5.3 `configurable`）、**生命周期**（§6）、**权限授予**（§7）。

**可以借鉴 MCP 的两点**：
1. **stdio 优先**——已验证、跨语言、隔离好；
2. **能力协商先于服务**——`init` 一次说清，避免「调用时才发现不支持」。

**不必借鉴 MCP 的一点**：JSON-RPC 2.0 的完整报文规范（`jsonrpc`/`method`/`params`）。
本方案已有 `PluginMessageWire`，加 `op` + `id` 即可；引入 JSON-RPC 是**第三套**
线上约定（现有已有两套：Tauri IPC 与 HTTP/WS），徒增不一致。

## 关键决策

### D-407 进程外插件本期不实施：范围声明与重启条件

**裁决**：本期只做**源码内编译期插件**——插件是一个 Rust crate，随二进制编译，经 `Plugin` trait
与 `PLUGIN.yml` 装配；不实现进程外插件、不做运行期安装。本文 §3–§9 的性质因此从「施工图」改为
**设计预留**，只作未来裁决输入。

**为什么现在不做**：

- 没有真实消费者：今天所有插件都是内置 crate，没有「必须非 Rust 实现」或「不重新编译就要装上」的需求；
- 进程外插件把路由、资源树、配置、生命周期四条面都变成跨进程序列化问题（§5 的线上协议），
  在插件数量与异构实现都还没出现时落地，只会造出一套没有第二个使用者的机制；
- 权限强制（§7）在「没有外部插件、没有需要侧数据」时无法校准，先做等于凭空发明阈值。

**重启条件**（两者满足其一，并经架构裁决）：

1. 出现**非 Rust 实现**的真实插件需求（例如必须复用某个现成的 Python / Node 服务）；
2. 出现**运行期安装 / 卸载**的真实需求，且编译期装配无法满足。

届时以本文为输入重新裁决，不从零发明。

**不做什么**：不因此删除本文任何设计；不把 §9 第二/三期排进任何批次；不在内置插件路径上预留
外部分支（避免「为未来留一个恒空的槽位」）。§10 的 D2 / D3 / D4 一并暂不裁决。

### D-520 核心插件默认加载且不可删除，可选插件由插件市场按需安装

**问题**：今天 31 个内置 crate 里 29 个进 `REQUIRED_PLUGINS`，`ensure_required()` 在首次启动时
把它们全部补出目录，`mount_all()` 再按目录扫描挂载。用户看到的是一张 29 项的清单，其中
多数从未主动选择过——「插件」于是退化成一张出厂零件表，而不是可裁剪的能力集合。

**裁决**：把内置插件分成两层，判据由各插件 `PLUGIN.yml` 唯一声明（D-174 / D-181 的投影纪律不变）：

- **核心插件**：`plugin_assembly: sub_agent` 且未声明 `plugin_optional`。它们进
  `ASSEMBLY_CORE_PLUGINS`，是注入 `REQUIRED_PLUGINS` 的唯一清单：首次启动补目录、默认加载，
  且容器拒绝卸载（`PluginRegistry::uninstall` 的 `required` 判据）。`plugin_manager` 与 `vdfs`
  两个界面底座仍额外受 `ASSEMBLY_UNDISABLABLE_PLUGINS` 约束，不可停用也不可删除。
- **可选插件**：声明 `plugin_optional: true`。它们进 `ASSEMBLY_OPTIONAL_PLUGINS`，不补目录、
  不默认加载，作为插件市场的候选；安装后与核心插件同权（可停用、可删除），删除即回到候选。

`ASSEMBLY_SUB_AGENT_PLUGINS` 保留为「所有子树插件」的文档与审计口径，不再充当默认装配清单。
生成器拒绝「可选且不可停用」的声明：一个默认不加载的插件不可能是界面底座。

**插件市场的边界**：市场是 `symbio-plugin-plugin_manager` 的呈现门面，注册表权威仍在容器
（D-174 的分工不变）。候选判据 = 「声明为可选 ∧ 当前未装配 ∧ 本构建确实链接了该工厂」——
三项缺一不可，缺第三项会给出一个点了没反应的安装按钮。「未装配」按**挂载实例**判，不按
目录存在判：历史 homedir 会残留旧版默认装配留下的可选插件目录，那些目录没挂上也不在跑，
按目录判会把市场占满到「一个都没有」；从市场安装这类残留目录走容器 `install`（只按实例表
判重），正好重新启用它。候选项带 `source: builtin` 字段；
外部插件的形态、权限与连接协议仍按 D-407 暂不实施，本决策只为它留出一个可扩展的候选模型，
不在内置路径上预留恒空分支。

**市场的交互形态**：市场**不是** VDFS 清单里的节点，而是「添加插件」这一动作打开的页面。
`plugin_manager` 根节点声明 `new_type`（`ext` / `node_ext` 均为 `market`，`title = 添加插件`），
候选随 `new_type.schema` 下发；点击安装走草稿保存，写回当前目录（= 容器根上的安装动词）。
工作台对 **schema 驱动的选择器页**（落成 `ext = market`，由前端渲染注册表分类）不自动
开草稿：进入管理页第一眼必须是已装插件列表，市场只由用户点「添加插件」进入——否则
前端的默认自动开草稿会把市场铺在右栏，把「先看列表」的语义冲掉。该判据不新增内核协议
字段（公共数据面只许降），也不在前端写资源类型名。容器根上的通用安装表单不再由本插件
转发：它是空下拉，既不是市场也没有候选。

**与 D-407 的关系**：这里做的是**编译期已链接插件的运行期装卸**——不需要新 crate、不需要
进程外协议、不改变 `Plugin` trait 与 `PLUGIN.yml` 的通信协议（D-486 规则 E）。D-407 暂缓的是
「非 Rust 实现 / 不重新编译即可装入」的进程外插件，两者不冲突；其重启条件原样有效。

### D-521 界面偏好归独立后端插件：localStorage 只做首屏快照

**问题**：`plugin_manager` 的清单末尾有「外观」「关于」两个分区，节点 `kind = plugin_manager`，
数据在前端 store 与 `package.json` 里，VDFS 节点正文恒空、读写一律 `Forbidden`。「一切皆插件」
的一致性在这里破了一个口子：用户看到的是插件管理里的两行，它们却不是任何插件的产出——
后端既不知道主题偏好，也无法在别处复用它。

**裁决**：新增独立后端插件 `symbio-plugin-ui_prefs`，把这两行的**节点归属与数据权威**
迁到它名下；入口仍挂在 `<插件管理>` 清单里，用户的操作路径不变。

- `ui_prefs` 是核心插件（`plugin_undisablable: true`），提供配置文档
  `<根>/ui_prefs/PLUGIN.yml`，由 `PluginConfigMount` 统一负责校验、落盘与广播。
- `plugin_manager` 的分区节点 `kind` 改为 `ui_prefs`；「外观」的读写转发到上述配置文档，
  「关于」没有用户数据，正文恒空、读写仍明确拒绝。`plugin_manager` 不持有副本，也不声明
  这份配置——重复声明会让同一份数据出现两个入口。
- `ui_prefs` 不声明 `configurable`：否则条目上会多出一张通用外观表单，与专属面板并存。

**localStorage 的身份**：`main.ts` 在 `app.mount` 之前同步调用 `useAppearanceStore().apply()`
以防主题闪烁 / 白屏，这是一条同步路径，不能改成异步 VDFS 读取。因此 localStorage 保留，
但身份从「唯一数据源」降为「首屏快照 + 离线降级」：后端配置读到后覆盖快照；用户修改时
store 即时生效并写快照，面板同时把完整配置写回后端；后端缺席（插件未装配 / 读取失败）
时退回首屏快照，功能不残废。

**「关于」为什么不落盘**：版本来自编译期，描述是硬编码自述，引导按钮是纯 UI 流程状态。
不为「一致」而制造一份没有消费者的数据；它归 `ui_prefs` 只是节点归属，正文恒空。

### D-522 必装、默认内置可删、市场可选三档拆分：删与不删独立于开箱装配

**问题**：D-520 把「默认装配」与「不可删除」绑在同一份 `ASSEMBLY_CORE_PLUGINS` 上——
核心集里的插件首次启动补目录、默认加载，同时容器拒绝卸载。用户看到的是一张绝大多数
都标着「必需」的插件清单：一个只是装了就开箱可用的能力，与一个删掉系统就跑不起来的
底座，被同一个「必需」标签抹平。工具、网络、技能这些一次正常会话用得上的能力，
和高阶读数、行业渠道这些用不用都行的能力，同列在一张不可删的表里。

**裁决**：把原来的核心集按两个正交维度拆开。「默认装配」与「市场可选」仍由各插件
`PLUGIN.yml` 声明（D-174 / D-181 / D-520 的投影纪律不变）；**必装与否不由插件声明，
而由装配策略写死**——「我是不是系统骨干」是装配方的判断，让插件自己写
`plugin_required: true` 等于把「减少必装」的裁决权交回每个插件：

- **必装集**（装配策略 `scripts/facts/assembly.mjs` 的 `REQUIRED_IDS` →
  `ASSEMBLY_REQUIRED_PLUGINS`）：不可删除的最小底座。`PluginRegistry::is_required` 查这一份
  （不再是整个 core），`uninstall` 据此拒绝，前端只读投影 `plugin_required` 也读它。
  判据是「完成一次正常会话是否离不了，或少了它整个界面无法再操作」——插件管理、会话、
  机制环、模型，加界面底座 VDFS 与界面偏好。生成器校验每个必装 id 都在默认装配集里，
  且插件不得自行声明必装（残留 `plugin_required` 判红）。增删必装须改装配策略文件。
- **默认内置可删**：`plugin_assembly: sub_agent`、`plugin_optional` 与 `plugin_required`
  都未声明。进 `ASSEMBLY_CORE_PLUGINS`，首次启动补目录、默认加载（开箱完整），
  但不在必装集里，用户可以卸载。一次正常会话需要、但删掉仍有平凡值的那些能力
  （执行工具、路由、子智能体、本地文件、工作区记忆等）在这一档。
- **市场可选**（`plugin_optional: true` → `ASSEMBLY_OPTIONAL_PLUGINS`）：语义与 D-520 相同，
  不默认装配、按需安装。高阶读数与行业集成在这一档。

**两个维度为什么不合并**：合并会让「开箱就有」等价于「不许删」，用户为一个默认开着、
自己从没选过的能力找不到卸载入口。拆开后，`ensure_required` 读 core（决定补哪些目录），
`is_required` 读必装集（决定能不能删），各读各的清单；一份插件可以默认就在、同时允许删除。

**系统文档的边界**：可选插件的具体身份不从装配策略层列举——它们是能力目录里的条目，
机制文档只说「一档是按什么判据划分的」，不把某档具体有哪些插件写成系统事实。
清单的实际归属由 `ASSEMBLY_*` 生成物与各插件 `PLUGIN.yml` 回答（PI-001 同源纪律）。

### D-523 图标内容由插件自给、前端直接渲染

**问题**：插件管理列表里，多数条目的图标是同一枚齿轮。根因有两端：插件其实早就在
`PluginMeta.icon` 里写了图标声明，但这个字段**运行期零消费**——`entry_node` 把所有
条目的 `kind` 设成 `plugin_manager`，前端 `iconForNode` 只按 `name` / `kind` 查，未登记的
插件一律落到 `plugin_manager` 那枚齿轮。链路是断的。

**裁决**：图标**内容**由插件自己给出，前端只负责画，不持有任何图形资产。

- **内容住在插件里**：插件在 `Plugin::meta()` 的 `with_icon(...)` 里直接写一段
  SVG 图元串（feather 风格 24×24，如 `<path d="M4 12h4…"/><circle cx="12" …/>`），
  不再写「图标名」。这就是「每个插件自己决定显示什么图标」——图长什么样由插件的
  这段代码定义，改它即改图，前端零改动。
- **走 D-032 身份投影链**：装配期 `PluginDir::seed_identity` 把 `meta().icon` 原样投影
  成 manifest 的 `plugin_icon`（**只补缺失、用户可改**），此后 manifest 权威。两个消费端
  都读它——插件管理列表的 `entry_node` 与挂载点节点（composite 的 `vdfs.rs` 里的
  `dir_node`）把这段 SVG 内容放进节点顶层属性 `plugin_icon`；停用插件不被构造，但身份已在 manifest 里，
  列表照常出图。`PluginIdentity.icon` 与 `PluginEntry.icon` 各补一格投影载体
  （CS-009 放宽见 `arch-shape-audit.mjs` 的 D-523 行）——它们承载的是插件自给的内容，
  不是新长出的业务数据面，没有新增世界域名 / 端口名 / 事实名。
- **前端零字典**：`registry/vdfsIcons.ts` 的 `iconFromSvg` 把 `plugin_icon` 内容直接包进
  统一 `<svg viewBox="0 0 24 24">` 壳渲染（同串缓存复用）；`iconForNode` 回退链新增第 0 跳
  「自报优先」，SVG 内容非字符串 / 空串则回退到既有登记，不留空白。前端不维护
  「名字 → 图」字典，也无需为新图标改代码。**矢量**：SVG 图元任意缩放不失真，
  尺寸交给容器 CSS。
- **其余图标各归其主**：详情字段 emoji（`FIELD_ICONS`）与机制动作图标（`ACTION_ICONS`）
  仍由后端给语义名、前端映射视觉——它们不是插件自画像，是另一套机制，不在本次范围。

被否候选：① 插件只给图标名、前端维护「名 → SVG」字典——那样图形资产仍在前端，插件只
选了个标识，不是「插件提供图像内容」；② 后端托管 SVG 资产库再按名取——同样把内容留在
了后端共享面而非插件自身，且触碰 plugin-api 的转发棘轮。两者都违背本裁决「内容住在插件
里、前端零图形资产」。

### D-478 事件钩子按「通知物是不是事实」分流：三个有产者，十一个不补

**问题**：`HookEvent` 的 14 个变体里只有三个有产者，而 `fire_hook` 的注释与归档 ADR 把
十四个都写成「会响」。订阅是**按名字**的：用户在 `hook` 插件里写一条 `Stop`，得到的是一条
静默——契约面写着「有这个事件」，实现里却是「这个事件不响」。这不是文档陈旧，是
**契约在无声地缩水**。

**裁决一：一个变体该不该有产者，只看它要通知的事情是不是已经是事实。**

- **已经是事实** ⇒ 没有产者，订阅方读事实（跨插件的名字经 `PLUGIN.yml` 的 `shared_events`
  投影成生成常量）。同一件事两条通道必然漂移：事实被行写、被投影、被 `unless` 读，
  而钩子那份是没有 owner 的旁路拷贝——它不参与判定，却看起来参与。
- **不是事实** ⇒ 有产者。属于这一类的只有「动作的前后沿」：工具调用发生**之前**、
  被拦下**之前**、压缩发生**之前**——这些**时刻**没有任何格可以订阅，事后那条事实
  也替代不了「拦在它前面」。

逐个结论（`grep -rn "fire_hook(" crates/` 的产者以非测试调用点为准）：

| 变体 | 结论 | 通知物 |
|---|---|---|
| `PreToolUse` | **有产者**（工具端口执行体，调用前） | 时刻，无事实 |
| `PostToolUse` | **有产者**（同上，调用后） | 时刻，无事实 |
| `PreCompact` | **有产者**（压缩端口执行体，压缩前）；通知语义、不读 `should_proceed` | 时刻，无事实 |
| `PostToolUseFailure` | 不补 | `artifact.added`（`success = false` + `failure_kind`） |
| `Notification` | 不补 | 无对应事实：真通知该是自己的事实（带 owner 与格位），不是一条通用字符串 |
| `UserPromptSubmit` | 不补 | `user.message`（开轮事实的溯源也指向它） |
| `SessionStart` | 不补 | `user.message` + `session.config`（本轮生效的提示词 / 工具表 / 设置） |
| `SessionEnd` | 不补 | `session.terminated`（`(Scope, Closed)`）／收束另有 `session.settled` |
| `Stop` | 不补 | `chat.assistant.final`（终答）+ `session.settled`；「为什么停」在驱动返回里 |
| `SubagentStart` | 不补 | `artifact.added`（`tool = agent_run`，含参数） |
| `SubagentStop` | 不补 | 同上（含 `success` / `text`） |
| `PostCompact` | 不补（见裁决三） | `session.consolidated`（`generation` / `fidelity` / `sources`） |
| `PermissionRequest` | 不补 | `authz.granted` / `authz.denied`（带工具名与拒因） |
| `StopFailure` | 不补 | `driver.stalled`（`D-393` 的安全阀出口） |

**裁决二：生命周期四变体（`UserPromptSubmit` / `Stop` / `SessionStart` / `SessionEnd`）不补产者，
也不为此扩 `RowRequest`。**

它们要落在 session 的行里，而 `RowRequest` 今天不带插件句柄。补这一格等于扩**行机制的世界
能力面**，撞 `D-306` 裁决二；而它们要通知的事分别已是 `user.message`、`chat.assistant.final` +
`session.settled`、`user.message` + `session.config`、`session.terminated`。为一格通知手段去扩
世界能力面，是拿机制付通知的账——行不带句柄这条边界原样保留，一行代码不改。

**裁决三：`PostCompact` 不拿错的数字凑载荷。**

它的载荷要「压缩前后消息数」，而压缩端口执行体手里只有压缩叶（`snapshot()` 交回摘要与可能的
终答），**原始段的消息账在上下文管线**。压缩的**结果**已落 `session.consolidated`；计数是**读数**，
订阅方拿它评估压缩效果——错数比没数更坏。重开条件：上下文管线交出一份前后计数，且出现两个
以上按它做判断的订阅方；届时按裁决一补产者，不提前塞一个占位数字。

**保留变体不删。** `event_name()` 是线格式的名字，用户配置按名字写；删变体是破坏契约面，
而「无产者」是可以写在契约上的事实。归档 ADR 不改（它是历史记录），现状 owner 是本节与
`hooks.rs` 的变体注释。

**判据**：
1. `crates/symbio-plugin-api/src/hooks.rs` 的 14 个变体逐个有结论：有产者，或一行
   「无产者（`D-478`）」+ 指向的事实名（枚举头注释写明三个产者与「其余不补」的口径）；
2. `grep -rn "fire_hook(" crates/` 的非测试调用点 = 3（`plugin-tool/src/port.rs` 两处、
   `plugin-compact/src/port.rs` 一处）；`pre_compact_is_fired_by_the_executor_without_changing_the_outcome`
   钉住「通知语义、不读 `should_proceed`、压缩照常落 `session.consolidated`」；
3. `plugin-surface-audit` 的 HS-002 不涨：变体与 `fire_hook` 都是既有公开项，本裁决不新增。

**不做什么**：不给无产者变体造假触发点（那是把契约面变成装饰）；不在 `RowRequest` 上加插件
句柄（`D-306` 裁决二）；不动 `PreToolUse` / `PostToolUse` 的语义与两个触发点。
