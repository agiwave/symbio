# 第三方插件体系

本文定义进程外插件接入宿主的协议与信任边界。内置源码插件与外部插件必须适配为同一个
`Plugin`，容器不区分二者。

适用范围包括源码内编译期插件；进程外传输只在出现非 Rust 实现或运行期安装的真实需求时
启用。没有真实对端时不在内置路径预留恒空分支，避免把猜测固化为公共协议。

## 1. 目标与不变量

| 不变量 | 约束 |
|---|---|
| 目录归属 | 一个插件一个目录，配置、身份与状态随目录迁移 |
| 地址一致 | 目录名、实例名与路由前缀一致 |
| 插件隔离 | 插件之间不可见，只经公共契约交互 |
| 容器通用 | 容器只认 `Plugin`，不认具体内置或外部实现 |

外部适配器负责把协议调用翻译为本地 `Plugin` 调用；容器、路由、发现和生命周期与内置插件
共用。外部实现不得要求容器增加按来源分叉的逻辑。

## 2. Provider 解析

`plugin_provider` 同时表达内置构造器和外部连接描述，不新增连接类保留键。

```text
web                         → Builtin
ext:stdio:./weather          → External(Stdio)
ext:http:https://...         → External(Http)
```

解析发生在装配方。无 `ext:` 前缀时走内置构造器；有前缀时构造外部适配器。解析后二者都
成为普通 `Plugin`，后续装配流程完全一致。

### 2.1 传输选择

| 形态 | 隔离 | 跨语言 | 规则 |
|---|---|---|---|
| stdio 子进程 | 进程级 | 是 | 首选，复用 JSON 帧 |
| HTTP/WS 端点 | 网络边界 | 是 | 次选，复用线路信封 |
| 同进程动态库 | 无 | 否 | 不作为第三方默认方案 |
| WASM | 取决于运行时 | 是 | 有真实沙箱需求时再评估 |

stdio 优先的理由是进程隔离、稳定跨语言线格式和现有帧协议可复用。动态库不解决隔离，且
依赖不稳定 ABI，不能与进程隔离方案等同。

## 3. Manifest

```yaml
plugin_provider: "ext:stdio:./weather"
plugin_name: weather
plugin_enabled: true
plugin_title: 天气
plugin_description: 天气查询
plugin_version: 1.2.0
plugin_author: maintainer@example.com
plugin_api: "1"
plugin_grants: [fs.read, net.http]

# 以下为插件私有配置
units: metric
```

| 字段 | 语义 |
|---|---|
| `plugin_provider` | 内置构造器或外部连接描述 |
| `plugin_name` | 实例名，缺省为目录名 |
| `plugin_enabled` | 装配位，缺省启用 |
| `plugin_title` / `plugin_description` / `plugin_version` / `plugin_author` | 展示身份 |
| `plugin_api` | 插件要求的宿主 API 版本 |
| `plugin_grants` | 宿主授予的能力 |

身份在装配期由出厂声明投影到 manifest，运行期只读 manifest。停用插件仍有身份，只是不
构造实例。

`plugin_api` 必须在启动外部进程前校验，避免先产生副作用再发现不兼容。`plugin_grants`
必须由宿主维护并随目录审计。插件需要什么在 `init` 响应声明，不在 manifest 自报；授予与
需要分开，才能检测“授予不足”。

## 4. 线上协议

### 4.1 请求与响应

宿主到插件：

```json
{
  "op": "route",
  "id": 1,
  "path": "forecast",
  "metadata": { "trace_id": "...", "session_id": "..." },
  "payload": {}
}
```

一次性响应：

```json
{ "id": 1, "ok": true, "payload": {} }
{ "id": 1, "ok": false, "error": { "code": "NOT_FOUND", "message": "..." } }
```

流式响应复用同一请求 id：

```json
{ "id": 1, "frame": "data", "value": {} }
{ "id": 1, "frame": "error", "message": "...", "details": {} }
{ "id": 1, "frame": "end" }
```

`op` 闭集为 `route / traverse / vdfs / init / shutdown`。错误码复用宿主 ABI；帧只表达数据、
错误与结束，不另造执行状态机。

### 4.2 上下文子集

只有 `SymbioKey::WIRE` 允许的字符串或可序列化值能进入外部 `metadata`。父插件引用、访问者、
闭包 sink 和中止令牌等进程内对象不得跨线传输。

- 能力、选项和配置发现改为初始化声明；
- 执行期事件出口复用流式帧；
- 中止使用带外控制消息，不伪装成业务帧；
- 父插件引用不提供，跨插件需求必须走公共路由契约。

## 5. 初始化声明

`init` 在服务开始前执行。插件返回：

```json
{
  "id": 1,
  "ok": true,
  "declare": {
    "api": "1",
    "capabilities": [],
    "options": [],
    "configurable": {},
    "vdfs_root": true,
    "needs": ["fs.read", "net.http"]
  }
}
```

宿主必须校验 API 版本与权限交集。版本不兼容或需要未获授予时拒绝初始化并记录缺失项。

外部适配器缓存初始化声明。`traverse` 对发现路径返回缓存的能力、选项和配置声明；其他
路径转发给外部进程。内置插件动态计算，外部插件初始化声明，对容器暴露同一种发现结果。

## 6. 生命周期

```rust
fn start(&self, ctx: Arc<dyn PluginInvokeRequest>) -> Result<(), PluginError>;

async fn stop(
    self: Arc<Self>,
    reason: PluginStopReason,
) -> Result<(), PluginError>;
```

`start` 同步，因为装配与构造路径是同步的；`stop` 异步，因为关闭连接、刷新和等待进程退出
需要 await。二者都是可选钩子，默认无操作。

| 动作 | 顺序 |
|---|---|
| 装配 | 构造完成后调用 `start` |
| 停用 | 移除实例前调用 `stop(Disabled)` |
| 卸载 | 删除目录前调用 `stop(Uninstalled)` |
| 退出 | 递归调用 `stop(Shutdown)` |

外部适配器 `start` 负责启动进程并完成 `init`；`stop` 负责发送 `shutdown`、等待响应、关闭
输入并等待退出，超时强制终止。内置插件不因这两个钩子改变默认行为。

事件钩子只通知“发生前”且没有可订阅事实的时刻。已有事实能完整表达的事件不再增加重复
钩子；新增钩子必须证明没有等价事实通道。

## 7. 权限与信任

```text
manifest.plugin_grants = 宿主授予
init.declare.needs     = 插件需要
有效权限              = 授予 ∩ 需要
```

| 能力 | 含义 |
|---|---|
| `fs.read` / `fs.write` | 读写插件目录之外的文件 |
| `net.http` | 出站 HTTP |
| `proc.spawn` | 启动子进程 |
| `env.read` | 读取环境变量 |
| `host.ctx` | 读取会话与追踪元数据 |
| `vdfs.read` / `vdfs.write` | 读写共享资源空间 |
| `event.publish` | 向广播事件总线发布 |

能力名是闭集，插件不得自定义。新增能力必须更新本表、权限执行方和反向用例。宿主授予与
插件需要缺一不可：只有授予无法判断插件意图，只有需要则等于插件自授权。

权限声明与运行时沙箱必须区分。声明校验只能拒绝不满足条件的初始化，不能证明进程运行后
不会越权。插件内部工具安全策略与宿主授权分层共存，不互相替代。

## 8. 装配策略

默认装配与可删除性正交：

| 类别 | 默认行为 | 删除规则 |
|---|---|---|
| 必需 | 始终参与装配 | 由宿主策略拒绝删除 |
| 内置可选 | 默认启用 | 可停用或卸载 |
| 市场可选 | 默认不启用 | 安装后按用户策略启用 |

具体清单属于装配事实，不写进容器或架构文档。卸载必须保留用户数据还是删除数据，由停止
原因和插件契约明确，不靠隐式 `Drop`。

## 9. 与 MCP 的关系

MCP 的核心接入点是工具、资源和提示词；本体系的接入点是完整 `Plugin`，额外覆盖路由、
资源树挂载、配置和生命周期。可借鉴 stdio 优先与初始化能力协商，不引入第二套 JSON-RPC
约定；宿主已有线路信封增加操作头即可。

## 10. 安全边界

启动前拒绝不兼容版本、权限不足或声明非法的插件。进程隔离降低崩溃与内存影响，不等于
完整沙箱。需要运行时资源限制时，必须新增明确的执行机制与可观察判据，不能把 manifest
声明当作安全证明。
