# 机制形状规格

> **一句话**：DE-047 给的是判据（七职、五事实、归属），本文补的是**形状**——债表长什么样、
> 驱动何时返回、流式怎么分片、同轮能不能并发、何时算完。形状写死之后，「加一个能力」
> 才有一份可检验的局部性承诺，而不是每次遇边界都拿最熟的那种形状（债 / 端口 / 阶段）来补。
>
> 本文只写机制形状，**不写任何业务规则**；业务如何用这些形状，归各能力插件的设计。

## §0 总判据：局部性

五条形状各配一条验证方式，形式统一：**新增能力只动一个插件 crate**，
`crates/symbio-plugin-loop` / `crates/symbio-plugin-api` / `crates/symbio-kernel` 的 diff 为 0。
验证方式不给「应该只动插件」的散文，给可执行的断言：验收提交里对上述三个 crate 跑
`git diff --stat <batch>^ -- <crate>`，输出必须为空；同时跑 `loop-purity-audit`（LP-001…LP-005）。

## §1 债表是数据，且带条件

**形状。** 一行债 = 身份 + 触发条件 + 排除条件。

- 身份：`(scope, port, id)`。`id` 由欠债方从**产生这笔债的事实**派生，禁计数；`attempt` 在债键里推进，不进身份。
- 触发条件（「某事实出现才欠」）有两种写法：
  - `after = <前置债 id>`：前置债收束（`response` / `failed`）之前，本行不可还；
  - `when = <事实种类>`：该种类的事实在本可见域存在才欠。环只把字符串交给宿主的
    `exists(kind, scope)`，不解释它是什么。
- 排除条件（「某事实已存在则不欠」）：`unless = <事实 id>`。命中即本圈不产出该行。
- 行只读事实投影，不读引擎自述；表由**端口插件自报**，宿主按族收集，环按行选债。

**环需要什么。** 每圈重问一次 `rows(view, scope)`；对带 `when` 的行问一次 `exists(kind, scope)`。
每行只给身份、条件、载荷、租约与尝试上限。

**环不需要什么。** 不需要认识行名、端口语义、触发 / 排除的业务含义；不需要知道「事实种类」来自
哪个插件、存在哪里；不需要保存上一圈的选债结果。

**判据。** 往复（A → B → A）与终止（没有行可还）全部由条件表达，环的 `plan` 只做条件求值；
跨行前置只写 `id`，不写端口名；业务事实（不在环五事实内）的存在性只经 `kind` 字符串 +
宿主谓词，不把业务名写进环。

**验证方式。** 假插件只在自己的 crate 里申报两行：B 的 `after = A.id`、C 的 `unless = A.id`；
另一行带 `when = <种类>`：宿主答「不存在」⇒ 不派发，答「存在」⇒ 派发一次；不碰三个冻结 crate。

**与现有代码的关系。** `DebtRow` / `DebtSpec` 已带 `after` / `when` / `unless`，`plan` 对三种条件
各做一次求值；`exists` 是宿主侧实现（世界事实的种类清单），环侧只调用。条件求值属**选债**一职。

## §2 驱动边界 = 无债即返

**形状。** `drive(ctx, scope)` 同步穷尽到「这一圈没有可还的债」就返回，出口三选一：
`NoDebt`（账上没有未收束的债）、`Waiting(<在飞债的键>)`、`NeedsHuman(<只能等外部事实的债的键>)`。
它**不阻塞**等用户、等审批、等外部回调；那些都只是「新事实到达 → 再调用一次 `drive`」。

- `Waiting` = **在飞**：某端口已派发、租约未过。环自己还能推进（应答落格或租约到期都会
  再踢），所以调用方**不得**把它当成「本轮空闲」——更不能在此时投影 / 收口。
- `NeedsHuman` = **只有外部事实才能推进**：执行体明确挂起（`sent{deadline_ms:null}`，等答复 /
  授权 / 超时唤醒），或债开着却没有任何行能还。环自己已无动作可做，**这才是**把控制权
  交还调用方的时刻。
- 与安全阀 `Exhausted` / `Stalled` 的区别是「停得正不正当」：后两者是没跑完（预算用尽 /
  零进展），必须让调用面看见；`NeedsHuman` 是正常的一轮结束（还在等，但等的不是环）。

**环需要什么。** 事实投影的读写、每圈的当前时刻、按端口名解析执行体。

**环不需要什么。** 不需要「人」端口，不需要「会话」端口；挂起不是新机制——它只用一个
字段（`deadline_ms: null`）表达「这一笔等外部事实」，此刻没有执行体在跑。

**判据。** `drive` 的返回时刻只取决于「有没有可还的债」，不取决于任何外部事件；
同一 scope 两次 `drive` 之间，环不留跨步状态。

**验证方式。** 假插件的执行体只在「入队事实到达」时才可派发：第一次 `drive` 返回 `NoDebt`（瞬时）；
宿主落一条入队事实后再 `drive`，同一行才被派发；全程不新增端口、不改环。

**与现有代码的冲突。** 无。当前 `drive` 已是无债即返；`outlet()` 已经把世界事实转出环外。

## §3 流式 = 分片

**形状。** 一笔债可以产出**多条** `response` 事实：分片按产出顺序落账，末条带完成标记；
配对键始终是 `(scope, port, id, attempt)`，分片序号**只在载荷里**（不进身份、不进配对键）。

**环需要什么。** 执行体返回 / `emit` 的多条 `response` 草稿：按序落账，不合并、不挑第一条。

**环不需要什么。** 不需要认识分片序号的含义，不需要「流式」专用事实种类、专用出口或专用等待态。

**判据。** 加一个流式端口不改环：分片只是同一笔债的多条收束前事实。

**验证方式。** 假插件的执行体 `emit` 三条 `response`（载荷含 `shard: 1|2|3`，末条 `done: true`）；
断言落账三条、`DebtKey` 三处完全相同；不改环。

**与现有代码的冲突。**
- `response_payload` 只取**第一条** `response` 草稿，其余被丢弃；环最后只追加一条 `response`。
  最小改法：环按 `CollectingWriter` 的收集顺序逐条追加。
- 宿主的写口按 `(kind, key)` 吸收重复，多条同键 `response` 会被吞成一条。
  最小改法：宿主的吸收键扩为 `(kind, key, 载荷里的分片号)`；分片号缺席时退回 `(kind, key)`。
  两处都是一次性机制改动，不增加事实种类。

## §4 同轮可派发多笔债

**形状。** 债表里**互不依赖**的若干行可以同时派发；一次 `drive` 的等待集合 = 这一圈全部在飞债的键。
前置条件（§1 的 `after`）仍串行：前置未收束的行不参与并发。

**生产现状（2026-11-07）。** 生产装配（`Host::with_store`）把并发度固定为 **1**：上面这条
路径只有单测覆盖（`independent_rows_run_concurrently_within_the_cap` 用 2 路会合点证明
它能并发），**线上每圈实际只派发一笔**。何时开多笔、开多大是另一次裁决；在那之前，
凡「同轮并发发生」的描述都只描述机制能力，不描述运行事实。（执行体自身的批次并发是
另一回事，归 provider 内部，见 `PortDecl.concurrency`。）

**环需要什么。** `plan` 一次给出全部可派发行；`drive` 并发执行它们，全部收束后再重算一圈。

**环不需要什么。** 不需要并发度参数、不需要批单元、不需要调度策略——并发是「这一圈有几行可还」的直接结果。

**判据。** 同轮多笔债不引入新单元：N 行 = N 笔债，只是同一圈的 N 次 `dispatch`。

**验证方式。** 假插件申报两行互不依赖的债；断言一次 `drive` 的 `dispatched == 2`、`Waiting` 同时包含两键；
第二笔的执行体在与第一笔同圈被调用；不改环之外的任何 crate。

**与现有代码的冲突。**
- `plan` 返回第一个可派发行就停；`dispatch` 内联 `await` 执行体，因此一次 `drive` 实际串行。
  `DriveOutcome::Waiting` 也只收第一个在飞键。
  最小改法：`plan` 返回可派发批；`drive` 用并发组合（如 `futures::join_all`）执行批内各笔；
  `Waiting` 收集全部在飞键。环的一次性机制改动。

## §5 终止 = 事实谓词

**形状。** 一个 scope 算完 = 已落终答事实 ∧ 该 scope 无未还债（`unresolved(scope)` 为空）。
判定由**写方**做：它读事实投影，谓词成立就落一条收束事实。环既不判、也不写。

**环需要什么。** 无新增——环只提供只读投影。

**环不需要什么。** 不需要「收幕」动作、终结指令、阶段出口；`drive` 出口没有「完成」这一态。

**判据。** 「算完」是事实的函数，不是一次控制动作；同一事实集重复驱动只得到同一结论。

**验证方式。** 写方只在新事实到达后重算谓词；断言同一事实集重复驱动不产生第二条收束事实（幂等），
并且删掉写方这一行谓词后，环照常运转（环零知识）。

**与现有代码的冲突。**
- **缺机制。** 本地写方目前读不到环的事实投影：宿主把 `FactView` 只交给 `DebtSource::rows`
  这一处，`DebtFacts` 又是按 `id` 归并的窄视图（只有结局与尝试号，没有终答载荷）。
  最小改法（环 / 契约零改）：宿主在每次 `drive` 前后，把同一份只读投影交给**簿记写方**
  （宿主自己持有的事实，不经环）。这需要一条宿主侧的写方注册面——它属于宿主，不属于环。
  形状已由 D-367 裁决（`termination` 族 + `TerminationWriter`），本节按那条裁决实现。
- 若顺序 1（建会话 → 用户发一句 → 模型回复 → 落库）被这一处挡住，按纪律停下报「缺哪个机制」，
  不在环里补终答判定。

## §6 门禁判据：不是外部世界，就不是端口

端口 = 与外部世界交互：**不可控、有延迟、可能失败**。本地能力（存储、转写、簿记）一律以
「写事实」参与，**不许声明端口**。

**机器覆盖（两臂）。**
- 结构臂：`symbio-host` 的收集面只认 `PORT_FAMILY` 行，且每条 port 行的提供者必须有执行体
  （`executor()` 为 `Some`）；任何 `DEBT_FAMILY` 行的端口必须有对应 port 行与执行体，
  租约与尝试上限必须有限。没有执行体的「端口」在装配期即缺席，欠不出可等待的债。
- 语词臂：`scripts/loop-purity-audit.mjs` LP-003（环与端口受理面零世界语义词根）、
  LP-004 / LP-005（`plugin-api` 的端口契约不具名任何世界）。

**边界。** 两臂判的是**装配形状**，判不出一个插件是否在「假装」外部世界——那要评审。
把本地能力做成端口时，它的债会表现为「永远立即成功、租约永远用不上」的一类假债；
这类行的存在本身就是评审信号，本规格不靠脚本识别它。

## §7 落地顺序

1. 宿主独立 + 债表自报（宿主按族收集、无端口白名单；端口插件各自申报债行）；
2. 假插件 `"demo"` 验收：注册 `demo` 端口 + 一笔债，只改新 crate，跑通
   「环选债 → 透传字符串 → 宿主查到执行体 → 执行体还事实 → 环配对」；
3. 回到 e2e 顺序 1。

第 2 步跑不通就停下报「哪一处挡住了」；不绕过、不放宽本规格。

## §8 需要先裁决的环一次性改动

§1 的 `unless`、§3 的两处分片追加、§4 的同轮并发与完整等待集合，都是环的一次性机制改动，
不属于「加端口」。在接受任何能力实现之前先裁决这三处；做完后 §1 / §3 / §4 的验证方式
应当直接可跑。

## 关键决策

### D-324 端口准入：不是外部世界，就不是端口

端口 = 与外部世界交互（不可控、有延迟、可能失败）。本地能力（存储、转写、簿记）一律以
「写事实」参与，不许声明端口。把它做成端口的代价是：环为它欠债、等待、配对，凭空多出
一类「永远立即成功」的假债，租约与重试对它形同虚设；同时多出一个必须实现的执行体接口，
加能力时多一处必改点。门禁覆盖见 §6。

### D-325 机制形状五条固化

债表带触发 / 排除条件；驱动无债即返；流式 = 同一债键的多条事实分片；同轮可并发多笔互不
依赖的债（**机制能力**；生产默认 1，见 §4 现状）；终止 = 事实谓词。五条是**形状**，不是建议：加能力只动插件，三条判据线
（环、接口、内核）都不因新增端口或新增债务行而改动（验证方式见 §0–§5）。

### D-359 驱动出口三态：把「在飞」与「等外部事实」分开

t29 的形态：两种停都报同一个 `Waiting`，而宿主的 `settled` 只看「驱动还在不在跑」，
于是 CLI 在「应答还没落格」的空档去投影，记忆巩固只看到本轮一半的编码、跳过合并。

裁决（**修 bug，不改契约**）：`settled` 的本意是「没有活可干」，而在飞的债就是活 ⇒
在飞不是 settled；只有外部事实才能推进时，才是交还控制权的时刻。据此给 §2 的出口加第三态：

- `Waiting` = 环自己还能推进（在飞）；宿主不得据此记空闲、不得投影；
- `NeedsHuman` = 环已推不动，只等外部事实（答复 / 授权 / 超时唤醒）；宿主据此交还；
- `Exhausted` / `Stalled` = 没跑完的安全阀；不是交还，是必须被看见的异常。

宿主侧的兑现是 `KickState` 的第三个条件位（`in_flight`）：只有 `Waiting` 置位，
`settled` 在 `running` / `dirty` / `in_flight` 三者全空时才返回。判据不落在调用方时机上——
换一个调用方（CLI / 收轮后台）不需要各自记得「等编码」。

### D-360 债行第五个谓词 `after_port(port)`：与 `when_no_open` 对偶，缺席即收束

t21-E / t22-C 的两个反例把现有谓词的边界照出来了：`when_id` 只表达「那条事实来了」，
表达不了「它不会来」；而计划在派发前一次成型（D-343），所以「还没判」与「根本没这个能力」
在事实面上同形。分类插件缺席时，模型行按 `when_id(classify.answered)` 会永远欠着——这就是
刚消灭的静默停摆换了个门进来；反过来，让执行体在发送前再查一次事实，又与环的派发记账分叉。

裁决：只加**一个**谓词 `after_port(port)`，与 `when_no_open` 用同一把尺子（对债状态取否定）：

- **认领** = 申报方这一轮报了这一行、且它那笔债还开着（已派发未收束，不看 `when` 的判定）；
  或者这一圈有动作的行（首派发的行还没有 `sent`）所在端口。两处来源合起来才算完整，
  单看 `when` 会在回执刚落、下一圈还没 parse 的空档里误判「没人认领」。
- **缺席即收束** = 没有任何行认领该端口 ⇒ 前提已了，依赖行照常可还。卸载一个插件
  不需要给依赖方留墓碑事实。
- **上一轮遗留的未收束债不算认领**：这一轮没人再报它，它由自己的租约判死；否则一次
  中断的往返会挡住整个下一轮（t49）。
- **不许变成新的静默门**：认领了却永不收束 ⇒ 依赖行留在 `Work.blocked`，出口必须是
  `Stalled`（不是 `NoDebt`）；被 `after_port` 挡住的行与在飞 / 挂起一起交给调用方。
  gate 债自己的租约 / 预算照旧走 `Exhausted` / 过期判死两个可见出口。

不取 `gate` / `after_gate` 这对新词：语义只有一条（「这一类工作这一圈有没有人认领」），
新词会让它看起来是第二套机制，而实际只是「对债状态取否定」这一族的第二个成员。

**什么时候才允许再加第六个**：出现一个**现有五个谓词都表达不了、且答案只能由债状态回答**
的新反例（必须写明 e2e 编号，如本条的 t21-E / t22-C），并且它与既有谓词的否定 / 对偶关系
能用一个词说清。凑不出这两条就组合现有谓词表达；凑得出也仍然一次只加一个，单独一笔、
DE-050 §1.1 的计数同步 +1，不许在同一批里顺手加第二个。

### D-362 「未选分支」判断下沉 kernel：事实层判断不留成插件的反向耦合

**背景**：模型插件在装配请求包时要裁掉被重试 / 切换换下的支。折法原本住在
`symbio_sdk::projection::branch`（应用侧门面），插件因此依赖 `symbio-sdk`——
`plugin-entry-audit` E-009 与 `plugin-surface-audit` HS-001 同时红。

两条捷径都不取：

- 把 `MessageVocab` / `MessageMutations` / `unselected_roots_named` 加进门面白名单：
  `unselected_roots_named` 只有一个消费方，过不了 C-003 的「≥2 个消费方」；且为了让门变绿
  去调宽门面，正是 HS-002 要防的「拿机制面去付实现面的账」。
- 给模型插件开一条限期豁免：等于承认一条反向耦合长期存在，把账推给下一次。

**裁决**：只把**判断本身**下沉到 kernel，不是搬整个 `projection::{branch,mutations,vocab}`：

- 「哪一支是活的、此刻读哪一支」是**事实层判断**（只读 `turn.branch` /
  `turn.branch_selected` 的载荷），不是「怎么画树」的呈现判断；它今天在投影层，是按
  「谁先用到」放错了 crate。
- 落点 `symbio_kernel::event::branch`（`branch_marks` / `unselected_roots` / `removed_ids`）：
  两条名字由调用方给，内核不认识业务词。
- `symbio-sdk::projection::branch` 只保留**呈现出口**（`stamp_branches` 把结论盖成
  `meta.branch`）并调用 kernel 的折法；`MessageMutations::collect` 的删除扫描改调
  `removed_ids`。「一份数据一个构造点」不许破——投影、请求包裁支、模型端口的请求装配
  读的是同一个函数。
- 搬完 `model` crate 不再依赖 `symbio-sdk`（测试夹具的 dev-dependency 保留）。

**停下来的条件**（留给后来者）：如果这条判断真的依赖只有呈现层才有的东西（节点形状、
`ChatNode` 的字段），说明它不是事实层判断，不许硬搬——那要回到本讨论重新裁决。
`branch_marks` 的 `live` 是闭包参数、返回的是组位置值对象，都不依赖节点形状，故本条成立。

### D-365 驱动重入位按装配根唯一：等的那份与踢的那份必须是同一实例

**背景**（t29）：`settled` 读的 `KickState` 与写口 `kick` 写的不是同一个实例——一份
永远空闲，等待立即返回。根因是**同一部署被绑了两次**：装配入口绑 home，插件
`drive_entry` 绑自己的父 composite，`HostDriveBinding::bind` 每次 `new` 一份。D-359
把「在飞」与「交还人工」分开的修复因此在 CLI 路径上**从未生效**：串行能绿，靠的是
收轮侧另一份实例的显式等待。

**裁决**（三层，缺一层都会退回原形）：

1. **构造只经 binding，类型上堵住第二份**。`HostDrive` 与其 `new` 住进私有子模块
   `host`，模块外拿不到构造入口；`HostDriveBinding::bind` 按**根的地址**缓存并持强引用
   （根不会被释放，地址不会复用）。「一个根一份」不再是约定，是没有第二条构造路径。
2. **根的身份先归一**。部署根是 **worker composite**（业务插件都挂在它下面），不是
   home。归一只经 `plugin-api` 的共享表：Home 构造 worker 后
   `publish_deployment_root(worker)`，宿主入口与插件都从 `deployment_root()` 取——
   插件与宿主因此都不直接依赖 `symbio-plugin-home`（它可卸载，EX-004）。表可重复
   登记，reload 重建 worker 后覆盖。
3. **等待方绑自己的根**。`project_final_turn` 的等待取调用方传入的本部署根驱动
   （会话插件 `drive_entry` / 收轮任务开轮时绑好的那一份），不再读进程级主根入口；
   子智能体容器的会话等自己的根，不等到别人的空闲上。

**判据**（第一道是类型，第二道是单测）：

- `drive.test.rs::binding_is_one_instance_per_root`：同根两次 `bind` 必须 `Arc::ptr_eq`，
  异根必须不等。
- `drive.test.rs::main_entry_resolves_to_the_bound_instance`：主部署入口解析到的必须
  就是 `bind` 交出的那一份。
- t29 并发 20 批 × 12 路全绿（串行绿不构成证据）；验收探针须显示 CLI 的 `settled` 与
  `project_final_turn` 等待 `waited_ms` 非 0，且两者指向同一个驱动实例。

**纪律**：凡「加了等待 / 同步然后串行绿了」，必须能指出**哪一份实例在等、谁在通知**；
说不出这两头就不算修好。

**已知边界（本批未收，按同一形状登记）**：

- `store::fact_source::STORAGE_DIR` 是进程级首个会话插件的目录（子智能体树的会话
  插件目录不同）。今天的开面（`open_fact_source`）只服务主根 CLI；一旦子智能体会话
  也要从开面读，开面契约必须带上根，不能继续取全局首个。
  **触发条件（不是愿望，是责任线）**：任何人让**子智能体树的会话**调用
  `FactSourceOpener::open`——出现这样的调用点、需求或 e2e 用例即算——必须**先**改契约
  （`open` 带上根，或登记「会话 → 根」），**再**改实现；不得先让开面继续取进程级首个
  目录。读到这条的人：下一个动开面契约、或让子智能体会话走开面读事实的人。

### D-366 入批顺序按（行名, 债 id）全序，不继承装配顺序

**问题**：债表由宿主按能力收集顺序拼出（`IndexMap` 插入序 = 插件挂载序）。环此前直接
按表序入批，于是同一组债换个装配顺序就换一个派发顺序与落格次序——行为依赖一个与
语义无关的偶然量，而「顺序碰巧对」还会掩盖真正的时序缺口。

**裁决**：`plan` 在分桶之前对候选行排一次全序，键为 `(行名, 债 id, 端口)`（前两位就是
名字与 id；端口只用于不同端口恰好同名的两行）。排序只决定**并列者之间的次序**，不表达
任何依赖：

- 真的有时序要求的债必须用谓词写出来——`after`（前置债收束）、`after_port`（端口这一圈
  没人认领）、`when_no_open`（端口债全部还清）；顺序碰巧对不算成立；
- 因此不与「能力之间本应有时序」冲突：需要先 A 后 B 的地方，A 通过上述谓词挡住 B，
  而不是靠 A 在表里排得靠前。排序只消除并列者的偶然顺序，不会让任何一行提前。

**判据**：`engine.test.rs::batch_order_depends_on_name_and_id_not_assembly_order`——同一组
债正序 / 倒序申报，落格序列（`(kind, port:id)`）必须逐项相等；只比 `dispatched` 不够。

### D-367 终止写方是宿主侧登记面：谁登记谁判，事实经同一投影回读

**问题**：§5 把「一个 scope 算完 = 已落终答 ∧ 无未还债」定为**写方**的谓词，但宿主只把
`FactView` 交给 `DebtSource::rows`——簿记写方没有任何入口读到同一份投影；`DebtFacts`
又是按 `id` 归并的窄视图，没有终答载荷。于是「终止」只能长在环里、或长在某条行的私货里，
两者都违反「环不判、写方落事实」。

**裁决**：新增 `termination` 能力族（`symbio_plugin_api::termination`），形状与
`drive` / `port` / `debt` 同一手法：

- **谁有权终止**：往 `TERMINATION_FAMILY` 登记一行 `TerminationPayload` 的插件。权利是
  **声明数据**；宿主按行收集，不认插件名，也不给内置写方开旁路。
- **交付什么**：宿主在每次 `drive` **前后**各调一次 `observe(TerminationView)`；视图只有
  两份东西——本会话全量只读投影（`&[DriveFact]`）与宿主的 `exhausted`（本次驱动
  `NoDebt`）。写方**不**读环内部状态，也**不**自行判「有没有未还债」。
- **落哪条事实**：写方交回 `Vec<FactDraft>`；草稿不指定写方，落库前由宿主按事件声明
  解析 owner（I1），与通用世界写口同一条路径。终止格是 `Scope × Closed`，落在 I3
  「这一轮为什么停」的判定范围内：载荷带 `root_id` 与该轮的 `reason`，且 `reason`
  **原样取终答事实上的那一格**——「为什么停」的 owner 只有一个（写终答的那一行），
  终止格不另起一个值。终答本身缺 `reason` 时本写方不落格，不用编造值盖住那个缺口。
- **环怎么读到**：终止事实与任何世界事实一样进事实源 → 投影。环**零知识**：需要它的
  债行用 `unless` 按名字问；不需要就什么都不加。

**判据**：
1. `termination.test.rs`：谓词三态（非 `NoDebt` 不落 / 有终答才落 / 同 `root_id` 只落一次）；
   终答缺 `reason` 时不落格；
2. e2e（t97）：一轮正常收束后 `session.terminated` 恰好一条，值 = 该轮 `root_id`，
   `reason` 原样等于该轮终答；再驱动一轮不再追加；
3. 删掉写方登记后环照常运转（零知识），只是不再有终止事实。

**不做什么**：不把终止塞进 `session.settled`。`settled` 是**收束贡献**的关账（终答之后跑
行、落贡献），终止是**整轮**的关账（终答 ∧ 无债）；两条件不同，合并会把「贡献落完但债
未清」误报成「算完」。

### D-369 债视图的单实例口径：`latest_fact_id` 只指认当前那一份，多实例必须逐条

**问题**：`DebtFacts::latest_fact_id(kind)` 返回该种类**最后记入**的身份；九个生产调用点
都用它指认「当前那一份」——当前轮的 `user.message`、最近一次工具往返、最近一条答复。
这个前提（**同一时刻至多一份有效实例**）此前只写在任务台账里（且只覆盖 classify），
契约本身没有口径。前提不成立时它会**静默**丢掉较旧的那一份：债务不再被申报，回合计不
静止，而所有「事实存在」型断言仍是绿的（这类断言不会自己变红）。工具恢复行正是这样配对的：
「最近一条 `user.answer` × 最近一条 `tool.requested`」——两条请求同时在场时，最近的那条
不是配对。

**裁决**：

1. **口径固定**（`plugin-api::debt` 的文档与判据同址）：`latest_fact_id` 回答「当前计划
   所对的那**一份**实例是谁」，不是「同类事实的列表」。跨轮的多条不算——最新一条就是
   当前轮 / 当前这笔。调用方只有在同一时刻至多一份有效实例时才可用它；否则必须改用
   `facts_of` 逐条取。
2. **配对按 wire id，不按位置**：工具恢复行读 `user.answer.call_id`，在
   `tool.requested.calls[].id` 里反查到**所属的那条请求**，债键仍回 `tool:<request_id>`
   （与首派同一键，`attempt` 不加）。一条答复只恢复它自己的请求；找不到所属请求 ⇒ 不恢复，
   **不拿最新请求顶替**。其余调用点（当前轮 `user.message`、首派的最新生往返、最近产物）
   维持单实例口径，前提由写方保证：一回合一条 `user.message`（t18 钉住）、工具往返串行。
   分类的 `ask_for` 仍用 `rev().find`（与策略文档说法一致），前提是**同一计划行同一时刻
   只欠一条 ask**（一行一次分类）；出现同轮多 ask 的那天，它与工具恢复是同一处缺陷，
   一并改为逐条。
3. **同一请求的多条答复**仍只认最后一条：一次恢复只消费一条答复。批内多卡（一个
   `tool.requested` 里两条待用户动作的调用）需要**逐调用债务**，属「批债 / 逐笔债」的
   单独裁决，本批不动；触发信号与修法登记在任务台账的「债行同族写法」一节。

**判据**：
1. `debt.test.rs::latest_fact_id_names_the_current_instance_while_facts_of_lists_all`：
   契约口径（最新一条 vs 全部）；
2. `tool/debt.test.rs`：答复属于较早请求、较新请求同时在场 ⇒ 恢复键落在**较早**请求；
   两条答复各归各的请求 ⇒ 两行；答复找不到所属请求 ⇒ 零恢复行（不顶替）；
   同一请求两条答复 ⇒ 一行、取最后一条（已知边界）；
3. 既有 e2e t27（单次审批 → 恢复 → 收束）原样绿：配对改的只是债键来源，恢复链路的
   出口不变；**同一轮两次待答复卡的真链路**不在本批加——它的调用卡投影缺口先登记在
   契约读者缺口台账，属批内多卡 / 逐笔债的同一裁决。

**不做什么**：不把恢复改成逐调用债务（批债 / 逐笔债另议）；不按「最近」兼容旧行为——
位置配对正是本条的缺陷本身。
