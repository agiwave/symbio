# 模块架构

> [DE-001](001-核心架构.md "DE-001-核心架构") 回答"系统里**存在什么**"。本文件回答"**代码拆成哪些 crate、依赖朝哪边、谁守哪条不变量**"。
>
> **两者不矛盾**：01 说的是"机制只有 1 个原语（架构层面）"，
> 本文件说的是"实现层面有几个 crate（施工层面）"。crate 的**数量**不增加机制，
> 它只把可独立替换、可独立编译的部分切开。权威 crate 清单在代码里——每个 crate 的
> `lib.rs` 头注释写自己是什么；本文只写**为什么这么拆**与**判据落在哪**。

---

## 1. 为什么需要两个视图

| 视图 | 问的问题 | "模块"的含义 |
|---|---|---|
| **架构视图**（DE-001 §0） | 系统里有哪些**机制** | 只有 `Store` 一个原语（其余是数据） |
| **crate 视图**（本文件） | 代码怎么拆、谁依赖谁、谁能并行 | 若干**可独立替换的 crate** |

**关键约束**：crate 切出来的每一个包，其"可替换性"都必须是**架构允许**的——
即替换它不需要动 [DE-016 §1](016-工程落地与验证.md "DE-016-工程落地与验证") 的 F1–F6。

## 2. crate 拓扑

```
                     ┌──────────────────────────────┐
                     │ symbio（装配）               │
                     │ 链接插件 crate · 装配策略     │
                     └──────────┬────────────┬──────┘
                                │            │
              ┌─────────────────▼──┐   ┌─────▼──────────────┐
              │ symbio-host        │   │ symbio-cli         │
              │ port 行 · 每会话驱动│   │ 控制台客户端        │
              └─────────┬──────────┘   └─────┬──────────────┘
                        │                  │
     ┌──────────────────▼──────────────────▼──────────────────┐
     │ symbio-plugin-api（扩展层门面）                        │
     │ 自有实现面：effects / port / text / context / reports  │
     │ 白名单转发：kernel 语法 + sdk 机制 + deploy 装配常量    │
     └──────────────┬────────────────────────────┬───────────┘
                    │                            │
        ┌───────────▼──────────┐      ┌───────────▼──────────┐
        │ symbio-sdk           │      │ symbio-deploy        │
        │ 宿主机制与策略       │      │ 生成物：id / 装配位   │
        └───────────┬──────────┘      └──────────────────────┘
                    │
        ┌───────────▼──────────┐
        │ symbio-kernel        │
        │ 封闭语法             │
        └──────────────────────┘
```

**插件层是两类，依赖方向不同**：

- **扩展层插件**（能力包与结构件）只依赖 `symbio-plugin-api`——它们看不见 `kernel` / `sdk` /
  `deploy` 的路径（[D-253](023-内核边界与扩展局部性.md "DE-023-内核边界与扩展局部性")）。
- **控制面插件**（`loop` / `session`）按 [DE-026](026-能力拆分与影响类.md "DE-026-能力拆分与影响类")
  的影响类运行，认识宿主的容器概念（轮次 / 幕），因此直接依赖 `symbio-kernel` + `symbio-sdk`。

**provider 层**（`symbio-provider-*` / `symbio-providers`）是基础设施实现：嵌入推理、
`vdfs_service`、内存检索、默认收集器。它们不承载架构判据，入口清单见
[`symbio-providers/src/lib.rs`](../../crates/symbio-providers/src/lib.rs)。

## 3. crate 一览

| crate | 职责 | 可替换性 |
|---|---|---|
| `symbio-kernel` | **封闭语法**：Event 信封与 Entity×Verb、View 与 Budget、`Store` trait、投影构造器、声明容器与环求解器、时延档位；外加**冻结机制原语**（信封解包 / 出口与中止 / 存储基线 / 表单求解器，清单见 [D-398](023-内核边界与扩展局部性.md "DE-023-内核边界与扩展局部性")） | **不可替换**：语法一改，全仓跟着改 |
| `symbio-sdk` | **宿主机制与策略**：配置 IO、事件总线、VDFS 地址装配、授权判定、actor 策略、投影重建、提示保真、日志 | 机制可替换、策略可增删；**不新增语法** |
| `symbio-plugin-api` | **扩展层门面**：自有 `effects::apply` / 端口校验 / `text` 预算 / `reports` / `context` 装配；白名单转发 kernel 语法、sdk 机制与 deploy 常量 | 对扩展层插件不可替换；**白名单只许收窄** |
| `symbio-host` | **宿主运行时**：发现全部 port 行、按会话起一次驱动、把债表当数据读、按根缓存驱动实例与每会话重入位 | 可替换；**不认识环的类型** |
| `symbio-deploy` | **部署事实**（生成物）：`PLUGIN_ID_*` / `ASSEMBLY_*`，由各插件 `PLUGIN.yml` 投影 | 生成物，不手改；零内部依赖 |
| `symbio` | **装配 crate**：链接插件 crate（漏一行 = `inventory` 注册丢失）、装配策略、日志与根插件构造 | 可替换；**插件之间不得经它互相可见** |
| `symbio-plugin-*` | 能力包 / 结构件 / 控制面；一个插件一个 crate | 扩展层插件可卸载；控制面插件按影响类 |
| `symbio-provider-*` | 基础设施实现（嵌入、检索、VDFS 落盘、默认收集器） | 可替换 |
| `symbio-cli` / `symbio-testkit` | 消费面（控制台客户端）与测试设施 | 不在架构层 |

### 3.1 依赖清单（只允许单向）

<!-- list:module-deps owner -->

| crate | 可以依赖 | **禁止依赖** | 强制方式 |
|---|---|---|---|
| `symbio-kernel` | 外部小依赖 | 任何 Symbio crate | 语法层无出边 |
| `symbio-sdk` | `symbio-kernel` | 其余 Symbio crate | `symbio-sdk/Cargo.toml` 的依赖面即判据：出现第二个 Symbio crate 就说明又有机制放错了层 |
| `symbio-plugin-api` | `symbio-kernel` · `symbio-sdk` · `symbio-deploy` | `symbio-host` · `symbio` · 任何具体插件 | `plugin-surface-audit` HS-005（门面 manifest 只许这三条） |
| 扩展层插件 | `symbio-plugin-api` | `symbio-kernel` · `symbio-sdk` · `symbio-deploy` · `symbio-host` · `symbio` · 兄弟插件 | HS-001：源码与 manifest 出现被禁前缀即红 |
| 控制面插件（`loop` / `session`） | `symbio-kernel` · `symbio-sdk` · `symbio-plugin-api` | 兄弟插件 · `symbio-host` · `symbio` | 同上 + [DE-026](026-能力拆分与影响类.md "DE-026-能力拆分与影响类") 的影响类 |
| `symbio-host` | `symbio-kernel` · `symbio-sdk` · `symbio-plugin-api` · `symbio-providers` | 任何插件实现（运行期经能力收集取回） | 宿主不认识环的类型 |
| `symbio-deploy` | 无内部依赖 | 一切 | 零依赖生成物 |
| `symbio` | 全部（只做链接与装配） | — | 插件 crate 的 `pub use` 由生成器投影 |
| 插件 ↔ 插件 | 只经 `parent.route(ctx.set(PATH, ROUTE_X))` | `use` 对方任何符号 | [D-042](002-架构总览.md "DE-002-架构总览") + E-009 |

**"依赖"在这里的含义是"类型定义与机制入口"**——所有 crate 都可以依赖**事件与 View 的类型定义**
（这是共享契约，住在内核），除此之外彼此不依赖。这正是「契约从边上挪到中心」。

> **`Projection` 的强制方式**：**泛型形状约束**（见 [DE-001 §1.4](001-核心架构.md "DE-001-核心架构")）——
> `Projection::new` 的签名只接受 `Fn(&[E], Timestamp, Budget) -> View<V>`，
> 于是「体内偷偷读 `Store`」写不出来，编译不过，符合 J3。
>
> ⚠️ **不要把它说成「私有构造」**：`Projection::new` 是 `pub fn`，`f` 字段私有；
> 强制力来自**泛型边界**（拿到 `Store` 的闭包不满足 `Fn` 签名），不是可见性。
> 说错了会让后来者以为可见性在承重（去把 `new` 改成私有的那天，真正承重的泛型
> 边界反而没人看了）。

### 3.2 两类依赖如何被杜绝

| 类型 | 若发生会怎样 | 为什么不会发生 |
|---|---|---|
| **代码依赖**（插件 A 调插件 B） | 出现调用环、改一处动多处 | 扩展层插件只认门面；跨插件调用只能 `parent.route(...)`，拿不到对方句柄 |
| **类型依赖**（投影 A 读投影 B 的输出） | 投影层层嵌套，无法平铺测试 | 投影构造器的签名是 `Fn(&[E], ...)`——**只能读日志，拿不到另一个投影** |

> **这两条是"零耦合"的技术实现**。注意它们不是靠"约定不要这样写"，
> 而是靠**签名与 manifest 白名单让错误写法编译不过**（J3：静默失效 → 编译期强制）。

### 3.3 `symbio-sdk::adapters` 的依赖注入：按时延档位分级（事前闸门）

**时延闸门（[DE-001 §4.1](001-核心架构.md "DE-001-核心架构")）不是新机制，就是机制层的注入策略。**
`symbio-sdk` 的 `adapters` 域按档位签发零大小能力令牌，并**只注入该档位允许的依赖**：

| 档位 | 注入的依赖 | 令牌 | 拿不到的 |
|---|---|---|---|
| 反射 | `RuleEngine` | `RuleOnly` | `Classifier`、`LlmClient`（**类型上就没有方法可调**） |
| 快速 | `Classifier` | `ClassifyOnly`（`CanClassify`） | `LlmClient`（不满足 `CanGenerate`） |
| 深度 / 自主 | `LlmClient` + 工具 | `FullModel`（`CanGenerate`） | — |

**为什么放在 `adapters`**：它是"一切副作用只在这里"的域，
"能不能碰模型"本质是"能不能拿到外部资源句柄"——**归属这里**。
这样一来，"反射层不得调模型"不需要 actor 自律，也不需要治理层事后检查：
**调用方拿不到句柄，因为它没被注入。**

**零运行时开销**：令牌是 ZST，`size_of == 0`；`assemble` 是一个 `match`，
编译期静态分派。实测见 `verify/latency_gate.rs`。

### 3.4 `symbio-kernel` 的判据：语法类型 + 冻结机制原语

判据不是「没有一行实现」（它与 253 个 `pub fn` 相反），而是正向清单，见
本文关键决策 `D-398`：

| 半边 | 判什么 | 强制方式 |
|---|---|---|
| 可执行 | 内核文件集的生产代码出现 `PLUGIN.yml` 的 **owner**（`session/main`）或**能力名**（`judge.intent`）完整字面量 | **CS-010**（`arch-shape-audit`）；正例在 `arch-shape-audit.test.mjs`。既有覆盖面：CS-004 / CS-005 / CS-008 / CS-001 / CS-009 |
| 人工审 | 每新增 `pub fn` / `pub trait` / 模块，审三件事：① 词汇归哪一类（地址语法 / 协议词汇，还是能力名 / owner 名 / 业务概念名）；② 参数与返回是否只碰通用形状（`EventEnvelope` / `PluginInvokeRequest` / `Value`）；③ 默认体里有没有策略 | 写进改动的那次提交；分类表见 D-398——`chat/principal.rs` 的主体名与端口名常量属**地址语法**（允许项），不记为例外 |

四处常被问到的「实现」逐条裁决（`MemoryStore` / `capability_invoke` / `exec` /
`present`·`detail`）与行数实测在 `D-398` 的「逐条裁决」表，
结论均为**合规**（都属于「冻结机制原语」或「语法类型 + 冻结求解器」）。

## 4. 可替换性与替换判据

| 对象 | 能不能换 | 判据 |
|---|---|---|
| `symbio-kernel` 的语法 | **不能** | 换语法 = 改冻结面（F1–F6），不是"替换实现" |
| `Store` 的实现（`memory` / `wal`） | 能 | 实现替换不构成架构改动：调用方只依赖 `Store` trait |
| `symbio-sdk` 的机制 | 能，但不得新增语法 | 换实现后内核零改动；新增词汇走声明表 |
| `symbio-plugin-api` 的白名单 | 只许收窄 | `plugin-surface-audit` 的棘轮：变宽即红 |
| 单个扩展层插件 | 能（可卸载） | 卸掉后系统仍完整运行；`loop` / `session` 的会话通道仍可用 |
| `symbio-host` / `symbio` | 能 | 换装配方不改任何插件；换宿主不改环的类型 |

**并行开发的前提**仍是那三条：`Store` 契约先冻结、事件格式先冻结、接口用 mock 顶替。
共享契约稳定 = 可以并行；**契约不稳，拆成多少 crate 都不能并行**。

**加一个能力的判据**：建 crate + 写 `PLUGIN.yml` + 声明自己的端口 / 行 / 工具；`symbio-kernel` /
`symbio-sdk` / `symbio-plugin-api` / 控制面插件的 diff 为 0。这条判据由 `plugins/*` 的
装配与表面审计执行，不靠人记。

## 5. crate × 四条不变量：谁应该被判违规

> **开发调试的核心问题：出了违规，该去哪个 crate / 层找？**
> 下表是"违规判定归属"——每个部分负责守哪条线。这是 CI 断言分派到责任人的依据。

<!-- list:invariants owner -->

| | I1 单通道 | I2 无溯源不声明 | I3 到点必答 | 授权成对 |
|---|:-:|:-:|:-:|:-:|
| `symbio-kernel` | **`seq` 单调** | 信封存 `produced_by` | — | — |
| `symbio-sdk` | — | 投影传递溯源 | 超预算标 `degraded` | **读写成对**（判定与闸门） |
| `symbio-plugin-api` | — | 效果草稿带溯源 | `text` 预算按声明切分 | **端口校验** |
| `symbio-host` | **每会话一次驱动** | 外部结果当事实记 | 超时返错不外抛 | 不绕过授权 |
| 插件层 | 不直接写别的主体 | **产出即带溯源** | **预算内产出** | 不越权调用 |
| `symbio`（装配） | — | — | — | — |

**读法**：任一条不变量被违反，故障必然落在这张表某个格子里。
例如"静默超时"→ `symbio-host` 或 `symbio-sdk`；"投影漂移"→ sdk 的投影域；
"重复 final"→ kernel 的 `seq` 或 sdk 的仲裁。

## 6. 三条容易踩的坑

1. **把 `adapters` 的副作用泄露到投影**。投影里调 LLM 会让回放漂移——
 签名（无 `Clock`、无外部句柄）**能让它编译不过**，但前提是别给投影加上"便捷的"外部参数。
2. **把 `symbio-plugin-api` 做成转发中转**。它的每一条白名单都要能报出一个真实消费方；
 一旦它开始"帮插件调宿主"，它就从门面变成第二套实现层。
3. **用机制面去付实现面的账**。内核形状与门面白名单都是只许收窄的棘轮；
 实现困难时该改实现或发起架构讨论，而不是把机制放宽一行。

## 7. 与 DE-001 的对应关系（防两套说法）

| DE-001 说的是 | 本文件说的是 |
|---|---|
| 只有 1 个原语 `Store` | `symbio-kernel` 的 `Store` trait 是唯一不可替换的契约 |
| 投影是签名约束不是机制 | 构造器在 kernel，投影函数随 owner（sdk 或插件） |
| Actor 是一等概念不是原语 | actor 策略在 `symbio-sdk`，能力包在插件层 |
| 机制表恒定 | crate 的**职责边界**稳定；增长的是插件与声明行 |

> **一句话对齐**：01 管"不许加机制"，本文件管"代码放哪个 crate"。两者共用同一份契约（事件格式 + 类型定义）。

## 关键决策

> 本节是**仍然约束现行代码的取舍**：每条一句决策、一句理由。已退场或主题已消失的决策不在其中（`git log` 是历史）。

### D-039 session 按域重组：一域一目录，编排层与领域层分离

DE-002 把 `session` 的规模债判为「带触发条件的延后」，并写明命中触发条件时应由新决策取代、而非直接删除。现三条同时成立：①「改 A 必须同时改 B」的跨文件连锁确已出现，根因是 `session` 内部职责混杂；②单次改动的 diff 大到无法被人完整审阅——若干文件同时装着几类互不相干的职责；③各部分职责的归属与作用域能明确说清，下放不再需要「先切再看」。

### D-398 `kernel` 的判据换成正向清单：语法类型 + 冻结机制原语

`kernel` 旧的判据是「没有一行实现」，它与代码相反：`crates/symbio-kernel` 的 **253 个
`pub fn`** 里，`MemoryStore`、`capability_invoke`、`exec`、`present` 都是可读的实现，不是
类型声明。**判据与代码相反时没有第三种后果**——读者要么把它当口号，要么把合法实现当
违规；两条路都让判据停止工作（`D-280` 的同一病灶：不红的判据等于不存在）。

判据因此换成**正向清单**（它判「在不在名单里」，不判「有没有代码」）：

> `kernel` 只含**语法类型**（形状 / 闭集 / 线格式常量）与**冻结机制原语**
> （信封解包、出口与中止、存储基线、表单求解器——逐条登记，增一条要一次 D 级裁决）；
> 里面的字符串只有**地址语法**与**协议词汇**，没有**业务坐标**。

#### 什么是地址语法、什么是业务坐标（分类判据，不是例外清单）

判据按**词的种类**分，不按「今天恰好出现了哪几个」分——例外会攒，分类不会。

| 允许（内核本来就要说清「怎么寻址、字段叫什么」） | 不允许（认了它就是把业务写进语法） |
|---|---|
| **地址语法**：主语与寻址约定——`session/{name}` 的模板、`person/local`、裸 `user` 别名、端口名（`tool` / `model` / `notify`） | **能力名**：`judge.intent`、`reply`、`produce.artifact` 这一类「某条能力叫什么」 |
| **协议字段名**：`port` / `kind` / `payload` / `idempotency_key` 这类信封与载荷的键 | **owner 名**：`session/main`、`vdfs/write` 这一类「某条事实归谁」的完整体 |
| **信封字段名**：`event_id` / `seq` / `assign_seq` / request-key 常量 | **业务概念名**：某个业务实体的专名（`Entity` 闭集之外的） |

分界线的判法：**这句话是「地址怎么写」还是「谁叫什么」**。`session/{name}` 是在说
「主语地址的形状」，换一个角色名它照样成立；`session/main` 是在说「`main` 这个主体」，
换一个部署就要改内核。端口名的判法同理——端口名是寻址坐标（`tool` 指向「工具这一类提供者」），
不是某条能力或某个 owner 的名字；它与插件 id 同集时另受 CS-004 管，不同集时也只受本条约束。

#### 可执行的那一半

- **CS-010**：内核文件集的生产代码里出现 `PLUGIN.yml` `principal_*` 行的 **owner**
  （`session/main`、`vdfs/write`…）或**能力名**（`judge.intent`…）的**完整字面量** ⇒ 红。
  名单从各插件 `PLUGIN.yml` 现读，加插件不加判据；一条 `principal_*` 都读不到 ⇒ 报「不适用」
  （夹具仓库），不是「扫 0 条 = 全绿」。用例五条（能力名红 / owner 红 / 注释与裸子串不红 /
  只量内核文件集 / 无声明即「不适用」）在 `arch-shape-audit.test.mjs`。
- 既有覆盖面：**CS-004**（插件 id 字面量棘轮）、**CS-005 / CS-008**（业务事件常量与事件名
  字面量归零）、**CS-001 / CS-009**（trait / `fn` / 默认体 / 字段与变体只许降）。
- **这一半的缝隙必须写出来**：字面量能拼出来（`concat!` / 常量拼接）能绕过 CS-010；
  它判的是「内核**直接**写了一个业务坐标」，不是「内核不可能拿到业务坐标」。所以它
  是必要条件，不是充分条件——充分条件由下面那一半补。

#### 人工审的那一半（新增内核 `pub fn` / `pub trait` / 模块时逐条过）

1. **词汇归哪一类**：它引入的每个字符串，按上面那张表落在「地址语法 / 协议词汇」还是
   「能力名 / owner 名 / 业务概念名」？判不准时问一句「换个部署、加条能力，这行要不要改」——
   要改就是业务坐标。
2. **依赖形状**：它的参数与返回是否只碰 `EventEnvelope` / `PluginInvokeRequest` / `Value`
   这类通用形状，而不读任何 `EventDecl` / `PLUGIN.yml` 的**具体值**？
3. **默认体**：默认实现里有没有策略（挑选、优先级、回落）？策略归 `symbio-sdk` 与宿主，
   内核只留「唯一正确做法」与「做不了」。

`crates/symbio-kernel/src/chat/principal.rs:207/213/216` 的 `session/{name}` / `person/local` /
`user` 按这张表是**地址语法**（允许项），不是例外；CS-010 判不到它们不是判据的缝隙，
是它们本来就不在该判的对象里。**业务概念名**那一路由 CS-005 / CS-008 判（事件常量与事件名
字面量归零），不重复计。

#### 四处「实现」的逐条裁决

|---|---|---|---|---|

**登记义务**：这条判据的可执行半边是 CS-010，人工半边是上面三条。新增第 N 个「冻结机制原语」

### D-399 `plugin-api` 自有实现的行数只许降：冻结成棘轮，不靠散文

`plugin-api` 是扩展层的契约面：插件作者读它、实现它，机制与运行时都在它后面。它的
「自有实现」（`effects` / `port` / `text` / `context` / `reports`）一旦长回去，扩展层的
读者就多了一份与契约无关的机制代码，而这件事此前只有一句散文——散文拦不住逐行添加。

判据落成一条棘轮：`scripts/baselines/plugin-api-loc.json` 记下五个文件的行数与全 crate
生产行数合计，**超一行即红**（`FA-001`）；行数下降也必须同批下调基线（`FA-002`），否则
「删 N 行再加 N 行」能把棘轮抹平。**测试代码不计**（`*.test.rs` / `tests.rs` /
`#[cfg(test)] mod` 由 `isTestFile` 统一排除），文件内的空行与注释照算——契约面的文档
注释也是读者要读的那部分。每个数字都带能打开的 `adr`（`FA-003`）；范围读不出退 2
（`FA-004`），不许把「读不出」当成「0 行 ⇒ 通过」。基线文件自身受 `35-baseline` 的棘轮
元守卫（`facade-loc` 那一项）——把某个数字改大同样红，否则改基线就是唯一的绕过口。

初始读数：`effects` 562 / `port` 589 / `text` 314 / `context` 355 / `reports` 344，
合计 **4,921** 行（crate 内 21 个生产文件）。实测口径与回归用例见
`scripts/facade-loc-audit.mjs` 与 `scripts/facade-loc-audit.test.mjs`。

**为什么不做成「每个文件各自钉死」**：另外 16 个文件是契约类型（`Event` / `PluginMeta` /
`DriveKey` 这类），它们的行数随契约演进，钉死会把「加一个字段」也变成人工裁决；合计是
那一层的上限，五个自有实现文件是逐项的上限——前者防总量长，后者防「总量不变、实现搬家」。

### D-400 `settled` 是查询口，不是状态：状态与等待体在 `symbio-host`，装配层只解析入口

`DriveEntry::settled` 的语义是「等本会话空闲」，它需要 `running` / `dirty` / `in_flight`
三个位与一个唤醒句柄。这些住在 `HostDrive` 的 `KickState`（`crates/symbio-host/src/drive.rs`），
装配层不持有任何一份。

判据两条，都可机械核验：

1. **谁持有 `KickState`，谁才是回答「还能不能推进」的地方。** 装配 crate 内出现
   `AtomicBool` / `Notify` / 按会话索引的表，就是第二份状态；`symbio-host` 之外出现
   `is_settled` / `wait_idle` 的实现体，同理。
2. **门面只做「解析入口 + 转发」。** `declared_drive_entry()` 是装配选择；
   `HostDrive` 的 `settled`（`DriveEntry` 实现）→ `wait_idle` 是等待体。查询口可以住在
   任一层的门面上，但读到的必须是第 1 条那个唯一状态。

现状：`symbio::drive::settled` 是 `symbio_host::drive::settled` 的再导出，装配 crate 的
`[dependencies]` 不再有 `tokio` / `serde_json`——唤醒句柄与安全阀载荷都随状态搬走了。
判据用例：`crates/symbio/src/drive.test.rs` 的 `settled_port_resolves_the_registered_entry`
（空闲即返回，证明解析的是登记入口）+ 宿主侧 `settled_waits_for_idle` /
`settled_does_not_wake_while_a_port_is_in_flight`（等的是 `KickState`，且在飞不放行）。

### D-405 删模块是交接判据，不是删文件：提交正文回答「旧调用点 → 新等价物」

删一个模块（尤其是删旧编排）时，被删掉的不只是函数体，还有它**调用了哪些校验 / 裁剪 /
判据**。这些入口多数是 `pub`：调用点没了以后 `cargo` 不报、设计文档照引、所有门禁照绿，
而判据已经不再运行。端口装配判重（`capability_port_check`）与上下文段裁剪
（`fit_sections`）就是这样在删旧编排时静默失效的——函数还在门面上，只是再没有人调它。

裁决两条：

1. **删模块的提交正文回答固定一问**：这个模块当时调用了哪些「校验 / 裁剪 / 判据」入口
   （逐条列出符号），新路径的等价物在哪（符号 + 文件），或说明「该判据已并入 X」。
   没有等价物时只许两种动作：同批接线（并补判据用例），或登记进
   `scripts/baselines/arch-dead-code.json`（`why` 落 `待裁`）并在任务卡里写到期日。
   固定问答形态：

   ```
   Removed-Calls: <旧符号> → <新符号 @ 文件> | 已删除：<为什么此判据不再需要> | 待裁：<基线条目 + 期限>
   ```

2. **机械面由 `arch-dead-code-audit`（`AD-001…004`）判，不靠自觉**：`AD-001` 在**删调用点
   的那一批**就会红（符号变零调用且不在基线）；`AD-002` 拦住「删了不撤基线」留下的余量；
   `AD-003` 要求 `why` 与可打开的 `evidence`。回放是这条纪律的验收方式——差集就是必须
   逐条回答的清单：

   ```bash
   node scripts/arch-dead-code-audit.mjs --at=<删前提交>
   node scripts/arch-dead-code-audit.mjs --at=<删后提交>
   ```

**为什么放在本文件**：这条纪律的对象是模块边界（谁在调谁、判据住在哪一层），而本文件是
这一层事实的 owner；提交正文只是它的载体。

### D-408 `effects` / `behaviors` 整块归机制臂：契约与注册表不能分居

`plugin-api` 的收窄清单里写着「`effects::apply` 迁 `sdk`、`api` 只转出」（总账在
[DE-025](025-能力包与扩展面.md "DE-025-能力包与扩展面") 的 `D-399`），隐含前提是「契约留在
`plugin-api`、实现搬到 `sdk`」。这条前提在 `effects` 上**不成立**——不是有人偷懒，是三条
硬事实叠在一起：

1. `handlers()` 遍历的是 `inventory::iter::<BehaviorDecl>()`。`BehaviorDecl` 是
   `inventory::collect!` 的采集类型，那个 `Collect` 实现在**定义类型的那棵树**生成；
   跨 crate 遍历要求先能**命名**这个类型。
2. 能命名它就必然依赖它所在的 crate。而 `symbio-sdk` 的依赖面判据是「只有内核」
   （`D-258`，`crates/symbio-sdk/Cargo.toml` 的注释就是这条判据本身）。方向是
   `plugin-api → sdk`，反过来不存在。
3. `BehaviorDecl` 的字段是 `&'static dyn ToolBehavior`；`ToolBehavior::kind()` 返回
   `behaviors::Kind`；`apply` 收 `&EffectCall`；`EffectCall` 由 `EffectInput` +
   `EffectEnv` 补齐。trait、`Kind`、草稿类型、注册表是**同一个类型闭包**，拆不开。

于是「留在 `api` 的那一半」不可能是契约：留下的只能是完整类型闭包，搬得走的只能是空壳。
**裁决：整块搬。**

- `effects.rs`（562 行）与 `behaviors.rs`（87 行）连同测试整块住在
  `crates/symbio-sdk/src/plugin/`（`effects.rs` / `behaviors.rs`）。
- `submit_behavior!` 宏随注册表搬走（它要 `$crate::effects::BehaviorDecl` 与
  `$crate::inventory`，而这两样都住 `sdk` 了），`plugin-api` 用一行 `pub use` 把它转出；
  插件侧写法 `symbio_plugin_api::submit_behavior!(X)` 不变（E-009：扩展插件只依赖门面一条边）。
- **归属理由**：`effects` 是**机制**——注册表、按 owner 定序、按声明选实现、写口求值时机。
  契约是**声明面**：`PLUGIN.yml` 的行、`EventDecl`、端口行。`ToolBehavior` 是实现这套机制的
  扩展点，它不带任何业务词（`Kind` 只有两格）。按 `D-255`，门面有两臂——语法臂来自 kernel，
  机制臂来自 sdk：`effects` 属于机制臂，此前是放错了树。

**不做什么**：不给它造「契约副本 + 实现副本」的分居形状（两份同名类型正是 `D-280` 修过的病）；
不把 `inventory` 换成运行时注册表（`D-363`：没有第二份清单可漂移）；不为搬迁顺手加面
（净零搬迁，`D-404`）。

**判据**：`FA-001` 的 `effects` 一栏从 562 掉到十几行、门面合计同批下调（`FA-002`）；
`arch-dead-code` 里 `effects` 相关条目的 `path` 随搬迁改址，存量条数不变（`AD-002`）；
`Migration:` + `from` / `to` 齐备且机制面净零 ⇒ 记 `relocation`（不记欠账、不抵账）。
**搬迁不产生迁移的量**：它换的是「机制住在哪一层」，不是「少了一条能力」——把它记成迁移
等于让门面缩水冒充能力拆分。

> **一处基线随之抬升，记在这里免得后来者以为是凭空放宽**：`CS-009` 只扫 `sdk` + `kernel`，
> 这些枚举此前住 `plugin-api`（不在扫描面），整块搬进来后 `enumVariants` 从 236 涨到 244。
> 搬的是同一份类型闭包、地址变了而已，故按 `CS-002` 抬到实测值（不留余量），依据就是本节。
> **宏与模块名都在门面根上转出**：`submit_behavior!` 与注册表模块一起搬进 sdk 后，
> 门面写 `pub use symbio_sdk::submit_behavior;`。宏、模块名与普通符号同一把尺子记进
> SDK 臂（HS-002）——它们都是门面对插件的承诺。`D-413` 把各模块的转出统一到根之后，
> 计件口径见那一节的判据。

### D-417 插件链接行改成私有 `use … as _;`：链接不是出口

  `pub use symbio_plugin_api::{hooks, routes};`；生成块（当前 32 行）只做私有链接。
- 插件 crate 一个都不删：漏一行链接的后果仍是 `inventory` 注册项被链接器丢掉

**判据与读数（同批）**：

### D-419 `symbio-sdk` 的同名模块只留自己的实现：内核词汇不留第二条路径

`D-277` 把 sdk 根上的 `pub use symbio_kernel::*` 收成了私有 `use`，但各**域模块**仍

### D-434 死码台账「待裁」六条逐条裁决：删掉第二个转换器，三个构造/查询口归契约面

`AD-002` 的台账里挂着六条 `待裁：60cedd50 删旧编排时丢掉最后的调用点，需按新路径接线或删除`。
「待裁」本身是欠账：**留一条没有理由的公开面，等于给下一次新增留一格免费余量**。逐条裁：

- **`FactDraft::into_event` —— 删。** 它不是「暂时没人调」，而是**残留的第二个转换器**：
  写口的 `draft_into_event`（`crates/symbio-sdk/src/plugin/fact_source.rs`）把载荷里的
  `cost_ms` 提进信封（成本台账与 `I3` 只认信封那一列），`into_event` 不提——两条路并存时
  走错一条就静默丢成本，而 `rows.rs` 的模块图恰好指着错的那条（`宿主唯一写口
  ──FactDraft::into_event──▶`）。两处口径合一：
  - 删掉该方法；7 处测试调用点（`effects.test` / `settle.test` / `memory` 的语义召回 /
    `task` 的三处效果落格）改走 `draft_into_event`——测试从此覆盖**真实写口**，
    而不是一条只在测试里活着的捷径；
  - 修 `rows.rs` 模块图与 `settle.rs` 的 rustdoc 链接（原来都指向已删的方法，后者是会断的
    文档内链）；`DE-026` 的 `D-252` 正文同步改成「草稿 → 入库事件的唯一转换是写口」。
- **`port_of` —— 留，改记为查询口。** 「按名取一行端口声明」是声明表的读法，
  `None` 表示漏声明而不是默认值。环的那几处不调它是对的：装配判据问的是**存在性**
  （`ports().iter().any(|p| p.port == …)`），拿整行去判存在反而绕；取声明的是执行侧的端口
  实现。留它是因为换掉不会少一个概念，只会让下一个读声明表的人再写一遍 `iter().find`。
- **`with_cost_ms` / `with_status` —— 留，改记为构造口。** 它们与同一类型上已按契约面保留的
  `with_kind` / `with_size` / `with_children` / `with_search` 是同一族：信封 / 节点格的链式
  写法。生产调用点选择直接写字段（`draft_into_event` 里提 `cost_ms`、插件节点投影里
  `n.status = …`），那是调用点的口味，不是这两个口该退场的理由——**判据要的是「有没有人在用
  这个形状」，不是「每个字段都得走一次 builder」**。

**判据**：`arch-dead-code` 的零调用条数与基线同批下调 54 → 53（`AD-002`，只许降）；
三条改记性质的条目在 `why` 里写清「谁在用、为什么留着、决策号」；`symbio-kernel` /
`symbio-sdk` / `symbio-plugin-memory` / `symbio-plugin-task` 的用例全绿。

**不做什么**：不为「保留」而保留（`into_event` 就是被这条否掉的：它和写口抢同一个转换，
留着必然有人走错）；不把 `with_*` 一族整体删掉换成公开字段赋值（那是另一种一次性大改，
且插件侧已经在按链式读）；不新增「死码台账条目到期日」这类机制——条目该不该留由裁决回答，
一周后自动变绿只会把问题推给时间。
