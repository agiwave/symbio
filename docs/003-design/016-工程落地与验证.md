# 工程落地与验证

> 回答三个问题：**什么被冻结** · **凭什么相信它撑得住** · **什么没有被证明**。

---

## 1. 冻结契约：6 个锚点，1 条元规则

> 冻结契约容易膨胀成一份长长的规则清单。按 J1 检验，真正需要冻结的不是若干条独立规则，
> 而是**同一条元规则在几个位置的锚点**。

**元规则（唯一）**：

> **元素数不随场景数增长。** 被冻结的 6 个位置，就是"元素数"这个量的定义域。

| 锚点 | 被冻结的东西 | 修改它 = |
|---|---|---|
| **F1** | `Store` trait 签名（`append` / `range` / `head`） | 架构变更 |
| **F2** | `Projection` 的**构造形状**（唯一入口 `new`；形参无 `&Store` / 无 `&mut` / 无 `Clock` / 无 `Principal`；`now` 是参数；返回 `View` 非 `Result`） | 架构变更 |
| **F3** | `ActorSpec` 字段集（5 个）+ **档位→令牌映射**（反射 `RuleOnly` / 快速 `ClassifyOnly` / 深度 `FullModel`） | 架构变更 |
| **F4** | 三条不变量 I1 / I2 / I3 | 架构变更 |
| **F5** | 三个封闭集合：动词 5 个、能力 7 个、模式 3 个 | 架构变更 |
| **F6** | 参数表键集（11 个，见 [DE-001 §8](001-核心架构.md "DE-001-核心架构")） | 架构变更 |

**不属于上表的任何变化都是数据变化**，不算架构变更：加事件格子、加投影、加 ActorSpec 行、加 grants 行、加 Principal。

> **F2 的措辞已强化**：从"签名形状"改为"**构造形状**"。
> 差别在于前者只是一种约定（你可以不遵守），后者是**唯一入口的泛型约束**（不遵守就编译不过）。
> 这是 J3 在冻结契约上的直接体现——**能被绕过的"约束"不该进冻结契约**。
>
> **F3 新增了档位→令牌映射**：它是"时延闸门"（[DE-001 §4.1](001-核心架构.md "DE-001-核心架构")）落进冻结契约的部分。
> 把它冻住的意义：**"反射档拿不到模型"是由类型保证的，不能在某次重构里被悄悄放宽**。
> 若哪天有人给 `RuleOnly` 加上 `CanClassify`，F3 的 CI 断言立刻红。

## 2. 四层判层：新需求来了先判层

| 层 | 含义 | 例子 | 是否重构 |
|---|---|---|:-:|
| **L-data** | 加数据 | 新 `Principal`、新 grants 行、新实体格子 | 否 |
| **L-grid** | 加网格格子（已有实体 × 已有动词） | `memory.recalled` | 否 |
| **L-schema** | 加新实体 / 新动词 / 新参数键 | 加 `commitment` 实体 | 否（但需决策登记） |
| **L-mechanism** | 修改 F1–F6 | 给 `Store` 加 `update` | **是** |

**判层方法**：从上往下试，第一个能装下的层就是它的层。装到 L-mechanism 才需要重开架构讨论。

### 2.1 平凡值强制（J2 的可执行形式）

> 一条关键的工程纪律：**零 LLM 全链路彩排**——先用 4 个 Stub 跑通完整事件序列，再逐个换成真实现。
> 本方案把它从"阶段一的一个步骤"提升为**通用纪律**。

**每个新参数必须给出平凡值，且平凡值下系统必须完整运行。**

| 参数 | 平凡值 | 平凡值下会发生什么 |
|---|---|---|
| `actor.pattern` | `decider` | 全规则驱动，无 LLM 也能跑完整链路 |
| `actor.capability` | 空集 | 该主体只写非权威事件 |
| `actor.budget_ms` | `60000` | 全部走深度层，慢但正确 |
| `scope` | `root` | 无子智能体，单主体 |
| `vis_scope` | `thread_private` | 无跨主体共享 |
| `projection` | 仅 `eval` | 只有评测视图 |

**这就是"分阶段不改架构"的技术前提**：Event Log 的 schema 从第一天起就是终态，
后续阶段只是让某些事件从"恒等策略下的默认产出"变成"真实策略下的正常产出"——**没有任何数据迁移**。

> 推论（退化特例归零）：代码里不出现 `if (children.length === 1)`、
> `if (depends_on.length === 0)` 这类分支——**空集与单元素是一等输入，不是特例**。

## 3. 决策流程

> ### 前置闸门（本节最重要的一条）
>
> **任何"为了某个场景而修改 F1–F6"的提议，默认视为架构本身的缺陷信号**——
> 它说明先前的抽象没有覆盖住这类需求，而不是这个场景太特殊。为场景改架构，正是"架构没想清楚"的证据。
>
> 所以动架构之前**必须先做第 0 步**：
>
> **0. 先找同构的既有模式。** 系统里是否已经存在解决同一类问题的机制？
> v2 的抽象层很少——正因为少，同类问题的解法会反复出现。
> 只有当"已有模式确实不够用"被写清楚之后，才有资格讨论改架构。
>
> **实例**：S10（个人认知体系）最初判断需要扩展 `store` 的值域以支持"入库过滤"。
> 复核后发现它与 DE-001 §9.3 的**遗忘是同一个模式**（排除而非删除），
> 归入 `recall` 的过滤参数即可，**零架构改动**。详见 [DE-040-个人认知体系注入](040-个人认知体系注入.md "DE-040-个人认知体系注入") §5。

需要修改 F1–F6 时：

1. 说明**为什么它不能被表达为参数取值**（必须用 J1 检验过）；
2. 说明**旧数据如何迁移**（若无迁移方案，说明为什么不需要）；
3. 同步更新 CI 断言与 `verify/` 程序；
4. 记录**推翻条件**——什么新证据出现时这条决策应当被撤销。

## 4. 守恒律：唯一可自动审计的"不重构"保证

> "将来不会重构"是一个**承诺**，无法证明。可以证明的是更弱但有用的命题：
> **机制数不随场景数增长。**

`verify/mechanism_growth.rs` 实测（路线图 13 阶 §3 的赋值 + 20 个自造压力场景）：

```
机制表（01 §8 生成，顶层键）：10 项；§8 登记的键（含子键）：11 项
路线图各阶 §3 的赋值越界键：0 个
自造场景数：20 越界键（需要新机制的）：0 个

场景 1 个 → 用到机制 5 种
场景 5 个 → 用到机制 5 种
场景 10 个 → 用到机制 8 种
场景 20 个 → 用到机制 9 种
```

机制表本身不在程序里手填——它由 `scripts/gen-verify-facts.mjs` 从 DE-001 §8 生成（[第 5.3 节](#53-数据的外置与生成)）。

**读法**：增长的是"启用了哪些已有参数"，不是"发明了多少机制"。
第 21 个场景来了，**照样要重跑这个程序**——它不保证未来，只保证"到目前为止每一次扩展都是通过参数完成的"。

## 5. 验证纪律与实测

### 5.1 五条纪律

> 架构文档里的"验证程序"有四种典型的自欺方式。以下四条纪律逐条对应。

| # | 纪律 | 它拦住的反模式 |
|---|---|---|
| 1 | 每条声称对应一条可执行断言 | 零断言的程序不可能失败：9 个程序只有 1 条断言时，"全部通过"是空的 |
| 2 | 断言的**输入不得包含结论** | 把结论写成常量再断言常量：例如把"是否会增长"硬编码成 `false`，再断言它不增长 |
| 3 | 每条断言配**反向用例**（改输入，结论必须变） | 硬编码返回值（如直接 `return (2, ...)`）：改任何输入，结论都不变 |
| 4 | **声称"编译期强制"的，必须附一段已知编译不过的代码** | "强制"没有反向用例时，无法区分"真的强制"与"恰好没写错"——第 3 条在编译期的镜像 |
| 5 | **编译期反例必须写在外部模块里** | 私有字段**同模块内可访问**；反例写错位置会"编译通过"，于是"必须失败"变成假话 |

**第 4 条的落地形式**（`verify/projection_purity.rs` / `verify/latency_gate.rs` / `verify/conation_minimal.rs`）：

```rust
#[cfg(feature = "should_not_compile")]
mod must_fail { /* 故意编译不过的代码 */ }
```

```
# 期望非 0 退出（-o 不要用 /dev/null，Windows MSVC 链接器需要真实路径）
rustc --edition 2021 --check-cfg 'cfg(feature)' \
 --cfg 'feature="should_not_compile"' <file>.rs -o should_fail.exe
```

实测错误恰为纯净性 / 档位 / 闸门违规（`E0593` arity 不符、`E0277` trait 不满足、
`E0308` 类型不符、`E0451` 私有字段、`E0061` 参数不足），
**而不是被无关约束顺手挡掉**——反向用例必须为正确的原因失败。

> **第 5 条是本轮新增的**（`conation_minimal.rs` 暴露）：把 `CandidateIntent.approved`
> 的伪造用例写在主模块里时，它**编译通过**了——因为同模块可访问私有字段。
> 修正后（放进 `mod outsider { ... }`）才得到正确的 `E0451`。
> 这条纪律的意义：**"必须失败"的用例，本身也要有一个反向用例来证明它会失败。**

### 5.3 数据的外置与生成

**判据在程序里，数据在文档里。** `verify/` 各程序吃的计划数据——机制表、13 阶的赋值向量与
退路口、能力名册与它的三处声明——都不是程序里的手填常量，而由 `scripts/gen-verify-facts.mjs`
从权威表生成 `verify/facts/mod.rs`（生成物，不手改），程序 `mod facts;` 消费：

| 生成物 | owner |
|---|---|
| `MECHANISMS` / `PARAM_KEYS` | [DE-001 §8](001-核心架构.md "DE-001-核心架构") 的权威参数表；顶层键与子键按**形状**分（含 `.` 且首段已登记 ⇒ 子键） |
| `DIMENSIONS` / `AXES` / `AXIS_POLARITIES` / `LEVEL_MAX` / `KINDS` / `TIER_CORES` / `OVERLAP_LIMIT` / `CAPABILITIES` | [DE-008](008-能力注册表与能力坐标系.md "DE-008-能力注册表与能力坐标系") §2 五维表 · §3 五轴表（末两列是**极性**）· §3.1 刻度表（**列数** = 等级格数）· §3.2 天梯表 · §3.3 共线上限 · §6.1 名册与类型闭集表 |
| `PSEUDO` | 02 §5 伪高阶表的「说法」列 |
| `DECLARED_DIM_COUNTS` / `DECLARED_GROWTH` / `DECLARED_SOCIAL` / `DECLARED_OVERLAP` | DE-008 §2「条数」列 / §6.2 生长位表 / §7 社会性表 / §3.3 超限共线登记 |
| `STAGE_CLAIMS` | [DE-030-能力阶梯总览](030-能力阶梯总览.md "DE-030-能力阶梯总览") 阶梯总表的「新增机制键」「参数变化」两列 |
| `STAGE_DOCS` | 各阶 `S0N-*.md` §3 的 `capability-assign` 赋值块 + §4 里加粗平凡值的那一行 |

三条规矩，都是为了让「改了文档而绿灯照旧」不可能发生：

- **读不出来必须红**：表头改名、块缺失、数字解析不出、退路口加粗行不唯一 ⇒ 生成器抛错，
 绝不返回一张空表（空表会让程序拿着残缺数据照常断言）。
- **声明与数据分家**：总表那一列、DE-008 §2 的条数、§6.2 的生长位都是**被验的结论**，程序从数据算出来
 再对它们——所以文档两处不同步，红的就是程序。
- **生成归门禁自己做**：`gate.d/55-verify.mjs` 先跑生成器（`autoWork`：漂移当场暂存），
 再编译各程序；CI 档存在未提交差异即红。

## 9. 插话：阻塞与恢复流程

> [DE-001 §6](001-核心架构.md "DE-001-核心架构") 有 `control` 实体，[DE-037-插话与实时打断](037-插话与实时打断.md "DE-037-插话与实时打断") 说明它为何不需要新机制。
> 本节给**可照着实现的具体流程**——这是判据推不出来的部分。

### 9.1 判定顺序

```
用户消息到达 → turn/opened
 │
 ▼
抢占判定者（Decider, budget_ms = 80）
 │
 ├── 当前无在跑任务 → 【通过】直接开始新 turn
 ├── 当前任务可中断 → 【挂起】写 task/held，记录 as-of 时间戳 T
 ├── 当前任务不可中断 → 【排队】新 turn 排队，不抢占
 └── 判定超时（>80ms） → 【默认：继续】不挂起
```

> **超时默认"继续"而不是"挂起"**：挂起会留下一个需要恢复的状态，
> 继续不会。两个选择都可能错，但**错的代价不对称**——所以默认选代价小的那个。

> **判据输入的形状本身也是判据**：「任务开启后有过收束发言」比的是 `task.opened`
> **之后**有没有 `chat.assistant.final`。同一轮的收束发言若排在 `task.opened` 之后入格，
> 这条恒成立 ⇒ 判定恒为「排队」，挂起一次都不会发生。所以收束转写必须**先落这一轮
> 说了什么，再落它派生出的承诺 / 任务 / 熔断**（顺序在代码里是判据，不是排版）。

### 9.2 挂起与恢复

| 步骤 | 动作 | 事件 |
|---|---|---|
| 1 | 记录当前 `seq` 为 `T` | — |
| 2 | 写挂起事件 | `task/held`（`task.blocked`） |
| 3 | 被挂起任务从 `readyset` 中消失（投影自动排除，无需额外代码） | — |
| 4 | 处理插话 | `turn/opened` → `turn/closed` |
| 5 | 以 `T` 为 as-of 重放投影，恢复上下文 | — |
| 6 | 写恢复事件 | `task/progressed` |
| 7 | 任务重新进入 `readyset` | — |

**恢复不需要状态迁移代码**——投影是纯函数，给同一个 `T` 就得到同一个视图。
这一步是"投影是纯函数"在工程上最直接的回报。

### 9.3 边界情况

| 情况 | 处理 | 理由 |
|---|---|---|
| final 已发出后到达插话 | **不抢占**，排队为新 turn | 已发出的发言不可撤回 |
| 插话期间又来插话 | 新插话抢占当前插话（后者优先级更高） | 用户最新意图优先 |
| 挂起超过 TTL | 强制释放，写 `closed`，可被重新调度 | 防止永久挂起（J3：静默失效） |
| 挂起期间任务被其他主体完成 | 恢复时检测到终态，直接跳过 | 幂等 |

## 12. 出口判据

与 SP-003 §2 同一口径，三条缺一不可：

1. **单测**：读方**复算**——同一份事件切片，出口的读数与直接 `apply` 逐字相等；
 含**反向用例**（改一个事件 ⇒ 读数必须变）。
2. **e2e**：`node e2e/run-tests.mjs tNN` 绿，从**真实会话目录**的 WAL 读，不是造样本。
3. **门禁**：`node scripts/gate.mjs` 全绿。

> **为什么"复算"是硬要求**：本方案的唯一风险是"出口自己算了一遍，与投影漂移成两份口径"。
> 判据因此必须**同源**：出口只能调**已有的**投影，不得另写一份统计。缺了它，
> 加固等于给同一件事长出了第二个定义（PL-009 §4 的反向用例纪律同源）。

本仓的健壮性面已逐处登记（`panic-audit` 的 PN-001…003），但覆盖率这条相邻的 量化面一直没有判据。后来接下这条延后，并写明处置只有两种：接 `cargo-llvm-cov` 逐 crate 阈值进 `RATCHETS`（floor，只许涨），或者在一条决策里写下 「为什么不划算」——理由不许只存在于任务条目里。

仓里同时存在三组「先做什么」的陈述，而它们回答的不是同一个问题： 阶认知阶梯（[DE-030-能力阶梯总览](030-能力阶梯总览.md "DE-030-能力阶梯总览")）按能力递进排列， 回答「要长这个能力，得先有什么」； 行业前沿参照（[行业前沿参照](../004-ref/011-行业能力前沿参照.md "RE-011-行业能力前沿参照")）按 与行业坐标的差距排列，回答「先补哪一块更值」；

### D-097 抽象层级的离线效标：措辞依赖度 = 原述 − 换述 recall@k，换述集冻结并带指纹锁

「抽象层级」这条轴从「本轴目前只能人工判」改成「离线读数 + 残余人工判」，由三条具体决定支撑： 读数 = 原述 recall@k − 换述 recall@k，叫依赖度（越大越依赖字面）。它由 [`verify/recall_eval.rs`](verify/recall_eval.rs) 打印——池不动，只把 条用例的查询换成同义换述再跑一遍同一个生产排序内核。


### D-135 定稿答话轮的收束格必须带措辞往返的实测 `cost_ms`——成本台账不因「请求是静默的」而漏记整类轮次

### D-142 行尾是判据的**输入前提**：一处默认 + 一条守卫，而不是每个解析器各自补 `\r?`

**现场**（2026-10-24）：`.gitattributes` 声明「仓库与工作树都是 LF」，而实际有 98 个
受版本控制的文本文件在工作树里是 CRLF。`git diff` 对此**一个字符都不显示**——attr 在
diff 时把工作树 CRLF 归一化掉了，于是整仓「看起来干净」。受害的是读取侧：
`route-facts.routeArmDocs` 按 `^\s*\/\/[/!]?\s?(.*)$` 抽「路由臂上方的 `///`」，JS 的 `.`
不吃 `\r`、`$` 又要求行尾对齐，于是 CRLF 文件里整段注释一条都抽不到——能力矩阵里
`compose/wording` 的职责静默变成 `—`，`facts` 测试报「表里没写」。
**守卫红了，报的却是另一件事。**

**结论**：行尾属于**输入的前提**，前提只能有一处判据。`.gitattributes` 给一条默认
`* text=auto eol=lf`（`text=auto` 让 git 自己按内容判二进制，比人工列白名单可靠），
`scripts/eol-audit.mjs` 判三面：工作树带不带 `\r`、声明有没有、入库 blob 有没有。
判据的语料取自 `git ls-files` 与 `git check-attr`——不维护扩展名清单，
因为「清单漏了新类型」正是要拦的东西之一（实测 70 个文本文件在旧清单之外）。

**否决的三个替代**：

① **在每个按行解析的正则里补 `\r?`**。每个解析器各持一份「行尾无关」的口径，而那份
口径没人复核：今天补了三个正则，明天新写的第四个照样踩。更糟的是它把「输入带 CRLF」
从**可观测的违规**降级成「静默容忍」——读取器永远不会说出真相，报错永远落在下游。
与 `SP-013`「锚必须是版本化的地址」同型：把环境的默认值变成被检查的事实，而不是让
每处代码各自猜。

② **判据只判「已知会被解析的」类型**（`.md` / `.mjs` / `.rs`）。清单的失效形态是
新类型没人加，而 `*.tsx` / `*.yml` / `*.json` 一样会被 `readFile` + 按行切分读。
按类型判等于把「哪些文件会被读」事先钉死，而这件事本身是变化的。

③ **靠 `core.autocrlf=false` 让检出保持 LF**。那是**本机配置**不是仓的事实：换一台
机器、换 CI 就不成立，且不可核对（`git config` 不在版本库里）。这正是
`.gitattributes` 存在的理由——同一类「本机默认值冒充仓的约定」在 D-013（盘符路径）
里已经付过一次代价。

**边界**（写在这里免得被当成保证）：二进制按内容判（前 8KB 有 `NUL` 即不判），
二进制文件没有「行尾」这个概念；工作树缺文件（子模块、未检出）时三条都判不出来——
那是「判不了」，不是「通过」，判据不因此转绿也不因此转红。

**收口读数**：清零后 `git add -A` 的内容差异为 **0**——index 本来就是 LF，
漂移只发生在工作树，这正是它不被任何 diff 发现的原因。

判据：`scripts/eol-audit.mjs`（EOL-001 工作树 / EOL-002 声明 / EOL-003 入库）与
`scripts/eol-audit.test.mjs`（三条各一条反向用例：CRLF 工作树、无声明、
先提交后声明造出的 CRLF blob）。

### D-143 「对拍」的寿命等于两个实现并存的窗口——窗口关闭后判据换成结构面 + 行为面

[DE-090-过渡方案](090-过渡方案.md "DE-090-过渡方案") §1.1 给步 1 / 2 / 3 的收口判据都写着**对拍**：「全量 / 增量投影随机切点对拍」、
「事实网格 + Step 序列逐格比对」。这两条今天**不可能核对**，而原因不是没人做：

- 步 5 删掉 v1 外壳之后，对拍的**另一方不存在**了——`Step` 枚举与 `run_with_tools` 的
  生产实现都已退场（前者整个消失，后者只剩 `.test.rs` 里的一具壳）；
- 投影本身收敛成了纯函数（`projection::apply`，`scripts` 侧无状态），「增量投影」这个
  对象在目标形状里也不存在——没有第二个实现可以逐格比。

判据照旧写着，那几格就会永远停在「无法核对」，而「已收口」与「判据失效」在报告上
长得一模一样。故改判为两条，各自可复跑：

- **结构面**：行表逐行用例（`cargo test -p symbio --lib loop_rows::tests`，51 条，
  覆盖每行的 `owes` / `until` / 装载期缺口 / 全局裁决序）+ 投影重建的确定性与落库形状
  复刻（`cargo test -p symbio --lib projection::rebuild::tests`，28 条）；
- **行为面**：e2e 全量（`node scripts/gate.mjs --only=e2e`）。

否决的三个替代：① **把 v1 路径留成测试专用开关以维持对拍**——测试里养一份死实现，
等于把删掉的代码变成永久负债，而且它会自己腐烂（`run_with_tools` 现在只剩 `.test.rs`
里的一具壳，已经没有人知道它算不算「旧路径」）；② **保留「对拍」字样但注明「历史判据」**
——读者会以为它还能跑，这正是 D-142 那条「判不了的判据不许亮绿灯」的反面；
③ **只留 e2e**——行为面绿不等于每一格都对，删掉结构面就没人管「这一行为什么现在欠」。

判据的适用范围写在这里：**对拍只在两个实现并存的迁移窗口里成立**，窗口一关就要么改判、
要么删掉，不许挂着。


### D-154 规范执行方覆盖率先定「合法的人工理由」再计数——机器判据 / 人工理由 / 缺失三分

GO-003 E3 要的是「每条活跃规范都指得出执行方」，但「执行方」一直靠评审认。
现在判据是 `scripts/spec-coverage-audit.mjs`（SPC-001…003）：

- 逐条读 `docs/005-spec/` 下的规范文档的 `## 判据` 小节；小节里引用的 `scripts/**` 脚本
  或已登记的判据码都算**机器执行方**；
- 显式写 `无机器判据：<理由>` 算**人工执行方**，理由须是非空且成句（≥ 8 个非空白字符）——
  没有理由的「无机器判据」等于「不想写」，判红；
- 两者都没有 = **缺失**，判红；活跃规范逐条必须落进前两类，人工类数量进基线只降不升。

口径本身也判：`SPC-003` 要求条目数与 `## 判据` 解析结果自洽、编号不重复——
否则「27 条全覆盖」可能只是扫描漏读。

**否决**：把「无机器判据」直接当绿——那会让豁免变成默认，覆盖率越高越说明没人写判据。

### D-155 注入矩阵是「注入种类 × 能力面」的逐格归属，不是用例清单

E2 的缺口不是「没有异常用例」，而是**覆盖面不可盘点**。矩阵的唯一数据源是
`e2e/injection-matrix.mjs`（12 种注入 × 4 个能力面 = 48 格），每格三选一：

- `cases`：用例编号，必须真实存在于 `e2e/cases/tNN-*.mjs` 且代码里真用了该场景字段；
- `na`：该面不适用，写清理由；
- `gap`：已登记缺口，必须挂一个能打开的 owner（任务或设计条目）并写理由。

`scripts/injection-matrix-audit.mjs`（INJ-001…003）双向判：夹具里的字段在用例侧
必须被认领（反向扫描，注释不算），矩阵里写的字段必须在 mock 里真的存在。
生成物是 `docs/004-ref/012-注入矩阵.md`（`stamp: false`，纯函数渲染）。

当前 48 格 = 用例 12 · 不适用 33 · 已登记缺口 3；三个缺口都是 MCP 侧的
disconnect / initialize 失败 / 工具延迟，统一挂 DE-039 的接线阶段——
**缺口是登记过的，不是没发现**。

### D-156 「一个前端分支」按两条同构轴计数，框架格恒为 0

GO-002 T4 的「框架零类型分支」原先没有口径。现在定义为
`scripts/kind-branch-audit.mjs`（KB-001 / KB-002），两条轴同构计数：

| 轴 | 比较 | 派生判据 | 映射表 |
|---|---|---|---|
| 形态 | `NODE_KIND_*` | `nodeKindOf` / `messageTypeOf` | `Record<NodeKind, …>` |
| 资源类型 | `VDFS_EXT_*` / `VDFS_KIND_*` | `vdfsExtOf` / `resolveVdfsRenderer` / `renderer*` 变量 | `Record<…, VdfsRenderer>` |

渲染器字面量（`'form'` / `'session'` / `'message'` …）直接比较也计一格——它就是
资源分派写死在框架里的样子。`f.widget === 'form'`、`specOf(f).tag === 'form'` 属于
表单控件轴，排除。

分两格：`registry`（机制层，判据与映射表允许存在，进基线只降不升）与
`framework`（组件 / store / service / composable / view，**恒为 0**）。
框架要认资源类型，只能在 `registry/` 加具名谓词（`isFormRenderer` / `isSessionNode` /
`isMessagesSeg` / `isInboxSeg`）再从调用方引用——「新增一类资源 = 一份配置 + 一个渲染器 +
一条导航注册」由此变成可数的事实。

**否决**：只数 `NodeKind`——资源分派（renderer / ext / kind）才是业务渗进三栏框架的主要通道，
漏掉它，框架格可以在「零 kind 分支」的绿灯下继续长类型分支。
