# 工程落地与验证

> 回答三个问题：**什么被冻结** · **凭什么相信它撑得住** · **什么没有被证明**。

---

## 1. 冻结契约：6 个锚点，1 条元规则

> 冻结契约容易膨胀成一份长长的规则清单。按 J1 检验，真正需要冻结的不是若干条独立规则，
> 而是**同一条元规则在几个位置的锚点**。

**元规则（唯一）**：

> **元素数不随场景数增长。** 被冻结的 6 个位置，就是"元素数"这个量的定义域。

| 锚点 | 被冻结的东西 | 修改它 = |
|---|---|---|
| **F1** | `Store` trait 签名（`append` / `range` / `head`） | 架构变更 |
| **F2** | `Projection` 的**构造形状**（唯一入口 `new`；形参无 `&Store` / 无 `&mut` / 无 `Clock` / 无 `Principal`；`now` 是参数；返回 `View` 非 `Result`） | 架构变更 |
| **F3** | `ActorSpec` 字段集（5 个）——**档位→令牌映射**已随 `D-438` 退役（见 `018-模块架构 §3.3` 的缺口登记） | 架构变更 |
| **F4** | 三条不变量 I1 / I2 / I3 | 架构变更 |
| **F5** | 三个封闭集合：动词 5 个、能力 7 个、模式 3 个 | 架构变更 |
| **F6** | 参数表键集（11 个，见 [DE-001 §8](001-核心架构.md "DE-001-核心架构")） | 架构变更 |

**不属于上表的任何变化都是数据变化**，不算架构变更：加事件格子、加投影、加 ActorSpec 行、加 grants 行、加 Principal。

> **F2 的措辞已强化**：从"签名形状"改为"**构造形状**"。
> 差别在于前者只是一种约定（你可以不遵守），后者是**唯一入口的泛型约束**（不遵守就编译不过）。
> 这是 J3 在冻结契约上的直接体现——**能被绕过的"约束"不该进冻结契约**。
>
> **F3 的档位→令牌映射已退役（`D-438`）**：它的载体 `LlmAdapter` 在模型往返改走 `port.model` 后没有生产实现，`sdk::adapters` 整块退场；**"反射档拿不到模型"今天没有执行面**（缺口见 `018-模块架构 §3.3`），冻结面只剩 `ActorSpec` 五个字段。

## 2. 四层判层：新需求来了先判层

| 层 | 含义 | 例子 | 是否重构 |
|---|---|---|:-:|
| **L-data** | 加数据 | 新 `Principal`、新 grants 行、新实体格子 | 否 |
| **L-grid** | 加网格格子（已有实体 × 已有动词） | `memory.recalled` | 否 |
| **L-schema** | 加新实体 / 新动词 / 新参数键 | 加 `commitment` 实体 | 否（但需决策登记） |
| **L-mechanism** | 修改 F1–F6 | 给 `Store` 加 `update` | **是** |

**判层方法**：从上往下试，第一个能装下的层就是它的层。装到 L-mechanism 才需要重开架构讨论。

### 2.1 平凡值强制（J2 的可执行形式）

> 一条关键的工程纪律：**零 LLM 全链路彩排**——先用 4 个 Stub 跑通完整事件序列，再逐个换成真实现。
> 本方案把它从施工步骤提升为**通用纪律**。

**每个新参数必须给出平凡值，且平凡值下系统必须完整运行。**

| 参数 | 平凡值 | 平凡值下会发生什么 |
|---|---|---|
| `actor.pattern` | `decider` | 全规则驱动，无 LLM 也能跑完整链路 |
| `actor.capability` | 空集 | 该主体只写非权威事件 |
| `actor.budget_ms` | `60000` | 全部走深度层，慢但正确 |
| `scope` | `root` | 无子智能体，单主体 |
| `vis_scope` | `thread_private` | 无跨主体共享 |
| `projection` | 仅 `eval` | 只有评测视图 |

**这就是"分阶段不改架构"的技术前提**：Event Log 的 schema 从第一天起就是终态，
后续阶段只是让某些事件从"恒等策略下的默认产出"变成"真实策略下的正常产出"——**没有任何数据迁移**。

> 推论（退化特例归零）：代码里不出现 `if (children.length === 1)`、
> `if (depends_on.length === 0)` 这类分支——**空集与单元素是一等输入，不是特例**。

## 3. 决策流程

> ### 前置闸门（本节最重要的一条）
>
> **任何"为了某个场景而修改 F1–F6"的提议，默认视为架构本身的缺陷信号**——
> 它说明先前的抽象没有覆盖住这类需求，而不是这个场景太特殊。为场景改架构，正是"架构没想清楚"的证据。
>
> 所以动架构之前**必须先做第 0 步**：
>
> **0. 先找同构的既有模式。** 系统里是否已经存在解决同一类问题的机制？
> v2 的抽象层很少——正因为少，同类问题的解法会反复出现。
> 只有当"已有模式确实不够用"被写清楚之后，才有资格讨论改架构。
>
> **实例**：S10（个人认知体系）最初判断需要扩展 `store` 的值域以支持"入库过滤"。
> 复核后发现它与 DE-001 §9.3 的**遗忘是同一个模式**（排除而非删除），
> 归入 `recall` 的过滤参数即可，**零架构改动**。详见 [DE-040-个人认知体系注入](040-个人认知体系注入.md "DE-040-个人认知体系注入") §5。

需要修改 F1–F6 时：

1. 说明**为什么它不能被表达为参数取值**（必须用 J1 检验过）；
2. 说明**旧数据如何迁移**（若无迁移方案，说明为什么不需要）；
3. 同步更新 CI 断言与 `verify/` 程序；
4. 记录**推翻条件**——什么新证据出现时这条决策应当被撤销。

## 4. 守恒律：唯一可自动审计的"不重构"保证

> "将来不会重构"是一个**承诺**，无法证明。可以证明的是更弱但有用的命题：
> **机制数不随场景数增长。**

`verify/mechanism_growth.rs` 实测（路线图 13 阶 §3 的赋值 + 20 个自造压力场景）：

```
机制表（DE-001 §8 生成，顶层键）：10 项；§8 登记的键（含子键）：11 项
路线图各阶 §3 的赋值越界键：0 个
自造场景数：20 越界键（需要新机制的）：0 个

场景 1 个 → 用到机制 5 种
场景 5 个 → 用到机制 5 种
场景 10 个 → 用到机制 8 种
场景 20 个 → 用到机制 9 种
```

机制表本身不在程序里手填——它由 `scripts/gen-verify-facts.mjs` 从 DE-001 §8 生成（[第 5.3 节](#53-数据的外置与生成)）。

**读法**：增长的是"启用了哪些已有参数"，不是"发明了多少机制"。
第 21 个场景来了，**照样要重跑这个程序**——它不保证未来，只保证"到目前为止每一次扩展都是通过参数完成的"。

## 5. 验证纪律与实测

### 5.1 五条纪律

> 架构文档里的"验证程序"有四种典型的自欺方式。以下四条纪律逐条对应。

| # | 纪律 | 它拦住的反模式 |
|---|---|---|
| 1 | 每条声称对应一条可执行断言 | 零断言的程序不可能失败：9 个程序只有 1 条断言时，"全部通过"是空的 |
| 2 | 断言的**输入不得包含结论** | 把结论写成常量再断言常量：例如把"是否会增长"硬编码成 `false`，再断言它不增长 |
| 3 | 每条断言配**反向用例**（改输入，结论必须变） | 硬编码返回值（如直接 `return (2, ...)`）：改任何输入，结论都不变 |
| 4 | **声称"编译期强制"的，必须附一段已知编译不过的代码** | "强制"没有反向用例时，无法区分"真的强制"与"恰好没写错"——第 3 条在编译期的镜像 |
| 5 | **编译期反例必须写在外部模块里** | 私有字段**同模块内可访问**；反例写错位置会"编译通过"，于是"必须失败"变成假话 |

**第 4 条的落地形式**（`verify/projection_purity.rs` / `verify/latency_gate.rs` / `verify/conation_minimal.rs`）：

```rust
#[cfg(feature = "should_not_compile")]
mod must_fail { /* 故意编译不过的代码 */ }
```

```
# 期望非 0 退出（-o 不要用 /dev/null，Windows MSVC 链接器需要真实路径）
rustc --edition 2021 --check-cfg 'cfg(feature)' \
 --cfg 'feature="should_not_compile"' <file>.rs -o should_fail.exe
```

实测错误恰为纯净性 / 档位 / 闸门违规（`E0593` arity 不符、`E0277` trait 不满足、
`E0308` 类型不符、`E0451` 私有字段、`E0061` 参数不足），
**而不是被无关约束顺手挡掉**——反向用例必须为正确的原因失败。

> **第 5 条是本轮新增的**（`conation_minimal.rs` 暴露）：把 `CandidateIntent.approved`
> 的伪造用例写在主模块里时，它**编译通过**了——因为同模块可访问私有字段。
> 修正后（放进 `mod outsider { ... }`）才得到正确的 `E0451`。
> 这条纪律的意义：**"必须失败"的用例，本身也要有一个反向用例来证明它会失败。**

### 5.3 数据的外置与生成

**判据在程序里，数据在文档里。** `verify/` 各程序吃的计划数据——机制表、13 阶的赋值向量与
退路口、能力名册与它的三处声明——都不是程序里的手填常量，而由 `scripts/gen-verify-facts.mjs`
从权威表生成 `verify/facts/mod.rs`（生成物，不手改），程序 `mod facts;` 消费：

| 生成物 | owner |
|---|---|
| `MECHANISMS` / `PARAM_KEYS` | [DE-001 §8](001-核心架构.md "DE-001-核心架构") 的权威参数表；顶层键与子键按**形状**分（含 `.` 且首段已登记 ⇒ 子键） |
| `DIMENSIONS` / `AXES` / `AXIS_POLARITIES` / `LEVEL_MAX` / `KINDS` / `TIER_CORES` / `OVERLAP_LIMIT` / `CAPABILITIES` | [DE-008](008-能力注册表与能力坐标系.md "DE-008-能力注册表与能力坐标系") §2 五维表 · §3 五轴表（末两列是**极性**）· §3.1 刻度表（**列数** = 等级格数）· §3.2 天梯表 · §3.3 共线上限 · §6.1 名册与类型闭集表 |
| `PSEUDO` | DE-008 §5 伪高阶表的「说法」列 |
| `DECLARED_DIM_COUNTS` / `DECLARED_GROWTH` / `DECLARED_SOCIAL` / `DECLARED_OVERLAP` | DE-008 §2「条数」列 / §6.2 生长位表 / §7 社会性表 / §3.3 超限共线登记 |
| `STAGE_CLAIMS` | [DE-030-能力阶梯总览](030-能力阶梯总览.md "DE-030-能力阶梯总览") 阶梯总表的「新增机制键」「参数变化」两列 |
| `STAGE_DOCS` | 各阶 `S0N-*.md` §3 的 `capability-assign` 赋值块 + §4 里加粗平凡值的那一行 |

三条规矩，都是为了让「改了文档而绿灯照旧」不可能发生：

- **读不出来必须红**：表头改名、块缺失、数字解析不出、退路口加粗行不唯一 ⇒ 生成器抛错，
 绝不返回一张空表（空表会让程序拿着残缺数据照常断言）。
- **声明与数据分家**：总表那一列、DE-008 §2 的条数、§6.2 的生长位都是**被验的结论**，程序从数据算出来
 再对它们——所以文档两处不同步，红的就是程序。
- **生成归门禁自己做**：`gate.d/55-verify.mjs` 先跑生成器（`autoWork`：漂移当场暂存），
 再编译各程序；CI 档存在未提交差异即红。

## 9. 插话：阻塞与恢复流程

> [DE-001 §6](001-核心架构.md "DE-001-核心架构") 有 `control` 实体，[DE-037-插话与实时打断](037-插话与实时打断.md "DE-037-插话与实时打断") 说明它为何不需要新机制。
> 本节给**可照着实现的具体流程**——这是判据推不出来的部分。

### 9.1 判定顺序

```
用户消息到达 → turn/opened
 │
 ▼
抢占判定者（Decider, budget_ms = 80）
 │
 ├── 当前无在跑任务 → 【通过】直接开始新 turn
 ├── 当前任务可中断 → 【挂起】写 task/held，记录 as-of 时间戳 T
 ├── 当前任务不可中断 → 【排队】新 turn 排队，不抢占
 └── 判定超时（>80ms） → 【默认：继续】不挂起
```

> **超时默认"继续"而不是"挂起"**：挂起会留下一个需要恢复的状态，
> 继续不会。两个选择都可能错，但**错的代价不对称**——所以默认选代价小的那个。

> **判据输入的形状本身也是判据**：「任务开启后有过收束发言」比的是 `task.opened`
> **之后**有没有 `chat.assistant.final`。同一轮的收束发言若排在 `task.opened` 之后入格，
> 这条恒成立 ⇒ 判定恒为「排队」，挂起一次都不会发生。所以收束转写必须**先落这一轮
> 说了什么，再落它派生出的承诺 / 任务 / 熔断**（顺序在代码里是判据，不是排版）。

### 9.2 挂起与恢复

| 步骤 | 动作 | 事件 |
|---|---|---|
| 1 | 记录当前 `seq` 为 `T` | — |
| 2 | 写挂起事件 | `task/held`（`task.blocked`） |
| 3 | 被挂起任务从 `readyset` 中消失（投影自动排除，无需额外代码） | — |
| 4 | 处理插话 | `turn/opened` → `turn/closed` |
| 5 | 以 `T` 为 as-of 重放投影，恢复上下文 | — |
| 6 | 写恢复事件 | `task/progressed` |
| 7 | 任务重新进入 `readyset` | — |

**恢复不需要状态迁移代码**——投影是纯函数，给同一个 `T` 就得到同一个视图。
这一步是"投影是纯函数"在工程上最直接的回报。

### 9.3 边界情况

| 情况 | 处理 | 理由 |
|---|---|---|
| final 已发出后到达插话 | **不抢占**，排队为新 turn | 已发出的发言不可撤回 |
| 插话期间又来插话 | 新插话抢占当前插话（后者优先级更高） | 用户最新意图优先 |
| 挂起超过 TTL | 强制释放，写 `closed`，可被重新调度 | 防止永久挂起（J3：静默失效） |
| 挂起期间任务被其他主体完成 | 恢复时检测到终态，直接跳过 | 幂等 |

## 12. 出口判据

与 SP-003 §2 同一口径，三条缺一不可：

1. **单测**：读方**复算**——同一份事件切片，出口的读数与直接 `apply` 逐字相等；
 含**反向用例**（改一个事件 ⇒ 读数必须变）。
2. **e2e**：`node e2e/run-tests.mjs tNN` 绿，从**真实会话目录**的 WAL 读，不是造样本。
3. **门禁**：`node scripts/gate.mjs` 全绿。

> **为什么"复算"是硬要求**：本方案的唯一风险是"出口自己算了一遍，与投影漂移成两份口径"。
> 判据因此必须**同源**：出口只能调**已有的**投影，不得另写一份统计。缺了它，
> 加固等于给同一件事长出了第二个定义（反向用例纪律同源）。

## 关键决策

> 本节是**仍然约束现行代码的取舍**：每条一句决策、一句理由。已退场或主题已消失的决策不在其中（`git log` 是历史）。

### D-044 实测与判据同源：成本 / 时延 / 兜底率是事件网格一等数据

SLO 的三列实测口径全部从事件网格统计，不设任何旁路计数器： 埋点在**执行体边界**——`port.model` 的 `ModelExecutor` 实测耗时并写进事实的 `cost_ms`（`D-438` 之前挂在 `LlmAdapter::generate_timed` 上，那个 trait 已退场；`RoundOutput` 这类产物形状本身随 `D-439` 退回插件，不再是架构层词汇），实测值由调用方写进 `chat.assistant.final` 的 `cost_ms`；`cost.ledger`（名册 #18 的声明视图，住在成本能力包）从事件切片累计，熔断判据（`CircuitBreaker` 的「已耗多少」） 读台账，不读运行时计数器；

### D-058 「跑过真实会话」的落地形态 = 门内有界压测，判据读生产出口——换基边界由此归出一条纪律三个出口

[13 终点第 3 条](../archive/13-质量改进总纲.md)要求「`full` 是出厂路径，且被真实负载压过——不是『跑过 e2e』，是『跑过真实会话』」（登记条目待立项）。D-057 补上了形状记录，但它自己明说不回答「压过之后还成立吗」。

### D-060 覆盖率阈值不进门禁：不做逐 crate 的 `cargo-llvm-cov` floor，理由与重开条件写在这里

本仓的健壮性面已逐处登记（`panic-audit` 的 PN-001…003），但覆盖率这条相邻的量化面一直没有判据。这条量化面后来被接下，并写明处置只有两种：接 `cargo-llvm-cov` 逐 crate 阈值进 `RATCHETS`（floor，只许涨），或者在一条决策里写下「为什么不划算」——理由不许只存在于任务条目里。

### D-090 三套序各有唯一 owner：依赖序是硬约束、价值序是权重、施工序只在可行域内

仓里同时存在三组「先做什么」的陈述，而它们回答的不是同一个问题：阶认知阶梯（[DE-030-能力阶梯总览](030-能力阶梯总览.md "DE-030-能力阶梯总览")）按能力递进排列，回答「要长这个能力，得先有什么」；行业前沿参照（[行业前沿参照](../004-ref/011-行业能力前沿参照.md "RE-011-行业能力前沿参照")）按与行业坐标的差距排列，回答「先补哪一块更值」；任务册（[docs/007-task](../007-task/README.md "T-000-任务汇总")）按「现在能开工的」排列，回答「下一刀切在哪」。

三套序因此各有唯一 owner，任何一方都不许改写另一方：

| 序 | owner | 它是什么 | 它不是什么 |
|---|---|---|---|
| 依赖序 | 任务条目头的 `deps` | 硬约束：`deps` 未闭环时开工即错，「对方交给我什么」必须答得具体 | 不是排期建议，不是对借用面的转述 |
| 价值序 | `prio` + `track` | 权重：同等可行时先补哪块更值 | 不是先做什么 |
| 施工序 | 实际提交先后（`git log`） | 可行域内的一个解，随时可变 | 不是依赖，不回写 `deps` |

**反例（2026-10-28 实测）**：任务册里「在途可观测」与「环表合一」两条一度被判成
「借用面互逆」——后者的 `deps` 写着前者，而前者又认定「必须等后者先把 `Ctx` 立起来」，
因为 in-flight 槽要求 `TurnSession<'a>` 带生命周期参数，而 `ActorEntry` 是
`for<'a> fn(&'a mut TurnStep) -> StepFuture<'a>` 的 HRTB，`for<'a>` 无法对两个生命周期
全量化。两边各写一条「先等对方」，就成了自我循环的一对。

实测的答案是：**这条互逆根本不成立**。出路不是给草稿加生命周期参数，而是把 `TurnStep` 的
端口全部 owned 化（`Arc<dyn Store>` / `Arc<dyn LlmAdapter>` / `Arc<dyn DeltaSink>` /
`FullModel` 加 `Copy`）——借用消灭之后 future 是 `'static`，`for<'a>` 只需对一个生命周期
成立，「在途可观测」于是独立做完、单独提交，一天之内闭环。

**所以错的是把「Rust 借用事实」当成了「调度依赖」**（与 `D-222` 删掉第四台 host 的理由
同源：类型系统的约束是实现的约束，不是任务的约束）。借用面挡住的从来不是「谁先做」，
而是「怎么切」——它属于施工序，不属于 `deps`。

反过来的边界也要写清：**真依赖有两类，都必须留在 `deps` 里。**

1. **对方的产物是本任务的输入接口**。「幕按裁决退场」要等环表落地才谈得上「按裁决退场」；
   「环表合一」等「在途可观测」是因为合表之后 `await-*` 这批行不必再拆一次。
2. **复用对方定下的口径**。「工具端口的在途可观测」这一类边属于其中：它直接复用
   `waiting` / `open_calls` / `model_open` 三处口径，三处改一处则另一处必须跟着改。这类边
   在对方闭环、口径已在主干上时就地摘掉——**摘掉不等于它不是真依赖**，只是「前置」这件事
   在对方闭环之后不再由任务册表达。它与第 1 类**不是同一类依赖**，别照「环表合一」的旧例
   再判一次互逆。

**判据**：`deps` 里每一条都要能回答「对方交给我的**具体产物或口径**是什么」。答不出的，
就是施工序被误写成了依赖序，删掉即可；若两条 `deps` 互相指向，先查这条是不是借用面
造的假依赖——把端口 owned 化之后再判一次，通常就不互逆了。

### D-097 抽象层级的离线效标：措辞依赖度 = 原述 − 换述 recall@k，换述集冻结并带指纹锁

「抽象层级」这条轴从「本轴目前只能人工判」改成「离线读数 + 残余人工判」，由三条具体决定支撑：读数 = 原述 recall@k − 换述 recall@k，叫依赖度（越大越依赖字面）。它由 [`verify/recall_eval.rs`](verify/recall_eval.rs) 打印——池不动，只把 33 条用例的查询换成同义换述再跑一遍同一个生产排序内核。


### D-135 定稿答话轮的收束格必须带措辞往返的实测 `cost_ms`——成本台账不因「请求是静默的」而漏记整类轮次

`classify` 判 `Answered` 的轮不进驱动循环，本轮唯一的模型往返发生在
`compose/wording` 里。此前 `execute_final_reply_turn` 落收束格时把 `cost_ms`
硬写成 `0`：内部请求不写事件是对的（D-044：台账只读落格事件），但这次往返的
代价属于**这一轮的收束格**，不随事件回来，`cost.ledger` 与 SLO 的分子分母就会
系统性少掉整类 `Answered` 轮次。

取值链固定为一条：`port.model` 的执行体实测（`ModelExecutor` 把 `cost_ms` 写进事实）→ `WordingReply.cost_ms`
→ `TurnInput::final_cost_ms` → `chat.assistant.final.cost_ms`。模板产线与无模型
往返的路径恒 `0`；生成失败退模板时仍记这次失败请求的实测耗时（代价已经发生）。

判据：收束格与 `TurnOutcome` 都带传入的实测值；`WordingReply` 的 `cost_ms` 带
`serde(default)`，仓外调用方不传时为 `0`（向后兼容）。

### D-142 行尾是判据的**输入前提**：一处默认 + 一条守卫，而不是每个解析器各自补 `\r?`

**现场**（2026-10-24）：`.gitattributes` 声明「仓库与工作树都是 LF」，而实际有 98 个
受版本控制的文本文件在工作树里是 CRLF。`git diff` 对此**一个字符都不显示**——attr 在
diff 时把工作树 CRLF 归一化掉了，于是整仓「看起来干净」。受害的是读取侧：
`route-facts.routeArmDocs` 按 `^\s*\/\/[/!]?\s?(.*)$` 抽「路由臂上方的 `///`」，JS 的 `.`
不吃 `\r`、`$` 又要求行尾对齐，于是 CRLF 文件里整段注释一条都抽不到——能力矩阵里
`compose/wording` 的职责静默变成 `—`，`facts` 测试报「表里没写」。
**守卫红了，报的却是另一件事。**

**结论**：行尾属于**输入的前提**，前提只能有一处判据。`.gitattributes` 给一条默认
`* text=auto eol=lf`（`text=auto` 让 git 自己按内容判二进制，比人工列白名单可靠），
`scripts/eol-audit.mjs` 判三面：工作树带不带 `\r`、声明有没有、入库 blob 有没有。
判据的语料取自 `git ls-files` 与 `git check-attr`——不维护扩展名清单，
因为「清单漏了新类型」正是要拦的东西之一（实测 70 个文本文件在旧清单之外）。

**否决的三个替代**：

① **在每个按行解析的正则里补 `\r?`**。每个解析器各持一份「行尾无关」的口径，而那份
口径没人复核：今天补了三个正则，明天新写的第四个照样踩。更糟的是它把「输入带 CRLF」
从**可观测的违规**降级成「静默容忍」——读取器永远不会说出真相，报错永远落在下游。
与 `SP-013`「锚必须是版本化的地址」同型：把环境的默认值变成被检查的事实，而不是让
每处代码各自猜。

② **判据只判「已知会被解析的」类型**（`.md` / `.mjs` / `.rs`）。清单的失效形态是
新类型没人加，而 `*.tsx` / `*.yml` / `*.json` 一样会被 `readFile` + 按行切分读。
按类型判等于把「哪些文件会被读」事先钉死，而这件事本身是变化的。

③ **靠 `core.autocrlf=false` 让检出保持 LF**。那是**本机配置**不是仓的事实：换一台
机器、换 CI 就不成立，且不可核对（`git config` 不在版本库里）。这正是
`.gitattributes` 存在的理由——同一类「本机默认值冒充仓的约定」在 D-013（盘符路径）
里已经付过一次代价。

**边界**（写在这里免得被当成保证）：二进制按内容判（前 8KB 有 `NUL` 即不判），
二进制文件没有「行尾」这个概念；工作树缺文件（子模块、未检出）时三条都判不出来——
那是「判不了」，不是「通过」，判据不因此转绿也不因此转红。

**收口读数**：清零后 `git add -A` 的内容差异为 **0**——index 本来就是 LF，
漂移只发生在工作树，这正是它不被任何 diff 发现的原因。

判据：`scripts/eol-audit.mjs`（EOL-001 工作树 / EOL-002 声明 / EOL-003 入库）与
`scripts/eol-audit.test.mjs`（三条各一条反向用例：CRLF 工作树、无声明、
先提交后声明造出的 CRLF blob）。

### D-143 「对拍」的寿命等于两个实现并存的窗口——窗口关闭后判据换成结构面 + 行为面

迁移期的收口判据原先都写着**对拍**：「全量 / 增量投影随机切点对拍」、

- v1 外壳删掉之后，对拍的**另一方不存在**了——`Step` 枚举与 `run_with_tools` 的

- 投影本身收敛成了纯函数（`projection::apply`，`scripts` 侧无状态），「增量投影」这个
  对象在目标形状里也不存在——没有第二个实现可以逐格比。

判据照旧写着，那几格就会永远停在「无法核对」，而「已收口」与「判据失效」在报告上
长得一模一样。故改判为两条，各自可复跑：

- **结构面**：债行逐行用例（`cargo test -p symbio-plugin-loop --lib ring::`，

- **行为面**：e2e 全量（`node scripts/gate.mjs --only=e2e`）。

否决的三个替代：① **把 v1 路径留成测试专用开关以维持对拍**——测试里养一份死实现，
等于把删掉的代码变成永久负债，而且它会自己腐烂（测试夹具若从生产派发器分叉出来，
就是又一份没人说得清是不是「旧路径」的实现）；② **保留「对拍」字样但注明「历史判据」**

③ **只留 e2e**——行为面绿不等于每一格都对，删掉结构面就没人管「这一行为什么现在欠」。

判据的适用范围写在这里：**对拍只在两个实现并存的迁移窗口里成立**，窗口一关就要么改判、
要么删掉，不许挂着。

### D-234 终态判据的执行方是一个脚本、一张固定的码表，收束格只从一个构造点写出去

`SP-033` 的六条不变量落地时，判据面有三件事必须同时定下来，否则其中任意一件都会在下一批
被「顺手」改坏：

**① 六条不变量 → 八条码，码表是判据集本身。** `scripts/control-plane-audit.mjs` 用 `CP-001`…`CP-008`
分判 `TC-1`（`CP-001` 循环体 / `CP-002` 选债口 / `CP-003` 五道守卫 + 类型守）、`TC-2`（`CP-004` 行名与
执行体名）、`TC-3`（`CP-008` 声明面出口）、`TC-4`（`CP-005` 收束格构造点）、`TC-5`（`CP-006` 机制面
指纹）、`TC-6`（`CP-007` 判据集闭集）。`TC-n` 的条数钉在脚本常量上，`TC_MAP` 必须与规范逐条对上，
每条码只许挂一条不变量——于是「给某个新能力单开一条专用判据」表现为第七条 `TC-n` 或一条重复挂载的
码，两条都判红。**判据条数不随能力数增长**这条元判据，执行方就是这张表。

**② 机制面是字节基线，改它是决策。** `TC-5` 的编排侧那一半此前数不到：冻结求解器字节只保证
「加端口不改引擎」，而「新端口得自带一段循环 / 一台 host」在编排层是看不见的。基线
（`scripts/baselines/control-plane.json`）冻结三段剥注释后的字节——驱动循环体、选债包装 `fn next`、
在途判据 `fn waiting`——并把控制面生产文件数做成只许降的棘轮，同时要求基线挂的那条决策打得开。
冻结**不是不许改**：机制演进照改，但当批要更新基线并写清「这次属于哪一类」。这与 `PTS-003` /
`PTS-004` 是同一套形状，理由也相同——**约束要能追溯到一条决策，否则它只是一个数字**。

**③ 收束格只有一个构造点，声明面的 owner 不变。** `chat.assistant.final` 原先有五条路径各写一遍
（驱动循环的 `close-turn`、零往返轮的轮首、快路、流式完成、中止），`chat.assistant.fallback`
另有三处。它们的差别只在**何时写、载荷写什么**，事实的形状（id `f-{turn}`、`turn × closed`、
溯源指向用户格）该由一处决定。现在两条格各只有一处 `Event::pending`：
`crates/symbio-plugin-session/src/convergence.rs` 的收束路径。**写方身份不在构造点决定**——`actor.principal` 由调用方给，声明面
照旧只有 `ACTOR_CLOSE.writes` 覆盖两格；它回答「谁有权写」，构造点回答「从哪里写出去」。
「多条路径各自写同一格」在事实面上看不出来（每一条都是合法 append），所以这一条只能静态判。

**反向用例与判据同批**（`SP-033` §5 程序 4）：八条码各有一条「故意改坏就红」的夹具
（`scripts/control-plane-audit.test.mjs`）——影子 `loop`、派发器外直问求解器、删一道守卫、
动作签名多一份 `&mut`、内核里写行名、第二处收束格 append、驱动循环改一字节、第七条 `TC-n`、
`seal` 改借用式。没有反向用例的判据分不清「真的在算」与「恰好没写错」。

### D-273 门禁按**变更范围**收窄：阶段声明输入面，范围求不出即全跑，跳过必留 `⊘`

门禁原先没有「本次改了什么」这个概念：12 个阶段、179 项每轮全跑，实测冷缓存 **6m58s**，而这些
阶段的输入里没有 `.md`——「改一句文档」与「改 core 的公开面」付同一个价格，而 `docs(…)` 是本仓
最常见的一类提交（远端 v2 最近 21 个提交里 12 个），所以这不是偶发成本，是日常成本。

**裁决：跑不跑由「这一轮改了什么」决定，不由「门禁总共有哪些项」决定。**

1. **阶段声明输入面**（`needs: ['rust']` 等）：backend / msrv 吃 `rust`，前端两段吃 `frontend`，
   e2e 吃 `rust` + `e2e`；`docs` 的**守卫本体**无条件跑（它们扫的就是真仓），**检查器自己的
   回归测试**吃 `scripts`。
2. **范围求值 fail-open**（`gate.d/_scope.mjs`）：`base...HEAD` ∪ 工作区未提交改动；`base` 取
   `--base=` > `@{upstream}` > `origin/v2` > `origin/main`。任一步读不出来 ⇒ 全跑。**两个方向
   的代价不对称**：多跑一轮是几分钟，少跑一个阶段是假绿。
3. **跳过必须留痕**：汇总里一行 `⊘` 加「未触及哪个面 + 怎么强制全跑」（D-224）。门禁自身有
   **未提交**改动 ⇒ `forceAll`：改门禁的那一次必须按新门禁全跑。

### D-274 rustdoc 阶段**整个废弃**；backend 只留「真跑用例」——超时是不等还是杀，也要判

D-273 之后，改 Rust 的那一轮仍然慢。2026-11-01 在 20 核本机实测（只改

而它只判「文档注释里的链接指向的符号还在不在」。

**裁决：删掉 `gate.d/15-rustdoc.mjs`、`scripts/cargo-doc-gate.mjs` 及其回归测试。**

先前的处置是「判据留着、代价交给内容指纹」。那个处置没有错，是**买不到它想买的东西**：指纹只
覆盖「内容没变而 mtime 变了」那一档，而**改了 core 就必然全树各渲一遍**（插件的文档会 re-export
core 的项）——改 core 是本仓主干的改动形态，不是例外。

**为什么这一条可以废弃、别的守卫不行**——判据是「它守的东西有没有第二个消费者，失效时读文档的
人会不会被误导」：断链的产物是**文档**不是行为；本仓的 rustdoc HTML 没有消费者（真实消费者是
IDE 的 Ctrl+click，读的是源码注释）；rustdoc 早已把解析不了的链接降级成纯文本，于是「断链」在

且没有一轮门禁会发现。需要时手跑：`RUSTDOCFLAGS='-D rustdoc::broken_intra_doc_links
-D rustdoc::invalid_rust_codeblocks' cargo doc --no-deps --workspace`。

**顺带否掉一条看起来白拿的路**：`cargo test --workspace` 本来就收集 doctest，「把两条 lint 挂到
doctest 上等于免费」很有吸引力。**实测不成立**——故意写两条断链后 `cargo test --doc -p
symbio-kernel` 退出码 0、零告警（`rustdoc --test` 只抽代码块，不跑链接解析）。

**同一轮修掉两条「真等墙钟」用例**（43.9s 里 32.4s 是它们）：`unreachable_endpoint_maps_to_
generation_failed` **17.75s → 0.01s**（`start_paused = true`；它断言的是「网络错误 →
`GenerationFailed`」，不是退避曲线，曲线由 `backoff_delay` 单测钉）；`timeout_is_enforced_and_

future，而 `output()` 的读管道在 tokio 阻塞任务上、**丢弃 future 不取消它**，于是报「timed out」
时钩子进程还在跑、还在写文件；`.kill_on_drop(true)` 才是「超时就杀掉」。剩下的 1.79s 是平台

`-n 2 -w 500`，那条约束写在用例注释里，改前先读。

**判据**：`gate.test.mjs` 里「rustdoc 必须存在且标 parallel」两条断言**反转**成
`idx('rustdoc') === -1`（不许悄悄加回来，要加先推翻本条）；同处把「跑 backend 的 job 必须点名
rustdoc」升级成**对全部阶段成立**——`gate.d/*.mjs` 声明的每个 id 都必须在 `ci.yml` 的某个
`--only=` 里出现。

后面，零收益，不做。

### D-275 e2e 的墙钟由「最慢一例」与「它何时开始」决定——三处真等待，两处真排队

D-274 之后 e2e 成了唯一的关键路径（1m40s）。它的成本结构与 backend 不同：不是「某一项太重」，
而是**少数几例在等生产定时器**，加上**排期把慢例放在最后**。实测 88 例：总工作量 310.6s、最慢
单例 65.3s（`t90`）、墙钟 99s，而前 10 例占 72% 的工作量。

| 用例 | 它等的是 | 实测的浪费 | 处置 |
|---|---|---|---|
| `t90` | 心跳调度器的一个 tick | 等完之后又把**同一扇窗**睡一遍（`sleep(firedAt - startedAt) + 5s`，26s） | 只跨过两侧起跑的偏差（3s） |
| `t36` | 两条会话各自的到点格点 | 两个 id 的相位是 21s 与 4s ⇒ 落在**两个不同 tick** | 换成相位 1s / 4s 的 id |
| `t53` | 一次完整的退避阶梯 | 对话面默认开启 ⇒ 分类请求也走同一阶梯、失败后整轮重发 ⇒ 付**两遍** | 钉 `DIALOG_FACE_OFF` |

`t90` 那 22 秒的判据：两侧吃**同一个会话 id**，而到点 = `interval_seconds + phase_ms(id)`，相位
由确定性哈希给出 ⇒ 两侧落在**同一格点**，启用侧一触发就证明停用侧那一格点同样成立。所以在
`firedAt` 之后再睡一遍整个窗口，等于把同一扇窗等两次（余量算术写在用例注释里，前提是
`INTERVAL` 远小于 tick）。`t36` 那一步不是「讨好哈希」：它的头注本来就写着「两会话在**同一个
tick** 各触发一次」，旧 id 的相位 21s/4s 让这个假设**当时就不成立**，只是靠 100s 兜底兜住了。
两处都记了代价——换工具链后 `DefaultHasher` 变 ⇒ 回落成多等一两个 tick，**仍绿，只是慢**。

**两处真排队**：起跑顺序改为按上一轮实测耗时降序（LPT，FIFO 50.7s → 36.8s，一个用例都没少跑）；
并发度改为从实测推导 `min(机器槽位, ⌈总工作量/最慢单例⌉)`——旧默认 6 是「理论最优 ≈ 5.7」算出来
的（当时最慢是 `t36` 的 15.5s），慢例削平后这个数变成 10.7、6 就成了瓶颈。机制与旋钮由
[e2e/README](../../e2e/README.md) 与 `scripts/e2e-order.mjs` 持有，结构上限 `CONCURRENCY_CEILING` 只写一处。

**结果**：88 例 **99s → 20.7s**，工作量 310.6 → 219s，最慢单例 65.3 → 20.4s，并发 11，88/88 通过。

**明确记下现在的下界，以及为什么不再往下压**：`t36` 的 15.4s **就是 tick 本身**（15s 一扫、首
tick 被丢弃），`t53` 的 20.3s 是**一次退避阶梯**（其中 8s 是 Windows：`connect()` 到没人监听的
端口要 2.0s，`std::net` 同步与 tokio 异步都是，而 node 的非阻塞 `connect` 只要 0–2ms）。再往下
只有三条路，都不做：给调度器加 `tick_seconds` 旋钮（把生产不变量变成测试参数）；减少重试次数
（那是用户可见的产品行为）；把两例移出默认门禁（用「看不见」换「跑得快」，正是 D-224 判的
静默消失）。

**判据**：`scripts/e2e-order.test.mjs` 10 条（降序 / `index` 仍是原序号 / 未知按中位数 / 空表
退化 / 稳定性 / 脏数据 / 缓存往返 / 损坏 / 并发度推导 / 无数据回退）；`gate.test.mjs` 那条
「e2e 并发上限」改为钉 `CONCURRENCY_CEILING`（判「上限是结构常量、不随核数涨」）。

### D-295 D-016 的豁免只对「机器读字段」开：默认仍不给豁免

D-016 原本一句「不给豁免」，理由是 task 收口即删 ⇒ 引用必然悬空。这条理由成立的前提是
**引用没有人复核**。当引用所在字段本身就是另一条判据的输入时，前提不成立：那条判据每轮门禁
都会重新解析它（存在性、未收口、可达性），悬空会在**同一次门禁**里变红，不会静默。

因此 D-016 只在**行内档**开豁免（`doc-link-allow D-016: 理由`，本行或前一行，理由不可为空），
且理由必须写明**由哪条判据复核**。散文与源码注释里的指路照旧判红——那里没有机械复核，
任务一删就只剩一个悬空人名。豁免是「引用有复核」的声明，不是「这条引用别管」的声明。

首个采用点是能力账的「移除计划」列（`D-294`）：承接任务由 `EX-006` 每轮校验，计划里不写
任务编号就无法判「谁接棒」。这条豁免的存量以 `doc-link-allow D-016` 的出现为准，新增一处
就要写明它的复核判据。
