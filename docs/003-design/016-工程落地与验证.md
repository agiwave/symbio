# 工程落地与验证

本文回答：什么契约必须稳定、如何证明实现没有破坏它、哪些结论尚未被证明。
不记录迁移步骤、模块归属、测试函数、通过数量或历史基线。结构事实归
[当前事实表](../004-ref/006-当前事实表.md "RE-006-当前事实表")，任务与证据归 task，历史归 `git log`。

## 1. 变更判层

新需求先按表达层次判断，而不是先改机制：

| 层 | 变化 | 处理 |
|---|---|---|
| 数据 | 新主体、授权行、事件实例 | 直接实现 |
| 网格 | 已有实体与动词的新组合 | 扩展声明与测试 |
| 模式 | 新实体、动词或参数键 | 检查既有表达，确认后扩展 |
| 机制 | 原语签名、构造形状、不变量或控制面协议 | 先进行架构讨论 |

修改机制前必须找到同构既有模式，并写清为什么参数、数据和网格确实不足。实现困难、
类型借用或单次场景特殊都不是改变架构的理由。

机制变更必须同时处理旧数据兼容、生产消费方、断言、反向用例和文档 owner。没有迁移
方案时，必须说明为什么无需迁移。

## 2. 平凡值与守恒

每个新参数必须有平凡值，平凡值下系统仍能完整运行。空集、单元素和多元素是同一模型的
合法输入，不得用场景特例替代统一规则。

架构承诺的不是“永不重构”，而是可检验的守恒：场景与能力增长应使用已有参数、事实和
执行体，不线性增加原语、驱动循环或公共门面。新增场景必须重新运行守恒判据；历史通过
不代表未来自动成立。

## 3. 验证纪律

| 纪律 | 要求 |
|---|---|
| 声称可执行 | 每条架构声称至少对应一条可执行断言 |
| 输入独立 | 断言输入不得包含结论，不得把预期写成常量再验证常量 |
| 反向用例 | 改变输入必须改变结论；合法输入不得误报 |
| 编译期强制 | 声称编译不过的代码必须实际编译失败 |
| 失败原因正确 | 编译失败必须来自目标约束，不能碰巧被无关错误挡住 |
| 反例位置正确 | 私有成员反例放在外部模块，避免同模块访问权制造假失败 |
| 非空执行 | 判据读空、阶段零项或执行方缺失不得当作通过 |

提示词、注释和设计愿望不是机器判据。无法机器执行的规范必须显式给出人工执行方式与
理由，并纳入覆盖检查。

## 4. 验证层次

### 4.1 单元与性质测试

优先验证不变量、纯函数、类型边界和局部契约。共享机制必须覆盖其全部消费族，不能只测
一个代表插件。投影需要双跑逐字节比较，并注入一个事件后验证结果确实改变。

### 4.2 端到端测试

端到端必须走真实装配、真实协议入口和真实事实源，不得用测试专用分叉替代生产路径。
注入用例按“注入种类 × 能力面”登记，每格必须是用例、明确不适用或有 owner 的缺口。

实时与时序用例优先使用状态、序号或水位等确定性信号，不用任意 sleep 等待。不得为了
降低墙钟时间放宽时序断言、隐藏用例或把生产不变量变成测试旋钮。

### 4.3 全量门禁

全量门禁验证跨模块接线、生成物一致性、审计回归和完整消费族。局部测试通过不能替代
全量门禁；门禁红灯必须修复，或按豁免机制登记理由、执行方、期限和清除任务。

## 5. 出口判据

一个共享面或读侧出口的完成必须同时满足：

1. **单测同源**：出口读数由既有投影复算，逐项相等，并有反向用例；
2. **端到端真实**：从真实运行与真实事实源读取，不造一份平行统计；
3. **门禁全绿**：生成物、接线、审计和回归均通过。

出口只能消费已有权威投影，不得另写一份统计口径。无法从事实重建的状态不得作为完成
证据。实现状态与文档状态分开：代码可运行不等于规范已完成，规范 active 不等于所有实现
已存在。

## 6. 验证数据与生成

判据放在程序，权威数据放在唯一 owner。验证程序从规范表或声明生成事实，不在程序内
手填第二份常量。

- 读取失败、表头漂移、重复条目或解析为空必须报错；
- 被验结论与源数据分开，程序计算后再对账；
- 生成与验证分离，检查模式只比对，不静默修复后报告通过；
- 生成物不手改，未提交漂移必须判红；
- 自动输出无时间戳、随机顺序或本机路径，保证可复现。

验证面登记至少应说明：

| 字段 | 要求 |
|---|---|
| 验证面 | 稳定的不变量、机制或消费族名称 |
| 判据 | 实际检查的性质，不写通过数量 |
| 执行方 | 生产测试、验证程序或审计脚本 |
| 反向用例 | 哪个输入变化必须使结论变化 |
| 数据 owner | 权威表、代码声明或事实源 |
| 边界 | 该判据没有证明什么 |

具体程序清单、断言数量和历史结果由代码与运行日志提供，不在文档复制。

## 7. 量化与校准

### 7.1 指标

不变量与质量指标必须绑定测量方式、违规动作和用户可见出口：

- 投影确定性与重放一致性；
- 终答唯一性与溯源完整；
- 权限违反与静默超时；
- 检索、巩固和语义漂移质量；
- 时延、成本与回退率。

指标未校准时必须标为设定值，不得写成实测或承诺。校准记录由该指标的唯一 ref owner
保存；本规范只定义测量纪律。

### 7.2 用户可见读数

能力出口不能只证明“测试通过”，还必须能回答“用户看到的什么数变了”。每个出口指标
应有生产读数列、标签、单位、口径和呈现方式。暂时没有读数列的指标必须显式登记为缺口，
不能以单测存在代替用户可见性。

## 8. 门禁机制

### 8.1 清单来自声明

静态审计通过目录发现和脚本自声明分桶，不维护手写执行表。每个脚本必须声明角色，并
提供与角色匹配的回归测试。接线审计双向对账“声明集”和“实际执行集”：

- 声明但未执行必须判红；
- 执行但未声明必须判红；
- 枚举范围过窄、零项执行或空阶段必须判红；
- 允许为空的阶段必须给出具体理由，不能用布尔开关代替。

### 8.2 变更范围

阶段声明自己的输入面。门禁按实际变更范围收窄，但必须满足：

- 无法求出可靠范围时全跑，宁可多跑不可假绿；
- 跳过阶段必须在汇总中可见，并说明未触及的面与强制全跑方式；
- 修改门禁自身时必须按新门禁全跑；
- 检查器回归测试随检查器代码变化执行，不随被检查物任意挑测。

### 8.3 分频

低漂移判据可以降低频率，但必须满足：单次提交不会改变其性质、延迟发现的损失小、仍有
明确执行方和定期对账。不得通过删除声明或改角色让判据静默消失。周档必须能手工触发，
并在活跃分支由全量门禁补位。

### 8.4 成本主张

延迟、并发和缓存优化必须可被一次测量推翻。比较总墙钟、最慢用例、排队和真实执行成本，
不能只报告单步耗时。不得用扩大等待预算、减少用例或放宽断言制造绿灯。

## 9. 基线与棘轮

形状、门面和死码等基线用于阻止公共面悄悄变宽。基线不是事实来源，也不得通过对齐现状
掩盖新增债务。

- 只许收窄的棘轮不放宽；
- 确需变宽时必须证明其属于公共机制，并更新对应断言与文档 owner；
- 存量型账本的新增、上调、指纹变化和删除都必须署名；
- 署名说明变化性质与理由，不使用架构决策编号；
- 无法机械判断的理由由评审执行，并保留反向用例。

## 10. 真实环境验证

真实 provider 和真实负载验证使用显式入口，不混入默认门禁。缺少 provider、服务不可达或
模型未加载时拒绝启动，不回退 mock。

真实运行必须有界，判据读生产出口、事实源和权威转写，不读内部私有状态。mock 探针与
真实服务探针分开：真实环境没有的探测面不得伪装成已验证。

## 11. 诚实边界

验证报告必须区分：

- **可执行证明**：有断言、有反向用例、改变输入会红；
- **有依据的判断**：说明依据和反证现象；
- **开放命题**：说明当前无法封闭；
- **缺口**：有 owner、触发条件和关闭判据。

已关闭缺口不留在活跃缺口表；常驻约束不标记为完成。没有 owner 的状态清单会漂移，
没有反证的“永不重构”只是愿望。

## 12. 依赖与施工序

依赖序、价值序和施工序是不同概念：

- `deps` 只表达前置产物或口径，不表达实现便利；
- `prio` 只在同等可行时排序；
- 实际提交顺序是可行域内的解，不回写依赖；
- 类型借用问题通过调整实现切分解决，不制造任务互逆。

一项结构性改动若需要靠放大补丁掩盖抽象错误，应重新切分，而不是继续堆叠。一个任务
可以分多次提交，回退单位是提交，不是任务或文档批次。
