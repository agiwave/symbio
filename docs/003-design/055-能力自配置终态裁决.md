# 能力自配置终态裁决

> **一句话**：配置归谁，与什么时候读它，是两件事。真源随能力包走，交付放在开轮
> 收集期，决策仍只读那一条快照事实——`session` 因此不必认识任何能力名。

本篇承载「配置随能力包走」这一格的终态裁决与作废旧判定清单。目标判据见
[DE-002](002-架构总览.md "DE-002-架构总览")，扩展面闭表见
[DE-025](025-能力包与扩展面.md "DE-025-能力包与扩展面")，作废协议见
[DE-047](047-义务环判据与归属推导.md "DE-047-义务环判据与归属推导") §3。

### D-427 能力配置的真源在能力包：快照由能力贡献，宿主只收集

**背景**：`DE-002` 把「新能力只碰自己的包，`core` / `kernel` / `loop` / `session`
diff = 0」写成硬判据，`DE-025` 开头把「配置随能力包走」写成一句话。配置这一格至今
没兑现：`SessionConfig` 代管 `classify_enabled` / `compose_enabled` / `opening_enabled` /
`progress_*` / `task_cap` / `skill_compile_enabled` / `conation_enabled` 等一整片能力开关，
`plugin/turn.rs` 又把它们硬编码投影成 `session.config`，甚至为了算 `compose_enabled`
去债表按 `PLUGIN_ID_COMPOSE` 查插件在场。于是「加一个开关」要改会话的配置结构、
默认函数、表单项、投影行，可能还要加一条按名判断——T1 不成立，`session` 认识能力名。

挡在这条路上的不是机制缺口，是两条旧判定：`D-252` 第 2 条把「让能力自带配置面」列为
被否（理由「生效时刻会漂」），`D-379` ① 把快照钉成 `SessionConfig` 字段的平铺投影、
③ 把轮首装配钉成唯一写方。但这两条理由真正否掉的是**「能力在决策时刻读自己的活
配置」**，并没有否掉「能力在收集期把自己那一格的值交给宿主」。把「配置归谁」与
「什么时候读」拆开，两条纪律可以同时成立。

**裁决**：

1. **真源随能力包走**。每个开关 / 阈值的 schema、表单项、出厂默认值、读写都归 owner
   能力插件自己的 `PLUGIN.yml`（自己的 `DetailDefinition`）。没有独立插件的实现体
   （首响 / 中途汇报）要么按迁移批拆成自己的能力包，要么逐条写明它属于「会话基底」
   ——不允许含糊地留在中间态。
2. **贡献是收集期声明，不是决策期读活值**。复用 `CAPABILITY_VISITOR` 与开轮那一次
   `traverse`，新增族 `config.snapshot`（`CapabilityFamily::multi`，族是值不是内核
   枚举）。插件侧只有 `capability_announce_config_snapshot(ctx, key, value)` 一个入口，
   与 `capability_announce_configurable` 同形；宿主侧只有
   `capability_config_snapshot(visitor)` 一个读口，按注册序折成一张 JSON 对象。两侧都
   不认识键名、不提任何能力名、不交配置类型。不新增上下文键、不新增实体、不新增事件
   类型。
3. **生效时刻不变**。轮首装配把会话基底格与所有贡献格合成**一条** `session.config`
   （`Scope` / `Asserted`）；决策仍只读这条事实，读不到就用出厂值，配置改动仍晚一轮
   生效（`D-379` ②④ 保留）。能力不在决策路径上读自己的活配置，所以「生效时刻会漂」
   不成立。
4. **会话基底的边界**。`session` 只写 `system_prompt` / `tools` /
   `tools_empty_reason` / `capability_errors` 这类本轮装配面；生产源码里不得出现能力
   键名字面量，不得按 `PLUGIN_ID_*` 分流。原来「`compose_enabled` = 配置值 ∧ 债表里
   有 `<debt>compose`」由 `compose` 插件自己在收集期收敛：挂载即贡献有效值，未挂载
   就没有这一格，读方按缺省 `false`。
   **会话基底格（`opening_*` / `progress_*`）由本插件在写格处直接投影，不绕广播**：
   它们的真源（`SessionConfig`）与实现体（`opening.rs` / `progress.rs`）都在本插件，
   绕一次收集期声明只会让「这一格在这一轮是否可见」依赖 `traverse` 与写格的先后——
   那是一条自造的时序依赖。广播通道只服务**别人家的格子**。这条区分同时决定了 SDK
   依赖面：`session` 因此只多出一个读口（`capability_config_snapshot`），上报口一个
   都不多，读口按 `E-009` 限期豁免的既有口径登记（该豁免随 `session` 退役同批删除）。
5. **谁贡献谁负责默认值**。当前 `classify_enabled` / `compose_enabled` 出厂是 `true`，
   而读方缺席缺省是 `false`；迁移时插件必须显式贡献 `true`，否则卸载或缺键会静默把
   「默认开」变成「默认关」。卸载 = 该格无人贡献 = 读方出厂值，系统完整运行、不留
   静默边（T3）。
6. **门面账**。插件侧声明口上 `symbio-plugin-api`：不提能力名，且每一条带开关的能力
   都要用（≥2 条，满足 `DE-025` §5.1 两条准入）。宿主侧读口只有控制面 `session` 消费，
   按 `HS-003` 不上门面（与 `ViewUnavailable` 同例）。`SDK_BASELINE` 上调一档挂本条
   编号。

**按 `DE-047` §3 作废协议显式作废**（原文保留、标注作废、指向本条编号，不静默改写）：

- [DE-026](026-能力拆分与影响类.md "DE-026-能力拆分与影响类") `D-252` 第 2 条**被否**
  项中「让能力自带配置面（PLUGIN.yml 私有键）——生效时刻会漂，且绕过了『决策只读
  快照』那条既有纪律」：**作废，替代判据见本条**。能力自带配置面成立；「决策只读
  快照」由裁决 3 原样保留。`D-252` 第 2 条正文「能力读事实不读活值」不变。
- [DE-045](045-能力包迁出与落地裁决.md "DE-045-能力包迁出与落地裁决") `D-379`
  ①「快照是 `SessionConfig` 的平铺投影，键名逐字相同」与 ③「写方唯一是轮首装配
  （能力只按共享名读、不认识 `SessionConfig` 类型）」中的**投影与唯一写方**部分：
  **作废，替代判据见本条**。②缺字段取出厂值、④晚一轮生效继续有效；③「读方不认识
  `SessionConfig` 类型」继续有效且被本条加强为「宿主也不认识能力键名」。

**判据**：① 新加一个带开关的能力，`core` / `kernel` / `loop` / `session` 生产源码
diff = 0；② `session` 生产源码里没有能力开关键名字面量、没有按 `PLUGIN_ID_*` 的分支；
③ 卸载任一能力插件，该格在 `session.config` 里缺席、读方取出厂值、系统完整运行；
④ 决策路径上不存在能力读自己活配置的通道；⑤ SDK 单测钉住「多插件贡献 → 宿主合并」
「同键后声明覆盖」「无关族的行不进快照」。

**代价**：能力包多一次收集期声明调用；`session.config` 的载荷键集合从编译期闭集变成
运行期按挂载派生的集合——这是「配置随能力包走」的必要代价，换掉的是编译期那份能力
清单。因此参考文档的 `plugin-configs` 封闭集与 e2e 的配置注入点必须跟着换 owner，
否则文档与运行期各自报一份不同的键表。

**不做什么**：不让能力在决策期回调自己的配置文档（那才是生效时刻会漂）；不把整份
配置结构或 `SessionConfig` 类型交过插件边界；不为「立即生效」在触发路径加活配置
回退；不改 `session.config` 这一事实的格位、owner 与读法；不因为方便就把键名收进
内核枚举。
