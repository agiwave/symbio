# 能力自配置终态裁决

> **一句话**：配置归谁，与什么时候读它，是两件事。真源随能力包走，交付放在开轮
> 收集期，决策仍只读那一条快照事实——`session` 因此不必认识任何能力名。

本篇承载「配置随能力包走」这一格的终态裁决与作废旧判定清单。目标判据见
[DE-002](002-架构总览.md "DE-002-架构总览")，扩展面闭表见
[DE-025](025-能力包与扩展面.md "DE-025-能力包与扩展面")，作废协议见
[DE-047](047-义务环判据与归属推导.md "DE-047-义务环判据与归属推导") §3。

### D-427 能力配置的真源在能力包：快照由能力贡献，宿主只收集

**背景**：`DE-002` 把「新能力只碰自己的包，`core` / `kernel` / `loop` / `session`
diff = 0」写成硬判据，`DE-025` 开头把「配置随能力包走」写成一句话。配置这一格至今
没兑现：`SessionConfig` 代管 `classify_enabled` / `compose_enabled` / `opening_enabled` /
`progress_*` / `task_cap` / `skill_compile_enabled` / `conation_enabled` 等一整片能力开关，
`plugin/turn.rs` 又把它们硬编码投影成 `session.config`，甚至为了算 `compose_enabled`
去债表按 `PLUGIN_ID_COMPOSE` 查插件在场。于是「加一个开关」要改会话的配置结构、
默认函数、表单项、投影行，可能还要加一条按名判断——T1 不成立，`session` 认识能力名。

挡在这条路上的不是机制缺口，是两条旧判定：`D-252` 第 2 条把「让能力自带配置面」列为
被否（理由「生效时刻会漂」），`D-379` ① 把快照钉成 `SessionConfig` 字段的平铺投影、
③ 把轮首装配钉成唯一写方。但这两条理由真正否掉的是**「能力在决策时刻读自己的活
配置」**，并没有否掉「能力在收集期把自己那一格的值交给宿主」。把「配置归谁」与
「什么时候读」拆开，两条纪律可以同时成立。

**裁决**：

1. **真源随能力包走**。每个开关 / 阈值的 schema、表单项、出厂默认值、读写都归 owner
   能力插件自己的 `PLUGIN.yml`（自己的 `DetailDefinition`）。没有独立插件的实现体
   （首响 / 中途汇报）要么按迁移批拆成自己的能力包，要么逐条写明它属于「会话基底」
   ——不允许含糊地留在中间态。
2. **贡献是收集期声明，不是决策期读活值**。复用 `CAPABILITY_VISITOR` 与开轮那一次
   `traverse`，新增族 `config.snapshot`（`CapabilityFamily::multi`，族是值不是内核
   枚举）。插件侧只有 `capability_announce_config_snapshot(ctx, key, value)` 一个入口，
   与 `capability_announce_configurable` 同形；宿主侧只有
   `capability_config_snapshot(visitor)` 一个读口，按注册序折成一张 JSON 对象。两侧都
   不认识键名、不提任何能力名、不交配置类型。不新增上下文键、不新增实体、不新增事件
   类型。
3. **生效时刻不变**。轮首装配把会话基底格与所有贡献格合成**一条** `session.config`
   （`Scope` / `Asserted`）；决策仍只读这条事实，读不到就用出厂值，配置改动仍晚一轮
   生效（`D-379` ②④ 保留）。能力不在决策路径上读自己的活配置，所以「生效时刻会漂」
   不成立。
4. **会话基底的边界**。`session` 只写 `system_prompt` / `tools` /
   `tools_empty_reason` / `capability_errors` 这类本轮装配面；生产源码里不得出现能力
   键名字面量，不得按 `PLUGIN_ID_*` 分流。原来「`compose_enabled` = 配置值 ∧ 债表里
   有 `<debt>compose`」由 `compose` 插件自己在收集期收敛：挂载即贡献有效值，未挂载
   就没有这一格，读方按缺省 `false`。
   **会话基底格（`opening_*` / `progress_*`）由本插件在写格处直接投影，不绕广播**：
   它们的真源（`SessionConfig`）与实现体（`opening.rs` / `progress.rs`）都在本插件，
   绕一次收集期声明只会让「这一格在这一轮是否可见」依赖 `traverse` 与写格的先后——
   那是一条自造的时序依赖。广播通道只服务**别人家的格子**。这条区分同时决定了 SDK
   依赖面：`session` 因此只多出一个读口（`capability_config_snapshot`），上报口一个
   都不多，读口按 `E-009` 限期豁免的既有口径登记（该豁免随 `session` 退役同批删除）。
5. **谁贡献谁负责默认值**。当前 `classify_enabled` / `compose_enabled` 出厂是 `true`，
   而读方缺席缺省是 `false`；迁移时插件必须显式贡献 `true`，否则卸载或缺键会静默把
   「默认开」变成「默认关」。卸载 = 该格无人贡献 = 读方出厂值，系统完整运行、不留
   静默边（T3）。
6. **门面账**。插件侧声明口上 `symbio-plugin-api`：不提能力名，且每一条带开关的能力
   都要用（≥2 条，满足 `DE-025` §5.1 两条准入）。宿主侧读口只有控制面 `session` 消费，
   按 `HS-003` 不上门面（与 `ViewUnavailable` 同例）。`SDK_BASELINE` 上调一档挂本条
   编号。

**按 `DE-047` §3 作废协议显式作废**（原文保留、标注作废、指向本条编号，不静默改写）：

- [DE-026](026-能力拆分与影响类.md "DE-026-能力拆分与影响类") `D-252` 第 2 条**被否**
  项中「让能力自带配置面（PLUGIN.yml 私有键）——生效时刻会漂，且绕过了『决策只读
  快照』那条既有纪律」：**作废，替代判据见本条**。能力自带配置面成立；「决策只读
  快照」由裁决 3 原样保留。`D-252` 第 2 条正文「能力读事实不读活值」不变。
- [DE-045](045-能力包迁出与落地裁决.md "DE-045-能力包迁出与落地裁决") `D-379`
  ①「快照是 `SessionConfig` 的平铺投影，键名逐字相同」与 ③「写方唯一是轮首装配
  （能力只按共享名读、不认识 `SessionConfig` 类型）」中的**投影与唯一写方**部分：
  **作废，替代判据见本条**。②缺字段取出厂值、④晚一轮生效继续有效；③「读方不认识
  `SessionConfig` 类型」继续有效且被本条加强为「宿主也不认识能力键名」。

**判据**：① 新加一个带开关的能力，`core` / `kernel` / `loop` / `session` 生产源码
diff = 0；② `session` 生产源码里没有能力开关键名字面量、没有按 `PLUGIN_ID_*` 的分支；
③ 卸载任一能力插件，该格在 `session.config` 里缺席、读方取出厂值、系统完整运行；
④ 决策路径上不存在能力读自己活配置的通道；⑤ SDK 单测钉住「多插件贡献 → 宿主合并」
「同键后声明覆盖」「无关族的行不进快照」。

**代价**：能力包多一次收集期声明调用；`session.config` 的载荷键集合从编译期闭集变成
运行期按挂载派生的集合——这是「配置随能力包走」的必要代价，换掉的是编译期那份能力
清单。因此参考文档的 `plugin-configs` 封闭集与 e2e 的配置注入点必须跟着换 owner，
否则文档与运行期各自报一份不同的键表。

**不做什么**：不让能力在决策期回调自己的配置文档（那才是生效时刻会漂）；不把整份
配置结构或 `SessionConfig` 类型交过插件边界；不为「立即生效」在触发路径加活配置
回退；不改 `session.config` 这一事实的格位、owner 与读法；不因为方便就把键名收进
内核枚举。

### D-428 收集期前缀去重改由声明面回答在场

**背景**：能力自配置迁移批点名的最后一处「收集期按名判断」是工具表去重。子 Agent 把同一能力
以 `agent_<id>_<name>` 再注册一遍（`PrefixedCapability` 只改名、执行透传），会话装配
此前从 `agent_` 起试遍所有 `_` 切点，只要切点后的基名也在工具集合里就判为副本。
那份前缀规则属于 `symbio-plugin-agent`，控制面却在解析它：前缀一改、或某个工具名
恰好含相同切点，判定就静默错（副本留下 ⇒ 模型看见两个同能力；独有工具被误删 ⇒
能力凭空消失）。`DE-002` §4 的「控制面不按能力名留分支」不只管 `PLUGIN_ID_*`，
也管这种把别人的命名形状抄进控制面的写法。

**裁决**：

1. **答案归声明方**。`SubAgentVisitor::put` 在写前缀工具行的同一处，用开放构造口
   写一条 `SCOPE_TWIN` 族声明行，载荷是 `(前缀名, 本名)` 原始元组；族是值
   （`CapabilityFamily::multi`），常量与读口住 `symbio-sdk`，内核零改动。声明方与
   读方之间不共享任何结构体，控制面不解析任何名字形状。族名取 `scope_twin` 而不用
   点分的 `scope.twin`：`scope` 是 `Entity::Scope` 的小写，点分串在机制层会被
   `CS-008` 按「首段 ∈ `Entity` 闭集」读成事件名字面量；本族是能力表的一项、不是事件族，
   按该闭集反向约束命名即可，不为它开豁免、不改判据——「子 Agent 作用域」与「可见域」
   本来也不是一回事。
2. **宿主只做集合判定**。`capability_scope_twins` 是宿主侧唯一读口；装配面按
   「前缀名 ∧ 本名**都**在本轮工具表里」折叠出要去掉的那一份。本名缺席（能力被卸载、
   子树独有工具）⇒ 前缀那份必须保留，否则卸载一个插件会静默丢能力（T3）。
   判定与写入 / 遍历顺序无关——这是集合判定，不是遍历序判定。
3. **判定时点不变**。去重仍在收集完成后的装配面做，不搬回写入侧：`DefaultToolVisitor`
   的写入顺序不确定，按内表现问「根上有没有同名」会重新引入顺序依赖。声明行只答
   「谁是谁的副本」，不答「该不该删」。
4. **门面账**。族常量 `SCOPE_TWIN` 是声明方要用的共享词汇，按 `HS-002` 转出一条
   （`SDK_BASELINE` 127 → 128 挂本条编号）；宿主侧读口只有控制面 `session` 消费，
   按 `HS-003` 不上门面（与 `ViewUnavailable` 同例）。两条准入同样成立：不含任何
   能力名，且声明方 / 读方是两个消费方。
5. **不新增通道**。沿用开轮那一次 `traverse` 与 `CAPABILITY_VISITOR`，不新增上下文键、
   不新增实体、不新增事件类型；声明行的键与工具行不同名（表键是全表唯一命名空间），
   键的形状由声明方自己给，读侧只读载荷。

**判据**：① 会话侧单测钉住「声明的副本去掉 / 子树独有工具保留 / 未声明的名字一个
都不删 / 本名缺席时前缀工具保留 / 声明指向缺席名是空操作 / 换序结果相同」——
每条都是反向用例，尤其「未声明就不许删」直接钉死按名字猜的旧形状；② SDK 单测钉住
「只收 `(String, String)` 载荷的行 / 无关族不进读数 / 无声明返回空表」；③ agent 侧
单测钉住「每个前缀工具都交出一对本名」；④ 卸载声明方 ⇒ 无声明 ⇒ 一个工具都不删。

**代价**：声明方每次 `put` 多写一行；能力表多一个族（族是值，内核零改动）。
换掉的是控制面里那份前缀语法——它本来就没有 owner 在会话侧。

**不做什么**：不在控制面解析名字形状或切点；不按写入顺序判在场；不把去重搬回
写入侧；不为它新开上下文槽 / 事件类型 / 端口；不因为「族常量转出了一条」就把
读口也搬上门面。

### D-429 首响与中途汇报的归属：会话基底，不是未拆完的能力

**背景**：能力自配置迁移批的另一处残留是 `opening.rs` / `progress.rs` 的实现体仍在
`symbio-plugin-session`，`SessionConfig` 仍持有 `opening_*` / `progress_*` 两族键，
`plugin/turn.rs` 在写 `session.config` 那一处直接投影它们（D-427 裁决 4）。
`D-427` 裁决 1 要求「没有独立插件的实现体要么拆成自己的能力包，要么逐条写明它属于
会话基底」——此前只有一段「暂判」，不是裁决。含糊留在中间态是这一批明确不许的。

**裁决**：

1. **两者属会话基底，不属于能力**。逐条理由：① 没有独立事实族——它们只写
   `chat.assistant.opening` / `chat.assistant.reported` 两格，没有自己的债行产线、
   没有可被替换的提供者；② 没有独立路由 / 端口 / 可卸载边界——卸载 `session` 之外
   没有任何插件会因它们消失而少一项能力，只是会话呈现节奏变静默；③ 两者只描述
   **会话自身的呈现节奏**（派活前说不说一句、长任务中途要不要打断），不回答
   「系统能做什么」；④ 既有裁决已把它们钉在会话侧：`D-103` 把首响与追加合并为
   `reply` 的一个座位、`D-426` 把首响挂轮根、`D-344` 让首响行经 `route` 取措辞。
   按 `DE-026` §1 的五类残留，它们落在**会话基底**（呈现节奏的读写接口）与
   **过程体**（实时面在途帧）的交界，不是「能拆未拆」。
2. **真源与实现体同住，写格处直接投影**。`SessionConfig` 与两个实现体都留在本插件，
   键在写 `session.config` 处投影，不绕收集期广播（绕一次只会让这一格的可⻅性依赖
   `traverse` 与写格的先后）。广播通道只服务别人家的格子——这条区分同时决定 SDK
   依赖面：`session` 只多一个读口、不多上报口（D-427 裁决 4）。
3. **迁出触发写死，不留「以后再说」**。下一次拆分批次逐条复核；任一条件成立即必须
   拆成自己的能力包，并同步删掉 `SessionConfig` 与 `RE-001` 的 session 行里的键：
   ① 长出独立事实族或独立视图；② 长出独立路由 / 端口；③ 出现可卸载边界（卸载后
   有某个能力消失）；④ 出现第二个消费者要求不同的呈现节奏。在触发条件成立之前，
   这项残留是**已裁决**，不是「拆到一半」。
4. **键名不是能力名**。`opening_*` / `progress_*` 描述会话基底的参数，控制面源码里
   出现它们不违反「`session` 不认识任何具体能力名」；违反的标志是出现
   `PLUGIN_ID_*` 分流或别的能力包的开关键（D-427 判据 ②，由 `plugin-entry-audit`
   的 `E-009` 与代码复核守）。

**判据**：① `session` 生产源码里没有能力开关键名字面量、没有按 `PLUGIN_ID_*` 的分支；
② 卸载任一能力插件，这些格仍在、系统完整运行（T3）；③ 本条列出的四条迁出触发
在复核时逐条可查，写成裁决而非口号。

**不做什么**：不为「看起来像能力」造两个空壳插件；不把这两族键收进内核枚举或
共享词汇表；不为立即生效在触发路径加活配置回退；不把会话基底格改成广播贡献
（那只会自造一条时序依赖）。

### D-430 能力自配置迁移批收口：终态兑现与义务环判据面复核

**背景**：本批的终态是「每个能力的配置由能力插件自己持有并声明，接入走通用机制，
`symbio-plugin-session` 只保留会话基底、不认识任何具体能力名」（`DE-002` §4 /
`DE-025`）。D-427 把真源与开轮快照交回能力包，D-428 收掉收集期最后一处按名判断，
D-429 把首响与中途汇报的归属从「暂判」提升为写死迁出触发的裁决。三条裁决合起来
逐句兑现终态；本条记收口时的复核结论，**不新增机制**。

**裁决**：

1. **终态三句逐条有主**。① 配置真源随能力包走、宿主只读开轮事实（D-427）；
   ② 收集期不再按名字形状判断在场，`SCOPE_TWIN` 声明面只交 `(前缀名, 本名)`
   原始元组、控制面做一次集合判定（D-428）；③ `opening_*` / `progress_*` 属会话基底，
   键在写格处直接投影、不绕广播，四条迁出触发写死（D-429）。控制面源码里没有
   `PLUGIN_ID_*` 分流、没有别的能力包的开关键字面量、没有按 `agent_` 前缀试遍
   `_` 切点的猜法。
2. **义务环判据面没有失衡**。本批没有新增 `TC-n`、没有放宽既有判据、没有为
   `SCOPE_TWIN` 或会话基底单开一条专用判据码——`SP-033` 的 `TC-6`「判据集是闭集」
   因此未被扩写。新形状全部由既有面承接：门面臂 +1（`HS-002`，挂 D-428）、`E-009`
   限期豁免的符号集 +1（挂 D-428，理由与 `capability_config_snapshot` 同形）、
   `OBLIGATION_PRECHECK_BASELINE` 由 3 收到 0 是**收窄**（`SP-033` §4 的四条退场读数
   仍带码打印，不是静默删除）。六条 `TC-n` 的执行方在收口门禁中逐条实跑：有脚本的
   照旧判，标为类型 / 代码复核 / 评审守的仍按 `SP-033` §3「今天」列的口径不变——
   没有把「无执行方」改写成假绿灯，也没有为了刷绿给它们补专用脚本。
