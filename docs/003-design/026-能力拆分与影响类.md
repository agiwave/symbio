# 能力拆分与影响类

> **一句话**：一个能力 = 事实 + 视图 + 行 + 执行体；前三个成员已经能随插件走，
> 第四个只需要引擎提供**一个**通用执行体。全面拆分 = 把 `loop` / `session` 里
> 每一处按能力名写的策略搬到它自己的 crate，控制面只留五类残留。

本文回答三件事：拆分的判据（§1）、能力能对系统做的全部动作（§2）、代表能力怎么落地
（§3）。扩展面的清单归 [DE-025](025-能力包与扩展面.md "DE-025-能力包与扩展面")；
内核封闭语法归 [DE-023](023-内核边界与扩展局部性.md "DE-023-内核边界与扩展局部性")；
环与端口的定义归 [DE-015](015-义务环.md "DE-015-义务环")（D-222）。

## 1. 判据：T1 / T2 / T3，目标是全面拆分

| 编号 | 判据 | 它回答什么 |
|---|---|---|
| **T1 新增** | 新能力只改自己目录，`core` / `kernel` / `loop` / `session` diff = 0，端到端用例通过 | 「以后加能力要不要动架构」 |
| **T2 拆除** | 删掉 `loop` / `session` 里那份实现，行为由插件等价提供，观察到的行为差异为零 | 「存量能力能不能拆出去」 |
| **T3 卸载** | 卸载插件后系统完整运行，该能力消失且不留静默边 | 「可卸载」是否成立 |

**T1 是硬判据，T2 是终态。** 只做到 T1 时，新能力可以长在插件里，但 `loop` / `session`
仍按能力名持有旧实现——控制面继续变胖，扩展性只在纸面上。所以本方案不把 T1 当完成；
终态要求 `loop` / `session` 只留下五类东西：

| 残留类 | 判据 | 例子 |
|---|---|---|
| **环** | 推进与选债本身 | `drive` / `owed` / 一张表（D-222） |
| **写口** | 唯一写入口与写闸 | `FactDraft` 的落格 |
| **全局守门** | 量词跨全量、必须由引擎强制（I-8） | 授权、不变量、承诺配对、单写者顺序 |
| **过程体** | 不是状态转移，是过程本身（I-7） | 模型往返的流式读取、工具批次在途 |
| **会话基底** | 存储、转写、收件箱的读写接口 | `SessionStore` 的接缝 |

账本只许降，最终归零到「五类之外没有名字」。任何一条留守项都要写明「为什么它不是
能力」——写了不成立的，就说明它该搬。

**账本的对象是名册全表。** [DE-008](008-能力注册表与能力坐标系.md "DE-008-能力注册表与能力坐标系") §6.1 的 54 行能力是拆分的**完整输入**：
终态要求**逐行**有处置，不是只处理举例的三条。一条能力可以留在控制面，但必须写明它
属于哪一类残留；「今天没有端口」不构成留守理由——端口是可以补的，补端口先于下结论。

**先补架构，再拆；架构补件必须显式且通用。** 现状的架构**不足以**支撑存量横向拆分——
32 条已锚定能力里今天 0 条能靠新建插件拆出。因此 D-240…D-243 的
端口与通用件不是「拆分之外的额外工作」，而是拆分的前置：I-1 轮级写、I-4 模型往返、
I-2 成本与优先级、I-5 通用省略各缺一项，缺一项就有一批能力迁不动。

结论是**先后**，不是「不许改」：架构设计（含后续发现的补件）走决策，落在迁移批次**之外**，
必须是**通用的**（不含任何能力名、至少服务一条真实能力）；迁移批次只做搬运，其 diff 应是
删除 + 绑定切换。若某一批发现还需要新机制，说明设计**不足**——停下，补一条 `### D-NNN`
与独立提交，再恢复迁移。判失败的不是「加了机制」，而是：机制**夹带**在迁移提交里（验证信号被污染）、
或者把某条能力的**实现**搬进 `core` / `kernel` / `loop` / `session` 冒充端口（反向拆分）。

## 2. 影响类闭表

**判定与强制分开。** 能力可以**产出**判定——一条事实、一次放行或拒绝；引擎**强制**
的是「什么算合法」：授权、不变量、承诺配对、单写者顺序。因此「判断闭集」闭的是
**强制点**（I-8），不是判定的生产者。一个能力说「这次调用不该放行」，它交的是
`Refuse`；它不能改的是「授权表允不允许」这件事本身。

| 编号 | 影响类 | 能力交什么 | 宿主做什么 | 今天 |
|---|---|---|---|---|
| **I-1** | 写事实（含判定事实） | `Vec<FactDraft>` | 补宿主面（轮锚 / 溯源 / 主体）、过写闸、落格 | 已可用：工具效果后与**轮级**（`plugin_row`，D-241）两处，纯值进、草稿出 |
| **I-2** | 上下文段 | `ContextSection { slot, text, cost, prio }` | 按 owner 序收集、按预算确定性裁剪、超界报告 | 段已可；**成本与优先级未声明**（D-243） |
| **I-3** | 前置裁决 | `Allow` / `Refuse(理由)` | fail-closed 合并，先拒绝者胜 | 已可用（D-219）；读数表仍是闭的 |
| **I-4** | 模型往返 | 提示 + 解析函数（纯值） | 调模型、管预算与租约、请求与应答落格 | 可用：`RowStep::Ask` + `RowHandler::parse`（D-242），心跳与租约沿用 `model` 端口 |
| **I-5** | 上下文省略 / 改写 | 一条「某区间被摘要取代」的事实 | 组装时不选那一区间 | 只有「隐藏未选分支」一条硬编码规则（D-243） |
| **I-6** | 请求下一段 | 一条让 `continue-turn` 行前件成立的事实 | 环继续推进（D-222 裁决 2） | 前件已是事实驱动；待首个消费者验证 |
| **I-7** | 过程体（流式 / 在途） | — | 引擎自己执行 | **不开放** |
| **I-8** | 强制（全局守门） | — | 内核执行 | **不开放** |

**闭的是影响类，不是能力。** I-1…I-8 是能力与引擎之间的全部接口形状：新增能力 =
选一格 + 落一个实例；新增一格 = 架构决策。这条区分是可判的——一条能力若能写成
「读已记录的事实 → 交上面某一种值」，它就是插件；写不进去，它要么属于 I-7 / I-8，
要么需要新开一格，后者必须走决策。

### 2.1 实体是另一条边界

`Entity` 是 12 个变体的闭集（`Domain` 是唯一的领域扩展位），能力包只声明事实名与
格位，**不得新增实体**（D-244）。想进入转写、轮、任务这类核心语义的能力，只能用
核心实体；这是**语义决定**，不是能力扩展。

这不是瓶颈，因为「能力要出现在哪里」本来就只有两种答案：核心语义（用核心实体）或
领域私有（用 `Domain`，`core` 一律不解释）。三个代表能力的落点因此都不需要新实体。

### 2.2 名册五档与本文处置

给 54 行名册做判定时常用五档（可插件 / 缺端口 / 控制面 / 共享折叠 / 机制本体）。
五档描述的是**今天有没有路**，不是**本体能不能拆**。本文的处置如下：

| 判定 | 今天的意思 | 本文处置 |
|---|---|---|
| **A 可插件** | 今天就能只改自己的 crate | 直接落能力包；模板是 EX-001 夹具 |
| **B 缺端口** | 只差一个通用端口 | 新增影响类或端口 = 架构决策；先裁决再落，不得绕过 |
| **C 控制面** | 判断或时机住在 `loop` / `session` 的私有表里 | **劈成两半**：判定生产者按 I-1 / I-3 / I-4 迁出；强制点按 I-8 留守。整条留在控制面只在它**整条**是强制点时才成立 |
| **D 共享折叠** | 读者 ≥2 个插件 | **不再算不可拆**：折叠搬 owner 能力包，第二读者改名字读（D-221）。搬不动的只剩「搬了会变慢」这类实现顾虑，不是架构理由 |
| **E 机制本体** | 封闭语法 / 判断种类 / 配对契约 | 留守；它的**实例层**仍可 A（再加一个工具 / 供应商 / 行） |

这张表的用处是把「0/32 可拆」翻译成可执行的账：那 0 是**端口读数**，不是本体判定。
补上 I-1 轮级写口、I-4 模型往返、I-5 通用省略与通用执行体之后，C 类里凡是
「读已记录的事实 → 交一种值」的都能迁；D 类走名字读；剩下的 E 与环 / 写口 / 过程体 /
会话基底才是真留守。**逐行结果归任务体系**，本文只定处置规则与终态判据（D-246）。

逐行账因此住在任务体系而不是本文：它是 `EX-006` 每轮读的输入，也是迁移中某行需要补端口时
改判「待裁决」的落点。迁移收口时逐行账随任务退场，**留守行与理由并入本节**作为永久记录。

按这条规则落账，名册 32 行**已锚定**能力里除 11 行 E 机制外全部有迁出路径
（C 15 + D 6）；22 行**未落地**里 10 行 A 直接可插件、4 行 C 生产者按同规则可迁、
1 行 B 待裁决、7 行留守。也就是说：已落地能力的迁移面不是「挑几条样本」，
而是除机制本体之外的全部。

## 3. 形状样本：三个代表能力

三条样本只用来展示三种形状，不是账本本身；账本覆盖
[DE-008](008-能力注册表与能力坐标系.md "DE-008-能力注册表与能力坐标系") §6.1 的全部 54 行。

| 能力 | 时机 | 输入 | 输出 | 缺什么 | 终态 |
|---|---|---|---|---|---|
| **主动开口** | 定时 / 空闲 | 会话状态、目标 | 收件箱一条事实（I-1） | 无 | **今天即可**：[heartbeat](../../crates/symbio-plugin-heartbeat/src/plugin.rs "heartbeat") 就是插件，自带扫描循环、经路由写收件箱，不碰 `loop` 内部 |
| **反思** | 轮末（一条事实） | 转写切片 + 视图 | 洞察事实 + 可选段（I-1 / I-2） | 模型往返（I-4） | 独立 crate：一条行 + 一次模型往返 + 一条 `Memory` / `Domain` 事实 |
| **压缩** | 超阈值（视图折出债） | 转写切片 | 摘要事实 + 省略事实（I-1 / I-5） | 模型往返 + 通用省略 | 独立 crate：摘要落 `Message` 事实，组装按省略事实跳过区间 |

三个样本缺的**不是三种不同的原因**，而是三样通用件：通用执行体、模型往返、通用省略。
主动开口什么都不缺，它今天已经是插件——这是「插件能承载能力」不是假想的直接证据。

### 3.1 模板：主动开口的 T1 / T2 / T3 读数

主动开口不需要迁移，它的用处是把「一条能力摘掉之后怎么算数」冻成模板
（`e2e/cases/t90-heartbeat-capability-off.mjs`，后面的迁移批次照抄这四个读数）：

| 读数 | 怎么取 | 为什么是这一条 |
|---|---|---|
| **能力在不在** | 停用侧的工具面不含 `heartbeat`，且其余工具仍在 | 只验停用侧的话，工具面整体变空也会绿 |
| **不再产生事实** | 停用侧一个触发窗内，转写与模型往返**两处**都不出现提示词 | 转写没写不等于没发出去 |
| **到过点** | 同一窗口内启用侧真的把提示词落进转写 | 否则「停用侧没有」可能只是还没到点 |
| **系统完整运行** | 停用侧窗口之后仍能跑完一轮；配置仍读得出（缺的是执行者，不是数据） | 「没触发」不能是「没配置」或「系统坏了」 |

可复用的一条只有一句：**同一份会话数据、同一个会话 id、两侧同时起步**——空闲相位与扫描
tick 相同，一侧触发过，另一侧的窗口就必然已经过去；否则「没触发」与「还没到点」在读数上
不可分。T1 与 T2 在这里是空集：既有能力的停用不改控制面（`loop` / `session` diff = 0 由提交
本身可核），也没有旧实现要删——`EX-002` 判的是**新增**能力包的提交，本条不是。

## 4. 顺序与失败语义

一条能力插进来，不能改变别人的顺序，也不能把环卡死：

| 关注点 | 规则 |
|---|---|
| **顺序** | 全局 `(prio, name, key)` 升序（`Decl` 已如此）；能力不得依赖「谁先被收集」，也不得自定顺序 |
| **声明即绑定** | `Decl.by` 解析不到执行体 ⇒ `seal` 期红；不再由派发器静默过滤（今天是静默） |
| **失败** | 路由失败 / 超时 ⇒ 债不还（`ActorError`），由 `lease` / `max_attempts` 兜底；不许吞 |
| **权限** | 插件行与其它插件同一个授权面：`PLUGIN.yml` 的 `principal_*` 生成授权行 |
| **隔离强度** | 插件是可信代码（与今天所有插件同级）；沙箱与运行期装配不在本方案内（D-217 / D-245） |

## 5. 判据

| 编号 | 判据 | 反向用例 | 状态 |
|---|---|---|---|
| **EX-002** | T1：新能力只改自己目录，`core` / `kernel` / `loop` / `session` diff = 0，端到端用例通过（执行方 `scripts/extension-locality-audit.mjs`） | 在 `loop` 里加一行按能力名分支 ⇒ 红 | 已成 |
| **EX-003** | T2：一条能力迁出后旧实现已删（同提交），行为用例不变。`同提交删除` / `只许删除与绑定切换` 归 `scripts/capability-migration-audit.mjs`；`两份实现同时生效` 归 `seal` 的 `Gap::Duplicate{Name,Event,Fact,View,Actor,Port}`；行为不变由该批端到端用例判 | 迁移提交只改测试、旧实现留着 ⇒ 红；同名声明两份 ⇒ 装载期红 | 已成 |
| **EX-004** | T3：卸载插件 ⇒ 能力消失、系统完整运行、无静默边。静态一半（可卸载插件的编译期边为 0）归 `scripts/uninstall-edge-audit.mjs`；运行期一半归 `composite::tests` 的卸载用例、e2e `t88`（停用）与 `t80`（残留目录） | 别的 crate `use` 可卸载插件、或其清单写依赖 ⇒ 红；停用后工具仍在 ⇒ `t88` 红 | 已成 |
| **EX-005** | 声明即绑定：`Decl.by` 解析不到执行体 ⇒ `seal` 期红 | 声明一条无人执行的行 ⇒ 红（今天绿） | 已成 |
| **SC-006**（既有） | 全面拆分终态：`loop` / `session` 非测试代码零工具名——「能力名」里可机械判的那一半；账本 `scripts/baselines/tool-names.json` 只许降。能力名本身的归宿由 `EX-006` 与迁移任务收口 | 新写一处工具名 ⇒ `SC-006` 红；删了代码而基线没跟上 ⇒ 红 | 已成 |
| **EX-006** | 名册全覆盖：`DE-008 §6.1` 的 54 行每一行恰好一条处置——拆分目标指得出 crate，留守项写明残留类与理由（执行方 `scripts/capability-ledger-audit.mjs`） | 漏一行、或「能拆未拆」⇒ 红 | 已成 |
| **EX-007** | 迁移提交只做搬运：正文一行 `Migration: <批次>` 认迁移类；`core` / `kernel` / `plugin-api` 非生成 `.rs` diff = 0、`loop` / `session` 没有新增带能力名（插件 id / 工具名）的源码行、且至少删掉一行旧实现；架构补件单列，挂能打开的 `### D-NNN`，新增的非注释代码不含插件 id 与工具名（执行方 `scripts/capability-migration-audit.mjs`） | 迁移提交夹带机制增量 ⇒ 红；补件只为容纳一条能力 ⇒ 红；把能力实现搬进架构模块 ⇒ 红并停工 | 已成 |

七条都要求「改输入后结论必须变」。判据必须先于迁移落地——否则迁移会以「全绿」的
形式停在半路：`seal` 通过、`ActorDecl` 在、测试也绿，而派发时整条被过滤掉。

`SC-006` 这一行**不新开执行方**：`plugin-special-case-audit` 从 D-212 / D-218 起就在判
「工具名落在 `core` / `kernel` / `loop` / `session` 四棵树的非测试代码里」，逐处基线
（文件 + 名字 + 处数）只许降、每处挂能打开的决策。再写一条判同一形状的脚本，就是
第二个 owner——同一处新增会在两条码下各红一次，而删代码后两条基线都要各改一遍。

`EX-002` 的判定读**提交 diff 的四棵树指纹**，不读「有没有新 crate」：新增
`crates/symbio-plugin-<名字>/PLUGIN.yml` 的提交，父提交与本提交的 `core` / `kernel` /
`loop` / `session` 目录指纹必须逐一相等。两处例外各有理由：已存在的 `*.gen.rs` 是清单的
镜像（作者只改自己目录，生成器保证内容与清单一致），**新出现**的 `*.gen.rs` 不豁免——
那是新增一条生成面，属补件；判据诞生前的 crate 拆分（`BEFORE_GUARD`）逐条带理由地
不追溯。正向证据是 EX-001 的夹具提交（`77ff41fa`），它不在提交范围里也每轮判一次；
端到端那一半仍是 `e2e/cases/t89-notes-extension.mjs`。

`EX-003` 不新开「按名字再判一遍两份实现」的守卫：同名声明在装载期已由 `seal` 的
`Gap::Duplicate*` 判红（`crates/symbio-kernel/src/decl/ring.rs`），再写一条就是第二个
owner（与 `SC-006` 同一条纪律）。提交 diff 这一半判的是 `seal` 看不见的事实——
插件落了而旧实现没删，同一次装载里可能只生效一份，而账面上迁移已经宣布完成。

`EX-004` 的静态一半只判**可卸载**插件：`plugin_manager` / `vdfs` 是界面底座
（`ASSEMBLY_UNDISABLABLE_PLUGINS`），没有「卸载」这条路，对它们的编译期边不构成静默边。
生成的 `plugin-links` 标记块是装配点本身，块外的手写引用全部算边；标记块缺失也判红——
那时生成行会被当成手写边，报错会指向一整屏假阳性，真问题反而看不见。

`EX-007` 用正文一行 `Migration:` 声明迁移类（与 `Core-Change:` 同一种形状）：
「这次提交是迁移还是补件」是提交的意图，不是某个文件的属性。没有声明时按「架构面新增
`pub` 项」认补件，其余不判——宁可漏判，也不猜。判据只追溯 `BEFORE_GUARD` 之后的提交：
此前按旧纪律写的提交不追溯，追溯的唯一效果是逼人重写历史。正向证据是补件夹具提交
（`709ee583`，D-219 / D-220），它不在提交范围里也每轮判一次。

## 6. 与既有裁决的关系

- **D-208（判断闭集）** 按 D-240 收窄：闭的是强制点与顺序，不是判定的生产者。
- **D-222（端口闭集）** 不被推翻：模型往返是第三个端口，判据仍是「派出之后控制面
  不持有对方状态」；执行体不是端口，它是环内一步。
- **D-217（两个开关）** 不被推翻：链接期贡献与运行期停用的分界不变；第三方独立
  进程插件只能覆盖「会调用的东西」，本方案不改变这一点。
- **DE-021 §7（不再切插件）** 只适用于「按 crate 切控制面」的旧口径；按能力四元组
  拆分是另一件事（D-239）。

## 关键决策

### D-239 T1 是硬判据，T2 是终态

**裁决**：「一个能力一个插件」的硬判据是 T1（新增能力只改自己目录，控制面 diff = 0，
端到端通过）；本方案同时以 T2（存量拆除）为终态，不以 T1 代替 T2。T3 是两者的共同
底线。

**理由**：原判据把扩展（新增）与重构（拆除）混成一句。只做 T1，`loop` / `session`
仍是能力容器，控制面继续变胖；只按 T2 现状判「架构失败」，则用重构难度否定了扩展
可能。两个方向都有对象可指，才谈得上验证。

**被否**：只做 T1（存量不动，控制面继续长）；以 T2 的 0/32 直接判架构不可扩展
（没有先补执行体，等于用缺件证明缺件）。

### D-240 影响类闭集：判定可以开放，强制必须留核

**裁决**：能力对系统的动作收成 8 类（I-1…I-8）。能力可以产出判定（`FactDraft` /
`Verdict`）；授权、不变量、承诺配对、单写者顺序由引擎强制。新增影响类是架构变更，
新增能力不是。

**理由**：回放只承诺 L0 + L1，读日志、不重执行判断（[DE-001 §11](001-核心架构.md "DE-001-核心架构")），
所以执行体的位置不影响回放；真正不能被能力改写的是「什么算合法」，那是量词跨全量的
性质，插件看不见全量，放出去必然静默空转（J3）。

**被否**：把判定的生产者与强制点合成一个「判断闭集」（执行体因此无处可去）；影响类
按能力增长（端口数随能力数增长，拆了等于没拆）。

### D-241 通用行执行体：一次绑定，所有能力共用

**裁决**：新增一个 `ActorEntry` `plugin_row`，`run` 只做三件事：按声明把债实例与事实
切片经容器路由发出去、把 `Vec<FactDraft>` / `Verdict` 拿回来、交宿主唯一写口落格。
执行体只收纯值；`by` 由 `ActorDecl` 绑定；解析不到在 `seal` 期红。

**理由**：四元组里只有执行体不可插件（`ActorEntry` / `Action` 是 `loop` 的 `pub(crate)`）。
给每个能力加一个 `ActorEntry` 会让绑定表随能力数增长——那只是把 `loop` 的分支换成
`loop` 的表格，扩展性没有增加。通用执行体不认识任何能力名，顺序由既有 `prio` 决定，
失败由既有租约兜底。

**被否**：把 `&mut Ctx` 开给插件（持有整轮可变状态，顺序与失败都不可判）；按能力名
注册执行体（绑定表增长）；把 `TurnState` 复制一份给插件（两份真相）。

### D-242 模型往返是第三个端口

**裁决**：能力可以声明「这一步要一次模型往返」：宿主执行、预算与租约归宿主、请求与
应答落格；能力只给提示与解析函数（纯值）。端口满足 D-222 §一：派出之后控制面不持有
对方状态。

**理由**：反思、压缩、技能编译都需要 LLM；不开口，它们只能住 `loop`。这不增加一种
「判断」，只增加一次往返。

**被否**：插件直连 provider（凭据 / 预算 / 落格散落，且跨插件依赖 provider crate）；
宿主为某个能力特制原语（能力名进控制面）。

### D-243 上下文段有成本与优先级；省略是一条通用事实

**裁决**：`ContextSection` 增加成本与优先级，宿主按 owner 序收集后按确定规则裁剪、
超界报告；「某区间被摘要取代」是一条事实，组装按事实省略区间，不为压缩特判。

**理由**：多能力同时贡献段会撑爆窗口；今天只有「隐藏未选分支」一条硬编码规则，
它不能推广到第二个能力——那正是「加一个能力改一次组装」的形状。

**被否**：每个能力自己调窗口（预算没有唯一裁决）；按插件名判断省略（能力名进控制面）。

### D-244 Entity 是封闭语法，能力不得新增实体

**裁决**：`Entity` 保持 12 个变体的闭集（含 `Domain` 一个扩展位）；能力包只声明事实
名与格位，不得新增实体；新领域落 `Domain`，`core` 一律不解释。新增实体是架构决策，
默认答案是「用 `Domain`」。

**理由**：实体是本体，不是能力。开放它会丢掉读侧的穷尽检查（J3），而 12 个实体已经
覆盖核心语义（轮、任务、产物、裁决、记忆、承诺、意图、会话串、控制、系统、消息、领域）。
三个代表能力都用现成实体：反思 → `Memory` / `Domain`，压缩 → `Message`，主动开口 →
`Turn` 或收件箱事实。

**被否**：`Entity` 改成任意字符串；一个能力一个实体。

### D-245 迁移纪律：先落插件，切换与删除同提交

**裁决**：允许插件先落（未绑定、不生效），但「绑定切换 + 旧实现删除」必须在同一提交；
禁止两份实现同时生效；每一刀带 T1 / T2 / T3 三条用例与一条反向用例。

**理由**：双生效 = 两套语义 + 回放分叉；先删后建 = 中间态系统不完整。两者都会让
「拆到一半」的状态无法判断。

**被否**：灰度双写；用配置开关长期保留两份实现。

### D-246 名册 54 行逐条处置，能拆都拆

**裁决**：[DE-008](008-能力注册表与能力坐标系.md "DE-008-能力注册表与能力坐标系") §6.1 的 54 行名册是拆分账本的**完整输入**；
终态要求每一行恰好一条处置——要么搬进能力包（指得出 crate），要么留守并写明残留类
与理由。合法留守只有：**E 机制本体**、**I-7 过程体**、**I-8 强制点**、**环 / 写口 /
会话基底**、以及「另一读者尚未改名字读」的共享折叠（D-221 的过渡态，必须挂任务）。
「今天没有端口」「拆起来难」不是留守理由；既有按消费方归 owner 的裁决（D-190 等）
只说明今天住在哪，不构成留守理由。A 类行（今天即可插件）不进迁移账，但必须以能力包
落地作为正向验证；B 类行先裁决端口，未裁决前记为「待决策」，不是留守。

**理由**：「32 条已锚定 0 条可拆」量的是**端口缺口**，不是本体的可拆性；只补端口
不逐条处置，会停在「新增可以、存量不动」的半程。逐行账是唯一能防「拆到一半宣布完成」
的形状，也是「一个能力一个插件」这条不可妥协项的兑现方式。

**被否**：按五档原样接受（把今天的端口缺口当终态）；只拆 `loop` / 只拆带模型往返的；
把读数类折叠排除在账本外（它们同样是控制面里的能力名）。

**对 D-190 的限定**：D-190 的三分里，「抢占 → session」「熔断 → loop」是 **crate 归属**，
按本裁决迁到各自能力包；「淘汰裁决留核」不变（它在名册 #30，属 E）。

### D-247 拆分以架构设计为前置；机制增量显式、通用、不夹带

**前提**：今天的架构**不足以**支撑存量横向拆分——端口缺口是实测的，不是猜测（I-1 轮级写、
I-4 模型往返、I-2 成本与优先级、I-5 通用省略各缺一项）。所以「拆分期间架构不动」不是本裁决的
内容：补端口与通用件**是拆分能否发生的前提**，D-240…D-243 落定之前，任何「0/N 可拆」的读数
都只是缺件的读数。

**裁决**：机制增量与迁移搬运**分成两类提交**，各有各的判据：

1. **架构补件**（可改 `core` / `kernel` / `plugin-api`）：

   - 必须先有一条 `### D-NNN` 说清「哪条能力因缺它而迁不动、它服务哪些能力」；
   - 必须**通用**：不含任何能力名 / 工具名，至少服务一条真实能力（不是为单条能力定制的通道）；
   - 影响类若新增，仍是架构变更（D-240），不因「为了拆分」而放宽；
   - 补件落地后，被它解锁的那一行回到迁移批次。

2. **迁移批次**（S6 起）：

   - `core` / `kernel` diff = 0；
   - `loop` / `session` 的 diff 只含**删除**旧实现与**切换绑定**，不夹带新机制——行、执行体、
     分支、常量、状态字段都不许为某条能力新加；
   - 生成物与装配链接行可以随插件增删，它们不是机制。

若某一批发现「还需要一条机制才能迁」，说明**前置设计不足**：停下这一批，按第 1 类补决策与
独立提交，再恢复迁移；不许在迁移提交里顺手加。判失败的只有三件事，与「有没有加机制」无关：

- **夹带**：机制混在迁移提交里，使「这批只靠搬运」的验证信号失真；
- **定制**：所谓端口只服务一条能力、带着能力名，那只是把分支改名成 trait；
- **反向拆分**：把某条能力的**实现**从 `loop` / `session` 搬进 `core` / `kernel` 或另一个
  控制面模块来「满足」封闭集——功能代码进了架构，控制面没变薄。

**理由**：要验证的是「架构够不够」，不是「拆分者有多能绕」。把两件事塞进同一个提交，红绿就
不再说明任何时候；分开之后，每条能力的迁移 diff 本身就是「这条能力只需要端口 + 搬运」的证据，
而任何一条停在迁移批次门口的能力，都精确地指出还缺哪一项机制——这正是本方案想要的读数。

**被否**：迁移期一律禁增（把端口缺口当成永久结论，等于放弃拆分）；迁移期「先加后删」
（中间态两份实现）；按能力补端口（端口数随能力数增长）；把判定实现搬进 kernel 以绕开控制面
（反向拆分）。

### D-248 行级写入归属：共享执行体的收口与依赖图按行判

**裁决**：装配方把每条行实现声明的逐行写入名单（`RowHandler::writes`）作为
`Builder::seal` 的输入交进去；装载期第 6 条（执行体收口）与依赖图按**这一行**
的名单判。没有逐行名单的行（`run` 就是那一行自己的执行体）退回 `ActorDecl.writes`
——那是该行自己的名单，同一条口径。

**理由**：`ActorDecl.writes` 是**执行体级**的并集，够通用行执行体（D-241）让多行共用
一条声明；但并集包含每一行自己的出口，第二行一出现，每行的出口都会被「别的行」认领，
依赖图退化成完全图，任意两行成假环。这是 S4 夹具落第二行时实测到的
（`notes.index` ↔ `notes.reflect`），不是预判。逐行名单本来就由能力实现声明、运行期
已按它对账；交给装载检查只是让静态判据与运行期判据同源，没有新增第二份真相。

**被否**：给每一行注册一条 `ActorDecl`（绑定表随能力数增长，D-241 已否）；对共享
执行体的行整体放弃成边（真死锁也看不见）；把逐行名单复制进 `Decl`（同一个事实两个
声明位，静态与运行期会漂移）。
