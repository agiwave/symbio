# 能力拆分与影响类

> **一句话**：一个能力 = 事实 + 视图 + 行 + 执行体；前三个成员已经能随插件走，
> 第四个只需要引擎提供**一个**通用执行体。全面拆分 = 把 `loop` / `session` 里
> 每一处按能力名写的策略搬到它自己的 crate，控制面只留五类残留。

本文回答三件事：拆分的判据（§1）、能力能对系统做的全部动作（§2）、代表能力怎么落地
（§3）。扩展面的清单归 [DE-025](025-能力包与扩展面.md "DE-025-能力包与扩展面")；
内核封闭语法归 [DE-023](023-内核边界与扩展局部性.md "DE-023-内核边界与扩展局部性")；
环与端口的定义归 [DE-051](051-机制形状规格.md "DE-051-机制形状规格")。

## 1. 判据：T1 / T2 / T3，目标是全面拆分

| 编号 | 判据 | 它回答什么 |
|---|---|---|
| **T1 新增** | 新能力只改自己目录，`core` / `kernel` / `loop` / `session` diff = 0，端到端用例通过 | 「以后加能力要不要动架构」 |
| **T2 拆除** | 删掉 `loop` / `session` 里那份实现，行为由插件等价提供，观察到的行为差异为零 | 「存量能力能不能拆出去」 |
| **T3 卸载** | 卸载插件后系统完整运行，该能力消失且不留静默边 | 「可卸载」是否成立 |

**T1 是硬判据，T2 是终态。** 只做到 T1 时，新能力可以长在插件里，但 `loop` / `session` 仍按能力名持有旧实现——控制面继续变胖，扩展性只在纸面上。
所以本方案不把 T1 当完成；终态要求 `loop` / `session` 只留下五类东西：

| 残留类 | 判据 | 例子 |
|---|---|---|
| **环** | 推进与选债本身 | `drive` / `owed` / 一张表（D-222） |
| **写口** | 唯一写入口与写闸 | `FactDraft` 的落格 |
| **全局守门** | 量词跨全量、必须由引擎强制（I-8） | 授权、不变量、承诺配对、单写者顺序 |
| **过程体** | 不是状态转移，是过程本身（I-7） | 模型往返的流式读取、工具批次在途 |
| **会话基底** | 存储、转写、收件箱的读写接口 | `SessionStore` 的接缝 |

账本只许降，最终归零到「五类之外没有名字」。任何一条留守项都要写明「为什么它不是能力」——写了不成立的，就说明它该搬。

**账本的对象是名册全表。** [DE-008](008-能力注册表与能力坐标系.md "DE-008-能力注册表与能力坐标系") §6.1 的 54 行能力是拆分的**完整输入**：终态要求**逐行**有处置，不是只处理举例的三条。
一条能力可以留在控制面，但必须写明它属于哪一类残留；「今天没有端口」不构成留守理由——端口是可以补的，补端口先于下结论。

**先补架构，再拆；架构补件必须显式且通用。** 补件前的架构**不足以**支撑存量横向拆分——32 条已锚定能力里 0 条能靠新建插件拆出。
因此 D-240…D-243 的端口与通用件不是「拆分之外的额外工作」，而是拆分的前置：I-1 轮级写、I-4 模型往返、I-2 成本与优先级、I-5 通用省略各缺一项，缺一项就有一批能力迁不动（四项现已可用，见 §2）。
迁移中另有一处「疑似缺口」：提示成形前的摘行与抢先作答。复核后判定**不构成缺口**——两种需要各归既有的面（D-251），不新开端口。

结论是**先后**，不是「不许改」：架构设计（含后续发现的补件）走决策，落在迁移批次**之外**，必须是**通用的**（不含任何能力名、至少服务一条真实能力）；
迁移批次只做搬运，其 diff 应是删除 + 绑定切换。若某一批发现还需要新机制，说明设计**不足**——停下，补一条 `### D-NNN` 与独立提交，再恢复迁移。
判失败的不是「加了机制」，而是：机制**夹带**在迁移提交里（验证信号被污染）、或者把某条能力的**实现**搬进 `core` / `kernel` / `loop` / `session` 冒充端口（反向拆分）。

## 2. 影响类闭表

**判定与强制分开。** 能力可以**产出**判定——一条事实、一次放行或拒绝；引擎**强制**
的是「什么算合法」：授权、不变量、承诺配对、单写者顺序。因此「判断闭集」闭的是
**强制点**（I-8），不是判定的生产者。一个能力说「这次调用不该放行」，它交的是
`Refuse`；它不能改的是「授权表允不允许」这件事本身。

| 编号 | 影响类 | 能力交什么 | 宿主做什么 | 今天 |
|---|---|---|---|---|
| **I-1** | 写事实（含判定事实） | `Vec<FactDraft>` | 补宿主面（词干 / 溯源 / 主体）、过写闸、落格 | 已可用：工具效果后、**轮级**（`plugin_row`，D-241）与**收束时**（`Contributor`，D-250）三处，纯值进、草稿出 |
| **I-2** | 上下文段 | `ContextSection { slot, text, cost, prio }` | 按 owner 序收集、按预算确定性裁剪、超界报告 | 已可用：段携带 `cost` / `prio`（D-243），宿主按 owner 字典序收集后确定性裁剪并报告超界；能力只管交段 |
| **I-3** | 提示前裁决 | 调用前：`Allow` / `Refuse(理由)` | fail-closed 合并，先拒绝者胜 | 已可用（D-219）；「摘行」是读方按名字过滤、「抢先作答」是 I-1 的反射行——都不新开端口（D-251）；读数表仍是闭的 |
| **I-4** | 模型往返 | 提示 + 解析函数（纯值） | 调模型、管预算与租约、请求与应答落格 | 可用：`RowStep::Ask` + `RowHandler::parse`（D-242），心跳与租约沿用 `model` 端口 |
| **I-5** | 上下文省略 / 改写 | 一条「某区间被摘要取代」的事实（`message.added` 载荷的 `elision`，D-249） | 组装时不选那一区间（与未选中分支共用 `Elisions::elides`） | 已可用：显式区间与分支事实在同一个应用点合流；夹具 `notes.summarize` + e2e `t91` |
| **I-6** | 请求下一段 | 一条让 `continue-turn` 行前件成立的事实 | 环继续推进（D-222 裁决 2） | 前件已是事实驱动；待首个消费者验证 |
| **I-7** | 过程体（流式 / 在途） | — | 引擎自己执行 | **不开放** |
| **I-8** | 强制（全局守门） | — | 内核执行 | **不开放** |

**闭的是影响类，不是能力。** I-1…I-8 是能力与引擎之间的全部接口形状：新增能力 =
选一格 + 落一个实例；新增一格 = 架构决策。这条区分是可判的——一条能力若能写成
「读已记录的事实 → 交上面某一种值」，它就是插件；写不进去，它要么属于 I-7 / I-8，
要么需要新开一格，后者必须走决策。

### 2.1 实体是另一条边界

`Entity` 是 12 个变体的闭集（`Domain` 是唯一的领域扩展位），能力包只声明事实名与
格位，**不得新增实体**（D-244）。想进入转写、轮、任务这类核心语义的能力，只能用
核心实体；这是**语义决定**，不是能力扩展。

这不是瓶颈，因为「能力要出现在哪里」本来就只有两种答案：核心语义（用核心实体）或
领域私有（用 `Domain`，`core` 一律不解释）。三个代表能力的落点因此都不需要新实体。

### 2.2 名册五档与本文处置

给 54 行名册做判定时常用五档（可插件 / 缺端口 / 控制面 / 共享折叠 / 机制本体）。
五档描述的是**今天有没有路**，不是**本体能不能拆**。本文的处置如下：

| 判定 | 今天的意思 | 本文处置 |
|---|---|---|
| **A 可插件** | 今天就能只改自己的 crate | 直接落能力包；模板是 EX-001 夹具 |
| **B 缺端口** | 只差一个通用端口 | 新增影响类或端口 = 架构决策；先裁决再落，不得绕过 |
| **C 控制面** | 判断或时机住在 `loop` / `session` 的私有表里 | **劈成两半**：判定生产者按 I-1 / I-3 / I-4 迁出；强制点按 I-8 留守。整条留在控制面只在它**整条**是强制点时才成立 |
| **D 共享折叠** | 读者 ≥2 个插件 | **不再算不可拆**：折叠搬 owner 能力包，第二读者改名字读（D-221）。搬不动的只剩「搬了会变慢」这类实现顾虑，不是架构理由 |
| **E 机制本体** | 封闭语法 / 判断种类 / 配对契约 | 留守；它的**实例层**仍可 A（再加一个工具 / 供应商 / 行） |

这张表的用处是把「0/32 可拆」翻译成可执行的账：那 0 是**端口读数**，不是本体判定。
补上 I-1 轮级写口、I-4 模型往返、I-5 通用省略与通用执行体之后，C 类里凡是
「读已记录的事实 → 交一种值」的都能迁；D 类走名字读；剩下的 E 与环 / 写口 / 过程体 /
会话基底才是真留守。**逐行结果归任务体系**，本文只定处置规则与终态判据（D-246）。

逐行账住在本文（§2.3），不住任务体系：它是 `EX-006` 每轮读的输入，也是迁移中某行需要
补端口时改判「待裁决」的落点——**改判是设计决定，落点只能是设计文档**。任务文件是过渡
载体（RG-031），账放在那里会在任务退场时一起消失，而它要活到 S11 之后。

按这条规则落账，名册 32 行**已锚定**能力里除 11 行 E 机制外全部有迁出路径
（C 15 + D 6）；22 行**未落地**里 10 行 A 直接可插件、4 行 C 生产者按同规则可迁、
1 行 B 已裁为留守（多模态，`D-266`）、8 行留守。也就是说：已落地能力的迁移面不是「挑几条样本」，
而是除机制本体之外的全部。

### 2.3 逐行处置账（54 行 = 拆 32 · 留守 21 · 不做 1 · 待裁决 0）

每一行回答三件事：**本体是什么**（执行体 / 判定生产者 / 纯读数 / 机制）；**输出落在哪个影响类**（I-1…I-6）；**若写不进影响类**，属于哪一类留守（环 / 写口 / 全局守门 / 过程体 / 会话基底）。
E 档不另立残留类——它的每一行都落在这五类之一，理由列写明是哪一种封闭语法 / 判断种类 / 配对契约。

`归` 列是**交付承诺**：记为拆的行必须落到 S6（`loop` 存量）/ S7（`session` 存量，含随 conation / 主动性包落地的四条未建能力）/ S8（共享折叠搬 owner）/ S9（未落地能力包）之一。
待裁决落 S10；留守行与「不做（边界）」行不给交付段（`—`）；`EX-006` 判这一列——缺段或段不在闭集即红，「拆」不是一句承诺，得有人认领。

**「决定不做」单列，不许混进「拆」**：能力不存在（或按裁决删除而不换 crate）时记
`不做（边界）`，理由里挂决策号，写明重启条件。把它记成 `拆` 会让完成率虚高——判据对
「记为拆、目标 crate 在 `crates/` 下不存在」的行直接判红（`EX-006` 的 crate 存在性那一臂）。

**判据是「能拆都拆」**：只有写不进影响类的才留守；「今天没有端口」先补端口，不作为留守
理由。两行共用一份实现是合法的（技能路由的两行、校准的两行），账里写明「与某行同包」。

## 3. 形状样本：三个代表能力

三条样本只用来展示三种形状，不是账本本身；账本覆盖
[DE-008](008-能力注册表与能力坐标系.md "DE-008-能力注册表与能力坐标系") §6.1 的全部 54 行。

| 能力 | 时机 | 输入 | 输出 | 缺什么 | 终态 |

| **主动开口** | 定时 / 空闲 | 会话状态、目标 | 收件箱一条事实（I-1） | 无 | **今天即可**：[heartbeat](../../crates/symbio-plugin-heartbeat/src/plugin.rs "heartbeat") 就是插件，自带扫描循环、经路由写收件箱，不碰 `loop` 内部 |

| **压缩** | 超阈值（视图折出债） | 转写切片 | 摘要事实 + 省略事实（I-1 / I-5） | 无 | 独立 crate：摘要落 `Message` 事实，组装按省略事实跳过区间 |

### 3.1 模板：主动开口的 T1 / T2 / T3 读数

主动开口不需要迁移，它的用处是把「一条能力摘掉之后怎么算数」冻成模板
（`e2e/cases/t90-heartbeat-capability-off.mjs`，后面的迁移批次照抄这四个读数）：

| 读数 | 怎么取 | 为什么是这一条 |
|---|---|---|
| **能力在不在** | 停用侧的工具面不含 `heartbeat`，且其余工具仍在 | 只验停用侧的话，工具面整体变空也会绿 |
| **不再产生事实** | 停用侧一个触发窗内，转写与模型往返**两处**都不出现提示词 | 转写没写不等于没发出去 |
| **到过点** | 同一窗口内启用侧真的把提示词落进转写 | 否则「停用侧没有」可能只是还没到点 |
| **系统完整运行** | 停用侧窗口之后仍能跑完一轮；配置仍读得出（缺的是执行者，不是数据） | 「没触发」不能是「没配置」或「系统坏了」 |

可复用的一条只有一句：**同一份会话数据、同一个会话 id、两侧同时起步**——空闲相位与扫描
tick 相同，一侧触发过，另一侧的窗口就必然已经过去；否则「没触发」与「还没到点」在读数上
不可分。T1 与 T2 在这里是空集：既有能力的停用不改控制面（`loop` / `session` diff = 0 由提交
本身可核），也没有旧实现要删——`EX-002` 判的是**新增**能力包的提交，本条不是。

## 4. 顺序与失败语义

一条能力插进来，不能改变别人的顺序，也不能把环卡死：

| 关注点 | 规则 |
|---|---|
| **顺序** | 全局 `(prio, name, key)` 升序（`Decl` 已如此）；能力不得依赖「谁先被收集」，也不得自定顺序 |
| **声明即绑定** | `Decl.by` 解析不到执行体 ⇒ `seal` 期红；不再由派发器静默过滤（今天是静默） |
| **失败** | 路由失败 / 超时 ⇒ 债不还（`ActorError`），由 `lease` / `max_attempts` 兜底；不许吞 |
| **权限** | 插件行与其它插件同一个授权面：`PLUGIN.yml` 的 `principal_*` 生成授权行 |
| **隔离强度** | 插件是可信代码（与今天所有插件同级）；沙箱与运行期装配不在本方案内（D-217 / D-245） |

`EX-003` 不新开「按名字再判一遍两份实现」的守卫：同名声明在装载期已由 `seal` 的

owner（与 `SC-006` 同一条纪律）。提交 diff 这一半判的是 `seal` 看不见的事实——
插件落了而旧实现没删，同一次装载里可能只生效一份，而账面上迁移已经宣布完成。

`EX-004` 的静态一半只判**可卸载**插件：`plugin_manager` / `vdfs` 是界面底座
（`ASSEMBLY_UNDISABLABLE_PLUGINS`），没有「卸载」这条路，对它们的编译期边不构成静默边。
生成的 `plugin-links` 标记块是装配点本身，块外的手写引用全部算边；标记块缺失也判红——
那时生成行会被当成手写边，报错会指向一整屏假阳性，真问题反而看不见。

`EX-007` 用正文一行 `Migration:` 声明迁移类（与 `Core-Change:` 同一种形状）：
「这次提交是迁移还是补件」是提交的意图，不是某个文件的属性。没有声明时按「架构面新增
`pub` 项」认补件，其余不判——宁可漏判，也不猜。判据只追溯 `BEFORE_GUARD` 之后的提交：
此前按旧纪律写的提交不追溯，追溯的唯一效果是逼人重写历史。正向证据是补件夹具提交
（`709ee583`，D-219 / D-220），它不在提交范围里也每轮判一次。

`EX-008` 判的是**形状**，不是措辞：注释与文档里说「这一轮」不红（那是叙述宿主的行为），
端口上有一格 `turn` 才红。读法与 `SC-006` 同一条纪律——只认非注释代码里的标识符与类型，
豁免是一张**逐条带理由**的清单而不是通配：生成表（`events.rs` / `routes.rs`）
是清单的镜像，容器词出现在那里是控制面声明的事实名；core 的 `Event.turn`
与 loop 的 `t{turn}` 由 D-236 与本条 D-252 各自认下。判据只追溯 `BEFORE_GUARD` 之后
新写的端口形状，存量豁免同样逐条点名——把「已有」写成第二张基线，就是给自己留一条
慢慢变宽的路。

## 6. 与既有裁决的关系

- **D-208（判断闭集）** 按 D-240 收窄：闭的是强制点与顺序，不是判定的生产者。
- **D-222（端口闭集）** 不被推翻：模型往返是第三个端口，判据仍是「派出之后控制面
  不持有对方状态」；执行体不是端口，它是环内一步。
- **D-217（两个开关）** 不被推翻：链接期贡献与运行期停用的分界不变；第三方独立
  进程插件只能覆盖「会调用的东西」，本方案不改变这一点。
- **DE-021 §7（不再切插件）** 只适用于「按 crate 切控制面」的旧口径；按能力四元组
  拆分是另一件事（D-239）。

## 关键决策

本文持有**判据与纪律**的裁决。逐条能力落进某个能力包的**落地裁决**（`D-260` 起：一条行
产物、一次迁出、一张跨插件读面各自为什么长成那样）住在
[DE-045-能力包迁出与落地裁决](045-能力包迁出与落地裁决.md)——判据是闭表，落地是逐批增量，
两族写在一起迟早互相挤出位置。

### D-239 T1 是硬判据，T2 是终态

**裁决**：「一个能力一个插件」的硬判据是 T1（新增能力只改自己目录，控制面 diff = 0，
端到端通过）；本方案同时以 T2（存量拆除）为终态，不以 T1 代替 T2。T3 是两者的共同
底线。

**理由**：原判据把扩展（新增）与重构（拆除）混成一句。只做 T1，`loop` / `session`
仍是能力容器，控制面继续变胖；只按 T2 现状判「架构失败」，则用重构难度否定了扩展
可能。两个方向都有对象可指，才谈得上验证。

**被否**：只做 T1（存量不动，控制面继续长）；以 T2 的 0/32 直接判架构不可扩展
（没有先补执行体，等于用缺件证明缺件）。

### D-240 影响类闭集：判定可以开放，强制必须留核

**裁决**：能力对系统的动作收成 8 类（I-1…I-8）。能力可以产出判定（`FactDraft` /
`Verdict`）；授权、不变量、承诺配对、单写者顺序由引擎强制。新增影响类是架构变更，
新增能力不是。

**理由**：回放只承诺 L0 + L1，读日志、不重执行判断（[DE-001 §11](001-核心架构.md "DE-001-核心架构")），
所以执行体的位置不影响回放；真正不能被能力改写的是「什么算合法」，那是量词跨全量的
性质，插件看不见全量，放出去必然静默空转（J3）。

**被否**：把判定的生产者与强制点合成一个「判断闭集」（执行体因此无处可去）；影响类
按能力增长（端口数随能力数增长，拆了等于没拆）。

### D-241 通用行执行体：一次绑定，所有能力共用

**裁决**：新增一个 `ActorEntry` `plugin_row`，`run` 只做三件事：按声明把债实例与事实
切片经容器路由发出去、把 `Vec<FactDraft>` / `Verdict` 拿回来、交宿主唯一写口落格。
执行体只收纯值；`by` 由 `ActorDecl` 绑定；解析不到在 `seal` 期红。

**理由**：四元组里只有执行体不可插件（`ActorEntry` / `Action` 是 `loop` 的 `pub(crate)`）。
给每个能力加一个 `ActorEntry` 会让绑定表随能力数增长——那只是把 `loop` 的分支换成
`loop` 的表格，扩展性没有增加。通用执行体不认识任何能力名，顺序由既有 `prio` 决定，
失败由既有租约兜底。

**被否**：把 `&mut Ctx` 开给插件（持有整轮可变状态，顺序与失败都不可判）；按能力名
注册执行体（绑定表增长）；把 `TurnState` 复制一份给插件（两份真相）。

### D-242 模型往返是第三个端口

**裁决**：能力可以声明「这一步要一次模型往返」：宿主执行、预算与租约归宿主、请求与
应答落格；能力只给提示与解析函数（纯值）。端口满足 D-222 §一：派出之后控制面不持有
对方状态。

**理由**：反思、压缩、技能编译都需要 LLM；不开口，它们只能住 `loop`。这不增加一种
「判断」，只增加一次往返。

**被否**：插件直连 provider（凭据 / 预算 / 落格散落，且跨插件依赖 provider crate）；
宿主为某个能力特制原语（能力名进控制面）。

### D-243 上下文段有成本与优先级；省略是一条通用事实

**裁决**：`ContextSection` 增加成本与优先级，宿主按 owner 序收集后按确定规则裁剪、
超界报告；「某区间被摘要取代」是一条事实，组装按事实省略区间，不为压缩特判。

**理由**：多能力同时贡献段会撑爆窗口；今天只有「隐藏未选分支」一条硬编码规则，
它不能推广到第二个能力——那正是「加一个能力改一次组装」的形状。

**被否**：每个能力自己调窗口（预算没有唯一裁决）；按插件名判断省略（能力名进控制面）。

### D-244 Entity 是封闭语法，能力不得新增实体

**裁决**：`Entity` 保持 12 个变体的闭集（含 `Domain` 一个扩展位）；能力包只声明事实
名与格位，不得新增实体；新领域落 `Domain`，`core` 一律不解释。新增实体是架构决策，
默认答案是「用 `Domain`」。

**理由**：实体是本体，不是能力。开放它会丢掉读侧的穷尽检查（J3），而 12 个实体已经
覆盖核心语义（轮、任务、产物、裁决、记忆、承诺、意图、会话串、控制、系统、消息、领域）。
三个代表能力都用现成实体：反思 → `Memory` / `Domain`，压缩 → `Message`，主动开口 →
`Turn` 或收件箱事实。

**被否**：`Entity` 改成任意字符串；一个能力一个实体。

### D-245 迁移纪律：先落插件，切换与删除同提交

**裁决**：允许插件先落（未绑定、不生效），但「绑定切换 + 旧实现删除」必须在同一提交；
禁止两份实现同时生效；每一刀带 T1 / T2 / T3 三条用例与一条反向用例。

**理由**：双生效 = 两套语义 + 回放分叉；先删后建 = 中间态系统不完整。两者都会让
「拆到一半」的状态无法判断。

**被否**：灰度双写；用配置开关长期保留两份实现。

### D-246 名册 54 行逐条处置，能拆都拆

**裁决**：[DE-008](008-能力注册表与能力坐标系.md "DE-008-能力注册表与能力坐标系") §6.1 的 54 行名册是拆分账本的**完整输入**；
终态要求每一行恰好一条处置——要么搬进能力包（指得出 crate），要么留守并写明残留类
与理由。合法留守只有：**E 机制本体**、**I-7 过程体**、**I-8 强制点**、**环 / 写口 /
会话基底**、以及「另一读者尚未改名字读」的共享折叠（D-221 的过渡态，必须挂任务）。
「今天没有端口」「拆起来难」不是留守理由；既有按消费方归 owner 的裁决（D-190 等）
只说明今天住在哪，不构成留守理由。A 类行（今天即可插件）不进迁移账，但必须以能力包
落地作为正向验证；B 类行先裁决端口，未裁决前记为「待决策」，不是留守。

**理由**：「32 条已锚定 0 条可拆」量的是**端口缺口**，不是本体的可拆性；只补端口
不逐条处置，会停在「新增可以、存量不动」的半程。逐行账是唯一能防「拆到一半宣布完成」
的形状，也是「一个能力一个插件」这条不可妥协项的兑现方式。

**被否**：按五档原样接受（把今天的端口缺口当终态）；只拆 `loop` / 只拆带模型往返的；
把读数类折叠排除在账本外（它们同样是控制面里的能力名）。

**对 D-190 的限定**：D-190 的三分里，「抢占 → session」「熔断 → loop」是 **crate 归属**，
按本裁决迁到各自能力包；「淘汰裁决留核」不变（它在名册 #30，属 E）。

### D-247 拆分以架构设计为前置；机制增量显式、通用、不夹带

**前提**：本裁决落定时的架构**不足以**支撑存量横向拆分——端口缺口是实测的，不是猜测（I-1 轮级写、
I-4 模型往返、I-2 成本与优先级、I-5 通用省略各缺一项）。所以「拆分期间架构不动」不是本裁决的
内容：补端口与通用件**是拆分能否发生的前提**，D-240…D-243 落定之前，任何「0/N 可拆」的读数
都只是缺件的读数。

**裁决**：机制增量与迁移搬运**分成两类提交**，各有各的判据：

1. **架构补件**（可改 `core` / `kernel` / `plugin-api`）：

   - 必须先有一条 `### D-NNN` 说清「哪条能力因缺它而迁不动、它服务哪些能力」；
   - 必须**通用**：不含任何能力名 / 工具名，至少服务一条真实能力（不是为单条能力定制的通道）；
   - 影响类若新增，仍是架构变更（D-240），不因「为了拆分」而放宽；
   - 补件落地后，被它解锁的那一行回到迁移批次。

2. **迁移批次**（S6 起）：

   - `core` / `kernel` diff = 0；**订正（`D-283`）**：判的是**变宽**不是「碰过」——
     机制面**新增行为 0**，删除行照放（折叠住在 `sdk/projection/` 的那一批要靠同一次
     提交把旧实现删掉），树名单随 `D-279` 是 `sdk` / `kernel` / `plugin-api`；
   - `loop` / `session` 的 diff 只含**删除**旧实现与**切换绑定**，不夹带新机制——行、执行体、
     分支、常量、状态字段都不许为某条能力新加；
   - 生成物与装配链接行可以随插件增删，它们不是机制。

若某一批发现「还需要一条机制才能迁」，说明**前置设计不足**：停下这一批，按第 1 类补决策与
独立提交，再恢复迁移；不许在迁移提交里顺手加。判失败的只有三件事，与「有没有加机制」无关：

- **夹带**：机制混在迁移提交里，使「这批只靠搬运」的验证信号失真；
- **定制**：所谓端口只服务一条能力、带着能力名，那只是把分支改名成 trait；
- **反向拆分**：把某条能力的**实现**从 `loop` / `session` 搬进 `core` / `kernel` 或另一个
  控制面模块来「满足」封闭集——功能代码进了架构，控制面没变薄。

**理由**：要验证的是「架构够不够」，不是「拆分者有多能绕」。把两件事塞进同一个提交，红绿就
不再说明任何时候；分开之后，每条能力的迁移 diff 本身就是「这条能力只需要端口 + 搬运」的证据，
而任何一条停在迁移批次门口的能力，都精确地指出还缺哪一项机制——这正是本方案想要的读数。

**被否**：迁移期一律禁增（把端口缺口当成永久结论，等于放弃拆分）；迁移期「先加后删」
（中间态两份实现）；按能力补端口（端口数随能力数增长）；把判定实现搬进 kernel 以绕开控制面
（反向拆分）。

### D-248 行级写入归属：共享执行体的收口与依赖图按行判

**裁决**：装配方把每条行实现声明的逐行写入名单（`RowHandler::writes`）作为
`Builder::seal` 的输入交进去；装载期第 6 条（执行体收口）与依赖图按**这一行**
的名单判。没有逐行名单的行（`run` 就是那一行自己的执行体）退回 `ActorDecl.writes`
——那是该行自己的名单，同一条口径。

**理由**：`ActorDecl.writes` 是**执行体级**的并集，够通用行执行体（D-241）让多行共用
一条声明；但并集包含每一行自己的出口，第二行一出现，每行的出口都会被「别的行」认领，
依赖图退化成完全图，任意两行成假环。这是 S4 夹具落第二行时实测到的
（`notes.index` ↔ `notes.reflect`），不是预判。逐行名单本来就由能力实现声明、运行期
已按它对账；交给装载检查只是让静态判据与运行期判据同源，没有新增第二份真相。

**被否**：给每一行注册一条 `ActorDecl`（绑定表随能力数增长，D-241 已否）；对共享
执行体的行整体放弃成边（真死锁也看不见）；把逐行名单复制进 `Decl`（同一个事实两个
声明位，静态与运行期会漂移）。

### D-249 区间省略是一条事实：`message.added` 带 `elision`，与未选中分支共用同一个应用点

**裁决**：「某段历史被摘要取代」写成一条事实——`message.added`（`message × opened`）
的载荷带 `elision: { from, to, reason }`，`from` / `to` 是事件 `seq` 的闭区间，载荷里的
`messages` 是取代那段区间的正文。组装 prompt 时「哪条事件不读」只有一个函数
（`Elisions::elides`）：显式区间与既有的「未选中分支」（D-173 的折叠）在同一个判据上
合流，转写投影与 D-048 的双向复核**共用同一份**——两个出口各判一遍的分叉是静默的。

`message.added` 因此有两副面孔，判别位是载荷带不带 `elision`（`is_replacement`）：

- **不带**：界面卡片（D-054 决策 1）。`exclude_from_context` 恒为真，行为逐字不变；
- **带**：取代正文。载荷节点按自己的 `meta.exclude_from_context` 进请求包（与压缩快照
  同一份翻译），被指区间里的旧事件照进转写、只标「不进请求包」。

区间只认存储分配的 `seq`：轮号不唯一、下标随切片漂移；`seq: None`（夹具 / 未落盘）
不命中显式区间；`from > to` 或非正整数视为没有省略——容错方向是**少藏**，多藏一段
模型看不见的话不会报错。

**理由**：一次压缩是**原子陈述**——取代物与被取代的区间必须在同一条事实里，读者不可能
只读到一半。拆成两条事件要靠连接键再拼回来，而「两条事实之间的一致性」正是事实网格
不保证的东西。正向证据：`notes` 夹具的 `notes.summarize`（摘要落 `message.added`，
区间取那次工具结果的 `seq`）与 `e2e/cases/t91-notes-elision.mjs`。

**被否**：新开一个 `context.elided` 事件（取代物与区间分成两条；且 I-5 与分支本该是
同一条形状，新事件就是第二种）；在组装点按事件 kind 特判压缩（能力名 / 事件名进控制面）；
每条能力自己调窗口或自己过滤历史（预算与「哪段不读」没有唯一裁决）。

### D-250 收束贡献：能力在收束之后以纯值交派生事实

**裁决**：收束之后的派生事实（记忆编码与巩固、技能编译、任务调度…）走第四个端口
`Contributor`（模块 [`settle`]，读作「收束这一刻」）：能力提交一个纯函数
`contribute(&Settling) -> Vec<Contribution>`，宿主在轮收束之后按 `(prio, owner)` 逐个
询问，**每问一个之前重取一次史**（后一个贡献者看得见前一个刚落格的草稿），再经唯一
写入口落格。草稿的 `turn` 与 `ts` 由宿主盖章（`ts` = 本次收束时刻）；`actor` 可由能力
声明——记忆的事实归认知归属人（`person/local`），与跑轮主体可能不同。`Settling` 交的
是收束这一刻的值：面（生成 / 定稿答话）、时刻、主体、溯源锚、**幂等词干 `anchor`**、
用户发言、收束正文、完整史——没有轮号，也没有配置包（见 D-252）。

**理由**：这一族贡献**天然可能为空**（空发言不编码、活记忆不足四条不巩固、没有就绪
任务不派活）。写成环上的债，就要给每条能力编一个永远空转的 `owes`，环会在同一个债上
反复选中它直到步数上界；「贡献」不是欠账，空是合法结局。也不走效果端口：效果由一次
工具调用触发，这里由「这一轮收束了」触发，且要看得见完整史。按序刷新史则把依赖
（编码 → 巩固、任务表 → 调度）做成端口上的一格 `prio`，而不是藏进贡献者的内部状态。

**被否**：把轮末派生事实并进 `plugin_row`（空转债）；给贡献者 store 句柄（写口不唯一、
顺序不可判，与 D-241 同一条否定）；由宿主按能力名调用（那正是今天的形状）。

### D-251 提示前不开端口：摘行与抢先作答各走既有的两条面

**裁决（否定）**：不为「提示成形之前」新开端口。原先提议的第五个端口 `PromptGate`（能力
提交 `filter` 摘行 + `answer` 抢先作答，宿主在召回视图成形之后、段渲染之前逐个询问）
**整条撤回**，`symbio-plugin-api` 不设 `gate` 模块：端口是给多条能力共用的形状，一项
**单消费方**的需要不构成端口——`PromptGate` 的提议者只有技能能力一条，入参还把召回
视图的行（`RecallLine`）包了进去，那是业务视图，不是宿主面。

两项需要各归既有的面：

- **抢先作答**是「不调模型也能落一条收束」，落在 I-1 的**反射行执行体**：能力行返回
  `RowStep::Facts` 即零模型往返写格（`plugin_row`，D-241），草稿由宿主写口盖章。判断
  「这一轮该不该照固化套路答」是能力自己的事，读的是它自己的事实（开关在
  `session.config`，D-252），宿主不按能力名分支。
- **摘行**是**读方的过滤**，走 D-221 的**名字读**：渲染召回段的 provider 按名字读技能
  能力落的「这条技能最近回退过」事实，自己决定这一行不渲染。摘行与渲染因此同处一室
  ——这正是原提案要避开的「两处必然漂移」；而它恰恰说明不需要宿主代摘。

**被否（保留记录）**：给 provider 改写别人段的权力；在 `loop` 里按能力名分支；每个闸
各持一个写口。这三条与原提案的否定理由相同，且在新裁决下根本不再出现——没有闸，就没
有「闸的写口」。

### D-252 扩展面不说容器词：端口只交词干，开关是一条事实

**裁决**：`turn`（轮次）是业务容器概念，不是架构语义。[DE-001](001-核心架构.md "DE-001-核心架构")
定的引擎契约写得直白：「引擎只认识七个词……没有 `model`、没有 `tool`、没有 `turn`」；
[DE-051](051-机制形状规格.md "DE-051-机制形状规格") 的端口闭集不收 `turn` 端口群——
`announce-model` 这一类名字里的 turn 是幕的残留。
[DE-012](012-会话输入与地址.md "DE-012-会话输入与地址") D-236 又裁定 `Entity::Turn` 是
**格位身份**而不是轮次节点。本条把同一条裁决推到能力面：

1. **端口输入包里没有轮号**。`ContextRequest` / `EffectEnv` / `EffectCall` /
   `RowRequest` / `Settling` 一律不带 `turn`；需要跨请求唯一的幂等键时
   读宿主给的 `anchor: &str`——`t{turn}` 这一行住在控制面（轮号的唯一分配点），能力
   只拿到一个不透明词干。`FactDraft::into_event` 不再收轮号，`Event.turn` 由宿主在
   落格时盖。
2. **端口不接配置包**。撤销 `TurnSettings` 进能力面（原 `TurnEnd.settings`）。能力要读的开关是**一条事实**：宿主把当轮生效的配置投影
   落成 `session.config`（它本来就只让决策读这条快照，不读 `SessionConfig` 活值），
   能力按共享名读自己那一格，读不到就用出厂值。两侧都不新增机制：写方与生效时刻都已
   存在，名字走 `PLUGIN.yml` 的 `shared_events` 进生成表（D-204）。
3. **端口与类型名去掉容器词**。轮末贡献 → **收束贡献**（模块 `settle`、
   `Contributor` / `Settling` / `Contribution`）；上下文节奏 `Cadence::Turn` →
   `Cadence::Utterance`（一次发言收一次 / 一次请求收一次）。「提示前闸」不再有类型可改
   ——整条端口已撤回（D-251）。

判据 `EX-008` 把这三条钉在门禁里：`crates/symbio-plugin-api` 的**非生成**源码里，端口
形状（类型名、trait 名、枚举变体、字段名、`pub fn` 形参）不得出现容器词。有名豁免三处
——① 生成表里的事实与格位名（`events.rs` 的 `turn.*`、`Entity::Turn`：那是控制面声明的
**事实名**，不是端口形状）；② 控制面的轮号分配与词干生成（`loop` 的 `t{turn}`）；
③ core 的信封字段与按它折叠的 I1 / I3 不变量。

**理由**：

- **容器词进端口 = 能力被迫认识宿主的时间单位**。新架构里一次模型请求与一次工具交换
  是两个端口（D-222 的往返身份格 + D-213 的效果写口），承担判据的是「哪一次往返」
  「哪一笔债」，不是「第几轮」。端口交 `turn` 就是把已经退役的幕重新发给每张能力表，
  而能力一旦按它算，环的边界变了它就跟着错。
- **幂等只需要一个不重复的词干，不需要那个词干的含义**。`{anchor}-s{n}`、`v2c-{anchor}-{call_id}`
  要的是跨请求唯一；宿主给一个不透明串就够，给数字等于邀请能力自己拼 `t{turn}` 或
  按轮号算别的东西——那才是真的把轮次变成能力面的判据。
- **配置包是更大的一次泄漏**：`TurnSettings` 十五格里只有一格（`progress_max_per_turn`）
  真的与轮次有关，交整包等于把控制面的配置类型变成每个能力包的依赖，也等于给「加一个
  开关就动架构面」留一条常开的通道。`session.config` 本来就是宿主给决策读的**当轮快照**
  （控制面文档明写「决策只读它，不读 `SessionConfig` 活值」）——把同一条口径推到能力面
  不新增机制，只是让开关有一个事实形状。读不到的缺省用 core 的出厂常量（`TASK_CAP`），
  与「临时会话没有事实源」的既有分支同形。

**被否**：在端口上单列某一格（`task_cap: usize`，D-215 的老形状——每加一个开关就在
`ContextRequest` 上凿一个洞）；交整份 `TurnSettings`（本条作废它的落地：能力读宿主的
配置结构就是反向依赖）；让能力自带配置面（PLUGIN.yml 私有键）——生效时刻
会漂，且绕过了「决策只读快照」那条既有纪律；彻底废除 `turn`——I1（每轮至多一条定稿、
开格唯一）与 I3（未闭合配对）按它折叠，会话 WAL 的写闸也按它判，那是**网格身份**不是
端口词汇（D-236 已裁，豁免②③ 就是它的边界）。

### D-283 迁移批可以把折叠从机制面删走：`EX-007` 判的是「变宽」，不是「碰过」

**裁决**：`EX-007` 对迁移批的机制面口径从「三棵架构树（`symbio-sdk` / `symbio-kernel` /
`symbio-plugin-api`）的非生成 `.rs` **diff = 0**」改成**「新增行为 0，删除行不限」**。
`S8` 的一批因此是一个提交：折叠落能力包 + 第二读者改名字读 + 机制面那条折叠整文件删除。

**为什么非改不可**（两条判据互相挡住，不是便利）：

1. `S8` 那六行的搬法是**一条动作的两半**：同一提交把第二读者的类型读改成
   `ViewRead::named`，并**删掉机制面那条折叠**。`D-245` 的「绑定切换 + 旧实现删除同提交」
   落到它们（名册 #18 / 19 / 20 / 22 / 23 / 28）身上，删的就是机制面的文件——那些折叠
   今天住在 `symbio-sdk/src/projection/` 里，§2.3 账里那一列写的就是它们的位置。
2. 树名单在 `D-279` 之后从 `symbio-core` 扩到 `symbio-sdk`，判据文字照抄了旧范围的
   「diff = 0」，于是同一次删除从「旧实现删除」变成了「迁移夹带机制增量」。这条冲突
   不是判据太严，是它判错了对象：`EX-007` 存在的全部理由是「别在迁移批里给机制面
   **开新口子**」（`D-247`），删除一条折叠是反方向。
3. 全仓对机制面的通用口径本来就是**只许降**：`CS-001` / `CS-002` / `HS-002` / `PP-004`
   都是「变宽即红、收窄只提示」。迁移批单独要求「一分不碰」，等于把棘轮的下方也封掉，
   而 `S8` 整段的产出就是那一条下方。

**保留的强度**（没有一处变松）：

- 机制面**新增**一行非生成源码 ⇒ 照旧红。为某条能力在 `sdk` 加一个分支、把实现搬进
  机制面凑封闭集（`D-247` 的反向拆分）都在这一档；改法只是把「diff = 0」换成「added = 0」。
- 搬走的折叠必须**落在能力包里**并被读到：`PP-003`（构造器在折叠目录之外要有生产
  消费方）、`E-009` / `CS-007`（名字与 owner）、`HS-002`（门面三臂只许降）同批判它。
  删了不搬 = 功能消失，由端到端与 `EX-004`（可卸载性）判，不由本条判。
- 控制面（`loop` / `session`）那半条一字不改：不许新增带能力名的行，且至少删掉一行
  旧实现（`EX-003`）。

**理由**：

- **判据要判意图，措辞不能承载意图**。「写了 `Migration:` 就必须机制面零改动」会让
  诚实的作者去做两件更坏的事：把 trailer 省掉（`EX-003` 从此判不到这一批），或把一批
  拆成三个提交——中间那个提交里折叠已无人消费，`PP-003` 当场红，而它没有任何一条
  判据是在保护的东西。
- **「旧实现」住在哪是历史，不是所有权**。`D-245` 禁的是两份实现同时生效，不是禁
  机制面变薄。`S8` 的存在理由（`PP-004` 把「折叠长回 core」判成机器可红的病）恰恰
  是要把这些文件从机制面删走。

**被否**：

- **拆成「包先落 → 切绑定 → 删机制面」三个提交**：第二个提交的 `PP-003` 红是必然的
  （构造器失去全部生产消费方），六行折叠就要挂六次「已知红」；而 `D-245` 允许的两步
  形状是「未绑定、不生效」，不是「已生效两份」。
- **迁移提交不写 `Migration:` trailer**：`classifyCommit` 因此不去判它，`EX-003` 的
  「同提交删除」也一并失效——为了让一条措辞不红而取消声明，是把判据换成沉默。
- **在 `sdk` 留一行 `pub use` 转发**：`D-272` 刚把根出口从 324 收到 34，转发桩是往回走，
  而 `PP-004` 数的就是这些文件还在不在。
- **给 `S8` 单开一类「搬迁批」（新增第三种 trailer）**：三类提交变成四类，每加一类
  就多一处「声明错了类别」的漏洞；而本条不需要新类别，需要的只是让原有类别判对它
  真正在意的那个方向。

**落地**：`scripts/capability-migration-audit.mjs` 的 `migrationErrors` 里那条
`archTouched`（`(added || removed)`）改成 `archAdded`（只看 `added`）；回归测试把
「迁移提交改 SDK 机制面 ⇒ 红」钉成「**新增**源码行 ⇒ 红」，并补一条正例「机制面整文件
删除 + 行落在能力包 ⇒ 绿」。第一个按新口径走完的批次是 `S8a`（名册 #18 成本台账 →
`crates/symbio-plugin-cost`）。

### D-294 首条能力准入：≥1 条能力 + 明确的移除计划，计划缺一即「无计划」

**裁决**：修订 `D-269` 的第一条准入。新开一格扩展面的准入从「不提能力名 ∧ **≥2 条
能力**」改为「不提能力名 ∧ **≥1 条能力 + 明确的移除计划**」。移除计划由三样组成，
缺一即判「无计划」：

| 项 | 形状 | 怎么判 |
|---|---|---|
| 期限 | 一个日期（`YYYY-MM-DD`），落在未来 | 日期可解析，且晚于账本登记日 |
| 触发条件 | 第二条能力何时出现（一句可判定的条件，不是愿望） | 写在骨架行上，能回答「满足 / 不满足」 |
| 承接任务 | 一个存在的任务编号（`T-NNN`） | 在任务表里查得到、状态非 done / wont，且沿它的 `deps` 闭包走得到本行的宿主任务 |

**承接必须是任务，不接受 `D-NNN`**：`deps` 闭包只有任务才走得了；设计决策没有承接关系，
把它写成承接方等于让「谁来做」落空。

`D-269` 的其余部分原样：位置仍是闭表、三格仍明确无位、第二条准入（**不提能力名**）
不变、`HS-002` 与 `EX-007` 的两个计数器不变。判「无计划」的执行方沿用
`scripts/capability-ledger-audit.mjs`（`EX-006`），不新开脚本。

**理由**：

1. **「≥2 条」把单例族按数学排除，而不是按判断排除**。`D-269` 的站位表把「一格」定义为
   一族时机；真实能力里有单例的（首条读数型能力只有一条），「等第二条」等于要求先造一条
   没有需求的同类能力来满足计数——这是用数量替代论证，与 `D-269` 理由 1 反对的「族不可
   证伪」是同一个病，只是方向相反。
2. **计划三样都能机械核对**。日期可解析、任务号存在、触发条件写成一句可判定的话——三者
   不需要 review 解释「你为什么觉得会来第二条」；它们把「暂开一格」从承诺变成债。
3. **`≥1` 只放数量，不放「不提能力名」**。第二条准入仍要求位置名与能力名分离：单例能力
   可以把行与执行体放进自己的包，但扩展面的格名不许是它的名字。放宽的是「几条」，不是
   「谁的名字」。
4. **首条落地必须有骨架，骨架必须有退出路径**。没有计划的骨架是永久面；`HS-002` 的棘轮
   只判「不涨」，判不到「这一格本来是临时的」。把期限与承接任务写进账本，`EX-006` 才能
   在第二条落地时判「骨架删了没有」。

**被否**：

- **C1：准入仍写 ≥2，计划另行记账**。「计划」没有宿主就没有判据；而 `≥2` 仍然数学排除
  单例族，等于把 `D-269` 的空格永远留着。
- **C3：单例族永远不做**。首条读数型能力是真实需求（`S9` 有一条），按它不做等于让名册里
  的「拆（未落地）」永久停在承诺上。
- **只写一句「单例可以例外」，不写三样**。例外句不可判定，下一次开格照样没有代价；
  `D-269` 理由 2（增长没有代价就会一直长）原样成立。
- **直接改写 `D-269` 原文、不留原裁决与锚点**。历史锚点是判据的一部分：`D-269` 的两条
  准入、三个空格与两个计数器是它当时的裁决，修订只能加注记指向本条，不能把原文改成
  「一直就是 ≥1」。
- **为「无计划」新开脚本**。`EX-006` 已经在读账本与名册之间的对账；计划三样是账本行的
  三个字段，加一张表比加一个脚本窄。

**代价**：单例能力可以先进骨架，代价是账本上多一行有期限的临时面；期限到而第二条未出现
时，承接任务必须做出「删骨架」或「续期并说明」的裁决，续期不能静默。`capability-ledger-
audit` 的账本读取多三列，骨架行的维护成本高于常驻行。

**判据**：

- 账本里每一条「首条 + 骨架」的行，期限 / 触发条件 / 承接任务三样齐全；缺一，`EX-006` 红。
- 期限已过、或承接任务编号不存在、或 `deps` 从该任务到不了骨架行 ⇒ `EX-006` 红。
- 第二条能力落地时，同一提交删除骨架行或把它切到第二条的绑定（`D-245` 的「未绑定、不
  生效」→「已绑定、单份生效」），账本同步。
- `D-269` 的其余准入与两个计数器仍按原文判，不因本条放宽。

**与既有裁决的关系**：

- `D-269`：只修订第一条准入的数量与计划要求；位置闭表、第二条准入、两个计数器与聚合
  触发「没有位置且不开」全部原样。原文保留，本条是其订正。
- `D-291`：`D-291` 的四块按「不开放的位置」判不成批；本条不改变那些位置的性质，只回答
  「如果将来要开一格，准入是什么」。
- `D-020` / `D-228`：准入只判扩展面的新位置，不判对话面 / 阶段格的写口；两处的唯一写口
  不因本条变化。
- `D-093` / `D-222`：准入判据不进行、不进环，环的选债与一次一笔债不变。

**落地**：`scripts/capability-ledger-audit.mjs` 的账本行多读三个字段（期限 / 触发条件 /
承接任务），无效即 `EX-006` 红。第一个按本条开出骨架的是 §2.3.1 里 S9 那条读数型能力：
#34 预测（`crates/symbio-plugin-forecast`），骨架计划见 §2.3.1 #34 行（期限 / 触发 / 承接
三样都在那里判），端到端读数在 `e2e/cases/t95-forecast-remaining.mjs` 读回
`forecast.remaining`。当前 `EX-006` 报「名册 54 行 = 账本 54 行（拆 32 · 留守 21 ·
不做 1 · 待裁决 0）」，计划三样齐全。

### D-331 B 类死码以台账为唯一判据：未接回的能力不许静默存在

**背景**：B2 删掉旧编排之后，`crates/symbio-plugin-session` 里留下一批「能力还在、生产
调用方随旧编排一起消失」的符号（`cargo check --workspace --all-targets` 实测 30 组 /
52 个符号）。它们不是该删的死代码——收件箱、抢占、压缩、补充整合、记忆召回这些能力在
新义务环里都有位置（批次见台账 `batch` 列）；但也正因为如此，`clippy -D warnings` 会把
它们变成一张永远红的清单，而「先加 `#[allow(dead_code)]`」会让判据从此看不见任何新死码。

**裁决**：

- **台账是唯一的豁免形态**：`scripts/exemptions/session-dead-code.json`（`rule: D-331`）。
  每行记 `path` + `symbols` + `capability`（这项能力是什么）+ `future_caller`（将来谁
  调它）+ `batch`（接入批次）+ `e2e`（关联用例）。`landed_batches` 记已落地的批次名。
- **判据**：`scripts/session-dead-code-audit.mjs`（`SD-001`）挂在 backend 阶段、与 clippy
  同泳道；clippy 参数加 `-A dead_code`，这一族的豁免与销账归台账判。
- **四条红**：源码报 `dead_code` 而台账没有该符号 ⇒ 红；台账有而源码已不再报（已有生产
  消费者或符号已不存在）⇒ 红，要求删行；某行所属批次已写进 `landed_batches` ⇒ 红，要求
  销账；源码出现 `#[allow(dead_code)]` / `#![allow(dead_code)]` ⇒ 红（`cfg_attr(not(test)
  , …)` 不是生产豁免，不在禁止面）。
- **台账为空且源码无 `dead_code` = 能力全部接入完成**（判据给绿）。台账不是保险：每一行
  都是「这项能力还没接回来」的欠条，接入完成必须销账，不得长期保留。
- 清单本身不进本文：符号会随接入逐行消失，复制一份正文必然漂移；要读当前欠条就读台账。

**与既有裁决的关系**：`R-001`（pub 声明级死码）与 `R-002`（承认标记要有理由）照旧，本
条只判 `dead_code` 这一族在 `symbio-plugin-session` 的欠账面；`-A dead_code` 只让开这一
族，其余 clippy lint 一条不放。

### D-372 扩展本地性只有一套口径：五棵树 + 补件/迁移付账线

**背景**：同一个「新能力只改自己目录」在三处写成三套：拆分总任务的 exit 是
`kernel` / `plugin-api` / `loop` / `session`（漏 `sdk`）；A 类能力插件化任务的 exit 是
`kernel` / `loop` / `session`（`plugin-api` 只做能力名限制）；`extension-locality-audit`
的 `TREES` 是 `sdk` / `kernel` / `loop` / `session`（漏 `plugin-api`）。实际执行的是
最后一套，于是「加能力时顺手给 `plugin-api` 加一个 `pub`」在三处都被放过。
同一段文字里还有一个手写读数「补件 20 / 迁移 5 = 4:1」——实测是 21 / 15 = 1.40:1；
手写数字漂了，而没有任何一道门会因为它漂了而红。

**裁决**：

1. **唯一口径 = 五棵树的并集**：`sdk` / `kernel` / `plugin-api` / `loop` / `session`，
   常量只定义在 `capability-migration-audit.PROTECTED_TREES`，
   `extension-locality-audit.TREES` 直接引用；两条任务的 exit 写同一组名字。
   **为什么以最宽为真**：少一棵就留一条「加能力时顺手改这里」的路，而 `plugin-api` 恰恰
   是能力最常伸手的那棵——它长得最像能力的地盘，才最需要在判据里被点名。取并集而不是
   交集，是因为任何一套旧口径出现过的树，都是某一套口径认为该守的。
2. **补件/迁移比进门禁**：判据落地当天的存量记为**欠账本金**
   （`BASELINE.capabilitySupplements = 21` / `capabilityMigrations = 15`）。此后
   `debt = (补件 − 本金补件) − (迁移 − 本金迁移)`；`debt > 0` ⇒ 红。目标仍是累计
   ≤1:1，但**不拿比值当阈值**：计数随范围基线变化，比值会假红；差值只在真实新增时变。
   比值与目标缺口每轮打印，作为读数。
3. **读数为准**：拆分总任务里的手写数字删掉，改为「以 `capability-migration-audit`
   的输出为准」；`20 / 5` 这类快照不再出现在文档里。

**判据**：

- `node scripts/extension-locality-audit.mjs --strict` 打印五棵树，夹具 `f5e4bbed` 绿；
  加一个只在 `plugin-api` 手写面上改动的能力包 ⇒ 红（单测）。
- `node scripts/capability-migration-audit.mjs --strict` 打印累计比与欠账；
  自判据起只补不搬 ⇒ 红（`supplementRatioReading` 单测）。
- 两处口径同时变红或同时变绿：`TREES` 与 `PROTECTED_TREES` 是同一个数组，不存在第三份。

**不做什么**：不为历史提交重写历史。口径加宽后按新口径会红的四个存量提交进
`GRANDFATHERED`，逐条写清「当时判据不含 `plugin-api`、改的是 `behaviors.rs` 中心名单
（D-363 已退场）与清单镜像」；名单只减不增。
