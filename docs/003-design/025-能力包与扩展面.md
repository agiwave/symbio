# 能力包与扩展面

> **一句话**：能力的实现、状态、时机、效果、上下文、配置与身份**随能力包走**；
> 架构只保留**影响类**（能力能对系统做的八件事）与**执行顺序**。
> 新增能力 = 在已有影响类里落一个实例；只有新增影响类或新增实体才改架构。

本文回答「加一个能力为什么还要改架构」以及「改成什么形状才不用改」。契约的共享面
（事件格位、跨插件地址、声明收集）归 [DE-024](024-能力横向扩充的通路.md "DE-024-能力横向扩充的通路")；内核边界与
封闭语法清单归 [DE-023](023-内核边界与扩展局部性.md "DE-023-内核边界与扩展局部性")；本文只定义**能力包**这一层。

**目标是全面的拆分，不是「新能力可以做成插件」的弱化版**：`loop` / `session` 里不得
再按能力名存在分支、行、常量或策略；它们留下的只能是**环、写口、全局守门、过程体、
会话基底**五类，且每一类都要逐条写明「为什么它不是能力」（§2.7 的残留账本）。
判断这句话是否兑现，看的是「删掉了什么」，不是「新增了什么」。

## 1. 三个词

**能力包** = 一个插件 crate 加上它自己的全部声明：

```text
crates/symbio-plugin-<cap>/
  src/tool.rs        Capability 实现
  src/decl.rs        EventDecl / FactDecl / ViewDecl / Rows
  src/row.rs         行执行体：纯值进、数据出（D-241）
  src/behavior.rs    ToolBehavior（前置判断 / 后置效果）
  src/context.rs     ContextProvider（每次上下文收集贡献）
  src/settle.rs      Contributor（收束之后以纯值交派生事实，D-250）
  src/projections/   只给自己读的折叠（D-221：读者只有 owner 时住这里）
  PLUGIN.yml         plugin_id / assembly / routes / shared_events / shared_views / principals
```

**判断种类** = 架构必须认识、且只能由架构定义的**语义**：事件动词、判据角色、权威动作、
停机原因、协议事实、写闸与不变量。它回答的是「一条事实**是什么意思**」。
新增一种判断种类是架构变更；新增一个能力**不是**。

**影响类** = 能力能对系统做的**动作形状**。它回答的是「能力**能做到什么**」，与
「它根据什么判」分开：能力可以**产出**判定（一条事实、一次放行/拒绝），但「什么算
合法」由引擎的全局守门**强制**。影响类是闭集（[DE-026](026-能力拆分与影响类.md "DE-026-能力拆分与影响类")
的 I-1…I-8），能力是它的实例，因此闭集有限、能力无限。

## 2. 扩展面

下表是能力包能提供的全部声明面，每一面都已落地；各影响类的读数逐行见
[DE-026](026-能力拆分与影响类.md "DE-026-能力拆分与影响类") 的 I-1…I-8。

| 面 | 归属 | 架构提供什么 | 加一个实例要改哪 |
|---|---|---|---|
| 工具 | 能力包 | `Capability` trait、注册表 | 自己的插件 |
| 事件 / 事实 / 视图 | 能力包 | 声明容器、`seal`、写闸 | 自己的 `decl` + 跨插件时自己的 `PLUGIN.yml` |
| **折叠（投影）** | 能力包 | `Projection` 框架 + `ViewDecl` + 按名字读口 | 自己的 `projections/`（自读）或 `decl` + `shared_views`（给人读） |
| 跨插件地址 | 能力包 | `routes.rs` 生成物 | 自己的 `PLUGIN.yml` |
| **效果** | 能力包 | `ToolBehavior` 端口 + `FactDraft` | 自己的 `behavior.rs` |
| **前置判断** | 能力包 | `ToolBehavior::before` 端口 + `BeforeRequest` | 自己的 `behavior.rs` |
| **上下文** | 能力包 | `ContextProvider` 端口 | 自己的 `context.rs` |
| **领域** | 能力包 | `Entity` 的 `Domain` 扩展位 + owner 声明 | 自己的 `EventDecl` |
| **行为** | 能力包 | `CapabilityMeta.behaviors` 开放集合 | 自己的行为名 + handler |
| **主体 / 权限** | 能力包 | 清单生成 `authz` 行 | 自己的 `PLUGIN.yml` |
| **行 / 执行体** | 能力包 | `Decl` + `ActorDecl` + 通用执行体 `plugin_row`（D-241） | 自己的 `decl` + `row.rs` + 自己的 `PLUGIN.yml` 路由 |
| **模型往返** | 能力包 | 第三个端口：宿主执行、预算与租约归宿主、请求应答落格（D-242） | 自己的 `row.rs` 里声明提示与解析 |
| **收束贡献** | 能力包 | `Contributor` 端口 + `Contribution`：宿主按 `(prio, owner)` 询问、落格前刷新史；信封由宿主盖，端口只交幂等词干（D-250 / D-252） | 自己的 `settle.rs` |
| **上下文省略 / 段预算** | 能力包 | 通用省略（`Elisions` + `message.added` 的 `elision`，D-249）与段的成本 / 优先级声明（D-243） | 自己的 `decl` + `context.rs` |

### 2.0 能力的形状：四元组

任意一条能力，按机制拆开只有四个成员：

| 成员 | 回答 | 由谁提供 | 今天的可插件性 |
|---|---|---|---|
| **事实** | 它读写哪些格位 | 能力包的 `EventDecl` / `FactDecl` | 可（D-209） |
| **视图** | 它怎么把事件流折成读数 | 能力包的 `ViewDecl`（自读或共享） | 可（D-221） |
| **行** | 什么时候它欠一笔账 | 能力包的 `Decl`（`owes` 指向事实或视图） | 可（D-241：`decl` 交行，`by` 写 `plugin_row`） |
| **执行体** | 欠账时做什么 | 能力包的 `row.rs` | 可（D-241：`submit_row!` 交实现，`rows::RowHandler::run` 收纯值、交草稿） |

所以「一个能力一个插件」是否成立，只取决于一个二元问题：**插件能不能提供一条行的
执行体**。四者的可插件性都由 D-209 / D-221 / D-241 给出，执行体的形状见下。

这不是把 `&mut Ctx` 开给插件——那会让插件持有整轮可变状态，顺序与失败都无法判。
执行体的形状收窄成 `Readings -> Outcome`：

```text
债实例 + 本行声明的事实切片  →  Vec<FactDraft> | Verdict  →  宿主写口落格
```

纯值进、数据出、由宿主按 `(prio, name, key)` 全序求值、失败即债不还（租约兜底）。
它与 `ToolBehavior` / `ContextProvider` 是同一种形状，只是换了一个时机。

### 2.1 效果：能力自己产生，宿主只写

`Capability::execute` 的返回仍是工具结果；**能力的效果**由它自己注册的
`ToolBehavior` 交出：

```text
call → [before × N] → execute → [after × N] → Vec<FactDraft> → 唯一写入口
```

- `before` 只做判断（放行 / 拒绝），任一拒绝即拒绝（fail-closed）。
- `after` 只产出 `FactDraft { kind, entity, verb, payload, key }`，**不碰 WAL**。
- 宿主按 owner 序遍历、按注册序落格；写闸仍是唯一写入口（I1 不破）。
- 行为实现住能力插件；收集点住 `symbio-plugin-api`（`inventory`）；
  `loop` 只依赖 plugin-api，**不认识任何工具名或兄弟插件**。

`before` 的入参是纯值 `BeforeRequest`：线上全名、调用 id、定稿参数、发起主体、本工具
声明的行为名、本会话事实切片，以及控制面在批首判好的读数 `BeforeReadings`（D-219）。
三条随之定下：

- **按声明选实现**：只有工具在 `CapabilityMeta.behaviors` 里声明了该行为名，实现才被问；
- **只判不写**：不产事实、不改参数——参数是模型看到的那一份，`before` 无权改写；
- **判断需要的宿主结论走读数**：能力拿不到的跨会话折叠值（如淘汰回路收回 `assign.work`）
  由控制面批首算好、按值递入；加一条读数 = 新增一种判断输入，走决策。

顺序是判据：宿主闸（外部执行）先判，声明闸随后按 owner 字典序问，先拒绝者胜。
外部执行留在宿主是**判断归属**的结论——它问的是「这通调用能不能开窗」（授权 / 预算 /
时延），退出语义是控制面事实（零事件 / `task.controlled`），不属于任何单个工具的能力声明。

效果有两种落法，端口给两处出口（D-214）：

| 出口 | 造不造新格 | 时机 | 用途 |
|---|---|---|---|
| `after` | 造 | 唯一写口（宿主盖章：归属 / 溯源 / 时刻） | 任务表、委托承诺 |
| `annotate` | 不造，只补字段 | 调用收口（只要「发生了什么」） | 产物格的载荷富化，如 `file_op` |

分界的判据是「有没有新格」：文件变更账本来就是 `artifact.added` 的一格，缺的只是
「这次写属于哪种动作」，而那是工具自己的身份——补字段比造一格更诚实，也让读侧不必
按名字猜（`session/projections/changes.rs` 现在只认 `file_op` 字段）。

### 2.2 上下文：能力贡献，宿主收集

`ContextProvider` 与 `ToolBehavior` 同一形态：能力插件注册，`loop` 在各收集点按节奏
收集全部 provider 的输出。`run_recall` 从「记忆 + 技能 + 任务段的固定实现」退化为
「遍历 provider、按 owner 序拼接」；新增 RAG / 日历 / 项目文档上下文不再改 `loop`。

端口只交**值**，不交句柄（D-215）：`ContextRequest` 是本轮已经取好的读数（请求序号 /
读方主体 / 用户发言 / 事实切片 / 已判过的召回视图），`provide` 因此是纯
函数——可单测、不持状态，plugin-api 也不必认识宿主的会话类型。

| 关注点 | 谁决定 | 端口交什么 |
|---|---|---|
| 有哪些段 | 各能力包（提交序 = owner 序 + 声明序） | `ContextSection { slot, text }` |
| 段里写什么 | 控制面**判完**之后 | 协议形状的值（`RecallFacts`），不是 `RecallView` |
| 段排在哪儿 | 视图次序（= 装配次序 = 模型读到的次序） | 不查表、不重排 |
| 段算不算数 | 控制面（D-208） | provider 无权改判 |

`slots` 只登记宿主**当前**认识的段名（`RECALL` / `READYSET` / `DELEGATE`），不参与
拼接——新段名由声明方自带。

段的收集分两种**节奏**（D-220）：`Cadence::Utterance` 在一次开口时收集，输入只有读侧值包；
`Cadence::Request` 在工具清单收集成形之后、每次模型请求收集一次，输入额外带
`LiveInputs`（收集后的工具清单 / 委派判定结论 / worker 进展）。宿主先收发言级段、再收
请求级段，拼成一个数组——段的先后仍是判据。委派者真源（`DELEGATE`）走请求级节奏：
它要的是收集完成后的工具清单，发言级拿不到；Q1 判定仍在控制面，provider 只渲染判完的
`DelegateVerdict`。

### 2.3 领域：一个扩展位，不是一列开放字符串

`Entity` 保留 11 个核心实体，另加 `Domain` 作为**领域扩展位**：

- 新领域的事实落 `Domain × Verb`，名字、格位、角色由 owner 的 `EventDecl` 声明；
- 写闸按冻结表校验；`core` 不认识的实体一律忽略；
- `Verb` 仍封闭；`FactRole` 仍是判断种类，不随领域开放。

`Domain` 是**一次性**架构决策；之后 notes / calendar 这类新领域零 kernel diff。
把 `Entity` 直接改成任意字符串会丢掉 F5 的编译期闭集，不采用。

两侧各有判据（缺一条，扩展位就只是「多了一个没人管的变体」）：

| 侧 | 判据 | 它证明什么 |
|---|---|---|
| 写 | `a_domain_cell_is_gated_like_any_other_declared_cell` | 写闸对 `Domain` **没有特判**：owner 声明了就放行，自述挪格照拒，没有声明的实例上答 `OffGrid` |
| 读 | `a_domain_cell_is_never_a_chat_slot` | `core` 不会因为「放行」就懂这个领域：`Domain × 五动词` 一律不是对话槽位 |

两侧合起来才是 D-209 的全部：**放行靠声明，理解靠 owner**。若读侧为了「让 notes 也
显示在转写上」加一档 `ChatSlot`，那正是「加一个领域要改架构」的回流形状——读侧用例
会红，逼那条改动去走决策。

### 2.4 行为：开放集合，不再逐位加字段

`CapabilityMeta.behaviors: &'static [&'static str]` 取代逐项布尔位：

- 已知行为名是**宿主词汇**，住 `symbio_plugin_api::behaviors`，与 `Capability` 同层；
- 新行为**实例**（「我的工具也写任务表」）= 插件声明一个名字 + 注册 handler，零架构 diff；
- 新行为**语义**（框架第一次出现这种判断）= 架构变更，必须走决策；
- 不为「声明数 / 变体数」再加计数器；端到端夹具才是判据。

### 2.5 部署：清单是事实源，生成物是镜像

`PLUGIN.yml` 是部署事实的唯一声明处。每加一条部署事实 = 改**自己目录**里的清单，
中心文件零 diff；漂移由 `node scripts/gen-facts.mjs --check` 判红。

| 清单键 | 生成物 | 它替掉的手写处 |
|---|---|---|
| `plugin_id` / `plugin_assembly` / `plugin_order` / `plugin_undisablable` | `crates/symbio-deploy/src/lib.rs` | 装配清单（插件 id / 子树 / 不可停用集） |
| `plugin_routes` | `crates/symbio-plugin-api/src/routes.rs` | 跨插件地址常量 |
| `shared_events` | `crates/symbio-plugin-api/src/events.rs` | 跨插件事件名常量 |
| `shared_views` | `crates/symbio-plugin-api/src/view_names.rs` | 不替手写处——它是新面：跨插件读折叠只按这份名单（§2.6） |
| `principal_*` | `crates/symbio-core/src/authz/rows.gen.rs` | 授权表 `ROWS`（主体 / 能力 / 可见域） |
| `tool_namespace` | `crates/symbio-kernel/src/chat/tool_namespaces.gen.rs` | `tool_principal` 里写死的命名空间匹配臂 |
| `trigger_kinds` | `crates/symbio-kernel/src/event/trigger_kinds.gen.rs` | `session` 写臂里对单一 kind 的等值比较 |
| （目录本身） | `crates/symbio/Cargo.toml` 与 `crates/symbio/src/lib.rs` 的标记块 | 插件链接行（依赖行 + `pub use`） |

三条形态约定（D-216）：

- **行表**（`rows.gen.rs`）：整份文件是生成物，模块用 `#[path]` 引入；
- **标记块**（`Cargo.toml` / `lib.rs`）：生成器只拥有 `begin`/`end` 之间那一段，
  块外字节原样保留——那两份文件还有大量手写内容，整份渲染等于换掉它们的作者；
- **登记表**（`EVENT_TRIGGER_KINDS` / `TOOL_NAMESPACES`）：生成的是**成员集合**，
  消费方只判成员资格，不认具体取值。

名字与理由仍住代码：`PRINCIPAL_*` 常量的文档注释写着「这一行为什么这么窄」，
`EVENT_TRIGGER_KIND_SCHEDULED` 写着「这个取值说哪件事」。生成器对两者做**双向核对**
（常量集合 ⇄ 清单集合），任一侧多出来都抛错——名字与行分家时，谁都不会报错，
只会静默多出一条没人引用的权限或一个没人能判的身份。

### 2.6 视图：折叠跟着读者走，跨插件只按名字读

一条折叠（把事件流算成一个读数的纯函数）住在**谁读它**的地方：

| 消费方分布 | 归属 | 本仓现状 |
|---|---|---|
| 只有 owner 自己在读 | owner 插件的 `projections/` | `checkpoint` / `fallback` / `slo` / `span` / `changes` → `session`；`consolidate` → `loop` |
| ≥2 个 crate 在读，且都是架构层读者 | `symbio_core::projection` | 6 条：`calibration` / `cost` / `readyset` / `reputation` / `transcript` / `turnstate` |
| 别的**插件**想读 owner 的折叠 | owner 声明 `ViewDecl` + `PLUGIN.yml` 写一行 `shared_views` | `notes.recent` / `notes.digest`（夹具，读者是 `session` 的通用出口） |

第三行是横向扩展的那条路，插件侧看到的只有三样东西：

```rust
// owner 侧：名字、版本、读了哪些字段、求值函数都在自己的 decl 里
ViewDecl { name: "notes.recent", ver: 1, reads: &[("notes.created", "text")], cost: 4096, eval }
// owner 侧：PLUGIN.yml
shared_views: notes.recent, notes.digest
// 读方侧：不认识 owner 是谁，只遍历清单生成物
for v in symbio_plugin_api::shared_views() { ViewRead::named(v.name)?.read_all(snapshot)? }
```

四条规矩（D-221）：

- **读方零知识**：`session` 的 `capability_views` 列只遍历清单，代码里没有 `notes` 这个
  词；加一条共享视图 = owner 改自己两处 + 跑一次生成，读方一行不动。
- **不在名单里就读不到**：`ViewRead` 只认生成的 `SHARED_VIEWS`；缺席有四种各自可辨的
  说法（`not_sealed` / `not_shared` / `unknown` / `over_budget`），都是**可诊断的缺席**，
  不静默返回空值。
- **不静默截断**：`cost` 是 owner 声明的条数上界，超了报 `OverBudget { events, cost }`——
  而不是悄悄算一个小一点的数。
- **core 不再长回折叠**：`PP-004` 把「产投影文件数 / 投影构造器条数」钉成只许降的棘轮，
  放宽要按 `PP-005` 挂一条打开得了的 `### D-NNN`（与 `CS-001` / `CS-009` 同一口径）。

`seal` 在冻结时就把声明面钉住：视图读的字段必须是已声明的事实字段
（`UndeclaredField`）、`evidence` 必须是 `reads` 的子集（`EvidenceNotRead`），
所以「跨插件读口」拿到的永远是 owner 自己认领过的形状。

### 2.7 影响类闭表与全面拆分

能力能对系统做的全部事情收在一张八格的闭表里（I-1…I-8），能力是它的实例。全面拆分
（T1 / T2 / T3）、残留五类、迁移纪律与五条新判据归
[DE-026](026-能力拆分与影响类.md "DE-026-能力拆分与影响类")。本节只留一句判据：
**能力可以产出判定，引擎强制「什么算合法」**——闭的是强制点与执行顺序，不是判定的
生产者。

## 3. 契约

1. **跨插件编译期零依赖**（[DE-024](024-能力横向扩充的通路.md "DE-024-能力横向扩充的通路") D-192）：能力包之间不
   import、不经宿主门面转发、不共享 `contract` 模块。
2. **收集点唯一**：`tool behavior` / `context provider` / 声明表都经
   `symbio-plugin-api` 的 `inventory` 收集；提交点住能力包，装配方只 `seal`。
3. **写口唯一**：行为与上下文都只产出数据；事实由 `loop` 的唯一写入口落格。
4. **顺序确定**：按 owner 字典序，再按声明序；判断类任一拒绝即拒绝，效果类按同序追加。
5. **装配位是开关**：停用插件 ⇒ 它不再被构造，它的工具 / 路由 / 挂载点从这棵树消失，
   系统其余部分完整运行。`submit_declarations!` / `submit_behavior!` /
   `submit_context_provider!` 是**链接期**贡献，随二进制里有没有这个 crate 而定，
   不随运行期开关变化——两种开关的分界见 D-217。
6. **共享类型只有三条出路**：JSON 形状（0 成本）、清单词汇（0 成本）、上移领域模块
   （C-003 / C-004 的决策成本）。不上移就不得让第二个插件依赖第一个。
7. **控制面不认识能力名**：能力接入后，`loop` / `session` 的 diff 只能是「删旧实现 +
   一行绑定」。控制面按影响类与 `(prio, name, key)` 执行，不按能力名分支、不按能力名
   查表（D-239 / D-245）。
8. **声明即绑定**：`Decl.by` 必须解析到一个已绑定的执行体；解析不到在 `seal` 期红，
   不再由派发器静默过滤（D-241）。
9. **能力产判定，引擎做强制**：能力只能交 `FactDraft` / `Verdict`；授权、不变量、
   承诺配对、单写者顺序的实现不得出现在能力包里（D-240）。

`CS-009` 补的是现有棘轮的盲区：`CS-001` 只数 trait / `fn` / 默认体，`CapabilityMeta`
的字段、`Entity` 的变体、`FactRole` 的变体都不在它的判定面里——内核可以靠数据面
持续变宽而全绿。`SC-006` 把「按工具名分流」从 `session` 扩到 `core` / `kernel` / `loop`，
且判的是**出现**而不是比较位置：`session/projections/changes.rs` 那种按名字出富化的读法会被
当场抓住。迁移期不追求清零，存量记在 `scripts/baselines/tool-names.json`（文件 + 名字 +
处数）：超一处即红，代码少了而基线没跟上同样红；基线条目与代码内
`// special-case-allow SC-006:` 都必须挂一条能打开的 `### D-NNN`（D-218）。

`CS-009` 的读法是**两格总量**（`structFields` / `enumVariants`），不逐 struct / 逐
enum 设上限：逐项上限要求维护一张按名字的表，那张表本身就是「加一个 struct 要改
脚本」的又一处中心文件。总量是同一件事的等价判据——任何新增都抬总数，逐项清单只在
`--verbose` 里出，用来回答「涨的那一个是谁」。放宽的资格与 `CS-001` 同一条口径
（`core-shape-allow <格>: D-NNN <理由>`，ADR 必须能打开），`35-baseline` 另判「数字
不得比上一版更松」。**它上线时的第一处放宽就是 `Domain`**：那一条变体是 D-209 换来
的一次性代价，棘轮当场报红、豁免注释把决策挂上——这正是它该有的样子。

`EX-001` 的夹具是 `crates/symbio-plugin-notes`：一个工具（`notes_add`）、一条前置判断
（重复便签在执行前被拒）、一条 `Domain × Opened` 事件（`notes.created`）、一个上下文段、

`notes.summarize` 把一段工具结果写成带 `elision` 的 `message.added`），各经一个
plugin-api 提交点接入。
落地 diff 里 `crates/symbio-core` 与 `crates/symbio-kernel` 零改动；运行期读数在
`e2e/cases/t89-notes-extension.mjs`（工具进模型工具面 → 行为落格 → 下一轮上下文段出现 →

**运行期停用**停的是实例与工具，链接期贡献不随之消失（D-217）。

`PP-004` 判的是**core 这一侧的投影面**，不是「core 有多少 `.rs`」：`vocab.rs` /
`task_vocab.rs` 是折叠的参数表，`mod.rs` 是 `Projection` 框架本身——它们长宽都不判。
两格的现值（`files 6` / `ctors 6`）是 D-221 下沉六条之后冻结的，`35-baseline` 另判

`symbio_sdk/projection/`，「加一个能力」就永远等于「改架构模块」——而这件事在门禁里
原本长得像全绿。

## 6. 不做

- 不开任何形态的插件间依赖：`contract` 模块、`pub use` 转发、只依赖类型不依赖实现。
- 不打开判断种类：`Verb`、`FactRole`、`governance::Capability`、`ClosureReason`、协议五格。
- 不让能力直接写 WAL：行为只返回 `FactDraft`，写口仍是唯一写入口。
- 不把 `loop` 变成任意语义解释器：开放的是输入与贡献，不是判断。
- 不从 YAML 生成 Rust 类型：跨插件类型走 JSON 形状或显式上移。
- 不再加「就这一次」的内核布尔位 / 枚举变体。
- **不新增实体**：能力包只声明事实名与格位，新领域落 `Domain`（D-244）。
- **不把 `&mut Ctx` 或轮内状态交给能力**：执行体只收纯值、只产数据（D-241）。
- **不按能力名开端口 / 加执行体**：端口与执行体按影响类开一次，所有能力共用（D-240）。
- **不允许新旧两份实现同时生效**：切换绑定与删除旧实现同提交（D-245）。

## 关键决策

### D-207 能力的效果随能力走

**裁决**：能力的效果由能力包自己注册的 `ToolBehavior` 交出，宿主只负责按序执行与
唯一写入口落格。`ToolBehavior` 与收集器住 `symbio-plugin-api`，提交点住能力插件；
`loop` 不按工具名分流，也不为每种效果加字段。

**理由**：工具名/状态是能力的实现细节，不是架构词汇。把效果留在 `loop` / `core`，
每加一个带状态的能力就多一个内核字段、一段宿主分支、一个 core 类型——`todo_write`
与 `agent_run` 已经各付过一次。效果随能力走之后，这两个能力的行为实现与记录类型
回到各自插件，`core` 只留通用 `FactDraft`。

**被否候选**：

- 继续加 `CapabilityMeta` 布尔位：每个新效果改一次内核 struct，且 `CS-001` 看不见。
- 让能力直接持有 WAL 写口：绕过唯一写入口与写闸，I1 不成立。
- 把行为 handler 留在 `loop` 按名字分派：换一个能力仍要改 `loop`，只是把字段换成分支。

### D-208 控制面的输入开放，判断闭集

**裁决**：`loop` 是调度器，不是能力的容器。能力的**贡献**（上下文、效果、行）经通用
端口进入；**判断**（欠什么、何时停、谁有权威）仍住控制面，新增判断走决策。

**理由**：把判断也开放，等于让任意插件改写一轮的语义，回放与不变量同时失去承重点。
但「记忆召回 + 技能路由 + 任务段」这种固定拼装不是判断，是输入；它必须能被新 provider
替换，否则每个 RAG/日历能力都要改 `loop`。

**订正（D-240）**：本条闭的是**强制点与执行顺序**，不是判定的生产者。能力可以产出
判定（`Refuse`、一条「预算已尽」的事实），但不能实现授权 / 不变量 / 承诺配对 /
单写者顺序；执行体可以离开控制面，只要它收纯值、产数据、由环按 `(prio, name, key)`
求值。原句「判断仍住控制面」按此收窄，理由同 [DE-001 §11](001-核心架构.md "DE-001-核心架构")
放弃 L2 之后的口径：回放读日志，不重执行判断。

### D-209 领域轴用一个扩展位

**裁决**：`Entity` 保留 11 个核心实体，增加 `Domain` 作为扩展位。新领域事实落
`Domain × Verb`，名字与格位由 owner 的 `EventDecl` 声明，`core` 对未知领域不解释。
`Verb` 与 `FactRole` 不开放。

**理由**：D-203 之后判据读「格子 + 角色」，`Entity` 已主要承担命名空间；把整个
`Entity` 改成开放字符串会丢掉 F5 的编译期闭集，而一个 `Domain` 变体足以吸收
notes / calendar 这类新领域。一次性决策换长期零 kernel diff。

**被否候选**：

- 把新领域硬塞进 `Memory` / `Task`：格子的语义被复用，读侧只能靠载荷猜，正是
  D-205 / D-206 已经否掉的形状。
- `Entity` 改成任意字符串：失去编译期穷尽检查，J3 失效。

### D-210 行为是开放集合，声明必须显式

**裁决**：`CapabilityMeta` 只保留一个 `behaviors` 开放集合；已知行为名住
`symbio_plugin_api::behaviors`。新行为实例由能力包声明并实现；新行为语义是架构变更。
不再为「某个工具属于哪道闸」增加内核布尔位。

**理由**：行为名是宿主词汇，不是内核语法；把它做成开放集合，`kernel` 的数据面不再
随能力数量增长。显式声明让「忘了声明」在装配/收集期有名有姓，而不是靠中心基线代账。

**被否候选**：

- 保留布尔位 + 再开一个 `custom: Vec<String>`：两份真相，读侧要判断以哪份为准。
- 让行为名完全任意、框架不校验：未知行为静默不生效，正是 J3 要消灭的形状；已知名
  必须在宿主词汇里登记。

### D-211 部署事实由清单生成

**裁决**：主体、权限、工具命名空间、触发 kind、插件链接行都由 `PLUGIN.yml` 生成；
手写中心表退出。生成器逐条核对声明与代码，漂移由 `gen-facts --check` 判红。

**理由**：这些是部署事实，不是语法。它们今天住在 `core/authz`、`tool_principal`、
`event` 域与 `Cargo.toml` 里，每加一个能力/主体就改一处中心文件——这正是「加能力改
架构」的残余来源。地址与装配位已经走通同一条路，主体与链接没有理由例外。

### D-212 判据反向：数据面与能力名

**裁决**：新增 `CS-009`（内核数据面只许降）与 `SC-006`（工具名不得出现在
`core` / `kernel` / `loop` / `session`）；扩展夹具必须证明一个新能力包只经 plugin-api
接入。`Core-Change` 只接受两种理由：新增判断种类，或实现通用端口。

**理由**：现有棘轮守住接缝面，却放过数据面；`CapabilityMeta` 的布尔位、`Entity` 的
变体都是这样长回来的。判据不反向，清完的账会以「就这一次」的形态重新长出来。

### D-213 效果在写口求值，工具层只交纯值

**裁决**：工具执行层交 `EffectInput`（工具 / 调用 id / 参数 / 成败 / 结果 / 原因 /
声明的行为名），**不带**幂等词干、溯源与主体；唯一的写口把宿主面补成 `EffectCall`
再问 `ToolBehavior::after`，拿回的 `FactDraft` 由它落格。

**理由**：`after` 需要的幂等词干、`user_seq` 与两个主体，只有落格点才知道。
若在调用当场求值，这四个值要一路穿过批处理、并行收口与未执行收口五层签名，而它们
与「这次调用发生了什么」无关。两段式让工具层只做观察、写口只做盖章——两处各自
只有一份事实，行为实现拿到的仍是完整的调用语义。

**被否候选**：

- 调用当场求值、把词干穿到执行层：五个函数各多一个参数，且执行层因此知道宿主的
  容器边界——它今天只认批。
- 让 `after` 只给 `{kind, payload, key}`、主体与锚全由宿主补：承诺号必须含幂等词干
  （跨请求幂等），而宿主补不了载荷里的 `id`——那是承诺域的配对键。

### D-214 富化不造格，效果要看得见本轮

**裁决**：两件事一起定，因为它们是同一个「效果端口够不够用」问题的两面。

1. `ToolBehavior` 增加 `annotate(&EffectInput) -> Vec<(&'static str, Value)>`：只给
   **已经要落**的产物格补字段，不造新格。收集口径与 `after` 同（按工具声明的行为名
   选、按 owner 序），但**时机更早**——它只要「这次调用发生了什么」，在调用收口就能
   算，不必等轮锚。
2. `EffectEnv` / `EffectCall` 增加 `applied: &[Event]`：本轮**已落格**的草稿，按落笔
   顺序。`facts()` 把轮初 `snapshot` 与本轮 `applied` 串成一条按发生顺序的历史。

**理由**：

- 工作目录变更账不需要新格。`artifact.added` 已经记下了 `tool` / `args` / `success`，
  缺的只有「这次写属于哪种动作」。造一个 `file.changed` 会让同一件事有两格、两份
  幂等键、两条读路径；而按工具名判动作又正是 `SC-006` 要消灭的形状。补字段是第三条
  路：动作进载荷、跟着事实走，读侧零工具名。
- 两处出口时机不同，不该合成一次求值。合成只有两种结果：把富化拖到落格（它不需要），
  或把效果提前到调用当场（它缺词干与主体，见 D-213）。
- `applied` 不是「让行为看见更多」，是**让同一轮的判据与串行一致**。效果按历史折叠
  （「这条任务开过没有」）时，两个调用若都从轮初快照出发，第二个看不见第一个刚开的
  格，就会把同一格再开一次——这跟效果写得好不好无关，是宿主少交了一片事实。写口本来
  就在按序落格，把它落过的那几条顺路交回去，成本是零。

**被否候选**：

- 为文件变更造 `file.changed` 事件：同一件事两格，读侧还要定「以哪格为准」。
- 富化让读侧做（`changes.rs` 自己认 `vdfs_write`）：这就是 `SC-006` 要抓的形态，
  换一个文件工具名就要改 core。
- 让 `after` 一次交「草稿 + 富化」：两者入参不同（一个有宿主面、一个没有），合并只会
  逼其中一个接受它不需要的依赖。
- 同轮效果靠「写口重跑一遍全部草稿」来互相可见：重跑会让已落格的幂等键撞车，而且
  已经 `store.append` 过的事件不能再来一次。

### D-215 上下文端口的入参是值，段身份是宿主词汇

**裁决**：`ContextProvider::provide` 收一个**纯值包** `ContextRequest`（请求序号 /
读方主体 / 用户发言 / 事实切片 / 已判过的召回视图），交一串
`ContextSection { slot, text }`。三条随之定下：

1. **入参里没有句柄、没有 `async`**——provider 是纯函数；
2. **已判过的值以协议形状交过去**（`RecallFacts` / `RecallLine`），不是
   `RecallView`——`loop` 的类型不进 plugin-api；
3. **段身份是 `&'static str`**（`slots` 只登记已知名字），拼接按视图次序、不查表。

**理由**：

- 事实是值（DE-001 D-084）。同一轮内各读方看同一刻的事实，provider 若自己开源就会
  读到第二个版本；而事实切片已经在控制面手上，顺路交过去是零成本。
- 纯函数才可单测、才不持状态。给 provider 一个会话句柄，等于让 plugin-api 认识宿主的
  会话类型——那是插件 → 宿主的反向依赖，比插件间依赖更难拆。
- 判据留控制面（D-208）。召回的条目可见性、技能路由摘掉低置信技能，都发生在
  `run_recall`；provider 收到的是**判完的**视图，它无权改判，因此「换一个渲染者」不
  改变判断。
- 段身份不能枚举：provider 来自任意插件，宿主不可能预先枚举完所有段。这与 D-210 对
  行为名的裁决同形（已知名登记、新名由声明方自带）。区别在失效方式——拼接方按视图
  次序取全部段，没有第二处按名字查表，所以拼错只影响它自己那段的 `meta.kind` 标记，
  不会静默丢掉一整段。

**边界**：请求期才产生的产物（工具清单 / worker 进展）**不进本值包**——发言级收集时
工具收集尚未完成。它们由 D-220 的 `LiveInputs` 在请求级节奏递入，仍是「宿主取好的值」，
本裁决的「纯值」判据对两种节奏同样成立。

**被否候选**：

- 保留 `SectionKind` 枚举在宿主：它存在的唯一理由是「装配处与渲染处两处拼写要一致」；
  端口化后拼写只剩 `ContextSection::slot` 一处，枚举就退化成「加一段要改宿主」的
  又一个中心表。
- 让 provider 拿 `&Session` / `&TurnCtx` 自己取数：反向依赖 + 事实不唯一，且单测要造
  一整个会话。
- 在**发言级**收集 `DELEGATE`：此时工具收集尚未完成，读到的是残缺的工具集，段内容随
  插件装配次序变化——顺序确定（§3 第 4 条）当场失效。D-220 的请求级节奏在收集
  之后收集，避开的正是这一点。
- 用 `sections()` 拼完后按 `slots::KNOWN` 重排：查表就是第二处拼写，且新段名不在表里
  时会静默掉段。

### D-216 部署事实的三种生成形态，名字留代码、行留清单

**裁决**：`GEN-002` 的生成物按「生成器拥有多少」分三种形态，不许混用：

| 形态 | 用在 | 生成器拥有 |
|---|---|---|
| 行表 | `authz/rows.gen.rs` | 整份文件（`#[path]` 引入，文件头写明「请勿手改」） |
| 标记块 | `Cargo.toml` / `lib.rs` | 只 `begin`/`end` 之间那一段，块外字节原样保留 |
| 登记表 | `EVENT_TRIGGER_KINDS` / `TOOL_NAMESPACES` | 成员集合；消费方只判成员资格 |

同时定下两条归属：**名字与理由留代码**（`PRINCIPAL_*` / `EVENT_TRIGGER_KIND_SCHEDULED`
的文档注释），**行与取值留清单**；生成器对两侧做**双向核对**，任一侧多出来即抛错。

**理由**：

- 三处手写中心表的失效方向各不相同，所以形态不能统一。授权表是**一张表**——整份
  生成最干净，文件头一句「请勿手改」就够；`Cargo.toml` / `lib.rs` 不是生成物（还有
  package、lints、门面出口），整份渲染等于把作者换成生成器，每加一条普通依赖都要
  先改模板；触发方式与工具命名空间是**成员资格**——生成一个具体取值（`"scheduled"`）
  会把「有哪些取值」这件事再钉死一次，而消费方只需要「在不在里面」。
- 名字必须留代码，因为**理由不是部署事实**。「自主行只持 `define.work`，因为它不得
  冒充用户对话」这句话塞进 YAML 会让清单变成第二份设计文档，且没有文档审读的那套
  判据（链接、编号、计数）看着它。
- 双向核对是这条裁决的关键：名字与行分家之后，多一条常量（清单漏了它）与多一行
  （常量没了、权限还在生效）**都不会让编译失败**。生成器抛错 + 一条 Rust 判据
  （`every_principal_constant_is_a_row_and_every_row_is_a_constant`）两面夹住。
- 反推不成立，所以 `tool_namespace` 是**显式声明**而不是从 `principal_*` 的 id 前缀
  推：「命名空间属于工具族」不是能从主体行读出来的性质（`scheduler/main` 与
  `session/main` 也是主体），反推要维护一份「哪些命名空间不是工具」的黑名单——
  那又是一处中心表。

**被否候选**：

- 把 `ROWS` 生成成纯字面量（不引用 `PRINCIPAL_*` 常量）：常量立刻变成没人用的
  装饰（编译器 7 条 dead-code 警告），而「这一行为什么这么窄」的理由失去挂载点。
- 整份渲染 `Cargo.toml` / `lib.rs`：两份文件的大部分内容与插件清单无关，生成器
  一接手就要为 package 字段、lints、dev-deps 各留一处模板变量。
- 让 `tool_principal` 继续写死命名空间、只在文档里登记：漏一个插件的后果是那个
  插件的工具主体静默落 `legacy/<name>`——地址还在、族也对，只是与授权表那一行
  对不上，没有任何东西会红。
- 触发方式放开成任意字符串：拼错的 kind 会被静默读成「普通用户消息」，那一轮不再是
  自主的，而事实源里少的那四格没有任何东西会补。

### D-217 装配位有两个开关：运行期停的是实例，链接期停的才是贡献

**裁决**：§3 第 5 条的「装配位」分为两个**不同层**的开关，不得混为一谈：

| 开关 | 在哪 | 停掉它 ⇒ 什么消失 | 粒度 |
|---|---|---|---|
| **运行期装配位** | `<插件根>/<id>/PLUGIN.yml` 的 `plugin_enabled` | 插件实例不被构造：它的工具从模型工具面消失，路由 / 挂载点 / 后台行为从这棵树消失 | **每棵树**（子智能体各有自己的目录） |
| **链接期装配** | `PLUGIN.yml` 的 `plugin_assembly` + `symbio` 的依赖行 | 整个 crate 不在二进制里：`submit_declarations!` / `submit_behavior!` / `submit_context_provider!` 的贡献一并消失 | **每份二进制**（进程级） |

运行期停用**不**移除链接期贡献，这是 `inventory` 的收集方式决定的，不是漏实现：
收集点是编译期集合，条目属于进程而不属于某棵树。两个后果必须写在这里，而不是
留给读者猜：

1. **行为不会再触发**：行为只由「工具声明了该行为名」选中，而工具随实例消失 ⇒ 没有
   新的 `FactDraft`。声明仍在，写闸照旧只放行它声明过的格子——但已无写者。
2. **上下文 provider 仍在收集表里**：它会继续渲染**历史事实**。停用一个生产方之后，
   它过去产出的事实还在事实源里，而 provider 没有「本棵树启用了谁」的输入（那要让它
   认识装配面，是插件 → 宿主的反向依赖）。

因此「停用后它的上下文也消失」只在**链接期**停用时成立。要彻底移除一个能力，正确
的杠杆是构建时不链接它，不是运行期旗标。

**理由**：

- 运行期开关的粒度是**树**，而 `inventory` 的粒度是**进程**。把两者对齐需要在收集点
  引入「当前树启用了谁」的全局可变状态：一个进程里同时有系统树与多棵子智能体树，
  同一份 provider 表无法表达「在根树停用、在子树启用」。
- 修正 §3 第 5 条比造一个违背上述粒度的过滤器便宜且诚实。原来的「全部消失」把两件事
  写成了件，读者会以为运行期旗标能代替构建裁剪——那正是最危险的那种「看起来能」。
- 扩展性不受影响：**加一个能力仍然只改自己的插件**。两种开关都在部署侧，都不需要
  动 core / kernel / loop / session。

**被否候选**：

- 在 `plugin-api` 存一张「已启用 owner 集合」，收集时过滤：进程全局表无法表达每棵树
  的差异；测试会因共享全局状态而顺序相关；且它把「装配期事实」重新变成一处可变
  注册表，违背 §3 第 2 条的收集点唯一。
- 让 provider / 行为按 `PLUGIN_DIR` 现扫兄弟目录判断自己是否启用：让每个贡献者都
  认识装配面，且每轮收集变成磁盘 I/O；同一件事两个 owner。
- 在文档里删掉第 5 条：开关确实存在（T88 已把工具面的进出钉住），删掉会把真实能力
  说成不存在；缺的是**分界**，不是这条判据本身。

### D-218 `SC-006` 的存量记在逐处基线上，每一处挂一条能打开的决策

**裁决**：`SC-006` 不设清零期限，存量记在 `scripts/baselines/tool-names.json`：文件 +
工具名 + 处数。超出一处即红；代码里少了而基线没跟上同样红（**只许降**）。基线条目与
代码内 `// special-case-allow SC-006: D-NNN 理由` 都必须写一条**能打开的**
`### D-NNN`——指向不存在的决策的豁免不算豁免（与 CS-002 / PTS-004 同一条资格线）。

**理由**：

- 这四棵树是「加能力不该动」的架构面，迁移期仍有一处合法存量：会话写臂推导自主轮
  参数时读 `heartbeat.include_history`（D-076 #5），那是心跳插件的 metadata 命名空间，
  与工具同名只是命名巧合。把它写成「比较位置」的例外会让判据变形——非比较位置的
  按名读恰恰是 SC-001 抓不到、而这条要抓的形态。
- 配额必须是**逐处**的：一个总数允许「这处清了、那处又长回来」而数字不变。逐处键
  （文件 + 名字）让新位置、新名字都拿不到额度，也把「这一处为什么还在」钉在纸上。
- 资格线挂在既有决策上，而不是新开一张豁免登记表：能力名进架构面只有一种合法理由，
  即一条写下来的裁决；表只会变成第二份需要维护的名单。

**被否候选**：

- 数字总量基线（如「四棵树合计 1 处」）：替换一处不涨总数，判据看不见。
- 先清零、下批再上判据：迁移期长度不可控，判据会先被关掉，而且不会自己回来。
- 只判比较位置（沿用 SC-001）：`session/projections/changes.rs` 那种「按工具名出富化」是读取，
  不是比较，正好漏网。

### D-219 前置判断的输入是纯值，选择靠声明，判断留 owner

**裁决**：工具执行**之前**的判断由 `ToolBehavior::before` 承担，形状收窄为三条：

1. **纯值入参**：`BeforeRequest { tool, call_id, args, principal, declared, facts,
   readings }`——没有句柄、没有 `async`，与效果端口同一条「事实是值」口径；`args` 只读。
2. **按声明选实现**：只有工具在 `CapabilityMeta.behaviors` 里声明了该行为名，实现才
   被问；未声明的实现看不到任何调用（`apply_before` 先筛声明）。
3. **判断闭集，输入开放**：能力拿不到的**跨会话折叠值**由控制面批首算好，按
   `BeforeReadings` 递入（当前一项：`assign_work_revoked`）。加一条读数 = 新增一种
   判断输入，走决策；实现只能返回 `Allow` / `Refuse(BeforeRefusal)`，`Refuse` 一律
   fail-closed。

`BeforeRefusal` 带判断归属名、回灌拒因、`failure_kind` 与 `notes_delegation`：
`true`（默认）= 这次调用本来会产效果，拒止同样算没履约（写违约承诺）；`false` =
工具根本没跑，「声明过什么」无从说起（任务表写侧）。

**三道存量判断的归属**：

| 判断 | owner | 依据 |
|---|---|---|
| 淘汰（`assign.work` 被收回） | `symbio-plugin-agent` 的 `DelegationGate` | 判断读的是 `assign_work_revoked` 读数，语义属于委派 |
| 任务表写侧 | `symbio-plugin-loop` 的 `TaskTable` | `define.work` / `assert.verification` 的行与写方都在本插件 |
| 外部执行 | **留宿主**（`dispatch::gates`） | 问的是「这通调用能不能开窗」：授权 / 预算 / 时延是执行窗的输入，退出语义是控制面事实（零事件 / `task.controlled`） |

外部执行留在宿主是**判断归属**的结论，不是「守卫不得不驻留」：它的输入与出口都不属于
某个能力包，而「哪个工具受该闸管辖」本身由执行窗的授权面回答。把它塞进 `before` 会让
每个能力实现都要认识预算与熔断。

**顺序**：宿主闸（外部执行）先判，声明闸随后按 owner 字典序问，先拒绝者胜；这与 §3
第 4 条同一条顺序。选择口径与效果端口共用 `behaviors_of`（先全名相等、再取最后一段），
挂载前缀（`local/todo_write`）不会让声明失配。

**为什么 `before` 不写事实、不改参数**：

- 写口唯一（I1）：判断若能在执行前落格，「没跑成的调用」与「跑成了的调用」在事实面
  就分不开；拒绝的记账由宿主在收口时按 `notes_delegation` 决定。
- 改写参数会让模型看到的一份与真正执行的一份分离——`args` 是调用定稿，执行层与结果
  节点都对它取同一份；要换参数应该换工具契约，不是在闸上打补丁。

**被否候选**：

- `before` 返回值带「改写后的参数」：两条真相（模型看到的 / 执行的）从此刻起分家，
  而结果节点、事件载荷与审计面都只认其中一条。
- 把 `before` 也交给 `loop` 按工具名分派：换一个能力仍要改 `loop`，只是把字段换成分支
  ——与 D-207 否掉的是同一形状。
- 让能力在 `before` 里直接读存储 / 会话句柄：事实不唯一 + 反向依赖；需要历史时读
  `facts` 切片即可。

### D-220 上下文分两种节奏：发言级值与请求级产物

**裁决**：`ContextProvider` 增加 `cadence()`，收集分两档：

| 节奏 | 何时收集 | 入参 | 现有段 |
|---|---|---|---|
| `Cadence::Utterance`（默认） | 一次开口收一次（`run_recall`） | `ContextRequest` 的常驻字段 | 召回 / 调度 |
| `Cadence::Request` | 每次模型请求、工具收集之后 | 常驻字段 + `LiveInputs` | 委派者真源 |

`LiveInputs { tools, delegate, workers }` 是**收集完成后的本轮产物**：工具清单是遍历
广播的产物（发言级取不齐），worker 进展读自存储。`DelegateVerdict` 三态
（`NotJudged` / `Start { reason }` / `Idle`）是控制面 Q1 判完的结论——provider 不读
配置、不重判（D-208），只渲染。宿主先收发言级段、再收请求级段，拼成同一个数组；段的
先后仍是判据（召回 → 调度 → 委派），且与端口化之前逐字一致。

**理由**：

- 段的内容不都在发言级就齐。把 `DELEGATE` 硬塞进发言级收集，会读到残缺的工具集（D-215
  的被否候选）；把它留在 `inputs.rs` 手拼，则「有哪几段」又写回宿主，加一段仍要改
  宿主——那正是本决策要拆掉的形状。
- 两种节奏而不是「provider 拿句柄自己取数」：请求级产物仍是**值**，由控制面在收集
  完成后一次取齐；provider 看不到 `traverse`，也就没有「什么时候取」的自由。
- Q1 判定留控制面：`worker_start_reason` 读本轮发言与配置面，provider 拿不到配置、
  也不该重判；`LiveInputs` 交的是判完的三态，连「未命中」都显式落笔（可审计）。

**被否候选**：

- 让 provider `async` 并拿会话句柄，自己取工具清单 / worker 进展：反向依赖 + 事实
  不唯一 + 单测要造整个会话。
- 把 `tools` / `workers` 塞进发言级的 `ContextRequest`：发言级时 `tools` 还没收齐，读到
  的是遍历顺序的残片。
- 把 Q1 连同配置一起交给 provider：判断随渲染走，换一个 provider 就换一套判据，
  D-208 的「判断闭集」当场失效。
- 只加一个「请求级 provider」开关而在同一数组里发言级收集：开关只表达「要不要问」，
  表达不了「什么时候问」——收集时机才是这条例外的全部内容。

### D-221 折叠跟着读者走，跨插件读折叠只按名字

**裁决**：投影（将事件流折成一个读数的纯函数）不是判断种类，归属由**消费方分布**决定；
跨插件读别人的折叠只经「声明 + 清单 + 按名字读口」这一条路。三件事一起定：

1. **下沉判据**：一条 `Projection` 只有一个 owner 在读 ⇒ 归那个 owner 的
   `src/projections/`；读者 ≥2 且都在架构层 ⇒ 才留在 `symbio_core::projection`。
   本批据此下沉六条：`checkpoint` / `fallback` / `slo` / `span` / `changes` → `session`，
   `consolidate` → `loop`；core 的投影面由此定为 `files 6 / ctors 6`。
   折叠之间要共用的判据放进**不产投影的共享读侧**（`session/projections/tiers.rs`），
   而不是让两个折叠互导。
2. **跨插件读口**：owner 在自家 `decl` 里写 `ViewDecl`（名字 / 版本 / `reads` /
   `evidence` / `cost` / `eval`），在自家 `PLUGIN.yml` 里写一行 `shared_views`；
   `scripts/facts/views-rs.mjs` 生成 `crates/symbio-plugin-api/src/view_names.rs`，
   读方经 `symbio_plugin_api::views::ViewRead::named(...)`。读方代码里不出现 owner 的
   插件名、类型或算法。缺席有四种各自可辨的说法（`not_sealed` / `not_shared` /
   `unknown` / `over_budget`），超上界报 `OverBudget` 而不是截断出一个小一点的数。
   `session` 的 `session/stats` 因此有一列 `capability_views`：它只遍历清单，
   owner 从清单来、版本与值从 owner 的 `ViewDecl` 现算。
3. **棘轮**：`PP-004` 把 core 投影面两格钉成只许降，放宽要按 `PP-005` 在本脚本旁写
   `projection-purity-allow <格>: D-NNN <理由>` 且那条决策存在；`35-baseline` 另判
   「数字不得比上一版更松」。纯净性判据（`PP-001` / `PP-002` / `PP-003`）跟着折叠走：
   判定面是**所有折叠根**（core 的 `projection/` + 各 crate 的 `projections/`）。

**理由**：

- 把折叠留在 core，「加一个能力」就永远等于「改架构模块」——本仓对「不具备横向扩展
  能力的架构」的判定正是这个形状。折叠折的是**某个能力的**事件，内核认识的是
  `Projection` 框架与 `seal` 判据，不是「巩固接受边界」这种语义。
- 归属只问读者分布，不问守卫：`PP-004` 的存在恰恰让「留在 core」失去技术借口——
  判据反过来变成棘轮的一端，而不是驻留理由（守卫不影响架构决策这条总纪律的本例）。
- 判据跟代码走，下沉才不是逃逸：若 `PP-001` / `PP-002` 只扫 core 的目录，把折叠迁到
  owner 那里就顺带让它脱离确定性判定，等于用架构换判据覆盖面——两者都不许。
- 按名字读而不是按类型读：类型读口要求读方 `use` owner 的返回类型，那是跨插件编译期
  依赖（E-009）；`Value` + 清单名字两边只认字符串，owner 换算法读方零改动。
- 缺席必须可诊断：`session/stats` 那列把「没公开 / 没声明 / 没冻结 / 超界」各写一个
  `reason`，与本仓「有据的空 vs 不给你看」的口径一致（`may_read` / `has_wal` 同一族）。
- 超界不截断：静默返回一个较小的数，读数看着正常而语义已经变了；`cost` 是 owner
  自己声明的上界，越过它就是契约问题，不是显示问题。

**被否候选**：

- 在 core 留一张「按名字分发的通用投影注册表」，把六条折叠折成一份：注册表要认识每条
  折叠的输入形状，加一个能力仍要动 core——只是把改字段换成改表。
- 宿主按插件名分派读口（`if owner == "notes"`）：与 D-207 否掉的「按工具名出效果」同形。
- 让读方 `use` owner 的投影函数：跨插件编译期依赖，E-009 直接判红。
- 下沉后把 `PP-001` / `PP-002` 留在 core：判据覆盖面缩水，而没人会为此开决策。
- 给 `symbio_core::projection` 的长宽留「合理余量」（如 `files ≤ 8`）：棘轮的约束力来自
  现值，不来自余量；余量就是下一次「顺手加一条」的邀请函。
- 用视图名当字段名直接读 WAL（不声明 `ViewDecl`）：绕过 `seal` 的字段与 `evidence` 判据，
  owner 改口径时读方无声跟随。
