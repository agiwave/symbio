# 插话与实时打断

## 内容

前置：S06 ｜ **新增机制键 0** ｜ 参数变化 4
## 1. 场景：要什么能力

智能体正在说话 / 正在跑长任务时，用户插一句话；系统能**在反射层内**决定"放行 / 挂起 / 排队"，
事后还能回到被打断的地方。

相对 S06 高了什么：**系统第一次需要在几十毫秒内对外部信号做决策**。
S06 及以前的所有决策都在 300ms 以上，本阶把反射层（≤80ms）真正点亮。

## 2. 为什么它能落在 v2 上（J1）

| 看起来新的东西 | 实际是 |
|---|---|
| 打断信号 | `control/opened`（`task.controlled`）事件 |
| 抢占判定 | 一个 `Decider`，`budget_ms = 80` |
| 被挂起的状态 | `task/held`（`task.held`）——**挂起就是一条事件** |
| 恢复 | 从 `seq` 重放 → 投影自动回到断点 |

**关键**："挂起"不需要新状态机。挂起 = 一条 `held` 事件；恢复 = 投影自然包含它。
这也是为什么本阶**新增机制键 = 0**——打断在 v2 里不是新机制，只是新的一格事件 + 一个更快的 Actor。

## 3. 增量清单（只加数据）

| 类型 | 内容 |
|---|---|
| 事件格子 | `control/opened`（`task.controlled`）、`task/held`（`task.held`） |
| ActorSpec 行 | 抢占判定者 `{ pattern: decider, capabilities: [JudgeIntent], budget_ms: 80, scope: root }` |
| grants 行 | 抢占判定者 ▸ 可写 `task.controlled`，不可写 `chat.assistant.*` |
| 投影参数 | `projection = turnstate`（该 turn 的事件，常数开销） |

**本阶点亮的机制键**（阶梯总表的「新增机制键」由这张块算出；`scripts/gen-verify-facts.mjs` 从这里取输入）：

```capability-assign
event.entity = control
event.verb = held
actor.budget_ms = 80
projection = turnstate
```

**裁决（2026-10-13）：「改道」不落地，正文按实现口径订正。**
`Preemption`（`crates/symbio-plugin-session/src/transcript/inbox.rs`）只有 Proceed / Suspend / Queue / TimeoutDefaultContinue——**无改道分支**，且不该有：

1. 改道的语义是「把在跑任务的目的地换掉」，那要先**理解插话**——正是 §7 自己划给 `Reasoner` 层（300ms+）的事，与反射档（≤80ms）的预算相斥；
2. 它今天既**没有写方**（没有任何代码算出「改道到哪」）也**没有消费方**（调用方只处理那四种结论）——给一个两端都没有的名字建分支，是本轮拒绝 `task.ready` / `task.assigned` 的同一条理由；
3. `Preemption` 是插件（`crates/symbio-plugin-session/src/transcript/inbox.rs`）内的枚举，加变体同样是**形状变宽**，按 [D-055](001-核心架构.md "DE-001-核心架构") 要先立决策。

故本阶的真实能力 = 「放行 / 挂起 / 排队 + 超时默认继续」；§1 与 §7 的「停 / 继续 / 改道」措辞已同批订正为「放行 / 挂起 / 排队」。§6 的四条验收断言一字未动（它们判的正是那四种结论）。

## 4. 平凡值与回退（J2）

| 参数 | 完整值 | **平凡值** | 平凡值下 |
|---|---|---|---|
| `event.entity` | `control` | **`scope`** | 仍完整运行——不接受插话，退化为 "跑完再说" |
| `actor.budget_ms` | `80` | `60000` | 仍完整运行——判定慢，用户感到迟钝但不出错 |

**`control` 关闭 = 本阶整阶可跳过**，且系统仍完整。这是插话能力"是数据不是机制"的直接证据。

## 5. 静默失效与强制（J3）

| 约束 | 违反时信号 | 强制方式 |
|---|---|---|
| 抢占判定必须在 80ms 内产出 | **无**——只是慢，无人报错 | I3：超时必须产出 fallback 事件 |
| 被挂起的任务不得被二次调度 | **无**——可能重复执行 | `readyset` 排除 `held` 状态（投影过滤） |
| 抢占判定者不得直接发言 | **无** | grants 表：无 `reply.*` 写权 |

## 6. 验收断言

1. 注入打断事件 → 80ms 内必须存在一条 `task.controlled`（或 fallback）。
2. 挂起期间该任务不出现在 `readyset` 中。
3. 恢复后投影与挂起前一致（除新增的 `held`/`controlled` 事件外）。
4. **反向用例**：把预算放宽到 60000ms → 断言 1 的判定结果必须改变（证明预算参数真的在生效）。

**§6 验收断言的执行方**：1 = `crates/symbio-plugin-session/src/transcript/inbox.test.rs::interruption_within_reflex_budget_produces_control_event`；2 = 「挂起后不再进候选集」，随折叠归任务能力包的 `crates/symbio-plugin-task/src/readyset.test.rs::a_suspended_task_leaves_the_ready_set_and_progress_restores_it`（`D-289`）；3 = 同上一条的后半（以挂起锚 `as-of` 重放与挂起前一致，也在同一条用例里）；4 = `widening_budget_changes_preemption_outcome`（同文件）。

## 8. 这一阶做不了什么

边界的唯一账本：[SC-007-插话与实时打断](../002-scene/007-插话与实时打断.md "SC-007-插话与实时打断")（用户语言）。机制面独有边界（用户可见范围之外的工程约束）：

- 「改道」不在本阶：`Preemption`（`crates/symbio-plugin-session/src/transcript/inbox.rs`）没有改道分支，也不该有——改道要先理解插话语义（`Reasoner` 层，300ms+），加一个既无写方也无消费方的分支只会让「本阶能改道」看起来有代码支撑（裁决记录见 §3.1）。
- 真正的硬实时（T7 的具身 / 闭环控制）仍无实现；本阶只有预算断言（基准见 `RE-004-slo-calibration`，它量的是链路自身开销，不是闭环控制）。
- 多个插话并发到达时的优先级是 `readyset` 的打分参数问题。

## 9. 关键决策

### D-380 抢占三态不跨窗开面：#14 的阻塞是闭环未接线，不是缺端口

- **背景（按代码现状，不按设计意图）**。迁移清单的 #14 行把阻塞写成「判定与落格被刻意分开，
  `PreemptPending` 三态由会话状态背着，搬判定要开跨窗端口」；但代码里 `PreemptionDecider`、
  `spec`、`decide`、`held_event` / `resume_event` / `control_event` 五个符号在
  `scripts/exemptions/session-dead-code.json` 登记为死代码，`batch: preemption`，
  `future_caller` 写的是「抢占批次的判定 → 落格闭环」；生产代码没有任何地方写
  `ActiveSessionState::preempt`，`task.held` 也没有生产写方。也就是说三态今天没有判定方、
  没有落格方，空闲分支的 `preempt.is_some()` 恒假。
- **裁决**。
  ① **不开跨窗端口**：端口是给两个 owner 用的；今天只有一个（`session` 自己），开面即把
  未验证的状态机冻结进机制面（`CS-001` 只许降、`HS-002` / `HS-006` 只许不涨），收益为零、
  代价是永久的机制债。
  ② **#14 不迁**：判定器与三态留在 `session`，直到 `preemption` 批次把「忙窗判定 → 空闲
  落格」接线并通过 `t34`；接线后若判定仍要拆出，再按那时的证据另裁（可能是一条债行或
  一次跨插件调用，不预设端口）。
  ③ **迁移清单的 #14 行阻塞改写**为「闭环未接线（`preemption` 批次）」，不写成「缺补件」；
  `S7` 的补件计数因此不 +1。
- **谁写谁读（现状）**。写方：无（判定与落格函数只有测试调用）。读方：空闲分支
  `preempt != None` 的闸门（恒假）。接线后的写方 = 忙窗判定（`decide` → `held_event` /
  `resume_event` / `control_event`），读方 = 空闲分支（落地并与 `task.held` 对齐）——
  两端都在 `session` 内，跨窗是**同一个 owner 的两个写窗口**，不是两个 owner。
- **代价**。不做：`#14` 的迁移推迟到 `preemption` 批次之后；在此之前它留在名册的
  「拆（阻塞）」行，阻塞措辞按实际状态写。
- **判据**。`preemption` 批次接线后，`session-dead-code.json` 里这五条豁免必须删除
  （死代码审计会红）。在此之前，任何给三态加端口的提案先回答一句「第二个 owner 是谁」。
- **不做什么**。不为迁而死代码开面；不删三态（豁免已挂 `preemption` 批次）；不在 `S7`
  里顺手接线抢占（那是另一段的机制增量）。
