# 架构总览：原则与分层

本文定义架构判断原则、分层边界与插件通信契约，不维护模块清单、迁移进度或实现案例。
核心模型见 [核心架构](001-核心架构.md "DE-001-核心架构")，验证纪律见 [工程落地与验证](016-工程落地与验证.md "DE-016-工程落地与验证")；
当前插件、挂载点、路由与工具事实由 [当前事实表](../004-ref/006-当前事实表.md "RE-006-当前事实表") 提供。

## 1. 分形插件架构

### 1.1 容器与叶子同构

容器与叶子实现同一个 `Plugin` 契约。容器可以包含子插件，但对外仍只暴露相同的
`route` 与 `traverse` 能力；调用方不需要知道目标是容器还是叶子。

插件树的每个节点都拥有相对自己的子地址。绝对地址由父容器沿路由逐层剥离，叶子只
匹配相对臂。地址规则见 [插件路由与地址](006-插件路由与地址.md "DE-006-插件路由与地址")。

### 1.2 对称通信

所有调用经统一的 `route` 入口表达，不按同步、异步、流式或双向会话建立平行入口。
载荷与通道形态由 [协议规范](005-协议规范.md "DE-005-协议规范") 定义。

跨插件调用必须经共同父容器路由，并使用路径常量描述下一跳。插件不得强引用兄弟插件：
强引用会把树形装配变成双向图，使停用、卸载和生命周期失去单一归属。

### 1.3 一个能力一个插件

能力应封装为可独立启停的插件；控制面与共享框架不得按具体能力名分支。新增能力只能增加
装配数据、声明和路由，不得复制驱动循环或另建一套调度机制。

默认装配与可删除性是正交属性。必装插件由装配策略决定，可选插件可以被删除；具体清单
属于生成事实，不写进架构规范。

## 2. 分层边界

| 层 | 职责 | 禁止承担 |
|---|---|---|
| `kernel` | 最小内核语法、领域词汇、不变量与原语签名 | 具体业务策略、插件编排 |
| `sdk` | 构建插件与宿主服务的公共机制、授权、投影与端口 | 单个能力的私有实现 |
| `contract` | 跨模块稳定协议、线格式与共享数据类型 | 具体插件状态 |
| `deploy` | 可执行程序组装、运行入口与进程边界 | 反向定义内核语义 |

分层按依赖方向收敛，不按文件数量或目录名认定。跨层只能依赖更靠近内核的稳定契约；
共享语义必须有唯一 owner，消费方不得复制一份近似实现。

扩展层门面是有限白名单。新能力进入门面会扩大所有使用者的表面，因此门面只许收窄；
确需扩大时，必须先证明该概念属于公共机制，而不是某个插件的便利。

## 3. 架构判断原则

### 3.1 可表达性

新增需求首先检查既有原语、参数值域、事件格子与投影能否表达。机制不随场景数增长；
增长应发生在数据和装配层。只有既有表达确实不足时，才讨论修改机制面。

### 3.2 平凡值

每个新参数都必须有平凡值，平凡值下系统仍能完整运行。空集、单元素与多元素是同一模型的
合法输入，不得用场景特例分支替代统一规则。

### 3.3 静默失效

约束失效时必须产生可观察信号。能由类型系统强制的不得只靠注释；需要运行期或静态检查的，
必须有可执行判据与反向用例。提示词不是执行边界。

### 3.4 共同事实格式

模块之间通过共同的事实格式和端口通信，不建立两两直接依赖。一个共享概念只能有一个
契约 owner；消费方按契约读取，不复制 owner 的私有结构。

## 4. 妥协边界

架构机制、插件契约、共享协议与控制面切分不可妥协；模块内部算法、局部数据组织和实现
语言用法可以妥协。实现困难不是改变架构的理由，应先检查表达方式，再按
[架构改动边界](../005-spec/003.md "SP-003") 发起讨论。

架构声称必须配可执行断言；断言输入不得包含结论，并必须有改变输入即改变结论的反向用例。
没有真实对端的协议不预留恒空分支，以免把猜测固化为公共契约。
