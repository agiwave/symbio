# 架构总览：原则与分层

> 本文只写**判断一次架构改动是否成立的原则**：设计哲学、目录分层、`Plugin` 契约、
> 六条取舍、三条判据、架构面的妥协边界。
>
> **目标形态本身**在 [DE-001](001-核心架构.md "DE-001-核心架构")（原语 / Actor / 控制面 /
> Agent 组织）；**施工路径与现状差距**在 [DE-090](090-过渡方案.md "DE-090-过渡方案")；
> **架构必须成立什么**由 [GO-002](../001-goal/002-技术目标.md "GO-002-技术目标") 定义；
> **判据怎么执行**归 [DE-016](016-工程落地与验证.md "DE-016-工程落地与验证")。
> 运行时拓扑以 [系统地图](004-系统地图.md "DE-004-系统地图") 为准；
> 插件 × 挂载点 × 路由 × 工具的权威清单以
> [当前事实表](../004-ref/006-当前事实表.md "RE-006-当前事实表") §1 为准。

## 核心设计哲学

Symbio 的设计核心是**分形插件架构（Fractal Plugin Architecture）**。

### 1. 自相似性

每个插件都可以作为容器包含子插件，对外暴露的接口完全一致。容器类插件（`home` /
`composite`）和业务叶子插件（`local` / `web` / `model` / `agent` …）在接口上是对等的
——`Plugin` trait 只需要实现 `route` 与 `traverse` 两个方法。

### 2. 对称通信

通过统一的 `route` 入口，抹平同步调用、异步流式输出和双向会话的差异；用一个枚举
覆盖 3 种载荷：`Empty` / `Data(PluginSerializeData)` / `Session(PluginChannel)`。

### 3. 能力路由

路径即路由。通过 `/` 分隔的字符串（如 `session/stats`、`local/content_search`）
定位任何插件或具体能力。`traverse` 与 `route` 共享同一路径协议。
（资源不走这条语法——统一经 `vdfs/*` + `<根>/…` 地址。）

### 4. 扁平化实现

物理代码平铺（`symbio/src/plugins/<name>/`），逻辑层级通过 `Composite` 容器动态维护。

## 核心目录分工（`symbio/src`）

源码分三层，**权威清单在代码里**（各模块 `//!` 头注释写明自己是什么）：

- **`symbio_core/` — 内核契约层**：`Plugin` / `PluginInvokeRequest` / `PluginPayload`、
 能力系统（`capability*`）、跨端 schema、资源访问契约（`vdfs`）、模型契约
 （`model_provider`）、上下文键（`keys`）等。**准入判据是「依赖方数量」，不是
 「够不够底层」**（[D-023](001-核心架构.md "DE-001-核心架构")）。
 模块清单见 [`symbio_core/mod.rs`](../../symbio/src/symbio_core/mod.rs)。
- **`plugins/` — 实现层**：所有插件平铺存放，容器与叶子实现同一 `Plugin` trait；
 职责与插件清单见 [`docs/README.md` §模块文档地图](../README.md#模块文档地图 "docs/README")
 与[当前事实表](../004-ref/006-当前事实表.md "RE-006-当前事实表") §1
 （**本文不复制插件表**——手抄一份必然漂移）。
- **`providers/` — 基础设施层**：嵌入推理与 `vdfs_service`（资源落盘的集中实现）。
 实现清单见 [`providers/mod.rs`](../../symbio/src/providers/mod.rs)。

## 核心 Trait 与路由

`Plugin` trait、帧 / 载荷 / 通道的**线上形状**以 [协议规范](005-协议规范.md "DE-005-协议规范")
为准；绝对地址 vs 相对臂的**地址规则**见
[插件路由地址规则](006-插件路由与地址.md "DE-006-插件路由与地址")。
本节只保留一句契约：**容器与叶子实现同一 `Plugin` trait，寻址全凭路径字符串，
容器在 `route` 里剥离当前层级后转发**；签名与规则表不在此复制。

跨插件调用的唯一合法形态是 `parent.route(ctx.set(PATH, ROUTE_X))`，调用方不得
`use` 被调方的任何符号（[D-042](002-架构总览.md "DE-002-架构总览")）。

## 0. 架构必须成立什么

「架构必须成立什么」的 owner 是 [GO-002 · 技术目标](../001-goal/002-技术目标.md "GO-002-技术目标")
——架构必须成立什么、违反哪条判据会变红，都在那里；本文不复述。
**「为什么这样设计」**只在各设计文档的「关键决策」节里，本文也不复述。

> **一句话架构**：一个智能体平台 = **1 个原语 + 1 个签名约束 + 1 个使用者概念
> + 3 条不变量 + N 行参数数据**。
>
> **新场景 = 加事件格子 + 加投影参数 + 加一行 ActorSpec + 加一行 grants。**
> **新能力 = 在五维五轴坐标系里占一个格子 + 取一组参数值。**

## 2. 六条设计取舍

| 取舍点 | 本方案的选择 | 理由 |
|---|---|---|
| **原语数量** | 1 个（`Store`） | 元素类型与行为都不构成原语（[DE-001 §1](001-核心架构.md "DE-001-核心架构")） |
| **投影的形态** | 函数签名约束（泛型形状受限，`new` 是 `pub`）；不做成 trait | trait 不增加强制力，却多一层抽象；但裸 `type` 别名**也不够**——需要 `new` 配一个泛型边界做不可伪造的门（[DE-001 §1.4](001-核心架构.md "DE-001-核心架构")） |
| **行为（Actor）的地位** | 一等概念，不是原语 | 它无状态、无接口、无不变量——是装配线不是砖 |
| **需要记住的约束** | 3 条判据 | 清单会增长，判据不会（§3） |
| **时延** | 一等契约（不变量 I3） | 对话是基础能力，不能只靠工程优化 |
| **回放承诺** | 只承诺 L0 + L1，**明确放弃 L2** | L2（重执行一致）原理上不成立（[DE-001 §11](001-核心架构.md "DE-001-核心架构")） |

## 3. 三条判据（全部设计的收敛点）

> 架构设计里最容易膨胀的是"注意事项清单"。**清单会增长，判据不会。**

| 判据 | 内容 | 它替代了什么 |
|---|---|---|
| **J1 可表达性** | 若 X 能用**已有参数的新取值**表达，它就是数据，不是机制 | 候选原语清单、退化规则清单、逐条冻结的契约清单 |
| **J2 平凡值** | 任何参数必须存在**平凡值**，且平凡值下系统必须完整运行 | 所有"分阶段简化"的特例分支 |
| **J3 静默失效** | 若某约束被违反时**不产生错误信号**，它必须做成编译期强制或 CI 断言 | 权限、可见域、投影纯度、预算的"靠自觉" |

**J1 决定"能不能加"，J2 决定"简化是否合法"，J3 决定"要不要强制"。** 其余规则都是这三条的推论。

## 4. 架构面的妥协边界

标尺一句话：**架构面必须落地，不得妥协；只有模块内部实现可以妥协。**

| 层 | 内容 | 能否妥协 | 判据 |
|---|---|:-:|---|
| **架构面 · 机制** | 冻结锚点、机制表顶层键、三条不变量、封闭集合 | ❌ | 妥协的代价不是"少一个功能"，而是**后续每次迭代都要重新决定同一件事**——架构的价值正在于"以后再也不必决定" |
| **架构面 · 切分** | **一个能力一个插件**：插件名 = 能力名、可卸载（没有它系统仍完整运行）、互不相关 | ❌ | 插件边界**就是**架构的切分线，它决定"以后加一个能力要不要动已有的插件" |
| **模块内部** | 某插件内部怎么拆函数、字段叫什么、投影函数写几行、单测放哪、e2e 怎么编排 | ✅ | 改动**不出该插件的边界**，换一种写法不影响其它插件，也不触碰冻结面 |

> **为什么把"切分"也算进架构面**：把两个能力塞进一个胖插件，短期少写几行，
> 长期每加一个能力都要重读那个胖插件，且卸载任一个都要动另一个——
> **切分错了，机制再对也救不回来**。

> **一句话**：**妥协的额度只够用在"怎么写"，不够用在"分成几块"。**

**「可卸载」这一行的可跑判据**（不是愿望、也不是「设计上支持」）：`cargo test -p symbio --lib composite::tests` ——
卸载 `loop` 之后会话存储的四条通道（清单 / stat / 转写 / 收件箱写）全绿且 `loop/<sid>` 起始地址为
`NotFound`；只剩 `loop`（等价于卸载了 `session`）时它能构造出来，但每一轮都被 `Forbidden` 挡住
（缺派发令牌）；**必需**插件卸载被 `Invalid` 拒绝且目录还在。三条用例与 `DE-090 §1.1` 步 6 同源。

迁移批次与"本步不做"的正当性判据归 [SP-003](../005-spec/003.md "SP-003")；进度本身归
[DE-090](090-过渡方案.md "DE-090-过渡方案")，本文不记录。

## 5. 模块划分与契约

> 架构 = **模块划分 + 模块间契约**。最好的架构同时做到两件事：
> ① 模块能不断扩充而**不需要修改架构**；② 模块间**完全解耦**（高内聚、零依赖）。
> 这两件事通常互相拉扯——解耦要加中间层，扩展要动接口。本方案靠一处设计同时拿到：
> **把契约从"模块之间"挪到"模块与共享事实源之间"。**

| | 本方案的答案 |
|---|---|
| **模块划分** | 有接口、有边界、可被替换的模块**只有 1 个：`Store`**。<br/>其余（投影、Actor、能力）全是**数据行 + 纯函数**——不是代码模块 |
| **模块间契约** | 不是 A 调 B 的接口，而是**所有模块共同遵守的事件格式**。<br/>契约数从 O(N²) 降到 **O(N)**，新增模块不需要知道任何既有模块 |
| **可扩展性** | 新增能力 = 加事件格子 + ActorSpec 行 + grants 行 + 投影参数 |
| **零耦合** | 代码依赖与类型依赖**被杜绝**；剩下的只有"对事件的依赖"，**不是对模块的依赖**（[DE-018 §3.2](018-模块架构.md "DE-018-模块架构")） |

**三条代价**（不写清楚就会被误读成银弹）：

1. 事件 schema 必须是终态——定错了代价极高；
2. 封闭的是**坐标系**，开放的是**实例**，可扩展性是"在封闭坐标系内无限"；
3. 零耦合意味着**全局性质无处安放**，只能外置为 CI 断言（这正是 J3 的原因）。

> **工程切分见 [DE-018](018-模块架构.md "DE-018-模块架构")**：把系统切成可独立替换的包
> （`store` 唯一不可替换），每个包锚定在某条不变量上，并给出"违规该去哪个模块找"的
> 责任表。DE-001 的"1 个模块"是**架构记账**，DE-018 的"多个包"是**工程切分**——
> 两者不矛盾。

## 6. 验证纪律

架构声称只有在**可执行断言**下才算成立；程序清单、跑法与证据结果归
[DE-016 §5.2](016-工程落地与验证.md "DE-016-工程落地与验证")。四条纪律针对架构文档
最常见的四种自欺：

1. 每条声称对应一条可执行断言——**零断言的程序不可能失败**，"编译运行通过"本身不是证据；
2. 断言的**输入不得包含结论**——把结论写成常量再断言常量等于没验证；
3. 每条断言配一个**反向用例**——改输入后结论必须改变。改了不变，说明判据没在算；
4. **"强制"本身也要有反向用例**——声称"编译期强制"的，必须附一段**已知编译不过**的
 代码，才能区分"真的强制"与"恰好没写错"。

## 关键决策

> 本节是**仍然约束现行代码的取舍**：每条一句决策、一句理由。已退场或主题已消失的决策不在其中（`git log` 是历史）。

### D-001 分形插件架构：容器与叶子同接口

容器与叶子使用同一套 `Plugin` 接口。`home` → `worker(composite)` → 业务插件即是这棵树（插件清单见 [当前事实表](../004-ref/006-当前事实表.md "RE-006-当前事实表") §1）。 自相似（任意插件可被容器包裹以叠加中间件）、可组合（新能力只需实现 `Plugin` 并注册）、可测试（每个插件可独立测试）。 路由解析有运行期开销（可忽略）；

### D-007 静态注册（inventory）

用 `submit_object_creator!` + `inventory` 做编译期静态注册。 零配置（新增插件无需改注册代码）；编译期保证；惰性初始化（首次使用时收集）。 依赖 `inventory` crate；注册顺序不确定（通常无关）。

### D-032 插件身份归 PLUGIN.yml——PluginMeta 从元信息降为出厂自述

评审记录了一处`Plugin::meta` 返回 `PluginMeta`（含 `id` / `name` / `version` / `author`），而 trait 注释自承「唯一运行期消费方是容器」，插件的身份实际来自各自的 `PLUGIN.yml`。

### D-033 生命周期钩子：start 同步、stop 异步，停用与卸载各给理由

`Plugin` trait 原先没有生命周期钩子，「停用」的语义因此只能是「不构造」：插件没有任何机会做清理——关监听、停后台任务、落盘，全都要靠 `Drop`。而 `Drop` 是同步的：不能 await、不能报错、也不区分「停用」「卸载」「退出」。

### D-036 对象创建机制独立成 creator 域——它是系统级反射机制，不是插件专属

`create_object` / `has_creator` / `creator_ids` / `submit_object_creator!` 与注册表内部结构住在 `plugin` 域。三条已有决策都没有决定这件事——D-007 定静态注册的手段、D-023 定「依赖方 ≤ 1 就下沉」、D-035 引用它作为「按 id 装配」的机制，没有一条说它属于 `plugin`。

### D-042 跨插件调用一律经容器 route + 路径常量，不持有对方类型

插件 A 调用插件 B 的唯一合法形态是 `parent.route(ctx.set(PATH, ROUTE_X))` （`parent` 是容器弱引用）。调用方不得 `use` 被调方的任何符号； `ctx` 里的载荷类型必须住在 `symbio_core`。 `agent_run` → `session/chat/send` 已经是这个形态，但它是惯例而非规则。

### D-075 卸载能力先于目录分离：session 切分立三条前置，会话记忆与存储留守

[DE-090](090-过渡方案.md "DE-090-过渡方案") §1 的步骤 6 判据是 「每个插件可独立卸载且系统仍完整」，已把它接成任务并要求先审再切。 会话记忆与存储不切出：它们是会话数据本身，不是可卸载的能力。

### D-092 本阶不做 A2A 对外互操作：定位是本地平台，跨平台协商等有第二个真实对端再说

本阶不实现 A2A（Agent2Agent）对外互操作，也不发布 Agent Card。 内部的多主体与对等协商 （[DE-001 §12](001-核心架构.md "DE-001-核心架构")）继续按自己的事件模型走， 不为将来可能的 A2A 预留抽象。等出现第二个真实对端（不是演示、不是自家另一个实例） 时再开这一批。

### D-098 A2A 对外互操作：暂不接——部署形态还没有对端，task 语义的映射设计先落纸

暂不接 A2A；触发条件（真实跨厂商互操作需求 / 部署形态长出对外服务面）满足其一即重开， 届时照本文的映射表直接施工，不重新裁决。理由与被否掉的替代方案见下。

### D-108 淘汰是单向门：恢复的生产触发器缺席记为边界，自动恢复在本判据下不可能

`EliminationDecider::restoration_event` 保持「有形状、无生产写方」（`#[cfg(test)]`）。 恢复的机制半边是完整的：同格事件（`verdict.asserted`，`change = "restore"`） + last-wins 折叠（`GrantsOverlay`）+ 撤销回路单测。

### D-113 执行方有两种形态——拒绝与显式降级；两者都算 ②，③ 只留给「没有任何人判」

拒绝（错误返回）与 显式降级（当场出声 / 计数 / 置位，且读侧同一判据可复现）。 显式降级要算 ②，必须两条同时成立：当场出声（不静默）+ 有一个可判读的 读数承接同一事实——只打日志没有读数，仍然是 ③。 规则写了，没有任何执行方。③ 必须挂 `mechanism-allow` 带期限， 期限指向尚未闭环的任务或一条决策（这条不变，ME-004 不动代码）。

### D-157 未承诺能力不进承诺清单：SC-014…018 五项草案移出路线图

[GO-001 §1.1](../001-goal/001-产品目标.md "GO-001-产品目标") 曾列出五项有场景、无机制、无判据的能力。
裁决：**全部移出承诺清单，场景文档保留为草案，不立项**。理由按本仓的判据纪律逐项成立：

1. **判据必须先于能力**（GO-003 的判据纪律）：五项的「用户应该看到」全是「缺口：无判据」，
   先写判据再补能力会把愿望写成验收；
2. **机制要么不存在、要么没有消费方**：深度研究缺长循环进度与引用溯源；浏览器自动化缺外部
   运行时与跨步骤会话；数据 / 文件分析缺行级溯源与分页；定时巡检的触发面已有
   （`system.triggered` → `conation.expressed`），但结果收敛口径没有事实；对抗评审依赖
   SC-013 的多智能体能力与尚不存在的质量读数；
3. **承诺清单的语义是「已承诺、有 owner」**，不是「可能有用」。留在表里会让「缺口可查」
   与「承诺」混成同一列。

**重开条件**（任一）：出现真实消费方且能指认一条已有读数作为判据；或某项的机制先以独立设计
落成（含生产者 / 消费者），再回 GO-001 立项。五项草案的正文与边界保留在 `docs/002-scene/`，
它们仍是讨论材料，但不占承诺清单。
