# 义务环判据与归属推导

> **一句话**：环只认「债」这一种单位——**一次端口调用一笔债**，债由 decl 欠出、由 provider 还清，
> 环只做七项职务；不是这七项的东西，不得以机制形式留在环里。
>
> 本文是归属判定的**唯一判据**。凡与本文冲突的既有判断，按 §3 作废清单处理：
> **原文标注作废并指向本条编号，不静默改写**。

## §0 五条不变量

**I-1 单位是债。** 一次端口调用 = 一笔债，事实五格 `request` / `sent` / `response` /
`failed` / `retry`，幂等键 `(port, id, attempt)`。环上**没有「批」这种单元**，也没有
「一个响应包一批调用」；N 次调用 = N 笔债。

**I-2 债由 decl 欠出。** decl 只引用**事实行与端口名**，不引用端口实现、不读端口载荷。
「要调工具」不是模型响应携带的语义，而是声明方（行为 / 能力插件里的 decl）依据事实欠出
`request(port=<工具端口>)`。

**I-3 环的职务只有七项。** 选债 / 派发 / 等待 / 配对 / 记账 / 预算与租约 / 重放。
「保留」的环元素必须能指认它属于其中哪一项。

**I-4 环不碰世界语义。** 环不解析端口载荷、不读 gate、不做批、不做并发策略、不做重试判据、
不做终答判定、不按 turn 组织。

**I-5 provider 只做两件事。** 按契约执行一笔债、把事实写到行上。执行、并发、guard、熔断、
广播、超时、结果守卫全部是 provider 的内部实现。

**I-6 端口接口必须通用。** `PortProvider`（及 `plugin-api` 里所有端口受理面）是环通向世界
的唯一入口，**世界端口种类是开放的**，接口不得具名任何具体世界。

1. **端口身份是数据不是类型**：provider 申报自己服务的端口名（可多个），环只按端口名解析
   provider；不得出现 `ModelProvider` / `ToolProvider` 这类按世界命名的 trait 或分支。
   `D-437` 之后前半句是**结构事实**而非纪律：`ModelProvider` 已经不在环依赖的任何 crate 里，
   想违反得先新增一条依赖边。
2. **载荷通用**：输入 = 端口名 + 行 / 值草稿；输出 = 事实草稿或错误（错误只带通用分类：
   不可重试 / 可重试 / 需人介入）。接口中不得出现 `ToolCall`、`ModelAsk`、`tool_batch`
   一类具名载荷或具名方法。
3. **行形状归端口插件**：某端口有哪些行、字段如何校验，由该端口所属插件声明，provider
   执行时按行契约自校验；接口不承载世界契约细节。
4. **一次一笔**：`execute` 只承诺执行一笔债。并发由宿主调度多笔债或 provider 内部自理，
   接口不出现批、并发度、熔断、gate 读数等策略参数。
5. **执行上下文通用**：`deadline`、取消、幂等键作为通用上下文传入，命名不得带世界词。
6. **能力协商通用**：可选能力位只允许 `streaming` / `cancel` / `idempotent` 这类通用词。
7. **注册即扩展**：端口执行体经装配期的 `PortBindings::bind` 挂上（`bind` 是唯一写入、
   读侧 `get` / `snapshot` 按端口名取），新增世界端口不需要改环、改注册面、改接口。

I-6 是 I-5 的**接口面**：I-5 说「provider 做什么」，I-6 说「环用什么形状问它」。
只要接口具名了一个世界，第二个世界就要么复制一份接口、要么往环里长一个分支——两种都
把世界语义搬回了环。

## §1 唯一判定式

对任一元素，依次问：

1. **它是七项职务之一吗？** 是 ⇒ 归环（保留 / 改写），并指明哪一项职务。
   否 ⇒ 进入 2。
2. **能写成「读事实 → 欠 `request(port=…)`」吗？** 能 ⇒ 归 decl。
3. **能写成「执行一笔债 → 写 `response`」吗？** 能 ⇒ 归 provider。
4. **两者都写不出** ⇒ **不得以机制形式存在**：删除，或降成数据（纯值 / 声明）。

判定式只有这四行；「实现困难」「已有代码顺手」都不构成改变归属的理由（SP-003 纪律 0）。

**端口受理面的额外一问（I-6）**：判为「归 provider」的元素，若它落在**环与 provider 的
接口**上（`PortProvider` 及其方法、端口合同类型），还要再问一次「这个形状具名了某个世界吗？」
具名 ⇒ 改写为通用形状（端口名 + 行 / 值草稿 + 通用错误分类），或移交 provider 内部；
不具名 ⇒ 保留。

## §4 三道门禁

可机械校验的都落成脚本（判据码 `LP-*`，挂 `gate.d`），不可机械校验的留在 §2 判定表。

**LP-001 类型边界**：`crates/symbio-plugin-loop/src` 的生产源码不得 import 任何端口载荷 /
读数类型，只许端口名、事实行、债。判据由 `scripts/loop-purity-audit.mjs` 执行，基线
（`scripts/loop-purity-baseline.json`，LP-001…005 共用一份、字段各管一条）**只许降**。

**LP-002 依赖边界**：`symbio-plugin-loop` 的 Cargo 清单不得依赖任何 provider / 插件 crate
（`symbio-provider-*`、`symbio-plugin-<name>`；`symbio-plugin-api` 是机制门面，不在禁列）。

**LP-003 世界语义词根**：loop 生产源码不得出现 `batch` / `gate` / `read_gates` / `llm` /
`tool` / `model` / `Batch*` / `Gate*` / `Tool*` / `Model*` / `Turn*` / `turn_*` 词根与硬编码
端口行名。基线**只许降**，新增即红；当前读数以脚本输出为准，不在文档里写死计数。

**LP-004 端口接口世界词根（I-6.1 / I-6.2）**：`crates/symbio-plugin-api/src/port.rs` 的
`pub trait` / `pub fn` / `pub struct` / `pub enum` 名字与 `PortProvider` 方法名不得出现
`llm` / `tool` / `model` / `batch` / `gate` 词根。端口名本身由端口插件自报，是数据、不受判。
基线只许降。

**LP-005 载荷类型通用（I-6.2）**：端口受理面的函数签名只许出现通用载荷类型
（`PortInput` / `PortOutcome` / `PortExecContext` / `PortCapabilities` / `PortErrorClass` /
`&dyn PortProvider` / `Arc<dyn PortExecutor>`）；具名载荷入签名即红。基线只许降。

**两人端口验收（不可机械校验的那一半）**：与 model / tool 无关的端口由**各自独立**的
provider 实现同一套通用接口（`PortProvider` + `PortExecutor`），跑通
`request → sent → response` 与 `request → sent → failed` 两条完整债链路。环侧的同一个
通用派发路径由 `crates/symbio-plugin-loop/src/ring/engine.test.rs` 的桩执行体覆盖；
生产第三端口的接入验收在 `crates/symbio/src/notify_port_acceptance.test.rs`。端口声明由所属
插件提交，宿主收集为 `executor(port)`；环不持端口清单，新增端口 loop 侧零改动（D-301 / D-302）。

  带 `Core-Change`。
- **P2 目标。** 把「轮编排」整条移出环：入口改为按债驱动，环只保留**选债 / 派发 / 等待 /
  配对 / 记账 / 预算租约 / 重放**七职。
  轮编排指五样：幕锚与恢复、轮首判决与措辞、模型往返草稿、工具批生命周期、收幕落库 / 派生 / 展示桥；改由事实行、端口执行体、投影器与能力包承接。
- **现状入口链（职责与世界语义）。**

     → `finish_turn`；承载轮首判决与措辞、召回 / 压缩输入、唤醒翻译、落库锚。
  3. `turn_exec::drive`（`turn_exec.rs` 1,732 + `turn_exec/**` 2,261）：幕首 / 轮首四行 /

  4. `SessionDispatchPort` → `tool_dispatch`（1,810 行）：`ToolDispatch` 八面 + 三动作，批配对、节点补建（助手正文 / 推理 / 工具卡）、`CallOutcome` 映射、授权输入、唤醒合成、`RoundEnv`；承载「批是单元、响应展开成 N 调用、节点可写」。

### D-352 中止是驱动级信号：单一所有者 + 随驱动目标入环

> 兑现 §6 的「`abort` 留环（驱动级信号）」；信号通道的形状由此条定死。

- **单一所有者。** 在途 Turn 的信号对象归 `ActiveSessionState`（会话状态）唯一持有；
  `SessionFactSource` 只持同一个 `Arc` 的引用，每次踢驱动读**当前值**挂进
  `DriveTarget::abort`。两份 `Option` 就是两个真源（动作写一边、驱动读另一边，
  中止永不生效）。
- **只置位、不清槽。** 中止动作（`action(<sid>, "abort")`）只把信号置为已取消；
  取走会让本轮后续派发（如工具行）读到空槽、由环现造死信号——「用户按下中止、
  工具照常跑」，中止退化成「只打断当前这次调用」。注销只在 `finish_turn` 的
  同一临界区做一次（工作态落闲与信号注销一起可见）。
- **入口。** `DriveTarget` 新增可选槽；`drain` 把它交给 `FactWorld`，`drive_on_new_fact`
  挂进本轮 ctx 的 `ABORT_SIGNAL`；环构造 `PortExecContext.abort` 时从 ctx 读回
  （不再是 `ExecAbortSignal::new()` 的现造死信号）。
- **执行侧。** 环在派发前检查：已取消 ⇒ 不起新活，按 `failed{status:"aborted"}` 关账；
  模型执行体 `select!` 到 `abort.cancelled()` 即 drop 往返（半截正文由流快照留痕）；
  工具端沿用 ctx 读面（本地 shell 已 `select!` 到同一信号）。
- **收束。** 中止不是失败：`failed.status=="aborted"` ⇒ 会话收束不落兜底、不推失败节点，
  落 `chat.assistant.final{status:"aborted", reason:"interrupted"}`；`outcome=aborted`
  由 `finish_turn` 缓存与 `runtime` 对 `final.status` 的折取给出。SLO 时延排除中止样本
  （被打断的耗时不代表服务能力）。
- **判据。** 这一槽是 `DriveTarget` 的公共形状变更（`symbio-plugin-api`）；它不新增端口动作、
  不改内核语法，只把既有契约 `ABORT_SIGNAL` 的那一头接上。

### D-354 「还开着」按 (port,id) 的最新 attempt 回答

> 归属：读侧口径（`FactView::unresolved()`）。不改 `retry` 的写侧形状。

- **口径。** 一笔债的身份仍是 `(port,id,attempt)`，但「这笔债还开着吗」只由**最新
  attempt** 回答：attempt N 被 `retry` 指向 N+1 后不再算活。
- **为什么。** `retry` 落在下一 attempt 的键上，从不给旧 attempt 落收束；逐 attempt
  独立判 `closes()` 会把每个旧 attempt 留成永久孤儿。`when_no_open` 因此永久不成立，
  出口还会是 `NoDebt`——宿主记 `idle`，轮静默停摆。
- **不改写侧。** `retry` 同时承担「开下一 attempt」的职责，动它会牵到 `attempt()`；
  本条只把读侧改成按最新 attempt 折叠，写侧形状与既有用例的事实序列都不动。
- **中断窗口。** `request` 已落、`sent` 未落就中断：最新 attempt 无收束 ⇒ **算开着**。
  它不会成为新孤儿——下一圈 `plan` 见该键没有 `sent` 会重新派发（同一 attempt，
  `request` 由事实源按身份去重）；若行已不可派，出口按 `D-359` 报 `NeedsHuman`。
- **消费方。** 本会话唯一的生产读方是 `when_no_open`（另有重放判据读同一投影）；
  口径变窄后，`model-after-tools` 在工具重试成功后恢复可欠。

### D-355 出口 `NoDebt` 只用于「账上没有未收束债」

> 归属：出口判据（`drive()` 的返回分支），不是选债。

- **规则。** 没有可派发、可过期、在飞的债之后，还要再看一眼 `unresolved()`：
  空 ⇒ `NoDebt`；非空 ⇒ 把开着的键一并交回调用方（按 `D-359` 分 `Waiting` / `NeedsHuman`）。
- **为什么。** 行被 `when_no_open` 挡住、又无别的行可派，是「还欠着但没人能还」；
  报 `NoDebt` 会让宿主把 `idle` 记成正常完成，而这一轮既没有终答、也没有失败格。
- **之后怎么醒。** 出口不改唤醒机制：驱动只由写口的 `kick` 触发
  （`HostDrive` 的 `running/dirty` + 下一次 `append` 的踢），没有定时器；再有任何
  事实写入（用户发言、授权、外部事件）都会重跑 `drive`，届时重新判一次。
- **边界。** 本条只定 `NoDebt` 的条件；「在飞」与「开着但无人能还」的分工不在这里，
  归 `D-359`（051 §2）。

### D-356 步数上界是环的硬安全阀

> 归属：出口判据（`drive()` 的步数计数与返回分支），不是选债。

- **规则。** 一次驱动最多走 `STEP_BUDGET = 128` 圈（一圈一次 `plan`）。用尽 ⇒ 返回
  `Exhausted { steps, outstanding }`，把仍未收束的债交回调用方；宿主不得据此记 `idle`，
  必须在调用方看得见的地方留痕。
- **为什么 128。** 正常一轮的步数 ≈ 债的「波次」：同一圈的批量派发只算一步，十几轮工具
  往返也只有几十步。再高就不是现实负载，而是环在自旋。它是环对自身推进的硬约束，
  **不放 `DriveSupport` 的配置面**——交出去就等于「能不能跑飞」由每个执行体自觉。
- **超界不静默。** `Exhausted` 既不是 `Waiting`（那是等下一次踢），也不是 `NoDebt`
  （账上还开着债）；语义是「这一轮没跑完」，调用方必须看得见。
- **与中止的关系。** 中止是逻辑停止（`D-352`），步数上界是物理停止；两者都不改写
  已有事实，只决定这一轮不再派发。

### D-357 无进展 = 同一圈没有任何新增事实

> 归属：推进判据（`advanced()`），不是出口归类。

- **规则。** 每完成一圈派发或一圈过期处理，比较这一圈前后的 `(kind, key)` 事实集合：
  一条新增都没有 ⇒ `Stalled(unresolved)`，停环并交回未收束的债。
- **为什么不数「连续 N 圈」。** 「连续 N 圈」要拍一个数字，而数字的合法性无处可证；
  「同一圈零新增」落在事实层面：环的一圈本来就要么落事实、要么推进租约，两者都没有
  意味着这一圈对账本毫无贡献——再跑一圈仍是同一状态，只会在原地自旋。
- **与「空账本」的关系。** 这是 `TC-1c` 的空账本 / 无进展守卫在现引擎里的判法：
  旧条文按「日志尾段为空」判，现按事实身份集合的差判，口径一致、输入不同。
- **可测性。** 正常 `dispatch` / `expire` 都会落新事实，所以生产里「同圈零新增」罕见；
  守卫用 `TestCtx::ignoring_writes()`（把投递全吸收）专测，保证「不写事实的推进」
  不会变成无限自旋。

### D-376 派发时点与确定性时钟：`sent` 先落、执行体后台、迟归整笔丢弃、`now` 只读事实

> 归属：派发时点（`dispatch` / `finish`）与环的时钟（`now_ms`），不是选债。
> 兑现 `DE-022` §1 的 `before` 位与 `D-314` 的「`sent` / `retry` 留环」；本条的契约变更是
> 删宿主面 `DriveSupport::now_ms`、加 `DriveCtx::shared` / `DriveCtx::now_ms`。

- **`sent` 是 `before` 事实，先落再调执行体。** 租约从 `sent.at_ms` 起算
  （`deadline = sent.at_ms + lease_ms`）。执行体挂死时账上已经有这条租约，下一圈
  `plan` 看得到它，`expire` 才能判死或推进 attempt。旧形状把 `sent` 写在执行体返回
  **之后**，执行体一挂，环就停在 `await` 上，`expire` 永远排不上——「租约」只是字段，
  不是超时。`request` 紧随 `sent`、仍在执行体之前落：执行期间产生的世界事实以
  `request` 为直接前件（I2 的溯源锚），租约只是基础设施，不顶替「这次请求」的因果位。
- **执行体在后台任务里跑，不挡 `drive`。** 派发只负责落 `request` / `sent` 并
  `tokio::spawn`；本圈先给已完成的执行体几轮让出机会（保持「派发即完成」的既有
  语义），仍未完成的留在后台，完成时经 `finish` 回写并再踢一次驱动。**不 `abort`**：
  取消会让迟归不可验证，也可能把已有外部副作用切成半截。
- **执行体的读面是这一圈计划时的快照。** 计划只用一次事实快照（`D-343`），派发出去的
  执行体若跑起来再读活账本，就会看见同批兄弟刚落下的事实——「哪一笔先完成」于是决定
  请求正文。快照在 `drive` 里取一次、整批共用（`SnapshotReader`），同批的每一笔看到
  同一份账；先后仍由行的谓词（`after` / `after_port` / `when_no_open`）表达，不由调度
  机缘表达。`finish` 判迟归时读的是活账本：那是「这一笔现在还开不开」的事，不是输入。
- **消费工具产物的行等工具端口收束。** `owes.source` 是工具产物的声明行（`notes.index`
  一类）在计划层带 `after_port(tool)`（`decl_rows`）。产物落格与 `response` 落账都在
  `finish` 里写，谁先到不能由调度机缘决定；门收束后消费行与收尾轮同一圈派发，收尾
  请求的正文因此不含本轮工具才产出的世界事实。
- **挂起用同 attempt 的第二条 `sent` 表达。** 事实源按 `(kind, key)` 吸收重复，先落的
  带租约 `sent` 改不成挂起；挂起因此再落一条 `sent{deadline_ms:null, shard:1}`。
  计划层取最后一条，读到 `null` ⇒ 只等挂起点之后的触发事实，债继续开着。
- **迟归整笔丢弃。** `finish` 落格前先看 `(port, id, attempt)` 这一笔还开不开：账上
  attempt 已推进（`retry` 落在 N+1）、同键已有收束（`failed` / `response`）、或租约
  已过（`now >= deadline`），任一成立 ⇒ 连同执行体产生的草稿一起丢弃。迟到的一次
  往返不许再落格，更不许长出新债。
- **`now` 只读事实。** `now` 取事实时间轴上最晚的 `ts`，不读墙钟。要推进时间就落一条
  带更晚 `at_ms` 的事实——时间是账上的数据，不是进程的环境。宿主实现必须取**全部**
  事实（含世界事实）的最晚 `ts`：触发一次驱动的往往是用户消息 / 工具回执这类世界
  事实，只看五类协议事实会在首圈得到 0，把刚派发的租约算成「早已过期」。宿主面
  随之收窄：删除 `DriveSupport::now_ms`；环内的「现在」由 `DriveCtx::now_ms` 提供
  （默认取五类事实，宿主覆盖为全部事实）。环需要可持有的写口时用 `DriveCtx::shared()`
  拿同一份事实账的句柄（克隆句柄，不克隆账本）。
- **安全阀出口对所有宿主可见。** `Exhausted` / `Stalled` 是 `DriveOutcome` 的中性面，
  随 `DriveReport` 从 `DriveRunner` 返回；唯一生产入口 `drain` 经 `drive_notice` 出声
  （`crates/symbio/src/drive.rs`）。不是 CLI 专有，也不靠宿主各自的日志。
- **判据。**
  1. 挂死执行体：`sent` 在执行体返回前已在账上；执行体挂住时 `drive` 返回
     `Waiting`，落一条更晚的时钟事实后 `expire` 判死并推进环；放行后迟归不落任何
     事实（`a_hung_executor_lets_expire_advance_and_drops_the_late_return`）。
  2. 确定性：同一份事实日志重放两次，事实序列逐字节相同；新落事实的 `at_ms` 一律
     等于日志里的最晚时间，不随墙钟漂移；同一圈派发的执行体读到同一份事实快照，
     请求正文不随同批兄弟的完成先后变化（`replaying_the_same_fact_log_is_byte_identical`）。
  3. 出口：`Exhausted` / `Stalled` 在 `DriveOutcome` 上可断言，`drive_notice` 有出声音
     的用例（`crates/symbio/src/drive.test.rs`）。
- **不改什么。** `response` / `failed` 的载荷仍归执行体（`D-314`）；本条只改它们的
  **落格时点**与背后的事实句柄，不把载荷装配搬回环。

### D-378 工具债的粒度：一调用一笔债，批次只是组织键

> 归属：债表粒度（配对键面）。兑现 I-1「N 次调用 = N 笔债」，不是给环加调度层。
> 本条只冻结键面与语义，实现另开任务。

- **问题。** `tool/debt.rs` 从 `latest_fact_id(EVENT_TOOL_REQUESTED)` 派生**一条**债
  `tool:<request_id>`，载荷把整份 `calls[]` 交给执行体，执行体在内部展开
  （`open_drafts` 为这一笔债落 N 条 `request`，`run_requested` 在 `for` 里逐条跑）。
  这与 I-1 正面冲突：环上出现了「一个响应包一批调用」的单元。三处可观测后果：
  1. **租约 / 尝试 / 幂等是整批的**：一次慢调用把 600s 租约挂住，`expire` 推进
     attempt 后整份清单重入；产物键按 `artifact:{call_id}` 幂等，但外部副作用没有
     幂等保证。
  2. **审批**：一笔要人确认时整笔债返回 `NeedsHuman`，`tool.calls.done` 不落，
     下一轮模型的 `when_no_open(tool)` 等的是**整批**，账上分不出哪几笔已经完成。
  3. **恢复**：多条答复按 `request_id` 去重（`resume` 只留最后一条），同一批里
     第二个待批调用会静默吞掉前一个答复（同一轮第二次提问的调用卡缺失，债层成因就在这里）。
  另有一条同源的读法缺陷：`latest_fact_id` 是单实例惯用法，可见域里有两条
  `tool.requested` 时只有最新一条会开债，旧的一条永远不欠。

- **两种形状（谓词表达）。**
  - **批债（现状）**：
    `DebtSpec::new("tool-calls", TOOL, "tool:<request_id>", {request_id})`
    `.when(tool.requested).lease(600_000, 2)`；恢复行复用同一 id、`.when(user.answer)`。
    谓词只问「这一类事实存在」，批次内容全部在执行体里展开。
  - **逐笔债（取此）**：每笔调用一条
    `DebtSpec::new("tool-call", TOOL, "tool:<request_id>:<call_id>", {request_id, call_id})`
    `.when(tool.call.requested).lease(600_000, 2)`；同一请求内除第一笔外再加
    `.when_id(sent, "tool:<request_id>:<前一 call_id>")` 串**派发链**（见下条）；
    恢复行复用同一 id、`.when(user.answer)`，按 `call_id` 一一配对。

- **裁决。** 取**逐笔债**。`(port, id, attempt)` 的 id 改为
  `tool:<request_id>:<call_id>`：`request_id` 是这一轮模型往返的幂等键
  （`exec.idempotency_key`），`call_id` 是 provider wire id。`request_id` 只作
  **组织键**（投影 / 轮次 / `tool.calls.done` 的分组），不再是债键，环上不出现「批」。
  **拆分发生在写方**：模型执行体按 `calls[]` 落 N 条**逐调用标记事实**
  `tool.call.requested`（载荷只带 `{request_id, call_id}`，调用详情仍留在
  `tool.requested` 的 `calls[]`），债表只按事实行存在性开债——I-2「decl 不读端口
  载荷」不破。**不**给 `DebtSpec` 加 `expand`：那会让债表读 `calls[]` 这个载荷字段，
  且与内核 `Decl.expand` 形成两套展开机制；`Decl.expand` 仍是声明表路径的对偶，
  不搬到命令式债行。维持批债的唯一合法路径是改写 I-1
  （「一次世界交互一笔债」），那会同时放弃逐调用的租约 / 重试 / 审批归因；本轮不选。

- **`when_no_open` / `after_port` 怎么落。** 两者**不改语义、不改代码**，仍是端口级
  判据；变的只是端口上「未收束债」的集合从一整批变成逐调用：
  - `when_no_open(tool)`（`model-after-tools`）：所有调用债都收束后才欠下一轮模型；
    挂起的那一笔仍在集合里，因此下一轮继续等——这是必须的（缺一条结果就不该续跑）。
    与现状的差别是可归因：其余调用已经各自收束，不再被一笔不透明的批债遮住。
  - `after_port(tool)`（工具产物的消费行）：端口这一圈仍有调用被认领就不进计划；
    方向不变，粒度变细。
  - 不新增谓词；`when` / `when_id` / `unless` / 租约判据全部沿用。

- **首派次序（派发链，不绑收束）。** 同一请求的调用按 `calls[]` 串一条链：后一笔的
  `when_id` 绑前一笔的 `sent` 事实（环的「已派发」，按债 id 读），**不**绑
  `response` / `failed` 收束事实。绑收束会让一笔 `sent{deadline_ms:null}`（待批）
  堵住整条链，后面的调用永远选不到，直接违反上一条「其余调用照常派发、照常收束」；
  绑派发只钉住首派次序，挂起的那一笔不挡后面。跨请求不串（链只在同一 `request_id`
  内）。读面是 `exists_id(kind, id)`，只比 `kind + key.id`、**不比 attempt**——问的是
  「这一 id 有过 `sent`」，因此单调：前一笔重试到 attempt 2 不会把后一笔重新挂住。

- **迟归。** 每笔调用各自有 `(id, attempt)` 与租约，`finish` 的迟归判据只看这一笔：
  attempt 已推进 / 同键已收束 / 租约已过 ⇒ 丢弃这一次迟归。其余调用不受影响；
  重试只重跑那一笔，已经收束的调用不会因别人的 attempt 被重新执行。

- **部分失败。** 每笔调用以自己的 `response` / `failed` 收束；一笔失败不收束别人。
  一轮工具「完成」= `calls[]` 里每笔都有终局事实；`tool.calls.done:<request_id>`
  由**终止写方**（与 session 终止写方同类）在每次驱动前后从各笔债的终局重算并补写，
  **不**由执行体的最后一步写——执行体中途死掉时，这一批不能永久停在「未完成」；
  也不由环判定、不按债状态数数。会话侧 `progress` 仍只读这一条标记，不做计数。

- **挂起一笔时其余调用。** 其余调用照常派发、照常收束；只有待批的那一笔以
  `sent{deadline_ms:null}` 挂起。下一轮模型仍等它（`when_no_open(tool)`），但账上
  其余几笔已是终局，UI 的已完成卡片不再被整批拖住。同一批里多笔待批变成多条独立
  债，一个 `user.answer.call_id` 只对应一笔，不再有「最后一条答复覆盖前一条」。

- **代价。**
  1. 写方每轮多落 N 条标记事实（每轮调用数通常个位数，append-only）；
     `tool.requested` 仍是这一轮的清单事实，投影 / 重建 / 轮次窗口不用改读法。
  2. 债表删掉 `latest_fact_id` 的单实例读法，改为按标记事实逐条开债；
     `user.answer` 的配对仍是 D-369 的 `call_id` 读法，但现在是一对一。
  3. 执行体收到的是单笔调用，`run_requested` 里的批循环与 `awaiting_user` 汇总拆掉；
     `tool.calls.done` 的写点从「执行体批尾」改为「终止写方按各笔终局重算补写」。
  4. 用例面：现有「一轮一条 `tool.requested` ⇒ 一笔债」的断言改成「N 条标记 ⇒ N 笔
     债」，并补部分失败 / 一笔待批 / 一笔迟归 / 一笔重试四组。
  5. 环：零改动——这是兑现 I-1，不是给环加能力。

- **不改什么。** 不新增环的批概念、并发策略或新谓词（I-4 / I-6）；不改
  `tool.requested` 的载荷与投影分组；不顺手修同一轮第二次提问的投影缺卡（那是读侧节点
  挂靠，另案）；不在本条落实现。

### D-442 重试归属到行：`retry` 载荷指认重跑行（D-351 的后继）

- **问题。** D-351 留的尾巴：工具端口的首派行（`tool-call`）与恢复行（`tool-resume`）
  共用同一债键 `(port, id)`（D-378 的一调用一笔债）。attempt 自增后，`plan` 的无 `sent`
  分支按**表序先到先得**选行——恢复执行失败可重试时，新 attempt 上重跑的是表序第一行
  （首派行），整次首派跟着重来，而不是实际失败的恢复行。表序是与语义无关的偶然量，
  不该决定「谁重跑」。
- **裁决。** 归属写成三段行账，环不新增机制形状（五类事实、幂等键、租约语义全不动）：
  1. **派发记账**：`sent` 载荷多带一格 `row`（在跑那行的行名）。`sent` 本来就是
     「这一笔由谁在跑」的账，行名是它缺的最后一格。
  2. **推进转录**：租约过期与可重试失败落 `retry` / `failed` 时，把 `sent` 里的
     `row` 原样带进载荷——`retry` 是唯一的「换 attempt 推进」事实，归属必须搭它走。
  3. **选行归属**：`plan` 的无 `sent` 分支先读 `retry.row`：指认了谁，新 attempt 就
     只归谁——表序不再参与重跑；指认的行整圈无人申报（行被删 / 触发事实消失）⇒
     **孤儿判死**（`failed{reason:"retry owner row gone"}`）。没有 `sent` 就没有租约，
     留着只会悬挂；可见的失败优于不可见的停摆（与 `D-357` 同一口径）。
- **不动的路径。** 挂起重燃（恢复的正常路径）走同 attempt 的
  `sent{deadline_ms:null}` 重燃，不产生新 attempt、不涉归属；首派照旧（首圈无
  `retry`，无指认即表序，与旧行为一致）。
- **回落。** 旧账里的 `sent` / `retry` 没有 `row` 时，选行回落表序——与旧行为逐字节
  等价，存档重放不需要迁移。
- **判据**：引擎测试两笔——共键两行、`retry` 指认表序后者 ⇒ 重跑的是被指认行
  （`retry_follows_the_row_that_ran_not_table_order`）；`retry` 指认的行无人申报 ⇒
  无执行体调用、落 `failed`（`retry_owner_row_gone_lands_failed`）。
- **运行期半边不做 e2e，判据钉在引擎层。** 共键两行的重试在真实会话里只有一条
  可达路径：恢复行（`tool-resume`，默认租约 60s / 3 次）在批准恢复里跑真实工具、
  租约到期落 `retry{row}`。把它编进 e2e 需要一次真实工具执行挂起超过 60s 且整个
  会话仍在 CLI 窗口内收束——绿依赖墙钟计时，是脆弱用例；而恢复执行的错误路径
  恒判 `NonRetryable`（缺读面 / 缺产物是账实不符，重跑无益），没有第二条可编排的
  注入口。归属语义在引擎层两笔单测里是**确定性**的（行与事实直接构造，不涉计时），
  那是它该住的层；为凑一条 e2e 给生产代码开计时钩子，代价大于收益。


### D-461 数据的折叠跟着写方走：读数不跨插件折别人的载荷

> 归属：判定式第 4 行（「两者都写不出 ⇒ 降成数据」）在**读侧**的推论。
> 本条不改环、不改端口接口、不改任何事实名；它只回答「一本读数该在哪个插件里折」。

- **问题（一处铁证）。** 模型往返的用量与金额，一件事四段、跨两个插件：

  | 段 | 原来住哪 | 证据 |
  |---|---|---|
  | 写载荷 `usage` / `spend` | `model` | `crates/symbio-plugin-model/src/port.rs` 的 `payload["usage"] / ["spend"]` |
  | 声明「进台账」（两枚章） | `model` 的债行 | `crates/symbio-plugin-model/src/debt.rs` 的 `.accounts_usage().accounts_spend()` |
  | 按章盖章 | 环（原样盖，不判） | `crates/symbio-plugin-loop/src/ring/engine.rs` 的 `stamp_row` |
  | **折成两本账** | **`session`** | `crates/symbio-plugin-session/src/{token,spend}_ledger.rs`（本条已迁走） |

  provider）。它是环的七职之一吗？不是。⇒ 第 4 行：**降成数据**。而「降成数据」的

### D-462 搬不动的载荷格，契约接在判据上，不接在常量上

> 归属：`D-461`（数据跟着写方走）的补条。`D-461` 的前提是「一个写方、一个读方」，
> 所以那两本账能整个搬进 `model`。产物格不是这个形状，而两种「给键找个公共的家」
> 的做法都被判据否掉了——本条记的是那个「否」以及退到哪里。

- **现场。** `artifact.added` 的载荷格有两个写点、三个读点，且读点跨层：

  | 段 | 谁 | 位置 |
  |---|---|---|
  | 基础格（`tool` / `text` / `tool_call_id` / `args` / `success` / `needs_user_action` / `prompt` / `failure_kind`） | `tool` 的唯一装配点 | `crates/symbio-plugin-tool/src/port.rs` 的 `artifact_payload` |
  | 富化格（`file_op`） | 行为的 `annotate`（今天只有 `vdfs`） | `crates/symbio-plugin-vdfs/src/behavior.rs` |
  | 读方 | 机制层一份、插件层两份 | `sdk` 的 `rebuild::artifact_nodes` / `session/projections/changes.rs` / `model/port.rs` 的产物分支 |

  失效形态与 `usage` / `spend` 同一族：写方改名 ⇒ 读方 `payload.get` 读到 `None` ⇒ 走
  默认值（`success` 默认 `true`、`failure_kind` 默认空、`file_op` 缺席即「不是变更」）
  ⇒ 一个**完全合法**的读数。没有判据会红，也没有日志。

- **第一版做法（被否）：把键收进机制层当公共词表。** 落在 `symbio-sdk` 的 `effects`
  （`FileOp` 本来就在那儿），由门面整模块转出。`EX-007`（`D-247`）当场红：

  > 补件不是通用的（1 处带能力名 / 工具名，如 `crates/symbio-sdk/src/plugin/effects.rs`：
  > 插件 id `"tool"` —— `pub const ARTIFACT_TOOL: &str = "tool";`）

  这不是误伤。**机制层认得「有个插件叫 tool」本身就是它不该有的知识**；`D-392` 的
  纪律是词汇由 owner 的清单投影、机制层不手抄。这条判据替本条挡掉了一个看起来最省事
  的落点。

- **第二版做法（被否）：从 owner 的清单生成一份词表。** `events.rs` 走的就是这条路。
  但生成器只能投影**清单里已有的东西**，而产物格今天不在任何清单里——协议五格不登记
  载荷形状（`D-346`）。要生成，先得给 `PLUGIN.yml` 加一节「产物键」，而那一节的唯一
  消费者是这条判据：**为判据造一份事实源**，正是 `D-455` 否掉的形态（判据不许自己塞
  参数），只不过这次塞的是清单。

- **裁决。** 这一格的契约**只能由判据接**：**写方是账本，读方来对账**。写方的键从
  `artifact_payload` 的 `json!` 与各 `annotate` 的元组读出来（源码即账本，不需要第二份
  声明）；读点读的每一格都必须在账上；没有写方、读方却要兼容的格（`round`）在判据里
  显式列出，并且**写方一出现就必须从那一条删掉**。

- **与 `D-461` 的分界（一句话）。** `D-461` 管「折叠归谁」——能搬就搬；本条管「搬不动的
  那些格，契约挂在哪」——挂判据。两条合起来：**能单一拼写的地方就单一拼写，不能的地方
  就单一判据**。

- **判据（`SV-004`，进 `30-docs` 门禁）：**

  | 条 | 判什么 | 它拦的腐烂 |
  |---|---|---|
  | ① | 登记的读点读的每个键，都在写方账上（装配 ∪ 追加）或容错档里 | 写方改名 / 删格，读方静默读空 |
  | ② | 行为的追加键不得与装配格重名 | 两个写点争同一格，读方分不清谁说了算 |
  | ③ | 容错档里的键不得同时有写方 | 容错档变成垃圾桶（「没人写」的格悄悄住进去） |

  登记范围是**函数 / 分支**，不是整份文件：`text` / `tool` 在同一个文件里属于不同的事实
  （应答正文 / 节点正文 / 产物正文），按文件扫会把「同形异义」判成耦合；`model` 的
  `turn_input` 按 `EVENT_ARTIFACT_ADDED =>` 那条分支切，其余键一概不算。两个读点都没读到
  任何键时判红——那说明 `fn` 名或取值形状变了，判据正在恒真。

- **没拿到的那一半，说清。** 读方仍各写一份字面量：**「单一拼写」在这一层拿不到**
  （拿得到它的两个落点，一个被 `EX-007` 挡，一个被 `D-455` 挡）。拿到的是「改一处就红」
  ——对静默读空这个失效形态，红就够了。

### D-463 读可以跨插件，折不能跨插件

> 归属：`D-461` / `D-462` 之后被反复问到的那一问——「能不能让读写都在同一个插件里」。
> 本条不改环、不改协议，只把这条通路的**边界**画清：哪些是机制已经给的，哪些是机制
> 拿不到的，以及「聚合」在这个仓里到底有几种形态。

- **问题要拆成两个动作。** 「读」= 取一个已算好的值；「折」= 在事实切片上跑一个函数。
  今天这个仓里两者的归属规则**完全不同**，混为一谈就会得出错误的结论：

  | 动作 | 谁做 | 机制 | 跨插件合法？ |
  |---|---|---|---|
  | 读 | 任何插件，经 `read_view(name, snapshot)` | 从冻结表取 owner 的 `eval` 跑 | **合法，且是唯一通路** |
  | 折 | 只有 owner，写 `ViewDecl.eval` | 声明在哪个 crate 就归哪个 owner | **不合法**（`D-461` 的现场） |

- **读这一层，机制上早就是「读写同插件」。** `read_view` 跑的是 owner 的 `eval`，读方
  拿到的永远是 owner 算好的一个 `Value`（`crates/symbio-sdk/src/plugin/reports.rs`）。
  `session` 从来没有「折别人的载荷」这个动作——它只**要**。所以「跨插件数据投影聚合」
  不是缺机制：`ViewDecl` + `ReportDecl` 就是那个机制。

- **病在「折」不在「读」。** `D-461` 搬走的两本账病在哪：`token_ledger` 是 `session`
  写的函数，跑在 `model` 写的事实上——**一个函数、两个 owner**。这才是「读写不同插件」。

- **「聚合」在这个仓里只有一种形态。** 三种可能被混用，机制只给一种：

  | 形态 | 机制 | 结论 |
  |---|---|---|
  | 同构合并（N 片**同一条**视图 → 一个数） | `ViewDecl.agg: Option<fn(&[Value]) -> Value>`（`D-281`） | 有 |
  | 视图读视图（A + B → C） | **无位置**：`eval` 的入参是 `fn(&[Event], i64)`，类型上就够不着别的视图 | 不是遗漏，是防环 |
  | 报表读报表 | **无位置**：`ReportCtx` 只有 `principal` / `cap` / `readable` | 同上 |

  后两条是硬的：视图之间若能互相读，`evidence` 展开事实名那套依赖图就废了（依赖图的边按出口格配，见 DE-050）。
  跨视图合成因此只有一条正路——**A 的输出落成一条有 `FactDecl` 的事实，B 读那条事实**，
  于是它回到上表第一行的「合法的跨插件读」。

- **「同插件」能机制化到哪一级（这是本条的正题）。**

  | 级 | 形式 | 今天 | 缺口 |
  |---|---|---|---|
  | 位置 | 视图与所读载荷的写方**同 crate** | 有（`D-461` 靠搬；编译器与用例在手边） | 靠纪律，不靠判据 |
  | 声明 | 视图 owner == 所读事实的 owner | **撤回（`D-479`）**：读跨插件合法，这条规则不成立 | 无（不是缺口） |
  | 出口 | 报表 owner == 折账的 owner | **注释声称同源，实际未校验** | 见下 |

  三张 owner 表都在（`event_owners` / `fact_owners` / `view_owners`，
  `crates/symbio-kernel/src/decl/mod.rs`），三个访问器也都在（`event_owner` /
  `fact_owner` / `view_owner`）。**但「视图 owner == 事实 owner」不是一条该判的规则**：
  `view_owners` 的生产消费者是**出口**那一级（装配期把它喂给 `check_view_owners`，`D-465`），
  而「视图读别家事实」属合法的跨插件读。撤回理由与重开条件见 `D-479`。

- **为什么第二级不能硬判（与 `D-462` 同一堵墙）。** 判 `view_owner == fact_owner` 会
  误伤两类合法读：`slo` 读 `turn.dispatch.tier`（owner 是 `loop`）、以及所有读协议五格的
  视图。根因是 **「事实的 owner」与「载荷的写方」不是一回事**：`response` 由环落账
  （owner = 内核），`response.usage` 由 `model` 写。所以「同插件」在载荷格上只能落到
  **同 crate**——这与 `D-462` 撞的是同一堵墙：载荷写方没有登记的位置，给它造位置会撞
  `EX-007`（机制层不许出现插件 id）或 `D-455`（为判据造事实源）。

- **第三级是真的可做，且发现一处假承诺。** `ReportDecl.owner` 的文档写着「与 `ViewDecl`
  的 owner 同源」，事实是：

  | 项 | 实际 |
  |---|---|
  | 拼写 | `ReportDecl.owner` 是短名 `"model"`；`ViewDecl` 的 owner 是 crate 路径 `"crates/symbio-plugin-model"` |
  | 校验 | `validate` 只判 `slot` / `views` / `fleet` 的形状，**从不查 `owner`**；`owner` 只出现在错误信息里 |

  这是三档里唯一能硬判、且不会误伤的一条：**出这条列的人，必须就是折这条账的人**
  （归一规则 `crates/symbio-plugin-X` → `X`，`glossary` 这类短名原样通过）。它拦的是
  「A 插件把 B 插件的视图登记成自己的出口」与「视图搬走而报表没跟」。

- **一句话。** 「读写同插件」的正确形式不是「插件互不读」——那会把 `slo` 读派发档这类
  合法聚合也拆掉；而是**折的人必须是写的人，读的人必须经由折的人**。前者靠位置（同 crate），
  后者靠机制（`read_view` 只认冻结表里的 owner 函数）。中间那条「owner 对账」是可加固的
  缝，不是必需的墙。

### D-464 全局可变的尺子，让「同一把尺」只是语法承诺

> 归属：`D-463` 的同一族——**机制文档里的承诺，只有在类型上成立才算数**。本条记一次
> 门禁偶发红查出来的既有缺陷，以及它「改了哪一半、没改哪一半」。

- **现场。** `port::tests::section_budget_trims_low_priority_sections` 偶发红：
  `kept.len()` 期望 1、实得 0（「只留得下一段」，结果一段都没留下）。单独跑与连跑三次
  全绿，只在全量并行时出现。

- **根因链（三段，都在代码里）。**

  | 段 | 事实 |
  |---|---|
  | 尺子 | `default_tokenizer()` 是 `OnceLock` 单例，校准系数是 `ratio: AtomicU32`（`crates/symbio-sdk/src/text/tokenizer.rs`） |
  | 换尺的人 | `port.rs` 每收到一次带 `usage.input` 的应答就 `default_tokenizer().feedback(actual, estimated)`（`D-433` 的校准回灌） |
  | 两次读尺 | 用例先 `budget = tok.count(&high)`，再 `fit_sections(..., \|t\| tok.count(t))` —— 同一个实例，两个时刻 |

  并行时另一次往返的 `feedback` 插在两次读数之间：预算按系数 `r₁` 算、成本按 `r₂` 算，
  系数变大一点，高优先级段就「放不下」。

- **定性：这不是测试笔误。** `fit_sections` 的文档写着「成本必须与预算同一把尺」（`D-243`），
  而在一个全局可变系数上，「同一实例」并不等于「同一个值」——承诺在语法上成立、在语义上
  不成立。

- **已修的那一半。** 用例改为注入**确定性成本**（`|text| text.len()`）。被测的是
  「按优先级贪心裁」这条机制，与尺子的具体读数无关；「同一把尺」另有用例钉
  （`section_budget_subtracts_history_and_overhead` 与 `sdk` 的 `fit_sections` 三条）。

- **没修的那一半，说清。** 生产侧 `port.rs` 的 `section_budget` 与 `fit_sections` 仍可能
  用上两个系数。影响是「差千分之几、多裁或少裁一段」，不是正确性错误，所以不在这条线上
  放大改动。要做时的第一步很明确：`CalibratedTokenizer` 加一个 `frozen()` 返回固定系数的
  计量器，`section_budget` 改收它——但那会牵动 `prompt_tokens_with` 的签名与它的
  「用了哪把尺子」用例，值得单开一轮。


### D-465 出口 owner 从标签变成受检的承诺

> 归属：`D-463` 第三级的落地。`D-463` 把「读写同插件」拆成三档，只有第三档
> （`ReportDecl.owner` == 所读视图的折账 owner）能硬判；本条把那一档从「写在文档里的
> 一句该做」做成**装配期会红的一条判据**。

- **现场（`D-463` 已记，此处只列事实）。** `ReportDecl.owner` 的文档写着「与 `ViewDecl`
  的 owner 同源」，实际两种拼写（短名 `"model"` vs crate 路径 `"crates/symbio-plugin-model"`），
  而 `validate` 的四类判据没有一类碰它——`owner` 此前只出现在错误信息里。

- **做法三件，各就各位。**

  | 件 | 位置 | 它做什么 |
  |---|---|---|
  | `owner_short` | `sdk/plugin/reports.rs` | 归一：`crates/symbio-plugin-model` → `model`，短名与 `kernel` 原样通过 |
  | `check_view_owners` | 同上 | 对账：逐条视图问「你是谁折的」，与报表署的名比；查不到（视图搬走 / 名字打错）与不是同一人（署错 owner）各出一条**人读的诊断句** |
  | `assert_report_owners` | `declarations.rs::assemble_declarations`（`crates/symbio-sdk/src`） | 判：装配期把对账清单变成一次断言失败 |

- **归一不搬家。** 判据不该要求两种拼写统一：`ViewDecl` 的 owner 是 `declare` 的入参（要能
  grep 到目录），`ReportDecl.owner` 是给人读的标签（进错误信息）。统一形状的代价是全仓改名，
  改完仍然没人查；一行 `strip_prefix` 归一 + 一次比对才是判据。**两种拼写并存是既成形状，
  不是待还的债。**

- **为什么是断言，不是 `Gap`，也不是 `ReportError` 的返回。** 前两条与 `D-339` 同源：
  `Gap` 是内核声明 / 环的词汇，报表是出品装配面（`D-387` 划的界，`reports` 模块文档写着
  「不把错误类型塞回内核」）。至于为什么不让调用方接 `Result`：`validate` 那四类可以降级
  （少一列读数），而**署错 owner 的列没有降级形态**——这条列读出来是对的，只是「谁对这条
  口径负责」的答案是假的。没有人负责的口径比没有这一列更贵。所以它与
  `assert_owners_registered` 并列，在启动前停住。

- **为什么不是 `SV-005` 那种脚本判据。** 这条判据的输入是**冻结声明表**——一个链接期集合
  （哪些插件 crate 在构建里）。Node 侧只能从 Rust 源码正则反推「这个 `const` 落在谁的
  `declare` 里」，那正是 `SV-004` 踩过的坑（见 `D-462`：正则读点恒空、注入才能验证）。
  判据落在唯一同时握着两张表的地方：`assemble_declarations` 既造冻结表，又能问
  `reports()`（同一 crate，两个 `OnceLock` 互不回调，无环）。

- **不会在子集装配里假红。** 报表与它的视图在同一插件 crate 里提交，链接到其一即链接到
  另一个；缺视图只可能是真的缺（视图搬走 / 名字打错），那正是要拦的形状。

- **拦哪三种形状（已注入验证）。**

  | 注入 | 判据输出 |
  |---|---|
  | `model` 的报表署名改 `"models"` | `报表 usage 署 models，但它读的视图 model.usage 由 crates/symbio-plugin-model 折` |
  | `views: &[TOKEN_LEDGER]` 改 `&["model.usage.typo"]` | `报表 usage 要读的视图 model.usage.typo 不在冻结声明表里` |
  | 还原 | 全绿（`crates/symbio` 的 2 条装配判据 + `model/ledger` 的 8 条口径用例不动） |

- **一次被本仓另一条判据否掉的设计。** 第一版把两条诊断做成 `ReportError` 的新变体
  （`UnknownView` / `OwnerMismatch`），门禁当场红：`CS-009`（`arch-shape-audit`）
  数 `pub enum` 变体总数，基线 260 被这两格顶到 262。**不是误伤**：这两个变体没有匹配者
  ——唯一的消费者是装配期 `assert!` 的文本。为一行日志把契约面撑宽两格，与 `D-462`
  「不设公共词表」是同一条纪律的另一面（**没有第二个消费者，就不给它造形状**）。改交
  `Vec<String>`（人读的诊断句）：判据不降级，形状不新增，`CS-009` 的余量不被填。
- **空名不在这里判。** `views` 里的空串归 `EmptyViewName`（`validate` 已判）；对账跳过，
  否则同一处错误报两遍，「哪条判据红了」变得不可数。

- **没做的部分，说清。** 只对账 `ReportDecl.owner ↔ 视图 owner`。`fleet` 落点
  （`axes.conation` 这类）与 `render` 产出的内部键不在本条：前者由装配写进 `fleet` 时才知道
  自己是哪一格，后者是 owner 自己的形状、读方零知识。第二级（`view_owner == fact_owner`）
  已按 `D-479` 撤回（`response.usage` 这类载荷格上「事实 owner」与「写方」不是一回事）。

- **两处连带修正。** ①`Frozen::view_owner` 此前挂 `#[cfg_attr(not(test), allow(dead_code))]`
  ——三个 owner 访问器里唯一没有生产消费者的一张表；本条之后它有了消费者，`allow` 撤掉。
  ②同一条事实在 `scripts/baselines/arch-dead-code.json` 里也有一行（零调用 47 → 46，
  `AD-002` 判「在基线里但已经接线」⇒ 必须同批下调）：基线留出的余量会被下一次新增正好
  填进来，所以销账必须同批做。

### D-479 第二级撤回：「视图 owner == 事实 owner」不是一对可判关系

> 归属：`D-463` 那张三级表中间一行的收口。这一行长期挂着「数据就绪，校验缺席」，
> 被反复当成欠账盘点；本条核完认为它**不是判据没写，是规则本身不成立**。

- **三件事的核查。** ①`view_owners` 有生产消费者——装配期 `assemble_declarations` 把
  `frozen.view_owner` 喂给 `check_view_owners`（`D-465` 的出口对账），`allow(dead_code)`
  已撤，死码基线同批下调。②`ViewDecl.reads` 声明的是**读**，不是折；`D-463` 第一张表已定
  「读跨插件合法且是唯一通路，折才必须同 owner」。按 owner 相等判，等于把合法读判成违规。
  ③这不是理论：今天 **14 条视图里 7 条**读的是别家 owner 的名字。

  | 视图 | 读的载荷 | 事实 owner |
  |---|---|---|
  | `slo.latency` / `slo.fallback` | `turn.dispatch` | `loop` |
  | `conation.autonomy` / `forecast.remaining` | `task.held` / `task.asserted` / `task.opened` | `task` |
  | `skill.calibration` / `skill.retreat` | `memory.encoded` / `memory.calibrated` | `memory` |
  | `reputation.ledger` | `commitment.opened` 等 | `agent` |

  判据落地当天红的就是这七条，而它们全是「读数不替谁关门」的合法聚合。

- **裁决：撤回第二级，归属表从三级改两级。**

  | 级 | 判什么 | 判据落在哪 |
  |---|---|---|
  | 位置 | 折的函数与它读的载荷**同 crate**（`D-461` 的搬法：「一个函数、两个 owner」过不了编译） | 编译器 + 用例 |
  | 出口 | 报表 owner == 折账（视图）的 owner | 装配断言 `check_view_owners`（`D-465`） |

  「同插件」在载荷格上只能落到同 crate——这是 `D-463` 已经推出的结论；落到同 crate 之后
  第二级与第一级是**同一条判据**，没有独立内容，因此不留名字。

- **不再给载荷字段造登记位。** 要让「事实 owner == 载荷写方」成为可判，得给每个字段登记
  写方：进内核语法（`FactDecl.fields` 从名字变成 `(名字, 写方)`）撞 `D-455`「为判据造数据源」，
  在机制层写插件 id 撞 `EX-007`。它要防的那类缺陷（`token_ledger` 读 `response.usage` 却在
  `session` 里折）已被位置与出口两级夹住，剩下的只是「诊断更细」。

- **重开条件（可观测，不是「以后再说」）。**
  1. 出现一次「A 的视图读了 B 未对外导出的载荷字段，B 改字段后 A 静默返回空」的真实事故
     ——读数为空而全部判据仍绿；
  2. `shared_events` 扩到事实 / 视图位：那时「视图只能读对外导出的名字」成为可判，且
     **不需要新数据面**，判据与 `check_view_owners` 同住装配期。

- **判据**：`DE-047` 的归属表是两级；`view_owners` 的消费者写成「出口对账」。本条不新增
  代码，`cargo test --workspace` 与既有装配判据原样绿（这也正是「不需要判据」的证据）。

- **不做什么**：不为第二级造事实源（`D-455`）；不在机制层出现插件 id（`EX-007`）；
  不把「A 不许读 B」当规则——那会拆掉 `slo` / `forecast` / `skill` / `reputation` 的合法聚合。
