# Agent 目录规范

> 协议标识：`agent-dir/v2`。Agent 在系统中的位置与装配形态见
> [DE-001 §12.3](001-核心架构.md "DE-001-核心架构")；本文只定义目录协议本身。
>
> v1 定义的是「一个可分发的包里有哪些约定目录」——`prompts/` `skills/` `mcps/` 由宿主
> 自己解释。v2 换了一个主张：**Agent 就是一棵插件树**，约定目录不再由宿主硬编码——
> 技能就是 `skill` 插件、MCP 就是 `mcp` 插件。
>
> 而根下的 `AGENTS.md` **不是插件**：它是这个 Agent 自己的指令文件（§6），
> 由**托管该目录的宿主插件**解释——不需要为它单独造一个插件实例。
>
> **本规范的规范性部分与具体实现无关**（§4–§7、§10、§11）。宿主如何装配、插件
> 提供者有哪些，属于宿主剖面（附录 A 记录 symbio 的剖面）。

### 本规范中的要求级别

关键词「**必须**（MUST）」「**不得**（MUST NOT）」「**应当**（SHOULD）」
「**可以**（MAY）」按 RFC 2119 的语义解释。

---

## 1. 范围与核心主张

**一个 Agent = 一个目录。目录里有什么，它就会什么。**

| 维度 | OAB v1 | 本规范 v2 |
|---|---|---|
| 单元 | bundle（包格式） | **Agent 目录** |
| 技能 | `skills/<n>/SKILL.md`，宿主解释为提示词 | `skill/` 插件目录，宿主**已有的**技能系统 |
| 工具 | `mcps/<n>.yaml`，宿主自己接 MCP | `mcp/` 插件目录，宿主**已有的** MCP 客户端 |
| 人格 | `prompts/<n>.md`（OAB 独有） | 根目录 `AGENTS.md`（行业通行约定） |
| 装配 | 宿主扫约定目录 | **宿主用同一套插件容器装配** |

### 1.1 同构：父子是同一种东西

这是 v2 与 v1 最本质的差别。

```text
系统 Agent = 系统根 ← 由插件容器装配
子 Agent = 系统根/agent/<id> ← 由同一个插件容器装配
```

两者的**内部结构完全相同**：一层目录 = 一个插件，配置与数据同处。差别只在两处：

1. **谁托管它**：系统 Agent 由宿主直接装配；子 Agent 由 Agent 插件托管（§9）；
2. **插件清单多少**：系统 Agent 挂宿主的全部插件；子 Agent **应当**只挂 `mcp` / `skill`
 等少数与「认知能力」相关的插件（§7.2）。

由此得到一个推论，也是本规范最实用的一条：

> **任何能装进子 Agent 的东西，都能装进系统 Agent；反之亦然。**
> 不存在「只有 bundle 才有」的能力。

### 1.2 不再定义的东西

v1 的下列概念在 v2 中**全部删除**，因为它们已经被宿主既有的插件体系覆盖，
再定义一份就是同一件事两套实现：

- `skills/` 与 `mcps/` 两个约定目录及其解析规则（v1 的约定目录与解析规则）；
- 「工具唯一来源是 MCP」这条约束——它现在由宿主的 `mcp` 插件承载，
 规范不再替宿主决定工具从哪来；
- `prompts/` 的 `priority` 装配与 `$bundle.*` 模板变量（v1 的 `priority` 装配与模板变量）。

### 1.3 不在本规范范围内

- 插件容器的扫描与构造机制；
- 各能力插件（技能 / MCP）自身的配置格式与运行时行为；
- Agent 的发现方式、管理界面与分发渠道；
- 权限执行面的具体代码实现（本规范定义**执行语义**，§5.3；判据落在宿主的
  `web` / `vdfs` 路径入口与装载期，不由本规范规定实现）。

## 2. 术语

- **Agent 目录**：一个 Agent 的完整运行目录，是本规范的基本单元。
- **系统 Agent**：宿主的根 Agent，其目录即**系统根**。
- **子 Agent**：由 Agent 插件托管、位于系统根 `agent/<id>` 下的 Agent。
- **宿主（Host）**：装配 Agent 目录并让其能力对模型生效的一方。
- **能力插件**：Agent 目录下的一个子目录，承载一类能力（如 `mcp/` `skill/`）。
- **插件容器**：宿主中负责扫描目录、构造插件的通用机制（symbio 中是 `composite`）。

## 3. 一致性要求

### 3.1 Agent 目录（生产方）

符合本规范的 Agent 目录**必须**满足：

1. 根目录存在 `manifest.yaml`（或 `.yml` / `.json`），且符合 §5；
2. 每个子目录若承载能力插件，**必须**按宿主剖面的要求自证身份（附录 A.2）；
3. 所有资源引用**不得**指向 Agent 目录之外。

### 3.2 宿主

符合本规范的宿主**必须**满足：

1. **必须**用**同一个**插件容器装配系统 Agent 与子 Agent（§1.1 是规范性要求，
 不是实现建议）；
2. **必须**把 Agent 目录下每个能力插件交给**宿主已有的对应系统**去处理，
 **不得**为 Agent 单独再实现一份技能 / MCP 的解释逻辑；
3. **必须**把根目录 `AGENTS.md` 视为该 Agent 自身的指令与记忆（§6）——
 由**托管该目录的那一方**读取、注入，并给出可编辑地址与容量闸门（§6.2），
 且**不得**让两个 Agent 拥有同一个作用域（§6.2）；
4. **必须**执行 §10 的版本门槛校验，不匹配时拒绝加载；
5. **必须**实现 §11 的安全约束。

> 第 2 条是本规范的灵魂。v1 的失败之处恰恰在这里：它让宿主为 bundle 再写一遍
> 技能与 MCP 的解析，结果两条链长期不同步——宿主侧的技能有工具、bundle 侧的只有
> 提示词，MCP 声明甚至只落了一条日志从未真正启动。

## 4. Agent 目录结构

```text
<agent dir>/
├── manifest.yaml ← 必需。身份 / 版本 / 权限（§5）
├── AGENTS.md ← 该 Agent 自身的指令 / 记忆本体（§6）
├── mcp/ ← 能力插件：MCP server 与工具
│ └── PLUGIN.yml
├── skill/ ← 能力插件：技能
│ └── PLUGIN.yml
└── <其它能力插件>/ ← 由宿主剖面决定
```

### 4.1 约定优于配置

能力插件**不需要在 `manifest.yaml` 里登记**——目录里有就表示已安装。
`manifest.yaml` 只承载**无法从目录推导的信息**：身份、兼容性门槛、权限声明。

### 4.2 目录命名

能力插件目录**使用单数**（`mcp` / `skill`）：它不是一个「装了很多东西的
分类目录」，而是**一个插件实例自己的目录**，与宿主里其它插件目录同构。

（对照 v1 的复数 `skills/` `mcps/`：那时它是「很多份技能文件放在一个约定位置」，
现在它是「技能插件这个实例住在这里」。）

### 4.3 路径根规则

目录内引用的相对路径一律以 **Agent 目录根**为基准。

## 5. manifest.yaml

```yaml
spec: "agent-dir/v2"
id: "com.acme.code-reviewer"
name: "代码评审专家"
version: "1.2.0"
description: "以资深评审视角审查代码……"
authors: ["acme@example.com"]
license: "MIT"
icon: "assets/icon.svg"

requires:
 spec: "^2"

permissions:
 network:
 domains: ["api.github.com"]
 fs:
 read: ["assets/**"]
 limits:
 max_prompt_bytes: 65536
```

### 5.1 字段规则

<!-- list:agent-dir-fields owner -->

| 字段 | 要求 |
|---|---|
| `spec` | **必须**为 `"agent-dir/v2"` |
| `id` | **必须**。以 `[a-z0-9]` 开头，仅含小写字母/数字/`.`/`-`/`_`，长度 1–128 |
| `name` | **必须**。展示名 |
| `version` | **必须**。semver 字符串 |
| `requires.spec` | **必须**。形如 `^N` 或 `N`，见 §10 |
| `icon` | Agent 目录内相对路径，**不得**指向目录外 |
| `permissions.fs.read\|write` | glob 模式，相对 Agent 根，**不得**含 `..`（装载期校验；执行语义见 §5.3） |
| 未知字段 | **必须**允许存在并忽略（向前兼容） |

`manifest` **不得**声明 `skills`、`mcps`、`tools`、`prompts` 之类重复登记目录事实的
字段——能力由目录承载（§4.1）。

### 5.2 身份与目录名的关系

子 Agent 的**目录名**即其实例名。**应当**与 `manifest.id` 的末段一致；不一致时以
`manifest.id` 为准（目录名可能因文件系统限制而变形）。

### 5.3 权限执行模型

四个字段（`network` / `fs.read` / `fs.write` / `limits`）是**授权清单（grant）**，
不是「上限（ceiling）」：列了才能用，没列就是没有。**空清单 = 一律拒**
（fail-closed），与授权表同一条纪律——「不声明就有」的边界不是边界。
裁决（含被否候选）见
[D-153](011-Agent目录规范.md "DE-011-Agent目录规范")。

| 字段 | 执行面 | 判据 |
|---|---|---|
| `network.domains` | 出站请求发出前 | 按**标签边界**匹配主机（`*.example.com` 命中裸域名与任一子域；`evil-example.com` 不中）。空清单 ⇒ 拒 |
| `fs.read` / `fs.write` | 文件路径入口 | glob 相对 **Agent 目录根**判定（§4.3），只管**这个包自己的目录**。空清单 ⇒ 拒 |
| `limits` | 装载期（能力收集那一趟） | 超限即**整轮拒载**，不是运行时截断 |

**glob 语义**：`*` 不跨目录段、`**` 跨任意段、`?` 单字符；空路径（Agent 根本身）
只被 `**` 与 `.` 命中。含 `..` 的 glob 在**装载期**即拒（§5.1）——它是执行面的输入，
一个能逃出包的 glob 会让整份清单失去意义。

**管辖范围**：`fs` 的 glob 只描述 Agent 访问**它自己那个目录**（`<根>/agent/<id>/…`，
含它子树里那份记忆文件）。用户工作目录里的文件不归它管——那是宿主策略
（工作区闸 + 审批）的地界；**别的** Agent 的包也不归它管（没有谁的 manifest 能
描述别人的树）。虚拟地址与物理绝对路径落在 Agent 目录内是**同案**。

**不在守的范围**（写在这里，省得下一个人以为漏了）：shell 的整条命令是**不透明**的，
按参数字符串做 glob 判定是安全表演（命令可以 `cat`、可以 `python -c`、可以软链接）；
MCP 服务器自己发的请求同样出不了一层；模型 API 往返不是工具出站，不该被 Agent
声明闸住（否则没有任何 Agent 能说话）。这三类的既有控制（命令白名单 + 审批闸 /
MCP 授权 / 模型选择）各归其位。

> 四字段同批落地执行方之前，它们是**声明性质**（Rust 侧叫
> `declared_permissions`），见 [D-102](011-Agent目录规范.md "DE-011-Agent目录规范")；
> 「同批为何是硬的、名字的两态」见
> [D-140](011-Agent目录规范.md "DE-011-Agent目录规范")。

## 6. AGENTS.md —— 人格与记忆

Agent 目录下的 `AGENTS.md` 承载两样东西：**它是谁**（人格）与**它记得什么**（记忆）。

刻意选用 `AGENTS.md` 这个行业通行文件名，理由与宿主**工作区 / 智能体**两层记忆一致：
它**不属于某个特定工具**，换工具照样生效，能被 `git` 版本化、被 review。
（宿主还有第三层——会话记忆，落在 `.symbio/session/<id>/MEMORY.md`。它**不适用**
这条约定：会话目录不是 agent 目录，没有「一个 Agent 住在这里」这回事。）

- **必须**是 UTF-8 纯文本；
- 文件不存在 / 为空 = 该 Agent 没有人格与记忆，**不得**报错、也**不得**注入占位文本；
- **不可删除**：要清空就写入空内容。

### 6.1 与系统提示词的关系

宿主**必须**把它注入系统提示词。注入多少、超出如何截断，由宿主按自己的容量策略
决定；本规范只要求**注入的内容与文件一致**，不得改写。

宿主**应当**同时给出它的**可编辑地址**与容量闸门——一个模型改不动、只能干看的
「指令」等于半件东西（§6.2 判据 1）。

### 6.2 一个作用域只有一个所有者

这是**并集装配（§8.2）能成立的前提**：

> 同一个 `AGENTS.md` **不得**被两个所有者同时拥有。

否则同一份内容会进两次上下文，而模型改不动它——两份都失去意义。

「所有者」= **同时掌握读写面与注入面的那一方**。规范不规定它是谁（那是宿主剖面的事），
但规定了两条可检验的判据：

1. 注入该文件的**必须**与提供其可编辑地址、执行其容量闸门的，**是同一个所有者**；
2. 该所有者**必须**按作用域区分文件——「系统 Agent 自己的那份」与
 「每个子 Agent 各自那份」是**两个作用域、两份文件**，不得用一份文件兼任。

⚠️ **不得靠改指其它插件的作用域来实现第 2 条。** 例如「把子 Agent 树里
`memory` 的工作区腿改指到 `<agent dir>`」这种办法，会让它名实不符（工作区腿
只认 `{workdir}`，见 A.3），于是同一份文件被两个所有者各注入一次。正确做法是
**分形**：同一个插件在每棵树里各有一个实例，实例从**自己目录的父目录**推导
智能体作用域——实例落在 `<agent dir>` 之下，它的作用域自然就是 `<agent dir>`。
symbio 的具体做法见附录 A.3。

## 7. 能力插件

### 7.1 格式由宿主剖面决定

本规范**不定义**能力插件内部的配置格式——那是宿主的既有系统，规范不去重写它。
本规范只要求：

1. 每个能力插件目录**必须**能被宿主的插件容器识别（附录 A.2）；
2. 宿主**必须**把它交给对应的既有系统，而不是另起一套（§3.2 第 2 条）。

### 7.2 推荐的最小集合

子 Agent **应当**只挂与认知能力相关的插件。symbio 剖面的推荐集合：

| 目录 | 承载 | 说明 |
|---|---|---|
| `mcp/` | MCP server 与工具 | 工具来源 |
| `skill/` | 技能 | 按需取用的手册与技能工具 |

⚠️ 根下的 `AGENTS.md` **不在**这张表里：它不是能力插件，而是目录自己的指令文件，
由托管该目录的宿主插件解释（§6 / §6.2）——为它造一个「记忆插件」实例，
等于让一个空壳插件去解释它所在目录的父级文件，作用域与容器规则都对不上。

子 Agent **不得**挂载与会话编排、模型网关、宿主基础设施相关的插件——那些属于系统
Agent，不属于「一个 Agent 会什么」。

### 7.3 失败语义

单个能力插件构造失败是**软故障**：记一条诊断并跳过，Agent 其余部分照常装配。
`manifest` 缺失或校验失败是**硬错误**：拒绝加载整个 Agent（§10）。

## 8. 装配语义

### 8.1 装配者是插件容器

宿主**必须**用**同一个**插件容器装配系统 Agent 与子 Agent。容器的职责（本规范
不作规定，由宿主自定）通常是：扫描目录、为每个能力插件构造实例、把该插件自己的
目录告知它。

### 8.2 并集：子 Agent 的能力是叠加，不是替换

会话绑定某个 Agent 时，宿主**必须**让**系统 Agent 与子 Agent 双方的能力都生效**
——并集，不是就近覆盖。

理由：系统 Agent 的基础设施（会话、模型网关、文件系统工具等）不因子 Agent 而消失；
子 Agent 只是**附加**它自己的技能、工具与记忆。

### 8.3 命名空间隔离（并集的必要条件）

并集**必须**以命名空间隔离为前提，否则「并集」会退化成「互相覆盖」：

1. **提示词段**：宿主**必须**给来自不同 Agent 的同名段加上来源标记，使它们都进入
 上下文，而不是后者覆盖前者；
2. **工具**：同名工具**不得**同时暴露给模型。宿主**必须**消歧（加来源前缀 / 后缀），
 或拒绝加载并记录明确诊断；
3. **VDFS 挂载点**：同类挂载点**应当**按来源分层，避免两个 Agent 的节点混在同一路径下。

> ⚠️ 实现提示：装配顺序**不得**被依赖。宿主若用无序容器（哈希表）遍历插件，
> 「后注册者覆盖」是不确定的——必须先做命名空间隔离，再谈注入。

## 9. 托管关系（子 Agent）

子 Agent 位于系统 Agent 的 `agent/<id>/` 下，由 Agent 插件托管。

宿主**必须**满足：

1. Agent 插件**必须**能枚举 `agent/` 下的子 Agent 目录（目录名 = 实例名）；
2. 为每个子 Agent **必须**用插件容器构造一棵独立的插件树（§8.1）；
3. 构造时**必须**把自己声明的必需插件目录补出来（§7.2 的推荐集合）；
4. 会话绑定到某个子 Agent 时，**必须**把能力收集与系统提示词收集转发进它的插件树
 （§8.2）；
5. 子 Agent 树**不得**被系统 Agent 的插件容器当作普通插件扫描到——宿主**必须**
 保证插件容器只扫一层。

### 9.1 构造时机

本规范不作要求。宿主**可以**在启动时全量构造，也**可以**惰性构造并缓存。
**应当**惰性构造：子 Agent 数量可能很多，全量构造会连带启动全部 MCP server。

## 10. 版本化与接入判定

沿用 v1：协议版本 `spec: "agent-dir/vN"` 是匹配判定的基准，Agent 版本 `version`
仅信息性。

1. Agent 在 `requires.spec` 声明依赖的协议主版本（如 `"^2"`）；
2. 宿主在**加载期**严格匹配：`^N` 与宿主支持的主版本**相等**方可接入；
3. **不匹配必须拒绝接入**，且**不得**静默降级为「无人格的通用助手」；
 错误信息**必须**写明双侧版本。

## 11. 安全考虑

1. **路径穿越**：Agent 目录内所有路径引用**必须**被限制在目录内；解包归档时
 **必须**逐条目校验规范化路径落在目标目录内。
2. **提示注入**：`AGENTS.md` 与技能内容会进入系统提示词。宿主**应当**向用户明示
 Agent 来源，并对来自不可信第三方的 Agent 保持警惕。
3. **工具风险**：工具由 `mcp/` 插件提供，其隔离与审计由宿主的 MCP 客户端策略决定。
4. **资源限额**：宿主**必须**执行 `permissions.limits`——超限即整轮拒载，
 不是运行时截断。四个字段一并接入，不接受部分执行（半执行不进仓、名字只有两态见
 [D-140](011-Agent目录规范.md "DE-011-Agent目录规范")）。四字段的执行面、glob 语义
 与不在守的范围见 §5.3；整条链的裁决见
 [D-153](011-Agent目录规范.md "DE-011-Agent目录规范")。

## 附录 A：symbio 剖面

> 本附录是**信息性**的，记录 symbio 作为宿主的具体做法，不构成规范要求。

### A.1 装配

- 插件容器 = `composite` 插件；系统根由 `home` 经 `PLUGIN_DIR` 告知它；
- 子 Agent 树由 `agent` 插件构造，做法与 `home` 构造 `worker` 完全同形：
 设 `PLUGIN_DIR = <agent dir>`、设 `REQUIRED_PLUGINS = ASSEMBLY_SUB_AGENT_PLUGINS`
 （与系统树共享同一份清单——`memory` / `setting` 的分形实例由它带进子树），
 再 `creator_create_object("composite", …)`；
- `composite` 只扫一层目录，因此 `agent/<id>` 不会被系统树误扫（§9 第 5 条）。

### A.2 能力插件的自证

一层目录是一个插件：目录下的 `PLUGIN.yml` 可被解析、且 `plugin_provider` 指向一个
已注册的工厂，即为合格的能力插件。无 `PLUGIN.yml` 的目录静默跳过（它不是插件）。

### A.3 两份 `AGENTS.md` 归 `memory` 插件

`memory` 插件是记忆的唯一所有者（智能体记忆 + 工作区记忆，两作用域同住
`<根>/memory` 一个挂载点），它以**分形**同时覆盖两个作用域的智能体记忆：

| 作用域 | 物理落位 | 可编辑地址 | 片段标题 |
|---|---|---|---|
| 系统 Agent（宿主自身） | `{homedir}/AGENTS.md` | `<根>/memory/AGENTS.md` | 【智能体记忆】 |
| 子 Agent | `<agent dir>/AGENTS.md` | `<根>/agent/<id>/memory/AGENTS.md` | 【智能体记忆】 |

两条落位都不需要新的上下文键：智能体腿的作用域取自**本插件目录的父目录**（容器
规则是「一层目录 = 一个插件，插件并列在智能体目录下」——系统实例落在
`<homedir>/memory`，子树实例落在 `<agent dir>/memory`）。两个作用域由**同一个
插件的两个实例**天然分开：实例从自己目录的父目录取作用域，谁也不必认识谁的
目录。子树的注册仍经作用域 visitor 加 `agent/<id>/` 前缀（A.4），因此与系统侧
不冲突。工作区腿（挂载名 `WORKSPACE.md`，物理 `{workdir}/AGENTS.md`）同住这个
挂载点，作用域来自会话而非装配。

⚠️ 子树的 `WORKDIR` **不得**被覆写成 Agent 目录。`memory` 工作区腿的作用域
语义是 `{workdir}`，覆写使它名实不符，并与系统侧那个实例读同一份工作区文件、
注入两次。子树**继承**父会话的 `WORKDIR`。

### A.4 并集的命名空间隔离

`put(CapabilityRow::prompt(name, …))` 当前是同名覆盖、且 `composite` 遍历顺序不确定。
实现并集前**必须**先引入来源标记（例如段名带 `agent/<id>/` 前缀），
使两段都进上下文而非互相覆盖。

## 关键决策

> 本节是**仍然约束现行代码的取舍**：每条一句决策、一句理由。已退场或主题已消失的决策不在其中（`git log` 是历史）。

### D-005 Agent 目录宿主（agent-dir/v2）

`agent` 插件是智能体域的托管 agent 目录、经 `<根>/agent` 的 `zip` 新建类型导入、并装配为子树。目录协议是 `agent-dir/v2`——技能 / MCP 复用宿主既有的 `skill` / `mcp` 插件目录，人格是根 `AGENTS.md`。宿主不解释任何「约定目录」：`manifest.yaml` 的 `spec` 与 `requires.spec` 同时满足 §10 门槛，才是唯一接入判据。

### D-026 子智能体的完整会话在 VDFS 空间内自驱动（inbox）

`agent_run` 是「在父会话下派生一次性子会话」的工具，产出归档在父会话的 `subsession` 集合——钉死这一点是为了不把它和「子智能体」混为一谈。「子智能体」是一等`agent/<id>/` 已装配为含自身 `session` 插件实例的完整子树，其存储目录就是自己的插件目录——缺的不是空间，而是在没有调用方连接时驱动它跑一轮的入口。

### D-047 委派者三项真源：判定回 reason、能力走注入、进展读磁盘事实

目标形态是主会话不持有工具，于是主会话缺三样外部事实——worker 何时启动、自己有哪些能力、进展如何。[D-046](001-核心架构.md#d-046-事实能力进-symbio_core不以可选插件承载必须有值的机制 "DE-001-核心架构") 已定 `feat/v2-bridge-b1-fact-envelope` 的处置边界：其插件式结构不在移植清单上，其中的体验价值（含委派者三项真源）另按设计文档路径评估，且改行为面的先写决策。本条即那个「先写决策」的产物。

### D-065 对等侧收束：`commitment.asserted` 缺的不是「写方」而是「对等 offer/assert」——② 与 ③ 同一批，收束格按种类判

能力扩充阶梯（[DE-030-能力阶梯总览](030-能力阶梯总览.md)）的 S08 （[DE-038-多主体与对等承诺](038-多主体与对等承诺.md)）承诺「多主体 + 可追责的契约」， 落地排期待定。

### D-067 产物收束的不变量面：C4 认产物格、`closure_denied` 数产物、恢复锚刻意不认——三处口径一次说清

[D-065](011-Agent目录规范.md#d-065-对等侧收束commitmentasserted-缺的不是写方而是对等-offerassert②-与-③-同一批收束格按种类判 "DE-011-Agent目录规范") 裁决「收束格按种类判」（发言收束问 `reply.*`、产物收束问 `produce.artifact`），并把「对等主体跑一轮」定为合并批。本条裁决的是那次裁决没有覆盖的三处下游口径——它们不在 D-065 的决策文本里， 但收束分种类一落地就必然撞上；

### D-099 授权默认翻 fail-closed——未登记主体不再派生主智能体能力集，认不出的能力名按已收回判

授权面的两处 fail-open 默认翻成 fail-closed，使 「少一行是一条拒绝，不是一条漏判」成为全表唯一口径： `authz::matrix_for` 的派生分支删除。未登记的 `session/<id>`（子智能体 / 对等体） 与 `person/*` / `system/*` 同款处理：表里没有它的行 ⇒ 每个谓词为假。要能写自己的 收束格，就必须在 `authz::ROWS` 里有自己那一行——窄行是唯一入口。

### D-102 Agent 权限声明的中间态——没有执行方，已被 D-153 取代

**本条已失效**：它记录的中间态（Rust 侧改名 `declared_permissions`、四个字段
「没有执行方」）随 [D-153](011-Agent目录规范.md "DE-011-Agent目录规范") 落地
消失——四字段同批有执行方，名字改回 `permissions`。保留在此只因
「同批是硬的、名字只有两态」那段推理仍由 [D-140](011-Agent目录规范.md "DE-011-Agent目录规范")
承载，而 D-102 是它的前置事实；新代码以 §5.3 与 D-153 为准。

### D-140 权限四字段的「同批」是硬约束，名字只有两态——半执行不进仓

[D-102](011-Agent目录规范.md "DE-011-Agent目录规范") 只回答了「这个字段现在是什么」，
没有回答两个必然撞上的问题：**「四字段同批」是排期偏好还是不可妥协**，以及
**半执行时这个字段该叫什么**。本条把两问一起裁掉。

**「同批」是硬的**，理由三条：

1. 四字段共用一条装载路径（`manifest` → `AgentSpec` → 装配），接线点在同一次装配里，
   分批接省不下工作量，只多一个中间态；
2. 中间态的害处是**安全语义错误**而不是缺功能——「声明要成为安全边界」的全部意义在于
   宿主据它过滤；只执行一部分时，宿主看起来在守边界、实际只守了一半，而守了哪一半
  只能靠读代码；
3. 「分批便于独立回退」不成立：回退单位是 git 提交，不是字段。

**名字只有两态**：`declared_permissions` = 四字段都没有执行方，`permissions` =
四字段都有执行方。**不存在第三态**——因为「半执行」这个状态本身不许进仓：一次做不完
就留在工作区（或按 `SP-003 §0 纪律 6` 开一条有名有姓、有期限的豁免），不进提交。
这与「修不完就一起留在工作区」是同一条纪律在权限面上的实例。

**带豁免落半执行时的最小形态**（唯一例外）：§5.3 逐字段列「执行 / 仅声明」，
字段名保持 `declared_permissions`（它陈述的「没有全部执行方」仍有真值），豁免在
执行面收口（四字段各有一条反向用例）时失效，§11-4 与 `DE-090 §4.1` 同步标注。**不许只在 Rust 侧注释里说**——
「哪些字段真管用」的事实 owner 是本规范 §5.3，不是代码注释。

**名字回退的触发条件**：四字段各有一条反向用例（越界必拒、零副作用）全绿的那一个提交里，
改名与文档改状态**同批**完成——`declared_permissions` → `permissions`，§5.3 / §11-4 /
`DE-090 §4.1` / `docs/004-ref/010-机制强制等级清单.md` 的 `声明·Agent 权限` 行四处同步。

| 被否的候选 | 否掉的理由 |
|---|---|
| 允许分档，每档配一个名字（`permissions_partial` 之类） | 名字变成进度条，读的人还得查表；声明面要多承载一个与安全无关的维度 |
| 保留 `declared_permissions` 永久，只改文档 | 把一条已过期的事实留在最显眼的位置——四字段都执行了，名字还在说「没有」 |
| 加编译期告警（`#[deprecated]` 之类）兜住半执行 | 告警落在包作者侧（跨仓），而「哪些字段管用」是宿主侧的事实；包作者看不到宿主的告警 |

### D-153 权限四字段的执行面同批落地——空清单即拒，glob 只管自己的包

[D-140](011-Agent目录规范.md "DE-011-Agent目录规范") 定了「同批是硬的、名字只有两态」，
执行面已同批落地（`declared_permissions` → `permissions`，四处同步）。本条裁的是
兑现时必然撞上的四个语义问题——它们不在 D-140 的决策文本里，但执行面一落地就必然要回答。

**语义是 grant，不是 ceiling**：四个字段是**授权清单**——列了才能用，没列就是没有。
**空清单 = 一律拒**（fail-closed），与授权表（D-099）同一条纪律。「不声明就有」
的边界不是边界，那正是 D-102 判过的坏形状的执行面版本。

**glob 只管自己的包**：`fs` 的 glob 相对 Agent 目录根判定，管的是 Agent 访问
**它自己那个目录**。别人的包与用户工作目录都不归它管——没有谁的 manifest 能描述
别人的树，而工作目录是宿主策略（工作区闸 + 审批）的地界。虚拟地址
（`<根>/agent/<id>/<rel>`）与物理绝对路径落在 Agent 目录内是**同案**；段边界按
目录比（`<root>-evil/x` 不算 `<root>` 里面）。

**三处执行面**：`network.domains` 在出站请求发出前判、`fs` 两个清单在文件路径
入口判、`limits` 在装载期判（超限即整轮拒载——注册进来的行随轮丢弃，等价于拒载）。
判据与代码的归属在 core 的 `symbio_core::agent`：写侧只有 `agent` 插件（唯一能把
`agent_id` 解析成声明的地方），读侧是 `web` / `vdfs` 两族互不相认的宿主工具——
按「插件之间互不 import」的架构原则，声明形状与判据必须作为共享设施住 core。

**不在守的范围**：shell 的整条命令是不透明的，按参数字符串做 glob 判定是安全表演；
MCP 服务器自己发的请求出不了一层；模型 API 往返不是工具出站。三者的既有控制
（命令白名单 + 审批闸 / MCP 授权 / 模型选择）各归其位——把 Agent 声明接到这三处
只会得到一台到处红灯的死机器，不是更安全的机器。

| 被否的候选 | 否掉的理由 |
|---|---|
| 空清单 = 不限制（ceiling 语义） | 与授权表的 fail-closed 纪律相反；「不声明就有」让声明失去边界意义 |
| glob 允许 `..`（相对路径自然延伸） | 执行面的输入，一个能逃出包的 glob 让整份清单失去意义；装载期拒而不是逐次拒 |
| `fs` glob 同时管用户工作目录 | 包作者无权描述工作区；那是宿主策略的地界，两个 owner 必然漂移 |
| shell / MCP / 模型往返也接 Agent 声明 | 命令 opaque、MCP 自发出站、模型往返不是工具出站——接上就是死机器（见上） |
