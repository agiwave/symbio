# 工具调用与产物

## 内容

前置：S01 ｜ **新增机制键 0** ｜ 参数变化 4
## 1. 场景：要什么能力

不只是"说话"，而是**动手**：调一次外部能力（搜索 / 计算 / 读文件），并把结果留成可追溯的产物。

相对 S01 高了什么：**输出从"一句话"变成"一个可被后续步骤引用的对象"**。这一步是 S03 多步任务的前提——
没有产物，多步之间就只能用自然语言传递中间结果，返工无从判定。

## 2. 为什么它能落在 v2 上（J1）

工具调用看上去像"新的一类东西"（很多架构会为它单开一个 Tool 子系统），拆开看只有三件事：

| 看起来新的东西 | 实际是 |
|---|---|
| 工具调用 | 一个 `Reasoner` 的一次 `progressed`，带了副作用 |
| 工具结果 | 一条 `artifact/asserted` 事件——**它是事实，不是特殊类型** |
| 工具清单 | 数据（`grants` 表里的一行），不是机制 |

**判据**：产物能被后续事件引用（`produced_by`）、能被投影过滤、能被审计——它完全符合"事件"的定义。
按 J1，能用已有元素表达的就是数据，不是机制。**新增机制键 = 0**。

### 3.2 方向裁决：产物进不进上下文

**裁决：取「进上下文」。**
§3 的增量行与 §6 相应断言按此表述，`capability-assign` 块的**形状**不动
（机读侧只取机制**键**集，`display` 那个取值不参与 `gen-verify-facts` 的判定）。

**依据三条，都是代码事实，不是偏好**：

1. **不给模型看，模型会重复干活。** `crates/symbio-plugin-model/src/message_builder.rs` 写得很直接——「模型必须看到
 『我请求了什么、拿到了什么』，否则会重复调用同一个工具」。工具交换不是外部信息，
 是模型**自己行为的记忆**；把它排除不是省 token，是让同一动作被重复发起。
2. **「不进上下文」从来不是缺机制，而是逐格取舍。** `TranscriptEntry` 上已有
 `exclude_from_context` 字段，且被用在别处：`message.opened` 的压缩记录节恒 `true`
 （它按定义是界面文本），轮边界汇报与对话面开场白带同一标记。产物格写的是 `false`
 ——是**决定**，不是**缺省**。
3. **产物闸的边界已经划清，且与本裁决一致。** `port.rs::land_artifact`：「闸管的是『入格』，
 不是『发生过』」——不持 `produce.artifact` 主体时这一格**不落**，但**结果照进 prompt**。
 把「是否入格」（授权面）与「模型是否看见」（表达面）分开，正是本裁决站得住的原因。

**对齐「言 / 行」两维的读数口径**（`[[DE-008-能力注册表与能力坐标系|DE-008]]` §2）：
产物属**行**（工具、执行、副作用）；喂回模型的上下文属**言**的表达面。二者不冲突——
进上下文的那份不是「外部输入」，而是「行」在「言」上的**自我回声**。
反过来把它排除，行在言的输入面上就失忆了：那不是省 token，是同一动作重复发起。

> **本裁决买断的是什么**：它**只**决定产物（工具结果）是否进 prompt，
> 不决定**别的**格进不进（那些仍逐格判 `exclude_from_context`），也不决定产物大小怎么截断
> （那是各工具自己的回执口径，见工具 schema）。若将来出现「某个工具回执过大」，
> 处置是**该工具**截断，不是把整族逐出上下文。

**§6 验收断言的执行方**：1 = `turn_runner.test.rs:1728,1783` + e2e t2/t26；2 = `tool_executor.test.rs:1017-1030`；3 = `invariants::budget_exceeded` + `docs/003-design/verify/budget.rs`；4 = `invariants/mod.test.rs` + `verify/invariants.rs` 反例档。

**名册 S02 行**：工具接入→锚 `capability/mod.rs` 生产在用 ✓（`CapabilityCategory` 是**分类标签**）；副作用分级→锚 `breaker.rs`（批首判据：授权走 `production_matrix()`、已耗走声明视图 `cost.ledger`，未授权即 `Refuse`——「分级」的落点在这里，不在分类标签）；幂等与重试→「—」（事实有 `store/mod.rs:106 AppendError::Duplicate`，名册未锚）；执行隔离→「—」（最近似 = WAL 写者令牌 `store/wal.rs`）。

## 4. 平凡值与回退（J2）

| 参数 | 完整值 | **平凡值** | 平凡值下 |
|---|---|---|---|
| `actor.capability` | `produce.artifact` | **`reply`** | 仍完整运行——只用文字描述结果，不留产物 |
| `projection` | `transcript`（产物 tool 行） | `turnstate` | 仍完整运行——模型看不到跨轮工具记忆，退化成「每轮重新交代」；不会崩，但会重复调用工具 |

**注意平凡值不是"关掉功能"**：退回 `reply` 后系统照样能对话、照样能完成闭环，
只是产物不再可被引用 → 返工判定会退化，但**不会崩**。这就是"平凡值下系统完整运行"的含义。

## 5. 静默失效与强制（J3）

| 约束 | 违反时信号 | 强制方式 |
|---|---|---|
| 产物必须带 `produced_by` | **无** | I2 断言 |
| 未授权主体不得产生产物 | **无**（只是多了一条事件） | 写侧 `grants_of` 编译期强制 |
| 工具超时必须有产出 | **无**——静默超时 | I3 断言（`budget.rs` 的 `Yield` 判据：`Silent` 变体即违规） |

## 6. 验收断言

1. 一次工具调用 → 恰好一条 `artifact.added`，`produced_by` 指向发起它的 `task/turn`。
2. 未授权主体尝试写入 → 编译期或运行时拒绝，**且不产生事件**。
3. 工具超时 → 必须产出 fallback 事件，不允许静默。
4. **反向用例**：构造一条 `produced_by` 为空的 `artifact.added` → 断言 1 必须失败。
5. **工具交换必须进上下文**（§3.2 裁决的落点）：一轮里发生过工具调用时，下一次请求的
 messages 里有配对的 `tool` 消息，且 `id` 与请求里的 `tool_calls` 一致、内容是真实
 回执——**模型看不见就重复调用**，这是断言 1 的另一半（事件在格 ≠ 模型看得见）。
 **反向用例**：把该格 `exclude_from_context` 翻成 `true` → 断言 5 必须失败。

**§6 验收断言的执行方**：1 = `turn_runner.test.rs:1728,1783` + e2e t2/t26；2 = `tool_executor.test.rs:1017-1030`；3 = `invariants::budget_exceeded` + `docs/003-design/verify/budget.rs`；4 = `invariants/mod.test.rs` + `verify/invariants.rs` 反例档；**5 = e2e `t27`（审批恢复后同轮续写，工具交换不丢）+ `t55`（多轮工具的跨轮记忆）+ `t59`（工具面契约）+ `t46`（prompt 形状基线逐字段比）**。

## 9. 工具面的暴露层

### D-383 工具面分两层：暴露层由工具自报，激活信号复用已有调用事实

**现状（按代码）**。

- 轮首装配把 `family::TOOL` 的**全部**元数据写进 `session.config.tools`：
  `crates/symbio-plugin-session/src/plugin/turn.rs` 的
  `manager.list(family::TOOL).map(|row| row.meta())`，随后原样进载荷（同文件的
  `"tools": tools`）。这里没有「这一轮用不用」的判断。
- 模型端口只读最近一条 `session.config` 的 `tools` 字段，并把整份交给协议写手：
  `crates/symbio-plugin-model/src/port.rs::turn_input`（每笔模型请求重跑，见同一文件的
  `turn_input(&facts, &events)` 调用点）。四种协议只序列化 `name` / `description` /
  `input_schema`（`protocols/openai_chat.rs`、`openai_responses.rs`、`anthropic_messages.rs`、
  `gemini_api.rs`）。
- `CapabilityMeta` 今天有 `name` / `description` / `input_schema` / `category` / `examples` /
  `risk` / `behaviors`（`crates/symbio-kernel/src/capability/mod.rs`）。`behaviors` 是
  **效果名**，`#[serde(skip)]`，它回答「调用成功后落什么事实」，不回答「注入哪一层」。
- 部署面的开关只有 `plugin_enabled`：它让插件的工具**整体**从工具面消失（`D-217`）。
  那是「装不装」，不是「装了但这次不用」——按它分层的代价是能力在界面上整个消失。
- 本轮采样：工具声明 29,242 B，占请求体 97.1%，每轮全量重发。

**为什么现有形状不够**。

1. **声明面够，激活面与投影面不够**。每枚工具在 `meta()` 里自报描述、风险、行为，已经
   是「能力自己声明」的那张表；缺的是**两样**：字段里没有「我属于哪一层」，请求视图里
   没有「这一层此刻是否在场」的判断。前者加一格自报字段即可，后者不能由 session 在轮首
   一次性写完——那会把激活时刻钉死在轮边界，同轮内的调用永远看不见自己刚激活的面。
2. **`plugin_enabled` 不能替代**。它是部署级、整插件、不可回退；按需暴露是会话级、逐组、
   可随调用出现。两者量词不同，合成一个就没有「装了、配了、但这次不需要」这一态。
3. **过滤必须只在一处**。工具表在四种协议里各序列化一遍；把过滤放进协议写手就是四条
   同规则的分支。放到请求视图（`turn_input`）只需要一个纯函数，协议写手一字不改，且
   「声明多少 / 注入多少」仍能由 `session.config` 与请求体两份读数直接对照。

**裁决**。

① **声明**：`CapabilityMeta` 加 `exposure: ToolExposure`，三变体——
`Always`（默认，今天的行为）、`OnDemand { group: String }`（该组激活后才注入）、
`Entry { activates: String }`（例外：始终注入，成功调用即激活该组）。`group` / `activates`
是**不透明字符串**，由工具自己在 `meta()` 里给，宿主不认识任何一组的名字。

② **默认字节不变**：`Always` 不序列化（`skip_serializing_if`），未声明的工具在
`session.config` 与请求体里逐字与今天相同。

③ **激活不新开事实**：复用 `artifact.added` 的 `tool` 与 `success`（唯一构造点
`symbio-plugin-tool/src/port.rs::artifact_payload`；模型端口已读同一 kind）。一次
`success = true` 且 `needs_user_action = false` 的 `Entry` 调用 ⇒ 该组在本会话激活。
激活是集合语义：同一组被多次调用只算一次，不需要新键、不需要新写方。

④ **唯一投影**：`model::port::turn_input` 在把工具表交给协议写手之前过滤——保留
`Always` 与 `Entry`，`OnDemand { group }` 仅当该组已激活。`session.config.tools` 仍是
**全量声明**，不是第二份「活跃集」。

⑤ **声明期判据**：每个被引用的 `group` 至少要有一枚 `Entry { activates: group }`，否则
该组永远不可达。由扩展面审计与 e2e 夹具判红，运行期不做兜底扫描。

**谁写谁读**。

| 环节 | 谁 | 写 / 读什么 |
|---|---|---|
| 声明 | 每枚工具自己（`meta()`） | 写 `exposure`；宿主只收集，不维护名单 |
| 激活 | `tool` 执行体（既有唯一写点） | 写 `artifact.added { tool, success, needs_user_action }`，不新增事实 |
| 投影 | `model::port::turn_input`（唯一） | 读全量声明 + 已成功调用事实，产出本次请求的工具表 |
| 协议 | 四个写手 | 只序列化收到的工具，不知道「层」的存在 |
| 审计 | `session.config.tools` 与请求体 | 声明量 vs 注入量，两份读数直接对照 |

**代价**。

- 机制面：`kernel` 加一个字段（带默认值与跳过序列化），`model` 加一个纯函数；**不新增**
  事件、端口、`pub trait`、写方，`session` / `loop` diff = 0。
- 能力面：想按需暴露的能力多一枚常驻的小 entry 工具（几百字节），其余工具未被激活时
  **0 字节**；不声明者的字节与今天完全一致。
- 行为面：激活是**会话级粘性**——调用事实不删，一旦激活不再回收；entry 工具本身始终在
  工具面里。生效点是**下一次模型请求**（`turn_input` 每笔请求重跑），不是同一次请求内。
- 风险面：能力只声明 `OnDemand` 而不给 entry ⇒ 该组不可达，由⑤判红；entry 工具的描述
  是模型唯一能看到的「这一组能开什么」，写不清就等于没开。

**验收（硬用例）**。

1. **0 字节**：夹具里一枚 `OnDemand` 工具在 entry 未被调用前，mock LLM 收到的请求体里
   该工具名与 schema **出现 0 次**，且请求体字节差 = 该 schema 的序列化长度。
2. **出现**：调用 entry 成功后的**下一次**模型请求体里出现该组工具；同一会话后续请求
   持续出现。
3. **默认不变**：未声明 `exposure` 的能力，加入夹具前后请求体**逐字相同**（含字节数）。
4. **声明与注入分离**：两次请求的 `session.config.tools` 都含被延迟的工具（声明不等于
   注入）。
5. **反向**：`success = false` 或 `needs_user_action = true` 的 entry 调用不得激活该组。
6. **位置**：`EX-001` 的夹具加一组延迟工具 + 一枚 entry 工具，判据取 mock LLM 的请求体，
   不取工具列表的返回值。

**已知边界与触发条件**。

- **无取消激活、无预算回收**。触发：常驻 entry 工具本身超过请求体的约定份额，或出现
  「用完即收」的用例时，另立决策。
- **激活只能由成功调用产生**。用户意图、宿主事件直接激活某组不在本条；触发：出现
  「一次调用都没有、但必须看见」的用例。
- **压缩会带走激活证据**。激活集合从 `facts` 里的 `artifact.added` 重算；换基后这些
  事实若不在可见切片里，该组回到未激活。触发：出现「压缩后仍需保持激活」的用例时，
  改为写一条可回放的粘性事实（新 owner，另立决策）。
- **供应商若要求会话内工具集合稳定**，本条不承诺；遇到时按供应商记边界，不在此加分支。

**不做**。

- 不在 `session` / `loop` 写能力名、组名或开关清单。
- 不新开 `tool.exposed` 一类事故事实，也不加宿主激活工具：那会多一个「活跃集」的 owner，
  并与已有的成功调用事实重复。
- 不在四个协议写手里各过滤一遍。
- 不给 `Always` 以外的默认值——未声明就是今天的全量注入。

**与 `D-269` / `D-217` 的关系**：本条不是新站位格（没有新时刻、新触发），是「装配期
声明表」这一行的属性 + 请求视图的投影，阶梯的机制键数不变；`plugin_enabled` 的部署语义
原样不动（`D-217`）；不新增 `pub trait`。
