# 个人认知体系注入

## 内容

前置：S06、S09 ｜ **新增机制键 0** ｜ **架构改动 0** ｜ 参数变化 5 ｜ 阶段二→四

## 1. 场景：要什么能力

让智能体带上**某个（些）人的认知能力**：七类认知内容（知识 / 经验 / 技能 / 判断 / 策略 / 直觉 / 情绪）、
内容密度分级、通用性分级（L0–4）、五层存储、激活扩散检索、内外双轨动作空间。
> 本阶对应 `reference/01-认知架构模型.md` 那套体系——**它是本阶梯里压力最大的一阶**：
> 16 条需求用满 10 个机制键里的 **9** 个（`cognitive_fit.rs` 算出）。唯一没被取用的 `store`
> 判的是**部署**，而认知体系要的是索引——索引是 `Store` 的实现细节，见 §2 的 `C06`。

相对 S09 高了什么：S09 加的是"能做什么"，本阶加的是"**像谁那样想**"。

### 3.1 落地状态：这一节里哪些参数今天存在

上表的「投影参数」是**设计记法**（`recall:<键>=<值>` = "这个投影取一个参数"），不是字符串
配置面——仓里没有按这个名字解析的入口。逐条对代码：

| 参数 | 今天 | 说明 |
|---|---|---|
| `recall:tag` | **已在生产** | `recall(viewer, tag)` 的 `tag` 形参。全仓**唯一传标签**的调用点是 `consolidate`（`recall_view` 与 `encode` 都传 `None`），它靠这个过滤只合并同标签的记忆 |
| `recall:layer` / `spread` / `decay` / `density` / `min_generality` | **未落地** | 形参不存在；各自的前置条件不同（`min_generality` 连**值的写方**都没有，见下） |

**为什么 `min_generality` 不照抄落地**：它过滤的是"通用性分级"，而**没有任何地方给一条
记忆标 L0–4**——分级器是算法问题，§7 已把它划在架构之外。参数加上去、值恒缺省 ⇒ 过滤器
**恒真**：多一个看起来在工作、实际从不排除任何东西的旋钮，比没有它更坏（[DE-016](016-工程落地与验证.md "DE-016-工程落地与验证")
全篇批的就是"能算却没人读"）。故本阶**只认机制、不落参数**：等分级器出现，落地动作是
"给 `memory.encoded` 的载荷加一个字段"，读侧那一半照 §5 的结论接。

**已落地的那个实例是承重的**，也是本阶唯一能在生产链上看见的后果：`recall` 的 `tag`
过滤若退化成恒真，`consolidate` 眼里的"最旧两条"会变成**技能**——技能被当经验合并、
随后被排除式遗忘，**没有任何报错**。判据 = `recall.test.rs`（排除 / 可逆 / 活参数三条）
+ `memory_events.test.rs::consolidation_never_merges_across_tags`（生产后果）。
这也是 [DE-016 §4 C16](016-工程落地与验证.md "DE-016-工程落地与验证") 的机制形态。

**§3 其余增量的落地状态**（与上表同批核实，补齐口径）：

| 增量 | 今天 | 说明 |
|---|---|---|
| grants 行 `person:*` ▸ shared | **已在生产（裁决后形态：不加行 + 内容侧产地）** | `authz/mod.rs` ROWS 仍无 person 行（归属裁决见下方块，）：人的读权走 **owner 相等**；「共享」经**内容侧可见域产地**成为生产面——`memory.encoded` 载荷 `vis_scope`（写方两值）+ `stats.rs` 读闸按内容可见域判 |
| `recall:tag` 的 `judgment` 取值 | **已在生产** | 已落实：`memory_events::JUDGMENT_TAG`——轮末把本轮**成功收束**的正文编成 tag=判断 的记忆（`derived_facts::record_learning` 步 11b，与用户发言那条同文去重 / 同截断 / 同溯源；兜底收束不记）。七类认知内容里的「经验」「技能」「判断」从此都有生产写方 |
| 成本侧保留策略 | **已在生产（两个写方标签）** | 保留 = 巩固 + 排除式遗忘：`CONSOLIDABLE_TAGS = [经验, 判断]`（批④ 推广，每条同标签活记忆 ≥4 ⇒ 合并最旧两条，代数上界 max_gen=3 收口），技能标签**在外**（合并会毁 `skill_id` 身份，它有编译 / 置信度闸 / 反自动化回退自己的生命周期）。DE-001 §9.1 的「窗口 / 冷层 / 常驻 / 短」参数化判**阶外**，裁决见下 |

**裁决（2026-10-13，）：`person:*` 行不落地——今天的表形状表达不出它，先立决策再落地。**

三条证据都指向同一个结论：

1. **成对性要求 grants 非空**（`PermissionMatrix::new` 的 `PairingViolation::ReadOnly`），而 7 项能力闭集按「**智能体的**权威动作种类」划分——`authz/mod.rs` 模块头「两张表里的人」已写明**没有一项是「人」的动作种类**。给 `person:*` 填任何一项都是语义谎报，填空则构造期即拒。**「只读成员」这种行形态今天不存在**。
2. **`person:*` 是字面量，不是通配**：`grants_of` / `sees_of` 都是字符串**全等**匹配，而人的地址是具体值（`person/local`）——写一行 `person:*` **永远不会被命中**。塞进表里就是一条死行：它既不授权也不拒绝，只让「本阶有 person 行」看起来有代码支撑——比没有更坏。
3. **`VisScope::Shared` 也没有生产产地**：读侧唯一调用点 `plugins/session/stats.rs` 传的是 `VisScope::default`（`ThreadPrivate`），而 `can_see` 的 `scope` 形参是**内容的**可见域——今天没有任何载荷字段承载它（`memory.encoded` 的载荷里没有 `vis_scope`）。故「共享」要成为生产面，缺的不是一行，而是**内容的可见域产地** + 一个真传 `Shared` 的读侧调用点。

⇒ 落地方向（须先按 [D-055](001-核心架构.md "DE-001-核心架构") 立决策，写方与消费方同批落地）：要么给表加一条**只读成员**行形态（对非智能体主体放宽成对性），要么把「人的读权」表达成 **owner 相等**（`thread_private` 已如此）并把「共享」做成**内容侧**的可见域产地。已登记为待立项。

**裁决（2026-10-15）：人的读权 = owner 相等，不加行；「共享」做成内容侧可见域产地，写方与读方同批落地。**

上一条裁决给的两条路里选第二条，三条理由：

1. **第一条路是形状变宽，第二条路不加任何形状**。「只读成员」行形态 = 对非智能体主体放宽成对性，按 [D-055](001-核心架构.md "DE-001-核心架构") 得先立一条可打开的决策；而人的读权用 **owner 相等**就能表达（`thread_private` 已如此，C10）。且 `person:*` 是字面量不是通配——人的地址是具体值 `person/local`，那一行**永远不会被命中**。为一条死行放宽 core 形状，是拿架构成本换一个看起来在工作的装饰。
2. **7 项能力闭集里没有「人」的动作种类**（`authz/mod.rs` 模块头「两张表里的人」）：给 `person:*` 填任何一项都是语义谎报，填空则构造期即拒（`PairingViolation::ReadOnly`）。这不是表漏了一行，是**主体种类不同**——人的读权不来自能力，来自归属。
3. **「共享」的真实缺口在内容侧**（上一条裁决的第 3 条已定位）：`can_see(viewer, owner, scope)` 的 `scope` 是**内容的**可见域，而今天没有任何载荷承载它。补一行 grants 不治这个病。

⇒ 落地面（写方与消费方同批， ①②）：

- **产地（①）**：`memory.encoded` 载荷加 `vis_scope` 字段（`VisScope::name` / `from_name` 一对字符串形态；认不出的值落 `thread_private`——不把笔误读成越权）。写方生产两值：**经验**（用户发言，人的认知）取 `shared`，**判断**（智能体收束）取 `thread_private`（C10 缺省）；巩固产物继承源可见域（合并放大可见域比丢一次合并更坏）。
- **读方（②）**：`stats.rs` 的读侧闸从恒传 `VisScope::default` 改为按**内容侧最宽可见域**判（`content_scope_of`：这份事实源只要有共享内容就不是纯私有的），并叠**属主恒放行**（`user` 在矩阵无行，`shared` 的「矩阵内可见」若不叠这条会把属主本人挡在门外）。矩阵内主体读得到他人共享内容、矩阵外主体照旧空切片、属主本人与接线前逐字一致。

⇒ 这一步之后，本阶 grants 行的**语义**（智能体读、本人写）全部有生产支撑，只是形态不是一行 grants，而是「内容侧产地 + 归属相等」。判据 = `stats.test.rs::a_matrix_member_reads_shared_content_and_an_outsider_still_cannot`（含反向对照：无共享内容 ⇒ 矩阵成员照旧空切片）+ `memory_events.test.rs` 两条 + `governance/mod.test.rs` 两条 + e2e `t73`（正反两面的生产出口读数）。

**裁决（2026-10-14，）：保留策略落地为「巩固 + 排除式遗忘」，DE-001 §9.1 的「窗口 / 冷层 / 常驻 / 短」参数化判阶外。**

逐格对账（本阶只对**有写方**的东西作判断）：

| DE-001 §9.1 的格 | 今天 | 裁决 |
|---|---|---|
| 工作记忆 = 窗口 | 轮次窗口 / 会话上下文窗口（snapshot 投影 + `context_window`） | **已落地**（S01 既有，不属本阶增量） |
| 情景记忆 = 冷层 | `memory.encoded` 无限留存于 Log，投影侧由巩固收敛 | **已落地为巩固**：`CONSOLIDABLE_TAGS` 每个标签 ≥4 条合并最旧两条、代数上界 3、排除式遗忘可撤销（批④ 覆盖经验 / 判断两个生产写方）。「冷层」若是**存储分层**，那是 `Store` 的实现细节（DE-001 §9.2：索引与存储分层不进签名），WAL 归档段已承担它；若是**投影参数**，巩固就是它今天的形状 |
| 语义记忆 = 常驻 | 无写方（载荷里没有 `vec` 键，[D-110](../../symbio/src/plugins/memory/README.md "symbio/src/plugins/memory/README")；`codebase_search` 是工具不喂记忆） | **阶外**：给没有写方的 tier 配保留参数 = 死旋钮（同 `min_generality` 的判据，§3.1 上表） |
| 程序记忆 = 常驻 | `skill` 标签，编译 / 置信度闸 / 反自动化回退自成生命周期 | **阶外**：它已有独立生命周期，不由巩固代管（合并会毁 `skill_id`）；「常驻」由 append-only 的 Log 天然保证 |

## 5. ⚠️ 一处被复核推翻的"架构改动"——本阶最值得读的一节

### 5.1 最初的判断（错的）

认知文档说 "Level 0–1：LLM 已覆盖，**无需存储**"。
我最初据此判断：要系统级保证，就得让 `append` 能拒绝 → 扩展 `store` 值域 → **触及唯一原语**。
据此在路线图里标了"13 阶中唯一触及原语的一处"。

### 5.2 复核：这是把读侧问题误当成写侧问题

问一句"不存 L0–1 到底防的是什么"，答案是两条：

| 声称的危害 | 它发生在哪一侧 |
|---|---|
| 浪费存储 | 写侧，但**由保留策略解决**（DE-001 §9.1 已有：窗口 / 冷层 / 常驻 / 短） |
| 稀释个人记忆的检索质量 | **读侧**——稀释只在检索那一刻才存在 |

真正的目标**只有一个是写侧的，而且已有参数覆盖**；核心目标（检索质量）是**读侧现象**。
为读侧问题去改写侧的原语，是把问题的位置认错了。

### 5.3 系统里已经有同构的模式：遗忘

[DE-001 §9.3](001-核心架构.md "DE-001-核心架构")：

> **遗忘是 `memory.forgotten` 事件（不是物理删除；Log 永不删，只是投影不再包含）。**

"通用性过滤"与"遗忘"是**同一个模式**：某些内容不再进入 `Recall` 视图，但事实仍在日志里。
既然遗忘是投影参数，通用性过滤也必须是投影参数。**为它单开一条写侧机制，等于在同一个问题上做两套设计。**

### 5.4 决定性理由：可逆性

写侧过滤**不可逆**——一旦"通用性分类器"判断错了（把 L2 判成 L1），内容永久丢失，
而且丢的时候**没有任何错误信号**（J3 所说的静默失效）。
读侧过滤**可逆**——改阈值即可召回，且能回过头审计"当初过滤掉了什么"。

v2 的全部设计都押在"事实永不丢、只改投影"上（append-only + 投影派生）。
写侧过滤是**对这条立场的直接违背**。

### 5.5 结论与本阶的实际做法

| 关注点 | 做法 | 是否改架构 |
|---|---|---|
| 检索质量（核心目标） | `recall:min_generality=2`（读侧投影参数） | **否** |
| 存储成本 | 保留策略（已有参数）+ ingest Actor 的 emit 策略（数据） | **否** |
| 合规性"绝不落盘" | **尚未出现**；若真出现，走决策，且必须过 [DE-016 §3 前置闸门](016-工程落地与验证.md "DE-016-工程落地与验证") | 待定 |

**因此本阶架构改动 = 0**，与其余 12 阶一致。

### 5.6 这一节的元教训（比结论更重要）

> **为某个场景改架构，本身就是架构没想清楚的信号。**
> 遇到这种提议，先问"系统里有没有同构的既有模式"——本例的答案是 DE-001 §9.3 的遗忘。
> 我已经把这条写成决策流程的**前置闸门**（[DE-016 §3](016-工程落地与验证.md "DE-016-工程落地与验证")）：
> 动 F1–F6 之前必须先做第 0 步，找不到同构模式就要写清"为什么已有模式不够用"。

## 6. 验收断言

1. 认知体系 16 条需求 → 越界键 = 0 **且越界取值 = 0**（`cognitive_fit.rs`，取值逐条对 01 §8）。
2. 后台巩固后 `as-of=T` 视图逐字节不变（认知体系会长期跑巩固）。
3. 扩散检索超预算 → `degraded: true` 且带部分结果，不允许静默返回空。
4. **可逆性**：把读侧过滤的阈值调回 0 → 此前被排除的内容**必须重新可检索**（写侧过滤做不到）。
 已落地的实例是 `recall` 的 `tag` 过滤（`min_generality` 本身未落地，见 §3.1）——判据 =
 `recall.test.rs`：放宽阈值即召回，且两次调用之间**事实源逐字节不变**。
5. **反向用例**：注入一条要求"独立认知存储层"的需求 → 审计必须报越界键。
6. **反向用例**：改用写侧过滤实现 → 断言 4 必须失败（内容已丢失，无法召回）。
7. **反向用例**：把某条需求的取值改成 01 §8 之外的值 → 断言 1 必须失败。同一条注入里
 另带两个**合法**取值（通配段 `child:<id>`、子键参数 `recall:tag=…`）作放行对照——
 只会报错的判据与永真的标志一样不值钱。

> 5 / 6 / 7 三条跑在**设计级程序** [`verify/cognitive_fit.rs`](verify/cognitive_fit.rs) 上
> （`rustc` 编译 + 运行，门禁的 verify 档）——它证的是"这套设计装得下"，与 1–4 里跑在生产
> 代码上的判据**不是同一种证据**，引用时别混。同理，1 的两个"= 0"审的是**设计记法**层面
> （键名 ∈ 机制表、取值 ∈ §8 值域），不检查那个取值今天有没有实现——§3.1 才是实现状态。
