# 能力注册表建设

回答开工前必须先答的三个问题。

范围：`symbio_core` 的收集口（`CapabilityVisitor` / `OptionVisitor` / `ConfigurableVisitor`）+
三个默认收集器（`providers/collectors/`）+ 第二实现方（`SubAgentVisitor`）。**不含** 19 个工具的
`Capability::execute` 实现体。

> **本文的定位**：注册表的**建设方案与裁决**——判据、目标形状、三问裁决、落地形态、出口条件。
> 注册表的**当前形态**（能力名册、类型闭集）与「能力能长到哪去」的坐标系论述在
> [DE-008-能力注册表与能力坐标系](008-能力注册表与能力坐标系.md "DE-008-能力注册表与能力坐标系")。
> 两篇原本是一个文件（一个文件装了两件事、各自从 §1 编号），编号因此不唯一；按「一个文件一篇文档」拆开。

## §1 判据：每一步 core 三格净下降，session 行数不增

| 判据 | 表达 | 现有棘轮 |
|---|---|---|
| core 形状只降不升 | `pub trait` 18 · `fn` 成员 56 · 默认体 18 | `core-shape-audit.mjs`（CS-001） |
| 收集口收敛 | `CapabilityVisitor` 16 方法 + `OptionVisitor` 2 + `ConfigurableVisitor` 2 ⇒ **1 个 trait，3 个方法** | 本文档 §2 的账 |
| session 不增 | `session` 非测试行数 ≤ 搬入前 | `find` + `wc -l` |
| 行为不变 | 工具清单逐条比对 + schema 导出比对 + e2e 77 条 | 现有 e2e |
| 零新增机制键 | --- | `verify/mechanism_growth` |

**「不新增 trait、就地变形」是关键选择**：如果新写一个 `trait Registry` 再慢慢删旧 trait，
中途 `pub trait` 会从 20 涨到 21，CS-001 当场判红。因此正确形态是**把 `CapabilityVisitor`
这个 trait 就地改成 3 个方法**——trait 数不变（变换过程中恒为 20），方法数每一步严格下降。
trait 改名（`CapabilityVisitor` → `Registry`）是最后一步的纯重命名。

## §2 六个族，一张表

`Registry` 三方法的表达力来自**族是载荷变体**：加一个族 = 加一个变体，不是加三个方法。
十六方法要解决的问题不是「一个方法参数太多」，而是**六个族各写了一整套三方法**——同一件事
（把登记项交给引擎）被说了六遍。

| 族（`CapabilityRowKind`） | 载荷 | 行名 | 谁读 |
|---|---|---|---|
| `Tool` | `Arc<dyn Capability>` | `meta.name` | 工具循环；子 Agent 作用域投影 |
| `Model` | `{ provider, active }` | `provider_id` | 会话引擎取生效者；插件选自己的模型 |
| `Prompt` | `{ text }` | 段名 | 会话装配系统提示词；`compose` 拼提示词 |
| `Mount` | `{ provider, active }` | 目录名（根行固定 `<root>`） | 访问层取 `<根>` 的服务者 |
| `Option` | `{ field, order }` | `field.key` | 前端设置表单；装配期选项快照 |
| `Configurable` | `Box<VdfsItem>` | 目录名 | 可配置目录清单 |

`Policy` **不在表里**（[D-089](014-单环一表.md "DE-014-单环一表")）：策略的判据依赖 `loop` 私有的
`LoopState`，它接不上这张「在共享地址上被 ≥2 个消费方看见」的表，本就不该有变体。

收集器有**两个实现方**，这是迁移的真正成本所在：

- `providers/collectors/tool_visitor.rs:69` `DefaultToolVisitor`——生产主路；
- `plugins/agent/host/scope.rs:116` `SubAgentVisitor`——子智能体作用域投影，
 它必须与被投影者**同时**改，否则子智能体的工具集会静默退回空表。

`ConfigurableVisitor`（`capability/configurable.rs:63`）与另外两个 visitor 同源（插件配置树的
收集口），并入同一 trait 的动作一并记账，不另立批次。实测它是 **2 个方法**
（`register_configurable` · `list_configurables`）， 原记的「3」多数了一个自由函数。

## §3 表的目标形状

```rust
enum RowKind { Policy, Tool, Model, Prompt, Mount, Option }

struct Row {
 name: String,
 prio: u32,
 kind: RowKind,
 schema: RowSchema, // Tool ⇒ CapabilityMeta；Option ⇒ DetailField；其余按需
 run: Run,
 effects: RowEffects, // risk / approval / retention（Tool 已有）+ 预算档（Policy）
}

enum Run {
 /// 纯决策：策略行。签名收 `&State`——它结构上碰不到 ctx（见 §4 Q1）。
 Policy(fn(&State) -> Option<Step>),
 /// 有副作用执行：能力行。见 §4 Q2。
 Cap(Arc<dyn Capability>),
}
```

trait 只剩三个方法：

```rust
trait Registry {
 fn put(&self, row: Row) -> Result<, RowConflict>;
 fn get(&self, name: &str) -> Option<Row>;
 fn list(&self, kind: RowKind) -> Vec<Row>; // 按 (prio, name) 升序
}
```

`session/loop_registry.rs` 是这张表的**第一任实现**——它现在就长这样，
只是 `RowKind` 与 `Run` 的 `Cap` 变体还没落地。**策略目录的行多一个 `site` 字段**
（决策点闭集，[D-093](014-单环一表.md "DE-014-单环一表")）：能力行不按决策点分，
所以那个字段不属于共享形状，是策略目录特有的第六列。**这张表从 session 出发，最终搬进 core**：
策略行是 `session` 的私有知识，能力行是全插件共用的协议，两者必须同表才能说
「一个能力一个入口」。搬的动作属步骤 6（切插件），不在步骤 4 内。

## §4 三问的裁决（含对 DE-014 §4 的修正）

### Q1 `ctx` 信封与 §3 硬规则 a「只携带引用」

**裁决：`ctx` 不进表。** 它是**执行期环境**，不是**注册数据**。

```rust
// 执行侧持有 ctx，注册行只持能力与判据
let row = registry.get(name)?;
row.run.invoke(args, &env, ctx).await // ctx 由调用方给，不由行携带
```

`Policy` 与 `Cap` 是 `Run` 的两个变体，**策略行在类型上就拿不到 ctx**——不是靠纪律，
是签名。这也让 `Arc<dyn PluginInvokeRequest>` 保持"在每个需要它的调用点显式传入"，
与现网逐字一致。

### Q2 工具结果 → `Vec<Fact>`：**修正 DE-014 §4 的 `Exec` 签名**

DE-014 §4 写的是 `Fn(Capsule, &Store) -> BoxFuture<Result<Vec<Fact>, ExecError>>`。
**不按这个签名实现**，三条理由：

1. **现网 `Capability::execute(args, &ExecEnv, ctx) -> Result<Value, PluginError>` 已经是
 `Run` 的 `Cap` 变体的完整形态**。19 个工具无一需要 `&Store`；让它们都拿到一个 store 句柄，
 是在为一个假设给所有人加参数。
2. **「谁落格」现在有唯一答案**：调用方（`turn_exec` 收束时写）。改成执行体自己产 Fact，
 等于同时改 19 个实现的职责与网格的写方纪律——那是另一个批次，不是搬迁。
3. **`Vec<Fact>` 需要 `ExecError` 与事实网格的类型打通**，那是 core 的形状变更，
 必须走 CS-002 并有决策。迁移批次里夹带它，会把 300 行熔断线直接顶穿。

因此：**`Run` 只有 `Policy` 与 `Cap(Arc<dyn Capability>)` 两个变体**。`Exec` 签名在
**第一个真正需要 Store 的能力族**出现时再引入，届时它的 `&Store` 是 per-session 的
`EventWalStore`（与 `turn_exec` 持有的同一个），不会是全局 store。

> DE-014 §4 的 `Exec` 段与 §5 步骤 4 与此处口径一致。

### Q3 `&Store` 是哪个 Store：**推迟，且推迟本身就是答案**

所有签名零 `Store`。若将来某族需要，判据是：**只可能是 per-session WAL**，因为
跨会话的写入口子一旦打开，double-write 就会从"两处记账"变成"两个真源"。
把它做成显式参数（而不是全局单例）也是同一条理由：参数拦得住调用方，全局拦不住。

## §5 落地形态

- **行词汇** `capability/row.rs`：`CapabilityRowKind`（六值）+ `CapabilityRowPayload` +
 `CapabilityRow`（**两个字段**：名字 + 载荷；族别从载荷派生，结构上不存在两种答案）。
 改一个族 = 加一个变体，`list(kind)` 的签名不再变形——十六方法糜烂的来路正在于「每加一族都要动签名」。
- **meta 不另存一份**：`row.meta` 每次从能力自述现取。两份表示只会在改名装饰器
 （`PrefixedCapability`）上分叉，而那种装饰器改的正是 `meta.name` 本身。
- **`invoke` 不在表上**：按名执行 = `get(name)` + `capability_invoke`，NotFound 文案
 逐字保持。`put` 内裹审批闸（纪律原样）。
- **顺序 = 注册序**：`list(kind)` 按族过滤后即表序（IndexMap），族内不按名重排
 （[D-057](../../symbio/src/plugins/session/README.md "symbio/src/plugins/session/README")）。策略行的 `(prio, name)` 先命中者胜在 session 的
 `loop_registry`，两件事。
- **生效位长在行上**：`Model` / `Mount` 带 `active` 位——「生效者必然是目录里的一员」这条
 不变量由**结构**承载，不再是批量注册的签名。`put` 收到带生效位的行时，先把同族旧生效行
 降位：降位是**换一个 `Arc` 副本入表**（`CapabilityRow::demote`），不是就地改位，否则读者会
 读到「两个生效者」的中间态。旧行**留在表里**（降为普通目录行）：`active` 只答「谁在槽里」，
 「目录里有谁」是同一批行的另一问。
- **根行的行名由构造函数填**：根不是某个插件的目录，不可能由调用方命名，故填保留值
 `"<root>"`，读侧按 `active` 找。一族两形由此各被一处守住——「根不可按名查」与
 「根不在挂载点清单里」是同一个过滤的正反两面。
- **提示词行 = 一段文字**：段名的两条语义写在 `capability/prompt.rs` 模块文档——**注册在这里的
 一定会送达模型**（没有「取一个」的竞争）、**段名是覆盖键不是分类**；空段由拼接方跳过。
- **选项行带 `order` 但不下发**：读侧 `capability_option_fields` 稳定排序后即丢——排序答案与字段
 是同一行的两个事实。
- **作用域规则只在 `put` 一处**：`SubAgentVisitor::put` 按族判——工具 / 提示词 / 选项加
 `agent/<id>/` 前缀，模型族丢弃子 Agent 的注册，子树根行丢弃（否则劫持整个 `<根>`，
 判据 = `scope.test.rs` 单测 + e2e t39）。写入口只有一个，作用域规则也就只有一处。
- **读侧是自由函数，不回头往 trait 挂方法**：`capability_model_active` / `capability_model_resolve`
 （严格查 id，取不到落回生效者——降级方向只有一处定义）、`capability_prompts`、
 `capability_vdfs_root` / `capability_mounts` / `capability_mount`、`capability_option_fields`。
 `capability_mounts` 是**预留的 LLM 可见资源裁剪入口**，当前读侧只有单测——不是死代码，
 判据写在 `mount.rs` 模块文档。
- **同族重注册 = 表语义（同名覆盖）**，不再整体替换目录；跨族同名（表键是全表唯一的名字空间）
 **留一条告警再覆盖**——静默被顶掉的那一族不会以任何别的方式表现出来。告警上岗即顶掉三处
 真碰撞（提示词段名与插件名撞键 memory / setting / model），改的是段名：`agent-memory` /
 `agent-setting` / `model-persona`。
- **收集口名 vs 通道名**：`CAPABILITY_VISITOR` / `OPTION_VISITOR` / `CONFIGURABLE_VISITOR`
 三个键与键类型 `…VisitorKey` 保留——它们命名的是**广播通道**（与 `TRAVERSE_AVAILABLE_*`
 端点成对），不是收集口 trait；实现名 `DefaultToolVisitor` 同此理由保留（住 collectors 层）。
- **core 三格 18/56/18**，`SHAPE_BASELINE` 与之相等。
- **守门人**：同一份清单以两种口径导出逐条相等（走表的 `list(Tool)` 与 `CapabilityMeta` 全量
 转储，含顺序），加顺序 / 覆盖 / 缺失 / 单槽移交 / 族内排序五格；e2e 全绿。

## §6 session 不增的纪律

步骤 4 会让 `session` 变**小**的可能性来自 （`v2_` 前缀退役）与 （工具名
元数据化）先落地。两条硬规矩：

1. **新机制进 `loop_registry`**（它是 `loop` 插件的种子），不进 `chat_loop`。
2. **`chat_loop` 问表**：把 `if let Some(x) = ...` 换成 `registry.get(name)`，净行数为负或零；
 出现净增长时，说明混进了别的东西。

## §8 风险与不动清单

- **`SubAgentVisitor` 是第二个实现方**，漏改它 = 子智能体工具集静默退空。判据：
 e2e（含子智能体场景）全绿，不能只靠单测。
- **`invoke` 是热路径**：`registry.get(name)` 比 `DashMap` 直读多一次匹配。
 判据是 `verify/latency_gate` 不红；若红，`get` 用 `DashMap<name, Row>` 加只读快照，
 `list(kind)` 走排序后的 `Vec`，两者同一份事实的两个视图。
- **不动**：`Capability::execute` 的签名、`PluginError`、`ExecEnv`、审批闸门的
 `risk_for` 取值口径（动的是它的**来源**，不是它的值）。
- **不动**：`traverse` 的广播协议本身。改的是广播的**接收端**（visitor → registry），
 广播方（插件）的调用形态一行不改。

2. `providers/collectors/` 三个 visitor 收敛为一个 registry 实现；
 `SubAgentVisitor` 是同一张表的作用域投影。**已达成**。
3. 工具清单两种口径逐条相等，e2e 全过，core 三格棘轮不升。**已达成**。
4. `session/loop_registry.rs` 长成策略 + 能力同表，行数不含工具实现体。
