# 会话输入与地址

> 本文回答「会话的**输入**（发消息 / 停止 / 重试审批）应该落在哪」。
> 「收件箱怎么消费」见 `crates/symbio-plugin-session/src/transcript/inbox.rs` 与 D-026；
> 「实时面怎么投递」见 D-025 与 [DE-009 §9](009-VDFS规范.md "DE-009-VDFS规范")。本文不复述它们。

---

## 1. 症状

子智能体空间里发起会话后发消息，消息跑在**父智能体**的空间里；同一会话的「停止」
按钮点了没反应。

---

## 2. 根因（三条，逐条可核对）

### 根因 A：`chat/send` / `chat/abort` 是**全局路由**，落点恒为根 session 插件实例

> 两条路由不承担输入（[D-066](012-会话输入与地址.md "DE-012-会话输入与地址")）。本节记录
> 问题发生时的入口形状，作为设计动机。

- `crates/symbio-plugin-session/src/plugin.rs:436-437` 把两条路由交给 `self`——而 `self`
 是**收到这次 `route` 的那个 `SessionPlugin` 实例**。
- 会话发言只有**一条**绝对地址 `session/chat/send`（当时的常量名
 `ROUTE_SESSION_CHAT_SEND`），由**根 composite** 分发 ⇒ 恒为根实例。
- 子智能体空间有**自己的** `SessionPlugin` 实例（`<根>/agent/<id>/session`），但它
 **没有路由入口**：`crates/symbio-plugin-agent/src/host/plugin.rs:577-584` 明确
 `NotFound` 并指路 VDFS。`agent/<id>` 只在 agent 插件的 VDFS 视图里作为挂载点存在。
- 后果：消息进的是**根实例的收件箱**、由根实例消费（`inbox.rs:194`），编排拿到的
 `parent` 是根 composite（`orchestrator/entry.rs:249`）⇒ 人格 / 工具 / 存储全是
 父智能体的。**这就是「发到了父智能体」。**
- `chat/abort` 更安静：根实例 `active_mgr.get_or_create(子 sid)` 造出一个**空状态**，
 `handle_abort`（`orchestrator/consume.rs:369`）读到 `abort_signal = None` ⇒
 什么都不做（还要空等 3s 兜底）。停止无效，且根实例里多一个永生幽灵状态。

### 根因 B：前端会话层**按 id 寻址**，且只认一个全局挂载目录

- `tauri/src/services/vdfsScheme.ts:64-101`：`cachedMountDir` 是**一个**值，来自根
 清单 ⇒ 恒为 `<根>/session`。
- `tauri/src/stores/sessionTranscriptSync.ts:309`：`path.startsWith(\`${S.mountDir}/\`)`
 ——子智能体会话的变更地址 `<根>/agent/<id>/session/<sid>/message/<mid>` **前缀不
 匹配 ⇒ 前端根本收不到**。即使后端跑对了，显示链路也断在这里。
- `stores/sessions.ts:693` 新建会话也写这个全局 mountDir ⇒ 在子空间里点「新建会话」
 会建到根空间去。
- `components/session/ChatMainPanel.vue:95-97`：`:sessionId="store.activeId"`——地址
 在 `components/vdfs/Session.vue` 的 `watch( => props.node?.name)` 就被丢掉了，
 只剩名字；两个空间里的同名 id 会撞车。

### 根因 C：输入面**没有地址这一维**，所以不可能送对

`chat/send` 的信封里只有 `session_id`（一个裸名字），没有「这个会话住在哪个空间」
的任何信息。D-026 已经在**后端**解决了「空间怎么自驱动」（写 inbox 即入队，
e2e `t15-subagent-inbox` 覆盖），但**入口那一跳没跟着改**：前端仍在调路由。

### 结论

不是「发送没走到 inbox」——后端 inbox 是对的。是**入口选错了**：路由是
address-less 的，而子智能体空间只有 address 可达。

---

## 3. 决策

1. **会话的输入统一表达为「对这个会话地址的一次写入 / 动作」。** 路由不再承担输入。
2. 三个入口（见 §4 地址表）。
3. **`chat/send` / `chat/abort` 不承担输入**：它们是「address-less 的入口」——那正是
 bug 本身。输入只有地址写入。
4. **前端会话的身份从「id」升级为「地址」**（`mountDir` + `sid`）。
5. **用户消息的显示恒由后端通知驱动**；「排队中」也是一个可被观察的节点，任何发送
 方的消息都走同一条路进前端。

---

## 4. 地址表（输入面的唯一形态）

`<A>` = 会话地址 = `<挂载目录>/<sid>`（如 `<根>/session/abc`、
`<根>/agent/reviewer/session/sub-1`）。

| 意图 | 地址操作 | 语义 |
|---|---|---|
| 发一条用户消息 | `write(<A>/inbox/<iid>)` | 入队；空间空闲时自己消费 |
| 取消一条排队消息 | `delete(<A>/inbox/<iid>)` | 队列项没了；已出队 ⇒ `NotFound` |
| 清空排队 | `action(<A>/inbox, "clear")` | 只清未消费的 |
| **停止正在跑的那一轮** | `action(<A>, "abort")` | 收敛在途 Turn |
| **重试 / 审批 / 补充 / 回答** | `action(<A>/message/<mid>, "<动作>")` | 落在当时那条消息上 |

三条落点的分界（与 D-026 已确立的口径一致，不新增概念）：

- **会话节点 `<A>`** 上的动作 = 对「正在跑的这一轮」；
- **`<A>/inbox/<iid>`** = 对「还没成为消息的消息」；
- **`<A>/message/<mid>`** = 对「已经是转写里的一条消息」。

「停止」在 UI 上是**两个动作**：`action(<A>, "abort")` + `action(<A>/inbox, "clear")`。
不给 `abort` 加 `clear_inbox` 开关——机制动词保持单一职责，组合发生在调用方。
（只 `abort` 不清队的话，消费者下一趟立刻取下一条继续跑，「点了停止它又跑起来了」。）

`<动作>` 的词表 = `ResumeAction` 的线上词形（`snake_case`，跨栈契约已由
`resume_action_wire_words_are_snake_case` 钉住）：
`retry_subtree` / `retry_compaction` / `retry` / `approve` / `reject` / `supply` / `answer`。
**不另造一套动作名**：它们是同一批语义，多一套就多一处漂移。

## 5. 后端落点

### 5.1 `VDFS_ACTION_ABORT`（`crates/symbio-core/src/vdfs/words.rs`，与 `truncate` / `clear` 并列）

`session_at` 的 `Action` 臂：

```
action(<A>, "abort") → self.abort_turn(id)
```

`abort_turn` 取 state → `handle_abort`，只有这一份实现。回执
`{ok, message, data:{session_id}}`。会话不在 / 没有在途轮次 ⇒ `ok:false` +
明确文案（不静默成功）。

### 5.2 resume 动作（`messages_at` 的 `Action` 臂）

```
action(<A>/message/<mid>, <ResumeAction>) payload: {args?, reason?, answer?, mode?, risk_level?}
```

实现 = 直连 `start_turn`（不入队——恢复必须落在当时那条消息上，见 D-026）。
忙碌 ⇒ 回执 `ok:false` + `session_busy`（前端据此复位 working，与
`useChatConnection.resume` 的 `session_busy` 分支对应）。

`messages_at` 收到 `ctx: &VdfsContext`，经 `vdfs_host_ctx` 取回
`PluginInvokeRequest`（与 `agent_run` 的 `register_subsession` 同款手法）。

### 5.3 收件箱写入带上 `WORKDIR`

`inbox_at`（`crates/symbio-plugin-session/src/plugin/vdfs_inbox.rs`）接 `ctx`，
入队时把 `vdfs_host_ctx(ctx).get(WORKDIR)` 带进队列项——否则经 VDFS 写入的会话
拿不到 host 的工作目录回退源。
（`mode` / `risk_level` / `provider_id` 不由写体携带——它们由会话 metadata 解析，
`start_turn` 的回退链覆盖。）

### 5.4 出队时发一条**无载荷**变更

`drain_inbox_once`（`crates/symbio-plugin-session/src/transcript/inbox.rs`）
`pop_front` 后发一条
`change_subs.notify(&VdfsChange::bare(inbox_item_path(sid, iid)))`，
与 `cancel_inbox_item` 同款（「载荷缺失 + 回读 NotFound」= 删除，D-025）——
否则订阅方会永久保留一个已消失的队列项。
**这是 §6.6 排队态显示能成立的前提。**

## 6. 前端落点

### 6.1 `services/vdfsScheme.ts`：按挂载目录缓存

- `ensureSessionScheme(mountDir)`：`Map<mountDir, {messagesSeg, inboxSeg}>` 缓存。
- `ensureSessionMountDir` 是**默认**入口（= 根清单里 `new_type.ext === 'session'`
 的那个），即 `<根>/session`。
- `inboxSeg`：按 `VDFS_KIND_INBOX` 从会话内部子项解析，与 `messagesSeg` 同款
 （段名是展示名，不写死——`vdfsScheme` 的模块头已经把这条写明了）。

### 6.2 `stores/sessions.ts`：会话条目带上 `mountDir`

- `sessionMounts` 记「会话 id → 它所在的挂载目录」，`refreshList` 按挂载目录取。
- `activeId` 是地址末段，`activeAddr` 是完整地址（`<挂载目录>/<id>`）——跨进程的
 每一次寻址都用后者。
- `createSession` 写**当前**挂载目录；`selectSession` 收地址，同名 sid 在不同空间
 不撞车。

### 6.3 实时消费端：前缀是一组已登记挂载目录

`sessionTranscriptSync.ts` / `sessionNodeSync.ts` / `sessionInboxSync.ts` 三个
消费端各维护**已登记挂载目录集合**，分别由 `registerSessionMount(mountDir)` /
`registerTranscriptMount(mountDir)` / `registerInboxMount(mountDir)` 登记；进入
子智能体空间（该空间的 `session` 挂载被列出 / 选中）时登记。前缀匹配是「命中任一
已登记前缀」。

### 6.4 `Session.vue` → `ChatMainPanel` → `ModelChatPanel`：把地址传下去

- `Session.vue`：`watch( => props.node?.path)` → `store.selectSession(addr)`。
- `ChatMainPanel.vue`：`:sessionAddr="store.activeAddr ?? ''"`。
- `useChatConnection`：入参 `sessionAddr`，`sid` 由末段派生。

### 6.5 `useChatConnection` 的三个动作走地址

```
send(msg) → writeVdfs(<A>/inbox/<msg.id>, JSON.stringify(msg))
abort → runVdfsAction(<A>, 'abort') + runVdfsAction(<A>/inbox, 'clear')
resume(p) → runVdfsAction(<A>/message/<p.targetId>, p.action, {args, reason, answer, mode, risk_level})
```

- **不做乐观回显**（注释已写明理由）：写 inbox ≠ 已落库。
- `working` 乐观置位保留（等待期的可视反馈）。

### 6.6 排队态显示（第三个实时面消费端）

`tauri/src/stores/sessionInboxSync.ts`（实时面消费端）+
`components/message/InboxPending.vue`（气泡）+ `sessions` store 的 inbox 三个收敛
动作与 `refreshInbox`：订阅 `<A>/inbox` 段，把队列项渲染成「待发送」气泡；条目消失
（出队变更，见 §5.4）即移除，落库后由 §6.3 的转写帧接手——**同一个 id**，所以是
「换位置」不是「多一条」。

**为什么值得做**：用户消息一旦被消费，后端已发权威帧（落库回包，见
`crates/symbio-plugin-session/src/docs/109-vdfs-session-messages.md` 第 3.4 节），
前端本来就能显示——无论发送方是前端、CLI、telegram 还是心跳。唯一看不见的窗口是
**排队中**；而这个窗口对「不是我发的消息」同样存在。把它补上，多发送方才是真闭合。

**与骨架兜底并存**：`ModelChatPanel.showTyping` 的「空白流 + working ⇒ 补骨架」不
退。刚发送的一瞬两者都为真；更多见的是反过来——别的发送方的消息已被取出、落库帧
还在路上，队列已空而骨架仍是界面上唯一的「在跑」信号。两条判据各自独立。

## 7. 取舍与代价（不粉饰）

- **前端会话条目的身份是地址**：`stores/sessions` / 三个 sync / 三个组件都拿
 `mountDir` + `sid`，而不是只拿 id。只改发送不改显示，子空间跑起来的消息前端仍然
 收不到（根因 B）。
- **输入面只有一个入口**：不再有「路由能到、地址到不了」这类分叉。
- **「停止」是两次 IPC**：`action(<A>, "abort")` + `action(<A>/inbox, "clear")`。
 可接受：按钮是低频操作，换来机制动词的单一职责。
- **排队态显示引入一个 UI 状态**（待发送）。它同时闭合两处可见性缺口：①排队的消息
 看起来已经发完了（D-026 明确要避免）；②别的发送方的消息在消费前不可见。
- **边界**：`<A>/inbox` 写入不携带 `mode` / `risk_level`，由会话 metadata 回退。
 若将来出现「同一次发送要覆盖会话默认运行模式」的需求，再在正文里开一个可选字段，
 不预先加。

## 关键决策

> 本节是**仍然约束现行代码的取舍**：每条一句决策、一句理由。已退场或主题已消失的决策不在其中（`git log` 是历史）。

### D-031 会话的输入 = 地址上的写入 / 动作（chat/send 与 chat/abort 退役）

会话输入只表达为对会话地址的写入 / 动作。`chat/send` / `chat/abort` 是地址无关的全局路由，由根 composite 分发 ⇒ 落点恒为根 `SessionPlugin` 实例，而子智能体空间有自己的实例却没有路由入口——消息因此由根实例消费，人格 / 工具 / 存储全是父智能体的，同一会话的「停止」也打不到正确的实例。改成 `<A>/inbox` 写入与 `<A>` / `<A>/message/<mid>` 动作后，落点随地址走。

### D-066 输入面退役的前置条件解除：地址写入不承载运行选项——三项运行参数已有会话 metadata 回退，协议面不必变宽

输入面退役的最后一道前置条件——地址写入面「表达不了本次运行的选项」——不需要协议变宽来解决：`provider_id` / `mode` / `risk_level` 描述的是会话级事实，契约已有 `req > metadata > 默认` 的回退链；`agent_run` 已在写子会话 metadata，心跳的 `include_history` 是本次发送属性，telegram 的 `mode` 是通道属性，CLI 的调用级覆盖改由「选项变过就先写会话 metadata」表达。

### D-236 `Entity::Turn` 是事实网格的格身份，不是「轮节点」——会话事件族留，`turn.branch_selected` 留

[D-129](015-义务环.md "DE-015-义务环") 的结论（中断轮的终态归骨架节点 `aborted`，不补一条 `turn × Closed`）不变；
但它那句「`Turn` 概念已从协议里退役」**射程过宽**——代码里 `Entity::Turn` 仍是 `user.message`（开轮）、
`chat.assistant.final` / `fallback`（收束）、`turn.dispatch` / `turn.stage` / `turn.branch*`（断言）的格位，
`symbio_core::invariants` 的开轮唯一、`≤1 final/turn`、停机事实与预算声明全按这一格判。本条收准射程，回答三问：

| 问 | 裁 | 理由 |
|---|---|---|
| `turn.branch_selected` 与 `Entity::Turn` 在会话事件族里留还是退 | **留** | `turn.branch` / `turn.branch_selected` 是 [DE-001](001-核心架构.md "DE-001-核心架构") 的 `D-173` 立的目标事实：「此刻读哪一支」只有事实能说；组的键是成员根节点 id，不是轮号。`Entity::Turn` 是格身份，退掉它等于把按格判的那组不变量一起退掉 |
| 以 `Entity::Turn` 为轴的投影（`fallback_rate` / `slo_report`）与 transcript / stats 的轮次分组跟谁 | **跟格与 `e.turn` 号**，不跟节点树 | 投影读的是 `Entity::Turn` 的格 + `e.turn` 号；`ChatNode` 是呈现读侧，不是分组轴。呈现可以重排 / 隐藏，统计不能跟着藏——两处认同一份格，不互相定义 |
| `D-129` 与代码（`switch_branch` 落 `Entity::Turn`）冲突以哪侧为准 | **代码这一侧**，`D-129` 收窄 | `D-129` 真正裁的是「中断轮不按 `Opened` / `Closed` 配对补终态」——`Turn` 作为**生命周期配对**的终态 owner 退场；`Turn` 作为**事实格**从未退场。会话面按 `ChatNode` 父子树**呈现**，与格不冲突 |

**「退役」从此只指一件事**：v1 的「一轮 = 一对 turn 节点、中断时给这对节点补 terminal」不再存在；中断的终态是
骨架节点的 `aborted`。它不是「事件族退场」，也不是「`Entity::Turn` 退场」。

**可核**：`symbio_core::invariants` 的 `is_turn_open` / `is_turn_final` / `unresolved_turns` 按格判（不点名字，`D-203`）；
`turn.branch_selected` 的写方唯一（`session::commands::switch_branch`），读法口径归 `D-173`。
