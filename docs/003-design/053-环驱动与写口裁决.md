# 环驱动与写口裁决（D-320–D-323、D-326、D-336–D-349）

> 本篇自 DE-048 拆出（同一批裁决只搬家，不改写）：端口机制裁决（D-300–D-319）见
> [DE-048-端口机制裁决](048-端口机制裁决.md)；判据、判定式、作废清单与门禁见 [DE-047-义务环判据与归属推导](047-义务环判据与归属推导.md)。
> D-313 的迁移排期留在 DE-047。

## 关键决策

### D-320 驱动二分：编排入口 `entry` 与薄环 `ring`（已作废，见 D-321）

- **状态：已作废（D-321）。** 本节保留原文以便追溯；判据与授权一律以 D-321 为准。
- **裁决。** 原 `stage_driver.rs` 拆成两份：`entry.rs` 只做**编排**（幕的开启、
  收束与幕间接续；按结局决定「收幕还是接下一幕」），`ring.rs` 只做**债表上的一层薄
  循环**。`stage_driver.rs` 不再存在，也不以中性名保留同一台阶段机。
- **环的白名单（五类，超出即判残留）。** ① 选债：读事实切片 → `loop_rows::next`
  取最小可还的一笔；② `run_port(端口名)`：把这一笔交给绑定表里的动作，由动作按端口名
  受理；③ 落事实与关账：读动作前后的账本尾段，判写封闭与停机格；
  ④ 预算 / 租约守卫：`over_step_limit`（判据是**已 `sent` 的笔数**，不读任何阶段格）、
  `waiting`（未收清）；⑤ 停机判据：无债可还时「在等 / 不前进」两档。
  环不按阶段号 / 轮次序号分支，也不解释行名与端口名。
- **编址归端口。** 协议配对键（`s{n}`、`call id`）由 `port=model` / `port=tool` 的
  执行体生成与解释；环只传递与配对，不用轮号当序。会话推进（开轮 / 唤醒 / 收尾 /
  `finalize`）由 `port=session` 以事实表达（`session.opened` / `session.finalized`
  一类），不在端口内复刻按序号推进的阶段表。
- **判据面。** `CP-003` 的「循环体内」按 `entry.rs` + `ring.rs` 这一对文件判：五道
  守卫仍各只许一个调用点（`aborted` / `abort_before_first_request` 属幕的边界，落在
  `entry.rs`；其余三道在 `ring.rs`），不许出现第二条检查路径。`CP-001` / `CP-002`
  仍只认 `ring.rs` 的唯一循环体与唯一选债口。
- **本次不完成的（如实记）。** `turn.stage` 行与其格子仍在，其内容二分（协议格 →
  `port=model`、会话推进 → `port=session`）是下一个退场单元；本决策只裁驱动文件的
  二分与环白名单，不授权任何端口内阶段机。

### D-321 撤销 D-320：编排不属环内七职，判据主语回到整个 loop

- **D-320 作废。** 编排不属环内七职；判据主语为 `crates/symbio-plugin-loop`
  全部生产文件，不缩到 `ring.rs`；`entry.rs` 为残留，去留按残留处理。
- **撤销理由。** D-320 把「编排」立为环内合法住民，并把判据范围从整个 crate
  缩到 `ring.rs`；结果 `entry.rs` 的 `loop {}` / `open_stage` / `close_stage` /
  `next_stage_round` / `StageRuntime` 仍在，门禁全绿而阶段机健在——这是判据空转，
  不是漏检。
- **环的白名单只约束 `ring.rs` 的代码形状，不构成对任何编排的授权。** 判据主语为
  `crates/symbio-plugin-loop` 全部生产文件。幕的开启 / 收束 / 接续要么归
  `port=session` 的协议线（由事实驱动，不按序号推进），要么由「选债 +
  `run_port`」自然涌现。
- **阶段值不造新名。** 八个 `turn.stage` 取值一律化归为「某端口的一笔 `request`
  及其 `response`」；世界事件名只许出现在该端口自己的声明域，不作为环的判据常量。
- **例外：`turn.stage` 作为能力效果面类型名与 `event_id` 形状属契约冻结**
  （`EffectFace::Stage`，D-293；e2e `t96` / `t97` 已发出的对外契约）。仅许在
  能力 / 效果端口的声明域声明与写入；`symbio-plugin-loop` 不许 import、不许写、
  不许拿它当 `until` 判据、不许解析 `event_id` 里的轮号。清除条件：B3 展示面
  turn 拆除时同批改 e2e，届时一起消失。不得写成永久豁免。

### D-322 环内「已发生」是非债领域事实 `loop.step`，不伪造债务答复

- **背景。** D-321 要求八个阶段值化归债配对。但若环自己写 `request` 又写
  `response`，就是「自问自答」的假账：`response` 是世界的答复，环写它等于配对
  自证，`until` 永远「已还」。授权拒绝的调用同理——没碰到世界的调用写 `sent`
  也是假账。
- **决定。** 环内的一次性步骤不改写成端口债务，而是**环自己的领域事实**
  `loop.step`：`id`（行表数据）+ `anchor`（幕锚）+ `round`（载荷之数）+ 不透明
  载荷。判据是「已发生」，不带 `attempt`，不使用 `request` / `response` 词汇。
- **配对键 = `scope` + `anchor` + 债 id。** 轮号**不进键、不进事件 id**：同一轮
  可以先后开好几幕，轮号重复而幕锚不重复。`round` 只作预算的数（
  `over_step_limit` 数已 `sent` 的笔数）。
- **步 id 只住行数据。** `STEP_*` 常量属于 `loop_rows.rs` 的行表数据（终极形态由
  C 批注册表引入）；事实层（`stage_events`）不持有任何步名闭集，端口名与债务 id
  由调用方当实参传入。环按表查，不按行名分支。
- **`stage_events.rs` 的长期去向。** 它是「环写世界事实」的工地：
  `land_effect`（效果面 `turn.stage`）随 B3 展示面拆除缩成协议数据或整体搬进
  `port=session`；`land`（`loop.step`）随 C 批行表参数化收窄。本文件不是终点。
- **判据。** 环内同一笔不得既写 `request` 又写 `response`；`response` / `failed`
  只由端口执行体写。`loop.step` 不承担任何端口答复语义。

### D-323 债 id 归环、由事实派生；端口只回显（`next_round_trip` 按此删除）

- **依据。** D-320 已被 D-321 撤销，「协议键由执行体生成」随之作废，D-314 与 D-320
  的表面冲突消失。因此不向端口要 id（那会把债的身份交给世界），也不新增 `model.trip`
  按 `trip_no` 配对（那只是把计数器搬进世界，环仍要数）。
- **裁决三条。**
  1. `request.id` 由**欠债方（环）**生成，且必须**由事实派生**：id 里只许出现端口名 +
     产生这笔债的那条事实的 id。首趟用会话开启 / 用户消息事实的 id；续趟用触发它的
     那组调用的 id（多个按稳定顺序拼 / 散列成定长串）。**禁止计数**——不许 `s{n}`、
     不许 `round+1`、不许 `d{anchor}` 中的序号段。理由一句：幂等键必须是一笔债的
     身份，不是它的编号。
  2. 执行体不解读 id，只回显：`response` / `failed` 带同一个 id 与 `attempt`；
     执行体不得自己造 id。
  3. `until` 配对键 = `(port, id, attempt)`；`attempt` 由环的租约递增，属中性字段。
- **落点。** `next_round_trip` 不是换键：**删掉计数器**、改成上述派生规则（P2-6 段 3
  施工）；`loop_rows.rs` 里 announce-model 的 `owes` 随之改指派生 id。
- **连带。** `loop.step`（D-322）不作长期机制：它是环给自己开的进度条，P2-6 段 3
  整条删除，不改名、不改判据。

### D-336 跨插件模型往返：共享载荷住 SDK 词汇层 + 端口按用途分成员 + 执行体归端口提供方

- **裁决四条。**
  1. **端口名与执行体均全局按名解析**，债行申报方的端口不必由自己提供。宿主把全部
     `port` 行的端口名 → 执行体建一张全局表（`crates/symbio-host/src/lib.rs:188-199`），
     环派发时只按 `row.port` 取（`crates/symbio-plugin-loop/src/ring/engine.rs:260`，
     解析口 `engine.rs:36`）；`DebtSpec.port` 是端口名字符串，没有「申报方必须提供同名
     端口」的断言。因此 compact 可以申报一行欠 `model` 插件的端口。
  2. **执行体归端口提供方**，因此「拿摘要」与「落压缩事实」必须分属两行。`compact-summarize`
     的 `port = model.assist`，执行体在 model 插件，只负责一次问答；`compact-write` 的
     `port = compact`，执行体在 compact 插件，负责读回摘要并落 `session.consolidated`。
     把两件事塞进一行等于让 model 插件写会话世界的事实，违反 I-4（环与端口不碰世界语义）
     的同一条归属尺子。
  3. **共享载荷住 SDK 词汇层**（与 `ChatNode` 同层：`symbio_sdk::chat::chat_node`，
     经门面既有转发到 `symbio_plugin_api::chat_node`），不进 `plugin-api` 的白名单。
     理由：问答请求 / 回复是**词汇形状**，不是宿主机制；门面新增条目会同时动 HS-002 棘轮
     与「机制层不认识世界语义」的判据。
  4. `model.assist` **只做一次性问答**：不参与对话轮、不带工具、不留会话历史。它的
     `response` 不进入 `turn_input` 的 messages（会话历史只收 `port == model` 的应答），
     也不往展示面写流式帧。
- **被否项。**
  - **A（猜 `model` 载荷形状）**：compact 直接给 `model` 端口写一个「请摘要」载荷，
    model 执行体靠键名猜用途——端口名不表达用途，第二种用途到来时无从区分。
  - **B（`plugin-api` seam）**：在门面上开一个跨插件调用缝。那会把世界语义（问答请求
    的形状与用途）塞进机制层，并让 HS-002 为一条世界需求变宽。
  - **C（事实接力要改 model 债表）**：让 model 自己申报「摘要欠债」。model 不知道会话
    何时需要压缩，改它的债表等于把 compact 的策略写进 model。
  - **②（`@@SUMMARY@@` 隐式替换约定）**：用正文里的标记串在重建面做隐式替换——标记
    会漏进用户可见文本，且把「摘要」变成第二种隐式协议。
- **落点。** 共享载荷 `chat_node::AssistRequest` / `AssistReply`；model 插件新增独立
  提供者 `AssistPort`（端口 `model.assist`，执行体只调 `round_trip`、传空工具表、
  静默流式出口）；compact 的两行债见其 `debt.rs`。端口名避开环事件 id 的保留字符
  （`:`），协议事实的端口位仍从事件 id 还原。
- **已知项（编码风险）**：环的事件 id `ring:{port}:{id}:{attempt}:{kind}` 是
  **「分隔符与内容共用字符空间」**的形态——端口位按 `:` 定界，而债 id 自身也含 `:`，
  靠从右定界把两者分开。端口名一旦含 `:`，端口位就被截断（`model:assist` 会被读成
  `model`），事实键与债键对不上：实测同一笔摘要被重派 39 377 次。**唯一防线是注册期
  拒绝**——`port_rows` 在种行前对保留集 `PORT_NAME_RESERVED`（目前只有 `:`）做
  fail-closed 校验，不转义、不做解码兜底。新增端口名必须避开保留集。
- **已知项（水位字段耦合）**：`compact` 的 `rows()` 读 `chat.assistant.final` 载荷里的
  `context.request_tokens` / `limit_tokens`；这两个字段由 model 执行体写，**不是 SDK
  共享类型**——被否项 A「猜载荷形状」的缺陷在选债层复现。当前唯一消费者是 compact，
  先认；**第二个插件需要同一字段时，提升为 SDK 共享类型，不许各自猜**。

### D-337 只读声明句柄进执行上下文：`PortDeclReader`

- **裁决。** `PortExecContext` 增一格 `decls: Option<Arc<dyn PortDeclReader>>`（随
  `PortExecHandles` 由宿主装配、环原样转交）。句柄只有两个读口：`view(name)` 取
  `ViewDecl`（段身份 / 视图口径），`rows()` 取全部 `Decl`（债行声明：`by` / `owes` /
  `until`）。**没有写口**，也不暴露 `Frozen` 的其余面。
- **为什么不选「session 把段正文写进请求载荷」。** 那要求 session 认识 task 的段语义：
  哪一段、叫什么身份、优先级多少、何时收集。装配（段在请求里的位置、计量与裁剪、
  `role: system`）归 `model` 端口执行体，session 只该说「这一轮发生了什么」。
  把段正文塞进载荷还有一个旧病复发：载荷里重新出现世界形状的「段」，而端口名不表达
  用途——与 D-336 被否项 A（猜载荷形状）同一条理由。
- **为什么必须只读。** 声明表的唯一写通路是插件自己的 `traverse` + 能力收集
  （`submit_declarations!` → 冻结表）。执行期若能写声明，就绕过了那条收集：新增的
  行 / 视图没有任何装载期检查的对象（写入封闭、依赖图、`OrphanActor` 全部空转），
  而「停用即缺席」也立刻失效。`Frozen` 本身没有 `&mut self` 方法；本句柄只是把已有
  的只读表发进执行上下文，不新建第二张表。
- **两个读口服务谁。** `view` 给装配侧取段身份（名字来自声明，不由执行体拼字符串）；
  `rows` 给运行期债适配读「这一行欠什么、什么时候算还」（`plugin_row` 行执行体的输入）。
- **未收口。** 句柄只挂在 `PortExecContext`；环自己的债源读同一张冻结表（`rows()`），
  不复用本句柄——两处的读法各自成立，合并要等第三处读点出现。
- **本决策已回退（`9802eabc`）。** 找不到自然消费者：段身份在 `ContextSection.slot`、
  债行由 `sealed_declarations().rows()` 直接读，全仓没有执行体通过该句柄读声明；
  只读声明句柄不保留（`PortDeclReader` / `sealed_decl_reader()` 与上下文两格一并删除），
  不留空壳。

### D-338 `Ask` 的债归申报方：在等事实 + 机制派生身份

- **裁决。** `RowStep::Ask` 不调模型：`plugin_row` 执行体落一条「在等」事实后挂起；债由
  **申报方**自己声明（notes 申报一条 `model.assist` 行）。端口名可以写别的插件的成员——
  这是 D-336 裁决 1 的既有形态（compact 同样写着 `model.assist`），不是跨世界依赖。
- **事实形状。** 种类 `plugin.row.asked`（`rows::ASK_KIND`，**一个**名字）；id =
  `rows::ask_id(row, key, attempt)`＝`<row>:<key trace>:<attempt>`；载荷
  `{"row": <行名>, "key": <债键>, "prompt": <提示正文>}`。**谁写**：`plugin_row`
  执行体（唯一写方，机制侧）。**谁读**：申报方的债行按 `row` 从载荷里挑自己那行、
  按同一 id 做 `when_id`、并从载荷取提示；`plugin_row` 执行体按同一 id 找
  `response` / `failed` 配对。
- **为什么种类是一个名字。** 世界格子只认声明表上的名字（`wal.rs` 的 `declared_vocab`
  按 `(Entity, Verb)` 校验）。逐行造名（`plugin-row.asked:<行名>`）会让任何未登记的行名
  落进 `OffGrid`，而 `PortFactEmit::emit` 不返回错误——事实会静默丢失。行名因此进载荷，
  种类只剩一个（`plugin-loop/src/vocab.rs` 登记）。
- **为什么必须落事实。** 静态债表没有「这一行此刻在 Ask」这个状态；没有事实，申报方
  只能靠全局 `unless` 猜，第二次反思就再也开不出来。
- **为什么身份由机制派生。** `(row, key, attempt)` 三样环已经都有；让插件在 `ModelAsk`
  里自带 id 等于把配对职责搬进插件载荷（与 D-242 被否项 1 同一条）。
- **为什么端口取 `model.assist`。** `model` 端口的执行体只从会话事实装配输入、载荷只带
  身份（`model/src/port.rs`），一行提示插不进去；`model.assist` 正是一次性问答的成员
  （D-336 裁决 4）。D-304 写的「`request(port=model)`」指的是**模型世界的那一笔往返**，
  到了实现层按一次性问答成员落地。
- **挂起与再触发。** `Ask` 之后执行体返回 `NeedsHuman`：环落 `sent{deadline_ms:null}`，
  债务留在原地。回执落在 sent 之后，行按 `when = response` 重新触发，**同一 attempt** 再
  派发一次；这次执行体读回执并调 [`RowHandler::parse`]，不重发提示、不加 attempt。
- **被否 A（环从事实合成债务）。** 那会把「一次世界交互 = 一笔债」从债表下沉到环，属于
  D-325 五级机制形状的改动；并且与 model 的 `model-reply` 形成两个 owner 认领同一笔 request。
- **被否 C（给 `Decl` 加伴随声明字段）。** 与 D-306（最终删掉 `by` / `tier`）方向相反。
- **债表载荷读口。** 申报方要拿提示正文，只能读「在等」事实的载荷；`DebtFacts` 增
  `facts_of(kind)`（该种类的身份 + 载荷全集）与 `fact_payload(kind, id)`（只读副本，
  判定仍只看种类与身份，不因载荷分支）。申报方用 `key` 里的 `tool_call_id` 认自己那笔
  输入，并以同一键的 `notes.insight` 做 `unless_id`：没有它，同一「在等」事实会在回执
  之后继续产债。

- **裁决：由既有的开面调用方在开面时复制。** 播种点是 `SessionPlugin::fact_source`
  （`crates/symbio-plugin-session/src/plugin.rs`）——开轮写面的唯一开面，由
  `vdfs_inbox.rs` 的「入队即开轮」调用、`handle_consume` / `handle_project` 经

  插件集合清单，没有开面代码。**不为这条裁决新开 crate / 新组件。**
- **播种判据（`SessionStore::seed_open_verdicts`）。** 仅在会话**尚无事实**
  （`head() == 0`）时执行一次：扫描既有的部署级读 `deep_snapshots()`，按
  `(subject, capability)` last-wins 取**时刻最后**的一条（`ts` 定序，同刻按 `seq` /
  `event_id` 定序），把该条 `verdict.asserted` 复制进本会话 WAL。复制保留原
  `actor` / `payload` / `produced_by`；**不新增信封字段**，审计对账用
  `produced_by` + 载荷 `source_seq`（被复制事实的 `seq`）。复制走 `Store::append`
  直落 WAL，不经 `FactSource::append`——播种**不踢驱动**。
- **唯一允许的直写点（第二处即红）。** `seed_open_verdicts` 里的 `Store::append`
  是**唯一**获准绕过 `FactSource::append` 的**开面 / 部署级复制**直写点，理由只有
  三条：① 播种发生在开轮业务事实之前，踢驱动会开出一个没有 `user.message` 的空轮；
  ② `actor` 是复制来的原值，不是在这里新盖主体（解析 `@principal` 仍只发生在
  `FactSource::append`）；③ 播入事实不参与 owes / settled。它仍经 `WalStore` 的
  写侧闸（形状 / 归属 / 溯源），不是绕过事实源校验的暗门。会话自己的业务事实仍只走
  `FactSource::append`；既有的两个存储所有者写窗口（自主触发事实、消息投影格）不在
  「开面复制」判据内。**再出现第二个面向开面 / 部署级复制的直写口，即红**——它不是
  本裁决留给后来者的通用旁路。
- **诚实边界（台账：已知缺口）。** 只保证**开面时**一致，**运行期不追发**：会话开面
  之后才被撤销（或恢复）的主体，在该会话内**仍按开面时的读数行动**，直到它下一次开面
  （新会话）才看到变化。这是已知缺口，不假装实时同步，也不在文档里暗示「一撤销就全网
  生效」。
- **播入事实不参与 owes / settled。** 它是普通的 `verdict × asserted` 事实：义务环不认
  这个格子（`crates/symbio-plugin-loop` 不读 verdict），既不产生债、也不结算债；唯一
  读方是读侧覆盖层（`EliminationDecider::verdict_grants_changes` → `GrantsOverlay`）。
- **索引不出开面那一处。** 跨会话折叠只在 `seed_open_verdicts` 内出现：不进
  `DriveTarget`、不进 `PortExecContext`、不随任何执行体传递；执行体仍只看会话本地切片
  （`HostReader`）。否则就是换了个名字的 fleet 读口。
- **幂等与失败。** 同一 `(subject, capability)` 只播一条；重复 `append` 按 `Duplicate`
  视为已播（并发开面不重复）。目标 WAL 写失败显式报错，不静默跳过。

### D-342 `after` 管时序，执行体不复判：时间差由派发顺序解决

### D-343 一轮计划只读一份事实快照：计划的一致读面

- **形状。** `HostDriveSupport::rows()` 刷新一次投影并把结果缓存为**本轮计划快照**；
  `declared_facts` 从同一份快照构造；同一轮 `plan()` 里的 `exists` / `exists_id` /
  `exists_since` 都读这份缓存、不再各自刷新；下一轮 `rows()` 再刷新。环的

- **理由：计划是一次判定，判据必须同源。** 此前 `rows()`（债表的身份/载荷读面）与
  `exists_id`（选债的存在性读面）各自刷一次投影；两次读之间落格的事实会让同一轮

  config」→ 模型行不挂 `after`、分类行不申报；选债判「有 config」→ 模型行照派，
  主线抢在判决之前发出（t21-A 与 t92 第二轮的同一根因）。
- **兑现既有约定，不是新机制。** `D-342` 的「计划用派发前的事实」与 `when_id`
  「与 `when` 同一条读面」都要求同源；`exists_since` 进 `DriveSupport` 带默认实现
  （宿主覆盖），不扩 `FactSource` 五方法契约、不加端口、不改 `loop` 的世界语义，
  也不把「再查一次」下沉到执行体（`D-342` 已否决）。
- **边界。** 世界事实的身份与载荷改从**投影**取（端口位为空即世界事实，协议事实
  的端口位由 `ring:` 身份还原）；协议事实仍只贡献尝试号与收束。投影按 `event_id`
  去重、以事实源为唯一输入，本次只是把「读几次」收敛为「读一次」。

### D-344 行为什么能拿 ctx：同一份执行上下文，跨插件只走 route

- **问题。** 首响（`chat.assistant.opening`）要求行在执行期向 compose 取一句措辞。
  旧的行入口 `RowHandler::run` 是同步的、`RowRequest` 里没有任何句柄，行只能落事实；
  而「再查一次 / 直接摸别的插件」两条路都被否决（D-342、D-343）。缺的是**一个受人
  支配的调用面**，不是又一个事实读口。
- **裁决一：行拿到的就是派发它的那份 `exec.ctx`。** `RowHandler` 增
  `run_ctx(req, ctx)`，默认实现原样转调同步的 `run`——**其它行实现零改动**；
  `ctx` 直接取 `PortExecContext.ctx`，不另造句柄、不加 `parent` 字段、不把会话 /
  端口身份再塞一份进 `RowRequest`。需要父句柄时从同一份 ctx 的 `parent()` 取，
  需要会话身份时从同一份 ctx 的 `SESSION_ID` 取——**不出现第二个事实来源**。
- **裁决二：跨插件调用只走 route，不直连插件。** 行只许做「`fork` 子上下文 → 设
  `PATH` 与载荷 → 经 `parent().route(child)` 取答复」。答案由对方插件的**已声明
  能力**给出，行不 import 对方、不读对方存储、不拿对方的内部类型。路由是插件间唯一
  的横向接口；行拿 ctx 不是为了绕过它。
- **裁决三：谁想用 ctx 直接摸别处数据，按本条驳回。** 判据只有一条——**这次调用
  有没有经过 `route`**。在行里直接读别人的事实源 / 存储 / 字段，即使用同一份 ctx
  取到句柄，也属越界；合法的横向依赖仍回到「申报一行债 + 对方端口 / 路由」。
- **与既有裁决的关系。** 不改环（环不碰世界语义）、不改执行体的「只执行载荷」、
  不把判据下沉到行（行的同步判断仍是同步判断，异步只用于差遣路由）。首响这一笔即
  本条的兑现：会话的行等 `classify.escalate`、经路由取 compose 的模板措辞、落
  `chat.assistant.opening`；模型行按 `after(session.opening:id=…)` 等它收束。

### D-351 恢复失败判 NonRetryable：当前选择、非能力上限

- **裁决。** 答复恢复读不到 `user.answer` / 找不到该调用的产物时，端口交
  `PortErrorClass::NonRetryable`，环不抬 attempt、不重发首派。
- **为什么这样选。** 恢复债行复用首派债键（`tool:<request_id>`），attempt 自增会让
  「首派」在新 attempt 上重跑一次（同一笔世界交互执行两遍）。缺读面 / 缺产物不是
  时机问题而是账实不符，重试不会让它出现。
- **后继。** 「重试归属到行」已由 [D-442](047-义务环判据与归属推导.md "DE-047-义务环判据与归属推导")
  落地（`retry` 载荷指认重跑行，恢复行重试不再带动首派重来）。本条的 NonRetryable
  选择照旧成立：缺读面 / 缺产物是账实不符，不是时机问题——归属到行解决的是
  「谁来重跑」，不改变「这种失败重跑也无益」的判断。

### D-385 端口派发的授权面：环不判定、能力自判，`permitted` 不得由环代填

- **事实。** `crates/symbio-plugin-loop/src/ring/engine.rs` 构造 `PortExecContext` 时无条件写
  `permitted: true`、`deny_reason: String::new()`，全仓生产构造点只有这一处。而
  `crates/symbio-plugin-api/src/port.rs` 对该字段的说明是「宿主侧的产物闸结论；执行体只按
  结论记账，不自判」。读者只有工具端口
  （`crates/symbio-plugin-tool/src/port.rs::artifact_ctx` 把它当 `allowed`），其余执行体不读。
- **这一格在说哪种谎。** 它不是「环判过并通过」，而是「环把判定位当成常量占位」：对下
  暗示「已授权，你放心跑」，对上又没有任何判据可以追溯。横向扩展后风险具体化——能力只要
  申报一笔债、自带 `PortExecutor`，就能拿到 `permitted: true` 一路跑。
- **三个候选与代价。**
  - **环判**（派发前读 `production_matrix` / 主体 / 能力名）：环必须认识「主体是谁」
    「这笔债属于哪种能力」——那是世界语义，与 D-300 / D-315 的「环不持有世界语义」冲突；
    端口新增一族就要改环；且环拿不到风险档（D-350 / D-368 已裁：唯一解析点在执行期闸门）。
  - **端口提供方在受理时判**：提供方认识自己那一族的调用形状，但它判的是「这通调用合不
    合法」，不是「这个能力有没有资格申报这笔债」；两者合并会把 D-342 划开的「宿主闸 /
    能力闸」时序边界重新抹掉，且每多一种端口就多一份实现。
  - **能力执行体自判**：它本来就知道自己的名字与要做的动作；`production_matrix` 与
    `CAP_*` 已经经 `symbio-plugin-api` 可取（D-276 的 SDK 臂）；不新增架构面，也不要求环
    认识主体。
- **裁决。** 采用**能力自判、环不判**：
  1. `PortExecContext` **不再有授权输入格**：`permitted` / `deny_reason` 两个字段从上下文里
     删除。环不构造、不代填，也不提供「我没判」的占位——留在输入里的空字段一定会活到
     下一次重构，最后变成「永远不填但一直在那儿」。
  2. 判定结论是**执行结果的一部分（输出）**：`PortOutcome` 增一格类型化结论
     `authz: AuthzVerdict`，取值 `Authorized | Denied { reason }`。执行体先自判、按结论
     行动，再把同一结论随结果交回；宿主与读方要看「放没放」，读输出，不读输入。
  3. 判定输入是部署授权表与主体：`production_matrix()` 的 `grants_of` / `can_*`；主体取自
     执行上下文（`source` / `origin` 或宿主交来的主体），能力名由执行体自己持有。判定
     函数只在 `symbio-sdk` 有一份（D-251）。

  `PortOutcome.authz`；环不再替它写 `true`。先有本条，`rows()` 的三个 early return

  4. 工具端口的产物闸按 `PortOutcome.authz` 读写，t78 的批准路径不回退；

### D-394 收束载荷盖章，读侧不认端口名

端口债的读方（模型转写里哪条 `response` 算 assistant 消息、工具结果卡、用量 / 金额台账、
`assist` 回执）一旦按端口名比较（`fact.port == MODEL_PORT` / `payload.port == Some("model")`），
每加一个世界端口，读侧就要跟着补一处特判——「新增一个端口 = 0 个架构改动」这句话在
读侧就不成立。`answer.rs` 与 `compact/port.rs` 直接引全局端口常量时，读方比债行本身更清楚
它该读谁。

- **裁决：环在收束载荷里盖章，读侧只认章与数据。**
  1. 债行声明语义（`DebtSpec` / `DriveRow` / `DebtRow`）：`role: ReplyRole`（`reader` /
     `internal`）、`accounts_usage: bool`、`accounts_spend: bool`、
     `failure: FailureProjection`（`none` / `tool_call`）。语义章契约的唯一 owner 是
     `crates/symbio-sdk/src/port_stamp.rs`；`plugin-api` 只 re-export，不另立一份。
  2. 环在 `sent` / `response` / `failed` 的载荷里写 `stamp`：`{ role, usage?, spend?,
     failure? }`——缺席即「本行不声明这一格」，不写 `false` / `"none"` 占位。
  3. 读侧（`model/port.rs`、`model/ledger.rs`、`projection/{mutations,rebuild}.rs`、
     `answer` / `compact`）只读 `stamp` 与载荷数据，**不许再比较端口名**。
     `answer` / `compact` 的上游端口由债行自己声明（`RowRequest.after_port`），读方按它
     取回执，不引全局端口常量。
- **判据。** `port-surface-audit` 的 PTS-007：`symbio-sdk` / `symbio-plugin-api` /
  `symbio-plugin-session` 的非测试源码里，凡「端口上下文 + `==` / `!=` + 端口取值（字面量
  或解析到端口取值的常量）」三者齐备即红，报 `文件:行 + 端口名`。回归测试注入
  `if port == "model"` 与 `port == PORT_TOOL` 必须红，`stamp.role == Some("reader")` 与
  测试夹具必须绿；三个读侧树读不出时判红（不得「没什么可判 ⇒ 通过」）。
  这一格的读数就是那句可判的话：**新增一个世界端口，改动架构文件数 = 0**。
- **适用范围（判据的对象，不是扫描落点）。** 它管的是**架构层与骨架**的读侧——
  `kernel` / `sdk` / `plugin-api` / `loop` / `session` 里「读事实并决定语义」的代码；
  判的是**耦合**（读方依赖别人的端口名）。**能力插件比对自己端口的名字属所有权，
  不是耦合**：`tool/round_done.rs` 的 `fact.key.port == TOOL`、`telegram/port.rs` 的
  `input.port != NOTIFY` 刻意不判。扫描落点当前是 `sdk` / `plugin-api` / `session`
  三棵树，`kernel` 与 `loop` 的端口无感由 PTS-002 / PTS-003 判。
- **机制端口不是世界端口。** `loop/plugin_rows.rs` 的
  `is_row_port(port) == plugin_row` 保留：`plugin_row` 是环执行自己行表用的机制端口，
  不出现在「新增一个世界端口」的成本里，因此不进「改动架构文件数 = 0」这条统计。
- **不做什么。** 不给读侧加「按端口登记读法」的表（那是把读侧重新绑回端口名）；不在读侧
  为旧事实补 `stamp` 的向后兼容垫片（没有章的事实不识别，是本条的直接结果）；不把
  `after_port` 退化成全局端口常量。


### D-435 终答只有一个形状：答话轮与工具轮同一份载荷、同一条折叠路径、同一棵树

`D-345` 记的是「`chat.assistant.final` 有两个产出点，各自拼载荷」。复盘之后，真正的分歧
不是字段，是**树**：work 轮的正文是轮根下的 `Text` 子节点，答话轮的正文是一条**根级**
节点（与用户发言互兄弟），思考还挂在答话之下——同一件事在存储层有两种拓扑。`D-426` 已就
首响裁决过一次（根级会让按根切窗口多算一轮、渲染会把它排到轮末），答话是同一个问题。

- **裁决一：`dialog` 子对象退场，终答只有一份载荷。** 三个写方（模型端口 / 答话行 /
  中止收束）今后交的都是同一组键：`root_id` · `text` · `answer` · `answer_id` ·
  `reasoning` · `reasoning_id` · `principal` · `cost_ms`，外加可选的 `status` /
  `reason`（闭集收束理由）/ `meta`（对话面标记）。重建侧因此只剩**一条**折叠路径：
  轮骨架（`id = root_id`，与用户节点同 id ⇒「同 id 只认首次」并进那一条）+ 思考 / 正文
  子节点。
- **裁决二：对话面标记走 `meta`，不另立节点形状。** `surface = "reply"` 与「为什么这样
  措辞」的理由码（`from_context` / `thanks` / `clarify`）原本在 `dialog` 里、由一个专用
  构造器落成节点。改由载荷 `meta` 随正文子节点复刻——与 `user_node` 复刻 `payload.meta`
  是同一条纪律，不是第二套约定。读方（CLI 的 `is_progress_surface`、e2e 的
  `meta.surface === "reply"`）一个字都不用改：它们读的本来就是 `meta`。
- **裁决三：答话的正文身份由内核那份派生算。** `answer_id` 走
  `event_output_text_node_id(...)`，答话轮没有流式节点 ⇒ 回退 `{root}-text`。这与被中止
  轮 `failed` 半截的正文身份**同源**：中止时两格折出的节点按 id 合成一条，不会多出第二个
  节点（旧形状下一条是根级、一条是子节点，同 id 靠「只认首次」硬压，顺序一变就露）。
- **裁决四：终态移交按「状态不是 `Completed`」判，不按「有没有 `error`」。** 中止轮没有
  错误信息（它没失败），旧判据因此把它一起跳过——而旧形状之所以没露，是因为中止轮还
  会落一条**空正文节点**来承这个状态（`dialog` 分支无条件产节点）。空节点退场后，终态
  必须由骨架移交给轮根（用户消息节点兼任轮组，`D-335`）：中止轮在读面上就是「这一轮被
  按停」，与失败轮同一条路径。`error` 缺席时不覆盖既有那格。
- **不是「抽一个 payload 组装函数」。** 上一轮登记的落点是这个，但抽出来也只能让两份载荷
  长得像——树还是两棵，而树是实时面、重建面、按根切窗口与前端渲染共同的输入。合的是
  **拓扑**，不是字符串。
- **也不新开一个插件（横向扩展在这里已经是满分）。** 答话的接入面本来就是一个
  `plugin_row` 行（`session.answer`：一条声明 + 一个执行体），加载期有归宿、写入面封闭、
  棘轮看得见。它拆不出独立 crate 的原因是可量的：措辞往返（`compose/wording`）由终答 /
  首响 / 汇报三条落格行共用，而它的上下文 `dialog_context` 是会话的对话线折叠——拆出去
  要么复制三份，要么造一个「谁都不拥有」的共享工具层（`C-003` 单消费方占公共面）。
  真正的成本从来不在「谁写这一格」，而在投影层那条**专用分支**，它已经删了。
- **判据。**
  1. 全仓 `"dialog"` 载荷 0 处（写方与读方一起退场）；
  2. `rebuild.test.rs::answered_turn_folds_into_the_same_tree_as_a_work_turn`：答话的
     正文与思考同挂轮根、正文带 `meta.surface` / `meta.reason`；
  3. e2e `t21` / `t22`：答话节点的父 = 用户消息节点（不再是 `null`），思考与正文同级；
  4. `rebuild.test.rs::aborted_status_lands_on_the_round_root`：空正文的中止轮不产正文
     节点，`aborted` 落在轮根上且不携 `error`；
  5. e2e `t7` 的判据从「aborted 落在正文节点」改成「aborted 落在轮根、其余 aborted 节点
     不越出轮根」——它真正要拦的东西（有节点停在 `streaming` / 会话 `outcome` 不是
     `aborted`）一字未动；
  6. `cargo test --workspace` 与 e2e 全量通过。
- **不做什么。** 不给首响（`chat.assistant.opening`）也换成 `meta` 装载：它的节点 id 有
  `opening:` 前缀的存量容错规则，且它已经是轮根下的子节点（`D-426`），改它只是把一条
  已经正确的路径再洗一遍。不动 `ReportDraft`（进度汇报站在**轮边界**上，根级是对的）。
  不为旧事件保留 `dialog` 读取垫片：两个旧写方都把 `text` 写在了顶层，折叠结果不变；
  只有「`dialog.text` 与顶层 `text` 不一致」的残破事实会少一个节点，那种事实没有第二条
  自洽读法，不猜。

### D-439 判据从「住哪个模块」换成「读者在哪一侧」：模型产物退回 model 插件，工具契约不搬层

`D-438` 的判据是「内核装错了地方」——结论没错，但方向仍停在**架构模块之间搬家**：`kernel` 搬到 `sdk`，而 `sdk` 也是架构模块。目标既然是「义务环 + 世界端口」，判据就该问**读者在哪一侧**：

1. **只有一侧读 ⇒ 那是那个插件的私有词汇**（`D-023` 依赖方数量判据的严格版）；
2. **两侧以上读、且都是插件 ⇒ 跨插件词汇留在共享层**。共享层不是收纳箱：只有**数据**能靠搬层解决归属；**执行契约**不能——它要么被一个更通用的协议替代，要么留在原处。换个架构模块住不会让它消失（门面与 sdk 同为架构模块）；
3. **环读 ⇒ 语法，进内核**（今天的四 trait 一格不动）。

按这条重判 `D-438` 的盘点表，**有一行结论要改**。原因是一件事：`D-438` 的「生产读者」栏是照端口**之前**的形状填的——端口落地后会话侧不再持有 `RoundOutput`，它读执行体落下的**事实键**（`usage` / `spend` / `reason` / `truncated`）。

| `Capability` / `capability_invoke` / 工具行构造 | 8 个工具插件 + `plugin-tool` 分发 + 审批闸 + agent 的改名装饰器；**环零处** | 工具世界内部的**执行契约**：搬层不减少架构词汇，换类型可以（`D-440`） | 由通用 `PortExecutor` 取代（`D-440`） |

- **工具侧第一层判定：平替不行、搬层无意义。** 门面（`symbio-plugin-api`）与 sdk 同为架构模块，上一版「搬到门面 `tool` 模块」的结论作废。「在不改派发模型的前提下用 `PortExecutor` 平替 `Capability`」要付的代价，取自 `symbio-plugin-api/src/port.rs` 的**实际合同**，逐项比对（这一层判的是**平替**，不是 `D-440` 的原理路径）：

  - **不动 `dialog`。** 它的读者是 `compose` / `classify` / `session` 三个插件（经门面），符合「两侧以上 ⇒ 共享层」。

### D-440 架构原理复核：端口集是装配期收集出来的，工具就是端口

**判定：`Capability` 可以废除，用 port 相关接口替代。** 中间两轮把当前实现当公理
（「端口名是 `&'static str`」「端口集由 `registered_ports` 从能力表反推」），两条都已
作废。设计方案只问一件事：按「义务环 + 世界端口」，什么形态概念最少。

## 原理：端口是装配期的事实，不是编译期的常量

- 环只认「一笔债 → 端口名（字符串）→ 执行体 → 事实」，**不解释端口名**（I-6.2）。
- 端口集由**这一轮活着的插件**决定：启停、MCP server 上线、子 Agent 作用域创建 / 销毁
  都会增减端口。它天然动态，且应当由**收集**得到，而不是从一张表的行名前缀反推。
- 执行体只有一种通用形状：`PortExecutor`（`PortInput → PortOutcome`）。模型与工具都是
  它的实现，架构层不为任何一个世界留专用 trait。

## 终态（四层）

| 层 | 内容 | 有没有模型 / 工具词 |
|---|---|---|
| 协议 | `PortProvider` / `PortExecutor` / `PortInput` / `PortOutcome` | 零 |
| 收集 | 装配期端口收集：活插件申报 `(端口名, provider_id, 执行体)`，收集器直接成表、同名当场判重、缺席即 `Absent` | 零（端口名是数据） |
| 数据 | 一张纯数据表：工具描述 / JSON Schema / 风险 / 行为名、模型目录、提示词、挂载、选项、配置 | 只有数据字段名，无接口 |
| 环 | `Call.port` 是运行时字符串，查收集表取执行体、转交、落事实 | 零 |

**工具就是端口**：端口名 = 工具 wire name（运行时拼出的实例名），每个工具插件申报自己的
端口并交出通用执行体；`plugin-tool` 这个「工具世界总代理」、`Capability` trait、
`capability_invoke`、工具行的 `Arc<dyn Capability>` / `ToolPayload` / `cap()` / `meta()` /
`CapabilityRow::tool` 一起退场。模型与工具同形，架构层只剩通用协议 + 一张数据表。

## 收集式为什么比派生式好

端口集不混在能力表里：装配期的专用容器按端口名收集绑定，判重在登记时做（同名两
provider 当场指名冲突），停用即不申报即缺席。键就是端口名本身，不存在编码行名、前缀
反推，也没有「端口名必须能塞进行名」的隐含约束。收集式与能力收集同构，不新增机制种类。

## 三个落点（实施前先定）

1. `meta()` / `risk_for(&args)` → 注册时的**数据行**；动态风险由执行体在
   `PortOutcome.authz` 自判（该字段本就是「执行体自判授权结论」，D-385）。
   `PrefixedCapability` 与 `ApprovalGate` 这两层「包一层」随之消失——动态端口名天然
   支持前缀，审批回到宿主按数据的通用闸门。
2. `Value` → 工具结果事实（`result_text` / `pending` / `failure_kind` / 守卫）：今天
   `plugin-tool` 一处收口，终态由每个端口执行体把结果写进 `PortOutcome.facts[0]`
   （与 model 端口自己折事实同形），宿主唯一写口按通用规则落行。约定一条：
   结果放 `facts`，工具失败不写 `error`（失败是信息性事实）。
3. 模型下行工具清单：由数据行 + 收集到的端口按注册序装配（D-057 顺序不变）；
   `Call.port` 由常量 `tool` 换成运行时工具名，环仍只转交字符串、不解释。

## 不做什么

不新开 crate、不把契约搬进 sdk / 门面（换住址不减少架构词汇）、不给端口协议加具名
世界的方法（I-6.2 一格不动）、不把 `CapabilityMeta` 等纯数据搬出共享层。
