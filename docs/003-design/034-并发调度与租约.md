# 并发调度与租约

## 内容

前置：S03 ｜ **新增机制键 0** ｜ 参数变化 4
## 1. 场景：要什么能力

多个任务同时在跑，谁就绪谁上；同一资源同一时刻只有一人持有（租约）；冲突时有仲裁而不是竞态。

相对 S03 高了什么：**从"一个执行序列"到"一个调度系统"**。T2 的任务图是静态的，
T3 的调度器要在运行时判定就绪、发放租约、处理抢占。

## 2. 为什么它能落在 v2 上（J1）

并发最容易诱使架构师引入"调度器组件"。拆开看：

| 看起来新的东西 | 实际是 |
|---|---|
| 调度器 | 一个 `Decider`，输入 `ReadySet` 视图，输出 `task.assigned` 事件 |
| 就绪判定 | `projection = readyset`——**纯函数，从事件序列算** |
| 租约 | 带 `until_ms` 的 `task.assigned` 事件，不是锁原语 |
| 仲裁 | 单写者 FIFO——I1 的推论，不是新机制 |

**关键**：租约是**事件**不是锁。锁需要"持有状态"，事件不需要——持有状态由投影算出。
所以整个系统没有并发原语，只有一个 FIFO 和一条单调 `seq`。**新增机制键 = 0**。

## 4. 平凡值与回退（J2）

| 参数 | 完整值 | **平凡值** | 平凡值下 |
|---|---|---|---|
| `projection` | `readyset` | **`readyset:cap=1`** | 仍完整运行——就绪集容量为 1，退化为串行 FIFO |
| `actor.budget_ms` | `80` | `60000` | 仍完整运行——调度慢，但不错 |

**`cap=1` 是本阶最漂亮的一个平凡值**：把并发度调到 1，调度器、租约、仲裁逻辑**一行代码都不用改**，
系统自动变成 串行执行。这说明并发度确实是参数而非结构。

`cap` 的写方是**会话配置**（`PLUGIN.yml` 的 `task_cap`）：它不是行常量、也不是调度器的字段——
「这台机器上的这个会话允许同时推进几件事」是配置，不是机制。读侧按 `cap.max(1)` 归一：
`0` 与 `1` 同义（容量为零的调度器不是「更保守」，是「永不动」）。

## 5. 静默失效与强制（J3）

| 约束 | 违反时信号 | 强制方式 |
|---|---|---|
| `seq` 严格单调 | **无**——只是顺序乱了 | CI 断言（`invariants.rs`） |
| 单写者 FIFO | **无**——竞态只在压力下偶发 | 运行时 FIFO + 静态扫描无主体直连 |
| 租约 TTL 必须被检查 | **无**——可能死锁且无人报错 | 调度者每轮扫一遍史：`until_ms <= now` 且任务非终态 ⇒ 判死并落 `task.ready{reason: "lease_expired"}`（`an_expired_lease_is_judged_dead_and_reassigned`）+ 预算内必产出（I3） |

## 6. 验收断言

1. 打乱事件到达顺序 → `seq` 单调断言必须仍然成立（由 Store 保证，不由调用方保证）。
 执行方：`store/mod.test.rs` + e2e **t32**（双进程第二写者拿 `NotTheWriter`）+
 `e2e/helpers.mjs` 的 seq 断言 + `verify/invariants.rs` 的 `I1SeqNotMonotonic`。
2. 同一笔活被注入 100 次 → 只发**一笔**租约（抢同一份活有仲裁）。
 执行方：`crates/symbio-plugin-loop/src/task_events.test.rs::a_hundred_injections_yield_exactly_one_lease`——
 每轮重算就绪集、重跑调度者、把事实落格，100 轮下来 `task.assigned` 恰一条。
3. `cap = 1` 下并行请求退化为串行，且系统完整运行。
 执行方：`the_ready_set_capacity_is_a_parameter_not_a_structure`——同一份事件切片上
 `cap = 1` 给一笔、`cap = 4` 给四笔，判据一行不改（这就是 §4 的 J2）。
4. 反向：`cap = 4` 时四条同时进候选（**不是**「cap 只是个装饰」）。
 执行方：同上一条的后半段。
5. 租约到期 ⇒ **判死**，不静默挂起。
 执行方：`an_expired_lease_is_judged_dead_and_reassigned`——到期那一轮先落
 `task.ready{reason: "lease_expired"}`（死因有事实），再重派。

## 关键决策

### D-139 D-064 重开：`task.ready` / `task.assigned` 进事件词汇表，`readyset` 加 `cap`——写方与消费方同批落地

D-064（2026-10-13）收窄的理由是「新增事件名动 `symbio_core` 事件词汇表，而本阶梯承诺
架构改动 = 0」。**收窄当时是对的，重开不是否定它**——重开的理由是它自设的两个前提
都成立了：

1. **消费方出现了**。收窄时 `task.assigned` 没有读者；现在义务环已经把「一切控制面
   推进都是表里的一笔债」变成机制现实，`task.ready` / `task.assigned` 作为事实有
   明确的行表读者（调度者行的 `owes` / `until`），不再是悬空词汇。
2. **SC-004 的用户判据是已承诺场景**（并行推进 + 抢同一份活有仲裁），它的缺口
   （[SC-004-并发调度与租约](../002-scene/004-并发调度与租约.md "SC-004-并发调度与租约") 的账本）挂在账上等着收窄裁决重开。按「最终目标优先」，
   承诺过的能力不该因为「实现起来事件词汇表要变宽」而无限期后置——词汇表变宽
   走 D-055 的决策通道，本条就是那个决策。

**裁决**（四条，缺一即回到收窄态）：

| # | 裁决 | 理由 |
|:-:|---|---|
| 1 | 词汇表新增 `task.ready` / `task.assigned` 两格（D-055 通道） | 就绪与发放是调度仅有的两个**用户可见判断**（SC-004），它们必须有事实形态才能被行表消费、被回放审计。只活在投影里 ⇒ 「谁在什么时候把活给了谁」回放看不见，调度行为不可审计 |
| 2 | `readyset` 加 `cap` 参数，平凡值 `cap=1` 退化串行（J2 已写明一行代码不改） | 并发度是参数不是结构——这是本阶设计自证过的；`cap` 的写方是会话配置，不是行常量 |
| 3 | 调度者是一个 `Decider` ActorSpec 行（反射档 80ms），`task.assigned` 的**唯一写方**（写侧闸） | 调度器 = 一个 Decider（§2 的拆解）；写侧闸是单写者的可执行形式（反向用例：非调度者写 `task.assigned` ⇒ 红） |
| 4 | **写方与消费方同批落地**（D-064 自设的重开条件照抄）：调度者行 + 写侧闸 + `cap` + 租约 TTL 判死，一个提交收口 | 不许先加事件看看效果——没有消费方的词汇 = 恒空旋钮（SP-009），正是 D-064 当初要拦的形状 |

**被否的候选**：

| 候选 | 否掉的理由 |
|---|---|
| `task.ready` 不进词汇表，就绪只靠 `readyset` 投影现算 | 投影是纯函数没错，但「就绪」是调度者** acted on **的判断输入——把输入留在投影、只落输出（`assigned`），回放时无法区分「算过但没派」与「没算」；且跨会话的候选集交换（多工人场景）没有可引用的事实 |
| 调度器做成组件（独立模块 + 直接调用） | 违背 DE-030 的拆解（调度器 = 一个 Decider）与义务环「没有第二个调度器」（D-118 决策 1）——组件式调度器就是旁路收编要消灭的那类第二套调度 |
| 维持收窄，等「架构改动 = 0」的窗口 | 不存在这样的窗口：词汇表变宽永远是 D-055 决策，等窗口 = 把已承诺的用户能力无限期后置（GO-001 §3 批评的正是这个形态） |

**代价说清**：事件词汇表 +2（核心公共面变宽，这是 D-055 通道的正常成本，不是意外）；
测试 +3 条反向用例（非调度者写 `assigned` ⇒ 闸红；`cap=1` 下并行请求退化为串行且完整；
TTL 到期 ⇒ 判死不静默）。

### D-150 S04 落地的三个形状：租约是事件、到期即放回、`cap` 只有会话一个写方、调度只在一处判死

D-139 定的四条裁决（词汇表变宽 / `cap` 是参数 / 调度者是 `Decider` 且唯一写方 / 同批落地）
在 S04 落地时必然要选**具体形状**——同一条裁决可以写成很多种代码，形状选错则裁决落空。
这里记的是选中的三种形状，以及被否掉的三种「看起来更省事」的形状。

**三个形状**：

| # | 形状 | 为什么是这个形状 |
|:-:|---|---|
| 1 | **租约是事件，不是可变状态**：一笔租约就是一条 `task.assigned{task_id, owner, lease_ms, until_ms}`；「它还有效吗」由 `readyset` 在投影里比 `until_ms <= now` 现算，任何地方都不存 `HashSet<TaskId>` | 判据只吃**史**（seq + 时间戳），于是同一份切片永远算出同一批结果：回放、重放、跨进程复算全都不需要额外输入。反过来，任何一处持有内存态，投影就不再是纯函数，重启即失效 |
| 2 | **到期即放回，且放回要留事实**：`task.assigned` 的 `until_ms <= now` 且任务非终态 ⇒ 调度者补一条 `task.ready{reason: "lease_expired", expired_owner, until_ms}`，然后才重新发放 | 「突然又能派了」与「有人判过它死了」在回放里必须分得开——否则租约到期这件事对审计不可见，等于又退回「静默挂起」（§5 表最后一行要防的正是它）。死因写在 `reason` 上，判死这件事本身就有账 |
| 3 | **`cap` 只有一个写方（会话配置），调度只在一处接线**：`SessionConfig::task_cap` → `readyset(cap)` 与 `ScheduleDecider` 共用同一个值；`readyset` 内部 `cap.max(1)` 归一（`1` 与 `0` 同义 = 串行 FIFO）；调度在 `turn_exec/persist` 的**轮末一处**接：重新取史 → 算视图 → 跑调度者 → 落格 | 并发度是**运行期参数**不是结构（§4 的 J2）。写方只有一个，才有「谁把并发调大了」的可追性；接线只有一处，才不会有第二个调度器（D-118 决策 1）。`cap.max(1)` 把「未配置」收敛成最保守的串行，而不是 `0` ⇒ 一笔都不派（那会让空配置变成停机） |

第 3 条里那个「轮末重新取史」不是随手写的：`record_derived` 之后史已经变长（承诺、任务表、
熔断都刚落了格），拿旧快照算就绪会漏掉本轮刚开的任务——**调度必须排在本轮所有派生事实之后**。
这也是它在 `persist` 里位于 `record_derived` 与 `record_elimination` 之间的原因。

**被否的候选**：

| 候选 | 否掉的理由 |
|---|---|
| 把 `cap` 做成行常量（调度者行上的 `cap` 字段） | 行表是**债务表**，不是配置表：调并发不会改变谁的债，只会改变同一时刻交出去几笔。做进行常量就有了一个没有写方、永远填死的旋钮（SP-009 的另一面：不是空旋钮，是僵旋钮），配置面板改不动它 |
| 让调度者自己持有状态（内存里记「我派过谁」） | 判据一旦依赖内存，「派过没有」就只有活着的那个进程知道：重启后重复发放，回放时算不出当时的裁决。D-139 裁决 1 要求 `task.ready` 进词汇表，正是为了不靠内存回答这个问题 |
| 用挂起态（`task.held`）兼任租约 | `held` 是生命周期状态，没有时间语义。把 `until_ms` 塞进状态，投影就变成「状态 × 时钟」的混合判据——同一个任务在同一时刻既 held 又 expired，谁先谁后没有答案。租约是**期限**，期限只能由时间判 |
| 判死交给读方（谁读就绪集谁顺手判） | 读方是纯函数、无写权。判死要落事实，落事实必须有写侧闸（`assign.work`）——把判死挪到读方等于绕开闸门，正是 D-139 裁决 3 要拦的形状 |

**代价说清**：`ReadySetView` 多一个 `cap` 字段（读口的返回形状变了，`/readyset` 的消费方
要跟着认这个字段）；每轮多一次 `store.range(0)` 取史（调度者判死与判「记过就绪」都要看全史，
这条开销随事件数线性增长，是「判据不靠内存」的直接账单）。
