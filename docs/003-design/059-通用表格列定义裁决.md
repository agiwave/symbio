# 059 通用表格列定义裁决（D-532）

> 一句话：详情表单的 `table` widget 与 `DetailColumn` 是**机制原生的通用对象数组编辑能力**，
> 不是沙箱专用表单；它带来的 7 个数据面格子与 1 条门面语法臂，是同一份列契约在内核与
> 门面两侧的形状，按 CS-002 / HS-006 立此决策逐条论证「必需」。

### D-532 通用表格列定义：对象数组编辑是机制能力，不是插件特例

**背景**：沙箱能力约束从「JSON 裸文本」改成用户明确要求的结构化规则编辑——一行一条规则，
列是「对象 / 匹配模式 / 值 / 动作 / 风险档」（讨论稿§「规则模型」）。裸文本方案被用户否定
（「json 编辑更不易用」），根因是表单机制只有标量 widget，没有对象数组编辑能力。本次补齐
的是**通用表格机制**，列定义由插件声明，机制层不含任何沙箱 / 命令 / 路径业务词。

**裁决**：

1. **`table` 是通用 widget**：与 `text` / `select` / `json` 同级，由 `DetailField.widget` 选择；
   它只表达「这个字段是一个对象数组，按列编辑」，不预设任何行语义。机制层新增的
   `tableRows` / `tableNewRow` / `tableRemoveRow` 纯函数只认列定义，不认业务字段。
2. **`DetailColumn` 是机制原生的列声明**：六格——`key`（行对象里的键）、`label`（表头）、
   `widget`（该列用 `text` / `select` / `number` 哪种标量控件）、`options`（select 候选）、
   `default`（新增行预填）、`placeholder`（输入提示）。六格折不开：少 `options` 就无法渲染
   枚举列，少 `default` 就无法预填合法首行；降 `pub(crate)` 不行——写方是声明表格的插件
   （沙箱），读方是前端表单机制经门面镜像，跨 crate 且插件互不可见（E-009）。
3. **`DetailField.columns` 是列定义的唯一挂载点**：一列数组字段的列结构只能随字段声明走，
   不能塞进 `options`（那是标量选项的候选值，语义不同），也不能新增「沙箱规则字段」之类的
   专用类型——后者会让表单机制反向依赖插件业务词，正是 D-531 反复否定的方向。
4. **`DetailColumn` 经门面再导出是必要语法臂**：插件要声明 `DetailField.columns`，就必须在
   自己的 crate 里构造 `DetailColumn`；门面是插件唯一可依赖的机制层（E-009 插件互不可见）。
   这是同名的 kernel 共享语法经 `symbio-plugin-api` 整模块转出，不是新增可写路径。
5. **通用性边界**：没有新增世界域名 / 端口名 / 事实名，也没有为某个插件开专属口子——任何
   插件未来要编辑对象数组（规则表、映射表、多值参数表）都复用同一列契约，零 kernel 改动。

**不做什么**（防止退回特例）：

- 不在 `DetailColumn` / `table` 机制里出现 `shell` / `path` / `sandbox` / `risk` 等业务词；
- 不给沙箱新增专用 widget 或专用 detail 字段类型；
- 不把规则表做成前端路由硬编码——继续走 VDFS provider 的 definition-driven detail。

**Core-Change**：这是 kernel 数据面 + 门面各一处改动。CS-009 上 `DetailColumn` 六格 +
`DetailField.columns` 一格共 7 格；HS-006 上门面语法臂 +1。两者都是同一份列契约的形状，
理由在本条 2 / 4 逐条给出，基线分别钉到实测 622 / 110，不留余量。
