# 义务环事实词表与债务表

> 放 `docs/003-design/` 的理由：这两张表是**插件与环之间的长期契约**（哪些事实存在、哪条债等哪条事实），
> 不是某次任务的进度。`docs/007-task/` 记录「这次要做什么、做到哪」，契约要留在设计层。

## 0. 记号与总原则

- `response(P:X)`：端口 `P` 对债 `X` 的收束事实。**它的 `kind` 必须是表一里的某条领域事实**。
- `debt(P:X)`：债身份 `(port, id, attempt)`。`id` 由欠债方从事实派生；`attempt` 只由租约推进。
- 表二的触发条件只能读表一的事实（含外部事件），不读任何引擎自述。
- **禁止出现的词**：步骤、阶段、轮次、第 N 次、序号。它们不是事实，是旧引擎的进度自述。

**事实身份规则（全表适用）**：每条能力事实的 `id` = 产生它的债 `id`（**不含 `attempt`**）。
`attempt` 只进环的配对键，不进事实身份——这是重放收敛的前提（见 §4）。

## 1. 表一：事实词表

| 事实名 | 性质 | 由哪个插件写 | 载荷字段 | 谁读它 |
|---|---|---|---|---|
| `user.message` | 外部世界发生 | `session`（经 gateway 路由） | `scope`、`principal`、`text`、`msg_key` | `recall`、`model`、`compress`、`session` |
| `scope.opened` | 会话生命周期 | `session` | `scope`、`principal` | `recall`、`model`、`tool`、`approval`、`compress`、`session` |
| `scope.closed` | 会话生命周期 | `session` | `scope`、`outcome` | `session`、前端投影 |
| `abort.requested` | 外部世界发生 | `session` / `gateway` | `scope`、`reason`、`request_key` | `session` |
| `aborted` | 会话生命周期 | `session` | `scope`、`reason`、`request_key` | `model`、`tool`、`session` |
| `recall.completed` | 能力完成（`recall` 端口的 response） | `recall` | `scope`、`context_key`、`items[]`（`fact_id` / `text` / `score`） | `model`、`session` |
| `compress.completed` | 能力完成（`compress` 端口的 response） | `compress` | `scope`、`context_key`、`summary`、`snapshot_key`、`covers[]` | `model`、`session`、前端投影 |
| `model.replied` | 能力完成（`model` 端口的 response） | `model` | `scope`、`input_key`、`final`、`text`、`calls[]`（`call_id` / `name` / `args` / `needs_approval`） | `tool`、`approval`、`session` |
| `tool.result` | 能力完成（`tool` 端口的 response） | `tool` | `scope`、`model_key`、`call_id`、`ok`、`text` | `model`、`session` |
| `tool.denied` | 能力完成（`tool` 端口的 response） | `tool` | `scope`、`model_key`、`call_id`、`reason` | `model`、`session` |
| `approval.requested` | 能力完成（`approval` 端口的 response） | `approval` | `scope`、`model_key`、`call_id`、`tool`、`summary` | `session` / 前端、`tool` |
| `approval.granted` | 外部世界发生（用户动作） | `session` / `gateway` | `scope`、`call_id`、`by` | `tool`、`approval` |
| `approval.denied` | 外部世界发生（用户动作） | `session` / `gateway` | `scope`、`call_id`、`reason` | `tool` |
| `finalized` | 能力完成（`session` 端口的 response） | `session` | `scope`、`text`、`transcript_key`、`from_model_key` | 前端投影、`session` |

命名口径：

- `context_key` = `hash(scope + user.message 的身份 + 可见域)`；召回与压缩共用它，**与工具结果无关**，
  所以工具往返不会让召回/压缩重新开账。
- `input_key` = `hash(按序拼接的模型输入事实身份)`；输入 = `user.message` + `recall.completed` +
  `compress.completed`（若有） + 上一 `model.replied` + 该次应答全部 `tool.result` / `tool.denied`。
  同一输入 ⇒ 同一 `input_key` ⇒ 同一债 id ⇒ 不会重开。
- `model_key` = `(model, model.replied 的事实 id, 产生它的 attempt)`，供工具/审批债派生 id。
- `covers[]` 记录压缩覆盖的事实身份集合（不记区间序号）。

### 1.1 债行只允许五个谓词

一张债表的一行只表达「欠不欠」与「什么时候可还」，谓词闭集如下（**不许再加第六个**）：

1. `when(<事实种类>)`：该种类的事实在本可见域存在才欠。环把字符串原样交给宿主的
   `exists(kind, scope)`，不解释它是什么。
2. `unless(<事实 id>)`：该 id 的事实已存在则不欠（排除条件）。
3. `when_no_open(<端口名>)`：该端口的债**全部还清**才欠。读的是**债状态**
   （本 scope 有没有该端口的未收束 `request`），不是事实状态；端口名同样是字符串。
4. `after_port(<端口名>)`：该端口**这一轮**还有人认领（可派发 / 在飞 / 挂起）⇒ 本行
   不进计划；该端口**没人认领** ⇒ 前提已了，本行照常可还（**缺席即收束**）。读的
   同样是债状态，与 `when_no_open` 同一条读面、方向相反；端口名是字符串，**依赖方
   只认端口，不写兄弟插件的行名，也不拼债 id**。上一轮遗留的未收束债**不算认领**——
   债表按当轮事实现算，遗留债由它自己的租约收束，不该挡住新一轮。
5. 无条件：以上都省略 ⇒ 无条件欠一笔（是否已收束仍由环的配对键判定）。

归属：五个谓词全部属于**选债**。`when` / `unless` 问宿主事实存在性；`when_no_open` /
`after_port` 读环自己的债状态，`after_port` 只决定「这一圈进不进计划」，且**同一次
计划内一次算全**——前提端口有没有人认领，由同一次计划的行集合回答，不第二次读事实
（D-343）。**能力方自己报行，中央不设计规则。**

`after_port` 为什么非它不可：`when` / `when_id` / `after` 只能表达「某条事实来了」，
**表达不了「它不会来」**。判在派发前一次完成时，「还没判」与「根本没这个能力」在
事实面上同形：能力未挂载 / 开关关闭时，前置债永远不会出现，`when_id` / `after` 会把
依赖方**永久挡住**。`after_port` 把这个否定留在债状态里：依赖方等的是**端口这一圈的
认领**，没人认领就当作已了。它同时满足两条硬约束——(1) 只读债状态，不引入新事实种类；
(2) 依赖方只写端口（`plugin_row` / `model` …），因此「删掉兄弟插件的行名常量」与
「区分挂载 / 开关」是同一个改动。

前提债不是新的静默门：被 `after_port` 挡住的行走同一圈的计划，前提行本身有租约与
尝试上界（`plugin_row` 行 60s / 1 次）；认领了却收不了束的，租约到期会被判死
（`failed`），端口随之清空。一圈没有任何动作、而账上仍有依赖方被挡住时，环报
`Stalled`（**不是 `NoDebt`**）。「认领了却永不收束」因此停在可见出口，不会变成
依赖方永远不说话。

判据：某能力用五谓词表达不出来时，先问「是否该拆成两笔债」「是否缺一条事实」；
两者都不成立，才讨论给机制加谓词——**加谓词是最后一步，不是第一步**。允许加第六个的
唯一时机是出现**新的一类状态**（不是新的一类世界事实），且必须同时说明：它读哪一层
状态、与既有哪个谓词对偶、如何保证不引入第二遍事实读取、它的债如何保证租约 / 预算
（不许新开静默停摆）。**只为少写一两个兄弟插件的行名，永远不构成加谓词的理由。**

## 2. 表二：债务表

> 标注：表中 `session` 作为**端口**的行（`open-scope` / `finalize` / `abort` / `close-scope`）按
> **D-324** 作废——会话是本地簿记，不是外部世界。开场 / 收束 / 中止改为会话插件直接写事实，
> 环不再为它们欠债。行保留在此仅作历史对照，不再作为实现依据。

| 行名 | 欠哪个端口 | 债 id 派生规则（禁计数） | `until` 配对 | 触发条件 |
|---|---|---|---|---|
| `open-scope` | `session` | `open:{scope}`；`scope` 由 `user.message` 的 `(principal, 会话容器)` 派生 | `response(session)` ⇒ `scope.opened` | `user.message` ∧ ¬`scope.opened` ∧ ¬`aborted` ∧ ¬`scope.closed` |
| `recall` | `recall` | `recall:{context_key}` | `response(recall)` ⇒ `recall.completed` | `scope.opened` ∧ `user.message` ∧ ¬`recall.completed(context_key)` ∧ ¬`aborted` |
| `model-call` | `model` | `model:{input_key}` | `response(model)` ⇒ `model.replied` | `scope.opened` ∧ `user.message` ∧ `recall.completed(context_key)` ∧ ¬`model.replied(input_key)` ∧ ¬`aborted` ∧ 输入中每个 `call_id` 都已有 `tool.result` 或 `tool.denied` |
| `tool-call` | `tool` | `tool:{model_key}:{call_id}` | `response(tool)` ⇒ `tool.result` | `model.replied` 含该 `call_id` ∧ ¬`tool.result(call_id)` ∧ ¬`tool.denied(call_id)` ∧ (`needs_approval=false` ∨ `approval.granted(call_id)`) ∧ ¬`aborted` |
| `tool-deny` | `tool` | `tool:{model_key}:{call_id}:denied` | `response(tool)` ⇒ `tool.denied` | `model.replied` 含该 `call_id` ∧ `approval.denied(call_id)` ∧ ¬`tool.result(call_id)` ∧ ¬`tool.denied(call_id)` ∧ ¬`aborted` |
| `approval-ask` | `approval` | `approval:{model_key}:{call_id}` | `response(approval)` ⇒ `approval.requested` | `model.replied` 含该 `call_id` ∧ `needs_approval=true` ∧ ¬`approval.requested(call_id)` ∧ ¬`approval.granted(call_id)` ∧ ¬`approval.denied(call_id)` ∧ ¬`aborted` |
| `compress` | `compress` | `compress:{context_key}` | `response(compress)` ⇒ `compress.completed` | 该 scope 可见事实的 token 水位超过阈值 ∧ ¬`compress.completed(context_key)` ∧ ¬`aborted`（水位从事实文本长度累加，不读步数） |
| `finalize` | `session` | `final:{model_key}` | `response(session)` ⇒ `finalized` | `model.replied(final=true)` ∧ ¬`finalized(scope)` ∧ ¬`aborted` |
| `abort` | `session` | `abort:{scope}:{request_key}` | `response(session)` ⇒ `aborted` | `abort.requested(scope)` ∧ ¬`aborted(scope)` |
| `close-scope` | `session` | `close:{scope}:{finalized_key}` | `response(session)` ⇒ `scope.closed` | `finalized(scope)` ∧ 该 scope 无更晚的 `user.message` ∧ 债表对该 scope 不再产出任何未收束行 ∧ ¬`aborted` ∧ ¬`scope.closed` |

表二自检：

- 每条 `until` 都落在表一的**能力完成事实**：`scope.opened` / `recall.completed` / `model.replied` /
  `tool.result` / `tool.denied` / `approval.requested` / `compress.completed` / `finalized` /
  `aborted` / `scope.closed`——没有一条是引擎进度。
- 表一没有悬空名字：每个事实都在表二的触发条件或 `until` 里被引用。
- 表一、表二都没有步骤 / 阶段 / 轮次 / 序号字段。

## 3. 三个硬点

### 3.1 模型 ↔ 工具往复 = 条件性再欠一笔

1. `model.replied` 带 `calls[]` ⇒ 表二按每个调用产出 `tool-call` 行；需要审批的调用先产出
   `approval-ask` 行，用户决定写 `approval.granted` / `approval.denied` 后才分别产出 `tool-call` /
   `tool-deny`。
2. 当该次应答的每个 `call_id` 都有 `tool.result` 或 `tool.denied` 后，`model-call` 的触发条件重新成立，
   但 `input_key` 已经不同（输入里含工具结果），所以这是一笔**新债**，不是老债的重复执行。
3. 终止：模型对同一输入重复应答（`input_key` 相同）⇒ 债 id 相同 ⇒ 环视作已收束，不再开账；
   再加 `Limits.max_dispatches` 的预算上界。预算是环的护栏，不是事实。

### 3.2 一个 scope 何时算完（谓词，不含步骤）

```
complete(scope) :=
      finalized(scope)
   ∧ ¬aborted(scope)
   ∧ ¬scope.closed(scope)
   ∧ 不存在更晚于 finalized 的 user.message(scope)
   ∧ 债表对该 scope 不再产出任何未收束行
```

前四项是事实，最后一项是对债表的求值（对同一批事实重算一次行集）。
`close-scope` 行由这个谓词触发；它落 `scope.closed` 后，谓词不再成立。

### 3.3 重放收敛

- **幂等键 = 债身份**：`(port, id, attempt)`；`id` 由输入事实派生，`attempt` 只由租约推进。
- 环只落五类事实：`request` / `sent` / `response` / `failed` / `retry`，并落盘。
- 重起后：
  - 已有 `response` / `failed` 的债 ⇒ 直接视为收束，**不执行**；
  - 只有 `request`、无 `sent` ⇒ 补派发；
  - 有 `sent`、无收束且租约已过 ⇒ 落 `retry(attempt+1)` 再派发；
  - 同一 `(kind, key)` 重复投递被账本吸收。
- 领域事实的 `id` 不含 `attempt`（§0）：即使同一债因租约重试执行两次，写出的仍是一条事实，
  下游读到的身份不变，不会出现两份 `model.replied` / `tool.result`。

### 3.4 agent 的最小债规则（谓词的最小实证）

模型端口只需自报两行，就覆盖第一条 e2e 的全部往复：

| 行 | 端口 | 债 id | 谓词 | 说明 |
|---|---|---|---|---|
| `model-reply` | `model` | `model:{input_key}` | `when(<用户输入事实>)` + `unless(<终答事实>)` | 有输入、尚无对应终答 ⇒ 欠一笔 |
| `model-after-tools` | `model` | `model:{input_key'}` | `when_no_open(<工具端口名>)` | 该 scope 无未还工具债 ⇒ 欠一笔 |

第二行不需要执行体写「批次完成」事实：工具是否全部还清由**债状态**回答，
这正是 `when_no_open` 存在的理由。

## 4. 加一个新能力只动什么

一个新能力插件只交三样东西，**环与宿主零改动**：

1. 它写的事实名（表一加一行）；
2. 它的债表行：端口名、`id` 派生规则、`until`、触发条件（表二加一行）；
3. 它的执行体（只读写事实，拿不到派发句柄）。

**能力折算判据（不是口号）**：每个能力 = 一个插件，自己报自己的债行、自己写自己的事实；
中央只提供**五个谓词**，不设计任何能力的规则。验收方式：新增一个能力时，只改它自己的 crate
（声明 + 执行体），环、宿主、`plugin-api`、`kernel` 的 diff 为 0；若做不到，先按 §1.1 的判据
检查是不是行拆错了或事实缺了，而不是先加谓词。

落地前提（实现时必须满足，否则第三张验收不成立）：

- 插件声明必须是**运行期可枚举的数据**（`PLUGIN.yml` + 声明注册），宿主只做「收集声明 → 交给环」，
  不把任何能力名写进代码；
- 环只认表二的行数据：端口名是字符串，`until` 是事实名匹配，触发条件是事实谓词；
- 谁写哪条事实由声明给出，环不替任何插件写领域事实。
