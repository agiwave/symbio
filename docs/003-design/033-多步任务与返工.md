# 多步任务与返工

## 内容

前置：S02 ｜ **新增机制键 1**（`scope`）｜ 参数变化 5 ｜ 阶段三

## 1. 场景：要什么能力

一个请求拆成多步；某一步被独立验证判为不合格时，**产生返工而不是将错就错**。

相对 S02 高了什么：**从"一次动作"到"有向图 + 质量闸门"**。这是 T2 与 T1 的分界线：
T1 做一步看一步，T2 能规划并把质量判定写进流程。

## 2. 为什么它能落在 v2 上（J1）

| 看起来新的东西 | 实际是 |
|---|---|
| 任务图（DAG） | 事件的 `depends_on` 字段——**数据** |
| 子任务 | `scope = child:<id>`，一条参数 |
| 返工 | `task/asserted`（`task.rework_created`）事件——**不是回滚** |
| 独立验证者 | 一行 ActorSpec，`capabilities: [AssertVerification]` |

**关键**：返工是**新增一条事件**，不是修改历史。日志永不改，投影自然排除被取代的节点。
这一点决定了整个系统不需要"事务"——**append-only 已经提供了撤销语义**。

## 3. 增量清单（只加数据）

| 类型 | 内容 |
|---|---|
| 事件格子 | 新增 `task/opened|progressed|held|asserted` 各格（网格已有实体 `task`） |
| 新参数键 | **`scope`**（`root` / `child:<id>`）——本阶唯一新增机制键 |
| ActorSpec 行 | 规划者 `{ pattern: decider, capabilities: [DefineWork], budget_ms: 60000 }`<br/>验证者 `{ pattern: decider, capabilities: [AssertVerification], budget_ms: 5000 }` |
| grants 行 | 规划者 ▸ `define.work`；验证者 ▸ `assert.verification`；**二者互不可写** |
| 投影参数 | `projection = readyset`（只取终态 + `depends_on` 闭合） |

**本阶点亮的机制键**（阶梯总表的「新增机制键」由这张块算出；`scripts/gen-verify-facts.mjs` 从这里取输入）：

```capability-assign
event.entity = task
event.verb = progressed
actor.pattern = decider
actor.capability = define.work
scope = child:<id>
```

## 4. 平凡值与回退（J2）

| 参数 | 完整值 | **平凡值** | 平凡值下 |
|---|---|---|---|
| `scope` | `child:<id>` | **`root`** | 仍完整运行——不拆子作用域，主线程线性推进 |
| `actor.capability` | `assert.verification` | 空集 | 仍完整运行——无独立验证，退化为 S02 的一步到位 |

**`scope = root` 是本阶的退路口**：所有子任务压平到根作用域，递归结构消失，
但事件、投影、验证全都照常工作。这就是"递归是参数不是机制"的可检验后果。

## 5. 静默失效与强制（J3）

| 约束 | 违反时信号 | 强制方式 |
|---|---|---|
| 依赖图无环 | **无**——可能只是跑不完 | CI 断言（`termination.rs` 的 Kahn 检测） |
| 规划者不得自验 | **无** | grants 表强制：验证者 ≠ 产出者 |
| 返工次数有界 | **无**——可能无限返工 | 终止性前提：rework 有界（`termination.rs`） |

## 6. 验收断言

1. 构造含环的依赖图 → 无环检测必须报错。
2. 同一主体同时持有 `define.work` 与 `assert.verification` → 授权检查必须拒绝。
3. 注入 N 步任务 → 在 rework 上界内终止。
4. **反向用例**：把环去掉一个依赖 → 断言 1 必须通过（证明检测在算，不是常量 `false`）。

**§6 验收断言的执行方**：1 = `a_dependency_cycle_is_flagged_and_yields_an_empty_readyset`（`plugins/loop/task_events.test.rs:168`）+ 设计级 `verify/termination.rs` 的 `check_acyclic`；2 = `self_verifier_is_rejected_at_construction`（`symbio_core/actors/mod.test.rs:1455`，同一用例带「拆成两个主体 ⇒ 通过」的反向半）；3 = `n_step_chain_terminates_within_rework_bound`（同文件 `:1604`）+ `exceeding_the_rework_bound_is_flagged`（`plugins/loop/task_events.test.rs:326`）；4 = `verify/termination.rs` 的反事实实现 `is_acyclic_ignoring_cycles`（关掉环检测后环必须检测不到）。

## 8. 这一阶做不了什么

边界的唯一账本：[SC-003-多步任务与返工](../002-scene/003-多步任务与返工.md)（用户语言）。机制面独有边界（用户可见范围之外的工程约束）：

- **独立验证子系统不建**：「验证者 ≠ 产出者」（C15）的独立判定今天没有生产消费方——没有「谁来验收、验什么」的数据（完成度追求在 §3.1 名册里诚实留空），判定组件无从定义。未来能力：出现任务完成度的真实消费方（SC-003 判据拉动的验收需求）时，按**判定组件**形态立批（reflex / arbiter 先例：行给事件 actor 与闸授权，执行路径是编排器里的代码路径，不是会话）——`session/verifier` 行已在，事件词汇若要新增照 [D-055](001-核心架构.md "DE-001-核心架构") 先立决策。

## 9. 关键决策

### D-133 任务清单的工具侧记忆是**进程作用域**，持久真相是 `task.*` 事实——跨进程合并基准为空是边界，不是漏接

`local/todo_write` 的 `merge = true` 只在**同一进程**内按 id 合并；进程退出后基准为空。
跨进程的持久状态是 `task.*` 事实：`task_events::write` 每轮从事实快照重建观察状态，
工具只负责把本轮声明交给写方，不自己维护第二份可持久化的账。

为什么不让工具读事实源：

- 能力上下文只递值（[D-084](001-核心架构.md "DE-001-核心架构")），工具拿不到 `Store`；
  为了一份**确认回显**新开一个跨插件键 / 端口，把任务图的读侧接进工具，
  收益与面积不成比例；
- 工具结果只回确认、不回全量清单（`todo_write.rs` 的回显策略）。重启后模型需要的
  「清单还在不在」由请求视图置顶的`【任务调度】`段回答——它读的是同一份事实源
  （`task_events::prompt_section`），不是工具内存。

代价（写在明处）：重启后第一次 `merge = true` 的 `count` 只数本次声明项；它不影响
事实源与调度段，模型按 id 继续声明即可，`task_events` 不会把旧任务当成新任务。
要支持「跨进程续写整张清单」，得先给工具一个真正的持久读侧（一个值形态的任务快照键），
那是与「能力上下文只递值」同批的裁决，今天不做。
