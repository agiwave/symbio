# 端口终态加严裁决（D-444–D-447）

> 本篇自 DE-053 拆出：D-440 完成的是「删除 Capability 执行接口」这一窄目标，
> 本批收它留下的实质残留。四条裁决分别管**端口身份 / wire 别名**、**描述与执行同源**、
> **逐调用债与结果归属**、**门禁收窄**。链路、终态边界与硬验收以本篇为准。

## 关键决策

### D-444 端口身份与 wire 别名分离：消歧在请求成形前，不在返回时

**判定：D-440「端口名 = 工具 wire name」这句只在本批次内成立，本条把它作废。**

端口名是**内部身份**（可含 `.`，随 MCP server / 子 Agent 作用域动态生成）；wire name 是
**模型侧别名**，只在本轮暴露集合里有意义。身份不受模型协议字符集支配：把
`capability_to_wire` 放在共享层、再由四个协议各调一次，等于让身份去迁就线格式，且
`a.b` 与 `a__b` 都映成 `a__b`。`DE-001` §12 / `DE-011` §8.3 要求「同名工具必须消歧或
拒绝加载」，靠返回时「精确匹配优先」不满足——那是**选一个**，不是**拒绝歧义**。

**裁决**：

1. 别名是**描述数据**，不是转换函数：装配期由本次作用域收集为每个显式暴露的工具算一次
   wire name，写进描述行；清单装配、四个协议的下行序列化、模型返回调用的解析读**同一份**
   数据。共享层不出现 `PromptMessage` / 协议字符集换算的模型策略。
2. **请求成形前消歧**：本轮暴露集合内两个身份投影到同一 wire name，装配期即拒绝——
   落错误进错误桶、冲突两方都不暴露，并把原因写进 `session.config` 的空表原因；
   不把有歧义的清单送给模型，不靠返回时优先级掩盖。
3. 别名映射随**本轮暴露快照**。插件停用、撤权、MCP server 变化或实现替换后，旧调用
   不得静默绑定到同名新实现：解析只在本轮快照里查，查不到即失败事实。
4. 内部端口永不因「有端口行」自动进清单；端口行是执行视图，不是暴露声明。

**判据**：wire 碰撞反例（同一装配内 `a.b` / `a__b` 并存的拒绝）、协议序列化与清单同源
审计、模型协议类型不进通用端口的类型耦合审计。

**不做什么**：不改名 `capability_to_wire` 后保留同一套反推；不为兼容性保留「精确匹配
优先」这条回落；不把消歧做成前端展示层的责任。

### D-445 描述与执行同源装配，清单只认本轮暴露集合

**判定：一次装配、两个读视图，禁止两份独立注册事实。**

执行视图（端口名 → 提供者身份、执行体）与描述视图（说明 / 参数 Schema / 风险声明 /
暴露标记）由**同一个插件在同一次作用域收集里**产生；`register_tool` 一次写入两行、
共用一份 `CapabilityMeta` 与一张有序表。一个插件可让多个端口绑定共用一个执行体，
无须为每个工具再造一种接口。

**裁决**：

1. 工具清单 = **显式暴露 ∩ 当前作用域允许 ∩ 有效绑定**，保持注册顺序（D-057）；
   孤儿描述行（有描述、无执行体）不进清单，纯投影 / 簿记贡献不按 D-324 制造假债。
2. 模型返回的调用**只认本次实际暴露的集合**：未知 wire 名、无效参数、未暴露名称一律
   失败事实，**不回落宿主路由**、不回落任意端口。沿用已有配置、调用事实记录映射与
   绑定身份。
3. 端口收集**按端口键判重**：同一键两绑定当场指名冲突，不 `insert` 覆盖；session 与
   host 的端口集由同一次装配来源得出；删除 `<port:…>` 行名编码反推，行名只作表键。
4. 子 Agent 作用域过滤按族别 / 作用域数据，不依赖能力行的 `cap()`；新端口贡献沿用
   同一套过滤，不另开 `pending` 专用分支。

**判据**：同名绑定冲突反例、描述与执行漂移审计、子 Agent 不泄漏作用域、MCP 变化不误绑
旧调用、空工具集正常回答。

### D-446 逐调用债、调用集合收束、结果归属与审批时序

**判定：模型只提出意图，不执行端口；每个调用独立欠债。**

完整链路：活插件贡献 → 同次收集与校验 → 模型插件投影本次 tools → 模型返回调用 →
校验并记录调用意图事实 → 声明方生成逐调用债 → 义务环派发目标端口 → 结果事实 →
模型插件组装下一次请求。

**裁决**：

1. 每个调用独立欠债，保留调用身份、审批、重试、取消与迟归处理；模型续跑等待**本次
   调用集合收束**，不再等待固定的 `tool` 端口清空。
2. **结果先成为事实，再投影成模型消息**：工具业务失败是反馈给模型的信息事实，
   端口协议失败另行分类；`PortReply` 只作不透明承载，通用端口不绑定模型消息类型。
3. **动态风险必须在副作用之前判定**。`PortOutcome.authz` 是执行体自判的**结论**，不是
   事后补一个字段就获得执行前保护；通用授权机制可复用，但模型 / 工具策略不得重新
   进入环。审批包装的删减以「执行前判定仍在」为前提，不得机械替换。
4. 事实写方归各端口执行体；`plugin-tool` 不再代持 `authz.*` / 结果 / 收束事实的
   所有权。落账幂等不等于外部副作用恰好执行一次（EX-003 同一条纪律）。
5. 迁移期可短期对照注册结果，**不得让旧、新两条执行路径同时生效**。

**判据**：多调用 / 待批恢复 / 部分失败 / 取消 / 重试 / 迟归 / 重放语义保持；审批时序
反例（副作用先于判定的装配判红）；消费面 e2e。

**为什么「调用集合收束」必须新增两格内核数据面**（`core-shape-allow structFields` 的论证，
见 `scripts/arch-shape-audit.mjs`）：原来的谓词只有一格端口名，语义是「这条端口上一笔未收束
的债都不许有」。要让续跑只等**本次调用**的那几笔，就必须能表达「端口 + 一批债 id」——
这两半是**同一个判据的两面**，没有独立变化的余地，所以它们是一个类型的两个字段，不是
两处可分别取值的配置。折不开的理由逐条：① 折成 `(String, Option<Vec<String>>)` 元组塞回
原字段，调用方就得各拼一半，`covers()`（唯一判据）无处安放，判据会散到每个申报方；
② 降成 `pub(crate)` 不行——读它的两侧是环（`symbio-plugin-loop`）与申报方插件，跨 crate。
它补的是**新判据能力**：没有新增世界域名 / 端口名 / 事实名，也没有为某个插件开的口子。

### D-447 门禁收窄：动态端口准入、类型耦合与注册反例

**判定：现有绿灯只证明「旧判据没被破坏」，不证明终态达成。**

`obligation-ring-accept.mjs` 的静态 `DECLARED_PORTS` 白名单要求「加端口先改验收表」，
与 D-440「端口名不进声明表」正面冲突；新增端口不改既有基础模块的硬验收因此落空。

**裁决**：

1. 端口准入判据改读**装配期收集结果**（动态端口集），静态白名单只作漂移对照、不作
   拒绝依据；核心形状 / 门面 / 端口审计同步收窄。
2. 增**类型耦合判据**：通用端口契约（`PortInput` / `PortOutcome` / `PortReply`）与
   宿主 / 环的驱动事实不得出现模型协议类型或模型侧措辞判定。判定面只覆盖通用端口
   契约及传递它的驱动 / 环事实（`PTC-001/002`）；`contract/dialog` 的会话域措辞判定
   `needs_wording_generation` 与 `sdk/projection/transcript` 的转写 → 模型消息转换
   属 ④ 的行为闭包迁移，本轮**未闭合**，不因不在判定面而算作已迁出。
3. 增**动态注册反例**：wire 碰撞、未暴露名称、非法参数、空工具集、同名绑定覆盖、
   子 Agent 作用域泄漏、MCP 变化误绑；每类都有可跑的判据，不靠注释声明。
4. 收口信号 = 消费面 e2e 全绿 + 全量门禁全绿 + 上述反例判据全绿；不为消红放宽判据。

**不做什么**：不把「审计关键词改名」算作迁移完成；不用 `gate --write` 重生成汇总区来
掩盖基线漂移。

### D-448 「转写 → 模型消息」是删掉的，不是搬进模型插件的

**判定：D-447 ② 的清单里那两处 SDK 领域实现，性质不同，处置也不同。**

1. **`sdk/projection/transcript.rs` 的 `From<&TranscriptEntry> for PromptMessage` —
   删除**。查证：它**没有生产读者**，唯一的读者是 `symbio-sdk` 自己的两个测试；请求包
   的消息在 `crates/symbio-plugin-model/src/port.rs` 里现造（`call_{name}_{root}_{idx}`
   的合成键）。也就是说，同一件事有两份实现，且 sdk 那份更弱（`call_{tool}_0` 分不出
   同一工具的第几次调用）。「搬进模型插件」会把这份更弱的实现搬到有正确实现的地方，
   结果是两条规则并存、谁先被调用看路径——那不是迁移，是加一份要漂移的副本。
   **终态**：转写只给事实（条目带 role / tool / text），合成调用键的唯一规则住在组装
   请求那一侧。SDK 不再组装模型消息。
2. **`sdk/dialog` 的 `needs_wording_generation` — 不搬**。它是 `Verdict` **自身理由码
   的派生事实**（只有 `from_context` 那一支要花一次模型往返），两个读者分别是 `compose`
   （要不要生成）与 `session`（这次对外调用算不算一笔端口 `model` 的账）。类型是自己
   这一行的 owner，读口跟着类型走；把判定搬进任一消费者，另一处就得重判一遍，
   而它漂移的形态是两个静默错误：**记了账却没打模型** / **打了模型没账**。
   「机制承担领域实现」指的是一段领域**行为**借住在机制层，不包括领域类型自己的一行
   派生读口——何况 `Verdict` 本就是 `plugin-api` 转出的共享词汇（D-279）。

**判据**：`port-type-coupling-audit` 的 PTC-001 / PTC-002 判红面覆盖那 4 份通用端口
契约；`sdk` 侧不再有 `impl From<…> for PromptMessage`。

### D-449 审批闸门与事实写方：留在端口执行体一侧，不搬进各工具

**判定：D-446 那两条「移交」对本仓的工具面不成立——它们已经在执行体侧了，再拆会造出
第二份判定。**

1. **事实写方已在端口执行体里**。`authz.*` 与 `artifact.added` 由
   `crates/symbio-plugin-tool/src/port.rs` 写，而它就是 `tool` 端口的 `PortExecutor`
   ——D-446 说的「原总代理」在 D-440 那批里已经不存在了。把写方再分给「每个工具的执行体」
   意味着每个工具各自写协议事实，那是同一形状的多份实现。
2. **`GatedExecutor` 保留**，它是**声明式工具的唯一通用闸门**：这类工具没有自己的代码
   （能力由 `PLUGIN.yml` 声明、执行体由收集器给），「连同审批一起迁移」在它们身上没有
   落点——真按字面做，等于让每个声明式工具自带一份审批代码。手写执行体的 `local` /
   `web` 在自己 `route` 的第一段调**同一个** `approval_gate`，判定只有一份。
   D-446 真正要保的是**时序**：判定在副作用之前，`PortOutcome.authz` 是结论不是事后补
   字段——这条由 `crates/symbio-provider-collectors/src/approval.rs` 的端口用例钉着
   （拦下时返回停等载荷且 `authz` 维持放行：停等不是拒绝）。
   **不许变成的形状**：工具执行体内再判一次授权；闸门在副作用之后。

### D-450 参数合法性归执行体，端口只保证「不经手 + 不冒充」

**判定：端口层不做 JSON Schema 校验。「非法参数不误执行」这条验收，落在两条端口保证上，
而判定权在执行体。**

1. **谁判**：`arguments` 的形状是**外部世界**的形状（MCP server 的 `inputSchema`、本地工具
   自己的前置检查）。端口是零世界词的通用契约（D-440），它不知道也不该知道某个工具的
   参数该长什么样。端口层塞一份校验器 = 同一件事两处判定，漂移形态是「校验放行的参数
   执行体拒绝」/「校验拒绝的参数执行体本可以跑」——与 D-445 ③ 反对的「描述与执行漂移」
   是同一个病。
2. **端口保证的两条**：**不经手**（参数原样交给执行体，不解析、不补默认、不把坏形状换成
   `{}`——换成 `{}` 就把「参数不合法」洗成「参数合法但意图错了」，那才是误执行）与
   **不冒充**（执行体拒收即失败事实，`success` 不写 true，正文是执行体的拒收理由）。
3. **不许变成的形状**：端口把 `arguments` 字符串替模型解析成对象；缺参数补 `{}`；
   或把执行体的 `ValidationError` 折成成功。

**判据**：`crates/symbio-plugin-tool/src/port.test.rs::malformed_arguments_reach_the_executor_verbatim_and_a_rejection_never_claims_success`
——合法参数报成功（正向对照）、JSON 字符串与缺失参数都原样抵达执行体（`Null` 就是
`Null`）、两条拒收都落 `success: false` 且正文是执行体的理由。

### D-466 插件不执行工具：`route` 的第二条执行面删除，闸门只剩一个调用点

**判定：`D-449` 说「闸门留在端口执行体一侧、不搬进各工具」，而 `local` / `web` 各自在
`route` 里又写了一遍判闸 + 造 `PortExecContext` + 拆信封——裁决已下、落地没收干净。**

两个插件的 `route` 分支按**工具名**（`path == meta.name`）直接执行：判闸走同一份
`approval_gate`，但上下文是现造的最小端口上下文（幂等键、会话身份、归属、事实读面
全空）。它与 `port.tool` 的逐调用簿记是**同一工具的两种执行条件**，而仓内没有读者：
`crates/symbio` / `crates/symbio-cli` 只按地址面调 `route`，`tauri` 只有通用入口
`route_v2`，`e2e/cases` 没有按工具名调 `route` 的用例。

**裁决（删除，不重设计）：**

1. `local` / `web` 的 `route` 只保留父容器转发（`path` 以 `/` 开头 ⇒ 交给 parent）与
   `NotFound`；对工具名一律 `NotFound`。
2. 判定与执行体仍是同一份：`register_tool` 在注册收口点裹上 `GatedExecutor`，闸门的
   生产调用点由此收敛到 `GatedExecutor::execute` **一处**。
3. 没声明执行体的路径本来就不该有：新增工具走 `register_tool`，它同时给端口行与工具行；
   「工具行在表里但没人裹闸」这种装配不再可表达。

**判据：** `local` / `web` 各有一条反例用例（`route_does_not_execute_tools_by_name`：
按工具名 `route` 必须 `NotFound`，且执行体一次都没跑）；`approval_gate(` 的生产调用点
只剩 `provider-collectors/src/approval.rs` 一处（`scripts/dynamic-port-registration-audit.mjs`
的 DPR-004 判的是另一条回落，不覆盖本处，故这条由静态读调用点 + 两条用例守）。

### D-468 端口集的载体是装配期容器：端口不借能力行存在

**判定：D-445 的判据一条不动，换的是「执行视图」的载体——端口集不再是一族能力行，
而是本次装配专用的一份收集容器。**

D-445 ③ 说「端口收集按端口键判重」，但那套判重挂在能力表上：`multi("port")` 族 +
`<port:{port}>:{provider_id}` 表键。载体带出两处只有载体才需要的形状：端口身份被编码
进行名（读方不得不反推），以及 `:` 的隐含保留约束（事件 id 的定界与表键的定界撞在一起）。
更要紧的是**表上无法区分端口集与工具目录**：两者同族不同名，于是每个读方（host 的
`gather`、session 的 `turn`、`plugin-tool`、子 Agent 作用域）都得自己再 filter 一遍
`PortPayload::port`——同一遍规则写四份，新增读方就再写一份。这与 D-445 反对的
「两份独立注册事实」是同一个病，只是形态从「两份事实」变成「一份事实挂在错误的载体上」。

**裁决：**

1. 端口集 = 本次装配新建的 `PortBindings`（挂在 `ctx[PORT_BINDINGS]`），条目只有两态：
   `Ok((提供者 id, 执行体))` 或 `Err(冲突说明)`。读口是 `get` / `snapshot` / `bound`；
   写入只走 `PortBindings::bind`——插件的整组端口经 `register_ports`，工具端口经
   `register_tool`，两条都落在同一方法上。容器**每次装配新建**，复用等于把旧绑定带进
   新装配。
2. 判重**加严**而不是持平：同名再登记永久把该键转成不可执行（两方名字都在错误里），
   先到者不「胜出」——两份都可能被派发到，挑一个就是描述与执行漂移；`snapshot()` 任一
   冲突**整份** `Err`，host `gather` 当场返回装配失败。无执行体与冲突同一条路（落错误
   桶、键不可执行），不再有「跳过这一笔」的静默态。
3. 端口集开放：`PORT_FAMILY` 与 `port_row_name` 退场，新增端口不改基础模块这条不变；
   端口名不再进表键，`:` 的约束只剩事件 id 那一条——`check_port_name` 仍在登记期
   fail-closed（D-336），不转义。
4. 作用域前缀在**登记期**套上：`register_ports` 从 `ctx[PORT_SCOPE]` 读前缀，把端口名
   写好再入容器。子 Agent 的作用域代理不再碰端口、不再有 `pending` 配对，
   「`register_tool` 先写端口行后写工具行」的隐含顺序契约一并消失。`register_tool`
   因此从 `(visitor, …)` 改成 `(ctx, …)`：同一次调用写工具行（进 visitor）与端口绑定
   （进容器），两者用同一份前缀。
5. 端口名与工具名同源这条不变：作用域把工具行改名成 `agent_<id>_<name>` 时，绑定用
   同一个前缀，派发按前缀名查得到执行体；前缀为空（系统树）⇒ 端口名原样。

**判据：** `port.test.rs::registration_writes_no_capability_rows`（登记一行能力行都不写
d——这条就是旧载体的反例）、`duplicate_provider_is_loud`（两方指名 + 快照整份 Err +
错误桶）、`provider_without_executor_is_rejected`、`scope_prefix_is_applied_at_registration`；
`scope.test.rs` 的前缀用例；`grep -rn "PORT_FAMILY\|port_row_name" --include=*.rs` 归零；
`dynamic-port-registration-audit` DPR-001…004 仍绿（端口集离开能力表之后，四类反例的
承接体不变：判重、受检插入、清单只认有效绑定、无路由回落）。

### D-469 协议命名的所有者是模型插件：经 route 下发投影，装配方不认字符集

**判定：`D-444` ① 已判「别名是描述数据、装配期算一次」，但规则住在哪里没收干净。**
`capability_to_wire` 仍躺在共享层（`sdk` 定义、门面转出），生产调用点四处：session 装配、
model 的历史消息序列化、tool 的返回解析兜底、门面转发。协议字符集是**模型侧**的知识：
谁把工具清单交给模型，谁就该负责命名；共享层持有它，等于让每个读方都保留一份「名字
怎么变成线上形态」的资格。

**裁决：**

1. 规则唯一实现在 `crates/symbio-plugin-model/src/tool_projection.rs`；共享层的同名实现
   删除（`sdk` 的 `tool_name` 模块、门面转出、对应单测整体搬走）。本仓不再有第二份
   字符集规则，「谁消费别名表」与「谁算别名」是两件事。
2. session 只交**候选暴露集合**（显式暴露 ∩ 作用域 ∩ 有效绑定、已按声明面去重，保持
   注册序），经 `model/project_tools` route 取回 `{ exposed, aliases, collisions }`：
   `exposed` 原样过滤清单，`aliases` / `collisions` 原样写进 `session.config`。会话不认
   `[A-Za-z0-9_-]`，也不做 `_` 替换——它只转发「模型插件说哪些能见、各自叫什么」。
3. 碰撞判据**不动**（`D-444` ②）：投影按 wire 分组，组内 >1 个身份 ⇒ 整组退出
   `exposed` 并把 `{ wire, names }` 记进 `collisions`；整组退出后清单为空时
   `tools_empty_reason` 仍是 `wire_alias_collision`。碰撞反例随规则一起搬到
   `tool_projection.test.rs`，不再留在 session。
4. `plugin-tool` 的返回解析只读本轮 `session.config` 的别名表；删除「按 TOOL 行 ∩
   端口键重建别名表」的兜底——没有本轮快照就落失败事实（`D-444` ③），不自行投影。
5. `model/types.rs` 的历史 `tool_calls` 序列化不再投影：历史里的名字本来就是当时的
   wire 名（对字符集内的名字投影是恒等映射），原样回灌，请求形状不变。

**判据**：`capability_to_wire` 的生产调用点只剩 `plugin-model/src/tool_projection.rs`
（测试与门面转发不计，门面转出本批一并删除）；`collision_rejects_the_whole_group_and_reports_the_reason`、
`a_changed_tool_set_never_rebinds_last_rounds_wire_name` 在模型插件的投影单测里；
`wire_names_resolve_to_canonical_capabilities` 的夹具改读 `session.config` 的别名表
（不再走重建兜底）；`cargo test -p symbio-plugin-model -p symbio-plugin-session
-p symbio-plugin-tool` 全绿。

**不做什么**：不为 route 不可用保留第二份本地投影（投影缺席 ⇒ 本轮无工具，原因记
`projection_unavailable`）；不把别名表挪出 `session.config`——它是本轮快照的唯一载体
（`D-444` ③），模型与工具解析各读同一份。

### D-471 派发清单的载荷键契约挂在哪

> 归属：边四（读侧归位，`D-461`）的第三格——`D-462` 答了产物格（`artifact.added`），
> 本条答**同一问在 `tool.requested` 的 `calls[]` 元素上的答案**。结论与前格同形但**退得
> 更远**：产物格今天接上了判据（`SV-004`），这一格**今天接不上**——不是不想接，是接成
> 会误报。入场的「谁消费」答出来了，「判据怎么守」答不出不误报的机械形态，如实记下。

- **现场。** `tool.requested` 的载荷是 `{ root_id, calls }`，`calls[]` 的元素键是跨插件的
  隐式契约。写方**唯一**（`model` 的 `dispatch_calls`，`crates/symbio-plugin-model/src/port.rs`：
  `json!` 写 `id` / `name` / `arguments`，条件写 `node_id` / `overflow_notice`），读方五个，
  跨四个 crate 与机制层——

  | 读点 | 谁 | 位置 | 读的元素键 |
  |---|---|---|---|
  | ① | 机制层折叠 | `crates/symbio-sdk/src/projection/rebuild.rs` 的 `rebuild`（`group_of_call` / `node_of_call` 两段） | `id`（配 `root_id`）、`node_id` |
  | ② | 会话实时投影 | `crates/symbio-plugin-session/src/transcript/live.rs` 的 `partners` + `remember_request` | `id` |
  | ③ | 工具执行体 | `crates/symbio-plugin-tool/src/port.rs` 的 `read_requested` | `id` / `name` / `node_id` / `arguments` / `overflow_notice` |
  | ④ | 工具轮收束 | `crates/symbio-plugin-tool/src/round_done.rs` 的 `observe` | `id` |
  | ⑤ | 模型逐笔标记 | `crates/symbio-plugin-model/src/port.rs` 的标记派生（`execute` 内） | `id` |

  失效形态与产物格**同一族**：写方把 `node_id` 改名成 `card_id`，`rebuild` 的 `node_of_call`
  读到 `None` ⇒ 工具卡节点身份缺失 ⇒ 实时面那张卡停在 `streaming`（`D-382` ③ 的 t10 现场），
  而「没有 `node_id`」在读侧是**合法**的空值——没有判据会红，也没有日志。`id` 更甚：它是
  产物配对（`artifact.added` 的 `tool_call_id`）、逐笔债标记（`tool.call.requested`）、轮收束
  计数（`tool.calls.done`）的共同身份键，改名即静默断链。

- **一个加重情节：`calls` 不是唯一读 `call.get(...)` 的数组。** `response` 事实的载荷里
  **也有**一个 `calls`（`outcome_payload` 写，元素键与 `tool.requested` 的**同源**——
  `dispatch_calls` 的同一个向量同时喂两处，`port.rs` 的注释「派发清单只有一份构造」），
  **此外还有一个 `tool_calls`**（`outcome_payload` 另写，元素键是 `id` / `wire_id` /
  `name` / `arguments` / `parse_error` / `overflow_notice`——**不同的键宇宙**：`wire_id` /
  `parse_error` 只在 `tool_calls`，`node_id` 只在 `calls`）。`rebuild` 这一个函数里，
  读 `calls` 的两段（①）与读 `tool_calls` 的一段（`call.get("wire_id")`）**同形**：
  都是 `for call in …payload.get("calls"/"tool_calls")… { call.get("…") }`。

- **第一版做法（被否）：把元素键收进机制层当公共词表。** 与 `D-462` 第一版同病——落
  `symbio-sdk` 的 `effects` / `projection` 词汇模块，`EX-007`（`D-247`）当场红：机制层
  认得「工具派发清单有 `node_id` 这一格」本身就是它不该有的业务知识。

- **第二版做法（被否）：从 owner 的清单生成一份元素键词表。** 与 `D-462` 第二版同病——
  生成器只能投影清单里已有的东西，而 `calls` 的元素键今天不在任何清单里（协议五格不登记
  载荷形状，`D-346`；`tool.requested` 只有 `EventDecl`、没有 `FactDecl`）。要生成，先得给
  `PLUGIN.yml` 加一节「派发清单键」，而那一节的唯一消费者是这条判据：**为判据造一份事实源**，
  正是 `D-455` 否掉的形态。

- **第三版做法（被否，今天接不上）：把 `calls` 格并入 `SV-004` 的「写方账本 + 读点对账」。**
  产物格今天能接，是因为它的三个读点（`artifact_nodes` / `changes` 全文 / `turn_input` 的
  `EVENT_ARTIFACT_ADDED` 分支）**各自只读产物格**——按函数 / 分支收窄后，提取的键天然属于
  产物格。`calls` 格做不到：`rebuild` 这一个函数同时读 `calls`（①）与 `tool_calls`（读
  `wire_id`），按函数提取会把 `wire_id` 收进 `calls` 的读点键集，而 `wire_id` 不在
  `dispatch_calls` 的账上 ⇒ **判据误红**；按文件提取更宽。把 `tool_calls` 的键也并进账本
  则是把**两个事实的载荷契约**合成一份——`D-462` 判过「同形异义按文件扫会误判耦合」，
  这里是同一条病在数组维度的复现。**接成就会误报，不接判据空转——两坑之间，今天选
  「如实记下，不接」。**

- **裁决。**
  1. **契约挂在「谁消费」上，先答这一半**：五个读点如上表，写方唯一（`dispatch_calls`）。
     这一半今天就能落进文档与注释，让「写方改名 ⇒ 读方静默读空」的失效形态**有据可查**
     （改 `dispatch_calls` 的人能对着这张表逐个核对自己有没有动五格里的任何一个）。
  2. **判这一半不硬接**：`SV-004` 今天不扩 `calls` 格。接它的前置是**把 `rebuild` 里读
     `calls` 的两段与读 `tool_calls` 的一段拆成各自的函数**（或等价的按段登记机制）——
     那时按函数收窄就能只提取 `calls` 的读点键，`wire_id` 不再混入。**这是下一张入场券**，
     不在本条开工（拆 `rebuild` 是机制层投影面的结构改动，要单独论证，不夹带在「答入场券」
     这一步里）。
  3. **`calls` 这一格不进词表**：`D-462` 已经判过「键的公共家」这条路不通（`EX-007` /
     `D-455` 两堵墙），本条不重审。

- **与 `D-462` 的分界（一句话）。** `D-462` 管产物格，读点天然可按函数 / 分支收窄，判据
  今天接上了；本条管派发清单格，读点函数混读两种同形数组，**判据今天接不成**——同样的

  > 可行，上表五个读点（六个登记函数——②的 `partners` 与 `remember_request` 同文件
  > 各一）全部登记进 `SV-004` 的派发清单格账，取键 12 处全在写方五格账上。「判据
  > 接不成」的退让到此为止，产物格与派发清单格两格的判据都接上了。

### D-472 拆 rebuild 读段的入场券怎么写

## 现场（今天的代码形状）

- `crates/symbio-sdk/src/projection/rebuild.rs` 的 `rebuild` 是三入参纯函数
  （事件切片 + 两份词表，产 `Vec<ChatNode>`）。读 `calls` 的两段与读 `tool_calls` 的
  一段**都是函数体内的局部绑定，不是独立函数**：`group_of_call` 从 `tool.requested`
  的 `root_id` 与 `calls[].id` 折出分组表；`node_of_call` 的主来源是 `tool.requested`
  的 `calls[].id` 与 `node_id`；紧随其后有一段命令式循环，用 `tool_calls[].id` 与
  `wire_id` 以 `or_insert_with` **补写同一张表**。两张表在 `nodes_of` 里合流。
  补写段不按事实种类过滤，只按载荷形状扫全事件。
- 两个数组的 `id` **同形异义**：`calls[].id` 是配对用的 wire id，`tool_calls[].id` 是
  工具卡的节点 id；`node_id` 只在前者，`wire_id` 与 `parse_error` 只在后者。写侧在
  `crates/symbio-plugin-model/src/port.rs` 的 `dispatch_calls` 与 `outcome_payload`：
  `dispatch_calls` 的基础三格由 `json!` 写出，`node_id` 与 `overflow_notice` 是**条件
  追加**的 `entry["…"]`。
- `SV-004` 的实现在 `scripts/shared-name-audit.mjs`：读点按 `fn`、整份文件、
  `match` 分支三种形状收窄，`ARTIFACT_READ_SITES` 今天只登记产物格的三个读点；取键
  正则只认 `payload.get("…")`、`payload["…"]`、`text_of(…,"…")` 这三种**顶层**形状；
  写方账本由 `topLevelKeys` 从 `artifact_payload` 的 `json!` 对象内文读出。

## 一个必须摆上桌的读数

`D-471` 说「拆完按函数收窄就能只提取 `calls` 的读点键」。按今天的实现，这句话**还差
两格**：`calls` 的元素键写作 `call.get("id")` 与 `call.get("node_id")`，不在 `SV-004`
的取键形状里；写方的 `node_id` 与 `overflow_notice` 是 `entry["…"]` 条件追加，也不在
`topLevelKeys` 读得到的 `json!` 对象里。也就是说，**拆读段只买到「按函数收窄后不混入
`wire_id`」这一半**；要让判据真的接上 `calls` 格，还得扩两种取键形状。

## 既有约束（本条不重审）

- `EX-007` / `D-247`：机制层不认业务键名，元素键不收成公共词表。
- `D-455`：不为判据另造一份事实源。
- `D-462`：登记范围是函数 / 分支，不是整份文件；一个事实只有一个 owner。
- `D-463`：读可以跨插件，折不能跨插件。
- `D-471` 裁决 3：`calls` 这一格不进词表。
- `crates/symbio-sdk/src/projection/rebuild.test.rs` 的确定性用例
  （`rebuild_is_deterministic` 与 `rebuild_with_mutations_is_deterministic`）要求
  同输入逐字同输出；`scripts/shared-name-audit.test.mjs` 的产物格回归用例盯的是
  读点恒真与写方改名。

## 裁决

1. **拆，边界按数组分。** `rebuild` 一个函数体里混读 `calls`（`tool.requested` 与
   `response`，同源键宇宙）与 `tool_calls`（另一个键宇宙）——两张表同形、`id` 同形异义、
   补写段不按事实种类过滤，**这一个函数装着两种载荷契约的读法，本身就是职责失守**。
   拆分的理由是这条**结构裁决**，独立于判据是否接得上而成立——不是「结构服从判据」，
   `D-455` 的纪律没有被动用。函数边界**按读的数组分**：读 `calls` 的段归一处（不分
   事实种类——两处 `calls` 同源同键宇宙），读 `tool_calls` 的补写段归另一处；
   `node_of_call` 的后置补写语义（`or_insert_with` 不覆盖）在拆出的边界上**显式表达**
   （返回值或第二次合并），合并顺序保持今天的语义（先折 requested 表、后补写），
   两个确定性用例是回归闸门——同输入必须逐字同输出。
2. **扩，同批扩两种取键形状。** `SV-004` 在**已登记的函数体**内补认两种键：① 元素键
   （循环变量 / 局部绑定上的 `call.get("…")`）；② 写方的条件追加键（`entry["…"]`）。
   **登记范围仍是函数 / 分支的闭集**（`D-462` 不破）——扩的是「函数体内键的取法深度」，
   不是收窄单位；正因为拆完后 `calls` 读点各归各的函数，函数体内提取的元素键才天然
   只属于 `calls` 格，不需要判据去做控制流分析（走法乙的死因不复现）。
3. **拆与扩同批。** 只拆不扩，收口时判据仍接不上 `calls` 格——那是一个半成品批次；
   只扩不拆，扩出来的形状要在混读的函数体上工作，必误收 `wire_id`。两半互为成立条件，
   **一个施工单元，一批做完**。`D-471` 的「不夹带」按裁决的纪律不按批次：它不夹带的
   是「答入场券」这一步，本条是裁决后的完整施工单元，与摘账批次「取字改走门面 +
   同批下调基线」同一条分批逻辑。

## 走法备查（裁决前的讨论稿保留）

## 一句话张力（裁决前的问法）

「装配变成数据贡献」在**贡献面**今天已经是事实：session 交出去的全是数据行，它不
贡献能力。剩下没变的是 `turn.rs` 里那段**自己的**开轮编排——它不是对环的贡献，
而是写自身存储的调用点。于是「由 loop 侧接住」这句要先答：接的是**贡献面**（已经
接住了），还是**开轮这段编排本身**（那会同时碰到 `D-458` / `D-459` 判「存储与
地址面随身份留下」，以及 `SRA-004` 盯的「事实源开面恰好一家」）？两者混在一句
exit 里，「还差什么」就永远读不清。

## 裁决

1. **出口问的是贡献面——而它已经成立。** 「装配变成数据贡献」在 `D-440` 之后就是
   今天的现场：session 贡献出去的全是数据行，turn 钩子里不再有**能力**（工具零条、
   端口零条）。出口里「session 不再需要 turn 钩子」这半句从此读作「不再需要 turn
   钩子里的**能力贡献**」——不是「turn.rs 这个文件消失」。
2. **开轮编排是数据面的一部分，随身份留下。** 十步里的写格走的是 session 自己的
   存储开面，存储不能换 owner（`D-458`：会话记忆与存储是会话数据本身）；装配在
   身份上依附开轮（`D-457`：幂等键与 `produced_by` 都从它派生）。把编排搬去任何
   一方，都是在搬**已经判过随身份留下的数据面**。`turn.rs` 自己编排自己存储的写
   入，就是「数据面随身份留下」的形状——**边二没有可施工对象，不登记任务**。
3. **拒绝「甲 · 把开轮表达成环的行数据」，理由记档。** 按最终目标态与架构简单度
   两条标准：① 甲要给十步里没有事实可读的步**新增事件格**——机制变更，且那些步
   写的是 session 自己的存储，环要执行就得经 `drive_entry` 写进 session 的存储
   语义，「loop 认得 session」只是换了写法；② 编排知识并没有消失，只是被重编码成
   第二份表示（行数据 + 环的解释执行）——**同一份顺序知识两处持有**，恰是
   「一个事实一个 owner」反对的形状；③ `D-445` 不许两条路径并存，而行数据执行
   与 turn 钩子在过渡期必然并存。乙（整单元搬进 loop）撞 `D-457` 与 `SRA-004`
   的唯一登记点；丙（只折 `session.config`）被 `D-457` 判语法上不成立；丁（宿主接）
   被判控制面知识往上堆。四条都有墙，且都比现状复杂。
4. **`D-451` 的表就地修正一处**（与 `D-456` / `D-457` / `D-459` / `D-460` 同法）：
   边二行状态「未界定」改为「**闭合（D-473）**」。施工边（二）与两条改判边
   （一读数 / 三验收条件）就此全部定性完毕：**退役线从此没有施工边**，只剩符号
   冻结账守成（只许降）与边四读数线。`D-081` 的三问验收式不变——
   下一次任何一边被动到时照跑，本条没有施工，无须重跑。

## 一句话张力（裁决前的问法）

「冻结账守成」登记成一个 `doing` 任务，读出来像「这条线正在推进」；实际上它的每一格
进度都由别的施工批贡献，任务文档只负责「记得有这条账」。可是「记得」这件事判据已经
做了——账本文件在门禁里、复核日写在 `expires`、保留依据写在 `retire`。一个既无施工
面、又不承担记忆职责的 `doing` 条目，就是 `D-451` §3 反对的「以后再说」的假计划，
只是换了个方向：不是「写不出入场券就登记」，而是「施工面写完了，任务却赖着不走」。

## 裁决

1. **无施工面的守成线不占任务账。** 判据能自守的账，不需要任务文档当容器。任务账
   的条目必须有可执行的动作；守成动作（跑门禁、看读数）不属于任何一条任务，属于
   每一次施工批的收尾纪律。
2. **冻结账的主人换成裁决号。** `knife` 从持刀任务号改指 `D-460`——保留依据、
   复核日（2027-06-30）与「随身份保留」的定性都由它给出；裁决不随任务收口消失，
   比「主人是个已删文件」稳定。`SRA-003` 的通道本就为此预留，判据逻辑零改动。
3. **持刀任务按 RG-031 收口删除。** 两份任务文档的结论早已住在判定与设计文档里
   （`D-451` / `D-456` / `D-458` / `D-459` / `D-460` / `D-473` 与各自的施工批决策），
   删文档不删知识；任务索引随登记投影自动收敛。
4. **复核机制不变。** 2027-06-30 复核日是 `SRA-003` 盯着的日期，不是任务清单上的
   到期项——到点重新裁决的是账的定性（`D-460`），本条只裁决「谁持有它」。

## 不做什么

不动豁免账的符号面与判据逻辑（`session-retire-audit` 只改夹具字面量与真实账的
`knife` 一处）；不把「跑门禁」「复核豁免账」登记成新任务；不提前删除或续期冻结账
