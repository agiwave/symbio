# 登记与汇总机制

本文定义文档登记、引用、状态、依赖与自动汇总机制。字段形状归
[文档字段规范](../005-spec/001.md "SP-001")，文档职责归 [文档中心](../README.md "docs/README")，判据码归
[RE-008-判据码登记表](../004-ref/GATE_CODES.md "RE-008-判据码登记表")。

## 1. 内容归属

| 内容 | owner | 规则 |
|---|---|---|
| 长期规范与通用约束 | `spec` / `design` | 写规则、边界与理由，不写施工过程 |
| 待办与验收任务 | `task` | 写输入、出口、状态和证据 |
| 实现细节 | 代码 | 目录、符号、算法和性能优化以代码为准 |
| 历史过程 | `git log` | 搬迁、被否方案、实测记录和阶段收口不进入现行规范 |

不建立架构决策编号、决策账本或判例登记形态。设计理由必须能由当前规则理解；失去现行
约束力的历史不因“曾被引用”而留在活跃文档中。

## 2. 文件即条目

每篇活跃文档以 front-matter 登记，文件本身就是条目，不设第二处登记表。

- front-matter 使用受限 YAML 子集；未知字段、重复字段和非法形状必须判红。
- 文档编号在登记集中唯一，`kind`、`id`、`title`、`status`、`created` 为基本字段。
- 文档类 `title` 必须等于首个 H1；文件名与编号关系由字段规范约束。
- `kind` 只来自 front-matter。目录是组织方式，不参与种类判定；移动文档必须同步身份。
- 目录 `README.md` 的自注册 meta 定义该种类的编号前缀、标签、状态机和必填小节。
- 新增种类必须有目录、meta 和回归测试，不新开脚本命名空间或判据码命名空间。

状态只写在条目 front-matter。总账、汇总页和看板都是投影，不得手工维护第二份状态。

## 3. 引用

### 3.1 只写登记编号

人只写 `[[编号]]` 或 `[[编号|显示文字]]`；显示锚点时写在 `#` 后。站内地址由生成器按
编号解析并重算，不手写文档路径。

引用必须指向存在且唯一的登记编号。生成器只处理可识别的登记引用；外部链接、纯锚点、
代码路径和普通非登记链接不纳入重算。生成与检查分离：写入模式更新派生内容，检查模式
只比对差异，不得静默修复后报告通过。

### 3.2 自描述与生成标记

汇总标记区内不手写内容，标记区外不放手工汇总副本。标记区必须成对且唯一，生成器只改写
标记之间。数据读取失败、表头缺失或条目解析失败必须报错，不得返回空表后继续生成绿灯。

自动汇总不写时间戳、随机顺序或本机路径；相同登记输入必须产生逐字节相同的结果。

## 4. 依赖与分解

`deps` 与 `parent` 表达不同关系：

| 字段 | 含义 | 形状 |
|---|---|---|
| `deps` | 生效前必须闭环的前置义务 | 可跨种类的有向无环图 |
| `parent` | 条目是谁的一部分 | 同种类单父树 |

一个条目最多一个 `parent`。共享前置用 `deps` 表达，不把树形字段变成多父关系。编号平铺，
不把层级、优先级或目录位置编进身份。

依赖必须指向存在的条目且不得成环。`deps` 是硬约束，不能用 `prio` 替代；每条依赖应能
说明前置条目交付的具体产物或口径。

父子状态必须单调：子条目生效时父不得仍未生效，父退场时子不得仍生效。部分完成可以存在，
档位倒挂不得存在。

## 5. 状态与完成

### 5.1 文档类

文档状态只回答“是否现行”：`draft` → `active` → `retired`。`retired` 必须有 `reason`。
实现程度由 `impl` 单独表达，不混入文档有效性。

退场文档只保留简短说明、现行 owner 指向和必要的兼容说明，不保留决策锚点、被否方案或
历史正文。目标规范迁入 active 文档后，原处删除；历史归 `git log`。

### 5.2 任务与规范

任务完成必须同时满足：

- 前置依赖已闭环；
- `status: done` 时 `evidence` 指向可核对的提交、事实或守卫；
- `signal` 已清空；
- 未完成项 `wont` 时 `reason` 说明为何不再执行；
- 规范 `retired` 时 `reason` 说明替代关系。

状态变化只改条目自身。任务不能压过规范；冲突必须修改任务，或按豁免机制登记有清除
任务的例外。

### 5.3 优先级

`prio` 的 `now / next / later` 只排同层顺序，不裁决冲突，也不构成依赖。看板按拓扑序、
优先级、编号确定性排序；缺席优先级不判红。

## 6. 冲突消解

| 冲突 | 处理 |
|---|---|
| 事实与事实 | 按职责表找唯一 owner，改引用方，不投票 |
| 规范与规范 | 合并、退场或用 `supersedes` 指向替代规范；同主题不得两条 active 互相矛盾 |
| 规则与任务 | 任务服从规则；例外必须有理由、执行方和清除任务 |
| 判据与判据 | 一个事实只允许一条权威判据，重复判据按接线错误处理 |

`supersedes` 必须指向存在的规范、不得自指或成环，也不得让两条互相替代的规范同时 active。

## 7. 汇总与守卫

- 登记审计校验字段、编号、标题、状态、依赖、引用与生成标记。
- 看板查询与汇总消费同一登记数据；登记有误时只报错，不输出貌似权威的结论。
- 守卫必须宁红不漏：空输入、漏扫、读不出数据和执行方缺失都不得当作通过。
- 每条机器判据必须有反向用例；允许人工执行的规范必须显式写明理由和执行方式。
- 代码投影生成物由各自生成器负责，不手工复制到登记文档。
- 一次性报告不进入仓库，现行文档不写变更史。

## 8. 接管既有内容

接管任务、散落规范或人工清单时，先确定事实 owner，再按“新定义 → 验证 → 删除旧定义”
完成迁移。新规范与旧定义不得长期并存。

守卫账本的明细由代码计算，规范只写口径和执行方；人工维护的待办写成 task。不得新建
手写汇总表，也不得把“整理文档”本身当作没有可验证出口的任务。
