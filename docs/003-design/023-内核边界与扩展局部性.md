# 内核边界与扩展局部性

> 本文是「架构稳定、横向扩展更强」方案的仓内登记版：先冻结**语法**，把**词汇与行为**
> 交给 owner 声明。判据不是「core 改了几行」，而是**扩展是否触发 core 改动**。

## 1. 一句话模型

**内核只装语法；插件声明词汇；行为由 owner 实现。**

- **语法（封闭）**：Event 信封、Entity×Verb、5 条协议事实、`ActorSpec` 五字段、
  `Pattern` / `Scope`、环求解器、5 个 trait。加入语法要走 ADR，不随功能改。
- **词汇（开放）**：事实名 / 格位、视图名 / 字段、插件 id、路由、装配位、rows、actors、
  ports、能力实例。由 owner 声明，内核只 `seal`。
- **行为（开放）**：投影函数、actor 策略、执行体、工具。由 owner 实现。

## 2. 三个不变量（这才是门禁对象）

1. **扩展局部性**：新增事实 / 字段、视图 / 读数、策略 / 执行体、插件、共享类型这五类
   扩展，`kernel diff = 0` 且 `loop` / `session` **控制面** diff = 0，`seal` 与回放通过。
   后者的口径是：控制面只按**影响类**与**执行顺序**运行，不认识任何能力名；能力名出现在
   这两处即判红（[DE-026](026-能力拆分与影响类.md "DE-026-能力拆分与影响类") D-240，判据 EX-002；控制面里工具名的存量由既有的 SC-006 逐处判）。
   控制面这一半**尚未兑现**：行的执行体还不能由插件绑定（[DE-026](026-能力拆分与影响类.md "DE-026-能力拆分与影响类") §5）。
   迁移提交同一条判据的形态是**不含机制增量**——需要补件时单列一条 `### D-NNN` 的独立提交，
   通用且不含能力名，迁移提交本身只删旧实现与切换绑定（D-247 / `EX-007`）。
   上界同在此处：`Entity` 不变体——能力只产出既有实体的事实（D-244）。
2. **kernel 纯度**：kernel 源码里领域名词 0 个、`crate::plugins` 引用 0 处。
3. **根账本只降不升**：C-003 管内核公共面的 0 消费方 / 单消费方存量，C-004 冻结非内核
   账本条数（270，只许降）；投影类豁免清零（D-186）。

不为「声明数 / 变体数」再加计数器——那是代理指标，扩展夹具才是可执行的判据。

## 4. 什么不做

不建独立的中央 schema 文件；不造 `ProjectionRegistry`；不把 `ActorEntry` 搬进 core；
不全量迁 actors；不新增第二套审计脚本；**不把整个 core 照搬进 kernel**——那不是拆边界，
只是给同一份账本换名字（D-188）。A/B 阶段只搬声明、不搬实现；C 阶段才动实现。

## 5. 封闭语法清单

Event 信封 · Entity×Verb · 5 条协议事实 · `ActorSpec` 五字段 · `Pattern` / `Scope` ·
环求解器（`Decl` / `Pattern` / `owed` / `drive`）· 5 个 trait（Store / Capability /
ModelProvider / VdfsProvider / Registry）。

## 关键决策

### D-177 封闭语法、开放词汇

内核只保留 §5 的语法清单；事实名、视图名、插件 id、路由、装配位、能力族等词汇由
owner 声明，内核只 `seal` 与生成索引。理由：此前把「被两个插件看见」误当成「该进内核」，
导致词汇与语法同寿命，功能每加一项都在动内核。

被否候选：按消费方数决定一切（词汇因此永久留 core）；把 21 个域拆 21 个 crate。

### D-178 owner-local 声明取代中央 schema

声明以 `PluginDeclarations` 为单位由 owner 插件交出，`Builder` 只做扩展口，
`seal` 做 8 条装载检查；内核预置**只有协议五格**。新增视图 / 事实 = owner 文件加一行，
不再改中央 `BUILTIN_*` 表。owner 不是声明上的字段：`declare` 的第一个参数就是交表方，
`Frozen` 逐条记下 `fact_owner` / `view_owner`，`seal` 以「表长 = 清单长」钉住不缺条目
（同一次登记不产生第二处可漂的 owner）。控制面视图的迁移是此条的先行样本。

### D-179 kernel 纯度是硬判据

kernel 源码领域名词 0、`crate::plugins` 引用 0；由 `core-shape-audit` 扩展判据执行。
注释里的 `crate::plugins` 不算引用（判据按代码解析），但不得借此写实现依赖。

### D-180 共享类型归生产者 owner

跨插件共享的类型归**生产者**的域账本 owner；物理位置随消费者数量走：只有一个消费者时
留在生产方 crate 内（消费方经容器路由拿 JSON 形状，不 import 类型），第二个消费者出现时
上移 core 的对应领域模块——C-003 的「≥2 消费方」条件恰在这一刻满足，棘轮因此不构成阻力。
**不存在 `contract` 模块**：让消费方依赖生产者的 crate 与 E-009 直接冲突，那条路已被
[DE-024](024-能力横向扩充的通路.md "DE-024-能力横向扩充的通路") 的 D-192 修订否决。
C-002 过渡期继续拦深引，manifest 记录 owner。投影的**构造器**（`Projection`）是机制，
占根出口；视图类型与投影函数跟消费方走——`spend_ledger` 是第一个样本，
`token_ledger`（唯一消费方 `crates/symbio-plugin-session/src/stats.rs`）是第二个。

### D-181 根账本与装配清单走向生成或消失

`core/mod.rs` 的根导出与 `assembly.rs` 的 id / 清单，最终由 manifest 生成或随 crate 边界
消失；过程指标是「手改次数 = 0」，不是条目数增长。

装配侧的先行样本：每个插件目录的 `PLUGIN.yml` 是 id / 装配位 / 停用性的唯一声明处，
`scripts/facts/assembly.mjs` 把它们投影成 `crates/symbio-deploy/src/lib.rs`，
`symbio/src/assembly.rs` 只是它的门面。加插件 = 建 crate + 写声明 + 代码——装配方与内核都不需要人改；
手改生成区由 `gen-facts --check` 判红（`facts/assembly.test.mjs` 覆盖缺声明 / id 不一致 /
顺序重复三个方向）。

### D-182 新增能力族默认插件本地

六族是共享词汇；新族默认住声明方插件（`CapabilityFamily` 常量 + 载荷类型）。
只有长到 ≥2 个共享消费方时才搬进共享词汇，且按 D-175 的形状走。

### D-183 crate 拆分是后置选项

先模块（`kernel.rs` 门面）后 crate；Phase C 不作为 A/B 的前置条件。拆 crate 的收益是
把 C-002 的文本审计换成 cargo 依赖方向，而不是新增架构层。

### D-184 路由常量随 `fire_hook` 的搬迁走，不在 B3 生成

`ROUTE_*` 不能像 `PLUGIN_ID_*` 那样在 B3 搬去 host：`ROUTE_HOOK_FIRE` 的唯一 core 消费方
是 `fire_hook`（现住 `crates/symbio-plugin-api/src/hooks.rs::fire_hook`，session / loop 共用的机制助手）。
把它搬到 host 的 `routes` 门面会让 core 依赖 host（反向依赖，D-179 禁止）；在 core 里生成又会让加插件
改 core（D-181 禁止）。两条路都破坏既有判据，故剩余路由常量的收尾与 `fire_hook` 的搬迁
同步，归 C（实现搬迁）。B3 的「身份 + 装配清单」部分独立成立，已落。

被否候选：在 core 保留一份私有 `HOOK_ROUTE` 字面量（E-012 看不见的漂移）；
让 `fire_hook` 逐调用点传 route 字符串（7 个调用点只是把同一条地址抄七遍）。

### D-185 内核按文件集划线，门面是模块不是域

内核边界按**声明落点**判定：`symbio_core/kernel.rs` 是封闭语法的唯一汇合口（只重导出、
不拥有声明），它用一行 `core-kernel-files:` 声明哪些文件算内核（Event / Store /
Projection / 环 / 容器与 `seal` / `ActorSpec` / `Pattern`·`Scope` / 五个 trait 的声明文件）。
CS-001（形状）与 CS-004（插件 id 字面量）只量这份文件集；CS-003（零 `crate::plugins`）
仍量全 core——依赖方向是全局不变量，不随内核边界变化。根用 `pub use kernel::*` 平铺，
对外路径不变；`kernel` 不是目录、不成为命名审计的「域」，否则语法符号会被记到一个假
owner 上，依赖图与域前缀表同时失真。

被否候选：(a) 把整本根账本搬进这个门面——词汇与语法混住，域 owner 全丢；(b) 现在就
把 `event/` / `store/` / `decl/` 物理搬进 `kernel/` 目录——大量机械 churn，而 `Projection`
与域 trait 的声明仍散在域里，边界并不因此更真；留给 C 拆 crate 时按文件集抽文件。

### D-186 C-003 收窄必须配一条条数棘轮（C-004）

C-003 只对内核公共面判「0 消费方 / 单消费方」之后，内核之外的根出口**不再受任何判据**——
新增一个共享类型仍可随手进根出口，「加能力就得改架构」会由此悄悄回来。所以同批落 C-004：
非内核根账本条目数冻结在 270（只许降）。两者互补而非替代——C-003 管内核**质量**（每条
出口都得跨出 core 且不止一个消费方），C-004 管其余**体量**（不再增长）。

只冻结条数而不对 `[L1]` 的单消费方域出口再设第二道门：那些条目要搬走必须动实现
（B 阶段只搬声明，§4），再判一次只会把它们逼成豁免账本——C-003 的豁免账本已经证明
那条路会养出空转条目。处置归 C。

被否候选：(a) 让 C-003 继续管全部根出口——正是 D-185 要消除的失真（域词汇被当成
内核语法来判）；(b) 只收窄不加棘轮——留下一片判据真空，而真空比过严更危险（没人看得出
它空了）。

### D-187 `[L1]` 是候选报告，不是搬迁清单

`core-export-audit --verbose` 的 `[L1]` 段（非内核根账本里的单消费方域出口）容易被读成
C0 的工作清单。逐条核过后，13 条里没有一条能按「不改行为 / 不动声明」搬出 core：
**单消费方是结果，不是归属**。命中下列任一条即留根：

1. **配对契约**：出方向与入方向同住。`capability_to_wire` 与 `capability_resolve`
   是同一份线上语法的两半，模块文档把「必须成对」写成硬约束——只搬入方向，
   出方向留在 core，两侧判据当场分叉。
2. **单一统计口径 / 单一机制状态**：类型行为（`SloLatencyView::merge` /
   `FallbackRateView::merge` 的跨会话聚合）、两列共用的 tier 归属、`logger_init`
   的 once-state（日志宏直接读它）、`check_all` 的不变量清单、`creator_ids` 背后的
   注册表——搬走就是把一份口径或一份状态切成两份。
3. **跨 crate API**：`logger_parse_level` / `logger_set_min_level` 的消费方是 `cli`；
   core 不能依赖 cli，cli 也不能持有 core 的日志状态。
4. **闭集词汇 / 签名 / 安全面**：`EMBEDDING_NOOP` 与 `EMBEDDING_LOCAL`、`EVENT_BUS_KIND_SYSTEM`
   与同类事件 kind 是同一词汇面；`EmbeddingError` 是 `EmbeddingService` 的返回类型；
   `text_truncate_bytes` 存在的理由就是让每个截断点走同一把尺；`branch_hide_unselected`
   与两个私有助手同族，单搬要先把它依赖的私有面提成根出口。

C0 的可搬条目因此是 **0**。C 阶段的实质工作只剩 C0.5（`fire_hook` 与 `ROUTE_*`
一起搬，D-184）、C1（actor 策略，跨域部分单独论证）、C2（拆 crate，根账本随边界消失）。
C-004 的「单消费方 13」随之回到它本来的身份：报告——它指出「若 owner 变更，这里要
一起动」的位置，不是待办。

判据面的同批修正：消费方计数按**声明方**认整文件测试模块（`#[cfg(test)] mod <stem>;`），
不再只看文件名。`EventStore` 的唯一消费方是 loop 的测试助手，因此不在清单里（剩 13 条）。

被否候选：(a) 按 `[L1]` 逐条搬——每一项都要先提私有面 / 切口径 / 反向依赖，
与「纯机械」的前提相反；(b) 给 `[L1]` 加豁免账本——C-003 的投影豁免已经证明
空转条目会自己长出来，而 C-004 只需要一条条数棘轮。

### D-188 C2 的抽取单位是依赖闭包，不是文件集

`core-kernel-files:` 的 10 个文件**不是依赖闭合集**。逐文件核过第一层 `use` 之后，
闭包会带进：`plugin/{mod,error,transport}`（`PluginInvokeRequest` / `PluginError` /
`PluginPayload`）· `exec`（`ExecEnv`）· `chat/{chat_node,principal}`（`ChatNode`）·
`vdfs/{context,error,request,change,content,node,access}`（`VdfsRequest` / `Response` /
`Context` / `Error`）· `adapters::LatencyTier` · `view`（`Budget` / `View`）·
`authz` + `governance`（`ActorSpec` 的授权读法）· `present::ReadingSection`（`ChatNode` 的
读数面板字段）。按文件集硬抽只有两种结局：`symbio_core ↔ symbio_kernel` 循环，或把**词汇与
部署表**一起塞进内核（违反 D-177 / D-179）。

C2 因此按**依赖方向**分两步，每步都是一个可编译、可提交的迁移步：

- **C2a（结构层）**：`symbio_kernel` 先装已闭合子集——`event/`、`view/`（`Budget` / `View`）、
  `store/`、`projection/`（只装 `Projection` 构造器，投影函数留 core）、`decl/`、
  `adapters::LatencyTier`（先拆成独立文件）。core 依赖 kernel；`kernel.rs` 门面把这批符号
  改为从 `symbio_kernel` 转出，对外路径仍是 `symbio_core::<符号>`。此步不动任何 trait 签名。
- **C2b（契约层）**：五个 trait 及其**签名类型**按依赖序搬入 kernel（`Capability` /
  `Registry` / `CapabilityMeta` / `CapabilityRow` / `CapabilityFamily`、`ModelProvider` /
  `TurnOutput`、`VdfsProvider`、`Store`（已在 C2a）、`Plugin` / `PluginInvoke*` / `PluginError` /
  `PluginPayload`、`ExecEnv`、`ChatNode`，以及 `ActorSpec` / `Pattern` / `Scope`）。
  `ActorSpec` 的授权读法（`trivial` / `can_*` / `Pattern::for_principal`）改为 **core 侧自由函数**：
  `authz` / `governance` 是**部署表**，不进内核；它们不是语法，而是本机事实（D-099）。
  插件改为 `use symbio_kernel::…`；`symbio_core/mod.rs` 的根账本随条目迁出只降不升（C-004）。
- **判据面**：C-001 / C-002 在 kernel crate 内退化为 cargo 依赖方向（kernel 不能依赖 core，
  也不能 `pub mod` 开域门）；CS-001 / CS-004 的判定根目录是 `crates/symbio-kernel/src`，文件集标记
  只在那个 crate 的 `lib.rs`（core 的 `kernel.rs` 只剩转出，不再持有判定范围）；
  CS-003（零 `crate::plugins`）仍量两个 crate 的全部源码。
- **落地形状**：`ActorSpec` / `Pattern` / `Scope` 的数据面在 `symbio_kernel::actors`；
  读本机部署表的三类动作——平凡值（`trivial_actor_spec`，测试面）、模式派生
  （`pattern_for_principal`）、能力位判定（`actor_can_*`）——是 `symbio_core::actors` 的
  自由函数。宿主 crate 不能给内核类型写固有 impl（orphan），而这正是「数据在核内、
  读法在宿主」所需的形状；`pub(crate)` 出根供插件使用，根账本不因它们增加（C-004）。
- **剩余存量**：`Principal::from_legacy` / `tool_principal` 的工具族前缀表随 `Principal`
  类型进了内核（CS-004 冻结 13 处，见审计脚本的 `NOUN_BASELINE`），清理它需要把这两个
  解析入口也改成宿主侧自由函数；`capability/family.rs` 的家族 id `"model"` 与插件目录同名
  属报出的家族词汇（冻结 1 处）。

被否候选：

(a) **撤销 C2**（最小方案）——放弃 D-183 的唯一收益（把 C-002 的文本审计换成 cargo 方向），
且让「根账本消失」永远停在文件集层面；
(b) **按文件集硬抽**——闭包造成循环依赖，见上；
(c) **瘦内核 + trait 泛型化**——`Arc<dyn Capability>` / `Arc<dyn ModelProvider>` /
`Arc<dyn VdfsProvider>` 在 36 个文件、`CapabilityRow` 与 `Registry` 的签名里被持有；
泛型化/关联类型要改写全部这些公共面并牺牲对象安全与 F1 冻结端口，换来的只是
「kernel 不依赖 plugin / exec / chat / vdfs」——代价是**端口本身变形**，与「内核只装语法」
相反；
(d) **整个 core 照搬**——内核长成第二个大账本，根账本不消失，只是改名。

### D-189 actor 策略按单消费方归 owner，配对与跨域留核

C1 的判定与 D-187 同构，只是对象从「根出口」换成「actor 策略实现」：
**单消费方是结果，不是归属**。逐模块核过生产消费方后，落点如下。

- **搬回 owner（单生产消费方、无配对 / 跨域语义）**：
  - `ScheduleDecider` / `ScheduleFact` / `SCHEDULE_BUDGET_MS` → `crates/symbio-plugin-task/src/task`
    （唯一写方就是本文件的任务转写口）；
  - `SkillCompiler` / `SkillRouter` / `SkillRoute` → `crates/symbio-plugin-loop/src/skill_events`
    （编译与路由成对，仍在同一文件里成对）；
  - `recalled_event` → `crates/symbio-plugin-loop/src/memory_events`（唯一消费方是
    `record_recalled`；`RecallTranslator` 是无状态翻译，不再单独留一个主体类型）；
  - `AutonomousInitiator` / `IntentGate` / `ConationPolicy` / `ConationCandidate` /
    `IntentDecision` / `ApprovedIntent` → `crates/symbio-plugin-session/src/transcript/autonomous`
    （自主层与意欲闸门在同一文件里成对——闸门与自主层同批成对的判据不变）；
  - `render_messages` → `crates/symbio-plugin-loop/src/turn_runner::prepare`（唯一生产调用点是请求装配；
    core 侧那份只剩测试夹具，删除）。
- **留核（命中 D-187 的留根判据）**：
  - `commitment_events` / `commitment_records`：写侧成格与读侧翻译的**配对契约**，
    写方在 loop、读方在 session（D-187 第 1 条）；拆开就是两套配对规则；
  - `control`（`PreemptionDecider` / `EliminationDecider` / `CircuitBreaker` /
    `GateDecision` / `Preemption`）：`PreemptionDecider` 的唯一生产消费方是 session
    收件箱，但 `EliminationDecider` 同时被 session 工具层与 loop 轮末驱动、
    `CircuitBreaker` 是 S09 执行闸的开口——**同一策略面在两个 owner 里扮演不同角色**，
    按 C1 的明文单独论证（本批不动；该遗留已由 D-190 收口）。
- **词汇留核**：`SKILL_TAG` 是 loop 写、session 读的共享词汇（D-177 / D-182），
  行为搬走、常量留下。

判据面：`actors` 只剩 `commitment` / `control` / `spec` / `SKILL_TAG`；根账本只降；
NDC-001 的 `RecallTranslator` 随实现退役（`CommitmentKeeper` 仍在留核的 commitment 里）；
策略测试随实现迁到 owner 的 `.test.rs`（`symbio-plugin-task` 的 `task` / loop 的 `skill_events` /
`memory_events`，session 的 `autonomous`），core 只留授权面与投影面断言。
NDC-001 只查**主体类型名的指称**：`Pattern::Decider` 是 `symbio-kernel` 的封闭语法
枚举变体（`ActorSpec.pattern` 的取值），声明档位不产生到主体对象的边，故扫描先剔除
`Pattern::<变体>` 再判主体名——否则「按裁决者档位跑」会被误读成「持有裁决者」。

被否候选：

(a) **把 commitment 拆成写方留 loop、读方留 session**——两侧各写一份配对规则，
    载荷 `id` 的成对性从此靠两份代码对齐；
(b) **迁 control**——搬任一处都让另一处反向依赖兄弟插件（E-009 / E-013），
    而 `CircuitBreaker` 的 S09 闸门语义还没有单消费方；
(c) **给搬走的策略保留 core 薄壳（`pub use loop::…`）**——core 反向依赖插件，
    CS-003 当场判红，且「策略扩展不触发 core 改动」不再成立。

### D-190 control 按消费方拆三块：抢占归 session、熔断归 loop、淘汰裁决留核

D-189 把 `control` 整体留核，理由是「同一策略面在两个 owner 里扮演不同角色」。
那个理由是**对 `EliminationDecider` 成立**，却被当成整份文件的属性。逐条核过生产
消费方后，跨域与否是**每个策略各自的属性**，不是文件属性：

- **`PreemptionDecider` / `Preemption` → `crates/symbio-plugin-session/src/transcript/inbox`**：
  `spec` / `decide` / `held_event` / `resume_event` / `control_event` 五个生产调用点
  全在同一文件（忙窗判定与空闲落格）。没有第二个 owner ⇒ 单消费方，按 D-189 的
  第一判据归 owner。
- **`CircuitBreaker` / `GateDecision` → `crates/symbio-plugin-loop/src/tools/dispatch/gates`**：
  唯一生产消费方是 loop 的 `external_execution`（`gate`）与
  `derived_facts::record_derived`（`break_event`）。两处同属 loop 一个插件——
  **同插件内引用不产生 E-009 / E-013 的跨插件反向依赖**，故落点就在闸门判据旁。
- **`EliminationDecider` 留核**：这是真的跨两个 owner 且角色不同——写侧裁决在 loop
  `derived_facts::record_elimination`（`spec` / `elimination_event` / `THRESHOLD`），
  读侧翻译在 session `plugin/run_actions`（`verdict_grants_changes`）。而
  `verdict_grants_changes` 是 `elimination_event` 载荷的配对翻译（D-187 第 1 条），
  搬任一侧都要把另一侧切成第二套规则。

判据面：`actors` 只剩 `commitment` / `control`（只装 `EliminationDecider`）/ `spec` /
`SKILL_TAG`；`symbio_core` 根账本删除四个名字（`Preemption` / `PreemptionDecider` /
`CircuitBreaker` / `GateDecision`），只降不升；`PRINCIPAL_REFLEX` 与
`EVENT_CONTROL_OPENED` 升为**生产** `pub(crate)` 根出口——两侧插件各有一个写方，
而 C-002 禁深引域目录。策略测试随实现迁：抢占用例进 `inbox.test.rs`、熔断用例进
loop 的闸门测试，淘汰用例留 core（含授权面与投影面断言）。

被否候选：

(a) **整体留核**——把「同文件」当成「同 owner」。两个策略各自只有一个 owner，
    留下只会让 core 继续为插件的本地策略付维护面，D-189 的明文遗留永远收不了口；
(b) **只搬 Preemption、熔断留核**——熔断同样有唯一消费方（loop），分两批只是把
    同一条判据用两次，不改变任何风险；真正需要单独论证的跨域项只有
    `EliminationDecider`，它已经留核；
(c) **给 core 留薄壳（`pub use …`）**——core 反向依赖插件，CS-003 当场判红
    （同 D-189 候选 c）。

### D-253 扩展层宿主面收成一个门面，控制面不入此列

D-183 把「crate 拆分」定为后置选项，收益是「把 C-002 的文本审计换成 cargo 依赖方向」。
crate 拆了（C2a / C2b），**依赖方向却没有被用起来**：21 个非控制面插件仍在源码里直接写
`symbio_core::`（494 处）、`symbio_kernel::`、`symbio_deploy::`，每个 manifest 都列三到
四行内部依赖。「插件依赖几个架构模块」于是仍由一个偶然事实决定——某段代码当初顺手写了
哪个前缀——而不是由边界决定。`symbio-plugin-api` 依赖 `symbio-core` 更让「插件只依赖
一个宿主面」的收益归零：传递依赖 103 个 crate，其中 `grep` / `ignore` / `notify` /
`tempfile` 与插件毫无关系。

本条的裁决分三件，缺一件都不成立：

1. **`symbio-plugin-api` 是扩展层插件的唯一宿主依赖**，用**白名单**转发：
   `symbio-core` 的 133 个机制符号、`symbio-kernel` 的 115 个语法符号、`symbio-deploy`
   的装配常量。语法与机制分两臂导出，来源在门面上看得见（D-255）。
2. **控制面 `loop` / `session` 不入此门面**，继续直接依赖 core。它们按
   [DE-026](026-能力拆分与影响类.md "DE-026-能力拆分与影响类") 的影响类运行，本来就认识
   宿主的容器概念（`turn` / 幕）；把它们压进门面只会逼出一批「端口形状不说容器词」的
   假豁免，正是 EX-008 要拦的形态。判据因此按**插件身份**分档，而不是一刀切。
3. **两条判据接管这件事**：HS-001 判「非控制面插件的源码（注释外）与 manifest 里
   出现 `symbio_core` / `symbio-kernel` / `symbio-deploy` ⇒ 红」；HS-002 判**机制臂**条数
   **只降不升**（新增一条要配一条决策理由，与 C-004 同一形状）。语法臂不计债，但同样受
   HS-003 管：两臂的每一条都要报得出消费方。

**为什么是白名单而不是通配。** `pub use symbio_core::*` 一行就能让编译通过，但「插件能
看见什么」会重新变成隐式集合——core 的 270 条根账本里任何一条增长都自动成为插件的可选
面，D-177 花了整轮迁移才把词汇从内核里摘出去，通配会一次全放回来。白名单要求每条都能
报出一个真实消费方（与 C-003 同一把尺子），因此它同时是一份**可审的插件契约清单**：
这份清单就是「插件宿主面」的现行定义。其中机制臂 133 条逼近 core 的 270 条根账本，
说明 core 的公开面此前从未按「谁在用」筛过：压缩这一臂就是下一步的活，而不是本轮能顺手
完成的。

**代价说实话。** 本条不把传递依赖从 103 降到 10——插件真用的机制（`submit_object_creator`、
`PluginDir`、`capability_invoke`、`node_build`）都在 core，而 `plugin-api → core` 这条边
因此仍在。收益是**依赖图第一次表达意图**：插件只指向一个门面，门面里每一条都写明消费方，
控制面与扩展层的分界由判据守。要把 `plugin-api` 变成只依赖 kernel，得先把这些机制从
core 剥成独立的 SDK 层——那是下一条决策的活，不是这一条能夹带的。

**下一步的起点（已经量过一次，免得下次从零开始）。** 机制臂的 133 条在
`crates/symbio-kernel/src` 里没有同名定义——它们都要 core 的机制支撑（而语法臂的 115 条
按 D-255 已改从 kernel 直取，换边不改变任何类型身份）。这 133 条的分布是实际体积：98 条按定义
文件落在 19 个域（`dialog` 17 · `plugin` 16 · `event_bus` 10 · `projection` 9 · `vdfs` 8 ·
`authz` 7 · `adapters` 6 · `capability` 5 · `agent` 4 · `creator` 3 · 其余 9 域 13 条），
35 条是域模块的再导出（`capability_*` 一族、`plugin_warn` 等日志宏、`AGENT_ID` / `PATH` /
`WORKDIR` 等 11 个键常量）。所以「让 `plugin-api` 只依赖 kernel」要动的不是这份名单、而是名单背后的
`dialog` / `event_bus` / `plugin::dir` 这些宿主子系统——**不是搬运，是切实现面**。本条把
它记作「下一件事有明确体积」，不记作「还差一步」。

**被否候选：**

(a) **通配转发**（`pub use symbio_core::*`）——见上，把显式清单换回隐式集合，
    D-177 / C-003 的收益一起归还；
(b) **把 `loop` / `session` 也压进门面**——控制面认识 `turn` 不是缺陷，是它的职责；
    压进去只能靠豁免抹平，而豁免一旦按「宿主容器词」开张，EX-008 就没有边界了；
(c) **让 `plugin-api` 只依赖 `kernel`**——插件真用的机制全在 core，那样只能把这些机制
    原样搬一次，得到一个改名的 core（DE-023 §4 已否的同一条路：换名字不是拆边界）；
(d) **反过来把 `plugin-api` 并回 core（两 crate）**——能消掉一个 crate，但消不掉
    「插件直接摸 core 内部」这件事：core 根账本仍是插件的可选面，且 `plugin-api`
    现在承载的端口（`ToolBehavior` / `RowHandler` / `ContextProvider` / `Contributor`）
    会与 core 的机制实现混在同一张公开面上，C-003 再也分不清哪条是给插件的。

**白名单的口径**（三条同源，缺一条就被绕开）：

- **收生产也收测试**（`src/**/*.rs`，`*.test.rs` 也算消费方）——测试验证的是「插件用门面
  能不能做到这件事」，把它排除会让门面的一半没人走。
- **`*.test.rs` 不判直接依赖**（HS-001 跳过）：测试是插件的内部验证，不是它对外承诺的
  依赖面。容器测试要扮演一次「轮次派发」才能验证路由转发，那批符号（`TurnSpec` /
  `TurnDispatch` / `turnstate` / `LOOP_RUN_TURN` …）属于**控制面**的容器概念，白名单里
  没有也不该有；`composite` / `model` 的测试因此从 `[dev-dependencies]` 直接取 core。
  这与 EX-008 对 `*.test.rs` 不判是同一条纪律（D-252：测试可以把宿主词汇摆上桌）。
- **`symbio-providers` 不进门面**：它是**服务实现层**（嵌入推理把 `ort` / ONNX 带进来），
  转发它会把重依赖塞进一个本该轻量的门面，而"用一个具体实现"与"认识宿主契约"是两件事。
  用它的插件（`web` / `model` / `mcp` / `skill` …）仍按普通库依赖它，manifest 里那一行不是
  架构依赖，与 `serde` / `tokio` 同类。**这句话的成立条件是 D-254**：它的 `embedding` 臂
  （`ort` + `tokenizers`）是 `optional` 且默认关闭——`default` 一旦放开，「依赖一行」就等价于
  「链接一套推理运行时」。

- **唯一两个例外是端口签名**：`TurnOutput` / `TurnToolCallInfo` 在 EX-008 里各留一条
  逐名豁免——它们是 `ModelProvider` 的**签名类型**，模型插件必须能命名；D-252 拦的是
  「配置 / 开关类型进能力面」，不是端口签名本身。改名要动 wire，收益只有脚本好看一点。

### D-254 插件胶水层的重臂不默认开启

D-253 把 `symbio-providers` 排除在门面之外，理由是「用一个具体实现」与「认识宿主契约」
是两件事，那一行 manifest 与 `serde` / `tokio` 同类。这句话此前只对了一半：serde 不会
为了一个 derive 拉进一套推理引擎，而 `symbio-providers` 会。它的 `embedding` 臂无条件
依赖 `ort` + `tokenizers`，把这一层的传递依赖从 113 顶到 **168**；而 19 个依赖它的扩展层
插件里，**21 处引用集中在 `DefaultToolVisitor`** 这一个胶水符号上，真正问嵌入的只有
`local` 一个（读 `embedding_unavailable_reason` 写降级原因）。于是「插件只依赖一个门面」
在依赖图上成立、在编译代价上不成立：一个只想要收集器的插件照样链接 ONNX 运行时。

裁决三件：

1. **`embedding` 臂可选**：`symbio-provider-embedding` 声明 `optional = true`，
   `[features] default = []`。
2. **要它的地方显式开**：宿主 `symbio`（能力实现经 `submit_object_creator!` 注册在二进制里，
   关了就是关掉语义检索）与 `plugin-local`（写降级原因）。其余插件照默认拿到的，是与
   `plugin-api` 同一量级的胶水。
3. **HS-004 判这件事**：静态判 manifest——`optional = true` 且 `default` 不含 `embedding`。
   判据不编译，是因为编译判据要在一个 feature 组合上把 155 个依赖重编一遍，代价比这条规则
   本身的价值高一个量级；而这两行 manifest 就是决策的**全部**物理形态，判它们够了。

实测（`cargo tree` 计数，正常依赖）：`agent` **168 → 119**（`ort` / `tokenizers` 离开树）、
`local` 173（该开的开）、只依赖门面的 `notes` 105。插件依赖面因此回到「门面 + 一层胶水」，
而不是「门面 + 一套推理运行时」。**代价**：默认值与直觉相反——新插件若真要用嵌入，要自己
加 `features = ["embedding"]`，否则拿到的是「不可用原因」而不是实例；这条写进本段，是因为
默认关的那一侧没人会主动查。

**被否候选：**

(a) **让插件直接依赖具体的 `symbio-provider-*` 子 crate**——依赖量同样降下来，但把「谁提供
    哪块胶水」变成每个插件各自的版本拼装，且 `DefaultToolVisitor` / `MemoryFile` 这些跨插件
    共用的口径会被拆到不同行上；胶水层作为「一份口径」的存在理由（D-023 的依赖方数量判据）
    就没了；
(b) **`default = ["embedding"]`，让第三方显式关**——默认值就是文档。默认开的那一侧永远
    没人去关，等于没改；
(c) **用编译判据**（`cargo check -p <插件>` 不带 feature）——见裁决三，代价与收益不成比例；
(d) **把嵌入实现挪出本层**——`EMBEDDING_LOCAL` 的注册点必须在宿主二进制里才有效（
    `submit_object_creator!` 是链接期收集），挪走只会把同一份依赖换个位置。

### D-255 门面按来源分两臂：语法直取内核，机制才计债

D-253 的门面是**一块** `pub use symbio_core::{…248 条…}`。这块里住着两种性质完全不同的
东西：115 条在 `crates/symbio-kernel/src` 有同名定义（`Event` / `ViewDecl` / `VfsError` /
`ModelProvider` 这类封闭语法），它们经 core 根的平铺进来；另 133 条是 core 自己的机制
（`submit_object_creator` 的链接期收集、`PluginDir` 的配置 IO、`capability_invoke` 的调用栈）。
一块写在一起的两个后果都是实的：

1. **棘轮的数字失去意义**。HS-002 数的是「门面还剩多少条」，可这个数里 46% 与债无关——
   它只是在数内核本来就有的类型。目标写着「降到 0」，减法里却混着不该减的项。
2. **「这一条为什么给插件」在门面上答不出来**。`Event` 与 `PluginDir` 在同一块里，
   评审看不出哪一条是内核契约、哪一条是宿主机制外泄；也看不出 core 的平铺仍是插件的
   第二条取法（`symbio_core::Event` 与 `symbio_kernel::Event` 同名同物）。

裁决：**门面按来源分两臂**。

1. **语法臂直取 `symbio-kernel`**，115 条按 kernel 的 14 个子模块分组（`event` / `exec` /
   `plugin::transport` / `vdfs::words` …）。`symbio-plugin-api` 的 manifest 因此多一条
   `symbio-kernel`——它直接依赖 6 个 crate，是这条依赖链上最便宜的一环。
2. **机制臂留在 `symbio-core`**，133 条，**这才是欠账**。HS-002 只压这一臂，基线
   248 → 133；语法臂不进棘轮，但仍受 HS-003 管（两臂的每一条都要报得出消费方）。
3. **不扩 kernel 的根**。语法臂写子模块路径而不是往 `kernel/lib.rs` 加 115 行 `pub use`：
   kernel 根现在只导出 10 个符号，它是「封闭语法的最小承诺」，扩根等于把全部子模块升成
   语法面，CS-001 / C-003 对内核形状的判定会连同边界一起失效。

**收益是可判的。** 从今天起「插件宿主面还欠多少」就是 HS-002 打出的那个数（本条落地时 133，
[D-256](#d-256-纯契约迁进内核机制臂-133--115) 之后 115），减一条降一条；而「语法能不能只从 kernel 取」不再是一个待议问题，它是编译结果——
`plugin-api` 若再写 `pub use symbio_core::{Event}`，`Event` 会同时有两条来源，评审一眼可见。

**代价说实话。** 这条**没有**降低任何插件的传递依赖：`plugin-api → core` 仍然在，103 个
crate 一个不少（D-254 只摘掉了 `ort` / `tokenizers`）。本条买到的是**账本的准确性**：
它把「要不要让门面只依赖 kernel」从一句口号，变成 133 这个可以一条条往下减的数。

**被否候选：**

(a) **115 条留在机制臂里，靠注释标出来源**——注释不是判据。HS-002 数的仍是 248，
    下一个人看不出哪些能减、哪些不能，与本次改动前没有区别；
(b) **往 `kernel/lib.rs` 平铺这 115 条，门面写一块 `pub use symbio_kernel::{…}`**——
    见裁决三：kernel 根从 10 条涨到 125 条，等于把「封闭语法的最小承诺」换成 core 的
    镜像，而 `core-export-audit` 的 C-003 / C-004 正是按「根账本」判形状的，判据会一起失真；
(c) **`pub use symbio_kernel::*`**——与 D-253 否通配同因：把显式清单换回隐式集合，
    内核任何一条新导出都自动成为插件可选面；
(d) **把 133 条机制里的「纯契约类型」先搬进 kernel**（`dialog` 的 17 条、`adapters` 的端口
    trait 等）——方向对，但那是**改谁的边界**，不是**改门面怎么导出**，混在这一条里会让
    两种回退单位消失。它单列为下一条（`dialog` 是首选：303 行里没有一个实现）。

### D-256 纯契约迁进内核：机制臂 133 → 115

D-255 的被否候选 (d) 说「把机制臂里的纯契约类型搬进 kernel 方向对，但那是改边界、不是改导出
方式，单列一条」。这一条就是它。两个对象都量过：`dialog` 303 行里**没有一个实现**（请求 /
出参形状、一个闭集枚举、九个理由码常量）；`PromptMessage` 是 `LlmAdapter::generate(tok,
&[PromptMessage])` 的**入参形状**——它是 adapter 端口的签名类型，与 `TurnOutput` 是端口出参
同一类，而不是 core 的机制。

`dialog` 卡在一个依赖上：`DecisionPlan.messages: Vec<PromptMessage>`，而 `PromptMessage` 原先
住在 core 的投影树下（`projection::transcript`）。所以顺序是**两步**，各自可独立回退：
`PromptMessage` 先进内核，`dialog` 再整块搬。

裁决三件：

1. **`PromptMessage` / `PromptToolCall` 住 `symbio-kernel` 的 `llm` 模块**（`llm/
   prompt_message.rs`）。`transcript.rs` 只留 `From<&TranscriptEntry>`——「从一条转写行构造出
   一条消息」是**投影的知识**，不是模型的词汇；形状与构造分处两个 crate，正是语法 / 机制的
   分界线。「内核文件集」标记（CS-001 / CS-004 的判定范围）同步收录这个文件。
2. **`dialog` 整块住 `symbio-kernel`**，模块头从「为什么在 core」改写成「为什么在 kernel」：
   准入判据仍是 D-023 的「依赖方 ≥ 2」（`session` 发起、`classify` / `compose` 消费），但共享层
   里它属于**语法**那一半——判它有没有资格待在内核的尺子只有一条：加字段是数据变更，
   加一条「这一轮走哪条路」（`Verdict` 的变体）才是机制变更。测试文件随模块一起搬
   （`dialog/mod.test.rs` 断言的是理由码**字面值**，那是线格式契约，与它住哪个 crate 无关）。
3. **core 根继续平铺这 17 条**（平铺本身由 D-257 撤掉），控制面 `loop` / `session` 的 import 面不动；门面改从内核取，
   **机制臂 133 → 115**，HS-002 基线同步下调到 115。C-004 的非内核根账本条目数因此**不变**
   ——迁的是符号的定义处，不是它能不能出现在根上。

**为什么 core 根的平铺不一起撤。** 撤掉它要动控制面三个插件的 import 面（`plugin-loop` 里
8 处 `symbio_core::PromptMessage` 一类），而这一步的收益是「依赖图更干净」，不是「门面的债
更少」——两件事的回退单位不同，混在一批里就再也分不清是哪一件坏了。先让门面指向内核
（可判、可棘轮），再单独撤根平铺。

**代价说实话。** 插件传递依赖一条没少：`plugin-api → core` 这条边不动，103 个 crate 仍在。
买到的是两件事：机制臂里 18 条不再需要 core 的机制支撑（它们本来就不需要，只是过去没地方去），
以及「让门面只依赖 kernel」的距离从 133 条缩到 115 条——剩下的每一条都能报出它指向的宿主
子系统（`PluginDir` 的配置 IO、`EventBus` 的订阅表、`capability_invoke` 的调用栈、`principal`
的授权表），没有一个还能靠「它其实是纯数据」蒙混过去。

**被否候选：**

(a) **先搬 `dialog` 再补 `PromptMessage`**——编译不过：`DecisionPlan` 的字段类型在 core，
    而 kernel 不得依赖 core（依赖方向颠倒）。顺序由依赖决定，不由工作量决定；
(b) **把 `DecisionPlan.messages` 改成 `Vec<ChatNode>`，绕开 `PromptMessage`**——本模块的请求
    还会被网关原样转发给仓外调用方（`gateway/server.rs`），改字段类型是**破坏性 wire 变更**，
    而收益只是少搬一个 40 行的类型；
(c) **`PromptMessage` 留在 core，只搬 `dialog` 的一半**（`DecisionPlan` 留在 core）——一个契约
    拆成两处住，`DecideOutcome::NeedsModel` 引用 `DecisionPlan` 就会让 kernel 反向依赖 core；
(d) **顺手把 `adapters` 的端口 trait（`LlmAdapter` / 部署令牌）也搬进内核**——那是**机制**
    侧（令牌签发是部署策略，且带 `async_trait`），与本条的「纯契约」不是一类；混进来会让
    这一条的回退单位消失，也把 CS-001 的 trait 格数一起推高。

### D-257 撤掉 core 根对内核符号的平铺：一个符号只有一个可写名字

D-256 把 `dialog` 与 `PromptMessage` 搬进内核时留了一句话：「core 根继续平铺这 17 条，控制面
的 import 面不动」。那是**迁移期的便利**，不是边界——它让同一批符号在 `symbio_core::Verdict`
与 `symbio_kernel::dialog::Verdict` 两处都写得通。留下的后果是可测的：

- 控制面 19 处 import 里，写哪个前缀取决于当初谁顺手写了哪个（`compose.rs` 走
  `symbio_core::{ComposeRequest, …}`，同目录的 `port/classify.rs` 也走 core，而
  `plugin-classify` 已经走门面的语法臂）；
- C-004 的**非内核根账本**里因此混进 19 条内核语法：那张账本数的是「core 的共享类型还剩多少」，
  一旦它同时数内核的类型，数字就不再回答它自己那个问题；
- 更根本的一条：门面已经把语法臂指向内核（D-255），core 的根却继续出一份**副本清单**。
  两份清单可以各自漂移——内核加一个 `Verdict` 变体、core 根的清单不必动，编译器不会说话。

裁决三件：

1. **根平铺撤掉**。`crates/symbio-core/src/lib.rs` 不再 `pub use symbio_kernel::…`。控制面按
   `symbio_kernel::dialog::{…}` / `symbio_kernel::llm::{PromptMessage, PromptToolCall}` 直取；
   core 内部（`adapters` / `prompt_fidelity`）同样走内核路径，`transcript.rs` 只留
   `From<&TranscriptEntry>` 那条投影知识。
2. **域模块的镜像转发不动**。`chat/mod.rs` 的 `pub use symbio_kernel::chat::chat_node::*;` 这类
   转发保留：它续的是**域路径**（`symbio_core::chat::chat_node` 在 core README 的域登记表里写作
   「主题命名空间」），而根平铺没有域语义——`symbio_core::Verdict` 说不出它属于哪个域。判据因此只判
   根 `lib.rs`（C-005），一句话可核：**根上只出 core 自己定义的东西**。
3. **账本随之下调 343 → 324**，HS-002 的机制臂不动（它数的是门面，不是 core 的根）。那 19 条
   不是「清偿了 19 条存量」，是**本来就不该记在这张账上**——与 D-191「拆 crate 让 `pub(crate) use`
   浮上台面」同一性质的口径修正，方向相反。

**代价说实话。** 21 个文件、约 40 处 import 改了前缀，控制面的 `use` 行因此长了一截
（`symbio_kernel::dialog::` 比 `symbio_core::` 长 6 个字符）。买到的是一条**可判的边界**：
「core 的公开面」从此不含内核语法，C-004 的数字回到它自己的问题；内核新增一个契约时，
消费方在编译期就被指到 `symbio_kernel`，不存在第二份可以忘记同步的清单。

**被否候选：**

(a) **连域模块的镜像转发一起撤**（`chat/mod.rs` / `event/mod.rs` / `store/mod.rs` 等 20 处）——
    那会把控制面与 core 内部的 `symbio_core::chat::…` 路径全部改一遍（百余处），而收益只是
    「core 一次都不出现 `symbio_kernel::`」。镜像转发是 core README 域登记表里的域路径，与根平铺不同类：
    它保留**域归属**，根平铺不保留；两件事的回退单位不同，混在一批里分不清是哪一件坏了。
(b) **给控制面留 `pub(crate) use` 走 core 内部路径**——跨 crate 不可见，编译不过：控制面是
    独立 crate，同一条依赖只能写成 `pub`。
(c) **让控制面也走门面**——控制面按 [DE-026](026-能力拆分与影响类.md "DE-026-能力拆分与影响类")
    不入此列；D-253 候选 (b) 否的就是这条，压进去只能靠豁免抹平。
(d) **保留平铺但在根上加注释说明「这是重定向」**——两个可写名字仍在，注释不参与编译，
    漂移照旧发生；判据也无从写起（注释不是形状）。

### D-258 插件可依赖的机制层独立成 crate：`symbio-sdk`

D-253 的代价段写过一句话：「要把 `plugin-api` 变成只依赖 kernel，得先把这些机制从 core
剥成独立的 SDK 层。」这一条落地它，但**判据不是「底层」而是「认不认容器概念」**：

| 层 | 收什么 | 判据 |
|---|---|---|
| `symbio-kernel` | 形状、闭集、线格式常量 | 没有一行实现 |
| `symbio-sdk` | 配置 IO、事件总线、地址装配、构造器登记、日志、协议键、文本与时钟 | 有实现，但只碰内核词汇与自己的表 |
| `symbio-core` | 主体策略、轮次编排、装配与校验、能力调用栈 | 认识容器概念（`turn` / `Session` / 幕） |

判据为什么用「认不认识容器概念」而不是「谁在用」：`vdfs_watch_changes` 与
`turnstate` 都**有实现**，前者只对地址与变更说话（SDK），后者描述的是**一轮**（core）。
用「谁在用」分，`plugin-loop` 与 `plugin-session` 会把两边都拖进来；用「说的是什么」分，
一条符号落在哪层是可以逐条复核的。

**第一批搬走 7 个域**（它们在 core 里对其它域**零依赖**，是依赖图上的叶子）：

| 域 | 行数 | 门面里的条数 |
|---|---|---|
| `vdfs`（地址装配 / 上下文 / 变更监视） | 635 | 10 |
| `event_bus`（订阅表 / 信封 / 重同步） | 641 | 10 |
| `keys`（协议键常量） | 182 | 12 |
| `creator`（构造器链接期登记） | 206 | 4 |
| `logger`（四个宏与级别闸） | 225 | 4 |
| `text`（安全截断 / 巩固合并） | 225 | 2 |
| `clock` | 25 | 1 |

**第二批搬走 5 个域**（按依赖序自底向上：先零依赖的 `adapters` / `chat`，再 `llm`、
`plugin`（配置 IO，依赖已进 SDK 的 `keys`）、`capability`（调用栈））：

| 域 | 内容 | 门面里的条数 |
|---|---|---|
| `plugin` | 配置文件的读写、插件目录扫描、`impl_config_mount_vdfs!` 宏 | 16 |
| `capability` | 能力模型 / 选项 / 提示 / 名字归一 / VDFS 根 / 失败类别 | 14 |
| `adapters` | `LlmAdapter` / `ProviderLlmAdapter` / 增量汇 | 6 |
| `llm` | 帧原语与短 id（`llm/turn` / `llm/frames`） | 3 |
| `chat` | `ChatNode` 转写、`ChatRequest`、`Principal`（三个子命名空间 + 主体常量） | 6 |

**第三批搬走 2 个域**（它们与已搬走的两批不同：不是叶子，但依赖的只有已进 SDK 的 `keys`
与内核词汇）：

| 域 | 内容 | 门面里的条数 |
|---|---|---|
| `agent` | Agent 包的四字段授权声明与判定（`AgentPermissions` / `AgentScope` / `agent_perms_of`） | 4 |
| `embedding` | 嵌入服务抽象层（`EmbeddingService` trait 与服务 id） | 2 |

**裁决五件：**

1. **新 crate `symbio-sdk` 只依赖 `symbio-kernel`**。它的 manifest 里出现第二个 Symbio
   crate（尤其 `symbio-core`）就说明又有机制不是「插件能用的」——那条该留在 core。
2. **core 的域目录改成转发桩**（`pub use symbio_sdk::<域>::*;`）。域目录是
   `core-naming-audit` 与 core 的 README 里那张域登记表的核对面（N-004），一个域不能因为「实现搬走了」
   就从表里消失；`symbio_core::text::…` 这类控制面路径也不必跟着搬。
3. **门面按来源分三臂**：语法（kernel，134）· SDK（108，**不计债**）· core（115 → 72 → 25 →
   19 → **6**，欠账）。HS-002 的基线随批次下调（115 → 72 → 25 → 19 → 6），只数 core 那一臂；SDK 臂与语法臂
   一样受 HS-003 管（每条都要报得出扩展层消费方）。判据读白名单的**两种排版**（花括号组
   与单名一行）：只认前者时，一条 `pub use symbio_kernel::view::Budget;` 就能让
   HS-003 整条绕过去——一行、无逗号、无人注意，正是空转条目最爱藏的形状。
4. **HS-001 的禁用清单加 `symbio-sdk`**（manifest 与源码前缀）：插件仍然只认门面。
   SDK 公开是为了「门面背后能取到它」，不是为了「插件可以绕过门面」。
5. **日志宏的调用点改走持有者的路径**：`#[macro_export]` 宏挂在定义 crate 的根，定义搬进
   SDK 之后 `symbio_core::plugin_warn!` 不再存在。控制面与插件共 162 处改成
   `symbio_plugin_api::plugin_warn!`（门面转发），provider 侧 3 处改成
   `symbio_sdk::plugin_warn!`。core 的根**不**转发这几个宏——同一个名字两个可写路径正是
   C-005 拦的形态，宏不因为它是宏就例外。

**这一批之后剩下的 19 条，形状与障碍见 D-259**：那 19 条不是同一类，逐条判下去之后
门面只剩 `authz` 4 条与 `actors` 2 条——它们读授权矩阵与履约环，按判据该留。

**代价说实话。** 传递依赖仍有一条（`plugin-api` 经 core 拿剩下的 6 条），crate 数从
5 个变 6 个，`cargo` 图深了一层。买到的是三件事：① 109 条机制**不再需要 core 的支撑**，
它们是真正的「插件能用」而不是「宿主内部恰好公开」；② 判据从「机制臂只许降」变成
「core 臂只许降」，而 SDK 臂的存在让「哪一半是欠账」在门面上直接可读；③ 每一批的
依赖序是量出来的，不是按文件大小猜的。

**被否候选：**

(a) **一次性搬完 115 条**——`authz` 依赖 `governance`、`projection` 依赖 `event`/`view`，
    全部一起动等于把 core 的依赖图重排一遍，编译错误会同时来自十几个方向，分不清是
    「搬错层」还是「漏了 re-export」；分批按依赖序走，每一批都能独立回退。
(b) **只搬「插件用得最多」的几条**（`capability_invoke` / `node_build`）——那会把一个域
    拆成两处住（`capability` 的类型在 core、函数在 SDK），比不搬更糟：层归属从此说不清。
(c) **让 `plugin-api` 直接依赖 `symbio-sdk` 的模块路径**（`symbio_sdk::event_bus::…` 透传）——
    门面就退化成编译器插件，HS-003 的「每条都要报得出消费方」无从判；白名单必须逐条列。
(d) **把 `symbio-sdk` 并进 `symbio-kernel`**（少一个 crate）——内核的判据是「没有一行
    实现」，`event_bus` 的订阅表与 `vdfs` 的 root 表都是状态；并进去会让 CS-001 的
    「封闭语法 trait 数」失去意义，也让「内核可以安全地被任何 crate 依赖」这句话失效。

### D-259 `turn` 不是容器，是信封上的一个字段：`turn` / `projection` / `invariants` 三域下沉，core 臂 19 → 6

D-258 把 19 条留在 core 臂上，理由是三条障碍。这一条把三条障碍逐条量了一遍，结论是
**其中两条根本不存在**，第三条是真的但不是「还没搬」。

**先答那个问题：`turn` 还是架构元素吗？** 不是。它现在的全部含义是内核信封上的一个
`u64`——`Event::turn` 的注释就是「所属回合，N3 按它分桶」，读侧按它分组、写侧按它落值，
**没有任何一处持有或推进它**。D-222 已经做过一次同类降级：幕从编排单元降成身份
（`turn` 端口整组退场、`execute-turn` 改名 `announce-model`）。降级之后还留在 core 的
`turn` 域只剩三件没有生命周期决策的事——按身份交付一份工作包（`dispatch`）、按形状造节点
（`node_build`）、记一笔产物（`facts`）。三件都只碰内核词汇与自己的表。

同一把尺子量另外两域：`projection` 的构造约束（F2）让它拿不到 `Store`，形状是
`&[Event] → 视图` 的纯折叠；`invariants` 是「事件切片 ⇒ 违规清单」的纯函数，跑在导出
的事件序列上也不需要运行时。**「认不认容器概念」的判据从来不是看词里有没有 `turn`,
而是看它要不要持有一个生命周期**——按这条判，三域都该走。

**第四批搬走 3 个域**：

| 域 | 内容 | 门面里的条数 |
|---|---|---|
| `projection` | 纯折叠（`cost` / `calibration` / `reputation` / `readyset` / `transcript` / `branch` / `elision` / `mutations` / `rebuild` / `vocab`） | 9 |
| `turn` | 交付 / 造节点 / 记产物（`dispatch` / `node_build` / `facts`） | 4 |
| `invariants` | 可执行不变量（F4）与网格判据的核 | 1 |

**裁决五件：**

1. **`turnstate.rs` / `turns.rs` 不用先归到 `turn` 域**。D-258 记的障碍是「搬折叠要先把
   这两个文件挪走，否则一个域劈成两处住」——这个前提在三域**一起**下沉时不成立：`turn`
   自己走了，目录跟着整体搬家，`projection/` 里那两个文件与 `turn/` 仍是相邻的两处，
   谁也没劈开。为「目录好看」改域归属是一次所有权变更（动 N-001 的前缀规则与 N-004 的
   登记表），收益是零——它们读的是同一个信封字段。
2. **core 的域目录照旧留转发桩**，`symbio_core::projection::…` / `symbio_core::turn::…` /
   `symbio_core::invariants::…` 三条控制面路径一个字不改；根别名（`check_all` /
   `node_build` / `TASK_CAP` / 七个投影名）也照旧。**搬的是住址，不是归属。**
3. **`test_fixtures` 随 `projection` 走，但 core 只用不拥有**。它给用例提供事件拼写与三张
   词表，`projection` 与仍住 core 的 `actors` / `governance` 用例共用同一份——两份真源会
   让「同一性质两份结论」重演（D-188 抽 `invariants::kernel` 时踩过）。core 侧写成
   `#[cfg(test)] use symbio_sdk::test_fixtures;` 而**不是** `pub use`：私有绑定对后代模块
   可见，用例照旧能写 `crate::test_fixtures::…`，但根公共面不多这一条——多出来会被 C-004
   记成「新占根出口的共享类型」，而它只是 core 借了 SDK 的一份拼写。
4. **SDK 新增 `test-fixtures` feature**（默认关）。生产构建不开它：生产拼写来自各 owner
   清单的生成物，`test_fixtures` 一份都不参与。
5. **HS-005「门面不得依赖 core」仍然不加**。剩下 6 条不是进度条而是边界：`authz` 4 条
   （`principal_of` / `production_matrix` / `CAP_DEFINE_WORK` / `CAP_ASSERT_VERIFICATION`）
   读的是授权表与义务环算出来的**生效矩阵**，`actors` 2 条（`actor_can_assign_work` /
   `commitment_events`）读 `ActorSpec` 的授权字段与承诺环。要让它们下来，只有两条路：
   把「能力名闭集」从义务环里拆出来，或者让 SDK 认识「此刻这个主体能做什么」——
   后者比欠账更贵。判据加得比边界早，只会逼出一条豁免。

**这一批顺带露出的判据裂缝**（都已经修掉）：

- `doc-count-audit` 用 `check_all` 的函数体条数判文档里的数字，路径写死在 core 的
  `invariants/mod.rs`——文件搬走后它读成 `null` 并报「来源读不出来」，这是它自己设计里
  最坏的失败形态（退化成什么都没检查）。路径跟着实现走。
- `extension-vocab-audit`（EX-008）按标识符扫容器词，门面的 `pub use symbio_sdk::turn::…`
  里的**路径段** `turn` 被算成了形状名。判据要拦的是「类型 / 变体 / 字段 / 形参认识容器」，
  一行 `pub use` 哪个都不是。豁免按标识符**精确等值**，所以它只放过恰好叫 `turn` 的那一段：
  同文件里新出现的 `TurnSpec` 之类仍是另一个标识符，照旧判红。
- `schema-audit` 的 `expandUse` 遇到文档注释里写出的 use 片段会指数展开直到
  `RangeError: Invalid string length`（整轮门禁因此红）。加了深度闸：超过 8 层按原样当一条
  路径，交给下游报「指不到」，而不是让判据脚本自己崩掉。
- `doc-link-audit` 的 evidence 缩写表只认识 `symbio_core/`，`symbio_sdk/` 一律判「指不到」。
  改成 crate 目录表（core / sdk / kernel / deploy）。

**代价说实话。** 传递依赖仍在（`plugin-api → core`，为最后 6 条），crate 数不变。买到的是：
core 臂从 19 条降到 6 条，而**降下来的 13 条里没有一条是「换名字」**——它们原本就该在 SDK，
只是被「`turn` 是容器」这个错误的词判困在 core 里。判据本身因此更准：现在 core 臂上的
每一条都能指着义务环说「这一条要它」。

**被否候选：**

(a) **只搬 `projection` / `invariants`，留着 `turn` 在 core**——那正是 D-258 记的第一条障碍：
    `turnstate` / `turns` 与折叠同目录，一个域劈成两处住。三域同批走才没有这个问题。
(b) **先把 `turnstate` / `turns` 归到 `turn` 域再搬**——为目录形态做一次所有权变更
    （N-001 前缀、N-004 登记表、`core-naming-audit` 的域判定都要跟着动），而收益只是
    「两个文件换个目录」。判据要的是层归属正确，不是目录整齐。
(c) **把 `authz` 也搬下去，让门面彻底不依赖 core**——`authz` 读 `governance` 的能力闭集，
    闭集与义务环的判据是同一份东西；硬搬等于把义务环的一半复制进 SDK。这正是本条裁决 5
    要避免的「为了一个数字把判据做坏」。
(d) **加 HS-005 并把 6 条写进豁免**——豁免一旦按「authz / actors 的符号」开张，它就不再是
    「还欠着」，而是「永远欠着」；判据的价值在于它红了以后有一件事可做，而不是有一行可写。
(e) **`turn` 域改名（`dispatch` / `delivery`）再搬**——改的是名字，不是边界。域名的价值在于
    它与信封字段同名、读写两侧一眼对得上；换一个更抽象的词只会让「这一域读的是哪条事实」
    变得更难查。
