# 内核边界与扩展局部性

> 内核只装封闭语法；owner 声明开放词汇；行为在 owner 实现。
> 衡量边界是否成立，看新增能力是否改变了受保护的机制面，而不是看代码总量。

整体分层与依赖方向见 [DE-018](018-模块架构.md)；声明与生成通路见 [DE-024](024-能力横向扩充的通路.md)；能力包和扩展位置见 [DE-025](025-能力包与扩展面.md)。
当前 crate、模块、路由和生成物事实由 [RE-006](../004-ref/006-当前事实表.md) 提供。

## 1. 封闭语法与开放词汇

封闭语法是机制必须理解的最小合同：事件信封、`Entity×Verb`、五类协议事实、模式与债的
数据结构、声明容器与冻结校验、存储与 VDFS 等基础原语的签名。它们描述所有能力共有的
形状，不描述某项业务何时发生、由谁负责。

开放词汇包括事实名、视图名、插件身份、路由、装配位、端口、能力族和业务执行体。它们由
真实 owner 声明和实现，机制只按声明装载、校验、索引和生成。具体名单是生成事实，不写成
设计规范。

行为开放，边界不开放：owner 可以替换投影算法、行实现、工具和提供方，但不能在内核里
增加按插件 id、业务 owner、能力名或事件名分支的路径。机制读格子、角色、载荷形状和声明，
不读某个业务名字来决定流程。

封闭不等于永不变化，而是变化必须先证明现有语法无法表达，并按架构变更纪律讨论。
实现困难、少写一个适配器、避免一次机械移动，都不是扩大语法面的理由。

## 2. 当前物理拓扑与依赖方向

| 边界 | 当前职责 | 依赖规则 |
|---|---|---|
| `symbio-platform::kernel` | 封闭语法与最小冻结原语 | 不依赖 SDK、控制面或插件 |
| `symbio-platform::contract` | 内核不读的共享纯形状与线格式 | 只依赖更靠近内核的稳定形状 |
| `symbio-platform::sdk` | 跨插件共用的宿主机制、投影、授权、端口与装配服务 | 可依赖 `kernel/contract`，不反向依赖控制面 |
| `symbio-platform::deploy` | 由 owner 清单生成的编译期装配常量 | 不承担领域语义 |
| `symbio-runtime::{server,host}` | 运行入口、容器、会话服务和进程边界 | 可使用平台，不把业务策略写进宿主 |
| `symbio-plugin-api` | 扩展层可见的有限门面 | 从平台四臂逐条转出，不通配导出 |
| `symbio-providers` | 外部世界连接与服务实现 | 不认识插件、端口或业务事实 |
| `symbio-http` | 与能力无关的入站线路设施 | 不拥有能力语义 |

平台内部方向是 `sdk → kernel/contract`、`contract → kernel`；`deploy` 不形成领域依赖。
crate 名和目录只承载物理边界，不替代“谁拥有语义”的判断。一个符号在外部只有一条权威
可写路径，不在根门面、模块门面和原定义处同时保留可用别名。

## 3. owner-local 声明

声明以 owner 为单位提交。`Builder::declare` 的第一个参数就是交表方，不在每条声明里
再存一份 owner；`Frozen` 保存事实和视图的归属，供索引、生成与冲突报告使用。

`PluginDeclarations` 表达事实、视图、端口、执行体与行；`EventDecl` 表达业务事件名到格位
的角色声明。二者分工不同：前者描述载荷和机制输入，后者描述事实信封的角色与主体。
交表方 owner 与事实信封中的主体字段不是同一个概念，不得互相替代。

`Builder::seal(row_writes)` 是唯一冻结入口。它一次性返回全部装载缺口，包括重名、未知
名字、无生产者前件、写入重叠、声明不完整和会开账却无执行体。约束失效必须显式失败，
不能把缺失输入当成空集放行。

只有协议五格由内核预置；业务名字不由中央手写表维护。清单驱动的路由、共享事件、工具
命名空间和行绑定由生成器产出。作者只改 owner 清单与实现，不手改生成区；生成物与清单
不一致时门禁判红。

## 4. 归属规则

归属由依赖与生成事实决定，不按文件坐标、历史先后或“谁先写过”决定：

1. **唯一生产消费方的实现跟随消费方。** 没有第二个真实读者，就没有共享层的入场券。
2. **跨插件共用的纯机制归 SDK。** 它必须在不认识具体能力名或插件 id 的前提下说明合同。
3. **配对契约与封闭语法留在内核或契约层。** 需要成对读写的线格式、全局量词和不变量不能
   为了局部搬迁拆成两份。
4. **共享词汇由 owner 声明并生成。** 消费方按名字和稳定 JSON 形状读取，不复制 owner 的
   私有类型与实现。
5. **一个符号只有一个可写路径。** 搬迁时同时交接实现、声明和生成源，不保留兼容别名。

“被两个插件看见”只说明需要共享读法，不自动说明类型或实现应上移。先判断读者是否真的
依赖同一形状，再判断该形状是开放词汇、纯契约还是有状态机制。投影随其生产消费方走；
报表则由 owner 登记描述符，读方按描述符和槽位读取。

## 5. 扩展层门面

扩展层插件在源码中只写 `symbio_plugin_api::*`。直接写 `symbio_platform::*` 会绕开门面
白名单的计件与消费方核对，因此 `HS-001` 对所有扩展层源码禁止这一前缀。

扩展层插件的内部生产依赖闭集是：

- `symbio-plugin-api`：宿主词汇与扩展契约；
- `symbio-providers`：外部世界连接原语；
- `symbio-http`：通用入站线路设施；
- 不提供宿主语义的第三方库。

控制面因职责可以直连 `symbio-platform`：它按轮推进、读取事实流并持有容器概念。豁免只适用
源码前缀，不适用 manifest 依赖边。控制面不能借身份把兄弟插件或另一个共享层塞进依赖图。

门面按 `kernel/contract/sdk/deploy` 四臂逐条转发。通配导出、整模块转发和改名转发都必须
可计数；语法臂、机制臂与模块级转发都只许收窄。每一条白名单必须有真实扩展层消费方，
零消费条目应删除。门面只服务扩展层，不把控制面的私有容器概念转给所有插件。

`symbio-providers` 的准入不是永久豁免：它自身不得依赖任何插件，生产源码不得出现端口名或
业务事实名，否则会成为第二个插件共享层。重推理能力保持可选，默认构建不开启嵌入运行时；
需要它的宿主和插件显式选择该 feature，并把不可用原因作为可诊断结果返回。

## 6. 插件间零编译依赖

插件之间不得 import 兄弟 crate，不得经宿主根门面转发，不得设置 dev-dependency 例外，
不得共享一个名为 `contract` 的兄弟模块，也不得用 `include!`/`#[path]` 把兄弟源码搬进来。
运行期互调只经共同父容器路由；载荷使用 `PluginFrame/PluginPayload` 的 JSON 形状。

编译期零依赖使每个能力可以独立删除、替换或停用。若两个能力确实需要共享一个新概念，
先检查它是不是已有机制；不是，则在平台中按第 4 节归属，而不是建立两两依赖。

`E-009` 同时覆盖清单改名、workspace 继承、源码引用、宿主生产依赖、旧同 crate 路径和
源码搬运。`E-007` 禁止强引用兄弟插件实例；`E-014` 禁止真插件导出根暴露可被兄弟依赖的
公开类型。测试面同样不得依赖兄弟实现；需要链接注册表时使用装配测试口，不 import 类型。

## 7. 扩展局部性

新增能力只改自己的清单、声明、生成输入和实现。受保护面包括平台 `kernel/sdk`、扩展
门面、控制面与宿主；它们的非生成内容不得因新增能力而改变。

真实生成物可以随 owner 清单变化，但生成面本身不得顺手新增。作者不手改生成结果，也不
新增一条只为某个能力服务的中央分支。`EX-002` 比较新增能力包的提交中受保护树指纹，
生成物按已登记的生成路径处理。

能力迁移与机制补件分开：补件必须通用、至少服务一个真实能力且不含能力名；迁移只删除
旧实现、切换声明和绑定。机制面净变化不得为正，净零搬迁不抵净减迁移。需要新表达时先
完成机制设计与验证，再继续搬运，不能把实现困难变成留守理由。

## 8. 门禁与失效方向

| 判据 | 守的形状 |
|---|---|
| `CS-001/CS-002` | 内核基础 trait 数量、成员数与默认体只许收窄；变宽必须论证 |
| `CS-003/CS-004/CS-008/CS-010` | 机制不引用插件实现、不持业务名字与 owner 坐标 |
| `CS-009` | 公共数据面字段与枚举变体不随能力增长 |
| `HS-001…HS-006` | 门面源码前缀、白名单消费方、件数与重臂默认状态 |
| `E-009/E-013` | 插件零编译依赖与控制面 import 闭族 |
| `EX-002/EX-008` | 新增能力局部性与扩展面零容器词 |
| `CP-004` | 机制代码不持业务事件名或派发端口名 |

扫描范围读不出、声明源缺失、生成器无输入时都必须判红，不能按零违规通过。门禁证明的是
可执行的结构约束，不代替对“为什么属于这里”的设计判断；但任何豁免都不得吞掉判据对象。
