# 内核边界与扩展局部性

> 本文是「架构稳定、横向扩展更强」方案的仓内登记版：先冻结**语法**，把**词汇与行为**
> 交给 owner 声明。判据不是「core 改了几行」，而是**扩展是否触发 core 改动**。

## 1. 一句话模型

**内核只装语法；插件声明词汇；行为由 owner 实现。**

- **语法（封闭）**：Event 信封、Entity×Verb、5 条协议事实、`ActorSpec` 五字段、
  `Pattern` / `Scope`、环求解器、5 个 trait。加入语法要走 ADR，不随功能改。
- **词汇（开放）**：事实名 / 格位、视图名 / 字段、插件 id、路由、装配位、rows、actors、
  ports、能力实例。由 owner 声明，内核只 `seal`。
- **行为（开放）**：投影函数、actor 策略、执行体、工具。由 owner 实现。

## 2. 三个不变量（这才是门禁对象）

1. **扩展局部性**：新增事实 / 字段、视图 / 读数、策略 / 执行体、插件、共享类型这五类
   扩展，`kernel diff = 0` 且 `loop` / `session` **控制面** diff = 0，`seal` 与回放通过。
   后者的口径是：控制面只按**影响类**与**执行顺序**运行，不认识任何能力名；能力名出现在
   这两处即判红（[DE-026](026-能力拆分与影响类.md "DE-026-能力拆分与影响类") D-240，判据 EX-002；控制面里工具名的存量由既有的 SC-006 逐处判）。
   控制面这一半**尚未兑现**：行的执行体还不能由插件绑定（[DE-026](026-能力拆分与影响类.md "DE-026-能力拆分与影响类") §5）。
   迁移提交同一条判据的形态是**不含机制增量**——需要补件时单列一条 `### D-NNN` 的独立提交，
   通用且不含能力名，迁移提交本身只删旧实现与切换绑定（D-247 / `EX-007`）。
   上界同在此处：`Entity` 不变体——能力只产出既有实体的事实（D-244）。
2. **kernel 纯度**：kernel 源码里领域名词 0 个、`crate::plugins` 引用 0 处。
3. **根账本只降不升**：C-003 管内核公共面的 0 消费方 / 单消费方存量，C-004 冻结非内核
   账本条数（270，只许降）；投影类豁免清零（D-186）。

不为「声明数 / 变体数」再加计数器——那是代理指标，扩展夹具才是可执行的判据。

## 4. 什么不做

不建独立的中央 schema 文件；不造 `ProjectionRegistry`；不把 `ActorEntry` 搬进 core；
不全量迁 actors；不新增第二套审计脚本；**不把整个 core 照搬进 kernel**——那不是拆边界，
只是给同一份账本换名字（D-188）。A/B 阶段只搬声明、不搬实现；C 阶段才动实现。

## 5. 封闭语法清单

Event 信封 · Entity×Verb · 5 条协议事实 · `ActorSpec` 五字段 · `Pattern` / `Scope` ·
环求解器（`Decl` / `Pattern` / `owed` / `drive`）· 5 个 trait（Store / Capability /
ModelProvider / VdfsProvider / Registry）。

## 关键决策

### D-177 封闭语法、开放词汇

内核只保留 §5 的语法清单；事实名、视图名、插件 id、路由、装配位、能力族等词汇由
owner 声明，内核只 `seal` 与生成索引。理由：此前把「被两个插件看见」误当成「该进内核」，
导致词汇与语法同寿命，功能每加一项都在动内核。

被否候选：按消费方数决定一切（词汇因此永久留 core）；把 21 个域拆 21 个 crate。

### D-178 owner-local 声明取代中央 schema

声明以 `PluginDeclarations` 为单位由 owner 插件交出，`Builder` 只做扩展口，
`seal` 做 8 条装载检查；内核预置**只有协议五格**。新增视图 / 事实 = owner 文件加一行，
不再改中央 `BUILTIN_*` 表。owner 不是声明上的字段：`declare` 的第一个参数就是交表方，
`Frozen` 逐条记下 `fact_owner` / `view_owner`，`seal` 以「表长 = 清单长」钉住不缺条目
（同一次登记不产生第二处可漂的 owner）。控制面视图的迁移是此条的先行样本。

### D-179 kernel 纯度是硬判据

kernel 源码领域名词 0、`crate::plugins` 引用 0；由 `core-shape-audit` 扩展判据执行。
注释里的 `crate::plugins` 不算引用（判据按代码解析），但不得借此写实现依赖。

### D-180 共享类型归生产者 owner

跨插件共享的类型归**生产者**的域账本 owner；物理位置随消费者数量走：只有一个消费者时
留在生产方 crate 内（消费方经容器路由拿 JSON 形状，不 import 类型），第二个消费者出现时
上移 core 的对应领域模块——C-003 的「≥2 消费方」条件恰在这一刻满足，棘轮因此不构成阻力。
**不存在 `contract` 模块**：让消费方依赖生产者的 crate 与 E-009 直接冲突，那条路已被
[DE-024](024-能力横向扩充的通路.md "DE-024-能力横向扩充的通路") 的 D-192 修订否决。
C-002 过渡期继续拦深引，manifest 记录 owner。投影的**构造器**（`Projection`）是机制，
占根出口；视图类型与投影函数跟消费方走——`spend_ledger` 是第一个样本，
`token_ledger`（唯一消费方 `crates/symbio-plugin-session/src/stats.rs`）是第二个。

### D-181 根账本与装配清单走向生成或消失

`core/mod.rs` 的根导出与 `assembly.rs` 的 id / 清单，最终由 manifest 生成或随 crate 边界
消失；过程指标是「手改次数 = 0」，不是条目数增长。

装配侧的先行样本：每个插件目录的 `PLUGIN.yml` 是 id / 装配位 / 停用性的唯一声明处，
`scripts/facts/assembly.mjs` 把它们投影成 `crates/symbio-deploy/src/lib.rs`，
`symbio/src/assembly.rs` 只是它的门面。加插件 = 建 crate + 写声明 + 代码——装配方与内核都不需要人改；
手改生成区由 `gen-facts --check` 判红（`facts/assembly.test.mjs` 覆盖缺声明 / id 不一致 /
顺序重复三个方向）。

### D-182 新增能力族默认插件本地

六族是共享词汇；新族默认住声明方插件（`CapabilityFamily` 常量 + 载荷类型）。
只有长到 ≥2 个共享消费方时才搬进共享词汇，且按 D-175 的形状走。

### D-183 crate 拆分是后置选项

先模块（`kernel.rs` 门面）后 crate；Phase C 不作为 A/B 的前置条件。拆 crate 的收益是
把 C-002 的文本审计换成 cargo 依赖方向，而不是新增架构层。

### D-184 路由常量随 `fire_hook` 的搬迁走，不在 B3 生成

`ROUTE_*` 不能像 `PLUGIN_ID_*` 那样在 B3 搬去 host：`ROUTE_HOOK_FIRE` 的唯一 core 消费方
是 `fire_hook`（现住 `crates/symbio-plugin-api/src/hooks.rs::fire_hook`，session / loop 共用的机制助手）。
把它搬到 host 的 `routes` 门面会让 core 依赖 host（反向依赖，D-179 禁止）；在 core 里生成又会让加插件
改 core（D-181 禁止）。两条路都破坏既有判据，故剩余路由常量的收尾与 `fire_hook` 的搬迁
同步，归 C（实现搬迁）。B3 的「身份 + 装配清单」部分独立成立，已落。

被否候选：在 core 保留一份私有 `HOOK_ROUTE` 字面量（E-012 看不见的漂移）；
让 `fire_hook` 逐调用点传 route 字符串（7 个调用点只是把同一条地址抄七遍）。

### D-185 内核按文件集划线，门面是模块不是域

内核边界按**声明落点**判定：`symbio_core/kernel.rs` 是封闭语法的唯一汇合口（只重导出、
不拥有声明），它用一行 `core-kernel-files:` 声明哪些文件算内核（Event / Store /
Projection / 环 / 容器与 `seal` / `ActorSpec` / `Pattern`·`Scope` / 五个 trait 的声明文件）。
CS-001（形状）与 CS-004（插件 id 字面量）只量这份文件集；CS-003（零 `crate::plugins`）
仍量全 core——依赖方向是全局不变量，不随内核边界变化。根用 `pub use kernel::*` 平铺，
对外路径不变；`kernel` 不是目录、不成为命名审计的「域」，否则语法符号会被记到一个假
owner 上，依赖图与域前缀表同时失真。

被否候选：(a) 把整本根账本搬进这个门面——词汇与语法混住，域 owner 全丢；(b) 现在就
把 `event/` / `store/` / `decl/` 物理搬进 `kernel/` 目录——大量机械 churn，而 `Projection`
与域 trait 的声明仍散在域里，边界并不因此更真；留给 C 拆 crate 时按文件集抽文件。

### D-186 C-003 收窄必须配一条条数棘轮（C-004）

C-003 只对内核公共面判「0 消费方 / 单消费方」之后，内核之外的根出口**不再受任何判据**——
新增一个共享类型仍可随手进根出口，「加能力就得改架构」会由此悄悄回来。所以同批落 C-004：
非内核根账本条目数冻结在 270（只许降）。两者互补而非替代——C-003 管内核**质量**（每条
出口都得跨出 core 且不止一个消费方），C-004 管其余**体量**（不再增长）。

只冻结条数而不对 `[L1]` 的单消费方域出口再设第二道门：那些条目要搬走必须动实现
（B 阶段只搬声明，§4），再判一次只会把它们逼成豁免账本——C-003 的豁免账本已经证明
那条路会养出空转条目。处置归 C。

被否候选：(a) 让 C-003 继续管全部根出口——正是 D-185 要消除的失真（域词汇被当成
内核语法来判）；(b) 只收窄不加棘轮——留下一片判据真空，而真空比过严更危险（没人看得出
它空了）。

### D-187 `[L1]` 是候选报告，不是搬迁清单

`core-export-audit --verbose` 的 `[L1]` 段（非内核根账本里的单消费方域出口）容易被读成
C0 的工作清单。逐条核过后，13 条里没有一条能按「不改行为 / 不动声明」搬出 core：
**单消费方是结果，不是归属**。命中下列任一条即留根：

1. **配对契约**：出方向与入方向同住。`capability_to_wire` 与 `capability_resolve`
   是同一份线上语法的两半，模块文档把「必须成对」写成硬约束——只搬入方向，
   出方向留在 core，两侧判据当场分叉。
2. **单一统计口径 / 单一机制状态**：类型行为（`SloLatencyView::merge` /
   `FallbackRateView::merge` 的跨会话聚合）、两列共用的 tier 归属、`logger_init`
   的 once-state（日志宏直接读它）、`check_all` 的不变量清单、`creator_ids` 背后的
   注册表——搬走就是把一份口径或一份状态切成两份。
3. **跨 crate API**：`logger_parse_level` / `logger_set_min_level` 的消费方是 `cli`；
   core 不能依赖 cli，cli 也不能持有 core 的日志状态。
4. **闭集词汇 / 签名 / 安全面**：`EMBEDDING_NOOP` 与 `EMBEDDING_LOCAL`、`EVENT_BUS_KIND_SYSTEM`
   与同类事件 kind 是同一词汇面；`EmbeddingError` 是 `EmbeddingService` 的返回类型；
   `text_truncate_bytes` 存在的理由就是让每个截断点走同一把尺；`branch_hide_unselected`
   与两个私有助手同族，单搬要先把它依赖的私有面提成根出口。

C0 的可搬条目因此是 **0**。C 阶段的实质工作只剩 C0.5（`fire_hook` 与 `ROUTE_*`
一起搬，D-184）、C1（actor 策略，跨域部分单独论证）、C2（拆 crate，根账本随边界消失）。
C-004 的「单消费方 13」随之回到它本来的身份：报告——它指出「若 owner 变更，这里要
一起动」的位置，不是待办。

判据面的同批修正：消费方计数按**声明方**认整文件测试模块（`#[cfg(test)] mod <stem>;`），
不再只看文件名。`EventStore` 的唯一消费方是 loop 的测试助手，因此不在清单里（剩 13 条）。

被否候选：(a) 按 `[L1]` 逐条搬——每一项都要先提私有面 / 切口径 / 反向依赖，
与「纯机械」的前提相反；(b) 给 `[L1]` 加豁免账本——C-003 的投影豁免已经证明
空转条目会自己长出来，而 C-004 只需要一条条数棘轮。

### D-188 C2 的抽取单位是依赖闭包，不是文件集

`core-kernel-files:` 的 10 个文件**不是依赖闭合集**。逐文件核过第一层 `use` 之后，
闭包会带进：`plugin/{mod,error,transport}`（`PluginInvokeRequest` / `PluginError` /
`PluginPayload`）· `exec`（`ExecEnv`）· `chat/{chat_node,principal}`（`ChatNode`）·
`vdfs/{context,error,request,change,content,node,access}`（`VdfsRequest` / `Response` /
`Context` / `Error`）· `adapters::LatencyTier` · `view`（`Budget` / `View`）·
`authz` + `governance`（`ActorSpec` 的授权读法）· `present::ReadingSection`（`ChatNode` 的
读数面板字段）。按文件集硬抽只有两种结局：`symbio_core ↔ symbio_kernel` 循环，或把**词汇与
部署表**一起塞进内核（违反 D-177 / D-179）。

C2 因此按**依赖方向**分两步，每步都是一个可编译、可提交的迁移步：

- **C2a（结构层）**：`symbio_kernel` 先装已闭合子集——`event/`、`view/`（`Budget` / `View`）、
  `store/`、`projection/`（只装 `Projection` 构造器，投影函数留 core）、`decl/`、
  `adapters::LatencyTier`（先拆成独立文件）。core 依赖 kernel；`kernel.rs` 门面把这批符号
  改为从 `symbio_kernel` 转出，对外路径仍是 `symbio_core::<符号>`。此步不动任何 trait 签名。
- **C2b（契约层）**：五个 trait 及其**签名类型**按依赖序搬入 kernel（`Capability` /
  `Registry` / `CapabilityMeta` / `CapabilityRow` / `CapabilityFamily`、`ModelProvider` /
  `TurnOutput`、`VdfsProvider`、`Store`（已在 C2a）、`Plugin` / `PluginInvoke*` / `PluginError` /
  `PluginPayload`、`ExecEnv`、`ChatNode`，以及 `ActorSpec` / `Pattern` / `Scope`）。
  `ActorSpec` 的授权读法（`trivial` / `can_*` / `Pattern::for_principal`）改为 **core 侧自由函数**：
  `authz` / `governance` 是**部署表**，不进内核；它们不是语法，而是本机事实（D-099）。
  插件改为 `use symbio_kernel::…`；`symbio_core/mod.rs` 的根账本随条目迁出只降不升（C-004）。
- **判据面**：C-001 / C-002 在 kernel crate 内退化为 cargo 依赖方向（kernel 不能依赖 core，
  也不能 `pub mod` 开域门）；CS-001 / CS-004 的判定根目录是 `crates/symbio-kernel/src`，文件集标记
  只在那个 crate 的 `lib.rs`（core 的 `kernel.rs` 只剩转出，不再持有判定范围）；
  CS-003（零 `crate::plugins`）仍量两个 crate 的全部源码。
- **落地形状**：`ActorSpec` / `Pattern` / `Scope` 的数据面在 `symbio_kernel::actors`；
  读本机部署表的三类动作——平凡值（`trivial_actor_spec`，测试面）、模式派生
  （`pattern_for_principal`）、能力位判定（`actor_can_*`）——是 `symbio_core::actors` 的
  自由函数。宿主 crate 不能给内核类型写固有 impl（orphan），而这正是「数据在核内、
  读法在宿主」所需的形状；`pub(crate)` 出根供插件使用，根账本不因它们增加（C-004）。
- **剩余存量**：`Principal::from_legacy` / `tool_principal` 的工具族前缀表随 `Principal`
  类型进了内核（CS-004 冻结 13 处，见审计脚本的 `NOUN_BASELINE`），清理它需要把这两个
  解析入口也改成宿主侧自由函数；`capability/family.rs` 的家族 id `"model"` 与插件目录同名
  属报出的家族词汇（冻结 1 处）。

被否候选：

(a) **撤销 C2**（最小方案）——放弃 D-183 的唯一收益（把 C-002 的文本审计换成 cargo 方向），
且让「根账本消失」永远停在文件集层面；
(b) **按文件集硬抽**——闭包造成循环依赖，见上；
(c) **瘦内核 + trait 泛型化**——`Arc<dyn Capability>` / `Arc<dyn ModelProvider>` /
`Arc<dyn VdfsProvider>` 在 36 个文件、`CapabilityRow` 与 `Registry` 的签名里被持有；
泛型化/关联类型要改写全部这些公共面并牺牲对象安全与 F1 冻结端口，换来的只是
「kernel 不依赖 plugin / exec / chat / vdfs」——代价是**端口本身变形**，与「内核只装语法」
相反；
(d) **整个 core 照搬**——内核长成第二个大账本，根账本不消失，只是改名。

### D-189 actor 策略按单消费方归 owner，配对与跨域留核

C1 的判定与 D-187 同构，只是对象从「根出口」换成「actor 策略实现」：
**单消费方是结果，不是归属**。逐模块核过生产消费方后，落点如下。

- **搬回 owner（单生产消费方、无配对 / 跨域语义）**：
  - `ScheduleDecider` / `ScheduleFact` / `SCHEDULE_BUDGET_MS` → `crates/symbio-plugin-loop/src/task_events`
    （唯一写方就是本文件的任务转写口）；
  - `SkillCompiler` / `SkillRouter` / `SkillRoute` → `crates/symbio-plugin-loop/src/skill_events`
    （编译与路由成对，仍在同一文件里成对）；
  - `recalled_event` → `crates/symbio-plugin-loop/src/memory_events`（唯一消费方是
    `record_recalled`；`RecallTranslator` 是无状态翻译，不再单独留一个主体类型）；
  - `AutonomousInitiator` / `IntentGate` / `ConationPolicy` / `ConationCandidate` /
    `IntentDecision` / `ApprovedIntent` → `crates/symbio-plugin-session/src/transcript/autonomous`
    （自主层与意欲闸门在同一文件里成对——闸门与自主层同批成对的判据不变）；
  - `render_messages` → `crates/symbio-plugin-loop/src/turn_runner::prepare`（唯一生产调用点是请求装配；
    core 侧那份只剩测试夹具，删除）。
- **留核（命中 D-187 的留根判据）**：
  - `commitment_events` / `commitment_records`：写侧成格与读侧翻译的**配对契约**，
    写方在 loop、读方在 session（D-187 第 1 条）；拆开就是两套配对规则；
  - `control`（`PreemptionDecider` / `EliminationDecider` / `CircuitBreaker` /
    `GateDecision` / `Preemption`）：`PreemptionDecider` 的唯一生产消费方是 session
    收件箱，但 `EliminationDecider` 同时被 session 工具层与 loop 轮末驱动、
    `CircuitBreaker` 是 S09 执行闸的开口——**同一策略面在两个 owner 里扮演不同角色**，
    按 C1 的明文单独论证（本批不动；该遗留已由 D-190 收口）。
- **词汇留核**：`SKILL_TAG` 是 loop 写、session 读的共享词汇（D-177 / D-182），
  行为搬走、常量留下。

判据面：`actors` 只剩 `commitment` / `control` / `spec` / `SKILL_TAG`；根账本只降；
NDC-001 的 `RecallTranslator` 随实现退役（`CommitmentKeeper` 仍在留核的 commitment 里）；
策略测试随实现迁到 owner 的 `.test.rs`（loop 的 `task_events` / `skill_events` /
`memory_events`，session 的 `autonomous`），core 只留授权面与投影面断言。
NDC-001 只查**主体类型名的指称**：`Pattern::Decider` 是 `symbio-kernel` 的封闭语法
枚举变体（`ActorSpec.pattern` 的取值），声明档位不产生到主体对象的边，故扫描先剔除
`Pattern::<变体>` 再判主体名——否则「按裁决者档位跑」会被误读成「持有裁决者」。

被否候选：

(a) **把 commitment 拆成写方留 loop、读方留 session**——两侧各写一份配对规则，
    载荷 `id` 的成对性从此靠两份代码对齐；
(b) **迁 control**——搬任一处都让另一处反向依赖兄弟插件（E-009 / E-013），
    而 `CircuitBreaker` 的 S09 闸门语义还没有单消费方；
(c) **给搬走的策略保留 core 薄壳（`pub use loop::…`）**——core 反向依赖插件，
    CS-003 当场判红，且「策略扩展不触发 core 改动」不再成立。

### D-190 control 按消费方拆三块：抢占归 session、熔断归 loop、淘汰裁决留核

D-189 把 `control` 整体留核，理由是「同一策略面在两个 owner 里扮演不同角色」。
那个理由是**对 `EliminationDecider` 成立**，却被当成整份文件的属性。逐条核过生产
消费方后，跨域与否是**每个策略各自的属性**，不是文件属性：

- **`PreemptionDecider` / `Preemption` → `crates/symbio-plugin-session/src/transcript/inbox`**：
  `spec` / `decide` / `held_event` / `resume_event` / `control_event` 五个生产调用点
  全在同一文件（忙窗判定与空闲落格）。没有第二个 owner ⇒ 单消费方，按 D-189 的
  第一判据归 owner。
- **`CircuitBreaker` / `GateDecision` → `crates/symbio-plugin-loop/src/tools/dispatch/gates`**：
  唯一生产消费方是 loop 的 `external_execution`（`gate`）与
  `derived_facts::record_derived`（`break_event`）。两处同属 loop 一个插件——
  **同插件内引用不产生 E-009 / E-013 的跨插件反向依赖**，故落点就在闸门判据旁。
- **`EliminationDecider` 留核**：这是真的跨两个 owner 且角色不同——写侧裁决在 loop
  `derived_facts::record_elimination`（`spec` / `elimination_event` / `THRESHOLD`），
  读侧翻译在 session `plugin/run_actions`（`verdict_grants_changes`）。而
  `verdict_grants_changes` 是 `elimination_event` 载荷的配对翻译（D-187 第 1 条），
  搬任一侧都要把另一侧切成第二套规则。

判据面：`actors` 只剩 `commitment` / `control`（只装 `EliminationDecider`）/ `spec` /
`SKILL_TAG`；`symbio_core` 根账本删除四个名字（`Preemption` / `PreemptionDecider` /
`CircuitBreaker` / `GateDecision`），只降不升；`PRINCIPAL_REFLEX` 与
`EVENT_CONTROL_OPENED` 升为**生产** `pub(crate)` 根出口——两侧插件各有一个写方，
而 C-002 禁深引域目录。策略测试随实现迁：抢占用例进 `inbox.test.rs`、熔断用例进
loop 的闸门测试，淘汰用例留 core（含授权面与投影面断言）。

被否候选：

(a) **整体留核**——把「同文件」当成「同 owner」。两个策略各自只有一个 owner，
    留下只会让 core 继续为插件的本地策略付维护面，D-189 的明文遗留永远收不了口；
(b) **只搬 Preemption、熔断留核**——熔断同样有唯一消费方（loop），分两批只是把
    同一条判据用两次，不改变任何风险；真正需要单独论证的跨域项只有
    `EliminationDecider`，它已经留核；
(c) **给 core 留薄壳（`pub use …`）**——core 反向依赖插件，CS-003 当场判红
    （同 D-189 候选 c）。
