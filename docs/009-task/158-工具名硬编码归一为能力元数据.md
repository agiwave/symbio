## 内容

父任务：[T-156-架构机制化与旧代码清理批](156-架构机制化与旧代码清理批.md)
依据：判据 J3（若某约束被违反时**不产生错误信号**，它必须做成编译期强制或 CI 断言）·
[PL-012 §0.1.2](../004-plan/012-高阶智能体平台v2.md "PL-012-高阶智能体平台v2")（模块内部可妥协，切分不可）

**问题**：工具执行层有三类闸门，都按**工具名字符串**判定：

| 闸门 | 位置 | 判定方式 |
|---|---|---|
| 淘汰闸（委派已撤销时拦 `agent_run`） | `tool_executor.rs:1164` | 裸字面量 |
| 委派登记（只记 `agent_run` 的委派） | `delegation.rs:39` | 裸字面量 |
| 任务表闸（只处理 `todo_write` 的任务声明） | `task_decl.rs:67` | 裸字面量（而 `task_table.rs:64` 另有常量） |
| 收束拦截（`context_compact` 不走标准分发） | `chat_loop/turn.rs:137` | ✅ **已经常量**（形态正确） |

**按名匹配是静默失效**：把 `agent_run` 改名，两处闸门都不会报错、不会有测试失败——它们只是
**静默地不再匹配**，淘汰闸失效且无人知晓。这正是 J3 要求「必须强制或断言」的那类失效。

**本条要买到的性质**：新增一个需要特殊闸门待遇的工具 ⇒ 在能力元数据上**声明一位**，
执行器查表；漏声明时**当场行为不符**（工具该被拦没被拦，e2e 会红），而不是静默通过。
（落地三位：`provides_assign_work` / `records_delegation_promise` / `owns_task_table`，
见下方处理过程。）

## 处理过程

- **第一步是归一常量**（低风险、可单独提交，`f21342b1`）：`agent_run` 收成命名常量
  `AGENT_RUN_TOOL`，与 `TODO_WRITE_TOOL` / `CONTEXT_COMPACT_TOOL_NAME` 同形，消除三处<!-- doc-symbol-allow: 记名的两个符号是步 1 的中间形态，步 2 机制化后已退役——「不存在」正是机制化生效的状态 -->
  形态不一致；`note_tasks` 的 inline 判据改用 `is_task_table_tool` 助手。
- **第二步才是机制化**（元数据位）：判据是「执行器读的是**声明**，不是**名字**」。
  元数据位落在 `CapabilityMeta` 一侧——注意 `symbio_core` 有**两个 Capability**（`capability` 域的
  LLM 工具描述符 vs `governance` 域的权限矩阵键），本条属前者，改动可能触碰 core 形状，
  若需变宽须走 CS-002（`core-shape-allow` + 存在的 ADR）。**实测未触**：三个新字段是
  `pub struct` 的字段（CS-001 只数 `pub trait` 与其 `fn` 成员），零 builder 方法，三格不动。
- **`context_compact` 是正面样板**：它已有常量且调用点经常量引用，施工时以它为形态基准。
- 收束拦截（`context_compact` 不走 CapabilityVisitor 分发）是**有意设计**（它需要编排器内部的
  压缩链路），机制化的是「按名判定」这层，不是取消这个拦截。**它没有进位**：v2 路径不把
  该工具注入工具清单，注册面里没有它，位也无处可读——保持常量引用即是正解（任务表已判 ✅）。

### 落地形态（2026-10-17）

三个位，而不是「一个淘汰豁免位包打天下」——语义按闸门要什么定，名字按读起来是什么定
（signal 里举的 `elimination_exempt` 等名字只是示例，未采用）：

| 位 | 声明方 | 闸门 |
|---|---|---|
| `provides_assign_work` | `agent_run` | 淘汰闸（`delegation_revoked` 时拒止） |
| `records_delegation_promise` | `agent_run` | 承诺记账（`note_delegation`） |
| `owns_task_table` | `todo_write` | 任务表写侧资格闸 + 任务声明记账（`note_tasks`） |

- **`ToolDecls`**（`tool_executor/decls.rs`，新建）：批首从 `ctx` 的 `CAPABILITY_VISITOR`
  读一次 `list_capability()`，三个 `HashSet` 按 `meta.name` 收键；查询法的匹配口径
  **逐字保持机制化之前**（派活/立约 = 线上全名等值含 trim；任务表 = 取末段比短名）。
- **步 1 的 `AGENT_RUN_TOOL` 随之退役**：机制化后最后一个字面量住址也没了——常量是<!-- doc-symbol-allow: 记名的三个符号随机制化退役，「不存在」正是判据搬进声明后的状态 -->
  中间形态，声明是终态。`TODO_WRITE_TOOL` / `is_task_table_tool` 同理（其「工具名判据」
  用例迁入 `decls.test.rs`，并补子作用域前缀名与无 visitor 两条）。
- **子作用域语义的如实记账**：改名投影（`PrefixedCapability`）只换名字、原样透传位
  （与 T-138 的 `risk_for` 透传同一纪律），所以闸门在绑定子智能体的会话里**同样命中**
  （`agent_<id>_agent_run`）。此前按字面量等值判，前缀名一个都不中——这是按名判据的
  既有缺口，不是本批开的口子；e2e 77 条覆盖的路径（主会话 / 跨会话）行为不变。
- **行为不变的判据**：`cargo test -p symbio --lib` 1752 passed（`v2_exec` 的代际立约
  用例改为经注册面喂声明——与生产 `capabilities.rs` 同形）；全量门禁含 e2e 77 条全绿。
