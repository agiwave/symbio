## 内容

`content_search` 的截断纪律是「给前 1000 条 + 尾部一句 `[结果已限制为前 1000 条匹配]`」，
超出的部分归档到会话目录 `tool_archives/`（整份原文可取）。归档这一半是对的，
缺的是**读数**：模型看到的只有「被限制了」，看不到「一共多少条、剩下的怎么拿」。

于是聚合型问题必然失败。实测（会话 `cli1a14222066f0`，任务是数一下全仓 `unwrap()` 有多少处）：

```
第 5 次请求：content_search pattern=unwrap\(   → 原文 109772 字符 / 命中 1000 条被截断
第 6 次请求：模型**原样重发**同一条调用        → 归档两份，文件名尾哈希相同（8e33644e）
                                    ⇒ 同一份结果，两次执行
```

重发不是模型的随机行为：它需要的是「总数」，而结果里没有一个字提到总数，
也没有一个可以 narrowing 的抓手（按目录分段？翻页？），所以它唯一的动作就是**再问一次**。
这一轮因此白跑，还把上下文又撑大了一格——正是那次长跑最后卡在单请求 6 分钟之上的成因之一
（`chat.assistant.*` 帧到轮末才到达的缺位见 [T-136-轮中对话面节点不入实时面](136-轮中对话面节点不入实时面.md)）。

两件分开做，各自可回退：

1. **读数补齐**（改一处尾部提示的形状）：把 `match_count`（真实命中数）、已给条数、
   `offset` 用法与归档地址一起写进结果末尾。这是纯输出面，不动检索语义。
2. **重复调用可见**（改一处执行面）：同一轮内**同工具同参数**的第二次调用，
   在执行侧给一条提示（「与本轮第 N 次调用同参，结果相同」）——不拦截、不改结果，
   只让模型看见自己正在绕圈。是否值得拦（例如连拒两次）留给实际数据再判。

## 处理过程

- **读数补齐**（`content_search.rs` 尾部读数）：收集窗口只约束**收集**、不约束**扫描**——
  走完全程才累计出 `match_count`（真实命中数）与 `line_index`（输出行总数），于是尾部能说清
  「一共多少、这次给了哪一段、剩下的怎么拿」：
  `[结果已分页：共 N 处命中、M 行输出；本次给出第 a–b 行（k 行），其后还有 w 行。取后续用
  offset=b（head_limit 控每页行数）；只问总数用 output_mode="count"；或按 path/include/type 收窄]`。
  另补一格越界读数（`offset` 落在末尾之后 ⇒ 总数 + 从 0 起取），否则模型只会拿到空结果再重发一次。
  判据：`content_search.test.rs::truncated_tail_reports_total_and_next_offset`（形状含总量与
  翻页指引）、`offset_skips_leading_match_lines` / `offset_and_head_limit_combine_on_match_lines`
  钉住窗口口径。检索语义未动。
- **重复调用可见**（`tools/tool_executor.rs` 执行面）：签名 = `name` + 分隔符 + **序列化后的参数文本**，
  本轮起点取 `get_context_messages` 里已有的 ToolCall 节点（要按 id 排除**本批自己**那几条——转写里
  它们已经在了），批内每执行一条就把它加进已见集合。命中同签名 ⇒ 在该条工具结果尾部追加
  「[重复调用] 与本次会话第 N 次工具调用同工具同参数，结果相同；翻页用 offset、收窄换 pattern」，
  并 `plugin_warn!` 一条后端日志。**不拦截、不改结果**（是否值得拦留给实际数据）；
  interaction 类结果不带这条（它的正文是给用户看的表单，不是检索读数）。
  判据：`tool_executor.test.rs` 四格——同批内重复 / 转写里重复 / 参数不同不算重复 / 键序归一后仍判重复。
- 2026-10-17 两项各自独立落地、各自可回退；全量门禁 109/109（轮次 `20261017-121200`）。
