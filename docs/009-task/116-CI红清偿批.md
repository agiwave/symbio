## 内容

`v2` 自 2026-10-13 起 13 次 run 里 12 次红（唯一绿的是 run 38405380079）。`CONTRIBUTING.md` §6 写的是
「推送后通过 PR 提交，CI 必须全绿」，而当前 HEAD 就是红的。三条红是**三个不同的根因**，
所以拆成三批，各批独立可回退：

| 批 | 红的项 | 现象 | 根因 |
|---|---|---|---|
| ① | `cargo test --workspace` | `plugins::local::content_search::tests::offset_skips_leading_match_lines`（`.test.rs:165`）与 `offset_and_head_limit_combine_on_match_lines`（`:184`）在 Linux 红、Windows 绿 | [T-113-本地检索输出残余批](113-本地检索输出残余批.md) 补的单测把**文件系统遍历序**当成了断言依据 |
| ② | `security-check` | `error: 4 vulnerabilities found!` | RUSTSEC-2026-0346/0347/0348/0349（均 rustls，日期 2026-10-14），补丁版本 `>= 0.23.46` |
| ③ | `e2e-check` | `t36-autonomous-initiator` 恒定红（10-14 起每轮都是它），10-15 之前的 t16/t21 另计 | 用例把**平台相关的目录遍历序**当成 mock 场景的配对顺序（见「处理过程」③）|

### ① 不只是测试不稳，是用户可见的分页窗口随平台变

`content_search.rs::search` 逐 `WalkBuilder::build()` 的产出**原序**拼进 `out`，随后
`apply_line_pagination` 按**行**切 `offset` / `head_limit`，`MAX_RESULTS` 也在同一序上截断。
NTFS 的目录项返回序恰是名字序，ext4 是哈希序 —— 于是同一份代码、同一个查询：

- Windows：`a.rs:1 … a.rs:3, b.rs:1, b.rs:2` ⇒ `offset=1` 跳过的是 `a.rs:1`；
- Linux：`b.rs` 可能整体在前 ⇒ 跳过的与截断的都是另一批行。

测试红只是这件事**最先可见的地方**，判据本身没有错（它断言的是「应当有的行为」），
错的是实现没有把输出序钉住。同一形状在 `codebase_search.rs::keyword_search`（嵌入服务不可用时的
降级路径，按 `limit` 截断）也成立；索引侧 `scan_files` 已自带 `out.sort_by(|a,b| a.rel.cmp(&b.rel))`，
所以只有降级路径缺这一格。

修法：两处 `WalkBuilder` 都钉 `sort_by_file_name`，输出序成为与文件系统无关的确定序；
判据补一条**直接钉这个不变量**的用例（`output_order_is_name_then_line_not_fs_walk_order`），
而不是只钉两条分页用例——分页用例是它的下游症状。

### ② rustls 四个 advisory 全在补丁位上

四条都是 2026-10-14 发布的 rustls  advisories（`crypto-failure` ×3 + `denotation of
DoS` ×1），`patched = [">= 0.23.46"]`，而锁的是 `0.23.45`。同一次 run 里另外 10 条
（`unmaintained` / `unsound` / `yanked`）是**允许显示的 warning**，不是失败原因——
所以这一批只做一次同小版本升级，不动依赖树形状。

### ③ t36 在 Linux 上恒定红，本机绿

`等待 SID_OK 的心跳轮落进转写 超时（100000ms）`。预算本身不算紧：调度器 15s 一 tick +
按会话 id 的确定性抖动 ≤30s + `interval_seconds` 下限 10s ⇒ 期望 ~55s，100s 有约一倍余量。
而它**每轮都红**，且 CI 那侧 `并发 4｜最慢单例 100.8s`（就是这条超时本身），
「慢」解释不了恒定。

四类失败在这条用例里长得一模一样（前三类是「没到点」，第四类是「到点了但配错了会话」），
现有的诊断（`cli.out.stderr` 末 1200 字符）区分不了它们：

1. 调度器压根没扫到 ⇒ LLM 请求数停在 4；
2. 扫到了但触发被挡下（`heartbeat/mod.rs::record_autonomous_trigger` 的两条早退：
   会话正在工作 / 事实源 `head == 0`）⇒ 请求数停在 4，stderr 里有 `[Heartbeat]` 的拒发理由；
3. 轮跑了但提示词没落进转写读出口 ⇒ 请求数在涨；
4. **配对错位**（不是「没到点」）：装心跳的发言同文 ⇒ 哪个会话拿到哪条 mock 场景由**到达
   顺序**决定，两会话的心跳轮都跑、只是提示词互换 ⇒ 前三条的读数**全部**看起来正常。
   这一类只在跨平台时现形，靠现场快照才看得见。

本批先把**现场取全**（`diagnose()`：两会话的转写用户发言 + `session/stats` 就绪集 + LLM 请求数 +
stderr 末 8000 字符，三处超时都接上），拿到一次 Linux 的证据再定改法——没有证据就改超时
或改判据，等于用放宽掩盖病因。

## 处理过程

- ① 落地：`content_search.rs` / `codebase_search.rs::keyword_search` 各钉一处
  `sort_by_file_name`，`content_search.test.rs` 补不变量用例。本机
  `cargo test -p symbio --lib plugins::local::content_search` 9/9 绿（含两条此前只在
  Windows 绿的用例）。**CI 已复核**：run 38752533977 / 38754539354 的 `rust-checks (dev)`
  与 `(release)` 全绿——两条分页单测在 Linux 不再红，不变量用例同批绿。
- ② 落地：`cargo update -p rustls --precise 0.23.46`，`cargo check --workspace --all-targets` 绿。
  **CI 已复核**：`security-check` 绿（四条 rustls advisory 由 0.23.46 覆盖；同批另有 9 条
  是 `--ignore` 允许的 warning，本就不是失败原因）。
- ③ 进行中：CI 现场已取到**一半**——stderr 尾部显示 `hb_e2e-t36-ok` / `hb_e2e-t36-broad`
  两条心跳任务**都起了轮**（`[Session] Turn 任务启动` + `[Turn] 第 0 轮开始` + 两次
  `[LLM] 请求发起` 都 200 收尾）⇒ 本节列的前两种病因（调度器没扫到 / 触发被闸门与
  `head==0` 挡下）被排除，剩下的分歧只在「提示词没落进转写读出口」与「断在更后面的就绪集」。
  而决定性那三行没出现在日志里，是**快照自己的顺序**造成的：门禁只印失败日志的末 40 行，
  8000 字符的 stderr 转储排在读数之后，把读数推出了窗口。已把读数排到最后，并用
  `timeoutMs=1000` 强制超时验过快照打得出来（本机读数：请求数停在 4、转写只有「开始工作」、
  就绪集 `ready:[]` —— 正是「还没到点」该有的样子）。**改法等下一次 CI 的读数**。
- ③ 落地（读数 38756732677 拿到后）：**病因不在产品，在这条用例的配对方式**。CI 快照读的是
  「两个会话的心跳轮都跑了，但提示词**互换了**」——`e2e-t36-ok` 的转写里是长提示词、stderr
  里跟着 `[Heartbeat] 意图闸门拒绝（会话 e2e-t36-ok）：goal too broad`，而 `e2e-t36-broad`
  跑出 6 轮 `推进待办` 且就绪集里有 `hb-5`。机制侧全部按判据工作，红的是**判据自己**：
  装心跳的两条发言同文（`MSG`），两条 mock 场景同 `match` + `once` ⇒ 谁拿到哪条场景由
  **到达顺序**决定，而到达顺序取自会话目录遍历（`plugins/session/store/mod.rs::session_dirs_under`
  = 未排序的 `read_dir`）——名字序在 NTFS、哈希序在 ext4。**「本机绿」这一次不是实现的平台差异，
  是测试把平台差异写进了编配**（§③ 前三种病因因此都不成立，快照是唯一能揭穿它的东西）。
  改法：发言按会话**分文**（`MSG_OK` / `MSG_BROAD`，互不为子串），配对键由内容给出，与顺序无关；
  同时把装心跳那两条断言从「全量请求里 `some` 含某提示词」改成**按会话读自己的工具调用**
  （`hbCallsOf`）——旧写法在互换时**两句同时满足**（CI 实测：红的只是后面的心跳轮与就绪集，
  症状离真因隔两层）。反转验证：把放行侧场景的提示词换成长提示词 ⇒ 新断言 546ms 内变红，
  旧写法不会。转写与就绪集两条判据**一字未动**，本机复跑绿。
  遗留（本批不做，另议）：`session_dirs_under` 这类未排序的 `read_dir` 是 S-013 未覆盖的**同一类的
  产品侧实例**——遍历序是否会进到用户可见的输出（会话列表顺序、`fleet_reading` 聚合），
  属实现面判定，不在「CI 清偿」这一步里顺手动。
- 机制面落地（裁决：**门内一条静态判据**，不靠人记得）：`scripts/grep-audit.mjs` 新增
  **S-013** —— `WalkBuilder::new` 构造点在同一函数体内必须出现一次 `.sort_by(` /
  `.sort_by_file_name(`，否则变红。留痕口 `// grep-audit-allow S-013: 理由` 要求理由能指认
  「序在哪里被钉住」，本仓第一处合法豁免就是 `walk_source_files`（它的输出被 `scan_files`
  末尾的 `out.sort_by(rel)` 钉住）。回归测试 6 条：未钉变红 · 两种排序调用放行 ·
  **下一个函数**里的排序不替这里说话（作用域边界）· 豁免缺理由变红 · scope 内无构造点静默通过 ·
  全仓三处构造点绿。同一类「判据/实现依赖平台」的两次实例：[T-093-prompt形状基线平台绑定](093-prompt形状基线平台绑定.md)
  是 shell 工具名的平台变体，本条是路径序。
