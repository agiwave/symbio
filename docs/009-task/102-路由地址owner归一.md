## 内容

用户问的是**分工**而不是文字：「路由列表究竟应该哪个文档维护或呈现，能力列表同理」。

审计结论（`scripts/facts/` 与 docs 全仓）：

| 事实 | 唯一 owner | 其它 |
|---|---|---|
| 工具短名（19） | `CURRENT.md §2.1`（代码提取） | 全仓无第二处成表复述 ✓ |
| VDFS 操作（13） | `CURRENT.md §2.2`（代码提取） | AR-013 / AR-012 / RE-001 均无成表复述 ✓ |
| **路由地址** | **无** ⚠️ | §2.3 有 20 条（代码投影）；RE-003 有 45 条（**手写**） |

能力面已经干净。**路由是唯一的洞**，形状很具体：同一串地址，代码里有一份、RE-003 里
一份，两份都是「拥有」；而两处**保证等级不同**——§2.3「必然与代码一致」，RE-003 自称
「人工维护，因此也是唯一会漂移的一份」。后者那句话本身就是在承认自己会漂。

RE-003 多出来的 25 条是**运行期动态路由**（`vdfs/*`、`local/<工具短名>`、退役的
`session/*` 臂）与 model provider（`openai_chat` 等）。它们**必须**留在 RE-003——
它们没有可静态枚举的 `match` 臂，CURRENT §2.3 结构上装不下。所以 RE-003 作为
**超集**是对的，要消掉的是**重叠那部分的第二份手写**。

## 为什么判据解决不了（这是本条最值得记的部分）

试过用判据管「RE-003 多出来的那条是不是漏同步的静态路由」，**结论是判据猜不出来**：

- 要判「这条是不是本该静态的」，得先知道哪些静态的——那正是 §2.3；
- 可 §2.3 是代码投影，RE-003 里**手写的新地址**既不在代码里也不在 §2.3 里，
  判据无从分辨它是「漏同步」还是「合法的动态路由」；
- 按插件前缀猜会**当场误伤**：`session/open` 的前缀是 `session`，而 `session/stats`
  是静态的，于是全部历史 session 路由被误判成漏同步。

所以正解**不是加判据，是让两个 owner 在结构上不可能存在**——把静态部分交给生成器，
手写只保留只有人才知道的东西（调用方 / 返回类型 / 退役索引）。

## 已落地的部分

不猜的部分先钉住（`scripts/facts.test.mjs`，24 → 26 条）：

- **RE-003 必须提到 §2.3 的每一条静态路由**（缺一条判红）。这是
  `scripts/facts/current.mjs` 文件头那句「两者交叉核对构成漂移门禁」的执行方——
  查过：E-006 只查路径**前缀**合法性、M-008 只查前端有没有写死地址，**两处都不做
  行集对账**，那句话此前没有执行方。口径只判**缺**不判**多**：多出来的是动态路由，
  是 RE-003 作为超集存在的理由。
- **指向 CURRENT.md 的节次指路必须有效**（新增）。能力矩阵 §6→§2 那次迁移漏了两类，
  D-007 结构上抓不到：① **链接显示文字**（`[[RE-006-当前事实表#23-…|§6.3]]` 目标改了、
  文字没改，13 处）；② **语义指路**（`CURRENT.md §3.2` 指 VDFS 操作闭集，而那一节的
  内容在同一次去重里被改写——**位置没变，位置上的东西换了**，任何按锚点判的守卫都
  抓不到）。反向验证两类形态都判红。
