## 内容

父设计：总报告 A3 · 08 报告建议 6 · [PL-012](../004-plan/012-高阶智能体平台v2.md "PL-012-高阶智能体平台v2") §3（三条不变量 I1 / I2 / I3）

**现状**：三条不变量的兑现度差别很大——

| 不变量 | 现状 | 判定 |
|---|---|---|
| I3（唯一构造点 + 类型级禁模型 + 中止即状态） | 兑现最好 | 已兑现 |
| I1（单通道） | 只在体检里查，**写侧零阻断** | 部分兑现 |
| I2（溯源） | 同上 | 部分兑现 |

**「体检」与「闸门」的差别**：体检发现违例只记一笔，写入照常发生；闸门发现违例时
**这一条写不进去**。前者是观测，后者是保证——v2 要的是后者。

**为什么风险高，以及怎么降**：08 报告明确标「可能触发现有会话失败」。所以本批的顺序是硬约束：

1. **先只读**：在写入口跑 `check_all` 但只统计、不阻断，跑一段真实使用（e2e + 日常会话）；
2. **再看违例率**：违例率非零 ⇒ 先查清是「存量数据不合规」还是「写路径本身在违规」——
   前者要清查与处置方案，后者是本批真正要修的东西；
3. **最后翻阻断**：违例率归零后翻，且翻的那一批单独提交（默认档位变更，纪律 1b 第 4 条）。

**一处诚实的边界**：I1 / I2 的「阻断」在**哪个入口**阻断要写清楚。同一个会话有三条写路径
（用户输入、工具结果、收尾落格），在不同入口阻断的后果完全不同——「全部入口都阻断」听起来
最安全，实际会把「一次违规写」升级成「会话卡死」。入口清单与各自的失败语义是本批的第一个产出。

### 入口清单与失败语义（本批第一个产出）

**只有一个写入口**：`WalStore::append`（`symbio/src/plugins/session/store/wal.rs`）。三条真实
写路径——用户输入（`u-{turn}` 开轮）、工具结果（`artifact.added` 产物格）、收尾落格
（`f-{turn}` final / fallback）——全部经 `Store::append` 进同一个 WAL，没有旁路实现
（`MemoryStore` 是 core 的平凡基线与测试替身，不承载会话事实）。因此闸门挂在 `append` 内，
**不存在「某个入口忘了拦」**；这也让「入口清单」退化成一张处置表：

| 判据 | 处置 | 拒绝会不会钉死会话 | 理由 |
|---|---|---|---|
| I2 声明缺 `produced_by` | **拒绝**（`AppendError::Invariant{ I2, .. }`） | 不会 | 没有上游的声明无法审计也无法撤销；生产者补上即可，重试安全 |
| I1 同轮第二条 `final` | **拒绝**（`I1`） | 不会 | 这一轮已有收束，第二条会让「每轮至多一条 final」失效；同 id 重放仍走 `Duplicate` |
| I1 同轮第二条开轮（不同 id） | **拒绝**（`I1`） | 不会 | 同 id 重放更早被 `Duplicate` 拦下；能走到这里是两条不同事件抢同一轮 |
| I3 新轮越过未收束的旧轮 | **显式降级**（`plugin_warn!` 出声 + 计数） | **会** | 崩溃恢复恰好长这样（上一轮停在半路，重启后开下一轮）；拒绝会让会话再也写不进任何事实 |

**I3 的降级为什么仍算「不静默」**：写入口当场以 `[invariant-I3]` 出声，读侧
`check_all` 的 `unresolved_turns` 会把同一处缺口报成违规——两条信号指向同一个事实。
反过来说，「I3 的写侧阻断」不由闸门承担，而由既有的发言收束闸（ADR-067 的
`closure_gate`）承担：到点必答缺的是收束格，不是「新开轮」这个动作。

**为什么闸门不逐条调用 `check_all`**：`check_all` 的其余判据（seq 跳号、未收束、依赖成环）
都是**整段历史**的聚合，写入口手里只有「这一条 + 索引」。写侧跑的是同一批判据的
单事件切片（`is_turn_open` / `is_turn_final` / `closes_turn` / `provenance_violation`，
读侧那四条检查已改为调用同一组函数——不是第二套规则）；聚合判据仍然只在读侧对完整切片判。

### 存量清查与「观察段」的处置

- **生产构造点**（静态清查，全部带 `produced_by`）：`turn_runner/{prepare,stream,reflex,settle,batch}.rs`、
  `turn_exec/call.rs`、`task_events.rs`、`message_events.rs`、`memory_events.rs`、
  `derived_facts.rs`、`symbio_core/actors/{skill,recall}.rs`。没有发现「生产代码忘带溯源」的构造点。
- **仓内语料的违例**：闸门一开，10 个既有夹具当场变红——8 个 I2（final / 进展 / 记忆 / 任务
  断言缺 `produced_by`）、2 个 I1（同一轮开两次 / 同一轮两条 final）。处置是**修夹具**而不是
  给夹具开豁免：它们本来就在造不合规的事实，闸门把它们照出来了。
- **观察段没有留成「默认关闭的开关」**：本批直接以阻断形态入库，证据是**同一套闸门在
  全量单测（1878）与 e2e（77 例）语料上零拒绝**——任何一条违规都会让那条用例当场变红，
  这比「先记一笔再翻」更强。不采用「先只读一段」的形态，是因为它会留下一个默认关闭的
  档位，正是本批要拆的虚闸；风险由 I3 降级 + I1/I2 的可重试性兜住。
- **磁盘上的既有用户会话没有逐仓清查**（本环境拿不到用户数据）：处置口径是**不回改历史**——
  读侧 `check_all` 照报，写侧只拒「新的坏事实」。真有存量违规时表现为某轮收束被拒而非静默接受。
