## 内容

[T-107](107-角色主体执行路径批.md "T-107-角色主体执行路径批") 落地了 `agent:planner` / `agent:verifier`
两行（ThreadPrivate、各持 `define.work` / `assert.verification`）与任务表写侧闸（两项能力的真读方），
但两主体的**会话驱动路径**存在结构性阻断，当时判「推不开」，记录如下：

- 收束闸（`turn_runner::closure_gate`）两臂：发言臂问 `reply.first`、产物臂问 `produce.artifact`。
  两行独持主体**两臂全不命中** ⇒ `closure_denied` ⇒ `v2_exec` 跳过全部派生事实
  （承诺 / 任务 / 记忆）——planner 立了任务也不落格，verifier 的判定没有承载事件。
- 给行硬加收束能力（如让 planner 持 `produce.artifact`）= 推翻 T-123 规格（「二者互不可写」
  的 C15 结构 + verifier 不持产出的语义）；硬把两臂改成「或」= 放宽所有人的收束条件。
- 先例参照：reflex（`PreemptionDecider`）/ arbiter（`EliminationDecider`）/
  autonomous（`AutonomousInitiator`）都是**规则驱动组件**而非会话——「何时规划 / 由谁触发验证」
  大概率也该是组件形态（发起模型不同：规划挂在任务链头，验证挂在产出之后），但这是新子系统设计，
  T-107 不顺手定。

本任务承载这份裁决与（若落地）路径。三行的登记行与写侧闸事实见
[T-123 §3.1](../009-task/123-多步任务与返工.md "T-123-多步任务与返工")。

## 处理过程

- 2026-10-16 **裁决（status: done）：形态 = (c) 维持现状，会话驱动路径不建**。三形态逐一评过：

  - **(a) 收束闸加第三臂（工作臂问 `define.work`）**：否。收束臂只解决「格子落不落」，
    不解决「格子给谁用」——规划者会话立的 task 格落它自己的 WAL，而 readyset /
    执行消费方（`v2_tasks::prompt_section`）读的是**执行会话自己的**事实源，
    跨会话任务事实流不存在。(a) 因此实为一个子系统（收束臂 + 跨会话任务流 +
    消费方语义），不是一行代码；无消费方拉动不建。
  - **(b) 规则驱动组件**：是**独立验证**的正确方向（reflex / arbiter 先例：行给
    事件 actor 与闸授权，执行路径是编排器里的代码路径），但今天没有「任务完成度
    的真实消费方」（T-123 §3.1 完成度追求诚实留空）——没有「谁来验收、验什么」
    的数据，组件无从定义。**登记为未来能力**（T-123 §8），触发条件 = 出现
    任务完成度的真实消费方。
  - **(c) 维持现状**：**采纳**。规划本身今天就是会话主体的轮内能力（Reasoner +
    `todo_write` 资格闸，T-107 落的读方）；两行的语义钉死 = **资格行**（任务表
    写侧闸的读方 + 委派身份的 actor 权威——`--agent planner` 的委派子会话可作
    规划顾问，收束答复经工具结果回流父会话，收束格不落但答案照回，t73 同款
    记录面）。

  裁决落 [T-123 §3.1](../009-task/123-多步任务与返工.md "T-123-多步任务与返工")（行列改记裁决）+ §8（独立验证登记为不建的未来能力）。
  **不触及 `symbio_core` 事件词汇或公共面**（零改动）⇒ exit ① 的 ADR 分支未触发，
  无需放宽决策。验证：`node scripts/gate.mjs` 全绿（docs 面全过）。
