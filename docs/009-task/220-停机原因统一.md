## 内容

父设计：[PL-016 · 义务环](../004-plan/016-义务环.md "PL-016-义务环") §4.3

**先纠正一个前提。** 初稿说"停机原因无统一载体"——不完全对：载体有三个，
而且**三个形状问的是同一个问题**。

| 形状 | 出现在 | 说什么 |
|---|---|---|
| `payload.status` ∈ `completed` / `failed` / `aborted` | 全部收束格（`with_status`） | 结果是哪一类 |
| `payload.terminated.reason = "aborted"` | 中止收束格（`with_terminated`） | 为什么中止 |
| `payload.why` | 兜底收束格（`settle.rs`） | 为什么兜底 |

**真正的缺口是这三者语义重叠且都不够用**：

- `status: completed` 里混了「自然说完」与「策略终止后收束」——后者不是"说完了"。
- `status: aborted` 里混了「用户打断」与「上界耗尽」——前者是用户的决定，后者是系统的失败。
- `terminated.reason` 只有一个取值 `"aborted"`，等于没有信息。
- `why` 是自由文本，不可判。

**于是"这一轮为什么停"这个问题，今天只能靠读三个键 + 猜**。而它正是重启后
最需要回答的问题：PL-014 §3 规则 f/g 要求终止必须落事实，义务环里更是没有 `Halt`
这个值——"停"只有一种表达，就是"没有债了"，那么"为什么没有债了"必须写在事实里。

**补法**：统一到 `reason`，取值闭集，必填。

| `reason` | 谁写 | 含义 |
|---|---|---|
| `completed` | 正常收束 | 说完了 |
| `interrupted` | 中止收束 | 用户打断（或首请求前到达的中止） |
| `exhausted` | 上界收束 | 步数 / 预算耗尽 |
| `fallback` | 兜底收束 | 主路径失败，兜底顶上 |
| `denied` | 收束闸拒绝 | 见 [T-219](219-拒绝落事实.md "T-219-拒绝落事实")——注意它**不产生收束格**，`reason` 落在 `authz.denied` 上 |

**`status` 保留，但只留结果面三值**（`completed` / `failed` / `aborted`）：
结果与原因是两个维度，合成一个字段会让"失败且被拒"这种组合表达不出来。
**`terminated.reason` 与 `why` 退役**——它们的内容进 `reason`，`terminated.at` 保留
（那是时刻，不是原因）。

**义务环里的额外收益**：PL-014 需要一个运行期分支 `None => halt(NoRule)`
（"没规则可用了"也是一种停机）。义务环里**这个分支不存在**——装载期"每行收口"
保证每种应答都有归宿，规则缺口在装载期就被拦住。所以 `reason` 的闭集里
**没有 `no_rule`**，这不是遗漏。

## 判据

| # | 判据 | 检查方式 |
|:-:|---|---|
| 1 | 每条 `turn × closed` 的 `reason` 非空 | 审计断言（`invariants`） |
| 2 | `reason` 在闭集内 | 同上，越界即红 |
| 3 | 四种终止各自可达 | 反向用例：逐个产生点构造，缺一个就红 |
| 4 | `terminated.reason` / `why` 不再被写 | 静态扫描：`turn_runner/` 下无这两处写入 |
| 5 | 读侧不被破坏 | 全量 e2e；前端与 `cli` 若读 `why`，同批改成 `reason` |

## 处理过程

- 2026-10-21 立项。来源：PL-016 §4.3 的核对——缺口不是"没有载体"，是**三个形状重叠且都不够用**。
  任务范围因此从"新增 `reason`"改成"把三个形状收成一个 + 补全取值"。
- 2026-10-21 为什么 now：独立于形状（与表无关），且 `turn.closed` 的产生点只有四处，
  协议名一收敛（T-224）这些点要跟着改一遍——现在做成本最低。
- 2026-10-22 施工。五处核对把方案改小了，也改对了一处前提：

  **订正一：`turn × closed` 有六个产生点，不是四个；且横跨两个事件名。**
  `prepare`（定稿答话）/ `reflex`（反射档）/ `stream`（正常收束 + 中止）/
  `settle`（兜底 + 中止）。兜底格的事件名是 `chat.assistant.fallback`，
  **与收束格不是同一个名字**——`closes_turn` 因此要同时认两个。另：`stream.rs`
  里那条 `status: "pending"` 在 `turn × progressed` 格，**不是停机格**，不在本任务范围
  （它在等用户，没有"停"）。

  **订正二：`exhausted` 立项时没有产生点，本任务补上。**
  设计表里写了"上界耗尽"，但代码里 `ModelFinishReason::Length`（max_tokens 掐断）
  只存在于 `TurnOutcome.finish`，**从不落格**——被掐断的一轮与自然说完的一轮在日志上
  完全同形（都是 `status: completed`）。这正是 §"真正的缺口"描述的那种混淆，所以补了
  `reason_of_finish`：`Length ⇒ exhausted`，其余 `completed`。`status` 仍是 `completed`
  （答出来了，只是没答完）——结果与原因两个维度在此分开。
  残留：`ContentFilter` / `Other(String)` 今天也走 `completed`。不新立取值，因为闭集的
  意义就在于可穷举；这一处残留记在这里，等真有用例再收敛。

  **订正三：`why` 的内容不是停机原因，是细节——所以它不能简单删掉。**
  立项时写"`why` 退役、内容并入 `reason`"。核对后：`why` 装的是 `AdapterError::to_string()`
  （"模型返回 429"这类原文），而 `RuntimeOutcome::Failed { error }`、`transcript` 投影的
  兜底行、`rebuild` 折回节点的 `error`、`prompt_fidelity` 的正文比对——**四处读侧都靠它**。
  删掉它，用户看到的兜底行就空了。所以拆成两个字段：`reason`（闭集，可判、可统计）
  + `detail`（自由文本，只给人读）。**只许对 `reason` 做分支。**
  `terminated.reason` 则真退役（恒为 `"aborted"`，与顶层 `reason: interrupted` 是同一件事
  的两份账）；`terminated.at` 保留——那是时刻，不是原因。

  **订正四：`why` 在别的格子上仍然合法。** `commitment.breach` / `memory.consolidated` /
  `worker_progress` 都写 `why`，那些格子**没有竞争的 `reason` 字段**，不存在混淆。
  S-016 的范围因此收在三个构造点文件，不扫整个目录——范围写大了的规则比没有规则更糟
  （首批就误命中 `with_terminated(with_reason(..))` 与 `memory_events`，各改一轮正则）。

  **判据 4 的形态换了。** 原写"静态扫描 `turn_runner/` 下无这两处写入"——正则表达不了
  "哪是停机格"。落成 S-016：三个构造点文件里 `terminated.reason` 与停机格 `why` 零出现，
  配五条回归用例（两个形状各自即红 / 新形状与合法组合放行 / 别的格子不误伤 /
  注释行不判 / 空理由不算豁免）。
