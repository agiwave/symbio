## 内容

父任务：[T-236-义务环符合性收口批](236-义务环符合性收口批.md)。
来源：[T-244-唤醒事实接入与resume旁路退役](244-唤醒事实接入与resume旁路退役.md) 步 5e 的 CLI 实测对账。

**事实**：最短的那条生产路径——`classify` 判 `Answered` 的**短路轮**（定稿答话轮）——
它的收束格由轮首准备**就地**落，不经 `close-turn` 行。

CLI 实测（会话 `verify-t244-a` 幕一，58 格 / 11 组往返）：

```
seq 3   request  {via:"compose/wording", port:"model"}   ← 措辞产线的模型往返
seq 4   sent     {id:"model-0-d0-w0", port:"model"}
seq 5   response {id:"model-0-d0-w0", port:"model"}      ← 载荷里**没有** calls
seq 6   turn.stage {stage:"decide", reason:"from_context"}
seq 7   turn.dispatch
seq 8   chat.assistant.final {reason:"completed"}        ← prepare 的 1b 分支就地落的
```

这一轮**没有** `request(port=turn)`、没有 `execute-turn` 派发、没有 `close-turn` 派发：
`execute_final_reply_turn`（`turn_exec/persist.rs`）把答话交给运行器
（`TurnInput::final_reply`），运行器的轮首准备 1b 分支（`turn_runner/prepare.rs`）
落完收束格就 `PreparedFlow::Done` 返回——**驱动循环压根没进**。

对照同一会话幕二（工具轮）：`execute-turn` → `open-tools` → `authorize-tool` →
`dispatch-tools` → … → `close-turn`（执行体 `close`）→ `chat.assistant.final`。
收束格在那一轮是**行表派发的**。

## 为什么它进不了 `close-turn` 行（这不是实现取巧）

`close-turn` 的前件是 `turn.closeable`（[ADR-121](../010-adr/121.md) 决策 2）：

```
closeable = ¬closed ∧ (has_final ∨ model_outcome_failed)
has_final = ¬closed ∧ 本幕最近一条 response(port=model) 的 `calls` 为空
```

短路轮的那条 `response(port=model)` 是**措辞产线**的往返，它的载荷里**没有 `calls` 这一格**
⇒ `has_final` 取不到数组 ⇒ 不成立；`model_outcome_failed` 也不成立（没有 `failed(port=model)`）
⇒ `closeable` 为假 ⇒ **`close-turn` 这一行对这一轮永远开不出账**。

即使把 `calls: []` 补上（[ADR-122](../010-adr/122.md) 决策 5 写的是「一次真实往返 ⇒
`calls` 为空数组」），前件就成立了一半；剩下的一半是**驱动循环压根没进**：1b 分支
`PreparedFlow::Done` 提前返回。改成 `Run` 之后，`execute-turn`（60）会**同时**欠账
（`tools_open = false` 对这一轮成立），于是「收束行开不出账 ⇒ 驱动去跑一次模型往返」——
而这一轮的定义就是「一次模型请求都不发」。这是本任务真正的难点：**前件与驱动两处
都得同时解决**，否则短路轮会变成「多打一次模型的轮」。

## 三个候选形状（裁决时挑一个，理由写在 ADR 里）

1. **前件走日志 + 驱动进环**：给短路轮一个日志上可判的前件（措辞往返的
   `response` 带 `calls: []` ⇒ `has_final` 成立；或新增一条领域格 / 视图字段），
   同时让 1b 分支改为寄存结局、返回 `Run`，由 `close-turn` 行的执行体落格。
   **要一并回答**：模板产线（`compose` 没挂上 / 措辞为空 ⇒ 那一轮**没有**任何
   `response(port=model)`）时前件怎么判？答不上来就退化成「多打一次模型」。
2. **零模型往返的轮不进环**：明文裁决「收束行覆盖的是**派发过模型往返**的轮」，
   短路轮的行首准备就地落格是**方案允许的形状**，把它写进 PL-017 §3.1 的覆盖边界，
   并把「`close` 执行体是两条收束格的唯一写方」这句限定成「**在执行体之间**」（它
   本来就只约束执行体之间的写集不相交）。
3. **短路轮也走驱动，但前件是「本轮已有一条 `response(port=model)`」**：与候选 1 同源，
   差别在措辞产线那一轮**零往返**时（模板线）仍要有形状——多半要一条新的日志事实。

## 验收口径

1. 裁决先行：一条 ADR 或 PL-017 小节写明选哪个候选、其余两个为什么否掉；
   未裁决不动模块（`AGENTS.md`「架构改动：只认方案为源」）。
2. 裁决落地后，`chat.assistant.final` / `chat.assistant.fallback` 的写方**唯一**：
   `grep` 断言 `turn_runner/prepare.rs` 里不再有这两格的就地落格（收束格只由
   `close` 执行体写），或（候选 2）明文写清「就地落格是允许的」并把该断言的
   口径改成「执行体之间唯一」。
3. 用例：一条钉住**短路轮**的收束格落点（候选 1：收束格由 `close-turn` 行的执行体落，
   断言 `[Loop] 派发 close-turn` 那一行；候选 2：断言就地落格且不派发任何行），
   加一条**反例**：把前件退回 `has_final` ⇒ 短路轮用例转红。
4. CLI 复验：一条**纯问答**实测会话（短路轮）+ 一条工具轮会话，
   `node scripts/obligation-ring-accept.mjs --homedir=.symbio --session=<短路轮>
   --session=<工具轮> --cli-log=<日志> --strict` 全项通过。

  模型不再参与），差别只在答话怎么来的；按「有没有 `response(port=model)`」分叉，会把
  一条产品路径拆成两套调度形状，而且**零往返的那一半判不出来**（模板产线同形却无格）。

  内存草稿，前件只能靠外形猜），要么把收束格溯源改挂到措辞往返上，后者直接破 I2。
  于是裁决「环调度的是欠着的往返」：定稿轮一件不欠，收束格就地落是允许的形状。

  用例的作用不是「证明实现对」，而是**把不对称钉住**：表对这类切片给出的答案就是
  `close-turn`，而产品路径不进驱动、表不被问——不钉住它，下一个人会照本任务的第一版
  判断（「该派发却没派发」）再追一遍。
