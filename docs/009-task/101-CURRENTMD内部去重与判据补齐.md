## 内容

用户指出：`CURRENT.md` 内有不少重复内容，且已收集的信息不该在其它文档重复描述；要求系统
梳理文档体系——分工是否合理、内容是否重复、机制是否完备。

逐条量化后确认**这不是观感问题，是可数的事实**：

| 重复项 | 数量 | 性质 |
|---|---|---|
| 工具短名 | §2 列 25 条，§6.1 **也**列 25 条，交集 **25/25** | §2 第三列是人写的 `TOOL_NOTES`（20 条）——生成器里唯一的手写内容 |
| VDFS 操作 | §3.2 列名 13 个，§6.2 **也**列 13 个 | §3.2 第二条的 9 个工具短名 **9/9 已在 §6.1** |
| 路由 | §1 列 20 条，§6.3 **也**列 20 条 | 同一批字符串两个切面 |
| 路由条数 | §3.1 报「20 条」，§6.3 首行再报一次 | 同一数字两处 |

**根因是机制性的**：T-098 新增 §6 时**没有删掉它覆盖掉的 §2/§3 内容**。新增一节而
不撤旧 owner，同一批事实就并存两遍——而 §2 的备注列恰好是这份「代码投影」里唯一
会漂移的东西：它与代码提取的 description 逐条讲同一件事，代码改了它不改，看起来
却和别的列一样是「从代码来的」。

  同时把两条既有判据的定位从**写死节号**改成**按内容定位**——`/^### 6\./` 在提位那一刻
  匹配不到，循环体一次都不进，断言 `bad === []` **恒真**。恒真的守卫比没有守卫更坏：
  它占着判据码，让人以为这一族已被守住。
- **判据的三次自我修正**（都是当场红给自己看的，记在这里因为它们比判据本身更值得留）：
  1. 首版按**字面形状**判身份（`` | `x_y` | `` 算工具、`` | `a/b` | `` 算路由），
     在本仓**当场三处误报**：插件总表第一列是插件目录名（`agent`、`web`，形状与工具短名
     无差别）；VDFS 操作 `vdfs/read` 形状与路由**完全一样**；代码规模表的 `symbio/src`
     也是 `词/词`。改按**集合成员身份**判——`vdfs/read` 不在路由集里，`symbio/src` 哪儿都不在。
  2. 只判**表格**时，注入验证**当场漏过**当年的 §3.2——它根本不是表，是 ` · ` 串起来的一行。
     改成按**块**（空行分隔的连续行）归集后又漏过一次——那是**每行一个 bullet** 的列表块。
  3. 跨文档首版也判散文块，**三处误报**且理由各不相同：AR-013 在讲每个操作的**机制**、
     RE-001 那处是 gateway **只读白名单**（配置值碰巧由操作名拼成）、T-056 在描述要删的
     e2e 用例。共同点是**散文里点名 N 个成员是在讲机制**，机制归各自的 owner。
     故跨文档**只判成表**，文件内散文块照样判（生成器我控制，写成散文块一样多余）。
  - 结论写进判据注释：**跨文档只判成表**；文件内表格与散文块都判。
  - 另一条已知边界同样写明而非掩盖：**成表不足以判定复述**——一张表可以**以成员为键**
    而讲另一件事（session README 的「工具名 → 结果取哪个字段」）。白名单每条都写明
    **它保的是什么**，新增一条必须同样写清。
