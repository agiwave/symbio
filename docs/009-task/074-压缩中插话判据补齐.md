## 内容

[RE-005](../006-ref/005-e2e覆盖矩阵.md "RE-005-e2e覆盖矩阵") 四个缺口里三条有归宿（`t53` 已清偿、MCP 断连挂靠 [T-129](../009-task/129-外部执行与熔断.md "T-129-外部执行与熔断")、WS 断链明确不做
且写明撤销须另立任务加 ADR），只有「压缩进行中用户插话」停在「暂不补（待评估）」——
一个既不是排期也不是裁决的悬置态。本任务把「待评估」推进成二选一。

现状判据面：压缩侧在 `t18`（水位触发 / 熔断 / 重试恢复），插话侧在 `t34`（忙窗插话抢占），
**两者的交叠窗**（压缩进行中收到插话）没有用例钉过——这正是矩阵自记「读数无生产出口」处。

## 处理过程

- 2026-10-13 登记（[RE-005](../006-ref/005-e2e覆盖矩阵.md "RE-005-e2e覆盖矩阵") 缺口表「待评估」悬置态收口）
- 2026-10-16 清偿：选「落一条新 e2e」分支，新建 `e2e/cases/t63-compression-interjection.mjs`。
  判据 = 压缩进行中（摘要请求在飞）从 gateway HTTP 边界发插话，插话**不丢**、按排队顺序
  在压缩收敛后被消费；与 `t34` 忙窗插话判据同形（忙窗从「工具轮在飞」换成「压缩轮在飞」）。
  **生产出口的确立**是本条的关键收获：压缩中的插话既不在实时面（SID 作用域的 WS 帧
  要等轮次收敛才推），也不在转写（收敛前无 Text 节点可读）——两者都是「事后出口」。
  真正能判「插话没被吞」的是 **mock-llm 的请求记录**：收敛后第一轮的主线请求里，
  插话的用户消息必须在场（按序）。这把「MockLLM 请求记录 = 模型视角的生产出口」从
  T-096 的契约面反哺回行为面，RE-005 缺口表该行随之改判「已清偿」。
  实现教训：REPL 会话 id 必须取**被测会话 SID**——写成中立 id 会让 `cli.send` 的发言
  进错会话，实时面永远等不到（首轮填充 60s 超时的症状）。
