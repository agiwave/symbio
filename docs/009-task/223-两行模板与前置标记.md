## 内容

父设计：[PL-016 · 义务环](../004-plan/016-义务环.md "PL-016-义务环") §2.3

**两行主模板 + 一条通用租约行**——每端口固定两行，差异只有 `by` 一个字段；第三行由
`PortDecl` 参数化，不随端口手写：

```
行 A  dispatch-<port>   owes:   request(port=<port>, id, attempt)
                        until:  sent(port=<port>, id, attempt) | failed(port=<port>, id)
                        before: sent                        ← 引擎在运行前落
                        by:     courier

行 B  await-<port>      owes:   sent(port=<port>, id, attempt)
                        until:  response(port=<port>, id, attempt)
                              | failed(port=<port>, id)
                              | retry(port=<port>, id, attempt)
                        by:     None                        ← 全部差异就在这个 None

行 C  lease-<port>      owes:   stale_sent(port=<port>)     ← 视图，带 now
                        until:  response | failed | retry（同一 id / attempt）
                        by:     lease_keeper
                        unless: attempt ≥ max_attempts       ← 由视图折成布尔
```

**`sent` 为什么必须由引擎写，不能由搬运者写**：搬运者的 `run` 可能**不产生事实就返回**
（异步派发就是这样）。如果 `sent` 由搬运者写，那么"派出去了"这件事依赖搬运者自觉；
一旦它忘了，`dispatch` 行永远不还清，环就死在那里——而**它不报错**。
所以引擎在调 `run` **之前**落 `sent`（`before` 字段），这是引擎仅有的几个写动作之一
（其余是追加执行体交回的事实、`Err` 时写 `failed`、中止 / 上界时写收束格）。

**`sent` 之后崩溃怎么办**：`await` 行 `by = None`，没有应答就永久 blocked——这正是
PL-016 §2.6 第 7 条的缺口。`lease` 行补上：`stale_sent` 视图把"发送超过 `lease_ms`
仍无应答"折成 `stale:true`，`lease_keeper` 按 `max_attempts` 决定重试还是判死。
重试落 `retry{attempt}` + `request{attempt+1}`；旧尝试由 `retry` 收清，新尝试走
`dispatch` → `sent` → `await`。**幂等键是逻辑 `id`**，重复派发由适配器按 `id` 去重。
`retry` 的 `FactDecl` 在本任务补上（T-221 首批只声明四条协议事实）——**声明按事实名一次，
不按端口重复**；名字已在 T-224 入了 `CELLS`，这里不碰网格。

**`Wait` 折叠**：`by = None` 对 `drive` 是透明的——恒 `blocked`、永不选中。
它存在的理由不是"它是一类债"，而是让 `open ≠ ∅ ∧ actionable = ∅` 这个状态**可表达**：
"在等"与"没事"必须能区分。**这是"这笔账不由引擎执行"的唯一声明位。**

**`Ask` 折叠**：`request{port:turn}` 是一行普通的 `dispatch` 债。
PL-014 §3 自己写了 `Ask` 是 `Act(Model 行)` 的特例、"工程取舍不是逻辑必然"——
本任务兑现这条自认。**但预算档位不能丢**：今天 `Ask` 独立成值是为了把
`RuleOnly` / `ClassifyOnly` / `FullModel` 三档 ZST 闸在类型上（PL-001 §10）。
折叠后这层闸门必须落在 `Effects` 上（`Row.effects` 已有这个字段），
**不能因为 `Ask` 没了就把档位也丢了**——这是本任务最容易做丢的一处。

**为什么首端口是 `turn` 而不是 `model`**：`turn` 执行体内部仍是今天的
`run_with_tools`，零内部改动；控制面只看到"这一轮该执行 / 已派出 / 回来了"。
把模型调用本身变成债，需要把 `run_with_tools` 的模型→工具→模型内环倒过来——
那是 PL-014 步骤 1 / PL-017 的范围。硬塞进本任务会顶穿 T-216 的 300 行熔断线，
而熔断线的含义正是"抽象错了"；这里抽象没错，是**批次放错了**（PL-016 §2.7）。

**在途进日志，是这一整步换来的东西**：今天"在途"是内存里的一个集合，崩溃即失忆；
折叠之后 `in_flight = sent ∧ ¬(response | failed | retry)` 是个**视图**，重启后从日志
重建。崩溃恢复因此第一次能回答"上次死的时候还有哪些**轮**没回来"。
**诚实的边界**：这一批的粒度是轮；单次模型 / 工具调用要等 PL-017。

**施工顺序**：先只做 `turn` 这一个端口（三行），跑通 e2e，再按需铺工具 / 时钟 / 存储。
一个端口跑不通就铺开，会在四处同时埋同一个错。

**明确不做**：不新增机制键（`before` 已在 `Decl` 里，`courier` / `lease_keeper` 是普通
执行体名）；不在本任务里倒置 `run_with_tools`；不做模型 / 工具的单次调用端口。

## 判据

| # | 判据 | 检查方式 |
|:-:|---|---|
| 1 | 加一个端口 = **0 个新事实名** + 1 个 `PortDecl` + 1 个适配器 + 2 行主模板，`drive`/`owed` diff = 0 | 源码级断言 |
| 2 | `sent` 只由引擎写 | 静态扫描：搬运者的 `run` 不产出 `sent` |
| 3 | 搬运者返回空事实时引擎写 `failed` 而不是静默挂起 | 用例：`run = Ok(vec![])` 且无进展 ⇒ 收束 `exhausted{no_progress}`；`run = Err` ⇒ `failed` |
| 4 | 崩溃后 `in_flight` 可从日志重建 | 用例：只给日志，不给内存状态 |
| 5 | 预算档位仍被闸住 | 用例：反射档请求模型 ⇒ 拒绝（档位在 `Effects` 上生效） |
| 6 | 重复派发有幂等键 | 用例：同一逻辑 `id` 二次 `run`，适配器按 `id` 去重；`sent` 按 `(id, attempt)` 不重复落 |
| 7 | `sent` 无应答时租约能重试或判死 | 用例：只给 `sent`，推进 `now` 超过 `lease_ms` ⇒ `retry` 或 `failed` |
| 8 | 尝试号进键，旧尝试被 `retry` 收清 | 用例：两次尝试的 `response` 不会互相收清 |

## 处理过程

- 2026-10-21 立项。前置 T-222（表化）——没有 `Decl` 就没有 `before` 字段可挂；
  协议名与判据门禁（T-224）也必须在之前——名字不入网格，首次 `append` 即 `OffGrid`。
- 2026-10-21 一处已识别但需在实现时复核的风险：`sent` 是**每条搬运路径多一条事实**
  （PL-016 §7.2 代价 2）。若某端口的调用频率高到让日志膨胀，需要在 T-223 之后
  重新评估——但**不能靠"不落 sent"来省**，那会把崩溃可判别性一起省掉。
- 2026-10-22 范围收准：首端口从 `model` 改成 `turn`。原写法要求把模型调用变成债，
  但模型调用在 `turn_runner` / `turn_exec` 里，不在本任务的文件面内；按原写法施工
  等于在 T-216 里重写 `run_with_tools`，与 300 行熔断线冲突。裁决见 ADR-115 决策 5，
  细粒度端口移交 PL-017 / T-227。同批补上租约行：没有它，`sent` 之后崩溃会让
  `await` 永久 blocked——初稿的"崩溃可判别"只做到了"看得出在等"，没做到"能恢复"。
