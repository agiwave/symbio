前置已完成：步骤 0–5 全部落地并各自成提交（施工账见
[T-165-控制面收敛](165-控制面收敛.md "T-165-控制面收敛")，末批裁决见
[ADR-074](../010-adr/074.md "ADR-074")）。PL-014 的禁令随之解除——**在此之前启动本步只是搬家**，
因为驱动器还认 v1 外壳的簿记，切片边界对不上运行时的真实依赖。

判据只有一条硬的：**每个插件可独立卸载且系统仍完整**（v2 切分不得妥协的原判据）。
「切成五个目录」不是成果，「卸载其中任何一个都不塌」才是。

### 为什么先审再切

步骤 1–5 把执行路径收成了**单环 + 一张能力表**，于是切分边界第一次可以用**注册表里的行**来描述，
而不是用文件归属来猜。现状里三件事已经成立，先认清它们，别把已完成的事再切一遍：

- **记忆面已有独立插件**：`plugins/memory` 是长期记忆与工作区两腿的持有者（一个插件、两个实例的分形），
  session 侧只剩 `memory.rs` + `v2_memory.rs` 那 716 行（非测试）的**会话视图**（召回段排版与目录作用域判定）。
  这 716 行是「宿主侧的读法」还是「独立一片」，要先裁决再动手。
- **工具面已有注册通道**：`plugins/local` / `plugins/mcp` / `plugins/vdfs` / `plugins/agent` 各自把工具
  以能力行交进 `Registry`（RE-006 §2.1 的 19 条里 session 只贡献 `heartbeat` 一条）；session 的 `tools/`
  是**分发与执行**基础设施（`tool_executor` 族、`tool_result_guard`、`decls` / `task_table`），
  不是工具清单。切这里的判据是「`DispatchPort` 这条口能不能从宿主里摘出来」，不是行数。
- **上下文与请求视图是策略行的宿主**：步骤 3–4 之后，水位策略与裁剪段已经能从表里读；
  `context*` + `message_build*` + `tokenizer*` 那 6,250 行里有多少属于「视图构造」这一职责、多少属于「压缩执行」，
  与 [T-166](166-上下文淡化层级未接入v2请求.md "T-166-上下文淡化层级未接入v2请求") 的裁决**互相制约**——
  三层淡化的接入方式一旦改变，`context/` 的边界就跟着变。两件事的先后顺序要在 ADR 里写明，
  不要先切再改。

### 施工批次（待 ADR 定稿后逐批展开）

先立 ADR，再按 ADR 定的顺序逐批搬。以下顺序按「搬不动的风险最高先做」估的，ADR 可以推翻它：

1. **审切片与依赖**：以注册表的行为单位列出每条能力/策略依赖什么状态（`Run` 的格、
   `TurnState` 的格、store 句柄），凡「依赖宿主私有状态」的切片登记为留守，并写明理由。
2. **第一个搬出去的一定是最小那片**：能独立卸载这件事需要一条守卫来钉，第一次做这条守卫
   要在影响面最小的片上练手，不要第一刀就切驱动器。
3. **驱动器（`loop`）单独立片是最后一步**：`chat_loop` + `turn_runner` + `v2_exec` + `orchestrator`
   是 10,143 行（含测试 17,800）的环，它卸载后 session 只剩存储与生命周期——那才是「系统仍完整」的最强形态，
   也是 [AR-015-core-loop](../../symbio/src/plugins/session/docs/015-core-loop.md "AR-015-core-loop")
   描述的形状能不能真正拆开的验收。**搬之前它必须已经是纯的**：步骤 1–5 之后它对存储的唯一
   触点是 sink 与句柄，这一点要在 ADR 里逐条核。
