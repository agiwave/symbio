## 内容

地址解析规则（`physical.rs::join_target`）是**有意**的：首部的 `/` 只是地址分隔符，
相对工作目录；只有带盘符或真根的路径才直用（资源面另有一支，其根名归 `plugins/vdfs/fs.rs` 所有）。
规则本身没错，错在**结果不回读它**：写类工具把**入参**原样塞进 `path` 与人类文案里，
于是解析这一步对用户（对模型）是不可见的。

实测（会话 `cli1a1421b7ecf0`，模型按 POSIX 习惯打了绝对地址）：

```
入参   {"path":"/Bing/symbio/tmp/cli-smoke.md"}
vdfs_write → {"created":true,"message":"已创建文件 /Bing/symbio/tmp/cli-smoke.md",
              "path":"/Bing/symbio/tmp/cli-smoke.md","success":true}
vdfs_read  ← 同一条入参 ⇒ 读回内容，模型据此宣布「已验证存在」
```

而字节实际落在 `<仓库根>\Bing\symbio\tmp\cli-smoke.md` —— 工作目录下多出一棵
`Bing/symbio/…` 的**影子树**。写与读都报成功且都回显同一个错误地址，
所以这条链上**没有任何一处**能发现落点不对：自我验证把缺陷闭环了。同一形状还让
「写到了仓库外」这类误伤变成「写进了仓库里没人看得见的目录」——更难发现。

本轮已做掉的是**文案格**（`PATH_DESC`，八份工具 schema 共用这一个 owner，已写明
`/` 不是文件系统根、绝对 POSIX 地址会造出重复目录树）；文案只能降低发生率，
**消不掉**它：只要结果里没有解析后的落点，模型（和人）就没有核对的手段。

修法边界：只在**返回载荷**上补一格 `resolved`（`physical.rs` 已经有那个值，只是没往外给），
不改 `join_target` 的语义——那是既有的地址契约，改它属于另一件事（要不要拒绝工作目录外的
绝对地址，先立 ADR 再说）。
