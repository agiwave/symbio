## 内容

本任务由 [T-076](076-e2e面缺失补齐批.md "T-076-e2e面缺失补齐批") 的面审计开出。
RE-005 的「多协议适配」行自开行起就写着同一句话：**e2e 只走一条 SSE 形状**
（OpenAI Chat 形，由 t1 族承载）。而 ADR-004 决策的是**四套**适配器——
`openai_chat` / `openai_responses` / `anthropic_messages` / `gemini_api`。
「同一套代码对接四家」这条架构主张，目前只有各协议自己的 Rust 单测在守，
**端到端一条都没有**。

### 为什么这一行**不需要**能力新增（与 T-109 / T-110 不同）

驱动面齐备，全部在配置里：

| 适配器 | 请求路径（由 `api_base` 拼出） | 配置位 |
|---|---|---|
| `openai_chat` | `{api_base}/chat/completions` | `api_protocol` · `api_base` |
| `openai_responses` | `{api_base}/responses` | 同上 |
| `anthropic_messages` | `{api_base}/messages` | 同上 |
| `gemini_api` | `{api_base}/models/{model}:streamGenerateContent?alt=sse&key=…` | 同上 |

`ModelProviderConfig` 的 `api_base` 与 `api_protocol` 都是 `provider.json` 里的普通字段
（`model_providers.rs:48,62`），`e2e/helpers.mjs::providerConfig` 已经能把 `api_base`
指向本地 mock。所以缺的只有一件事：**mock-llm 目前只认 `*/chat/completions`**
（`mock-llm.mjs` 的 `url.pathname.endsWith('/chat/completions')`），其余三条路径会落到
404 分支。

### 要做的两件事

1. **mock-llm 扩成按路径分派**：保留现有的 OpenAI Chat 事件构造器不动（t1–t63 全靠它），
   新增三套线格式的 `buildEvents` 变体 + 各自的路由分支。三套的 SSE 形状各不相同
   （`responses` 的 `response.output_text.delta` / `anthropic` 的 `event:` 行 +
   `content_block_delta` / `gemini` 的 `candidates[].content.parts[].text`），
   而**故障注入与流控制（`dropAfter` / `stallAfter` / `malformed`）应当共用一套**
   ——它们是「网络层」的事，与线格式无关；各写一份必然漂移。
2. **一条用例**：同一句用户发言 + 同一次工具调用，在四个 `api_protocol` 下各跑一遍。
   判据：CLI 正文一致、工具回路成立、转写不变量成立。**不是**「四条用例」——
   协议是同一个被测链路的参数，按参数展开比复制四份文件更能暴露「只有一家对」的漂移。

### 边界（写清不做什么）

- **不做**四家的全部差异面（各自特有的字段、错误形状、多模态块）：那是各协议单测的
  地盘，e2e 只回答「换协议后用户链路还通不通」。
- **不做**真实 provider 的形状对照：那是 `e2e/ab/`（门外，不进任何门禁）的职责。

## 处理过程

- 2026-10-15 登记：T-076 面审计逐插件核实驱动面时确认——四协议路径与配置位均已在位，
  唯一缺口在 mock 侧。
- 2026-10-15 落地：`e2e/cases/t66-multi-protocol.mjs`——**一条用例按 `api_protocol`
  参数展开四次**（同一个 `for` 循环换协议），判据只取用户可见出口（CLI 正文 /
  mock 侧请求体 / 转写读出口）。
  - mock 侧改造（`e2e/mock-llm.mjs`，**未动生产代码**）：`resolveFormat` 按路径分派
    四种线格式；`readTurn` 做**格式无关**的「用户文本 + 工具结果轮」判定（四协议承载
    形状不同——工具结果分别是 `role:"tool"` / `function_call_output` / `tool_result` /
    `functionResponse`）；三套新线格式的 frames 构造器（responses / anthropic / gemini）；
    通用流写出按格式分派 `frames` + `terminator`，故障注入（`dropAfter` / `stallAfter` /
    `malformed`）四格式共用一套。openai_chat 逐字节不变（t1 / t2 回归绿）。
  - **两处核实订正**（原任务文档写错）：①gemini 路径**无 query**（旧写
    `?alt=sse&key=…` 是错的——`get_api_url` 只拼到 `:streamGenerateContent`，key 走
    `x-goog-api-key` 头）；②gemini 消费的是**裸 JSON 数组流**而非 SSE
    （`parse_line` 直接对整行做 JSON 解析、不 strip `data:`，且显式跳过 `[` / `]` / `,` 行）。
  - **两处负向自检**：禁用 gemini 分派 ⇒ gemini 轮 404 变红；破坏 anthropic 工具结果轮
    判定 ⇒ 该轮落默认回复、stdout 断言红。
  - 全量门禁绿，`BASELINE.e2eCases` 63 → 64。
