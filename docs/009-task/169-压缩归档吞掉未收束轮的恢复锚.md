## 内容

父任务：[T-167-会话插件切分](167-会话插件切分.md)（P6-② 施工复核表逐点定窗时撞出来的，属既有缺陷，
与 `range` 语义归一无关——归一前后同一段代码读的是同一批事件）。

**形状**：一轮停在「等用户动作」上时，它在事实源里只有用户格（`turn × opened`），
收束格刻意留给恢复幕（[ADR-067](../010-adr/067.md) 决策 3）。而压缩落格后立刻 `archive_before(新快照 seq)`，
把 `seq` 在它之前的**一切**移出 live 段——其中包括那一轮的用户格。触发只需要
「轮 k 未收束期间发生过一次落格」，与它是不是同一个请求无关：

```
turn k 开格（awaiting approval，无收束格）
  → 此刻任何一次压缩落格：
      · 轮外路  retry_compaction（process_resume 在循环**之前**调用，见 pipeline.rs:797）
      · 轮内路  夹在中间执行的另一个执行轮（close_turn 注册的压缩寄存在它的下一个执行口落格）
    → consolidate_into_wal 落快照 + archive_before(快照 seq) → k 的用户格进了归档段
  → 用户点了审批，恢复请求进来 → execute_turn(resume = Some(..))
  → last_open_turn(current_window(range(0))) 只在**现行窗口**（最新快照之后）里找
  → None → PluginError::InternalError("续写轮找不到未收束的轮次（事实源与恢复路径不一致）")
```

同一轮的**轮号**不受影响：快照载荷带轮次水位 `turns`，`count_user_messages` 从最新快照
起折、水位与其下标之后的计数相加（`turn_exec.rs` 该函数文档立的正是这条不变量）。
缺的只有**恢复锚**——`last_open_turn` 判的是现行窗口，因为一个已被压缩取代的陈轮不该当
恢复锚；而「未收束」与「已被取代」这两件事此刻同时成立，判据就把它当陈轮丢了。
（P6-② 里钉的「先在同一个执行轮内算 `(turn_no, resume_anchor)` 再压」只覆盖**同一个请求**
既是续写轮又落快照那种情形，覆盖不了「归档发生在更早的请求」——那才是本条的形状。）

**为什么不在 P6-② 顺手修**：那一刀的全部承诺是「只改读法、不改行为」，动归档刀口是
行为变更。而「未收束的那一段该不该进被取代前缀」是压缩语义的问题：快照的语义是
「这份列表取代了它之前的一切」，可那一轮**还没被它取代完**（收束格仍在将来）。两种
出路（刀口避让 / 锚点改读完整史并自己辨新旧）给出的网格形状不同，得先有裁决——
按仓规（架构改动只认方案为源，[PL-006-分步实施计划](../004-plan/006-分步实施计划.md) §3 纪律 0）发起一次讨论、立 ADR，再实施。

**影响面**：只影响「压缩 + 待恢复」同时成立的会话。退化是**一条明确的错误**，不是
静默丢数据：归档段不删，事后按完整史仍能把那一轮读回来。
