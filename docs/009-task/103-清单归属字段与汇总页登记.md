## 内容

用户连续三轮把「同一事实被写两遍」从**修文档**推到**修机制**：

1. 「所有文档的 meta 里表明它包含哪些列表，不写=单内容文档；扫全仓查重复，重叠判红」
   → `lists` 字段 + RG-026…RG-029（声明层），判据分两层：**单文档**判「我声明的清单正文里有没有对应的东西」（RG-029，只读这一篇），**跨文档**判「两篇是否都声称拥有同一份」（RG-027，只读每篇 front-matter，不碰正文表）。
2. 「CURRENT.md 也纳入编号体系，放进 ref，引用标准化」
   → `docs/006-ref/006-当前事实表.md`，正式登记（原先免登记，所以别人只能手写 `../CURRENT.md#…`——本仓为它专门加过一条节次指路判据，而那条判据本不该存在）。
3. 「再有一个 ref 文档，根据 meta 里的 list 字段生成清单总账，重复则生成即红」
   → `docs/006-ref/007-清单归属总账.md`。
4. 「INDEX.md 也纳入编号体系，比如 xx-000 替代 index.md」
   → 9 个 kind 汇总页改为 `<前缀>-000-<X>汇总.md`，登记为 `projection: true`；它们各自声明 `lists: [<kind>-entries=owner]`，因此也进 RE-007（14 份清单）。

  消费方全在本 crate 内，`pub(crate)` 完全够用。所谓「洞」今天**零个消费者**，
  为它扩公开面正是「为读者根本不需要的东西扩 API」。
- **用户一句追问定性**：「如果下沉会造成依赖反转，就说明它不是单消费方啊？判断逻辑有问题吧？」
  ——这句是对的。**下沉的前提是「B 只被 A 依赖」**，前提成立时 B 合进 A 是纯粹移动、
  不可能反转；前提不成立时下沉才是反转。`isSinkCandidate` 的职责正是**先验明这个前提**，
  它没验，所以判错。
- **同域使用算不算耦合——算，而且没有第二个概念**。我第一轮说「core 内部另有依赖 ⇒ 真·耦合」，
  用「耦合」这个词把一件事说成了两类，是**造词**：**消费就是依赖，自己依赖自己也是依赖**。
  `SilentDeltas` 声明在 `adapters`、被 `provider_adapter.rs`（同域）用着，那就是 `adapters`
  在消费它——凭什么判它该下沉到插件？滤掉 core 内部的依赖等于**假装 core 不用它**。
- **口径 3 已删**（`collectCoreDomainConsumers` 的「声明域自身不算」）。三处联动：
  1. **同域使用计入消费方**。存量影响：`--verbose` 前后清单 diff = **释放 40 条、
     新增 0 条**，C-003 56 → **16**。⚠️ 这不是「清偿了 40 条」，是**判据修好后它们本就不算
     违规**；剩下 16 条（宿主接缝 / 跨 crate 契约一类）才是真的还没处置的存量。
  2. **必须一起钉住一个副作用**：域的 `mod.rs` 里 `pub struct X;` 与 `pub use …X…` 是
     **声明 / 导出清单**，不是使用。只删口径 3 而不滤这两行，实测会得到 **0/0**——
     每个符号都被自己的声明算成消费方，**判据恒绿**。所以判据改成「排除声明行与 `pub use` 行」。
  3. **`collectCoreBindings` 随之冗余，已删**。它是上一轮为「core 内 `impl <Trait> for …`」
     单独补的一层；口径 3 一去，同域的任何非声明引用都会算成消费方，实测关掉它 C-003
     **逐条不变（16/16）** ⇒ 冗余。留着它就是多一处会静默腐烂、且今天恒真的判断层。
  一句话：**「消费就是依赖，自己依赖自己也是依赖」这条原则一旦成立，就不需要给 trait 实现
  单开一个特例探测器。** 两条是同一个病的两副面孔。
  ⚠️ 被推翻的是我自己的两条判断，第二次是「同域提及 ⇒ 仍判红」那条**回归测试**——它钉的是
  错的答案，已改（见 `core-export-audit.test.mjs`）。
- **`SilentDeltas` 重复随之消除，且不需要豁免**。它与上一条是同一件事的两端：副本之所以
  存在，是因为 `SilentDeltas` 在根出口是 `pub(crate)`，而插件不能深引 `symbio_core::adapters::…`
  ——**core 把自己已有的实现藏起来，逼着消费者复制**。副本的注释还给了理由：「为一次
  『什么都不做』去拓宽 core 的公开面（并因此多一个单消费方符号、动棘轮）不划算」——
  **那条理由整个建立在已被推翻的判据上**：导出后 C-003 仍是 16/16，不产生新违规、不动棘轮。
  现在它从 `pub(crate) use` 进 adapters 的 `pub use` 块，插件侧那份连同理由注释一并删除。
  ⚠️ **顺序要紧：先修判据，再去重。** 反过来做会被判据挡住，然后就会有人开始想「要不豁免了吧」
  ——那正是这个坑的入口。

## 收束：「根导出下沉」的判据写成完整规则

规则从讨论稿收敛为**五档结论**，落在 `symbio_core/README.md §4` 第一问（该判据的 owner），
并由 `core-export-audit.test.mjs` 逐档钉住（20/20）：

| 情形 | 结论 |
| --- | --- |
| 含测试消费方 0 | 待处置（收窄）——根出口对它没用 |
| 含测试 > 0、生产 0 | 合法根出口，不收窄也不下沉 |
| 生产消费方 ≥ 2 | 保留 |
| 生产 = 1 且 core 内（任意域）有消费者 | 保留 |
| 生产 = 1 且 core 内无消费者 | 待处置（按 §4 四问判：下沉 / 成文契约 / 豁免） |

讨论稿里被推翻的四点，都记在 README 里，不在这里复述：

- **「同域」应为任意 core 域**——实测当前 16 条单消费方**全部无 core 消费者**
  （同域 0、跨域 0），所以那个洞今天不吃亏，但规则本身有洞。
- **结论不是「下沉」而是「待处置」**——判据能判"该处置"，动作要按四问走；
  账本里那 6 条正是「单消费方但不可下沉」（宿主接缝 / 跨进程契约 / 类型行为）。
- **唯一消费方是 core 自己 ⇒ 无需下沉**——这类符号落「0 消费方」档，模型里根本进不了
  单消费方档。已加回归测试钉住。
- **棘轮不是「当场判红」**：存量压住，新增才红。
