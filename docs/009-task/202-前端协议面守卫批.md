## 内容

父设计：15 报告建议 1 / 7 · 总报告 C7

**洞的形状**：前端读后端字段有**两种**方式——顶层字段（有镜像审计守着）与 `meta` 里的键
（**没有守卫**）。于是「后端改一个 `meta` 键名」这件事的后果是：前端少渲染一列，
**全仓不红**，只有用户看得出。

**为什么先补读数方言**：`ReadingPanel` / `ReadingRow` / `ReadingSection` / `ReadingTone`
是「读数面板」的跨栈契约，PL-010 批 0 的验收链依赖它。它们今天两侧**本来就对齐**——
所以补守卫只增不减，零风险，收益是「以后改字段名会红」。

**两处要同时修的注释**：`reading.ts` 里写着「schema-audit 对两侧对账」，
而实际上 schema-audit 不管这四个结构体——注释指向了一个不存在的守卫，比没有注释更糟
（下一个人会以为有人在守）。

**meta 键白名单的边界**（原报告已提示）：白名单本身会漂，维护成本与地址常量同一类。
所以本批的顺序是：**先做镜像守卫（结构体 + 词表），再做白名单**；且白名单只覆盖
「前端读、后端拥有」的那批键，不试图覆盖全部 `meta`。

**不做的事**：不把 `meta` 整体改成强类型。那是协议面变更（顶层字段 vs `meta` 的边界，
[ADR-070](../010-adr/070.md "ADR-070")），归 [T-208](208-消息域读数参数化批.md "T-208-消息域读数参数化批")。

### 段一（已落）：读数方言进镜像守卫

- **结构体组 3 对**：`ReadingRow` / `ReadingSection` / `ReadingPanel` 进
  `protocol-mirror-audit.mjs::STRUCT_SETS`，后端真源 `present/reading.rs`，前端
  `schemas/reading.ts`。两侧字段数逐对相等（4 / 2 / 3）。
- **词表组 1 对**：`ReadingTone` ↔ `READING_TONES`。前端原来写成裸联合
  `'normal' | 'warn'`，**没有词表就没有可比对的集合**——后端加一档前端不会红，正是
  本批要补的洞。改成「先有 `as const` 数组、再派生类型」，取值集合不变，消费方零改动。
- **注释改指向**：`reading.ts` 顶部原本写「schema-audit 对两侧对账」，而 schema-audit
  不管这四个结构体——指向一个不存在的守卫比没有注释更糟。现指向
  `protocol-mirror-audit.mjs` 的两张登记表。
- **红得起来**：回归夹具铺满新登记的四对（少铺一对基线就红），并新增两条注入用例——
  读数行字段改名 ⇒ 红（`前端持有后端不存在的字段：label`）；语气词表多一档 ⇒ 红。
  基线汇总断言从「C 6 + D 19」改为「C 7 + D 22」。

### 段二（待落）：`meta` 键白名单

**扫到的读点**（只扫「提到了 `ChatNode` 的前端生产文件」，避免把日志对象 / VDFS
详情的同名 `meta` 误算进来）：

| 键 | 前端读点 | 归属 |
|---|---|---|
| `compacted` / `compact_trigger` / `post_tokens` | `NoticeNode.vue` · `messageTypes.ts` | 后端（`loop/context/pipeline.rs`） |
| `ephemeral` | `ModelChatPanel.vue` · `messageTypes.ts` | 后端（`session/chat_session.rs`） |
| `error` / `failure_kind` / `started_at` | `useMessageContent.ts` · `useChatConnection.ts` · `messageTypes.ts` | 后端（节点构造 / `resume`） |
| `recoverable` / `prompt` / `tool_name` | `useChatConnection.ts` · `messageTypes.ts` · `chat_node.ts` | 后端（`ChatNode` 访问器 / 投影） |
| `agent_id` / `agent_name` | `messageTypes.ts` | 后端（会话 / 子代理宿主） |
| `style_tag` / `transcript_path` | `messageTypes.ts` | 后端（产者决定） |
| `__toolRequest` | `messageTypes.ts` | **前端自持**（渲染标记，不进后端存在性检查） |
| `workdir` | `sessions.ts`（**写**也在前端） | **前端自持** |

**两条判据**（落地时同组）：

1. **读点 ⊆ 白名单**：白名单外的 `meta.X` 读点 ⇒ 红（新增读点必须登记，登记时写明
   后端 owner）；
2. **白名单条目在后端仍存在**：每个「后端拥有」的键，其字面必须仍在登记的 owner
   文件里出现 ⇒ 否则红（后端改名 / 删除后，前端那条读点读 `undefined`，本条把它变成
   可红）。前端自持的键只做第 1 条，不做第 2 条。

**已知边界（写进判据注释，不留给下一个人猜）**：第 2 条判的是「字面从 owner 文件里
整词消失」，不是「语义上不再产出」——`error` / `tool` 这类通用词在 owner 文件里另有
用途时，改名不会立刻红。真正的根治是让键名只有一份（生成常量），那是协议面变更，
归 [T-208](208-消息域读数参数化批.md "T-208-消息域读数参数化批")，本批不越界。
