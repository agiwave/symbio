## 内容

父设计：05 报告建议 3 / 4 / 5

**会话机制（评级 B）剩下的三项，性质完全不同**：

| 项 | 性质 | 为什么值得做 |
|---|---|---|
| 寄存态无归宿 | **数据缺口**：崩溃即丢用户正在编辑的内容 | 这是本机制唯一可见的数据缺口 |
| 四套序号并存 | **认知债**：同一会话里四个「序号」 | 已有一次序号混淆类缺陷（压缩归档吞掉未收束轮） |
| 三个大文件 | **可导航性**：存储、统计、资源提供者三个千行上下的文件 | 不是为了行数，是为了「这一段错了谁会红」 |

**寄存态这条要过一道拷问**（原报告明确）：落格寄存本身是一条事实，但「寄存」是不是
**第五种原语**？答案很可能是「不是」——更可能是既有原语的**延迟落格**形态。
本批的第一步是回答这个拷问，答完再动手；若答成「要第五种原语」，那属于机制变更，须走 ADR。

**为什么依赖 [T-189](189-轮执行阶段数据化批.md "T-189-轮执行阶段数据化批")**：原报告明确
「大文件拆分应排在单环之后」——阶段数据化会重排 `turn_runner` / `turn_exec` 与存储读侧的
交界，先拆文件再改控制流等于把同一批代码搬两次。这条依赖是本批唯一的硬顺序。

**序号 newtype 是低风险高收益的一条**：四套序号的混淆已经造成过一次真实缺陷，
把「哪个序号」变成类型而不是命名约定，是最便宜的防复发手段。

- 2026-10-21 **段一（项四）落地**，范围按「命名能不能挡住一次真实的错」逐套判定：
  - **在途号**：`transcript.rs` 的裸常量 + 自由函数
    （`INFLIGHT_SEQ_BASE` / `is_inflight_seq`）合成一个类型 `InflightSeq`——号段下界、
    计数器（`first` / `after` / `raw`）、边界判据（`occupies`）三个事实归一个名字管。
    类型上的收益是一条具体的：转写自己的计数器 `next_seq` 从此**只能是**在途号，
    它不再可能被误接成一个存储号。判据 `inflight_seq_occupies_only_its_own_segment`
    在原有号段边界四格外补了计数器那一格（首个号 = 下界、`after` 不离开号段）。
  - **重建号**：`projection/rebuild.rs` 的裸 `i64` 计数器换成模块私有类型 `RebuildSeq`，
    节点上的重建号**只有一个来路**（`assign`）。这条挡住的是本模块最容易顺手写出来的错：
    快照载荷里带的是**存储层槽位号**（量级可以很大且不连续），直接沿用会让
    「快照列表内部单调、与后继事件不单调」，而前端的排序键只有一个。
    判据已在 `rebuild.test.rs` 的 `seq_is_renumbered_monotonically_across_the_snapshot_boundary`
    （载荷带 `9_999`，重建必须无视它）——行为零变化，故不新增测试。
  - **文档归一**：四套序号 + 一个同名不同物的 WAL `Seq`，一张表写在本域
    `symbio/src/plugins/session/docs/022-vdfs-session-messages.md` §3.3（它同时取代了
    原先 §3.4 那张只有两行的表——同一事实不留两处）；`ChatNode.seq` 字段文档只指回这张表。
    表里刻意收了 WAL `Seq`：**「seq」在本仓不是一个含义**，读代码时最容易串的就是它——
    本域连日志计数器都改名成 `frame_no` 避它。
  - **两处不做，各自有理由**：
    ① **`StoredSeq` 不建**。设想里的判据是「存储水位的构造器拒收在途号段」，但它与
    现存的恢复路径**互斥**：存量会话里被泄漏抬高的水位已经躺在存储中，把它滤掉等于
    **压低**水位，此后新分配的号会排到那些既有消息之前——正是 §3.3 表里「权威号跨进程
    稳定」这条的反面。`max_seq` 取「全部 seq 的最大、不挑号段」因此是有意的，
    现在这段判断写进了它自己的文档。新泄漏由**边界**（`InflightSeq::occupies`）挡住，
    水位这一侧不需要再判一次。一个只能原样收下所有数的 newtype 是空壳，不进类型系统
    （同 [ADR-110](../010-adr/110.md) 的取向：不登记没有兑现的机制）。
  ② **WAL `Seq` 不动**：它早就是 core 的 newtype（`event/mod.rs`），这一格本来就是兑现的。
- 2026-10-21 **段二（项三）落地**：寄存区从进程内静态表搬到**会话目录里的文件队列**。
  - **先过拷问：寄存是不是第五种原语**。答案不是。`ParkedChange` 的形状刻意 =
    `append` 的入参元组（`kind` / `verb` / `id_prefix` / `target` / `payload`），
    不新增 `kind`、不新增读侧投影、折叠语义与就地落格完全一致——它只是**同一次落格
    晚一点发生**。既然是延迟而不是新格位，就不是架构改动，不需要 ADR
    （AGENTS.md「架构改动只认方案为源」在这里的合法动作是**不改架构**）。
    顺着这条也拒掉了一个诱人的收尾：给 `MessageChange` 加第四格 `parked`。
    那一格会立刻成为新的事实词汇而**一个读方都没有**（寄存件落格后走的还是
    `message.edited` / `removed` / `added`），按 [ADR-110](../010-adr/110.md) 不登记。
  - **触发条件先收窄过一次，而收窄改变了结论**。
    [PL-014-单环一表收敛](../004-plan/014-单环一表收敛.md) §2.2 推论 3「一写者」落地后
    （`SessionStore::facts` 按会话缓存**唯一**一个 RW 句柄，只有 `delete_session` 逐出），
    同进程里第二个 RW 持令牌者的形态**不存在**；而 `WalStore::append` 永不重新取令牌
    （`writer` 为空即 `NotTheWriter`）。⇒ 今天还能拿到 `NotWriter` 的只剩**跨进程**一种。
    进程内静态寄存区恰好在这种形态下**永远救不回来**：寄存躺在没令牌的那个进程的内存里，
    持令牌的进程在另一个地址空间，它的 `drain_parked` 看不见；那个进程一退出
    （CLI 一条命令就是短命进程）寄存随之消失。所以旧形态不是「崩溃才丢」，
    是**触发即丢**，还把它换来的 `AppendOutcome::Parked` 回执坐实成一句假话——
    比 T-164 要修的 `Failed` 更糟。
  - **形状：一条变更一个文件**（`<会话目录>/transcripts/pending/`，与 WAL 归档段
    `transcripts/wal-archive` 同一套会话布局词汇；路径由 `EventWalStore::dir()`
    自己给出，调用方不再重新派生一遍布局）。寄存的可见性因此不再依赖寄存者活着：
    崩溃、退出、另一个进程补落，三种都走同一条路。搬过来三条现成纪律，不新造：
    **先落盘再回执**（写寄存区失败 = 这条变更没有任何副本 ⇒ `Failed` 冒泡，
    绝不回 `Parked`）、**一件一份 + `.staged` 暂名再改名**（与 `archive_before` 同手法，
    崩在改名前只留下看不见的半件，由补落方顺手清掉）、**有界 + 出声**
    （`PARK_CAP` 与丢最旧的告警照旧）。补落的**顺序**是新出现的判据：按文件名升序
    逐件落，拿不到令牌就**整队停下**而不是跳过——跳过等于把后寄存的排在先寄存的之前落格。
  - **新增判据**（`message_events.test.rs`，五条）：寄存件在盘上 ⇒ 从未参与寄存的
    新令牌句柄也能补落（这条是整段改动的承重判据，旧实现在这里必然红）、
    两件按寄存先后落格、`.staged` 半件不进事实源且被清理、满界丢最旧而新的照样寄存、
    寄存写不进去冒泡成 `Failed`。
- 2026-10-21 **段三（项五）落地**：三个大文件按「这一段错了谁会红」各自拆开，
  行为与判据零变化（判据数 1962 持平）。
  - **存储 `store/mod.rs`（1076 → 483）**：分出 `store/facts.rs`（277：事实源句柄 +
    运行时事实缓存，红的是「读到的事实不对 / 缓存串了」）与 `store/layout.rs`
    （398：目录寻址、两种落盘形状、原子写与自愈解析，红的是「目录与文件本身」——
    读不出来、整份写坏、清单少一项、子会话寻不到址）。「磁盘布局」那节叙事跟着实现
    一起搬进 `layout`，**同一事实不留两处**；`current_window` 留在 `mod.rs`——它既不是
    布局也不是句柄，只对已经读出来的 `&[Event]` 切窗口，红的是「上下文从哪读」。
    `panic-allow` 登记跟着代码搬家（PN 判据要求理由与它解释的那段代码同处一文件）。
  - **资源提供者 `plugin/vdfs_provider.rs`（1122 → 259）**：按**域**分四份——本文件留
    路由 + 订阅表 + 跨域共用读值（红的是「地址归错域」或「几面同时看不见」），
    `vdfs_catalog`（430，目录域）、`vdfs_messages`（279，转写域，也是写侧最重的一域）、
    `vdfs_inbox`（212，收件箱域）。后两者与目录域分开的理由是红的性质不同：目录域红
    「看不见」，转写域红「改坏了」，收件箱域红「停了还在不在」（它的生命周期是运行态，
    转写是事实源的渲染）。**「路径 → 域」的映射仍只有一处**（`dispatch`），拆的是域内
    实现；跨文件的新缝隙只有 `pub(super)` 一层，模块外看不见。
  - **统计 `stats.rs`（819 → 535）**：分出 `stats_reading.rs`（312，口径装配）。判据是
    两种红的**处置动作**不同：`stats.rs` 红「读不到 / 契约字段缺」（改取数范围与出口
    形状），`stats_reading.rs` 红「某一格的数字与 core 口径不符」（改换算）。于是
    「只调已有投影，不另写一份统计」这条纪律不再靠同一文件里的位置提示，而是写在两个
    模块头上各自成立。
  - **拆分的边界一律落在既有归属上**（域 / 布局 / 句柄 / 装配），没有新抽象、新端口、
    新类型，也没有为「让文件变小」而发明的中间层。拆文件最容易留下的病灶是文档指向
    搬走的东西，这一条由 `cargo doc -D broken_intra_doc_links`（门禁内）守住。
