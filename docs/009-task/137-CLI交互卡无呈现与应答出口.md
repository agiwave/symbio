## 内容

`UserPrompt` 是会话契约里的一等节点：承载 `ask_user` 提问与工具执行前的 confirm，
状态 `WaitingUserAction`，回答以一条带 `meta.responds_to` 的普通 user 消息回填。

CLI 这一侧**两端都缺**：

1. **看不见**——`cli/src/render.rs` 的 match 里 `UserPrompt`（与 `Compression`）落进
   `_ => false`，注释写着「无正文可渲染」。可 `meta.prompt` 里带的是要用户确认什么、
   有哪些选项，这些正是终端要打印的东西。
2. **答不了**——REPL 的命令表只有 `/new` `/session` `/provider` `/workdir` `/stats` `/exit`，
   没有任何「回答这一张卡」的入口；非交互模式更是发一条就退出。

而 `args.rs` 把默认模式设成 `auto` 的理由写得很清楚：「CLI 没有交互卡片的渲染能力，
遇到需审批的工具时应让后端返回友好错误继续，而不是挂起等待一个永远不会到来的点击」。
这个取舍在 `auto` 下是自洽的（后端返回 `PERMISSION_DENIED` 文本喂回模型），
但于是**终端用户永远看不到审批这件事本身**——他只看到模型莫名绕开了高风险动作；
一旦有人按 `--mode interactive` 启动（本仓的用法示例里就有），
本轮会停在 `WaitingUserAction` 上，而 CLI 既不打卡也没有回答通道，只剩 `TURN_TIMEOUT`（900s）到点报错
——这一句是**从代码推出来的**（渲染臂 + 命令表两处都缺，没有别的可能），闭本任务前要用一次真触发闸门的调用实测取一次现场。

两条路都要，但判据不同：`interactive` 下**把卡打在 stderr 并读一行作为回答**（走 `responds_to` 那条回填协议）；
`auto` 下**播报一句「本轮被权限闸门拦下，已按无人值守继续」**（现在是静默的）。
