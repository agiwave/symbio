## 内容

父批次：[T-230 内环收口批](230-内环收口批.md "T-230-内环收口批") ·
机制：[ADR-116](../010-adr/116.md "ADR-116") ·
行归属裁决：[ADR-117](../010-adr/117.md "ADR-117") ·
前置：[T-231](231-恢复调用进债环.md "T-231-恢复调用进债环")。

T-227 步 3 的 `dispatch-tools` 用**蕴含**代替合取：

```
dispatch-tools   owes: authz.granted(port=tool)     ← granted ⇒ request 在数据上成立
```

T-229 给了求解器集合展开，但 ADR-117 核对实现后把「创建」与「派发」拆成两段债：
派发行必须被授权闸住（否则被拒绝的调用仍有模型响应，派发会绕过授权），而恢复调用
根本没有模型响应。因此 `expand` 落在**创建行**，不是派发行：

```
open-tools       owes: response(port=model)
                 expand: (calls, id)                 ← N 个调用 = N 笔子债
                 until: request(port=tool)

dispatch-tools   owes: authz.granted(port=tool)      ← 保持 T-227 的写法
                 until: sent(port=tool) | failed(port=tool)
```

- `expand` 只作用在 `owes`；`until` / `unless` 按键命中，不展开。
- 元素键是**协议调用 id**，与 `request` / `authz.*` / `sent` 同键；跨轮不能撞键
  （模型原样 id 可能重复，元素里带编码后的协议 id）。
- `response.has_tool_calls` 不再是必需的 `eq`：`calls` 为空数组 ⇒ 展开出 0 笔债。
- `authorize-tool`（prio 0）仍先于创建 / 派发；`open-tools`（prio 67）先于
  `dispatch-tools`（prio 68）。

**边界**：本任务只做创建行的前件与展开 + 响应载荷，**不改**
`turn_exec::drive_steps` 的调度（那是 T-233），也不重写批次执行实现（PL-017 §7）。
