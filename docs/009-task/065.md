## 内容

`node e2e/run-tests.mjs` 全量 45 用例中 t30 失败（2026-10-13 发现）。对照实验（`git stash` 后用 HEAD `584b7f60` 重跑）**同样失败**——既有失败，与 2026-10-13 的 actor/ts 收口、vdfs 树回执修复无关。

断言反向②：子会话的用户正文 C1 只准出现在已声明的跨会话召回段（`meta.kind = recall_context` 或 content 以【长期记忆】开头的独立消息），线程里出现即串主体。实测 C1 出现在父会话 composed prompt 的**内联**【长期记忆】小节里——该消息 content 不以【长期记忆】开头 ⇒ 既不被 `threadBody` 排除、也不被 `recallText` 收录，两个通道判定都落空。

## 处理过程

2026-10-13：全量 e2e 验证 actor/ts 修复时发现；stash 对照实验定性为既有失败。侦查线索：`threadBody` / `recallText`（t30:102-122）按「content 前缀 + meta.kind」切分通道；需分清是实现把召回并进了 composed prompt（测试切分逻辑该更新），还是编码范围把子会话用户发言编进了父会话可召回记忆（真串主体）。

2026-10-13（定案）：**实现无串主体，测试切分粒度过粗**。链路考古：召回在请求视图里是独立消息（`meta.kind = recall_context`，`build_request_view` 置顶注入，设计文档明言「不进系统提示词」）；但 openai_chat 协议 `prepare_request` 的 `merge_leading_system` **出厂只发一条 system**（文档化决策）——基础系统提示（【工作区记忆】【会话记忆】等注册段）与 prefix 消息（召回/就绪/委派）并成一条，召回于是成为合并消息里的一个**小节**，不再以【长期记忆】开头 ⇒ 切分器两个通道判定都落空。判定为测试期望过时：通道语义（召回 = 设计内背景事实，线程 = 本会话）没变，变的是线上判别粒度。

修复：t30 切分器升级为**小节粒度**——`splitRecall` 按「小节头 `【长期记忆】跨会话召回` + 连续 `- ` 条目行」（`prompt_section` 的固定排版）把每条消息切成 thread / recall 两半；`recallText` 收小节正文，`threadBody` 摘小节（纯召回消息整条摘除）。t30 回绿，45 用例全绿。
