## 内容

父设计：10 报告建议 S-2 / S-3 · 12 报告建议 3 · 11 报告建议 5 · [PL-012](../004-plan/012-高阶智能体平台v2.md "PL-012-高阶智能体平台v2") §3 判据 J3

**四处的共同形状**：**失败与「没有」同形**。用户看到的结果一样（搜不到 / 钩子没生效 /
工具不见了），但原因完全不同——一处是降级，一处是配置错，一处是代码缺陷。

| 处 | 现状 | 用户看到的 |
|---|---|---|
| `keyword_search` 正则编译失败 | 静默退回 | 「没搜到」 |
| embedding 全局初始化失败 | 永久降级（`LazyLock` 缓存了失败） | 「没搜到」（且本进程内永不自愈） |
| `fire_hook` 插件缺失 / 执行异常 | 静默 | 「钩子跑了」（实际没跑） |
| MCP 非法工具名被过滤 | 告警不带名字 | 「某个 server 的工具不见了」 |

**为什么这一批值得单独做**：本仓的判据文化很强（每个决策有 ADR、每次事故固化为结构），
但**「降级要说得出来」这条纪律在实现面还没有统一落点**。这四处都是低成本、可观测性收益直接的
位置——它们的共同修法不是加功能，而是**让已有的失败带上名字**。

**两处形态选择要写清**（否则会各写各的）：

- `fire_hook`：**最小形态**是往输出上下文注入固定标记（不改返回类型、不影响 `should_proceed`
  判定链），**完整形态**是改返回类型（影响三个消费点）。原报告建议先最小形态，本批沿用——
  语义变更须先裁决，而「可观测」这个收益不需要等裁决。
- embedding：**可重试**（`OnceLock` + 显式 `get_or_try_init` + 退避）与**说得更响**（一次性提示）
  二选一。可重试更彻底，但每次失败都要重试初始化，需要退避；说得更响更便宜，
  但「本进程内不会自愈」这个事实仍在。选哪条要在正文里写明理由。

## 处理过程

- 2026-10-20 立批。来源：10 报告 S-2 / S-3 + 12 报告建议 3 + 11 报告建议 5。
- 2026-10-20 为什么合成一批：四项都是「失败要有名字」的同类动作，判据形状相同
  （构造一个失败输入，断言返回体里有可辨标记）；合成一批可以用同一套判据模板，
  分开做会写四遍相似的用例。
- 2026-10-20 与 [T-184](184-机制强制等级清单批.md "T-184-机制强制等级清单批") 的关系：
  这四项在清单里都是 ③ 类（纯声明：写了「要降级 / 要出声」，没有执行方），
  本批是它们从 ③ 变成 ② 的动作。
- 2026-10-20 **`keyword_search`：字面量回退 + 说明**。非法正则不再返回空，而是
  用 `regex::escape(query)` 按字面量重试一次，并把「查询不是合法正则（原因），
  已按字面量匹配」写进返回体的 `notice`；字面量也编译不出来时才返回空 + 说明。
  选「回退」而不是「只报错」：用户输入的多半是含 `(` / `[` 的普通文本，直接报错
  等于为了一个转义符把一次检索作废；但**回退本身也要说出来**，否则「按字面量匹配」
  与「正则匹配」的结果差异无人知道。合法查询但零命中 ⇒ `notice` 为 `null`——
  这才是「真的没搜到」。
- 2026-10-20 **embedding：可重试（退避 30s）+ 原因进返回体**，两样都做。只做
  「说得更响」会保留「本进程内永不自愈」这个事实，而初始化失败可能是瞬态
  （临时缺库 / 内存紧张）——修好了也用不上是更坏的静默。`LazyLock<Result<..>>`
  换成 `OnceLock<Mutex<InitState>>`：成功实例 + `RetryGate`（`last_error` /
  `next_retry_at`），窗口内返回「上次失败（原因），Ns 后重试」，窗口过后下一次取用
  重试，成功即清空。`codebase_search` 另经 `providers::embedding_unavailable_reason()`
  把原因写进 `notice` 与 `message`：实例恒能拿到（失败给 Noop），不单独问一次的话
  「语义检索没搜到」与「根本没跑」在返回体里同形。`RetryGate` 是纯数据，判据直接
  打在它身上（窗口内拒绝 / 窗口外放行 / 成功清空）。
- 2026-10-20 **`fire_hook`：最小形态**。不改返回类型、不动 `should_proceed` 判定链：
  路由失败与载荷解析失败各写一条 `tracing::warn!`，并在 `context` 里注入固定标记
  `[hook-unavailable] <事件> <原因>`。`parent` 为 `None` **不**打标记——那是「进程内
  直调、没有编排层」的合法形态，不是失败。判据：两条失败路径都 `should_proceed == true`
  且 `context` 带标记与事件名；无父插件时 `context` 仍为 `None`。
- 2026-10-20 **MCP：交名字而不是计数**。`filter_valid_tool_names` 的第二个返回值从
  `usize` 改成 `Vec<String>`（被丢弃的原名），`manager` 的告警带上前 5 个名字与
  省略数。只报「过滤了 2 个」时，用户知道工具少了却永远查不出是哪个——这正是本批
  要消灭的形态。测试同步改成断言名字集合。
