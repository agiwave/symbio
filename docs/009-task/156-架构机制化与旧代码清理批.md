## 内容

父设计：[PL-012 §0.1.2](../004-plan/012-高阶智能体平台v2.md "PL-012-高阶智能体平台v2")（架构面切分不可妥协）·
[PL-001 §8](../004-plan/001-核心架构.md "PL-001-核心架构")（权威参数表：能用已有参数新取值表达的就是数据）·
判据 J1 可表达性 / J3 静默失效

**起因**：一轮架构复盘（对话面 → 运行流程 → v2 落地对账）得出的判断是——
本仓的病**不在「抽象不够」，而在「抽象接线不全」**：core 侧 Store / Projection / 事件网格 /
授权矩阵是真机制且被棘轮守住，但插件侧未享受同等纪律，于是**真实需求绕过机制各自长出特判**。

本批的性质是**兑现已有机制**，不是加新机制：七条子任务全部落在「已有参数的新取值」上，
**新增机制键 = 0**，且不触碰 F1–F6 冻结锚点（core 形状棘轮只降不升）。

**按 PL-006 §0 纪律 1 的批次纪律**：七条各自成批、各自独立回退；父任务只做编排，不引入改动。
每条子任务落地时须带一条默认路径的 e2e 或既有用例断言（纪律 2 / 纪律 5）。

## 处理过程

- 2026-10-17 立批——起因是用户对当前架构的判断：「机制化和抽象都不够，特殊化偏多，造成代码量大」。
  逐条核实后确认该判断**成立但需分层**：臃肿有四种性质（本质复杂度 / 机制未兑现 / 接缝样板 /
  迁移中途状态），只有后三种可清，本批覆盖后三种中价值最高的七条。
- **登记前核实修正了三处判断**（写进 signal 的必须是核实过的快照，不是探索报告的转述）：
  ① `messages.json` **不是**死代码残留——写侧已随 ADR-049 停写且有测试断言，真实欠账是注释；
  ② 供应商 `reasoning` 字段**不是**散落特判——已是带日期带测试的 fallback 链，真正散落的是
  `max_tokens` 下限三个魔法数；③ 工具名**不是**全盘硬编码——`todo_write` / `context_compact`
  已有常量，欠的是形态归一与「按名判定」本身的机制化。
  这三处修正直接改变了子任务性质（删代码 → 清注释 / 收表 → 归一常量），
  也说明**登记前逐条跑 grep 核实不可省**。
- 未纳入本批的两条，理由写明（不是遗漏）：
  - **session 插件拆分**（28803 行实现占 `symbio/src` 全部实现的 35%，违反 PL-012 §0.1.2
    「一个能力一个插件、可卸载」）——属**另一个迁移步**，混进本批会让本批无法独立回退
    （PL-006 纪律 1）。**目前尚无对应任务条目**（[T-017](017.md) 是已完成的「两个巨型文件混域」，
    对象是 `tool_executor.rs` / `actors/mod.rs`，与插件级切分不是一回事）；
    拆分边界（它该拆成几个插件）需要先做一次勘察，再单独立条目排期。
  - **接缝样板机制化**（11+ 处手写 `impl VdfsProvider` / `route()` 三行样板 / `traverse()` 形态不一）
    ——已有范本（`PluginConfigMount` blanket impl 覆盖 5 个插件），但逐处判定哪些是纯样板、
    哪些真有逻辑需要单独勘察，价值低于本批七条，列为后续批次。
