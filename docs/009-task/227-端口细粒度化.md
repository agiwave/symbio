## 内容

父设计：[PL-017 · 端口细粒度化](../004-plan/017-端口细粒度化.md "PL-017-端口细粒度化")

**它解决的是 PL-016 留下的最后一层"环中环"。** T-223 之后，控制面是债环，但
`turn` 执行体内部仍是 747 行的 `run_with_tools`：模型调用与工具批次都不落事实，
崩溃只能重放整轮。本任务把这个内环倒过来。

**四组行**（复用 PL-016 的五个协议名，**不新增事实名**）：

```
dispatch-model   owes: request(port=model)          ← 落地的形状（与 turn 同模板）
                 until: sent(port=model) | failed
                 before: sent · by: courier
await-model      owes: sent(port=model)
                 until: response(port=model) | failed | retry
                 by: None

dispatch-tool    owes: request(port=tool)          ← 批由决策者写一条 request 开账
                 until: sent(port=tool) | failed
                 before: sent · by: courier
await-tool       owes: sent(port=tool)
                 until: response(port=tool) | failed | retry
                 by: None

close-turn       owes: turn.has_final ∧ ¬closed
                 until: chat.assistant.final | chat.assistant.fallback
                 by: closer
```

`turn.needs_model` / `turn.has_final` / `response.has_tool_calls` 是视图字段，不是新名字。

**四条边界**：

1. **流式不是债。** `courier` 在 `sent` 后把 `ExecEventSink` 的帧直通；`response`
   只在流结束时落一条。把 token 级帧写进日志会淹掉事实面（PL-014 §3 已裁决）。
2. **工具批是一次调用（步 3 的收窄）。** 初稿把批拆成 N 笔子债（`expand`），
   前提是执行体按调用跑；现网执行体是**批原子**的（批首闸门读一次、交互模式一条
   待用户动作就收掉批尾、批尾统一收口），拆出来的 N 笔账没有一笔能独立派发。
   单次调用的结果本来就逐条是事实（`artifact.added` 带 `tool_call_id`），恢复面
   因此不丢信息。执行体将来按调用跑时，`expand` 才成为它的形状（记在 PL-017 §3.1）。
3. **审批 / 补充 / 中止是唤醒源。** 它们由外部落事实（`approval.*` /
   `user.message` / 收束格），`await-tool` 的 `until` 增加对应名字。
   迁移完成前 `resume.rs` 的旁路保留；**最后一步必须删它**，否则有两条恢复路径。
4. **`turn` 执行体退成薄壳。** 它不再持有模型 / 工具循环，只负责把输入交回控制面；
   `turn_runner` 的 `while` 消失是本任务最硬的判据。

**施工分五步，每步一个提交**（PL-017 §4）：

| 步 | 内容 | 前置 |
|:-:|---|---|
| 1 | 把 `run_with_tools` 抽成 Step 循环（纯内部重构，行为不变） | T-223 |
| 2 | 模型端口两行 + 适配器 | 1 |
| 3 | 工具批端口两行 + 适配器（**调用单元 = 批**，见下） | 2 |
| 4 | 收束成行（`close-turn`）+ 收束行的授权级联（[ADR-116](../010-adr/116.md "ADR-116")） | 3 |
| 5 | 审批 / 补充 / 中止接入；删 `resume.rs` 旁路 | 4 |

**步 4 / 步 5 的先后被对调了（2026-10-22）**：初稿把「接入唤醒 + 删旁路」排在
「收束成行」之前。删旁路的前提是**已经有另一条恢复路径**，而唤醒只有在一个真正
的驱动器里才成立——执行体还在自己 `while` 的时候删掉 `resume.rs`，挂起的审批就
没有任何恢复路径了。所以先让控制面闭环（收束成行），再拆恢复的旧路。

**熔断线按提交计**：单次结构性改动 > 300 行 = 退回。步 1 可能接近上限，所以它必须是
**纯内部重构**（不改行为），否则应拆得更细。

    `reason: exhausted` + `detail: step_limit`（与 `finish_reason = length` 同一闭集
    值，读侧不必学新词）。落格走 `settle::append_exhausted`，与兜底共用
    `land_failure`（闸门 / 幂等键 / `produced` 形状一致，只差 `reason`）。
  - **口径修正**：PL-017 §4 步 1 标称的「纯内部重构，行为不变」不覆盖这条上界——上界

  - 用例：`a_runaway_adapter_is_stopped_at_the_step_bound`（永远要工具的适配器 ⇒
    恰好 64 次模型往返后收束为 `exhausted`）。反向自检：删掉上界检查，用例**不会
    变红而是挂住**——那正是它防的病。

- 2026-10-22 **步 2 落地**：模型端口两行 + 适配器。
  - **行表**：`dispatch-model`（prio 66）/ `await-model`（prio 71），与 `turn` 的两行
    **同模板**（`owes` = `request{port:model}`，`until` = `sent` / `failed`；

    类型，就只能给它们同一个形状。

  （prio 72）两行 + `PORTS` 一条 `PortDecl { port: "tool", lease_ms: 600_000,
  max_attempts: 1 }`；`stream.rs` 的 `call_tools` 包住整批派发。判据 7 第二次被真实
  走了一遍：**0 个新事实名、0 行求解器改动**（`port-surface-audit` PTS-003 基线
  未动），加端口只加了「1 条 `PortDecl` + 2 行 + 1 处调用点」。

    `dispatch-tools`）：`every_port_row_is_in_the_table` 机械检查「每个端口两行」，
    模板一旦允许例外，加端口就不再是纯加法。
  - **调用单元是「批」，不是「单次调用」**（与初稿的 `expand` 不同，理由记在
    「四条边界」第 2 条与 `PORTS` 的 `tool` 一节）：执行体是批原子的，拆成 N 笔

    工具——跳过会让模型下一轮看到「请求过却什么也没发生」。
  - 用例：`every_tool_batch_leaves_a_sent_and_an_answer`（一批 ⇒ 一条 `request` /
    `sent` / 应答，三者同 id；工具端口三格在产物格之前）。反向自检：把

- 2026-10-22 **步 4 落地（收束成行 + 收束行的授权级联）**：收束不再是执行体里的
  一个 `if`，而是债环里两行；[ADR-116](../010-adr/116.md "ADR-116") 的三条事实
  因此第一次有了结构上的落点。
  - **行表**（插在表最前，`prio` 0 / 5）：

    ```
    authorize-close  owes:  turn.closing{turn}                     prio 0  by: authorizer
                     until: authz.granted | authz.denied
    close-turn       owes:  authz.granted{turn, kind=speech}       prio 5  by: closer
                     until: chat.assistant.final | chat.assistant.fallback
    ```

    **三格一条线**：`turn.closing`（决策）→ `authz.granted` / `authz.denied`
    （结论）→ 收束格（只有 `granted` 才开账）。判据 8b 从此是**结构**而不是行为：
    `denied` ⇒ `close-turn` 的 `owes` 不成立，表自己就不让收束格落下。
  - **前件不是 `turn.has_final`**（ADR-116 初稿写错了，本步修正）：六条收束路径
    里**三条零模型往返**——首请求前中止（`stream::aborted`）、定稿答话
    （`prepare` 1b）、反射档（`reflex::run_reflex`）。以"模型回来了"为前件，这三
    条永不收束，收束行会在三条路径上把一轮话卡死。**决策本身**（`turn.closing`）
    是唯一对六条路径都成立的前件。副作用是好的：`response{port:model}` 的载荷
    **不必**补「有没有请求工具」「正文是否非空」两个字段，ADR-116 决策 3 列的
    第二个前置条件被**结构性消掉**，不是被绕过。
  - **`prio` 不照抄 0 / 10**：`policy.classify` 已占 10，而表要求 `prio` 全局
    严格递增。为凑一个整数把十二条行整体重编号 = 制造一次纯噪声的 diff（且下次
    加行还要再来一次）。取 0 / 5 仍落在 `execute-turn`（60）之前，"收束类判据
    先于执行类判据"的语义不变。理由写进了 `loop_rows.rs` 的头注释。
  - **级联的第三问走「问行」而不是「查有没有 `granted`」**：`close::allow` 依次
    做三件事——落 `turn.closing`（幂等键 `closing-{turn}-{kind}`）→ 若欠
    `authorize-close` 则过 `closure_gate` 并落 `authz.granted` / `authz.denied`
    （`grant-{turn}-{kind}` / `deny-{turn}-{kind}`）→ **问表**：`close-turn` 还
    欠不欠。第三问刻意问表：判据只该有一处，否则代码里会多出一个不跟表变的第二
    判据，下次改表它就撒谎。
  - **收拢到一处**：`turn_runner.rs` 里本地那套 `ClosureKind` / `closure_granted`
    / `closure_gate` / `deny` / `within_delegation_ceiling`（约 200 行）整体迁到
    `loop/close.rs`，六个收束点统一改走 `allow(...)`。六个调用点的形状一致：
    `if let Verdict::Denied(why) = allow(...) { warn + 返回未收束 outcome }`。
    这不触 S-015 守卫（新调用点不含 `!closure_granted(`）。
  - **fail-closed 且不上抛**：三格任一落不进去都不放行，只 warn。此刻的任务是
    **收尾**——把记账失败变成 `Err`，它会吃掉"这一轮怎么结束"这个正在回答的
    问题。理由写进 `close.rs` 的模块文档。
  - **棘轮收紧**：`DECLARED_EVENT_NAMES` 40 → 42、`BUILTIN_FACTS` 15 → 17；
    `facts_without_a_row_are_pinned` 的孤儿集从 `["turn.dispatch","authz.denied"]`
    缩到 `["turn.dispatch"]`——`authz.denied` 从"声明了但没行消费"变成有行消费，
    这正是判据 8b 想要的形状。
  - 用例：`close.test.rs` 四条（`a_granted_closure_lands_the_intent_and_the_grant`
    钉三格顺序与 `produced_by`；`a_denied_closure_never_opens_the_close_row` 是
    判据 8b 的正面用例——只有 `authz.denied`、`close-turn` 与 `authorize-close`
    都不欠；`asking_twice_does_not_duplicate_the_decision` 钉幂等；
    `the_intent_names_the_cell_it_will_land` 钉载荷 `key` 就是收束格将落的那个
    key）+ `loop_rows.test.rs` 四条行级用例。既有用例只改断言：六处事件序列各
    多两格，`turn_runner_events_are_replayable` 的计数 24 → 32（第 4 轮接着写在
    同一本台账上，断言取在第 4 轮之后）。
  - **步 4 尚未满足的**：判据 1（步循环仍在 `run_with_tools` 里）、判据 6（唤醒
    事实）、判据 8（`resume.rs` 旁路）。判据 3 / 5 的用例已随本批补上（见下一条）。
- 2026-10-22 **补判据 3 / 5 的用例**（步 4 落地时这两条只「天然满足」，没有判据）：
  - **判据 3**（`in_flight` 按调用重建）：`in_flight_rebuilds_per_call_not_per_turn`。
    只喂一串 `request` / `sent` / `response` 问视图，同一轮里放**两次**模型往返 +
    一批工具，要求回来过的那次**不许**留在在途表里。它防的是「一轮在途」这种按轮
    折叠的粗口径——恢复时会把已经回来的调用算成没回来，重跑就是重复执行副作用。
    反向自检：删掉 `response` 那一格，三条全在途，第一条断言随即变红。
  - **判据 5**（流式帧直通且不产生事实）：`streaming_frames_reach_the_sink_without_adding_a_fact`。

## 步 5 的施工方案（2026-10-22 记，尚未施工）

步 5 = 「审批 / 补充 / 中止接入 + 删 `resume.rs` 旁路」。核对之后发现它有一件
**必须先做的事**，否则做出来的会是一个假驱动。

### 先决：`request` 不能当驱动器的输入

`dispatch-model` / `dispatch-tool` 现在的 `owes` 是 `request(port:model)` /
`request(port:tool)`，而 `request` 是**调用点自己**在派发前一刻写的
（`stream.rs::open_call` 的 `announce`）。这带来一个结构性后果：

> 驱动器若问表「现在欠什么」，答案恒为「什么也不欠」——因为能让它欠的那条事实
> 还没写。写了之后表当然说欠，但那时调用已经决定要发生了。

于是「下一步调模型还是调工具」这个判断**只能在代码里**，表无法参与。今天它写在
`stream_round` 的 `classify_round` 里；判据 1 要求的「循环离开执行体」于是无从
落地——把循环搬到 `chat_loop` 只是换了个文件放同一段顺序。

**所以步 5 的第一步是把前件改回视图**（也就是 PL-017 §3.1 原本写的目标形状，
步 2 / 步 3 标称的「与 `turn` 同模板」是落地时的简化）：

```
dispatch-model  owes: turn.needs_model      ← 视图，不是 request
dispatch-tool   owes: turn.needs_tools      ← 视图，不是 request
```

- `response{port:model}` 的载荷要补 `has_tool_calls`（`FactDecl` 换一份
  `RESPONSE_FIELDS`）——`turn.needs_tools` 的唯一输入。
  ⚠️ 这与 ADR-116 的裁决**不冲突**：那里说的是「收束的前件不需要它」，不是
  「任何地方都不需要它」。收束仍以 `turn.closing` 为前件。
- `turn.needs_model` = 本幕未收束 ∧ 无「末次模型应答已给出定稿」∧ 无在途
  `model` 调用 ∧ 无待办工具批。后两条是必需的：没有「无待办工具批」这一条，
  模型刚回完（还欠工具批）时 `needs_model` 又是真的，而它 `prio` 66 先于工具批
  的 67 ⇒ 驱动器会跳过工具批再调一次模型。
- `request` 仍是记账（「这一次调用发生过」），但**不再是驱动器的输入**。

判据是一条反向用例：**先问表再落 `request` ⇒ 不欠；先落 `request` 再问 ⇒ 欠**。
它解释的是「为什么必须改」，而不是「改了之后怎样」。

### 三小步

| 小步 | 内容 | 判据 |
|:-:|---|---|
| 5a | 前件改视图（`turn.needs_model` / `turn.needs_tools` + `has_tool_calls` 载荷） | 上面那条反向用例 + 既有序列用例全绿 |
| 5b | 驱动上移：`run_with_tools` 只跑**一笔债**，`chat_loop` 的 `loop` 每次问表取最小（`ring::drive` 去 `#[cfg(test)]`） | 判据 1（源码扫描：`turn_runner` 无循环） |
| 5c | 唤醒事实接入 + 删 `resume.rs` 旁路 | 判据 6 / 8 |

### 5c 里的一个未决语义（施工前必须定）

判据 6 写的是「审批 / 补充 / 中止都能唤醒 `await` 行」。三者的语义**不一样**：

| 唤醒源 | 落下的事实 | 等待该结束吗 |
|---|---|:-:|
| 审批 | `turn.stage{stage:"resume"}`（已存在） | **是**——恢复开新幕，`drive_of` 按幕锚收窄，上一幕的 `sent` 落在切片外，`await-*` 自然不欠 |
| 中止 | 收束格（`status:"aborted"`） | **是**——这一轮要收束了 |
| 补充 | `user.message`（同一幕内） | **否**——工具还在跑，等待仍然成立 |

前两者**已经**由现有机制成立（幕锚收窄 / 收束），不需要往 `until` 里加名字；
补充若加进 `until` 则语义错（一次插话会关掉一个还在跑的调用的账）。因此 5c 的
实际工作是：**补充要成为一条可被驱动器看见的意图**（「本幕有新发言 ⇒ 再来一次
模型往返」），而不是「补充关掉等待」。这个形状要在施工前定，否则会写出一个
「用户插一句话就丢掉了正在跑的工具批」的 bug。
