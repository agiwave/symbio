## 内容

父设计：[PL-017 · 端口细粒度化](../004-plan/017-端口细粒度化.md "PL-017-端口细粒度化")

**它解决的是 PL-016 留下的最后一层"环中环"。** T-223 之后，控制面是债环，但
`turn` 执行体内部仍是 747 行的 `run_with_tools`：模型调用与工具批次都不落事实，
崩溃只能重放整轮。本任务把这个内环倒过来。

**四组行**（复用 PL-016 的五个协议名，**不新增事实名**）：

```
dispatch-model   owes: request(port=model)          ← 落地的形状（与 turn 同模板）
                 until: sent(port=model) | failed
                 before: sent · by: courier
await-model      owes: sent(port=model)
                 until: response(port=model) | failed | retry
                 by: None

dispatch-tool    owes: request(port=tool)          ← 批由决策者写一条 request 开账
                 until: sent(port=tool) | failed
                 before: sent · by: courier
await-tool       owes: sent(port=tool)
                 until: response(port=tool) | failed | retry
                 by: None

close-turn       owes: turn.has_final ∧ ¬closed
                 until: chat.assistant.final | chat.assistant.fallback
                 by: closer
```

`turn.needs_model` / `turn.has_final` / `response.has_tool_calls` 是视图字段，不是新名字。

**四条边界**：

1. **流式不是债。** `courier` 在 `sent` 后把 `ExecEventSink` 的帧直通；`response`
   只在流结束时落一条。把 token 级帧写进日志会淹掉事实面（PL-014 §3 已裁决）。
2. **工具批是一次调用（步 3 的收窄）。** 初稿把批拆成 N 笔子债（`expand`），
   前提是执行体按调用跑；现网执行体是**批原子**的（批首闸门读一次、交互模式一条
   待用户动作就收掉批尾、批尾统一收口），拆出来的 N 笔账没有一笔能独立派发。
   单次调用的结果本来就逐条是事实（`artifact.added` 带 `tool_call_id`），恢复面
   因此不丢信息。执行体将来按调用跑时，`expand` 才成为它的形状（记在 PL-017 §3.1）。
3. **审批 / 补充 / 中止是唤醒源。** 它们由外部落事实（`approval.*` /
   `user.message` / 收束格），`await-tool` 的 `until` 增加对应名字。
   迁移完成前 `resume.rs` 的旁路保留；**最后一步必须删它**，否则有两条恢复路径。
4. **`turn` 执行体退成薄壳。** 它不再持有模型 / 工具循环，只负责把输入交回控制面；
   `turn_runner` 的 `while` 消失是本任务最硬的判据。

**施工分五步，每步一个提交**（PL-017 §4）：

| 步 | 内容 | 前置 |
|:-:|---|---|
| 1 | 把 `run_with_tools` 抽成 Step 循环（纯内部重构，行为不变） | T-223 |
| 2 | 模型端口两行 + 适配器 | 1 |
| 3 | 工具批端口两行 + 适配器（**调用单元 = 批**，见下） | 2 |
| 4 | 审批 / 补充 / 中止接入；删 `resume.rs` 旁路 | 3 |
| 5 | 收束成行（`close-turn`）+ 收束行的授权级联（[ADR-116](../010-adr/116.md "ADR-116")） | 4 |

**熔断线按提交计**：单次结构性改动 > 300 行 = 退回。步 1 可能接近上限，所以它必须是
**纯内部重构**（不改行为），否则应拆得更细。

## 处理过程

- 2026-10-22 立项。来源：第三轮核对发现 T-223 初稿"先做模型端口"与自己的文件面
  （不含 `turn_runner` / `turn_exec` / `tools`）冲突；模型端口不是一次调用替换，
  而是把内环倒置。ADR-115 决策 5 把它从 T-216 切出来，立 PL-017 与本任务。
- 2026-10-22 为什么 `prio: later`：它依赖 T-223/T-224 的事实面，且本身是一次执行
  引擎重写；在粗端口跑通、e2e 稳定之前动它，会把两个变量混在一次改动里。
  这不是"以后再说"——PL-017 的目标形状与判据已经写死，只等前置。
- 2026-10-22 **接收 [T-226-授权行](226-授权行.md) 移交的授权级联**（判据 8b）。理由是“一次调用要有一个
  可判的能力”：`request{port:turn}` 不带能力维度，而工具调用自带（审批 + 权限面，
  t78 钉的就是审批先于执行）——级联只有在细端口上才有前件可判。因此
  `authorize` / `dispatch` 两行的 `prio` 级联进本任务的第 3 步，不另立任务。
- 2026-10-22 **步 1 落地**：轮内循环写成**显式步循环**（`steps` 计数 + 上界检查 +
  一步一次 `stream_round`），步的边界从此是代码里的一处，而不是「回 `None` 就再来
  一圈」的隐含约定。
  - **唯一的行为变化是上界**：`MAX_STEPS_PER_DRIVE = 64`（[ADR-115](../010-adr/115.md
    "ADR-115") 决策 3）。此前这一圈**没有上界**：一个总请求工具的适配器能让这一轮
    永不返回，而每圈都真花一次模型往返。上界是**停机判据**不是性能阀——到顶落
    `reason: exhausted` + `detail: step_limit`（与 `finish_reason = length` 同一闭集
    值，读侧不必学新词）。落格走 `settle::append_exhausted`，与兜底共用
    `land_failure`（闸门 / 幂等键 / `produced` 形状一致，只差 `reason`）。
  - **口径修正**：PL-017 §4 步 1 标称的「纯内部重构，行为不变」不覆盖这条上界——上界
    来自 [ADR-115](../010-adr/115.md "ADR-115") 决策 3（不是新规则），差异记在这里。
  - 用例：`a_runaway_adapter_is_stopped_at_the_step_bound`（永远要工具的适配器 ⇒
    恰好 64 次模型往返后收束为 `exhausted`）。反向自检：删掉上界检查，用例**不会
    变红而是挂住**——那正是它防的病。
  - **步 1 尚未满足的**：判据 1（`turn_runner` 内没有 `while` 驱动模型 / 工具）。步
    2 把模型调用变成行之后，循环才真正离开执行体。
- 2026-10-22 **步 2 落地**：模型端口两行 + 适配器。
  - **行表**：`dispatch-model`（prio 66）/ `await-model`（prio 71），与 `turn` 的两行
    **同模板**（`owes` = `request{port:model}`，`until` = `sent` / `failed`；
    `await` 的 `until` 再加 `response` / `retry`）——判据 7「加一个端口 = 0 个新事实名
    + 1 个 `PortDecl` + 2 行」在本步**首次被真实走了一遍**。
  - **端口声明**：`PORTS` 加一条 `PortDecl { port: "model", before: sent, lease_ms:
    600_000, max_attempts: 1 }`。租约与 `turn` 同量级（慢的那一头同样是模型排队）；
    `max_attempts = 1` 同理——进程重启后等这笔应答的 future 已经不在了，重试只会
    留下一条**永不派发**的 `request`。等步 4 的唤醒事实接上（有活着的等待方）时，
    这个上限才可以 > 1。
  - **接线**：`stream.rs` 新增 `call_model`——**协议事实的唯一写方**仍是 `port`
    模块（`announce` 写 `request`，`dispatch` 落 `sent` 与 `response` / `failed`）。
    运行器只做活：它把「这一次模型往返」交给引擎，不自己记账。
  - **逻辑 id** = `model-{turn}-d{drive_seq}-s{step}`。三个后缀各管一件事：轮号
    （哪一轮）、**幕锚**（续写幕复用轮号，只带轮号会与首幕撞成同一笔——首幕已经
    有过 `sent`，幂等键命中之后派发会被拒）、**步号**（一次往返一个 id，否则第二
    次的 `sent` 撞第一次的幂等键）。
  - **失败分三类**（`ModelCallError`）：适配器**中止** ⇒ 中止收束格；适配器**失败**
    ⇒ 兜底格；**协议事实落不进去** ⇒ 往上传（事件都记不下来，后面的一切都不可信）；
    **控制面不一致**（行不欠 / 端口没声明）⇒ 如实当失败报。把它们揉进一个错误
    类型，就只能给它们同一个形状。
  - **判据 2 钉住**：`every_model_call_leaves_a_sent_and_an_answer`（每次模型往返
    都有 `request` / `sent` / 应答，三者同 id，两次往返两个 id）+ 行侧的
    `a_model_request_opens_dispatch_and_sent_closes_it` /
    `a_model_failure_closes_both_the_dispatch_and_the_wait` /
    `the_model_rows_do_not_disturb_the_turn_rows`。
  - **事实量上升**（PL-017 §6 已预告）：每次模型往返多 3 格（`request` / `sent` /
    `response`）。既有用例的事件序列断言因此改写——它们改为断言**整条序列**
    （新增 `kinds` 辅助函数），而不是散在各处改下标。
  - **步 2 尚未满足的**：判据 1（循环仍在执行体里——模型调用已是行，但**驱动**它
    的步循环还在 `run_with_tools`；这正是步 3 要做的事：工具批次也变成行之后，
    循环才能彻底离开执行体）。判据 3（`in_flight` 按调用重建）与判据 5（流式帧
    不产生事实）在本步**天然满足**（模型端口的 `sent` 落的是协议事实，流式帧仍
    直通 `ExecEventSink`），但它们的用例要到步 3 / 步 4 才补齐。
- 2026-10-22 **步 3 落地（3a：工具批端口）**：`dispatch-tool`（prio 67）/ `await-tool`
  （prio 72）两行 + `PORTS` 一条 `PortDecl { port: "tool", lease_ms: 600_000,
  max_attempts: 1 }`；`stream.rs` 的 `call_tools` 包住整批派发。判据 7 第二次被真实
  走了一遍：**0 个新事实名、0 行求解器改动**（`port-surface-audit` PTS-003 基线
  未动），加端口只加了「1 条 `PortDecl` + 2 行 + 1 处调用点」。
  - **行名按端口名派生**（`dispatch-tool` / `await-tool`，不是初稿的
    `dispatch-tools`）：`every_port_row_is_in_the_table` 机械检查「每个端口两行」，
    模板一旦允许例外，加端口就不再是纯加法。
  - **调用单元是「批」，不是「单次调用」**（与初稿的 `expand` 不同，理由记在
    「四条边界」第 2 条与 `PORTS` 的 `tool` 一节）：执行体是批原子的，拆成 N 笔
    子债会得到 N 笔**无法独立派发**的账。`expand` 因此**没有实现**——它属于
    「执行体按调用跑」的那一天，不是今天。
  - **协议事实先于产物格**：`request` → `sent` → 跑批 → `response` → `artifact.added`。
    批返回之后它的结果才成为事实；崩溃在 `sent` 与 `response` 之间时，日志里
    「这一批派出去了、没回来」是可读的。
  - **`why` 位不撒谎**：分发契约本身不可失败（工具报错是**信息性结果**，要喂回
    模型），所以 `call_tools` 的 `E = String` 永远不会被返回；`failed` 只由引擎的
    记账路径落。控制面不一致（行不欠 / 端口没声明）走**兜底格**而不是静默跳过
    工具——跳过会让模型下一轮看到「请求过却什么也没发生」。
  - 用例：`every_tool_batch_leaves_a_sent_and_an_answer`（一批 ⇒ 一条 `request` /
    `sent` / 应答，三者同 id；工具端口三格在产物格之前）。反向自检：把
    `call_tools` 换回裸的 `dispatch.dispatch(&rt)`，用例红在「一批 ⇒ 一条 request」。
  - **步 3b（授权级联）不在本步落地，家已改到收束行**：
    [ADR-116](../010-adr/116.md "ADR-116") 记了三条代码里可查的事实——工具批的
    派发时刻没有单一可判的能力、拒止的产物是**结果**（拦在派发之前会让下一条请求
    带一条没有结果的 `tool_call`）、拒止按设计**零事件**（`RefusalTraceKind::ZeroEvent`
    是四份事实出口之一）。因此 `authorize` / `dispatch` 两行的级联随**步 5**（收束
    成行）落地，判据 8b 的判据面一并改到 `close-turn`。
  - **步 3 尚未满足的**：判据 1（步循环仍在 `run_with_tools` 里——工具批已是行，但
    **驱动**它的是执行体的 `while`；那要等收束也变成行，步 5）、判据 3 / 5 的用例
    （与步 4 一起补）、判据 6（唤醒事实）、判据 8（`resume.rs` 旁路）。
