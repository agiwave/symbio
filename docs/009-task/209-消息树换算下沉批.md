## 内容

父设计：总报告 B4 · 07 报告建议 3

**问题**：275 行的消息树换算住在模型插件里，且**正确性靠注释里的经验维持**。
两处消费方（主路径与另一条消费路径）各自理解同一份换算，一旦分叉无人会红。

**两件事，一个目的**：

1. **拆模块**：消息形状换算 / 树形路径 / 跨轮降级三段——不是为了行数，而是为了让
   「哪一段错了谁会红」有答案；
2. **沉 core**：换算是不含 IO 的纯函数；它是否下沉由 [ADR-023](../010-adr/023.md) 的依赖方数量判据裁决，
   两个以上消费方才沉（实测结果见下方处理过程）。

**「事故知识从注释升级为绿」是本批真正的判据**：这段代码的历史事故（树形路径拼错、
降级后恢复轮丢失）都记在注释里，注释不会红。把 t27 / t38 的判据各配一条**具名测试**，
事故知识才变成「改错了就红」。

**风险如实写**：换算分支多（树形 / 降级 / 恢复轮），搬家时须**逐分支对照行为**。
这也是本批排 later 的原因之一——它不产生新能力，只降低下一次改换算的风险；
在机制面收敛（now / next）之前做，会与它们争同一批 review 注意力。

**不新增机制**：纯函数下沉不改契约形状，机制键 0、trait 0。

## 迁移记录（逐分支对照）

拆分的判据是「哪一段错了谁会红」，所以对照按**段**列，每段列出它承载的全部判据分支，
以及搬家时对该分支做了什么。三段各自一句话的边界：tree 只回答「在哪、归谁」，
shape 只回答「有这个东西时长成什么形状」，degrade 只回答「这个东西缺了怎么办」。

### 树形路径 → `message_builder/tree.rs`（`RequestTree`）

| # | 分支 | 原样搬 | 搬家中的改动 | 谁会红 |
|---|---|---|---|---|
| T1 | `children` 孩子表按**落库序**累积 | ✅ | 无（`kids()` 返回 `&[&ChatNode]` 切片，仍是同一份 `Vec` 的顺序） | 聚合取值顺序变了：文本 / 思考「取后写的」这条隐式判据失效 |
| T2 | `wire_ids`：只对 `is_tool_call()` 节点建表，`tool_call_id` 空白则回退节点 id | ✅ | 无（移到 `wire_id_of` 闭包同一份逻辑） | 恢复轮把节点 id 发给只认 wire id 的协议（OpenAI Responses 的 `call_id` 链） |
| T3 | `consumed`：每个根级 Turn 收**全部子孙** id、**不含 Turn 自身**，栈式迭代 | ✅ | 无 | 含自身 ⇒ 根级 Turn 永不聚合（请求包丢整轮）；不含子孙 ⇒ reasoning / 工具参数 / 结果重复一遍 |
| T4 | `retained_reasoning`：携带 Reasoning 的根级 Turn，`rev().take(2)` | ✅ | 常量 `RETAINED_RECENT_REASONING = 2` 随段搬入，判据不变 | 思考全清（模型重复思考）或全回传（浪费 token + 复述旧结论） |
| T5 | `is_root`：`parent_id` 缺失**或**指向不在本批的节点（裸根形态） | ✅ | 由闭包捕获 `by_id` 改为显式参数（脱离函数作用域后必需），真值表不变 | 子节点被当根单独发一条 |
| T6 | `find_tool_result` 三分支：非空直接 `Text(Tool)` → `Turn(Tool)` 包装内的 `Text`（子 agent 会话）→ 任意直接 `Text(Tool)` | ✅ | 自由函数改为 `RequestTree` 方法（同一 `children`） | 跨轮工具结果配不上，落到占位（模型看见「被中断」而实际有结果） |

### 消息形状换算 → `message_builder/shape.rs`

| # | 分支 | 原样搬 | 搬家中的改动 | 谁会红 |
|---|---|---|---|---|
| S1 | `Turn` → 一条 `assistant`：`role` 强制、`content` / `reasoning_content` / `tool_calls` 三格先清空 | ✅ | 无 | 上一格的残留混进本轮 |
| S2 | Reasoning 子节点仅当 `retains_reasoning` 才写 `reasoning_content` | ✅ | 判据换成 `tree` 的方法调用 | 同 T4 |
| S3 | `Text` 子节点覆盖式取值（后写胜出） | ✅ | 无 | 一轮多段正文时只剩第一段 |
| S4 | `ToolCall` → `tool_calls`：合法 JSON 文本以 `Value::String` **原样透传**（省一次物化 + re-serialize），非法回退 `{}`；`id` 取 wire id 回退节点 id；`name` 缺失取空串 | ✅ | 无（含「落库时已规范化」的注释，它解释的正是这段透传） | 参数被 re-serialize 改写 → 与签发值不一致 |
| S5 | 结果节点 → 独立 `role=tool`，`tool_call_id` = 该 ToolCall 的 wire id（可能是 `None`，交给清洗段扔） | ✅ | 无 | 结果与调用配不上 → provider 400 |
| S6 | 失败 `Turn`：半截输出照常聚合，正文尾部交 `degrade::append_interrupt_note` | ✅ | `if status == Failed` 的判据留在 shape（它属「有这个东西时长成什么形状」），拼接收进 degrade | 「降级没生效」与「聚合写错了」混成同一条红 |
| S7 | 根级非 `Turn` 非压缩 → `plain_root`；`Tool` 角色回填父 ToolCall 的 wire id，回退 `parent_id` 原值 | ✅ | 无 | 历史数据（无 `tool_call_id` 字段）的回退路径消失 |
| S8 | 压缩节点不发（`else if is_compression()` 空分支） | ✅ | 留在 `flatten_chat_messages` 编排里，注释随段 | 压缩动作被当成对话事实喂回模型 |

### 跨轮降级 → `message_builder/degrade.rs`

| # | 分支 | 原样搬 | 搬家中的改动 | 谁会红 |
|---|---|---|---|---|
| D1 | 缺结果的 `ToolCall` → 占位 `role=tool`（`[工具 X 的执行被中断，未产生结果。]`），且必须在聚合遍内进 `tool_results`（先于 D4 的孤儿剔除） | ✅ | 抽成 `placeholder_tool_result(tool_name, wire_id)`；顺序约束写进函数文档，因为它是调用方的义务 | 占位被当孤儿误删 → 「有 tool_call 无 tool_result」400，一整轮恢复不了 |
| D2 | 结果节点 `status=Failed` → `success=Some(false)`（Anthropic `is_error`）；非失败不动这一格留 `None` | ✅ | 抽成 `mark_failed_result` | 跨轮工具失败被过滤丢失，模型看不见 |
| D3 | 失败 Turn 的中断说明：有 `error` 带原因 / 无 `error` 用兜底文案；已有非空正文则 `\n\n` 追加，否则整条替换 | ✅ | `native.content` 改为 `take()`（原式在同一语句里移出再回填，等价） | 思维链断裂，模型把半截输出当完整结论 |
| D4 | 清洗 ①：`role=tool` 且（无 id 或 id 不在本批 `tool_calls` 集合）→ 扔 | ✅ | 两层 `if let / else` 改写成 `match { Some(tid) if contains => 留, _ => 扔 }`——**本批唯一一处非逐字**，三格真值表（Some&in / Some&out / None）逐格核对一致 | 脏消息发到 provider 触发反序列化失败 |
| D5 | 清洗 ②：`assistant` 且正文空或缺失、无 `reasoning_content`、无 `tool_calls` → 扔 | ✅ | 无 | 空壳回合发到 provider |

### 恢复轮（跨段合起来才成立的那一支）

`e2e/cases/t27-approval-resume` 的形状是 T2（wire id）+ S4 + S5 + D1 + D3 四段协作的结果，
任何一段单独正确都不够：中断轮的 `tool_call` 与它的占位结果必须回传**同一个** provider
原始 id，节点 id 一律不外泄。`e2e/cases/t38-transcript-tool-projection` 依赖的是
T6 第二分支（`Turn(Tool)` 包装）+ S5，即第二轮请求包带上第一轮的子 agent 结果。
这两条就是下面新增具名判据各自钉住的形状。

## 处理过程

- 2026-10-20 立批。来源：总报告 B4 + 07 报告建议 3。
- 2026-10-20 顺序：先拆模块（行为零变化），再沉 core（位置变化），最后补测试——
  三步分开提交，任一步出错都能单独定位；合并成一步会让「行为变了」与「位置变了」混在一起。
- 2026-10-20 与 [T-197-模型消费端口归一批](197-模型消费端口归一批.md) 的关系：
  T-197 改「取模型能力走哪条链」，本批改「换算逻辑住哪」。两者都在模型面，
  但 T-197 先行（它决定换算还有几个消费方，而消费方数量正是下沉判据的输入）。
- 2026-10-21 段二实测后结案为**不沉**，不是降标：出口条写的是「符合 [ADR-023](../010-adr/023.md) 依赖方
  数量判据（两个以上消费方）」，判据本身要求的动作是**数依赖方**，而数出来的答案是
  `flatten_chat_messages` 的四个调用点（anthropic / gemini / openai_chat / openai_responses）
  **同住 `plugins/model/protocols/` 一个模块**——一个模块依赖的内容一律留在该模块，
  core 只放契约不放实现。出口条里那句「两个以上消费方」是立批时**未经测量的假设**，
  按 ADR-023 的原文（判据可 grep 一遍就有答案）测出来它不成立，于是这一半的正确落地
  就是把裁决写进 `message_builder.rs` 模块文档并说明「第二个模块出现时再谈上提」。
- 2026-10-21 段一与段三同批提交（`7974e55b`）：段二既然不产生代码搬家，三步只剩两步，
  而「行为零变化的搬运」与「搬运之后新增的具名判据」在同一个提交里反而是**更强的证明**——
  既有 16 条 flatten 用例一条断言未改就通过，正是「换算逻辑零变化」的凭证；把测试单独
  拆一个提交会让第一个提交没有任何判据背书。事实表（同一份生成文件）也同时含两段的行数，
  硬拆会在中间提交里留下与树不符的规模数。
- 2026-10-21 新夹具的 `role` 格直写全部集中在一个构造器（带一条具名豁免注释），
  S-014 存量 151 持平——搬换算不该顺手把棘轮顶高。
