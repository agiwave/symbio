## 内容

父设计：[ADR-075](../010-adr/075.md "ADR-075") · [PL-014](../004-plan/014-单环一表收敛.md "PL-014-单环一表收敛") §5 步骤 6 前置 P1（常驻任务可取消）

**问题**：分形插件架构的卖点是「插件可组合、可卸载」，但**只有 start 没有 stop 的插件树不可靠**。
`Plugin::stop` 的缺口自 ADR-075 点名至今未补：

- gateway / telegram 插件**被停用后，后台长轮询 / 监听仍在跑**；
- 没有并发上限、没有幂等（入站请求重复处理无保护，另立 [T-194](194-入站边界加固批.md "T-194-入站边界加固批")）；
- telegram 的 chat_id 绑定、hook 注册等关键状态**纯内存**，进程重启即失（落盘归 T-194）。

**为什么这是 now**：它是本轮全部建议里**唯一「已登记且已过期」的债**——ADR-075 早已裁决，
`Plugin::stop` 的默认实现为空，接上不改变现有行为，成本低而收益直接落在「停用是否真的停用」
这个可观测事实上。补这一处同时解锁 gateway / telegram / heartbeat / hook 四个外围插件的可靠性。

**边界**：本批只做**插件级停用收口**。进程退出的整树广播已由
[T-078](078-shutdown接线批.md "T-078-shutdown接线批") 落地（`PluginStopReason::Shutdown`，
composite 遍历是 owner），不重做；telegram 的 `stop_listener` 已有 e2e 用例
（[T-110](110-通道与自动化面e2e补位.md "T-110-通道与自动化面e2e补位")），复用而不另写。

**判据形态**：不是「调用了 stop」，而是「停用之后后台没有残留」——用独立探针（一个不经过插件
的观测点）看，而不是问插件自己「你停了吗」。
