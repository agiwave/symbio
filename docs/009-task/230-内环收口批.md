## 内容

父设计：[PL-017 · 端口细粒度化](../004-plan/017-端口细粒度化.md "PL-017-端口细粒度化")；
形状裁决：[ADR-114](../010-adr/114.md "ADR-114") · [ADR-115](../010-adr/115.md "ADR-115") ·
[T-229 的集合展开](../010-adr/116.md "ADR-116")。

T-227 把 `run_with_tools` 的内环拆成了行，但**收口留了两处形态偏差**（T-227
「处理过程」末条如实记着）：

1. **工具批次没有用 `Decl.expand` 展开**——改在派发时每调用落一对 `request` / `sent`。
   机制层已由 T-229（ADR-116）补齐，**生产行接入**尚未做。
2. **步循环没有进引擎的行调度**——从 `turn_runner` 移到了 `turn_exec::drive_steps`，
   运行器退成单步，但「读行债 → 派发」的引擎调度仍是 T-216 / PL-016 的剩余迁移。

本批把这两处收口到目标形状。**它不是新架构**：PL-014 §2.1 的终点
（`agent = fixpoint(decide) over (事实日志 × 世界端口)`）不变，变的是「谁在驱动这个
不动点」——从执行器里的 `begin` / `step` 循环换回引擎的 `owed` / `drive`。

**批内分解**（子任务各自一个提交）：

| 子任务 | 内容 | 前置 |
|---|---|---|
| [T-231](231-恢复调用进债环.md "T-231-恢复调用进债环") | 恢复调用进债环：审批后的那一笔要有自己的债前件 | — |
| [T-232](232-创建行接入集合展开.md "T-232-创建行接入集合展开") | 创建行 `open-tools` 接入 `expand`（派发行仍欠 `authz.granted`，ADR-117） | T-231 |
| [T-233](233-引擎行驱动调度.md "T-233-引擎行驱动调度") | `drive_steps` 的手写循环换成「读行债 → 派发」 | T-232 |
| [T-234](234-流式帧不入事实用例.md "T-234-流式帧不入事实用例") | 判据 5 用例：流式帧直通且日志不增 | — |

**顺序理由**：T-231 是 T-232 的前置（否则 `dispatch-tools` 一迁到 `response`，恢复
那一笔就失去债）；T-232 落地后工具批次才真正由 `expand` 表达，T-233 才能把这个
集合交给引擎调度。T-234 独立，先把判据补上不挡任何事。

**不在本批**：不做通用并行调度器（PL-017 §7）；不做 L2 级重执行一致（PL-001 §11）；
不改工具 schema / 流式协议 / 审批 API。

- 2026-10-22 立批。来源：T-227 收口时如实记录的两处形态偏差 + 核对
  `turn_exec::drive_steps`（循环仍在执行器，`drive` 仍是 `#[cfg(test)]`）+

  架构形状要先有方案 / ADR 裁决，再由实现跟进；本子任务先做设计再落地，
  不拿实现难度当改形状的理由。
