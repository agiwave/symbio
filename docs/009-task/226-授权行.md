## 内容

父设计：[PL-016 · 义务环](../004-plan/016-义务环.md "PL-016-义务环") §4.2 ·
[ADR-115](../010-adr/115.md "ADR-115") 决策 6

**T-219 已经做了哪一半。** `authz.denied{key, kind, reason, detail}` 已落事实，写侧在
`turn_runner::deny`；矩阵与三层判定原样。缺的是**放行侧**与**表里的顺序**：

| 今天 | 缺口 |
|---|---|
| 拒绝落 `denied`，允许不落任何事实 | "允许"只能靠"没有 `denied`"推断——又是用"没写"表达状态 |
| 判定在 `closure_gate` 里按种类分两臂 | 判定正确，但它不在表里，`owes` 无法以它为前件 |
| 派发 / 收束直接调执行体 | 没有一行能表达"先授权、后派发" |

**两行级联**：

```
行  authorize   owes:   request(port, id)
                until:  authz.granted(id) | authz.denied(id)
                by:     authorizer
                prio:   0                 ← 必须早于 dispatch

行  dispatch    owes:   request(port, id) ∧ authz.granted(id)
                until:  sent(port, id, attempt) | failed(port, id)
                by:     courier
                prio:   10
```

`authorize` 先还清；它交回 `granted` 后，`dispatch` 的 `owes` 才成立；交回 `denied`
后 `dispatch` **永不成立**——没有 `granted` 就没有前件。**不需要否定原子**：

- `owes` 是正事实的合取（`request ∧ granted`）；
- `until` 是正事实的析取；
- "没有授权记录"与"被拒绝"在匹配上完全可分（后者有 `denied`，前者两者都没有，
  `authorize` 行仍开着）。

**`key` 的形状**：`id` 的取值，编码"主体 × 能力 × 资源"，例如
`session/main#chat.assistant.final#turn-42`。`Pattern` 只做等值匹配，不需要引擎认识
三个维度。矩阵的判定函数原样返回一个布尔与原因，`authorizer` 把它翻成
`granted{id}` 或 `denied{id, why}`——**判定位置不动，只补事实出口**。

**为什么不做成 `drive` 里的前置检查**：那会让引擎认识"授权"这个业务概念，且拒绝路径
变成异常分支。义务环里没有异常分支，只有事实；`prio: 0` 就是"先授权"的全部表达。

**明确不做**：

- 不改 `PermissionMatrix` 的三层判定与 fail-closed 语义。
- 不做"按维度分别匹配"的键表达式（那是 `Pattern` 的新语法，走新裁决）。
- 不把 `denied` 算成收束：被拒的一轮仍 `unresolved`（T-219 的三条边界不变）。
- 不为授权新开 `Entity` 行；`authz.*` 落既有 `turn × asserted`。

## 判据

| # | 判据 | 检查方式 |
|:-:|---|---|
| 1 | `authorize` 行先于 `dispatch` 行 | 用例：同 `id` 两笔债，`prio` 决定顺序 |
| 2 | `denied` ⇒ 没有 `sent` 事实 | 用例：拒绝后日志里查不到该 `id` 的 `sent` |
| 3 | `granted` ⇒ 才可能 `sent` | 用例：没有 `granted` 时 `dispatch` 不成立 |
| 4 | `owes` 里没有否定原子 | 类型上：`Pattern` 只有正合取（装载期检查） |
| 5 | 矩阵判定的既有用例逐条不变 | 对拍：T-219 的拒绝用例 + 允许用例 |
| 6 | 放行 / 拒绝都可回放 | 用例：只给日志，重算 `authorize` 行的欠账 |
| 7 | 网格新增 1 个名字（`authz.granted`）：31 个业务名 + 5 个协议名 = 36 → 37 | `git diff` 只增不删 |

## 处理过程

- 2026-10-22 立项。T-219 只落了拒绝侧；第三轮核对发现 `¬permitted` 作为 `owes`
  会逼 `Pattern` 长出否定原子，并与 `open` 公式里的"不存在 `until`"叠加，让
  "无记录"与"被拒绝"不可分（fail-open 风险）。ADR-115 决策 6 改成正事实级联。
- 2026-10-22 为什么排在 T-224 之后：两行要匹配 `request` / `sent`，这两个协议名在
  T-224 才入库。`authz.granted` 本身是业务事实，由本任务新增。
- 2026-10-22 与 T-219 的关系：**不是推翻，是补另一半**。T-219 的 `denied` 事实、
  幂等键、三条边界全部保留；本任务只加 `granted` 与两行的顺序。
- 2026-10-22 施工前分析（T-223 落地后重读本任务的出口，发现前件无内容可判）：

  **级联的两行要成立，`request` 必须携带一个能力维度。** 但粗端口 `turn` 的
  `request` 只带 `port / id / attempt`——它说的是「这一轮欠一次往返」，不是
  「这个主体要做一件需要许可的事」。现网唯一可问的授权判定是写侧收束闸
  （`closure_gate(actor, Speech|Artifact)`，7 个调用点全在落收束格之前，T-219 未动），
  拿它去给 `turn` 派发做前件会得到两种结果，两种都不诚实：

  | 把 `authorize` 判成 | 后果 |
  |---|---|
  | 恒过（“是这轮自己的主体”） | 一行永远能还清的债 + 每轮一条无读方的 `granted` 事实——剧场 |
  | 按 `Speech` 判 | 不持 `reply.*` 但持产物能力的主体连轮都跑不了——而产物本可以在轮内落 |

  **不选“先落 `granted` 事实、级联以后再说”。** 那会把一条**无读方**的事实
  入库（装载期只会报 `OrphanFact`），并在 `in_flight` 之外多一份“谁被允许过”的
  影子账——比不记更坏：它看起来像已经实现了级联。

  **正当的家在 T-227。** 级联需要的是「一次调用有一个可判的能力」：
  `dispatch-tools` 的工具调用正是这种形状（它有自己的审批与权限面，t78 钉的就是
  审批先于执行），`dispatch-model` 也可以用档位作能力。所以：本任务的**两行级联**
  移交 [T-227](227-端口细粒度化.md "T-227-端口细粒度化") 的第 3–4 步（工具批次端口
  + 唤醒源接入），作为它的判据之一；T-226 保留的是“拒绝/放行必须都是写了的事实”
  这条已由 T-219 兑现的形状。

  **所以本任务停在 `doing`，不宣称完成。** 留下的是一条有名有姓的移交
  （T-227 步 3–4），而不是一个能变绿的空行。T-216 批次因此也停在 `doing`：
  它的“判据 16 条全绿”里含这一条。
