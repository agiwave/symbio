## 内容

父设计：01 报告建议 2 / 3 · 02 报告建议 2 · 总报告 C4 与 §4.4 断层四

**同一件事有两处以上表述时，漂移只是时间问题**。本批收三处：

| 现象 | 现状 | 风险 |
|---|---|---|
| `PluginMeta` 身份残留 | 「出厂 id」与「PLUGIN.yml 身份」两套口径（与 ADR-032 部分冲突） | 停用 / 未构造插件的身份依赖「首次装配过」的历史 |
| `work` 幽灵命名空间 | 命名存在，但无对应插件 | 「前缀 = 目录名」这条不变量有例外，而 E-002 只判**引用**侧（谁写了 `work/…`），注册侧（臂本身就长在 `home` 的 `match` 里）无人判 ⇒ 幽灵一路活到文档照抄才被人看见 |
| 构造失败只有日志 | 未注册 / TypeId 不符 / 构造 panic 三种失败同形 | J3：构造失败只进日志，注册表里看不出来 |

**三处的共同形状**：**身份与清单没有单一 owner**。v2 的 I1 单通道不只约束状态变更，
也约束**同一概念的表述**——这是本仓文档纪律已经立住的规矩（一个事实一个 owner），
只是尚未在代码身份层全面落实。

**为什么 `PluginMeta` 只能「按既定归属推进」而不是现在就删**：ADR-032 已裁决
「不提前立项，随 A1 波次」。本批的价值在于**不要把它从波次里弄丢**——不是重新论证该不该做。

**构造失败结构化的收益**（比它看起来重要）：它是 J3 的直接兑现——把「构造失败只进日志」
的静默面变成**注册表可见状态**。用户在插件管理页今天只能看到「在」与「不在」，
本批之后能看到「配了一半」之外的第三种：**装配失败，原因是 X**。

**与 [T-192](192-root装配为composite批.md "T-192-root装配为composite批") 的关系**：T-192 改
「谁来当根容器」，本批改「身份挂在哪」。原计划「容器定了，身份归属才有唯一答案，故 T-192 先行」
已随 T-192 转 `wont` 而失效——**但只有 ① 受影响**：`PluginMeta` 身份字段的删除要等 A1 波次
（ADR-032 明令不提前立项），而根容器是谁并不改变「出厂 id 与 manifest 身份是两套口径」这件事。
②（`work` 命名空间）与 ③（构造失败可见）都不动装配形状，照做。

## 处理过程

- 2026-10-20 立批。来源：01 报告建议 2 / 3 + 02 报告建议 2 + 总报告 C4 的三项。
- 2026-10-20 为什么合成一批：三项都在装配期、都改「身份 / 命名」这一类事实，分开做会三次
  触碰同一批装配代码；且它们的判据互相印证（身份单源之后，`work` 白名单与构造失败列才有落点）。
- 2026-10-20 与 [T-215](215-路由与载荷契约单源化批.md "T-215-路由与载荷契约单源化批") 的分工：
  本批让「前缀 = 目录名」无例外；T-215 讨论「路由清单能不能由 manifest 自动生成」——
  后者需要 trait 变宽，须先过 ADR，不能与本批混提。
- 2026-10-21 ②（`work` 幽灵命名空间）闭环，**按 owner 归属而不是按原 exit 的字面**做：
  原 exit 写「收编为真插件目录」，核完事实后否决——`work` 不是「一个还没被做成插件的能力」，
  它就是 home 自己那份 `<homedir>/PLUGIN.yml` 的 `work` 配置段（读写方都在 `home/plugin.rs`
  的同一个 `match` 里），为它新建一个插件目录是**为一条写错的名字补一个架构元素**。
  落地即改名：两条臂 `work/set_workspace` · `work/get_workspace` → `home/set_workspace` ·
  `home/get_workspace`，`home/schemas.rs` 里的契约模块 `work_get_workspace` → `home_get_workspace`，
  前端 `services/home.ts`、只读白名单判据、e2e `t69` 注释、`003-ROUTES` / `001-CONFIGURATION`
  / `002-DATA_FLOW` / `005-SYSTEM_MAP` / `005-e2e覆盖矩阵` / `AR-008` 同步，生成物
  （`routes.gen.ts` · `CURRENT.md`）重跑。对外地址自此**全部**满足「前缀 = 目录名」。
- 2026-10-21 顺带订正两处任务书事实错误（都写在上面的表与 exit 里，不订正就会被照抄施工）：
  ① E-002 **没有** `work` 白名单可删——它原本只判**引用**侧（某处写了 `hooks/fire`），
  臂本身的前缀无人判（引用侧要保守：全仓字面量里大半是 MIME、JSON-RPC 方法名、shell 候选与
  模型 id，按形状全量判会产出几十条误报）。补的是**注册侧**判据：home 的臂必须以 `home/`
  开头（它收到的是未剥离的 PATH），其余插件的臂不得写成绝对形（容器剥首段才转发）。
  ② 「gateway 只读白名单放行 `work/get_workspace`」是文档口径——[T-115](115-入站边界可达面与白名单一致批.md "T-115-入站边界可达面与白名单一致批") 之后白名单里根本没有它，
  `003-ROUTES` 那行照抄的是旧状态，一并订正（`AR-008` §4.1「未命中兜底上行转发」同样与
  `Composite::route` 的实际行为相反，按 t69 ⑦ 钉住的边界事实重写）。
