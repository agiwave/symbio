## 1. 场景：要什么能力

多个任务同时在跑，谁就绪谁上；同一资源同一时刻只有一人持有（租约）；冲突时有仲裁而不是竞态。

相对 S03 高了什么：**从"一个执行序列"到"一个调度系统"**。T2 的任务图是静态的，
T3 的调度器要在运行时判定就绪、发放租约、处理抢占。

## 2. 为什么它能落在 v2 上（J1）

并发最容易诱使架构师引入"调度器组件"。拆开看：

| 看起来新的东西 | 实际是 |
|---|---|
| 调度器 | 一个 `Decider`，输入 `ReadySet` 视图，输出 `task.assigned` 事件 |
| 就绪判定 | `projection = readyset`——**纯函数，从事件序列算** |
| 租约 | `task/held`（`task.blocked`）+ 带 TTL 的事件，不是锁原语 |
| 仲裁 | 单写者 FIFO——I1 的推论，不是新机制 |

**关键**：租约是**事件**不是锁。锁需要"持有状态"，事件不需要——持有状态由投影算出。
所以整个系统没有并发原语，只有一个 FIFO 和一条单调 `seq`。**新增机制键 = 0**。

## 4. 平凡值与回退（J2）

| 参数 | 完整值 | **平凡值** | 平凡值下 |
|---|---|---|---|
| `projection` | `readyset` | **`readyset:cap=1`** | 仍完整运行——就绪集容量为 1，退化为串行 FIFO |
| `actor.budget_ms` | `80` | `60000` | 仍完整运行——调度慢，但不错 |

**`cap=1` 是本阶最漂亮的一个平凡值**：把并发度调到 1，调度器、租约、仲裁逻辑**一行代码都不用改**，
系统自动变成 S03 的串行执行。这说明并发度确实是参数而非结构。

> ⚠️ **今天这一行是设计意图，不是可执行事实**：`readyset` **没有**容量参数（模块头把容量推给
> 「调用方的调度器」，而该调度器不存在）。行保留加粗是生成器要求（每阶恰有一行加粗平凡值），
> 落地形态与处置见 [ADR-064](../010-adr/064.md)。

## 5. 静默失效与强制（J3）

| 约束 | 违反时信号 | 强制方式 |
|---|---|---|
| `seq` 严格单调 | **无**——只是顺序乱了 | CI 断言（`invariants.rs`） |
| 单写者 FIFO | **无**——竞态只在压力下偶发 | 运行时 FIFO + 静态扫描无主体直连 |
| 租约 TTL 必须被检查 | **无**——可能死锁且无人报错 | 调度者预算内必产出（I3） |

## 8. 这一阶做不了什么

边界的唯一账本：[SC-004-并发调度与租约](../002-scene/004-并发调度与租约.md)（用户语言）。机制面独有边界（用户可见范围之外的工程约束）：

- 分布式部署下 `seq` 单调如何保证**未展开**（[T-014](../009-task/014.md)）——单进程 FIFO 成立，多副本要补一条 ADR。
- 优先级、公平性、饥饿——都是 `readyset` 的打分参数，不是机制。
- **调度器 / 租约 TTL / `cap` 参数**要动 `symbio_core` 的事件词汇表（核心公共面变宽），
  不在本阶梯「架构改动 = 0」的承诺内；将来要做须先按 [ADR-055](../010-adr/055.md) 立放宽决策，
  且**写方与消费方同批落地**（收窄裁决见 [ADR-064](../010-adr/064.md)）。
