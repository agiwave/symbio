## 内容

父任务：[T-156-架构机制化与旧代码清理批](156-架构机制化与旧代码清理批.md)
依据：[ADR-055](../010-adr/055.md "ADR-055")（core 形状棘轮：只许降不许升，收窄不需要批准、变宽需要论证）·
判据 J3（静默失效 → 必须做成断言）· AGENTS.md「不要拿机制面去付实现面的账」

**问题**：本仓有一套成熟的**可执行审计文化**——五个 core 审计 + 两个专项审计，每条判据都能红、
都带基线与回归测试。但**这套纪律只覆盖 core，插件层是空的**。

后果不是理论风险，而是本批**另外三条子任务各自照出了一次回流**：

| 回流类型 | 实例 | 今天的守卫 |
|---|---|:-:|
| 工具执行流程按工具名字符串判定 | `tool_executor.rs:1164` · `delegation.rs:39` | 无 |
| 协议层新增供应商 `if` 而不落档案表 | 三个协议各写各的 `max_tokens` 下限 | 无 |
| 冻结字段无生产读方（假机制） | `ActorSpec.pattern` · `ClassifyOnly` | 无 |

**这三条都能在合入时被一条守卫挡住，而不是等下一轮架构复盘再人工发现。**

## 处理过程

- **不是新机制，是平移**：照 `core-shape-audit.mjs` 的形状（提取 → 比基线 → 变宽判红 →
  基线可降不可升 → 带回归测试）做插件层的对应物。
- **首版守两条**（与本批子任务一一对应，判据即出口）：
  1. **特判审计**：`plugins/session/tools/**` 下对工具名的字面量比较判红（存量按基线压住）；
  2. **供应商审计**：`plugins/model/protocols/**` 下新增的供应商特判分支须落在档案表里
     ——这条依赖 [T-161-模型供应商参数档案表化](161-模型供应商参数档案表化.md) 先落地（有了表才有判据）。
- **第三条（假机制）单独议**：「字段有定义无读方」的判据需要跨文件的读方统计，
  形态上接近 `core-export-audit` 的消费方计数，成本更高，可作为本条的第二版。
- **基线纪律照搬**：存量判红会立刻炸一屏，须按棘轮惯例压进 `BASELINE`（`T-032` 已指出
  「BASELINE 是源码常量可被静默下调」的弱点，新守卫要一并考虑）。
- **依赖关系**：条目 2 依赖 [T-161-模型供应商参数档案表化](161-模型供应商参数档案表化.md)；
  条目 1 与 [T-158-工具名硬编码归一为能力元数据](158-工具名硬编码归一为能力元数据.md) 同向（那条做归一，这条防再散）。
