## 内容

父计划：[PL-014 单环一表收敛](../004-plan/014-单环一表收敛.md "PL-014-单环一表收敛") §5 步骤 5
（删 v1 外壳）；「压缩入口唯一」的裁决见 [ADR-072](../010-adr/072.md "ADR-072")。

分层口径（L1–L6 各挡什么）归
[AR-014 上下文压缩设计](../../symbio/src/plugins/session/docs/014-context-compression-design.md "AR-014-context-compression-design")，
本文不复述。本文只登记一件事：**其中三层在 v2 的执行路径上没有接入**，以及接入或不接入各要付什么。

### 证据（2026-10-18 逐行核过）

- `chat_loop.rs` 步骤 4 交进 `V2Turn` 的只有 `prefix: request_view_prefix(&inputs.request_view)`——
  即 `build_request_view` 产物里**只有置顶三段**（记忆 / 就绪 / 委派）进请求；裁剪后的历史
  部分没有消费者。
- **裁剪的成本照付**：`prepare_turn_inputs` 每轮仍完整跑一遍 `build_request_view`（三层淡化 +
  骨架化都在内存里对全历史重算），产物随即被丢弃。所以这不是"为了省时间没接"，而是
  **算了不用**——接不接都要先解释这条。
- 运行器自己起基线：`turn_runner.rs` 从 `store.range(Seq::new(0))` 取全量，过
  `window_by_turn` / `filter_visible`，再 `render_messages` 成消息；每一轮请求是
  `base_messages.clone()` 拼本轮 `exchange`。这条路**不经过** `context/view.rs`。
- 于是 `build_request_view` 内的三层恒不生效：L1 `fade_aged_content_nodes`（老正文内容淡化）、
  L2 `fade_aged_tool_results`（轮次淡化，还被 `fade_active` 双重挡着）、
  L3 `apply_layered_sliding_window`（分层滑窗骨架化）。
- v2 实际在限制上下文的只剩三件：`window_by_turn` 的轮次窗口、L0 单条守卫、
  L5 语义压缩（`auto_compress_process`：70% 阈值自动 + 人工重试）。
- 后果可测：长会话里工具结果与老轮次正文按原文进每一次请求，token 水位比设计口径高；
  而 `SessionConfig` 的 fade / window 旋钮与 AR-014 的分层表读起来像「已生效」。

**相邻但不同的一条**：`v2_exec.rs` 轮边界回调「先抽干、后汇报」的纪律里，「抽干会把静默时钟
归零」这一步只写在 `chat_loop.rs` 的抽干分支，而该分支的前提 `tool_rounds > 0` 在 v2 恒假
⇒ 用户补充到达后助手可能立刻抢报一句进度。它随 5b-2 的抽干分支一起处置，
登记在 [T-165](165-控制面收敛.md "T-165-控制面收敛") 的 5b 条，不在本文重复裁决。

### 为什么它不并进 5b

删死簿记（5b）改的是「谁在读恒 0 的字段」；本条改的是「请求里的历史由谁裁剪」。后者两个方向
都是形状决策：要么给运行器接上视图层（新时序——裁剪发生在每轮请求组装时，而运行器基线跨轮复用
`base_messages`），要么裁决三层不再需要（那 `SessionConfig` 的旋钮与 AR-014 的分层表一起改）。
都要 ADR，都不属于「删不可达代码」这一批。
