## 内容

父设计：15 报告建议 3 / 6

**问题**：前端今天**持有事实口径**——它知道压缩是「什么触发的」、token 怎么格式化、
记忆统计怎么算。这些是**后端的事实**，前端只是呈现。

| 前端持有的口径 | 应该住在哪 |
|---|---|
| 压缩触发文案表 | 后端（触发原因由后端判定） |
| token 格式化 | 后端（同一数字两处格式化必然不一致） |
| 记忆统计的计算 | 后端（统计口径是事实） |

**为什么这是 later**：它触及 [ADR-070](../010-adr/070.md "ADR-070") 决策 2 的边界
（顶层字段 vs `meta`），属**协议面改动**——按 [PL-006 §3 纪律 0](../004-plan/006-分步实施计划.md "PL-006-分步实施计划")，
必须先有 ADR 讨论，不能在任务里直接改。而且它的收益（「视图 = 参数」在消息域落地）
要等协议定了才拿得到。

**`messageTypes.ts` 的拆分是这批的配套而非主项**：1224 行单文件按职责切三块，
导出面不变、纯搬家；拆完之后建议 3 的迁移面变小。注意它是机制审计的例外清单成员
（按文件名匹配），拆文件后例外清单要同步更新——否则「例外」会指向一个不存在的文件。

**一条纪律**：本批**不新增投影**。读数片段复用既有呈现域的形状；若发现必须新增一个投影，
那是设计问题，回到 ADR 讨论。
