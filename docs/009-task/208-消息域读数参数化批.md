## 内容

父设计：15 报告建议 3 / 6

**问题**：前端今天**持有事实口径**——它知道压缩是「什么触发的」、token 怎么格式化、
记忆统计怎么算。这些是**后端的事实**，前端只是呈现。

| 前端持有的口径 | 应该住在哪 |
|---|---|
| 压缩触发文案表 | 后端（触发原因由后端判定） |
| token 格式化 | 后端（同一数字两处格式化必然不一致） |
| 记忆统计的计算 | 后端（统计口径是事实） |

**为什么这是 later**：它触及 [ADR-070](../010-adr/070.md "ADR-070") 决策 2 的边界
（顶层字段 vs `meta`），属**协议面改动**——按 [PL-006 §3 纪律 0](../004-plan/006-分步实施计划.md "PL-006-分步实施计划")，
必须先有 ADR 讨论，不能在任务里直接改。而且它的收益（「视图 = 参数」在消息域落地）
要等协议定了才拿得到。

**`messageTypes.ts` 的拆分是这批的配套而非主项**：千余行单文件按职责切三块，
导出面不变、纯搬家；拆完之后建议 3 的迁移面变小。
机制审计里没有指向这个文件的「例外清单」——M-001 按**目录**判（组件目录不得解释 `meta`，
取值集中到 registry），registry 自身不在它的扫描范围；M-004 的唯一 skip 是 `*Renderers.ts`。
拆文件真正要盯的是 M-001 / M-006 文案里 `registry/messageTypes` 这个**集中点的名字**：
拆完后集中点变成 registry 目录下的几个文件，文案指向的名字必须还能被读者找到。

**一条纪律**：本批**不新增投影**。读数片段复用既有呈现域的形状；若发现必须新增一个投影，
那是设计问题，回到 ADR 讨论。

## 处理过程

- 2026-10-20 立批。来源：15 报告建议 3（高价值 / 中成本 / 中风险）与建议 6。
- 2026-10-20 与 [T-202](202-前端协议面守卫批.md "T-202-前端协议面守卫批") 的关系：
  T-202 先把「字段名漂移」这个洞堵上（守卫），本批再消除漂移源（前端不再持有口径）。
  守卫先行，因为消除需要协议裁决，而洞不能一直开着。
- 2026-10-20 一处依赖：本批的 ADR 讨论需要 T-202 的 `meta` 键白名单作为输入——
  白名单列出的正是「前端读、后端拥有」的那批键，那批键的归属就是本批要裁决的对象。
- 2026-10-21 段一（协议裁决 + 口径迁出前端）。裁决落在 [ADR-111](../010-adr/111.md "ADR-111")，
  七条决策里定形的是三件：**载体复用**——不新增投影、不新增 core 导出、不动 trait，
  读数行用已有的 `ReadingSection`（`session/stats` 面板已在用它，前端镜像与守卫也已有）；
  **挂顶层** `ChatNode.stats`，判据仍是 ADR-070 决策 2 那一条（渲染器只遍历行，不懂业务名），
  顺带把 ADR-070 表里 `stats` 的携带范围从「只 Skeleton」订正为「由携带读数的节点携带」；
  **产地在出口不在写入**——装配点就是三条交付出口共用的 `present_message`，
  与 `title`/`icon`/`actions` 同一条纪律（存储与事件永不含呈现），代价是存量会话零迁移，
  数字从既有 `meta` 现算，`meta` 里的数字不动、仍是事实源。
- 2026-10-21 段一的兑现：`symbio/src/plugins/session/stats_reading.rs` 长出
  `notice_stats_of` + `present_message` + `format_tokens` + `trigger_label`，
  三处出口（会话叶子、转写列表、实时帧）从 `with_derived_presentation` 改走 `present_message`；
  前端 `NoticeNode.vue` 的 `hasStats`/`statFacts`/`memoryFacts` 三段口径塌成一个
  `factRows`（只把行拼成 `label value`），`messageTypes.ts` 删掉压缩统计、记忆统计、
  触发文案表、token 格式化四条口径；`protocol-mirror-audit` 的 H 组白名单随之删七条——
  **最省的一条清偿是把读点删掉**，登记的键越少，漂移面越小。
- 2026-10-21 一处订正：立批时写的「`messageTypes.ts` 是机制审计例外清单成员」不成立，
  M-001 按目录不按文件名，已在上方正文改为准确说法。
- 2026-10-21 段二（配套：`registry/messageTypes.ts` 按职责切三块，导出面不变）。
  切点是**职责**不是行数：`messageFacts.ts`（节点 → 词表取值 → `MessageFacets` + 谓词）、
  `messagePresentation.ts`（facets → 图标 / 标题 / 标签 / 折叠策略 + 渲染器标识的取值）、
  `messageRouting.ts`（标识 → 组件的登记表 + typing 占位合成）。依赖是单向的
  `facts ← presentation ← routing`，`messageRendererKey` 因此落在呈现侧（它读的是呈现表的
  一行），登记表只声明兜底键——反过来会把私有查表函数 `presentationOf` 顶到公开面上。
- 2026-10-21 段二留下的入口：`messageTypes.ts` 缩成 30 行转发。理由是**拆的是文件不是出口**：
  M-001 / M-006 的文案、28 处消费方、`@/registry/messageTypes` 这个名字共同构成「呈现判定的
  集中地」，改名或让消费方直连分文件都是把一次搬家做成协议改动。导出面用符号清单对照过：
  70 个符号逐字相同。
- 2026-10-21 段二踩到的一条守卫钝化：`style-audit` 的「registry 词表」规则只扫**组件显式
  import 的那个文件**，入口改成转发后，`NodeShell.vue` 里真实在用的修饰类（`thinking` /
  `sub` / `err` …）全部被报成「定义未使用」——**拆文件买到的第一个假红**。修法是沿
  `export * from` 做到不动点（带环保护），并补三条回归用例双向钉住：转发链上的词表算在用、
  没转发的兄弟文件仍报 unused（证明规则没被放宽成「registry 目录整体免检」）、循环转发不挂死。
- 2026-10-21 段二顺带订正两处现行文档的文件锚点：[PL-004](../004-plan/004-工程落地.md "PL-004-工程落地") 里指 `messageTypes.ts:104`/`:148`
  的行号换成 `messageFacts.ts` 的 `facetsOf` ⇒ `subSession`（行号是最容易过期的锚点），
  [AR-012](../005-arch/012-vdfs-frontend.md "AR-012-vdfs-frontend") 的 registry 分工表补上拆后的三块与入口的职责边界。
