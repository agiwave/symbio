## 内容

先说实测结论：**「中断后的连续对话」这一半已经能用**（v2 事实源扛住了硬杀）。
把正在跑长任务的 CLI 进程直接杀掉，会话 `cli1a14238023e0` 的 WAL 里 12 格事实按时序在：

```
0  user.message   Opened   turn=0     ← 用户的原话在
1  chat.assistant.opening             ← 「好，我来处理。」
2..11 artifact.added / chat.assistant.reported ×2   ← 八次工具结果与两次轮边界汇报都在
（无 chat.assistant.final）
```

再用 `-s cli1a14238023e0` 续一句「我上一条消息让你做什么？」，模型**原样复述**了原任务
（五段结构、目标路径 `tmp/quality-report-cli.md`、要求把全文打印出来），
续出的两格是 `12 user.message turn=1 / 13 opening / 14 final Closed turn=1`——
turn 号由 `count_user_messages` 给出，没有把被杀的那一轮当没发生。这条路径是对的。

**缺的是另一半：那一轮永远没有终态。** 现有落格覆盖的是**优雅中止**
（[ADR-052] 的 abort 路径：收到取消 ⇒ 在持写者令牌处落 `final{status:"aborted"}` + 半截正文入格）；
进程被杀时没有「收到取消」那一刻，谁也不会去落那一格。于是事实源里留下一条
`Opened` 而永不 `Closed` 的轮，后果分三层：

| 层 | 后果 | 现在能确认吗 |
|---|---|---|
| 不变量 | C4 按 turn 配对用户格与收束格，这一轮是**永久假缺口**（看起来像丢事件） | 能（形状就在这） |
| 读面 | 该轮的 Turn 根没有终态可折，重建出来是个「还在跑」的死节点 | **待实测**（需要一次打开会话后的读面快照） |
| 续写 | 续写锚点取 `last_open_turn`（已开未收束的那一轮）——如果这条规则真的被走到，被杀轮会**冒充**待恢复的那一轮，把新轮的身份锚到旧轮上 | **待实测**（本次实测走的是新开轮分支，没触发它） |

修法取向：**不在写方补**（写方已经不在了，这正是硬杀的定义），而在**读方开机时对账**——
打开会话、切读片之前，扫出「有 `Opened` 无 `Closed`」的轮，各补一条 abort 终态。
这一格是幂等的（`event_id` 仍按 `f-{turn}` 走，重复补会撞 Duplicate 而被认成已落），
且它把「进程被杀」从**事实缺失**降级成**状态未知**——而状态未知是本仓已有的形状。

先要钉死的是表里后两行的实测（读面快照 + 续写锚点是否会认错轮），拿到了再动代码；
如果第二行实测是「根节点没被建出来」，那这一格的价值排序要往前提。
