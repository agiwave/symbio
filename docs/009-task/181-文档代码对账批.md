## 内容

父设计：[PL-006 §0 纪律 6](../004-plan/006-分步实施计划.md "PL-006-分步实施计划")（门禁红的先修）· 工作区指令「一个事实只有一个 owner」

2026-10-20 的架构质量审计（临时分析稿）点名的**文档-代码漂移**，逐条核到代码：
五条是口径过期（成本低、破坏面小，但不修就会让后来者按旧口径施工），
第六条（PS-001）核出的结论与审计主张**相反**——它的判据不动，理由记在处理过程里。

| 处 | 漂移 |
|---|---|
| PL-001 §4.1 | 仍以三令牌形态叙述时延闸门，生产是两令牌（ADR-096 退役 ClassifyOnly），且没有 `assemble(tier)` 装配器 |
| ADR-075 | 「记忆两腿永久留守」与事件腿已迁 `loop` 的现状矛盾 |
| PL-010 | 「七个投影零生产消费者」已过时：18 个投影全有生产消费者 |
| 代码内注释 | `session/orchestrator.rs` 死条目 `broadcast`、`model/message_builder.rs` 过期模块头 |

## 处理过程

- 2026-10-20 立批。PS-001 放宽是唯一动判据的一条，单独成提交（基线重生成 + `t46` 复核）。
- 2026-10-21 **PL-001 §4.1**：按生产形态重写令牌段——两枚令牌 `RuleOnly` / `FullModel`
  （签发点 `TokenIssuer::issue_reflex` / `issue_deep`，`size_of == 0` 由 `adapters/mod.test.rs` 钉）；
  「快速档不得生成」的强制力在**返回类型**（`classify/decide.rs` 的
  `parse_verdict(&str) -> Option<Verdict>` 四变体闭集）而不是第三枚令牌；
  生产没有一个叫 `assemble(tier)` 的装配器——反射档的落地形态是
  `loop/turn_runner/reflex.rs::run_reflex`（签名结构上就没有 LLM 字段），
  `assemble(tier)` 只作为可执行论证住在 `verify/latency_gate.rs`（那段论证仍带三枚令牌，
  文中实测引的错误码就是它的）。
- 2026-10-21 **ADR-075**：留守名单里的「记忆两腿」改成「会话记忆 `memory.rs`（非测试 114）」——
  事件腿（S5 步 11–13：编码 / 召回 / 巩固）的实现住 `plugins/loop/memory_events.rs`，
  写的是 `v2-events.wal` 里的普通事件，因此随驱动器同片；标题与表格行同步。
- 2026-10-21 **PL-010**：「零生产消费者」这条断言的三个载体（§0、§1 第 9 行、§2 现状段）
  按现行读数改写。逐条核到的消费者：`session/stats.rs` 一处的读数口就吃掉
  `slo` / `fallback` / `cost` / `calibration` / `checkpoint` / `transcript` / `readyset` /
  `reputation` / `autonomy` / `conation` / `span` / `invariants`，其余六片各有自己的生产点
  （`mutations` 与 `rebuild` 在 `session/store/mod.rs`、`recall` 与 `consolidate` 在
  `loop/memory_events.rs`、`turns` 在 `loop/turn_exec/`、`prompt_fidelity` 在
  `loop/turn_runner/prepare.rs`、`transcript` / `turnstate` 另在 `session/worker_progress.rs`）。
  §1 的判定档位补第四档**已兑现**（报告点的是缺口，证据列给这条判据现在的读数口），
  第 11 行的路径跟着 `loop` 拆分改到位。§1 里与 [PL-009](../004-plan/009-多执行器与多主体加固实施方案.md "PL-009-多执行器与多主体加固实施方案")
  重叠的第 12–14 行也在本批订正。**与
  [T-214](214-文档口径对账批二.md "T-214-文档口径对账批二") 的边界**：PL-010 的 §0–§2 已由本批
  按现行读数收口，T-214 从 §3 起，不回头改这三段。
- 2026-10-21 **代码内注释**：`session/orchestrator.rs` 的模块分工表删掉不存在的 `broadcast`
  子模块（广播出口的真实 owner 是同插件的 `convergence.rs`，不在 `orchestrator/` 里），
  补齐 `consolidate` / `rate_limit` / `stop` 三行——表与 `mod` 声明一一对上；
  `model/message_builder.rs` 的模块头不再声称「会话持久化」（它只读已有节点、不落库，
  `model/mod.rs` 的同一条述行同步）；`session/stats.rs` 的背景段改述为
  「算得出 ≠ 读得到」，不再拿 dead_code 的那段当背景。
- 2026-10-21 **能力名册**：新增 [PL-002](../004-plan/002-能力坐标系.md "PL-002-能力坐标系") §6.1.1
  「一能力多居」对账口径——记忆 / 技能 / 任务三条能力的逐腿归属表，判据只挂名册那一行的主腿。
  没做成名册的第八列：一列只填一个取值，多腿并进锚点列会让 D-011 从「这个符号在不在」
  退化成「这一串里有一个在就行」，恰好丢掉它要防的信号。
- 2026-10-21 **PS-001 复核：判据不动，基线不重生成**。审计的前提（「一次无关改动也红」）
  核到代码不成立：`providers/collectors/tool_visitor.rs` 的 `rows` 是 `IndexMap`，
  注册序 = 能力收集的广播序，[ADR-057](../010-adr/057.md "ADR-057") 后果段记的两处不稳定
  （工具序、小节序）都由保序表闭合，t46 实测 20/20 一致。而**工具面换序本身就是形状的改动**
  （18KB 前缀作废，ADR-057 决策 2 明写「换序就是换形状」），把它放宽成「集合 + 数量」
  等于拆掉一条有真实代价背书的判据；差异文案已把新增与移除分开报，加一个工具不会被伪装成整表漂移。
  放宽一条 ADR 钉着的判据需要的是修订那条 ADR，而这里没有支持它的新事实。
