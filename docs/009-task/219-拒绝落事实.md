## 内容

父设计：[PL-016 · 义务环](../004-plan/016-义务环.md "PL-016-义务环") §4.2

**先纠正一个前提。** 初稿说"现状只有一句 `drive` 在 `run` 前查一次授权"——不成立。
实况是 `symbio_core/authz.rs` 一张 fail-closed 三层的 `PermissionMatrix`：写侧
`turn_runner::closure_granted` 按种类分两臂判（`can_land_speech` / `can_land_artifact`），
读侧 `stats` 判 `can_see`。**判定是健全的，缺的是否定的表达。**

**现状怎么表达否定**：拒绝 ⇒ **不落收束格** ⇒ 该轮留在未收束态。全项目唯一一处
**用「没写」表达「不许写」**的地方。后果三条，都不是"不好看"：

| 后果 | 具体 |
|---|---|
| 不可审计 | 事后无法回答"谁在什么时候因为什么被拒了"——日志里只有"该轮没收束" |
| 不可回放 | 回放重现不出这次拒绝：`denied` 不是事实，就没有东西可重放 |
| 与静默中断同形 | "被拒"和"根本没跑完"在日志上**长得一样** |

**它违反的是 I1（单通道），不是权限语义**：一切状态变更只经事实源，
那么"被拒绝"这个状态变更也必须是一条事实。

**补法**：拒绝时落 `authz.denied{key, kind, why}`，**判定与矩阵一个字不动**。

三条实现约束，缺一条就做错：

1. **拒绝轮仍然算未收束。** `denied` **不是**收束格。落了它之后该轮依然没有
   `chat.assistant.final` / `fallback`，`unresolved_turns` 照样报它。
   **如果为了让日志好看而把 `denied` 算成收束，等于把"静默中断"这条最该被发现的失效
   一起掩盖掉**——这是本任务最容易做反的一处。
2. **八个调用点同源。** `prepare.rs`(×2) / `settle.rs` / `reflex.rs` / `batch.rs` 各处
   自己 `if !closure_granted { … }`，落事实的动作必须收进一个函数（`deny(…)`），
   否则八处各写一遍 payload，键名第一次就分叉。
3. **新名字必须进 `CELLS`。** 入库闸门会答 `OffGrid`，忘登记第一次落格就红——
   这是免费的，不用另加门禁。

**为什么不做成 `drive` 里的前置检查**：那会让引擎认识"授权"这个业务概念，
且拒绝路径变成异常分支。义务环里没有异常分支，只有事实。

**本批只做前半**：把判定搬成表里一行（`owes: request(port) ∧ ¬permitted(key)`）
**要等表存在**（T-222 之后）——现在没有 `Decl`，搬过去只能造一个只有一行的假表。
`denied` 是那次搬迁的既成条件，不是替代品。

## 判据

| # | 判据 | 检查方式 |
|:-:|---|---|
| 1 | 拒绝 ⇒ 日志里有 `authz.denied` | 反向用例：删掉落事实那一行，用例必须红 |
| 2 | 拒绝轮**仍然**未收束 | `unresolved_turns` 用例：拒绝 + `denied` 仍报违规 |
| 3 | 八个调用点走同一个 `deny(…)` | 静态扫描：`closure_granted` 的否定分支里不出现 `append` |
| 4 | 新名字在 `CELLS` 里 | 入库闸门（`OffGrid`） |
| 5 | 允许路径零新增事实 | 全量 e2e 的事件条数不变 |

## 处理过程

- 2026-10-21 立项。来源：PL-016 §4.2 的核对——初稿把"权限没有位置"当缺口，
  实况是**判定健全、否定无载体**。**任务范围因此从"把授权做成一行债"缩为"把否定落成事实"**，
  搬迁部分推给 T-222 之后。
- 2026-10-21 为什么仍排 now：`denied` 是 T-222 那次搬迁的既成条件；而且它独立成立——
  即使义务环最终没落地，"被拒不可审计"也是当下的真缺陷。
- 2026-10-21 这条仍可能推翻自己：若授权必须按「主体 × 能力 × 资源」三维判而
  `Pattern` 表达不了，权限就得升成引擎维度，PL-016 §3.1 的"七个词"要改。
  **所以它必须先于形状替换。**
- 2026-10-21 施工中的四处订正，都值得记：
  ① **「八个调用点」的准确读法是 8 处调用、7 处否定 + 1 处肯定**。`closure_granted`
  共 8 个调用点（`prepare`×2 / `settle`×2 / `stream`×2 / `reflex`×1 / `batch`×1），
  其中 `prepare.rs` 的产物臂是**肯定**分支（`if closure_granted { … }`），不落否定事实。
  任务原文的「八个收束调用点」若照字面迁，会把那条肯定分支也改成 Err 形态——
  它本来就没有"被拒"这回事。
  ② **拆 `Result` 而不是加一个 `deny_reason()`**。两个函数各写一份「这一类格要什么
  能力」，拒绝原因与实际拒它的理由就会分叉——那时 `denied` 记的原因比不记更坏
  （它是一份**看起来可信**的错账）。拆成 `closure_gate` + 一行壳，判据只有一处。
  ③ **能力名不得不手写一份**：`governance` 是 core 的私有子模块，插件路径不进去。
  处置是**对拍**（`denial_names_the_capability_the_gate_judges` 用生产表派生的
  能力集正反两问），不是"相信这次没写错"。反向锚定那一条是必需的——只问正向时
  「拼写恒真」与「表里真有」不可分辨。
  ④ **判据 3 的形态从"静态扫描"落成一条门禁规则**。原本想写"否定分支里不出现
  `append`"，那是行级正则表达不了的（分支跨多行）。改成等价的、可判的：`!closure_granted(`
  零出现。否定分支回到旧写法时，拒绝就又成了「什么都没写」，而那种违反**不会有任何
  东西变红**——该轮照样留在未收束态，看起来和"正常被拒"一模一样。这正是需要守卫的形态。
