## 内容

[T-107](107-角色主体执行路径批.md "T-107-角色主体执行路径批") 附带修复了部署级读侧的嵌套遍历缺口：
子会话 WAL 住 `<根>/<safe(父)>/sessions/<safe(子)>/`（可分形嵌套），只扫一层的读方会**整棵子树看不见**。
当时三个同形扫描里修了两个——淘汰闸覆盖层（安全面，可绕过）与 stats 实例聚合（文档说假话）；
第三个是**记忆召回** `v2_memory::recall_view` 的一层 glob，当时判「暂不动」，理由：

- 它的文档与代码一致（没有「所有会话」式谎言），不存在诚实性问题；
- 「召回要不要覆盖嵌套子会话的记忆」是**语义问题**不是 bug：子会话的记忆归属哪个召回范围、
  跨会话召回会不会把委派执行的中间产物灌进主会话上下文，这些都是设计裁决，不该在
  修安全缺口的批里顺手定。

本任务承载这份裁决。三处读方的同一个坑的完整记录见
[paths.rs `session_wals_deep` 文档](../../symbio/src/plugins/session/paths.rs)与
[T-107 处理过程](107-角色主体执行路径批.md "T-107-角色主体执行路径批")。

## 处理过程

- 2026-10-16 **裁决（status: done）：维持一层 = 刻意范围**。三条理由（全文见
  `v2_memory::recall_view` 的「扫描范围」节）：

  1. **子会话的事实经工具结果回流**（S08 代际承诺：`agent_run` 的收束答复进父
     会话上下文）——子会话的 shared 记忆内容（被委派的 prompt）父会话本来就有
     （是它发的），判断记忆 thread_private 本就不出会话（T-117 之后更是判死了）：
     深遍的**边际信息量 ≈ 0**；
  2. **召回是有预算的检索**（`RECALL_MAX_FILES` = 16 名额 + 字节双上限）：
     分形委派树的 WAL 恒最新（mtime 序），深遍会让一棵树占满名额、把平级会话
     挤出扫描窗——那才是真丢失；
  3. 淘汰闸 / stats 深遍的理由（部署级事实必须完整——漏一格 = 漏一次违约 /
     漏一个会话的读数）在召回侧**不成立**：检索漏掉低增量来源不是错误，
     是预算的分配。

  判据 = `v2_memory.test.rs::recall_view_scan_is_one_level_deliberately`（嵌套
  子会话的记忆不进顶层召回，平级照常作对照）；`paths.rs` 与 `v2_memory.rs` 的
  文档同步把「开放问题」改成「已裁决」。改范围先改这条裁决。

- 2026-10-16 [T-107](107-角色主体执行路径批.md "T-107-角色主体执行路径批") 附带修复时登记：三处同形
  扫描只修两处（淘汰闸 = 安全面、stats = 文档说假话），召回一处因「语义问题开放」按纪律不顺手定，
  独立承载为本任务。
