## 内容

父设计：总报告 C2 · 12 报告建议 2 / 5 / 9 · [AR-008](../005-arch/008-http-api-transport.md "AR-008-http-api-transport")

**现状**：gateway 能把外部请求翻译成一次内部路由，但它只做到「能跑通」，没做到「可公网暴露」：

| 缺什么 | 后果 |
|---|---|
| 连接数上限 | 一次并发洪峰打穿进程（无 `Semaphore`） |
| 请求 id / 幂等键 | 同一请求重放两次 = 处理两次 |
| WS 令牌在 query 里 | 令牌进日志、进代理记录 |
| `update_offset` 纯内存 | 重启后重复处理历史更新 |
| `chat_id` 自动捕获纯内存 | 重启后绑定丢失，且无持久化 owner |

**为什么幂等要先裁决再动手**：幂等的语义有两条互斥路线——「重放返回旧结果」（缓存式）与
「重放直接拒绝」（锁式）。前者要存响应，后者要存键，两者的存储位置、过期策略、与
`store` 幂等语义的对齐方式都不同。原报告明确要求「先补 AR-008 风险条目再动代码」，
本批把这个顺序写进出口条件。

**不新增机制**：幂等 = `store` 幂等语义在入站侧的应用（总报告 §7 第 1 条），
并发上限是运行时参数，落盘走既有配置面机制——机制键 0、trait 0。

**与 [T-185](185-插件停用收口批.md "T-185-插件停用收口批") 的关系**：T-185 管「停用后后台
收口」（生命周期），本批管「在跑的时候边界稳不稳」（负载与语义）。两批都动 gateway / telegram，
但 T-185 先行——先让停用成立，再谈停用前的边界加固，否则加固的是一段随时可能在后台跑下去的东西。
