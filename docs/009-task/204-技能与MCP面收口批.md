## 内容

父设计：11 报告建议 1 / 2 / 3 / 6 · 总报告 C6 的 stdio 一半 · 场景文档「技能编译与自我改进」记为缺口的读数项

**这一批全是「同一件事写了几遍」与「承诺了但没实现」**：

| 项 | 现状 | 后果 |
|---|---|---|
| 技能指令前缀 | 三处各拼一遍（含措辞差异） | 改一处漏两处；`skill/execute` 与 `read_skill` 行为差异被藏起来 |
| 技能标签常量 | core 与 loop 各定义一次 | 改一边不改另一边 ⇒ 技能被当普通记忆召回却不进路由（注释记录过这个失效形态） |
| MCP `Sse` 传输 | 枚举里有，实现与 HTTP 相同 | 用户能选到一个「名字叫 SSE 但不是 SSE」的选项 |
| stdio 传输 | 每次重 spawn | 连接成本与冷启动延迟 |
| 技能编译读数 | 只有四列总量，无「开 / 关」 | 「不工作」与「没配置」同形 |

**优先删而不是补**（原报告的取向，本批沿用）：`Sse` 变体优先**删掉**——「枚举承诺了实现没有的
东西」比「少一个选项」更糟。若存量配置用了它，反序列化未知变体会失败，所以要先确认，
必要时保留变体但映射到 HTTP 并在测试动作里明确告警。

**读数项不新增投影**：技能编译状态是「读数补齐」，在既有 `session/stats` 的四列上增补即可——
新增投影会引入一个新的机制面，而这条需求的本质是「让人看得见」，不是「让系统多一个能力」。

**为什么 stdio 进这批**：它在本轮总报告 C6 与 11 报告 §3.2 都被点名，但 11 报告 §5 没单列。
本批把它收进来，理由是它和上面几项同属「MCP 扩展面的成本与一致性」；
出口允许「明确写下每次重 spawn 的理由」——有些传输每次重开是刻意的（无状态、隔离），
写清理由与改掉它同样合格。

## 处理过程

- 2026-10-20 立批。来源：11 报告建议 1 / 2 / 3 / 6 + 总报告 C6 的 stdio 一项。
- 2026-10-20 一处口径统一（原报告建议「顺手统一」）：兜底臂不做参数提示检查、
  而工具侧已经在检查——两处口径本该一致，本批统一为「都检查」，因为工具侧的行为是用户的
  实际体验，兜底臂的宽松只会让同一个技能在两条路径上表现不同。
- 2026-10-20 与 [T-210](210-资产与清单单源化批.md "T-210-资产与清单单源化批") 的分工：
  本批管「技能内容怎么组装、标签怎么定义」，T-210 管「技能清单从哪来」（目录扫描 vs 资源树）。
- 2026-10-21 完成。三项判断记在这里：
  1. **单点不只是合并代码**：原先兜底臂绕过参数提示检查，所以「组装」收敛后
     `assemble_response` 只接受 `raw_args`，缺参即返回可行动的校验错误——两条路径
     行为一致，不是把宽松路径抄进单点。
  2. **SSE 选「删变体 + 读入别名」**：直接删枚举会让存量 `server.json` 加载失败
     （用户被动丢配置），所以保留 `sse` 作为**只读别名**（自定义 `Deserialize` 映射
     到 `Http` 并告警），写回一律 `http`。实现本来就只有 HTTP 一条路径，别名不承诺
     任何未实现的能力。
  3. **stdio 重 spawn 写成决定而非欠账**：复用进程会把「配置里写一行」变成「常驻
     进程」，并引入失效协议、崩溃重连与僵尸管理；发现结果另有缓存，调用路径只多
     一轮握手。将来若真成瓶颈，应作为**单个 server 的配置项**引入（数据层选择），
     而不是改全局生命周期。
