## 内容

父任务：[T-156-架构机制化与旧代码清理批](156-架构机制化与旧代码清理批.md)
依据：判据 J1（**若 X 能用已有参数的新取值表达，它就是数据，不是机制**）·
[PL-001 §8](../004-plan/001-核心架构.md "PL-001-核心架构")（权威参数表：新增取值 = 改一行）

**先说清这条不是什么**：它**不是**「供应商特判散落各处」——那句初判经核实**部分成立**。
`reasoning` 字段的兼容已经是一条**带日期、带反向用例的 fallback 链**（`openai_chat.rs:53-82` 的
`amd_mimo_first_frame_with_null_reasoning_content_is_silent` 等三条测试），形态是对的，
欠的只是**它在两个协议文件里各写了一遍**。

真正散落的是 **`max_tokens` 下限**：三个协议各写各的魔法数与各写各的注释理由。

**问题**：这些是**供应商差异**，本质复杂度，砍不掉；但它们的**承载形态**可以机制化：

| 差异 | 现状 | 形态问题 |
|---|---|---|
| GLM 要求 `max_tokens > 2` | `openai_chat.rs:169` 写死 256 | 魔法数 + 内联理由 |
| Anthropic 兼容网关要求更大下限 | `anthropic_messages.rs:276` 写死 16 | 同上，各写各的 |
| Gemini 缺省 8192 | `gemini_api.rs:153` | 缺省值散在各处 |
| reasoning 字段名（`reasoning_content` vs `reasoning`） | 两个协议文件各实现一遍 fallback | 同一逻辑两份 |

**本条要买到的性质**：新增一个供应商怪癖（新的下限 / 新的字段名 / 新的空值形态）⇒
**在档案表加一行**，协议解析代码零改动。这正是你直觉里「统一可调度能力」的正确落点：
**供应商差异从「机制」降为「参数取值」。**

## 处理过程

- **落点在插件侧**，不动 core 棘轮：档案是 `plugins/model/` 内的一张数据表
  （模型名/协议 → 下限、字段名、怪癖标记），不是 core 的新 trait。
- **reasoning fallback 链两处合一**：`anthropic_messages.rs:386-399` 的二次实现应收敛到与
  `openai_chat.rs:24-34` 同一个函数，保留那三条反向用例。
- **`max_tokens` 下限不是「越小越好」也不是「越大越好」**：它是**协议约束的交集**
  （GLM > 2、Anthropic >= 1、部分网关更大），档案表要能表达「本协议的下限是多少 + 为什么」，
  而不是一个全局常量。
- **平凡值必须仍完整运行**（J2）：档案表缺省行（未知供应商）= 今天的行为，逐字节不变。

## 勘察发现：Anthropic thinking 的「确保 max_tokens 大于 budget」是死代码

请求构造里 `cfg.reasoning.is_some()` 分支把 `max_tokens` 抬到 `budget + 1024`，紧接着的
`if let Some(m) = cfg.max_tokens` 又把它覆盖回去——**两条路径都逃不掉**：

- `max_tokens` 为 `None`：budget 由 `unwrap_or(4096) / 2` 得 2048，`8192 <= 2048` 恒假，抬价分支不触发；
- `max_tokens` 为 `Some(m)`：抬价分支触发了也会被下面的赋值覆盖成 `m`。

后果：开启思考、且调用方给的 `max_tokens` 小于 budget 时，请求体里 `budget_tokens > max_tokens`，
Anthropic 侧会拒。**本条不改它**——修它会改变请求体，属语义变更，须单独裁决并成文 ADR；
而本条的出口判据是「行为不变」。已在代码旁标注失效事实，避免下一位读者继续信任这条守卫。
