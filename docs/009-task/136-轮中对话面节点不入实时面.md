## 内容

用户报告的「无法正常会话」在长轮次上最直观：**一次 8 分钟的任务轮，助手在会话面上一句话都没有**
（屏幕只有插件的工具日志在滚），该说的话——开场白与轮边界汇报——全部攒到轮末一起到达。
实测会话 `.symbio/session/cli1a14222066f0/` 的 WAL 里，
这些事实**都按时序落格了**：

```
seq 0  user.message              344c
seq 1  chat.assistant.opening      "好，我来处理。"       ← 轮首就该看见
seq 2..6 artifact.added          （五次工具结果）
seq 7  chat.assistant.reported     "已经完成 3 轮工具调用，用时约 1 分钟，还在继续。"
seq 9  chat.assistant.reported     "已经完成 4 轮工具调用…"
seq 12 chat.assistant.reported     "已经完成 6 轮工具调用…"
```

WAL 有、前端没有——因为**落格与下发是两件事**，而这两处只做了前一半：

| 节点 | 落格 | 下发（publish） |
|---|---|---|
| `chat.assistant.opening` | `turn_runner.rs` 步骤 1a：`store.append(...)` | ✗ |
| `chat.assistant.reported` | `v2_exec.rs` 轮边界汇报：`store.append(...)` + 塞进 `sink_msgs`（那是**回灌进下一轮请求的补充消息**，不是事件出口） | ✗ |
| 工具调用与结果 | 执行方落格 | ✓（`tools/tool_executor.rs` 把 `EVENT_SINK` 塞进 `tool_ctx`，状态帧当场发） |
| 收束 `chat.assistant.final` | 轮末 | ✓（`finish_turn` → `persist_messages` → `append_and_publish`） |

于是实时面上出现一条**反直觉的空窗**：工具在动（结果帧在发），助手说的话却一句没有，直到轮末
才「攒够了一次说完」。而 `chat.assistant.reported` 存在的理由正是「本轮还要跑很久，先报一句」
（缺口 4）——机制设计了这句话，投递路径却把它压到轮末，等于把它的设计目的抵消掉了。

顺带一条同源症状：[T-134-CLI会话可用性实测批](134-CLI会话可用性实测批.md) 已修的「答话末尾粘一句『我先看一下。』」也是这条
空窗的另一面——开场白在实时面上根本不来，只在轮末跟着转写一起到，所以它**看起来像答话的尾巴**。

## 处理过程

**开场白这一半已闭**（2026-10-16）：`turn_runner.rs` 步骤 1a 在 `store.append` 成功后
即以 `DeltaSink::on_tool_frame` 把同一个节点送上线（构造走 `chat_loop::dialog_node`，
节点 id 取落格载荷里那个 `dialog.id`——`rebuild::opening_node` 重建时读的也是它，
所以轮末落库镜像再送一次时消费端按 id 合并成同一格，不多一张卡）。

- 判据是一条单测 `opening_node_reaches_the_live_surface_at_production_time`：
  钉「开场白帧是 sink 上**第一**个到达的帧」而不只是「到达过」——到达时序正是这条缺陷本体。
  反向自检做过：把那行 `sink.on_tool_frame` 注掉，用例即红。
  `cargo test -p symbio --lib plugins::session::turn_runner` 31/31 绿。
- 时序的实测读数（不带 `-q`，会话 `cli1a1427637820`）：`… 我先看一下。` 落在日志第 23 行，
  后面才是第一条 `⚙ 调用工具`；上一轮修复前它在 `[Consume] Turn 任务正常结束` **之后**才出现。
  §处理过程 原先欠的那条时序读数因此一并结掉（工具帧一直是当场到的，表里第三行没有误）。
- 出口里那句「判据 = 一条 e2e」两半都钉成了**常驻用例**：汇报半边在
  `e2e/cases/t23-progress-report.mjs`（见下），开场白半边在 `e2e/cases/t22-compose.mjs` 的 B 线
  第 2 步（`opening` 帧早于第一条工具结果帧；基准为什么取工具帧而不取末轮正文，见 §evidence ⑦）。

**轮边界汇报这一半也已闭**（2026-10-16）。原先登记在这里的卡点（「载荷没有 id ⇒
实时面与重建面必然两个身份」）经读码**修正**——它不是堵点：重建侧 `reported_node` 走的正是
`event_payload_node_id(e, "id")`，载荷有 `id` 就读它、缺了才退回事件 id。于是写侧只需要
**一次构造、三处用**：`let node = draft.to_message()` → 落格载荷写 `"id": node.id` →
回灌 `sink_msgs` 与下发实时面送同一个 `node`，而 `rebuild.rs` 一行都不用改。

真正要盯的是投递通道的生命周期：那个汇报闭包里多一份 `Arc<UiBridge>`（现场没有
`dyn DeltaSink` 可用，`on_tool_frame` 就挂在同函数里 `execute_turn` 造的那条流式桥上），
而函数末尾的 `drop(bridge)` 是发射端退出**唯一**的信号——多养一份它，等于把那个信号推迟到
闭包死，而挂住的每一个 v2 工具轮都照挂不误。读码判断闭包随 `TurnInput` / `drop(dispatcher)`
在本轮内死去，因此安全；但这条不靠推理，由
`round_report_reaches_the_live_surface_before_turn_end` 钉住（用例能正常返回就是它成立的形状，
段内另断言到达序与「载荷 / 实时面 / 落库镜像三处同一个 id」）。

判据落成**两层**：单测那层见 §evidence ③，常驻 e2e 那层是**一条线一个用例**——汇报在
`e2e/cases/t23-progress-report.mjs` 的 A 线（投递前订阅 WS 实时面 ⇒ 断言汇报帧早于末轮正文帧），
开场白在 `e2e/cases/t22-compose.mjs` 的 B 线第 2 步（判决开着、走 `Escalate` 首响 + 工具轮
⇒ 断言首响帧早于第一条工具结果帧）。两条各自反向自检实跑过：注掉写侧那行下发、重建被测
二进制复跑 ⇒ 分别红在「report=22 answer=18」与「opening=15 tool=11」，正是这条缺陷的到达序形态；
恢复后两条各 1/1 绿。

2026-10-16 的回归读数：`cargo test -p symbio --lib plugins::session::` **655 passed / 0 failed**
（1012 条被前缀过滤），`cargo test -p symbio --lib` **1666 / 0**，`cargo test -p symbio-cli` 11/11，
docs 与 facts 门禁全绿，`node e2e/run-tests.mjs` **73 / 73**。

全量 e2e 那一跑最初是 **68/73**：`t9-ws-stream` 与 `t10-node-protocol` 红在「正文首帧应为
streaming，实得 completed」。那不是投递坏了——正是「落格即上线」让实时面上**先**到一个根级
界面文本节点（开场白），而这两条用例按 `type=text && role=assistant` 找「正文节点」，找到的
是那句开场白（它产生即定格，本就没有增量序列）。用例侧改按 `meta.exclude_from_context` 筛掉
界面文本（与 `cli/src/render.rs` 的 `is_progress_surface` 同一条判据），被钉的流式契约一字未动。
