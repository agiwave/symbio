## 内容

父设计：09 报告建议 S-2 · 11 报告建议 4 · 总报告 C4（技能清单双来源、两套检索内核、主体 id 推导）

**三项都是「同一概念有两个来源」**，且都在**资产面**（Agent 包 / 技能 / 检索）：

| 项 | 两个来源 | 后果 |
|---|---|---|
| 主体 id | 资产 id 的**形状**（含不含命名空间前缀）决定主体身份 | 改名即断链；命名空间登记表与 id 语法之间无一致性检查 |
| 技能清单 | 目录扫描一份、资源树一份 | 技能超过预算时，LLM 工具面与资源树不一致 |
| 检索内核 | 记忆一套、代码检索一套 | 同一「检索」语义两套实现，排序口径各说各话 |

**主体 id 这条最便宜也最该先做**：最小改动是在 manifest 加一个可选主体字段（或规定 id 为
不含斜杠的 slug），让「主体 id」成为**显式声明**而不是从 id 形状推断出来的。
原报告给的判据很具体：`principal_of` 对已带命名空间的原样认下（已有支持），裸名走兜底；
`is_valid_id` 加一条「不得含斜杠，或含斜杠必须与命名空间登记表匹配」+ 一个反例用例。

**技能清单这条只做一半**（原报告的建议，本批沿用）：先把「预算裁剪作用在合并后的集合上」，
风险可控；加载顺序从目录序变资源树序、同名冲突策略、多目录来源的语义重新表达，都是更难的一半，
放在同一批里会把一个低风险修复拖成一次设计。

**检索内核合一允许以「裁决」结案**：两套内核可能本就不该合一（记忆检索面向时间与来源，
代码检索面向路径与符号）。本批的第一个产出是**共同点与差异点清单**——
若结论是「不该合一」，就登记「谁是排序口径的唯一 owner」，那同样是收敛。

## 处理过程

- 2026-10-20 立批。来源：09 报告 S-2 + 11 报告建议 4 + 总报告 C4 的三项。
- 2026-10-20 为什么合成一批：三项都在「资产 / 清单 / 检索」这一层，且判据形状相同
  （同一概念在两个位置各有一份，改一处另一处不动）。分开做会写三遍相似的收敛论证。
- 2026-10-20 与 [T-204](204-技能与MCP面收口批.md "T-204-技能与MCP面收口批") 的分工：
  T-204 管技能内容怎么组装，本批管清单从哪来；与 [T-193](193-Agent权限声明执行方批.md "T-193-Agent权限声明执行方批")
  的分工：T-193 管包声明的能力范围，本批管包的身份怎么定。
- 2026-10-21 项一为什么选 slug 不选「manifest 加可选主体字段」：出口条把两种形状并列，但它们
  不是等价的。**加字段 = 开一条包自述族属的入口**——`principal: person/local` 写进包里，
  「这条主体是不是 agent 一族」就交给包作者，而它是可见域判据（`view::visible_to`）的分岔条件；
  字段还会和 id 形成两份身份，改一处另一处不动（本批要治的正是这个形态）。slug 规则把约束放在
  **加载期校验**上：包能起什么名字由字符集决定，族属由登记表决定，两侧各一份、中间一条判据。
- 2026-10-21 项二只做预算那一半，是原报告划的易/难分界而不是本批降标：预算扣在合并之前
  是纯缺陷（清单比预算小、覆盖被名额抢跑），修它不动任何人的语义；「加载顺序从目录序变
  资源树序」「同名冲突策略重述」会改技能在两个面上的**可见集合与顺序**，那是设计而不是缺陷。
  已知边界如实留在账上：资源树（`DirVdfs`）不设预算而工具面设预算，超出 `max_skills` 的技能
  仍然「树上看得见、清单里召不出」——本批把**数量**这一半修到预算精确，来源合一那一半没做。
- 2026-10-21 项三按出口条的第二种结案走（清单先行 ⇒ 裁决 + owner）。清单九格只有三格同口径
  （排序方向、平手要有次级键、截断在全序之后），所以「合一」的正确落点是那三格，而代码面当时
  恰恰缺平手判据——这就把一条纸面裁决变成了一次可钉的修复。owner 声明放在
  [ADR-109](../010-adr/109.md "ADR-109") 与两份模块文档各自的位置上，不新建第三处登记表。
