## 内容

父设计：09 报告建议 S-2 · 11 报告建议 4 · 总报告 C4（技能清单双来源、两套检索内核、主体 id 推导）

**三项都是「同一概念有两个来源」**，且都在**资产面**（Agent 包 / 技能 / 检索）：

| 项 | 两个来源 | 后果 |
|---|---|---|
| 主体 id | 资产 id 的**形状**（含不含命名空间前缀）决定主体身份 | 改名即断链；命名空间登记表与 id 语法之间无一致性检查 |
| 技能清单 | 目录扫描一份、资源树一份 | 技能超过预算时，LLM 工具面与资源树不一致 |
| 检索内核 | 记忆一套、代码检索一套 | 同一「检索」语义两套实现，排序口径各说各话 |

**主体 id 这条最便宜也最该先做**：最小改动是在 manifest 加一个可选主体字段（或规定 id 为
不含斜杠的 slug），让「主体 id」成为**显式声明**而不是从 id 形状推断出来的。
原报告给的判据很具体：`principal_of` 对已带命名空间的原样认下（已有支持），裸名走兜底；
`is_valid_id` 加一条「不得含斜杠，或含斜杠必须与命名空间登记表匹配」+ 一个反例用例。

**技能清单这条只做一半**（原报告的建议，本批沿用）：先把「预算裁剪作用在合并后的集合上」，
风险可控；加载顺序从目录序变资源树序、同名冲突策略、多目录来源的语义重新表达，都是更难的一半，
放在同一批里会把一个低风险修复拖成一次设计。

**检索内核合一允许以「裁决」结案**：两套内核可能本就不该合一（记忆检索面向时间与来源，
代码检索面向路径与符号）。本批的第一个产出是**共同点与差异点清单**——
若结论是「不该合一」，就登记「谁是排序口径的唯一 owner」，那同样是收敛。
