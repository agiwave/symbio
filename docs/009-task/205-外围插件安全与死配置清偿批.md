## 内容

父设计：12 报告建议 4 / 6 / 7 / 8

**四项的共同形状**：**同族两实现，一有一无**。

| 项 | 一处有 | 一处没有 |
|---|---|---|
| 私网地址检查 | 通用 HTTP 工具 | `web_fetch` |
| `build_ctx` | gateway 自己写一份 | 桌面端命令层再写一份（同构拷贝） |
| 匹配器过滤 | 配置条目里有 `matcher` 字段 | 执行器从不读它 |
| 配置项生效 | 部分键有读方 | `streaming_enabled` 无读方、`web_timeout` 不生效、白名单构造期快照 |

**「同族两实现」为什么值得单独一批**：它不会红、不会崩，只会让**同一类操作有两种行为**。
用户看到的是「为什么 web_fetch 能访问内网、web_search 不行」这种没法解释的差异，
而排查要读两个插件的两份实现——这类债的利息是**认知成本**，不是缺陷。

**两处改动会改变既有行为**（必须写明）：

- `web_fetch` 补私网检查 ⇒ 可能挡住某些合法的内网调用，README 要写清；
- 白名单改动态 ⇒ 改配置不再需要重载，但「构造期快照」原本隐含的稳定性消失了。

**删除优先于实现**（原报告取向）：`streaming_enabled` 无消费方，删掉比补上便宜；
`matcher` 若无真实使用场景，删字段比接上便宜——「没人调用的能力比没有更糟」是本仓的既有判据。
