## 内容

父设计：[PL-016 · 义务环](../004-plan/016-义务环.md "PL-016-义务环") §2.5 ·
[ADR-115](../010-adr/115.md "ADR-115") 决策 1–2

**为什么它必须排在 T-222 之前。** 表化之后每行的 `owes` 是 `Pattern`，匹配的是事实 /
视图。如果今天就照 `LoopState` 的字段搬，下面这些量没有事实可匹配：

| 今天的输入 | 从哪来 | 闭包后 |
|---|---|---|
| `first_utterance` / `user_meta` | 请求体 | `user.message` 事实（**先落**） |
| `classify_enabled` / `auto_compress` / `has_facts` | `SessionConfig` 快照 | `session.config` 事实 |
| `quiet_ms` / `last_user_facing_at` | `clock_now_ms()` + `TurnState` | 触发事件 `ts` − 最近一条助手文本事实的 `ts` → `report_due` 视图 |
| `reports` 配额 | `RoundProgress` 内存计数 | `chat.assistant.reported` 事实按 turn 计数 |
| `round` | `TurnState::request_round` | `turn.stage{stage:"round"}` 事实（引擎在每轮执行前落） |
| `done`（decide / recall / compress） | `TurnState::stages_done` 缓存 | `turn.stage` 事实的规范折叠 `stage_events::done` |
| `resume_allowed` | 请求体 `resume` | `turn.stage{stage:"resume", kind}` 的有无 |
| `has_match`（技能） | `turn.skill_hits` 内存 | `turn.stage{stage:"recall", result:"hit"\|"miss"}` |

**四处硬改动**：

1. **用户格前移。** 今天 `turn_runner::prepare_turn` 在 classify 之后才落
   `EVENT_USER_MESSAGE`（`prepare.rs` 约 96 行）。义务环里 `owes` 要匹配它，必须在
   任何判决 / 阶段事实之前落。写入点前移到主循环的开幕块（`chat_loop/drive.rs`），
   位置在闸门之后、判决之前；`prepare_turn` 只接收 `user_seq`，不再自己落。
2. **配置落事实。** `session.config` 在一幕开始时落一条，载荷是当幕生效的开关与阈值
   （`classify_enabled` / `auto_compress` / `progress.*` / `is_persistent`）。
   配置读取点仍是 `SessionConfig`，但**决策只读事实**；配置变了就落新事实。
   这是**新增事实名**（网格 30 → 32，与下一条 `turn.dispatch` 同批），与
   `turn.stage` 同落 `turn × asserted`：它是「这一轮以什么配置运行」的断言，与
   阶段事实同族同格。幂等键带幕号（`cfg-{turn}-{drive_seq}`）——续写幕的请求级
   开关可以与首幕不同，同一轮必须能有多份配置事实。业务名一个不改。
3. **阶段结果落事实。** `turn.stage` 已有 `stage` / `round` / `source` / `reason`；
   增加 `result`（`recall` 的 `hit|miss`、`resume` 的 `kind`）。**不新增事件名**——
   它仍是 `turn.stage`。幂等键加幕号（`st-{turn}-{round}-{stage}-{identity}`）：
   续写幕的 `round` 从 0 重来，不带幕号会撞首幕、把 `drive_seq` 指回首幕。
4. **档位单独落事实。** 用户格前移之后，档位要到召回 / 技能命中后的装配期才定，
   不能再塞回用户格。`turn.dispatch`（`turn × asserted`，`d-{turn}-{drive_seq}`）
   记当幕的 `tier` / `budget_ms` / `principal`；读方（兜底率 / SLO / C5）优先读它，
   历史 WAL 回退 `user.message` 的旧字段。
5. **时间入参化。** 视图的 `now` 是入参而不是自己读时钟：`ViewDecl.eval` 的签名
   就是 `fn(&[Event], i64)`，`report_due` 把 `now - ts` 与阈值比较，折成
   `due` 布尔。`drive` 侧的 `now_ms` 由触发事件带入——这一半随唯一消费者 `owed`
   在 T-222 落地，本任务只交付视图面（见施工订正七）。

**两个视图**（T-221 已声明 `turn_head` / `in_flight`，本任务补 `report_due`）：

```
turn_head{round, has_utterance, classify_enabled, done}
report_due{turn, due, reports, quota}
```

`turn_head` 的字段全部来自 `user.message` / `turn.stage` / `session.config`；
`report_due` 的字段全部来自助手文本事实 / `chat.assistant.reported` /
`session.config` / `now_ms`。**没有第四种来源。**

**为什么不在 `owed` 里读配置**：配置是"这一轮生效的值"，它会在轮中途变；读旁路等于
让同一份日志在不同时刻算出不同欠账。落成事实后，"哪一轮用了哪份配置"可回放、可 diff。

**明确不做**：

- 不改 `classify` / `recall` / `compress` / `report` 的**判定逻辑**——只改输入来源。
- 不新增 `turn.closed` 之类的事件名；收束仍用 `chat.assistant.final` / `.fallback`。
- 不引入独立定时器：`report_due` 只在有事件时求值（PL-016 §7.2 代价 10）。
- 不在本任务里表化——`Registry` / `LoopState` 的退役是 T-222。

## 处理过程

- 2026-10-22 立项。来源：第三轮核对发现 `LoopState` 的十个字段里，配置、墙钟、
  内存匹配结果三类不在事实面；照初稿表化会让 `owed` 继续读旁路，"纯函数"名不副实。
  ADR-115 决策 1–2 把输入闭包定为形状的一部分。
- 2026-10-22 与 [T-189](189-轮执行阶段数据化批.md "T-189-轮执行阶段数据化批") 的关系：
  T-189 已经落了 `turn.stage` 事实与 `done()` 的规范定义，本任务只是把它接进视图，
  **不是重造**；`TurnState::stages_done` 是 T-189 留下的生产侧缓存，本任务让它退役。
- 2026-10-22 一处必须复核的实现细节：用户格前移会改变 `produced_by` 的取值点
  （`user_seq` 从 `prepare_turn` 的返回值变成入参）。改之前先跑 I2 的溯源用例，
  确保断言类事件的 `produced_by` 仍指向用户格。
- 2026-10-22 施工订正一：**新增两个事件名，不是一条**。用户格前移之后档位在判决
  前尚未确定，只能另立 `turn.dispatch`（`turn × asserted`）。网格 30 → 32；
  `grid.test` 钉的声明事件名 33 → 35。原稿「不新增事件名」只对 `turn.stage.result`
  成立。
- 2026-10-22 施工订正二：`session.config` 按**幕**落，不是按轮落。幂等键
  `cfg-{turn}-{drive_seq}`，载荷七项（`classify_enabled` / `auto_compress` /
  `progress_enabled` / `progress_interval_ms` / `progress_min_rounds` /
  `progress_max_per_turn` / `is_persistent`）；`auto_compress` 记 `TurnRequest`
  折过的**生效值**，不是配置默认值。
- 2026-10-22 施工订正三：阶段名的闭集不是 `Capsule`。新增 `StageName`
  （`decide` / `report` / `compress` / `recall` / `reflex` / `resume` / `round`）；
  `resume` 与 `round` 是引擎记账、不派发任何臂，塞进 `Capsule` 会让「每条臂都有
  产出行」的对偶检查凭空多出两条永不派发的指令。两者之间只有单向
  `From<Capsule>`。
- 2026-10-22 施工订正四：用户格与压缩快照的相对顺序翻转。旧断言钉的是「快照早于
  开轮格」；用户格前移之后真实顺序是**用户格 < 快照 < 派发 / 执行事实**。用例
  `..._before_the_turn_runs` 随之改名并改断言——压缩仍是执行的前置动作，只是不再
  早于用户发言。
- 2026-10-22 施工订正五：`turn.dispatch` 有两个落点（`prepare_turn` 与
  `run_reflex`），载荷 `{tier, budget_ms, principal}`；用户格的新写入不再带
  `tier` / `budget_ms`（声明保留，供历史 WAL 读）。三处读方同批改读新格并保留回退。
- 2026-10-22 施工订正六：`stages_done` 的「对拍」不是新旧两份状态的对照——施工时
  生产侧只剩这一份缓存字段，本任务删掉字段本身；对拍改为 `done`（按轮扫全史）与
  `done_since`（按幕锚）的结论对照 + 续写幕回归。`ChatOrchestrator::classify_enabled`
  与 `TurnResume::user_seq` 随之退役（改读事实 / 由调用方直给），否则是死代码。
- 2026-10-22 施工订正七：`now_ms` 入参化只到**视图边界**。`report_due` / `turn_head`
  已是「日志 + now」的纯函数并有同切片求值用例；`begin_drive` 没有接 `now_ms`——
  它的唯一消费者是 T-222 的 `owed` / `drive`，本任务明确不表化。判据 2 的 grep
  因此与 T-222 判据 9 同口径，在那一步执行；本任务交付输入闭包的写侧与视图面。
- 2026-10-22 施工订正八：`report_due` 需要「用户看得见的动静」作静默锚点，同批把
  助手文本四格（`fallback` / `reported` / `opening` / `progress`）与
  `turn.supplemented` 声明进事实表（8 → 15 事实，2 → 3 视图）；`turn_head` 的
  `ver` 1 → 2。视图点名决定事实下限，这条下限是施工时才显形的。
