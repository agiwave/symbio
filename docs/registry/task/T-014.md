## 内容

`store` 的值域里写着 `distributed`，而 `Store` 的不变量里写着 **`seq` 单调**（I1）。
这两条在多副本下直接冲突：副本 A 与副本 B 各自追加，谁先谁后没有全局顺序，
而事件网格的溯源边依赖 `seq` 严格递增（[01 §13.3](../../plan/01-核心架构.md)
「溯源边只能从高 seq 指向低 seq」）——`seq` 一旦不是全局单调，派生图的无环保证就没了。

本仓当前的诚实状态：**没有分布式实现，也没有任何东西在宣称它可用**；
这条缺口挂在 [03 §7.3 G4](../../plan/03-演进与验证.md) 与 [04 §5 R5](../../plan/04-工程落地.md)。

要做的是一次**判断**而不是一段实现：多副本部署是否还在计划内？如果不在，
`store = distributed` 这个取值应当**从值域里退役**（它是 F6 冻结集的一格，退役要走 ADR），
比留一个"将来也许能用"的值域格更干净；如果在，则先定口径：

1. 全局序从哪来（共识日志 / 单写者代理 / 分区 + 分区序号）；
2. 同一 `event_id` 在两副本各命中一次时谁是权威（幂等去重按什么键）；
3. 溯源边在跨副本时指向什么（局部 seq 还是逻辑时钟）；
4. 一致性级别与 I3「到点必答」的关系（脑裂时哪边能发言）。

**判据不是"写完了"，是"ADR 的结论有一个能红的落点"**——
否则这又是一条写在文档里、没有任何东西看着的承诺。
