## 内容

按 [14 §6](../../plan/14-登记与汇总机制.md) 的 owner 前置判断拆解
[04 §3.1](../../plan/04-工程落地.md)：哪些行是守卫账本的**投影**
（owner 是守卫源码里的 WAIVERS / 账本，不迁，改成指认），哪些是**人维护的登记**
（才迁成条目）。迁的部分走协议三步：新定义 → 验证 → 删除老定义。
台账类的形态定案与 T-005 同批讨论（都是机制类元素），避免两次改机制。

## 处理过程

- **形态定案**（台账类共用判法，写回 [14 §6](../../plan/14-登记与汇总机制.md)）：
  按 owner 分行——**守卫账本的投影行 → `spec`**（只固化「口径必须成立 + 谁在判」的对账关系，
  明细由守卫现算）；**人维护的状态行 → `task`**（状态即 `status`）。**不加 kind**（同 T-005）。
- **逐行分流**：
  - **22 步状态**（A 表）⇒ `task` 条目 [`S22`](./S22.md)——它的状态是 task 类元素；
    逐批「缺口 → 接入判据」明细**不迁**（owner = 清偿批次提交 + [`S31-1`](../spec/S31-1.md) 的 R-002 账本）。
  - **死码台账 / 清偿批次表**（§3.1 前言 + 批次表 + 「已清偿 129」段）⇒ 守卫投影，
    登记为 `spec` [`S31-1`](../spec/S31-1.md)；owner = [`dead-code-audit`](../../../scripts/dead-code-audit.mjs) R-002 段。
  - **§1.3 逐阶出口表**（含「用户可见出口」列）⇒ `spec` [`S31-2`](../spec/S31-2.md)；
    owner = [`slo-exit-audit`](../../../scripts/slo-exit-audit.mjs)（该表是它的规则源）。
  - **§4 CI 断言清单（C1–C29 / C-D2–C-D4）**⇒ `spec` [`S31-3`](../spec/S31-3.md)；
    owner = 三个承接主体（`check_all` 不变量列 / `no-direct-call-audit` / verify 程序族）。
- **删除老定义**（同批）：04 §3.1 从 ~110 行的手抄表收敛为**指路索引**（谁登记在哪张表）；
  §3 引表的「状态不在这里」加指路；§3.2 前言与 13 §1 / 13 前言改口径引用（owner 从 04 改指条目）。
- **验证**：`registry-audit` 零违规；`gate --only=docs,facts` 全绿（含 `dead-code-audit`
  的 R-002 批号对账仍读 04 §3.1 的批次表——**规则源保留于此，不改判 04**：批号必须真实存在
  这条对账关系（防写不存在的批号）是它的价值，`spec/S31-1` 只登记口径、不做规则源）。
