## 决策

**背景**：VDFS 是**虚拟动态文件系统**——会话转写在这个语境里本来就有唯一自然形态：`<根>/session/<id>/message` 是一个文件夹、`<id>/message/<mid>` 是一个文件（一条消息）、流式输出即该文件的内容在增长。这套形态**数据面早已落地**（`transcript_of` 返回「落库转写 ∪ 本轮在途缓冲」；`read` 拿到的是已含增量的正文；`list` 按 `ChatMessage.seq` 排序）。**但通知面走偏了两次**：先把消息挂到 VDFS 变更频道上（带 `appended` / `delta` / `truncated` / `renamed` / `to` / `node` / `content` 一堆可选载荷），后拆掉改走独立的 `session/stream` 转写流，再往后把运行态也并进转写流。两次拆解的理由（**频道没有流内序号**、**载荷全量 / 增量混合**）是当时的正确判断，但被记成了**能力性结论**：「`appended` 需要的是**一条有序流**，而不是在资源变更频道上挂一个 `delta` 字段」。**这句话是错的**——错的不是观察，是**归因**：它把**数据的属性**（顺序）误当成了**传输的属性**。

**决策**：
1. **顺序是节点属性，不是投递属性**。`ChatMessage.seq` = 消息在该文件夹里的位置，由写入者分配、随节点下发；消费端按它排序。于是**到达顺序与显示顺序无关**：后生成的先到、两个并行工具的变更混着到，都正确显示——每个变更都指向一个明确的 `path`，节点自带位置。
2. **「追加」不是新取值，是载荷上的 `delta` 字段**：`delta` 有 ⇒ **尾部追加、零回读**；载荷无 ⇒ 节点变了、**回读**（`stat` / `read`）收敛。**取值集合上没有任何「操作枚举」**——消费端不需要猜「这次是追加还是替换」，字段的有无就是答案。任何「内容会增长」的 provider 都能用它（转写、日志、流水），**机制里没有任何会话特化**。
3. **不加快照载荷**（`node` / `content`）。理由是**独立于顺序**的：快照携带的是它**生成那一刻**的状态，迟应用会把运行态回退——这是**陈旧写入**问题，不是乱序问题；而回读（`stat` / `read`）永远最新且**幂等**，是正解。
4. **丢失靠幂等重读兜底，不靠序号**：`event_bus::try_publish` 满通道 → 保留订阅 + 补送 resync 标记；会话终态 → 宽限定时器 → 复查本地非终态节点 → 整份回读；订阅即登记（登记先于加载，避免启动窗口漏变更）。
5. **`session/stream` 与 `transcript_stream` 退役**：它存在的三条理由（顺序、背压、免回读）现在都不成立；`event_bus` 的 `kind = "vdfs"` 成为**唯一实时通道**，`symbio_core` 里不再有第二个投递设施——新域（MCP 工具流、模型流）**不需要再造一个**。
6. **信封收敛为 `{path, data?}`**：`data` 是该路径的业务载荷（消息节点上是 `ChatMessage`，会话节点上是 `VdfsNode`），**缺失 = 无载荷**（回读收敛）。**操作枚举（`created` / `updated` / `deleted`）整个退役**——它们描述的「资源层面发生了什么」与载荷描述的「业务数据变成了什么」是同一件事的两种说法，而消费端真正消费的只有后者。
7. **`path` 恒为被变更节点自身的地址**：集合项的地址形状统一为 `<sid>/<集合段>/<项 id>`，身份就是末段。会话是**容器**，其下是若干**并列的集合**（消息 / 子会话 / 记忆 / 工作目录……），所以**机制不认识任何一类集合**——新增一类集合只需在 `internal_dirs` 里声明一个段，信封与消费端都不动。
8. **删除的表达**：资源域 = 「载荷缺失 + 回读 `NotFound`」（删掉的节点本就没有视图可带）；消息域 = `ChatMessage.status = removed`（消息词汇本就有它）。

**理由**：
- **热路径用载荷、冷路径回读**——高频帧（逐 token）全部带增量，只有低频帧（创建 / 终态 / 压缩）才回读。**载荷该不该有，取决于它落在热路径还是冷路径上。**
- **`event_bus` 的背压纠正已上移**，所以「一条机制」的成本已从两处降到一处。
- **顺序从来不是投递层的职责**：两个并行工具的变更混着到、后生成的先到，显示都正确。

**后果与不变量**：
- **一个变更取值（或载荷字段）必须有生产性生产者**（这是批次 G 删除载荷时立的判据）。词汇表旁**必须同时留下生产者清单与本节链接**——否则下一个改动者会按「零生产者」再删一次。
- `delta` 回到它本来的位置——**`ChatMessage.delta` 字段本身**，不再是信封上的副本；门面不再换信封（与 `VdfsChange` 形状逐字相同的影子类型已合并删除）。
- 运行态随载荷带全量节点视图（与 `stat` 同一构造点），消费端零回读就地收敛；资源信号保持无载荷，消费端防抖重拉。

现行规范见 [design/vdfs.md](../../design/vdfs.md) §9「变更通知」。
