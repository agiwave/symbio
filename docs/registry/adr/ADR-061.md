## 决策

**背景**：规范 §8 与 MCP 对照时留了一个开放项（`D5`，登记处 [T-007](../task/T-007.md)）：
外部插件的报文要不要按 JSON-RPC 2.0 写。

**决策**：**不引入**。线格式沿用本仓已有的 `PluginMessageWire` / `PluginPayloadWire`，
外部插件的帧只在其上多两个字段：`op`（操作名）与 `id`（请求/响应配对）。

**理由**：

1. **本仓已经有两套线上约定**（Tauri IPC 与 HTTP/WS），`PluginMessageWire` 是插件域的
   那一套；再加 JSON-RPC 就是**第三套**，而这三套的差别恰好是静默的——
   都能跑通，只在出错形态与字段命名上分家。
2. **JSON-RPC 要的东西我们已经有了**：`op` ≈ `method`，`id` ≈ `id`，
   请求/响应配对 ≈ 它的核心卖点。它多出来的 `jsonrpc: "2.0"` 版本字段、
   `method`/`params` 的嵌套约定与错误对象结构，对一个**宿主自己定义**的插件协议没有收益。
3. **复用是实打实的代码量**：stdio 形态的接入成本之所以接近零（
   [ADR-058](ADR-058.md)），正因为「宿主已有的 `PluginFrame` 就是 JSON 帧」——
   换成 JSON-RPC 就要求在帧编解码之外再维护一层映射。

**被否决的方案**：

- **照 JSON-RPC 2.0 实现**：否决。理由 1/2/3。**从 MCP 借鉴的是形态（stdio 优先）
  与时序（能力协商先于服务），不是它的报文规范**（规范 §8 明列「不必借鉴的一点」）。
- **JSON-RPC 兼容层（对外说 RPC，对内翻成帧）**：否决。为一个**不存在的外部调用方**
  维护翻译层——外部插件由本规范定义，没有第三方客户端要按 RPC 说。
- **现在就把 `op`/`id` 并进 wire，本条顺手实现**：否决。这是第二期的事，
  决策与实现分批（08 §0 纪律 1）。

**后果与不变量**：

- **能力协商先于服务**（从 MCP 借的那点）：`init` 一次说清版本与需要/授予，
  避免「调用时才发现不支持」——这是 §5.3 `declare` 的时序，不因换报文而变。
- **不变量**：帧的**载荷**仍是各协议的线格式（`PluginPayloadWire`），本条只定**信封**；
  内置插件的进程内调用不经过这层，形状不变。
- **兼容性责任在 `plugin_api`**（[ADR-060](ADR-060.md)）：不靠 JSON-RPC 的版本字段兜底。
