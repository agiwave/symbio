## 决策

**背景**：规范 §7 定了能力闭集（九个）与「manifest 授予 ⊇ init 需要」的交集校验，
但「强制到什么程度」一直是倾向（`D3`，登记处 [T-007](../task/T-007.md)）。

**决策**：权限的强制点在**装配期**，不在运行期：

1. 宿主读 manifest 的 `plugin_grants`，插件在 `init` 响应里声明 `needs`，
   **授予 ⊉ 需要 ⇒ 拒绝 `init`**并记录缺失的能力——即「不信任就不装」；
2. **不引入运行时沙箱**（seccomp / 网络命名空间 / 系统调用过滤一概不做）；
3. 能力清单是**闭集**：新增能力必须改规范 §7 那张表 **且** 立一条 ADR，
   **不允许插件自定义能力名**。

**理由**：

1. **stdio 形态已经是进程级隔离**（[ADR-058](ADR-058.md)）：不共享内存、崩溃不传染。
   剩下要防的是「插件越界用宿主的能力」，而那件事宿主**有权在装配时就不答应**——
   拒绝启动比事后拦截更便宜，也更可审计。
2. **运行时沙箱是一条需要长期维护的平台能力**（各家 OS 的机制不同、与调试/性能相互干扰），
   把它和「开放第三方插件」绑在同一期，等于用最大的不确定项去付最确定的收益。
3. **闭集是交集校验成立的前提**：能力名可以自定义，「授予 ⊇ 需要」就退化成字符串游戏，
   两侧声明的表面文章下面没有任何约束。

**被否决的方案**：

- **加运行时沙箱（seccomp / 容器化子进程）**：本期否决。留待「有真实外部插件装进来了、
  且证明声明级校验不够」时单独立条——那时要论证的是拦哪一类越界，不是先建机制。
- **只做宿主侧声明，不要求插件声明 `needs`**：否决。只有「授予」没有「需要」，
  宿主不知道插件要干什么，只能全授，等于没约束。
- **反过来只信插件的 `needs`（自动授予所需）**：否决。权限由**被授权方**申请即由它说了算。
- **把 `event.publish` 并入 `vdfs.write`**：否决。投递事件是**广播**语义，影响面跨插件
  与前端，与写一个文件不是同一类风险。

**后果与不变量**：

- **两侧都声明，才有可检测状态**：`manifest` 记「宿主**授予**了什么」，`init` 记
  插件**需要**什么；「授予 < 需要」是本体系里第一个真正的权限失效形态，也是唯一要拦的。
- **权限面重心在「插件能对宿主做什么」**：`host.ctx` / `vdfs.*` / `event.publish` 与
  `fs.*` 同权重——一个能任意写 VDFS 的插件可以改会话转写、改别人的配置、伪造记忆，
  **根本不需要碰文件系统**。只列 `fs`/`net`/`proc` 会让模型看起来完整、实际漏掉最大一片。
- **与 `SecurityPolicy` 分层共存，不替换**：`SecurityPolicy`（`symbio/src/plugins/local/policy/mod.rs`）
  管「local 插件自己的工具怎么安全执行」，本条管「宿主允不允许一个插件碰共享空间」——
  前者是实现细节，后者是装配契约。
- **不变量**：`plugin_grants` 跟着插件目录走（I1），搬走目录 = 带走授予；
  本条不新增保留键之外的任何配置面（键的形态见 [ADR-060](ADR-060.md)）。
