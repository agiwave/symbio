## 决策

**背景**：规范 §6 要在 `Plugin` trait 上立生命周期钩子，钩子的粒度是开放项
（`D6`，登记处 [T-007](../task/T-007.md)：两钩子 vs 更多细粒度钩子）。

**决策**：**只有两个钩子**。

```rust
async fn start(self: Arc<Self>, ctx: Arc<dyn PluginInvokeRequest>) -> Result<(), PluginError> { Ok(()) }
async fn stop(self: Arc<Self>, reason: PluginStopReason) -> Result<(), PluginError> { Ok(()) }
```

- 两者都是**可选**的：带默认空实现，**既有生产侧 `impl Plugin` 一个都不必改**；
- `start` 在「装配后、开始服务前」调用一次；
- `stop` 在停用 / 卸载 / 进程退出前调用，**用 `reason` 区分三种情形**
  （`Disabled` / `Uninstalled` / `Shutdown`），而不是拆成三个钩子。

**理由**：

1. **钩子数与契约宽度是同一件事**：`Plugin` 是影响面最大的公共面之一（每个插件都要实现它）。
   多一个钩子 = 多一处「所有实现方都得知道」的地方，而收益只在**真有外部插件需要**时才出现。
   这正是 [ADR-055](ADR-055.md) 立的 CS-001 三格棘轮管着的形状——`traits` / `methods` /
   `defaults` 只许降；本条若把生命周期拆成四五个钩子，`methods` 与 `defaults` 两格都会变宽，
   那需要一条**放宽基线**的论证，而不是「顺手多给几个扩展点」。
2. **`reason` 参数与拆钩子的分野**：细粒度钩子（`on_disable` / `on_uninstall` / `on_shutdown`）
   的差别只在**为什么停**，不在**做什么**——同一套收尾逻辑按原因分支即可。
   拆成三个方法等于把一处 `match` 摊到 trait 面上，还要三个调用点。
3. **默认空实现是「加钩子不改变现状」的保证**：内置插件的行为与今天逐字节一致，
   这条决策因此可以独立回退（外部插件那侧没有实现，就没有既有依赖）。

**被否决的方案**：

- **更多细粒度钩子（`on_disable` / `on_uninstall` / `on_shutdown` / `on_config_change`）**：
  否决，理由 1/2。`on_config_change` 尤其：配置变更的现行形态是插件读自己的
  `PLUGIN.yml`（I1），不是宿主推送。
- **状态机式生命周期（`init` / `ready` / `draining` / `stopped` 多态 + 宿主驱动）**：
  否决。它把状态机的所有权搬进 trait 契约，宿主要为每个插件维护一台状态机，
  而当前唯一的需求是「起一次、停一次带原因」。
- **不加钩子，外部插件的收尾靠 drop / 进程退出**：否决。`stop(Uninstalled)` 要在
  **删目录之前**执行（插件的数据在自己的目录里，I1），`Drop` 无法保证这个时序，
  也拿不到 `reason`。

**后果与不变量**：

- **接线点都是既有动作**（规范 §6 的表）：`registry.mount_all()` 构造后 `start`；
  `set_enabled(false)` 移除前 `stop(Disabled)`；`uninstall()` 删目录前 `stop(Uninstalled)`;
  进程退出逐插件 `stop(Shutdown)`。不新增装配动作。
- **外部插件侧的实现**：`stop()` 发 `shutdown` 帧 → 等 `ok` → 关 stdin → 等进程退出 →
  **超时就 kill**（宽限期量级 5 秒）。「等」必须有上限——否则一个不肯退的子进程
  会把宿主的停用变成挂起。
- **不变量**：内置插件零行为变化；`Plugin` trait 的形状变化必须在提交里可见
  （CS-001 会判），本条按「加两个带默认体的成员」计，落地时若触宽即须先论证。
- **落点**：第二期（规范 §9）与「跑通一个外部插件」同批。
