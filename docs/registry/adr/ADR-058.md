## 决策

**背景**：[第三方插件规范](../../design/third-party-plugin-spec.md) §3.3 列出四种形态
（stdio / HTTP / WASM / 动态库），此前只有「本文倾向」。本条把它钉成决策
（登记处 [T-007](../task/T-007.md) 的 `D2`）。

**决策**：外部插件的接入形态**两档**：

1. **首选 stdio 子进程**——宿主 spawn 子进程，父写 stdin、子写 stdout，一行一个 JSON 帧；
2. **次选 HTTP(/WS) 端点**——插件是常驻服务，宿主按 §3.1 的值语法连过去。

**不做动态库**（`abi_stable` 那类同进程加载）；**WASM 后续单独评估**，不在本期承诺。

**理由**：

1. **第三方插件的核心诉求是隔离，而动态库只解决编译期**。同进程加载没有故障边界：
   插件 panic / 泄漏 / 死锁直接落在宿主进程上，且 Rust 无稳定 ABI，`abi_stable` 要求
   双方锁定同一版本——生态代价高、换来的东西与「隔离」无关（历史文档
   `docs/archive/proj/IMPROVEMENT_PLAN_2026.md` 曾把 `abi_stable` 与 `wasmtime` 并列，
   本条撤掉前者）。
2. **stdio 的成本几乎是零增量**：宿主已有的 `PluginFrame` 就是 JSON 帧，
   子进程只需「读一行 JSON、写一行 JSON」；这恰是 MCP 已验证多年的形态（跨语言、
   进程级隔离、崩溃不传染）。
3. **HTTP 次选不是备胎**：常驻服务、复用现成的 gateway 线上类型是真实场景；
   它排在 stdio 之后，是因为它把「网络边界」当成隔离边界，隔离强度与配置成本都不如进程。

**被否决的方案**：

- **动态库（`abi_stable`）**：否决，理由见上——它解决的与本体系要解决的问题不相干。
- **WASM（wasmtime）现在就做**：否决。沙箱确实是更强的隔离，但本仓没有任何 wasm 资产，
  且「宿主已有的帧编解码能不能直接复用」要先论证；留待有真实需求时单独立条。
- **只做 stdio，HTTP 等以后**：否决。`ext:` 值语法（[ADR-060](ADR-060.md)）本来就把传输
  写成值的一部分，两种形态共用同一套 `Plugin` 容器语义，先留第二个分支不是提前实现。

**后果与不变量**：

- **落点**：装配方 `composite` 的 provider 解析多一条分支（`ext:stdio:` / `ext:http:`），
  产出的 `ExternalPlugin` 是一个**普通的 `Plugin` 实现**——容器只认 trait，
  从这里往后与内置插件无差别（规范 §3.2）。
- **不变量**：内置路径**一个字节都不改**（无 `ext:` 前缀即走现有查表构造）；
  I2「挂载名 = 目录名 = 路由前缀」对外部插件同样成立，不因传输形态而变。
- **本条不决定**报文形态（[ADR-061](ADR-061.md)）与权限强制程度（[ADR-059](ADR-059.md)）。
