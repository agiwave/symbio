## 决策

**背景**：规范 §4 要在 `PLUGIN.yml` 里表达「怎么连到这个外部插件」，两条路都摆过：
扩展 `plugin_provider` 的**值**，或新增 `plugin_transport` / `plugin_endpoint` 等**键**
（`D4`，登记处 [T-007](../task/T-007.md)）。

**决策**：**只扩展值语法**，键的空间不动：

```yaml
plugin_provider: web                              # 内置：查表，现状完全不变
plugin_provider: "ext:stdio:./weather"            # 外部：stdio 子进程，可执行相对路径
plugin_provider: "ext:http:http://127.0.0.1:8080" # 外部：HTTP 端点
```

装配期把「查 `inventory` 表」升级为「解析值」，解析结果两种来源
（`Builtin(id)` / `External(transport, target)`），解析方是 `composite`——
与「谁构造插件」同处，不引入新角色。

**新增的保留键只有两个，且都不是连接键**：`plugin_api`（要求的宿主插件 API 版本）
与 `plugin_grants`（宿主授予的能力）。

**理由**：

1. **一个事实一个位置**：`plugin_provider` 已经在回答「这个目录的插件从哪来」，
   外部插件只是**另一个来源**。再加一组连接键，就把同一个问题写成两处，
   于是必然出现「`plugin_provider` 说 stdio、`plugin_endpoint` 说 http」这种没人裁决的组合。
2. **减少新加机制**：`PLUGIN.yml` 的骨架、`creator_has` 判据、`PluginEntry` 结构都不动，
   只多一条解析分支；键的语义闭集不变，配置文档与表单也不必重写一遍。
3. **`plugin_api` 必须在 manifest**：宿主要在**启动子进程之前**就知道「这个插件我认不认识」
   ——否则要么盲目启动（可能挂），要么起来后才发现不兼容（副作用已经产生）。
4. **`plugin_grants` 必须在 manifest**：权限是**宿主**的决定，必须在宿主侧可审计
   （I1：跟着目录走，搬走目录 = 带走授予）。

**被否决的方案**：

- **新增 `plugin_transport` / `plugin_endpoint` / `plugin_command` 三个键**：否决，理由见上；
  它还让「内置插件」这三个键全部为空，一份配置文件出现两套互斥的填法。
- **连接信息放到独立的 `external.yml`**：否决。违反 I1（一个插件目录一个配置文档），
  并让「搬走目录 = 带走全部装配信息」这条不变量出现例外。
- **值语法用 YAML 嵌套映射（`provider: {type: stdio, cmd: ...}`）**：否决。
  `plugin_provider` 现在是一个标量，`creator_has` 与装配判据都按标量读；
  改成映射要动的地方比一条 `ext:` 前缀解析多得多。

**后果与不变量**：

- **内置路径行为逐字节不变**：无 `ext:` 前缀即走现有构造，不解析、不分支。
- **插件「需要」什么不在 manifest 里**（那是 `init` 响应，[ADR-059](ADR-059.md)）：
  manifest 只记宿主授予了什么，两者分开才有「授予 < 需要」这个可检测状态。
- **值语法是解析契约不是文本约定**：`ext:` 之后第一段是传输名（`stdio` / `http`，
  闭集见 [ADR-058](ADR-058.md)），其余是目标；解析失败必须在装配期报错，
  不得退化成「当成内置 id 查表」。
- **落点**：第二期（规范 §9）；本条不实现任何解析代码。
