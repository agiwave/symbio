# Symbio 投影映射（DE-001 §8 取值 ↔ 代码模块）

> **文档类型：参考（手写）** — 左列的唯一 owner 是 [DE-001 DE-001 §8](../003-design/001-核心架构.md "DE-001-核心架构") 的
> `projection` 行；本表只回答「这个取值在代码里由谁承接」，不复述取值域，也不判取值。
>
> **为什么需要这张表**：同一层存在两套名字。DE-001 §8 的取值是**事件里能写的视图名**，`symbio_sdk/projection/`
> 里的是**实现文件**，两者不一一对应（`budget` 由成本能力包的 `ledger` 承接、`replay` 由 `rebuild.rs` 承接、
> `conation` 由会话插件的模块承接）。这些对应关系此前只写在各自文件头的散文注释里——
> 读得到、机器读不到，于是没人能证明它没漂。
>
> **承接方按消费方分布定**（[DE-025](../003-design/025-能力包与扩展面.md "DE-025-能力包与扩展面") D-221）：只被一个
> owner 读的折叠住 owner 的 `src/projections/`，本表把它的承接方写成 `—` 并在右列给出路径——
> 「在 core 的投影目录里」从来不是折叠的归属理由。
>
> **守卫**：[`doc-symbol-audit`](../../scripts/doc-symbol-audit.mjs) 的 **D-014** 三方对账——
> DE-001 §8 的取值集合 ↔ 本表的两张表 ↔ 真实目录。加取值不填表、加模块不归类、填了不存在的文件，任一即红。

## 1. DE-001 §8 的 14 个取值，各自由谁承接

| DE-001 §8 取值 | 承接方 | 形态 | 一句话 |
|---|---|---|:-:|
| `readyset` | — | 任务能力包 | 就绪判定（`非终态 ∧ depends_on 全部终态 ∧ 未挂起 ∧ 租约不在途`）。实现住在 `crates/symbio-plugin-task/src/readyset.rs::ready_all`——折叠连同对外名 `task.readyset` 一起交能力包（那张 `ViewDecl` 在 `decl.rs::VIEWS`），两个读者（`task` 的调度器、`session` 的就绪列）按名字读，不认识形状（[DE-026](../003-design/026-能力拆分与影响类.md "DE-026-能力拆分与影响类") 名册 `#23`，[DE-045](../003-design/045-能力包迁出与落地裁决.md "DE-045-能力包迁出与落地裁决") D-289）。本轮容量 `cap` 因此不在折叠里：`ViewDecl::eval` 没有形参通道，容量是**读者的预算**，不是算式的参数 |
| `turnstate` | — | 已退役 | 轮态随 `TurnState` 退场（D-317）：轮的身份改由 `scope` 键表达，不再有独立的轮态投影 |

| `eval` | — | 平凡值 | 平凡值本身就是「不启用任何投影」，故无文件——这一行是 DE-001 §8 的自指，不是缺实现 |

| `consolidate` | — | loop 插件 | 巩固的接受边界（架构只给位置，不给算法）。实现住在 `crates/symbio-plugin-loop/src/projections/consolidate.rs`——写方 `memory_events.rs` 是它的唯一生产消费方（[DE-025](../003-design/025-能力包与扩展面.md "DE-025-能力包与扩展面") D-221） |

| `calibration` | — | 技能能力包 | 技能的使用次数 / 回退次数。实现住在 `crates/symbio-plugin-skill/src/decl.rs::calibration_ledger`——观测格 `memory.calibrated` 的 owner 就是它，折法随词汇 owner 走（[DE-026](../003-design/026-能力拆分与影响类.md "DE-026-能力拆分与影响类") 名册 `#19` / `#20`）：它自己用置信度闸，会话统计按名字读那一列 |
| `budget` | — | 成本能力包 | 成本台账。实现住在 `crates/symbio-plugin-cost/src/decl.rs::ledger`——折叠连同对外名 `cost.ledger` 一起交能力包，两个读者（`loop` 的熔断闸门、`session` 的成本列）按名字读，不认识形状（[DE-026](../003-design/026-能力拆分与影响类.md "DE-026-能力拆分与影响类") 名册 `#18`）。`budget` 一词让给 view 域的 `Budget`（记账口径），故实现名与取值异名 |
| `replay` | `projection/rebuild.rs` | 模块（异名） | 回放重建：事件网格 → `ChatNode` 节点树（D-049 的读侧真源）。文件没沿用 `replay` 这个名字 |
| `skill_compile` | — | 写侧函数 | 裁决：写侧函数 + 开关，没有读侧投影，因此没有文件 |
| `conation` | — | 会话插件 | 「欲」的读侧形态：表达了哪些欲、各自有没有升格成任务。实现住在 `crates/symbio-plugin-session/src/conation.rs`——承接方按消费方分布定，唯一生产消费方是会话插件（[DE-024](../003-design/024-能力横向扩充的通路.md "DE-024-能力横向扩充的通路") D-201） |
| `snapshot` | — | 会话侧 | 压缩快照是会话上下文产物（`crates/symbio-plugin-loop/src/context/pipeline.rs`），不是 core 投影 |
| `display` | — | 已裁决不做 | 裁决：产物进上下文是目标形态；UI 侧渲染是 `rebuild.rs` 的节点重建，不是投影 |

**读法**：`形态 = —` 的几行不是「待办」，是**已裁决的现状**；凡将来落地，把 `—` 换成模块路径即可，
D-014 不会因此变红（它判的是覆盖，不判「必须实现」）。

## 2. 没有 DE-001 §8 取值的模块

`symbio_sdk/projection/` 里不是每个文件都对应一个 `projection` 取值——它们分三类：

| 模块 | 类别 | 职责 / 为什么不进 DE-001 §8 |
|---|---|---|
| `projection/mod.rs` | 目录 | trait 与冻结锚点 F2（构造形状），不是某个视图 |
| `projection/task_vocab.rs` | 词汇面 | 任务族五个名字的形状（`TaskVocab` 五格）——不是投影，一条都不折：任务能力包的 `readyset` 折叠在 owner 包里直接引用它（折叠搬出 core 后形参通道退场，[DE-045](../003-design/045-能力包迁出与落地裁决.md "DE-045-能力包迁出与落地裁决") D-289），会话插件的 `autonomy` 折叠仍在构造期收它（[DE-024](../003-design/024-能力横向扩充的通路.md "DE-024-能力横向扩充的通路") D-206 的现存理由：那条折叠不在任务包里） |
| `projection/vocab.rs` | 词汇面 | 对话面三张词汇表的形状（`ChatVocab` 11 / `MessageVocab` 5 / `CommitmentVocab` 4）+ 两个纯函数 `slot_of` / `slot_node_of`（名字 → `ChatSlot` → 节点 id）。不是投影：它是**已有折叠算法的参数表**，大小跟着折叠走、不跟着能力数量走。加一个新能力（自带事件、自带投影）时本文件零 diff——这正是它存在的理由。与 `task_vocab.rs` 拆成两个文件是因为消费方不同：任务族只有 `readyset` 与 `autonomy` 两个折叠，对话面有十一个 |
| `projection/transcript.rs` | 读视图 | 对话转写，`Reasoner` 组 prompt 的输入 |
| `projection/branch.rs` | 读视图 | 分支读法：`turn.branch` / `turn.branch_selected` → 组与「此刻读哪一支」。一份并组与选择折叠，两个问法——呈现侧盖章 `stamp_branches`（问「这支有没有节点」）、请求包侧 `branch_hide_unselected`（问「这支有没有被删掉」）。为什么「读哪一支」是事实而不是 UI 状态，见 [D-173](../003-design/001-核心架构.md "DE-001-核心架构") |
| `projection/mutations.rs` | 索引 | 消息列表变更的读侧索引（D-053） |
| `projection/elision.rs` | 索引 | 「这一段不读」的唯一读侧索引：未选中分支的根与带 `elision` 的诞生格声明的区间合流，`transcript` 与 `prompt_fidelity` 共用同一个应用点（D-249） |
| `projection/prompt_fidelity.rs` | 判据 | 事实网格 → prompt 的双向完整性判据（D-048） |

**读数口的落点按消费方分布**：[DE-008 §3.1.1](../003-design/008-能力注册表与能力坐标系.md "DE-008-能力注册表与能力坐标系")
「自主程度」的复算口径住在 `crates/symbio-plugin-session/src/autonomy.rs`——唯一生产消费方是
会话插件（[DE-024](../003-design/024-能力横向扩充的通路.md "DE-024-能力横向扩充的通路") D-200 / D-201），与上表
`conation` 那一行同法；它不在本表，因为本表只归类 `symbio_sdk/projection/` 里的文件。

**为什么它们不该有取值**：`projection` 取值描述的是「有哪些视图可以被指名启用」。读数口、统计列、
水位、判据都是**无条件存在**的读侧函数——没有「不启用」的形态，自然也不需要被登记成一个取值。
把这类文件塞进 DE-001 §8，等于让 `projection` 行同时表达两种东西，守恒律就失效了。

## 3. 已交还 owner 的折叠（不在 core 的投影目录里）

判据是消费方分布，不是目录名（[DE-025](../003-design/025-能力包与扩展面.md "DE-025-能力包与扩展面") D-221）。这几条折叠
今天住在读它们的插件自己的 `src/projections/` 或某个能力包里，`symbio_sdk/projection/` 里已经没有对应文件，
所以它们不在 §2 归类——本表仍登记它们，免得「按名字找不到实现」变成第二次考古。
时延 / 兜底 / 跨度三列、成本台账、校准账、声誉台账与就绪集已经再走了一步：它们连同对外名一起成了各自能力包的
`ViewDecl`（`#13` 的 `D-281` 两半折叠、`#18` 的 `D-285`、`#19` / `#20` 的 `D-286`、
`#22` / `#28` 的 `D-288`、`#23` 的 `D-289`），读方按名字读、不认识形状。

| 折叠 | 类别 | 现居处与职责 |
|---|---|---|
| 时域跨度（`span`） | 读数口 | `crates/symbio-plugin-slo/src/decl.rs::span`：DE-008「时域跨度」的复算口径——报数，不建视图；对外名 `slo.span`，跨会话中位数由 `span_merged` 交 |
| 时延列（`slo`） | 统计列 | `crates/symbio-plugin-slo/src/decl.rs::latency`：SLO [DE-016](../003-design/016-工程落地与验证.md "DE-016-工程落地与验证") §8.2 时延列的统计口径（`chat.assistant.final` 的 `cost_ms`）；对外名 `slo.latency`，档位归属与兜底率共用同文件的 `declared_tier` |
| 兜底率列（`fallback`） | 统计列 | `crates/symbio-plugin-slo/src/decl.rs::fallback`：SLO [DE-016](../003-design/016-工程落地与验证.md "DE-016-工程落地与验证") §8.2 兜底率列的统计口径（各档位的兜底占比，档位归属与 `latency` 同用 `declared_tier`）；对外名 `slo.fallback` |
| 校准账（`calibration`） | 统计列 | `crates/symbio-plugin-skill/src/decl.rs::calibration_ledger`：按 `skill_id` 累计使用与回退次数（`confidence = 1 − 回退率`），阈值与账在同一 crate；对外名 `skill.calibration`，读方是会话统计的校准列 |
| 成本台账（`budget`） | 统计列 | `crates/symbio-plugin-cost/src/decl.rs::ledger`：按主体累计 `cost_ms` 的台账（SLO [DE-016](../003-design/016-工程落地与验证.md "DE-016-工程落地与验证") §8.2 的成本列、[D-044](../003-design/001-核心架构.md "DE-001-核心架构") 的熔断读数来源）；对外名 `cost.ledger`，两个读者一个 owner |
| 声誉台账（`reputation`） | 统计列 + 裁决输入 | `crates/symbio-plugin-reputation/src/decl.rs::ledger`：按主体累计 `offered` / `kept` / `broken` 与 `score`——读的是承诺三条名字（`opened.id/from` / `released.id` / `broken.id`），同格的 `commitment.asserted` 自报进不了账（[DE-043](../003-design/043-多智能体社会.md "DE-043-多智能体社会") §6 断言 2）；对外名 `reputation.ledger`，两个读者一个 owner（`session` 的声誉列 + `loop` 的轮末淘汰回路，`D-288`）。它读的是「有格位、无事实声明」的断言格（[D-282](../003-design/045-能力包迁出与落地裁决.md "DE-045-能力包迁出与落地裁决")），故控制面不为它补 `FactDecl` |
| 就绪集（`readyset`） | 调度输入 + 统计列 | `crates/symbio-plugin-task/src/readyset.rs::ready_all`：任务族的全部就绪集（入队序、不设容量）——对外名 `task.readyset`，两个读者一个 owner（`task` 的调度器、`session` 的就绪列，`D-289`）。容量 `cap` 不在折叠里：`ViewDecl::eval` 没有形参通道，「本轮派几笔」由读者套在折叠结果上（`ready_view`）。它读的是自己包声明的 `task.*` 五格，词汇面与折叠同处 |
| 变更账（`changes`） | 读视图 | `crates/symbio-plugin-session/src/projections/changes.rs`：工作目录变更账——`artifact.added` → 每路径最新一次写动作（最近在前）；不是事件族，网格不变，写侧为什么不该另立 `file.*` 见 [D-169](../003-design/001-核心架构.md "DE-001-核心架构") |
| 巩固接受边界（`consolidate`） | 判据 | `crates/symbio-plugin-loop/src/projections/consolidate.rs`：`accept` 只由 `memory_events.rs` 在写格前问一次（§1 里 `consolidate` 那行的落点） |

**仍在 `symbio_sdk/projection/` 的只有一条**（`transcript`），
它有 ≥2 个非 core 的 crate 在读——读者迁完它才轮到下沉，
在那之前把这一格推回去就是 `PP-004` 的红。
