# 契约读者缺口台账

## 内容

## 1. 这是哪一类缺陷

**声明在、写方在、读方（或调用方）从未接上。** 契约三件套里缺的是**最后一跳**，
而这一跳在代码静态可读的面上常常「看起来有」：事件名出现在常量表、视图的 `reads`
列着它、trait 方法有完整实现——只是没有一条运行路径真的去读它 / 调它。

与 `D-369` 记下的 `rev().find` 那一族（只取最后一条 ask）同源——**事实落了、读的人没有**——
但更隐蔽：那一族的错是「读得不完整」，这里根本没有读的人。写方自己不会报错，载荷也照样进库，
所以所有「事实存在」型断言都是绿的。

严重性在于**失效被另一张脸遮住**：

- 对 `session.consolidated`：压缩确实发生、快照确实落库、对话面确实变短——每一格都真；
  但**模型输入从未受影响**，水位只涨不落，压缩在同一会话里反复触发。
- 对 `retire_prefix`：归档实现是真的（`archive_before` 真写盘），只是从来没人调这条
  契约；换基落格时由写方直接归档，这条方法没有读者，已删（§3）。

这两例都不是「机制坏了」，而是**机制与消费面之间断了一根线**：改动在写侧完全正确，
症状却出现在一个没人看的读数上。

## 2. 已修：`session.consolidated`

- 声明与写方：`symbio-plugin-compact`（D-053 / D-336 的换基事实），载荷 `messages`
  是整份消息列表，取代它之前的一切。
- 缺口：模型请求组装（`symbio-plugin-model` 的 `turn_input`）只按 `message.added`
  增量回灌，从未消费快照。于是压缩只改对话面，模型仍读全量历史。
- 实测（t47，修前）：整场压缩 **11 次**，主请求仍带 **21** 条 `user` 消息——压缩做了，
  输入没变。
- 修法：`turn_input` 从最近一条快照的载荷整份起折（与 `message.added` 共用同一译法
  `append_payload_nodes`）；修后压缩回落到 **2 次**，大结果被换基真正吃掉。
- 判据：t47 证据 ③（`session.consolidated` 落格 ≥ 2）＋证据 ⑤（主请求里不再出现
  大结果、轮次回落）。修前两条都绿、而事实无效——正是本类缺陷的典型：**要判「谁读了」，
  不能只判「谁写了」**。

## 3. 已结：`retire_prefix`（删除契约）

`FactSource::retire_prefix(before_seq)`（`crates/symbio-sdk/src/plugin/fact_source.rs`）
原先有完整实现（`symbio-plugin-session` 的 `store::fact_source` 调 `archive_before`），
也有契约文字（「该前缀已固化，可回收」），但**全仓没有调用点**。真正让归档发生的是换基
落格那条路径：`session.consolidated` 的处理器在写快照时直接调
`WalStore::archive_before`（`store/fact_source.rs`），写方自己完成回收，不需要再经一次
「宣布可回收」。

处置按「读者先有，契约后建」：**删除 `retire_prefix`**（trait 方法、两处实现、测试桩），
不保留一条没人调的契约。归档本身不变——`t45` 证明段存在、段号不重叠、压缩前轮次不复活
（实现见 `3c3e7941`）。

## 3a. 信封 `cost_ms`（同批补上）

t28 走绿时暴露的第三例，比第 2 节更早断：`cost_ms` 的**读方**齐全（`slo` 分位数、
成本台账、`I3` 预算判据都读事件的信封字段），**信封却从未被填**——模型端口把实测
耗时写在载荷的 `cost_ms` 里，`draft_into_event` 只搬载荷、不搬信封，于是所有读方
读到恒 0（`I3` 的预算判据也因此永不触发）。

修法在契约自己写明的位置：模块头说「信封的 `event_id` / `seq` / `ts` / `cost_ms`
一律由事实源在入库时生成」——`draft_into_event` 现在把载荷同名值提进信封。
这不是新增字段，是把已有契约的最后一句落地。

## 3b. 读数口径：中止轮不进时延样本（不是样本缺失）

`slo.latency` 只数 `chat.assistant.final` 的信封 `cost_ms`；t7 恢复中止后，中止轮也会
落一条 `final{status:"aborted"}`。**它按 `status` 排除，而非留空**——理由写死在这里：

中止样本的耗时是「被打断的那一截」，它度量的是用户按下停止的时点，不是模型 / 工具
的服务能力。把它计入会把 p95 往「用户手速」拉，属于**样本语义污染**；留空则会让读方
以为「这一档没跑过」，又是另一种误读。所以排除是口径决定，不是数据缺口——以后看到
`final` 条数多于时延样本数，先按本条核对，不要当成丢样本。

## 3c. 已结：执行上下文不带租约截止（D-370）

`PortExecContext.deadline_ms` 是「声明在、生产侧零读者」的典型：环在派发时写入
`sent.at_ms + lease_ms`，但没有任何执行体读它——模型端的 180s 流空闲 / 1800s 总超时、
工具端的 600s 空闲看护都是各执行体的常数。出路选了**删除**（不是接读者），理由：

- 租约（默认 60s）是环判断重派 / 判死的时间点，不是单次执行的时间预算；把它交给执行体
  当超时，会把正常的长模型调用误杀；
- 租约截止的**持久记录**已经在 `sent{deadline_ms}`：正常 / 可重试 / 判死写数值、挂起写
  `null`；引擎只按 `null` 判第三态，到期由 `sent.at_ms + row.lease_ms` 现算——不靠执行
  上下文那一份副本；
- 将来真要下发执行预算，必须是另一格、带读者与判据，不复用租约截止。

字段与全部构造点已删。判据：`grep deadline_ms` 的读点只剩引擎挂起判定与 `sent` 载荷；
lease / 挂起单测与 e2e t22（`sent.deadline_ms` 为正数）原样绿。**看到 `sent.deadline_ms`
不要当成执行体超时已生效**——它只是租约的簿记。

## 4. 以后怎么提前发现


1. **读方清单**：每一条 `shared_events` / 每一个公开 trait 方法，登记时同时填
   「读法」——owner 视图名、reader 函数、IPC 出口、调用点四者之一；填不出 = 红灯。
   清单按**格**而不是按**插件**组织（同一格可以有几个读法，但至少一个）。
2. **消费面检查**：每落一格先问「它能改变哪个用户可见的输出？」。答不出，它就只是
   日志，不该出现在契约表里；答得出就把那个输出写进对应 e2e 判据（t47 的
   「压缩后主请求变小」就是这么来的）。
3. **观测症状**：单调量（水位、压缩次数、被遗忘条数）只涨不落；同一载荷在对话面
   变了而请求面没变；「事实计数在涨、下游读数不随它变」——三者任一出现，先查读方。
4. **门禁化**：`shared-event-vocab-audit` 已要求共享格至少有一个**其他插件**引用；
   同类检查可以再加一条「引用方必须是读法而不是同名常量」——这条尚未进门禁，
   先按第 1、2 条人工过。

## 5. 抖动处置纪律

抖动本身不是缺陷，**「红了就重跑」的习惯**才是：真回归会被当成抖动放过。因此：

- 每次抖动都记下**用例名 + 失败点**（断言的那一格，不是用例名泛称）；
- 同一失败点累计到**两次**，即按缺陷查，不得再以「单跑绿」结案；
- 一次 rustc 进程级异常（Windows 访问冲突，退出码 0xC0000005）也按一条失败点登记；
- 凡「加了等待 / 同步然后串行绿了」，必须能指出**哪一份实例在等、谁在通知**。
  说不出这两头就不算修好，串行绿不构成证据（D-359 就是这样漏过去的：
  等待挂在一份永远空闲的实例上，串行绿靠的是另一条路径上的第二次等待）。
- **失败要留全文**。抖动恰恰是「只有断言带出的那段 stdout/stderr 才定得了归属」的那类
  失败，而终端历来只印末 8 行。独立入口 `e2e/run-tests.mjs` 现在把失败用例的**完整输出**
  按轮落到 `.workbuddy-ai/e2e-failures/<runId>/<case>.log` 并印出路径（门禁 `58-e2e.mjs`
  走 `ctx.run`，逐例日志本来就落盘）。

**抖动明细不在本文**——它是逐次发生的过程记录，归 `git log` 与失败日志；本文只留
上面这条处置纪律。已定案的缺陷与并发才暴露的确定性缺陷见 §5.1。

**「不复现」不等于「已修」**：读数只证明**这个压力档位上不再抖**，不证明这类已经消失。
并发数一旦越过机器的核数，并发墙钟就等于最慢单例，说明还没把机器跑过订；
`t4` / `t57` 的「两轮并成一次请求」与 `t23` 的「整轮卡住」因此保持
「未复现、未定案」，不上表、不当已修。

### 5.1 环境注意事项（不是抖动，是门禁继承的宿主状态）

门禁继承环境变量，`TEMP` 选错会稳定制造假红。两个反例：

- **RAM 盘上的 `TEMP`（`<盘符>:\Temp` 这类）**：`fs.realpathSync.native` 对任何路径都
  返回 `EISDIR`，`windows-restart` 的夹具因此全红；`content_search` 一族报 `os error 1`。
- **仓内临时目录（如 `.workbuddy-ai/tmp`）**：`eol-audit` / `_scope` 的自测把「不在
  git 仓里」当前置，仓内目录会被 git 向上发现，探针拿到 `diff` 而非 `all`。

两者都是环境事实、不是代码缺陷，但每次都会把门禁压成红。跑门禁要带**仓外、C 盘**的
真实临时目录（`LOCALAPPDATA` 默认就在 C 盘），例如 PowerShell：

```powershell
$env:TEMP="$env:LOCALAPPDATA\Temp"; $env:TMP=$env:TEMP; node scripts/gate.mjs
```

### 5.2 并发才暴露的确定性缺陷（与抖动并列的一类）

**单跑绿、并发红，不一定都是抖动。** 若失败点指向「读到的形状缺字段 / 身份帧不完整」，
而时序等待已经结束（终答已落、断言才读），那是**只有并发才暴露的确定性缺陷**：并发只是
把读时点推到了两份表示（状态帧与落库镜像）尚未一致的窗口里。它的复现条件就是并发，
不适用「同一失败点累计两次才按缺陷查」的阈值——第一次就该查「读到的节点形状是否完整」。

已定案实例：t24 / t99 的「应有 `tool_call` 节点」为空。根因不是时序：
`symbio-plugin-tool` 在执行窗口开始时发的那帧只带 `started_at` / `tool_name`，而
`Transcript::apply` 对 `meta` 是「有则覆盖」——`style_tag` 被整格覆盖，工具卡随即折回
`turn`。单跑能绿只因读时点晚于落库镜像按 `into_messages` 重建；并发把读时点提前到了
重建之前。修法是让该帧自足（补 `style_tag`），不是加等待。

## 6. 扩展通路的已知边界

glossary（会话内项目术语表）验证过「新能力按现有通路接进来」这条路：
新 crate + `PLUGIN.yml` 静态注册 + 一条真 e2e（t96），五个受保护目录零 diff（含
`plugin-api`，口径见 `D-372`）。
但结论不是「无墙」，而是**只碰生成物、不碰手写代码**——两处边界必须在这里留底。

### 6.1 已闭合的关卡：跨插件视图不再需要生成物

glossary 不需要跨插件视图（读面由上下文注入承担），所以那次验证零 diff。
下一个同类能力若**必须被别人按名字读**，会在 `shared_views` 这一格停下：
`scripts/facts/views-rs.mjs` 会把共享视图名写进
`crates/symbio-plugin-api/src/view_names.rs`，而该目录在硬判据里属于「不许改」。

**已由 `D-387` 关闭**：跨插件视图的公开动作改为 owner 自己在 `decl.rs` 里
`submit_reports!` 一条报表描述符，读方遍历 `reports()`；`shared_views` / `views-rs.mjs` /
`view_names.rs` 全部退役，生成物只余 `events.rs` / `routes.rs`。生成物判据本身不变：
清单的唯一真源是描述符的 `OUT_REL`（`generatedPaths()`），只豁免**已存在的**生成物、
不碰手写代码；新出现的生成件仍算机制补件（`D-371` 的通用那一半）。

### 6.2 真缺口：术语表只在会话内，跨会话共享缺持久化读面

glossary 的读面是**上下文注入**（`ContextProvider` 读会话投影），因此词表天然只有
会话内可见；新会话的投影里没有上一会话的 `glossary.defined`，模型看不到旧词表。
这不是实现缺陷，而是**能力面缺一条持久化读面**：

- 现状写方：`glossary.defined` 落在会话事实源（`glossary` owner，键 `g-{anchor}-{call_id}`）；
- 现状读方：`glossary_context`（同一会话的折叠，最多 20 条）；
- 缺的是：一条**跨会话**的读面（词表存储 / 检索端口），以及「谁有权写、按什么键合并
  同名词条」的裁决。

**触发条件**：出现「新会话要读上一会话的词表」这类需求（或子智能体要与主根共享术语），
必须先回来处理本条，再谈实现；在触发前，glossary 的能力声明保持 `session-scoped`。

## 7. 已转出的一项

本台账不再承载以下一条，它已转为独立任务：

- **驱动安全阀出口在非 CLI 宿主没有读者**：`Exhausted` / `Stalled` 的文案写在
  `crates/symbio-host/src/drive.rs::drive_notice` 的 stderr，GUI 宿主无人捕获，在界面上与
  「正常结束」同形。`D-376` 已把两条出口放进 `Host::drive` 的 `DriveReport` 返回值
  （`Exhausted` / `Stalled` 同形），但仓库里唯一调用方仍是 CLI 的 `drive_notice`。
  **已结（`D-393`）**：驱动入口在现有的判定点再落一条机制事实 `driver.stalled`
  （`{session_id, outcome, steps?, outstanding}`，两条出口共用一种形状），
  会话的 `runtime` 投影把它折成 `outcome = "failed"` + `error`（「驱动停摆：…未收束 N 笔」），
  非 CLI 宿主经 VDFS 读面直接可见；CLI 的 stderr 文案一字不改。
  落格走**只读开面**（不绑驱动）：出口事实是通知，不是环的输入。
  正向由 `crates/symbio/src/drive.test.rs` 与 `runtime.test.rs` 钉住；e2e 只钉反向
  （`e2e/cases/t104-driver-safety-valve.mjs`）——真实装配里工具结果会开新一轮，
  用户输入没有一条确定性的路径把安全阀顶开。
