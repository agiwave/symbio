# 异常注入矩阵 · 字段 × 能力面

> ⚠️ **本表由 `scripts/facts/injection-matrix.mjs` 从 `e2e/injection-matrix.mjs` 生成，请勿手改。**
> 数据源是同一条判据的输入，审计方是 `scripts/injection-matrix-audit.mjs`（INJ-001…003）。

## 1. 口径

**注入字段** = 夹具上可编排的故障 / 时序字段（`mock-llm` 的场景字段、`mock-mcp` 的脚本位）。
正常内容形状（`chunks` / `toolCalls`）与固定端点（`mock-http` 的 `/slow` / `/missing`）不是注入：
前者是正常输入，后者是靶子内容，都不能「按字段分级」。

**能力面** = 用户能看见注入后果的那一层，不是代码目录。一格 = 一个 `(kind, face)` 对，必须属于以下三类之一：

| 归属 | 含义 | 判据 |
|---|---|---|
| 用例号 | 该字段在这条面上有独立锚 | 编号必须解析到 `e2e/cases/tNN-*.mjs`，且该用例**代码**真的用了这个字段（注释不算） |
| `— 理由` | 这条面没有独立观测点 | 理由必须说清「为什么已由另一条面或另一层判据覆盖」；写不出就应落成缺口 |
| **缺口** | 应该有、暂时没有 | `owner` 必须解析到存在的任务（`T-NNN`）或设计条目（`DE-NNN`） |

未归属格与已登记缺口都进基线（只降不升，`gate.d/35-baseline.mjs`）。反向扫描也在审计里：
用例用了某字段、矩阵没有任何一格认领 ⇒ INJ-003 红——防的是「夹具加了用例、矩阵没人记得改」。

## 2. 矩阵

| 注入字段 | 对话主径（流式呈现 · 失败收敛 · 恢复轮） | 工具调用与反馈回路 | 压缩与长会话归档 | 会话生命周期（多轮 / 长驻 / 统计） |
|---|---|---|---|---|
| **provider 静态错误状态（4xx / 5xx）**（`status`） | t5 · t53 | — 工具轮的 provider 错误与对话轮共用同一失败通道；工具面独有的是 MCP 错误与断流重发 | t18 | t28 |
| **瞬时失败（前 N 次逻辑请求打 errorStatus，之后恢复）**（`failTimes`） | — 瞬时失败的重试语义由 `llm.status` 的多轮失败用例覆盖；`failTimes` 的独有形态是「同一会话第 N 轮坏」，落在 session 面（t47） | — 工具面用 `dropAfter` 钉断流重发的槽位（t54），不依赖瞬时 5xx 的计数语义 | — 压缩失败的静态故障由 `llm.status` / t18 覆盖；t18 注释提到的 `failTimes` 只解释计数口径，未使用该字段 | t47 |
| **plan 级 429 限流（滑动窗口配额）**（`rateLimit`） | t50 | — 限流按 provider 入口的请求计数，与能力面正交；t50 在 `DIALOG_FACE_OFF` 下只让主对话轮对表 | — 配额语义与能力面正交；t50 已钉限流后的冷却恢复，压缩请求共用同一客户端 | — 限流状态不进入会话账本；t50 已从用户可见面钉「被限又自己缓过来」 |
| **首字节延迟**（`latencyMs`） | t52 | — 首字节延迟是流控时序，不改变工具契约；t52 已钉客户端对延迟的容忍 | — 首字节延迟不改变压缩节点契约；流式预览的时序由 t18 的场景编排钉住 | — 延迟不改变会话账本；长驻稳定性由 t47 覆盖 |
| **帧间随机抖动**（`chunkJitterMs`） | t52 | — 帧抖动只影响流内节奏，拼接正确性由 t52 逐字断言覆盖 | — 帧抖动只影响节奏，摘要拼接正确性已由 t18 逐字断言 | — 抖动不改变会话账本；长驻稳定性由 t47 覆盖 |
| **流内停顿（不关连接）**（`stallAfter`） | t52 | — 停顿不关连接，空闲超时判据在客户端单点；t52 已钉 | — 停顿的容忍由客户端单点判；压缩面无独立空闲超时 | — 停顿不改变会话账本；超时收敛由 t52 覆盖 |
| **流中途断开连接**（`dropAfter`） | t49 | t54 | — 压缩请求的断流走同一客户端重试；t18 钉的是失败纪律与重试恢复，未单独编排中途断连 | — 断流后的续轮由 t49 ④（恢复轮）覆盖；会话生命周期面没有独有的断流形态 |
| **不规范 SSE 帧（badJson / truncated / garbage）**（`malformed`） | t51 | — 脏帧由客户端解析层单点处理；t51 已覆盖三种形态，工具面不重复注入 | — 脏帧在解析层统一处理；t51 已覆盖，摘要面不重复注入 | — 脏帧在解析层统一处理；t51 已覆盖，会话面无独立形态 |
| **工具调用回 JSON-RPC 错误**（`onCall.error`） | — 工具错误以工具反馈进入对话，形态在 tools 面钉住（t6 / t62）；对话面不另设 MCP 注入 | t6 · t62 | — 压缩轮不调用 MCP 工具（压缩是 provider 请求 + VDFS 归档），没有 MCP 连接 | — MCP 错误经工具反馈投影进转写；t6 的断言已从生产读出口取会话终态 |
| **工具调用中服务进程断连**（`onCall.disconnect`） | — MCP 客户端只有工具面一个消费方；断连的后果经工具反馈投影进对话，不构成对话面独有形态 | **缺口**：DE-039 —— mock-mcp 已支持 `onCall.disconnect`，但外部执行 / 熔断的上游接线在 DE-039 阶段；RE-005 已判定接线前不补用例，先补会测到 mock 的想象行为 | — 压缩面不持有 MCP 连接 | — MCP 客户端只在工具面；会话账本只记录结果，不持有连接 |
| **MCP 握手失败（initialize 回 error）**（`failInitialize`） | — 握手失败发生在插件装配期，对话链路看不到独立的连接状态 | **缺口**：DE-039 —— 握手失败后的插件降级路径同样属于外部执行接线；mock-mcp 已支持 `failInitialize`，待接线批次配用例 | — 压缩面不持有 MCP 连接 | — 握手失败发生在插件装配期，不进入会话账本 |
| **工具执行延迟（onCall.sleepMs）**（`onCall.sleepMs`） | — 工具延迟不改变对话契约形状；超时语义归 tools 面的熔断判据 | **缺口**：DE-039 —— 工具挂死的超时 / 熔断由 DE-039 接管；mock-mcp 的 `onCall.sleepMs` 已具备编排能力，接线前不写判据 | — 压缩面不持有 MCP 连接 | — 工具延迟不改变会话账本 |

## 3. 读数

- 12 种注入 × 4 个面 = **48 格**：用例 12 格 · 不适用 33 格 · 已登记缺口 3 格。
- 缺口 owner 全部为 `DE-039`（外部执行与熔断）：mock 夹具已具备编排能力，接线前不写判据，理由见 [RE-005-覆盖矩阵](005-e2e覆盖矩阵.md "RE-005-e2e覆盖矩阵") 的缺口节。
- 本表的正常 / 异常覆盖面按**能力域**看另一张表：`RE-005`；本表只回答「每种注入在每个面上有没有锚」。
