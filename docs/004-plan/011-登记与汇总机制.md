## 0. 顶层机制：单文档 + 元信息 + 自动汇总

项目里凡是「一堆条目汇成一张表」的地方（待办清单、规范清单、问题登记、纪律地图……），
手写表格的失效方式是同一套：**状态流转靠人改格子、依赖倒置没人判、表里的编号指到不存在的东西无人核对**——
而这正是 [SP-011](../008-spec/011.md)（机制优先）与 [SP-013](../008-spec/013.md)（出口可核对）要治的形态，
只是那两条纪律此前没有落到**登记处自身**。顶层解法四段：

1. **条目 = 数据**：每篇文档都是一个带 front-matter 的单文档，**文件本身即条目**，
   没有第二处登记表；编号、状态、依赖、证据全在机读字段里，正文承载人读内容
   （条目形态见 [SP-001](../008-spec/001.md)）。
2. **汇总 = 投影**：[文档中心总账](../README.md "docs/README")与各 kind 目录 `README.md` 的
   `<!-- registry:summary -->` 标记区由脚本渲染（RG-030：标记区恰一对，生成器只重写标记之间，
   **标记区之外手写**），**确定性输出、无时间戳**；门禁 [`gate.d/60-facts.mjs`](../../scripts/gate.d/60-facts.mjs) 的
   `autoWork` 自动重生成并暂存——与 `docs/006-ref/006-当前事实表.md` 是同一条约定：投影没人需要手更它，
   就不存在「忘了更」。
3. **引用 = 编号**：文档之间**只写编号**（`[[T-008]]`，显示文字写 `|` 后面），链接地址由
   [`gen-doc-refs`](../../scripts/gen-doc-refs.mjs) 从登记解析生成并在每次门禁重算；
   手工地址（指向已登记文档却不带编号）直接判红——编号是身份（稳定），地址是位置（会变），
   **位置不给人写、也不给人维护**（见 §1.1）。
4. **校验 = 守卫**：[`registry-audit`](../../scripts/registry-audit.mjs) 把字段 / 状态机 / 依赖 /
   分解 / 优先级 / 取代链 / 判据指认 / **未登记文档**全部机械判定（RG-001…RG-025），违规即红；
   范围读不出必须 exit 2，**不许退化成「什么都没校验」**。

**全套机制管什么**：**系统级文档（`docs/`）与模块级文档（各模块 `README.md` / `docs/`）
同属一套**——`kind` 只来自 front-matter，**目录不参与判定**（文档换目录只需把 `id` 跟着改，
判据会拦）。收录范围是「仓内每个活跃 `.md`」，豁免名单只有三类：**代码投影生成物**
（`CURRENT.md` / GATE_CODES / PROMPT_SHAPE / PROMPT_AB）、**历史归档**（`docs/archive/`）、
**非阅读面**（指令注入的 `AGENTS.md`、对外示例 `examples/`、工作区数据 `.symbio/` `.workbuddy-ai/`）。
豁免是**归属声明不是方便门**，名单住 `registry-lib` 的 `SCAN_SKIP_*`，每项写明理由。

## 1. 一个条目长什么样

两种形状，字段全集与状态矩阵以 [SP-001](../008-spec/001.md) 为准。

**条目类**（`task` / `spec` / `adr`）——编号见 id，**文件名 = 去掉前缀的主干**，住 `docs/<kind>/`：

    ---
    kind: task
    id: T-002
    title: 接管 13 §1 问题登记
    status: todo
    created: 2026-10-11
    track: meta
    deps: [T-001]
    ---
    ## 内容
    这条任务要做什么、为什么。
    ## 处理过程
    - 推进记录；闭环后仍可追加。

**文档类**（`goal` / `plan` / `arch` / `ref` / `guide`）——**文档即条目、在位存放**，
id = `<前缀>-<三位序号>[-名称]`、**文件名 = 去掉前缀的主干**（全仓一套规范见 [SP-001](../008-spec/001.md)）、
`title` 逐字等于正文首个 H1：

    ---
    kind: arch
    id: AR-013-vdfs
    title: VDFS —— 虚拟动态文件系统规范
    status: active
    created: 2026-09-13
    ---

    # VDFS —— 虚拟动态文件系统规范
    正文结构由文档自己定（文档类不强制必有小节）。

- front-matter 是**受限 YAML 子集**（零外部依赖）：只认四种值形态，未知字段 / 重复字段 /
  不合形状的行一律判红——拼错的字段名不会被静默忽略。
- **目录不参与判定**：`kind` 只来自 front-matter（RG-002 不再看目录）。规范化的目录
  （`docs/<kind>/` + 模块文档就地）是**组织习惯**，不是机制：搬去别的目录不会破机制，
  但**编号必须跟着改**——编号条目对文件名（RG-003）、`title` 对 H1（RG-021）。
- 编号全 registry 唯一（含跨 kind），所以 `deps` / `supersedes` / `clears` 敢跨 kind 指。

### 1.1 引用别的条目：只写编号，地址不手写

正文里引用其它文档时，**人只写编号**，写成 `[[编号]]`；要显示文字就写在 `|` 后面，
要锚点就写在 `#` 后面（三者可组合）：

```markdown
判据见 [[SP-001]]，整条纪律见 [[PL-006-分步实施计划#0-执行纪律五步每步都不得跳过|08 §0 纪律 3]]。
```

门禁的 `60-facts` 跑 [`gen-doc-refs`](../../scripts/gen-doc-refs.mjs) 把它展开成：

```markdown
判据见 [SP-001](../008-spec/001.md)，整条纪律见 [PL-006 §0 纪律 3](./006-分步实施计划.md#0-执行纪律五步每步都不得跳过 "PL-006-分步实施计划")。
```

**地址从此不是人写的东西**：它由编号/路径从登记解析出来，并由门禁每次全部重算。两种形态：

| 形态 | 链接长什么样 | 身份的载体 |
|---|---|---|
| 标签就是编号 | `[SP-001](../008-spec/001.md)` | 链接**文字** |
| 自定义显示文字 | `[PL-006 §0 纪律 3](./006-分步实施计划.md "PL-006-分步实施计划")` | 链接**标题**（Markdown 标准语法，渲染为悬停提示） |

所以：

- **搬家不用改入链**：编号不变则地址永远正确，全仓入链自己重算，不需要任何人维护；
- **手写错地址会被自愈**：写了旧地址没关系，下一次门禁把它改成当前地址（RF-002）——
  可读性不牺牲：「给人看的文字」在标签，「喂机制的编号」在标题，各占一个位置；
- **指到不存在的编号会红**：`[[不存在]]` 是 RF-001，**且一个文件都不写盘**——
  引用指向不存在的东西，只有写下它那一刻最便宜；
- **新写的手工地址会被拒**：地址指向某篇已登记文档、却既没有编号标签也没有编号标题，
  即 RF-003 判红——这种地址机制搬不动，搬走后没人改得动它。改写方式只有两种，
  都在编号里选一个：`[[编号]]` 或 `[[编号|显示文字]]`。
  例外：**自指**（链接目标就是本文）不判——它随文件一起搬，不会失效。

只管「认得出编号、或指向已登记文档」的站内链接：外链、纯锚点、指向代码 / 脚本 / 归档 /
生成页的普通链接一律不碰，**行内代码段里的记号也不碰**
（那是字面量——本页讲规则的那些例子就是靠它站住的），本机制不是通用链接重写器。

边界（自行承担的代价）：反引号里的自由路径（`docs/005-arch/013-vdfs.md`）不在重算范围——它不是
链接，机制搬不动它；这类写法只由 `doc-link` 的 D-006 判「写下时存在」。要入链自愈，
就写 `[[编号]]`。

### 1.2 分解：parent——父子机制（总目标→子目标、大任务→小任务）

「整体分解出部分」是跨 kind 的普遍需求：总目标分解出子目标、大任务分解出小任务、
产品功能分解出子功能、大阶段分解出子阶段。承载它的是 `parent` 字段——
**与 `deps` 正交的两个字段，各答一个问题**：

| | `deps` | `parent` |
|---|---|---|
| 回答什么 | 必须先有什么（前置义务） | 是谁的一部分（分解归属） |
| 图论形状 | DAG 的边（可跨 kind） | 树的边（只许同 kind，RG-024） |
| 强制性 | 生效档要求前置闭环（RG-008） | 父子状态档位单调（RG-025） |
| 与编号的关系 | 无约束 | 无约束——编号平铺，层级不进身份 |

- **值 = 单个父编号**（单值标量）：一个子条目只有一个父亲。多父没有语义——「两个大任务
  共享一个小任务」用两条 `deps` 边表达，`parent` 保持树形，渲染与查询才确定。
- **同 kind**：分解是同类事物的大小之分。任务服务于某阶段（跨 kind）用 `deps` 或正文引用，
  不塞进 `parent`——一个字段一种语义，塞两种就两种都读不出。
- **编号不体现父子**：子条目平铺分配，弱约定「在父编号之后取最近可用序号」（人读聚类与
  diff 友好，不是判据）。把层级编进编号（`GO-001.1`）是让身份承担会变的东西——与
  「目录不参与判定」同款哲学：位置与层级都是投影，编号是身份。
- **状态档位单调**（RG-025）：子生效 ⇒ 父不得停在未生效档（「小任务都 `doing` 了，大任务
  还写着 `todo`」是谎报）；父退场 ⇒ 子不得停在生效档（「大任务都 `done` 了，还有小任务
  `doing`」是谎报）。中间组合合法：父 `doing` 子 `todo`（分解未动）、子 `wont` 父 `doing`
  （中途砍子项）。档位表按 kind 取（task 的生效档 `doing`/`done`、退场档 `done`/`wont`；
  文档类 / spec 的生效档 `active`、退场档 `retired`；adr 的退场档 `superseded`/`withdrawn`）。
- **呈现 = 投影**：该 kind 的汇总块（`README.md` 标记区）新增「分解树」小节（该 kind 用到 `parent` 时才出现——没有
  分解数据的 kind，汇总页与本机制之前逐字节一致），有直接子条的父行带**子项状态计数**
  （`· 子项 done 2 / todo 1`——「大任务完成多少了」的最短答案，纯投影不新增字段）；
  仓根总账有「分解」列（该 kind 的有效 `parent` 边数，无分解的 kind 显示 `—`）。
  查询台 `node scripts/registry-board.mjs --children=<编号>`（子树递归孙辈，标题行带
  直接子状态分布与递归总数）与 `--parent=<编号>`（父链，从顶层祖先到当前条目）
  是同一数据的另两个出口。
- **新 kind 自动获得**：`parent` 是公共字段，新增 kind 无需任何接线即有分解能力
  （判据档位按该 kind README meta 的形状声明取，默认生效档 = 闭环档、退场档 = `retired`）。

## 2. kind 一览与新增方式

kind **集合**（有哪些、各自答什么问题、编号前缀、住的目录、汇总页）的 owner 是
[`docs/README` 的 `kinds` 表](../README.md "docs/README")——**此处不复述那张表**：
同一份集合写两处就是重复，哪怕第二处只多一列（汇总页那一列已加进原表）。
每 kind 一套的**状态词**，owner 是 [SP-001](../008-spec/001.md) 的状态词表（执行方在代码，那里是人读摘要）。

两类在机制上的分野只有一件事：**文档类在位存放**（正文即条目，编号形状见 README 的编号规范）；
条目类与文档类的**文件名都不带前缀**（主干 = id 去掉前缀与连字符）。目录习惯与状态机复杂度跟着这个分野走，编号规则不按类分化。

「现居目录」是**组织习惯，不是判据**：模块 `README.md` 与 `docs/005-arch/` 下的文档同属 `kind: arch`，
机制不区分系统级与模块级（同一篇文档换目录不必改 kind，但必须改 `id`）。

`adr` 的正文 owner 是 [ADR 索引](../010-adr/README.md "ADR-000-架构决策汇总")（单文档只存身份与状态，索引由 `registry-audit --write` 生成）。

**新增一个 kind = 三件事**：建目录、写该目录 `README.md` 的 meta（前缀 / 标签 / 状态机 /
必填小节——**kind 形状由 meta 自描述，机制代码零改动**）、加回归测试。**不新开脚本、不新开判据码命名空间**；
收录范围是固定的（RG-020），所以**没有「多出一个未登记的 kind 目录」这种态**——目录不参与判定，
未登记的 `.md` 一律按未登记文档判红。

**`adr` 为什么值得单开一个 kind**（而不是塞进 `spec`）：它证明「能用现有 kind 承载就不加
kind」这条判法有**边界**。ADR 状态在实践里有**两个正交维度**——**规范合法性**
（这条决策还算不算数）与**落地进展**（做到哪一步）。`spec` 的状态机装不下第二个维度：
硬塞就只有两条路，一是把「现行（含未完成项）」这类自由文本写进 `status`（违反 RG-004
的词表封闭），二是把「已落地 / 部分实施」也塞成状态词（那 `spec` 的 `retired` 语义立刻
被污染）。所以 `adr` 单开：`status` 管前者（`active` / `superseded` / `withdrawn`），
`impl` 管后者（`planned` / `partial` / `done` / `none`，RG-017）。**判法不是「宁少不多」，
是「一个 kind 只能有一条状态轴」**——超出这条轴的语义必须另开字段（这里）或另开 kind（此处）。

## 3. 状态流转与完成定义

- **状态只写在条目文件**：流转 = 改 front-matter 的 `status`，过程追加进 `## 处理过程`；
  总纲、总账、看板一律不抄状态（职责表在登记上的投影）。
- **完成定义**：task `done` ⇒ `evidence` 非空（提交 / 守卫锚）且 `signal` 清空；
  `wont` ⇒ `reason`；spec `retired` ⇒ `reason`。矩阵由 RG-007 执行。
- **前置闭环（RG-008，全部 kind 同一套，文档类不搞特殊化）**：条目进入「生效中」档
  ⇒ 所有 `deps` 已闭环——task 的 `doing` / `done`，spec / adr / 文档类
  （goal / plan / arch / ref / guide）的 `active`。闭环态按目标 kind 取：
  task = `done`，其余 = `active`。`deps` 指到不存在的编号直接红（RG-006），
  不得成环（RG-006）——**依赖是义务，不是注释**；`draft` / `retired` / `todo`
  不在门槛里（草案可以引草案）。
- **父子档位单调（RG-025，分解树上的状态说真话）**：子条目进入生效档 ⇒ 父条目不得停在
  未生效档；父条目进入退场档 ⇒ 子条目不得停在生效档。中间组合合法（父 `doing` 子 `todo`、
  子 `wont` 父 `doing`）——分解允许部分未动，不允许档位倒挂。档位表与完整语义见 §1.2。
- **看板与条目同序**：待处理列表按拓扑序渲染，前置在前；渲染确定性是 autoWork 的前提。
- **排序提示不是义务**：`task` 的可选 `prio`（`now / next / later`，缺席 = 最低档）只影响
  看板与汇总块的**同层排序**（先拓扑、后 prio、再编号）——`deps` 是义务（事实），
  `prio` 是提示（判断）；不想定级不必硬填，判据不因此判红。
- **文档类的状态只回答「还算不算数」**：`draft` → `active` → `retired`（`retired` ⇒ `reason`，
  由 RG-007 执行）；「做到哪一步」属于 `task`，不压进文档的状态列（同 `adr` 的 status/impl 拆轴）。
  文档类的 `status` 与 `task` / `spec` 的**不同轴**，但同属「状态只写在条目文件」这一条。
- **登记是收录的全部**：新增/搬迁一篇文档 = 写 front-matter + 改 `id`（文档类）+ 跑一次门禁；
  卡片、索引、看板都是由上面自动重算的投影。

## 4. 冲突与优先级（谁说了算）

**优先级只排顺序，不裁决冲突。** 让「高优先级的规则压过低优先级的规则」等于把矛盾合法化：
两条矛盾的规范可以合法并存，且优先级膨胀之后裁决本身又成了新冲突。本仓的裁决分层——
每层都有既有原语，新机制只延伸它们：

| 冲突 | 裁决原语 | 规则 |
|---|---|---|
| 事实 vs 事实 | [职责表](../README.md "docs/README")（一个事实一个 owner） | 两处矛盾 = 一处越界，改引用方，**不投票** |
| 规范 vs 规范 | 状态机 + `supersedes` | 同主题不许两条 `active` 并存：一条 `retired`（`reason` 写明被谁取代）或合并；新规范用 `supersedes` 显式指认取代链（RG-015：目标存在且为 spec、不自指、不成环、不得与自己同为 `active`） |
| 规则 vs 任务 | [SP-014](../008-spec/014.md)（豁免必有清除任务） | 任务**永远压不过规则**：要么改任务，要么登记豁免 + 清除任务 |
| 守卫 vs 守卫 | GW 接线名单 | 一个事实只许一条判据在判；两条守卫判同一件事 = 接线错误 |

优先级的赋值是**判断不是事实**，机制只保证三件事：词表封闭（RG-014）、缺席不判红、
排序确定（先拓扑、后 prio、再编号）。

## 5. 汇总与守卫（四条命令）

| 命令 | 角色 | 何时用 |
|---|---|---|
| `node scripts/registry-audit.mjs` | **守卫**（门禁 GUARDS，RG-001…RG-030） | 改完条目自查；CI 会跑 |
| `node scripts/registry-audit.mjs --write` | 守卫 + 重生成总账与各 kind 汇总块 | 门禁 `60-facts` 自动做，本地一般不用手跑 |

| `node scripts/registry-board.mjs` | **查询台**（`--kind=` `--status=` `--id=` `--children=` `--parent=`） | 想知道「现在要干什么」「某个大任务分解出了什么」时 |

- 判据码全表见 [GATE_CODES.md](../006-ref/GATE_CODES.md)；各码的主题与失效形态见
  [`registry-audit` 文件头](../../scripts/registry-audit.mjs)——本节不抄全表。
- **失效形态与测试策略**：这类守卫唯一的坏死方式是**判定写宽 ⇒ 违规条目照样过、日志一片绿**。
  回归测试 [registry-audit.test.mjs](../../scripts/registry-audit.test.mjs) 对每条判据
  「注入违规必须红、且只红这一条」，反向用例钉「合法条目不误报」，再加本仓 dogfood 断言
  （条目数非零、SP-001 真表等于代码 schema）防「读空即全绿」。

  比没有报告更坏。

## 6. 接管协议与清单（逐篇迁移，一篇一任务）

节奏：**先建机制，迁移另做**。每次接管 = `docs/009-task/` 里的一个任务，
判「要不要混进当前工作」只问 [docs/004-plan/README](012-高阶智能体平台v2.md "PL-012-高阶智能体平台v2") 的那两个问题。

**接管协议**——适用对象不只是任务表：规则、机制（守卫与豁免通道、自动重生成约定）、
散落的决策型表述，凡是「一堆条目汇成一张表 / 一段清单」的人工登记，都走这三步：

1. **新定义**：先在 registry 里立条目——字段齐全、判据可机检。机制不够用
   （缺 kind、缺字段、缺判据）⇒ **先登记一条完善机制的任务**（T-00* 模式），
   定案改机制、同批带回归测试，再回来迁。
2. **验证**：守卫零违规 + 引用方互索不断——文中锚点、编号互引全部改写到位
   （`doc-link` 全绿），并存期间新旧两处必须一致。
3. **删除老定义**：老处收敛为一行指路，与拆散**同一批提交**完成，不留两处半截登记。

**owner 判断前置**：迁的是「登记形态」，不是「事实归属」——先按[职责表](../README.md "docs/README")
问清这条事实的 owner。owner 本身不迁（代码投影、ADR 正文，见「明确不接管」）；
owner 就是人工登记处的才整表迁；台账类先分清哪些行是守卫账本的**投影**
（owner 是守卫源码，不迁）、哪些是人维护的登记（才迁）。

| 现有登记处 | 归属 kind | 接管任务 | 接管后原处只留 |
|---|---|---|---|
| [13 §1 问题登记](../archive/13-质量改进总纲.md)（跨轨状态表） | `task` | **T-002** | 一行指路 |
| [docs/README 纪律地图](../README.md "docs/README")（纪律 × owner × 判据列） | `spec` | **T-003** | 指路 |
| [13 §2.1 豁免登记表](../archive/13-质量改进总纲.md)（豁免通道 × 形态 × 清除任务） | `spec` + `clears` 字段（RG-016，不加 kind） | **T-005** | 指路 |
| [PL-004 §3.1](004-工程落地.md "PL-004-工程落地") 22 步状态台账（先分清守卫投影行） | 状态 → `task`；守卫投影 → `spec`（形态定案见下） | **T-006** | 指路（已定案，见下） |

**台账类的形态定案**（T-005 / T-006 共用的判法，落地过程见 [PL-004 §3.1](004-工程落地.md "PL-004-工程落地")）：
「一堆表格汇成的台账」先按 **owner 判断前置**分行——**守卫账本的投影行**（该表的内容由某个
守卫的常量 / 账本 / 现算结果决定，如死码棘轮、`session/stats` 读数列、CI 断言清单）⇒ 登记为
`spec` 条目，**只固化「这套口径必须成立 + 谁在判」的对账关系**，明细由守卫现算、不复述；
**人维护的状态行**（如表里的 ✅ / 待办）⇒ 登记为 `task` 条目（状态即条目的 `status` 字段）。
两种都**不新开 kind**——`spec` + `task` 已装得下（同 T-005 的「能用现有 kind 承载就不加 kind」）。

**决策类元素的登记形态**（T-004 定案）：决策（「为什么这样设计 + 被否决的方案」）的
**正文 owner 永远是 ADR**（[`docs/010-adr/`](../010-adr/) 单文档，
职责表），registry **不复制决策**。散落决策的接管边界只有两种情况：

- **已定案** ⇒ 在 ADR owner 补条目、原处改链接（原文若带正文，删正文只留指回）；
- **未定案的决策**（如某设计文档的「待确认决策」表）⇒ **原处那张表就是它的登记处**，不另开 `task`：
  设计文档自持一张完整的待确认表是它的职责，拆成指路会破坏文档完整性，而跟踪的增益只剩「别忘了」。
  **只有真要去推进定案时**才登记 `task`（`exit` = 「定案并写 ADR」）。
  判据（可核对）：`task` 表里不应存在「把某设计文档的待确认表改成 ADR 指路」这类**以改文档为 exit** 的条目。

**决策体自身接管**（T-008 定案）：ADR 的**登记形态**（编号 / 状态 / 落地进展 / 取代链）
住 `docs/010-adr/`，与上面的「散落决策」是两件事——前者是 ADR 自己那份手写索引，
后者是别处冒出来的决策。定案：**新开 `adr` kind**（理由见 §2），
**决策正文的 owner 随索引一并迁入 [docs/010-adr/](../010-adr/)**（
见下「明确不接管」）——迁的只是索引这一层登记形态。落地过程见
[`T-008`](../009-task/008.md "T-008")。

**不为决策新开 kind**（同 T-005 / T-006 的「能用现有 kind 承载就不加」）。
落地过程与清点结论见 [`T-004`](../009-task/004.md "T-004")。

**明确不接管**：

- 代码投影生成物（`docs/006-ref/006-当前事实表.md`、GATE_CODES、routes.gen）——owner 是各自 gen 脚本；
- 代码投影生成物之外的 ADR——**已全部接管**：编号 / 状态 / 落地进展 / 域 / 取代链
  与**决策正文**同框在 `docs/010-adr/` 下的单文件条目（每条一个 `ADR-NNN.md`），
  原 `DECISIONS.md` 索引与五个域分册已删除，registry 是唯一真源；散落在非 owner
  文档里的决策型表述只做清点与处置（T-004）。迁移见 [`T-008`](../009-task/008.md "T-008")；
- 一次性报告与归档（`docs/archive/`）——归档不进登记。

## 7. 明确不做

- **不做通用工作流引擎**：没有状态机 DSL、没有条件流转；kind 的差异只落在各自目录
  `README.md` 的 meta 自描述里，判据宁红不漏。
- **不把层级编进编号**：分解走 `parent` 字段，编号保持 `<前缀>-<三位序号>` 平铺——
  层级是投影（分解树小节 / board 查询），不是身份；编进去只会让改名与重排永远昂贵。
- **原表与迁移不拆批**：接管任务的出口是「原处只留指路」，拆散与删除同批完成，
  不留两处半截登记。
- **不手写地址**：文档地址（`docs/...`、`../009-task/008.md`）一律由机制生成与重算，
  手工写的只有编号；门禁一次把全仓已展开的地址校正到今天的位置（见 §1.1），
  所以既没有「改名后满地失效链接」这个态，也不接受「地址写错但能忍」。
- **汇总块不加时间戳、不写「最后更新于」**：确定性是自动重生成的前提。
- **不做守卫军备竞赛**：新增守卫的前提是**证明现有判据抓不到同一个失效**；守卫的守卫、
  为补上一条守卫的误报再叠一条守卫，都不是理由——那是把机制的重量当成了机制的收益。
