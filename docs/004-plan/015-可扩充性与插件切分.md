# PL-015 · 横向扩充与大模块拆分方案

> 三个行表已经落地（能力目录 / 策略目录 / 动作目录），横向扩充的**接入成本已经很低**。
> 剩下的摩擦不在"再加一层抽象"，而在三处**直线代码**：主循环的固定七步、臂的分派、
> 三个巨型函数。本方案只做这三处，不新增机制键、不新增 trait、不新增插件。

## §0 结论先行

1. **加一条策略 = 2 处，都在同一个文件**（`loop_registry.rs`：一个纯函数 + 一行注册），
   core 零改动。这是今天的真实成本，不是目标。
2. **加一个新时机（格）= 6 处 + 1 个调用点**，仍全部在 `plugins/loop` 内，core 零改动。
   成本高的原因不是"缺机制"，是主循环是**固定七步**、格必须提前声明。
3. **加一个臂 = 2 处 + 1 个调用点，且漏掉调用点时没有任何东西会红**——臂变成永不派发的
   死值。这是本方案要修的第一处。
4. **拆分已到插件级的尽头**：`loop` 已是独立插件（无 `route` 臂、无能力行、无常驻任务、
   只 1 条 Mount 行），再切没有判据可用。剩下的只能走**模块级 / 函数级**。
5. 方案两步：**A 驱动器**（把格与臂分派收进一个不动点循环）、**B 阶段拆分**（三个巨型
   函数按处理阶段拆，不按职责拆）。B 可独立开工，A 必须先做完投影收口。

## §1 现行形状：一轮怎么走

### 1.1 四层

| 层 | 落点 | 职责 |
|---|---|---|
| ① 装配 | `session/orchestrator/entry.rs` | 收件箱取批 → 落用户消息 → 装配 `chat_ctx` / `TurnDispatch` → 派发 `loop/<sid>` |
| ② 宿主 | `loop/provider.rs` | 取 `TURN_DISPATCH`（授权三条）→ 建 `LoopSession` → await ③ → 回 `TurnReport` |
| ③ 循环 | `loop/chat_loop.rs` + `chat_loop/{inputs,turn,compose}` | 前步骤 + **固定七步** + 唯一收尾 `finish_turn` |
| ④ 单轮执行 | `loop/turn_exec.rs` → `turn_runner.rs` → `tools/tool_executor.rs` | LLM 调用 + 工具轮 + 工具批处理 |

循环只能由 `return finish_turn(...)` 离开。四层结构、四个收口点的完整说明见
[AR-015-core-loop](../../symbio/src/plugins/session/docs/015-core-loop.md "AR-015-core-loop")。

### 1.2 三个行表（形状一份，目录三份）

| 目录 | 位置 | 行形状 | 裁决规则 | 消费方 |
|---|---|---|---|---|
| 能力目录 | `symbio_core::capability` | `{name, payload}`，六族 | `put` / `get` / `list(kind)` | ≥2（模型工具列表、VDFS、设置页、统计） |
| 策略目录 | `plugins/loop/loop_registry.rs` | `{name, site, prio, 纯判据}` | 格内 `(prio, name)` 升序，先命中者胜 | 1（环） |
| 动作目录 | `plugins/session/plugin/run_actions.rs` | `{op, 处理函数}` | 表内即闭集，装配期冻结 | 2（loop 派发、授权判据） |

三张表**不共类型**，但共一条形状纪律：一行 = 一个纯判据或一个处理函数 + 一份声明数据，
表本身不写分支。这条纪律的两次独立实例化见 [ADR-089](../010-adr/089.md "ADR-089")
（按消费方分目录）与 [ADR-094](../010-adr/094.md "ADR-094")（闭集即行表）。

### 1.3 一条事实轨

`State` 是 Store 的投影，`append` 是唯一交换点。策略行的判据读的是**投影**，不是环的私有
字段——这是"策略可以纯、可以回放"的前提（PL-014 §4 机制 1 的可靠性前提）。

### 1.4 五个问表点

主循环的七步里，有五处向策略目录提问：

| 问表点 | 格 | 期待的臂 |
|---|---|---|
| `chat_loop.rs`（步骤 2b） | `TurnHead` | `Decide` |
| `chat_loop/progress.rs`（轮边界回调） | `RoundBoundary` | `Report` |
| `chat_loop/inputs.rs`（步骤 3 ①） | `Compress` | `Compress` |
| `chat_loop/inputs.rs`（步骤 3 ③） | `TurnPrepare` | `Recall` |
| `turn_exec.rs`（快路） | `Reflex` | `Reflex` |

五处各构造一次状态、各问一次表、各按 `capsule()` 比较一次。**这就是"格"存在于类型里的
原因**：调用点知道自己在第几步，表不知道。

## §2 横向扩充的现状账

判据只有一条：**加一样东西要改几处，其中几处在 core，漏改时谁会红。**

| 扩充对象 | 落点 | 改几处 | 其中 core | 漏改时谁红 |
|---|---|---|---|---|
| 一个 LLM 工具 | 实现 `Capability` + `traverse` 收集 | 1 个文件 | 0 | 模型看不见它（e2e 兜） |
| 一个模型服务 / 提示词 / 挂载 / 选项 / 可配置 | 行上 `put` | 1 处 | 0 | 消费方读不到（各自用例） |
| 一个插件 | 目录 + `PLUGIN.yml` + `ASSEMBLY_SUB_AGENT_PLUGINS` 一行 | 3 处 | 0（不涨 CS-001 三格） | 不在名册 ⇒ 不装配 |
| **一条同格策略** | `loop_registry.rs`：一个 `fn` + 一行 `Row` | **2 处** | **0** | 无人：行在表里就生效 |
| **一条新格策略（新时机）** | `Site` 变体 · `Site::ALL` · `Site::name` · `LoopState` 变体 · `site()` · 构造器 | **6 处** + 1 调用点 | **0** | 漏 `ALL` ⇒ 启动期告警 + CI 红 |
| **一条新臂** | `Capsule` 变体 · `name()` · 调用点比较 | **2 处** + 1 调用点 | **0** | **无人**（臂永不派发，见 §4.2） |
| 一个 loop→session 动作 | core 纯值常量 · `RUN_OPS` 行 · 处理函数 | **3 处** | 1（`&'static str`） | 漏行 ⇒ 授权 `Forbidden` |
| 一个新能力族（第七族） | core 两个 enum 各加一个变体 + 生产点 | 3 处 | 3 | 无生产点 ⇒ ADR 门 |
| 一个新 `Verb` / `ActorSpec` 字段 / 参数键 | 封闭集 | —— | —— | 编译错误 / ADR 门 |

三格读数（CS-001 冻结值，只降不升）：`pub trait` **16**、`fn` 成员 **56**、默认体 **18**。

**这张表说明两件事**：

- **core 已经不是瓶颈**。九行里只有一行真正改 core，而且改的是一个字符串常量；其余
  全部落在插件内。所谓"必须改 `symbio_core` 才能扩充"在今天是**不成立**的。
- **瓶颈是"格"和"臂"两处**，都因为主循环是固定七步：格要提前声明、臂要在调用点分派。

## §3 三条已裁决的边界（不再讨论）

| 裁决 | 内容 | 违反要付什么 |

## §4 三处真摩擦

### 4.1 时机是类型，不是数据

加一格要改 6 处（§2 第 5 行）。这不是"少写了个注册口"，而是**调用点知道自己在第几步**：

```text
chat_loop 七步直线代码
  步骤 2b  → 构造 TurnHead  → decide → 比较 Decide
  步骤 3 ① → 构造 Compress  → decide → 比较 Compress
  ...
```

格的语义（"这一问发生在什么时候"）由**代码位置**承载，表只承载"这一格归谁"。于是：

- 加时机 = 同时改类型（`Site` / `LoopState`）与调用点（在七步里插一段）；
- 两个时机若在同一位置可竞争（例如"记忆召回"与"技能路由"共用 `TurnPrepare`），
  拆成两行需要"这一步做完了吗"这个簿记量——它在直线代码里只能靠代码位置隐含，
  所以 `policy.recall` 只能是一个胶囊带三件事。

这就是 `policy.recall` 至今是三合一的**结构性**原因，不是偷懒。

### 4.2 臂的分派散在调用点，漏改无声

`Capsule` 是闭集枚举（加值必须改枚举，`name()` 会编译错误），但**分派不在枚举上**：

```text
if builtin().decide(&state).capsule() == Some(Capsule::Recall) { ... }
```

五个调用点各比较一次。加一个 `Capsule` 变体、写好 `name()`、忘掉调用点比较——
编译通过、运行通过、**这条臂永远不派发**。按本仓自己的判据（"拼错 / 漏改时谁会红"），
这一处的答案是"没人会红"，它是本方案里唯一一个**静默失效**的扩充点。

### 4.3 三个巨型函数

`symbio/src/plugins` 下 `session` + `loop` 合计 3.2 万行（不含测试），前四名：

| 文件 | 行数 | 其中最大的函数 | 行数 |
|---|---|---|---|
| `loop/turn_runner.rs` | 2004 | `run_with_tools` | 784 |
| `loop/turn_exec.rs` | 1776 | `execute_turn` | 716 |
| `loop/tools/tool_executor.rs` | 1508 | `process_tool_calls_async` | 714 |
| `loop/context/pipeline.rs` | 987 | `compress_with_snapshot_core` | 150 |

三个函数都是**顺序过程**（准备输入 → 逐条处理 → 收口），不是"多个职责挤在一起"。
按职责拆会把一条线性流程切成互相传参的碎片；按**阶段**拆才是它们本来的形状。
拆分的收益不是行数好看，而是：每个阶段可以单独被判据钉住（"这一段错了谁会红"）。

## §5 方案

### 动作 A：驱动器——让"时机"消失

**目标形状**（PL-014 §4 机制 1）：

```rust
loop {
    let state = project(&facts, &config);          // 唯一状态来源
    match decide(&state, registry) {               // 全表问一次，先命中者胜
        Verdict::Hit(hit) => execute(hit, ...).await,
        Verdict::Declined { .. } => break,          // 无行认领 ⇒ 本轮该做的都做完了
        Verdict::Unmanned { site } => halt(site),   // 规则缺口必须可见
    }
}
```

分三步，每步一个提交：

**A1 投影收口**：五个构造器合并成**一个** `project(...)`。仍按格分形（`LoopState` 保持
枚举），但入口只有一个。这一步不改语义，只把"五处各拼一次"变成"一处拼、五处取"。

**A2 判据补全**：每条策略行的判据从**半判据**变成**全判据**——今天 `policy_report` 可以
假设"我只在轮边界被问到"，drive 之后它必须自己回答"现在是不是轮边界"。这是本方案
**唯一的语义工作量**，也是"时机变成数据"的实质：时机不再是类型，是判据的一个合取项。

**A3 不动点循环**：七步直线代码 → `loop { project → decide → execute }`。臂的分派收成
**一个** `match`，编译器强制穷尽——§4.2 的静默失效随之消失。`Site` 与 `prio` 的格内
唯一性随 A2 完成退场（行自带完整判据，跨行竞争由 `prio` 全局定序）。

**代价（诚实划界）**：

- 每次迭代扫全表（今天只扫本格）。表是 `fn` 指针数组，行数在 10 量级，代价可忽略；
  但**"行只读本格字段"从编译期性质退回判据期性质**——这是真实的损失，靠 A2 的
  全判据 + 每行的用例补，不能靠自觉。
- `execute` 变成一处 `match` 后，单臂的实现体仍散在各自模块（这是对的：臂是环的指令集，
  不是环的实现）。

**判据**：e2e 全量逐条不变 + 事件批序逐项相等 + 五个格各自的行为用例在"只问一行"
与"问全表"两种表下结果相同 + 每个 `Capsule` 变体至少被一条行产出（新用例，
补上 §4.2 缺的那条）。

**熔断线**：单批结构性改动 >300 行 = 抽象错了，退回（PL-014 §5 的既有纪律）。

### 动作 B：三个巨型函数按阶段拆

| 函数 | 阶段切点 | 落点 |
|---|---|---|
| `run_with_tools` 784 | ① 轮首准备 ② 请求 / 流式 ③ 工具批派发 ④ 轮边界判定 ⑤ 收束 | `turn_runner/{prepare,stream,batch,boundary,settle}.rs` |
| `execute_turn` 716 | ① 装配（提示词 / 工具 / 视图）② 调用 ③ 结局归类 ④ 落格 | `turn_exec/{assemble,call,outcome,persist}.rs` |
| `process_tool_calls_async` 714 | ① 批首闸门读数 ② 逐条执行 ③ 未执行收口 | `tools/dispatch/{gates,batch,unfinished}.rs` |

三条纪律：

1. **按阶段切，不按职责切**——切完每一段仍是一条顺序流程的一段，段间只传值。
2. **不改行为**：拆分批次与语义批次分开提交。拆分批次里出现任何 `if` 条件变化 = 切错了。
3. **每段一条判据**：切出来的段若说不出"这段错了谁会红"，说明切点选在流程中间而不是
   阶段边界。

**判据**：拆分前后事件批序逐项相等；lib 用例数与断言数不减；单文件回到 800 行以内。

### 动作 C（正交，不排期）：注册即事实

PL-014 步骤 4 收尾注留下的那条：注册行落为事实（安装 = append、卸载 = 墓碑），
`Registry` trait 随之消失、core 三格再降一格。它与本方案无依赖关系，**不要混做**——
它改的是能力目录的**持久化方式**，本方案改的是策略目录与环的形状。

## §6 下界：哪些永远不为 0

| 下界 | 为什么 |
|---|---|
| 新的副作用出口（loop→session 动作） | 跨插件墙的地址面必须有词表；词表在 core 是**纯值**，不是机制 |
| 新能力族的载荷变体 | 行载荷是 `enum`，新族 = 新变体 + 生产点；这是"一表装六族"的定义成本 |
| 新的封闭集值（`Verb` / `ActorSpec` 字段 / 参数键） | 封闭集是刻意的：开放它等于让机制面被数据改写 |
| 过程型时机（在途工具、流式 token） | 它们不是"状态转移"，是"过程本身"；格子化要求先有事实，而它们尚未成为事实 |

## §7 不做清单

| 不做 | 理由 |
|---|---|
| 把策略行合进 core 能力表 | ADR-089 已裁决；单消费方占公共面 |
| 给 `Registry` 加第四个方法 | 三方法是 AR-025 的收敛结果；加方法就是十六方法糜烂的来路 |
| 谓词 DSL / 脚本热加载策略 | 判据要能回放、能 diff、能被编译器检查；字符串谓词三条全丢 |
| 继续切插件 | 判据耗尽：`loop` 无 `route` 臂、无能力行、无常驻任务、只 1 条 Mount 行 |
| 按职责拆三个巨型函数 | 它们是顺序过程；按职责拆会产生互相传参的碎片 |
| 为了对称给 gate 脚本造统一 trait | 往 core 灌只为对称而存在的抽象，撞 CS-001（T-170 已核验否决） |

## §8 施工顺序

| 批 | 内容 | 前置 | 判据 |
|---|---|---|---|
| B1 | `process_tool_calls_async` 三段拆分 | 无 | 批序相等、单文件 <800 |
| B2 | `execute_turn` 四段拆分 | B1（同族手法先在小文件验一遍） | 同上 |
| B3 | `run_with_tools` 五段拆分 | B2 | 同上 |
| A1 | 五构造器 → 一个 `project` | 无（可与 B 并行） | 五格行为用例逐条不变 |
| A2 | 每条策略行补全判据 | A1 | 单行表与全表两种问法结果相同 |
| A3 | 七步 → 不动点循环 | A2 | 批序相等 + 每臂有产出用例 |

顺序约束只有一条：**A1 必须早于 A3**。否则五个构造器会被原样搬进 `drive` 的循环体，
把"直线代码的过渡形态"变成"循环里的过渡形态"，形状没变、代价更高。

## §9 登记义务

1. A2 的"半判据 → 全判据"是一次**语义收窄**，落地时若发现某行的判据无法脱离格表达，
   按 PL-014 §0 走 ADR，不改目标形状。
2. A3 若导致"行只读本格字段"的用例必须删除，删除理由进 ADR（这是编译期性质换
   判据期性质的账）。
3. B 系列每批一个提交，拆分与语义分开；任何一批超 300 行结构性改动即退回。
4. 本方案不新增机制键、不新增 trait、不新增插件 id；若施工中出现其中任何一项，
   说明抽象选错了，退回而不是登记。
