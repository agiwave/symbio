# PL-016 · 义务环

> **一句话**：一个会话收事实、算欠账、还债、再收事实。**没有别的。**
>
> 本方案是 [PL-014 §2.1](014-单环一表收敛.md "PL-014-单环一表收敛") 那句终点语义的直接实现，并把它的
> **两类产出收敛成一类**——裁决见 [ADR-114](../010-adr/114.md)。
> 它改的是**终点形状**，不是**施工路径**；PL-014 的六步路径与熔断线继续有效。

## §0 结论先行

1. **调度单元从 `Step` 换成「债」。** `owed` 返回**全量**欠账，`drive` 取最小的一笔。
   现状的短路选一个（`decide -> Option<Capsule>`，PL-014 目标词汇是 `Option<Step>`，尚未走到）退役。
2. **债只有一种形状**，差异全落在 `by` 一个字段上：`Some(名字)` 就调执行体，
   `None` 就恒 `blocked`、永不选中。**引擎对 `by` 只有一个动作，没有分支。**
3. **对外请求落为事实。** `request{port}` 进日志，"意图"这第二类产出消失；
   派发由一行债承担（`before: sent`），`sent` 由引擎写。
4. **`Wait` 与 `Ask` 折叠**——这两条是 PL-014 自己写下的自认（§2.1 折叠、§3 非极小点），
   本方案兑现它们。
5. **三处前置必须先补齐**（`produced_by` 不悬空 / 拒绝落事实 / 停机原因）。三处的实况
   与初稿说法**不同**（前两处不是"没有"，是"有但不完整"），核对结果见 §4。

## §2 目标形状

### 2.1 四步

```
① 收到事实  →  追加进日志
② 算欠账    →  从日志算出"还欠什么"，取最小的一笔
③ 运行它    →  交给一个执行体，它交回若干事实
④ 追加      →  回到 ②
```

④ 出现两次：填了 `before` 的行在运行前先落一条标记（`sent`），交回后再落一批。

```rust
impl Session {
    fn on_event(&mut self, e: Fact) {          // ①
        self.log.append(e);
        self.drive();
    }
    fn drive(&mut self) {
        while let Some(d) = self.min_debt() {                 // ② 取最小可还的债
            if let Some(k) = d.decl.before {                  // ④a 前置标记
                self.log.append(Fact::envelope(k, &d.key));
            }
            let facts = self.actors.run(d.decl.by, &d);        // ③ 运行，交回事实
            self.log.append_all(facts);                       // ④b
        }
    }
}
```

**没有别的调度代码。** 七个词里"优先"与"前置标记"就落在这两处。

### 2.2 债

> **一笔债 = 一条 liveness 性质 `owes ⇒ ◇ until` 的当前违例，外加"谁该还"。**

```
open(d, key)      := ∃ f ⊨ d.owes  ∧ key = bind(f) ∧ ¬∃ g ⊨ d.until ∧ key(g) = key
blocked(d, key)   := d.by = None  ∨  ∃ h ⊨ d.unless ∧ key(h) = key
actionable(d,key) := open ∧ ¬blocked
```

**`by` 只有两种取值，引擎只有一个动作：**

| `by` | 引擎做什么 | 谁负责不阻塞 |
|---|---|---|
| `Some(名字)` | `actors.run(名字, 债)`，追加返回的事实 | **那个执行体自己** |
| `None` | **什么都不做**——恒 blocked，永不选中 | — |

"决策债 / 搬运债 / 等待债"是**用法**，不是机制：`by` 指向纯函数叫决策债，
指向 `courier` 叫搬运债，是 `None` 叫等待债。**三者在 `drive` 里走同一行代码。**
同步与异步是执行体的实现细节，**不在协议里**，引擎也没有能力管（代价见 §7.2）。

### 2.3 表与两行模板

一行 = 一笔可能欠的账：

```rust
struct Decl {
    name:   &'static str,
    owes:   Pattern,
    until:  &'static [Pattern],                    // 任一命中即视为还清
    unless: &'static [Pattern],                    // 任一命中即挂起
    expand: Option<(&'static str, &'static str)>,  // (列表字段, 元素键字段)
    before: Option<FactKind>,                      // 运行前先追加一条此类型的事实
    by:     Option<&'static str>,                  // None ⇒ 无执行体，恒 blocked
    prio:   u8,
}
```

每个端口在表里固定占两行。**模板里没有因端口而异的部分**：

```
行 A  dispatch-<port>   owes:   request(port=<port>)
                        until:  sent(port=<port>) | failed(port=<port>)
                        before: sent
                        by:     courier

行 B  await-<port>      owes:   sent(port=<port>)
                        until:  response(port=<port>) | failed(port=<port>)
                        by:     None            ← 全部差异就在这个 None
```

`by = None` 那一行**对 `drive` 是透明的**（恒 blocked，永不选中）。它存在的理由不是
"它是一类债"，而是让 `open ≠ ∅ ∧ actionable = ∅` 这个状态可表达——也就是让
"在等"与"没事"可区分。**它是"这笔账不由引擎执行"的唯一声明位。**

### 2.4 四个协议名 + 端口

| 名字 | 含义 | 谁写 |
|---|---|---|
| `request{port}` | 该调了 | 决策者 |
| `sent{port}` | 已经派出去了 | 引擎（`before`） |
| `response{port}` | 回来了 | 搬运者 |
| `failed{port}` | 没成功 | 搬运者 |

**这四个名字是新增的，不是替换。** 现网 30 个事实名（`memory.recalled` /
`task.rework_created` / `chat.assistant.final` / `commitment.broken` …）**一个不动**——
它们是业务词汇，有各自真实的读方（385 处引用、24 处前端）。把它们压成 4 个协议名
不是简化，是**销毁语义**。

**真正的变化是补上一类从来不存在的事实**：今天"我要调模型""我要调工具"**不落日志**——
它们正是 PL-014 §2.1 里"意图"那一类产出。所以本方案不是"减少事件名"，
而是"把一直只活在内存里的那一类请求，变成可回放的事实"。

端口（模型 / 工具 / 时钟 / 存储）**全部同构**：子智能体是
`request{port:tool, tool:"agent_run"}`——"模型调用"可以是"工具调用"的一个取值，
所以框架层没有理由把它们分成两类。

**`port` 放哪儿，留给 T-224 裁决**（本方案只要求它可被 `Pattern` 匹配）。倾向**载荷**：
只有这 4 个名字有端口，放信封会让"每条事实都有端口"变成一句 30/34 情况下为假的话。
PL-016 初稿写"端口是信封字段"是**没想清楚就落笔**，此处改回待裁决。

## §3 引擎与插件契约

### 3.1 引擎只认识七个词

**事实 · 模式 · 键 · 视图 · 执行体 · 优先 · 前置标记。**

没有 `model`、没有 `tool`、没有 `turn`、没有 `user`、没有 `prompt`。**一个业务词都没有。**
插件能往这七个词里填内容，但**不能加第八个**。

### 3.2 插件交什么：五个注册口

```rust
impl Builder {
    fn fact(&mut self, d: FactDecl);                          // 事实声明
    fn view(&mut self, d: ViewDecl);                          // 视图声明
    fn actor(&mut self, d: ActorDecl);                        // 执行体
    fn adapter(&mut self, port: &'static str, f: AdapterFn);  // 端口适配器
    fn row(&mut self, d: Decl);                               // 表行
    fn seal(self) -> Result<Arc<Frozen>, Vec<CheckError>>;    // 冻结
}
```

`ActorDecl` 的四个字段不是装饰——裸函数也能跑，但**三样静态检查会全部失效**：

| 字段 | 谁用它 | 缺了会怎样 |
|---|---|---|
| `mode` | 令牌闸门（§3.4） | 分不清"反射档不许调模型" |
| `reads` | 装载期检查视图存在 | 视图名打错 ⇒ 运行期静默返回空 |
| `writes` | 写入封闭 / 死事实名检查 | 查不出"这个事实名没有任何人会产出" |

### 3.3 装载：三个时点

| 时点 | 谁在做 | 发生什么 |
|---|---|---|
| 编译期 | `linkme` / `inventory` | 收集插件实现，形成清单 |
| 装载期 | `Builder` | 填五张注册表 |
| 冻结 | `seal` | 跑五道检查；通过则产出不可变 `Arc<Frozen>` |

**"运行期不能注册"不是纪律，是类型**：`Session` 只拿得到 `Arc<Frozen>`，没有可变注册口。

### 3.4 装载期五道检查

| # | 检查 | 查什么 | 缺了会怎样 |
|---|---|---|---|
| 1 | 依赖图无环 | "谁还清谁"的保守图 | 类型级互相等待 ⇒ 死锁 |
| 2 | **每行收口** | `owes` 的每种应答至少命中一次 `until`/`unless` | 运行期死循环 |
| 3 | 字段都在声明里 | 模式与 `ActorDecl.reads` 引用的名字 ∈ 声明 | 运行期取不到字段 |
| 4 | 相交行对 | 可能同时命中的行对 | 静默遮蔽（静态不可判，只报告） |
| 5 | 写入封闭（可选） | 执行体实际写入 ⊆ `ActorDecl.writes` | 决策者伪造 `response` |

第 2 条比"每个事实名有归宿"更硬：后者只查名字**有没有被用到**，不查**这一行是不是
这笔债的 `until`**。名字有归宿但归错行，照样死循环。

**装载失败即拒绝启动，不许部分成功。**

## §4 三处前置缺口与补法

**这三处不补齐，形状不能换。** 补法都刻意做轻——不新增机制键。

### 4.1 溯源：边已经有了，缺的是「不悬空」

**缺口**（核对后的实况，与本方案初稿的说法不同）：信封**已经有**这条边——
`Event.produced_by: Option<u64>`（`symbio_core/event/mod.rs`），20+ 个构造点已经在填，
`invariants::provenance_violation` 也已经在查「断言类 / 记忆类 / 收束类事件必须非空」。
**真正的缺口是另外三处**：

| # | 缺口 | 后果 |
|---|---|---|
| 1 | 只查「有没有」，不查「指向谁」 | `produced_by: Some(999)` 指向一条不存在的事件，照样绿 |
| 2 | 名字两套 | 代码叫 `produced_by`，本方案初稿写 `caused_by`——两个名字 = 后来者查两遍 |
| 3 | 判据按事件种类硬枚举 | `needs_provenance` 里列了三种 kind，加一类就要改这个函数 |

**补法**：

1. **口径统一到 `produced_by`**：代码已有、构造点已铺开、不变量已在用。
   本方案的 `caused_by` 一律改称 `produced_by`，**不引入第二个名字**。
2. **加「不悬空且更小」**：`produced_by < seq`，且指向的 seq 确实在同一条日志里。
   前一半几乎免费（`produced_by` 只能取自一条已入库事件的 seq，而 seq 严格单调）；
   后一半要一条检查——回放时按 seq 建索引，落一条违规。
3. **派生图无环是免费的**：seq 严格单调 ⇒ 边只能从高指向低 ⇒ 天然 DAG
   （PL-001 §13.3 已论证过），**不另加无环检查**。

**为什么不反向改名成 `caused_by`**：20+ 构造点、一条不变量、两处审计都在用 `produced_by`。
改名是纯机械 diff、零语义收益——**该动的是还没落地的新文档，不是已落地的代码**。

**为什么第 3 条（按种类枚举）不在本批修**：它问的是「哪些事件算声称」，属 I2 的判据范围，
与本方案的形状无关；登记进 §7.3 不做清单。

### 4.2 权限：否定要落成事实，判定位置不动

**缺口**（核对后的实况，与本方案初稿的说法不同）：授权**不是**「`drive` 在 `run` 前查一次」。
`symbio_core/authz.rs` 有一张 fail-closed 三层的 `PermissionMatrix`：写侧在
`turn_runner::closure_granted` 按**种类**分两臂判（`can_reply` / `can_produce_artifact`），
读侧在 `stats` 判 `can_see`。**判定本身是健全的**——缺的不是判定，是**否定的表达**：

> 拒绝 = 拒绝入格 ⇒ 该轮**留在未收束态**。这是用「状态缺失」表达否定：
> 事后无法回答「谁、何时、因为什么被拒」，回放也重现不出这次拒绝。

**这违反的是 I1（单通道），不是权限语义。** 既然一切状态变更只经事实源，
那么「被拒绝」这个状态变更也必须是一条事实。现状是全项目唯一一处
**用「没写」表达「不许写」**的地方。

**补法**：`denied{key, why}` 落成事实；矩阵与判定位置**一个字不动**。

```
行  authorize   owes:   request(port) ∧ ¬permitted(key)
                until:  permitted(key) | denied(key)
                by:     Authorizer
                prio:   0                 ← 必须早于 dispatch
```

| 好处 | 说明 |
|---|---|
| 引擎不认识权限 | 权限是表里的一行，不是引擎的第八个词 |
| 拒绝可审计 | `denied` 是事实，不是日志字符串 |
| 与「写入封闭」分工清楚 | 装载期第 5 条管「形状」，这一行管「资格」 |

**但本批只做前半**（`denied` 事实 + 写侧落它）；后半（把判定搬成表行）**要等表存在**
（T-222 之后）——现在没有 `Decl`，搬过去只能造一个只有一行的假表。

**为什么不做成 `drive` 里的前置检查**：那会让引擎认识「授权」这个业务概念，
且拒绝路径变成异常分支——义务环里没有异常分支，只有事实。

**这条仍可能推翻自己**：如果授权必须按「主体 × 能力 × 资源」三维判而 `Pattern` 表达不了，
权限就得升成引擎维度，§3.1 的「七个词」要改。**所以它排在形状替换之前**（T-219 先于 T-222）。

### 4.3 停机原因：统一到 `turn.closed{reason}`，不新增载体

**缺口**：PL-014 §3 规则 f/g 要求 `Halt` 必须落事实，否则重启后无从知道为何停；
并区分策略终止 / 自然完结 / 兜底上界三种。义务环里没有 `Halt` 这个值。

**补法**：**不新增机制，把 `reason` 定为必填。**

| 终止 | 谁写 | 载体 |
|---|---|---|
| 业务判定终止 | 业务行 | `turn.closed{reason}` |
| 自然完结 | 业务行 | 同上 |
| 步数上界 | 引擎 | `turn.closed{exhausted}` |
| 规则缺口 | **不存在** | 装载期第 2 条已消除 |

**关键**：义务环里"规则缺口"不是运行期状态——`owes` 只有 `until` 一个去处，
装载期"每行收口"保证每种应答都有归宿。

**这里要说准，别把它算成新功劳**：现网的 `Verdict` 已经分了三值
（`Hit` / `Declined` / `Unmanned`），`Unmanned` 由 CI 的 `every_site_is_manned` 拦下——
**"本格没人值守"这个缺口今天已经可见**，不靠引擎分支。义务环加的是更硬的一档：
`every_site_is_manned` 只查"这一格有行"，不查"这一行的 `owes` 有没有归宿"。
**有行但归错行，照样死循环。** "每行收口"（§3.4 第 2 条）补的就是这一档。

**检查**：审计断言 `turn.closed` 的 `reason` 非空；缺则红。

## §5 施工路径

八步，每步一个提交，回退单位 = 提交。**前三步是前置补齐，第四步才换形状。**

| 步 | 内容 | 任务 | 前置 |
|:-:|---|---|---|
| 1 | 本方案与 ADR-114 定稿；PL-014 §2.1/§3 加指路 | T-217 | — |
| 2 | `produced_by` 不悬空检查 + 口径统一（不新增字段） | T-218 | 1 |
| 3 | `denied` 事实：拒绝从「没写」变成「写了」 | T-219 | 1 |
| 4 | `turn.closed.reason` 必填 + 审计断言 | T-220 | 1 |
| 5 | `FactDecl` 声明层：`owed` 里零业务字符串 | T-221 | 2 |
| 6 | 行从**函数**变**数据**（`Decl` + `Pattern`）；`decide` → `owed` 返回全量欠账，`drive` 取最小 | T-222 | 3·4·5 |
| 7 | 两行模板 + `sent` 前置标记；`Wait`/`Ask` 折叠 | T-223 | 6 |
| 8 | 端口调用落成 4 个协议名（**新增，不替换业务事实名**）+ 判据门禁 | T-224 | 7 |

**第 6 步是唯一的结构性改动，也是全案最容易被低估的一步。** 现行控制面
（`plugins/loop/loop_registry.rs`）的每一行是 `fn(&LoopState) -> Option<Capsule>`——
**行是代码**；本方案的行是 `Decl`，**行是数据**。所以第 6 步不是"把返回类型从
`Option<Capsule>` 换成 `Option<Debt>`"，而是**把「判断」从函数体搬进表里**：
需要 `Pattern`（模式语言）+ 视图（替代那个手写的五变体 `LoopState`）。
`Option<Step>` 是 PL-014 的目标词汇，现网还没走到那一步（只落了 `Act` 的载荷 `Capsule`）。

熔断线沿用 PL-014 §5 步 1 的口径：**结构性改动 > 300 行 = 抽象错了，退回**；
语义产出物（映射表 / 判据 / 对拍）不计入。

**为什么前三步先做**：只有步 3（权限）是真正"不做会返工"的——它可能推翻「七个词」。
步 2 与步 4 独立于形状（不悬空检查、`reason` 必填都与表无关），现在做的理由只是
**成本最低**：`produced_by` 的构造点刚铺开、`turn.closed` 的产生点还只有四处，
形状一换，这些点要跟着协议名一起再改一遍。

## §6 判据

全部可执行，**零新增机制键**。

| # | 判据 | 检查方式 |
|:-:|---|---|
| 1 | 加一个端口 = 3 条 `FactDecl` + 1 个适配器 + 2 行，**`drive` 与 `owed` 源码 diff = 0** | 源码级断言（本方案相对 PL-001「机制键守恒」的等价物） |
| 2 | 表里零代码 | 类型上：模式只有格子 / 名字 / 绑定 / 比较 |
| 3 | 视图互不可见 | 类型上：`eval` 只接 `&[Fact]` |
| 4 | 依赖图无环；相交行对被报告 | 装载期 |
| 5 | 每行收口 | 装载期 |
| 6 | 字段都在声明里 | 装载期 |
| 7 | **清空整张表 ⇒ 系统仍完整**（`owed = ∅` ⇒ 永不前进） | 空表试金石 |
| 8 | 事实的任意前缀都合法 | 拆批前先过粒度判据 |
| 9 | `produced_by` 不悬空且更小 | 装载期 + 审计 |
| 10 | `turn.closed.reason` 非空 | 审计断言 |
| 11 | **每个被声明的事实名都有归宿**（某行以它为 `owes` 或 `until`） | 装载期（接住现网 `Verdict::Unmanned` 的可观测性） |

判据 5 与判据 11 是两档，别混：**5 问"这一行的 `owes` 有没有去处"，11 问"这个事实名有没有人管"。**
前者防死循环，后者防"拼错的名字静默永不被消费"。现网 `every_site_is_manned` 只做到了 11 的更弱版。

判据 1 是本方案最硬的一条：它不是"机制键数不变"，是**这两段代码的字节不变**。

## §7 诚实标注与代价

### 7.1 这不是「更好」的证明

用 PL-014 §7 的 17 场景纸面推演（**未实测**）：**平 11 · 强 3 · 弱 2**。

强 3（SC-004 并发 / SC-007 打断 / SC-017 定时）恰好是 PL-014 交叉验证时最费力的三个发现
（F1 集合、F3 唤醒源）——本形状不需要"发现"，因为形状本来就覆盖。
弱 2（SC-003 返工 / SC-005 恢复）都落在"**事实之间的边不可信**"上：
SC-003 靠业务字段关联返工点，SC-005 靠业务事实推断"为何停"。**注意不是"边缺失"**——
边是有的（`produced_by`），只是不查悬空、也不写停因，所以推演时判了弱。

**性质**：用形状纯度换三处统一，代价是两处可审计性。那两处必须靠补齐，不能靠"更纯"糊过去。

**一个诚实的限定**：这份 17 场景推演是在 §4 那四处核对**之前**做的。
四处核对改变了步骤 2 / 3 / 4 / 8 的**成本**（都比初稿轻），但没有改变形状本身，
所以"平 11 · 强 3 · 弱 2"的判定仍然有效——**它比的是形状，不是工时**。

### 7.2 代价（全部已知）

1. **`drive` 的正确性依赖执行体不阻塞**。引擎对 `run` 只有一个约定：它返回事实。
   某个适配器同步等 30 秒，整个环就卡 30 秒，**引擎没有任何防线**——也不能有。
   "引擎不区分同步异步"的代价就是"引擎不保证异步"。
2. **每条搬运路径多一条事实**（`sent`）。换来"在途"进日志、崩溃可判别。
3. **`prio` 是唯一手写数字**，只在"同时欠多笔"时起作用；DAG 拓扑序可派生。
4. **视图求值成本**：`owed` 每轮对 `View` 原子求值，`memo` 只在单次调用内有效。
5. **搬运者 at-least-once**：崩溃重启可能重复一次调用，幂等键是债的 `key`。
6. **视图是协议的一部分**：改视图逻辑会改变历史 prompt 的重建结果（`view_ver`）。
7. **插件组合有静默停摆风险**：停用插件 A 的行后，依赖 A 产出的行永久停在"等"，
   不报错。只在声明了 `writes` 时查得出。

### 7.3 明确不做

- 不做"一切皆事件源"（把端口塞进日志）：审批与流式的延迟语义会劣化。
- 不承诺 L2 级重执行一致（PL-001 §11 的划界不变）。
- 不在表里放代码（复杂条件走视图或执行体）。
- 不让债跨主体可见。
- 不为"统一"把动态注册搬进运行期。
- **不改 `produced_by` 这个名字**，也不把 I2 的「按事件种类枚举」改成按声明判定——
  前者是零语义收益的机械 diff，后者是 I2 的判据范围问题，两者都只登记不动手。
- **不把 `PermissionMatrix` 搬进表里**（§4.2 后半）：判定位置不动，本方案只补否定的表达。
