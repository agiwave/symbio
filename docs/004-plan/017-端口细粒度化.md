# PL-017 · 端口细粒度化

> **一句话**：PL-016 让控制面变成债环，但 `turn` 执行体内部还是旧的
> `模型 → 工具批次 → 模型` 循环。本方案把这个内环拆成债，让每一次模型 / 工具调用
> 都成为可调度、可取消、可恢复的事实。

## §0 结论先行

1. **PL-016 的粗端口是第一步，不是终点。** `turn` 端口让"一轮"进了日志；
   单次模型 / 工具调用仍在执行体内部，崩溃只能重放整轮。
2. **内环倒置 = 三组行**：模型请求、工具批次、轮收束。三组行复用 PL-016 的
   `request` / `sent` / `response` / `failed` / `retry` 协议名，**不新增事实名**。
3. **流式不是债。** 流式帧仍走 `ExecEventSink` 直通（PL-014 §3 末段），
   它不改变事实面；债只描述"请求 / 应答 / 失败"。
4. **工具批次是集合，不是单项。** 一次模型响应可带多个工具调用；一个 `tool` 债
   的 `expand` 把批次展开成元素，元素之间并发（PL-014 F1）。
5. **前置是 PL-014 步骤 1。** 没有"把 `run_with_tools` 抽成 Step 循环"的中间态，
   本方案会变成一次 747 行重写。

## §2 缺口：今天的执行体内部

`run_with_tools`（`plugins/loop/turn_runner.rs`，747 行）在一个函数里做四件事：

```
while 未收束 {
    model := 调模型(上下文)          ← 不落 request / sent / response
    if model 无工具调用 { 收束; break }
    for batch in model.tool_calls {  ← 并发，但不落事实
        结果 := 执行工具(batch)
        写 artifact.added / tool 节点
    }
}
```

| 缺口 | 后果 |
|---|---|
| 模型调用不落事实 | 崩溃后不知道"上次发到哪一次模型请求"；`in_flight` 只到整轮 |
| 工具批次不落事实 | 批次内的并发与重试不可回放；审批恢复靠 `resume.rs` 的旁路 |
| 内环是代码 | 加一条"模型失败后换模型重试"只能改函数体，不能加行 |
| 中止在函数内部检查 | 中止粒度是"工具之间"，不是"每一次调用" |

## §3 目标形状

### 3.1 三组行

```
模型：
  dispatch-model   owes: turn.needs_model ∧ ¬closed
                   until: sent(port=model) | failed(port=model)
                   before: sent
                   by: courier

  await-model      owes: sent(port=model)
                   until: response(port=model) | failed(port=model) | retry(port=model)
                   by: None

工具批次：
  open-tools       owes: response(port=model)
                   until: request(port=tool)
                   by: courier
                   expand: (calls, call_id)        ← 一个批次展开成 N 个元素

  dispatch-tools   owes: authz.granted(port=tool)  ← 行归属见 ADR-117
                   until: sent(port=tool) | failed(port=tool)
                   before: sent
                   by: courier

  await-tools      owes: sent(port=tool)
                   until: response(port=tool) | failed(port=tool) | retry(port=tool)
                   by: None

收束：
  close-turn       owes: turn.has_final ∧ ¬closed
                   until: chat.assistant.final | chat.assistant.fallback
                   by: closer
```

`turn.needs_model` / `turn.has_final` / `response.has_tool_calls` 是**视图字段**，
不是新事实名。`chat.assistant.final` / `chat.assistant.fallback` 是既有收束格。

### 3.2 流式与审批

- **流式**：`courier` 在 `sent` 之后把 `ExecEventSink` 的帧直通给前端；
  帧不是事实，不参与 `owed`。`response` 只在流结束时落一条。
- **审批 / 用户补充 / 中止**：都是**外部事件**，由唤醒源落事实（`approval.*` /
  `user.message` / 收束格），`await-tools` 的 `until` 增加对应的事实名。
  `resume.rs` 的旁路在最后一条行迁完后退役——它今天存在，是因为内环没有事实面。
- **`ask_user`**：`request{port:user}` 的 `await` 行，`until: user.message`。
  这是 `Wait` 折叠在细粒度端口上的自然形态，不需要新机制。

### 3.3 并发

创建行 `open-tools` 的 `expand` 让一个批次成为 N 笔子债（派发行仍欠 `authz.granted`，
两段债的划分见 ADR-117）；`drive` 仍串行取最小，
但 `PortDecl` 声明 `concurrent: true` 时，同一 `batch_id` 的子债可并发派发，
引擎等整批 `sent` 后再进入 `await`。**并发集合是事实**（F1），不是执行体的自觉。

| 步 | 内容 | 任务 | 前置 |

每步一个提交，熔断线沿用 PL-014 §5 步 1：**单次提交结构性改动 > 300 行 = 退回**。

**步 1 落地注（2026-10-22）**：轮内循环是**显式步循环**，并带**步数上界**
（`MAX_STEPS_PER_DRIVE = 64` ⇒ 收束 `exhausted{step_limit}`）——上界是
[ADR-115](../010-adr/115.md "ADR-115") 决策 3 的要求：「不收敛」必须收束成一条可观测的
事实，而不是一个卡住的会话。步 1 标称的「纯内部重构，行为不变」不覆盖这条上界
（差异记在 [T-227](../009-task/227-端口细粒度化.md "T-227-端口细粒度化") 的处理过程里）。

**步 2 落地注（2026-10-22）**：模型端口两行 + 适配器。`dispatch-model` / `await-model`
与 `turn` 的两行**同模板**——加一个端口 = 0 个新事实名 + 1 个 `PortDecl` + 2 行
（判据 7 在本步第一次被真实走了一遍）。求解器（`decl/ring.rs`）**字节未变**
（`port-surface-audit` PTS-003 比对通过）。

- **逻辑 id** = `model-{turn}-d{drive_seq}-s{step}`：轮号 + **幕锚** + **步号**。
  幕锚防的是续写幕（复用轮号）与首幕撞成同一笔；步号防的是两次往返撞成同一笔
  （撞了就是幂等键吃掉第二次的 `sent`，日志里两次往返长成一次）。
- **失败分三类**：适配器中止 ⇒ 中止收束格；适配器失败 ⇒ 兜底格；协议事实落不进
  去 ⇒ 往上传；控制面不一致 ⇒ 如实当失败报。
- **事实量上升**：每次模型往返多 3 格（`request` / `sent` / `response`）——§6 已预
  告的代价，本步第一次兑现。

| 7 | 加一个端口 = 0 个新事实名 + 1 个 `PortDecl` + 2 行 | 源码级断言 |
| 8 | 全量门禁与 e2e 全绿 | 门禁 |

## §6 代价

- **事实量上升**：每次模型 / 工具调用至少 2 条（`sent` + 应答）。高频工具要评估日志
  膨胀，但**不能靠不落 `sent` 来省**。
- **流式与事实的边界要守**：流式帧不进日志，`response` 只在结束时落一条；
  否则日志会被 token 级帧淹没。
- **并发只在批次内**：单会话的债仍串行取最小；跨批次并发由 `expand` + `concurrent`
  声明，不是引擎的通用并行调度器。
- **审批语义要逐条迁移**：`resume.rs` 今天承担了工具恢复、审批、问答三条路径，
  迁完之前不能删旁路——两条路径并存是过渡态，必须有明确的删除步（步 5）。

## §7 明确不做

- 不把流式帧变成事实（PL-014 §3 已裁决）。
- 不承诺 L2 级重执行一致（PL-001 §11）。
- 不把工具批次做成通用并行调度器；并发只在 `expand` 的集合内。
- 不在本方案里改工具 schema / 流式协议 / 审批 API。
- 不为"细粒度"重写 `tools/dispatch/batch.rs` 的工具实现；只改它的调用点与事实落点。
