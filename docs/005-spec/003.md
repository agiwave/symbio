## 规范

任何改动按固定顺序推进，**每一步都不得跳过**：

1. **先实现**（含必要的类型约束）；
2. **再单测**（`*.test.rs` / `*.test.mjs`，与实现同模块）；
3. **再 e2e**（`e2e/cases/`，含 LLM mock，跑**出厂默认路径**）；
4. **最后全量门禁**（`node scripts/gate.mjs`）——**全绿才允许提交**。

第 3 步的**范围不看改动点、看消费面**：改 `model.assist` / 网关 / 收件箱这类被多个
用例族共用的面时，先列出依赖它的用例族并逐条单跑，再进第 4 步；只跑改动点旁边的一
两条不算跑过 e2e——共享通道的回归落在下游消费族里，改动点本身往往还是绿的。这是同
一形态的第二次：两次都是「改了共享面、只跑了直接相关用例」。

回退不是批次划分的依据：任何历史版本都在 git 里，`git revert` / `git reset` 就是回退单位。
批次划分只按「一次只改一件事」——理由是审得动、定位得准，不是「好回退」。

## 架构改动的边界（纪律 0）

**架构调整 = 修改模块之间的依赖或协议面**：谁依赖谁、跨模块的接口形状（trait / 类型 /
事实词表 / 路由 / 端口契约 / 封闭集值）。只有这一类改动适用「架构调整只认方案为源」——
先有规划的裁决、后有实施；**「模块实现困难」永远不是改架构的理由**。

**模块内部修改不算架构调整**，无论该模块是架构层（`symbio-kernel` / `symbio-sdk` /
`symbio-plugin-api` / `symbio-plugin-loop` / `symbio-plugin-session` / `symbio-host`）
还是能力插件：只改自己模块内的实现、常量、判据读法、局部加严，不触碰模块间依赖的，
按上面的正常施工顺序走，**不需要判定决策单**。

判法只看一件事：**这次改动有没有改变模块之间的依赖**。不看「改的是不是架构模块」，
也不看「改的是不是判据」——把判据面 / 机制面一律当成架构面，会把每一次局部收窄都升级成
一次裁决，裁决反而失去分量。收窄不需要批准、变宽需要论证（`CS-002` / `D-278`）仍按各自
判据执行；只有变宽改到**跨模块协议面**时才进入裁决通道。

## 判据

`scripts/gate.mjs` 全绿是提交的唯一出口（它汇总全部阶段的判据）。
