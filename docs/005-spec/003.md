## 规范

## 0. 架构改动的边界（纪律 0）

**架构调整 = 修改模块之间的依赖或协议面**：谁依赖谁、跨模块的接口形状（trait / 类型 /
事实词表 / 路由 / 端口契约 / 封闭集值）。只有这一类改动适用「架构调整只认方案为源」——
先有规划的裁决、后有实施；**「模块实现困难」永远不是改架构的理由**。

**模块内部修改不算架构调整**，无论该模块是架构层（`symbio-kernel` / `symbio-contract` /
`symbio-sdk` / `symbio-plugin-api` / `symbio-plugin-loop` / `symbio-plugin-session` / `symbio-host`）
还是能力插件：只改自己模块内的实现、常量、判据读法、局部加严，不触碰模块间依赖的，
按下面的正常施工顺序走，**不需要判定决策单**。

判法只看一件事：**这次改动有没有改变模块之间的依赖**。不看「改的是不是架构模块」，
也不看「改的是不是判据」——把判据面 / 机制面一律当成架构面，会把每一次局部收窄都升级成
一次裁决，裁决反而失去分量。收窄不需要批准、变宽需要论证（`CS-002` / `D-278`）仍按各自
判据执行；只有变宽改到**跨模块协议面**时才进入裁决通道。

## 1. 顺序：实现 → 单测 → e2e → 全部门禁，绿才提交

任何改动按固定顺序推进，**每一步都不得跳过**：

1. **先实现**（含必要的类型约束）；
2. **再单测**（`*.test.rs` / `*.test.mjs`，与实现同模块）；
3. **再 e2e**（`e2e/cases/`，含 LLM mock，跑**出厂默认路径**）；
4. **最后全量门禁**（`node scripts/gate.mjs`）——**全绿才允许提交**。

第 3 步的**范围不看改动点、看消费面**：改 `model.assist` / 网关 / 收件箱这类被多个
用例族共用的面时，先列出依赖它的用例族并逐条单跑，再进第 4 步；只跑改动点旁边的一
两条不算跑过 e2e——共享通道的回归落在下游消费族里，改动点本身往往还是绿的。这是同
一形态的第二次：两次都是「改了共享面、只跑了直接相关用例」。

回退不是批次划分的依据：任何历史版本都在 git 里，`git revert` / `git reset` 就是回退单位。
批次划分只按「一次只改一件事」——理由是审得动、定位得准，不是「好回退」。

## 2. 跨批行为变更的中间态提交

一次**跨多批**的行为变更，在纪律 1 下没有合法落点（中间态必红）。允许提交中间态的条件是**四条同时成立**：

1. **红点已登记**：每条失败都有归属（哪个缺口 / 哪条守卫）与收敛路径（指向某个在办任务或设计小节）；
2. **红点有守卫在看**：本批建了、或已有**能红的**守卫覆盖该类失效（不是「以后会补」）；
3. **提交信息引用红点登记表**，不写「全部通过」；
4. **本批不改生产默认档位**；改默认档位的那一批**单独成提交**。

**边界**：红点不明（不知道会红什么）不适用本条——那是 §1 的场景。
判据：人工核对（红点登记表逐条有归属）+ `scripts/check-commit-msg.mjs`（提交信息形状）。

## 3. 原子批次：多开关必须同翻

当一组开关满足「**单独翻其中任一个，观测值恒为零**」时，它们是一个原子单位，必须同批同翻。成立条件三条：

1. **说明原子性**：为什么这几个开关必须一起翻、单独回退一个会发生什么（可接受的中间态写明）；
2. **判据双向**：同翻后观测非零，**且**翻回去后归零——只有正向证明不了「是这组开关让它有样本」；
3. **观测期与默认期分离**：先看数据走观测形态（只翻不改变出厂行为的开关），「想看数据」不构成翻默认值的理由。

**边界**：只对「任一真子集观测恒零」的开关组成立；能拆的开关组照 §1 走普通批次。
**判据**：无机器判据——开关组的「任一真子集观测值恒零」只在一次真实批次里成立，门禁判断不了哪组开关属于同一原子批——依据是变更意图，不是代码形状；判据面是评审里的原子性论证加 e2e 双向断言。

## 4. 每一批新增一条 e2e，且跑出厂默认路径

每一批改动必须新增**一条** e2e 用例，并且它跑的是**出厂默认路径**：

- 用例落在 `e2e/cases/`，发现式加载（不需要登记到清单）；
- **跑的不是默认路径的用例不算这条纪律的判据**——非默认档位下的绿色证明不了出厂行为；
- 用例的输入不得包含结论（[验证纪律 2](022.md "SP-022")），且须配反向用例（[验证纪律 3](022.md "SP-022")）。

## 5. 架构改动必须逐条论证「必需」

**每一条架构改动都要论证「必需」；论证不出的改动直接删掉。** 「必需」指：不做这一步，
哪条判据兑现不了、哪个已登记缺陷关不掉。论证写在设计文档的正文里，不另开清单。

放宽既有形状（棘轮）**必须挂一条可打开的决策**：

- 形状只许收窄：内核生产侧的三格（`pub trait` 数 / `fn` 成员总数 / 带默认体的成员数）冻结成只许降的棘轮；
- 要放宽，就在设计文档里留一节 `### D-NNN` 说明为什么必需，并在基线旁写
 `core-shape-allow <格>: D-NNN <理由>`；那个锚点在设计文档里**必须真的存在**。

## 6. 不做历史数据兼容

新字段一律 `#[serde(default)]`（或等价的默认值声明）；**新语义只对「新产生的数据」成立**，
不为旧数据写迁移分支、不做双读兼容层。

理由：兼容层是**永久成本**，而本仓未发布、旧数据只存在于开发者的本机目录——
一段只服务一周前数据的分支会活到下一个读它的人误以为它还有用。

## 7. 完成判据必须含一条端到端判据

一批改动的完成判据必须含：**该步在出厂默认档位下被 e2e 全量压过，且行为与设计一致**。
只在非默认档位下验证的步骤**不算完成**。配套三条：

| # | 要求 | 挡住什么 |
|---|---|---|
| **C1** | 完成判据 = **默认路径经过它**，不是「有人调用它」 | 产物被旁路调用也算「接入」 |
| **C2** | 不许连续两步只加机制不切路径：机制可以一批加完，加完必须**立刻**有一个切换步 | 机制攒够了才有第一次端到端 |
| **C3** | 每步留一个「旧路已死」的证据：删掉被替代的旧实现后系统仍能跑 | 缺口在加法里存活 |

**C3 与加法的区别**是要紧的一条：加法没有「删掉旧路」这一步，所以缺口能在加法里活下来；
切换有，所以缺口活不过一批。
