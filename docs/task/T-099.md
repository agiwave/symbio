## 内容

阶梯文档回答的是「要长什么能力、能不能只加数据」，**从不回答「用户因此看见
什么」**。缺的那一栏正好是验收时唯一真正被问的那句：这一阶兑现了，用户看到
的是哪一处变化、从哪里读、拿什么证明它不是纸面能力。

同时暴露 [RE-005-e2e覆盖矩阵](../ref/RE-005-e2e覆盖矩阵.md) 的结构问题：它的**行集**（能力域）是手维护的，
而这份清单**从未与出厂面对账**——整插件面（`web` 的三个工具、`telegram` 全部
路由）不进行就进不了缺口表，而「格子全入格」的自洽掩盖了行的缺席。它自己在
缺口表里记着这件事，但记着不等于修好。

## 处置：RE-005 怎么改

**不删**。它有两块不能被生成物取代的东西：**格子归属**（哪条 e2e 钉了哪条能力）
与**缺口判定**（暂不补 / 明确不做，那是决策不是事实）。删掉它，这两样会散进
别的文档——正是 PL-011 §6 禁止的「留两处半截登记」。

**改行集**：能力域这一维改由 [T-098](T-098.md) 的能力矩阵给出（代码投影，本就存在，
只是没人抽），RE-005 只保留三列形态（正常 / 异常 / 缝隙）与缺口判定段。
「格子全入格」的自洽因此不再成立——行集是投影，投影与格子对不上就是缺口，
这正是它当初想抓而抓不到的形态。

## 纪律

**体验类断言只有落成 e2e 场景才算数。** 本任务往 ST 里写的每一句「用户看到
什么」，要么指得到一条 e2e 用例 / 一个生产读数口，要么明写「尚无用户可见
判据」。按本仓标准，没有判据支撑的体验描述连「设计」都算不上——它只是一份
意见，而意见写进验收文档会让那一栏永远绿。
