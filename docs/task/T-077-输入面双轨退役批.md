## 内容

[ADR-031](../adr/ADR-031.md) 自记残余（正文「未完成（有意留下，需要自己的 ADR）」）：
输入面今天**双轨并存**——inbox 地址写入（用户主路径）与 `chat/send` / `chat/abort` 两条路由
（委派、telegram、CLI 仍走）。按用户裁定「违背目标且因妥协留下的判定 = 历史遗留，必须有任务」，
本条接管该遗留；GO-000「一个事实只有一个 owner」叙事在双轨期间带病运行。

## 处理过程

- 2026-10-13 登记（ADR 全量复核发现：残余无任务承载，`docs/task/` 全目录 grep 零命中）。
- 2026-10-13 **步①（协议决定）落地 = [ADR-066](../adr/ADR-066.md "ADR-066")**：裁决「地址写入**不**承载运行选项」。
  三条依据：① `provider_id` / `mode` / `risk_level` 在契约里**已有会话 metadata 回退**
  （`orchestrator/entry.rs::resolve_session_params` 的三条对称链 `req > metadata > 默认`，
  其中 `provider_id` 那条**代码有、字段文档没写**——已在 `session_chat.rs` 的字段注释里补上，
  并把它标为本 ADR 的不变量）；② 三者描述的是**会话属性**（这个会话怎么跑），不是消息属性；
  ③ 四个调用方逐个核对，没有一个需要协议变宽——`agent_run` 要的三项全是会话属性且它**已经在写
  子会话 metadata**（`register_subsession`）、心跳**已经进程内直连**（`include_history` 是本次发送
  属性，留在 `Request`）、telegram 的 `mode: "auto"` 是通道属性、CLI 不带选项。
  否决了「包裹形状 `{message, params}`」（判别式从一条变两条，把 `parse_inbox_message`
  「取『以 `{` 开头』而不是『能不能解析』」那条纪律在同一个函数里推翻）与「平级保留键 `params`」
  （会成为 `ChatMessage` 字段子集里的保留键，要么静默丢弃、要么给它加一个不该有的字段）。
  据此 AR-010 §5.6 的状态由「⚠️ 前置条件」改为「✅ 已裁决」，§8.2 第 1 项改判为「前置条件已解除，
  待步② 执行」。**步② 的前置条件由此解除。**
- **步②（退役两条路由）/ 步③（§8 两个未打勾项）仍开。**
