## 处理过程

- 迁自 13 §1 问题登记（2026-10-11 进入登记机制）；批次内容与目标态归 13 §2，实施过程查 `git log`。
- 2026-10-12 落地（口径决策见 [ADR-057](../adr/ADR-057.md)）：

  **为什么从运行时抓**：起点尝试是静态读 `render_messages` / `request_view_prefix`，但它只能
  读出**打算**发什么；ADR-048a 争的是「适配器边界上有没有被拍平」，那是运行时事实。
  最终形态 = 真实链路（CLI × mock LLM × mock MCP）跑一次，mock 记录的**原样请求体**进提取器。

  **可复现性实测先行**（决定口径的关键一步）：连跑两次同场景、逐字段 diff，唯一漂移源是
  system 前缀记忆地址里的**会话 id** ⇒ 用例把 `SID` 钉死即可。另外实测到
  `tools` 数组**顺序每次不同**（名字集合稳定）⇒ 判据按排序后的名字比，
  `schema_bytes` 取逐工具求和（与顺序无关）。

  **口径**：结构进判据（信封 / 消息序列与 `tool_calls`+`tool_call_id` 载体 / system 小节
  **标签序列** / 工具数量与名字），规模只作观测。标签切分的坑：`【…】` 在正文里也会被引用
  （「与【智能体记忆】相互独立」），按标签切会把一段切成三节 ⇒ 判据改成「**行首**才算」。

  **基线第一次跑出来的数**（重生成当时快照，不是判据）：工具 schema **18247B** 对
  消息正文 **1119B** —— 出厂 prompt 的规模主体是**工具面**，不是消息结构；
  第二轮请求（1369B）比第一轮（1119B）多的那部分是【长期记忆】召回小节，
  它在第一轮不存在（标签序列里可见）。这正是「结构化代价在哪一列」第一次有了读数。

  **双向验证**：回归测试 20 条（含反向：正文措辞变长不得红；结构载体缺失必须红）；
  门内实跑再手动注入一次漂移（改基线里的 `vdfs_tree` 名字）⇒ t46 红并指出
  「新增 [vdfs_tree] 移除 [vdfs_tree_RENAMED]」，还原后复绿。

  **没做的事**：本批一个 prompt 字节都没改（记录面不通过改被记录的东西来变好）；
  「对模型更好还是更坏」仍需真实模型对照 ⇒ 那是 S-end② 的面。
