# 能力扩充阶梯 · 分布实施路线图

> **这一组文件是什么**：13 个从低阶到高阶的能力扩充场景，每个单独说明。
> 每个场景回答同一个问题：**要长这个能力，需要改架构吗？**
> 答案若不是"只加数据"，这个阶梯就失败——那是架构设计问题，不是排期问题。

---

## 0. 路线图一句话

**前 8 阶把机制键点亮完，后 5 阶只允许取新值；全梯 13 阶架构改动 = 0。**

机制键一共 10 个（见 [PL-001 §8](../plan/PL-001-核心架构.md "PL-001-核心架构")）。本阶梯的第 9–13 阶**新增机制键数量为 0**——
高阶能力全部是"已有参数的新取值"。这是"扩充不会重构"唯一可审计的形式。

> **这一句最初并不成立**：S10 曾被判为需要扩展 `store` 值域（入库过滤），是全梯唯一触及原语的地方。
> 复核后推翻——它与 §9.3 的"遗忘"是同一个模式，归入读侧投影参数即可。
> 详见 [ST-010 §5](ST-010-个人认知体系注入.md "ST-010-个人认知体系注入")，那一节比本路线图的其余部分都更值得读。

## 2. 每个场景文件的统一结构

| 节 | 回答 |
|---|---|
| §1 场景 | 这一阶要长什么能力，为什么它算"高一阶" |
| §2 落点 | J1 检验：它为什么能用已有参数表达，而不是新机制 |
| §3 增量清单 | 只加数据：事件格子 / ActorSpec 行 / grants 行 / 投影参数 |
| §4 平凡值与回退 | J2 检验：关掉它，系统是否仍完整运行 |
| §5 静默失效 / 架构复核 | J3 检验：违反时有没有错误信号；若涉及改架构，先过前置闸门 |
| §6 验收断言 | 可执行的出口判据 |
| §7 使用者看到什么 | **这一阶兑现了，用户看到哪一处变化、从哪读、拿什么证明**。每行只认 e2e 场景与生产读数口，两者皆无的如实标为缺口——没有判据支撑的体验描述连「设计」都算不上 |
| §8 做不了什么 | 这一阶的诚实边界 |

> **为什么 §7 独立成节而不是并进 §6**：§6 问的是「机制成立了吗」，执行方是断言与守卫；
> §7 问的是「**用户**看到了吗」，执行方是 e2e 场景与生产读数口。两者**判据不同源**——
> 一次断言全绿而用户什么都没看见，是这阶梯上真实发生过的事（[ST-004-并发调度与租约](ST-004-并发调度与租约.md) 的
> 租约、[ST-010-个人认知体系注入](ST-010-个人认知体系注入.md) 的四个投影参数都属此类）。把它们写在一处，
> 「机制成立」就会被读成「用户看见了」。

## 3. 机械审计

所有场景的赋值向量集中在一个程序里，可复算：

```
cd ../verify && rustc --edition 2021 scenario_ladder.rs -o sl && ./sl
```

程序回答四件事：

1. 13 阶**有没有任何一阶逼迫新增机制键**（越界键应为 0）；
2. 逐阶**新增键数量**是否如总表所声称（后 5 阶应为 0）；
3. 每阶是否声明了**真正的平凡值回退**（J2）——回退值等于正常运行值 = 没回退；
4. **有没有任何一阶需要扩展已有键的值域**（应为 0；非 0 必须走 ADR 前置闸门）。

反向用例：注入一个需要新机制的第 14 阶 / 一个假回退 / 删掉一个键，审计必须失败或结果必须改变。

## 5. 认知体系（`reference/01-认知架构模型.md`）在阶梯中的分布

认知体系**不是单独一阶，而是横跨五阶**。这本身就是重要的验证结果：
一套独立设计的内容体系，其需求**天然落在已有阶段上**，而不是逼出新的阶段。

| 认知体系的需求 | 落在 | 说明 |
|---|---|---|
| 七类认知内容（知识/经验/技能/判断/策略/直觉/情绪） | **S06** | `memory.encoded` 的 payload 标签 |
| 五层存储 | **S06** | 五个 `recall:layer` 投影参数，不是五套存储 |
| 向量 / 关系 / 时间索引 | **S06** | `Store` 实现细节 |
| 激活扩散 + 时间衰减 + 使用反馈 | **S06** | `recall:spread`、`recall:decay` + `memory.recalled` |
| 个人归属与跨主体借用 | **S08** | `principal` + `vis_scope = shared` |
| 内外双轨动作空间 | **S09** | 能力命名前缀 + grants 行 |
| 系统 2 → 系统 1 编译 | **S11** | `skill_compile` + 反自动化回退 |
| 内容密度金字塔 | **S10** | `recall:density` |
| 通用性分级（L0–4）与过滤 | **S10** | `recall:min_generality`（**读侧**，见 S10 §5） |

> 上表是**归属**（这条需求由哪一阶承担），**不是实现状态**：`recall:` 那一族投影参数今天
> 只有 `tag` 有形参——**内容过滤**参数全仓仅此一个（别的投影要么无参，要么取的是评分策略，
> 如 `reputation_with`）。逐条状态、以及"为什么 `min_generality` 不照抄落地"，见
> [ST-010 §3.1](ST-010-个人认知体系注入.md "ST-010-个人认知体系注入")。

**「欲」维度（Conation）的分布**：它不是认知体系的内容，而是本阶梯**自己**在 S12 第一次点亮的能力维度。
按 [PL-001 §4.2](../plan/PL-001-核心架构.md "PL-001-核心架构") 的最小可执行形态落成三条：

| 「欲」的子问题 | 落在 | 说明 |
|---|---|---|
| E1 欲是什么 | **S12** | `event.entity = conation`（`conation.expressed`）—— 加一格，不是加机制 |
| E2 欲如何不直接变成行 | **S12** | ZST 令牌 `GateWarrant`（同投影 `PureOnly`、时延 `RuleOnly` 的复用模式） |
| E3 欲如何被关停 | **S12** | `ConationPolicy.enabled`，平凡值 `false`（J2） |

> `verify/conation_minimal.rs` 实测：4 项「欲」能力全部落在**已有机制键的新取值**上，**新增机制键 = 0**。
> 这正是"用封闭坐标系吸收开放能力清单"的又一例证——连"能动性"这种最不像机制的能力也不例外。
>
> 上表同样是**归属**，不是实现状态：三条子问题今天都在生产（`AutonomousInitiator` +
> `IntentGate` + `ConationPolicy`），但 [ST-012 §3](ST-012-自主层与长期目标.md "ST-012-自主层与长期目标") 那四行里
> **「ActorSpec 行」只是目标**——逐条状态与理由见 [ST-012 §3.1](ST-012-自主层与长期目标.md "ST-012-自主层与长期目标")。

**不采用的 3 处**（理由）：

1. **System 1 / System 2 双系统** —— 与 [PL-001 §2.2 / §10](../plan/PL-001-核心架构.md "PL-001-核心架构") 冲突：
   快与慢是 `budget_ms` 的取值，不是两套系统。且 v2 已用 `skill_compile` + 回退表达了两者间的**动态转换**，
   比"两套静态系统"更强。
2. **五层存储做成五套存储** —— 按 J1 归约为投影参数，否则违反元素数守恒。
3. **L1–L5「专家拟合度 100% 以上」** —— 不可验证的营销化数字；v2 的 T1–T8 × 五轴刻度更可度量。

## 6. 这套阶梯证明不了的

- **场景是我想出来的，不是穷举的。** 第 14 个场景照样要重跑审计程序。
- **承载 ≠ 保证。** 每阶都证明"装得下"，不证明"装上好用"。召回质量、成本、真实延迟都在这套论证之外。
- **零新增键是必要条件，不是充分条件。** 真正的重构可能藏在**值的语义**里（S10 最初就是这样）。
  程序报不出这类问题，只有"先找同构既有模式"这道人工闸门能拦住——
  这条已经写进 [PL-003 §3 ADR 前置闸门](../plan/PL-003-演进与验证.md "PL-003-演进与验证")。
