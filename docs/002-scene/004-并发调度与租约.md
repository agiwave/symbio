# 并发调度与租约

> **一句话**：多个请求同时来时忙则排队、不丢不串；同一份会话同一时刻只有一人在写，冲突被明确拒绝。
> 支撑能力：[DE-034-并发调度与租约](../003-design/034-并发调度与租约.md)

## 场景

用户同时对同一会话发多个请求，或开两个窗口动同一份会话。期望的并发语义很朴素：
忙则排队、可取消，第二个写者被明确拒绝而不是静默覆盖。
今天的痛：并发之下要么消息丢失、要么互相覆盖，事后说不清哪条才是准的。

## 用户判据（诚实账）

| # | 用户应该看到 | 判据现状 |
|---|---|---|
| 1 | 同一会话并发请求：忙则排队，不丢、不串 | e2e：t15（排队 / 可取消）/ t34（忙窗插话挂起）（已有） |
| 2 | 两个进程同时写同一会话：第二个被明确拒绝，不是静默覆盖 | e2e：t32（已有） |
| 3 | 租约到期判死；优先级 / 并发上限 | 租约：CLI 实测（造「只有 `sent`」的 WAL 并回拨租期后重启，两口各落 `failed{why:"lease_expired"}`，`obligation-ring-accept --strict` 全项通过）；优先级 / 并发上限：未承诺——`session` 插件无 priority / 并发上限任何实现（全仓 grep 零命中），不是缺判据是缺能力 |

## 边界

不含进程重启后的调度状态恢复（那是断点恢复场景的事）；不含多副本部署下的顺序保证；
优先级与公平性是策略选择，系统只保证排队与拒绝发生。
