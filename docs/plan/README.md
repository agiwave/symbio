# 高阶智能体平台 · v2

> 一个面向**可长期演进、能力可持续增长而不重构架构**的高阶智能体系统设计。
>
> **一句话架构**：一个智能体平台 = **1 个原语 + 1 个签名约束 + 1 个使用者概念 + 3 条不变量 + N 行参数数据**。
>
> **新场景 = 加事件格子 + 加投影参数 + 加一行 ActorSpec + 加一行 grants。**
> **新能力 = 在五维五轴坐标系里占一个格子 + 取一组参数值。**

---

## 0. 这份设计要解决什么

| 目标 | 具体含义 | 兑现方式 |
|---|---|---|
| **能力规划得足够远** | 覆盖到当前能设想的最高阶形态 | 五维 × 五轴的**坐标系**，而不是一张会过时的能力清单（[02](./02-能力坐标系.md)） |
| **架构足够简洁** | 到达可论证的下界，无冗余机制 | 1 个原语 + 3 条判据，其余全部是参数（[01 §1](./01-核心架构.md)） |
| **扩展永不推翻重构** | 能力增长只新增数据与配置 | 冻结 6 个锚点 + 守恒律审计（[03](./03-演进与验证.md)） |
| **关键声称有证据** | 可复现，而不是修辞 | 14 个可编译运行的验证程序，全部带反向用例（[verify/](./verify/)） |

## 2. 六条设计取舍

| 取舍点 | 本方案的选择 | 理由 |
|---|---|---|
| **原语数量** | 1 个（`Store`） | 元素类型与行为都不构成原语（[01 §1](./01-核心架构.md)） |
| **投影的形态** | 函数签名约束，**+ 私有构造入口**；不做成 trait | trait 不增加强制力，却多一层抽象；但裸 `type` 别名**也不够**——需要 `new` 做不可伪造的门（[01 §1.4](./01-核心架构.md)） |
| **行为（Actor）的地位** | 一等概念，不是原语 | 它无状态、无接口、无不变量——是装配线不是砖 |
| **需要记住的约束** | 3 条判据 | 清单会增长，判据不会（§3） |
| **时延** | 一等契约（不变量 I3） | 对话是基础能力，不能只靠工程优化 |
| **回放承诺** | 只承诺 L0 + L1，**明确放弃 L2** | L2（重执行一致）原理上不成立（[01 §11](./01-核心架构.md)） |

## 3. 三条判据（全部设计的收敛点）

> 架构设计里最容易膨胀的是"注意事项清单"。**清单会增长，判据不会。**

| 判据 | 内容 | 它替代了什么 |
|---|---|---|
| **J1 可表达性** | 若 X 能用**已有参数的新取值**表达，它就是数据，不是机制 | 候选原语清单、退化规则清单、逐条冻结的契约清单 |
| **J2 平凡值** | 任何参数必须存在**平凡值**，且平凡值下系统必须完整运行 | 所有"分阶段简化"的特例分支 |
| **J3 静默失效** | 若某约束被违反时**不产生错误信号**，它必须做成编译期强制或 CI 断言 | 权限、可见域、投影纯度、预算的"靠自觉" |

**J1 决定"能不能加"，J2 决定"简化是否合法"，J3 决定"要不要强制"。** 其余规则都是这三条的推论。

## 4. 硬证据（全部实际编译运行通过）

```
cd verify && rustc --edition 2021 <file>.rs -o <out> && ./<out>
```

| 程序 | 验证什么 | 断言 | 反向用例 |
|---|---|:-:|:-:|
| `lower_bound.rs` | 职责分组由冲突矩阵**计算**得出 | 7 | 4 |
| `invariants.rs` | I1 单通道 / I2 无溯源 / I3 到点必答 | 5 | 3 |
| `mechanism_growth.rs` | 机制数不随场景数增长（守恒律） | 4 | 1 |
| `capability_frame.rs` | 54 项能力全归位 + 伪高阶识别 | 6 | 4 |
| `termination.rs` | 终止性三前提各自必要 | 8 | 2 |
| `budget.rs` | 四层时延 + 兜底契约 | 10 | 1 |
| `cognitive_fit.rs` | 外部认知体系能否**不改机制**地承载 | 19 | 6 |
| `scenario_ladder.rs` | 13 阶阶梯全程 **0 新增键 + 0 值域扩展** | 13 | 4 |
| `module_deps.rs` | 派生图无环由谁保证；代数发散由谁兜住 | 9 | 2 |
| **`projection_purity.rs`** | 投影纯度是**编译期强制**（句柄进不来），非约定 | 8 | **2 编译期** + 2 数据 |
| **`latency_gate.rs`** | 时延档位是**事前闸门**（反射档结构上拿不到模型） | 20+ | **2 编译期** + 2 数据 |
| **`consolidation_fidelity.rs`** | 巩固的**保真度下界**（质量约束，补 `max_gen`） | 12 | 3 + 1 平凡值 |
| **`semantic_drift_audit.rs`** | 值语义滑移审计（D1–D4 四维适应度函数） | 4 检查器 | 4 负样本 + 正样本无假阳性 |
| **`conation_minimal.rs`** | 「欲」的最小可执行形态（事件 + 类型闸门 + 平凡值） | 10+ | **3 编译期** + 3 数据 |

**验证纪律**（四条，针对架构文档最常见的四种自欺）：

1. 每条声称对应一条可执行断言——**零断言的程序不可能失败**，"编译运行通过"本身不是证据；
2. 断言的**输入不得包含结论**——把结论写成常量再断言常量（例如把"是否会增长"硬编码成 `false` 再断言它不增长）等于没验证；
3. 每条断言配一个**反向用例**——改输入后结论必须改变。改了不变，说明判据没在算；
4. **"强制"本身也要有反向用例**——声称"编译期强制"的，必须附一段**已知编译不过**的代码
   （见 `projection_purity.rs` / `latency_gate.rs` / `conation_minimal.rs` 的 `should_not_compile` feature），
   并用 `rustc --cfg 'feature="should_not_compile"'` 验证它**必然**失败。
   没有这条，无法区分"真的强制"与"恰好没写错"——这是第 3 条在**编译期强制**上的镜像。
   **关键陷阱**：反向用例必须写在**外部模块**里（`mod outsider { ... }`）——私有字段在同模块内可见，
   写错位置会让"必须失败"的用例反而通过（`conation_minimal.rs` 头部已标注此坑）。

> **编译期反向用例的跑法**（`-o` 不要用 `/dev/null`，Windows MSVC 链接器需要真实路径）：
> ```
> rustc --edition 2021 --check-cfg 'cfg(feature)' \
>       --cfg 'feature="should_not_compile"' <file>.rs -o should_fail.exe   # 期望非 0 退出
> ```

## 5. 模块划分与契约

> 架构 = **模块划分 + 模块间契约**。最好的架构同时做到两件事：
> ① 模块能不断扩充而**不需要修改架构**；② 模块间**完全解耦**（高内聚、零依赖）。
> 这两件事通常互相拉扯——解耦要加中间层，扩展要动接口。本方案靠一处设计同时拿到：
> **把契约从"模块之间"挪到"模块与共享事实源之间"。**

| | 本方案的答案 |
|---|---|
| **模块划分** | 有接口、有边界、可被替换的模块**只有 1 个：`Store`**。<br/>其余（投影、Actor、能力）全是**数据行 + 纯函数**——不是代码模块 |
| **模块间契约** | 不是 A 调 B 的接口，而是**所有模块共同遵守的事件格式**。<br/>契约数从 O(N²) 降到 **O(N)**，新增模块不需要知道任何既有模块 |
| **① 可扩展性** | 新增能力 = 加事件格子 + ActorSpec 行 + grants 行 + 投影参数。<br/>守恒律审计：13 阶全程 **0 新增机制键 + 0 值域扩展** |
| **② 零耦合** | 代码依赖与类型依赖**被杜绝**；剩下的只有"对事件的依赖"，**不是对模块的依赖**（[01 §13](../01-核心架构.md)） |

**三条代价**（不写清楚就会被误读成银弹）：
① 事件 schema 必须是终态——定错了代价极高；
② 封闭的是**坐标系**，开放的是**实例**，可扩展性是"在封闭坐标系内无限"；
③ 零耦合意味着**全局性质无处安放**，只能外置为 CI 断言（这正是 J3 的原因）。

> **施工视图见 [05-模块架构.md](./05-模块架构.md)**：把系统切成 6 个可独立替换的包
> （`store` 唯一不可替换），每个包锚定在某条不变量上，并给出"违规该去哪个模块找"的责任表。
> 01 的"1 个模块"是**架构记账**，05 的"6 个包"是**工程切分**——两者不矛盾。
