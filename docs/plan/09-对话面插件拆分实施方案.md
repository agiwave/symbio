## 0. 一句话

**plan 覆盖了 chat/worker 分离的全部 15 个机制点；4 处缺口全是「0 新增机制键」。**
但落地形状要改：**「少改动」指的是机制（F1–F6 / 机制键 10 个）不动，不是插件数不动。**
因此对话面拆成**两个**插件——**一个能力一个插件**，且各自"没有它系统也能正确运行"。

```text
机制面：0 新增机制键 · F1–F6 不动              ← 这才是「少改动」的度量
插件面：+2 插件（triage · reply）· +2 路由 · +2 core schema 模块
能力面：+2 能力（JudgeIntent · ReplyFirst+ReplyAppend），各自可单独卸载
```

> **判据不是"拆得越多越好"**：一个候选插件若与既有插件**卸载语义相同**，它就不是新能力，
> 而是既有插件的**数据**（§2.4 的两张表）。本场景停在这两个。

## 2. 一处必须记住的判据：少改动 ≠ 不拆插件

### 2.1 两个量：架构改动 vs 插件数量

**「架构改动」与「插件数量」是两个不同的量。** 本仓冻结的是前者，不是后者：

| 量 | 定义在哪 | 加一个插件会变吗 |
|---|---|---|
| **机制面** | [03 §1](./03-演进与验证.md) 的 F1–F6：`Store` 签名 / 投影构造形状 / `ActorSpec` 5 字段 / 三条不变量 / 三个封闭集合 / 参数表键集 | **不变** |
| **机制键数** | [01 §8](./01-核心架构.md)：10 个顶层键，恒定 | **不变** |
| **插件数** | 施工视图（[05](./05-模块架构.md)）——**可独立替换的包** | **+1** |
| **地址数** | 插件名 = 挂载点 = 路由前缀（ADR-032） | **+1** |

在 plan 自己的记账里，**一个插件就是一行 `ActorSpec` + 一个挂载点**——即 `L-data`。
换句话说：**拆插件在 plan 的记账下根本不构成架构改动。**
把「插件数」当成「架构改动」的度量，正是本方案要避免的那类混淆。

### 2.2 拆插件反而更强

| | 塞进 session | **独立插件（本文）** |
|---|---|---|
| "无工具"的保证 | 调用点传空工具列表 + **CI 断言** | 插件不注册 `Capability` ⇒ **结构上不可能** |
| 判决/措辞的边界 | 靠"这个函数别写太多" | 插件边界 = 编译单元边界 |
| 独立开关 / 独立模型 | 靠 session 内的配置块 | 插件目录 = 配置目录（各自的 `PLUGIN.yml`） |
| 跨插件依赖 | 不涉及 | 经容器 `route` + 常量，E-007 / E-009 **已在守** |
| 长期维护成本 | 0（但 session 持续变胖） | 一个需要维护的地址 |

**多一个地址是成本，但它是划算的**：地址是**身份**（ADR-032），
而分形插件架构（ADR-001 / ADR-002）的全部收益正来自"用地址切分职责"。
**把功能堆进 session 来省一个地址，是在用一个架构资产换一点短期便利。**

### 2.3 代价与退路：多一跳

判决与措辞若在**一次** LLM 调用里完成，`Answered` 路径只需一跳；拆开后是**两跳**
（`triage` 分类 → `reply` 生成）。这对**目标 1（直接回答要快）**是逆风。

对策——把代价压到有界：

| 路径 | 谁出力 | LLM 次数 |
|---|---|---|
| 规则命中（问候 / 致谢 / 确认 / 空输入） | `triage` 规则表 ⇒ `reply` 模板表 | **0** |
| 需要干活（`Escalate`） | `triage` 规则或快速档 ⇒ `reply` **模板**首响（不等判定） | ≤ 1 |
| 模糊输入直答 | `triage` 快速档**分类**（300ms，比生成便宜一个数量级）⇒ `reply` 生成 | 2 |

> **翻转条件（写下来，免得变成信仰）**：D0 埋点若证明"模糊输入直答"这一路的
> 两跳比单跳慢得不可接受（p95 差距 > 一次分类的预算），就把两行 `ActorSpec`
> **合并为一个插件**——这是 `L-data` 级的切换，不是架构变更。

### 2.4 插件粒度：按能力切，切到"卸载后系统仍完整运行"

> **最好的架构是一个能力一个插件**：有这个插件就拥有这个能力，**没有它系统也能正确运行**，
> 插件之间互不相关，且每个插件尽量小。

**判据三条**（缺一不可）：

| # | 判据 | 可执行形式 |
|---|---|---|
| 1 | **一个能力一个插件** | 插件名 = 能力名；能力可枚举（对照 [01 §7](./01-核心架构.md) 的 7 个能力封顶） |
| 2 | **可卸载** | 卸掉它，系统**完整运行**（退化，而不是崩溃）——这是 J2 平凡值的**插件版** |
| 3 | **零相关** | 不 import、不持有兄弟插件（`plugin-entry-audit` 的 E-007 / E-009 **已在守**） |

#### 能力盘点（本场景）

| 能力 | plan 的枚举 | 落点 | 为什么 |
|---|---|---|---|
| 判断"能不能直接答 / 该不该派活" | `JudgeIntent` | **`triage` 插件**（新增） | 有独立平凡值：卸载 ⇒ 全部派活 |
| 说人话（首响 / 答话 / 汇报） | `ReplyFirst` · `ReplyAppend` | **`reply` 插件**（新增） | 有独立平凡值：卸载 ⇒ 无 对话面文本，worker 正文照旧 |
| 干活（工具循环 / 上下文 / 存储） | `DefineWork` · `ProduceArtifact` | `session`（现状） | — |
| 补充整体整合 | 无对应枚举 | `session`（现状） | 它是**输入通道的消费粒度**，与收件箱是同一机制；搬出去会破坏"唯一输入入口"（ADR-026 / 031） |
| 呈现分界 | — | 前端 | 不涉及后端插件 |

**所以本场景新增 2 个插件，不是一个。**

#### 为什么 `triage` 与 `reply` 是两个能力，而不是一个

它们**各自可卸载**，且卸载后系统完整运行：

| 卸载 | 结果 | 完整运行？ |
|---|---|---|
| 卸载 `triage` | 全部输入直接进工具循环（= 今天的行为） | ✓ |
| 卸载 `reply` | 没有 对话面产出的文本；worker 的正文照旧（= 今天的行为） | ✓ |
| 都卸载 | = 今天的行为 | ✓ |

**零相关**：`reply` 不知道 `triage` 存在，`triage` 也不知道 `reply`——
两者都由 session 在 `ctx` 里喂输入（`triage` 拿"判决所需"，`reply` 拿"判决结果 + 事实"）。
session 是唯一调用者，两条边都指向它自己，**插件之间没有边**。

#### 不继续往下切

**建构简单也是判据。** 两个插件各自的入口、`README.md`、`PLUGIN.yml` 都是真实成本，
因此**不**再往下切：

| 不再切 | 为什么 |
|---|---|
| 把"首响"与"汇报"拆成两个插件 | 两者卸载语义**没有差别**（都是"没有 对话面文本"），拆开只是复制入口 |
| 把"规则表"拆成独立插件 | 它是 `triage` 的**数据**（一张表），不是独立能力——按 J1，是数据就不是机制 |
| 把"模板表"拆成独立插件 | 同上，它是 `reply` 的数据 |

**判据**：一个候选插件若与既有插件**卸载语义相同**，它就不是新能力，而是既有插件的**数据**。

### 2.5 结论

**本场景新增 2 个插件（`triage` · `reply`），0 新增机制键，F1–F6 不动。**
两个插件在结构上都是"无工具、无副作用、无状态"的——C-D1 那条 CI 断言随之**不再需要**
（它们不注册 `Capability`，工具集里结构上不会有它们）。

## 4. 目标架构

### 4.1 插件与地址

| 插件 | 角色 | 挂载点 | 自有路由 | LLM 可见工具 | 配置文件 | VDFS |
|---|---|---|---|---|---|---|
| `session` | 编排 + 工作 | `<根>/session` | `session/chat/send` · `session/chat/abort`（不动） | 现有工具集（不动） | `<根>/session/PLUGIN.yml` | 有 |
| `triage`（**新增**） | 判决（能不能直接答 / 该不该派活） | `<根>/triage` | `triage/decide` | **无** | `<根>/triage/PLUGIN.yml` | **无** |
| `reply`（**新增**） | 措辞（首响 / 答话 / 汇报） | `<根>/reply` | `reply/compose` | **无** | `<根>/reply/PLUGIN.yml` | **无** |

**「无工具」是结构保证**：模型能调用的工具来自 `traverse(TRAVERSE_AVAILABLE_TOOLS)`
→ `CapabilityVisitor::register`。`triage` / `reply` **都不注册任何 `Capability`**，
因此模型的工具集里**在结构上不可能**出现它们——不需要 C-D1 那条断言。

两者都**不实现 `VdfsProvider`**：无状态、不持有任何地址，因此没有挂载视图。

### 4.2 两条调用边，都从 session 出发（插件之间无边）

```text
┌───────────────────────── worker 容器（composite，现状） ─────────────────────────┐
│                                                                                │
│                   route(ROUTE_TRIAGE_DECIDE)          ┌─────────────────────┐   │
│              ┌───────────────────────────────────────▶│ triage（新增）       │   │
│              │                                        │ · 规则表 + 快速档分类 │   │
│              │◀───────────────────────────────────────│ · 输出**枚举**，不产出 │   │
│              │        返回判决（Answered / Escalate）    │   面向用户的正文     │   │
│  ┌───────────┴────────┐                               └─────────────────────┘   │
│  │ session（编排+工作） │                               ┌─────────────────────┐   │
│  │ · 唯一编排者        │ route(ROUTE_REPLY_COMPOSE)    │ reply（新增）        │   │
│  │ · 唯一转写写入者     │──────────────────────────────▶│ · 模板表 + 生成      │   │
│  │ · 唯一输入入口      │◀──────────────────────────────│ · 输出**文本**，不做  │   │
│  └───────────┬────────┘        返回文本                 │   判决               │   │
│              │                                        └─────────────────────┘   │
└──────────────┴──────────────────────────────────────────────────────────────────┘
               ▲ 唯一输入入口（不变）：write(<根>/session/<sid>/inbox/<iid>)
           用户 / 前端 / CLI / telegram
```

**两条边都从 session 出发，且都是单向的**：`triage` 与 `reply` 都无副作用
（不写地址、不派活、不起后台任务）⇒ 都不需要回调 session ⇒ 转写写入者仍是唯一的；
`triage` 与 `reply` 之间**没有边**，互不知道对方存在（§2.4 的"零相关"）。

**职责分界**（一条判据）：`triage` 只输出**枚举**（可被判定的东西），
`reply` 只输出**文本**（可被展示的东西）。**判决不做措辞，措辞不做判决。**

**调用形状**（与 `agent_run` → `session/chat/send` 同款，两个插件同形）：

```rust
// session 侧：判决
let mut c = ctx.fork();
c.set(PATH, ROUTE_TRIAGE_DECIDE.to_string());   // 常量，不写字面量（plugin-entry-audit E-003）
c.set(SESSION_ID, session_id.clone());
c.set_payload(DecideRequest { … })?;
let verdict: Verdict = parent.clone().route(c).await?.payload()?;

// session 侧：措辞
let mut c = ctx.fork();
c.set(PATH, ROUTE_REPLY_COMPOSE.to_string());
c.set(SESSION_ID, session_id.clone());
c.set_payload(ComposeRequest { verdict, snapshot, context_excerpt, … })?;
let text: String = parent.clone().route(c).await?.payload()?;
```

`parent` 是 `ChatOrchestrator::parent: Option<Arc<dyn Plugin>>`（[`chat_loop/state.rs`](../../symbio/src/plugins/session/chat_loop/state.rs)），
**已经是容器句柄**——本方案不需要新增任何持有关系（E-007 天然满足）。

### 4.3 轮边界抽干需要一次句柄注入

`run_chat_loop` 是自由函数，只拿得到 `ChatOrchestrator`，而抽干要读 `active_mgr` 与 `config`
——两者都在 `SessionPlugin` 上。**既有范式已经解决了这个问题**：

```rust
// chat_loop/state.rs —— 已有的同款注入
pub struct CompressionEmitter {
    plugin: Arc<crate::plugins::session::plugin::SessionPlugin>,
    pub(crate) state: Arc<crate::plugins::session::active::ActiveSessionState>,
}
```

照此加一个同形状的持有者（`ChatOrchestrator` 加一个 `Option<Arc<…>>` 字段，
在 [`orchestrator/consume.rs`](../../symbio/src/plugins/session/orchestrator/consume.rs) 构造处传入，
与 `phase: Option<Arc<CompressionEmitter>>` 并列）：

```text
ChatOrchestrator {
    provider, parent, context_limit, stop,
    compression: Option<Arc<CompressionEmitter>>,   // 已有
    supplements: Option<Arc<SupplementDrain>>,      // 同形状（S0）
    session_dir,
}
```

**插入点**（[`chat_loop.rs`](../../symbio/src/plugins/session/chat_loop.rs) 步骤 2 与步骤 3 之间，`gate_turn` 的 `match` 之后）：

```rust
match gate_turn(&turn_req, &turn) { /* … 不变 … */ }

// ── 新增：轮边界抽干（仅非首轮）────────────────────────────────
if turn.tool_rounds > 0 {
    if let Some(merged) = drain_supplements_into(&context.session, &ctx, &turn_req).await {
        context.messages.push(merged);
        // 刻意**不**推进 turn.last_saved：让下一次 persist_messages 带上它
    }
}

// ── 步骤 3：本轮输入准备（唯一准备点）──────────────────────────
let inputs = match prepare_turn_inputs(…)
```

三个"为什么"（同 [07 §3.1](./07-补充整合施工.md)）：

| 决策 | 理由 |
|---|---|
| 放在 `Gate::Proceed` **之后** | 闸门可能 `Exit` / `WaitForTools`；抽干后立刻退出 = 消费了队列却没用上 |
| 只在 `turn.tool_rounds > 0` | 首轮输入在**进入循环之前**已定（空闲路径由 `drain_inbox_once` 抽干；`chat/send` 路径由入口落库 + `single_message`）。首轮再抽一次是多余的，且会与 `single_message` 去重逻辑纠缠 |
| append 后**不动** `last_saved` | `persist_messages` 落 `[last_saved..]`；不动锚点 ⇒ 合并消息自动被下一次落库带上，**失败路径也不会丢** |

**为什么结构上不会插进工具批次中间**：`gate_turn` 只在 `turn.in_flight_tools` 为空时放行，
而级别 1（同步工具执行）下 `process_tool_calls_async` 是串行阻塞的——回到循环顶部时本批结果
**必然已齐**。因此本抽干点不可能落在 `assistant(tool_calls)` 与其 `tool` 结果之间（那会让部分协议直接 400）。

### 4.4 两条线：分界是一条纯函数

**结论：存储一份，输入分离，分界单点。**

| | **对话线** | **工作线** |
|---|---|---|
| 内容 | user 消息 + assistant **文本节点** | 推理 / 工具调用 / 工具结果 / Turn 容器 |
| 谁读 | `triage` / `reply` 的上下文 + 前端「对话」面板 | worker 的请求视图 + 前端「工作」面板 |

拟新增（与 `build_request_view` 同层，纯函数、可重放）：

```rust
/// 拟新增：session/context/conversation_view.rs
pub fn conversation_view(messages: &[ChatMessage], limit: usize) -> Vec<ChatMessage>;
```

**判据只认两条**：`role = user`，或（`role = assistant` 且是**不含 `tool_calls` 的文本节点**）。

三处共用（必须是同一份规则，否则会出现"界面看得到、插件看不到"的错位）：
`triage` / `reply` 的 `context_excerpt` / 前端「对话」面板 / 工作线请求视图的补集。

> **硬约束**：两个插件的请求视图里**不得出现** `tool_call` / `role = tool` / Turn 容器 / 推理节点。
> 工具结果可能含大块文件内容（几万 token 的源码、命令输出）——把它当"对话"喂进去，
> 既贵（每次判决都付）又错。**这条由投影函数保证，不由提示词保证**：进了包的东西，提示词管不住。

### 4.5 两个插件各自的上下文来源（各走既有通道）

| 来源 | 内容 | 通道 | 谁用 |
|---|---|---|---|
| **我知道什么** | 人格（setting）+ 会话记忆（session）+ 智能体记忆 / 工作区记忆（memory 双作用域） | `traverse(TRAVERSE_AVAILABLE_TOOLS)` → `list_system_prompts()` | `triage`（判"已知事实能否直答"）+ `reply`（措辞） |
| **现在在发生什么** | `RunSnapshot`：`status` / 在跑的工具 + 已用时 / 本轮已完成 / 失败原因 / 计划 | `ctx` 载荷，由 **session 投影** | 两者 |
| **我们聊过什么** | 对话线（§4.4），用它**自己的窗口** | `ctx` 载荷，由 **session 投影** | 两者 |

两个插件都从各自的 `traverse` 广播里取到 `get_model_provider()`（当次生效的 `ModelProvider`）——
**与 session 的取法是同一条路、同一组键**，只是各取各的，不共享状态。

> **运行现状不另建收集接口**：状态不是"注册型"贡献，它每次都在变；
> 且它的 owner 是**节点**（ADR-015 / ADR-025）。把它做成一个收集接口（`StatVisitor`）
> 就是给同一份事实造第二个来源，必然漂移——表现是"chat 说的和界面上显示的不一样"。

| 初稿 | 实际 | 为什么 |
|---|---|---|
| S1 加路由常量 `ROUTE_TRIAGE_DECIDE` / `ROUTE_REPLY_COMPOSE` | **推迟到 S2 / S3** | [`route.rs`](../../symbio/src/symbio_core/plugin/route.rs) 的模块文档：**不为「将来可能用到」的路由预置常量**，本模块只收有真实调用方的路径。S1 时 `session` 还没有调用点 ⇒ 加了就是零消费方的预留常量，正是那条规则要清掉的腐烂。S2 出现第一个调用方时再加 |

**契约形状**（判决是**枚举**，不是自由文本——否则编排层无法执行"必然启动 / 必然收尾"）：

```rust
/// triage 的入参：这一轮发生了什么
pub struct DecideRequest {
    pub session_id: String,
    pub utterance: Option<String>,
}

/// triage 的出参：这一轮该走哪条路（**闭集**）
pub enum Verdict {
    Answered { reason: String },   // 能直接答；reason 是**理由码**，决定措辞走模板还是生成
    Escalate { reason: String },   // 需要干活；reason 供 reply 选首响措辞
    Report,                        // 该汇报了；措辞由 reply 从运行现状组织
}

/// reply 的入参；出参是 `String`（一段面向用户的文本）
pub struct ComposeRequest {
    pub session_id: String,
    pub verdict: Verdict,
    pub max_chars: Option<usize>,
}
```

> **理由码是 `String` 而不是枚举**：理由码是**数据**（J1——能加取值就不加机制）。
> 新增一类"能直接答"的理由，只加一行码表，**不动 core**。
> 这与 `meta` 是自由 JSON 是同一条取舍。

**core 准入**：契约跨插件（`session` 生产，两个插件消费）⇒ 依赖方 ≥ 2，满足 ADR-023。
`Verdict` 的两个消费方在**本批就已成立**（`triage` 生产它、`reply` 消费它），
不依赖 S2 的 `session`。

**e2e `t20-plugin-skeleton.mjs`**（四条断言线，一条用例内覆盖）：

| 场景 | 编排 | 断言 |
|---|---|---|
| A 装配 | 空 homedir + 启用网关 | 两个插件目录与身份被补出来：`plugin_provider` / `plugin_name` == 目录名，`plugin_title` == 出厂标题（ADR-032 投影） |
| B 路由 | 经 `POST /api/v1/invoke`（外部客户端 → 容器 `route` 的真实边界） | `triage/decide` 恒 `{verdict: "escalate"}`、`reply/compose` 恒空串；未知子命令响亮失败 |
| C 零足迹 | 一轮真实工具回路（`toolCalls` → `vdfs_write`） | 工具真落盘；转写里**没有任何** `meta.surface` 节点 |
| D 卸载平凡值 | 停用两个插件后重启 | 两条路由都不可达；工具回路**照旧**跑通 |

> **为什么经网关而不是 CLI 命令**：路由是跨插件调用的地址，CLI 没有"直呼一条路由"的命令；
> 而 `POST /api/v1/invoke` 正是「外部客户端 → 容器 `route`」的真实边界（与前端同构）。
> 用一个测试专用的调用钩子只能证明"我写的那条路通"——那是同义反复。

**出口判据**：e2e 绿；门禁全绿（含 `plugin-entry-audit` 的 E-001–E-011）。

| 生成路径 | 发"我们刚才聊了什么" | 有 LLM 请求；答话节点进请求包（它不是 `exclude_from_context`） |
| 卸载平凡值 | 不挂载 `reply` | 无 对话面文本；worker 正文照旧——与今天逐字一致 |

---

### S4 · 中途汇报（G-B）

复用 [`heartbeat/mod.rs`](../../symbio/src/plugins/session/heartbeat/mod.rs) 的 15s tick，增加一条"该不该汇报"的判定：

```text
is_working
  && now - last_user_facing_at >= progress_interval_ms
  && progress_reports_this_turn < progress_max_per_turn
  && tool_rounds >= progress_min_rounds
        ⇒ route(ROUTE_TRIAGE_DECIDE, Progress) → Verdict::Report
        ⇒ route(ROUTE_REPLY_COMPOSE, Report)  → 写汇报节点
```

`ActiveSessionStateInner`（[`active.rs`](../../symbio/src/plugins/session/active.rs)）增 2 项会话内状态：
`last_user_facing_at`（毫秒时间戳）、`progress_reports_this_turn`（随 Turn 复位）。

`is_working` 是进程内状态 ⇒ 只有拥有该会话的进程会汇报，**天然不重复**。汇报不重试，失败即跳过。

> **触发权归编排层（`Decider`），措辞权归 `reply`**。两件事分开，才不会有"该说话时没人说话"。

**e2e `t23-progress-report.mjs`**：mock LLM 返回多轮 `toolCalls`（长任务）→ 断言中途出现
`meta.surface = "reply"` 的汇报节点；护栏生效（`progress_max_per_turn` 上限）；
`progress_enabled: false` 时零汇报节点。

---

### S5 · 呈现分界（G-D）

前端把工具 / 推理节点移出对话列，落到独立工作面板；对话面板只读对话线投影。
**架构改动：无**（纯呈现）。

**e2e `t24-panel-split.mjs`**：断言两个面板的订阅数据源不同（对话面板的帧集合不含 `tool_call`）。

> **不做这一步，S2/S3 的收益在界面上看不出来**——对话面的加入只会让现有那一列更乱。

---

### S6 · 调优

两个插件各自独立选模型 / 温度 / 提示词模板（各自的 `PLUGIN.yml`），可 A/B。
**架构改动：无。**

> 两个插件各自持有模型凭据，正是"一个能力一个插件"的直接回报：
> `triage` 可以用**最便宜最快**的分类模型，`reply` 用措辞更好的模型，互不牵制。

## 7. 平凡值与回退（J2）

### 7.1 配置平凡值

| 参数 | 完整值 | **平凡值** | 平凡值下 |
|---|---|---|---|
| `triage_enabled` | `true` | **`false`** | 全部输入直接进工具循环，行为与今天逐字一致 |
| `triage_rule_shortcut` | `true` | **`false`** | 规则表不生效，全部落快速档（慢但正确） |
| `reply_enabled` | `true` | **`false`** | 无 对话面文本；worker 正文照旧（今天的行为） |
| `progress_enabled` | `true` | **`false`** | 不汇报 |
| `supplements_enabled` | `true` | **`false`** | 一条消息 = 一轮 |
| `supplements_max_per_drain` | `20` | **`1`** | 退化为今天的 `pop_front` 一条 |
| `dialog_panel_split` | `true` | **`false`** | 单面板（今天的行为） |

**七个平凡值，任一个关闭都不影响其余功能。** 每一条都能被 e2e 直接验证（关掉它，行为与今天逐字一致）；
**无法被平凡值验证的配置项应删掉**——那是预留，不是参数。

> `supplements_enabled = false` 与 `supplements_max_per_drain = 1` **语义不同，都要有**：
> 前者关掉**整个特性**（含轮边界抽干），后者只限制**合并规模**。

### 7.2 卸载平凡值（比配置更强的一条）

**「没有这个插件，系统也能正确运行」的可执行形式不是配置开关，而是"不挂载"。**
配置开关验证的是"同一条代码路径的分支"，卸载验证的是"**插件边界真的存在**"——
后者才是"一个能力一个插件"的判据。

| 卸载 | 期望行为 | e2e |
|---|---|---|
| 不挂载 `triage` | 全部输入直接进工具循环（= 今天） | `t21` 的卸载用例 |
| 不挂载 `reply` | 无 对话面文本；worker 正文照旧（= 今天） | `t22` 的卸载用例 |
| 两个都不挂载 | = 今天的行为，**零差异** | 回归基线 |

> **卸载不是"关闭功能"，是"移除能力"**：它必须走**装配期**（不挂载 ⇒ 路由 `NotFound` ⇒
> session 按"缺插件"处理），而不是运行期读一个 `enabled` 字段。
> 两者的差别在于：前者证明**没有它也对**，后者只证明**有一个分支写对了**。

## 8. 边界（不做什么）

| 不做 | 一行理由 |
|---|---|
| 把判决与措辞塞进 `session` | 「少改动」度量的是**机制**（F1–F6），不是插件数；拆插件在 plan 记账下就是一行 `ActorSpec` |
| 把判决与措辞合成一个插件 | 两者**卸载语义不同**（§2.3 的对策表与翻转条件都写清了代价与退路） |
| 再往下切（首响 / 汇报 / 规则表 / 模板表各一个插件） | 卸载语义相同者不是新能力，是**数据**——拆开只是复制入口 |
| 插件直接写转写 | 转写只有一个写入者（ADR-020）；两个写入者会让 `seq` / 合帧 / 终态收敛同时失去单点保证 |
| 插件自己订阅状态、自行决定何时播报 | 触发条件归编排层（状态派生），插件只负责判决 / 措辞 |
| 新建 `StatVisitor` | 运行现状的 owner 是节点（ADR-015 / ADR-025），第二个来源必然漂移 |
| 为插件另建记忆 / 人格收集通道 | `register_system_prompt` 已是唯一注册入口，与 worker 共用同一批段 |
| 对话线与工作线各存一份 | 一条助手消息横跨两条线（正文 vs `tool_calls`），请求视图必须再 join 回来——混乱从呈现层搬到数据层 |
| 靠提示词让插件"别看工具结果" | 约束必须在投影层（C-D4）——进了包的东西提示词管不住 |
| 新增 `MessageType` 取值 | `meta` 是自由 JSON 且已有先例（`meta.kind = "context_nudge"`）——加字段是数据变化，改枚举是 schema 变化 |
| 引入全量 `caused_by` 溯源 | I2 是 v2 的**冻结契约，必须补**——它属"事件骨架"这一迁移步（[04 §3 第 1 步](./04-工程落地.md)），不在本场景批次内。本场景的 `meta.origin` 与 `caused_by` **同址**，补 I2 时不需要重写这些节点 |
| 让插件决定"要不要干活" | 判决插件只输出**枚举**，编排层执行；它无工具、无执行上下文 |
| 把 `session` 改名 `worker` | 插件名 = 地址（ADR-032），且 `worker` 已被 composite 容器占用；角色名写进 `PLUGIN.yml` 的 `plugin_title` |
