## 0. 一句话

**plan 覆盖了 chat/worker 分离的全部 15 个机制点；4 处缺口全是「0 新增机制键」。**
但落地形状要改：**「少改动」指的是机制（F1–F6 / 机制键 10 个）不动，不是插件数不动。**
因此对话面拆成**两个**插件——**一个能力一个插件**，且各自"没有它系统也能正确运行"。

```text
机制面：0 新增机制键 · F1–F6 不动              ← 这才是「少改动」的度量
插件面：+2 插件（classify · compose）· +2 路由 · +2 core schema 模块
能力面：+2 能力（JudgeIntent · ReplyFirst+ReplyAppend），各自可单独卸载
```

> **判据不是"拆得越多越好"**：一个候选插件若与既有插件**卸载语义相同**，它就不是新能力，
> 而是既有插件的**数据**（§2.4 的两张表）。本场景停在这两个。

## 2. 一处必须记住的判据：少改动 ≠ 不拆插件

### 2.1 两个量：架构改动 vs 插件数量

**「架构改动」与「插件数量」是两个不同的量。** 本仓冻结的是前者，不是后者：

| 量 | 定义在哪 | 加一个插件会变吗 |
|---|---|---|
| **机制面** | [03 §1](./03-演进与验证.md) 的 F1–F6：`Store` 签名 / 投影构造形状 / `ActorSpec` 5 字段 / 三条不变量 / 三个封闭集合 / 参数表键集 | **不变** |
| **机制键数** | [01 §8](./01-核心架构.md)：10 个顶层键，恒定 | **不变** |
| **插件数** | 施工视图（[05](./05-模块架构.md)）——**可独立替换的包** | **+1** |
| **地址数** | 插件名 = 挂载点 = 路由前缀（ADR-032） | **+1** |

在 plan 自己的记账里，**一个插件就是一行 `ActorSpec` + 一个挂载点**——即 `L-data`。
换句话说：**拆插件在 plan 的记账下根本不构成架构改动。**
把「插件数」当成「架构改动」的度量，正是本方案要避免的那类混淆。

### 2.2 拆插件反而更强

| | 塞进 session | **独立插件（本文）** |
|---|---|---|
| "无工具"的保证 | 调用点传空工具列表 + **CI 断言** | 插件不注册 `Capability` ⇒ **结构上不可能** |
| 判决/措辞的边界 | 靠"这个函数别写太多" | 插件边界 = 编译单元边界 |
| 独立开关 / 独立模型 | 靠 session 内的配置块 | 插件目录 = 配置目录（各自的 `PLUGIN.yml`） |
| 跨插件依赖 | 不涉及 | 经容器 `route` + 常量，E-007 / E-009 **已在守** |
| 长期维护成本 | 0（但 session 持续变胖） | 一个需要维护的地址 |

**多一个地址是成本，但它是划算的**：地址是**身份**（ADR-032），
而分形插件架构（ADR-001 / ADR-002）的全部收益正来自"用地址切分职责"。
**把功能堆进 session 来省一个地址，是在用一个架构资产换一点短期便利。**

### 2.3 代价与退路：多一跳

判决与措辞若在**一次** LLM 调用里完成，`Answered` 路径只需一跳；拆开后是**两跳**
（`classify` 分类 → `compose` 生成）。这对**目标 1（直接回答要快）**是逆风。

对策——把代价压到有界：

| 路径 | 谁出力 | LLM 次数 |
|---|---|---|
| 规则命中（问候 / 致谢 / 确认 / 空输入） | `classify` 规则表 ⇒ `compose` 模板表 | **0** |
| 需要干活（`Escalate`） | `classify` 规则或快速档 ⇒ `compose` **模板**首响（不等判定） | ≤ 1 |
| 模糊输入直答 | `classify` 快速档**分类**（300ms，比生成便宜一个数量级）⇒ `compose` 生成 | 2 |

> **翻转条件（写下来，免得变成信仰）**：D0 埋点若证明"模糊输入直答"这一路的
> 两跳比单跳慢得不可接受（p95 差距 > 一次分类的预算），就把两行 `ActorSpec`
> **合并为一个插件**——这是 `L-data` 级的切换，不是架构变更。

### 2.4 插件粒度：按能力切，切到"卸载后系统仍完整运行"

> **最好的架构是一个能力一个插件**：有这个插件就拥有这个能力，**没有它系统也能正确运行**，
> 插件之间互不相关，且每个插件尽量小。

**判据三条**（缺一不可）：

| # | 判据 | 可执行形式 |
|---|---|---|
| 1 | **一个能力一个插件** | 插件名 = 能力名；能力可枚举（对照 [01 §7](./01-核心架构.md) 的 7 个能力封顶） |
| 2 | **可卸载** | 卸掉它，系统**完整运行**（退化，而不是崩溃）——这是 J2 平凡值的**插件版** |
| 3 | **零相关** | 不 import、不持有兄弟插件（`plugin-entry-audit` 的 E-007 / E-009 **已在守**） |

#### 能力盘点（本场景）

| 能力 | plan 的枚举 | 落点 | 为什么 |
|---|---|---|---|
| 判断"能不能直接答 / 该不该派活" | `JudgeIntent` | **`classify` 插件**（新增） | 有独立平凡值：卸载 ⇒ 全部派活 |
| 说人话（首响 / 答话 / 汇报） | `ReplyFirst` · `ReplyAppend` | **`compose` 插件**（新增） | 有独立平凡值：卸载 ⇒ 无 对话面文本，worker 正文照旧 |
| 干活（工具循环 / 上下文 / 存储） | `DefineWork` · `ProduceArtifact` | `session`（现状） | — |
| 补充整体整合 | 无对应枚举 | `session`（现状） | 它是**输入通道的消费粒度**，与收件箱是同一机制；搬出去会破坏"唯一输入入口"（ADR-026 / 031） |
| 呈现分界 | — | 前端 | 不涉及后端插件 |

**所以本场景新增 2 个插件，不是一个。**

#### 为什么 `classify` 与 `compose` 是两个能力，而不是一个

它们**各自可卸载**，且卸载后系统完整运行：

| 卸载 | 结果 | 完整运行？ |
|---|---|---|
| 卸载 `classify` | 全部输入直接进工具循环（= 今天的行为） | ✓ |
| 卸载 `compose` | 没有 对话面产出的文本；worker 的正文照旧（= 今天的行为） | ✓ |
| 都卸载 | = 今天的行为 | ✓ |

**零相关**：`compose` 不知道 `classify` 存在，`classify` 也不知道 `compose`——
两者都由 session 在 `ctx` 里喂输入（`classify` 拿"判决所需"，`compose` 拿"判决结果 + 事实"）。
session 是唯一调用者，两条边都指向它自己，**插件之间没有边**。

#### 不继续往下切

**建构简单也是判据。** 两个插件各自的入口、`README.md`、`PLUGIN.yml` 都是真实成本，
因此**不**再往下切：

| 不再切 | 为什么 |
|---|---|
| 把"首响"与"汇报"拆成两个插件 | 两者卸载语义**没有差别**（都是"没有 对话面文本"），拆开只是复制入口 |
| 把"规则表"拆成独立插件 | 它是 `classify` 的**数据**（一张表），不是独立能力——按 J1，是数据就不是机制 |
| 把"模板表"拆成独立插件 | 同上，它是 `compose` 的数据 |

**判据**：一个候选插件若与既有插件**卸载语义相同**，它就不是新能力，而是既有插件的**数据**。

### 2.5 结论

**本场景新增 2 个插件（`classify` · `compose`），0 新增机制键，F1–F6 不动。**
两个插件在结构上都是"无工具、无副作用、无状态"的——C-D1 那条 CI 断言随之**不再需要**
（它们不注册 `Capability`，工具集里结构上不会有它们）。

## 4. 目标架构

### 4.1 插件与地址

| 插件 | 角色 | 挂载点 | 自有路由 | LLM 可见工具 | 配置文件 | VDFS |
|---|---|---|---|---|---|---|
| `session` | 编排 + 工作 | `<根>/session` | `session/chat/send` · `session/chat/abort`（不动） | 现有工具集（不动） | `<根>/session/PLUGIN.yml` | 有 |
| `classify`（**新增**） | 判决（能不能直接答 / 该不该派活） | `<根>/classify` | `classify/decide` | **无** | `<根>/classify/PLUGIN.yml` | **无** |
| `compose`（**新增**） | 措辞（首响 / 答话 / 汇报） | `<根>/compose` | `compose/wording` | **无** | `<根>/compose/PLUGIN.yml` | **无** |

**「无工具」是结构保证**：模型能调用的工具来自 `traverse(TRAVERSE_AVAILABLE_TOOLS)`
→ `CapabilityVisitor::register`。`classify` / `compose` **都不注册任何 `Capability`**，
因此模型的工具集里**在结构上不可能**出现它们——不需要 C-D1 那条断言。

两者都**不实现 `VdfsProvider`**：无状态、不持有任何地址，因此没有挂载视图。

### 4.2 两条调用边，都从 session 出发（插件之间无边）

```text
┌───────────────────────── worker 容器（composite，现状） ─────────────────────────┐
│                                                                                │
│                   route(ROUTE_TRIAGE_DECIDE)          ┌─────────────────────┐   │
│              ┌───────────────────────────────────────▶│ classify（新增）       │   │
│              │                                        │ · 规则表 + 快速档分类 │   │
│              │◀───────────────────────────────────────│ · 输出**枚举**，不产出 │   │
│              │        返回判决（Answered / Escalate）    │   面向用户的正文     │   │
│  ┌───────────┴────────┐                               └─────────────────────┘   │
│  │ session（编排+工作） │                               ┌─────────────────────┐   │
│  │ · 唯一编排者        │ route(ROUTE_REPLY_COMPOSE)    │ compose（新增）        │   │
│  │ · 唯一转写写入者     │──────────────────────────────▶│ · 模板表 + 生成      │   │
│  │ · 唯一输入入口      │◀──────────────────────────────│ · 输出**文本**，不做  │   │
│  └───────────┬────────┘        返回文本                 │   判决               │   │
│              │                                        └─────────────────────┘   │
└──────────────┴──────────────────────────────────────────────────────────────────┘
               ▲ 唯一输入入口（不变）：write(<根>/session/<sid>/inbox/<iid>)
           用户 / 前端 / CLI / telegram
```

**两条边都从 session 出发，且都是单向的**：`classify` 与 `compose` 都无副作用
（不写地址、不派活、不起后台任务）⇒ 都不需要回调 session ⇒ 转写写入者仍是唯一的；
`classify` 与 `compose` 之间**没有边**，互不知道对方存在（§2.4 的"零相关"）。

**职责分界**（一条判据）：`classify` 只输出**枚举**（可被判定的东西），
`compose` 只输出**文本**（可被展示的东西）。**判决不做措辞，措辞不做判决。**

**调用形状**（与 `agent_run` → `session/chat/send` 同款，两个插件同形）：

```rust
// session 侧：判决
let mut c = ctx.fork();
c.set(PATH, ROUTE_TRIAGE_DECIDE.to_string());   // 常量，不写字面量（plugin-entry-audit E-003）
c.set(SESSION_ID, session_id.clone());
c.set_payload(DecideRequest { … })?;
let verdict: Verdict = parent.clone().route(c).await?.payload()?;

// session 侧：措辞
let mut c = ctx.fork();
c.set(PATH, ROUTE_REPLY_COMPOSE.to_string());
c.set(SESSION_ID, session_id.clone());
c.set_payload(ComposeRequest { verdict, snapshot, context_excerpt, … })?;
let text: String = parent.clone().route(c).await?.payload()?;
```

`parent` 是 `ChatOrchestrator::parent: Option<Arc<dyn Plugin>>`（[`chat_loop/state.rs`](../../symbio/src/plugins/session/chat_loop/state.rs)），
**已经是容器句柄**——本方案不需要新增任何持有关系（E-007 天然满足）。

### 4.3 轮边界抽干需要一次句柄注入

`run_chat_loop` 是自由函数，只拿得到 `ChatOrchestrator`，而抽干要读 `active_mgr` 与 `config`
——两者都在 `SessionPlugin` 上。**既有范式已经解决了这个问题**：`CompressionEmitter`
（[`chat_loop/state.rs`](../../symbio/src/plugins/session/chat_loop/state.rs)）就是一个
"持 `Arc<SessionPlugin>` + `Arc<ActiveSessionState>` 的持有者"。照此加一个**同形状**的
`SupplementDrain`，挂进 `ChatOrchestrator`（与已有的 `compression: Option<Arc<…>>` 并列）。

> 插入点（`gate_turn` 之后 / 步骤 3 之前）、三条"为什么"、以及"为什么结构上不会插进工具批次
> 中间"——**owner 是 [07 §3](./07-补充整合施工.md)**，本文不复述。S0 已按它落地。

### 4.4 两条线：分界是一条纯函数

**结论：存储一份，输入分离，分界单点。**

| | **对话线** | **工作线** |
|---|---|---|
| 内容 | user 消息 + assistant **文本节点** | 推理 / 工具调用 / 工具结果 / Turn 容器 |
| 谁读 | `classify` / `compose` 的上下文 + 前端「对话」面板 | worker 的请求视图 + 前端「工作」面板 |

落点（与 `build_request_view` 同层，纯函数、可重放）：

```rust
/// session/context/conversation_view.rs
pub fn conversation_view(messages: &[ChatMessage], limit: usize) -> Vec<ChatMessage>;
```

**判据只有两条**：`role = user` 且是**文本节点**，或 `role = assistant` 且是**文本节点**。
`role` 挡掉工具结果（`tool`，可能含几万 token 的源码或命令输出）与系统注入（`system`）；
「文本节点」挡掉 `tool_call` / `reasoning` / `turn` / `compression` / `user_prompt`。

**位置（`parent_id`）不参与判定**——助手说的话有**两种**位置：`turn` 的子 `Text` 是
**回复正文**（用户真正读到的那段回答），根级的 assistant 文本是「单独说的一句话」
（首响 / 汇报）。两者都是"助手说过的话"，都得在对话线上。初稿只认根级，代价是
**插件看不到自己上一轮答过什么**（用户追问「那 LICENSE 呢？」时，判决只看得到问句）、
**前端「对话」面板看不到回答本身**（回答在 `turn` 组里）——那就不成其为对话。
由此，工作线的边界是**排除法**（不属于对话线的都是工作），不是位置法。

三处共用（必须是同一份规则，否则会出现"界面看得到、插件看不到"的错位）：
`classify` / `compose` 的请求 `context` / 前端「对话」面板 / 前端「工作」面板（根级的补集）。

> **硬约束**：两个插件的请求视图里**不得出现** `tool_call` / `role = tool` / Turn 容器 / 推理节点。
> 工具结果可能含大块文件内容（几万 token 的源码、命令输出）——把它当"对话"喂进去，
> 既贵（每次判决都付）又错。**这条由投影函数保证，不由提示词保证**：进了包的东西，提示词管不住。

### 4.5 两个插件各自的上下文来源（各走既有通道）

| 来源 | 内容 | 通道 | 谁用 |
|---|---|---|---|
| **我知道什么** | 人格（setting）+ 会话记忆（session）+ 智能体记忆 / 工作区记忆（memory 双作用域） | `traverse(TRAVERSE_AVAILABLE_TOOLS)` → `list_system_prompts()` | `classify`（判"已知事实能否直答"）+ `compose`（措辞） |
| **现在在发生什么** | `RunSnapshot`：`status` / 在跑的工具 + 已用时 / 本轮已完成 / 失败原因 / 计划 | `ctx` 载荷，由 **session 投影** | 两者 |
| **我们聊过什么** | 对话线（§4.4），用它**自己的窗口** | `ctx` 载荷，由 **session 投影** | 两者 |

两个插件都从各自的 `traverse` 广播里取到 `get_model_provider()`（当次生效的 `ModelProvider`）——
**与 session 的取法是同一条路、同一组键**，只是各取各的，不共享状态。

> **运行现状不另建收集接口**：状态不是"注册型"贡献，它每次都在变；
> 且它的 owner 是**节点**（ADR-015 / ADR-025）。把它做成一个收集接口（`StatVisitor`）
> 就是给同一份事实造第二个来源，必然漂移——表现是"chat 说的和界面上显示的不一样"。

| `Report` 的措辞由本批产出 | 本批**没有**产线（模板表不给 `Report` 行） | 汇报的措辞要从**运行现状**组织（在跑什么、跑了多久），那个快照到 S4 才有生产者。编一句必然与界面上的真实进展不符，比不说更糟 |
| e2e 只写了"答话节点进请求包" | 同时断言 **`Escalate` 首响不进请求包** | 首响是**界面开场白**，不是模型的对话内容；它紧跟用户消息，进了包会让线上出现连续两条 `assistant`（部分协议直接 400）。两个标记回答两个问题，必须**分开验** |

**三处相对初稿的收窄**（机制层面的展开见 `chat_loop/progress.rs` 的模块文档）：

| 初稿 | 实际 | 为什么 |
|---|---|---|
| 复用 `heartbeat/mod.rs` 的 15s tick | 触发点在**轮边界**（`run_chat_loop` 步骤 2d） | ① **写入者唯一**：汇报节点必须落在 `context.messages` 上才会被 `persist_messages` 带上（ADR-020），而那个列表是主循环的**局部变量**，后台任务够不着；② 判定所需的量都在主循环里，搬出去就是给同一份事实造第二个来源；③ 15s 粒度会让这个特性忽快忽慢，也让 e2e 依赖挂钟 |

| `route(ROUTE_TRIAGE_DECIDE, Progress) → Verdict::Report` | `session` **自己判出** `Report` | `classify` 手里没有"静默多久 / 跑了几轮 / 说过几次"这些量，也无法说"不汇报"（三个变体没有一个表示保持沉默）。让它盖章等于把一条恒真的判定伪装成语义判断：多一次 LLM 往返，还多一个"判错就沉默"的失败面 |

> "什么时候判"是同一件事，都归手里有那些量的那一方。
>

> 节点的运行态直接呈现，不经过本插件。

| 线 | 编排 | 断言 |
|---|---|---|
| A 长任务 | 3 轮工具（2 个轮边界），判决关掉 | 恰 2 条根级 `surface=compose` / `reason=progress` 节点（逐条查落点与剔除标记）；**总请求数仍是 3**——若汇报去问模型就会是 5，那正是这条要拦的 |
| B 配额护栏 | 同上 + `progress_max_per_turn=1` | 恰 1 条，且是**最早**那一次（护栏只封顶，不推迟第一次）；工具回路照旧两轮 |

> 那个沉默的失效面。实时面同理：工作节点若不再进实时面，工作列会空掉，而"没来"与

`protocol-mirror-audit` 守的是常量 / 枚举取值 / 字段名，**不守谓词**。因此这份规则
的镜像只能靠**两侧各自单测穷举**——**改规则必须同时改两处**。

> **不做这一步，S2–S4 的收益在界面上看不出来**——对话面的加入只会让现有那一列更乱。

### S6 · 调优

> **已落地**。两个插件各自独立选模型 / 提示词（各自的 `PLUGIN.yml`），可 A/B。
> **架构改动：有（一处，核心面）**——初稿写的"无"是**错的**，核对后不成立，见下。

**初稿为什么错**：`CapabilityVisitor` 的模型槽原本是**单槽**
（`provider: Arc<RwLock<Option<Arc<dyn ModelProvider>>>>`）。`model` 插件在 traverse 时
只按**会话选定的**那个 provider 注册唯一生效实例，重复注册即覆盖。于是插件只能拿到
**会话选定的**那一个模型——"各插件独立模型"在代码里**没有任何落点**，
写进 `PLUGIN.yml` 也只是个被忽略的键。这条不修，S6 就只剩提示词模板（半个能力）。

**两条判据**（写在这里，免得下次又被"改法看起来更小"带走）：

1. **一次注册，不是两次**。生效者与目录必须**同一次**进 visitor：拆成 `set_active()` +
   `set_catalog()` 就会允许"生效者不在目录里"这个**没有错误信号的非法状态**（会话报
   「未找到可用的 Model Provider」，而配置页一切正常）。合成一次 ⇒ 该状态构造不出来。
2. **降级方向只有一处定义**。`resolve_model_provider` 的默认实现是**唯一**降级点
   （"配了取不到 ⇒ 落回生效者"）。插件各自 `match` 一遍必然漂移（一个落回、一个报错、
   一个用默认），而这类漂移在单插件单测里全是绿的。

**三处相对初稿的收窄 / 展开**：

| 初稿 | 实际 | 为什么 |
|---|---|---|
| "架构改动：无" | **有**：模型槽 单槽 → 生效者 + 目录 | 见上：单槽下"独立模型"没有落点 |
| "各自独立选**温度**" | **不新增字段**——温度本就是 provider 条目的参数（`<根>/model/<id>/provider.json`） | 换一个条目就是换温度。给插件再加一个 `temperature` 键 = 同一件事两个 owner，冲突时无判据 |
| "提示词模板" | 提示词**可覆盖，但空串与缺席同义**（`non_empty` 归一） | 设置页清空输入框得到 `""`。若当成"配了个空提示词"，`compose` 的指令段会变成空文本 ⇒ 答话失去**全部约束**且日志正常 |

**降级而不失效**：写错的 provider id 落回会话选定值，判决 / 措辞整条产线**照常发生**；
代价是 typo **没有错误信号** ⇒ 调用方必须把"选中了哪个模型"记进日志（两个插件都走
`plugin_debug!`）。这是本批唯一"沉默的失效面"，`t25` 的 C 线钉的就是它。

**无法被平凡值验证的配置项应删掉**——那是预留，不是参数。

> **四个模型 / 提示词键的平凡值是"缺席"而不是某个具体值**：它们没有"关掉"这回事——
> 不写就是今天的行为（用会话选定的模型、用内置提示词）。**空串与缺席同义**（`non_empty`
> 归一）：设置页清空输入框得到的是 `""`，它必须落回内置值，否则 `compose.instruction` 会
> 变成"用空文本当指令"——答话失去全部约束且日志正常。写了一个**取不到**的 provider id
> 也算落回会话选定值（**降级而非失效**，见 §5 S6），但那**不是**平凡值：它多了一条
> 静默的失效面（typo 无错误信号），必须靠 `plugin_debug!` 留痕。三档（不写 / 写对 / 写错）
> 都在 `t25` 里各有断言。

> **验法各归其主**：后端配置（插件 / 会话）的平凡值由 e2e 关掉一个键直接验证
> （`t21`–`t25`）；`dialog_panel_split` 是**前端偏好**——不落转写、不经后端，e2e 无从观测
> （`t24` 只验后端事实）。它的平凡值由 `stores/__tests__/appearance.spec.ts` 验：关掉 ⇒ 单列
> 渲染同一批节点、选择活过重启、旧数据缺键落出厂值。**验法不同，判据相同**：关掉之后
> 用户看到的东西与引入分栏之前逐字一致。
>
> 键名与落点：前端 `dialogPanelSplit`（`localStorage` 的 `symbio.appearance`），
> 不是插件配置键——它没有后端消费者，写进插件配置就是给同一件事造第二个 owner。

> **"完整值"与"出厂默认"是两件事**：本表答的是"这个参数能取到什么、平凡值是什么"。
> 出厂默认的判据是**用户可见层面完整**：`classify_enabled`、`compose_enabled` 与
> `progress_enabled` 的出厂默认都是 `true`（`progress_enabled` 自 S4 起）——只交付
> 机制的那一批（S2）曾把 `classify_enabled` 留在 `false`，因为那时「你好」会变成沉默
> （回归，不是"少说一句"）。S3 落 `compose` 时一并翻 `true`，那正是这个开关唯一的
> "生效"动作（见 §5 S2 的"三处收窄"表）。
>
> `progress_enabled` 没有两段式：它的三个上界（间隔 / 最少轮次 / 每轮配额）各自都有
> 有意义的默认值，打开它不会把任何东西变沉默，也不会让短任务被打扰——**能一次交付
> 完整行为的那一批，就一次交付**。

> **两级开关各归其主**：`classify_enabled` 在 `SessionConfig`（**调用方**的配置面：要不要判决）；
> `rule_shortcut` 在 `ClassifyConfig`（**插件自己**的配置面：判决内部要不要先用规则表挡一层）。
> 调用方不该知道后者——它一知道，插件内部策略就成了跨插件契约。
> 这与 [06 §4.2](./06-会话响应性落地.md)「插件目录 = 配置目录」的对照表是同一条判据。

> `supplements_enabled = false` 与 `supplements_max_per_drain = 1` **语义不同，都要有**：
> 前者关掉**整个特性**（含轮边界抽干），后者只限制**合并规模**。

### 7.2 卸载平凡值（比配置更强的一条）

**「没有这个插件，系统也能正确运行」的可执行形式不是配置开关，而是"不挂载"。**
配置开关验证的是"同一条代码路径的分支"，卸载验证的是"**插件边界真的存在**"——
后者才是"一个能力一个插件"的判据。

| 卸载 | 期望行为 | e2e |
|---|---|---|
| 不挂载 `classify` | 全部输入直接进工具循环（= 今天） | `t21` 的卸载用例 |
| 不挂载 `compose` | 无 对话面文本；worker 正文照旧（= 今天） | `t22` 的卸载用例 |
| 两个都不挂载 | = 今天的行为，**零差异** | 回归基线 |

> **卸载不是"关闭功能"，是"移除能力"**：它必须走**装配期**（不挂载 ⇒ 路由 `NotFound` ⇒
> session 按"缺插件"处理），而不是运行期读一个 `enabled` 字段。
> 两者的差别在于：前者证明**没有它也对**，后者只证明**有一个分支写对了**。

## 8. 边界（不做什么）

| 不做 | 一行理由 |
|---|---|
| 把判决与措辞塞进 `session` | 「少改动」度量的是**机制**（F1–F6），不是插件数；拆插件在 plan 记账下就是一行 `ActorSpec` |
| 把判决与措辞合成一个插件 | 两者**卸载语义不同**（§2.3 的对策表与翻转条件都写清了代价与退路） |
| 再往下切（首响 / 汇报 / 规则表 / 模板表各一个插件） | 卸载语义相同者不是新能力，是**数据**——拆开只是复制入口 |
| 插件直接写转写 | 转写只有一个写入者（ADR-020）；两个写入者会让 `seq` / 合帧 / 终态收敛同时失去单点保证 |
| 插件自己订阅状态、自行决定何时播报 | 触发条件归编排层（状态派生），插件只负责判决 / 措辞 |
| 新建 `StatVisitor` | 运行现状的 owner 是节点（ADR-015 / ADR-025），第二个来源必然漂移 |
| 为插件另建记忆 / 人格收集通道 | `register_system_prompt` 已是唯一注册入口，与 worker 共用同一批段 |
| 对话线与工作线各存一份 | 一条助手消息横跨两条线（正文 vs `tool_calls`），请求视图必须再 join 回来——混乱从呈现层搬到数据层 |
| 靠提示词让插件"别看工具结果" | 约束必须在投影层（C-D4）——进了包的东西提示词管不住 |
| 新增 `MessageType` 取值 | `meta` 是自由 JSON 且已有先例（`meta.kind = "context_nudge"`）——加字段是数据变化，改枚举是 schema 变化 |
| 引入全量 `caused_by` 溯源 | I2 是 v2 的**冻结契约，必须补**——它属"事件骨架"这一迁移步（[04 §3 第 1 步](./04-工程落地.md)），不在本场景批次内。本场景的 `meta.origin` 与 `caused_by` **同址**，补 I2 时不需要重写这些节点 |
| 让插件决定"要不要干活" | 判决插件只输出**枚举**，编排层执行；它无工具、无执行上下文 |
| 把 `session` 改名 `worker` | 插件名 = 地址（ADR-032），且 `worker` 已被 composite 容器占用；角色名写进 `PLUGIN.yml` 的 `plugin_title` |
