# 06 · 落地桥接方案 —— 从现行体系到 v2 目标态

> **本文件回答一个问题**：v2 目标态（[01](./01-核心架构.md)–[05](./05-模块架构.md)）与
> **Symbio 现行代码**（[CURRENT.md](../CURRENT.md)）之间差距在哪、按什么顺序补、
> 怎么补才**不动现行架构**、补完之后**扩展能力才真的长出来**。
>
> **读者**：要开工的人。读完本文应能直接排期，不需要重读 v2 全五篇。
>
> **纪律**：本文**不复制** v2 的机制论证。凡是"为什么 1 个原语""为什么 J1/J2/J3"，
> 一律链接 [01](./01-核心架构.md) / [README §3](./README.md)。本文只写**差距、路径、判据**。

---

## 0. 一句话结论

**现行 Symbio 已经拥有 v2 的"骨架"和"血肉"，缺的是把它们连成"一条主动脉"。**

| v2 概念 | 现行对应物 | 状态 |
|---|---|---|
| `Store`（唯一原语） | `SessionStore` + `VdfsProvider` + `MemoryFile` | **分散在三处，各自成体系** |
| `Event`（共享契约） | `ChatMessage` + `PluginFrame` + `VdfsChange` | **有三套方言，无统一信封** |
| `Projection`（签名约束） | `chat_session/read.rs` 的滑动窗口 / 归一等纯函数 | **存在但未收口、未受约束** |
| `Actor`（一等概念） | `SessionPlugin` 的 `chat_loop` | **只有一个 Actor，且是硬编码的** |
| I1 单通道 | 有（`Plugin` trait 唯一入口 + VDFS） | **部分成立，无断言** |
| I2 无溯源不声明 | **无**（无 `caused_by`） | **缺失** |
| I3 到点必答 | 有（`WorkingGuard`/`AbortGuard`/兜底） | **成立，但未升级为不变量** |
| `Principal` / `grants` / `vis_scope` | **无**（仅预留键 `plugin_grants`，不强制） | **缺失** |
| 参数表 / 机制键 | `SessionConfig` + `PLUGIN.yml` 各插件自管 | **无统一坐标，无法审计守恒律** |

**桥接策略一句话**：**不新建 Event Log 去替换现有存储，而是把现有存储"提升"为
Event Log 的一个视图**——用**一个信封 + 一张投影表 + 一个断言目录**拿到 v2 的扩展性，
其余全部沿用现行代码。

> **代价必须说清**：这条路**放弃** v2 声称的"1 个原语"的纯粹记账，
> 换来的是**零重写、可增量交付**。诚实记账见 §6。
> 若追求纯 v2 记账，代价是重写 `session`（17809 行）/ `vdfs`（3012 行）/
> `providers/memory`（388 行）等核心实现（**实测实现行数**，不含测试），
> 外加前端链路——见 §6.2 的对照。

## 1. 差距分析：现行 vs v2（逐条可核对）

### 1.1 骨架层（已经在位，不需要改）

这三块**已经符合 v2**，是本方案的**既得资产**，不要动：

| 现行机制 | 为什么它已经是 v2 要的形状 | 佐证 |
|---|---|---|
| **分层插件树**（`Plugin` trait 唯一入口，容器剥离前缀转发） | 就是 v2 的 **I1 单通道**：一切协作经事实源，两主体无直连 | [OVERVIEW.md](../architecture/OVERVIEW.md)、[ADR-001](../DECISIONS.md) |
| **VDFS 统一资源面**（13 操作，`VdfsProvider`） | 就是 v2 的 **`Store` 读取面** + **可见域**雏形 | [design/vdfs.md](../design/vdfs.md)、ADR-011/028/030 |
| **`session` 唯一编排入口 + `chat_loop`** | 就是 v2 的 **Actor 装配线**（读视图 → 决策 → 写事件） | ADR-003、[session/README.md](../../symbio/src/plugins/session/README.md) |
| **`WorkingGuard` / `AbortGuard`**（RAII 保证收敛） | 就是 v2 的 **I3 到点必答**的运行时保障 | `session/orchestrator.rs` |
| **`MemoryFile` 两道闸门**（写拒绝 / 注入截断） | 就是 v2 的 **J2 平凡值纪律** + 可见域 | [providers/memory](../../symbio/src/providers/memory/mod.rs) |
| **`inventory` 静态注册 + `creator` 注册表** | 就是 v2 的 **"新能力 = 加数据行"**的现成载体 | ADR-007/036 |
| **`PLUGIN.yml` 逐插件配置 + 详情方言** | 就是 v2 的 **参数表的现行形态**（只是未统一坐标） | ADR-024/032 |

> **两处必须纠正的"同名异物"**（不纠正会在排期时按错的名字找代码，找不到）：
>
> | v2 的名词 | 现行代码里的东西 | 结论 |
> |---|---|---|
> | v2 `Capability` = **7 个权威动作**（`JudgeIntent` / `ReplyFirst` / `ProduceArtifact` …）用于**权限矩阵的键** | 代码里 `Capability` 是 **LLM 可见工具**的抽象（`CapabilityMeta` / `CapabilityCategory`：Chat/FileOperation/Mcp…），是**给模型看的工具分类** | **同名异物。** v2 的 7 能力枚举**在代码里不存在**；权限矩阵也**不存在** |
> | v2 `grants` / `Principal` / `vis_scope` | 代码里**只有**一个预留键 `PLUGIN_KEY_GRANTS`（ADR-032：「本期只定义与解析、**不强制**」），无矩阵、无 `Principal` 类型 | **未落地。** 属 §1.2 缺口，不是既有资产 |
>
> 这两条是 v2 与现行体系**最大的**概念落差。**本方案的排期不假设它们存在**——
> 凡是 v2 需要"授权成对"的地方，本方案先用**视图层过滤**（VDFS 可见性）顶替，
> 授权矩阵作为独立增量（见 §3 的 B3 备注）。

> **关键判断**：**不该**按 v2 的字面去重写这些。它们承担的功能与 v2 的目标态**等价**，
> 只是**命名与记账口径不同**。按字面重写是纯粹的净损失。

### 1.2 主动脉层（缺失，本方案要补的三件）

| # | 缺口 | 现行形态 | 后果 | 补法 |
|---|---|---|---|---|
| **G-A** | **无统一事件信封** | `ChatMessage` / `PluginFrame` / `VdfsChange` 三套方言；会话事件只活在自己的 `messages.json` | 无法跨域审计；无法做 I2；新能力**没有共同的"事实格式"可依附**——这正是 v2 §13.5 说的"契约在中心"的反面 | §2.1 加**一个** `Fact` 信封 |
| **G-B** | **投影散落、未受约束** | 滑动窗口住 `chat_session/read.rs`，淡化住 `context/view.rs`，压缩住 `context/pipeline.rs`——都是"能读任意东西"的普通函数 | 回放不确定；改一处不知影响哪；**无法给新能力提供"平铺测试"的落点** | §2.2 收口成**投影表** + 签名约束 |
| **G-C** | **Actor 硬编码** | `chat_loop` 把"用户消息→模型→工具→收尾"写死在一个大函数里 | 新 Actor（检索者 / 巩固者 / 判定者 / 仲裁者）**无处安放**，只能往 `chat_loop` 里塞 `if` | §2.3 抽象出 **ActorSpec 行**，`chat_loop` 退化为装配器 |
| **G-D** | **无授权矩阵** | 只有预留键 `PLUGIN_KEY_GRANTS`（ADR-032：定义但不强制）；无 `Principal` 类型、无 `caused_by` | **越权不可检测**（静默失效）；多主体（S08）一来就必然踩 | 视图层过滤先顶替；S08 排期时**同批**交付动作级授权（§2.3 备注） |

**这四条就是 v2 相对现行体系真正多出来的东西**，其余都是记账口径差异。

### 1.3 断言层（缺失，代价所在）

v2 的"扩展永不推翻"靠**守恒律审计**（`mechanism_growth.rs` / `scenario_ladder.rs`）。
现行体系**没有任何对应物**：没有统一参数表，所以没有可审计的"机制键集"。

> 这对应 v2 [03 §6 §7.3 G3/G5/G7](03-演进与验证.md)。**不补这一层，
> 前面两条补出来的扩展性会在两个迭代内悄悄退化。** 见 §3.3。

## 2. 方案：三件事，全部是"加法"

> **总原则**：**新增层，不改写既有层。** 每件事都可以独立交付、独立回滚，
> 且交付后**旧代码不动也能跑**（J2 平凡值）。
>
> **顺序不可颠倒**：A 是 B/C 的前提（没有统一事实格式，投影与 Actor 就没有共同的输入）。

### 2.1 第一件：`Fact` 信封 —— 把三套方言统一到一个只读的公共面

**不是**新建一个 Event Log 去替换 `messages.json`。**是**给已有事件加一个**公共只读视图**。

```rust
// 新增：core 里一个域（照 symbio_core/README.md 的域规范，域名 `fact`）
/// 所有可观测事实的统一信封。**只读**——写入仍走各自原有路径。
pub struct Fact {
    /// 全局单调序号。**跨会话、跨插件**唯一。
    /// 由现有 `SessionStore` 的 seq 分配点扩为进程级计数器。
    pub seq: u64,
    /// 事实类型：`turn.user_message` / `task.completed` / `memory.encoded` / `conation.expressed` …
    /// 收敛为 v2 [01 §6] 的 10 实体 × 5 动词网格。
    pub kind: FactKind,
    /// 谁产生的（v2 的 `Principal`）。现行 `actor` 字段语义等价。
    pub principal: Principal,
    /// **溯源**（v2 的 I2）。现行缺失，本方案补上。
    pub caused_by: Option<u64>,
    pub at_ms: u64,
    /// 载荷：沿用现行 schema（`ChatMessage` / `VdfsChange` …）——**不新建第二套结构**。
    pub payload: FactPayload,
}
```

**关键设计取舍（决定本方案是否"改动更小"）**：

| 传统做法 | 本方案 | 为什么 |
|---|---|---|
| 新建 Event Store，把 `messages.json` 迁进去 | **`messages.json` 保持不动**，`Fact` 是一条**派生视图**：`facts(from)` 从现有存储读出后包上信封 | 迁移全量历史数据的风险，换不来任何 v2 未承诺的能力 |
| 要求所有插件改写自己的事件 | 只有**需要跨域协作**的事实才必须实现 `FactSource`；其余**平凡值 = 不实现**（J2） | 新能力只在自己域内时，零迁移 |
| 一次到位做全局 seq | **进程级 seq 从 `SessionStore` 的分配点提升**，其余域先给 `seq = 0` 占位 | 平凡值下仍完整运行 |

**这一件的收益**：v2 §13.5 说的"契约数从 O(N²) 降到 O(N)"——新增 Actor / 投影
**只需要知道自己读哪些 `FactKind`、写哪些 `FactKind`**，不需要知道任何既有模块。

**交付判据**：
1. `Fact` 是只读的（无 `write` 方法）——**编译期**保证；
2. 现有全部会话可无损派生为 `Fact` 序列（往返测试：`messages.json → facts → messages` 逐字节相同）；
3. 不实现 `FactSource` 的插件**照常运行**（平凡值用例）。

### 2.2 第二件：投影表 —— 把散落的纯函数收口成一张受约束的表

**不是**把 `context/view.rs` 等搬到新目录。**是**给它们**登记 + 约束**。

```rust
// 沿用 v2 [01 §1.4] 的私有构造签名约束（字段私有 + 唯一入口）
pub struct Projection<V> { /* 私有 */ }
impl<V: 'static> Projection<V> {
    /// 唯一构造入口：形参表就是纯净性的全部表达。
    /// 拿不到 &Store / &mut / Clock / Principal；返回 View 而非 Result。
    pub fn new<F>(f: F) -> Self
    where F: Fn(&[Fact], Timestamp, Budget) -> View<V> + Send + Sync + 'static;
}
```

**收口清单（现行纯函数 → 登记为投影，行为零改动）**：

| 现行位置 | 登记为 | 消费者 | 平凡值 |
|---|---|---|---|
| `chat_session/read.rs::sliding_window` | `projection = snapshot` 的一个参数 | `chat_loop` | 保留**裸函数**（不登记也能跑） |
| `context/view.rs::fade_aged_content_nodes` | `projection = display` 的参数 | 请求视图 | 同上 |
| `context/pipeline.rs` 各步 | `projection = checkpoint` 的参数 | 崩溃恢复 | 同上 |
| 新增 `recall`（S06） | `projection = recall` | 检索 Actor | 平凡值 = `snapshot`（退化成只看当前窗口） |
| 新增 `conation`（S12） | `projection = conation` | 闸门 | 平凡值 = `enabled: false`（退化成纯响应式） |

**关键设计取舍**：

| 传统做法 | 本方案 | 为什么 |
|---|---|---|
| 强制所有投影必须经 `Projection::new` | **新增投影必须经 `new`；既有函数保持裸函数** | 一次性改写全部纯函数 = 大 diff 且无行为收益；新能力从第一天起就受约束即可 |
| 建 `projections/` 独立 crate | **投影仍住各自插件**，只是**登记进一张进程级表**（沿用 `inventory`） | 物理搬迁违反 ADR-039 的"域内落位"；登记表足够提供统一寻址 |
| 用 CI 扫描纯度（v2 二级强制） | **一级（构造约束）先上，二级扫描随 C26 后续补** | 一级就拦住了"顺手写一笔"（形参表）；二级是补盲区，可以后置 |

**这一件的收益**：新能力（检索 / 巩固 / 判定）**不再需要往 `chat_loop` 里加代码**，
只需要**登记一个投影 + 加一行 ActorSpec**——这正是 v2 §5 说的"模块能不断扩充而不改架构"。

**交付判据**：
1. 投影双跑逐字节相同（对应 v2 C6 / N1）；
2. `projection` 签名不含 `&Store` / `&mut` / `Clock`（对应 v2 C5 / C25）；
3. 既有裸函数**不被强制登记**，系统照常运行（J2）。

### 2.3 第三件：ActorSpec 行 —— 让 `chat_loop` 从"实现"退化为"装配"

**不是**重写 `chat_loop`。**是**把它内部**已经存在的模式**命名出来，并允许**注册新的**。

```rust
/// 一行 ActorSpec（v2 [01 §4] 的 5 个字段，**从现行 chat_loop 反推**，不是凭空设计）
pub struct ActorSpec {
    pub principal: Principal,          // 现行：session_id / agent_id（**无 Principal 类型，需新建**）
    pub pattern: Pattern,              // 现行 chat_loop 实际是 reasoner
    pub capabilities: Vec<Action>,     // 注意：**不是** core 的 Capability（那是工具分类）；
                                       //       是 v2 的 7 个权威动作，**需新建**，见下方备注
    pub budget_ms: u64,                // 现行：已有 max_tool_rounds / 超时兜底
    pub scope: Scope,                  // 现行：会话 / 子智能体（ADR-026 已是递归）
}
```

> **`capabilities` 字段的诚实备注**：v2 的 7 个权威动作（`JudgeIntent` / `ReplyFirst` /
> `ProduceArtifact` / `AssertVerification` / `AssignWork` / `DefineWork` / `ReplyAppend`）
> 在现行代码里**不存在**（见 §1.1 的同名异物表）。**本方案的第一版不引入它**——
> 第一版只有 `principal` / `pattern` / `budget_ms` / `scope` 四个字段，
> 权限靠**视图层过滤**（A 的记忆默认对 B 不可见，因为 B 的召回投影只读自己的可见域）。
> **动作级授权矩阵是独立增量**，且必须在**第一次出现"两个主体可能越权"之前**落地——
> 这是 v2 [01 §7] 说的"权限必须第零天就位"（它是**静默失效**的，事后补要重写历史事件）。
> 判定条件：**当 S08（多主体）进入排期时，授权矩阵与它同批交付，不得延后。**

**现行 `chat_loop` 已经隐含一个 Actor**：它就是 `{ pattern: reasoner, budget_ms: 60000, scope: root }`。
本方案做的是：

1. **把它显式声明为一行**（零行为变更——只是把散落的配置收进一个结构）；
2. **允许注册更多行**（检索者 / 巩固者 / 判定者）；
3. **`chat_loop` 改为按 `ActorSpec` 分发**——从"一个大函数"变成"一张表 + 一个执行器"。

**最早应该注册的三个新 Actor（按价值排序）**：

| Actor | pattern | 点亮能力 | 前置 |
|---|---|---|---|
| **检索者** | `translator` | S06 长期记忆（T3，是 T4–T8 的前提） | 投影表（§2.2） |
| **抢占判定者** | `decider`, `budget_ms = 80` | S07 插话（T3–T4） | ActorSpec（本件） |
| **验证者** | `decider`，与产出者不同 `principal` | S03/S08 不自验（C15） | ActorSpec + 溯源（§2.1） |

> **注意**：**不**引入 v2 [01 §4.1] 的 ZST 令牌闸门（`RuleOnly`/`ClassifyOnly`/`FullModel`）**作为前置条件**。
> 它是 v2 的**增强**（把 I3 从"事后检测"升级为"事前不可能"）。
> 现行 `chat_loop` 的 `budget_ms` 语义已经存在，**先按参数落地，令牌闸门作为后续增强**——
> 这样 S07 不被令牌机制阻塞。令牌闸门的价值见 [01 §4.1]，落地条件是"反射档真的上线"。

**交付判据**：
1. 现有 `chat_loop` 行为**逐字节不变**（回归测试全绿）；
2. 新注册的 Actor 可在**不修改** `chat_loop` 代码的前提下接入（这是"扩展不改架构"的验收）；
3. 移除新 Actor 后系统退化为现行形态（J2）。

## 3. 排期：四步，每步独立可回滚

> 与 v2 [04 §3](04-工程落地.md) 的 22 步**不是同一张表**：
> v2 从零建系统，本方案从现行系统增量补。**步数少，因为地基已经在位。**

| 步 | 内容 | 对应缺口 | 出口判据 | 可并行的线 |
|---|---|---|---|---|
| **B1 事实信封** | `Fact` 类型 + `FactSource` trait + 会话派生 | G-A | 往返测试逐字节相同；不实现者照常跑 | 1 条（必须先行） |
| **B2 投影表** | `Projection::new` + `inventory` 登记表 + **收口 3 个既有纯函数** | G-B | 双跑一致；既有裸函数不被强制 | 2 条：B2 / B1 后半 |
| **B3 Actor 行** | `ActorSpec` + `chat_loop` 装配化 + 注册**判定者** | G-C | 现行为不变；新 Actor 零改 `chat_loop` 接入 | 2 条：B3 / B2 |
| **— 闸门：断言目录 —** | 见 §3.3，**必须与 B3 同时或更早** | 断言层 | CI 全绿 | 1 条 |
| **B4 扩展验证** | 注册**检索者**（S06）；跑守恒审计 | G-A/B/C | 检索链路通；**新增机制键 = 0** | 全并行 |

**两处最容易排错的次序**：

1. **B1 必须先于 B2/B3**。没有统一事实格式就做投影/Actor，会让每个新能力各自发明一套输入——这正是现行体系已经有过的教训（三套方言）。对应 v2 §13.6 代价①"事件 schema 必须是终态"。
2. **断言目录不能排在最后**。它是 v2 [03 §7.3 G7](03-演进与验证.md)"静默失效"的兜底；排在最后，前面的扩展已经悄悄漂移了。

### 3.3 断言目录（本方案的"守恒律"最小版）

**不**照搬 v2 的 29 条 CI。**只建 4 条**——它们是现行体系**真正缺**的，且每条都对应一个已观察到的失败模式：

| # | 断言 | 对应 | 为什么现行体系需要它 |
|---|---|---|---|
| **A1** | 新增能力时 `FactKind` 的**新取值 ⊆ 机制表**（越界 = 失败） | v2 C18 | 现行无统一参数表 → 新能力**倾向发明新字段**，必须先立住这条 |
| **A2** | 断言类 `Fact` 的 `caused_by` 非空 | v2 C3 / I2 | 现行 I2 完全缺失，且**静默失效**（违反时无任何测试失败） |
| **A3** | 每 `turn` ≤ 1 条 final | v2 C2 / I1 | 现行有兜底但**无断言**，回归会静默通过 |
| **A4** | 投影双跑逐字节相同 | v2 C6 / N1 | 现行纯函数**无此保证**（它们能读任意东西） |

**机制表最小版**（本方案需要的"权威参数表"，对应 v2 [01 §8]）：把 `SessionConfig` +
各插件 `PLUGIN.yml` 中**已被 >1 个消费方使用**的键收敛成一张表。
**表本身由脚本生成**（沿用 `scripts/gen-current-facts.mjs` 的模式），不手写——
手写的表必然漂移（这正是 v2 [03 §7.3 G7](03-演进与验证.md) 的教训）。

> **A1 是本方案的核心断言**：它把"扩展要加数据、不要加机制"从**口头纪律**
> 变成**可执行的失败信号**。没有它，前三步补出来的扩展性会在两个迭代内退化。

## 4. 为什么这条路"改动更小"

**改动量对照（估算，以 `symbio/src` 现 218 文件 / 55823 行为基准）**：

| 做法 | 新建 | 改写 | 破坏现行测试 | 可增量交付 |
|---|---|---|---|---|
| **纯 v2 重写**（照 05 的 6 包重建） | `store` / `projections` / `actors` / `adapters` / `governance` 5 包 | `session`（17.8k 行）/ `vdfs`（3.0k 行）/ `memory`（0.4k 行）等核心实现 + 前端链路 | 全部 | 否（一次性） |
| **本方案（桥接）** | `fact` 域（~1 文件）+ `projection` 签名（~1 文件）+ `ActorSpec`（~1 文件） | `chat_loop` 装配化（1 处）；3 个纯函数加登记 | **0** | 是（B1–B4 各独立） |
| **什么都不做** | — | — | 0 | — |

**本方案的核心手法**：**把 v2 的"机制"降级为现行体系的"登记"**。

| v2 的机制 | 本方案的登记形态 | 收益是否减少 |
|---|---|---|
| `Store` 唯一原语 + append-only | 沿用 `SessionStore` + VDFS，**不改接口** | 否（VDFS 已提供 append-only 语义） |
| `Projection` 私有构造 | 新增投影受约束；既有纯函数登记 | 否（新能力从第一天受约束） |
| `ActorSpec` 数据行 | 显式声明 + 允许注册 | 否（扩展能力等价） |
| I1/I2/I3 不变量 | A2/A3 + 沿用 RAII 守卫 | 否（I2 是本方案**新补**的） |
| 机制表 10 键恒定 | 生成式最小表 + A1 断言 | 否（守恒审计等价） |

> **一句话**：**v2 的"1 个原语"是一个记账立场**（[01 §1.6] 自己承认），
> **本方案不追求那个数字，追求它想换来的东西**——扩展不改架构。
> 那件事**在现行体系上就能做到**，不需要先把系统推倒。

## 6. 诚实划界：本方案**没有**拿到的

> v2 全文贯穿一条纪律：**"承载 ≠ 保证"，"装得下 ≠ 好用"**（[02 §8]、[roadmap §6]）。
> 本方案同样必须有这一段，否则会被误读成"照做即可高枕无忧"。

### 6.1 本方案**放弃**的 v2 声称

| v2 声称 | 本方案 | 理由 |
|---|---|---|
| 原语计数 = 1 | **不主张**（诚实记账：现行体系是"多存储 + 一编排"） | 计数是立场不是结论（[01 §1.6]），追求它要重写 8 万行 |
| `Projection` 是**编译期强制**的纯净性 | **一级强制 + 既有函数豁免** | 全量改写无行为收益 |
| 时延闸门（ZST 令牌）**事前**拦模型调用 | **后置增强**，先按参数落地 | 前置会阻塞 S07；令牌的价值在反射档上线后才显现 |
| `verify/` 14 个可编译程序 | **只用其中 4 条**（§3.3） | 其余对应 v2 特有机制（令牌 / 代数），现行无对应物 |
| L0+L1 重放一致性 | **沿现行**（`messages.json` 本身可重放） | 本方案不改变重放语义 |

### 6.2 本方案**没有证明**的

- **召回质量**。§5 只说"装得下检索"，不说"检索得到对的东西"（v2 [03 §7.3 G6] 同样未证明）。
- **收敛性**。§2.2 的投影表不证"投影序列收敛"（v2 也只证任务终止，不证投影收敛）。
- **成本**。SLO 数字（v2 [04 §1]）本方案**未给**——现行体系亦未埋点。
  在埋点前，任何"扩展成本可接受"的说法都是修辞。
- **分布式**。`Fact.seq` 的进程级单调在单机成立，多副本不成立（v2 [04 §5 R5] 同样登记为风险）。

### 6.3 本方案**引入**的新风险

| # | 风险 | 触发信号 | 缓解 |
|---|---|---|---|
| **BR1** | `Fact` 成为**第二套真相**（与 `messages.json` 不一致） | 往返测试失败 | 强制 `Fact` 只读（无 write）+ 往返测试进 CI |
| **BR2** | 投影表**登记了但没被用**（"启用"却没生效） | 同一投影长期只取平凡值 | 对应 v2 D3（平凡值滥用）；生成式机制表可查 |
| **BR3** | 三层新增（信封/投影/Actor）**同时改**导致 diff 不可审阅 | 单次 PR 跨 3 层 | 严格按 §3 的 B1→B2→B3 顺序，每步独立提交 |
| **BR4** | A1 断言**被绕过**（新能力走既有键的"新语义"而非新取值） | 守恒审计全绿但能力走样 | 这是 v2 G7 的同一盲区（[03 §7.3]）；A1 补不了，需人工闸门"先找同构既有模式"（v2 [03 §3 第 0 步]） |

> **BR4 是最值得警惕的一条**：它说明**断言不能替代判断**。
> v2 自己也承认"零新增键是必要条件，不是充分条件"（[roadmap §6]）。
> 本方案的诚实立场与 v2 一致：**守恒审计是闸门，不是证明。**

## 8. B3 落地细则（实现前固化）

§2.3 给出了 ActorSpec 的**意图**与交付判据；本节把**字段取值、表的位置、装配点、
可选项边界**固定下来，避免实现期各自发明。原则沿用 B1/B2：**只有一条约束路径，
新增走这条路径；既有裸路径不强制迁移**。

### 8.1 ActorSpec 的四字段——取值来自现行 `chat_loop`，不是凭空设计

| 字段 | 类型 | 取值来源（现行代码） | 说明 |
|---|---|---|---|
| `principal` | `String` | `ctx[SESSION_ID]`（root 会话即 `session_id`） | 主体标识。**不新建 `Principal` 结构**——现行就是会话 id 字符串；结构体留给 S08（多主体）时再收 |
| `pattern` | `ActorPattern` 枚举 | `chat_loop` 实际是 `Reasoner` | 四个取值：`Reasoner` / `Translator` / `Decider` / `Verifier`（与 §2.3 的表一致） |
| `budget_ms` | `u64` | 现行 `session_cfg.model_chat_max_tool_rounds()` 的**超时语义**：无显式墙钟上限 ⇒ `0 = 不限` | `0` 表示"无墙钟预算"（与 `max_tool_rounds = 0 = 无限轮次` 同构，不是魔法数） |
| `scope` | `ActorScope` 枚举 | `Root`（无 `AGENT_ID`）/ `SubAgent(agent_id)` | 与 `ASSEMBLY_SUB_AGENT_PLUGINS` 的分形层级同构 |

> **`capabilities` 明确不进第一版**（§2.3 已给理由）：7 个权威动作在现行代码不存在，
> 第一版只有这 4 个字段；权限靠视图层过滤。动作级授权矩阵在 S08 同批交付。

### 8.2 表住 core，行住插件——与 B2 投影表同构

- **表**：`symbio_core::actor`（`ActorSpec` + `actor_register` / `actor_list` /
  `actor_get` / `actor_clear` + `ActorSource` trait）。与 `projection` 域对称：
  契约在 core，具体行由各插件登记。
- **行**：**谁的行为谁登记**。
  - `session/actors.rs` 登记 `session.reasoner` 行——它就是现行 `chat_loop` 的
    显式化（`principal = ""` 用**占位符**，运行期以会话 id 解析，见 §8.3）。
  - 新插件 `plugins/actor/`（**可选**）登记 `session.decider` 行——§2.3 的
    "抢占判定者"，`budget_ms = 80`。
- **注册时机**：`actor_register(&spec)` 在 `chat_loop` 首次运行时登记（幂等，同
  `name` 覆盖）。因此**无需改装配顺序**，也不需要新的"装配期钩子"——这是 B3
  能做到"零改装配"的关键。

### 8.3 `chat_loop` 的装配化——最小的那一刀

现行 `run_chat_loop` 已经是"装载上下文 → 闸门 → 准备输入 → LLM → 结算"的执行器。
B3 **不重写它**，只做两件事：

1. **入口处解析一次 ActorSpec**：`ActorSpec::resolve(...)` → 覆盖同 `name` 的登记行
   （把占位 `principal` 换成真实 `session_id`）→ 得到本轮生效的 `ActorSpec`；
2. **用 `ActorSpec` 取两处参数**，值与原取值**逐字节相同**：
   - `budget_ms`：`0` ⇒ 现行 `max_tool_rounds` 语义（交给 `gate_turn`，不变）；
   - `scope`：与现行 `ctx[AGENT_ID]` 存在性判定同义。

> **不引入** §2.3 提醒的 ZST 令牌闸门（`RuleOnly`/`ClassifyOnly`/`FullModel`）作为前置。
> `budget_ms` 按参数落地即可。

其余骨架（`gate_turn` / `finish_turn` / 12 个出口 / 单一收尾点）**一行不改**——它们
已经在做"执行器"，改反而是倒退。

### 8.4 可选项边界（J2 的落点）

| 项 | 缺省 | 移除后果 |
|---|---|---|
| `plugins/actor/` | **不在** `ASSEMBLY_SUB_AGENT_PLUGINS` | 判定者行不登记；`actor/list` 只剩 `session.reasoner`；**会话照常运行** |
| `session/actors.rs` 的 reasoner 行 | 总是登记（session 是必需插件） | 若缺，`chat_loop` 回落到**内置默认值**（与登记行取值相同）——不存在"会话开不起来" |

第二行是关键：**执行器不能依赖表非空**。`ActorSpec` 表为空时 `resolve` 返回内置默认
（`Reasoner` / `budget_ms = 0` / `Root`），这正是现行行为。于是"表"是**扩展点**，
不是**运行时必需品**——与 B2 的"既有裸函数不被强制登记"完全同构。

### 8.5 交付判据（复述 §2.3，加可核对方式）

1. **现行为逐字节不变**：`e2e/cases/t6-*.mjs`（会话链路）在改动前后输出相同 →
   回归全绿即证；
2. **新 Actor 零改 `chat_loop` 接入**：`plugins/actor/` 只调 `actor_register`，
   `chat_loop.rs` 的 diff 不含任何 `decider` 字样 → 可 `git diff` 核对；
3. **移除即退化（J2）**：`e2e/cases/t20-actor-spec.mjs` 把 `plugins/actor/` 的
   `PLUGIN.yml` 置 `plugin_enabled: false`，断言 `actor/list` 不含 `session.decider`
   而 `vdfs/root` 与真实会话仍可用。

### 8.6 新增断言 A5（守恒律补齐）

| # | 断言 | 对应 | 为什么需要 |
|---|---|---|---|
| **A5** | 每个 `ActorSpec` 的 `scope` 与登记者所在装配层一致（子 Agent 树里的行不得声明 `Root`） | v2 [01 §7] 权限第零天 | 与 A4 同构：把"越权"从**事后检查**变成**登记期不可能**——装配层是登记的上下文，越层的行**登记不进去** |

> A5 的强制点在**登记期**（`ActorSource::register` 的上下文决定可声明的 `scope`），
> 不是 CI 扫描：能被绕过的 CI 只会给出虚假的安全感（v2 [03 §7.3] G7 静默失效）。

## 9. B4 落地细则：注册检索者（S06），并跑守恒审计

§3 的表把 B4 定为**扩展验证**：不是新建地基，而是**用前三个桥头堡盖一间新房**，
看它是否真的"零改既有代码"。选 S06（长期记忆与语义检索）作这间房，因为它是
v2 [roadmap] 里 T3 的第一阶，也是 §5 表里**第一个点名要"0 机制 / 0 既有代码改动"**的能力。

### 9.1 B4 与前三个桥头堡的关系：一条链，不是四件独立的活

```text
B1 Fact 信封  ──►  B2 投影表  ──►  B3 Actor 行  ──►  B4 检索者
（统一原料）      （纯折叠）       （执行者声明）     （第一个真消费者）
```

B4 的价值在于：**它是前三个机制的第一个共同消费者**。B3 的 `decider` 只证明"Actor 能登记"，
它不读事实、不产出事实——那是一次**空转**。检索者不同：它要

| 要什么 | 由谁提供 | B4 需要改它吗 |
|---|---|---|
| 读哪些事实 | B1 `FactKind` 的 `memory.*` 格子 | **否**（格子已在网格内，只点亮） |
| 怎么折叠事实 | B2 投影表（`recall`） | **否**（新投影经 `Projection::new` 登记） |
| 以什么身份/预算跑 | B3 Actor 表（`session.retrieval`） | **否**（登记一行） |
| 怎么把结果给出去 | 一条只读内省路由（`list`） | **否**（新插件自己的路由） |

**四个"否"就是 B4 想验证的东西**——它若成立，§5 的"需要改的既有代码 = 0"就不是口号。

### 9.2 只加数据：B4 的增量清单

| 类型 | 内容 | 是不是新机制 |
|---|---|---|
| `FactKind` 格子 | `memory.encoded` / `memory.consolidated` / `memory.forgotten` / `memory.recalled` | **否**——四格在 B1 就已预留（`kind.rs` 的网格表），B4 只是**点亮** |
| ActorSpec 行 | 检索者 `session.retrieval` `{ pattern: translator, budget_ms: 500, scope: root }` | **否**——B3 的表能装任意行 |
| 投影 | `memory.recall`（平凡值 = 只看当前窗口，即 `snapshot` 语义） | **否**——B2 的 `Projection::new` 是唯一入口 |
| 路由 | `retrieval/list`（只读内省：跑一次 `recall` 投影回结果） | **否**——本插件自己的路由 |
| 插件 | `plugins/retrieval/`（**可选**，不在装配清单） | **否**——与 `fact_log` / `projection` / `actor` 同款 |

> **"新机制"的定义**（对齐断言 A1）：需要改 `symbio_core` 里**已有 trait 的签名**、
> 需要改 `chat_loop` / `SessionStore` / `Plugin` 的**既有代码**、或需要在 `PLUGIN.yml` 里
> 引入**新的保留键**。以上五项**一条都不满足**。

### 9.3 为什么检索者必须可选，且不依赖任何兄弟插件

| 边界 | 为什么 |
|---|---|
| **可选**：不在 `ASSEMBLY_SUB_AGENT_PLUGINS` | 它提供的是**召回能力**，不是地基。缺席 ⇒ 会话照常（J2） |
| **只读**：只跑投影、只查表，不写任何域 | 检索是**读视图 → 产出事实**；本轮只交付读的那半（写 `memory.recalled` 留待有真实消费方时加，那是一次加法） |
| **零插件依赖**：只经 `symbio_core` 的 projection / actor / fact API | 插件独立原则。它**不认识** `session` / `fact_log` / `projection` / `actor` |

> 第三行是难点：检索者要**从磁盘取事实**（像 `fact_log` 那样），但**不能 import `fact_log`**。
> 解法沿用 `fact_log` 自己的先例——**只依赖磁盘上的公开布局**（`<root>/session/<id>/messages.json`
> 是公开约定，见 `docs/design/vdfs.md`），**就地**派生事实。因此检索者与 `fact_log`
> 是**同一份约定**的两个独立消费者，互不相识。

### 9.4 平凡值（J2）：检索者缺席时，系统退化成什么

| 参数 | 完整值 | **平凡值** | 平凡值下 |
|---|---|---|---|
| 插件 | `plugins/retrieval/` 在位 | **不在位** | 无 `retrieval/list` 路由；**会话照常**。Actor 表里没有 `session.retrieval` 行——但它本来也只是"表里的一行" |
| 投影 | `memory.recall`（按 `memory.*` 格子召回） | **未登记** | 消费方取不到 ⇒ 按"只看当前窗口"处理，即 S01 的失忆助手 |
| `FactKind` | `memory.*` 四格点亮 | **不点亮** | 事实里不出现 `memory.*`，其余事实照常——这正是"加格子不改机制"的另一半 |

### 9.6.1 实现中被 e2e 抓出的一个真缺陷：事实类型有两套线上词形

这是本步**唯一**回了头改已提交代码的地方，记下来因为它有普适教训。

`FactKind` 原本 `derive(Serialize, Deserialize)` + `#[serde(rename_all = "snake_case")]`，
同时又有 `wire()` 返回 v2 网格的 `<实体>.<动词>`。于是：

| 场景 | 词形 |
|---|---|
| `wire()` / `entity()`（Rust 内比较） | `memory.encoded` |
| **线上 JSON 载荷**（跨进程） | `memory_encoded` |

**同一事实两种写法**。而它**在单测里测不出来**——单测两侧都调 `wire()` 比较，
永远一致；只有真实载荷跨越进程边界时才暴露。B4 的 e2e 第一次跑就撞上了
（断言 `kinds.has('memory.encoded')`，实得 `memory_encoded`）。

修法是**收敛为单一真相源**：手写 `Serialize` / `Deserialize` 委托 `wire()`，
反序列化按 `wire()` 在 `FactKind::ALL` 里反查，认不出就**报错**（不静默兜底）。
并加两条单测钉死（`serde_uses_wire_verbatim` / `unknown_wire_is_rejected`），
以及 e2e 里的反向断言（`kind` 不得出现纯 snake_case 词形）。

教训：**"两侧都用同一个方法比较"的单测证明不了序列化契约**——契约是跨进程的，
必须在跨进程用例里验。B1/B2/B3 的单测全绿却漏掉它，正是因为缺这条。

### 9.6.2 第二个真缺陷：召回窗口全局一条，跨会话召回名存实亡

`memory.recall` 的"当前窗口"原本**全局取尾部 8 轮用户事实**（`f.seq >= window_from`）。
但 B4 的检索者喂给投影的事实是**全部会话合并**的：seq 高位按会话字典序编码
（`SESSION_STRIDE = 2^40`，位次从 1 起）。于是全局尾部 8 轮**必然全部落在位次
最大的会话里**——其余会话的全部事实（包括它们各自的近期轮次）一律落窗。
S06 的核心卖点"跨会话记住"在多会话下**整体失效**，而单会话单测永远撞不到它。

修法：窗口**按 principal 分组**——每个主体从**自己的**用户事实序列里取尾部 8 轮
起点（`BTreeMap` 迭代按主体字典序 ⇒ 输出确定，A4 不破）；没有用户事实的主体取
哨兵 `FACT_NONE_SEQ`（无下界，全部入选，与旧全局语义同形）。输出新增 `windows`
数组承载权威数据，旧标量 `window_from_seq` 保留为"各主体下界最小值"的兼容字段
（单会话下与旧值逐分支相同 ⇒ T21 与既有单测零改动通过）。锁：多会话单测
`recall_windows_are_per_principal`（旧实现下必失败）+ 跨进程 e2e T22
（两个真实落盘会话、各 10 轮，断言两主体窗口下界独立、候选并存、双跑一致）。

教训：**"合并后仍然正确"的聚合必须在合并形态下验**——投影的输入契约是
"`&[Fact]`"，没有说"只有一个会话"；单测造的是单会话事实，就只证明了单会话。
凡是被喂"多来源合并数据"的折叠逻辑，用例必须至少给两个来源。

### 9.7 本步**没有**证明的（诚实划界，承 §6.2）

- **召回质量**未证明：`memory.recall` 返回的是"按窗口与 `memory.*` 格子折叠出的候选集"，
  不证明它"召回得对"。这是 S06 自己第 7 节也承认的分界（承载 ≠ 保证）。
- **巩固 / 遗忘**未落地：本轮只点亮 `memory.*` 的**读**侧（`encoded` / `recalled` 的派生），
  `consolidated` / `forgotten` 的**写**路径留待有真实触发方时再加。
- **跨主体隔离**未强制：S06 验收 3（A 的记忆对 B 不可见）需要 grants 行，那是 S08 的活。

## 10. B5 起：前后端步调一致的分期（消费接入 + 体验出口 + 主/Worker 会话分离）

> **本节回答的问题**：§3 的 B1–B4 出口判据**只有测试、没有体验**——四步走完，
> 用户在前端看不到任何变化（BR2「登记了但没被用」的实证）。从 B5 起立一条硬纪律：
> **每一期 = 一个后端能力出口 + 一个前端体验出口 + 双侧验证，同批交付；
> 没有体验出口的期不开工。**

### 10.1 分期总表

| 期 | 后端能力 | 体验出口 | 状态 |
|---|---|---|---|
| **B5 消费接入** | ① `memory_recall` LLM 工具（`retrieval::tool`，经 `traverse` 注册）；② v2 桥接四插件进系统默认装配（`home::SYSTEM_EXTRA_PLUGINS` → `REQUIRED_PLUGINS`，子树不挂） | 空环境新装即可用：新会话问「之前记过什么」，助手跨会话答出旧会话钉住的记忆；工具调用在会话里可见 | ✅ 已交付（e2e T23） |
| **R1-a 主会话快照化** | （前端）worker 过程不进主窗口：过程节点收成**一行状态条**（状态 / 轮次 / 最新一步），详情留 worker 会话历史 | 主窗口只有问答 + 状态行 | ⬜ |
| **R1-b 秒回 + 异步 worker** | `ReplyFirst`：先即时应答（零工具），重活转后台 worker 会话，完成后结果 **append** 回主会话 | 发消息立刻有回应；重活后台完成自动追加，不阻塞输入 | ⬜ |
| **R1-c 快照契约** | 状态快照 = worker 会话的**投影**（B2 机制的直接消费方：只加数据、不加机制） | 状态行按运行态帧实时刷新 | ⬜ |
| **B6 记忆面** | 会话记忆（`MEMORY.md`）的前端可见 / 可编辑入口 | 用户能看见、编辑自己被记住的东西 | ⬜ |
| **B7 自动召回注入** | `memory.recall` 非平凡时注入系统提示词段（消费侧二号） | 不调工具也记得 | ⬜ |

### 10.2 R1 的架构定案：主会话与 worker 会话是**两份历史**

**定案**（用户拍板）：与用户的问答是**主会话**；深度思考与多轮工具在**worker 会话**里做——
主会话激活 worker、worker 把**结果与状态快照**回传，**过程不进主会话**。

现行代码已有先例与大部分地基（`agent/host/subagent.rs` 的 `agent_run`）：

| 定案要素 | 现行对应物 | 状态 |
|---|---|---|
| worker 是独立会话历史 | `metadata.parent_session_id` 归档到父会话 `sessions/` 子目录、**不进用户会话列表** | ✅ |
| 主会话激活、后台推进 | `session/chat/send` 路由立即返回，子会话走同一条 `chat_loop` 后台跑 | ✅ |
| 结果回传主会话 | 完成 → 工具结果 = 最终文本 + `[subagent_session_id]`（可续会话追问细节） | ✅ |
| 过程另处可见 | `event_bus` + `vdfs/watch` 实时面（前端已靠它显示后台会话进度） | ✅ 通道已有 |
| **主会话只见状态快照** | ❌ 缺口①：转播桥把子会话流式帧**全量**转进父视图 | ⬜ R1-a |
| **第一时间反馈** | ❌ 缺口②：父工具**同步 await** 子会话完成，主会话轮次阻塞到 worker 结束 | ⬜ R1-b |
| **快照有契约** | ❌ 缺口③：呈现只是转播帧的副产品，没有"快照"定义 | ⬜ R1-c |

**为什么分离优于混合**（三条，供后来者复核）：① worker 的工具产物很大（仓内
`tool_archives/` 归档机制即证据），混入会污染主上下文；② 主转写是压缩 / 淡化的对象，
工具噪声会让压缩快照失真；③ N 个 worker 并行时混合历史是交错乱码，分离后每 worker
一条时间线、主会话只有 N 个状态节点。**诚实代价**：主会话 LLM 看不到过程细节，
追问须续 worker 会话（`[subagent_session_id]` 机制即为此）——代价小于"主窗口背全部过程"。

### 10.3 工具分级规则（B5 与 R1 不冲突的判据）

| 类别 | 判据 | 归属 |
|---|---|---|
| **轻查询** | 单发、毫秒级、只读（`memory_recall` / `vdfs_read` / 搜索类） | 可留主会话 |
| **重活** | 多轮工具、写盘、重度思考、秒级以上的模型调用 | **一律 worker 会话** |
