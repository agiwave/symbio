# 03 · 演进与验证

> 回答三个问题：**什么被冻结** · **凭什么相信它撑得住** · **什么没有被证明**。

## 1. 冻结契约：6 个锚点，1 条元规则

> 冻结契约容易膨胀成一份长长的规则清单。按 J1 检验，真正需要冻结的不是若干条独立规则，
> 而是**同一条元规则在几个位置的锚点**。

**元规则（唯一）**：

> **元素数不随场景数增长。** 被冻结的 6 个位置，就是"元素数"这个量的定义域。

| 锚点 | 被冻结的东西 | 修改它 = |
|---|---|---|
| **F1** | `Store` trait 签名（`append` / `range` / `head`） | 架构变更 |
| **F2** | `Projection` 的**构造形状**（唯一入口 `new`；形参无 `&Store` / 无 `&mut` / 无 `Clock` / 无 `Principal`；`now` 是参数；返回 `View` 非 `Result`） | 架构变更 |
| **F3** | `ActorSpec` 字段集（5 个）+ **档位→令牌映射**（反射 `RuleOnly` / 快速 `ClassifyOnly` / 深度 `FullModel`） | 架构变更 |
| **F4** | 三条不变量 I1 / I2 / I3 | 架构变更 |
| **F5** | 三个封闭集合：动词 5 个、能力 7 个、模式 3 个 | 架构变更 |
| **F6** | 参数表键集（11 个，见 [01 §8](./01-核心架构.md)） | 架构变更 |

**不属于上表的任何变化都是数据变化**，不算架构变更：加事件格子、加投影、加 ActorSpec 行、加 grants 行、加 Principal。

> **F2 的措辞已强化**：从"签名形状"改为"**构造形状**"。
> 差别在于前者只是一种约定（你可以不遵守），后者是**唯一入口的泛型约束**（不遵守就编译不过）。
> 这是 J3 在冻结契约上的直接体现——**能被绕过的"约束"不该进冻结契约**。
>
> **F3 新增了档位→令牌映射**：它是"时延闸门"（[01 §4.1](./01-核心架构.md)）落进冻结契约的部分。
> 把它冻住的意义：**"反射档拿不到模型"是由类型保证的，不能在某次重构里被悄悄放宽**。
> 若哪天有人给 `RuleOnly` 加上 `CanClassify`，F3 的 CI 断言立刻红。

## 2. 四层判层：新需求来了先判层

| 层 | 含义 | 例子 | 是否重构 |
|---|---|---|:-:|
| **L-data** | 加数据 | 新 `Principal`、新 grants 行、新实体格子 | 否 |
| **L-grid** | 加网格格子（已有实体 × 已有动词） | `memory.recalled` | 否 |
| **L-schema** | 加新实体 / 新动词 / 新参数键 | 加 `commitment` 实体 | 否（但需 ADR 登记） |
| **L-mechanism** | 修改 F1–F6 | 给 `Store` 加 `update()` | **是** |

**判层方法**：从上往下试，第一个能装下的层就是它的层。装到 L-mechanism 才需要重开架构讨论。

### 2.1 平凡值强制（J2 的可执行形式）

> 一条关键的工程纪律：**零 LLM 全链路彩排**——先用 4 个 Stub 跑通完整事件序列，再逐个换成真实现。
> 本方案把它从"阶段一的一个步骤"提升为**通用纪律**。

**每个新参数必须给出平凡值，且平凡值下系统必须完整运行。**

| 参数 | 平凡值 | 平凡值下会发生什么 |
|---|---|---|
| `actor.pattern` | `decider` | 全规则驱动，无 LLM 也能跑完整链路 |
| `actor.capability` | 空集 | 该主体只写非权威事件 |
| `actor.budget_ms` | `60000` | 全部走深度层，慢但正确 |
| `scope` | `root` | 无子智能体，单主体 |
| `vis_scope` | `thread_private` | 无跨主体共享 |
| `projection` | 仅 `eval` | 只有评测视图 |

**这就是"分阶段不改架构"的技术前提**：Event Log 的 schema 从第一天起就是终态，
后续阶段只是让某些事件从"恒等策略下的默认产出"变成"真实策略下的正常产出"——**没有任何数据迁移**。

> 推论（退化特例归零）：代码里不出现 `if (children.length === 1)`、
> `if (depends_on.length === 0)` 这类分支——**空集与单元素是一等输入，不是特例**。

## 3. ADR 流程

> ### 前置闸门（本节最重要的一条）
>
> **任何"为了某个场景而修改 F1–F6"的提议，默认视为架构本身的缺陷信号**——
> 它说明先前的抽象没有覆盖住这类需求，而不是这个场景太特殊。为场景改架构，正是"架构没想清楚"的证据。
>
> 所以动架构之前**必须先做第 0 步**：
>
> **0. 先找同构的既有模式。** 系统里是否已经存在解决同一类问题的机制？
> v2 的抽象层很少——正因为少，同类问题的解法会反复出现。
> 只有当"已有模式确实不够用"被写清楚之后，才有资格讨论改架构。
>
> **实例**：S10（个人认知体系）最初判断需要扩展 `store` 的值域以支持"入库过滤"。
> 复核后发现它与 §9.3 的**遗忘是同一个模式**（排除而非删除），
> 归入 `recall` 的过滤参数即可，**零架构改动**。详见 [roadmap/S10](./roadmap/S10-个人认知体系注入.md) §5。

需要修改 F1–F6 时：

1. 说明**为什么它不能被表达为参数取值**（必须用 J1 检验过）；
2. 说明**旧数据如何迁移**（若无迁移方案，说明为什么不需要）；
3. 同步更新 CI 断言与 `verify/` 程序；
4. 记录**推翻条件**——什么新证据出现时这条 ADR 应当被撤销。

## 4. 守恒律：唯一可自动审计的"不重构"保证

> "将来不会重构"是一个**承诺**，无法证明。可以证明的是更弱但有用的命题：
> **机制数不随场景数增长。**

`verify/mechanism_growth.rs` 实测（路线图 13 阶 §3 的赋值 + 20 个自造压力场景）：

```
机制表（01 §8 生成，顶层键）：10 项；§8 登记的键（含子键）：11 项
路线图各阶 §3 的赋值越界键：0 个
自造场景数：20          越界键（需要新机制的）：0 个

场景  1 个 → 用到机制 5 种
场景  5 个 → 用到机制 5 种
场景 10 个 → 用到机制 8 种
场景 20 个 → 用到机制 9 种
```

机制表本身不在程序里手填——它由 `scripts/gen-verify-facts.mjs` 从 01 §8 生成（[§5.3](#53-数据的外置与生成)）。

**读法**：增长的是"启用了哪些已有参数"，不是"发明了多少机制"。
第 21 个场景来了，**照样要重跑这个程序**——它不保证未来，只保证"到目前为止每一次扩展都是通过参数完成的"。

## 5. 验证纪律与实测

### 5.1 四条纪律

> 架构文档里的"验证程序"有四种典型的自欺方式。以下四条纪律逐条对应。

| # | 纪律 | 它拦住的反模式 |
|---|---|---|
| 1 | 每条声称对应一条可执行断言 | 零断言的程序不可能失败：9 个程序只有 1 条断言时，"全部通过"是空的 |
| 2 | 断言的**输入不得包含结论** | 把结论写成常量再断言常量：例如把"是否会增长"硬编码成 `false`，再断言它不增长 |
| 3 | 每条断言配**反向用例**（改输入，结论必须变） | 硬编码返回值（如直接 `return (2, ...)`）：改任何输入，结论都不变 |
| 4 | **声称"编译期强制"的，必须附一段已知编译不过的代码** | "强制"没有反向用例时，无法区分"真的强制"与"恰好没写错"——第 3 条在编译期的镜像 |
| 5 | **编译期反例必须写在外部模块里** | 私有字段**同模块内可访问**；反例写错位置会"编译通过"，于是"必须失败"变成假话 |

**第 4 条的落地形式**（`verify/projection_purity.rs` / `verify/latency_gate.rs` / `verify/conation_minimal.rs`）：

```rust
#[cfg(feature = "should_not_compile")]
mod must_fail { /* 故意编译不过的代码 */ }
```

```
# 期望非 0 退出（-o 不要用 /dev/null，Windows MSVC 链接器需要真实路径）
rustc --edition 2021 --check-cfg 'cfg(feature)' \
      --cfg 'feature="should_not_compile"' <file>.rs -o should_fail.exe
```

实测错误恰为纯净性 / 档位 / 闸门违规（`E0593` arity 不符、`E0277` trait 不满足、
`E0308` 类型不符、`E0451` 私有字段、`E0061` 参数不足），
**而不是被无关约束顺手挡掉**——反向用例必须为正确的原因失败。

> **第 5 条是本轮新增的**（`conation_minimal.rs` 暴露）：把 `CandidateIntent.approved`
> 的伪造用例写在主模块里时，它**编译通过**了——因为同模块可访问私有字段。
> 修正后（放进 `mod outsider { ... }`）才得到正确的 `E0451`。
> 这条纪律的意义：**"必须失败"的用例，本身也要有一个反向用例来证明它会失败。**

### 5.3 数据的外置与生成

**判据在程序里，数据在文档里。** `verify/` 各程序吃的计划数据——机制表、13 阶的赋值向量与
退路口、能力名册与它的三处声明——都不是程序里的手填常量，而由 `scripts/gen-verify-facts.mjs`
从权威表生成 `verify/facts/mod.rs`（生成物，不手改），程序 `mod facts;` 消费：

| 生成物 | owner |
|---|---|
| `MECHANISMS` / `PARAM_KEYS` | [01 §8](./01-核心架构.md) 的权威参数表；顶层键与子键按**形状**分（含 `.` 且首段已登记 ⇒ 子键） |
| `DIMENSIONS` / `AXES` / `TIER_MAX` / `CAPABILITIES` | [02](./02-能力坐标系.md) §2 五维表 / §3 五轴表 / §3.1 天梯表 / §6.1 能力名册 |
| `PSEUDO` | 02 §5 伪高阶表的「说法」列 |
| `DECLARED_DIM_COUNTS` / `DECLARED_GROWTH` / `DECLARED_SOCIAL` | 02 §2「条数」列 / §6.2 生长位表 / §7 社会性表 |
| `STAGE_CLAIMS` | [roadmap/00 §1](./roadmap/00-路线图总览.md) 阶梯总表的「新增机制键」「参数变化」两列 |
| `STAGE_DOCS` | 各阶 `S0N-*.md` §3 的 `capability-assign` 赋值块 + §4 里加粗平凡值的那一行 |

三条规矩，都是为了让「改了文档而绿灯照旧」不可能发生：

- **读不出来必须红**：表头改名、块缺失、数字解析不出、退路口加粗行不唯一 ⇒ 生成器抛错，
  绝不返回一张空表（空表会让程序拿着残缺数据照常断言）。
- **声明与数据分家**：总表那一列、§2 的条数、§6.2 的生长位都是**被验的结论**，程序从数据算出来
  再对它们——所以文档两处不同步，红的就是程序。
- **生成归门禁自己做**：`gate.d/55-verify.mjs` 先跑生成器（`autoWork`：漂移当场暂存），
  再编译各程序；CI 档存在未提交差异即红。

## 6. 阶段排期（点亮顺序）

> 每一级 = 同一组参数从平凡值切到完整值。**参数变化数**一栏是本阶段唯一的架构相关度量。
> **逐步展开见 [roadmap/](./roadmap/)**：13 个场景，每个说明本阶段具体往哪儿加数据行。
> **可执行的 22 步排期与出口判据见 [04 §3](./04-工程落地.md)**；
> **每步的模块归属与并行拆分见 [05 §4](./05-模块架构.md)**。

| 阶段 | 点亮 | 关键产出 | 参数变化 |
|---|---|---|:-:|
| **一 · MVP** | T1–T2 | 事件骨架 + **零 LLM 全链路彩排** + 真实执行 + 投影 + 长会话 | **0** |
| **二 · 多主体与记忆** | T3 | `Principal`/`Capability`/`VisScope` 就位 + **长期记忆与检索** + 巩固 | **4** |
| **三 · 任务树与验证** | T4–T5 | DAG 调度 + 并行 + 角色分离 + 独立验证返工 + 对等承诺 | **4** |
| **四 · 自治与学习** | T6–T8 | 定时触发 + 跨 turn 存续 + **时延分层全点亮** + 技能编译 + 校准 | **3** |

**两处容易排错的次序**：

1. **记忆排进阶段二**，而不是"以后再补"。理由：T3 是 T4–T8 的前提，缺了它后面全是空转。
2. **时延分层在阶段一就位**（至少反射 + 快速两层）。理由：对话是基础能力，不能等到最后才优化。

**每个阶段的出口判据**：`git diff` 中没有修改 F1–F6。

| `Act` 不是系统的构成者 | 判断（依据：无状态、无接口、无不变量） |
| 投影不做成 trait | 工程选择（依据：trait 不增加强制力） |
| 五维正交完备、五轴足以度量高阶 | 判断 |
| T8 是当前能想到的最远 | 判断，不是"存在的最远" |
| 不存在第 4 个原语 | **开放性命题**，永不封闭。只能说"到目前为止没有触发点" |

### 7.3 本方案的已知缺口（不隐藏）

| # | 缺口 | 影响 | 建议 |
|---|---|---|---|
| G1 | **无一行可运行的系统代码**，只有验证脚手架 | 最大落地风险 | 阶段一必须先做零 LLM 彩排，别先写 LLM 集成 |
| G2 | 具身 / 硬实时（T7）只有预算断言，没有实测 | T7 无法验收 | 阶段四需补实时闭环的延迟实测 |
| G3 | 成本模型只有参数，无实测数字 | 无法设 SLO | SLO 初值已在 [04 §1](./04-工程落地.md)；阶段一埋点后校准，阶段三出 P99 |
| G4 | `score` 单调与**分布式 Store** 的一致性如何共存未展开 | 多副本部署时可能撞墙 | 部署前补一条 ADR |
| G5 | 守恒律只审计 33 个场景（20 通用 + 13 阶梯） | 第 34 个照样要重跑 | 每次新增场景必须重跑 `mechanism_growth.rs` 与 `scenario_ladder.rs` |
| G6 | 记忆检索的召回质量未验证 | T3 的"能记住"可能只是"存了但找不到" | 阶段二需补检索召回评测 |
| G7 | **派生代数无上界**（巩固的巩固可无限推进） | 不产生环，但信息逐级失真且不可控 | **双约束**：`consolidate:max_gen`（形态）+ `consolidate:min_fidelity`（质量）+ C20/C21 断言（[01 §13.4](./01-核心架构.md)、[01 §9.3](./01-核心架构.md)） |
| G8 | **守恒审计只查"机制键/值域"，查不出"取值语义漂移"** | 两个审计器全绿，能力仍可能悄悄走样（G7 即由此长出） | `semantic_drift_audit.rs` 作常驻适应度闸门（C22–C24）；但它依赖"语义标签"需人工登记，标签本身的质量无法自动保证 |

> **G7 是本轮分析新发现的**：13 阶审计没有覆盖到它，因为审计只查"用不用新机制键"，
> **查不出"值的语义边界"**——与 S10 那处复核暴露的是同一类盲区。
> 遇到这类问题，靠的是 [§3 前置闸门](./03-演进与验证.md) 里的人工复核，不是程序。

> **G8 是修 G7 时顺手暴露的、更上一层的问题**：G7 是"一个具体盲区"，G8 是"这类盲区会不断再生"。
> 对策是把盲区检查**程序化**（`semantic_drift_audit.rs`），但**诚实地说**：
> 那个程序需要一个"语义标签"输入，而标签对不对，仍然靠人。
> 它把"每天靠人想"变成"每天靠程序问、人只管标签"——是改进，但不是终结。

> **列出缺口的意义**：它们是被明确写下的，而不是被“永不重构”的承诺覆盖掉的。
