## 0. 三条改进纪律

这三条不是风格偏好，每条都对应一类已被实测到的腐烂。

| # | 纪律 | 判据 | 它防的是 |
|---|---|---|---|
| **1** | **只写目标态** | 代码注释 / 现行文档里出现「本批」「待接」「尚未」「TODO」即红（轨 M 批 M6 守） | 注释叙述过程 ⇒ 代码改了注释不改，且读者分不清哪句还成立 |
| **2** | **机制优先** | 每条问题必须落成**一个守卫 / 一份真源 / 一个类型约束**；只做人工修正不算闭环 | 人工修一次，同类问题下一轮再来（实测本仓同类削格已发生两次） |
| **3** | **不新增真相** | 改文档时先确认那条事实的 owner；本文只链接，不复述 | 同一事实写两处 ⇒ 改一次要动两处，必然漂移 |

> **为什么第 2 条要写死**：本仓的守卫体系已经证明「有判据的问题会消失，没判据的问题会复发」。
> 本文的每条改进若不能变成一个守卫，它就只是待办，不是改进。

## 3. 推进顺序与依赖

```
第 1 阶（零行为风险，全是安全网）  M2 → M3 → M5 → M6 → M1 → C1
第 2 阶（真源与契约）              M4 → D1 → D2 → D3 → D4 → D5

第 5 阶（迁移主轨）                S0 → S1 → S2 → S3 → S4 → S5 → S6
```

三条依赖理由：

| 依赖 | 为什么不可颠倒 |
|---|---|
| **M 轨先于一切** | M2 守基线、M5/D-005 守符号、M1 守证据——后面每批的「改输入必须变红」都靠这些判据存在；先做 S 轨等于在无安全网下动地基 |
| **C1 先于 S 轨** | 会话真源归一会大量动 `session`，若 `classify`/`compose` 的词表抄本还在，切换期的一次漂移会伪装成迁移引入的回归 |
| **S0 的 ADR 先于 S1** | 改行为面先写 ADR（[04 §3.2](./04-工程落地.md) 定的顺序）；S1 之后各批都在动事实源语义 |

**每批完成的定义**：出口判据三条齐备 + 本文状态表更新该行 + 若引入新待办，登记处是 [04 §3.2](./04-工程落地.md) 或本文，**不是代码注释**。
