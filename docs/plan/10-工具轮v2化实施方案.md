## 0. 一句话

**工具轮是 v2 切换的最后一处结构缺口**：core 的 `LlmAdapter` 抽象把工具**两头都丢了**
（下行不传工具清单、上行不返回工具调用），v2 运行器因此在结构上做不了工具轮——
不是"还没接"，是"接不上"。本方案补三处契约（工具通道 / 分发通道 / 一个格子名），
再按能力切三批。

## 1. 缺口（现状 → 目标）

| # | 现状（v1 侧有 / v2 侧无） | 目标 |
|---|---|---|
| 1 | `ProviderLlmAdapter` 调 `execute_turn(…, &[], …)`——**工具清单下行恒空** | 工具清单从 `TurnInput` 一路传到 provider |
| 2 | `generate_streaming` 返回 `(String, u64)`，`TurnOutput.tool_calls` 被丢弃 | 工具调用上行到 v2 运行器 |
| 3 | 工具分发在 `session` 插件（`process_tool_calls_async`：要插件宿主 + 调用上下文 + 转写 + 会话目录） | core 定契约、`session` 实现（E-009：core 不得认识插件） |
| 4 | 网格里没有工具事实：`EVENT_ARTIFACT_ASSERTED` 不存在 | `artifact.added` 落格，`produced_by` 指向本轮用户格 |
| 5 | `v2_takeover` 要求 `inputs.tools.is_empty()`——工具轮一律回退 v1 | 放开（批 1 起，非交互工具轮走 v2） ✅ |
| 6 | e2e **零 v2 覆盖**（26 用例，0 个碰 `v2_mode`） | 每批一条 e2e，用 `/_requests` 回读请求体 ✅（批 1 = `t26`、批 2b = `t27`） |

> **第 6 条是本方案对既有工作的纠正**：v2 切换线（`v2_mode` 总开关 / 流式 / 执行器 /
> 中止语义四批）都只有单测，而 [08 §0 纪律 2](./08-分步实施计划.md) 要求每批一条 e2e。
> 单测证明不了"工具结果真的进了下一轮请求"——那要读回请求体（[08 §0.1](./08-分步实施计划.md)）。
> 本方案从批 1 起补齐，既有四批的 e2e 另立一批回填（不在本方案的批次内）。

## 2. 契约形状（三处新增，都是"加数据 / 加通道"）

### 2.1 `LlmAdapter` 的工具通道（core）

```rust
/// 一轮生成的**完整**产物（工具通道）：文本 + 本轮请求的工具调用 + 实测耗时。
pub struct LlmTurn {
    pub text: String,
    /// 模型**请求**的工具调用（尚未执行）。形状复用 core 既有 `TurnToolCallInfo`
    /// ——它是 provider 边界上已经在用的类型，另立一个必然要写映射（两处必然漂移）。
    pub tool_calls: Vec<TurnToolCallInfo>,
    pub cost_ms: u64,
}

/// 工具清单下行 + 工具调用上行。默认实现 = **忽略工具清单、`tool_calls` 恒空**
/// （不支持工具的适配器照常答文本——诚实降级，不是失败）。
async fn generate_turn(
    &self, tok: &FullModel, prompt: &str,
    tools: &[CapabilityMeta], sink: Arc<dyn DeltaSink>,
) -> Result<LlmTurn, AdapterError>;
```

`generate_streaming`（无工具）保留为**单工具轮的等价降级**：`generate_turn(…, &[], …)`
的薄包装，使"有工具"与"无工具"只有一条路径（Reasoner 的既有单路径纪律）。

### 2.2 `DispatchPort`：core 契约 + `session` 实现（core）

```rust
/// 一次工具调用的**事实形状**（core 侧，不认识插件）。
pub struct DispatchOutcome {
    pub call_id: String,          // 回填给模型时锚定 ToolCall
    pub name: String,
    pub text: String,             // 结果正文（失败也是正文——工具失败是信息性的）
    pub ok: bool,                 // 前端可区分展示；**不**改变 Turn 终态
    pub needs_user_action: bool,  // confirm / ask_user ⇒ 本轮收束等用户（批 2）
}

/// core 契约：一轮工具分发。**实现方是 `session` 插件**（它持有插件宿主与转写）。
pub trait DispatchPort: Send + Sync {
    async fn dispatch(&self, turn: &LlmTurn) -> Vec<DispatchOutcome>;
}
```

**为什么入参是整轮 `LlmTurn` 而不是只给 `tool_calls`**：分发方要落的是**一条完整的
助手轮**（中途正文 + 工具调用节点 + 结果节点）——只给 `tool_calls` 就落不出前半段，
下一轮请求里模型看不到自己请求过什么。

**为什么必须是 trait 而不是把分发搬进 core**：分发的全部输入（插件宿主、调用上下文、
转写、会话目录）都是插件侧的东西；core 认识插件即违 E-009，而依赖方向由编译器保证
（同 `ProviderLlmAdapter` 搬进 core 时的那条理由，ADR 见 [DECISIONS](../DECISIONS.md)）。

### 2.3 格子映射（数据，不加枚举）

| 事实 | 格子 | 名字 | 载荷要点 |
|---|---|---|---|
| 工具**结果** | `artifact × asserted` | `artifact.added`（新增名字常量） | `{ "tool": <name>, "text": <结果正文> }`，`produced_by` → **本轮用户格** |

**工具调用本身不单独占格**：S02 §3 的增量清单只有 `artifact.added` 一个格子，
验收断言也写「`caused_by` 指向发起它的 `task/turn`」（即本轮用户格）。
`task.progress` **不复用**——它已被抢占判定者（S07）按 `task_id` 消费，同 kind 两义
会让"挂起中"的判定跟着工具轮抖动。

### 2.4 恢复口径：**续写同一轮**（批 2 新增的判决）

批 1 只做到「等待轮停下且不落收束格」。批 2 要回答的是**恢复时那一轮算什么**——
答案由 C4 反推出来，不是选出来的：

| | 形状 | 后果 |
|---|---|---|
| 等待轮 | `u-{turn}` + `artifact.added`（pending 载荷）+ **无收束格** | `unresolved_turns`（C4）看得见这个缺口——「还没完」是诚实的 |
| 恢复轮（**本方案**） | 续写**同一** `turn`：不新开用户格，补 `artifact.added`（恢复结果）+ 收束格 | 原轮缺口被**真正填上**，C4 归零 |
| 恢复轮（若另开新轮） | `u-{turn+1}` + `f-{turn+1}` | 原轮**永远**等不到收束事件 ⇒ C4 把它当**永久假缺口** ⇒ 不变量失去判据价值 |

**判据是 C4 的配对方式**：`unresolved_turns` 按 **turn 号**配对（`opened` 遇**同号**
`closed` 才消除）。所以「续写同一轮」不是风格偏好，是让不变量继续成立的必要条件。

**交换怎么回到模型**：恢复方（`resume.rs`）是唯一知道「刚重跑了哪个工具、拿到什么」
的地方——它把这段交换（`ResumedTool`）交回 chat_loop，`v2_exec` 据此落 `artifact.added`
并拼进 prompt。**不让 v2 去会话存储里猜哪条是刚恢复的结果**：那是启发式，恢复方直给是事实。

**为什么用户格不重开**：恢复请求（approve / reject / answer）**没有**新用户发言
（`single_message` 为 `None`）。重开一格会让同一句话在网格里出现两次，且
`window_by_turn` 会把那一轮数成两轮。

> **e2e 的前置（批 2 的真实依赖）**：CLI 目前把 `resume: None` 写死
> （`cli/src/client.rs:455`）⇒ **没有恢复入口**。`t27` 要先补一个能驱动恢复的入口
> （CLI 旗标，或 e2e 直发 `session/chat/send` 的 `resume` 字段）。这是批 2 的
> **2b 子批**，机制与单测（2a）不受它阻塞。
>
> **已落地（2026-10-05）**：取第二种形态——**e2e 经 gateway HTTP 边界直发**
> `session/chat/send` 的 `resume` 字段（`t27`）。不动生产代码，且验的正是前端恢复
> 走的同一条路（`handle_chat_send_oneoff` 的 resume 分支 → `start_turn` 直连，
> `message` 与 `resume` 互斥、`target_id` = 提问所在 ToolCall 节点 id）。
> 「CLI 旗标」形态**本步不做**——它是给真人用户的入口，属独立一批（一步只改一件事）。

## 3. 批次（按能力切，每批一条 e2e）

| 批 | 能力 | 改动 | e2e |
|---|---|---|---|
| **1** | **非交互工具轮由 v2 执行** ✅ | §2.1 + §2.2 + 运行器工具循环 + `artifact.added` 落格 + 放开 `v2_takeover` 的 `tools.is_empty()` | `t26`：mock-llm `toolCalls` → 工具执行 → **`/_requests` 回读**：工具结果进了下一次请求；网格有 `artifact.added` 且带溯源 |
| **2a** | **审批与恢复（机制）** ✅ | `DispatchOutcome.needs_user_action` ⇒ 本轮收束等用户（批 1 已有）；恢复**续写同一轮**：`TurnResume`（core）+ `ResumeOutcome::Continue{resumed}`（插件）+ 落格与 prompt 回灌 | 单测：`resume_continues_same_turn_without_reopening_user_cell`（C4 缺口被填、用户格不重开） |
| **2b** | **审批与恢复（e2e）** ✅ | 补一个能驱动恢复的入口（**e2e 经 gateway 直发 `session/chat/send` 的 `resume`**） | `t27`：`ask_user`（interactive）→ 本轮停在等用户（WAL 有产物格、**无收束格**）→ 经 `resume: answer` 回填 → 续写**同一 turn** 并收束（WAL 同一 turn 有 final、用户格不重开） |
| **3** | **工具事实的投影消费** | `artifact.added` 进 `transcript` 投影（多轮 prompt 能重建含工具的对话） | 两轮工具轮的会话，第二轮请求包里带第一轮的工具结果（编号顺延——`t28` 已被 plan/12 占用） |

**顺序不可颠倒**：批 2 的恢复需要批 1 的循环；批 3 的投影需要批 1 的格子。

**每批出口判据**（[08 §2](./08-分步实施计划.md) 三条，缺一不可）：单测（新增分支全覆盖）+
e2e（`node e2e/run-tests.mjs tNN` 绿，含 LLM mock 与 `/_requests` 回读）+ 门禁（`node scripts/gate.mjs` 全绿）。

## 4. 架构改动登记（论证"必需"）

| # | 改动 | 必需的理由 | 不做的后果 |
|---|---|---|---|
| 1 | `LlmAdapter` 增 `generate_turn`（工具清单入 / 工具调用出） | 工具轮 v2 化的**前提本身**：现有抽象里没有工具的位置，运行器拿不到模型请求的工具调用 | 工具轮永远只能回退 v1——v2 切换线止步于此 |
| 2 | 新增 core `DispatchPort` 契约 + `DispatchOutcome` | 分发输入全在插件侧，core 认识插件违 E-009（依赖方向由编译器保证） | 要么把插件搬进 core（违 ADR-023 准入），要么 v2 永远做不了工具轮 |
| 3 | 新增事件名 `artifact.added` | S02 §3 的格子；`Entity::Artifact` / `Verb::Asserted` **已在冻结闭集内** ⇒ 加名字是数据变化（[01 §6](./01-核心架构.md)） | 工具结果无处落格，`caused_by` 无锚点 |
| 4 | 放开 `v2_takeover` 的 `tools.is_empty()` | **这就是批 1 的能力本身** | 工具轮仍走 v1 + 桥转写，v2 网格永远缺工具事实 |

## 5. 明确不做什么

| 不做 | 理由 |
|---|---|
| 为工具**调用**另立格子（如 `task.progress`） | S02 §3 的增量清单只有一个格子；`task.progress` 已被抢占判定者按 `task_id` 消费，同 kind 两义会污染挂起判定。要加先出 ADR |
| 把 `process_tool_calls_async` 搬进 core | 它要插件宿主 + 转写 + 会话目录；搬进去即 core 认识插件（违 E-009） |
| 改 `TurnOutput` / `TurnToolCallInfo` 形状 | 它们是 provider 边界已在用的类型；加映射层会造第二份形状 |
| 回填既有四批（总开关 / 流式 / 执行器 / 中止）的 e2e | 那是**另一个批次**（一步只改一件事）；本方案从批 1 起补齐，回填另立 |
| 动 `MessageType` / `MessageStatus` 枚举 | 跨栈 schema，前端逐字段镜像（[08 §4](./08-分步实施计划.md)） |

> **本表全部是"本步不做"，不是"不需要做"**——判据见 [plan/README §0.1.1](./README.md)。
