## 0. 顶层机制：单文档 + 元信息 + 自动汇总

项目里凡是「一堆条目汇成一张表」的地方（待办清单、规范清单、问题登记、纪律地图……），
手写表格的失效方式是同一套：**状态流转靠人改格子、依赖倒置没人判、表里的编号指到不存在的东西无人核对**——
而这正是 [13 §0](13-质量改进总纲.md) 纪律 2（机制优先）与纪律 4（出口可核对）要治的形态，
只是那两条纪律此前没有落到**登记处自身**。顶层解法三段：

1. **条目 = 数据**：每条任务 / 规范是一个带 front-matter 的单文档，住 `docs/registry/<kind>/<id>.md`；
   编号、状态、依赖、证据全在机读字段里，正文承载人读内容（条目形态见 [SP-001](../registry/spec/SP-001.md)）。
2. **汇总 = 投影**：[docs/registry/INDEX.md](../registry/INDEX.md) 总账与各 kind 的 INDEX 由脚本渲染，
   **确定性输出、无时间戳**；门禁 [`gate.d/60-facts.mjs`](../../scripts/gate.d/60-facts.mjs) 的
   `autoWork` 自动重生成并暂存——与 `docs/CURRENT.md` 是同一条约定：投影没人需要手更它，
   就不存在「忘了更」。
3. **校验 = 守卫**：[`registry-audit`](../../scripts/registry-audit.mjs) 把字段 / 状态机 / 依赖 /
   优先级 / 取代链 / 判据指认全部机械判定（RG-001…RG-019），违规即红；范围读不出必须 exit 2，
   **不许退化成「什么都没校验」**。

**边界（这是谁的活）**：本机制接管的是**人维护的汇总登记**。代码投影类的生成物
（`docs/CURRENT.md`、GATE_CODES、routes.gen）owner 是各自的 gen 脚本，**不搬进 registry**——
搬进去就是第二个真相源，违反职责表。

## 1. 一个条目长什么样

骨架示意，字段全集与状态矩阵以 [SP-001](../registry/spec/SP-001.md) 为准：

    ---
    kind: task
    id: T-002
    title: 接管 13 §1 问题登记
    status: todo
    created: 2026-10-11
    track: meta
    deps: [T-001]
    ---
    ## 内容
    这条任务要做什么、为什么。
    ## 处理过程
    - 推进记录；闭环后仍可追加。

- front-matter 是**受限 YAML 子集**（零外部依赖）：只认四种值形态，未知字段 / 重复字段 /
  不合形状的行一律判红——拼错的字段名不会被静默忽略。
- 正文小节按 kind 约定：task 是 `## 内容` + `## 处理过程`，spec 是 `## 规范` + `## 判据`。
- 文件名必须等于编号：`T-002` 只能住在 `docs/registry/task/T-002.md`；编号全 registry 唯一（含跨 kind），
  所以 `deps` 敢跨 kind 指。

## 2. kind 一览与新增方式

| kind | 回答什么 | 目录 | 状态词 | 汇总页 |
|---|---|---|---|---|
| `task` | 要推进的**事**（旧汇总文档的接管也走它） | `docs/registry/task/` | `todo` `doing` `done` `wont` | [task/INDEX.md](../registry/task/INDEX.md) |
| `spec` | 必须成立的**规范条文**（条文 + 判据） | `docs/registry/spec/` | `draft` `active` `retired` | [spec/INDEX.md](../registry/spec/INDEX.md) |
| `adr` | **架构决策**的身份与状态（正文 owner 是 [ADR 索引](../registry/adr/INDEX.md)） | `docs/registry/adr/` | `active` `superseded` `withdrawn`（+ `impl` 落地进展） | [adr/INDEX.md](../registry/adr/INDEX.md) |

**新增一个 kind = 三件事**：`registry-lib` 的 `KINDS` 加一份配置（状态机 + 必填小节）、
加一个渲染器、加回归测试。**不新开脚本、不新开判据码命名空间**；`docs/registry/` 下未登记的
kind 目录直接判红（RG-013——命名空间必须闭合，同 GW-004 的理）。

**`adr` 为什么值得单开一个 kind**（而不是塞进 `spec`）：它证明「能用现有 kind 承载就不加
kind」这条判法有**边界**。ADR 状态在实践里有**两个正交维度**——**规范合法性**
（这条决策还算不算数）与**落地进展**（做到哪一步）。`spec` 的状态机装不下第二个维度：
硬塞就只有两条路，一是把「现行（含未完成项）」这类自由文本写进 `status`（违反 RG-004
的词表封闭），二是把「已落地 / 部分实施」也塞成状态词（那 `spec` 的 `retired` 语义立刻
被污染）。所以 `adr` 单开：`status` 管前者（`active` / `superseded` / `withdrawn`），
`impl` 管后者（`planned` / `partial` / `done` / `none`，RG-017）。**判法不是「宁少不多」，
是「一个 kind 只能有一条状态轴」**——超出这条轴的语义必须另开字段（这里）或另开 kind（此处）。

## 3. 状态流转与完成定义

- **状态只写在条目文件**：流转 = 改 front-matter 的 `status`，过程追加进 `## 处理过程`；
  总纲、总账、看板一律不抄状态（职责表在登记上的投影）。
- **完成定义**：task `done` ⇒ `evidence` 非空（提交 / 守卫锚）且 `signal` 清空；
  `wont` ⇒ `reason`；spec `retired` ⇒ `reason`。矩阵由 RG-007 执行。
- **开工前置**：task 进入 `doing`（或进入 `done`）⇒ 所有 `deps` 已闭环；
  依赖不得悬空、不得成环（RG-006 / RG-008）。
- **看板与条目同序**：待处理列表按拓扑序渲染，前置在前；渲染确定性是 autoWork 的前提。
- **排序提示不是义务**：`task` 的可选 `prio`（`now / next / later`，缺席 = 最低档）只影响
  看板与 INDEX 的**同层排序**（先拓扑、后 prio、再编号）——`deps` 是义务（事实），
  `prio` 是提示（判断）；不想定级不必硬填，判据不因此判红。

## 4. 冲突与优先级（谁说了算）

**优先级只排顺序，不裁决冲突。** 让「高优先级的规则压过低优先级的规则」等于把矛盾合法化：
两条矛盾的规范可以合法并存，且优先级膨胀之后裁决本身又成了新冲突。本仓的裁决分层——
每层都有既有原语，新机制只延伸它们：

| 冲突 | 裁决原语 | 规则 |
|---|---|---|
| 事实 vs 事实 | [职责表](../README.md)（一个事实一个 owner） | 两处矛盾 = 一处越界，改引用方，**不投票** |
| 规范 vs 规范 | 状态机 + `supersedes` | 同主题不许两条 `active` 并存：一条 `retired`（`reason` 写明被谁取代）或合并；新规范用 `supersedes` 显式指认取代链（RG-015：目标存在且为 spec、不自指、不成环、不得与自己同为 `active`） |
| 规则 vs 任务 | [13 纪律 5](13-质量改进总纲.md)（豁免必有清除任务） | 任务**永远压不过规则**：要么改任务，要么登记豁免 + 清除任务 |
| 守卫 vs 守卫 | GW 接线名单 | 一个事实只许一条判据在判；两条守卫判同一件事 = 接线错误 |

优先级的赋值是**判断不是事实**，机制只保证三件事：词表封闭（RG-014）、缺席不判红、
排序确定（先拓扑、后 prio、再编号）。

## 5. 汇总与守卫（三条命令）

| 命令 | 角色 | 何时用 |
|---|---|---|
| `node scripts/registry-audit.mjs` | **守卫**（门禁 GUARDS） | 改完条目自查；CI 会跑 |
| `node scripts/registry-audit.mjs --write` | 守卫 + 重生成汇总页 | 门禁 `60-facts` 自动做，本地一般不用手跑 |
| `node scripts/registry-board.mjs` | **查询台**（`--kind=` `--status=` `--id=`） | 想知道「现在要干什么」时 |

- 判据码全表见 [GATE_CODES.md](../reference/GATE_CODES.md)；各码的主题与失效形态见
  [`registry-audit` 文件头](../../scripts/registry-audit.mjs)——本节不抄全表。
- **失效形态与测试策略**：这类守卫唯一的坏死方式是**判定写宽 ⇒ 违规条目照样过、日志一片绿**。
  回归测试 [registry-audit.test.mjs](../../scripts/registry-audit.test.mjs) 对每条判据
  「注入违规必须红、且只红这一条」，反向用例钉「合法条目不误报」，再加本仓 dogfood 断言
  （条目数非零、SP-001 真表等于代码 schema）防「读空即全绿」。
- **看板不判红、看板说真话**：汇总页「忘更新」不判红（确定性投影，autoWork 兜底）；
  但 `registry-board` 打印前先跑同一套校验，**有违规只报错、不出结论**——坏掉的报告天天被读，
  比没有报告更坏。

## 6. 接管协议与清单（逐篇迁移，一篇一任务）

节奏：**先建机制，迁移另做**。每次接管 = `docs/registry/task/` 里的一个任务，
可独立回退；判「要不要混进当前工作」只问 [plan/README §0.1](README.md) 的那两个问题。

**接管协议**——适用对象不只是任务表：规则、机制（守卫与豁免通道、自动重生成约定）、
散落的决策型表述，凡是「一堆条目汇成一张表 / 一段清单」的人工登记，都走这三步：

1. **新定义**：先在 registry 里立条目——字段齐全、判据可机检。机制不够用
   （缺 kind、缺字段、缺判据）⇒ **先登记一条完善机制的任务**（T-00* 模式），
   定案改机制、同批带回归测试，再回来迁。
2. **验证**：守卫零违规 + 引用方互索不断——文中锚点、编号互引全部改写到位
   （`doc-link` 全绿），并存期间新旧两处必须一致。
3. **删除老定义**：老处收敛为一行指路，与拆散**同一批提交**完成，不留两处半截登记。

**owner 判断前置**：迁的是「登记形态」，不是「事实归属」——先按[职责表](../README.md)
问清这条事实的 owner。owner 本身不迁（代码投影、ADR 正文，见「明确不接管」）；
owner 就是人工登记处的才整表迁；台账类先分清哪些行是守卫账本的**投影**
（owner 是守卫源码，不迁）、哪些是人维护的登记（才迁）。

| 现有登记处 | 归属 kind | 接管任务 | 接管后原处只留 |
|---|---|---|---|
| [13 §1 问题登记](13-质量改进总纲.md)（跨轨状态表） | `task` | **T-002** | 一行指路 |
| [docs/README 纪律地图](../README.md)（纪律 × owner × 判据列） | `spec` | **T-003** | 指路 |
| [13 §2.1 豁免登记表](13-质量改进总纲.md)（豁免通道 × 形态 × 清除任务） | `spec` + `clears` 字段（RG-016，不加 kind） | **T-005** | 指路 |
| [04 §3.1](04-工程落地.md) 22 步状态台账（先分清守卫投影行） | 状态 → `task`；守卫投影 → `spec`（形态定案见下） | **T-006** | 指路（已定案，见下） |
| 散落决策清点（plan / design 文档里的决策型表述） | 已定案 → 归 ADR（补条目 + 指回）；未定案 → `task`（跟进） | **T-004** | 指回 ADR / 指路 |
| [DECISIONS.md §0](../registry/adr/INDEX.md) 的 55 行手写 ADR 索引（编号 / 决策 / 状态） | `adr`（**新 kind**：`status` 规范合法性 + `impl` 落地进展，见 §2） | **T-008** | 索引收敛为指路，指向 [adr/INDEX.md](../registry/adr/INDEX.md) |

**台账类的形态定案**（T-005 / T-006 共用的判法，落地过程见 [04 §3.1](04-工程落地.md)）：
「一堆表格汇成的台账」先按 **owner 判断前置**分行——**守卫账本的投影行**（该表的内容由某个
守卫的常量 / 账本 / 现算结果决定，如死码棘轮、`session/stats` 读数列、CI 断言清单）⇒ 登记为
`spec` 条目，**只固化「这套口径必须成立 + 谁在判」的对账关系**，明细由守卫现算、不复述；
**人维护的状态行**（如表里的 ✅ / 待办）⇒ 登记为 `task` 条目（状态即条目的 `status` 字段）。
两种都**不新开 kind**——`spec` + `task` 已装得下（同 T-005 的「能用现有 kind 承载就不加 kind」）。

**决策类元素的登记形态**（T-004 定案）：决策（「为什么这样设计 + 被否决的方案」）的
**正文 owner 永远是 ADR**（[`docs/registry/adr/`](../registry/adr/) 单文档，
职责表），registry **不复制决策**。散落决策的接管边界只有两种情况：

- **已定案** ⇒ 在 ADR owner 补条目、原处改链接（原文若带正文，删正文只留指回）；
- **未定案的决策**（如某设计文档的「待确认决策」表）⇒ 登记为 `task`（它就是一条**跟进动作**，
  `exit` = 「定案并写 ADR」），原处只留指路。

**决策体自身接管**（T-008 定案）：ADR 的**登记形态**（编号 / 状态 / 落地进展 / 取代链）
住 `docs/registry/adr/`，与上面的「散落决策」是两件事——前者是 ADR 自己那份手写索引，
后者是别处冒出来的决策。定案：**新开 `adr` kind**（理由见 §2），
**决策正文的 owner 随索引一并迁入 [docs/registry/adr/](../registry/adr/)**（
见下「明确不接管」）——迁的只是索引这一层登记形态。落地过程见
[`T-008`](../registry/task/T-008.md)。

**不为决策新开 kind**（同 T-005 / T-006 的「能用现有 kind 承载就不加」）。
落地过程与清点结论见 [`T-004`](../registry/task/T-004.md)。

**明确不接管**：

- 代码投影生成物（`docs/CURRENT.md`、GATE_CODES、routes.gen）——owner 是各自 gen 脚本；
- 代码投影生成物之外的 ADR——**已全部接管**：编号 / 状态 / 落地进展 / 域 / 取代链
  与**决策正文**同框在 `docs/registry/adr/` 下的单文件条目（每条一个 `ADR-NNN.md`），
  原 `DECISIONS.md` 索引与五个域分册已删除，registry 是唯一真源；散落在非 owner
  文档里的决策型表述只做清点与处置（T-004）。迁移见 [`T-008`](../registry/task/T-008.md)；
- 一次性报告与归档（`docs/archive/`）——归档不进登记。

## 7. 明确不做

- **不做通用工作流引擎**：没有状态机 DSL、没有条件流转；kind 的差异只落在 `KINDS`
  的一份配置里，判据宁红不漏。
- **原表与迁移不拆批**：接管任务的出口是「原处只留指路」，拆散与删除同批完成，
  不留两处半截登记。
- **不在 `docs/` 下放条目文件**：条目是数据不是现行文档——`## 处理过程` 天然含过程叙述，
  会撞职责表的「现行文档不写变更史」；`doc-link` 的扫描范围也不含 `registry/`。
- **汇总页不加时间戳、不写「最后更新于」**：确定性是自动重生成的前提。
