# S07 · 插话与实时打断

> 天梯 **T3–T4** ｜ 前置：S06 ｜ **新增机制键 0** ｜ 参数变化 4 ｜ 阶段四

## 1. 场景：要什么能力

智能体正在说话 / 正在跑长任务时，用户插一句话；系统能**在反射层内**决定"停 / 继续 / 改道"，
事后还能回到被打断的地方。

相对 S06 高了什么：**系统第一次需要在几十毫秒内对外部信号做决策**。
S06 及以前的所有决策都在 300ms 以上，本阶把反射层（≤80ms）真正点亮。

## 2. 为什么它能落在 v2 上（J1）

| 看起来新的东西 | 实际是 |
|---|---|
| 打断信号 | `control/opened`（`task.controlled`）事件 |
| 抢占判定 | 一个 `Decider`，`budget_ms = 80` |
| 被挂起的状态 | `task/held`（`task.blocked`）——**挂起就是一条事件** |
| 恢复 | 从 `seq` 重放 → 投影自动回到断点 |

**关键**："挂起"不需要新状态机。挂起 = 一条 `held` 事件；恢复 = 投影自然包含它。
这也是为什么本阶**新增机制键 = 0**——打断在 v2 里不是新机制，只是新的一格事件 + 一个更快的 Actor。

## 3. 增量清单（只加数据）

| 类型 | 内容 |
|---|---|
| 事件格子 | `control/opened`（`task.controlled`）、`task/held`（`task.blocked`） |
| ActorSpec 行 | 抢占判定者 `{ pattern: decider, capabilities: [JudgeIntent], budget_ms: 80, scope: root }` |
| grants 行 | 抢占判定者 ▸ 可写 `task.controlled`，不可写 `chat.assistant.*` |
| 投影参数 | `projection = turnstate`（该 turn 的事件，常数开销） |

**本阶点亮的机制键**（阶梯总表的「新增机制键」由这张块算出；`scripts/gen-verify-facts.mjs` 从这里取输入）：

```capability-assign
event.entity = control
event.verb = held
actor.budget_ms = 80
projection = turnstate
```

## 4. 平凡值与回退（J2）

| 参数 | 完整值 | **平凡值** | 平凡值下 |
|---|---|---|---|
| `event.entity` | `control` | **`turn`** | 仍完整运行——不接受插话，退化为 S06 的"跑完再说" |
| `actor.budget_ms` | `80` | `60000` | 仍完整运行——判定慢，用户感到迟钝但不出错 |

**`control` 关闭 = 本阶整阶可跳过**，且系统仍完整。这是插话能力"是数据不是机制"的直接证据。

## 5. 静默失效与强制（J3）

| 约束 | 违反时信号 | 强制方式 |
|---|---|---|
| 抢占判定必须在 80ms 内产出 | **无**——只是慢，无人报错 | I3：超时必须产出 fallback 事件 |
| 被挂起的任务不得被二次调度 | **无**——可能重复执行 | `readyset` 排除 `held` 状态（投影过滤） |
| 抢占判定者不得直接发言 | **无** | grants 表：无 `reply.*` 写权 |

## 6. 验收断言

1. 注入打断事件 → 80ms 内必须存在一条 `task.controlled`（或 fallback）。
2. 挂起期间该任务不出现在 `readyset` 中。
3. 恢复后投影与挂起前一致（除新增的 `held`/`controlled` 事件外）。
4. **反向用例**：把预算放宽到 60000ms → 断言 1 的判定结果必须改变（证明预算参数真的在生效）。

## 7. 这一阶做不了什么

- 只能"停 / 继续 / 改道"三选一，**不能理解插话的语义并做复杂重规划**——那要回到 `Reasoner` 层（300ms+）
- 真正的硬实时（T7）未实测（[03 §7.3 G2](../03-演进与验证.md)）；本阶只有预算断言
- 多个插话并发到达时的优先级是 `readyset` 的打分参数问题，架构不规定策略
