## 0. 一句话

把「n 条补充 = n 轮」改成「n 条补充 = **同一轮的一条输入**」。
改 2 处调用点、加 1 个纯函数、加 1 个配置块；**不动存储格式、不动 `MessageType`、不动路由**。

## 1. 现状（代码事实）

### 1.1 入队与消费

| 环节 | 位置 | 现状 |
|---|---|---|
| 入队 | `symbio/src/plugins/session/transcript/inbox.rs:76`（`enqueue_inbox`） | `inbox.push_back(item)`，条目 id 三来源（地址末段 > 消息自带 id > 生成） |
| 消费 | 同文件 `:196`（`drain_inbox_once`） | **`pop_front()` 一条** → `run_inbox_turn` |
| 忙则不抢占 | 同文件 `:204` | `if is_working { continue }` —— 条目留在队里 |
| 启动一轮 | 同文件 `:247`（`run_inbox_turn`） | 自造 `ctx`（只带 `SESSION_ID` / `WORKDIR`），直呼 `start_turn` |

### 1.2 主循环骨架

`symbio/src/plugins/session/chat_loop.rs:77`（`run_chat_loop`）：

```text
前步骤 ① 请求快照 ② 开会话 ③ TurnState + 容器 ④ resume
loop
  步骤1 :149  加载上下文；:167 首轮追加 single_message；:180 对齐 last_saved
  步骤2 :185  gate_turn（唯一判定点）           ← Gate::Proceed / WaitForTools / Exit
  步骤3 :218  prepare_turn_inputs（唯一收集点） ← 请求视图在此构建（inputs.rs:165）
  步骤4 :248  execute_turn（唯一 LLM 发起处）
  步骤5       settle_reasoning
  步骤6       close_turn（工具分发 + 落库）
  步骤7 :333  finalize_turn_root
end loop（只能由 return 离开，全部经 finish_turn 收尾）
```

### 1.3 三条必须尊重的既有性质

| 性质 | 依据 | 对本方案的约束 |
|---|---|---|
| **工具批次同步跑完才回循环顶部** | `gate_turn`（`:374`）判的是 `turn.in_flight_tools`；级别 1 下 `process_tool_calls_async` 串行阻塞，回来时集合恒空 | 抽干点放在 `Gate::Proceed` **之后**，天然不会插在 `assistant(tool_calls)` 与其 `tool` 结果之间 |
| **落库按锚点增量切片** | `persist_messages`（`chat_loop/io.rs:48`）落 `context.messages[last_saved..]` | 在轮边界 append 后**不要动 `last_saved`**，下一次 `persist_messages` 自然带上它 |
| **轮起点判定只回看 Turn 之前** | `find_turn_user_split_idx`（`symbio/src/plugins/session/context.rs:165`）只扫 `messages[..turn_idx]` 且要求 `parent_id.is_none()` | 补充写在 Turn 根**之后**且 `parent_id = None`，不影响本轮起点 |

### 1.4 计数口径（两处不同，别混）

| 机制 | 位置 | 按什么计数 | 受补充条数影响 |
|---|---|---|---|
| **存储裁剪** | `symbio/src/plugins/session/chat_session/write.rs:363`（`prune_historical_tool_calls`） | **`role = User` 的消息数** | ✅ **是**——这就是必须合并成一条的理由 |
| 请求视图窗口 | `symbio/src/plugins/session/context/window.rs:344`（`apply_layered_sliding_window`） | **ToolCall 数** | ❌ 否 |

> 逐条追加会让 n 条补充吃掉 n 份**保留预算**，把更早的轮次提前挤出裁剪窗口。
> 合并成一条，n 条在计数上仍是一轮。

## 2. 改动点一：空闲起轮抽干整队

**位置**：`drain_inbox_once`（`inbox.rs:196`），`pop_front()` 一处改为"抽干"。

```text
今天：pop_front() 一条 → run_inbox_turn(item)
本方案：drain 至多 max_per_drain 条 → merge → run_inbox_turn(merged)
```

**必须逐条发 `bare` 变更**：抽走的每一条都要在它自己的地址上通知一次
（与 `cancel_inbox_item` / 现有出队同一手法）。漏发 = 前端认为它还挂在队里。

**启动失败的回滚语义要改**：今天是 `push_front(item)` 放回一条。抽干后是 n 条，
失败时必须把 **n 条按原顺序整体放回队首**（`for item in drained.into_iter().rev() { push_front }`），
否则顺序会被打乱——而顺序是这个队列唯一的不变量（FIFO，ADR-026）。

## 3. 改动点二：轮边界抽干并折进当前轮

**位置**：`run_chat_loop` 的 **步骤 2 与步骤 3 之间**（`chat_loop.rs:203` 与 `:215` 之间）。

```rust
match gate_turn(&turn_req, &turn) {
    Gate::Proceed => {}
    // …其余分支不变（不抽干）
}

// ── 新增：轮边界抽干（仅非首轮）────────────────────────────────────────
if turn.tool_rounds > 0 {
    if let Some(merged) = drain_supplements_into(&context.session, &ctx, &turn_req).await {
        context.messages.push(merged);
        // 刻意**不**推进 turn.last_saved：让下一次 persist_messages 带上它
    }
}

// ── 步骤 3：本轮输入准备（唯一准备点）────────────────────────────────
let inputs = match prepare_turn_inputs(…)
```

### 3.1 三个"为什么"

| 决策 | 理由 |
|---|---|
| 放在 `Gate::Proceed` **之后** | 闸门可能 `Exit`（软上限 / 中止）或 `WaitForTools`。抽干后立刻退出 = 消费了队列却没用上，还得补偿落库。放 Proceed 之后，**只有确定要发请求才抽** |
| 只在 `turn.tool_rounds > 0` | 首轮的输入在**进入循环之前**就定了（空闲路径由 `drain_inbox_once` 抽干；`chat/send` 路径由入口落库 + `single_message`）。首轮再抽一次是多余的，且会与 `single_message` 的去重逻辑纠缠 |
| append 后**不动** `last_saved` | `persist_messages` 落 `[last_saved..]`。不动锚点 ⇒ 合并消息自动被下一次落库带上（`close_turn` 或 `finish_turn`），**失败路径也不会丢** |

> **为什么不会插在工具批次中间**：`gate_turn` 只在 `turn.in_flight_tools` 为空时放行，
> 而级别 1（同步工具执行）下 `close_turn` 里的 `process_tool_calls_async` 是串行阻塞的——
> 回到循环顶部时本批结果**必然已齐**。因此本抽干点结构上不可能落在
> `assistant(tool_calls)` 与其 `tool` 结果之间（那会让部分协议直接 400）。

## 4. 合并规则（纯函数）

```rust
/// 拟新增：symbio/src/plugins/session/transcript/supplements.rs
/// 把一批补充条目合并成**一条**用户消息。纯函数（无 IO、无时钟），可单测双跑。
pub fn merge_supplements(items: &[InboxItem]) -> ChatMessage;
```

### 4.1 形状

```text
id            = items[0].id              // 取第一条的 id：地址末段即身份
role          = user
msg_type      = text
parent_id     = None                     // 顶层，与普通用户消息同形
status        = completed
content       = items[*].content 按原顺序拼接
meta.supplement       = true
meta.supplement_ids   = [items[0].id, items[1].id, …]
meta.supplement_count = n
```

### 4.2 正文拼接：**不改写用户原文**

用 `"\n\n"` 连接，**不加编号前缀、不加分隔线**。

> 改写用户原文是**不可逆的信息损失**——模型看到的必须是用户真正说过的话。
> 需要条目边界时读 `meta.supplement_count`；若实测证明模型确实分不清 n 条，
> 再考虑 `[i]` 前缀（那是一次**需要证据**的改动，不是起点）。

### 4.3 参数取谁：**取当前轮，不取条目**

`InboxItem` 带 `params` 与 `workdir`（`inbox.rs:92`），但**轮边界抽干发生在轮已经跑起来之后**——
provider / model / workdir 在那一刻已经是本轮的事实。因此：

> 补充只贡献**正文**。条目自带的 `params` / `workdir` **一律忽略**；
> 若与当前轮不同，记一条 `plugin_warn!`（可审计，不静默）。

## 5. 配置面

```yaml
# <根>/session/PLUGIN.yml
supplements_enabled: true         # 平凡值开关；false ⇒ 完全退回"一条消息 = 一轮"
supplements_max_per_drain: 20     # 单次抽干上限；超出者留队，下一个轮边界再抽
```

**两个字段，都是必需的**：

| 字段 | 为什么必需 | 为什么不是"预留" |
|---|---|---|
| `supplements_enabled` | J2 平凡值——关闭后必须完全退回现状，这是安全网 | 可被 e2e 直接验证（关掉它，行为与今天逐字一致） |
| `supplements_max_per_drain` | 合并**必须**有上界：无界合并会把一次刷屏变成一条巨型消息 | 上界是护栏，不是策略 |

**刻意不做的两个字段**（按"架构修改必须是必需的"筛掉）：

| 不做 | 为什么 |
|---|---|
| `settle_ms`（静默窗口） | **假想的**——它解决"整合过于零碎"，而这个问题**尚未被观测到**。等实测出现再加 |
| `supplements_merge_at_turn_boundary`（轮边界开关） | **与 `enabled` 重复**：关掉 `enabled` 两个抽干点一起失效，单独关边界点没有真实使用场景 |

配置走既有的 `capability_announce_configurable`（配置就是插件目录里的 `PLUGIN.yml`，
**没有第二条配置协议**）。`SessionConfig` 的每个字段都带 `#[serde(default)]`，
因此**新增字段无需任何数据迁移**——旧配置文件照常可用，缺键取默认值。

## 6. 验收

### 6.1 单测

| # | 用例 | 断言 |
|---|---|---|
| T1 | 队列放 3 条 → `drain_inbox_once` | 只启动 **1** 轮；转写里恰好 **1** 条 `role = user` 且 `parent_id` 为空的补充消息；`meta.supplement_count == 3` |
| T2 | 同上，检查条目 | 3 条各自发出 `bare` 变更；队列清空 |
| T3 | 启动失败回滚 | 队列恢复为**原顺序**的 3 条（FIFO 不破） |
| T4 | 轮边界：`tool_rounds = 1`，队列放 2 条 | 第 3 步的 `request_view` 里出现合并消息；它在 Turn 根**之后** |
| T5 | 回归：`find_turn_user_split_idx` | 补充存在与否，返回值**不变** |
| T6 | 合并纯函数 | 同输入双跑逐字节相同；`max_per_drain` 截断时留队条数正确 |

### 6.2 断言与落点（[06 §7](./06-会话响应性落地.md)）

| # | 断言 | 违反时 | 落在哪 |
|---|---|---|---|
| **C-D2** | 三条补充在存储里仍是**两条**用户消息（首条 + 合并成的一条） | 静默吃掉保留预算，更早轮次被提前挤出窗口 | e2e [`t19`](../../e2e/cases/t19-supplements-merge.mjs) 的 A / B / C 三条线 |
| **C-D2b** | 抽干调用的**位置**在 `gate_turn` 之后、`prepare_turn_inputs` 之前 | 前移 ⇒ 闸门退出时队列被消费却没人用；后移 ⇒ 合并消息进不了本轮请求 | `grep-audit` 的 **S-011**（静态查行号） |

> **两者的强制形式不同，理由见 [06 §7](./06-会话响应性落地.md)**：C-D2 违反时 e2e 会红，
> 所以它是**测试**；C-D2b 违反时任何测试都不会红（"行为看起来正常，只在特定时序下 400"），
> 所以它**必须**外置为静态断言。J3 只对后者提出强制要求。
>
> S-011 在**锚点缺失**（抽干点被删或改名）时判 ERROR 而**不接受豁免**——
> 守卫悄悄退化成空转，会以绿灯的形式提供虚假保证。

## 7. 平凡值、风险与待验证

### 7.1 平凡值（J2）

| 参数 | 平凡值 | 平凡值下 |
|---|---|---|
| `supplements_enabled` | **`false`** | 一条消息 = 一轮（今天的行为逐字一致） |
| `supplements_max_per_drain` | **`1`** | 空闲路径退化为今天的 `pop_front` 一条；轮边界路径仍生效 |

> **两个平凡值的语义不同，都要有**：`enabled = false` 关掉**整个特性**（含轮边界抽干）；
> `max_per_drain = 1` 只限制**合并规模**。前者是回退开关，后者是护栏——不是重复。

### 7.2 已解除的风险

| # | 项 | 结论 |
|---|---|---|
| ~~V1~~ | ~~前端乐观副本~~ | **已解除，且不需要任何前端改动**。`tauri/src/composables/useChatConnection.ts` 的 `send` 明确「**不做乐观回显**」——"消息出现在流里"就是"它已被处理"的唯一可观测证据，等待期间的可视反馈由 `working` 状态补骨架。因此 n→1 合并不可能留下孤儿气泡 |
| ~~V4~~ | ~~`chat/send` 路径的 id 复用~~ | **已解除**。同处注释写明：`outgoing.id` 就是队列条目 id，后端 `enqueue_inbox` 沿用调用方给的 id，消费时发出的**权威帧与这条消息同 id**（前端按 id 合并，不会出现两条）。因此 `id = items[0].id` 是**正确选择**，不是权衡 |
| V3 | `last_saved` 锚点与压缩路径 | 仍需覆盖：`close_turn` 里存在 `replace_messages` 后重置锚点的分支（`turn.rs:169`）。由 T4 覆盖 |

> **排队的补充消息在界面上是「inbox 集合里的条目」，不是对话流里的气泡**
> （`useChatConnection.ts`：「inbox 条目 = 还没成为消息的消息」）。
> 所以 n 条合并成 1 条的可视表现是干净的：**n 行「排队中」消失，1 条消息出现**。

### 7.3 明确不做的

| 不做 | 理由 |
|---|---|
| 新增 `MessageType` 取值 | `meta` 是自由 JSON，已有先例（`meta.kind = "context_nudge"`）——加字段是数据变化 |
| 新增收件箱集合 / 第二队列 | 现有队列就是输入缓冲，语义不变，只改**消费粒度** |
| 在 `drain_inbox_once` 之外再起一个抽干定时器 | 抽干的第二个时机是**轮边界**（代码位置），不是时间——定时器会引入"什么时候算边界"的第二份定义 |
| 让模型自己决定"要不要合并" | 合并是编排层的机械动作；交给模型等于让"一轮"这个计数单位取决于采样 |
| 改写用户原文以标注条目边界 | 不可逆的信息损失（§4.2） |

## 8. 落地顺序

| 步 | 动作 | 出口判据 |
|---|---|---|
| 1 | `merge_supplements` 纯函数 + T6 | 双跑逐字节相同 |
| 2 | `drain_inbox_once` 改抽干 + T1/T2/T3 | 3 条只起 1 轮；失败回滚保序 |
| 3 | 轮边界抽干点 + T4/T5 | 补充进请求视图且不破坏轮起点判定 |
| 4 | 配置块 + 三个平凡值 | `max_per_drain = 1` 时行为与现状逐字一致 |
| 5 | C-D2 / C-D2b 断言 | 两条断言在正确实现下绿、在错误实现下红 |
| 6 | 前端乐观副本契约（V1） | 合并后无孤儿气泡 |

**第 4 步是分界线**：在它完成之前不合并任何主分支——平凡值可回退是这批改动的安全网。
