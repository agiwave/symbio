## 0. 执行纪律（五步，每步都不得跳过）

| # | 纪律 | 判据 |
|---|---|---|
| **1** | **先实现，再单测，再 e2e（含 LLM mock），最后全门禁** | `node scripts/gate.mjs` 全绿才允许提交 —— **例外见纪律 1b** |
| **1b** | **跨批行为变更的中间态提交**（2026-10-09 补） | 见 §0.3 |
| **2** | **每一步都必须有一条新的 e2e 用例，且它跑的是**出厂默认路径** | 用例落在 `e2e/cases/`，发现式加载；**跑的不是默认路径的用例不算这条纪律的判据**（复盘 E2/E3） |
| **3** | **架构改动必须逐条论证"必需"** | 见 §3 登记表；论证不出"必需"的改动直接删掉 |
| **4** | **不做历史数据兼容** | 新字段一律 `#[serde(default)]`；新语义只对**新产生的数据**成立 |
| **5** | **完成判据必须含一条端到端判据**（2026-10-09 补） | 见 §0.4 |

### 0.3 纪律 1b：跨批行为变更的中间态提交

**问题**：纪律 1 只定义了「绿才能提交」。而一次**跨多批的行为变更**（例如
[ADR-048](../decisions/session.md#adr-048-出厂档位改-fullv2-链路是出厂路径bridge-退役)
的翻默认档位）在纪律 1 下**没有合法的落点**——中间态必然红，于是「不能提交、也不能
回退」把分支卡死。**这不是代码坏了修不动，是纪律与变更粒度不匹配。**

**这不是放宽纪律，是给它补一个缺的分支。** 允许提交的条件是**四条同时成立**：

1. 红点**已登记**：每一条失败都有归属（哪个缺口 / 哪条守卫 / 哪类形状）、有**收敛路径**
   （指向某个已登记的批次）；
2. 红点**有守卫在看**：本批建了、或已有**能红的**守卫覆盖该类失效（不是「以后会补」）；
3. 提交信息里**引用红点登记表**，不写「全部通过」；
4. 这一批**不改生产默认档位**，或者改默认档位的那一批**单独成提交**。

**判据形态**：`13 §「已知未闭合」` 那张表逐条有归属 + 提交信息引用了它。

**边界**：纪律 1b **不适用于「不知道会红什么」的情形**。红点不明 ⇒ 那是纪律 1 的场景，
不许用 1b 兜。

### 0.4 纪律 5：完成判据必须含一条端到端判据

**问题**（复盘 E1/E2/E4）：`04 §3.1` 的完成判据三条全是**局部可判定**的 ——
① 产物有生产调用点 ② 死码归零 ③ 门禁全绿。**没有一条问「这条链路在真实负载下跑得通吗」。**
于是 22 步能在一天内全部标 ✅，而整条链路从没被真实负载压过；而且过渡设施（`bridge`）
**也是生产调用点**，判据被一条注定退役的旁路满足了。

**补法**：完成判据加一条 —— **「该步在出厂默认档位下被 e2e 全量压过，且行为与设计一致」**。
只在非默认档位下验证的步骤**不算完成**。

配套三条（复盘 §7.4）：

| # | 判据 | 挡住什么 |
|---|---|---|
| **C1** | 每步的完成判据 = **默认路径经过它**，不是「有人调用它」 | 产物被旁路调用也算「接入」 |
| **C2** | **不许连续两步只加机制不切路径**：机制可以一批加完，加完必须**立刻**有一个切换步 | 机制攒够了才有第一次端到端 |
| **C3** | 每步留一个**「旧路已死」的证据**：删掉被替代的旧实现后系统仍能跑 | 缺口在加法里存活（加法无「删旧路」这一步） |

⚠️ **C3 与加法的区别**是这一整套里最要紧的一条：**加法没有「删掉旧路」这一步，所以缺口
能在加法里活下来；切换有，所以缺口活不过一批。** 本仓 `13 §S0–S6`（会话真源归一）就是
这个形状的现成模板。

### 0.5 排期缺的那条轴：切换轴

`04 §3` 的 22 步是**机制依赖序**（先 `Store`、再投影、再 `Actor`……）。而
**机制依赖序 ≠ 路径切换序**。按机制轴排期，**最后一个机制落地的那一刻，才是第一次端到端**
——于是「一次性」不是谁决定的，是**排期结构**决定的。

两条轴必须**分别排期**：

| 面 | 粒度 | 依据 |
|---|---|---|
| **机制面**（F1–F6、事件 schema） | **必须一次到位** | F1–F6 是**负向约束**（「修改它 = 架构变更」），它不「落地」只被遵守；schema 从第一天起就是终态 |
| **路径面**（生产路径切到新机制上） | **必须小步** | 它可分——一条调用点就是一步 |

**判据的粒度必须等于引入的粒度**（复盘 §7.3）：22 步每步都引入了一点点，所以它看起来
很像增量方案；但没有一步验收了那一点点——所有验收都压到了翻档位那天。

⚠️ **验证路径永远可以先切**：把 e2e 的档位参数切过去而**不动出厂默认**，是零生产风险、
回退成本为零的一步。缺的就是这一步——它让验证路径先过去，而不是让生产路径直接过去、
以「生产坏了」的形式暴露缺口。

### 0.1 为什么 e2e 必须带 LLM mock

`e2e/` 以 `cli/` 为被测前端，mock 与被测系统之间走**真实边界**：HTTP/SSE（LLM）、
stdio/JSON-RPC（MCP）、磁盘（homedir）。`e2e/mock-llm.mjs` 支持
`toolCalls` / `afterTool` / `chunks` / `chunkDelayMs` / `match` / `once` / 故障注入，
并用 `GET /_requests` 回读**完整请求体**——这正是验证"补充是否真的进了下一轮请求"的唯一手段。
单测证明不了这件事：它只证明"内存里的数组多了一条"。

### 0.2 被测二进制不需要手工重建

`scripts/cli-binary.mjs` 按**源码内容指纹**决定是否重建（门禁与 e2e 共用同一份判据）。
改完 Rust 源码直接跑 e2e 即可。

## 3. 架构改动登记（每条必须论证"必需"）

> 判据：**论证不出"必需"的改动直接删掉**。本表随批次推进追加。

### 3.1 S0 登记

| # | 改动 | 必需的理由 | 不做的后果 |
|---|---|---|---|
| 1 | `SessionConfig` 增 `supplements_enabled` | J2 平凡值——回退开关，可被 e2e 直接验证 | 特性无法回退，出问题只能改代码 |
| 2 | `SessionConfig` 增 `supplements_max_per_drain` | 合并**必须**有上界：无界合并把刷屏变成一条巨型消息 | 一次刷屏 = 一次上下文爆炸 |
| 3 | 新增 `merge_supplements` 纯函数 | 合并规则必须有**单点定义**（散在调用点必然漂移） | 两处抽干点各写一遍拼接逻辑 |
| 4 | `drain_inbox_once` 消费粒度 1 → n | **这就是特性本身** | 需求不成立 |
| 5 | `run_chat_loop` 插入轮边界抽干 | **这就是"边处理边综合"** | 补充只能等本轮结束，即"一条一条处理" |
| 6 | `meta.supplement*` 标记 | `supplement_ids` 是**可追溯性**（合并后原始条目 id 只此一处）；`supplement_count` 让模型知道有几条 | 合并后无法回溯用户到底发了几条 |

### 3.2 S1 登记（对话面切分）

| # | 改动 | 必需的理由 | 不做的后果 |
|---|---|---|---|
| 7 | 新增 `classify` 插件 + `classify/decide` 路由 | `JudgeIntent` 是**独立能力**：卸载它 ⇒ 全部输入直接进工具循环，系统完整运行（[09 §2.4](./09-对话面插件拆分实施方案.md)） | 判决逻辑寄居 `session`，卸载粒度消失 |
| 8 | 新增 `compose` 插件 + `compose/wording` 路由 | `ReplyFirst` / `ReplyAppend` 是**独立能力**：卸载它 ⇒ 无对话面文本，worker 正文照旧 | 措辞与判决绑死，无法各自选模型 / 各自开关 |
| 9 | 契约落 `symbio_core/schemas/` 各自模块 | 契约跨插件边界（session 生产、插件消费）⇒ 依赖方 ≥ 2，**满足** ADR-023 准入 | 插件间直引类型 ⇒ E-007 / E-009 违规 |

### 3.3 S2–S5 登记（**无架构改动**，逐条说明为什么）

| 批 | 本批加的是什么 | 为什么不算架构改动 |
|---|---|---|
| **S2** | `conversation_view` 纯函数 + `meta.exclude_from_context` 的**消费侧** + 路由常量 + `session` 一个调用点 | 纯函数与 `meta` 键都是**数据**（J1）；调用点是"谁来用这份数据"，不动机制 |
| **S3** | `ComposeRequest` 加 `context` / 去 `max_chars`、路由常量、落点（根级 + 两个标记） | 契约**加字段**是数据变化（J1）；落点由语义决定，不引入新机制 |
| **S4** | `RunSnapshot` + `ComposeRequest.snapshot`、`ProgressPolicy` + `due()`、四个旋钮 | `ProgressPolicy` 在 `session` **模块内部**（可妥协层）；`RunSnapshot` 是契约字段；触发点复用已有轮边界 |
| **S5** | 前端两列 + `dialogPanelSplit` 偏好；判据改「不看位置」 | 纯呈现；判据改写是**修文档**（09 §4.4 的自相矛盾），不是改机制 |

> 判据：**加了数据 / 加了调用点 / 改了文档，都不是架构改动。** 架构改动只有两种形态——
> 动冻结锚点（F1–F6 / 机制键 / 三不变量 / 三封闭集合），或**动能力切分**。本场景前者 0 处，
> 后者 1 处（S1 的拆两个插件）——见 §3.2。

### 3.4 S6 登记

| # | 改动 | 必需的理由 | 不做的后果 |
|---|---|---|---|
| 10 | 模型槽 **单槽 → 生效者 + 已启用目录**（`register_model_providers(active_id, available)` · `get_model_provider_by_id` · `resolve_model_provider`） | 「两个插件各自独立选模型」**就是 S6 的目标本身**。原槽是单槽（`Arc<RwLock<Option<…>>>`，重复注册即覆盖），插件只能拿到会话选定的那一个 ⇒ 该目标**没有任何落点** | 写进 `PLUGIN.yml` 的 `model` 键成为**注释**（没有任何读点）；S6 只剩提示词模板（半个能力） |
| 11 | `classify` 增 `model` / `system_prompt`；`compose` 新增 `ComposeConfig`（`model` / `instruction`） | 插件目录 = 配置目录（[06 §4.2](../archive/06-会话响应性落地.md)）；两个键的读者是**插件自己**，调用方不该知道 | 调优只能改代码 + 重编译 |
| 12 | **不**新增 `temperature` 键 | 温度本就是 **provider 条目**的参数（`<根>/model/<id>/provider.json`）⇒ **换条目就是换温度** | 同一件事两个 owner，且二者冲突时无判据 |

> 第 10 条的**两条判据**（为什么必须**一次**注册、为什么降级方向只能有**一处**定义）
> 写在 [09 §5 S6](./09-对话面插件拆分实施方案.md)——那是本表的理由，不在别处复述。

### 3.5 明确不新增

| 不新增 | 为什么 |
|---|---|
| `MessageType` 新取值 | `meta` 是自由 JSON，已有先例 `meta.kind`——加字段是数据变化，改枚举是 schema 变化 |
| 第二份存储 / 新集合 | 抽干改的是**消费粒度**，不是存储 |
| `settle_ms` 静默窗口 | **假想的**——"整合过于零碎"尚未被观测到 |
| 轮边界开关 | 与 `supplements_enabled` 重复，无真实使用场景 |
| 在 `session` 内建判决 / 措辞模块 | 判决与措辞是**两个可独立卸载的能力**，合并后卸载任一个都要改另一个（[09 §2.4](./09-对话面插件拆分实施方案.md)） |
| 把判决与措辞合成一个 `chat` 插件 | 同上——两者卸载语义不同，合成即失去"一个能力一个插件" |
| C-D1 断言（判决调用点不得收集工具） | 两个插件都不注册 `Capability`，"无工具"是**结构保证**，不需要断言补偿 |

## 4. 全局不做什么

| 不做 | 理由 |
|---|---|
| 改 `Store` / 引入 append-only 事实源 | **不是"不需要"，而是它属另一个迁移步**——[04 §3 第 1 步](./04-工程落地.md)的地基。混进本场景会让一步同时改"事实源"与"消费粒度"两件事，无法独立回退（[08 §0 纪律 3](./08-分步实施计划.md)）。读法见 [README §0.1](./README.md) |
| 改 `MessageType` / `MessageStatus` 枚举 | 跨栈 schema，前端逐字段镜像——改它是架构变更，收益为零 |
| 为兼容旧数据写迁移 | 纪律 4：新字段 `#[serde(default)]`，新语义只对新数据成立 |
| 跳过 e2e 直接提交 | 单测证明不了"补充真的进了下一轮请求"（那要读回请求体） |
| 一步做完四批再提交 | 每步必须能独立回退；回退单位是"一个特性" |

> **本表全部是"本步不做"，不是"不需要做"**——差别见 [README §0.1.1](./README.md)。
> 尤其第一行：改 `Store` / 引入 append-only 事实源是 v2 的**地基**，只是它属**另一个迁移步**；
> 把它说成"本场景不需要"是把目标当成了别人的事，是本方案要消除的偏差。
