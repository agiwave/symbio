## 0. 执行纪律（四步，每步都不得跳过）

| # | 纪律 | 判据 |
|---|---|---|
| **1** | **先实现，再单测，再 e2e（含 LLM mock），最后全门禁** | `node scripts/gate.mjs` 全绿才允许提交 |
| **2** | **每一步都必须有一条新的 e2e 用例** | 用例落在 `e2e/cases/`，发现式加载，无需登记 |
| **3** | **架构改动必须逐条论证"必需"** | 见 §3 登记表；论证不出"必需"的改动直接删掉 |
| **4** | **不做历史数据兼容** | 新字段一律 `#[serde(default)]`；新语义只对**新产生的数据**成立 |

### 0.1 为什么 e2e 必须带 LLM mock

`e2e/` 以 `cli/` 为被测前端，mock 与被测系统之间走**真实边界**：HTTP/SSE（LLM）、
stdio/JSON-RPC（MCP）、磁盘（homedir）。`e2e/mock-llm.mjs` 支持
`toolCalls` / `afterTool` / `chunks` / `chunkDelayMs` / `match` / `once` / 故障注入，
并用 `GET /_requests` 回读**完整请求体**——这正是验证"补充是否真的进了下一轮请求"的唯一手段。
单测证明不了这件事：它只证明"内存里的数组多了一条"。

### 0.2 被测二进制不需要手工重建

`scripts/cli-binary.mjs` 按**源码内容指纹**决定是否重建（门禁与 e2e 共用同一份判据）。
改完 Rust 源码直接跑 e2e 即可。

## 1. 批次总表

> **批次定义的 owner 是 [09 §5](./09-对话面插件拆分实施方案.md)**——每批的改动清单、契约形状、
> e2e 编排、出口判据都在那里。本节只给**执行视角的一行摘要**，不复制细节（否则两套批次号必然漂移）。

| 批 | 内容 | e2e | 依赖 |
|---|---|---|---|
| **S0** | 补充整合收口（轮边界抽干 + C-D2 / C-D2b） | `t19` | 无 |
| **S1** | 两个插件骨架 + 契约（恒 `Escalate` / 恒空文本） | `t20` | S0 |
| **S2** | 判决（规则短路 + 快速档 + `conversation_view` + 剔除） | `t21` | S1 |
| **S3** | 措辞（首响模板 + 答话生成） | `t22` | S2 |
| **S4** | 中途汇报（复用 15s tick） | `t23` | S3 |
| **S5** | 呈现分界（对话 / 工作两个面板） | `t24` | S4 |
| **S6** | 调优（两个插件各自独立模型 / 提示词） | — | S5 |

**S0 与 S1 是必须做对的两批**；S2 / S3 分别兑现"直接回答"与"说人话"，且**各自可独立卸载**；
S4 复用已有 tick，成本最低；S5 是呈现上的必要条件——不做，S2–S4 的收益在界面上看不出来。

**顺序不可颠倒**：S2 的判决需要 S0 的"合并成一条"才有正确输入
（否则判决会被逐条触发，正是要消除的行为）；S3 的措辞需要 S2 的判决结果。

## 3. 架构改动登记（每条必须论证"必需"）

> 判据：**论证不出"必需"的改动直接删掉**。本表随批次推进追加。

### 3.1 S0 登记

| # | 改动 | 必需的理由 | 不做的后果 |
|---|---|---|---|
| 1 | `SessionConfig` 增 `supplements_enabled` | J2 平凡值——回退开关，可被 e2e 直接验证 | 特性无法回退，出问题只能改代码 |
| 2 | `SessionConfig` 增 `supplements_max_per_drain` | 合并**必须**有上界：无界合并把刷屏变成一条巨型消息 | 一次刷屏 = 一次上下文爆炸 |
| 3 | 新增 `merge_supplements` 纯函数 | 合并规则必须有**单点定义**（散在调用点必然漂移） | 两处抽干点各写一遍拼接逻辑 |
| 4 | `drain_inbox_once` 消费粒度 1 → n | **这就是特性本身** | 需求不成立 |
| 5 | `run_chat_loop` 插入轮边界抽干 | **这就是"边处理边综合"** | 补充只能等本轮结束，即"一条一条处理" |
| 6 | `meta.supplement*` 标记 | `supplement_ids` 是**可追溯性**（合并后原始条目 id 只此一处）；`supplement_count` 让模型知道有几条 | 合并后无法回溯用户到底发了几条 |

### 3.2 S1 登记（对话面切分）

| # | 改动 | 必需的理由 | 不做的后果 |
|---|---|---|---|
| 7 | 新增 `triage` 插件 + `triage/decide` 路由 | `JudgeIntent` 是**独立能力**：卸载它 ⇒ 全部输入直接进工具循环，系统完整运行（[09 §2.4](./09-对话面插件拆分实施方案.md)） | 判决逻辑寄居 `session`，卸载粒度消失 |
| 8 | 新增 `reply` 插件 + `reply/compose` 路由 | `ReplyFirst` / `ReplyAppend` 是**独立能力**：卸载它 ⇒ 无对话面文本，worker 正文照旧 | 措辞与判决绑死，无法各自选模型 / 各自开关 |
| 9 | 契约落 `symbio_core/schemas/` 各自模块 | 契约跨插件边界（session 生产、插件消费）⇒ 依赖方 ≥ 2，**满足** ADR-023 准入 | 插件间直引类型 ⇒ E-007 / E-009 违规 |

### 3.3 明确不新增

| 不新增 | 为什么 |
|---|---|
| `MessageType` 新取值 | `meta` 是自由 JSON，已有先例 `meta.kind`——加字段是数据变化，改枚举是 schema 变化 |
| 第二份存储 / 新集合 | 抽干改的是**消费粒度**，不是存储 |
| `settle_ms` 静默窗口 | **假想的**——"整合过于零碎"尚未被观测到 |
| 轮边界开关 | 与 `supplements_enabled` 重复，无真实使用场景 |
| 在 `session` 内建判决 / 措辞模块 | 判决与措辞是**两个可独立卸载的能力**，合并后卸载任一个都要改另一个（[09 §2.4](./09-对话面插件拆分实施方案.md)） |
| 把判决与措辞合成一个 `chat` 插件 | 同上——两者卸载语义不同，合成即失去"一个能力一个插件" |
| C-D1 断言（判决调用点不得收集工具） | 两个插件都不注册 `Capability`，"无工具"是**结构保证**，不需要断言补偿 |

## 4. 全局不做什么

| 不做 | 理由 |
|---|---|
| 改 `Store` / 引入 append-only 事实源 | **不是"不需要"，而是它属另一个迁移步**——[04 §3 第 1 步](./04-工程落地.md)的地基。混进本场景会让一步同时改"事实源"与"消费粒度"两件事，无法独立回退（[08 §0 纪律 3](./08-分步实施计划.md)）。读法见 [README §0.1](./README.md) |
| 改 `MessageType` / `MessageStatus` 枚举 | 跨栈 schema，前端逐字段镜像——改它是架构变更，收益为零 |
| 为兼容旧数据写迁移 | 纪律 4：新字段 `#[serde(default)]`，新语义只对新数据成立 |
| 跳过 e2e 直接提交 | 单测证明不了"补充真的进了下一轮请求"（那要读回请求体） |
| 一步做完四批再提交 | 每步必须能独立回退；回退单位是"一个特性" |

> **本表全部是"本步不做"，不是"不需要做"**——差别见 [README §0.1.1](./README.md)。
> 尤其第一行：改 `Store` / 引入 append-only 事实源是 v2 的**地基**，只是它属**另一个迁移步**；
> 把它说成"本场景不需要"是把目标当成了别人的事，是本方案要消除的偏差。
