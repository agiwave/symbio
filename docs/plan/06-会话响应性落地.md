## 0. 结论

| 问题 | 答案 |
|---|---|
| plan 覆盖 chat/worker 分离场景了吗 | **覆盖**——15 个机制点里 11 个直接落在已有键上；4 处部分覆盖 |
| 4 处缺口的代价 | **全部 `新增机制键 = 0`**，全部是 L-grid / L-data（不改 F1–F6） |
| 落地要动什么（**架构面**） | **机制面 0 改动**（F1–F6 与机制表 10 键不动、不改 `MessageType` 枚举）；**切分面 +2 能力插件**（`triage` 判决 · `reply` 措辞，各自可卸载、互不相关）——施工形状见 [09](./09-对话面插件拆分实施方案.md) |
| 落地要动什么（**模块内部**） | 4 项数据 + 调用点调整（§4.1）。**这一层可以妥协**——它是实现细节，不进冻结面 |
| 覆盖多少场景 | **10 个**（§4.3） |

> 一句话：**架构面按 plan 落地——v2 是目标本身，不是"另一个系统的未来设计"；
> 只有模块内部实现允许妥协。** 这条标尺见 [README §0.1 / §0.1.2](./README.md)。

## 1. 覆盖矩阵

逐条对照 [../design/chat-worker-split.md](../design/chat-worker-split.md) 的机制点：

| # | chat/worker 分离的机制点 | plan 的落点 | 状态 |
|---|---|---|---|
| 1 | **能直接回答的直接回答** | `triage.verdict` / `triage.escaped` 事件格 + `JudgeIntent` 能力 + 快速档"直答/派活/反问/拒绝"四选一分类器（[01 §6/§10](./01-核心架构.md)） | ✅ 覆盖 |
| 2 | **用户补充被整体处理**（抽干 + 合并成一条） | 只有"停 / 继续 / 改道"三选一 + 排队（[04 §2](./04-工程落地.md)、[roadmap/S07](./roadmap/S07-插话与实时打断.md)） | ⚠️ **G-A** |
| 3 | **worker 中途也会说话**（进度汇报） | `chat.assistant.append` 是网格里的一格（[01 §6](./01-核心架构.md)） | ⚠️ **G-B** |
| 4 | 对话面无工具（结构保证） | 能力 7 封顶，只授 `JudgeIntent` / `ReplyFirst` / `ReplyAppend`；`triage` / `reply` **不注册任何 `Capability`** ⇒ 工具集里结构上不可能出现它们（[01 §4.1/§7](./01-核心架构.md)、[09 §4.1](./09-对话面插件拆分实施方案.md)） | ✅ 覆盖（更强：编译期） |
| 5 | chat 无副作用、判决与措辞分离 | Actor 无状态、无接口；`Translator` 不创造信息，只需 `reply.append`（[01 §4](./01-核心架构.md)） | ✅ 覆盖 |
| 6 | **异常一律升级**（fail-safe 多干一次活） | I3 到点必答；`chat.assistant.fallback` **是网格里的一格**，可审计、可统计（[01 §5/§6](./01-核心架构.md)、[S01 §2](./roadmap/S01-最小闭环.md)） | ✅ 覆盖（更强：留痕） |
| 7 | 契约跨插件 / 避免直接依赖 | 契约不在模块之间，在"模块与共享事件格式之间"，契约数 O(N)（[01 §13.5](./01-核心架构.md)） | ✅ 覆盖（更强：零耦合） |
| 8 | **两条线**（对话线 / 工作线） | `Snapshot`（Chat，≤1.5k tokens）vs `Display`（用户 UI）vs `TurnState` / `ReadySet`（[01 §3](./01-核心架构.md)） | ✅ 覆盖 |
| 9 | 分界规则是**单点纯函数** | 投影签名 `Fn(&[E], Timestamp, Budget) -> View<V>`，F2 冻结（[01 §3](./01-核心架构.md)、[03 §1](./03-演进与验证.md)） | ✅ 覆盖（更强：构造期强制） |
| 10 | 呈现上两个面板不混排 | `Display` 投影"滤掉系统事件"（[01 §3](./01-核心架构.md)），但**没说"哪一类不进对话面板"** | ⚠️ **G-D** |
| 11 | 转写写入者唯一 | I1 单通道 + `Store::append` 唯一写入口（[01 §5](./01-核心架构.md)） | ✅ 覆盖（更强） |
| 12 | chat 的记忆 / 人格来自既有通道 | 记忆是投影参数，不是独立通道（[01 §9.1](./01-核心架构.md)） | ✅ 覆盖 |
| 13 | 插件间零直接依赖 | L1 代码依赖 / L2 类型依赖**被杜绝**，CI C4 静态扫描（[01 §13.2](./01-核心架构.md)） | ✅ 覆盖（更强） |
| 14 | 复用既有定时 tick | 定时 = `system.triggered`；自主层 `budget_ms`（[01 §6](./01-核心架构.md)、[04 §3 第 21 步](./04-工程落地.md)） | ✅ 覆盖 |
| 15 | 不变量与失败处置 | I1 / I2 / I3 + CI 清单 29 条（[01 §5](./01-核心架构.md)、[04 §4](./04-工程落地.md)） | ✅ 覆盖（更强：可执行） |

**读法**：plan 在**结构层**比 chat/worker 分离文档更彻底（无工具从"结构保证"升级为"编译期不可能"、
两条线从"两个读法"升级为"两个投影签名"）；缺口集中在**行为参数**上——这正好是 J1 说的"该是数据的地方"。

## 2. 四处缺口

### G-A · 补充的"整体整合"（目标 2 的核心）

plan 的 S07 给的是**打断**语义（停 / 继续 / 改道 + 排队），而目标 2 要的是**合并**语义：
n 条补充在下一轮边界被抽干、拼成**一条**输入，作为**同一轮**的上下文折进当前工作。

| 项 | 内容 |
|---|---|
| J1 检验 | 不是新机制。每条补充本来就是一条 `user.message` 事件；**合并发生在投影里**，不产生新事件类型 |
| 落层 | **L-grid + L-data**：`projection.param`（合并窗口 `supplement:max_drain`）+ 一行 ActorSpec（Decider，判"何时抽干"） |
| 新增机制键 | **0** |
| 平凡值 | `supplements.enabled = false` → 退回"一条消息 = 一轮" |

> **为什么必须合并成一条而不是逐条追加**：**存储裁剪**（`prune_historical_tool_calls`，
> `symbio/src/plugins/session/chat_session/write.rs`）按 `role = User` 的消息数计算保留分水岭——
> 逐条追加会让 n 条补充吃掉 n 份保留预算，把更早的轮次提前挤出窗口。
> 合并成一条，n 条补充在计数上**仍是一轮**，与用户心智一致。
>
> ⚠️ **两处计数口径不同，不要混**：存储裁剪按 **User 消息**计数；
> 而请求视图窗口（`apply_layered_sliding_window`，`symbio/src/plugins/session/context/window.rs`）
> 按 **ToolCall** 计数，不受补充条数影响。

### G-B · 进度汇报的触发条件

`chat.assistant.append` 这一格**已经在网格里**（[01 §6](./01-核心架构.md)），缺的不是事件，是**谁在什么时候写它**。

| 项 | 内容 |
|---|---|
| J1 检验 | 触发判定是确定性规则（`now - last_user_facing_at ≥ interval` 且 `tool_rounds ≥ min_rounds` 且本轮次数 < 上限）→ `pattern = decider`，不占新机制 |
| 落层 | **L-data**：一行 ActorSpec（`decider`，读 `turnstate` 投影）+ `projection.param`（`progress:interval_ms` / `progress:max_per_turn` / `progress:min_rounds`） |
| 新增机制键 | **0** |
| 平凡值 | `progress.enabled = false` → 不汇报，行为与今天一致 |

> **"该汇报了"是状态派生的，不是模型自发的。** 这正是 plan 与 chat/worker 分离文档的一致处：
> 触发权归编排层（`Decider`），措辞权归 `Translator`。两件事分开，才不会有"该说话时没人说话"。

### G-C · triage 的反射档短路

plan 的反射档（80ms / `RuleOnly`）只被 S07 的抢占判定者占用。但**问候 / 致谢 / 确认 / 空输入**
这类输入不该付一次快速档（300ms）分类——它们是纯规则。

| 项 | 内容 |
|---|---|
| J1 检验 | 纯查表 → `pattern = decider` + `budget_ms = 80`，令牌 `RuleOnly` |
| 落层 | **L-data**：一行 ActorSpec + 一张规则表（规则表是数据） |
| 新增机制键 | **0** |
| 平凡值 | 规则表为空 → 全部落快速档（300ms），功能完整、只是慢 |

> **顺序也要钉住**：`Escalate` 的文本必须**先于** triage 的完整判定输出给用户。
> 否则"直接回答"省下的时间会被串行化吃掉——简单任务反而更慢。

### G-D · 呈现分界（哪一类不进对话面板）

plan 有 `Display` 投影且它"滤掉系统事件"，但没有规定**工具 / 推理节点不属于对话面板**。
不加这一条，chat 的加入只会让同一列更乱。

| 项 | 内容 |
|---|---|
| J1 检验 | 同一份 Log 的**第二个 Display 参数**，不是第二个投影类型 |
| 落层 | **L-grid**：`projection.param`（`display:surface = conversation \| work`） |
| 新增机制键 | **0** |
| 平凡值 | 单面板（今天的行为） |

> 四个缺口合起来：**0 新增机制键，0 值域扩展**。按 [03 §3 前置闸门](./03-演进与验证.md)，
> 它们连 ADR 都不需要——`scenario_ladder.rs` 式的审计可以直接把它们加进阶梯重跑。

## 3. 概念映射：plan ↔ 现仓

plan 是 v2 目标架构，现仓（Symbio）是插件分形架构。落地前必须把"概念"和"代码"对上：

| plan 的概念 | 现仓对应 | 差距 |
|---|---|---|
| `Store`（唯一原语，append-only，`seq` 单调） | `SessionStore`（`messages.json`）+ VDFS + `event_bus`（仅 `kind = "vdfs"`） | **最大差距**：无单一 append-only 事实源；`seq` 有（`ChatMessage.seq`，Lamport 计数），但存在 `replace_messages` 全表重写 |
| `Projection`（私有构造 + 编译期纯净） | `build_request_view`（`symbio/src/plugins/session/context/view.rs`）已是**纯函数**；前端派生按 ADR-015 也要求纯函数 | 纯度靠约定与测试，**无编译期强制**；无 `Budget` 参数；无第二个投影 |
| `ActorSpec`（5 字段数据行） | 插件 + `<根>/<插件>/PLUGIN.yml` 配置 | 无 `budget_ms`；无 `pattern` 概念（等价物是"调用点怎么写"） |
| 事件网格（10 实体 × 5 动词） | `MessageType`（6 值）+ `MessageStatus`（7 值）+ `meta: Option<Value>`（自由 JSON） | 网格未建立；但 `meta` 是自由 JSON，且**已有先例**（`meta.kind = "context_nudge"`） |
| 能力 7 封顶 + grants 读写成对 | `CapabilityVisitor::register`（注册即授权） | 无读侧授权；无 7 封顶 |
| **I1 单通道** | 转写唯一写入者（session）+ 收件箱唯一入口（ADR-020 / 026 / 031） | **已具备** |
| I2 无溯源不声明 | 无 `caused_by` | 缺 |
| I3 到点必答 | 无发言预算（模型请求的超时是传输层参数，不是发言预算） | 缺 |
| 时延四层 + 令牌闸门 | 无 | 缺 |

**这张表不是"边界"，而是施工清单**（读法见 [README §0.1](./README.md)）：

- **已具备**的那一列（I1 单通道、投影函数形状、`meta` 自由 JSON、收件箱唯一入口）**直接复用**；
- **缺**的那一列（I2 溯源 / I3 发言预算 / 时延四层 + 令牌闸门）是 v2 的 **F4 / F3 冻结契约**，
  属**必须补齐**的工作。把它们列为"可选增强"等于让本场景在 v2 之外落地——
  而那正是本方案要消除的偏差。

> **它们排在哪一步**：I2 / I3 / 时延分层属**事件骨架与预算**这一迁移步
> （[04 §3 第 1 / 6 步](./04-工程落地.md)），不属本场景批次。**"本步不做"与"不需要做"是两件事**——
> 见 [README §0.1.1](./README.md) 的判据表。

## 4. 落地形状：机制面 0 改动 + 切分面拆两个插件

### 4.1 模块内部改动清单（4 项，可妥协层）

**判据（只约束机制面）**：不新增机制键、不改 F1–F6、不改 `MessageType` 枚举、不改持久化格式。
**插件数不在此列**——拆插件在 plan 的记账下是 `L-data`（[09 §2.1](./09-对话面插件拆分实施方案.md)）。
下表 4 项是**模块内部实现**，即"可以妥协"的那一层（[README §0.1.2](./README.md)）；
插件的**切分**在 [09 §4](./09-对话面插件拆分实施方案.md)，它属架构面，不可妥协。

| # | 改动 | 位置 | 性质 |
|---|---|---|---|
| **1** | 新增投影函数 `conversation_view(messages, limit)` + 请求视图侧的剔除（`meta.exclude_from_context`） | `symbio/src/plugins/session/context/view.rs` 旁 | 纯函数，可双跑比对 |
| **2** | 判决 / 措辞的**调用点**：`chat_loop` 前步骤 + 轮边界各一处 | `symbio/src/plugins/session/chat_loop.rs` | 经容器 `route` 调插件（`triage/decide` · `reply/compose`，[09 §4.2](./09-对话面插件拆分实施方案.md)）；调用点在 session 内，插件本体在 `plugins/triage/` · `plugins/reply/` |
| **3** | 新增配置字段（**平铺**，见下） | `<根>/session/PLUGIN.yml` | 走既有 `capability_announce_configurable`，无第二配置协议 |
| **4** | 新增节点标记 `meta.surface`（`"reply"`）+ `meta.exclude_from_context`（`true`） | 判决 / 汇报节点 | `meta` 是自由 JSON → **数据变化**，不是 schema 变化 |

> **配置命名约定：平铺 + 前缀，不引入嵌套块。**
> `SessionConfig`（`symbio/src/plugins/session/config.rs`）是**平铺**结构，每个字段带
> `#[serde(default)]`。新字段沿用同一形态（`triage_*` / `reply_*` / `progress_*` / `supplements_*`），
> 而不是塞进嵌套的 `triage:` / `reply:` 块——**少一个结构体定义，且与既有 20 多个字段同形**。
> 平铺还有一个实际好处：`#[serde(default)]` 让**新增字段无需任何数据迁移**。
> 权威表见 [09 §7.1](./09-对话面插件拆分实施方案.md)。

**节点类型不新增**：判决文本、进度汇报、补充应答一律落成现有的
`role = assistant` + `msg_type = Text` 节点（`symbio/src/symbio_core/schemas/session/chat_message.rs`），
靠 `meta.surface` 区分来源。`MessageType` 保持 6 个取值不变。

**判决 / 措辞契约进 `symbio_core/schemas/`，不进公共域**：它们跨 `session` ↔ `triage`（`reply`）
边界，依赖方数量 ≥ 2，**满足** ADR-023 的 core 准入判据——但它们落在**各自的 schema 模块**里，
不摊进公共域（公共域每加一个类型，全体插件都要重新编译）。形状见 [09 §5 S1](./09-对话面插件拆分实施方案.md)。

### 4.2 对话面为什么拆成两个插件

> **结论**：对话面落成**两个独立插件**（`triage` 判决 · `reply` 措辞），各自可单独卸载，
> 彼此无边。完整形状、契约与批次见 [09](./09-对话面插件拆分实施方案.md)。
>
> 本节只留**判据**——它比结论更值得记住。

**判据：不要把「插件数量」当成「架构改动」的度量。**

| 量 | 定义在哪 | 加一个插件会变吗 |
|---|---|---|
| **机制面** | [03 §1](./03-演进与验证.md) 的 F1–F6：`Store` 签名 / 投影构造形状 / `ActorSpec` 5 字段 / 三条不变量 / 三个封闭集合 / 参数表键集 | **不变** |
| **机制键数** | [01 §8](./01-核心架构.md)：10 个顶层键，恒定 | **不变** |
| **插件数 / 地址数** | 施工视图（[05](./05-模块架构.md)）；插件名 = 挂载点（ADR-032） | **+1** |

在 plan 自己的记账里，**一个插件 = 一行 `ActorSpec` + 一个挂载点 = `L-data`**。
把插件数当架构改动，会得出一个看似精打细算、实则拿架构资产换短期便利的取舍：

| | 把对话面塞进 session | **独立插件（本方案）** |
|---|---|---|
| "无工具"的保证 | 调用点传空工具列表 + **CI 断言** | 插件不注册 `Capability` ⇒ **结构上不可能** |
| 判决 / 措辞的边界 | 靠"这个函数别写太多" | 插件边界 = 编译单元边界 |
| 独立开关 / 独立模型 | 靠配置块（`dialog_enabled`） | 插件目录 = 配置目录（各自 `PLUGIN.yml`） |
| 跨插件依赖 | 不涉及 | 经容器 `route` + 常量，E-007 / E-009 **已在守** |
| 长期维护成本 | 0（但 session 持续变胖） | 一个需要维护的地址 |

**多一个地址是不是成本？** 是——但地址是**身份**（ADR-032），而分形插件架构
（ADR-001 / ADR-002）的全部收益正来自"用地址切分职责"。省下它，
等于用一个架构资产换一点短期便利。**切分属架构面，不可妥协**（[README §0.1.2](./README.md)）。

> **不再往下切**：候选插件若与既有插件**卸载语义相同**，它不是新能力，而是既有插件的**数据**。
> 判据与两张表见 [09 §2.4](./09-对话面插件拆分实施方案.md)。本场景停在这两个。

### 4.3 场景覆盖账

机制面 0 新增键，十个场景：

| 场景 | 靠什么 | 已有 / 新增 |
|---|---|---|
| 问候 / 致谢 / 确认 直答 | 规则表（G-C 反射档） | 新增调用点 + 规则表 |
| 已知事实直答（记忆 / 项目状态） | `traverse` → `register_system_prompt`（既有通道）+ `conversation_view` | 已有通道 + 新增投影 |
| 需要干活（工具循环） | `chat_loop` 既有主循环 | **不变** |
| 中途补充整体整合 | 收件箱（ADR-026 / 031）+ 抽干合并（G-A） | 已有入口 + 新增抽干 |
| 中途进度汇报 | `session/heartbeat` 既有 15s tick + 汇报判定（G-B） | 已有 tick + 新增判定 |
| 打断 / 中止 | `session/chat/abort` + 收件箱排队（忙则不抢占） | **不变** |
| 断点恢复 | `session/resume.rs` 的 7 种 `ResumeAction` | **不变** |
| 长会话上下文治理 | 四层治理（工具结果守卫 / 语义压缩 / 主动压缩 / 请求视图） | **不变** |
| 子智能体委托 | `agent_run` → `session/chat/send`（跨插件调用先例） | **不变** |
| 多端接入（CLI / 前端 / telegram） | 唯一输入入口 `<根>/session/<sid>/inbox/<iid>` | **不变** |

**六个场景零改动，四个场景各加一项数据。**

## 5. 批次与验收

与 [04 §3 的 22 步排期](./04-工程落地.md)对齐——**不新开阶段，插在既有步之间**：

| 批次 | 内容 | 插入位置 | 验收判据 |
|---|---|---|---|
| **D0 · 先量** | 埋点：`入队 → 第一条面向用户文本落库` 的时延分布（p50 / p95），按"有无工具调用"分档 | 与第 6 步（兜底埋点 + 四层 `budget_ms`）同批 | 有一张数。没有它无法证明收益 |
| **D1 · triage** | 反射档规则短路（G-C）+ 快速档判决 + `meta.exclude_from_context` 剔除 | 第 6 步之后 | 关闭开关行为与今天逐字一致；简单问题不进工具循环 |
| **D2 · 补充整合** | 抽干整队 + 轮边界抽干 + 合并成一条（G-A） | 与第 9 步（`checkpoint` 投影）同批——两者都在改"轮次边界" | 连续三条补充只产生**一轮**整合处理 |
| **D3 · 进度汇报** | 复用 tick 的汇报判定 + 两项会话内状态（G-B） | 与第 21 步（定时触发 + 自主层）同批 | 长任务中途出现汇报节点；频率护栏生效 |

**D1 与 D2 是必须做对的两批**（对应目标 1 与目标 2）；D3 复用已有 tick，成本最低；
D4 是呈现上的必要条件——不做，D1–D3 的收益在界面上看不出来。

## 6. 平凡值与回退（J2）

每个参数必须有平凡值，且平凡值下系统**完整运行**：

| 参数 | **平凡值** | 平凡值下 |
|---|---|---|
| `triage_enabled` | **`false`** | 全部输入直接进工具循环，行为与今天逐字一致 |
| `rule_shortcut`（`triage` 插件自己的配置面） | **`false`** | 规则表不生效，全部落快速档（慢但正确） |
| `reply_enabled` | **`false`** | 无对话面文本；worker 正文照旧 |
| `progress_enabled` | **`false`** | 不汇报 |
| `supplements_enabled` | **`false`** | 一条消息 = 一轮 |
| `supplements_max_per_drain` | **`1`** | 退化为今天的 `pop_front` 一条 |
| `dialog_panel_split` | **`false`** | 单面板（今天的行为） |

**七个平凡值，任一个关闭都不影响其余功能**——这就是"分阶段不改架构"的技术前提。
完整表（含完整值列）见 [09 §7.1](./09-对话面插件拆分实施方案.md)。

> **还有一层更强的平凡值：卸载**。`triage` / `reply` 的平凡值是"**不挂载它**"——
> 卸载 `triage` ⇒ 全部输入直接进工具循环；卸载 `reply` ⇒ 无对话面文本、worker 正文照旧；
> 两个都卸载 ⇒ 今天的行为。**没有它们，系统仍完整运行**，走装配期 `NotFound` 而非运行期
> `enabled` 字段（[09 §7.2](./09-对话面插件拆分实施方案.md)）。
> 配置开关验证"分支写对了"，卸载验证"**插件边界真的存在**"——后者才是切分的判据。

> **平凡值不是"预留开关"**：每一条都能被 e2e 直接验证（关掉它，行为与今天逐字一致）。
> 反过来，任何**无法被平凡值验证**的配置项都应删掉——那是预留，不是参数。

## 7. 静默失效与强制（J3）

三条约束违反时**没有任何测试会失败**，因此必须做成断言：

| # | 约束 | 违反时 | 强制方式 |
|---|---|---|---|
| **C-D2** | 补充合并后仍算**一轮** | 窗口与裁剪分水岭悄悄漂移 | e2e [`t19`](../../e2e/cases/t19-supplements-merge.mjs)：三条补充在存储里必须仍是**两条**用户消息（首条 + 合并成的一条），且 `meta.supplement_count == n` |
| **C-D2b** | 抽干点夹在 `gate_turn` 与 `prepare_turn_inputs` **之间** | 前移 ⇒ 闸门 `Exit` / `WaitForTools` 时队列已被消费却没人用，补充**静默消失**；后移 ⇒ 合并消息进不了本轮请求。**两种都不产生错误信号** | `grep-audit` 的 **S-011**：三个锚点行号必须严格递增；**锚点缺失即 ERROR**——守卫不得悄悄退化成空转 |
| **C-D3** | `meta.exclude_from_context` 的节点不进请求包 | 界面文本污染模型上下文；`Escalate` 紧跟用户消息会让线上出现连续两条 `assistant`（部分协议直接 400） | `flatten_chat_messages` 剔除 + 单测断言 |
| **C-D4** | 对话投影不含 `ToolCall` / `role = tool` / `Turn` 容器 | 工具结果（可能含大块文件内容）被当"对话"喂给对话面：既贵又错 | 纯函数单测 + 双跑逐字节比对 |

> **C-D2 与 C-D2b 的强制形式为什么不同**：J3 只对**违反时不产生错误信号**的约束要求
> 编译期强制或 CI 断言。C-D2 违反时 e2e 会红（有信号）⇒ 它是**测试**，不是静态断言；
> C-D2b 违反时任何测试都不会红 ⇒ 它**必须**外置为静态断言。把两者都做成断言，
> 是把"有信号的"和"没信号的"混为一谈——而混淆的代价是**断言里塞进重复的测试**。
>
> **C-D1 不存在**：对话面拆成独立插件后，"判决 / 措辞不碰工具"是**结构保证**
> （`triage` / `reply` 不注册 `Capability`），**结构保证不需要断言补偿**（[09 §2.2](./09-对话面插件拆分实施方案.md)）。
>
> C-D4 的落点必须是**投影函数本身**，不能是提示词——进了包的东西，提示词管不住。

## 8. 边界（不做什么）

| 不做 | 一行理由 |
|---|---|
| 把判决与措辞合并成**一个** `chat` 插件 | 判决（`JudgeIntent`）与措辞（`ReplyFirst` / `ReplyAppend`）是**两个可独立卸载的能力**——合并后卸载任一个都要改另一个，违反"一个能力一个插件"（[09 §2.4](./09-对话面插件拆分实施方案.md)） |
| 把判决 / 措辞契约摊进 `symbio_core` 公共域 | 它们跨插件边界，**满足** ADR-023 的准入（依赖方 ≥ 2），因此落 `symbio_core/schemas/` 的各自模块；但公共域每加一个类型，全体插件都要重编译（[09 §5 S1](./09-对话面插件拆分实施方案.md)） |
| 新增 `MessageType` 取值 | `meta` 是自由 JSON 且已有先例（`meta.kind`）——加字段是数据变化，改枚举是 schema 变化 |
| 建第二份会话存储 | `Snapshot` 与 `Display` 是**同一份 Log 的两个投影**；分存储会把一条助手消息劈成两半，请求包必须再 join 回来 |
| 引入全量 `caused_by` 溯源 | I2 是 v2 的**冻结契约，必须补**——它属"事件骨架"这一迁移步（[04 §3 第 1 步](./04-工程落地.md)），不在本场景批次内。本场景在判决 / 汇报节点上带的 `meta.origin` 与 `caused_by` **同址**（都在 `meta`），因此补 I2 时不需要重写这些节点 |
| 把 triage 判决做成 LLM 自由文本 | 判决必须是**枚举**（`Answered` / `Escalate`），否则编排层无法执行"必然启动 / 必然收尾" |
| 用提示词约束对话面"别看工具结果" | 约束必须在投影层——进了包的东西提示词管不住（C-D4） |
| 为省事跳过 D0 埋点 | 没有基线数，"响应性变好了"就只是一句话 |
