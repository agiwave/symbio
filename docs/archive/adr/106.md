# D-106：模型消费端口归一

## 决策

1. **生产代码取模型能力只有一条链**：`LlmAdapter` + `TokenIssuer`。
   `classify/decide.rs` 与 `compose/wording.rs` 改经
   `ProviderLlmAdapter::for_turn` + `generate_turn(&FullModel, …)`；内部请求的形态
   一项不少——工具集 `&[]`、出口 `SilentDeltas`、system prompt 就地构造、中止走
   调用方给的共享信号。变的是**路径**，不是语义。
2. **唯一登记例外是压缩摘要**：`session/context/pipeline.rs::run_compression_llm`
   仍直调 `execute_turn`（IM-001）。它不是漏网：压缩要在帧面上把摘要增量改道到
   压缩节点（`compression_delta_gate`），端口今天没有对应的 sink 语义。它的形状
   仍按「内部请求」登记，直调点由 `internal-model-audit` 的 IM-004 核。
3. **协议解析 fail-closed**：`resolve_protocol_id` 返回 `Option<&'static str>`，
   未识别值**不兜底** `openai_chat`。保存前校验直接报错；能力收集期该条目不进目录；
   若未知者恰是**生效 provider**，写进 `CAPABILITY_ERRORS`，由编排方在启动链上中止
   并展示原因——而不是只说「没有可用的 Model Provider」。
4. **`ProviderLlmAdapter` 留 `symbio_core`**：依赖方是三个插件模块
   （`loop/turn_exec` / `classify` / `compose`）加 core 自身的端口彩排，且实现只依赖
   core 契约。按 [D-023](023.md) 的依赖方数量判据，留 core 成立；迁到任一消费方
   会让另外两个跨插件深引，迁到 `providers/` 会牵进 model 插件的私有件。它不是
   新接缝——`LlmAdapter` 才是接缝，本文件只是把 `ModelProvider` 折进接缝的纯胶水。
   对照表写在 `symbio_core/adapters/provider_adapter.rs` 文件头。
5. **cost_ms 只有一个计时口径**：adapter 边界的 `LlmTurn::cost_ms`。落格事件
   （final / fallback）照 [D-044](044.md) 进 `cost_ledger`；内部请求不写事件
   （[D-020](020.md)），因此只进日志——不为它们造第二套计时或旁路台账。

## 为什么

**双消费链的代价不是「多写几行」，是闸门有了死角。** 档位闸门挂在
`LlmAdapter::generate` 上，而 `ModelProvider::execute_turn` 对所有插件开放；
classify / compose 直调它就绕开了闸门。DE-002 当时把这类调用归为「内部请求」并
逐处登记，是**看见了**而不是**消除了**分叉。T-197 要消的是分叉本身。

**DE-002 否决「全部改走端口」的前提已经消失。** 那条否决有一条明写的理由：
对 compose 与压缩是空转、对 classify 要 core 变宽（补 `ClassifyOnly` 入口）。
[D-096](096.md) 已把 `ClassifyOnly` 退役——classify 不再需要那个入口；
compose 的空转判断也换了判据：本批要的不是「闸门多管一件事」，而是**成本实测与
能力取用只有一条链**。压缩不在本批，因为它的帧改写出口还没有端口形态（见决策 2）。

**协议兜底的方向与仓里同类判断相反。** `CapabilityRiskLevel::from_name` 的方向是
「宁可报错，不静默放宽」；协议解析把写错的 `api_protocol` 静默当 `openai_chat`，
等于把「配置错了」伪装成「配置能用」——错误从保存期推迟到运行期，症状还指不到
协议解析这一层。存量配置里的合法别名已被覆盖，反转只影响写错的值。

**位置复审的结论是「留」，但理由必须写下来。** `ProviderLlmAdapter` 消费方从
「会话 + 测试」变成「会话 + classify + compose + 测试」，正好跨过 D-023 的
多消费方判据；而它依赖的仍然全是 core 契约。留 core 不是「它够底层」，是
**依赖方数量与依赖方向都指向这里**。

## 否决的替代方案

- **保留两条链，只把 classify / compose 登记得更清楚**：登记解决「有没有人看见」，
  不解决「同一种能力有两个答案」。cost_ms 仍是一处有实测、一处没有。
- **在 classify / compose 各包一层本地适配器**：两个插件各写一份与
  `ProviderLlmAdapter` 同形的胶水，`PromptMessage → ChatNode` 的映射也会出现第三份。
  重复是可见的债，但这条债的利息是**下一次协议变化要改三处**。
- **`resolve_protocol_id` 保留兜底、只加 warning**：warning 不阻断任何东西，配置
  照样落盘、请求照样发错协议。要「进可观测面」就得有一个会让流程停下来的面
  （保存校验 / 能力错误桶），日志不是那个面。
- **本批把压缩摘要也迁到端口**：需要先在 `DeltaSink` 上表达「摘要增量改道到压缩
  节点、骨架帧吞掉」。那是新的端口语义，不是本批的机械收敛；硬塞会把压缩的帧面
  判据挤进 adapter，违反「一个事实一个 owner」。
- **把 `ProviderLlmAdapter` 迁到 `providers/` 或 `plugins/loop`**：前者牵进 model
  插件私有件，后者让 classify / compose 跨插件深引（E-007 / E-009）。

## 后果

- `internal-model-audit` 的存量从四处降到两处：闸门本体 + 压缩摘要。IM-004 的
  形状判据不变。
- classify / compose 现在必须拿到 `FullModel` 令牌（`TokenIssuer::issue_deep()`），
  `ClassifyOnly` 仍然不存在（D-096）。
- compose 的 `reasoning_id` 改由 compose 自己铸：静默请求没有流式节点 id 可带，
  端口只回文本；该 id 是「这次思考事实」的身份，供 `session` 复刻 Reason 节点。
- 未识别的 `api_protocol` 在保存时即报错；存量合法配置（含历史别名）不受影响。
- 依赖方对照表住 `provider_adapter.rs` 文件头，位置复审的理由与代码一起 review。

## 失效边界

- 压缩摘要拿到能表达「帧改道」的端口形态后，决策 2 的例外应关闭——那时
  `execute_turn` 的直调点只剩闸门本体。
- `ProviderLlmAdapter` 若开始依赖任何插件私有类型，D-023 的结论立即翻转：
  它必须迁到能看见那些类型的模块，而不是让 core 认识插件。
- 若 `resolve_protocol_id` 出现「需要默认值」的新消费方，那是一次新裁决，
  不能在调用点就地补 `unwrap_or(openai_chat)`。
