## 决策

**背景**：能力扩充阶梯（[T-120](../009-task/120-路线图总览.md "T-120-路线图总览")）的 S08
（[T-128](../009-task/128-多主体与对等承诺.md "T-128-多主体与对等承诺")）承诺「多主体 + 可追责的契约」，
落地排期在 [T-072](../009-task/072-对等主体生产增量.md "T-072-对等主体生产增量")。T-072 的 exit 把工作切成
三个「**可独立回退**的批」：① 对等主体窄 grants 行、② `commitment.asserted` 生产写方、
③ 不依附会话的 ActorSpec 构造路径。

`authz::ROWS` 第四行（`agent:peer-b`，只持 `produce.artifact`）落地后核实其余两批，
结论是 **exit 的批次结构本身不成立**，且 T-128 §3.1 / T-133 §3.1 有一条**写反了的断言**：

1. **`commitment.asserted` 不是「无生产写方」。** 它在生产里有写方：
   `symbio_core::actors::commitment::commitment_events` 的 `ok = false` 支
   （「违约才宣告」——S08 §5「违约可被观测是 T5 的全部前提」），调用链
   `plugins/session/tools/tool_executor.rs::note_delegation`（只认 `agent_run`）
   → 轮末 `v2_facts::record_derived` → `commitment_events`。
   **缺的不是写方，是「对等 offer/assert」这一支**：今天所有 `commitment.*` 都由**委派族**产生，
   且 `to` 在调用点被写死成 `PRINCIPAL_USER`（`v2_facts.rs`）——生产里不存在一条
   「本主体向**另一个主体**立约」的写路径。T-128 §3.1 与 T-133 §3.1 的
   「`commitment.asserted` 无生产写方——今天只在测试侧出现」据此订正。
2. **② 与 ③ 是同一批，不是两个可独立回退的批。** 对等主体的 `asserted` 写方按 T-072 自己的规定
   必须住在**轮末收束族**（`v2_facts`，不开第二条写通道——I1）。而收束族**只在该轮收束成功时执行**：
   `v2_exec::execute_turn` 在 `outcome.closure_denied` 时提前返回，承诺 / 任务表 / 熔断 / 记忆**一律不写**。
   于是「对等主体能不能跑一轮」是「它能不能写 `asserted`」的**前置**——② 依赖 ③。
3. **这条依赖不是理论上的，是一条今天就可复现的生产路径。** T-072 自己给对等侧定的起步形态是
   「第二个会话选定第二个 agent」（T-072「不是本任务范围」一节）。而
   `chat_loop::request_principal` = `principal_of(ctx[AGENT_ID])` ⇒ `--agent peer-b` 的会话主体是
   `agent:peer-b`；`authz::matrix_for` 对**登记过**的主体返回**表里那一行**（正是批① 判据
   `authz.test.rs::the_peer_row_is_narrower_than_the_derived_set` 所钉的行为）⇒ 只持 `produce.artifact`
   ⇒ `turn_runner::closure_granted`（`= matrix_for(p).can_reply(p, true)`）**恒判拒** ⇒ 该会话
   **每一轮都收束不了**（无 `chat.assistant.final` 格 ⇒ `check_all` 报 C4 未收束），且没有任何产物格。
   批① 之前这条只是 T-128 §3.1 预告的「张力」；批① 之后它是**一条已接通、会静默失败的路**。

**决策**：

1. **收束格按种类判，`closure_granted` 不恒问 `reply.*`。** 收束格有两类，各自的授权谓词是它自己那一类：

   | 收束格 | 事件 | 授权谓词 |
   |---|---|---|
   | **发言收束** | `chat.assistant.final` / `.append` / `.fallback` | `can_reply(principal, first)`——**今天的行为，一字不变** |
   | **产物收束** | `artifact.added` | `can_produce_artifact(principal)` |

   对等主体（只持 `produce.artifact`）因此**能跑一轮并收束为一件产物**，其轮末派生事实
   （`commitment.*`）照常入格。`closure_granted` 的签名由 `(principal)` 收为
   `(principal, kind)`，`kind` 是**两值枚举**（封顶 2，不出现第三类）。
2. **本条只定形状，不落地。** 今天六个调用点（`turn_runner.rs` 的深度档三处 / 反射档 /
   兜底格 / 中止格）写的**全是发言收束**——若此刻就加 `kind` 参数与产物收束分支，得到的是
   **一个没有生产方的机制**（[D-064](064.md) 理由 2 明令禁止的形态：没有写方的格子不先进词汇表）。
   落地条件 = **产物收束的写方与对等主体的 ActorSpec 构造路径同批出现**；在此之前
   `closure_granted` 与 `turn_runner` 的六个调用点**一字不动**。
3. **`asserted` 的对等写方由此定形**（写进 T-072）：由**对等主体自己的轮末收束**写（`v2_facts`），
   `from` = 该对等主体，`to` = **它的委托方主体**，即 DE-001 §12.2 的
   「跨体承诺 → `commitment.asserted` + 对方 Log 引用」。
   **`to` 必须是数据**：今天它是在调用点写死的常量（`PRINCIPAL_USER`），而对等侧要的
   「对方主体」在现有入站路径上**没有来源**——`gateway` 的入站请求不带主体
   （`plugins/gateway/` 全目录零 `principal`），会话 `user.message` 的 `actor` 是**会话自己**。
   故该批的第一件事是**给入站请求补上「来源主体」这一格数据**，而不是在调用点换个常量。
4. **否决「把子智能体当对等主体」。** T-128 §2 的分界是「递归是树、协作是图」：
   子智能体是 `agent_run` 的**派生物**（树），对等体是 `scope: root` 的**独立主体**（图——§3 的
   ActorSpec 行明写 `scope: root`）。让子会话（`metadata.parent_session_id` 非空）去写对等 `asserted`，
   等于**用树冒充图**，并把「图侧已落地」报成事实。
5. **批次结构订正**：T-072 的 exit 改为——① 已落地（保持）；**② + ③ 合并为「对等主体跑一轮」批**，
   同批落地同批复退，前置 = 本条 1 的收束分种类 + 对等 ActorSpec 构造 + 入站「来源主体」这一格数据；
   判据 = 一条 e2e（两会话两主体，对等主体跑一轮 ⇒ 它的 `commitment.*` 入格、请求包不串主体，
   `t30` 纪律复用）。
6. **T-128 §3.1 / T-133 §3.1 的表行按本条 1 与 4 订正。**

**理由**：

1. **「写方在、但写错了方向」比「写方不存在」更容易被误读成两种错。** 一条「无生产写方」的断言会让
   下一轮去做已经做过的事（再写一个 `declare` 出口）；反过来，一旦有人发现「其实有写方」，图侧就被
   顺手报成完成。两种误读都源于同一条没写清楚的话——所以订正的是**断言本身**，不是它的措辞。
2. **闸的判据必须是它要判的那件事。** `can_reply` 回答的是「能不能发言」，而被它拦下的是**整轮的
   派生事实**（承诺 / 任务 / 熔断 / 记忆）。用发言权去否决一个主体的全部记账，是把「不能发言」
   偷换成「不能记账」——这正是批① 把 `agent:peer-b` 登记成只持 `produce.artifact` 之后暴露出来的东西。
3. **「先加参数再找写方」在本仓已有判例。** [D-064](064.md) 拒绝为 `readyset` 先加 `cap`
   （没有调用方）、拒绝先把 `task.ready` / `task.assigned` 放进词汇表（没有写方）；同一条纪律要求
   本条决策 2 的「只定形状不落地」。
4. **对等侧的真实增量是一格数据**（入站请求的来源主体），不是一条新通道。这与 T-128 §2
   「通信 = 没有直连」同向：主体之间的承诺靠**同一份事实源里的一格**被对方读到，而「谁向我提的」
   本身就得先是数据——先有它，才有「向谁宣告」。
5. **批① 的方向是对的，不需要回退。** 「闸不能晚于发起者」（PL-009）要求窄行与对等主体同批；
   批① 提前把行立好，方向正确。本条要做的是把它**暴露出来的静默面**登记成合并批的入口，
   而不是把行撤掉。

**被否决的方案**：

- **让 `agent:peer-b` 也持 `reply.*`**：否决。那等于把批① 的判据作废（「对等行窄于派生整套」的全部意义
  是**不许**它拿 `reply.*`），并把「对等 = 一个会发言的会话」写成定义——与 §3 的 ActorSpec 行
  （`pattern: translator` / `capabilities: [ProduceArtifact]`）直接冲突。
- **让 `closure_granted` 对「不持 `reply.*`」的主体一律放行**：否决。那是把闸从「按能力判」降级成
  「按有没有能力判」——语义从「谁可以写这一类格」变成「谁不被排除」，fail-closed 的**结构**
  变成 fail-open 的开关。
- **批② 独立先落（只写 `asserted`，不管收束闸）**：否决。对等主体跑一轮必然 `closure_denied`
  ⇒ 写方**永远执行不到**；那样交付的是一个「有代码、有单测、生产里零次调用」的写方，比不写更坏。
- **用子会话（`agent_run` 的派生物）当对等主体**：否决，见决策 4。
- **把 `to` 在调用点从 `PRINCIPAL_USER` 换成另一个常量**：否决。那是把「对方是谁」从一格数据降级成
  一次猜测；对等协作的判据恰是**双方不从属**，而「谁是我的协作方」只能来自这次请求本身。
- **把 ② / ③ 的合并读成「③ 先做、② 后做」**：否决。合并的意思是**同批落地同批复退**，
  不是重新排序——分开排期会让「产物收束」这一个改动在没有对等主体时先落地（决策 2 禁的形态）。

**后果与不变量**：

- **本次不动任何生产代码**：不改 `closure_granted`、不改 `turn_runner` 的六个调用点、
  不改 `v2_facts` 的 `to`、不改 `authz::ROWS`。
- **批① 的落地不回退**：`agent:peer-b` 窄行保留（方向正确，见理由 5）；本条把它暴露出来的静默面
  登记为 T-072 合并批的入口。
- **`core-shape-audit` / `core-export-audit` 全程零违规**：本条不增删 `symbio_core` 的导出与形状
  ——收束分种类是**插件层**（`turn_runner`）的改动，`symbio_core` 一行不动。
- **不变量**：`closure_granted` 的调用点数量与「收束格种类数」必须相等。今天 6 个调用点全写
  **发言收束**；落地合并批时若出现产物收束的调用点，它必须走**同一张表**的第二行，
  而不是在调用点各写各的谓词——否则「谁可以写这一类格」会分叉成六份互相不知道的判决。
- **`impl: done` 的依据**：断言与批次结构已订正（T-128 §3.1 / T-133 §3.1 /
  [T-072](../009-task/072-对等主体生产增量.md "T-072-对等主体生产增量") 三处）；决策 1 的机制本身
  （`closure_granted` 的 `kind` 与产物收束）随 T-072 合并批落地——与「对等 ActorSpec 真值」
  「入站来源主体」两格数据同批，三处下游口径（C4 / `closure_denied` / 恢复锚）的裁决见
  **[D-067](067.md)**。
