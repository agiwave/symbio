## 决策

**背景（为什么必须补这一条）**：T-056 要把消息真源从 `messages.json` 换到 `v2-events.wal`。
换源的第一步判据（删掉缓存后会话仍能开且历史完整）已经绿了，但**主读路径整体切到重建
之前**有一个硬阻塞：**只有「追加」进了 WAL，其余对消息列表的变更全都没进**。

| 变更 | 进 WAL？ | 今天怎么表达 |
|---|---|---|
| 追加（轮次事实 / 工具结果） | ✅ | `v2_exec` 落格 |
| 编辑一条消息（`patch_message`） | ❌ | 只 `replace_messages` 重写 `messages.json` |
| 截断 / 清空（`truncate_messages`） | ❌ | 同上 |
| 压缩（L2 前缀重写，`replace_messages`） | ❌ | 同上 |

后果是可复现的：此刻若把主读路径整切到「从 WAL 重建」，**被截断的消息会复活**
（WAL 里从没记过「它没了」），编辑过的内容会回退成编辑前。这不是性能问题，是**正确性**
问题——所以它必须先解决，且它与 [[D-049|D-049]]
理由 1（一个事实只能有一个 owner）是同一条：变更的 owner 现在还是 `messages.json`。

**决策**：

1. **消息的变更也是「发生过什么」，因此入格**。编辑、截断、清空都是事实，不因为它们
   改的是「已有节点的形状」而变成呈现态——呈现态指的是 `delta` / 在途 `seq` / 等待态
   这类**一次渲染的快照**（D-049 理由 4），「用户删了这几条」不是快照，是发生过的事。
2. **新增实体 `Message`**（[DE-001 §6](../004-plan/001-核心架构.md "DE-001-核心架构") 网格加一行），两个格子：
   - `message.edited` 落在 `message × asserted`——「这条消息现在读作 Y」是一次断言；
   - `message.removed` 落在 `message × closed`——与 `memory × closed`（`memory.forgotten`）
     同形：「这条消息没了」。
   - 与 §6 已预留的 `user.message.edited`（`turn × opened`）的关系：那一格是「用户改
     刚发的那句话」这一**窄义**，而 CRUD 是**列表级、跨轮**的变更（截断一段可能横跨
     多轮）。归 `turn` 会把 `turn × opened`（= 一轮开始）的语义搞浑——一个截断不
     「开始一轮」。故按 §6 的准入三问（能归入已有实体？）的**否定**一侧，加 `message`
     实体；名字与预留的 `user.message.edited` 对齐为 `message.edited`。
3. **载荷**：
   - `message.edited`：`{ message: <ChatNode 的 JSON> }`——补丁**应用后**的整条消息。
     重建按 id 替换节点（与 `patch_message` 的「整条替换」语义一致）。
   - `message.removed`：`{ ids: [...] }`——**一次操作一条事实**，区间用 id 列表表达。
     逐条发事件会让一次截断写出几十条事实，而它们本是同一个动作。
4. **重建与转写投影都按事件顺序回放**：`edited` ⇒ 按 id 替换；`removed` ⇒ 按 id 丢弃。
   fold 因此从「纯追加」变成「追加 + 变更」，但**仍是纯函数**（同一事件序列 ⇒ 逐字
   同输出），这是重建的硬要求不变。
5. **`prompt_fidelity` 增第三类：变更类事件**。它既不产 prompt entry、也不是「按设计
   不进请求包」（那是界面文本）。缺这一类，判据会把变更事件当「不在投影范围内」静默
   跳过——而该模块自己已经警告过「判据的覆盖范围要与投影的实现范围同时长」（`turn.supplemented`
   漏登记那次）。
6. **压缩不逐条表达，走快照**。L2 压缩把一段历史改写成摘要，是**整体替换**，逐条
   `removed` + 逐条新增既啰嗦又表达不出「摘要取代了这一段」。压缩与 WAL 无界增长用
   **同一个机制**解决：写一条 `session.consolidated` **快照事件**（载荷 = 压缩后的消息
   列表），其后旧段归档。重建 = **最近快照 + 其后事实**。
   - 快照是**压缩点**，不是每轮都写——「整份覆盖写不可扩展」批评的是**每轮**重写
     `messages.json`（D-049 理由 2），不是周期性压缩点。快照事件本身仍是 append-only
     WAL 里的一条。
   - 段归档（`EventWalStore` 的分段 + 归档）是快照腿的实现面，与快照事件同批交付。

**理由**：

1. **一个事实只能有一个 owner。** 变更的 owner 必须从 `messages.json` 移到 WAL，否则
   换源永远换不干净——留下的那个 owner 正是「同一句话有两个地方能改」。
2. **事实是「发生过什么」，编辑与删除确实发生过。** 只留结果（快照）会丢掉「谁在
   什么时候删了这一段」——而审计与元认知要的正是这个。这与 [[D-052|D-052]]
   同一条：**完成态不是事实的前提**，同理「改过」也不是「没发生过」。
3. **区间操作一条事实。** 截断的语义是「从 X 起全没了」；逐条发事件会把**一个动作**
   拆成 n 条事实，n 随消息量增长，而事实网格的价值在于「一件事一个键」。
4. **快照腿解决的是另一个问题**（无界增长），不该与 CRUD 混为一谈。CRUD 是「变更
   怎么表达」，快照是「历史怎么不无限长」——两件事各有各的判据。

**被否决的方案**：

- **CRUD 也一律走快照**（任何非追加变更都写一份整列表快照）：否决。它把「编辑过」
  这件事本身丢了（只留结果），且每次变更写整份列表——对一次单条编辑是数量级的浪费。
  快照留给「压缩」这类**本来就是整体替换**的变更。
- **保留 `messages.json` 作 CRUD 的权威、WAL 只记追加**：否决。那正是 D-049 理由 1
  要消的形态（一个事实两个 owner），且主读路径永远切不过去。
- **复用 `turn` 实体（`turn × asserted` = `message.edited`）**：否决。见决策 2——截断
  跨轮，归 `turn` 会让「一轮开始」与「一段历史被删」同格。
- **逐条发 `message.removed`**：否决。见理由 3。

**迁移与回退的数据语义**（[13 §0 纪律 4](../../archive/13-质量改进总纲.md) 要求的一节；
本表接 [[D-049|D-049]] 的同名表）：

| 阶段 | 迁什么 | 回退会丢什么 |
|---|---|---|
| S2.7-b1（CRUD 入格） | `patch_message` / `truncate_messages` / clear 除重写缓存外**另落一条事实**（双写） | **零**：缓存仍在、仍是读侧真源，新落的事实无人消费；回退 = 去掉那几处 `append` |
| S2.7-b2（压缩腿） | 快照事件 + 段归档；重建改「最近快照 + 其后事实」 | **零**（归档段可保留一个版本周期；快照只是多一条事件） |
| S2.7-b3（主读切换） | 主读路径整体切重建、写侧停存正文、退役 S1 对账与 S2 旧读法 | **不再无损**（同 D-049）：回退后消息靠 WAL 重建，呈现细节可能不同（`seq` 分配、同轮兄弟次序） |

**后果与不变量**：

- WAL 仍 append-only（快照是**多一条事件**，不是改写历史）；同轮单一写方不变。
- 网格加一个实体（`message`）、三个名字（`message.edited` / `message.removed` /
  `session.consolidated`）——按 [DE-001 §6](../004-plan/001-核心架构.md "DE-001-核心架构") 的
  「新增事件 = 在网格里加一格」，是**数据变化不是机制变化**（J1 通过）。
- **本条的决策先于实现**：b1 / b2 / b3 各自单独立批、独立可回退；每批的出口判据在
  [13 §轨 S](../../archive/13-质量改进总纲.md) 表内。
- 与 D-049 的边界：D-049 定「目标态与迁移顺序」；本条定**迁移顺序里被漏掉的那一段**
  ——「非追加变更怎么进事实源」。没有本条，D-049 的目标态到不了（切过去就丢历史）。

**落地状态**：本条只定**格子与迁移顺序**（决策先于实现），三批的落地判据
均已有闭环承载者，故 `impl` 由 `partial` 升 `done`：

| 批次 | 落地锚 | 判据承载任务 |
|---|---|---|
| S2.7-b1（CRUD 入格） | `e62d8a85`（编辑 / 删除升为事实，重建与投影按 id 折叠，双写不切流） | [T-056](../009-task/056.md) |
| S2.7-b2（压缩腿 + 段归档） | `fd844424`（压缩升为事实，快照即取代，零回退损失） | [T-056](../009-task/056.md) |
| S2.7-b3（主读切换 + 写侧收口） | `941cf88d`（存储层变换入格 + 写者令牌寄存）、`e4743c11`（主读收敛单源、退役对账与旧读法） | [T-053](../009-task/053.md) / [T-054](../009-task/054.md) / [T-055](../009-task/055.md) / [T-056](../009-task/056.md) |

三个事件名 `message.added` / `message.edited` / `message.removed` 与 `session.consolidated`
已在 `symbio_core::event` 落常量、并在 [DE-001](../004-plan/001-核心架构.md "DE-001-核心架构") §6 网格里成行（`message` 行，
闭集四格）。决策 5 的第三类（变更类事件进 `prompt_fidelity`）与决策 6 的快照腿同批落地——
无实现残余，**没有留给后人的隐含缺口**。

**b3 的「失败升级为错误」已补齐（[T-164](../009-task/164-v2_messages落格失败升级裁决.md "T-164-v2_messages落格失败升级裁决")）。**

b3 行把「主读切换」与「写侧收口」写成一批，而写侧收口里有一条**行为**改动没落：
事实落不进去时该怎么处置。实现沿用了 b1/b2 的口径（只记日志、不冒泡），理由写在
`v2_messages` 的模块头——「附加事实失败不该把成功的动作说成失败」。那句话在 b1/b2
成立（缓存是读侧真源、事实是影子），**b3 切源之后前提没了**：事实是本体，放过它
等于「回执说改好了、重建后一看没改」，而且用户无感。

补齐后的口径是**五个结果、四种处置**（处置由调用方定）：

| 结果 | 触发 | 处置 |
|---|---|---|
| `Landed` / `Nothing` | 落了 / 本来就没有事实可落 | —— |
| `Parked` | 拿不到写者令牌 | 寄存，由持令牌方补落（[T-055](../009-task/055.md)） |
| `NoAnchor` | 切片里没有可用溯源锚（v1 遗留会话） | **豁免**：这类会话的读侧本就回落 `messages.json`（[[D-049|D-049]]） |
| `Failed` | 事实源打不开 / 追加被拒 | `apply` 在**写缓存之前**返回可见错误（编辑回执报失败） |

**与 [[D-044|D-044]] 的边界**：那边「落格失败只记警告不冒泡」管的是**轮末收束格**
（`chat.assistant.final` 等）——那些写发生在用户已经看见输出之后，写失败不该把一轮
对话判死。本条管的是**用户对列表的动作**（编辑 / 截断）：事实写不进去就是动作没发生，
报失败是如实。两条不冲突，因为前者是「事实是产出的尾巴」，后者是「事实就是产出」。

一处例外写清楚：写入期裁剪（`prune_tool_history`）的 `message.removed` 发生在写缓存
**之后**（裁剪决策在 `append_messages` 的临界区内产生），失败不能报错——报错会让调用方
重试，而重试等于把同一条用户消息再追加一遍。故保留「出声 + 有界」：被裁节点在下次
重建后复活（列表变长，不是数据丢失），日志把这次失败指出来。
