## 决策

**背景**：「`VdfsProvider` 去样板」的动议（把 `PluginConfigMount` 那类单点分发推广成
默认实现）要把 `symbio_core::VdfsProvider` 从**一个方法**扩成**十个方法**，其中 9 个带默认体。
按当时门禁口径算一遍：C-001 / C-002 看的是根出口的**形状字符串**，一个字符
没动；C-003 数的是**符号表**，`VdfsProvider` 早就是多消费方导出，符号 +0；`dead-code` /
`core-naming` / `no-direct-call` / `mechanism-audit` 的判据里没有「一个 trait 有几个成员」这一项。
**⇒ 契约面 ×10 的改动可以在门禁全绿下提交。**

而这条纪律本仓早就写了：`SP-003 §0 纪律 3`「架构改动必须逐条论证『必需』」，登记条目
[SP-007](../008-spec/007.md) —— 它的判据那一栏写的是「论证不出即删（**人工核对**）」。
于是全部约束取决于执行的人**记得**去核对。批次执行时最不缺的就是合理化：「加 9 个方法是实现层的
样板收敛，不算架构改动」。这条被实测到（同一批的量级：处方只消除约 200 行 /
1201 行，不到 20%；代价是核心契约面 1→10 个方法 + 取消 `request.rs` 论证所依赖的编译期穷尽）。

**决策**：

1. **立 `scripts/core-shape-audit.mjs`（CS-001）：core 公共形状的三格棘轮，冻结在实测值，只许降。**

   | 格 | 冻结值 | 它拦的膨胀 |
   |---|---|---|
   | `traits` | 20 | **新增接缝**：每多一个抽象，多一处「所有实现方都得知道」的地方 |
   | `methods` | 72 | **契约变宽**：既有接缝上挂新方法，影响面 = 全部实现方 |
   | `defaults` | 24 | **接口上长实现**：行为代码住进架构模块（方向是 0，存量随 `C-003` 的下沉一起收） |

   口径：`symbio_core` 生产侧（`*.test.rs` 与 `#[cfg(test)]` 模块不算，与 C-003 的
   「测试不是架构消费方」同一条），文本判定不建 AST，已知边界写在那份脚本文件头。

2. **CS-002：改棘轮数字必须挂一条能打开的决策。** 基线旁边要写
   `core-shape-allow <格>: ADR-NNN <非空理由>`，而 `ADR-NNN` 必须在 `docs/010-adr/` 真实存在。
   「批次需要 / 顺手 / 待补 / 见对话」都不算。

3. **`gate.d/35-baseline.mjs` 的 `RATCHETS` 清单加这一处落点**（`dir: ceiling` +
   `envVar: CORE_SHAPE_BASELINE`）——它比对 git 基准版本判「数字有没有比上一版更松」，
   与本条 2 **各判半条**：那边发现「变松了、旁边有没有注释」，这边判「注释够不够格」。
   两半合起来才是完整的「**放宽 = 写一份能被打开的决策**」，而不是「改一个数字」。

4. **`SP-007` 的判据从「人工核对」升级为指认 CS-001 / CS-002**（纪律条文本身不动，owner 仍在
   `SP-003 §3`；本条只把它的**核对方式**换掉）。

**理由**：

1. **架构模块的质量高于模块质量，因为它的影响面是全部的**。一份 `docs/003-design/README.md` §0.1.2
   的标尺说机制层不可妥协，但标尺是给人读的；把「不可妥协」翻译成「改了就红」才叫约束。
2. **棘轮不判论证内容，只保证决策存在。** 「这 9 个默认方法该不该加」仍是 ADR 与人的事；
   CS-001 只保证问出这个问题时**留下痕迹**——一次红、一行数字、一份 `docs/010-adr/` 文档。
   一个能把数字顺手改小的守卫和一个人工核对没有区别。
3. **三格的量级都是实测出来的，不是拍的**（`--verbose` 逐 trait 打印成员数与默认体数）。
   冻结值就是当前形状，所以本条**不要求任何整改**，只要求「此后不再长宽」。
4. **`defaults` 那一格是本条最特意的地方**。「架构里不应该有大量实现代码」是这次批次被叫停时
   给出的判断，而它的可执行形态就是「接口上每多一个默认体都要留一份决策」——
   不是审美偏好，是那条判断的机制化。

**被否决的方案**：

- **判行数**：否决。`SP-003 §3.3` 写着「加了数据 / 加了调用点 / 改了文档，都不是架构改动」，
  而契约加字段是数据变化——行棘轮会对它红，那是误报；一个只会误报的守卫最后一定被人
  喂豁免喂到失效（`core-export-audit.mjs` 的 T-059 注为此写过一整节）。
- **判枚举变体数**：不做。变体**是**形状量（`SP-003 §3.5` 把「`NodeKind` 新取值」列为
  不新增项），但它与「trait 宽度」不是同一个失效面。要加就单独论证一次，不顺手扩判据面。
- **把三格并进 `core-export-audit`（当 C-004 / C-005）**：否决。除了职责不同
  （那边判「**谁**能出现在公共面上」，这边判「公共面**有多宽**」），还有个机制性理由：
  `35-baseline` 读**落点文件**的基准版本，往已有文件里加新格会让它在落地那一次判「提取函数
  与落点形状脱节、判据失效」而红——新格必须住在一个**基准版本里还不存在**的落点上。
- **靠 rust-analyzer / syn 做 AST 解析**：否决。门禁的既有口径是纯 Node 文本扫描
  （`rust-scan.mjs` 是它的唯一真源），引入解析依赖会让这道守卫在 CI 上多一整个失败面。
- **只把纪律写得更严厉（加文档、加 AGENTS.md 一句「要谨慎」）**：否决。缺的从来不是措辞——
  `SP-003 §0 纪律 3` 已经写了，是它的判据没有执行方。
- **给那次去样板的处方直接写一条「允许放宽」的豁免**：否决。豁免与棘轮的分工是「存量」与「增量」，
  而那批该收成什么形态不由一条放宽豁免替它定——把未定案的东西登记成放宽，等于让批次替架构做决定。

**后果与不变量**：

- **此后凡是让 `symbio_core` 的公共面变宽的动作，都要先有一条 ADR。** 包括新增 trait、
  在既有 trait 上挂方法、给成员加默认体。反过来说：**收窄不需要批准**——
  降到基线下方时脚本会提示同步数字（棘轮只认更紧那一侧）。
- **`VdfsProvider` 的去样板从此有一个有牙齿的落点**：走「默认实现 +
  域方法」或「宏生成」都会把 `methods` 从 72 推到 81 上下 ⇒ 必须走 CS-002；把 `Watch` /
  `Unwatch` 的重复臂收到共享实现（trait 一格不动）则三格不动。**决策的形状由此可核对**：
  看它有没有触碰基线，而不是看它怎么描述自己。
- **`registry-audit` 与 CS-002 是两条独立的检查**：前者判 ADR **条目**合不合登记规范（字段 /
  状态 / `domain`），后者判**引用**能不能打开。指认不存在的 ADR 会被后者红，不会只留下一条
  读起来像真话的注释。
- **不变量**：`SHAPE_BASELINE`（审计侧）↔ `coreShapeCells`（元守卫侧）↔
  `CORE_SHAPE_BASELINE`（env 位置口径）三处的键名与键序必须一致；任何一边单改，
  `35-baseline` 会在基准版本里读不出格 ⇒ 判红（不是判绿）。
