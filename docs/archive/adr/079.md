## 决策

**背景**：[T-157](../009-task/157-ActorSpec-pattern死字段接线.md "T-157-ActorSpec-pattern死字段接线") 立项时的
判断是「`ActorSpec.pattern` 生产零读取，三处 Decider 特判各自为政——让它成为分派点」。核完前提
发现这句话里藏着一个**同名两物**：系统里有两个都叫 `pattern` 的东西，而且它们不是同一个。

| | core 的 `ActorSpec.pattern` | S11 §4 的 `actor.pattern` |
|---|---|---|
| 住在哪 | `symbio_core::actors::spec`，F3 冻结五字段之一 | [S11 §4](../009-task/131-技能编译与自我改进.md "T-131-技能编译与自我改进") 的 capability-assign 参数表 |
| 取值 | `Decider` / `Reasoner` / `Translator`（闭集三值） | `decider` / `reasoner`（平凡值 `reasoner`） |
| 谁给值 | `Pattern::for_principal`——**从授权表谓词派生**（`reply.*` ⇒ Reasoner；`produce.artifact` ⇒ Translator；其余 ⇒ Decider） | 配置开关 `skill_fast_path`（`SessionConfig`） |
| 意思 | **这个主体是哪一类**（它最便宜能做的事） | **技能命中时要不要跳过模型** |
| 有读方吗 | 无（本次核实：生产零读取） | 有（`chat_loop/inputs.rs` 的 `fast_armed` ⇒ `turn.skill_hits`） |

两个「pattern」共用一个词，于是代码里的注释把配置开关写成「S11 §4 的 `actor.pattern`」，
读代码的人自然以为 core 那个字段就是它——**这就是「假机制感」的来源**。字段躺着不是缺陷，
**注释说它管着什么、实际它不管**才是缺陷（J3）。

**裁决一：core 的 `ActorSpec.pattern` 不做分派点，且这不是「还没接」，是接不了。**

派生函数决定了它的信息量：`reply.* ⇒ Reasoner`。而**每一个会跑模型的轮次主体都持 `reply.*`**
（`session/main` 与它的子主体），所以凡是要分派「走不走模型」的地方，读到的永远是 `Reasoner`。
把它接成闸门，等于把技能快路（S11 的 `actor.pattern = decider`）**永久关死**——两处叫同一个名字，
接上去正好互相抵消。

反过来说：凡是 `Decider` 的主体（`session/arbiter` / `session/verifier` / `session/planner`）
本来就不跑模型，它们的分派早已由**类型**决定（`run_reflex` 只收 `RuleOnly` 令牌，
「反射档调模型」在类型上写不出来）——那里也不需要一个运行期字段。

**裁决二：三处 Decider 特判的共性在「输入形状」，不在「主体」。**

| 特判 | 判的是 | 为什么不能由主体属性决定 |
|---|---|---|
| `classify/rules.rs` 规则短路 | 这句话是不是礼节性的（问候 / 致谢 / 确认 / 空输入） | 同一个用户上一句问「周报怎么整理」、下一句说「谢谢」——主体没变，输入变了 |
| `turn_runner::run_reflex` 技能命中 | 这句话是否与某条已编译技能 `trigger` **逐字相同** | 命中率是**重复发言**的函数，不是主体的函数 |
| `orchestrator/entry.rs` 的 `ping` | 这条消息是不是健康探针 | 探针伪装成用户消息，判据在载荷形状上 |

三者是同一个 Reasoner 主体内部的**输入分流**，彼此也不互斥（探针先判、礼节其次、技能最后）。
把它们合成一条「按 pattern 分派」的链，会把三种不同的判据压成一条，而它们的判据函数没有公分母
——那正是 [DE-001 §0](../004-plan/001-核心架构.md "DE-001-核心架构") 说的「形状是裁决、路径是数据」的
反面：为了一个字段的可见性去改三处的判据。

**裁决三：F3 划界——冻结的是形状与闭集，不是「必须有分派读方」。**

`Pattern` 三值与 `ActorSpec` 五字段一个字不动（J1：能用已有参数新取值表达的，就是数据）。
本条只是把「它为什么没有分派读方」写成裁决，并给出**它是什么**：主体分类，供治理面
（⑥ `governance` 的能力校验）与审计读。这不违反 J3——J3 要的是「静默失效不可接受」，
而这里的失效从来不是「约束没被强制」，是**注释许诺了一个不存在的机制**；修法是把许诺改对。

## 否决的替代方案

- **把 `pattern` 接成 `run_reflex` 的闸门**（`actor.pattern == Decider` 才走快路）：被否，见裁决一。
  `session/main` 派生 `Reasoner` ⇒ 快路永不命中，`e2e/cases/t41-skill-fast-path.mjs` 会当场红。
  那条用例因此就是这条裁决的**机器判据**：谁把 pattern 接成分派点，它立刻失效。
- **让 `for_principal` 改从配置派生**（`skill_fast_path` 开 ⇒ `Decider`）：被否。那会把
  「主体是哪一类」变成「这一轮开了哪个开关」，同一个主体的 pattern 逐轮抖动；而它一旦抖动，
  授权面读它做的任何判断都会跟着抖。`budget_ms` 已经承担了「逐轮可变」的那部分，不必让
  `pattern` 也变。
- **删掉 `pattern` 字段**：被否。F3 冻结；且它在治理面有预定读方（能力校验要问「这个主体的
  权威动作与它的模式对得上吗」）。删字段是把一次注释错误升级成契约变更。

## 后果

- **三处特判保持原样**，但它们不再是「机制化不够」的证据：它们是**输入分流**，归属各自领域
  （classify 插件 / 技能编译 / 编排入口）。「不许长第四个」的守卫归
  [T-163](../009-task/163-插件层特判审计守卫.md "T-163-插件层特判审计守卫")——本条只划界，不建守卫。
- **注释订正**：`SessionConfig::skill_fast_path` / `ChatSession::skill_fast_path` /
  `chat_loop/inputs.rs` 的 `fast_armed` 三处不再自称「S11 §4 的 `actor.pattern`」，
  改称「S11 §4 参数表里的 `actor.pattern`（落地形态是开关）」，并注明与 core 字段**同名不同物**。
- **新增判据**：`chat_loop/state.test.rs` 钉住 `session/main ⇒ Reasoner`——这是裁决一的反证：
  一个「会跑模型」的主体派生出的 pattern 是 Reasoner，所以它不能拿来判「跑不跑模型」。
- **`impl: done` 的口径**：本条是裁决 + 注释订正 + 一条判据，没有行为变更；残余为零
  （三处特判的去留不在本条）。
