# D-114：控制面单元从 Step 收敛为债

## 决策

1. **控制面的调度单元是「债」，不是「Step」。** `owed(log, table, facts, views) -> Vec<Debt>`
   返回**全量**欠账；`drive` 按 `(prio, name, key)` 全序取第一笔 `actionable` 的执行。
   现状 `decide -> Option<Step>` 的短路选一个，退役。
2. **债只有一种形状，差异全落在 `by` 一个字段上**：
   `by = Some(名字)` ⇒ `actors.run(名字, 债)`；`by = None` ⇒ 恒 `blocked`、永不选中。
   **引擎对 `by` 只有一个动作**，不存在"决策债 / 搬运债"的分支。
3. **消除「意图」这第二类产出。** 现状 `decide` 产出 `[要追加的事实 | 要发往世界的意图]`
   两类；本裁决后只有一类——要追加的事实。对外请求落为 `request{port}` 事实，
   派发由一行债（`by = courier`，`before: sent`）承担。
4. **`Wait` 与 `Ask` 折叠。** `Wait` 折叠为 `by = None` 的债（[DE-014 §2.1](../004-plan/014-单环一表收敛.md "DE-014-单环一表")
   已把它标注为"迁移期接口，终点折叠"）；`Ask` 折叠为 `request{port:model}`
   （[DE-014 §3](../004-plan/014-单环一表收敛.md "DE-014-单环一表") 已自认它是 `Act(Model 行)` 的特例、
   "工程取舍不是逻辑必然"）。本裁决兑现这两条自认。
5. **三处前置补齐后才动工**：`produced_by` 的「不悬空」检查、权限的「否定落事实」、
   停机原因的统一载体。未补齐不动第 1 条——否则形状换完，审计与治理两条线同时缺腿。

## 理由

**这是形状裁决，走 ADR 是 [DE-014 §0](../004-plan/014-单环一表收敛.md "DE-014-单环一表") 的要求**，不是新增流程：
该节明文写着"目标形状（§2 一环一表一源、§2.1 终点坐标、§3 的 Step 词汇…）是裁决——
要改走 ADR，不在实现里绕过去"。

三条实质理由，全部来自 DE-014 自己的文本，不是外部主张：

| # | 依据 | 本裁决做了什么 |
|---|---|---|
| 1 | §2.1 写下终点：`decide → [事实 \| 意图]*` | 把「意图」也收进事实，终点变成单类产出 |
| 2 | §3 自认 `Ask` 是非极小点 | 兑现它，`Ask` 消失 |
| 3 | §2.1 自认 `Wait` 终点折叠 | 兑现它，`Wait` 消失 |

**为什么"请求落为事实"不是"把端口塞进日志"。** §2.1 与 §9.1 否决的是后者（会劣化审批与
流式的延迟语义），本裁决不碰端口：端口仍在环外，`courier` 仍调它。变的是**请求本身**——
"我要调什么"从"一个还没落成事实的意图"变成 `request{port}` 事实。端口没有进日志，
**请求进了**。这是 DE-014 §2.1 没找到的第三条路。

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 保留 `Step` 五值（现状） | 两个非极小点（`Ask` / `Wait`）留着；且"意图"是第二类产出，崩溃判别要靠执行器自觉记录派发格 |
| 把世界端口也塞进日志（一切皆事件源） | [DE-014 §9.1](../004-plan/014-单环一表收敛.md "DE-014-单环一表") 已否决，本裁决不重开 |
| 先补齐三处缺口、再裁决形状 | 权限（缺口 2）可能**推翻形状本身**——若权限必须做成引擎认识的一维，则"引擎不认识业务"这句要改。顺序反了会白补 |

## 后果

**必须同时补齐的三处**（[DE-015](../004-plan/016-义务环.md "DE-015-义务环") §4 有完整清单）：

| # | 缺口 | 不补的后果 |
|---|---|---|
| 1 | 溯源边**已有**（`Event.produced_by`），但只查"有没有"、不查"指向谁" | 悬空指向照样绿；且文档口径要与代码统一到 `produced_by` |
| 2 | 权限**判定健全**（`authz.rs` fail-closed 三层），但**否定不落事实** | 「被拒绝」只能靠"该轮留在未收束态"表达——事后无法回答谁因何被拒，回放重现不出 |
| 3 | 停机原因无统一载体 | 重启后只能靠业务事实推断"为何停" |

**其余后果**：

- 表从"每端口一行"变为"每端口两行"（派发 + 等待），换来 `sent` 进日志与崩溃可判别。
- **端口调用第一次落成事实**：新增协议名（`request` / `sent` / `response` / `failed`，
  `retry` 由 [[D-115|D-115]] 补为第 5 个）+ 端口标识。现网 30 个业务事实名
  **一个不动**——本裁决补的是一类从来不存在的事实（DE-014 §2.1 的"意图"），
  不是把 30 个名字压成几个。
- 事实类型必须先声明（`FactDecl`），通用函数不再理解任何执行体的私有载荷。
  输入闭包、异步执行契约与端口两级由 [[D-115|D-115]] 补全。

## 诚实标注：这不是「更好」的证明

用 [DE-014 §7](../004-plan/014-单环一表收敛.md "DE-014-单环一表") 的 17 场景验证集纸面推演（未实测）：
**平 11 · 本裁决强 3 · 本裁决弱 2**。

| | 场景 | 为什么 |
|---|---|---|
| **强 3** | SC-004 并发 / SC-007 打断 / SC-017 定时 | 恰好是 DE-014 交叉验证时最费力的三个发现（F1 集合、F3 唤醒源）——本形状不需要"发现"，因为形状本来就覆盖 |
| **弱 2** | SC-003 返工 / SC-005 恢复 | 都是"事实之间的边"缺失，即缺口 1 与缺口 3 |

**所以本裁决的性质是：用形状的纯度换三处统一，代价是两处可审计性。**
那两处必须由第 5 条的前置补齐，不能靠"形状更纯"糊过去。

**不承诺**：本裁决不主张义务环比 DE-014 的路径更优。DE-014 的价值在六步怎么切、
熔断线多少行、哪些死分支会牵出退役链——那些纯设计推演不出来（D-071/089/093 三次改判
都是落地时才发现的）。本裁决只改**终点形状**，不改**施工路径**。
