## 决策

**事件信封不加 `schema_version`，`payload` 保持无类型 JSON。** 作为交换，把「只增不改」
写成三条可核对的纪律，并**明写这套做法判不了的三类情形与它的失效边界**——
不写就是拿一句纪律盖住一个不可判定的事实。

## 背景

[`Event`](../../symbio/src/symbio_core/event/mod.rs "event/mod.rs") 的字段是
`event_id / kind / entity / verb / turn / actor / produced_by / cost_ms / ts / payload / seq`，
`payload` 是 `serde_json::Value`。全仓没有版本标记。

[SP-003 §4](../004-plan/006-分步实施计划.md "SP-003-分步实施计划") 的纪律 4 写着
「新字段 `#[serde(default)]`，新语义只对新数据成立」。这句话对**增量字段**有效：
旧事件缺这个键 ⇒ 取默认值，读侧不会崩。但对**语义变更**它给不出判据——程序拿不到
「这条事件是旧语义还是新语义」的任何依据，因为没有任何地方记着这件事。

外部把这列为事件溯源的四大失效模式之一（Schema 演进灾难）。本仓用一条纪律覆盖它，
而纪律没有可执行判据——这恰好违反 [GO-000 §1](../001-goal/000-价值主张.md "GO-000-价值主张")
「关键声称必须有证据」。

## 为什么不是加一个 `schema_version` 字段

版本号只在**同时存在多版本读方**时才有判别力。本仓的读方只有一份：当前这版代码。
在此前提下，`schema_version` 会立刻退化成「只写不读的值」——这正是
[DE-001 §8](../004-plan/001-核心架构.md "DE-001-核心架构") 明确不算作取值的那种东西：
一个没人读的字段让「事件长什么样」的陈述变稀，却挡不住任何一次真实的语义漂移。

要让它**有用**，必须同时保留每版读方的分派逻辑（`match v { 1 => old_read(), 2 => new_read() }`），
而 `old_read()` 的判据是「旧版本长什么样」——那份知识本仓没有保留（旧代码在 git 里，
不在运行路径上）。**加字段便宜，加分支不便宜**：先把字段加上，等真需要分支时，
字段已经在那儿但没人写过分支，等于给自己一个「看起来已版本化」的假安全感。

## 三条纪律（其中两条有执行方，第三条只有人）

| # | 纪律 | 可执行性 |
|---|---|---|
| 1 | **信封只增不改**：字段只加不删、不改名；新字段一律 `#[serde(default)]` | 见下「缺口」 |
| 2 | **payload 只增不改**：读侧一律按键取值（`payload.get("k")`），多余键忽略、缺键取缺省；禁止改已有键的**含义** | 读侧形态已如此（`memory_events.rs` / `skill_events.rs` / `task_events.rs` 全部 `payload.get(..)`），改含义仍只能靠评审 |
| 3 | **语义变更必须走 ADR，并在 §6 网格那一行写清「旧数据怎么解释」** | 人工 |

**缺口（不掩饰）**：纪律 1 目前没有机器判据。删字段或改字段名，编译期只会红在仓库内部
——已经落盘的 WAL 里那些键还在，replay 读出 `None`，**静默**。处置方式见「后续」：
把 `Event` 的字段名集合做成只增棘轮，改一次名红一次。

## 代价：三类判不了的情形

1. **字段改名**——旧 WAL 的键对不上新结构，读出默认值。结果不是报错，是**少了一半事实**，
   而且看起来完全正常（默认值通常恰好是合法值）。
2. **枚举取值语义改变**——`verb` 从一个含义滑到另一个含义，类型全程合法，读侧照算，
   只是算出来的东西不是当初写下的意思。这是本项目最忌讳的「第二处真相」的运行时版本。
3. **payload 结构收缩**——从对象改成标量（或反之）。读侧如果碰巧用 `get(..)` 取键，
   它会安静地拿到 `None` 并走缺省分支。

三类都是**静默**失效：不崩、不报、日志里看不出来。这正是要写进本节的原因——
一个已知不可判定的面，比一个假装可判定的面安全。

## 失效边界：本裁决在下列任一情形下作废，必须回来加版本号

1. **同一份 WAL 需要被两个版本的读方同时解读**——灰度期双读、跨版本回放对比、
   离线评测用旧代码读新数据。此时版本号从「无读方的字段」变成「唯一的判别依据」。
2. **出现外部事件源**——导入的第三方事件流，其版本演进不由本仓调度。
3. **某次变更无法用「只增」表达**——必须删字段、改字段名、或改 payload 既有键的含义。
   这种变更数量到 1 次，就足够让整条纪律失去「不需要版本号」的前提。

前两条出现时，**不要**先在信封上加一个孤零零的 `v` 字段——按上面的理由，那只是把
「不可判定」换成「看起来可判定」。要加就连读方分支一起加。

## 被否决的替代方案

- **`#[serde(deny_unknown_fields)]` 强制新旧对齐**：否决。它让旧读方遇到新字段直接崩，
  与 append-only 事实源的向前兼容方向相反——追加是新事实的权利，不是需要审批的变更。
- **为每个事件存一份 schema 副本**：否决。存下来的 schema 仍然是「写方以为的样子」，
  而漂移发生在「读方理解的样子」；副本只会让两边更自信。
- **不写这条 ADR，继续靠纪律 4 的口头约定**：否决。纪律的效力来自「违反时会红」，
  一条既不会红、也没写清边界的话，在第三次交接后就会变成「我们好像有版本化」的错觉。

## 后续

- 纪律 1 的机器判据（`Event` 字段名集合**只增**棘轮）尚未落地。落点必须是独立判据，
  **不能**并进 [`core-shape-audit`](../../scripts/core-shape-audit.mjs) —— 它的口径边界
  写着「不判行数：契约加字段是数据变化，棘轮会对它红，那是误报」；字段**增加**必须放行、
  字段**删除或改名**必须红，这是集合包含关系，不是数字棘轮。
- 一旦命中失效边界 1／2／3，本 ADR 状态改为 `superseded`，新 ADR 必须同时给出
  读方分支的判据来源（旧版本长什么样，存在哪）。
