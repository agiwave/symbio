## 决策

**触发**：[T-169](../009-task/169-压缩归档吞掉未收束轮的恢复锚.md "T-169-压缩归档吞掉未收束轮的恢复锚")。
一轮停在「等用户动作」上时，它在事实源里只有用户格（`turn × opened`），收束格刻意
留给恢复幕（[D-067](067.md "D-067") 决策 3）。此时任何一次压缩落格都会
`archive_before(快照 seq)`，把该轮的用户格移出 live 段。恢复请求进来后
`last_open_turn(current_window(range(0)))` 只在最新快照之后找 ⇒ `None` ⇒
`InternalError("续写轮找不到未收束的轮次")`。轮号不受影响（快照载荷的 `turns`
水位让 `count_user_messages` 接着数），缺的只有恢复锚。

**决策**（T-169 给出的两条出路里选后者）：**恢复锚读完整史，归档刀口不动**。

- `turn_exec::last_open_turn` 的输入从 `current_window(&snapshot)` 改为 `&snapshot`
  （`Store::range(0)`，含归档前缀）。
- `consolidate_into_wal` 的落格与 `archive_before` 一字不动；快照仍取代它之前的
  **一切**消息列表。
- `current_window` 的行为不变，但职责收窄：它服务「上下文 / 进度从哪读」，
  **不再**承担「找未收束轮次」。

## 理由

1. **快照的取代边界是消息列表，不是轮次生命周期。** 快照回答的是「给模型看的上下文
   从哪开始」；轮次事实（`turn × opened` / `turn × closed`）是 C4 的配对依据，不被
   压缩改写。C4（`invariants::unresolved_turns`）读的本来就是完整史——归档后它仍会报
   该轮未收束。恢复锚若改读窗口，同一份事实在 C4 眼里「未收束」、在恢复路径眼里
   「不存在」，这是两个读法对同一判据的分叉，而不是两种合理的口径。
2. **「未收束」与「已被取代」是正交的两件事。** 旧实现拿「在现行窗口里」代理
   「未收束」。代理在绝大多数时候成立，但 T-169 的形状恰好让两者同时为真：等待审批
   的那一轮既未收束、又被压缩取代。判据必须按它真正要问的问题写——「完整史里是否
   还有一个只有用户格、没有 final / fallback 的轮」。
3. **读完整史不会让「陈轮」重新变成锚。** `last_open_turn` 取**最后**一个开盘：
   已被 final / fallback 收束的轮不在候选集里；仍开着的轮按开盘序排，任何真正等待
   恢复的轮都排在更早的缺口之后。若比它更新的轮也开着，那本来就是现行契约下
   「最近一次停顿」的候选（见 D-067 决策 3，两者都不认产物格）——这不是本条引入
   的新行为。
4. **零结构变更。** 不新增事件、不新增字段、不新增 `Store` 方法，CS-001 三格不动；
   归档段布局、段名、`range(0) = 归档段 + live` 的拼接全部保持原样。

## 被否决的方案

- **T-169 方案 A：未收束的那一段不进被取代前缀。** 被否。`current_window` 按
  **最新快照的位置**切，不按归档段的边界切：把用户格留在 live 段但排在快照之前，
  窗口仍从快照起 ⇒ 恢复锚照样找不到。A 要成立只能连「窗口怎么切」一起改，而那会
  让「快照之后才是现行上下文」这条折叠基线失去唯一解释。
- **推迟压缩，直到没有未收束轮**（A 的可执行形态）。被否：等待审批 / 问答的轮可以
  无限期开着，压缩会被一个待办工具卡死；`retry_compaction` 恰恰跑在循环之前、正是
  为失败压缩重试，它要压的那段历史里有一位等待者就永远压不成。压缩的语义是
  「取代消息列表」，不是「等轮次收口」。
- **让 `archive_before` 跳过个别事件。** 被否：归档段必须是从头开始的连续前缀，
  段名（首末号）与 `range(0)` 的拼接都以此为据；跳过事件会在拼接里制造缺口或乱序，
  D-053 的「零回退损失」（逐条不重不漏）当场失效。
- **快照落格时把未收束轮的用户格另抄一条到快照之后。** 被否：那是伪造事实——同一句
  话在网格里出现两次；且抄出来的 seq 不同于原用户格，收束的溯源锚（I2）与 C4 的
  配对都会指错。

## 与 D-067 决策 3 的口径对账

两处判据回答的是不同维度的问题，**互不替代**：

| 问题 | 判据 | 归属 |
|---|---|---|
| 哪些事件算「这一轮收束了」 | 只认 final / fallback，**不认产物格** | D-067 决策 3（不变） |
| 在哪个范围里找未收束轮 | **完整史**，含归档前缀 | 本条（改为完整史） |

合起来：**完整史里，最近一个「只有用户格、没有 final / fallback」的轮**。
产物格既不让它提前收束（067），归档也不让它从判据里消失（085）。
两份文档各自在函数旁声明差异——D-067 说的「找不到未收束的轮次」是
**认了产物格**造成的假收束；本条说的是**窗口**造成的假缺席，两个因不能混。

## 后果与不变量

- **恢复链路**：压缩 + 待恢复同时成立的会话不再报 `InternalError`；续写仍落在原轮，
  `u-{turn}` 不重开、轮号不回退。
- **判据**：`turn_exec.test.rs` 两条用例（轮内 / 轮外两条落格路各一条）——
  一轮开格未收束 ⇒ 压缩落格并归档 ⇒ 完整史仍读作未收束 ⇒ 续写请求成功、
  收束格溯源仍指归档段里的用户格。旧读法下两条都红（`InternalError`）。
- **文档职责**：`current_window` 的文档不再声称用于找未收束轮次；
  `last_open_turn` 的文档写明输入必须是完整史。
- **不影响的面**：`count_user_messages` 的轮号水位、`current_window` 的消费方
  （`worker_progress` 的进度窗口）、归档布局与一写者语义（[D-084](084.md "D-084")）
  均不变。
