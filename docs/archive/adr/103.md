# D-103：授权能力闭集 7 → 6——首响与追加合并为 `reply`

## 决策

`Capability` 闭集去掉 `ReplyFirst` / `ReplyAppend`，合并为**一个** `Reply`（书写形态 `reply`）：

```rust
pub enum Capability {
    JudgeIntent, Reply, DefineWork,
    ProduceArtifact, AssertVerification, AssignWork,
}
```

`PermissionMatrix::can_reply` 不再接收 `first: bool`；`Capability::reply_capability`、
`ActorSpec::can_land_speech(first)` 的 `first` 参数、以及生产收束点的二分支同批消失。
`authz::ROWS` 里 `agent:main` 的 `reply.first` / `reply.append` 两行并成 `reply` 一行。

## 判据

与 [T-170](../009-task/170-横向扩展摩擦批.md "T-170-横向扩展摩擦批") 同一把尺：**这处机制不生效时谁会红？**

- 生产里所有收束调用点都在「本轮尚无收束格」的位置（`turn_runner::closure_granted` 的
  `ClosureKind::Speech`），`first` 恒为 `true`；`ReplyAppend` 分支只被单测喂到。
- 授权表里 `reply.append` 与 `reply.first` **总是同进同出**（所有持 `reply` 的主体两行都给），
  因此两行并成一行不改变任何主体的可用性——这是可核验的等价，不是偏好。
- 「首条 / 追加」是**轮次位置**，属于事实流的位置信息，不是「权威动作的种类」；
  §7 的三维表把能力的定义钉在后者上，前者的差别住在事件里（`turn` 已有的格）。

## 否决的替代

- **保留两值、把追加臂接上**：生产路径里不存在「本轮已有收束格后再发言」的合法动作——
  一轮只收束一次是事实网格的约束，接一个不存在的状态就是为不可达状态造机制。
- **保留两值、只删追加臂**：留下 `ReplyFirst` 这个名不副实的名字（它已经不是「首条」，
  而是「发言」），名字会继续暗示一个不存在的分叉。
- **把位置做成参数保留**：参数没有第二个取值，读方每次都要传 `true`——这是**待删的形状**，
  不是可扩展点。

## 后果

- 能力闭集 7 → 6（[DE-001 §7/§8](../004-plan/001-核心架构.md "DE-001-核心架构")）；
  机制键数与 `RowKind` 均不受影响（本条只动授权枚举，见 [D-071](071.md "D-071") 的同轴澄清）。
- 授权表少一行冗余：`agent:main` ▸ `reply`。持 `reply` 的主体集合与合并前**逐主体相同**，
  由 `authz.test.rs` 的等价断言钉住。
- 阶段文档的 `capability-assign` 块（S01 / S02 / S05 / S10）与验证程序输入同批改成 `reply`，
  `gen-verify-facts` 的取值域因此仍是**算出来的**，而不是留一个已不在闭集里的旧名。
- **本裁决向前生效**：授权能力若需第 7 值，按封闭集纪律逐条开 ADR 并给出「谁会红」的读方。
