## 决策

**背景**：`ChatMessage` 的 `MessageType::Turn` 名义上是"一轮响应"，实际承担的是**容器**职责——
文档原话：「`Turn` 与 `ToolCall` 是组合节点，
不含实际内容，仅分组子节点」。但「轮」这个词绑了三件事：

1. **C4 配对不变量**：一个 `user.message` 必须配一个 `Turn.Opened` 与一个 `Turn.Closed`（[D-052] 的 abort 路径也按 turn 走）
2. **写侧半格**：`resume.rs::RetryTurn` 只允许靶子是 `Turn`，VDFS 动作 `truncate` / `retry_turn` 也绑 turn
3. **读侧根**：`transcript_window` 取"最后一轮"、`count_user_messages` 数 turn 号

[DE-019] 要把前端切成「只认树、不认轮」的机制形态，同时 [T-135]（中断轮的收束缺位）与
[T-137]（CLI 交互卡无呈现）在旧协议下的修法要么是先补一对 Opened/Closed，要么是加一个专名节点，
两种都是把"轮"当协议原语。

**决策**（一条 ADR 里三件事，它们共用同一条判据：**前端只认机制，业务只活在后端**）：

### 1. `Turn` 语义从协议退役，改用 `Skeleton`

- `MessageType::Turn` → `NodeKind::Skeleton`（容器；`"run"` / `"tool"` / `"sub_agent"` 只是**后端注记**，见 §决策 3）
- `ResumeAction::RetryTurn` → `ResumeAction::RetrySubtree`（靶子=任意骨架，不再校验 `msg_type=Turn`）
- VDFS `truncate` / `retry_subtree` 动作的靶子检查从「必须是 Turn」改成「必须是 Skeleton」
- `count_user_messages` 那类「按 turn 配对」的不变量从协议层删除——骨架之间的**嵌套形状**
  由后端建树策略决定（见 [DE-019 §5]），前端不感知

「一轮」这个词从协议、注释与现行文档里**清空**；它是**特定建树策略下的显示效果**，不是概念。

**工具不是卡片，是一个容器节点**：一次工具调用就是 `Skeleton` + 它的子流（请求侧一个
`Body`、响应侧一串 `Body`/`Notice`/`Typing`），与"一整轮助手响应"在**结构上完全同构**——
都是「一个骨架挂一条子流」。因此**不存在独立的 tool 呈现**：`ToolCallNode` 与 `TurnGroupNode`
塌成同一个容器渲染器。「谁在说」（agent 请求 vs 工具返回）是 `principal.kind` 的**数据**，
决定侧向 / 徽标，不决定布局。

### 2. 顶层字段消费纪律

`ChatNode` 顶层字段**只承载**"前端不依赖业务语义就能消费"的东西——机制轴 + 呈现数据 + 内容三件套：

| 允许进顶层 | 不允许（沉 `meta` 或只留后端） |
|---|---|
| `id` / `parent_id` / `seq`（树 + 顺序锚） | `tool_call_id`（provider wire id，前端不消费） |
| `kind`（**唯一**呈现分派轴） | `role`（与 `principal` 前缀重复——见 [D-069]） |
| `status`（生命周期） | `name`（业务专名 → 用通用 `title`） |
| `principal`（主体：侧向 / 徽标） | 具体子类型枚举（`skeleton_kind` / `tool` / `reasoning` → **后端注记 `style_tag` 沉 `meta`**，前端不读，见 §决策 3） |
| `content` / `delta` / `error` / `timestamp` | 业务专名 MessageType（`Compression` / `UserPrompt` / `Reasoning` → 合并到 `Notice` / `Interaction`） |
| `stats`（读数行，由**携带读数的节点**携带——今天两个产者都是折叠叶；兑现与携带范围见 [[D-111|D-111]]） | |
| `title`（呈现文本：后端填，前端照显示） | |
| `icon`（呈现徽标：后端填标识，前端映射到 UI 资产） | |
| `actions`（本节点可发起的 `ResumeAction` 列表——把"能重试什么"从前端业务判据变成后端数据） | |
| `meta`（业务兜底） | |

**判据**：一个字段能不能进顶层，只问一处——前端 / CLI 有没有**不查看 meta 语义**就能消费它的地方？
答案没有 ⇒ 沉 `meta`。这条判据**落守卫**（`scripts/protocol-mirror-audit.mjs` G 组，[T-152]）：
扫 `chat_node.ts` 每一顶层字段，grep 前端 / CLI 消费者；命中但判据里读 `meta.xxx` 的算违规，红。

### 3. `NodeKind` 是前端**唯一**分派轴；`style_tag` 降级为后端注记

**这是对旧 §决策 3 的推翻。** 旧条款写「协议 enum 只表达呈现，业务分类走 `style_tag`，注册表按
(kind, style_tag) 分派」——听着像机制化，实则把 `reasoning` / `tool` / `compression` 这些**业务词**
换到 `style_tag` 里继续让前端 `switch`：前端照样认识 Reason/ToolCall/Compression，只是枚举挪了个位置。
**换名不是机制化。**

新条款：

- **前端只按 `NodeKind` 五值分派渲染器**，这五值是**纯 UI 形状**概念，不含任何业务：
  - `Body` = 展开的正文叶子；
  - `Notice` = **折叠的叶子**——`reasoning`（思考）与 `compression`（压缩）与未来 `step_summary`
    全在这一格，前端渲染它们**完全一样**（一个可折叠叶子 + `title` + `icon`），不需要知道这坨
    到底叫思考还是压缩；
  - `Skeleton` = **容器**——`run`（一整轮）与 `tool`（一次工具调用）与 `sub_agent` 全在这一格，
    前端一律递归渲染 `children`，不认 tool/turn；
  - `Interaction` = 待用户应答；
  - `Typing` = 占位。
- **同格内的业务差异全部落到 `title` / `icon` / `actions` 数据**（后端在构造节点时填），
  前端**照数据渲染**，绝不 `switch(style_tag)`。
- **`style_tag` 沉进 `meta`**：它仍是后端**业务判据**的载体（`is_reasoning` / `is_tool_call` /
  `is_compression`、LLM 请求重建），后端认识业务天经地义；但它**不再是前端消费的 wire 顶层字段**，
  因此不受 §决策 2 的 G 组"必须有非 meta 前端消费点"约束——它就是给后端自己用的。
- **`reasoning` 归位**：`Body + style_tag:"reasoning"`（[T-147c-ii] 的走偏）→ **`Notice`**
  （[DE-019 §3] 从一开始就定的）。这一挪同时是机制化的钥匙：reasoning 一旦和 compression 同格 `Notice`，
  前端对二者的渲染路径就**合并成一条**，`style_tag` 在前端彻底失业。
- **`actions` 上 wire**：今天「这个失败节点该发哪种重试」（`canRetryTool` / `canRetryCompaction` /
  `messageRetryTargetOf`）是前端**按业务类型**（tool_call / compression / run）推出来的——这是最后一处
  业务耦合。改成后端在节点上直接标 `actions: [resume_action...]`，前端只做「有 `retry` 就画重试、
  有 `approve` 就画批准」的**数据渲染**，不认识"工具"或"压缩"。

新工具 / 新事件类型 ⇒ **只改后端**（往 `meta` 里加 `style_tag` 注记 + 填 `title`/`icon`/`actions`），
**前端零改动**——这才是"加一种业务不动前端"的真机制化，而不是旧条款的"加一个 style_tag 改一次前端表"。

#### 3.1 `layout` 字段——明确否决

曾提议加 `layout` 给"同类节点内部不同摆法"开口子。**在 tool 塌成容器之后这个口子已无物可漏**：
容器只有一种排法（递归流）。渲染决策的**全部**依据已被覆盖——
是容器还是叶子→`kind`；靠左右→`principal.kind`；图标/标题→`icon`/`title`；动作→`actions`；
状态→`status`。加 `layout` = 在 `kind` 之外再造一个隐式形态枚举，前端又得 `switch(layout)`——
正是要废除的东西。**故 `layout` 不引入。**

### 4. `role` 字段删除

[D-069] 把四前缀铺到与 `role` 等宽之后，`role` 就成了**同一事实的第二份定义**——删。
`MessageRole::{User,Assistant,Tool,System}` 从协议里移除；前端所有 `role === 'user'` 判据换成
`principal_prefix_is('person')` 之类的**前缀判定**。

## 后果

**（1）已实施部分（改名批，[T-147] / [T-148]）**——保持不变：
- `chat_message.rs` → `chat_node.rs`；`ChatMessage` → `ChatNode`；`MessageType::Turn` 与 `MessageRole` 删除
- `ResumeAction::RetryTurn` → `RetrySubtree`；VDFS 动作靶子从 `Turn` 换成 `Skeleton`
- 存量读侧一次性映射（`legacy_shape_to_style_tag`）

**（2）机制化批重做的部分**：
- **`reasoning` 归位 `Notice`**（原 `Body + style_tag:"reasoning"`）：
  - `legacy_shape_to_style_tag`：`"reasoning" => (Notice, Some(REASONING))`
  - `NodeKind::Body` 文档、`is_reasoning` / `is_text` 谓词随之调整；`is_compression` 从「裸 `Notice`」
    改成「`Notice` + `style_tag != reasoning`」（否则 reasoning 归 Notice 后二者互撞）
  - 后端所有构造 reasoning 的点（`rebuild.rs` ×3 / `message_build.rs` / `stream.rs` /
    `chat_loop/state.rs` / `v2_exec.rs` ×2）从 `Body + with_style_tag(REASONING)` 改成 `Notice`
- **`style_tag` 从前端 wire 退役**：前端 `schemas/chat_node.ts` 删 `CHAT_STYLE_TAG_*` 常量与
  `foldNodeKind` / `NODE_KIND_PRESENTATION` / `messageTypeOf` 的 tag 折叠；后端仍写 `meta.style_tag` 供业务
- **前端呈现键全退役**：`NODE_KIND_TEXT` / `REASONING` / `TOOL_CALL` / `TURN` / `USER_PROMPT` /
  `COMPRESSION` 六业务键删除；`TYPE_PRESENTATION`（按业务键索引）拆成按 `NodeKind` 五值索引
- **渲染器 7 → 5**：`ToolCallNode` 与 `TurnGroupNode` 塌成**一个** `SkeletonNode`（容器递归）；
  `TextNode` / `CompressionNode` 塌成 `NoticeNode`（折叠叶子）；`UserPromptNode`→`InteractionNode`；
  `TypingNode`；`BodyNode`（展开正文）。`MemoryNode` 保留为 `Notice` 的 title 变体，不是新 kind。
- **加 wire 顶层字段**（symbio_core 变宽，受 CS-001 棘轮约束）：`title: Option<String>`、
  `icon: Option<String>`、`actions: Option<Vec<ResumeAction>>`；后端构造点填充
- **`actions` 取代前端业务重试判据**：`canRetryTool` / `canRetryCompaction` / `messageRetryTargetOf`
  读 `node.actions`，不再读业务类型
- **守卫同步**：`protocol-mirror-audit.mjs` C 组（NodeKind 五值不变，`CHAT_STYLE_TAG_*` 移出前端镜像
  词表 ⇒ A 组该项撤销）、D 组（新字段 ts↔rs 名对齐）、G 组（title/icon/actions 各有非 meta 前端消费点）
- **兼容**：`reasoning` 历史数据经 `legacy_shape_to_style_tag` 折成 `Notice`，读边界处理
- **风险**：前后端必须**同一原子批**翻转（`reasoning`→`Notice` 单独发会让前端把思考折进
  `notice.default=compression` 卡片）；100+ 单测红一次，同批改完
- **UI 面不在门禁覆盖内**：容器塌缩与 Notice 合并是渲染层改动，须在 Tauri 实机回归
