## 决策

**背景**：P6-③ 把 `WalStore` 一族请出机制层之后，能力在编译上已经拿不到 WAL；但「拿不到」
只解决了**禁止**，没回答**替代**——每个要在会话里读事实、落事实、发起一轮、对外作用的模块，
仍然各自决定「从哪拿、往哪写」。会话插件的十二个文件是现成标本：同一份会话事实源曾被它们
用 `session_dir → join(V2_WAL_FILE) → open*` 各自重放、各自取令牌。本记录把
[DE-014 §2.2](../004-plan/014-单环一表收敛.md "DE-014-单环一表") 已立的形状落成**可施工的
公用协议**：五类需要各给一种取得方式、一个持有者、一条编译或 grep 判据，并排定 P6-④ 的刀序。

### §1 协议：能力模块可以取得什么

`Capability::execute(args, env, ctx)` 的形态不变。一次能力调用里，上下文**只有五类**，
每一类只有一个来源，**不存在第二条**：

| 需要 | 唯一取得方式 | 能力的形态 | 持有者 |
|---|---|---|---|
| A 读本会话事实 | 引擎在调用点递**投影值 / 快照值** | `Vec<Event>`、具名投影产出、或已排版好的字符串 | 引擎 |
| B 落事实 | 能力交**待落事实值**；由引擎的单一落格口 `append` | 返参 / out-param 里的 `Event` 值 | 引擎 |
| C 让一轮发生 | 往目标会话的**地址**写一条触发事实 | `plugin/route` 或 VDFS `write` + 同步回包 | 能力持主动口引用（经 ctx） |
| D 对外作用 | 世界端口 `ExecEnv`（`ExecEventSink` + `ExecAbortSignal`） | 执行期双原语 | 能力（它本就是端口的实现方） |
| E 声明性上下文 | `keys` 域的**类型化 ctx 键** | 装配告知或事实的投影值 | 装配方 |

**能力面三条硬不变量**（由编译边界 + grep 判据共同守）：

1. **0 个 store 句柄**——能力模块的导入里不出现 `Store` 的具体实现，也不出现
   `Arc<dyn Store>`。B 类需要的值由能力交出、引擎落，能力不持有写口。
2. **0 条路径**——`session_dir` / `V2_WAL_FILE` / 任何「拼出事实源文件」的知识都不进能力面；
   能力若需要「哪个会话」这件事，取 `SESSION_ID` 这一条声明性键（E），不派生路径。
3. **0 个具体 store 类型**——`WalStore` 一族自 P6-③ 已是
   `pub(in crate::plugins::session)`，能力侧**写不出来**；本协议不新增任何端口 trait，
   以免 CS-001 三格变宽（[D-055](055.md "D-055")）。

### §2 引擎侧：唯一端口，构造一次

协议的另一半在引擎（会话插件）内部。事实轨的**唯一入口**是会话存储层：

- **唯一知情者**：`plugins/session/store` 是仓内唯一知道 WAL 布局（目录、锁文件、归档段、
  文件名）的模块；`EventWalStore::open` / `open_readonly` 只允许在这里出现。
- **构造一次**：`SessionStore` 按会话缓存**一个** `Arc<EventWalStore>`（`facts(id)`）。
  同一进程内所有引擎写方共享同一句柄 ⇒ 第二个「各自 replay、各自取令牌」的实例不存在，
  `head` 不会因并发开档而重复。跨进程仍有写者令牌，T-055 的寄存机器保留为**跨进程兜底**。
- **读方拿值**：`snapshot(id)` 返回 `Vec<Event>`（完整史，含归档前缀）；
  部署级读（召回、统计聚合、淘汰覆盖层）由存储层按读策略产出 `FleetSnapshot` **值**，
  读方不接触路径，也不各自遍历目录。
- **写方拿口**：`facts(id)` 只发给引擎自己的写点（轮执行、收件箱空闲写、自主触发、轮外压缩）。
  能力永远拿不到它——这是 B 与「能力自己写」的分界线。

`Store` 端口与 `range(from)` 语义维持 DE-014 §2.2 推论 1 的裁定：方法数不变，
`range` 含被取代前缀；窗口由消费方按 `Seq`/`Budget` 切。

### §3 为什么要分「能力面」与「引擎面」

能力（工具）与引擎（会话插件）不是同一类主体：能力**产生**要落的事实，引擎**决定**这些事实
按什么顺序、与哪些其它事实一起入格。若把写口交给能力，顺序与幂等就变成每个能力的自由裁量，
「一个 turn = 用户格 opened + 至多一条收束 closed」这类不变量立刻失去唯一守护者。反过来，
引擎内部的投影维护（收件箱、自主触发）本来就是「同一轮生命周期的托管方」，它们共享引擎的
唯一写口，不构成第二类主体。

因此本协议不新增 trait、不新增 ctx 键、不新增机制实例：它只是把**已有的**
`Capability` / `ExecEnv` / `keys` / `Registry` 与 `Store` / `Event` 词汇按「谁持有」重新排一次，
并把「谁能碰磁盘」收进编译边界。

### §4 P6-④ 刀序与判据

- **④a 写侧**：`SessionStore::facts(id)` / `snapshot(id)` / 部署级扫描落位；
  `turn_exec`、`message_events`、`inbox`、`autonomous`、轮外压缩改经唯一句柄；
  寄存路径只留跨进程分支。
- **④b 读侧**：`skill_events::route` / `task_events::prompt_section` /
  `worker_progress` / `memory_events::recall_view` / `stats::read` /
  `breaker` / `elimination` 改吃值（快照或扫描结果），不再拼路径。
- **④c 收口**：判据升为门禁断言（`facts-boundary-audit`，FB-001/FB-002 挂在 docs 阶段，
  回归测试双向钉住）。

判据（驱动器侧能力文件住 `plugins/loop/`，`rebuild` 住 `core/projection`；门禁清单随文件
owner 走）：

1. **grep 台账**（门禁 `facts-boundary-audit`）：能力文件点名单内 `session_dir` /
   `V2_WAL_FILE` / `open_readonly` = 0；**生产代码**里 `EventWalStore::open` /
   `open_readonly` 的调用点只许在 `plugins/session/store/`。测试夹具（`*.test.rs`）与存储层
   自己的测试可以直接开档——它们在造被测对象，不是在取得事实。
2. **构造一次**：单测证明同一 `SessionStore` 对同一会话两次 `facts` 返回同一实例；
   两个写者共享该实例 ⇒ 均成功 append，无 `head` 重复。
3. **行为不变**：既有测试基线不降；`Store` 方法数不变、CS-001 三格 18/56/18 不动、
   C-001/C-003 只降。
4. **跨进程兜底仍在**：两个各自 `open` 的实例（模拟两进程）中，非写者仍得到
   `NotTheWriter`，寄存补落路径保留。

**否决的替代方案**：

- **把 `Arc<dyn Store>` 作为能力 ctx 的一部分发下去**：被否。它把「顺序与幂等」交给每个能力，
  B 类退化成「能力自己写」，§3 的唯一守护者消失；且 `dyn Store` 进 ctx 会让能力侧的编译边界
  重新变宽，P6-③ 的收窄白做。
- **每个模块保留 `session_dir`，只把 `open` 换成共享函数**：被否。路径本身就是布局知识，
  共享函数只是把重复从「开档」挪到「拼路径」，判据 ② 永远为假。
- **为读侧新增 `FactsReader` trait 进 core**：被否。DE-014 §2.2 的读法归一是「`Store` 三法 +
  值」，新增 trait 会让 CS-001 变宽，且与「端口只在引擎手里」冲突——读方要的是值，不是口。
- **把 inbox / autonomous 的触发写入一并改成地址面**：**不并入本条，也不被否决**。
  它属 DE-014 §2.2 迁移表的 C 行，由 6b-③「两入口改地址面」承接；本条只做 A/B 行，
  先把「事实源只有一个写口」立住，C 行才有可写的对象。
