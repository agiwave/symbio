## 决策

**背景**：[D-082](082.md "D-082") 裁决一/二/四把 6b-③ 的形状定成「驱动器独立成
`plugins/loop`、触发走地址面、服务走 core 机制词汇」，[D-083](083.md "D-083") §4 把
跨墙通货闭族成四类、§5.4 把判据改为「驱动器文件 import 根 ⊆ §4 闭族」，
P5（运行态归源）与 P6（体系接口唯一化）已把运行态与存储实现请出机制层。剩下的是
**切片当刻的契约**：一次轮次在墙的两侧各归谁、过墙的是什么、从哪条路走、谁发帧、
谁触发 Stop。本记录逐条回答，不按触点临时发明端口（D-083 的教训：
按实现触点凑出的端口契约，面一旦立起来就会把临时形状永久化）。

一句话：**驱动器只执行一轮，数据面走 core 闭族词汇，控制面走地址面，生命周期留在会话。**

### §1 过墙的只有闭族四类，新增 trait 0

| 需要 | 通货 | 方向 | 落点 |
|---|---|---|---|
| 本轮输入与运行态对象 | [`TurnDispatch`](#2-turndispatch一次轮次的进程内交付包)（进程内 typed ctx 值，`WIRE=false`） | session → loop | core 模块 `turn::dispatch` |
| 本会话事实 | `Arc<dyn Store<Event = Event>>`（P6 已构造好的端口对象） | session → loop | `TurnDispatch.facts` |
| 世界端口 | `ExecEventSink` / `Arc<dyn ExecTranscriptWriter>` / `ExecAbortSignal` / `Arc<dyn ModelProvider>` | session → loop | `TurnDispatch` 字段 |
| 会话读写 | VDFS 地址 `session/<sid>/_run/<op>`（loop→session）与 `loop/<sid>`（session→loop） | 双向 | 已有地址面机制，载荷为纯值记录 / `ChatNode` |

闭族之外没有第五类，**不新增 trait**（CS-001 三格 18/56/18 不动）、不新增机制键
（DE-001 §8 的事件机制键 0）。typed ctx 键不是「机制键」：它是 P6 已确立的
声明性交付面（`SESSION_HANDLE` 的同族），`WIRE=false` 使它从类型上就不可能跨进程，
因此不会被误当成线上协议。

### §2 `TurnDispatch`：一次轮次的进程内交付包

session 在派发前把「执行这一轮需要的全部对象」装进一个值，挂到 **fork 后的 chat_ctx**
上的 `TURN_DISPATCH` 键；loop 的 provider 从 `VdfsContext` 取回宿主 ctx 后读取它。

| 字段 | 类型 | 为什么在这里 |
|---|---|---|
| `spec` | `TurnSpec` | 纯值输入（§3） |
| `facts` | `Option<Arc<dyn Store<Event = Event>>>` | 本会话事实轨端口；临时会话为 `None`（即原 `session.facts()`） |
| `sink` | `ExecEventSink` | 执行期帧出口（原 `run_chat_loop` 的入参） |
| `writer` | `Arc<dyn ExecTranscriptWriter>` | 压缩增量改道用的转写写口（原 `CompressionEmitter::transcript_writer`） |
| `abort` | `ExecAbortSignal` | 中止信号（原 `run_chat_loop` 的入参） |
| `provider` | `Arc<dyn ModelProvider>` | 本轮唯一生效模型服务（既有 core trait） |
| `parent` | `Option<Arc<dyn Plugin>>` | 作用域容器：loop 经它取 VDFS 视图回到 session（心跳/agent 同款，不持兄弟实例） |
| `context_limit` | `u32` | 本轮生效上下文上限（session 在派发前已解析） |

`TURN_DISPATCH` 的键类型与 `Value = Arc<TurnDispatch>` 住 core（两侧都要命名它），
`WIRE=false`、`parse → None`、`format → String::new()`——与 `SESSION_HANDLE`
的进程内键同一条纪律。**不把 `TurnDispatch` 塞进 `payload`**：payload 是本轮
`session_chat::Request`（线上契约），且扩展桶的 `payload()` 只支持可序列化类型，
trait object 与 sink 没有 JSON 形态。

`facts` 在 `run_chat_loop_task` 派发前解析（此时首条用户消息已落库，WAL 必然存在）：
- `Err` ⇒ 走 `fail_before_loop`（用户可见结局与原 `execute_turn` 首步失败一致）；
- `Ok(None)` ⇒ 临时会话，driver 内沿用「无事实源 ⇒ 不落派生事实」分支。

### §3 `TurnSpec` / `TurnSettings` / `TurnReport`：纯值面

`TurnSpec` 是 loop 能知道的**全部会话输入**，不含任何存储实现：

| 字段 | 类型 | 说明 |
|---|---|---|
| `session_id` | `String` | 地址与幂等键的唯一身份 |
| `tool_archive_dir` | `PathBuf` | **预计算**：`paths::session_subdir(..., TOOL_ARCHIVES_SUBDIR)` |
| `transcript_archive_dir` | `PathBuf` | **预计算**：`paths::session_subdir(..., TRANSCRIPTS_SUBDIR)` |
| `principal` | `String` | 本会话主体（`request_principal` 的取值点，派发前定） |
| `scope` | `Scope` | 子会话 ⇒ `Child(父主体)`、顶层 ⇒ `Root`；session 从 metadata 预计算 |
| `persistent` | `bool` | 临时会话判定（原 `store_handle().is_persistent()`） |
| `context_window` | `u64` | 原 `session.context_window()` |
| `settings` | `TurnSettings` | 驱动器读到的配置标量（见下） |

`TurnSettings` 只收**驱动器真正读的 14 个标量**：`auto_compress`、
`classify_enabled`、`compose_enabled`、`opening_enabled`、`progress_enabled`、
`progress_interval_ms`、`progress_min_rounds`、`progress_max_per_turn`、
`presentation_tree`、`skill_compile_enabled`、`skill_fast_path`、`worker_force_prefix`、
`worker_keywords`、`worker_min_chars`（`worker_*` 三字段同属委派段判据）。
`context_messages` **不在这里**：窗口裁剪发生在 session 侧 `get_context_messages`，
驱动器拿到的是已裁好的消息——把窗口配置过墙等于让两侧各裁一次。
存储策略字段（`max_messages` / `prune_tool_history` / `supplements_*` / `memory_*`）
**不过墙**——它们只服务会话侧的落库与抽干，属于 session 的领域判定。

**磁盘布局词汇不跨墙**：`paths` 的目录命名与 `V2_WAL_FILE` 从 loop 触点消失；
loop 只收已解析的 `PathBuf`（D-082 订正裁决第 5 条的复核结论）。

`TurnReport` 是 loop 交回 session 的唯一结局值（序列化进动作响应的 `data`）：

```rust
pub struct TurnReport {
    pub status: TurnStatus,          // Completed | Aborted | Failed
    pub error: Option<String>,       // Failed 的原因
    pub partial: Vec<ChatNode>,      // Aborted 时已产出的半截消息（由 loop 私有的退出类型携带，D-095）
    pub last_message: Option<String>,// Stop 钩子的 last_message（原 fire_stop_hook 的取值）
}
```

session 据此**原样重建**收尾分支：`Completed` ⇒ 正常收尾；`Aborted` ⇒
`persist_failure(..., NodeStatus::Aborted, partial)` + `SessionStateChange::aborted()`；
`Failed` ⇒ `teardown_failed_turn`。loop 不接触 `SessionStateChange` / `OUTCOME_*`，
它们留守 session（D-082 订正裁决第 3 条）。

### §4 loop→session 的内部动作面：`session/<sid>/_run/<op>`

session 的 VDFS provider 已按 `<sid>/<集合段>/<项>` 分域；新增一个**内部动作段**
`_run`，它不是资源、不出现在清单里，只接受 `Action`。

**授权判据（必须全部成立）**：

1. `ctx.get(TURN_DISPATCH)` 为 `Some(dispatch)`——进程内 typed 值，线上不可伪造；
2. `dispatch.spec.session_id == <sid>`——令牌只对**本轮会话**有效；
3. 动作名在下面的闭集内。

不满足 ⇒ `VdfsError::Forbidden`。理由：地址面对前端、LLM 工具、心跳全部可达；
内部动作若不加令牌，就等于给「改任意会话的写路径」开了第二个公开面。typed 键是
P6 之后已有的声明性交付面，不新增机制。

> **第 3 条的闭集已改组织方式**（[D-094](094.md "D-094")）：它不再是 core 里
> 手写的 `run_ops::ALL`，而是 session 的行表 `RUN_OPS` 自身——「在表内」与「有臂」
> 由构造保证相等。判据一字未改（不在表内 ⇒ `Forbidden`），下面的动作表内容不变。

**动作表**（`op` → 行为；返回为 `VdfsActionResult.data`）：

| op | 行为 | 返回 |
|---|---|---|
| `messages` | `session.get_messages()`（含 v1 回落） | `Vec<ChatNode>` |
| `context-messages` | `session.get_context_messages(None)`（滤 Failed / 剔孤儿 / 归一 / 轮窗） | `Vec<ChatNode>` |
| `add-by-runner` / `add-here` | `append_and_publish(..., Carrier::Runner / Carrier::Here, Transcript)`：落库、补身份、**把权威副本经转写发布** | 权威 `Vec<ChatNode>` |
| `edit-nodes` | `apply(Edited)` 后按调用方指定的帧形发布（`frame = state / message`） | 权威 `Vec<ChatNode>` |
| `remove-nodes` | `apply(Removed)` 后逐条发删除帧 | `()` |
| `replace-all` | `replace_all(nodes)` + `emit_transcript_rewritten(dropped, head)` | `()` |
| `drain-parked` | `message_events::drain_parked`（寄存的编辑/删除补落） | `()` |
| `consolidate` | 压缩入格 + `archive_before`（幂等按快照内容 id 比对） | `()` |
| `take-supplements` | `take_supplement_batch_sync` | `Option<DrainedSupplement>` |
| `worker-progress` | `worker_progress::for_session` | `Vec<WorkerProgress>` |
| `recall-snapshots` | `store.recall_snapshots(sid)` | `Vec<FleetSnapshot>` |
| `elimination-revoked` | 部署级覆盖层折叠，只回一个布尔（见下） | `bool` |
| `compression-begin` / `compression-finish` | 压缩节点的占位与定稿（含终态帧与 `persisted`） | `() / ChatNode` |

**为什么写动作自己发帧（不把权威副本交回 loop 发）**：
`session/docs/022-vdfs-session-messages.md` §3.4 的硬不变量是「每一条被落库的消息
都必须发一次变更（带存储分配的 `seq`）」，其实现是
`transcript::publish::append_and_publish`——**唯一的落库 + 回包实现**。缓存该实现的
两个半身分居两插件，就会重新长出「落库的忘了发、发帧的拿错号」那类静默缺陷。
动作在 session 侧调用同一个 `append_and_publish`（`PublishTarget::Transcript`），
把权威副本直接投进本会话转写；loop 拿回权威副本只为维护自己的内存镜像。
`append_and_publish` 的返回类型由 `()` 改为 `Result<Vec<ChatNode>, PluginError>`
（返回存储交回的权威副本），调用点按需取用。

**`edit-nodes` 的帧形为什么由调用方指定**：resume 的父节点更新只需要状态帧
（正文早已由 delta 上线），新子节点需要完整消息帧；压成一个形状会让其中一处
多发一次全文或让另一处前端停在旧状态。帧形是**调用意图**，随动作载荷给出。

**`elimination-revoked` 为什么只回布尔**：`EliminationInputs` 真正需要的只有
「该主体是否已被收回 `assign.work`」。把部署级全量事件（预算 16 文件 / 64MB）
JSON 化过墙再在 loop 里折一个布尔，是 P6「值注入」的反面——存储布局与遍历
留在 session，折叠判据（`GrantsOverlay` / `EliminationDecider`）仍在 core，
loop 只收结论值。

### §5 session→loop 的触发：`loop/<sid>` 的 `run_turn` 动作

- loop 插件注册自己的 VDFS provider（提供者即插件本身），地址空间里的挂载段 =
  `PLUGIN_ID_LOOP`（`"loop"`）。它只接受 `<sid>` 上的 `Action("run_turn")`，
  其余路径 `NotFound`。
- **整个动作体就是一轮执行**：loop 的 provider 取出 `TurnDispatch`，构造 loop 侧
  的 `LoopContext`，跑搬迁后的 `run_chat_loop`，把结局序列化成 `TurnReport` 放进
  `VdfsActionResult.data`。动作是 `async` 的，因此 session 侧「spawn + `select!`」
  的形状**一字不动**：`handle` 是这次 `dispatch` 的 future，watchdog 与
  `wait_state_superseded` 的判据不变。
- **派发点**：`orchestrator/consume.rs::run_chat_loop_task` 在完成 provider 解析、
  限流、`context_limit`、配置快照、sink/abort 构造之后，构造 `TurnDispatch`、
  `chat_ctx.fork()`、设置 `TURN_DISPATCH`，然后经**作用域容器**
  `parent.get_vfs_provider()` 派发 `loop/<sid>`。不用路由表缓存兄弟插件的 `Arc`
  ——停用时缓存不失效（D-082 已否决 `TurnStarter` 的正是这一点）。
- **loop 缺失 / 已停用** ⇒ 容器对 `loop` 段回 `NotFound` ⇒ session 走
  `fail_before_loop("对话驱动器未挂载…")`。这就是卸载判据的**运行期表达**：
  停用 loop ⇒ 不再开新一轮，而存储侧读写（收件箱继续入队）照常。
- **公开地址不动**：前端仍写 `session/<sid>`（恢复臂），收件箱消费者仍走
  `start_turn`；两者最终都汇入 `run_chat_loop_task` 的这一次内部派发
  （D-082 裁决二「公开面不动」的兑现形态）。

### §6 生命周期与归属

| 归属 | 内容 |
|---|---|
| **session 留守** | `orchestrator/*`（`start_turn`、`run_chat_loop_task`、`WorkingGuard`、watchdog/superseded、失败收尾）、`active/*`、`store/*`、`transcript/*`（含 `Transcript`、压缩发射器、补充抽干、落库回包）、`chat_session/*`、`message_events/*`、`types`、`config`、`paths`、`plugin/*`（公开 VDFS 面）、`commands`、`stats`、`worker_progress`（多步存储编排）、`memory*`、`runtime`、`workdir`、`options`/`capabilities` 收集、`rate_limit`、`convergence` |
| **loop 迁出** | `chat_loop/*`、`turn_exec`、`turn_runner`、`resume`、`context/*`（压缩产线）、`message_build`、`tokenizer`、`prompt`、`conversation_view`、`view`、`model_chat`（`Request` 上移 core）、`loop_registry`、`round_hook`、`tools/*`、`tool_dispatch`、`skill_events`、`derived_facts`、`task_events`、`memory_events` |

- **`Convergence` 归位 session 顶层**（D-082 裁决四）：它与 `chat_session` /
  `active` / `store` 同级，`orchestrator.rs` 的底座随两侧拆分。
- **`io.rs` 豁免废除**（D-082 裁决五）：`open_chat_session` 的缺句柄回退消失。
  会话句柄由 session 在派发前解析；临时会话以 `TurnSpec.persistent = false` +
  `facts = None` 表达，不再由 driver 构造 `PersistentChatSession::detached`。
- **`StopSignal` 留 session**：loop 在 `TurnReport.last_message` 里交回末条正文，
  session 的收尾统一触发 Stop。`UserPromptSubmit` 在 session 派发前触发
  （用户消息已在 `start_turn` 落库，语义不变）；`PreCompact` 与 `PreToolUse` /
  `PostToolUse` 随 driver 迁 loop。`fire_hook` 作为**共享路由助手**上移 core
  （`plugin/hook.rs`，纯 `Plugin::route` + 既有 `ROUTE_HOOK_FIRE`，不是新机制）。
- **`CompressionEmitter` / `SupplementDrain` 留 session**：它们持有活跃名册、
  转写与配置当前值，是 session 状态的一部分；driver 经 §4 的动作使用它们。
- **`rate_limit` 留 session**：它是派发**之前**的节奏闸门（位置即在
  `run_chat_loop_task`），不属于单轮执行。

### §8 装配与模块形状

- 新插件目录 `symbio/src/plugins/loop/`：`plugin.rs`（`build` / `get_vfs_provider` /

  仍是 `"loop"`（`PLUGIN_ID_LOOP`）。
- `ASSEMBLY_SUB_AGENT_PLUGINS` 增加 `"loop"`（`home::SYSTEM_PLUGINS` 是它的纯别名，
  只改一处字面量）。系统树与每棵子 Agent 子树同构各得一份。
- loop 本片**能力行 0、常驻任务 0**；它贡献 **1 条 Mount 行**（provider 即挂载点），

- 守卫用例（6b-④）：composite 真实 `mount_all` + 停用 `loop`，断言
  ① 写 loop 起始地址 `NotFound`、不再开新轮（收件箱继续入队）；
  ② 在飞的轮在注入的短时限内收敛（spawned 任务持端口 `Arc` 克隆，存活期长于插件）；
  ③ 存储侧 `list` / `stat` / 读转写 / 写收件箱全绿。

## 否决的替代方案

- **给 loop 一个 `SessionService` trait（或 `TurnHost`）**：D-083 §6 已逐法清点并废除
  ——面主体是宿主运行态的逐字段镜像，trait 数会回吐 §6 判据 2 的达成线。
- **把会话类型（`PersistentChatSession` / `SessionConfig` / `Session` / `SessionSummary`）
  直接过墙**：E-009 编译不成立；即便绕过，也把前端/落库契约钉成后端协议
  （D-082 订正裁决的原始判据）。
- **写动作只落库、由 loop 发帧**：会把 §3.4 的唯一实现拆成两半（见 §4）。
- **用 typed ctx 串联每个动作、不走 VDFS 地址**：ctx 键是单值且随请求共享，
  并发动作会互相覆盖；地址面是 D-083 已枚举的通货，还免费给出「停用 ⇒ NotFound」。
- **loop 动作立即返回、用频道回传结局**：频道不在闭族内，且会引入新的生命周期对象；
  「动作体 = 整轮 future」让 session 的 `select!` 与看门狗骨架原样保留。
- **把 `CompressionEmitter` 或 `SupplementDrain` 迁进 loop**：它们直接读写
  `ActiveSessionState` / `Transcript` / 配置当前值，迁过去等于把 session 状态撕成两半。
- **`deep-snapshots` 全量事件过墙**：见 §4 的布尔投影理由。
