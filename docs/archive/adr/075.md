## 决策

**背景**：[DE-014](../004-plan/014-单环一表收敛.md "DE-014-单环一表") §5 步骤 6 的判据是
「每个插件可独立卸载且系统仍完整」，[T-167](../009-task/167-会话插件切分.md "T-167-会话插件切分")
把它接成任务并要求先审再切。逐条核到 `file:line` 的读数里，有一条判据从未被检查过它
**能不能成立**：

- **注册表侧不是障碍**：`session` 的所有能力行只从一个地方 `put`——
  `SessionPlugin::traverse`（`plugins/session/plugin.rs` 579–632：option / tool / mount / prompt /
  `capability_announce_configurable` 全在这一处）；而那张表**每次收集都是新建的**
  （`capabilities.rs:70` `DefaultToolVisitor::new()` 后遍历容器子插件）。一个插件从容器里摘掉，
  下一轮收集自然不再有它的行。**卸载不需要「这行是谁给的」这一列**。
- **真正的障碍是两条常驻循环**：`heartbeat/mod.rs:149`（`run_heartbeat_loop`，`loop { ticker.tick() }`）
  与 `transcript/inbox.rs:171`（`spawn_inbox_consumer`，`loop { drain_inbox_once() }`），加上
  `workdir/fs_watcher.rs:60`——三处都在构造点 `spawn`（`plugin.rs` 367–375），**不留 `JoinHandle`、
  没有取消位**，而 `SessionPlugin` **没有实现 `Plugin::stop`**（默认体是 no-op，
  `symbio_core/plugin/mod.rs:409`）。把它们从容器里 `shift_remove` 之后，任务仍在跑、
  仍持着 `Arc<SessionPlugin>`——**「卸载」今天只是从名册里划掉一个名字**。
- **第三个障碍是手柄形状**：五处 `Arc`/`Weak<SessionPlugin>` 捕获——`orchestrator/sink.rs:35`
  （`TranscriptSink` 的生产实现反过来调 `plugin.emit_session_state`）、`chat_loop/state.rs:454`
  与 `:602`（`CompressionEmitter` 与 `SupplementDrain`；前者另有 `target()` 把宿主交给上下文面
  `context/pipeline.rs:630` 去落库）、`tools/heartbeat_tool.rs:31`（`Weak` 再 `upgrade`）、
  以及 `plugin/vdfs_provider.rs:523` 的 `me()`（provider 侧任何一次「开跑一轮」都要把整个插件的
  `Arc` 交给驱动器）。全仓**没有** `dyn Plugin → SessionPlugin` 的 downcast，所以这一类耦合
  只有这一种形态，可以逐条消掉。

**裁决一：步骤 6 的施工顺序反过来——先让「卸载」这件事真的发生，再谈目录归谁。**
三条前置，按影响面从小到大，各自成批、各自有机器判据：

- **P1 常驻任务可取消**：两条 loop 与 fs watcher 改为持有取消位（`stop` 里置位并 `abort`/等待退出），
  `SessionPlugin` 实现 `Plugin::stop`。判据：一条 e2e 或守卫用例钉「停用 session ⇒ 心跳不再触发新一轮、
  收件箱消费者退出」。这是判据本身，不是重构口味。
- **P2 `Arc<SessionPlugin>` → 窄手柄**：sink / emitter / drain 三处只拿它们实际用到的那件事
  （落一帧、发一条压缩事件、抽一份补充），不再拿整个插件；`me()` 那一处把「开跑一轮」升成一个
  显式端口。判据：`session/` 里 `Arc<SessionPlugin>` 的捕获点从 5 处降到 0（构造点除外）。
- **P3 跨片调用走表或端口**：`heartbeat` 需要的是「列出会话 + 排一条收件」，`inbox` 需要的是
  「启动一轮」——这些在切分后必须经能力行或路由臂拿到，而不是同结构体的方法调用。
  判据：被切的那片不再 `use super::` 宿主的私有项。
  **心跳片的实测面比这句列举更宽**：除了会话列表与入队，它还读宿主的运行时
  状态、直接开事实源落格、读配置一格、维护活动锚点，设置那一半另要 metadata 读写——**实际工作量
  在这些口上，不在搬目录上**。逐口读数（八条）与归属裁决由
  [D-076](076.md "D-076") 承接，
  本条不再复述那份清单（改一处口径动两处的账，正是那条纪律要拦的）。

**裁决二：不给 `CapabilityRow` 加「贡献者」列。** 这是一次典型的「拿 core 的变宽去付实现方的账」：
表逐次重建已经提供了卸载语义（背景第一条），加了列反而要再防它与实际 `put` 方不一致。
`CapabilityRow` 仍是两格（`name` + `payload`，`symbio_core/capability/row.rs:130`），
core 三格不动（CS-001 只降不升）。

**裁决三：留守名单——六段里只有一段现在被列为可切，两段永远不切。**

|---|---|---|

驱动器（17,800）单独立片是**最后一步**：P1–P3 落地、且它对存储的触点核到只剩 sink 与句柄之后才动。
卸载它之后 session 只剩存储与生命周期——那才是「系统仍完整」的最强形态。
（触点的准确表述是 P4「四个不」，见 [D-081](081.md "D-081")——「只剩 sink 与句柄」
按字面不可执行，句柄本身就是存储域对象；十处触点的逐条归属与判据形式归那条裁。）

**裁决三：上下文与请求视图不切。**

这一片不是「六段里最干净」：干净的那条理由（零 `SessionPlugin` 引用）只对宿主外壳成立，
对驱动器不成立——所以这不是「再做准备就能切」的押后，而是**判据选错了对象**，
它没有待办可留。两个理由：

- **两个方向互依 ⇒ 先切谁都是环**。切片被 15 个文件 30 处消费，其中 `turn_exec` 5 ·
  `turn_runner` 4 · `chat_loop*` 5+ · `orchestrator*` 2 · `tools/*` 4（合计 16 处在驱动器侧）；
  切片自己又反向依赖驱动器（上表已列）。而驱动器是最后一片。
- **两条「边界已解除」一条都没碰这层耦合**：`CompressionEmitter` 换名册（P2/3a）
  只换了它内部持有的句柄，没有动「谁掌握压缩这一次调用」；三层退役（D-078）删的是内容，
  没有动参数面。
- **顺带一条判据空转**：五族不贡献任何能力行、无常驻任务 ⇒ 出口 ② 的两半判据
  （卸载 ⇒ 能力行消失、停用 ⇒ 常驻任务退出）对这一片**没有可判对象**。

两个答案都不需要新事实，只需要承认判据选错了对象。结论即本条的最终形态，施工批次表见
[T-167](../009-task/167-会话插件切分.md "T-167-会话插件切分")：

**① 压缩核归驱动器同片，批次 5 撤销。** `context/pipeline.rs` + `context.rs`（1,327 行）
不再单列一片，随批次 6（驱动器）走。理由：九个函数的参数面就是 `&ChatOrchestrator` /
`&mut SessionContext`，它是驱动器的压缩半身——「先切它再切驱动器」等于把一个环切两刀；
而「先给 pipeline 换窄手柄再切」是把一次动作拆成两次，还得先为换手柄本身立一条裁决。
**把环上的一片提前搬到环外，不是减小环，是给它换一个更难看的位置。**

**② 出口 ② 的机器判据按「有没有能力行 / 常驻任务」分两种形式**（判据在此定义，
是否满足留给批次 6 真切的那一刻回答）：

| 切片的形状 | 「独立」的判据 |
|---|---|
| 贡献能力行或常驻任务（如心跳） | 沿用原判据：卸载 ⇒ 该片能力行在下一轮收集里消失、其余仍在；停用 ⇒ 常驻任务真的退出 |
| 两者皆无（如上下文剩余约 2,826 行） | **依赖方向单向 + 可独立测试**：该片不 `use super::` 其余切片，其余切片只经端口/表层碰它，且它能脱离驱动器单跑测试 |

**这不是把判据放水。** 「卸载 ⇔ 能力行」这条判据的全部作用力来自**注册表里的行**——
一片不注册任何能力、也没有常驻任务的代码，本来就不在那条判据的射程里，照搬它只是一个
永远为真的空判据（上面第三条已核）。换成依赖方向后，它仍然是一台机器：方向可 grep、
可独立测试可 `cargo test` 单跑。

**裁决四：剩下的跨片引用分两类，「调用」现在就归位，「词汇」随切片那一刻定。**
批次 4a 的实测口径（`session/` 里被切的两片 → 宿主外壳的**代码**引用，注释里的链接不算）：

- **owner 放错的调用**：落库回包出口 `append_and_publish` + `PublishTarget` 住转写域
  `transcript/publish.rs`——它的真实依赖是**会话引擎**（`PersistentChatSession::apply`）与
  **两条发布通道**（执行期 sink / 活跃名册），`plugin.rs` 那一格从未参与（四处调用点
  `use super::transcript::`）。
- **共享词汇，不是调用**：`types::Session` 一族（存储的记录类型）、`config::SessionConfig` /
  `PresentationTree`（配置面）、`paths::*`（会话寻址的双向映射），以及会话节点视图那一组
  （`plugin::OUTCOME_*` 三个结局常量 + `session_node` 渲染函数）。前三类**本来就归留守层所有**
  （存储与生命周期被四方反向依赖，是裁决三表里的事实），把它们提前换个目录不等于卸载能力；
  节点视图那一组是**provider 的呈现被驱动器用了一次**，改它必然动 `vdfs/watch` 的载荷形状，
  所以它的归属是批次 6（驱动器切片）的判据内容，不在归位批里顺手改。
- **为什么不一次搬清**：判据在切片真正独立的那一刻才咬人——那时宿主的 `pub(crate)` 项对它不再可见，
  要给的形态是**注入值而不是注入锁**（`TurnLauncher` / `Convergence` 已经是这个形状：按字段交出
  那几格，而不是把 `Arc<RwLock<整个配置>>` 当成契约）。提前搬是把一次改动拆成两次，
  而搬错层的代价由本插件外的所有消费方付（`paths.rs` 的引用方就有 20 个文件）。

## 否决的替代方案

- **先搬目录，再补卸载能力**：被否。搬目录把「一个 `impl Plugin`」变成「五个」，但五处 `Arc` 捕获
  跟着变成**跨 crate 的循环引用**，P2 的成本上升而非下降；而且搬完之后门禁全绿也证明不了判据成立——
  DE-014 对这一步的原判据（独立卸载）恰恰是没有测试的那一条。
- **给 `CapabilityRow` 加贡献者列，卸载时按列逐行清除**：被否，见裁决二。表逐次重建已经提供了
  这个语义，加列是把一次性成本换成永久的一致性负担。
- **把 `memory` / `compact` 照 DE-014 §5 的字面清单切成插件**：被否（memory）与推迟（compact），
  理由见裁决三表。这不是把方案原清单当成别人的设计——DE-014 §0 立的尺是「形状是裁决（走 ADR），
  路径是数据」，本条就是按这把尺改路径，改动同时回写在该任务的出口里。

## 后果

- **步骤 6 从「搬目录」变成「补一条一直缺的能力」**：`Plugin::stop` 这条钩子在 P1 之前全仓只有
  `composite` 一个实现（`plugins/composite/composite.rs:227`），其余插件的常驻资源同批接受同一判据
  检查——可照的样板是 `gateway` 的 `stop_server()`（`plugins/gateway/plugin.rs:176`：持有句柄、
  `take()` 出来再停，配置热更时先停后启），只是它今天挂在配置变更路径上、没接到 `Plugin::stop`。
  **心跳与收件箱这两条不修，任何插件都谈不上可卸载**。
- **判据机械化**：一条守卫钉「卸载该片 ⇒ 该片的能力行在下一轮收集里消失、其余仍在，且宿主仍完整」。
  现有覆盖逐条核对过：`t17-plugin-assembly.mjs` ④⑤ **确实**钉着「停用 local ⇒ 它提供的工具从 LLM
  清单消失」（按首轮/次轮差集判，不硬编码工具名），但它是**改 `PLUGIN.yml` 后重启进程**跑的——
  插件树在装配期定型，所以它验的是装配，不是运行期那条 `set_enabled` / `uninstall` 路径；
  `composite/registry.test.rs` 的两条只到「实例表摘掉 + 目录删掉」，没有接到下一轮收集。
  **缺的是这两半的合成**：运行期摘除 ⇒ 行消失，加上停用 ⇒ 常驻任务真的退出（后半已由 P1 的
  `stop_terminates_resident_loops` 在 session 上钉住，见下）。守卫用例因此落在心跳片那一批，
  形状见 [D-076](076.md "D-076") 的后果段，不在这里重复立。
- **core 不动**：三格 18/56/18 不变、机制键新增 0（v2 守恒律判据未放宽）；P1–P3 全部落在插件层。
- **T-167 的出口条件随之改**：原文三条（ADR 定边界 / 独立卸载判据 / 黑盒纪律 + 全绿）不变，
  但批次顺序按本 ADR 重排为 **P1 → 心跳片（练守卫）→ P2 → P3 → 上下文片 → 驱动器**
  （上下文片的排序理由已随 P2 与 [D-078](078.md) 清零，见裁决三）。
- **`impl: partial` 的档位说明**（残余逐条指得出归属）：**P1 已落地**——`SessionPlugin::stop`
  持停机位 + 唤醒 + 句柄册，两条 loop 在可取消点自己收尾、监听一次性交还，判据用例是
  `plugins/session/plugin.test.rs` 的 `stop_terminates_resident_loops`（停用后两条句柄都
  `is_finished()`）。**心跳片已切出**（[D-077](077.md "D-077") 定落点为一层插件目录，
  守卫用例见 [T-167](../009-task/167-会话插件切分.md "T-167-会话插件切分") 批次 2b）。
  **P2 已落地（五处清零）**：emitter 拿的是活跃会话名册
  （`ActiveSessionManager`，发布三个函数随它走），drain 拿的是取批那三样（`config` /
  `change_subs` / 会话状态，取批实现因此从 `impl SessionPlugin` 落成 `transcript/inbox.rs`
  的自由函数），`TranscriptSink` 与 `WorkingGuard` 拿的都是**收敛手柄** `Convergence`
  （存储格子 + 存储目录 + `config` + 名册；`emit_session_state` / `broadcast_error_with_idle` /
  `open_chat_session` 与失败收口的 `persist_failure` / `converge_inflight`，其 owner 全随手柄
  从插件搬走，存储的 `OnceCell` 也随之从插件字段搬到手柄上），`me()` 那一处升成了显式端口
  `orchestrator::TurnLauncher`（名册 + `config` + `change_subs` + 本插件目录 + 父插件弱引用，
  一轮执行的方法整批从 `impl SessionPlugin` 搬过去）——**插件上的自身弱引用与 `me()` 一起删了**，
  因为 `start_turn` 只要 `&self` 就够。剩下的 `Arc<Self>` 只在常驻任务的**构造点**
  （`start_resident_tasks` → `spawn_inbox_consumer`），那属 P1 的范围，判据「构造点除外」把它排除在外。
  上面「上下文与请求视图」那条排序理由的 P2 一半（`CompressionEmitter::target()` 要把宿主
  交出去）已随之解除；另一半也随 [D-078](078.md) 退役清零——三层淡化不再存在，这段只剩
  「三段注入 + 压缩流水线」，边界不再随任何未决裁决漂移；
  **P3 的心跳那一半随 2b 落地**（读写只走地址面）；其余跨片调用按**裁决四**分流——
  owner 放错的落库回包出口已归位转写域（`transcript/publish.rs`，批次 4a），共享词汇四类的

## 补注（T-185）：插件停用语义

T-185 开工时留了一个三选一：**停用中途的在途请求怎么办**（等待完成 / 立即中止 /
标记不可恢复）。裁决取「**按边界收口，不打断一次已进入分派的轮**」：

| 时机 | 处置 | 理由 |
|---|---|---|
| 还没被接下的连接 | 不再接受（accept 循环退出） | 停用的第一义就是「不再来新的」 |
| 已建立、还没有请求内容的连接 | 关闭（HTTP 回 503，WS 直接关） | 此时没有任何业务事实在飞，关它是纯清理 |
| 已经进入 `route` 的一次请求 / 一帧 | **让它跑完** | 网关只是转发层，一次工具轮的事实由会话侧收束；在转发中途掐断会把「停用一个通道」变成「一次未收束的轮」，那正是 I3 要拦的形态 |
| 已建立的流式通道 | 在下一帧边界关闭 | 帧边界是这条链路上唯一有「一次交换已经结束」语义的位置 |

「立即中止」被否，因为它把停用的可靠性成本转嫁给事实源；「标记不可恢复」被否，
因为它要求网关理解会话语义——那是转发层不该有的知识。收口逻辑因此在
`gateway/server.rs::stop` 一处实现，路由臂与 `Plugin::stop` 都只调它，不写第二份。
telegram 复用既有的 `stop_listener` 取消令牌，hook 清空注册表；web 没有常驻任务或注册态
（构造函数里的 `reqwest::Client` 随实例释放），因此继承默认 no-op 就是它的正确形态。
