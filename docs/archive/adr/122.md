# D-122：入账不是调用点的责任——classify 与 compress 的模型往返搬进环里发生

## 背景

[T-247-插件内部模型往返进环](../009-task/247-插件内部模型往返进环.md) 登记的缺口：
`obligation-ring-accept` 的 J8（真实模型 HTTP 调用数 == `sent(port=model)` 数 + 豁免）
在每一轮都差一次调用。差额来自**插件内部**的模型往返：`classify` 的快速档判决、
自动压缩的摘要。编排层手里只有「路由一次 `classify/decide`」这一个动作，
调用发生与否、发生几次，都在插件里。

三个候选（登记在 T-247 的 `exit`）共同的前提是：**入账动作发生在调用点附近**。
本对话里三次 CLI 实证把这条前提否掉了（T-243 复验会话 `verify-seal-1`）：
`classify` 各打了一次模型，应答不可解析 ⇒ `Escalate{unclassified}` ⇒ `source=fallback`，
事实层**连观测都没有**——`turn.stage{decide}` 的 `source` 记的是**判决的来源**，
不是「有没有打过模型」。候选 ② 「先问这次会不会打模型」在这个形状下连问都问不出来：
调用前插件自己不知道规则表命中，调用后事实层只留下来源。

## 决策

1. **协议格的写方不增加。** `request` / `sent` / `response` / `failed` / `retry` 只由引擎在
   它自己派发的那一次往返里写（[DE-015-义务环](../004-plan/016-义务环.md) §4 五事实、
   [[D-118|D-118]] 决策 6 写权按行切）。**任何插件都不经由 `ctx` 拿事实源句柄
   自己 announce 一组三格**——候选 ① 否。
   理由是管辖错位，不是洁癖：账上的 `sent` 一旦被引擎之外的东西写过，
   `lease`（看护派出未应答的往返）与 `retry`（按尝试号重放）就开始管**引擎无法重放**的调用，
   「崩溃后重放到上一次模型请求」这句话对这几笔成为假话。
2. **要入账就让它进环里发生：调用搬进行表，不搬记账。** `policy.classify`（prio 10，
   现 `by: None`）与 `policy.compress`（prio 30，现 `by: None`）各接一个执行体
   （`decide` / `compress`，名单见 [[D-118|D-118]] 决策 3），
   它们的模型往返走**引擎的 `model` 端口派发路径**——与 `dispatch-model` 同一条路、
   同一组三格、同一个 `Key::trace()`。插件侧不再保留直接打模型的入口。
   这样入账是**副产品**而不是责任：谁派发，谁写格，J8 的等式按构造成立。
3. **候选 ③ 的两半分开处置。** 「消灭插件内部路径」这一半**取**——第 2 条就是它的实现形状。
   「把模型分类并入工具循环首轮」这一半**否**：它改的是产品行为（路由判决由谁来出），
   而 DE-015 的行表里**已经为 classify 留了行**（`policy.classify` 的 `owes` / `until`
   都已定义），把能力并进首轮等于让那行永远空转，也否掉了「判决可能有、也可能没有模型
   往返」这个真实区别（规则表命中 ⇒ 零往返，这条在第 4 条里仍要可判定）。
4. **零往返的轮必须是「行不成立」，不是「行成立但没写格」。
   ** 规则表命中时 `policy.classify` 的 `until`（`turn_stages{decide}`）照样被落
   （判决这一步确实跑了），但**没有** `model` 端口的一组三格——这条与「打了模型并入账」
   在事实面可分，正是 T-247 验收口径 2 要的两条用例的形状。
5. **退化应答照样有应答格。** 本地模型 `finish=Length`、正文 0 字符那一类（T-142 出口）
   仍是一次真实往返：`request` + `sent` + `response` 三格齐，`calls` 为空数组。
   「本轮未产出答话」是**收束侧**的判断（落在收束格的 `reason`），不是端口侧缺格的理由。
   这条写明是为了 J8 在失败轮也成立（T-247 处理过程 2026-10-23 补记的那次差额）。

## 后果

- `scripts/obligation-ring-accept.mjs` 的 `MODEL_PATHS` 里 `classify/decide` 那条豁免
  （`task: T-247` / `until: 2026-11-05`）**删除**，且这条路径的观测从「读 CLI 日志的
  `logMarker`」改回「读事实层的三格」——日志口径是事实层不可判时的临时手段，
  本裁决把它要解决的成因消掉了。豁免表不许长第二行。
- 压缩路径按同一形状处理：`policy.compress` 接回执行体后，摘要调用成为一次端口往返；
  零模型调用的压缩（没有可压内容）与 classify 同判——行不成立或 `until` 由阶段事实关掉。
- 两处插件侧调用点随本裁决**消失**，实现批要一起收掉它们的登记，否则门禁当场红：
  `crates/symbio-plugin-classify/src/decide.rs:161`（`ProviderLlmAdapter::generate_turn` 直调）
  与 `crates/symbio-plugin-loop/src/context/pipeline.rs:957`（压缩摘要，`internal-model-allow
  IM-001` 豁免）。后者是 `IM-003`（悬空豁免）的判据对象——调用点搬走而标记留着，
  `scripts/internal-model-audit.mjs` 判红，不是「以后再说」。
- 实施是 T-247 的后半批（改模块），本 ADR 只是它的准入条件；
  在那之前 `classify` / `compress` 两行的 `by: None` 不许为了「让 J8 绿」而改成
  任何让插件自己写格的形状。

## 实施订正（2026-10-23，实现批落地后回表）

实现批（`b0a1c772`）落地后逐条对账，四处与本 ADR 的字面有偏。**决策不变**，订正的是
「决策该长成什么样」的描述——不订正的话，下一个人会照着字面去找不存在的东西：

1. **决策 2 的接线形状没有照字面发生：两行仍是 `by: None`。**
   `policy.classify`(10) / `policy.compress`(30) 仍标「未接线」，判决与压缩仍由
   `chat_loop` / `assemble` 按 `owes` 点问自己执行。这是 [[D-118|D-118]]
   订正 1 的口径（**行表接执行体归 DE-015 的细端口期**，与「模型往返入账」不是同一批）。
   入账因此不经行表派发，而经**端口层的两个包装器**在调用点完成：
   `port/classify.rs::classify_round_trip` 与 `port.rs::Compress::summary`——它们持
   `Round` / `Compress` 的入账面，落三格、数 `model_calls`，插件只交一个「这次往返长
   什么样」的闭包（`run`）。**决策 2 要防的事没有发生**：写格的是引擎侧的端口层，不是
   插件自己（第 1 条「协议格的写方不增加」成立），`lease` / `retry` 管辖的仍是引擎能
   重放的往返。差别只在「派发者是谁」——不是行表执行体，是端口层函数。
2. **「两处插件侧调用点随本裁决消失」不成立，改成「调用点保留、搬进包装器内部」。**
   `classify/decide.rs` 的 `ProviderLlmAdapter::generate_turn` 仍在 `classify_round_trip`
   的 `run` 闭包里；`pipeline.rs::run_compression_llm` 仍在 `Compress::summary` 的闭包里。
   于是「后果」段那句「实现批要一起收掉它们的登记，否则门禁当场红」的**前提消失**：
   `pipeline.rs` 的 `internal-model-allow IM-001` 标记**合法保留**（它标的是「压缩摘要是
   内部请求、不是对话轮次」这个仍然成立的事实），`IM-004`（登记形状）由 `tools=&[]`
   满足——那确实是内部请求的形状，不是悬空豁免。判据 `internal-model-audit` 全绿即此意。
3. **`MODEL_PATHS` 的 classify 条目是「改写」不是「删除」，且新增了 compress 条目。**
   删除的是 `logMarker` 那套日志口径（观测改读事实层 `turn.stage{decide}.model_calls`），
   条目本身留着——它仍是「这条路径的观测 ⇔ 三格」的对账条目，只是观测换了地方。同时
   按决策 2 的后半给压缩路径新增 `compress/summary` 条目（读
   `turn.stage{compress}.model_calls`，一格代表 0..2 次往返：纠正重试是第二笔）。
   两条的 `exemption` 都是 `null` ⇒ **豁免表为空**，这正是本 ADR 要的终态。
4. **本裁决没有覆盖的一条路径：轮外压缩重试。** `pipeline.rs:896` 的 `None` 分支
   （用户主动重试触发的压缩，`compress: None` 因为没有「轮」可挂）仍直调模型、不入账。
   这不是实现漏掉——决策 2 说的是「要入账就让它进环里发生」，而轮外重试**没有环可进**
   （它不在任何 `turn` 里）。处置登记为 [T-254](../009-task/254-轮外压缩重试不入账.md "T-254-轮外压缩重试不入账")，
   本 ADR 的覆盖边界到此为止，不假装它已经解决。
