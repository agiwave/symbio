## 决策


**背景**：`VdfsNode` 里有一个不属于它自己的字段：`path`。
1. **地址是关系，不是属性**。它回答的是「这个节点在**某一份列表**里的位置」，而同一个节点可以在不同列表里以不同地址出现（实证：设置页的一项指向插件自己那份配置文档 `<目录名>/PLUGIN.yml`，落在**另一个挂载点**里；同一份文档在自己的目录里就叫 `PLUGIN.yml`）。
2. **于是每个 provider 都得知道自己在树里的位置**：容器、虚拟层、三个存储实现各自在拼 `<父地址>/<name>`——同一条推导写了五遍；拼不出来的地方就留空，再靠访问层补一次。**两处都在补**，口径各自维护，必然漂移。
3. **`VdfsWriteResponse.path` 更含混**：具名写时它回传的是调用方刚给的地址（把已知的东西还回去）；匿名写时它是 provider 生成的名字**混在地址里**——前端因此要取末段，还得额外挡「空路径 == 虚拟根」这个哨兵。

**决策**：
1. **`VdfsNode` 去掉 `path`**——它是纯自述（`name` 已是父内的路径段）。
2. **新增 `VdfsItem { path, #[serde(flatten)] node }`**：`vdfs/list` / `vdfs/tree` 的每一项都是它。**线格式与「带 `path` 的节点」逐字节相同**，故不改变任何既有消费者读到的 JSON。
3. **`path` 的回填只有一处**：provider 不填时，分发层按 `<父地址>/<name>` 推导；只有「地址不是那个形状」时由拥有者自己填（设置页条目是唯一实例）。
4. **`VdfsContent` 去掉 `path`**——内容总是「请求的那个节点」的内容，地址在请求里已经有了。
5. **`VdfsWriteResponse.path` → `name: Option<String>`**：**仅匿名写有**，值是 `VdfsNode::name` 口径的路径段、不是地址——地址由调用方拿它和自己请求的那个目录拼（它本来就知道请求的是哪个目录）。

**理由**：**一条推导只写一处**（provider 不需要知道自己在树里的位置）；**回执只给调用方不知道的那一个**（具名写回传地址是冗余；匿名写唯一的新信息是 provider 生成的名字）；**线格式不变** ⇒ 这次拆分对任何既有消费者（含 CLI 与 e2e）都是**透明的**。
